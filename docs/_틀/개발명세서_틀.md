# 틀 — 개발명세서 (개발팀)

> **쓰는 때**: 작업 루틴 [3] 개발팀이 코딩을 마친 뒤. **검증팀([4])이 이걸 보고 코드리뷰한다.**
> **누가**: 개발팀 (PM 개발팀장 지휘) — 실제 구현한 사람이 쓴다
> **저장 위치**: `docs/개발/{erp|랜딩|백오피스|설치배포|업데이트배포}/`
> **파일명**: `{YYYYMMDD}_개발명세서_{주제}.md`
>
> ## 이 문서의 목적
> **"작업지시서(PRD)대로 만들었는가"를 검증팀이 판정할 수 있게 하는 것.**
> 자랑하는 문서가 아니라 **검증받는 문서**다. 안 한 것·못 한 것도 적는다.
>
> ## 🚫 참조식 원칙 (전 문서 공통)
> 작업지시서(PRD) 내용을 옮겨 적지 않는다. **주소만** 가리킨다.
> 여기엔 **"무엇을 어떻게 만들었나"**만 쓴다.

# 개발명세서 {YYYY-MM-DD} — {주제}

| 항목 | 내용 |

| PM 결재 | ✅ {날짜} / ⬜ 미결재(=코딩 금지 상태) |
| 개발팀 지휘 | PM 브라운킴 |
| 구현 담당 | {매니저·서브에이전트} |
| 커밋 | `{해시}` |

## 1. 무엇을 만들었나 (PRD 대비)

| PRD 요구 | 구현 | 상태 |
|---|---|---|
| {요구 1} | `파일:줄` | ✅완료 / ⚠️부분 / ❌미구현 |

> ⚠️ **부분·미구현은 반드시 적는다.** 숨기면 [4] 검증에서 잡히고, 그게 거짓봉합이다.

## 2. 변경 파일 목록

| 파일 | 변경 | 왜 |
|---|---|---|
| `src/…` | 추가 {N}줄 / 수정 {N}줄 | |

- 기존 코드 **추가만** 했는가 (헌법 #1 덮어쓰기 금지) — ⬜확인
- 새 테이블·컬럼이 있으면 clean DDL 편입 (헌법 #36) — ⬜확인 / 해당없음

## 3. 헌법 준수 (작업지시서 §3 대비)

| 조항 | 어떻게 지켰나 | 근거 |
|---|---|---|
| #NN | | `파일:줄` |

## 4. 자체 확인 결과 (실측 — "확인함" 금지)

| 항목 | 명령 | 결과 |
|---|---|---|
| 빌드 (헌법 #19) | `dotnet build` | errors {N} / warnings {N} |
| DDL 스모크 | `scripts/ddl-smoke-test.sh` | / 해당없음 |
| 동작 확인 | {실제 친 명령} | {실제 출력} |

## 5. 안 한 것 / 못 한 것

| 항목 | 왜 | 후속 |
|---|---|---|

> 범위 밖이면 "PRD 범위 밖"이라 적고, 막혔으면 막힌 이유를 적는다. **비워두지 않는다.**

## 6. [3-V] 병렬검증 지적 사항 (안철수 상무)

| # | 지적 | 봉합 | 이슈 문서 |
|---|---|---|---|

> 병렬검증 중 나온 지적은 **여기 요약 + 별도 이슈 문서**에 남긴다.

## 7. 검증팀에 요청 (자기 판단 아님)

- 특히 봐줬으면 하는 곳: {여기가 위험하다고 스스로 생각하는 지점}
- 회귀 우려: {이 변경이 깨뜨렸을 수 있는 기존 기능}

## 작성 지침

1. **"완료했습니다"로 끝내지 마라.** 어떤 명령을 쳤고 무엇이 나왔는지 적는다.
2. **§5(안 한 것)를 비우지 마라.** 전부 다 했다는 명세서는 검증팀이 못 믿는다.
3. **§7에서 스스로 위험한 곳을 지목하라.** 만든 사람이 가장 잘 안다. 숨기면 SoD가 무의미해진다.
4. PRD 내용을 옮겨 적지 마라 — 주소만. 검증팀은 PRD 를 직접 연다.
