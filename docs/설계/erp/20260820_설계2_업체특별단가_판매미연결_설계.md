## 1. 코드리뷰 결과 — **화면·API·DB 는 정상. 끊긴 건 출구다.**

| 층 | 상태 |

⇒ **"작동하냐"** 만 보면 **작동한다.** 6/23(19차) 할인율 봉합도 살아 있다.

### 🔴 그런데 — `partner_special_prices` 를 읽는 곳이 **자기 화면뿐이다**

전수 조사(`grep -rn "partner_special_prices" src/`) 결과 **7개 참조 전부** `PartnerService.cs` 안의
**그 화면 CRUD** 다. **판매 어느 화면도 이 표를 부르지 않는다:**

| 화면 | 특별단가 조회 |
|---|---|
| 견적 `Quotes.razor` | ❌ 없음 |
| 수주 `Sales/SalesOrderPage.razor` | ❌ 없음 |
| 거래명세서 `Sales/DeliveryPage.razor` | ❌ 없음 |

⚠️ `DeliveryPage.razor:575` 에 `line.UnitPrice = price` 가 있으나 이는
**[단가 일괄변경] 대화상자에서 사람이 친 값**이다(`BulkChangeUnitPriceAsync`). 특별단가 조회가 아니다.

🔴 **결론: 업체별 특별단가를 등록해도 판매 화면에서 단가가 자동으로 들어오지 않는다.**
   경리가 등록해 놓고 **매번 손으로 다시 친다.** 등록한 사람은 등록됐다고 믿는다.

### 이것은 *"고쳤다 ≠ 갔다"* 4차 재발과 같은 계통
만드는 쪽(등록)은 완성됐고 **쓰는 쪽으로 가는 길이 없다.** 코드는 매번 정상이고 **끊긴 건 전달 경로**다.
⇒ 검증을 *"저장되나"* 로 하면 **영원히 통과**한다. **"판매 화면에 그 값이 갔나"** 로 물어야 한다.

## 4. 🟢 설계 확정 (2026-08-20 사장님) — **자동 적용을 안 한다. 보여주고 사람이 고른다.**

> 🔴 사장님 원문:
> *"1) **업체 특별단가 우선.** 생각해보니, **상품 특별단가는 존재 자체가 큰 의미가 없네.**"*
> *"2) 단가는 **모든 워크플로우 명세서 작성시(발주,판매,반품,견적,수주,판매) 직접 작성이 가능**하되,
> **마우스 커서 갖다대면, 업체특별단가·최종단가·표준단가·혹은 상품특별단가를 고객이 볼 수 있도록**"*
> *"3) **고로 필터링은 필요가 없음** — 직접입력, 혹은 커서 갖다대서 나오는 금액 선택"*

### 4-1. 🔴 설계가 통째로 단순해졌다 — 앞선 두 안이 모두 폐기됐다

| 차수 | 안 | 결과 |
|---|---|---|
| 초안(PM) | 고정 우선순위 `업체 → 상품 → 기본` 자동 적용 | ❌ **폐기** (사장님: 코드가 정하지 마라) |
| 2차 | 두 축 독립 + **필터 선택 기능** | ❌ **폐기** (사장님: *"필터링은 필요가 없음"*) |
| 🟢 **본안** | **단가는 사람이 넣는다. 시스템은 근거를 보여주기만 한다.** | 🟢 확정 |

🟢 **왜 이게 더 나은가** — 앞의 두 안은 *"시스템이 어느 단가를 쓸지 정하는 문제"* 를 풀려 했다.
   사장님은 **그 문제 자체를 없애셨다.** 정하지 않으면 우선순위도·필터도·충돌 규칙도 필요 없다.
   ⇒ ⓑ *"둘 다 적용 시 곱하나 더하나"* 라는 **돈이 갈리던 질문도 함께 사라졌다.**
   🟢 헌법 #25(쉽게) · [[feedback_semi_auto_principle]](100% 자동은 없다)와 정확히 같은 방향이다.

### 4-2. 무엇을 만드나 — **입력칸 + 참고값 말풍선**

```
 단가 [  125,000  ]  ← 🔴 사람이 직접 친다 (막지 않는다)
        ↑ 커서를 올리면
      ┌──────────────────────────┐
      │ 업체특별단가   120,000  │ ← 클릭하면 그 값이 칸에 들어간다
      │ 최종단가       123,000  │
      │ 표준단가       130,000  │
      │ 상품특별단가   118,000  │
      └──────────────────────────┘
```

🔴 **핵심: 자동으로 채우지 않는다.** 칸은 비어 있거나 사람이 친 값 그대로다.
   말풍선은 **참고 자료**이고, 고르면 들어간다. 안 고르고 직접 쳐도 된다.

⚠️ **말풍선 값을 "적용된 단가" 로 오해하게 만들지 마라.** 보고 있는 것과 들어간 것은 다르다.

### 4-3. 🟢 "업체 특별단가 우선" 의 뜻 — **자동으로 채운다** (사장님 확정 2026-08-20 · C안)

> PM 이 세 갈래로 여쭙고 사장님이 **C** 를 고르셨다:
> A 그대로(표준단가 자동 유지) / B 자동 채움 제거 / 🟢 **C 업체특별단가를 우선으로 자동 채움**

```
품목 선택
   ├─ 업체특별단가 있다 → 🟢 그 값으로 채운다
   └─ 없다             → 표준단가(판매) · 매입단가(발주) 로 채운다  ← 종전 그대로
그 뒤 사람이 고쳐 쓴다 (직접 입력 · 말풍선에서 다른 값 선택)
```

🔴 **PM 이 §4-3 을 잘못 읽고 있었다 — 정정 기록.**
   초판에 *"자동 적용이 아니라 말풍선 표시 순서다 · 자동 적용으로 구현하면 3)을 어긴다"* 라고 적었다.
   **틀렸다.** 사장님 1) *"업체 특별단가 우선"* 은 **말 그대로 우선 적용**이다.
   3) *"필터링은 필요가 없음"* 은 **필터 UI 를 만들지 말라**는 뜻이지 *"자동으로 채우지 말라"* 가 아니었다.
   ⇒ 이 문서를 근거로 *"자동 채움은 위반"* 이라고 판단하지 마라. **C 가 정본이다.**

🟢 **왜 이것이 앞선 폐기안과 다른가** — 초안이 폐기된 것은 *"업체 → 상품 → 기본"* 이라는
   **여러 축의 우선순위를 코드가 정한 것**이었다. C 는 축이 **하나**다(업체특별단가 있나 없나).
   상품특별단가는 자동 적용에 **끼지 않는다**(§4-4) — 말풍선에 보여주기만 한다.
   ⇒ 우선순위 다툼도, 곱셈/덧셈 문제도 여전히 **없다.**

⚠️ **자동으로 채운 값도 잠그지 않는다.** 사람이 지우고 칠 수 있어야 한다(사장님 2) *"직접 작성이 가능하되"*).
⚠️ 기존 동작(표준단가·매입단가 자동 채움)은 **그대로 산다** — 없애지 마라(헌법 #1).

### 4-4. 🔴 상품 특별단가 — *"존재 자체가 큰 의미가 없다"*

사장님 판단. 그러나 **지우지 않는다**(헌법 #1 · #37).
- 화면·표는 **그대로 둔다** — 이미 쓰는 고객이 있을 수 있다
- 말풍선에는 **맨 아래**에 표시한다(사장님이 *"혹은 상품특별단가"* 로 마지막에 부르셨다)
- 🔴 **새 기능을 상품 특별단가 위에 얹지 않는다** — 의미가 옅다고 사장님이 판정한 축이다

### 4-5. 적용 범위 — **6화면 전부** (사장님 명시)

| 흐름 | 화면 |
|---|---|
| 매입 | **발주** · **매입** · **반품** |
| 판매 | **견적** · **수주** · **판매(거래명세서)** |

⇒ 헌법 #8 6단계 워크플로우의 **3단계(매입)·4단계(판매) 양쪽**.
🔴 **한 곳만 하고 "됐다" 하지 마라** — 6화면 전부에 같은 말풍선이 붙어야 한다.

### 4-6. 말풍선 4값의 출처 (실측 확인)

| 표시 | 출처 | 상태 |
|---|---|---|
| 업체특별단가 | `partner_special_prices.special_price` | 🟢 있다 |
| 표준단가 | `items.std_price` | 🟢 있다 |
| 상품특별단가 | `item_special_prices` | 🟢 있다 |
| **최종단가** | ⚠️ **그 업체에 마지막으로 거래한 단가** — 판매/매입 이력에서 뽑는다 | ⚠️ **조사 필요**(§7) |

⚠️ **최종단가는 판매·매입이 서로 다른 값**이다(판 값 ≠ 산 값). 화면에 맞는 쪽을 보여준다.

### 4-7. 확정 후에는 안 흔들린다 (헌법 #6)
문서가 **확정된 뒤** 단가 마스터가 바뀌어도 **이미 나간 문서의 단가는 그대로**다.
🟢 이 설계에서는 **자동 적용이 없으므로** 이 위험이 애초에 작다 — 값은 사람이 넣어 문서에 박힌다.

## 6. 검증 게이트 (SOP [7-V]) — 🔴 **본안에 맞춰 다시 썼다**

⚠️ 게이트를 **두 번 다시 썼다** — 초안(자동 적용) → 2차(자동 금지) → 🟢**본안 C**(업체특별단가만 자동).
   ⇒ 옛 게이트를 그대로 쓰면 **정반대를 검사**한다. G-4 계열은 **C안 기준**이다.

| # | 게이트 | 방법 |
|---|---|---|
| G-1 | **봉합 빼면 FAIL** | 말풍선 배선을 뺀 상태에서 **값이 안 뜨는 것**을 먼저 확인 |
| G-2 | 🔴 **"갔나" 로 판정** | *"조회 API 가 되나"* 금지. **6화면에서 커서를 올리면 실제로 뜨나** |
| G-3 | 🔴 **6화면 전부** | 발주·매입·반품·견적·수주·판매. **한 곳만 하고 됐다 하지 마라** |
| G-4 | 🟢 **업체특별단가가 자동으로 채워진다** (C안) | 특별단가 있는 업체 + 그 상품 ⇒ 품목 선택 시 **그 값이 들어와야** 한다. 표준단가가 들어오면 FAIL |
| G-4b | 🔴 **자동값을 잠그지 않는다** | 자동으로 채워진 뒤에도 **지우고 다시 칠 수 있어야** 한다 (사장님 2) *"직접 작성이 가능하되"*) |
| G-4c | 🔴 **상품특별단가는 자동 적용에 안 낀다** | 상품특별단가만 있는 경우 ⇒ **표준단가**가 들어와야 한다. 상품특별단가가 자동으로 들어오면 FAIL (§4-4) |
| G-5 | 직접 입력이 막히지 않는다 | 말풍선과 무관하게 **아무 값이나 칠 수 있어야** 한다 |
| G-6 | 고르면 들어간다 | 말풍선 값을 클릭 → 그 값이 **칸에 실제로 들어가나** |
| G-7 | 값이 없는 경우 | 특별단가 없는 업체·상품 — **말풍선이 깨지지 않고** 있는 값만 보인다 |
| G-8 | 🔴 **0원 표시 금지** | 값이 없으면 **줄을 빼거나 '없음'**. 0원으로 보이면 **진짜 0원과 구별이 안 된다** |
| G-9 | 매입·판매 최종단가 구분 | 판 값과 산 값이 **섞이지 않는지**(§4-6) |
| G-10 | 대조실험 | 특별단가 **있는 업체 / 없는 업체** 둘로 비교 ([[project_fixed_vs_delivered_gap]]) |

🔴 **G-4c 가 이 건의 수문장이다.** 자동 적용에 **끼는 축은 업체특별단가 하나뿐**이다.
   상품특별단가까지 자동으로 넣으면 **다시 우선순위 다툼**이 생기고, 그것이 초안이 폐기된 이유다.
   ⚠️ G-4(채워지나)와 G-4c(안 채워지나)는 **한 쌍**이다. 둘 다 봐야 C안이 지켜진다.

## 7. 조사 · 범위 밖

### 착수 중 확인할 것 (막지는 않는다)
1. ⚠️ **최종단가의 정의** — *"그 업체에 마지막으로 판/산 단가"* 로 이해했다.
   출처 후보: `sales_delivery_items` / `purchase_receipt_items`. **화면에 맞는 쪽**을 쓴다.
   ⚠️ `partner_special_prices.last_supply_date` 는 **날짜일 뿐 금액이 아니다.** 이걸 쓰지 마라.

### 범위 밖
- 상품특별단가(`item_special_prices`) **자체 수리** — 사장님이 *"존재 자체가 큰 의미가 없다"* 로
  판정하신 축이다. 말풍선에 **표시만** 하고 **손대지 않는다**(§4-4).
- 적용 기간(start/end) 기능 — 본안에서 위험이 사라졌다(§3). 나중에 쓰기로 하면 그때.
