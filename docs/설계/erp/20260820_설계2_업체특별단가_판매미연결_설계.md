> **상태**: 🟡 설계 (코드 무접촉) · **🔴 사장님 정책 결재 없이는 구현 불가**(§5)

## 1. 코드리뷰 결과 — **화면·API·DB 는 정상. 끊긴 건 출구다.**

| 층 | 상태 |
|---|---|
| 화면 `Partners/SpecialPricePage.razor` | 🟢 저장·삭제·할인율 모드 정상 |
| API `PartnerController.cs:229-265` | 🟢 조회·Upsert·삭제 3종 |
| 서비스 `PartnerService.cs:52-140` | 🟢 고정/할인 2모드 처리 · 할인율 0~100 검증 |
| DB `partner_special_prices` | 🟢 21컬럼 · 인덱스 정상 |

⇒ **"작동하냐"** 만 보면 **작동한다.** 6/23(19차) 할인율 봉합도 살아 있다.

### 🔴 그런데 — `partner_special_prices` 를 읽는 곳이 **자기 화면뿐이다**

전수 조사(`grep -rn "partner_special_prices" src/`) 결과 **7개 참조 전부** `PartnerService.cs` 안의
**그 화면 CRUD** 다. **판매 어느 화면도 이 표를 부르지 않는다:**

| 화면 | 특별단가 조회 |
|---|---|
| 견적 `Quotes.razor` | ❌ 없음 |
| 수주 `Sales/SalesOrderPage.razor` | ❌ 없음 |
| 거래명세서 `Sales/DeliveryPage.razor` | ❌ 없음 |

⚠️ `DeliveryPage.razor:575` 에 `line.UnitPrice = price` 가 있으나 이는
**[단가 일괄변경] 대화상자에서 사람이 친 값**이다(`BulkChangeUnitPriceAsync`). 특별단가 조회가 아니다.

🔴 **결론: 업체별 특별단가를 등록해도 판매 화면에서 단가가 자동으로 들어오지 않는다.**
   경리가 등록해 놓고 **매번 손으로 다시 친다.** 등록한 사람은 등록됐다고 믿는다.

### 이것은 *"고쳤다 ≠ 갔다"* 4차 재발과 같은 계통
만드는 쪽(등록)은 완성됐고 **쓰는 쪽으로 가는 길이 없다.** 코드는 매번 정상이고 **끊긴 건 전달 경로**다.
⇒ 검증을 *"저장되나"* 로 하면 **영원히 통과**한다. **"판매 화면에 그 값이 갔나"** 로 물어야 한다.

## 2. 실측 (2026-08-20, 이 PC = demo 운영)

```
SELECT COUNT(*) FROM partner_special_prices;  ⇒ 0
```
⇒ **현재 등록된 특별단가가 0건**이라 *"단가가 안 들어온다"* 는 증상이 **아직 안 드러났다.**
   고객이 쓰기 시작하면 **즉시 터진다.** (헌법 #39 — 운영은 읽기만. SELECT 만 했다)

## 3. 🔴 화면이 안 쓰는 컬럼 2개 — 같이 결정해야 한다

DB 에는 있는데 **화면이 한 번도 안 채우는** 칸:

| 컬럼 | 지금 | 문제 |
|---|---|---|
| `start_date` | INSERT 에 `NULL` 고정 (`PartnerService.cs:597`) | **적용 시작일이 없다** |
| `end_date` | 같음 | **만료가 없다 — 한 번 준 단가는 영원하다** |

⇒ *"이번 분기만 이 단가"* 를 못 한다. 지금 구조로 연결하면 **영구 할인**이 된다.
🔴 이건 **연결 전에 정해야 한다.** 연결하고 나서 바꾸면 이미 나간 견적의 단가가 흔들린다.

## 4. 설계 — 두 축은 **별개로 돌고, 겹치면 사람이 고른다**

🔴 **원칙 1: 단가 결정 로직을 화면마다 따로 짜지 않는다.**
   견적·수주·명세서·발주가 각자 계산하면 **화면마다 값이 달라진다**(원장·회계까지 번진다).
   ⇒ **서버에 단가 해석기 하나**를 두고 모든 화면이 그것만 부른다.

### 4-1. 🔴 두 특별단가는 **독립 축**이다 (사장님 확정 — §5)

```
업체특별단가 (partner_special_prices)  ─┐
                                        ├─ 별개로 돈다. 서로 종속 안 됨
상품특별단가 (item_special_prices)     ─┘
                                        ↓
                        겹치면 → 🔴 **필터 선택(사람)**
                                        ↓
                        아무것도 없으면 → 상품 기본단가
```

🔴 **고정 우선순위를 코드에 넣지 마라.** PM 초안이 *"업체 → 상품 → 기본"* 순서를 제안했으나
   **사장님이 뒤집으셨다** — *"둘다 적용시킬건지에 대한 **필터링 선택기능** 추가"*.
   ⇒ 어느 쪽이 이기는지는 **코드가 아니라 사용자가 정한다.**

### 4-2. 🔴 적용 범위 = **매입 · 판매 양쪽** (사장님 확정)
> *"특별단가가 **매입-판매 워크플로우 축**에 적용이 되야함"*

| 흐름 | 화면 | 지금 |
|---|---|---|
| 매입 | 발주 → 매입 | ❌ 특별단가 안 부름 |
| 판매 | 견적 → 수주 → 거래명세서 | ❌ 특별단가 안 부름 |

⇒ **6단계 워크플로우(헌법 #8)의 3단계·4단계 양쪽**에 해석기가 붙는다.
⚠️ 매입은 **매입처 단가**다. 같은 표를 쓰되 **판매가와 섞이지 않게** 한다(⚠️ 조사 필요 — §7).

### 4-3. 🔴 반자동 원칙 (헌법 · [[feedback_semi_auto_principle]])
> **제안값 → 사람이 수정 → 확정.** 100% 자동은 없다.

⇒ 특별단가는 **자동으로 채워 넣되 사람이 고칠 수 있어야** 한다. **잠그지 않는다.**
⇒ 고친 경우 **왜 달라졌는지 남는다**(수정 이력). 원장·세금계산서로 흐르는 값이라 근거가 필요하다.
🟢 §4-1 의 필터 선택도 **같은 정신**이다 — 시스템이 정하지 않고 사람이 정한다.

### 4-4. 확정 후에는 안 흔들린다 (헌법 #6)
견적·수주가 **확정된 뒤**에 특별단가를 바꿔도 **이미 나간 문서의 단가는 그대로**다.
⇒ 단가 해석은 **문서 작성 시점에 한 번**. 조회할 때마다 다시 계산하지 않는다.

## 5. 🟢 사장님 결재 (2026-08-20 · 일부 확정)

> 🔴 사장님 원문:
> *"특별단가가 **매입-판매 워크플로우 축에 적용**이 되야함.
> (워크플로우 흐름에 **업체특별단가, 상품 특별단가 별개로 돌아야 함**.
> **특별단가 적용업체 + 특별단가 적용상품은 둘다 적용시킬건지에 대한 필터링 선택기능 추가**)"*

### 5-1. 🟢 확정된 것

| # | 결정 |
|---|---|
| ① **적용 축** | 🟢 **매입·판매 워크플로우 양쪽 다** (§5 옛 ④ *"매입에도 적용하나"* 해소 — **적용한다**) |
| ② **두 특별단가 관계** | 🟢 **별개로 돈다.** 업체특별단가와 상품특별단가는 **서로 종속되지 않는 독립 축**이다 |
| ③ **겹칠 때** | 🟢 **자동으로 정하지 않는다** — **필터링 선택 기능**으로 사람이 고른다 |

🔴 **③이 이 설계의 핵심이고, PM 초안을 뒤집은 자리다.**
   PM 초안은 *"①업체 → ②상품 → ③기본"* 이라는 **고정 우선순위**를 제안했다.
   사장님은 **우선순위를 코드가 정하지 말라**고 하셨다.
   ⇒ 업체도 특별단가 대상이고 상품도 특별단가 대상일 때,
     **둘 다 적용할지 / 하나만 적용할지를 사용자가 고른다.**

   🟢 이것이 **반자동 원칙**([[feedback_semi_auto_principle]])과 정확히 같은 방향이다 —
     *"제안값 → 사람이 수정 → 확정"*. **100% 자동은 없다.**
   ⚠️ 다음 사람이 *"우선순위를 자동으로 하면 편하다"* 며 되돌리지 마라. **사장님이 명시로 막은 자리다.**

### 5-2. 🔴 아직 결재 안 난 것 (구현 전 필요)

| # | 무엇 | 왜 |
|---|---|---|
| ⓐ | **필터 선택을 어디에 두나** — 문서마다? 회사 기본값? 둘 다? | 화면 크기가 갈린다 |
| ⓑ | **둘 다 적용 시 계산 순서** | 업체 10% + 상품 5% 를 **곱하나 더하나** — 금액이 달라진다 |
| ⓒ | **적용 기간(start/end) 사용 여부** (§3) | 안 쓰면 **영구 할인**. 미결 상태 그대로 |
| ⓓ | **기본값** — 처음 설치했을 때 필터가 어느 쪽? | 고객이 안 고르면 무엇으로 도나 |

⚠️ ⓑ 는 **돈이 갈리는 자리**다. 곱셈(10%→5% 추가할인)과 덧셈(15% 할인)은 결과가 다르다.

## 6. 검증 게이트 (SOP [7-V])

| # | 게이트 | 방법 |
|---|---|---|
| G-1 | **봉합 빼면 FAIL** | 연결을 뺀 상태에서 **단가가 안 들어오는 것**을 먼저 확인 |
| G-2 | 🔴 **"갔나" 로 판정** | *"저장되나"* 금지. **특별단가 등록 → 견적 화면에서 그 값이 뜨나** |
| G-3 | 3화면 일치 | 견적·수주·명세서가 **같은 값** (해석기 한 곳 원칙 검증) |
| G-4 | 사람이 고칠 수 있나 | 반자동 원칙 — 자동으로 채우되 **수정 가능** |
| G-5 | 확정 후 불변 | 확정 문서의 단가가 **나중 변경에 안 흔들림**(헌법 #6) |
