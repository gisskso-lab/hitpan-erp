## 2. 무엇을 만드는가

     ────────────────────────────────────────
      문서종류  제목  신청자  신청일  상태
```

### 필터1 (5개) — `status` + **나와의 관계**

| 값 | 라벨 | 판정 |
|---|---|---|
| `pending` | 결재 대기 | 지금 **내 차례**인 문서 (위임 포함) — 종전 `GetPending` |
| `completed` | 결재 완료 | 내가 결재했고 **`ad.status='approved'`** |
| `rejected` | 반려 | 내가 관여했고 **`ad.status='rejected'`** 🔴신설 |
| `sent` | 내가 보낸 결재 | `requester_id = 나` — 종전 `GetSent` |
| `all` | 모든 결재 | **보낸이 · 결재자 · 대표이사** 가 볼 수 있는 범위 |

### 🔴 「모든 결재」 범위 — 사장님 결재 (2026-08-24)

> *"내가 보낸결재는 **보낸이가 볼수 있어야** 하고, **결재자, 대표이사도 볼 수 있어야** 함."*

⇒ **세 자리가 본다.** 「내가 관여한 것만」도 아니고 「전 직원 전체공개」도 아니다.

| 보는 사람 | 판정 | 보이는 범위 |
|---|---|---|
| **보낸이** | `ad.requester_id = 나` | 내가 올린 문서 |
| **결재자** | 내 이력이 있거나 · 지금 내 차례 | 내가 결재한/할 문서 |
| **대표이사** | 🔴 `u.is_parent = 1` | **회사 전체 결재** |

🔴 **대표 판정은 `users.is_parent = 1` 이다.** 새로 만들지 않는다 —
G1 에서 결재선 후보를 뽑을 때 쓴 바로 그 축이다(`EmployeeService.cs:119`).
`account_type='tenant_admin'` 으로 판정하면 **안 된다**: 그건 로그인 축이고,
결재는 `employee_id` 축으로 돈다(6/21 A-P0-1 봉합이 정확히 이 자리였다).

⚠️ **일반 직원에게 남의 휴가·경비가 새면 안 된다.** 대표가 아닌 사람에게
`all` 은 여전히 **보낸이 + 결재자** 합집합이다.

### 필터2 (11개) — `doc_type`

```
전체 · 일일보고서 · 주간보고서 · 월간보고서 · 경위서
     · 휴가 · 휴직 · 경비 · 초과근무 · 사직서 · 전자근로계약서

## 3. 어떻게 만드는가

### [A] API — 엔드포인트 1개로 합친다

```
GET /api/approval/documents?scope={pending|completed|rejected|sent|all}&docType={전체는 생략}
```

🔴 **기존 3개(`pending`·`sent`·`completed`)는 지우지 않는다** (헌법 #1).
- 사이드바 대기 건수 배지(`Sidebar.razor:361`)가 `pending` 을 부른다
- 8/23 실측 스크립트 2본이 이 주소를 쓴다
⇒ **남겨두고 새 것을 추가한다.** 지우면 배지가 죽는다.

### [B] SQL — 한 쿼리 + 조건 조립

```sql
FROM approval_documents ad
WHERE ad.tenant_id = @TenantId
  AND ad.doc_type NOT IN (ERP 7종)          -- ① 과 같은 기준
  AND (@DocType IS NULL OR ad.doc_type = @DocType)
  AND <scope 조건>
```

`scope` 별 조건:

| scope | 조건 |
|---|---|
| `pending` | `ad.status='pending'` AND 현재 seq 결재자가 나 (위임 포함) |
| `completed` | `ad.status='approved'` AND `EXISTS(내 이력)` |
| `rejected` | `ad.status='rejected'` AND (`EXISTS(내 이력)` OR `requester_id=나`) |
| `sent` | `ad.requester_id=@EmployeeId` |
| `all` | 🔴 **대표(`is_parent=1`)면 조건 없음**(회사 전체)<br>그 외는 위 넷의 **OR** |

🔴 **대표 판정은 SQL 안에서 하지 않는다.** 서비스가 **먼저** 한 번 조회해
`bool isOwner` 를 얻고, 참이면 scope 조건을 **통째로 생략**한다.
`OR (SELECT is_parent ...) = 1` 을 조건에 섞으면 **행마다 서브쿼리가 돌고**,
더 나쁘게는 **조건 하나 빠뜨렸을 때 전 직원에게 회사 전체가 새는** 형태가 된다.
**갈래를 눈에 보이게 둘로 가른다.**

🔴 **`rejected` 에 `requester_id=나` 를 넣는 이유**: 내가 올린 게 **1차에서 반려**되면
내 이력은 없다(나는 결재자가 아니다). 그때도 신청자에겐 보여야 한다 —
*"왜 안 오는지 모른다"* 를 없애는 게 이 필터의 목적이다.

### [C] 화면 — 새 1개 + 옛 3개는 넘긴다

- 신설 `Pages/Approval/ApprovalManagePage.razor` → `/approval`
- 🔴 옛 3주소(`/approval/pending` 등)는 **삭제하지 않고** 새 화면으로 **넘긴다**
  (즐겨찾기·북마크·메신저에 뿌린 링크가 죽으면 안 된다)
  넘길 때 **필터1을 그 주소에 맞춰 연다** — `/approval/pending` → 필터1=결재대기

### [D] 사이드바 — 3줄 → 1줄

```razor
<MudNavLink Href="/approval" ...>결재관리 [배지]</MudNavLink>
```
대기 건수 배지는 **「결재관리」 옆에** 그대로 단다.

## 5. 검증 기준 — 이걸로 판정한다

🔴 **HTTP 코드로 판정 금지** (8/23 교훈 §2). SPA 라 **없는 주소도 200** 이다.
🔴 **인증 없이 재면 전부 401** — 로그인 후 실측한다.

| # | 재는 것 | 통과 기준 |
|---|---|---|
| V-1 | 필터1 5개 · 필터2 11개 | **콤보박스 안 항목 수·글자**로 확인 |
| V-2 | 필터2 에 ERP 7종 없음 | 「거래명세서」·「견적서」 **없어야** 통과 |
| V-3 | 🔴 **반려 분리** | 반려 문서가 「완료」에 **안 뜨고** 「반려」에 **뜬다** |
| V-4 | 🔴 **1차 반려를 신청자가 본다** | 내 이력 없이도 「반려」에 뜬다 |
| V-5 | 필터2 교차 | 필터1×필터2 조합이 목록을 실제로 줄인다 |
| V-6 | 옛 주소 3개 | `/approval/pending` 이 필터1=대기로 열린다 |
| V-7 | 배지 생존 | 사이드바 대기 건수가 종전과 같다 |
| V-8 | 🔴 **일반 직원은 남의 결재 못 봄** | 「모든 결재」에 내가 관여 안 한 건 **없다** |
| V-9 | 🔴 **대표는 회사 전체를 봄** | 대표 로그인 시 남이 올린 문서가 **보인다** |

🔴 **V-3·V-4 는 게이트를 먼저 실패시켜 확인한다** — 봉합을 빼고 반려 문서가
「완료」에 뜨는 것을 **눈으로 보고** 나서 넣는다. 안 그러면 초록불이 어디서 왔는지 모른다.

## 6. 왜 지금 하면 두 번 안 만지나

① 이 **ERP 를 빼고 2종을 채워** 목록을 10종으로 확정했다.
그 확정 위에 필터를 얹는 것이라, ③④⑤ 에서 문서종류가 늘어도
**사전에 한 줄 추가하면 필터2가 따라온다**(사전을 순회해 만들기 때문).

⚠️ ③ 이 초과근무 직접신청을 만들면 그때 필터2가 **자동으로** 그 항목을 갖는다 —
필터 코드를 다시 안 고친다.
