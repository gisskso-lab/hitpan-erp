## 0. 🔴 선행 설계가 이미 있다 (사장님 지적 2026-08-10)

> 사장님: *"히트판 랜딩가입, 배포에서 **이미 그쪽으로 방향을 잡고 설계, 개발했어**."*

⚠️ **설계팀이 기존 설계를 확인하지 않고 신규 설계로 접근했다.** 아래는 **이미 확정된 설계**다.
**이 PRD 는 신규 설계가 아니라 기존 설계의 미이행분을 잇는 문서**로 성격이 바뀐다.

| 항목 | 기존 설계 (확정) | 코드 실태 |
|---|---|---|
| **OCR 용도** | `docs/설계/랜딩/DOMAIN_MODEL_LANDING.md:207`<br>*"OCR로 사업자번호 추출 → **입력값과 대조**"* | 🔴 미구현 (`Task.Delay`) |
| **업로드 API** | `docs/설계/랜딩/API_SPEC_LANDING.md:45`<br>`POST /signup/business-license` → `{upload_id, ocr_business_number, **is_match**}` | 🔴 미구현 |
| **파일 저장** | 〃 `:49` — **Cloudflare R2 위임**, 본사 DB 는 메타만 (헌법 #22) | 🔴 미구현 |
| **약관 필수** | `DOMAIN_MODEL_LANDING.md:210` — **필수 4건** 미동의 시 진행 불가 | 🔴 코드는 **3건** |
| **동의 기록** | 〃 `:211` — 동의 일시·IP·약관 버전 DB 기록 의무 | ⬜ 미확인 |

### ⭐ `is_match` — 기존 설계가 이미 답을 갖고 있었다

기존 설계의 OCR 은 **단순 추출이 아니라 "입력값과 대조"** 다.
사용자가 친 사업자번호와 **등록증에서 읽은 번호가 일치하는가**를 판정한다(`is_match`).

⇒ **이것이 사장님이 말씀하신 임의등록 차단의 구현체**다.
본 PRD §4-1 의 L-1~L-5 는 이 설계를 **다시 쓴 것이 아니라 이행**하는 것이다.

### ⚠️ 정정 — "약관 4건"은 신규 요구가 아니다

설계팀은 *"동의서를 신설해 3건→4건으로 늘리자"* 고 적었다. **틀렸다.**
**설계는 이미 4건이고, 코드가 3건인 것이 미이행**이다(`SignupPage.razor:415`).
새로 만드는 게 아니라 **설계대로 안 된 것을 맞추는 것**이다.

### ⬜ 확인 필요 — R2 저장 vs 심사 후 파기

기존 설계는 **Cloudflare R2 에 파일 위임**이고, 8/10 사장님 결재는 **심사 중만 보관 후 파기**다.
두 정책의 관계 정리 필요 → §9 미결 5번.

## 0-1. 🆕 정책 전환 — "최소한" → "등록증 정보는 다 갖는다"

> 사장님 (8/10): *"아직 미구현 영역이고, **원래는 설계는 고객사 정보를 최소한으로 본사가 가지고
> 있으려고** 했던거고, **지금은 사업자등록증 정보 정도는 다 갖고있자**는거야."*

⭐ **기존 설계가 틀린 게 아니라, 전제가 바뀐 것이다.**

| | 종전 설계 (2026-06) | 🆕 현재 (2026-08-10) |
|---|---|---|
| 본사 보유 | **최소한** — 해시만 | **사업자등록증 정보 전부** |
| 이유 | 데이터 최소주의(#22) 극단 적용 | **세금계산서 발행** + **임의등록 차단** |
| 등록증 파일 | R2 위임 | 심사 중만 → 파기 |
| 업무 데이터 | ⛔ 금지 | ⛔ **금지 (불변)** |

⇒ 확대되는 것은 **사업자등록증에 적힌 정보까지**다. 그 이상은 아니다.

### 🔴 화면 실측 (2026-08-10 · `test1.hitpan.kr/company`)

사장님이 보여주신 실제 화면 — **정책 전환이 왜 필요한지가 그대로 보인다**:

| 필드 | 현재 상태 | 원인 |
|---|---|---|
| 사용업체명 `test1` | 🔒 **랜딩 자동 반영 (변경 불가)** | 백오피스가 `company_name` 을 갖고 있다 |
| 사업자번호 `5651203021` | 🔒 **랜딩 자동 반영 (변경 불가)** | 부트스트랩 시 전달됨 |
| 우편번호·전화·주소·상세주소 | ⬜ **비어 있고 편집 가능** | 🔴 **백오피스가 값을 안 갖고 있다** |
| 종사업장번호·법인등록번호·업태 | ⬜ **비어 있고 편집 가능** | 🔴 **〃** |

⭐ **잠금 장치(2관문)는 이미 작동한다.** 화면에 🔒 자물쇠와 "랜딩 자동 반영 (변경 불가)" 가 떠 있다.

🔴 **문제는 잠긴 필드가 2개뿐이라는 것이다.**
주소·업태·종목이 비어 있는 이유 = **백오피스가 그 값을 수집하지 않았기 때문**이다.
그래서 **손으로 아무거나 칠 수 있다** — 이것이 사장님이 막으려는 **임의등록** 경로다.

### ⇒ 인과 사슬 (이 PRD 의 핵심 한 줄)

```
백오피스가 정보를 안 가짐  →  ERP 에 자동 반영할 값이 없음
                          →  빈칸으로 남음
                          →  사용자가 손으로 입력
                          →  🔴 임의등록 가능 (무단사용)
```

**정보를 다 가지면 → 다 자동 반영되고 → 다 잠긴다.**
지금은 **정보가 없어서 잠글 것도 없는** 상태다.

⇒ §4-2(백오피스 보관)와 §4-3(ERP 자동반영)은 별개 기능이 아니라 **하나의 사슬**이다.
수집을 안 하면 잠금도 불가능하다.

### 0-2. 🔴 필드 분류 — 전부 잠그는 것이 아니다 (사장님 지적 2026-08-10)

> 사장님: *"**전화번호, 주소, 상세주소, 우편번호는 그대로 비어있어**"*

⚠️ **설계팀 서술 정정** — 위에서 네 필드를 "백오피스가 안 가져서 빈칸" 으로 뭉뚱그렸다.
**성격이 다르다.** 사업자등록증에 **적혀 있는 것**과 **없는 것**을 갈라야 한다.

| 필드 | 등록증에 있나 | 처리 | 잠금 |
|---|---|---|---|
| 사용업체명(상호) | ✅ 있음 | 🔒 자동 반영 | **잠금** (현재 작동) |
| 사업자번호 | ✅ 있음 | 🔒 자동 반영 | **잠금** (현재 작동) |
| 대표자명 | ✅ 있음 | 🆕 자동 반영 | **잠금** |
| **주소** | ✅ 있음 (사업장 소재지) | 🆕 자동 반영 | **잠금** |
| **우편번호** | △ 주소에서 유도 | 🆕 자동 반영 | **잠금** |
| 업태 | ✅ 있음 | 🆕 자동 반영 | **잠금** |
| 종목 | ✅ 있음 | 🆕 자동 반영 | **잠금** |
| 법인등록번호 | ✅ 있음 (법인만) | 🆕 자동 반영 | **잠금** |
| **상세주소** | △ 등록증 주소에 포함되기도 | 🟡 **보완 입력 허용** | 열림 |
| 🔴 **전화번호** | ❌ **없음** | ⬜ **고객 직접 입력** | **열림** |
| 팩스·홈페이지·이메일 | ❌ 없음 | ⬜ 고객 직접 입력 | 열림 |
| 종사업장번호 | ❌ 없음(별도 발급) | ⬜ 고객 직접 입력 | 열림 |

⭐ **원칙: 등록증에서 읽은 값만 잠근다.**
등록증에 없는 값(전화·팩스·홈페이지)은 **잠글 근거가 없다** — 대조할 원본이 없기 때문이다.
무단사용 차단은 **"이 회사가 누구인가"** 를 고정하는 것이지, 연락처를 고정하는 게 아니다.

⚠️ **상세주소 주의** — 등록증 주소가 "○○시 ○○구 ○○로 123, 4층" 처럼 상세까지 포함될 수 있다.
OCR 이 어디까지 끊어 읽을지 **파싱 규칙 필요**(§9 미결 6번). 잘못 끊으면 잠긴 필드에 틀린 값이 들어가
**본사 승인 없이는 못 고치는 상태**가 된다 — 이게 가장 위험한 실패 모드다.

## 1. 제품 요구 — 목적이 **둘**이다 (혼동 금지)

| # | 목적 | 무엇이 필요한가 | 사장님 발언 |
|---|---|---|---|
| **①** | 🆕🔴 **히트판 무단사용 차단** | **등록증 이미지 + OCR 검증** | *"사업자등록증 OCR검증 이유는 히트판의 무단사용 때문이야"* (8/10) |
| ② | **본사→고객사 세금계산서 발행** | 사업자정보 6항목 보관 | *"세금계산서를 끊어줄 수 있어"* (8/10) |

⭐ **①이 OCR 의 진짜 이유다.** ②는 정보 수집만으로 해결되지만 **①은 등록증 실물이 있어야 한다.**

### 🔴 왜 국세청 API 로는 ①을 못 막는가

| 검증 수단 | 확인되는 것 | 무단사용 차단 |
|---|---|---|
| 국세청 진위확인 API | "이 사업자번호가 **실재하는가**" | ❌ **아무 회사 번호나 주워 넣어도 통과** |
| **등록증 이미지 + OCR** | "신청자가 그 사업자를 **보유하는가**" | 🟢 **차단됨** |

사업자번호는 **공개정보**다(세금계산서·홈페이지·명함에 다 적혀 있다).
번호만 검증하면 **남의 번호로 히트판을 설치할 수 있다.** 등록증 제출이 그걸 막는 유일한 관문이다.

⇒ **등록증 수집은 선택이 아니라 라이선스 통제의 핵심**이다. §9-1 참조.

### 1-1. ⭐ 무단사용 차단은 **2중 관문**이다 (사장님 설계)

> 사장님 (8/10): *"물론 국세청 API검사로 계정 가입때 절차를 거치지만 **한번 더** 기본 사업장에 대한
> 정보를 **임의로 바꾸지 못하는 절차**를 둠으로 무단사용을 막는거지"*

```
[1관문] 가입 시 — 국세청 진위확인 API
          ↓  막는 것: 실재하지 않는 사업자
[2관문] 설치 후 — 기본사업장정보 OCR 잠금
          ↓  막는 것: 가입 후 딴 회사로 바꿔치기
```

| 관문 | 시점 | 없으면 뚫리는 경로 |
|---|---|---|
| ① 국세청 API | 가입 | 가짜 번호로 가입 |
| ② **OCR 잠금** | **설치 후** | 🔴 **정상 가입 후 ERP 에서 회사정보만 바꿔 다른 사업장에서 사용** |

⚠️ **설계팀 오판 정정** — 두 검증을 *"어느 쪽이 나은가"* 로 비교했다. **경쟁 관계가 아니라 직렬이다.**
①만 있으면 가입은 정상 통과한 뒤 **ERP 안에서 얼마든지 바꿀 수 있다.** ②가 그 구멍을 닫는다.

⇒ **`is_locked_from_landing` 잠금(E-6)은 replay 방어일 뿐 아니라 무단사용 차단 장치**다.
변경요청에 **본사 승인 필수**(사장님 결재)인 이유도 여기 있다 — 자동 통과면 2관문이 무의미해진다.

## 3. 목표 상태 (TO-BE) — 사장님 오더 4번·5번 흐름

```
[신규 가입]
  랜딩: 사업자등록증 업로드
     ↓ OCR 인증 (실제로 글자를 읽는다)
     ↓ 국세청 진위확인 (계속사업자인가)
  백오피스: 사업자정보 저장 (평문·암호화)
     ↓ 심사 → 승인
     ↓ 🔴 등록증 파일 파기 (심사 종료 시점)
  ERP: 계정관리 → 회사정보 → 기본사업장정보 자동 등록
     ↓
  본사: 세금계산서 발행 가능 ✅

[정보 변경]
  ERP 기본사업장정보: [사업자정보 변경요청] 버튼
     ↓ OCR 재인증
  백오피스: 변경요청 접수
     ↓ 🔴 본사 승인 (필수 — 자동 통과 없음)
     ↓ 시리얼넘버 재발급
  ERP: 자동 반영
```

### 4-1. 랜딩 — OCR 인증

| L-2 | 추출 항목: 사업자번호·상호·대표자명·주소·업태·종목 | P0 | 🔴 없음 |

### 4-1-0. 🆕 반자동 OCR 흐름 — 사람이 최종 확인한다 (사장님 확정 2026-08-10)

> *"ocr인증을 반자동으로 하면되. 1. ocr 사진전송 2. 자체 검증, 데이터 추출
> 3. 추출한 데이터 보여주며 '사업자 등록증과 아래 사업자 정보가 일치합니까?' 4. y/n"*
> *"y 선택시 반영, n 선택시 수동작성 가능"*
> *"수동작성 햇던 정보도 실제 히트판에서는 사업자등록증 인증없이는 비활성화"*
> *"수동 작성시에도 ocr 검증으로서 최소한의 검증은 필요해!!!"*

```
1. 등록증 사진 전송
2. 자체 검증 + 데이터 추출
3. 추출값을 보여주며 묻는다
   "사업자 등록증과 아래 사업자 정보가 일치합니까?"
4. ├─ [예] → 그대로 반영
   └─ [아니오] → 수동 작성 (⚠️ 단 OCR 원본과 대조 통과해야 함 — §4-1-2)
                  ↓
   어느 쪽이든 확정되면 → 🔒 ERP 에서는 잠긴다
```

⭐ **OCR 이 100% 정확할 수 없다는 것을 전제로 한 설계다.**
기계가 읽고 **사람이 책임진다.** 이 확인 단계가 §0-2 의 "오독이 잠긴 채로 갇히는" 최악의
실패 모드를 막는 탈출구다.

⭐ **[아니오] 는 우회로가 아니다** — 수동 작성한 값도 확정되면 똑같이 잠긴다.
수동은 **오독을 고치는 창구**일 뿐, ERP 에서 자유롭게 고치는 권한이 아니다.
⇒ 임의등록 차단(§4-1-1)과 충돌하지 않는다.

### 4-1-2. 🔴 수동 작성도 OCR 원본과 대조한다 (관용 대조)

> 사장님: *"O 한글ㅇ 숫자0 과같은 햇갈리는 이미지와 구문은 인식을 못하더라도
> **누가봐도 틀린 구문은 잡아낼수 있잖아?** 그런건 잡아줘야함.
> 그래야 **불법사용방지에 대한 니즈가 확실**해져"*

⚠️ **[아니오] 후 수동 입력을 무검증으로 두면 그것이 곧 우회로다.**
아무 회사 이름이나 적어 통과시킬 수 있으면 2관문 전체가 무의미해진다.

| 구분 | 예 | 판정 |
|---|---|---|
| 🟢 **통과** (OCR 한계) | `O` ↔ `ㅇ` ↔ `0` · `1` ↔ `l` ↔ `I` · 띄어쓰기·`(주)`↔`주식회사` | 오독으로 보고 허용 |
| 🔴 **차단** (명백한 불일치) | `공영정보` → `삼성전자` · 사업자번호 자릿수가 통째로 다름 | 저장 거부 |

**대조 방식(설계팀 안)**:
- 비교 전 **정규화** — 공백·괄호·법인격 표기 제거, 혼동 문자군을 같은 값으로 치환
- 정규화 후 **유사도 임계치** 판정 (문자열 거리)
- **사업자번호는 숫자만 남겨 완전 일치** 요구 (여기서 관용을 주면 남의 번호가 통과한다)
- 임계치 미달이면 저장 거부 + 사유 표시

⚠️ **임계치 값은 실측으로 정한다** — 실제 등록증 표본 없이 숫자를 정하면 근거 없는 값이 된다.
너무 엄격하면 정상 고객이 막히고(8/02 사고), 너무 느슨하면 우회로가 된다.

### 4-1-1. 🔴 OCR 은 편의 기능이 아니라 **입력 통제 수단**이다

> 사장님 (8/10): *"기본사업장 정보를 OCR로 등록하여, **임의등록 못하게** 하기 위함이야."*

⚠️ **설계팀 정정** — 종전 L-3·L-5 는 "OCR 은 편의 기능, 수기 입력 폴백을 열어두자"였다.
**목적과 정면 충돌한다.** 수기 입력을 열면 그게 곧 임의등록 경로다.

| | 종전 설계 (폐기) | 🆕 정정 |
|---|---|---|
| 입력 경로 | OCR **또는** 수기 | **OCR 만** |
| OCR 실패 시 | 수기 입력으로 통과 | **본사 수동 심사** (자동 통과 없음) |
| 값 수정 | 자유 편집 | **오독 정정만** — 원본 대조 |

⭐ **원칙: 기본사업장정보에 사람이 직접 타이핑해 넣는 경로는 존재하지 않는다.**
값의 출처는 항상 **등록증 이미지**다.

⚠️ **8/02 사고와의 차이** — 그때 교훈은 *"외부 장애로 가입이 막히면 안 된다"* 였다.
그건 여전히 유효하나, 해법이 **"수기로 통과"가 아니라 "본사 수동 심사로 우회"** 다.
막히지 않게 하되, **검증 없이 통과하지는 않는다.**

### 9-1. 🔴 폐기된 안 — "등록증을 아예 안 받는다" (설계팀 오판 기록)

법무 조사가 **국세청 API 3필드(번호·대표자명·개업일자)만으로 검증 가능**하다는 것을 찾아냈고,
설계팀은 *"그러면 이미지를 받을 이유가 없다"* 고 권고했다. **틀렸다.**

> 사장님 (8/10): *"사업자등록증 OCR검증 이유는 히트판의 **무단사용** 때문이야."*
> 사장님 (8/10): *"기본사업장 정보를 OCR로 등록하여, **임의등록 못하게** 하기 위함이야."*

**설계팀이 목적을 세금계산서 하나로만 봤다.** 세금계산서만 목적이면 정보 수집으로 충분하고
등록증은 불필요하다 — 논리는 맞았으나 **전제가 틀렸다.**

⭐ **교훈**: *"이 기능이 왜 있는지"* 를 확인하지 않고 *"어떻게 하면 더 안전한지"* 만 따졌다.
법무 조사 결과가 아무리 좋아도 **목적을 모르면 잘못된 최적화**다 (헌법 #33 — 의중 100% 이해).

⇒ **등록증 수집은 유지한다.** 국세청 API 는 **폐업·휴업 확인용 보조 수단**으로 병행한다
(두 검증이 막는 것이 서로 다르다 — §1 표).
