## 0. 4인 공통 전제

사장님 원칙을 설계 언어로 옮기면 이렇다.

> **워치독은 ERP의 전제조건이 아니다. 감시자가 못 붙어도 피감시자는 일한다.**

이를 위반하는 현재 구조의 핵심은 **한 줄**이다.

```pascal
// installer/HitPan-Universal.iss:1809-1811
Exec('powershell.exe', '... InstallWatchdog.ps1 ...', '', SW_HIDE,
     ewWaitUntilTerminated, ResultCode);   // ← 시간 상한 없음
```

`ewWaitUntilTerminated`는 **끝날 때까지 무한 대기**한다. 스크립트가 32분을 쓰면 설치도 32분 멈춘다.
Inno Setup은 `ewWaitUntilTerminated`에 타임아웃 인자를 제공하지 않는다 — **구조적으로 상한을 걸 수 없다.**

따라서 상한은 **호출부가 아니라 피호출측(PowerShell)에서** 걸어야 한다. 이것이 4인 공통 결론이다.

## 1. 설계팀장 — 계층 분리 구조

### 1-1. 3계층 정의

```
┌─ 업무 계층 (ERP) ─────────────── 무엇도 막지 못한다
│   HitPan.API / HitPan.Web / MariaDB
├─ 복구 계층 (워치독 통신부) ────── 업무를 막지 않는다
│   WS28A~F,I · 헬스체크 · 터널 자가복구
└─ 설치 계층 (워치독 업데이트부) ── 복구를 막지 않는다
    고리1~4 · 백업 · 메타핑
```

### 1-2. 계층 간 의존 규칙 (단방향)

| 규칙 | 내용 |
|---|---|
| **R-1** | 하위 계층은 상위 계층을 **차단할 수 없다** |
| **R-2** | 상위 계층 실패는 하위 계층에 **전파되지 않는다** |
| **R-3** | 각 계층은 **독립적으로 복구** 가능해야 한다 |
| **R-4** | 계층 간 통신은 **비동기·무차단**. 응답 없어도 진행 |

### 1-3. 프로세스 분리 판단 (사장님 원칙 대비)

사장님 원칙에 **가장 충실한 것은 프로세스 분리**다(복구용 서비스 / 설치용 서비스 2개).
`sc failure`가 개별 재시작을 하려면 프로세스가 나뉘어야 하기 때문이다.

**다만 본 설계서는 실행 경계 분리(단계별 격리)까지만 담는다.** 사유:

| 항목 | 프로세스 분리 | 실행 경계 분리 |
|---|---|---|
| 사장님 원칙 충실도 | ◎ | ○ |
| 공사 규모 | 서비스 2개·설치 2배·자기갱신 문제 2배 | 코드 격리 |
| 오늘 발견 결함 해소 | ◎ | ◎ |
| 베타 일정 | 지연 | 유지 |

> **설계팀장 의견**: 프로세스 분리는 **정식 출시 전 별도 설계**로 올린다. 본 작업에서 실행 경계를
> 먼저 나눠 두면, 이후 프로세스 분리 시 **경계선이 이미 그어져 있어** 이관이 쉽다. 순서상 이득.
> **단, 이는 사장님 결재 사항이며 PM이 임의 결정하지 않는다.**

## 2. 네트워크 매니저(마이클) — 설치마법사 재설계

### 2-1. 진범 구조 분석

```
InstallWatchdog.ps1
  L9   $ErrorActionPreference = 'Stop'      ← 어떤 오류든 즉시 예외
  L32  sc.exe create        [비-CIM]  ✅ 성공
  L39  Start-Service        [SCM]     ✅ 성공 (RUNNING 실측)
  L57  Out-File Guardian    [파일]    ✅ 성공 (존재 확인)
  L60  New-ScheduledTaskAction   [CIM] ┐
  L62  New-ScheduledTaskTrigger  [CIM] ├ 32분 대기 → 예외
  L66  Register-ScheduledTask    [CIM] ┘
  L70  exit 0                            도달 못 함
```

**핵심 관측**: 같은 스크립트에서 **비-CIM은 전부 성공, CIM만 실패**.
사장님 PowerShell에서도 `Get-ScheduledTask` → `Cannot connect to CIM server` 동일 재현.

### 2-2. 설계 D-1 — CIM 제거 (정공법)

`ScheduledTasks` 모듈(CIM 기반)을 **`schtasks.exe`(비-CIM)로 전면 교체**한다.

| 현재 (CIM) | 전환 후 (비-CIM) |
|---|---|
| `New-ScheduledTaskAction` | `schtasks /Create` 인자 |
| `New-ScheduledTaskTrigger` | `/SC MINUTE /MO 5` |
| `New-ScheduledTaskPrincipal` | `/RU SYSTEM /RL HIGHEST` |
| `Register-ScheduledTask -Force` | `/F` |

> **근거**: `.iss` 다른 구간에서 `schtasks`를 이미 쓰고 있으며(L1305·L1837 등) 전부 정상 동작한다.
> 사내 검증된 방식이다. 신기술 도입이 아니라 **이미 되는 방식으로 통일**하는 것.

### 2-3. 설계 D-2 — 시간 상한 (피호출측)

`.iss`가 상한을 못 거므로 **PowerShell 스크립트 자신이** 상한을 갖는다.

| 구간 | 상한 제안 | 근거 |
|---|---|---|
| 서비스 등록(`sc create`) | 짧게 | 실측 즉시 완료 |
| 서비스 기동(`Start-Service`) | 중간 | SCM 기동 대기 필요 |
| Guardian 등록(`schtasks`) | 짧게 | 실측 즉시 완료 |
| **스크립트 전체** | **상한 필수** | 어떤 경우도 이 시간 초과 금지 |

> **구체 수치는 사장님 결재(Q-1) 후 확정.** 설계팀 권고는 "전체 상한을 두되, 고객이 멈췄다고
> 느끼지 않는 범위". 32분은 어떤 기준으로도 초과다.

**상한 구현 방식**: 각 단계를 작업(Job)으로 실행하고 상한 내 미완료 시 중단 → 다음 단계 진행.
`$ErrorActionPreference='Stop'`을 **구간별로 완화**해, 부가 단계 실패가 전체를 죽이지 않게 한다.

### 2-4. 설계 D-3 — 성공/실패 정확 판정

현재는 **스크립트 exit code만** 본다. 그래서 "서비스는 RUNNING인데 exit 1" 이 거짓 실패를 만들었다.

**전환**: exit code가 아니라 **실제 상태**로 판정한다.

```
워치독 성공 판정 = sc query HitPanWatchdog 가 RUNNING
Guardian 성공 판정 = schtasks /query 가 존재
```

각 항목을 **독립 판정**하여 부분 성공을 구분한다:

| 워치독 | Guardian | 판정 | 고객 안내 |
|---|---|---|---|
| RUNNING | 존재 | **완전 성공** | 안내 없음 |
| RUNNING | 없음 | **부분 성공** | 안내 + 본사 보고 |
| 미기동 | — | **실패** | 안내 + 본사 보고 |

### 2-5. 설계 D-4 — 진행 표시 (18분 구간)

.NET Hosting Bundle 18분·VC++ 4분 구간에 고객이 "멈췄나?" 오해한다.
`StatusMsg`에 **경과 안내**를 넣어 정상 진행임을 알린다. (기능 변경 아님, 문구 개선)

## 3. 백엔드 매니저 — 본사 선제 CS 백엔드 설계

### 3-1. 현황 (실측)

| 경로 | 상태 |
|---|---|
| 워치독 → 본사 메타핑 송신 (`MetaPingClient`) | ✅ 구현 (금지필드 27종 차단 내장) |
| 백오피스 수신 엔드포인트 | ❌ **0건** — grep 결과 없음 |
| 설치 → 본사 보고 | ❌ 없음 |

**설계 결론**: 워치독 메타핑과 설치 보고는 **같은 수신구를 공유**한다. 두 개를 따로 만들지 않는다.

### 3-2. 설계 B-1 — 수신 엔드포인트

**위치**: `HitPan.Backoffice.API` (클라우드, 헌법 #35 정합)

| 항목 | 설계 |
|---|---|
| 인증 | 시리얼 기반. ERP 로그인 토큰 사용 금지(계층 혼용 = 헌법 #7 위반) |
| 멱등 | 동일 시리얼+시각 중복 수신 시 갱신(중복 행 방지) |
| 저장 | 고객사별 **최신 상태 1행** + 이력 (CS가 추이를 봐야 함) |
| 실패 처리 | 수신 실패해도 **설치·워치독 무영향** (fire-and-forget) |

### 3-3. 설계 B-2 — 데이터 최소주의 게이트 (헌법 #22)

**수신측에서도 금지필드를 검사한다.** 송신측(`MetaPingClient`) 검사만 믿지 않는다 — 이중 방어.

```
허용 필드 (화이트리스트 — 이 외 전부 거부)
  tenant_serial, install_version, watchdog_status,
  guardian_status, tunnel_status, occurred_at

거부 시 = 400 + 로그. 저장 0건.
```

> 화이트리스트 방식을 쓴다(블랙리스트 아님). 새 필드가 실수로 들어와도 **기본 거부**.

### 3-4. 설계 B-3 — CS 조회 화면

**대상**: CS팀장(강지원) 및 본사 담당자

| 화면 요소 | 내용 |
|---|---|
| 목록 | 워치독/Guardian 미등록 고객사 |
| 정렬 | 최근 발생 순 |
| 표시 | 시리얼 · 버전 · 실패 항목 · 발생 시각 |
| 조치 | 담당자 확인 표시(중복 연락 방지) |

> **표시 금지**: 회사명·사업자번호·담당자명 등. 시리얼로만 식별(헌법 #22).
> CS가 시리얼로 고객사를 찾는 것은 기존 계정 관리 화면 몫이다 — **본 화면은 장애 상태만** 다룬다.

### 3-5. 설계 B-4 — 설치 프로그램 → 본사 보고

**설계 판단**: 설치 프로그램이 직접 HTTP를 쏘지 않는다.

| 방식 | 평가 |
|---|---|
| `.iss`에서 직접 HTTP | ✗ Inno Pascal의 HTTP는 제약이 크고 실패 처리가 빈약 |
| **PowerShell 보고 스크립트** | ✓ 기존 패턴(`AntivirusExceptions.ps1` 등)과 동일. 실패해도 무영향 |

**보고 시점**: 설치 마지막 단계. 성공/실패 **양쪽 다 보고**한다.
> 성공도 보고해야 본사가 "설치는 됐는데 보고가 안 온 고객사"(통신 자체 불가)를 구분할 수 있다.

**보고 실패 시**: 로그만 남기고 **설치는 완주**. 고객에게 추가 안내 없음(FR-3.4).

## 4. 풀스택 매니저(존) — 워치독 · 화면 격리 재설계

### 4-1. 워치독 루프 격리 (FR-4.1)

**현재** `Worker.cs:156-273` `RunOneLoopAsync` — 단계별 try/catch **0건**:

```
프로세스감시 → 터널secret → 서비스재설치 → 헬스체크 → 재부팅감지 → 업데이트평가
     ↑ 여기서 예외 나면 뒤 전부 스킵
```

바깥 catch(L146)가 프로세스는 살리지만, **그 루프의 나머지 단계는 통째로 건너뛴다.**
원인이 지속되면 뒤쪽 단계가 **영구 마비**된다. 로그도 "Watchdog loop failure" 한 줄뿐이라 범인을 모른다.

**전환**: 각 단계를 독립 실행한다.

```
Stage(프로세스감시)  → 실패해도 다음
Stage(터널secret)    → 실패해도 다음
Stage(서비스재설치)  → 실패해도 다음
Stage(헬스체크)      → 실패해도 다음
Stage(재부팅감지)    → 실패해도 다음
Stage(업데이트평가)  → 실패해도 다음
```

각 단계 실패 시: **단계명 + 원인**을 로그에 남기고 다음 단계 진행. 연속 실패는 별도 집계.

> **주의**: 이미 올바른 패턴이 같은 파일에 있다(L300-302, L408-410 업데이트 적용 구간).
> **패턴을 새로 만드는 게 아니라 메인 루프에 적용**하는 것이다.

### 4-2. 백오피스 레이아웃 격리 (FR-4.2·4.3)

**가장 위험한 지점**: `BackofficeSidebar.razor:96` `OnInitializedAsync`에 try/catch 없음.

이 컴포넌트는 **레이아웃 안**(셸)에 있다. 여기서 예외가 나면 페이지 본문뿐 아니라
**사이드바·상단바 포함 전체 렌더 트리**가 죽고, `ErrorBoundary`가 프로젝트 전체 0건이라
회로가 그대로 종료된다 → **완전 백지**.

| 대상 | 조치 |
|---|---|
| `BackofficeSidebar.razor:96` | try/catch + 기본값 유지 |
| `PlatformSidebar.razor:108` | 동일 |
| `ResellerSidebar.razor:58` | 동일 |
| 전역 | `ErrorBoundary` 적용 — 예외 시 복구 UI |

> **정답 패턴 존재**: `PlatformTopBar.razor:80-103`이 이미 try/catch + 기본값 유지로 되어 있다.
> 사이드바 3종만 누락. **사내 패턴 복사**로 해결된다.

### 4-3. 대시보드 부분 실패 허용 (FR-4.4)

`FinanceService.cs:459-614` `GetDashboardAsync` — try/catch **0건**.
쿼리 1개 실패 → **KPI 7종 + 차트 3종 전멸** → 프론트가 전 항목 0원 표시.

**설계 판단**: KPI 7종은 성능 목적으로 **의도적으로 UNION ALL 한 쿼리**로 묶여 있다(헌법 #16 정합).
이를 쪼개면 헌법 #16(MySqlConnection 병렬 금지) 위반 위험이 생긴다.

**전환**: 쿼리를 쪼개지 않고 **블록 단위로 격리**한다.

```
Try(KPI UNION 7종)   실패 → KPI만 0, 나머지 표시
Try(월별 추이)        실패 → 차트만 빈 상태
Try(거래처 TOP5)      실패 → 순위만 빈 상태
Try(최근거래)         실패 → 목록만 빈 상태
Try(안전재고 미달)    실패 → 재고만 빈 상태
```

부분 실패 시 화면에 **"일부 항목을 불러오지 못했습니다"** 표시(침묵 금지, 원칙 4).

### 4-4. 미들웨어 fail-open 통일 (FR-4.5)

같은 파이프라인에 **두 방식이 섞여 있다**:

| 미들웨어 | 현재 | 조치 |
|---|---|---|
| `SessionLimitMiddleware.cs:83` | ✅ fail-open (catch 후 `_next`) | 유지 (정답) |
| `TermsConsentMiddleware.cs:107` | ✅ fail-open | 유지 (정답) |
| `RateLimitMiddleware.cs:19-90` | ❌ try/catch 0건 → fail-closed | **fail-open 전환** |
| `HealthIpWhitelistMiddleware.cs:11` | ❌ 생성자 필드 파싱 → 전 API 500 | **안전 파싱 + fail-open** |

> 레이트리밋·IP화이트리스트는 **부가 기능**이다. 이것이 고장나서 로그인이 막히면 안 된다(원칙 3).

### 4-5. 기동 차단 — 보류 (FR-4.6)

`AuthExtensions.cs:20,29,38` (JWT 시크릿) / `Backoffice.API/Program.cs:120,127` (마이그레이션)은
실패 시 **프로세스 기동 자체를 막는다**.

**4인 공통 의견: 본 작업에서 손대지 않는다.**

사유: 약한 JWT 시크릿으로 기동을 허용하면 **보안 구멍**이다. 현재 fail-fast는
**의도된 보안 설계**일 가능성이 높다. 사장님 원칙("A만 죽는다")과 보안이 충돌하는 유일한 지점이다.

→ **보안 상무(안철수) 검토 + 사장님 결재** 후 별도 처리. (PRD Q-3)

의존관계 기준. 앞 단계 미완료 시 뒤 단계 착수 금지.

| **4** | 백오피스 레이아웃 격리 (4-2) | 풀스택 매니저 | 없음 — 독립 |
| **5** | 본사 수신 엔드포인트 (B-1·B-2) | 백엔드 매니저 | 없음 — 독립 |
| **6** | 설치 → 본사 보고 (B-4) | 네트워크+백엔드 | **5 완료 후** (수신구 필요) |

| **8** | 대시보드·미들웨어 격리 (4-3·4-4) | 풀스택 매니저 | 없음 — 독립 |
