## 1. 🔴 왜 셋을 한 문서로 묶나

**세 개가 한 자리에서 만난다.**

```
퇴직서 상신 → 결재 → 퇴사 확정
                      ├─ 사원 상태          🟢 이미 있다(§3-1)
                      ├─ 결재선에서 빼기     ← ①과 같은 자리
                      └─ 미결 회수          🟢 8/21 에 넣음
계약서 ─────→ 결재 ─┘                       ← ③이 같은 엔진을 탄다
```

⇒ 따로 하면 **같은 자리를 세 번 만진다.**
⇒ 상무님이 *"퇴사 처리 → 결재선 빼기 → 미결 회수를 **한 자리에 묶어라**"* 한 그 자리다.

## 2. 🔴 구멍 ① 결재선 2중화 — 축 중의 축

### 2-1. 실측 — 두 축이 서로를 모른다

| 축 | 표 | 누가 읽나 |
|---|---|---|
| **엔진 축** | `approval_doc_lines` | `ApprovalTriggerHelper.cs:37`·`:115` · `ApprovalService` |
| **직책 축** | `approval_line_steps` | `ApprovalLineService` · `PositionService` **뿐** |

🔴 **결재 엔진이 `approval_line_steps` 를 한 번도 안 읽는다**(참조 0건 실측).

```
approval_lines / approval_line_steps    직책·단계로 짠 결재선   ← 화면에서 만든다
                                         ✖ 안 이어짐
approval_doc_lines                       doc_type 전역 1행     ← 결재는 이것만 본다
```

⇒ **화면에서 직책으로 결재선을 짜도 실제 결재는 사람 고정 1행으로 돈다.**
   8/12 흐름설계서가 *"직급 결재선 테이블이 **엔진에 연결 안 됨**"* 이라 적은 그 자리.

### 2-2. 🔴 이것이 왜 모든 것의 뿌리인가

| 이 구멍 때문에 생기는 일 | 지금 |
|---|---|
| 부장이 바뀌면 **결재선이 죽는다** | 사람이 고정돼 있으니 |
| 부장이 퇴사하면 **그 문서종류 전체가 선다** | 상무님 *"최우선"* 지적 |
| **직권**이 매번 손으로 때우는 일이 된다 | 설3 §4-2 |
| **전결**의 `final_step_order` 가 기댈 단계가 불안하다 | 설3 §3-2 |

🔴 **직권·전결이 전부 이 축 위에 얹힌다.** 축이 안 서면 위에 얹는 것이 다 임시방편이 된다.

### 2-3. 🟢 무엇을 하나 — 배선 (표 신설 0)

**상신 시점에 `approval_line_steps` 를 읽어 `approval_doc_lines` 로 펼친다.**

```
상신
 └→ 결재선 조회   approval_line_steps (step_order · position_id · employee_id)
      ├ position_id 면 → 그 직책의 현재 재직자를 찾아 approver 로
      └ employee_id 면 → 그 사람 그대로
 └→ approval_doc_lines 로 펼침 → 기존 엔진이 그대로 돈다
```

🟢 **엔진을 안 고친다.** 엔진은 계속 `approval_doc_lines` 만 본다 ⇒ **회귀 위험 최소**.
🟢 **표 신설 0건** — 둘 다 이미 있다.

### 2-4. 🔴 직책 축의 값어치

`position_id` 로 걸면 **사람이 바뀌어도 결재선이 안 죽는다.**
⇒ 부장이 바뀌면 **새 부장이 자동으로 그 자리**에 온다.
⇒ 🟢 **직권의 필요를 줄인다** — 후임이 있으면 선이 안 끊긴다.

⚠️ **후임이 없으면** 여전히 공석 ⇒ **직권이 그때 필요**(설3).
   ⇒ 배선과 직권은 **서로를 대체하지 않는다.**

### 2-5. 🚨 착수 시 위험

| 자리 | 위험 |
|---|---|
| 🔴 기존 `approval_doc_lines` 를 **지우지 마라** | 이미 쓰는 고객이 있다(#1·#37) |
| 🔴 직책에 **재직자가 0명**일 때 | 상신이 **조용히 실패**하면 안 된다 — 사람에게 알린다 |
| 🔴 직책에 **여럿**일 때 | 누구를 고르나 — **§6 Q1** |
| ⚠️ `total_lines` 정합 | `:115` 가 세는 값과 펼친 결과가 **같아야** 한다 |

## 3. 🔴 구멍 ② 퇴직서

### 3-1. 🟢 실측 정정 — 사원 상태는 이미 제대로 된다

⚠️ **PM 이 앞서 *"`is_resigned`·`resign_reason` 을 아무도 안 채운다"* 고 보고했는데 틀렸다.**
   **옛 주석을 읽은 것**이고, 실제 코드(`EmployeeService.cs:566-575`)는 이렇게 채운다:

```sql
UPDATE employees
SET is_active = 0, is_resigned = 1,
    resign_date = COALESCE(@ResignDate, NOW(6)),
    resign_reason = COALESCE(@ResignReason, resign_reason)
```

🟢 **8/14 봉합으로 계정 자동삭제까지 들어가 있다**(사장님 *"퇴사자는 계정이 자동삭제 되도록!!!!"*).

⇒ 🔴 **퇴사 "처리" 는 멀쩡하다. 없는 것은 "직원이 올리는 문서" 다.**

### 3-2. 🔴 그래서 없는 것은 정확히 이것

| | 지금 | 필요 |
|---|---|---|
| 퇴사 **처리** | 🟢 관리자가 사원관리에서 | 그대로 |
| 퇴사 **문서**(직원 상신) | 🔴 **경로 0건** | 신규 |
| 퇴사 **결재** | 🔴 문서유형 없음 | 신규 |

⇒ 지금은 **직원이 그만두겠다고 올릴 자리가 없다.** 구두로 말하고 관리자가 처리한다.

### 3-3. 🟢 설계

```
문서유형   resignation   "사직서"
표         신설 필요 여부는 §6 Q2 (employees 칸 재사용 vs 신규 표)
상신       직원 → 퇴사희망일 · 사유
결재       기존 엔진 그대로 (①의 배선을 탄다)
승인 시    ProcessAsync 원본반영 →  EmployeeService 퇴사 처리 호출
             ├ is_resigned=1 · resign_date · resign_reason   🟢 이미 있는 로직 재사용
             ├ 계정 삭제                                      🟢 8/14 봉합 재사용
             ├ 결재선에서 빼기                                🔴 ①과 함께
             └ 미결 회수                                      🟢 8/21 에 넣음
```

🟢 **퇴사 로직을 새로 만들지 않는다.** 이미 있는 `EmployeeService` 를 **결재 승인 시점에 부른다.**

### 3-4. 🚨 위험

| 자리 | 위험 |
|---|---|
| 🔴 **대표(부모계정) 사직서** | 대표가 퇴사하면 **로그인이 잠긴다**(#38 — 복구 경로 없음) ⇒ **막아야** 한다 |
| 🔴 **승인 전에 퇴사 처리하면 안 된다** | 헌법 #6 — 확정 시점에만 |
| 🔴 **반려되면 아무 일도 안 일어나야** | 사원 상태 무변경 |
| ⚠️ 퇴직금 **정산 금액** | 🔴 **이번 범위 아님** — 회계 축(설1 §4) |

## 4. 🟡 구멍 ③ 계약서 결재 연결

### 4-1. 실측 — 화면은 있는데 서비스가 없다

| | 상태 |
|---|---|
| 화면 3개 | 🟢 목록 · 작성 · 서명(`/hr/labor-contracts*`) |
| 설계 | 🟢 8/11~8/12(ERD·PRD·기능정의서·흐름설계서) |
| **전용 서비스** | 🔴 **없다** — `labor_contracts` 를 읽는 곳이 **`ChatService` 뿐**(파일 공유용) |
| 결재 | 🔴 **안 탄다** — 문서유형 없음 |
| 상태 | `draft/sent/signed/voided` — **결재 상태와 별개로 돈다** |

### 4-2. 🟢 무엇을 하나

```
문서유형   labor_contract   "근로계약서"
상신       계약서 작성 → 상신
결재       기존 엔진 (①의 배선을 탄다)
승인 시    ProcessAsync 원본반영 → labor_contracts.status 전이
```

⚠️ **`status` 축이 두 개 겹친다** — 기존 `draft/sent/signed/voided` 와 결재 상태.
   ⇒ 🔴 **기존 축을 덮지 마라**(#1). 결재는 `approval_documents` 에서 돌고,
      계약서 상태는 **승인 후 `sent` 로 넘어가는 식**으로 잇는다 — 상세는 **§6 Q3**.

### 4-3. 🟢 이게 제일 가볍다

라벨 두 곳 + 트리거 + `ProcessAsync` 블록. **화면 신규 0건.**
