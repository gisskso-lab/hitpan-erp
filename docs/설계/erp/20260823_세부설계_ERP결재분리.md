## 1. 왜 분리하나

### ① 같은 일을 두 번 한다

ERP 워크플로에는 **확정** 이 이미 있고, 그것이 결재 자리를 한다.
확정한 문서를 결재로 또 태우면 **승인이 이중**이 된다.

### ② 결재함이 덮인다

거래명세서는 **가장 많이 나오는 문서**다. 하루 수십~수백 건이 결재함에 쌓이면
휴가·경비·보고서 같은 **진짜 사람 결재가 안 보인다.**

🔴 8/22 정본 설계에 상무님 경고가 이미 있다 — *"1번에 모으는 만큼 1번이 막히면 회사가 선다."*

### ③ 🔴 가짜 스위치가 더 위험하다 (실측)

| doc_type | 설정 화면 | 실제 트리거 |
|---|---|---|
| `delivery` 거래명세서 | 뜬다 | **있다** |
| `receipt` 매입명세서 | 뜬다 | **있다** |
| `sales_return` 매출반품 | 뜬다 | **있다** |
| `purchase_return` 매입반품 | 뜬다 | **있다** |
| `quotation` 견적서 | 뜬다 | 🔴 **0건** |
| `sales_order` 수주서 | 뜬다 | 🔴 **0건** |
| `purchase_order` 발주서 | 뜬다 | 🔴 **0건** |

⇒ 견적·수주·발주는 **켜도 아무 일이 안 일어난다.**
   고객사가 *"결재 걸었다"* 고 믿는데 **아무것도 안 걸린다.**
   8/21 휴직이 **반대 방향의 같은 병**이었다(목록에 없어서 켤 수가 없었다).

⇒ 트리거 있는 4종은 **실제로 위험**하고, 없는 3종은 **거짓말**이다. **7종 전부 뺀다.**

## 2. 🔴 실측이 설계를 정했다

### DocTypeLabels 는 **두 가지 일**을 한다

```
:15   사전 정의
:180  ← 설정 화면 목록을 만든다      ⇒ 여기서 ERP 를 걸러야 한다
:578  ← 결재 상세의 라벨을 찾아준다   ⇒ 여기서 빼면 옛 문서가 영문 코드로 뜬다
:983  ← 결재 목록의 라벨을 찾아준다   ⇒ 위와 같다
```

🔴 **사전에서 지우면 안 된다.** 지우면 이미 있는 ERP 결재 문서가
`GetValueOrDefault(docType)` 폴백을 타서 화면에 **`delivery` 같은 영문 코드**가 뜬다
(고객 노출 개발용어 금지). 500 이 안 나고 **조용히** 영문이 보인다.

⇒ **사전은 살리고, 목록 만들 때만 거른다.**

### 지금 도는 ERP 결재는 0건 (터널 실측)

```
pending    []
sent       []
completed  []
```

⇒ **갑자기 끊길 문서가 없다.** 헌법 #20(워크플로 안 끊긴다) 위반 없이 지금 뺄 수 있다.
⚠️ 다만 코드는 **도는 문서가 있어도 안전하도록** 짠다 — 다른 고객사는 다를 수 있다.

## 3. 무엇을 하는가

### [A] ERP 7종을 결재 설정 목록에서 뺀다

`GetSettingsAsync` 가 `DocTypeLabels` 를 순회할 때 **그룹웨어 것만** 담는다.

```
ErpDocTypes = { quotation, sales_order, delivery, purchase_order,
                receipt, sales_return, purchase_return }
```

- 🔴 **사전은 그대로 둔다** — 라벨 찾기가 계속 돌아야 한다(§2)
- 🔴 **표(`approval_settings`)의 기존 행도 안 지운다** — 헌법 #1·#37.
      안 읽히는 것과 잔재는 다르다. 나중에 되돌릴 수도 있다.

### [B] ERP 트리거 4곳을 끊는다

| 파일 | 위치 | doc_type |
|---|---|---|
| `SalesService` | 2곳 | `delivery` · `sales_return` |
| `PurchaseService` | 2곳 | `receipt` · `purchase_return` |

- 🔴 **`FinanceService` 의 `expense` 는 건드리지 않는다** — 경비는 **그룹웨어**다.
      사장님 지시 2번이 경비를 지출결의서로 결재 태우라는 것이다.
- 🔴 **확정 로직 자체는 손대지 않는다.** 결재 호출만 뺀다.
      확정이 승인이라는 축은 그대로다.

### [C] 이미 있는 ERP 결재 문서는 살린다

- 결재함 조회·상세는 **그대로** 둔다. 라벨도 정상으로 뜬다.
- 진행 중인 것이 있으면 **끝까지 갈 수 있다**(승인·반려 경로 무변경).
- ⇒ **신규만 막고, 있던 것은 흐르게 한다.**

### [D] 🔴 창구 통합에 **빠진 것을 채운다** (사장님 지시)

> *"결재목록 그룹웨어에서 **창구 하나로 통합**하기 위해서 **추가 해야 되는 부분들 추가**하고,
>  뺴야되는 ERP영역은 모두 빼"*

**빼기만 하면 창구가 안 선다.** 사장님 필터2(`보고서·휴가·휴직·경비신청·입사퇴사`)와
현재 결재종류를 대조하면 **2종이 비어 있다.**

#### 실측 대조

| 사장님 필터2 | 현재 doc_type | 상태 |
|---|---|---|
| 보고서 | `report_daily`·`report_weekly`·`report_monthly`·`report_incident` | 🟢 있음 |
| 휴가 | `leave` | 🟢 있음 |
| 휴직 | `absence` | 🟢 있음 |
| 경비신청 | `expense` | 🟢 있음 |
| **입사퇴사** | — | 🔴 **없다** |
| (초과근무) | `overtime` | 🟢 있음 — 지시 7번이 근태로 합치라 함 |
| **전자근로계약서** | — | 🔴 **없다** (지시 12번: *"작성 후 결재로 이동"*) |

#### 채울 것 2종

| doc_type | 라벨 | 근거 | 현재 상태 |
|---|---|---|---|
| `resignation` | 사직서 | 지시 15번 **입사퇴사** 메뉴 | 🔴 화면·표 **전부 없음** |
| `labor_contract` | 전자근로계약서 | 지시 12번 | 🟢 **화면 3개 이미 있음**<br>(`LaborContractCreate/List/Sign`)<br>🔴 **전용 서비스가 없다** |

🔴 **계약서는 신규가 아니라 배선이다.** 화면 3개와 `labor_contracts` 표가 이미 있고
**결재로 넘기는 연결만 없다.** 8/22 정본 설계에도 같은 판정이 있다 —
*"계약서: 화면·설계 이미 있고 전용 서비스만 없다."*

⚠️ **사직서는 진짜 신규다.** 다만 **퇴사 처리는 멀쩡히 있다**(`EmployeeResignDialog`·`ResignAsync`).
   없는 것은 **직원이 올리는 문서** 쪽이다. 8/22 설계 판정 그대로다.

#### 🔴 이 단계에서 어디까지 하나 — 경계

| | 이번 ① | 나중 |
|---|---|---|
| `DocTypeLabels` 에 2종 **등재** | 🟢 한다 | |
| 결재 설정 화면에 **행이 뜨게** | 🟢 한다 | |
| 결재선을 **짤 수 있게** | 🟢 한다 | |
| 상신 트리거(화면→결재) | | ⏸ **G3** |
| 사직서 화면·표 신설 | | ⏸ **⑤ 신규 메뉴** |

**왜 등재부터 하나** — 8/21 휴직 P0 가 정확히 그 반대였다.
`AbsenceService` 는 처음부터 `absence` 로 상신을 불렀는데 **사전에 없어서**
설정 화면에 행이 안 떴고 ⇒ 켤 방법이 없고 ⇒ 상신이 조용히 죽었다.
**화면은 버튼을 보여주는데 눌러도 아무 일이 없었다.**

⇒ **사전 등재가 먼저다.** 트리거를 먼저 붙이면 같은 사고가 난다.

### 하지 않는 것

- 🔴 `DocTypeLabels` 에서 ERP 항목 **삭제** — 라벨이 죽는다
- 🔴 `approval_settings` 표의 기존 행 **삭제** — #1·#37
- 🔴 확정 로직 **변경** — 이번 범위 아님
- 🔴 `expense` **제거** — 경비는 그룹웨어다
- 🔴 사직서 **화면·표 신설** — ⑤ 신규 메뉴에서 (여기선 **등재만**)
- 🔴 계약서 **상신 트리거** — G3 에서 (여기선 **등재만**)
- ⏸ 결재 필터(②) · 경비 지출결의서(③) — 다음 단계
