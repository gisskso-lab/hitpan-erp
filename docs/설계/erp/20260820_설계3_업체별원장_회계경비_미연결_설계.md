## 1. 답 — **연결 안 되어 있다.**

`Partners/PartnerLedgerPage.razor:96` 이 부르는 API 는 **딱 하나**:
```
api/reports/stock-ledger?view=partner
```
⇒ 이것은 **재고 수불부**다. 물건이 들고 난 기록이지 **돈 기록이 아니다.**
   `journal_lines`(회계 원장)도 경비도 **부르지 않는다.**

🔴 그래서 화면 이름은 *"업체별 원장"* 인데 **채권·채무 잔액이 없다.**
   *"이 업체에 얼마 받을 게 남았나"* 를 이 화면에서 알 수 없다.

## 3. 🔴🔴 연결 축 전수 점검 결과 (사장님 지시 *"제대로 점검할 것"*)

> 사장님: *"수불부는 **회계, 재고 연결 축 제대로 점검**할 것"*
> ⇒ 화면만 보지 않고 **두 원장이 실제로 이어지는지 DB 로 실측**했다. (헌법 #39 — SELECT 만)

### 3-1. 🔴 **결론: 재고와 회계는 지금 한 건도 안 이어진다**

```sql
SELECT COUNT(*) FROM stock_ledger sl
  JOIN journal_entries je ON je.source_id = sl.source_id AND je.tenant_id = sl.tenant_id;
⇒ 0                          ← 🔴 양방향 모두 0 (두 번 확인)
```

| 축 | 값 |
|---|---|
| `stock_ledger` 총 행 | **115,460** (`partner_id` 채워짐 **115,391** 🟢) |
| `journal_lines` 총 행 | **23,994** (`partner_id` 채워짐 **0** 🔴) |
| `stock_ledger` 문서 수 | 113,306 |
| `journal_entries` 문서 수 | 5,832 |
| **두 원장이 이어지는 건수** | 🔴 **0** |

### 3-2. 🔴 왜 0 인가 — **`source_id` 형식이 서로 다르다**

| 원장 | source_id 실제 값 |
|---|---|
| `stock_ledger` | `mig-00000000-0` · `mig-20000103-1` |
| `journal_entries` | `mig-docf7-20000401-0000` |

⇒ **애초에 만나도록 만들어지지 않았다.** 같은 거래인데 **서로 다른 이름표**를 달고 있다.
   JOIN 을 어떻게 짜도 0 이다. 🔴 **화면·쿼리로는 절대 못 푼다.**

### 3-3. 진범은 마이그레이션 **두 곳**

| # | 자리 | 무엇 |
|---|---|---|
| ① | `MdbMigrationService.cs:4999` | `PartnerId = null` **하드코딩** ⇒ 회계에 업체가 통째로 없다 |
| ② | 같은 파일 (재고·회계 각각의 `source_id` 생성) | 두 원장이 **다른 규칙**으로 이름표를 만든다 |

⚠️ 운반 경로(staging → INSERT `:5248`·`:5348`)는 `partner_id` 를 **정상적으로 나른다.**
   **출발점에서 비운 것**이다.

### 3-4. 🟢 **앞으로 생기는 실거래는 이어진다** (코드 확인)

실사용 경로는 **같은 문서 ID 를 양쪽에 쓴다**:
- `SalesService.cs:508` 재고/요약 `sourceId: delivery.DeliveryId`
- `SalesService.cs:514` 회계 `AutoJournalHelper.RecordSalesConfirmAsync(… delivery.DeliveryId)`
⇒ 🟢 **같은 열쇠**다. 이 경로로 들어온 자료는 JOIN 이 된다.

⚠️ **단 실측으로 확인하지 못했다** — demo DB 는 `source_type` 이 **전부 `migration`** 이라
   이 경로가 **아직 한 번도 안 돌았다.** 코드로만 확인했다. **실거래 1건으로 검증 필요**(§8).

### 3-5. ⚠️ 추가 발견 — `stock_ledger` INSERT 마다 컬럼이 다르다

`INSERT INTO stock_ledger` **10곳** 중 `partner_id` 를 **넣는 곳은 7곳**뿐이다.
`StockService.cs:210`(조정)·`BomService.cs:549` 등은 **업체를 안 넣는다.**
⚠️ 조정·BOM 은 업체가 없는 거래라 **정상일 수 있다.** 그러나 **확인 없이 "정상" 으로 넘기지 마라** — §8.

### 3-6. ⚠️ JOIN 이 느리다 (성능)

`source_id` JOIN 한 번에 **5분 이상**(300s 타임아웃). `stock_ledger.source_id` 에 **인덱스가 없다.**
⇒ 화면에서 이 JOIN 을 그대로 쓰면 **업체별 원장이 안 뜬다.** 인덱스 추가가 **선행**이다(§8).

## 4. 그래서 두 갈래다

### 4-A. **앞으로 생기는 자료** (AutoJournalHelper 경로)
`AutoJournalHelper` 는 `partnerId` 를 받게 되어 있다.
⚠️ **호출부가 실제로 업체를 넘기는지 확인 필요** — 판매·매입 기표 각 지점 전수 조사.
⇒ 넘기고 있으면 🟢 손댈 것 없음. 안 넘기면 그 자리만 채운다.
⚠️ 현재 DB 에 `source_type='migration'` 외 자료가 **0건**이라 **이 경로는 아직 한 번도 안 돌았다.**
   (demo 는 마이그레이션만 하고 실거래를 안 넣은 상태) ⇒ **실측으로 확인 못 했다. 코드로만 확인한다.**

### 4-B. **이미 들어온 레거시 23,994 라인** 🔴
`partner_id` 를 되채우려면 **레거시 DOCF7 에 업체 정보가 있는지**부터 봐야 한다.
- 있으면 → 마이그레이션 코드 수정 + **재적재**
- 없으면 → 🔴 **레거시에 없는 것은 만들어내지 않는다**(마이그 무결성 — *"레거시와 숫자가 맞는다"* 가 합격선)

🔴 **헌법 #3 — `journal_lines` 는 INSERT ONLY.** UPDATE 로 되채우면 **원장 훼손**이다.
   재적재는 `DataResetService` 계열의 **정식 경로**로만 한다(§18 예외 조항 확인 필요).
⚠️ **이 판단이 이 설계의 최대 리스크다.** 사장님 결재 없이 손대지 않는다.

## 5. 설계 — **수불부(재고)와 회계를 워크플로우 축으로 잇는다** (사장님 지시)

> 🔴 사장님 원문 (2026-08-20):
> *"수불부에는 재고, **회계 축의 워크플로우와 연결, 적용**되야 함"*

### 5-1. 무엇을 이으라는 것인가

지금 **한 거래가 두 갈래로 갈라져 서로 안 만난다:**

```
매입/판매 확정
   ├─→ stock_ledger   (물건이 움직인 기록)   → 수불부 화면 🟢 있다
   └─→ journal_lines  (돈이 움직인 기록)     → 업체별 원장 ❌ 없다
```

**같은 거래인데 두 기록이 화면에서 만나지 않는다.**
⇒ *"이 업체에 물건은 얼마나 나갔고, 돈은 얼마나 받을 게 남았나"* 를 **한 화면에서 못 본다.**

🔴 사장님 지시는 **이 둘을 워크플로우 축(= 같은 거래)으로 묶으라**는 것이다.

### 5-2. 무엇으로 잇나 — **이미 열쇠가 있다**

| 잇는 열쇠 | 상태 |
|---|---|
| `journal_entries.source_type` + `source_id` | 🟢 있다 (거래 종류·원본 문서 번호) |
| `journal_lines.partner_id` + `idx_jl_partner` | 🟢 컬럼·인덱스 둘 다 있다 |
| `stock_ledger` 의 거래 참조 | ⚠️ **조사 필요**(§8) |

⇒ 🟢 **DDL 변경 0 가능성이 높다.** 없는 것을 만드는 게 아니라 **안 잇고 있던 것을 잇는다.**
⚠️ 다만 §3 실측대로 **`partner_id` 가 전부 NULL** 이라, 열쇠는 있는데 **값이 없다**(§4).

### 5-3. 화면 설계 — 한 화면에 두 축

**현행 수불부를 치우지 않는다**(헌법 #1). 쓰는 사람이 있다. **더하는 것**이다.

```
[업체별 원장]  업체: (주)○○
┌────────────────────────────────────┐
│ 채권 잔액 ○○원 · 채무 잔액 ○○원  │ ← 회계 (신규)
├────────────────────────────────────┤
│ [거래내역(돈)] [수불부(물건)]        │ ← 탭
└────────────────────────────────────┘
```

🔴 **두 탭은 같은 거래를 서로 다른 눈으로 본 것**이다 — 한 거래를 골라 **양쪽을 오갈 수 있어야** 한다.
   그것이 사장님이 말한 *"워크플로우와 연결"* 이다. 나란히 두기만 하는 것은 연결이 아니다.

### 5-4. 🔴 경비는 선행 조건이다

사장님이 *"경비"* 를 함께 물으셨다. 메모리 이월 건 *"경비는 회계 정본에 연결만"* 과 같은 자리다.
**판매·매입·BOM 은 이미 기표되는데 경비만 빠져 있다.**
⇒ 경비가 회계에 안 들어가면 **업체별 원장에도 안 잡힌다.** 🔴 **이 건보다 먼저 봐야 한다.**

### 🔴 실거래 1건 검증이 가장 먼저다
demo DB 는 **전부 마이그레이션분**이라 실사용 경로가 한 번도 안 돌았다.
⇒ **매입 1건·판매 1건을 실제로 넣어** 두 원장이 이어지는지 본다.
   이어지면 **문제는 레거시분에 한정**되고, 안 이어지면 **실거래 경로도 고쳐야 한다.**
   ⚠️ 이 확인 전에는 **범위를 확정할 수 없다.**
