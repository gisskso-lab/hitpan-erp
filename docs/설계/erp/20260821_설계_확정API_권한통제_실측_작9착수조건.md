## 1. 왜 이걸 먼저 봤나

인수인계서 §4-4 가 작9 착수조건을 이렇게 걸어두었다:

> 🔴 **확정 API 권한 통제 실측이 먼저다.** 확정에 권한 검사가 없는데 결재까지 빼면
> **아무 통제 없이 확정되는 자리**가 생긴다 ⇒ 별건 P0.

사장님 결재(지시 7)는 *"판매확정·구매확정은 암묵적인 결재기능"* 이었다.
즉 **확정이 곧 승인**이므로 결재를 뺀다. 이 전제가 성립하려면
**확정 자체가 승인만큼 통제**돼 있어야 한다. 그것을 실측했다.

## 2. 실측 결과 — 확정 계열 전수

| # | 엔드포인트 | 클래스 정책 | 개별 권한 | 판정 |
|---|---|---|---|---|
| 1 | `POST /api/sales/deliveries/{id}/confirm` | `SalesOnly` | **없음** | 🔴 |
| 2 | `POST /api/sales/deliveries/bulk-confirm` | `SalesOnly` | **없음** | 🔴 일괄이라 영향 큼 |
| 3 | `POST /api/sales/returns/{id}/confirm` | `SalesOnly` | `Authorize(SalesManager)` | 🟢 유일 |
| 4 | `POST /api/purchase/returns/{id}/confirm` | `PurchaseOnly` | **없음** | 🔴 |
| 5 | `POST /api/purchase/receipts/{id}/confirm` | `PurchaseOnly` | **없음** | 🔴 |

측정 방법: `SalesController.cs` · `PurchaseController.cs` 의 확정 메서드 바로 위
attribute 를 **직접 열어서** 확인. grep 요약이 아니라 원문 라인을 읽었다.

### 2-1. 클래스 정책은 권한이 아니라 "부서 칸막이"다

`SalesOnly` / `PurchaseOnly` 는 **판매 모듈에 들어올 수 있나**를 가른다.
**확정할 수 있나**를 가르지 않는다.

🔴 **[3-V] 반증 시도가 오히려 근거를 굳혔다.** 정책 본문을 열어보니(`Program.cs:335-343`):

```
SalesOnly     → system_admin, sales_manager, ★sales_user★, TenantAdmin, tenant_admin
SalesManager  → system_admin, sales_manager,               TenantAdmin, tenant_admin
PurchaseOnly  → system_admin, purchase_manager,            TenantAdmin, tenant_admin
```

**`sales_user` 가 `SalesOnly` 에는 있고 `SalesManager` 에는 없다.**
⇒ 두 정책의 차이가 정확히 **일반 판매담당자 한 칸**이다.
⇒ `sales_user` 는 지금 **거래명세서를 확정할 수 있고**(#1·#2),
   **판매반품만 못 한다**(#3). 같은 확정 행위인데 갈린다.

확정은 헌법 #6 에 따라 **원장이 움직이는 시점**이다.

### 2-2. #3 만 다르다는 게 방증이다

5개 중 판매반품 확정 하나만 `SalesManager` 를 요구한다.
같은 성격의 행위에 통제가 제각각이라는 뜻이고,
**#3 이 옳고 나머지 4개가 빠진 것**으로 읽는 게 자연스럽다.

## 3. 작9 를 지금 하면 무슨 일이 나나

```
현재:  확정(통제 약함)  +  결재(통제 있음)   → 결재가 뒷문을 막고 있다
작9후: 확정(통제 약함)                        → 막는 게 아무것도 없다
```

결재 7종을 빼는 순간 **#1·#2·#4·#5 는 부서 접근권만으로 원장이 움직인다.**
특히 **#2 는 일괄**이라 한 번에 다량이 확정된다.

⇒ 이것은 작9 의 부작용이 아니라 **작9 의 전제가 아직 성립하지 않은 것**이다.

## 4. 건의 — 선후 교체

| 순서 | 작업 | 비고 |
|---|---|---|
| **선** | 확정 4곳에 권한 부여 (**작11** 신설 제안) | 작9 의 전제를 만든다 |
| 후 | 작9 ERP 7종 제거 | 전제 성립 후 |

🔴 **권한 코드명·기본 ON/OFF 는 PM 이 정하지 않는다.** 사장님 결재 사항이다.
사장님 확정 원칙(#11 · 예외처리 축)은 *"권한이 예외 · 기본 OFF · 고객사가 켠다"* 였다.
다만 확정 권한을 기본 OFF 로 두면 **기존 고객이 확정을 못 하게 되는 회귀**가 생긴다.
⇒ **기본값이 무엇이어야 하는지 질의 필요(U2).**
