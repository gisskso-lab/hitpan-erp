## 1. 업체주소 — 좌표가 안 찍히는 진짜 이유

### 현상
카카오맵은 뜨지만 **해당 주소 위치에 핀이 안 꽂힌다.**

### 원인 (실측)
`PartnerDetail.razor:171` — 주소 **문자열**을 좌표 자리에 넣고 있다.

```
kakaomap://route?ep={주소문자열}&by=CAR
https://map.kakao.com/link/to/{업체명},{주소문자열}
```

카카오 URL 스킴 규격상 두 파라미터 모두 **좌표(위도,경도)** 를 요구한다:
- `kakaomap://route?ep={lat},{lng}`
- `map.kakao.com/link/to/{name},{lat},{lng}`

주소 문자열을 넣으면 파싱에 실패하고, 앱·웹은 **좌표 없이 기본 위치(지도 첫 화면)로 열린다.**
⇒ "맵은 뜨는데 좌표가 안 찍힌다" 는 증상과 정확히 일치한다.

부수 원인: `partners` 에 **위도·경도 컬럼이 없다.** 좌표를 넣고 싶어도 보관할 자리가 없다.

### 설계
1. `partners` 에 `latitude` · `longitude` DECIMAL 컬럼 추가 (DB-105)
2. **우편번호 찾기 시점에 좌표를 함께 확보** — 다음 절 판정 참조
3. 네비 링크는 좌표가 있으면 좌표로, 없으면 **현행 주소 폴백 유지** (헌법 #20 — 끊김 금지)

### 좌표 확보 방식 — 판정

| 안 | 방식 | 키 | 판정 |
|---|---|---|---|
| A | 카카오 REST 지오코딩 API 서버 호출 | REST 키 필요 | ❌ 키 발급 + 본사 경유 = #18 위반 소지 |
| B | **Daum 우편번호 서비스가 내려주는 좌표 사용** | **키 불필요** | ✅ **채택** |
| C | 카카오맵 JS SDK 지오코더 | JS 키 필요 | △ 예비 |

**B 채택 근거**: 이미 쓰고 있는 `openDaumPostcode` 가 주소 선택 시 좌표를 함께 반환한다.
**추가 키 0건, 추가 외부 호출 0건, 본사 경유 0건** — 헌법 #18·#22 무위반.
좌표를 못 받는 주소는 `NULL` 로 두고 현행 주소 폴백이 받는다.

> ⚠️ 미확인: Daum 우편번호가 모든 주소에 좌표를 주지는 않는다. 실측에서 좌표 획득률을 측정하고,
> 미획득이 많으면 C안(JS SDK 지오코더)을 예비로 올린다. **좌표가 없어도 현행 동작은 안 죽는다.**

## 4. 자동발주·자동매입확정 중복 (P0 — 사장님 실측 지적)

### 현상
> "자동발주 클릭한 항목은 중복으로 자동발주 하지 않도록 자동발주 메시지 항목에서 사라지기"

### 원인 (실측 — 두 경로가 다르게 동작한다)

**BOM 경로** `BomService.OrderAlertAsync` — ✅ 정상
- `stock_alerts.status` 로 상태 관리
- `if (alert.Status != "pending") throw` — 재발주 차단
- 목록은 `status='pending'` 만 조회 ⇒ **발주한 항목은 사라진다**

**판매 경로** `SalesService.GetAutoOrderCandidatesAsync` — ❌ 멱등 없음

```
WHERE 재고 <= 안전재고 OR 재고 <= 0     ← 실시간 재고만 본다
```

**이미 발주한 사실을 조회에 반영하지 않는다.**
발주해도 물건이 실제 입고되기 전까지 재고는 그대로 → **다음 거래명세서 확정 때 같은 품목이 또 후보로 뜬다.**

`purchase_orders.is_auto=1` 을 **쓰기는 하는데 읽지 않는다** (DB-36 주석은 목록 노출 차단 용도만 언급).

### 설계 — 미결 발주 제외

후보 조회에 **"이미 열려 있는 자동발주가 있으면 제외"** 를 추가한다.

```sql
AND NOT EXISTS (
      SELECT 1 FROM purchase_order_items poi
        JOIN purchase_orders po ON po.po_id = poi.po_id AND po.tenant_id = poi.tenant_id
       WHERE poi.tenant_id = i.tenant_id
         AND poi.item_id   = i.item_id
         AND po.is_auto    = 1
         AND po.status IN ('draft','ordered','partial')  -- 미결 = 아직 입고 안 끝난 발주
         AND po.is_deleted = 0
    )
```

**판정 근거**:
- `draft`·`ordered`·`partial` = 발주했으나 입고가 안 끝남 ⇒ 재고에 아직 안 잡힘 ⇒ **중복 발주 위험 구간**
- 🔴 **`partial` 포함이 핵심** — 부분입고는 남은 수량이 여전히 미결이다. 빼면 부분입고 건이 다시 후보로 떠 중복 발주가 난다
- `received` 는 입고 완료 ⇒ 재고가 올라가 자연히 후보에서 빠진다 ⇒ 제외 불필요
- `cancelled` · `is_deleted=1` 은 제외 대상이 아니다 ⇒ **다시 발주할 수 있어야 한다** (헌법 #20)

**자동매입확정도 동일** — 후보가 안 뜨면 자동 사슬도 안 돈다. 같은 필터가 양쪽을 함께 막는다.

### ✅ DESCRIBE 실측 완료 (헌법 #13) — 설계 2건 교정됨

```
status     enum('draft','ordered','partial','received','cancelled')  NOT NULL DEFAULT 'draft'
is_deleted tinyint(1) NOT NULL DEFAULT 0
```

**교정 1 — `partial` 누락**: 초안은 `IN ('draft','ordered')` 였다. 실측 enum 에 `partial`(부분입고)이 있다.
부분입고는 **남은 수량이 미결**이므로 반드시 포함해야 한다. 빠뜨렸으면 부분입고 건에서 중복 발주가 그대로 재발했다.

**교정 2 — `is_deleted` 실재**: 컬럼이 존재하므로 `is_deleted = 0` 조건을 확정 반영한다.

> ⚠️ 표기 주의: enum 은 `cancelled`(L 2개)인데 코드 일부 문자열은 `canceled`(L 1개)를 쓴다.
> 신규 쿼리는 **enum 철자를 따른다.** (본 필터는 취소를 제외 대상에서 빼므로 직접 영향은 없다)

## 5. 기본창고 — 코드리뷰 결과 (사장님 지적 확인)

### 사장님 지적
> "상품마스터, bom에 등록된 기본창고 → 기본창고 설정하면 발주, 매입이 안되는거 같은데 코드리뷰 요청"

### 리뷰 결과 — 지적이 맞다. 원인은 예상과 다르다.

**`ItemDetail.razor:121` — 코드에 그대로 적혀 있다**

```csharp
private string? _selectedWarehouseId; // 참조용 — DB에 저장하지 않음
```

기본 창고 드롭다운은 **아무것도 저장하지 않는다.**
`items` 테이블 실측 40컬럼 — **창고 컬럼이 없다.** 저장 버그가 아니라 **저장할 자리가 없다.**

**발주·매입이 실제로 쓰는 창고**

```sql
SELECT warehouse_id FROM warehouses
 WHERE tenant_id=@T AND is_active=1
 ORDER BY (CASE WHEN wh_code IN ('MAIN','WH-MAIN') THEN 0 ELSE 1 END), wh_code
 LIMIT 1
```

테넌트 단위 폴백. **품목별 기본창고는 조회조차 하지 않는다.**

⇒ 기본창고를 설정해도 **아무 변화가 없다.** 화면이 사용자에게 거짓말을 하고 있다.

### 부가 발견 — "발주·매입이 안 된다" 의 다른 원인

활성 창고가 하나도 없으면 `"등록된 창고가 없습니다."` 예외로 **매입 확정이 중단된다.**
사장님이 보신 것이 이 오류라면 원인은 기본창고가 아니라 **창고 미등록**이다. 실측에서 분리 확인이 필요하다.

### 설계 — 🔴 사장님 결재 필요

| 안 | 내용 | 장 | 단 |
|---|---|---|---|
| **A** | `items.default_warehouse_id` 추가 + 발주·매입이 우선 사용 | 설정한 대로 동작 = 기대와 일치 | DDL + 출하DDL 동반 (#36) |
| B | 드롭다운 제거 | 거짓말 제거, 최소 변경 | 품목별 창고 지정 불가 |

**설계팀 권고: A안.**
근거 — 사장님이 "설정하면 발주·매입이 안 된다" 고 하신 것은 **설정이 동작하기를 기대하신 것**이다.
B안은 기대 자체를 없애는 것이라 오더의 의중(#33)과 어긋난다.

**A안 적용 시 창고 결정 순서** (헌법 #20 — 어느 단계에서도 안 끊긴다):

```
1. 발주·매입 라인에 직접 지정된 창고
2. items.default_warehouse_id        ← 신규
3. 테넌트 기본창고 (MAIN 우선)        ← 현행 폴백 유지
4. 없으면 명확한 오류                 ← 유령창고 기록 원천차단 (현행 유지)
```

현행 폴백을 **지우지 않고 앞에 한 단계 얹는다** (헌법 #1).
