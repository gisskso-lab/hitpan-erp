## §1 [문제] 무엇을 푸는가

- **지금**: 재고 조정 `StockService.cs:186` · 이관 `:326` 은 요청 `ItemId` · `WarehouseId` · `FromWarehouseId` · `ToWarehouseId` 를 그대로 `:216` · `:245` · `:360` · `:383` · `:406` · `:417` 에 쓴다. 매입 · 판매 · 반품 · 배송 묶음 9 입구도 줄 `WarehouseId` 를 그대로 저장하고 확정이 원장으로 옮긴다([1-V] §3 표).
- **결과**: 피해 회사 자료는 안 바뀐다(모든 SQL 에 `tenant_id`). 그러나 **내 회사 원장에 유령 창고 · 유령 품목 행**이 생기고 INSERT ONLY · 외래키 0 이라 지울 길이 없다. 아무 문자열이면 되므로 「없는 id」 가 더 쉬운 길([1-V] §5).
- **목표**: 저장 입구에서 **쓰기 전에** 「내 회사 · 쓰는 중인 창고」 와 「내 회사 품목」 만 통과시킨다. 정상 화면 사용자는 아무것도 못 느낀다(화면 목록이 이미 같은 기준 · `WarehouseController.cs:47-48`).

## §2 [공용 함수] `WarehouseTenantGuard`

**2-1 위치 · 꼴** — 새 파일 `src/HitPan.Application/Services/WarehouseTenantGuard.cs` · `public static class`(API 프로젝트 `DeliveryBatchService` 도 부름 · `ItemTenantGuard.cs` 와 같은 폴더 · 같은 꼴).

```
public const string NotUsableWarehouseMessage = (§2-3 문구);
public static Task EnsureWarehousesUsableAsync(
    IDbConnection db, string tenantId, IEnumerable<string?> warehouseIds,
    IDbTransaction? tx, CancellationToken ct)
```
- 인자 기본값(선택 인자) 0 — 반사로 부르는 게이트가 깨진 선례(메모리 「반사 함수 인자」) · 모든 호출이 5 인자를 다 씀.

**2-2 순서**
1. `ThrowIfNull(db · warehouseIds)`.
2. **null · 빈 · 공백만** 인 id 는 뺀다 — 매입 · 판매 · 반품은 「빈 칸 = 서버가 기본창고 채움」 길(`PurchaseService.cs:144-169` · `WarehouseResolver.cs:63-75` · 반품 확정 기본창고)이라 보존. 재고 길은 §3 이 먼저 거절.
3. 빈 아닌 id 가 **앞뒤 공백을 가지면 거절**(`id != id.Trim()`) — 자르지 않는다. 까닭: 서비스는 원래 값을 저장하는데(`WarehouseResolver.cs:64` 원값 반환 · `StockService.cs:227` 바인딩) 자른 값으로 검사하면 앞 공백 id 가 통과해 유령 행이 된다(F-8). 끝 공백도 거절해 C# 셈 ↔ 콜레이션(PAD SPACE) 셈 어긋남을 없앤다.
4. `Distinct(StringComparer.OrdinalIgnoreCase)` — 표 콜레이션 `utf8mb4_unicode_ci`(출하 DDL `warehouses` :4599) 와 셈을 맞춤.
5. 남은 수 0 → DB 안 감 · 돌아감.
6. `tenantId` 비면 거절(#2 · 조용히 통과 금지).
7. **한 번 묻는다** — `SELECT COUNT(*) FROM warehouses WHERE tenant_id = @TenantId AND is_active = 1 AND warehouse_id IN @Ids`(Dapper 목록 펼침 · #16 `Task.WhenAll` 0 · PK `warehouse_id` 라 셈 = 서로 다른 행).
8. 셈 ≠ 남은 수 → `throw new InvalidOperationException(NotUsableWarehouseMessage)`.

- 칸 대조(#13 · 출하 DDL 로 갈음): `warehouses` = `warehouse_id varchar(36) PK` · `tenant_id varchar(36) NOT NULL` · `is_active tinyint(1) NOT NULL`(`installer/hitpan_db_clean.sql:4583-4599`). 새 칸 · 표 · 인덱스 0 → 마이그 0.
- catch 0(#15) · 로그 = 전역 미들웨어 `LogWarning` 그대로.

**2-3 문구(상수 1)** — 「사용할 수 없는 창고가 들어 있어 저장할 수 없습니다. 창고를 다시 골라 주세요.」
- 다른 회사 창고 · 없는 창고 · 쉬게 한 창고를 가르지 않음(다른 회사 창고 id 유무 단서 0). 「사용할 수 없는」 = 쉬게 한 내 창고에도 맞는 말(Q3).

**2-4 잠금 · 트랜잭션(후4 교훈)**
- **잠금 없음**(`FOR UPDATE` · `LOCK IN SHARE MODE` 0) — `ItemTenantGuard` 와 같음. 검사와 쓰기 사이에 창고가 쉬게 되어도 남는 행은 「내 회사 실재 창고」 를 가리켜 유령이 아님. 공유 잠금은 관리자의 창고 수정을 트랜잭션 동안 막아 득보다 해.
- **연결에 트랜잭션이 열려 있으면 반드시 `tx` 를 넘긴다** — 후4 교훈(트랜잭션이 열린 연결에서 `tx` 없이 명령 = MySqlConnector 「active transaction」 예외 · 후1 §15 K9 · 런 45882896312). 이번 자리는 W10 만 트랜잭션 안(`DeliveryBatchService.cs:32` → `tx` 넘김) · 나머지는 모두 `BeginTransaction` **앞**이라 `null`(§4 표 「tx」 칸).
