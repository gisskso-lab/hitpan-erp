## §1 무엇이 고장났나 — 확정 사실만

```
SealKey    TpmKeyService.cs:78  Provider = CngProvider.MicrosoftPlatformCryptoProvider
           :79  KeyCreationOptions = OverwriteExistingKey
           :83  CngKey.Create(Rsa, KEY_NAME, keyParams)         → TPM 금고에 만든다
UnsealKey  TpmKeyService.cs:111 CngKey.Exists(KEY_NAME)          → 1인자 = Software 금고
           :113 CngKey.Open(KEY_NAME)                            → 1인자 = Software 금고
KEY_NAME   TpmKeyService.cs:35  "HitPan.TaxInvoice.MasterKey"    → 상수 하나뿐
```

PM 동작 실측(선행검증 §PM): Software 금고에만 만든 키가 `Exists(name)`=True · `Exists(name, Platform)`=**False**.
⇒ **공급자별로 키 공간이 완전히 분리된다.** 이름이 같아도 건너편은 못 본다.

그래서 일어나는 일:
`Exists` false → `TpmKeyService.cs:118` DPAPI LocalMachine 으로 **TPM RSA 암호문**을 풀려다 실패
→ `:123` CurrentUser 폴백도 실패 → 예외가 밖으로 나간다
→ `MainPcProofService.cs:137-146` 이 그 예외를 **`DifferentPc`** 로 흡수한다
→ `:171-174` **출입증을 안 준다** → `MainPcOnlyAttribute.cs:95-111` 이 403 `main_pc_only`.

🔴 여기서 더 나쁜 것: `:139` 주석이 *"오류가 아니라 정상 경로다"* 라고 적혀 있다.
⇒ **모든 해제 실패가 「컴퓨터가 바뀌었다」로 위장된다.** 진짜 고장이 안내 문구 뒤에 숨는다.
사장님이 본 [이 컴퓨터로 바꾸기] 버튼(`MainPcGate.razor:92`)이 그 위장의 결과다.

## §2 채택 — 봉투를 씌우고, 공급자를 말하게 한다 (절A)

### §2-1 왜 「공급자 한 줄 고치기」로 안 끝내나

`UnsealKey:111` 에 공급자만 넣으면 이 증상은 사라진다. 그러나 **세 가지가 남는다.**

1. `SealKey` 는 **세 갈래**로 나갈 수 있다 — TPM(`:83`) · DPAPI LocalMachine(`:93`) · DPAPI CurrentUser(`:98` catch 폴백).
   나온 값에는 **어느 갈래였는지 표식이 없다.** 해제는 추측하고, 틀리면 폴백을 또 추측한다.
2. `IsTpmAvailable()`(`:43-59`)은 TPM 을 **사실상 안 잰다** — `CngProvider.MicrosoftPlatformCryptoProvider` 는 그냥 객체라 항상 non-null.
   ⇒ TPM 없는 PC 에서도 TPM 갈래를 시도했다가 catch 로 떨어져 **CurrentUser** 로 봉인된다. 프로필이 바뀌면 그날로 안 풀린다.
3. `KEY_NAME` 이 세금계산서와 공유다(C-1 결재 = 분리).

⇒ **값 자신이 자기 출신을 말하게** 만든다. 그러면 해제에 추측이 0회가 된다.

### §2-2 봉투 포맷

```
[0..3]  매직 'H' 'P' 'M' '1'      — 메인PC 봉인 v1
[4]     갈래 1바이트              'P' = Platform(TPM) · 'L' = DPAPI LocalMachine · 'U' = DPAPI CurrentUser
[5..]   본문                      해당 갈래가 만든 바이트 그대로
```

- 오버헤드 5바이트. `VARBINARY(1024)` 여유 안에 들어간다 ⇒ **DDL 변경 없음.**
- 해제는 `[4]` 가 말하는 **그 방법 하나만** 쓴다. 실패하면 폴백하지 않고 **실패로 보고한다.**
  (지금은 실패가 폴백을 타고 내려가 「컴퓨터가 바뀌었다」로 끝난다 — 그 통로를 끊는다.)
- 매직이 없으면 = 옛 값 → §3.

### §2-3 새 서비스 (신규 파일 · 기존 파일 무접촉)

`src/HitPan.Application/Services/Security/MainPcSealService.cs` — `IMainPcSealService` 신설.

| 멤버 | 하는 일 |
|---|---|
| `byte[] Seal(byte[] raw)` | 갈래를 **재서** 고르고, 그 공급자로 봉인하고, 봉투를 씌운다 |
| `MainPcUnsealResult Unseal(byte[] envelope)` | 매직 확인 → 갈래 읽기 → **그 공급자를 명시해** 해제. 결과는 `Ok` / `LegacyFormat` / `NotThisPc` |
| `bool IsPlatformKspUsable()` | 🔴 **실제로 잰다** — 임시 키 이름으로 `CngKey.Create(..., Platform)` 을 시도해 보고 성공하면 **즉시 삭제**한다. 실물 `KEY_NAME` 무접촉 |

- 키 이름 상수 `HitPan.MainPc.SealKey` (C-1). `HitPan.TaxInvoice.MasterKey` 와 **글자가 겹치지 않는다.**
- 생성자에 **키 이름을 주입할 수 있게** 둔다(기본값 = 위 상수). 게이트가 격리된 이름으로 진짜 왕복을 돌기 위한 유일한 통로다(§5).
- 🚫 `ITpmKeyService` 를 **확장하지 않는다.** 확장하면 구현체 4개(`TpmKeyService` + 시험 가짜 3개)가 전부 깨진다(#12 grep 결과).
  별도 인터페이스면 세금계산서 경로는 **컴파일 단위로 무접촉**이다.

### §2-4 결선

`MainPcProofService` 는 `_tpm`(`:43`)을 **그대로 남기고** `_seal` 을 **더한다**(#1 추가만).
- `:235` `_tpm.SealKey(raw)` → `_seal.Seal(raw)`
- `:127` `_tpm.UnsealKey(sealedKey)` → `_seal.Unseal(sealedKey)` 의 결과로 갈래를 판정
- 생성자는 **오버로드를 더한다** — 기존 3인자 생성자를 지우지 않는다(기존 시험 무회귀).

## §3 옛 봉인값 — 「푼다」가 아니라 「알아본다」 (절B · C-2)

### §3-1 사실

`tenant_devices.mainpc_sealed_key` 에 값이 이미 있다(9/23 등록). 그 값은
`OverwriteExistingKey`(`TpmKeyService.cs:79`)로 **여러 번 덮인** TPM RSA 키로 봉인됐다.
덮인 키는 복구 수단이 없다. ⇒ **옛 값은 못 푼다는 전제로 설계한다.**

### §3-2 어떻게 보이나 — 막다른 방을 만들지 않는다

`MainPcProofOutcome` 에 값을 **하나 더한다**: `ReRegisterRequired`.
판정표(`MainPcProofService.JudgeRegistrationAsync`):

| 봉인칸 상태 | 판정 | 화면 |
|---|---|---|
| 없음/빈값 | `NotRegisteredYet` (종전) | [등록] 팝업 (종전) |
| 봉투 있음 · 이 PC 에서 풀림 | `MainPcConfirmed` (종전) | 조용히 통과 + 출입증 |
| 봉투 있음 · 안 풀림 | `DifferentPc` (종전) | [이 컴퓨터로 바꾸기] (종전) |
| **봉투 없음(옛 형식)** | **`ReRegisterRequired`** (신규) | **[다시 인증] 팝업** (신규) |

- 🔴 옛 값은 **풀려고 시도조차 안 한다.** 매직 4바이트만 본다 ⇒ TPM 접근 0회 · 예외 0회 · 로그 오염 0.
- 팝업 문구(고객어 · 개발용어 금지):
  *"자료보관 컴퓨터 인증을 한 번 더 받아야 합니다. 이 컴퓨터가 회사 자료가 들어 있는 그 컴퓨터가 맞으면 [다시 인증] 을 눌러 주세요."*
- 버튼이 부르는 곳은 **기존 `mainpc-register` 그대로**다. 새 API 를 만들지 않는다.
  `MainPcGate.RegisterAsync`(`:184-230`)가 왕복 → 등록 → `RunProofAsync()` 를 이미 한다.
- 🔴 대표(`tenant_admin`)에게만 뜬다 — `MainPcGate.razor:126` 의 기존 규칙을 그대로 따른다. 직원 화면은 변화 0.

### §3-3 자동 재봉인은 안 한다 (중요)

옛 값을 못 푼다 = **이 PC 가 그 PC 라는 증거가 없다.** 자동으로 새 키를 심으면
**아무 PC 나 먼저 로그인한 쪽이 메인PC 가 된다.** 반드시 대표 확인 1회를 거친다(반자동 원칙).

### §4-1 절C — 403 을 받으면 왕복을 한 번 더 돈다 (주 봉합)

`HitPanApiAuthHandler.cs:54` 에 **401 1회 자동 재발급**이 이미 있다. **그 옆에** 같은 모양으로 더한다.

- 동작: `MainPcGate` 가 쓰는 왕복을 **한 바퀴 돌고**(①표 → ②로컬 두드리기 → ③확인), 출입증을 받았으면 **원요청 1회 재시도**.
- 🔴 **재시도는 요청당 1회.** 실패하면 **60초 쿨다운** — 클라이언트 PC 에서 매 403 마다 왕복을 돌면 소음이 된다.
- 이 한 자리가 **셋을 동시에 덮는다**: C-3 경주 · C-5 30분 만료(`MainPcProofService.cs:191`) · SPA 이동 중 만료.
  🔴 `:186-189` 주석이 *"화면이 조용히 왕복을 다시 돌아 새로 받는다"* 라고 적혀 있는데 **그 코드가 없다.** 이 절이 그 주석을 코드로 만든다.

### §4-2 절D — 화면은 통과한 뒤에 부른다 (소음 제거)

## §5 게이트 — 진짜 왕복을 돌되 실물 키를 안 덮는다 (절E · C-7)

### §5-1 왜 게이트 18건이 다 통과했나

- `MainPcProofRoundTripGateTests.cs:98-99` — `SealKey` 를 부르면 **일부러 실패**시킨다(#39 보호).
- `MainPcSealRegistryGateTests.cs:173-196` — `SealKey`·`UnsealKey` **둘 다 가짜**.
⇒ **봉인 → 해제를 한 번도 이어서 돌린 적이 없다.** 글자는 다 보는데 **왕복 동작**을 안 본다.
누적 25번 지적된 *"게이트는 글자가 아니라 동작"* 의 26번째 재발이다.

### §5-2 격리 방식 (🚨 실물 키 무접촉의 근거)

`MainPcSealService` 생성자에 키 이름을 주입할 수 있으므로(§2-3), 게이트는
`HitPanTest.MainPcSeal.<GUID8>` 이라는 **1회용 이름**으로 서비스를 만들어 **진짜 Seal → 진짜 Unseal** 을 돈다.
`finally` 에서 그 이름의 키를 **삭제**하고, 삭제됐는지까지 확인한다.

- 실물 `HitPan.MainPc.SealKey` · `HitPan.TaxInvoice.MasterKey` 는 **이름이 안 겹치므로 안 덮인다.**
- PM 이 선행검증 §PM 에서 쓴 방식과 같다 — 이미 이 PC 에서 안전하게 돌려 본 방식이다.

### §5-3 CI 에서 실제로 도는가

- `build` 잡 = **`windows-latest`**(`.github/workflows/build-and-test.yml:20`) · `dotnet test src/HitPan.sln` 이 **필터 없이** 전부 문다 ⇒ 새 게이트 클래스는 **등록 없이도 돈다.**
- `db-gate` 잡 = `ubuntu-latest`(`:93`) ⇒ **CNG 가 없다.** 여기에 넣지 않는다.
- 🔴 **Software 금고는 어느 Windows 에나 있다.** ⇒ 본질(공급자 대칭)을 무는 게이트를 **Software 금고로** 세운다(G-21a).
  TPM 금고는 러너에 없을 수 있다 ⇒ **G-21b 는 TPM 이 있을 때만** 돌되, **G-21a 가 언제나 돌므로 건너뛰기가 본질을 가리지 못한다.**

### §개정1-1 S-5 ① 키 이름 — 서로 죽이지 않는 체계

🚨 *"한 PC 에 여러 사업장"* 은 사장님이 6월에 결재한 **실재 시나리오**다(`multi_business_per_pc`).
CNG 키 이름은 **PC 전체에서 하나**(SYSTEM 프로필 전역)인데 봉인값 칸은 **회사당 하나**(DB-120 `uq_tenant_main_pc`).
⇒ 이름이 하나면 두 회사가 **같은 칸을 놓고 싸운다.** M-12 와 **같은 모양**이다.

**이름 규칙 (개정)**

```
HitPan.MainPc.SealKey.{T16}.{GG}
  T16 = SHA-256( 소문자·앞뒤공백제거한 tenant_id ) 앞 8바이트 → 16자리 소문자 16진
  GG  = 세대 2자리 16진 (00~FF · 순환)
```

- **왜 해시인가** — `tenant_id` 는 `char(36)` GUID 다. 그대로 붙여도 되지만, 이름이 로그·오류 메시지에 그대로 실려 **회사 식별자가 밖으로 나간다.** 해시는 봉인 때도 해제 때도 **같은 입력에서 같은 값**이 나오므로 어디에도 저장할 필요가 없다.
- **왜 세대인가** — §개정1-2.
- 🔴 **`HitPan.TaxInvoice.MasterKey` 와 접두사부터 다르다.** 점(`.`) 뒤에 무엇이 붙어도 세금계산서 이름과 **글자가 겹치지 않는다.**
- 🔴 **이 이름은 `P`(TPM) 갈래에만 있다.** `L`(DPAPI LocalMachine)은 `ProtectedData.Protect` 라 **이름 있는 키를 만들지 않는다**(실측: `TpmKeyService.cs:93`). ⇒ **`L` 에는 덮어쓸 대상이 없다 = 죽는 일이 없다.** 대신 `L` 은 `optionalEntropy` 에 `T16` 을 넣어 **회사를 가른다**(지금은 `null` 이다).

**🚨 `OverwriteExistingKey` 가 언제 무엇을 죽이나**

| 이름 체계 | 상황 | 죽는 것 | 결과 |
|---|---|---|---|
| 실물 현행 (`HitPan.TaxInvoice.MasterKey` 공유) | 메인PC 등록 | **세금계산서 마스터키** | **M-12** — 확정 사고 |
| 1차 설계 (`HitPan.MainPc.SealKey` 단일) | 같은 회사 재등록 | 그 회사 직전 키 | DB 쓰기 성공 시 무해 · **실패 시 옛 봉투 영구 사망** |
| 1차 설계 (단일) | 한 PC · 회사 A → 회사 B 등록 | **A 의 키** | A 는 다음 로그인부터 `DifferentPc` · A 가 다시 등록하면 B 가 죽는다 ⇒ **영구 핑퐁** |
| 1차 설계 (단일) | 두 회사가 번갈아 접속 | 매번 상대 키 | 둘 다 **영원히 재등록**만 반복 |
| **개정 (회사별 + 세대)** | 재등록 | **아무것도** — 새 세대 이름에 만든다 | 실패해도 옛 값이 산다 |
| **개정** | 한 PC 두 회사 | **아무것도** — `T16` 이 다르다 | 공존 |
| **개정** | 세대 번호가 한 바퀴 돌아 충돌 | (예방한다) | 만들기 전에 `CngKey.Exists` 로 확인하고 **비어 있는 세대**로 민다 |

🔴 **개정안은 `OverwriteExistingKey` 를 한 번도 쓰지 않는다.** 그 옵션이 코드에 나타나면 [4] 반려 사유다.

### §개정1-2 S-5 ② 순서 — 등록이 실패해도 옛 봉인값은 산다

**답: 순서는 그대로 두되(봉인 → DB 쓰기) · 세대를 둔다.** 뒤집기는 불가능하다 — DB 에 쓸 바이트가 봉인의 결과물이다.

**왜 세대인가** — 문제는 순서가 아니라 **같은 이름을 덮는다**는 것이다. 새 세대 이름에 만들면 옛 키는 손대지 않은 채 남고, 실패해도 옛 봉투가 **그대로 풀린다.** 순서를 아무리 바꿔도 덮어쓰기가 남아 있으면 `rows==0` 한 번이 옛 값을 죽인다(`MainPcProofService.cs:235` → `:259-267`).

**등록 절차 (개정 · 6단계)**

| # | 하는 일 | 실패하면 |
|---|---|---|
| 1 | DB 의 현재 봉투를 읽어 세대 `g` 를 안다(봉투 없음/옛 값이면 `g` 미정) | 읽기 실패 = 등록 중단 · **아무것도 안 만든다** |
| 2 | 새 세대 `g' = (g+1) mod 256`. **그 이름이 이미 있으면 한 칸 더 민다**(최대 3회) | 3회 다 차 있으면 등록 거절 + 사유 안내 |
| 3 | `g'` 이름으로 키 생성 — **덮어쓰기 옵션 없이** | 생성 실패 = 등록 중단 · 옛 키 무접촉 |
| 4 | 봉인 → 봉투(`HPM2` · 갈래 · `g'`) 조립 | 실패 = 3의 키를 **지우고** 중단 |
| 5 | DB `UPDATE` (기존 `:259-267` 그대로) | 🔴 `rows==0` → **`g'` 키를 지우고** 실패 반환. **옛 키 `g` 는 손대지 않았다 ⇒ 옛 봉투 그대로 산다** |
| 6 | `rows==1` 확인 후 **옛 키 `g` 를 지운다**(best-effort) | 지우기 실패해도 무해 — 다음 등록의 2단계가 비켜 간다 |

🟢 이 순서면 **어느 단계에서 끊겨도 DB 의 봉투와 CNG 의 키가 항상 짝이 맞거나, 옛 짝이 그대로 남는다.** 짝 없는 상태가 생기지 않는다.

### §개정1-3 S-2 절C 범위 — 표면을 넓히지 않는다

**실측 사실**: `mainpc-challenge` · `mainpc-verify` 를 부르는 곳은 **`MainPcGate.razor:152,164,190` 뿐**이고, 그 컴포넌트는 `:126` 에서 `account_type == "tenant_admin"` 일 때만 돈다. ⇒ **오늘 출입증을 받은 사람은 대표뿐이다.**
1차 설계의 절C 는 이것을 「누구든 · 어느 화면이든」으로 넓혔다. **넓히지 않는다.**

**절C 개정 — 세 겹으로 좁힌다**

| 겹 | 조건 | 왜 |
|---|---|---|
| C-① **사람** | 프론트가 가진 `account_type == "tenant_admin"` 일 때만 자동 왕복 | 오늘과 **정확히 같은 표면**. 직원은 종전처럼 안내 화면을 본다 |
| C-② **경로** | 응답이 403 `main_pc_only` 이고 **요청 경로가 `/api/backup/` · `/api/data-reset/` · `/api/migration/` 로 시작할 때만** | 절D 가 아는 3화면과 1:1 이다. 다른 403 · 다른 경로는 **손대지 않는다** |
| C-③ **횟수** | 요청당 1회 · 60초 쿨다운(실패) · **동시 요청은 한 바퀴만**(§개정1-4 직렬화) | 소음·3중 왕복 차단 |

- 🔴 **서버는 화면 말을 안 믿는다.** C-① 은 클라이언트 절제일 뿐이다. 서버에서도 같은 선을 긋는 것(= `mainpc-challenge`/`mainpc-verify` 에 `account_type` 검사 추가)은 **범위 확장이 아니라 현행 표면의 강제**다. ⚠️ **확인 필요** — 넣을지는 PM 결재(§개정1-7 Q-1).
- 🚫 절C 는 출입증의 **권한**을 넓히지 않는다. 발급 조건도 종전과 같다. 바뀌는 것은 **언제 다시 받느냐**뿐이다.

### §개정1-4 S-1 MAC · S-3 직렬화 — 넣을지와 이유

**S-1 MAC: 🔴 별도 MAC 은 안 넣는다. 대신 봉투 안에 이름표를 넣는다.**

- **왜 MAC 이 답이 아닌가** — MAC 키를 어디에 두나? 같은 CNG 키로 봉인해야 한다 ⇒ **순환**이다. 봉투 머리(매직·갈래·세대)는 평문이지만 **위조해도 이득이 없다**: 갈래를 바꾸면 그 공급자로 해제가 실패하고(G-23), 세대를 바꾸면 **없는 키 이름**을 가리켜 실패한다. 위조의 결과가 전부 `NotThisPc` 다.
- **진짜 구멍은 따로 있다** — 판정이 *"풀렸나"* 뿐이라, **풀리기만 하면 누구의 봉투든 통과**한다(오라클). ⇒ 봉인 원문을 `tenantId ‖ deviceId ‖ 난수32` 로 바꾸고, 해제 뒤 **꺼낸 이름표가 지금 이 회사·이 기기와 같은지 대조**한다. 다르면 `NotThisPc`.
- 🟢 비용은 바이트 몇 십이고, RSA-OAEP · DPAPI 는 **이미 무결성을 갖는다**(변조하면 복호가 실패한다). MAC 을 더해도 새로 막는 것이 없다.
- 🟢 이것이 S-7 ③(다른 회사 봉투)을 **동작으로** 막는 자리다(G-30).

**S-3 직렬화: 🟢 넣는다.**

- 쿨다운은 **실패한 뒤**에만 걸린다. 화면 init 의 3콜이 **동시에** 403 을 받으면 셋 다 아직 실패 기록이 없어 **왕복이 3중으로 돈다.**
- 401 재시도 옆자리에 이미 있는 것과 같은 모양의 **단일 왕복 잠금**(`SemaphoreSlim(1,1)`)을 둔다. 먼저 들어온 하나가 왕복을 돌고, 나머지는 **그 결과를 기다렸다 쓴다.**
- 🔴 이게 없으면 G-26 의 *"60초 안에 두 번 왕복하지 않는다"* 가 **동시 요청에서 거짓**이 된다 — 게이트가 못 무는 구멍이다.

### §개정1-5 S-6 근거 정정 — `L` 은 안전해서 고른 것이 아니다

PM 이 §7 에서 O-3 를 닫으며 적은 *"`L` 은 TPM 이 없어도 되니 안전하다"* 는 **틀린 근거다.** 결론(`U` 로 봉인하지 않는다)은 **유지한다.**

| 갈래 | 무엇에 묶이나 | 한계 |
|---|---|---|
| `P` (TPM) | **하드웨어(TPM 칩)** | 마더보드 교체·BIOS 리셋이면 못 푼다 — 그게 설계 의도다 |
| `L` (DPAPI LocalMachine) | **이 Windows 설치본의 기계 키**(`%SystemRoot%\System32\Microsoft\Protect\S-1-5-18`) | 🔴 **하드웨어 결속이 아니다.** DB 와 MachineKeys 를 **함께 복사**하면 다른 PC 에서 풀린다 |
| `U` (DPAPI CurrentUser) | 실행 프로필 | 서비스 계정이 바뀌면 **조용히** 못 푼다 ⇒ **봉인에 쓰지 않는다**(O-3 유지) |

- ⇒ `L` 은 *"TPM 없는 고객을 받는 **최소 수단**"* 일 뿐 **하드웨어 결속이 아니다.** 설계문서는 이 한계를 이 표로 명시한다.
- 🔴 `L` 로 봉인된 회사는 **사본 복제로 메인PC 가 복제될 수 있다.** 이 트랙에서는 **막지 않는다.** ⇒ **별건 O-5** 로 연다(§개정1-7).
- 🟢 다만 §개정1-4 의 이름표(`tenantId ‖ deviceId`)가 **사본을 다른 회사·다른 기기줄에 갖다 쓰는 것**은 막는다. 같은 회사·같은 기기ID 째로 통째 복제하는 것은 남는다 — 그것이 O-5 다.

### §개정1-6 봉투 v2

```
[0..3]  'H' 'P' 'M' '2'      매직 (v1 은 쓰지 않는다 — 코드가 0줄이라 v1 값이 세상에 없다)
[4]     갈래 1바이트          'P' = TPM · 'L' = DPAPI LocalMachine
                              🚫 봉인은 'U' 를 만들지 않는다 (PM O-3) · 해제만 옛 값 호환으로 읽는다
[5]     세대 1바이트          0x00~0xFF · 'P' 갈래에서만 의미가 있다 ('L' 은 0x00 고정)
[6..]   본문                  그 갈래가 만든 바이트 그대로
                              (본문의 평문 = tenantId ‖ deviceId ‖ 난수32 — §개정1-4)
```

- 오버헤드 6바이트 + 이름표. `VARBINARY(1024)` 안에 들어간다 ⇒ **마이그레이션 여전히 불필요.** 현재 최대 번호 **DB-126** 확인 · `DB-127` 안 만든다 · 출하 DDL 무접촉(#36).
- 매직이 없으면 = 옛 값 → `LegacyFormat` → `ReRegisterRequired`(§3 그대로).

### §개정1-7 개정 뒤에도 남는 것 — PM·사장님 결재 필요
