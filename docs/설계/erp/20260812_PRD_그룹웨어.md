## 1. 제품 정의

### 1-1. 한 줄

> **히트판 그룹웨어는 "직원이 회사에 요청하고, 회사가 답하는" 모든 흐름을 담는다.**

### 1-2. 🔴 사장님이 그은 선 — 이것이 이 PRD 의 존재 이유

> *"**ERP의 부록수준이 아닌, 탄탄한 그룹웨어** 구현에 만전을 기하도록 할것."*

**"부록"과 "제품"의 차이를 이 문서는 이렇게 정의한다.**

| | 부록 수준 (지금) | 탄탄한 제품 (목표) |
|---|---|---|
| 기능 | 화면이 있다 | **흐름이 이어진다** |
| 신청 | 신청은 된다 | 신청 → **결재 → 반영**까지 간다 |
| 결과 | 승인하면 상태만 바뀐다 | 승인하면 **연차가 깎이고 회계에 잡힌다** |
| 발견 | 메뉴에 없으면 못 찾는다 | **알림이 찾아온다** |
| 신뢰 | 눌러도 되는지 모른다 | **되는 척하는 버튼이 없다** |

⇒ **판정 기준: "직원이 신청한 것이 끝까지 흘러가는가."**
화면 수가 아니라 **끊긴 자리의 수**로 이 제품을 평가한다.

### 1-3. 히트판 정신 적용

> *"이 화면, 처음 보는 사람이 혼자 쓸 수 있냐?"* — 모든 화면의 최종 통과 기준

그룹웨어는 **경리·현장직원이 하루에 여러 번** 쓰는 물건이다. ERP 본체보다 사용 빈도가 높다.
⇒ **입구를 여러 개 두되(화면·메신저·캘린더), 흐름은 하나로 합친다.**

## 2. 사용자

| 역할 | 하는 일 | 핵심 요구 |
|---|---|---|
| **직원** | 출퇴근·휴가·경비·초과근무 신청, 보고서 작성 | **쉽게, 물어보지 않고** |
| **팀장·부서장** | 결재 승인/반려 | **놓치지 않게(알림)**, 빠르게 |

| **대표(부모계정)** | 최종 결재, 급여·회계 확인 | **한눈에** |

인사담당자가 대신 등록·처리하는 흐름이 반드시 있어야 한다(8/11 사장님 결재 #1).

## 4. 🔴 핵심 설계 결정 (변경 시 전체 재설계)

### 4-1. 축 = 사원(`employees`)

> 흐름설계서 §3-5 전문 참조. 요약:
> 그룹웨어 8개 표 중 **7개가 이미 사원을 가리킨다.** 실측 사원 12명 중 계정 보유 1명.
> **계정을 축으로 잡으면 11명이 그룹웨어에서 사라진다.**

```
employees (사원) ★축
    ├─ user_id ────→ users (계정)     … NULL 허용
    ├─ position_id → positions (직급)  … 결재선이 여기 걸림
    └─ dept_id ────→ departments(부서) … 부서방이 여기 걸림
```

#### 🔴 예외 — 메신저는 계정 있는 사원만 (사장님 결재 2026-08-12)

> *"그룹웨어의 마스터는 사원. 하지만 **메신저는 계정이 있는 사원에게만 권한**을.
> **물리적으로 그렇게 될 수밖에 없으니**"*

**판정 기준이 여기서 나온다:**

| 성격 | 축 | 예 |
|---|---|---|
| **남이 대신 해줄 수 있는 것** | **사원** | 근태·휴가·경비·급여·계약 — 인사담당자 대행 가능 |
| **본인이 직접 해야만 하는 것** | **계정** | 메신저·로그인·전자서명 — **대신 말해줄 수 없다** |

**설계 반영**
- 메신저는 **계정 있는 사원에게만** 노출. 없으면 안내 문구
- **부서방 인원 = 그 부서 사원 중 계정 있는 사람** (부서 전원이 아님)
- **결재 알림도 계정 기준** — 계정 없는 결재자는 알림을 못 받으므로 **대리 처리 경로 필수**
- 근태·휴가·경비·급여·계약은 **계정 없어도 전부 된다**(대행)

> 8/11 결재 #1 *"계정 없는 사원을 막지 않는다"* 와 정합.
> **막지 않는다 = 업무에서 배제하지 않는다**이지, 로그인이 필요한 기능까지 준다는 뜻이 아니다.

### 4-2. 입구는 여럿, 흐름은 하나

```
화면 신청 ┐
메신저   ├──→ [결재 문서 생성] ──→ 결재선 ──→ 알림 ──→ 승인 ──→ 반영
캘린더   ┘         ★ 여기서 하나로 합쳐진다
```

🔴 사장님 지시 *"채팅창으로 작성시 워크플로우 로직에 **자동추가**"* 의 구현 원칙이 이것이다.
**메신저는 별개 기능이 아니라 결재 워크플로우의 또 다른 입구다.**

### 4-3. 결재선은 직급 기반

김삼성 상무: *"사람 이름으로 결재선을 짜면 **그 사람이 퇴사하는 날 회사의 모든 결재가 멈춥니다.**"*
⛔ **단, 정본 선택은 사장님·상무님 결재 사항**(흐름설계서 §3 P0-1 / §7-A 권고안).

### 4-4. 돈은 승인 시점에만 회계로 간다

- 그룹웨어 = **신청·승인** / 회계 = **금액 확정·전표**. 경계를 섞지 않는다
- 반영은 **결재 승인 시점에만**(헌법 #6) · 원장 **INSERT ONLY**(헌법 #3)
- 월마감 이후 소급 차단(ERP 경비의 검증된 패턴 재사용)

### 4-5. 🔴 AI 챗봇과 사내 메신저는 절대 합치지 않는다

**AI 챗봇은 대화를 외부(클로드·챗GPT·제미나이)로 보낸다. 사내 메신저는 회사 안에만 있어야 한다.**
UI 를 합치면 **사내 대화가 외부로 나가는 경로**가 생긴다 — 헌법 #18·#22 위반.

| | AI 도우미 | 사내 메신저 |
|---|---|---|
| 아이콘 | 로봇(`SmartToy`) — 기존 유지 | 사람·말풍선 |
| 데이터 | **외부 전송 있음** | **고객사 PC 안에만** |
| 위치 | 상단 바(기존) | 별도 창 + ERP 내 알림 |

## 5. 기능 요구 (개요 — 상세는 기능정의서)

### 5-1. 기존 20화면

| 축 | 화면 | 이번 조치 |
|---|---|---|
| 결재 | 대기함 · 보낸결재 · 완료결재 · 결재설정 | 유지 (정상) |
| 조직 | 사원관리 · HR직원현황 · 직급 · **부서** | 부서 축 정리 · 직급 중복 해소 |
| 근태 | 근태 · **근태캘린더** · **초과근무** | **메뉴 등재** · 초과근무 3종 분리 |
| 휴가 | 휴가연차 · 연차신청 · **휴가현황** · **휴가캘린더** | 메뉴 등재 · 하드코딩 제거 |
| 비용 | 경비신청 · **경비현황** | **회계 연결** · 영수증 첨부 |
| 계약 | 전자근로계약서 · 전자서명이력 | **사원 연결** · 결함 3건 봉합 |

**굵은 글씨 7개가 지금 메뉴에 없다.**

### 5-2. 신규 기능 (사장님 지시 7건)

| # | 기능 | 핵심 요구 |
|---|---|---|
| 1 | **보고서 4종** | 일일·주간·월간 보고서 + 경위서. 작성 → 결재 → 보관 |
| 2 | **사내 메신저** | 전체·부서별 채팅 · **양식 작성·전송** · **ERP 내 알림** · **팝업 별도 창** |
| 3 | **야근·초과근무·주말근무** | 3종 구분 신청 → 결재 → 급여 계산 근거 |

| 7 | **급여명세서 ↔ 회계** | 인건비 반영 |

## 7. 성공 기준 (DoD — 이 제품이 "됐다"의 정의)

### 7-1. 흐름 기준 (핵심)

- [ ] 직원이 **연차·경비·초과근무·보고서**를 신청하면 **결재함에 뜬다** (지금 경비·초과근무는 안 뜸)
- [ ] 승인하면 **원본과 회계에 반영된다** (지금 경비는 회계로 안 감)
- [ ] 결재가 올라오면 **알림이 간다** (지금 없음)
- [ ] **계정 없는 사원 11명**도 인사담당자를 통해 전 기능을 쓸 수 있다
- [ ] 결재선에 걸린 **사람이 퇴사해도 결재가 멈추지 않는다**

### 7-2. 정직 기준

- [ ] **누르면 실제로 되는 버튼만 있다** (무효화 버튼 사고 재발 0)
- [ ] 화면에 뜬 숫자가 **DB 실값이다** (연차 15일 하드코딩 제거)
- [ ] 무효/취소 상태가 **화면에 정확히 보인다**
- [ ] 실패를 성공으로 표시하지 않는다

### 7-3. 실측 기준

- [ ] 빌드 errors 0 / warnings 0 (헌법 #19)
- [ ] 🔴 **백지 환경(샌드박스) 실측** — 개발PC 정상은 검증이 아니다(2026-07-06 사장님)
- [ ] 신규 마이그레이션은 **`src/HitPan.API/Migrations/SQL/DB-NN_*.sql`** 에만 (8/12 사고)
- [ ] 게시 시 `requiresMigration=true`
