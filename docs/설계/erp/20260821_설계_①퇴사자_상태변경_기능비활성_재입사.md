## 1. 실측 — 지금 어떤가

### ✅ 이미 상태변경이다 (삭제 아님)

퇴사 처리는 `is_active=0` 으로 기록한다. **행을 지우지 않는다.**
⇒ 사장님 지시 ①은 **구조적으로 이미 만족**한다.

⚠️ 다만 `is_active` 와 `is_resigned` **두 칸이 같은 사실을 적고 있다**(퇴사 시 둘 다 바뀐다).
`is_resigned` 는 **읽는 코드가 전 코드에 0건**(코드 주석 실측). 정리 대상이나 이번 범위 밖.

### 🔴 안 되어 있는 것 — 지시 ②③

| 지시 | 현황 | 판정 |
|---|---|---|
| ① 상태변경 처리 | `is_active=0` | ✅ **된다** |
| ② **모든 기능 비활성** | 🔴 **아래 §2** | **미흡** |
| ③ **재입사 상태변경**(부모계정만) | 🔴 **경로 없음** | **없다** |

## 2. 🔴 지시 ② — "모든 기능 비활성" 이 안 되어 있다

### 2-1. 로그인 자체가 안 막힌다 (실측)

`AuthService.LoginAsync` 추적:
```
FindUserByEmailAsync(loginId)         ← users 조회. is_active 조건 ❌
  ↓ 잠금 확인 → 비밀번호 검증
FindActiveEmployeeByUserAsync(...)    ← employees 는 IsActive 거른다 ✅
  ↓
if (employee is null) { …백필… }      ← 🔴 없으면 만들어 준다
```

🔴 **문제**: 퇴사자는 `employees.is_active=0` 이라 조회에서 빠진다 → `employee is null` →
**자가치유 백필 로직**이 도는 경로로 들어간다. 이 백필은 **고아 계정 구제용**으로 만든 것이라
**퇴사자와 고아 계정을 구분하지 않는다.**

⇒ 퇴사자 계정이 **살아 있으면 로그인 자체가 가능**하다.

### 2-2. 결재선에서 안 빠진다 (상무님 지적 · PM 확인)

> 상무님: *"부장이 퇴사하면, 그 부장이 2단계 결재자인 **모든 문서가 동시에 멈춘다.** 한 건이 아니라 전부다."*

퇴사 처리는 `approval_doc_lines` 를 **건드리지 않는다**(실측).
⇒ 이것이 ①을 최우선으로 올린 이유다.

### 2-3. 퇴사를 막지 않는다 (설계 의도)

`GetResignPrecheckAsync` 주석: *"막지는 않고 무슨 일이 벌어지는지 알려준다(반자동 원칙)"*
⇒ **사장님 반자동 원칙과 일치**한다. 이건 유지한다.

|---|---|---|

### 3-2. 지시 ③ — 재입사

```
부모계정 관리자만  →  퇴사자 상태를 '재직' 으로 되돌린다
```

⚠️ **부모계정 한정**이 사장님 명시다. 일반 관리자도 안 된다.
⇒ `AccountTypeHelper.IsTenantAdmin` 판정 (초과근무 게이트와 같은 기준).

⚠️ **되살릴 때 결재선은 자동 복원하지 않는다** — 조직이 바뀌었을 수 있다. 사람이 다시 넣는다(반자동).

## 7. 추가 지시 — 퇴사자 숨김처리 + 필터 (2026-08-21)

> 사장님: *"실제 화면에 보여지는건 **숨김처리 필터링** 넣고"* / *"**퇴사자 숨김처리**"*

### 7-1. 실측 — 기본은 이미 숨겨진다 ✅

```
EmployeeController.GetList([FromQuery] bool includeResigned)   ← 기본값 false
EmployeeService  AND (@IncludeResigned = 1 OR e.is_active = 1) ← 안 넘기면 재직자만
```

⇒ **직원목록 API 는 기본이 "재직자만"** 이다. 화면이 따로 안 걸러도 퇴사자가 안 나온다.
🔴 **거르는 자리가 서버**라 화면이 빠뜨려도 새지 않는다 — 올바른 구조다.

| 화면 | 퇴사자 노출 |
|---|---|
| 사원관리(`/employees`) | 기본 숨김 + **[퇴사자 포함] 스위치** 있음 ✅ |
| 휴직·휴가·초과근무·급여·연차부여 | 기본 숨김 (API 기본값이 지킨다) ✅ |

### 7-2. 그래서 이번에 할 것

| 항목 | 조치 |
|---|---|
| 기본 숨김 | ✅ **이미 된다** — 회귀만 막는다(가드시험) |
| **퇴사자 보기 필터** | 사원관리 스위치를 **유지**. 다른 화면엔 넣지 않는다 |
| 🔴 **회귀 차단** | 누가 `includeResigned=true` 를 기본으로 바꾸면 **시험이 잡는다** |

⚠️ **다른 화면에 "퇴사자 포함" 을 넣지 않는 이유**: 휴가·초과근무·급여는 **재직자에게 하는 일**이다.
퇴사자를 고를 수 있게 하면 **퇴사자에게 휴가를 주는** 실수가 난다.
퇴사자 조회가 필요한 곳은 **사원관리(근로확인서 발급)** 하나다.

⇒ 사장님 오더 4번 *"전직원·부서별·직급별 필터"* 는 **④ 본안**에서 사원관리에 넣는다.
   그때 **재직/퇴사 축**도 그 필터에 함께 녹인다(지금 스위치를 필터로 승격).

## 8. 🔴 휴직자는 급여 비활성 대상이 **아니다** (사장님 못박음)

> 사장님 (2026-08-21): *"아까 이야기 했듯, **휴직에 휴직급여가 나갈 수도 있으니 급여 비활성 처리하면 안됨.** 수동입력"*

### 8-1. 🔴 퇴사와 휴직을 섞으면 안 된다

이 설계서 §3-1 의 "기능 비활성" 은 **퇴사자** 얘기다. **휴직자에게 적용하면 사고다.**

| | 퇴사자 | **휴직자** |
|---|---|---|
| 로그인 | ❌ 차단 | — (이번 범위 밖) |
| 결재선 | 해제 | — |
| **급여** | (재직 아님) | 🔴 **살아 있어야 한다 — 휴직급여** |
| 목록 노출 | 기본 숨김 | 🔴 **보여야 한다** |

⇒ **휴직 = 재직의 한 상태**다. 나가는 사람이 아니라 **잠시 쉬는 사람**이다.

### 8-2. 실측 — 이미 올바르게 되어 있다 ✅

`PayrollService` 급여대상 조회:
```sql
FROM employees e
LEFT JOIN employee_leave_of_absence a       ← 🔴 LEFT JOIN (INNER 아님)
  ON ... a.status IN ('approved','active','returned')
WHERE e.tenant_id = @TenantId
  AND e.is_active = 1                        ← 퇴사자만 뺀다. work_status 는 안 본다
```

🔴 **핵심 2가지**:
1. **`work_status` 로 거르지 않는다** — 휴직자도 급여 목록에 **그대로 뜬다** ✅
2. **`LEFT JOIN`** 이라 휴직 정보가 있으면 **붙여서** 보여준다 — 빼는 게 아니다 ✅

그리고 **휴직급여 칸이 이미 있다**: `employee_leave_of_absence.pay_amount` (실측),
급여 화면이 `AbsencePayAmount` 로 읽는다.

코드 주석도 사장님 원칙과 같은 말을 한다:
> *"담당자가 그냥 지나치면 안 되는 것들을 글로 말해 준다. **막지는 않는다 — 판단은 사람이 한다.**"*

⇒ **휴직자를 급여에서 빼지 않고, 휴직 사실을 알려주고, 금액은 사람이 넣는다.**
   사장님 *"수동입력"* 그대로다.

### 8-3. ⚠️ PM 이 조심할 것

내가 ②(휴직 자동 배치)에서 `work_status='absence'` 를 자동으로 바꾸게 만든다.
🔴 **그 값으로 급여를 거르는 코드를 절대 넣지 않는다.**

`work_status` 는 **조직도·화면 표시용**이지 **급여 판정용이 아니다.**
급여가 보는 것은 `is_active`(퇴사 여부) 하나뿐이어야 한다.
