### 설계가 고른 것 — 3줄

1. `ResolveDeviceType` 을 **`HitPan.Application` 으로 옮기고 양쪽이 같은 함수를 부른다**(§2).
   🔴 그대로 둔 채 부르는 것은 **불가능하다** — 계층 방향이 반대다(§2-1). 이걸 모르고 착수하면 순환참조에서 멈춘다.
2. 축 B 판정은 **`tenant_devices` 를 읽지 않는다**(§3). 지문 없는 로그인이 실재하기 때문이다.
3. `sid` 미탑재(C-2 ②)는 **호출 순서를 바꿔야** 성립한다(§4-2) — 지금은 토큰이 INSERT 보다 먼저 만들어진다.

### 🔴 이 설계가 하지 않는 것 (거짓봉합 방지)

**위조를 막지 않는다.** 브라우저는 자기가 PC 임을 증명할 수단이 없다(선행검증서 §3).
도달 목표는 *"JSON 한 칸 → 헤더까지 함께 위조해야 되는 수준"* = 8/18 V-05 가 이미 판정한 수준이다.
이것을 *"막았다"* 고 적으면 거짓봉합이다 (`TenantDeviceService.cs:679-682` 가 스스로 적어 둔 한계).

## §2 판정 자리를 하나로 — 어떻게 재사용하나

### §2-1 🔴 그냥 부를 수 없다 — 계층이 반대다

| 사실 | 근거 |
|---|---|
| `ResolveDeviceType` 은 **Infrastructure** 에 있다 · `internal static` | `TenantDeviceService.cs:2051` |
| `HitPan.Infrastructure` → `HitPan.Application` 을 참조한다 | `HitPan.Infrastructure.csproj:5` |
| `HitPan.Application` 은 Domain·Contracts 만 참조한다 | `HitPan.Application.csproj:4-5` |

⇒ `AuthService`(Application)가 `TenantDeviceService`(Infrastructure)를 부르면 **순환참조**다.
⇒ 그래서 **함수를 아래(Application)로 옮기고, 위(Infrastructure)가 그 함수를 부른다.** 복사가 아니다.

### §2-2 결정 — 판정 3함수를 `HitPan.Application/Common/DeviceTypeResolver.cs` 로 옮긴다

| 항목 | 내용 |
|---|---|
| 옮길 것 | `NormalizeDeviceType`(`:1990`) · `ResolveDeviceType`(`:2051`) · `JudgeTypeFromUserAgent`(`:2096`) **본문과 주석 블록 전부** |
| 접근성 | `public static` — `HitPan.Tests` 는 Application 을 직접 참조하고(`HitPan.Tests.csproj:19`), `InternalsVisibleTo` 는 **Infrastructure 에만** 있다(`HitPan.Infrastructure.csproj:13`). `internal` 로 옮기면 게이트가 못 본다 |
| 원 자리 | `TenantDeviceService` 의 세 메서드는 **시그니처를 남기고 본문을 위임 한 줄로** 바꾼다 — 기존 호출부 `:560`·`:691`·`:1566` 와 `DeviceTypeQrGateTests.cs:625` 가 그대로 돈다 |
| 주석 | 8/18 V-05 · 8/16 CR2-2 근거 블록은 **옮긴 파일로 함께 간다.** 원 자리에는 *"판정은 `DeviceTypeResolver` 로 옮겼다"* 한 줄만 (#1 — 지우지 않고 가리킨다) |
| 제거 | `AuthService.NormalizeDeviceKind`(`:196-198`) · `NormalizeDeviceKindForTests`(`:195`) — 게이트는 `DeviceTypeResolver.ResolveDeviceType` 을 직접 부른다 |

🔴 **왜 복사하지 않나** — 판정 자리가 둘이면 한쪽만 고쳐지는 사고가 난다. 이 레포에서 폴백 2곳(D-9)으로 이미 당했다.

### §2-3 서버가 읽은 User-Agent 를 판정까지 나르는 길

| 단계 | 내용 |
|---|---|
| ① DTO | `LoginRequest` 에 `public string? UserAgent { get; set; }` **추가**(`LoginRequest.cs:17-25` 기기 칸 옆) |
| ② 컨트롤러 | `AuthController.cs:50` `LoginAsync` **호출 직전**에 `request.UserAgent = Request.Headers["User-Agent"].ToString();` — **무조건 덮어쓴다** |
| ③ 판정 | `AuthService.cs:114` → `DeviceTypeResolver.ResolveDeviceType(request.DeviceType, request.UserAgent)` |

🔴 **②가 무조건 덮어쓰는 것이 이 설계의 핵심이다.** `LoginRequest` 는 `[FromBody]` 이므로
클라이언트가 `userAgent` 를 본문에 실을 수 있다. 덮어쓰기가 없으면 **자진신고 칸이 하나에서 둘로 늘어난다.**

## §3 🔴 지문 없는 로그인의 판정 (선행검증서 §5 의 물음에 대한 답)

**사실**: `AuthController.cs:69` 는 `DeviceFingerprint` 가 비면 기기 등록을 **통째로 건너뛴다**
⇒ `tenant_devices` 행이 **없는 로그인이 실재한다**.

**결정**: 축 B 판정은 **`tenant_devices` 를 읽지 않는다.** 판정 입력은 두 개뿐이다 —
① 클라이언트 신고값 `request.DeviceType` ② **서버가 읽은** `User-Agent`.

| 왜 | 내용 |
|---|---|
| 판정 불가 구간이 생기지 않는다 | `ResolveDeviceType` 은 **항상 값을 돌려준다**(`:2051-2074` — 둘 다 없으면 `?? "mobile"`). 지문 유무와 무관하다 |
| 행을 전제하면 구현이 메운다 | 행이 없을 때를 안 정하면 *"없으면 pc"* 같은 자기 판단이 들어간다 — 그 순간 C-3(싼 칸 원칙)이 뒤집히고 P0 다 |
| 시점도 맞지 않는다 | 축 B 는 `AuthService.cs:115`(상태 변경 **전**)에서 판정한다. 기기 등록은 그보다 **뒤**(`AuthController.cs:70~`)다 — 읽으려 해도 아직 행이 없다 |

⚠️ **그래서 남는 것**: `tenant_devices.status`(pending/approved/revoked)·`is_main_pc` 는 축 B 가
**안 본다.** 즉 *"등록도 안 된 기기가 PC 로 접속"* 은 축 B 가 아니라 **기기슬롯 축**이 막는다(기존 경로).
⇒ 이것을 축 B 로 끌어오는 것은 **별건 · 축 B 를 켜기 전 결재**다. 이번 범위 아님.

## §5 C-4 — 갱신이 만료 세션을 되살릴 때

지금: `AuthService.cs:483-488` 이 `sid` 만 보고 `UPDATE … expires_at = +8h` 를 **무조건** 돈다 ⇒ 만료된 PC1 이 부활해 PC2 와 **영구 공존**(F-6).

| 단계 | 동작 |
|---|---|
| 1 | 내 세션 한 줄을 먼저 읽는다 — `SELECT device_kind, expires_at FROM user_sessions WHERE session_id=@sid` |
| 2 | 행 없음(밀어내기로 지워짐) | 🟢 **현행 유지** — 되살리지 않는다(UPDATE 0행과 같은 결과) |
| 3 | 행 있고 `expires_at > NOW()` | 🟢 그대로 연장 (지금과 같다) |
| 4 | 행 있고 **만료** · `device_kind='mobile'` | 🟢 되살린다 (모바일은 축 B 대상 아님 — 9/25 결재) |
| 5 | 행 있고 **만료** · `device_kind='pc'` · 킬스위치 OFF | 🟢 되살린다 |
| 6 | 행 있고 **만료** · `device_kind='pc'` · 킬스위치 ON · **다른 PC 세션 없음** | 🟢 **되살린다** — 밤샘 근무는 정상 업무다(#20) |
| 7 | 위와 같고 **다른 PC 세션이 살아 있다** | 🔴 되살리지 않고 **401** → 재로그인 → 그 자리에서 409 + 밀어내기 선택 |

- 7 의 판정 SQL: `SELECT 1 FROM user_sessions WHERE user_id=@u AND device_kind='pc' AND session_id<>@sid AND expires_at > UTC_TIMESTAMP(6)`
- 7 의 반환: `UnauthorizedAccessException` — `AuthController.cs:379-382` 가 이미 **401 + 메시지**로 바꾼다(신설 경로 없음)
- 문구는 고객 언어로. 🚫 개발용어 금지
- 🔴 판정 실패(예외)는 **되살리는 쪽**으로 둔다(가용성 우선 · `:490-494` 원칙 그대로)

| 음성 대조군의 과녁 | *"컬럼을 지우면 내 SQL 이 FAIL"* 이 아니라 **"운영 호출 한 줄을 지우면 FAIL"** 이어야 한다 |
| 같은 파서 금지 | 대조 두 쪽을 같은 코드로 읽지 않는다(작1 §4 원칙 · 같은 커밋에서 어겼다) |
| DB 없으면 SKIP=미계측 | `HITPAN_REQUIRE_DB` 로 CI 에서 SKIP 을 막는다. 🔴 개발 PC 는 `CREATE DATABASE` 거부 ⇒ **`db-gate` 잡이 유일한 계측 경로 · PR 에서만 깨어난다** |
| 선례 | `MultiTenantIsolationTests` 가 `WebApplicationFactory` 를 쓴다 — 종단이 필요할 때 이 형태를 따른다 |

⚠️ **미확인**: 시험에서 `AuthService` 를 실 DB `IUnitOfWork`·`IAuthUserLookup` 으로 세울 수 있는지 안 재봤다.
⇒ 작업지시서는 **1순위 = `AuthService` 직접 생성 · 2순위 = `WebApplicationFactory` 종단** 두 길을 적고, 어느 쪽으로 갔는지 개발명세서에 남기게 한다.

## §11 ⚠️ 미확인 (전제로 쓰면 안 되는 것)

- ⚠️ 실물 재현 0건 — 개발 PC `hitpan` 계정 `CREATE DATABASE` 거부. 종단은 CI `db-gate` 만.
