## 1. 갈래 A — 두 모드 (본 설계 §2 보강)

### 1-1. 덮어쓰기 — 순서가 곧 설계다

```
[모드=덮어쓰기] 비번 + 확인문구 "덮어쓰기" (DataReset 과 같은 2단 확인 · MainPcOnly)
   → ① 백업 강제  IBackupService.RunBackupAsync(tenant, "before_migration_overwrite")  실패 시 중단
   → ② 초기화     IDataResetService.ResetAllAsync(그대로 호출 · 화이트리스트 무변경)
   → ③ 뼈대 재시드 ⛔Q1  표준 계정과목 27 · 대표 사원 1행(부모계정 user_id 연결·직급 대표이사) · 근로 기준값
   → ④ 잡 생성     MigrationJobStore.CreateAsync   ← 반드시 ② 뒤 (migration_jobs 가 초기화 대상)
   → ⑤ 이관(1단계 → 다이얼로그 → 2단계) → ⑥ 대사표
```
- ③ 은 `CompanyBootstrapProvisioner` 의 시드를 **호출 가능한 메서드로 뽑아**(`SeedStandardAccountsAsync` · `EnsureOwnerEmployeeAsync` · `SeedLaborPolicyAsync` — 기존 본문을 옮기지 않고 메서드 경계만 세운다, #1) 초기화 화면(`DataResetController`)과 덮어쓰기가 **같은 재시드를 탄다**. ⛔ **Q1 답 전 코드 금지**(6/23 "직원 삭제" ↔ 8/14 "대표 사원 자동등록" 충돌).
- ①·② 는 이미 있는 서비스 호출뿐 — 신설 0.
- 요청 DTO: `MdbMigrationRequest` 에 `Mode`("merge" 기본 / "overwrite") · `Password` · `ConfirmText` 추가(추가만).
- 화면 문구(개발용어 0): 「기존 자료를 모두 지우고 새로 가져오기」/「기존 자료는 두고 없는 것만 보태기」. 덮어쓰기 경고에 **「히트판에서 입력한 거래 N건이 지워집니다」** (건수는 `sales_deliveries`+`purchase_receipts`+`collections`+`payments` 중 `source_type<>'migration'`).

### 1-2. 병합 — 현행 유지 + 마스터 "빈칸만 채움"
- 거래: `source_id` UNIQUE `INSERT IGNORE`/UPSERT 현행 그대로(있으면 skip).
- 마스터(업체·상품·사원): 현행 `ON DUPLICATE KEY UPDATE` 는 **레거시가 ERP 를 덮는다**(본 설계 §4 P1 G-MH). 전결1 Q8 = (C) 충돌표 · 기본 (A) ERP 값 보존. **작22 는 (A)만** — 병합 모드일 때 UPDATE 절을 `col = COALESCE(NULLIF(col,''), VALUES(col))` 로(빈칸만 채움). **(C) 충돌표 UI 는 작23** (§8 하지 않는 것 · 한 화면씩 #10).
- 세션 튜닝: 병합 모드는 `unique_checks=1` (선행검증 §2-8 — IGNORE 멱등과 이론 충돌). 덮어쓰기(빈 표)는 0 유지. 속도 차는 실측으로 기록.
- 🔴 게이트 **G-M1**: 빈 DB 에 병합 = 덮어쓰기와 **표별 행수·합계 1행도 안 다름**(e2e 2회 실행 대조, baseline 도구 `--mode`).
- 게이트 **G-MH**: ERP 에서 고친 업체 단가·상품명이 병합 재이관 뒤 **유지**.

### 1-3. 1단계 → 다이얼로그 → 2단계 (5/16 사장님 UX 그대로)
- `/start` 는 **1단계만**(warehouse_migration · pyojun_master · **hr_reports 사원 의존 없음 → 2단계**) 돌리고 잡을 `paused` 로 둔다. SignalR `PhaseCompleted(1)` → 화면 다이얼로그 문안 **"1단계자료 이관완료. 2단계 자료 이관 계속 하시겠습니까?"**([5/16 §5](../../운영기록/20260516_2245_PM_마이그_두단계분리_사장님결재안.md) 사장님 문안 그대로).
- 「예」 → `POST legacy-mdb/{jobId}/continue` → 2단계(PANDATA 15잡 병렬 + POTHER 5잡 + 리빌드). 「아니오」 → 잡 `paused` 로 남고 ERP 는 마스터만으로 사용 가능(#20 흐름 안 끊김). 나중에 같은 화면에서 「이어서 가져오기」.
- 화면 진입 시 `GET legacy-mdb/current` (테넌트 최신 잡 — **DB `migration_jobs` 기준**, 메모리 `_jobs` 아님) 로 진행 중·중단 잡을 **다시 붙는다**(선행검증 §2-5: 지금은 재접속 0).

### 1-4. 체크포인트 = `RunTableStepAsync` 훅 하나
- jobId 있을 때만: 시작 시 `migration_checkpoints` UPSERT(`uk_job_table`) `running` → 끝나면 `done`(`processed_count`=행수·`completed_at`) / `failed`(`last_error`·`retry_count+1`). baseline 도구(jobId null)는 종전대로 skip(`TryInsertMigrationErrorAsync :692` 규칙과 동일).
- **재개**: `continue`/`resume` 는 같은 `jobId` 로 `MigrateAsync` 를 다시 부르고, `RunTableStepAsync` 가 `done` 인 표를 `skipped` 콜백으로 건너뛴다. 표 단위 트랜잭션이라 done = 전부 들어감. **`item_stock_rebuild` 는 항상 다시 돈다**(체크포인트 예외).
- `total_rows` 는 미리보기 카운트가 있으면 채우고 없으면 0. `last_pk_value` 는 이번엔 안 쓴다(표 단위 재개 — 행 단위 재개는 W4).
- 게이트 **G-CK**: e2e 에서 2단계 도중 취소 → `continue` → 이미 done 표는 skipped · 나머지만 실행 · 최종 대사표 = 무중단 실행과 동일.

### 1-5. `preview`·`reconcile` POST (결1 5 · 병렬이슈 11)
- `[HttpPost("legacy-mdb/preview")]`·`[HttpPost("legacy-mdb/reconcile")]` + 바디 `MdbMigrationRequest`. razor 두 호출(`:517`·`:754`)을 POST 로. **GET 두 개는 제거** — 같은 기능의 안전한 이동이지 기능 삭제가 아니다(비번이 URL·로그에 남는 구멍을 닫는 것이 목적이라 GET 을 남기면 봉합이 아니다). PM 전결.

### 1-6. 결1 7 — P2 계통
- 진행 카드 행수: `RunTableStepAsync` 콜백 `rows` 를 **후보(stage) 행수**로 통일 — UPSERT affected-rows(갱신=2) 를 그대로 보고하지 않는다. 병합 모드에선 툴팁에 「신규 N · 갱신 M · 중복 K」.
- `JournalSides` 양쪽 비영: 카운트 + `migration_errors` 1행(표 `journal_entries`, 유형 `both_sides_nonzero`) + 결과 카드 경고. 이 MDB 는 0행이라 게이트는 순수함수 케이스로.
- 비활성 MAIN: `EnsureMigrationWarehouseAsync :895-905` — 활성 창고가 0 이고 비활성 MAIN 만 있으면 **MAIN 을 활성으로 되살린다**(새 창고를 만들지 않는다 · 9/4 창고 정의 "MAIN 하나 = 미사용과 같다").
- `bank_transactions` 85→214s: 1/2단계 분리 후 W5 실측에서 재측정(설계 변경 없음).
