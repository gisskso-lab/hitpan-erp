## 0. 사장님 원칙 (본 PRD의 헌법)

> **"히트판의 개발취지는 각 기능별 철저한 모듈화가 기본 원칙이야.
> A가 안된다고 해서 시스템 전체가 다 안되는건 안되.
> A가 오류가 있을시, A만 안되고, 그래서 A만 복구하도록 해야지."**

> **"설치는 히트판개발팀이라면, 워치독은 검증팀의 역할이 되야하지.
> 검증팀이 검증에서 놓친게 있다고 한들, 히트판 개발팀이 개발을 안하고 쉬는게 아니잖아."**

> **"고객이 사용하는데는 문제가 없지만, 고객사의 워치독 등록실패에 대해선
> 본사가 선재적 대응을 할 수 있도록."**

### 이 원칙이 나온 배경 (2026-07-21 Sandbox 실측)

워치독 서비스 등록 시도가 **설치 전체를 32분간 정지**시켰다. ERP·DB·터널은 이미 준비 완료였는데,
감시자(워치독) 하나 때문에 고객이 32분을 대기했다. 그리고 32분 뒤 뜬 메시지는 **"실패했습니다"**
였으나, 실측 결과 워치독 서비스는 **정상 RUNNING**이었다.

즉 **① 검증팀이 개발팀을 멈춰 세웠고, ② 안내마저 사실과 달랐다.**

### 1-2. 진범 (반증 5회 후 확정)

**`InstallWatchdog.ps1` L60-67 `Register-ScheduledTask` (CIM 기반)**

```
L16  EXE 확인            ✅
L32  sc create           ✅  (비-CIM → 성공)
L39  Start-Service       ✅  (RUNNING 확인됨)
L57  Out-File Guardian   ✅  (파일 존재 확인됨)
L60-67 Register-ScheduledTask  ❌ 32분 대기 → 예외 → exit 1
L70  exit 0              도달 못 함
```

**결정적 방증**: 같은 스크립트 안에서 `sc.exe`(비-CIM)는 전부 성공, CIM 계열만 실패.
사장님 PowerShell에서도 `Get-ScheduledTask`가 **"Cannot connect to CIM server"** 로 동일하게 실패.
`$ErrorActionPreference='Stop'`(L9)이 예외를 exit 1로 변환.

> ⚠️ **미확정**: 이것이 Sandbox 고유 현상인지 실제 고객 PC에서도 재현되는지는 미검증.
> 다만 `schtasks.exe` 전환은 어느 쪽이든 안전한 봉합이다.

## 2. 문제 정의

### 2-1. P0 — 설치가 검증에 인질로 잡힘

워치독은 **ERP의 전제조건이 아니다.** 그런데 현재 구조는 워치독 등록이 끝나야 설치가 진행된다.

```
현재:  ERP준비완료 → [워치독 등록 32분 대기] → 설치완료
원칙:  ERP준비완료 → [워치독 등록 짧게 시도] → 설치완료 (실패해도 진행)
```

`.iss` L1808-1813이 `ewWaitUntilTerminated`로 무한 대기한다. 시간 제한이 없다.

### 2-2. P0 — 거짓 실패 안내 (CS 사고 유발)

현재 문구:
> "HitPan 서비스 자동 시작 등록에 실패했습니다. PC를 재부팅하면 자동으로 시작됩니다.
> **즉시 사용하려면 고객센터에 문의해 주세요.**"

문제 3중:
1. 실제로는 **성공**인데 실패로 표시 (워치독 RUNNING 실측)
2. 고객이 32분 기다린 끝에 "실패"를 봄 → 제품 신뢰 붕괴
3. **"고객센터 문의"** → 전 고객이 전화하면 CS 마비. 헛전화 다수.

### 2-3. P0 — 본사가 모른다 (선제 CS 불가)

**워치독이 안 붙으면 메타핑도 안 온다.** 죽은 사람이 자기 부고를 못 보내는 구조.

| 경로 | 상태 |
|---|---|
| 워치독 → 본사 메타핑 **송신** | ✅ 구현됨 (`MetaPingClient`, 헌법 #22 금지필드 27종 차단) |
| 백오피스 **수신** 엔드포인트 | ❌ **0건** |
| 설치 프로그램 → 본사 보고 | ❌ **없음** |

→ 지금 구조로는 **고객이 전화를 걸어야만** 본사가 안다. 선제 CS가 성립하지 않는다.

### 2-4. P0 — 모듈화 원칙 위반 (전 플랫폼)

사장님 원칙 "A가 죽으면 A만" 을 위반하는 지점이 **워치독·ERP·백오피스 전역**에 실재한다.

| 순위 | 위치 | A가 죽으면 → B까지 죽음 |
|---|---|---|
| 1 | `Watchdog/Worker.cs:156-273` | 프로세스감시 실패 → **터널복구·헬스체크·업데이트 전부 스킵** (단계별 try/catch 0건) |
| 2 | `API/Extensions/AuthExtensions.cs:20,29,38` | JWT 시크릿 문제 → **API 프로세스 기동 불가** (판매·매입·재고 전부) |
| 3 | `Backoffice/Layout/BackofficeSidebar.razor:96` | 사이드바 예외 → **화면 전체 백지** (레이아웃 안이라 셸까지 붕괴) |
| 4 | `Application/FinanceService.cs:459-614` | 쿼리 1개 실패 → **KPI 7종+차트 3종 전멸** (try/catch 0건, UNION 묶음) |
| 5 | `Backoffice.API/Program.cs:120,127` | 마이그 스크립트 1개 실패 → **백오피스 전체 기동 불가** |

| 7 | `API/Middleware/RateLimitMiddleware.cs:19-90` | 부가기능 예외 → **본 요청 차단** (fail-closed) |

> **패턴은 이미 사내에 있다. 적용이 안 된 곳이 문제다.**

## 3. 설계 원칙 (본 PRD의 산출물)

### 원칙 1 — 계층 분리: 복구 ≠ 설치 ≠ 업무

| 계층 | 역할 | 실패 시 고객 피해 | 절대 규칙 |
|---|---|---|---|
| **업무 (ERP)** | 개발팀 | 오늘 장사 못 함 | 최우선. 무엇도 이걸 막지 못한다 |
| **복구 (워치독 통신부)** | 검증팀 | 사고 시 자가복구 불가 | 업무를 **막지 않는다** |
| **설치 (워치독 업데이트부)** | 검증팀 | 옛 버전 유지 | 복구를 **막지 않는다** |

> **워치독은 ERP의 전제조건이 아니다.** 워치독 없이도 ERP는 100% 동작한다.

### 원칙 2 — 실패 격리: A가 죽으면 A만 죽는다

모든 다단계 실행은 **단계별 예외 경계**를 갖는다.

```
금지:  stepA(); stepB(); stepC();          // A 실패 → B·C 스킵
정본:  Try(stepA); Try(stepB); Try(stepC); // A 실패 → B·C 정상 진행
```

각 단계 실패는 ① 로그에 **단계명 명시** ② 다른 단계 **미차단** ③ **개별 복구** 가능.

### 원칙 3 — 부가기능은 fail-open, 핵심은 fail-safe

| 종류 | 실패 시 | 예 |
|---|---|---|
| **부가** (레이트리밋·텔레메트리·아이콘) | **통과시킨다** | RateLimit 예외 → 요청은 진행 |
| **핵심** (인증·암호화·원장) | **막는다** | JWT 검증 실패 → 401 |

단, **핵심이 막는 범위는 그 요청 하나**다. 프로세스 전체 기동을 막지 않는다.

### 원칙 4 — 실패는 반드시 알려진다 (선제 CS)

침묵 실패 금지(헌법 #15 확장). 실패는 3곳에 남는다:

1. **로그** — 단계명 + 원인
2. **고객 안내** — 사실대로. 과장·축소·거짓 금지
3. **본사 보고** — 고객 행동(전화)에 의존하지 않는다

### 원칙 5 — 시간 제한 필수

외부 명령을 기다리는 모든 호출은 **상한 시간**을 갖는다. 무한 대기 금지.
상한 초과 = 실패로 간주하고 **다음 단계로 진행**한다.
