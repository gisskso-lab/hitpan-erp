## 2. 방 — 3종

### 2-1. 방 종류

| 종류 | `room_type` | 누가 만드나 | 인원 | 이름 |
|---|---|---|---|---|
| **1:1 대화** | `direct` | 상대를 고르면 자동으로 열림 | 2명 고정 | 상대 이름 (저장 안 함) |
| **부서 대화** | `dept` | 사람이 만든다 (부서 선택) | 그 부서 사원 중 **계정 있는 사람** | 부서명 |
| **단체 대화** | `group` | 사람이 만든다 (사원 골라 초대) | 고른 사람 | **직접 입력** |

### 2-2. 🔴 부서가 0건이어도 메신저는 돌아간다

사장님 지시: *"부서는 고객사가 설정할 일"*

⇒ **1:1·단체는 부서와 무관하게 된다.** 부서방은 부서를 만든 뒤에 생기는 방이다.
부서가 0건이면 "부서 대화" 만들기에서 **안내 문구**만 뜬다 — 오류가 아니다.

```
부서 0건  →  1:1 ✅   단체 ✅   부서방 ⛔"부서를 먼저 만들어 주세요"
부서 등록  →  1:1 ✅   단체 ✅   부서방 ✅
```

### 2-3. 부서방을 자동 생성하지 않는 이유

헌법 [[feedback_semi_auto_principle]] — *"무조건 반자동"*.

부서를 만들 때 방을 자동으로 파면:
- 안 쓰는 방이 부서 수만큼 쌓인다
- 부서 개편 때 방을 어떻게 할지 아무도 모른다 (지우나? 합치나? 이력은?)

⇒ **사람이 만든다.** 부서를 고르면 인원은 자동으로 채우되(그건 편의), 만드는 건 사람이 누른다.

### 2-4. 1:1 방은 두 번 생기지 않는다

A→B 와 B→A 가 같은 방이어야 한다.
⇒ 참여자 두 사원 ID 를 **정렬해서 키로** 잡고 UNIQUE 를 건다. (§7 DDL `direct_key`)

## 3. 참여자 — 계정 있는 사원만

사장님 8/12 결재: *"메신저는 계정이 있는 사원에게만 권한을. 물리적으로 그렇게 될 수밖에 없으니"*

| 상태 | 메신저 |
|---|---|
| `employees.user_id` 있음 | ✅ 참여 가능 |
| `employees.user_id` NULL | ⛔ 대상에서 제외 — **초대 목록에 안 뜬다** |

부서방 인원도 같다 — **그 부서 사원 중 계정 있는 사람만**.

> 이것은 8/11 결재 *"계정 없는 사원을 막지 않는다"* 와 어긋나지 않는다.
> 막지 않는다 = **업무에서 배제하지 않는다**(근태·휴가·경비·급여·계약 전부 대행 가능)이지,
> 로그인이 필요한 기능까지 준다는 뜻이 아니다.

## 4. 🔴 문서 연결 — 링크 하나. 그 이상 만들지 않는다

### 4-0. 사장님이 범위를 자르셨다 (2026-08-13)

> *"그룹웨어 문서 전송은 그룹웨어에 **이미 있는 기능들 연결 정도**만 해도 됨"*
> *"메신저 채팅창에서 연차신청서 **생성해서 만들고 결재까지 기능을 넣을 필요까진 없음.** 연결까지만 해도 충분함"*
> *"**있는 기능 연결해서 사용하는게 훨씬 효율적임**"*

#### 🔴 옛 그림에서 잘려나간 것 — 다음 사람이 되돌리지 않게

| | 8/12 PRD (옛 그림) | **8/13 사장님 지시 = 지금 정본** |
|---|---|---|
| 메신저에서 문서 **생성** | *"입구는 여럿"* — 메신저도 입구 | ❌ **안 만든다** |
| 메신저에서 **결재 태움** | *"채팅창으로 작성시 워크플로우 자동추가"* | ❌ **안 만든다** |
| 문서 **연결(링크)** | — | ✅ **이것만 한다** |

⚠️ PRD §4-2 *"메신저는 결재 워크플로우의 또 다른 입구"* 는 **오늘 지시로 범위가 줄었다.**
PRD 를 폐기하는 게 아니라, **그 조항만 오늘 지시가 덮는다.** 판단 서열 = 최신 사장님 결재.

#### 왜 연결이 더 나은가 — 효율만이 아니라 안전

연차신청 화면은 이미 **잔여 연차 확인 · 결재선 · 이중차감 방지**(6/23 봉합)를 한다.
메신저에 신청 기능을 또 만들면 그 규칙이 **두 벌**이 되고, 두 벌은 반드시 갈라진다.
⇒ 링크로 보내면 규칙이 **한 벌**이다. 헌법 #1(덮어쓰기 금지) 정신과 같은 자리.

### 4-1. 완성 기준 — 사장님이 직접 쓰신 문구

```
[김철수]  "연차신청서" 를 전송하였습니다.
          클릭하시면 연차신청서 결재와 연결됩니다.
```

**이 문구가 나오고, 눌러서 그 화면으로 가면 완성이다.** 그 이상은 §11 로 뺀다.

### 4-2. 무엇을 붙일 수 있나

| 문서 | `ref_type` | 원본 테이블 | 누르면 가는 곳 |
|---|---|---|---|
| 결재문서 | `approval` | `approval_documents` | 결재 상세 |
| 휴가·연차 신청 | `leave` | `leave_requests` | 휴가 상세 |
| 경비 신청 | `expense` | `hr_expense_requests` | 경비 상세 |
| 급여명세서 | `payroll` | `payroll_slips` | 🔴 **본인 것만** (단계8 권한 그대로) |
| 근로계약서 | `contract` | `labor_contracts` | 계약 상세 |
| 업무보고서 | `report` | `hr_reports` | 보고서 상세 |

### 4-2. 붙이는 방식 — 참조만, 복사하지 않는다

```
메시지 ──ref_type + ref_id──→ 원본 문서
         (제목만 함께 저장 = 미리보기용)
```

**본문을 복사하지 않는다.** 이유:
- 원본이 바뀌면 메시지 속 사본은 틀린 내용이 된다
- 급여·경비 금액이 대화방에 **복사본으로 남으면** 권한을 우회한다

⇒ 메시지에는 **제목만** 남기고, 실제 내용은 **누를 때 그 화면의 권한으로** 본다.

### 4-3. 🔴 권한은 문서가 판정한다 — 메신저가 아니다

> **A가 B에게 급여명세서를 첨부해도, B는 그것을 열 수 없다.**

메신저는 "가는 길"만 놓는다. 열람 판정은 **원래 그 화면이 하던 대로** 한다.
단계8에서 만든 급여 3갈래 판정(부모계정·담당자·본인)이 그대로 작동한다.

⇒ 첨부는 **제목 + 링크**. 누르면 그 화면으로 가고, 권한 없으면 **거기서 막힌다.**

### 4-4. 이것이 상무님 "잡담방" 우려의 답이다

> *"메신저를 채팅으로 먼저 만들면 잡담방이 됩니다"*

문서가 붙으면 대화가 업무가 된다:
```
"연차신청서" 를 전송하였습니다. 클릭하시면 연차신청서 결재와 연결됩니다.
"경비신청서" 를 전송하였습니다. 클릭하시면 경비신청서 결재와 연결됩니다.
```
**메신저를 켤 이유가 잡담이 아니라 일이 된다.** 만드는 건 원래 화면에서 한다.

### 4-5. 🔴 메신저가 하는 일 / 안 하는 일

| | |
|---|---|
| ✅ **한다** | ① 있는 문서를 **고른다** ② 링크 문구를 **보낸다** ③ 누르면 **이동한다** |
| ❌ **안 한다** | 문서 **생성** · 결재 **상신** · 결재 **승인/반려** · 금액·날짜 **입력** |

⇒ 메신저는 **길만 놓는다.** 일은 원래 그 화면이 한다.

**첨부 만들기 화면** = 내가 볼 수 있는 문서 목록에서 **고르기만** 한다. 새로 만드는 버튼이 없다.

## 5. 읽음 — 사장님 지시 그대로

### 5-1. 표시 방식

| 방 | 표시 |
|---|---|
| **1:1** | 읽으면 **"읽음"**, 안 읽었으면 표시 없음 |
| **부서 · 단체** | 🔴 **읽은 사람 수를 숫자로** — `3` |

사장님 지시 *"몇 명이 읽었는지 = 00"* ⇒ **읽은 수**다. 안 읽은 수가 아니다.

```
[김철수] 내일 회의 10시입니다.        3   ← 3명이 읽었다
```

### 5-2. 언제 읽음이 되나

**대화방을 열어 그 메시지가 화면에 보일 때.** 목록에서 스쳐 지나간 건 읽음이 아니다.

⇒ 화면이 "여기까지 읽었다"를 서버에 알리고, 서버가 **보낸 사람에게 실시간으로** 전한다.

### 5-3. 자기가 보낸 건 자기가 읽은 걸로 치지 않는다

읽은 수에서 **보낸 사람은 뺀다.** 안 그러면 아무도 안 읽어도 `1` 이 뜬다.

## 6. 열람·삭제 — 사장님 결재

### 6-1. 본인 대화만 열람

| 누구 | 볼 수 있는 것 |
|---|---|
| 부모계정(사장) | 🔴 **자기가 낀 방만** — 남의 1:1 은 못 본다 |
| 일반 직원 | 자기가 낀 방만 |

**부모계정도 예외가 아니다.** 사장님이 "본인 대화만 열람"을 고르신 자리다.

> 급여(단계8)와 반대인 것이 맞다. 급여는 **줘야 하니까** 사장이 다 본다.
> 대화는 **줄 것이 없다.** 사장이 다 보면 아무도 안 쓴다.

### 6-2. 삭제 = 숨김만

- 메시지를 지우면 **내 화면에서만 사라진다**
- 원문은 DB 에 남는다 (`deleted_at` 만 찍는다)
- 상대 화면에는 그대로 있다

이유: 헌법 #3 정신(원장 INSERT ONLY)과 같은 자리 — **주고받은 기록을 한쪽이 없앨 수 없다.**

### 6-3. 방을 나가면

참여자 줄에 `left_at` 을 찍는다. 줄을 지우지 않는다.
⇒ **나가기 전 대화는 계속 보인다.** 나간 뒤 것만 안 온다.

## 8-2. 🔴 파일 전송

사장님 지시: *"파일전송 기능도 추가해. **엑셀, 캡쳐파일, 디자인파일** 등 업체에서 파일전송 기능도 많이 쓸거야"*

실무에서 견적 엑셀·화면 캡처·도면을 주고받는 일이 대화보다 많다. 여기서 막히면 **결국 카톡으로 보내게 된다** — 그러면 업무 자료가 회사 밖으로 나간다.

### 8-2-1. 확정 사항

| 항목 | 확정 | 근거 |
|---|---|---|
| **최대 크기** | 🔴 **20MB** | 사장님 *"20메가"* |
| **보관** | **디스크 폴더** (DB 엔 경로만) | 사장님 결재 |
| **실행파일** | 🔴 **막는다** | 사장님 결재 |
| **조각 업로드** | 🔴 **안 만든다** | 사장님 *"통신이 안정적이지 않다면 안되는걸로"* |
| **오래된 파일** | 자동 삭제 ❌ · **용량만 보여준다** | 사장님 결재 · 반자동 원칙 |

### 8-2-2. 🔴 100MB 를 접고 20MB 로 간 이유 — 되돌리지 말 것

사장님이 처음 *"100MB 정도면 왠만한 업무파일 되지 않을까? 가능??"* 하셨고,
PM 이 *"가능하다, 단 조각 업로드가 필요하다"* 고 답했다.
사장님이 **그 자리에서 접으셨다**:

> *"**통신이 안정적이지 않다면 안되는걸로 생각하자**"* / *"20메가"*

**이 판단이 맞다. 헌법 #27(통신 무결성 절대 우선)과 같은 자리다.**

- 조각 업로드로 100MB 를 **억지로 되게** 만들면, 되는 것처럼 보이다가
  **고객 사무실 인터넷이 느린 날 터진다.** 90% 에서 끊기는 것이 가장 나쁘다.
- 20MB 는 **한 번에 가거나, 안 가거나** 둘 중 하나다. 반쯤 간 상태가 없다.
- 되돌리기: 나중에 키우는 건 쉽다. **줄이는 건 어렵다**(이미 보낸 파일이 있으므로).

⇒ 🔴 **다음 사람이 "조각 업로드 넣으면 100MB 되잖아" 하지 말 것.** 사장님이 알고 접으셨다.

### 8-2-3. 막는 확장자 (실행파일)

```
exe · bat · cmd · com · scr · pif · ps1 · vbs · js · jar · msi · dll · hta · reg · lnk
```

**왜 막나** — 사내라도 한 명이 감염되면 메신저가 **전 직원에게 퍼뜨리는 통로**가 된다.
업무 파일(엑셀·한글·PDF·이미지·압축·CAD)은 전부 된다.

🔴 **확장자만 보지 않는다.** `.exe` 를 `.xlsx` 로 바꿔도 막아야 하므로 **파일 앞부분(시그니처)도 함께 본다.**
🔴 **저장 이름은 우리가 정한다** — 원래 이름을 그대로 쓰면 `..\..\` 같은 경로 조작이 들어온다.

### 8-2-4. 어디에 두나

```
{데이터폴더}/chat-files/{tenant_id}/{yyyyMM}/{file_id}.{ext}
```

- 🔴 **테넌트별로 폴더가 갈린다** (헌법 #2 격리 — 파일에도 적용)
- 월별로 나눠 한 폴더에 수만 개가 쌓이지 않게 한다
- DB 에는 **경로·원래이름·크기·형식**만 (`chat_files`)

⚠️ **백업 범위에 이 폴더를 넣어야 한다.** DB 만 백업하면 파일은 안 따라온다.
([[project_update_backup_workflow]] — 백업 실패 시 업데이트 차단과 같은 자리)

### 8-2-5. 내려받기도 권한을 본다

🔴 **파일 주소를 알아도, 그 방에 낀 사람이 아니면 못 받는다.**
업로드 때만 검사하고 내려받기를 열어두면 §6-1(본인 대화만 열람)이 무너진다.

### 8-2-6. 🔴 파일이 ERP 를 넘어뜨리지 못하게 — 3중 한도

사장님 지시: *"**히트판 ERP 데이터양이 많으면 과부화가 올 수 있어. 파일전송은 최소한으로**"*

**왜 이게 심각한가** — 히트판은 고객사 PC **한 대**에 DB·API·웹이 다 올라가 있다(로컬+터널).
메신저 파일이 쌓이면 디스크만 차는 게 아니라 **연쇄로 무너진다**:

```
파일 누적 → 백업이 느려짐 → 업데이트 전 백업 실패 → 🔴 업데이트가 차단됨
                                    ([[project_update_backup_workflow]] A+B 결합)
```

**메신저 파일 때문에 ERP 업데이트가 멈추는 것이 최악이다.** 업무 데이터가 아닌 것이 업무를 막는다.

⇒ **"최소한으로" 를 숫자로 못 박는다:**

| 한도 | 기본값 | 넘으면 |
|---|---|---|
| **한 개** | 20MB | 못 올림 (§8-2-1) |
| 🔴 **방 하나** | **500MB** | 못 올림 + *"이 대화방 파일이 가득 찼습니다. 정리해 주세요"* |
| 🔴 **회사 전체** | **5GB** | 못 올림 + 설정에서 조정 안내 |

- 🔴 **한도는 코드 상수가 아니라 설정 테이블** ([[feedback_semi_auto_principle]] — *"기준값은 코드상수 금지"*)
- 업무 데이터(매입·판매·재고)는 **이 한도와 무관하다.** 파일만 막힌다 — 🔴 **ERP 업무가 멈추면 안 된다**

**설정 화면에 두는 것** (사장님 결재 — 자동 삭제 ❌, 용량만 보여줌):

```
메신저 파일 사용량        1.2 GB / 5 GB   ▓▓▓░░░░░░░
  [폴더 열기]  [큰 파일부터 보기]
```

⇒ **차오르기 전에 보이게** 하고, **지우는 건 사람이 한다.** 자동 삭제는 되돌릴 수 없다(반자동 원칙).

## 9. 🔴 결재 결과가 신청자에게 **메시지로** 돌아온다

### 9-0. 알림이 아니라 메시지다 — 지시가 바뀐 자리

사장님 지시: *"그룹웨어 문서 **승인 혹은 반려시, 최초 발신인(신청자)에게 메시지** 보내야됨"*

⚠️ **처음 설계는 "알림"(종 아이콘)이었다. 사장님이 말씀하신 건 "메시지"다.**

| | 알림 (옛 설계) | 🔴 **메시지** (지금 정본) |
|---|---|---|
| 어디에 | 종 아이콘 | **대화방에 남는다** |
| 읽고 나면 | 사라진다 | **기록으로 남는다** |
| 읽음 | 없음 | **읽음이 찍힌다**(§5) |
| 누르면 | 이동 | 이동 |

⇒ **알림과 메시지를 둘 다 보내지 않는다.** 같은 소식이 두 번 오면 직원이 헷갈린다.
**메신저 메시지 하나로 간다.**

### 9-1. 한 바퀴가 돈다

```
신청자 ──[「연차신청서」를 전송하였습니다]──→ 결재자     (§4 · 오더 6)
신청자 ←──[「연차신청서」가 승인되었습니다]── 결재자     (🔴 오더 7)
```

**보낸 자리로 답이 온다.** 이것이 헌법 #20(워크플로우 안 끊김)의 이행이다.

### 9-2. 문구 — 사장님이 직접 쓰신 그대로

| 시점 | 받는 사람 | 문구 |
|---|---|---|
| **승인** | 🔴 **최초 발신인(신청자)** | `"연차신청서" 가 **승인되었습니다.**` |
| **반려** | 🔴 **최초 발신인(신청자)** | `"연차신청서" 가 **반려되었습니다.**` |
| 상신 | 다음 결재자 | `"연차신청서" 결재 요청이 도착했습니다.` |

모두 아래에 같은 줄이 붙는다:
```
클릭하시면 연차신청서 결재와 연결됩니다.
```

### 9-3. 🔴 한 곳에 모으되, 무엇인지 밝힌다 (인스타·페북 방식)

사장님 지시: *"**결재봇, 메시지봇 공유해도 될듯. 인스타나 페이스북 처럼.**
다만 **메시지인지, 결재안내인지는 안내**"*

**봇을 따로 두지 않는다.** 한 곳에 모이고, 각 줄이 자기가 뭔지 딱지로 밝힌다.

```
┌─ 알림 ─────────────────────────────┐
│ [결재]   "연차신청서" 가 승인되었습니다.  │
│          김부장 · 오전 10:14           │
│          눌러서 연차신청서 결재로 이동 →  │
├───────────────────────────────────┤
│ [메시지] 이번 주 회의 자료 확인 부탁드립니다 │
│          박대리 · 오전 9:30            │
└───────────────────────────────────┘
```

| 딱지 | 무엇 | 오는 것 |
|---|---|---|
| `[결재]` | 결재 안내 | 승인 · 반려 · 상신 |
| `[메시지]` | 사람이 쓴 말 | 1:1 · 부서 · 단체 대화 |

⇒ **한 곳에서 다 보이니 놓치지 않고, 딱지로 갈리니 헷갈리지 않는다.**
DDL 반영 = `chat_messages.msg_kind` (`text` · `approval`).

### 9-4. 어느 방으로 / 누가 보낸 것으로 (사장님 결재)

| | 결재 |
|---|---|
| **어느 방** | 🔴 **결재자 ↔ 신청자 1:1 방** — 없으면 그때 연다 |
| **보내는 이** | 🔴 **결재한 사람 이름으로** (`김부장`) — 봇 이름으로 가리지 않는다 |

봇은 **배달하는 자리**일 뿐이다. 누가 결재했는지가 보여야 반려 시 **그 방에서 바로 되물을 수 있다.**

### 9-5. 실측 — 지금은 0건

`ApprovalController` 의 알림 호출 **0건**. 상무님이 *"결재 알림부터"* 라 한 자리가 실제로 비어 있었다.

🔴 **결재 로직은 손대지 않는다.** PRD §3-2 *"결재 엔진 재작성 ❌"*.
메시지 발송 호출만 **추가**한다 (헌법 #1 — 수정 OK, 덮어쓰기 금지).

🔴 **메시지 발송 실패가 결재를 막으면 안 된다.** try-catch + `LogWarning` (헌법 #15 — 빈 catch 금지).
결재는 성공했는데 메시지가 안 갔다고 결재가 취소되면 **더 큰 사고다.**

```
  ○ 1:1 대화     → 사원 1명 고르기
  ○ 부서 대화     → 부서 고르기 (0건이면 안내)
  ○ 단체 대화     → 사원 여러 명 + 방 이름 입력
```

*"처음 보는 사람이 혼자 쓸 수 있냐"* — 세 갈래를 **한 자리에서** 고른다.

## 14. 검증 게이트 — 반증으로 확인할 것

> "됐다"가 아니라 **"안 되는 경우"** 를 찾는다.

| # | 반증 시나리오 | 기대 |
|---|---|---|
| V1 | A 가 자기가 안 낀 방 ID 를 주소에 넣는다 | ⛔ 막힘 |
| V2 | **부모계정**이 남의 1:1 방 ID 를 넣는다 | ⛔ 막힘 (§6-1) |
| V3 | 다른 테넌트 방 ID | ⛔ 막힘 |
| V4 | 계정 없는 사원을 초대 | ⛔ 목록에 없음 |
| V5 | A 가 B 에게 **B가 못 보는 급여명세서** 첨부 → B가 누름 | ⛔ 급여 화면에서 막힘 (§4-3) |
| V6 | 메시지 삭제 후 상대 화면 | ✅ 그대로 보임 (§6-2) |
| V7 | 아무도 안 읽음 | ✅ 읽은 수 `0` (보낸사람 제외, §5-3) |
| V8 | 부서 0건에서 메신저 진입 | ✅ 1:1·단체 정상 (§2-2) |
| V9 | 알림 서비스가 죽어 있을 때 결재 상신 | ✅ 결재는 성공 (§9) |
| V10 | 1:1 을 A→B, B→A 로 각각 연다 | ✅ 같은 방 (§2-4) |
| 🔴V11 | **메신저 API 로 문서를 생성**하려 한다 | ⛔ **그런 API 가 없다** (§4-5 경계 시험) |
