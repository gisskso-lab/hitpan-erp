## 2. 김삼성 상무 조언

> *"13화면을 다 만들어놓고 순서를 안 잡으면, 직원은 어디서 시작할지 모릅니다.
>  삼성에서도 그랬습니다. **기능이 없어서 안 쓴 게 아니라, 어디서부터 눌러야 할지 몰라서** 안 썼습니다."*

이 말은 히트판 정신과 같은 자리다 — *"쓰기가 겁나 쉬웠기 때문이다."*

### 2-1. 인사 워크플로우 6단계 — ERP 6단계와 같은 원리

```
① 계정   직원계정 생성 → 권한설정          ← 뿌리 (사장님 못박음)
② 신분   사원 등록 → 직급 → 부서            ← "이 사람이 누구인가"
③ 계약   전자근로계약서 → 서명              ← "언제부터 우리 직원인가"
④ 일상   근태 → 휴가·연차                   ← 매일 도는 것
⑤ 신청   연차신청 · 경비신청                ← 직원이 올리는 것
⑥ 결재   결재선 → 상신 → 승인 → 이력        ← 위가 판단하는 것
```

> *"히트판이 ERP 를 6단계로 잡은 건 잘한 겁니다. **인사도 똑같이 순서가 있습니다.**
>  지금 13화면은 이 순서 없이 나열돼 있습니다."*

### 2-2. 🔴 가장 큰 문제 — **③ 계약이 빠져 있다**

> *"②에서 ④로 바로 건너뜁니다. **입사일이 없는데 근태를 찍고 연차를 계산합니다.**"*

**연차는 입사일로 계산한다** — 1년 미만 월 1개 / 1년 이상 15개(법정).
입사일이 전자근로계약서에만 있고 근태·연차와 안 물리면 **연차 일수가 틀린다.**
숫자가 틀리는 게 아니라 **노동법 문제로 번진다.**

> *"화면을 하나 더 만드는 문제가 아니라 **순서를 바로잡는 문제**입니다."*

⚠️ **법무팀장 교차 확인 필요** — 근로기준법 연차 산정 기준.

### 2-3. 🔴 결재선은 **직급으로 짜야 한다** (상무님 단호)

> *"사람 이름으로 결재선을 짜면 **그 사람이 퇴사하는 날 회사의 모든 결재가 멈춥니다.**
>  삼성에서 실제로 겪었습니다."*

**현황**: `approval_line_steps` 에 `employee_id`(사람)와 `position_id`(직급)가 **둘 다** 있다.

**권고**
- 결재선은 **직급으로 정의**한다
- 실행 시점에 **그 직급인 사람을 찾아 넣는다**
- 사람 지정(`employee_id`)은 **대결(대리결재)** 용으로만 남긴다

⇒ 컬럼은 **둘 다 유지**한다(헌법 #1·#37 — 안 읽힌다 ≠ 잔재). **용도를 나눈다.**

### 2-4. 사내 메신저 — **결재 알림부터**

> *"메신저를 채팅으로 먼저 만들면 **잡담방**이 됩니다.
>  **'결재가 올라왔습니다' 알림부터** 붙이세요. 그러면 직원이 메신저를 켤 이유가 생깁니다.
>  채팅은 그 다음입니다."*

⇒ 1단계 **결재 알림** / 2단계 1:1 / 3단계 부서방.

## 3. 🔴 재설계의 구조적 쟁점 — 계정과 사원이 끊어진다

```
users(직원계정) ←── user_id ── employees(사원) ──→ 결재선·근태·휴가·계약서
                     ↑ DEFAULT NULL
```

**화살표가 거꾸로다.** 계정이 뿌리가 아니라 **사원에 딸린 선택 항목**이다.

⇒ **계정 없는 사원**이 결재선에 들어갈 수 있고, 그 사람은 **로그인할 수단이 없어 결재가 멈춘다.**
**헌법 #20(워크플로우는 절대 안 끊긴다) 정면.**

⚠️ 어제(챕터3)는 **화면 이동만** 연결했다. **데이터 축은 안 건드렸다.**

## 3-1. 🔴🔴 사장님이 짚은 결정적 지점 — **MDB 마이그레이션된 직원**

> *"MDB 데이터 마이그레이션시, **MDB통해 마이그레이션된 직원에 대해!!!**"*

**PM 이 완전히 놓치고 있던 자리다.**

레거시 히트판에서 넘어온 직원은 **계정이 없다.** MDB 에는 사원 명부가 있지
그 사람들의 히트판 로그인 계정이 있을 리 없다.

그런데 §3 에서 *"계정이 뿌리"* 로 설계를 잡았다. 그대로 가면
**마이그레이션된 직원 전원이 뿌리 없는 가지**가 된다.

### 왜 이게 결정적인가

사장님이 못박은 **마이그 합격선 = "레거시와 숫자가 맞는다"**
(원본이 살아 있어 **대조가 반드시 일어난다**).

레거시에 직원 50명인데 히트판에 50명이 안 뜨면 **거기서 마이그레이션 실패다.**
그런데 *"계정 없는 사원 금지"* 로 막으면 **50명이 아예 안 들어온다.**

🔴 베타 대상 = **대리점 10곳 + 기존 5만 고객사.** 첫 화면이 *"자료 옮겼는데 직원이 없다"* 가 된다.

⇒ **§5 1번 질문은 이미 답이 나왔다: 막으면 안 된다.**
   다만 지금처럼 **NULL 로 방치**하면 결재선이 끊기는 문제는 그대로다. **둘 다 풀어야 한다.**

## 3-2. 🔴 사장님 확정 — **연결은 양방향이어야 정합하다**

> *"계정추가 → 직원등록 도 되야 하지만
>  **역으로 직원등록 → 계정등록도 되야 정합함**"*

```
users(계정) ←──────────→ employees(사원)
                1:1
      양쪽 어디서 시작하든 만나야 한다
```

| 순서 | 언제 쓰이나 |
|---|---|
| **계정 → 직원** | 신규 입사자를 대표계정이 직접 만들 때 |
| **직원 → 계정** | 🔴 **MDB 마이그레이션** · 명부 먼저 받고 계정 나중 |

**한 방향만 허용하면 나머지가 막다른 길이 된다.** 마이그레이션이 정확히 그 길에 걸려 있었다.

### ⇒ 핵심 전환

문제는 *"계정 없는 사원을 허용하느냐"* 가 **아니었다.**
허용하되 — **그게 미완성 상태라는 걸 시스템이 알고 있어야** 한다.

지금 `user_id = NULL` 은 **조용하다. 끊긴 걸 아무도 모른다.**

### 그래서 필요한 것 2개

**① 양쪽에 연결 버튼**
- 직원계정 화면 → `[사원 등록]` (계정 있는데 사원 없을 때)
- 사원관리 화면 → `[계정 발급]` (사원 있는데 계정 없을 때)

**② 끊긴 것을 보여주는 자리**
- *"계정 미발급 12명"* — **마이그레이션 직후 이게 떠야 한다**
- 인사담당자가 보고 하나씩 처리한다

> **김삼성 상무**: *"삼성에서도 인수합병 때 같은 일이 있었습니다.
>  **명부는 먼저 오고 계정은 나중에** 옵니다. 그게 정상입니다.
>  문제는 그 중간 상태를 **시스템이 모르는 척** 하는 겁니다.
>  '계정 미발급 12명' 이라고 띄워주면 인사담당자가 하나씩 처리합니다."*

### ✅ 사장님 결재 — **수동 확정** (자동 생성 금지)

> *"**수동!!!** 결국 직원계정은 **그 계정을 사용하고자 하는 직원이 결정**해야지"*

🔴 **이건 편의 문제가 아니라 원칙이다.**
자동 생성은 **쓸 의사가 없는 사람 몫까지 시스템이 정해버리는 것**이다.

**자동이었으면 따라왔을 문제 3개 — 수동이라 전부 사라진다**

| | 자동 생성 시 | 수동이라서 |
|---|---|---|
| **초기 비밀번호** | 50명분 전달 경로 필요 → 종이·문자 어느 쪽이든 **유출 경로 신설** | 없음 |
| **안 쓰는 계정** | 퇴사자·생산직 계정이 **열린 채 방치** (보안 매니저 반려 사유) | 없음 |
| **약관 동의** | 헌법상 **모든 사용자 첫 로그인 필수 동의**인데, 남이 만든 계정에 **본인이 동의한 적 없는** 상태 | 본인이 받으니 정상 |

⚠️ **약관 항목은 특히 크다** — 동의 일시·IP·약관 버전을 DB 에 기록해야 하는데,
자동 생성분은 **누가 동의했는지 자체가 성립하지 않는다.**

### ⬜ 남은 부담 하나 — 50명이면 50번

**제안(⬜사장님 확인 필요): 일괄이되 자동은 아닌 방식**

사원관리에서 **계정 미발급자 목록**을 띄우고, 대표가 **체크박스로 골라** 한 번에 발급.

```
계정 미발급 12명
 ☑ 김철수  영업부   ← 쓸 사람만 고른다
 ☑ 이영희  경리부
 ☐ 박생산  생산부   ← 계정 안 쓰는 직원은 안 고름
        [선택한 2명 계정 발급]
```

🔴 **"누가 쓸지" 는 여전히 사람이 정한다 — 자동이 아니다.**
다만 12번 화면 왕복할 것을 한 번에 끝낸다. **사장님 원칙을 지키면서 누르는 부담만 없앤다.**

⚠️ 마이그레이션은 **원본이 살아 있는 복사**다(자료 손실 경로 없음).
그러나 **숫자가 안 맞으면 그 자체가 실패**다.

## 3-3. 사장님 원칙 — 계정 없는 사원의 **근태 처리**

> *"직원계정은 없지만 직원등록이 되있는 사원은 근태기록을 없애고,
>  다만, 그룹웨어에 **결근표시만** 하도록 해야겠지"*
>
> **✅ 사장님 정정 (같은 대화에서)**:
> *"**로그인이 안되기 때문에 자동근퇴기록이 물리적으로 불가능하기 때문에**"*
> *"**없앤다기 보다, 결근만 작성하도록**"*

### ✅ 확정 — 삭제가 아니다. **애초에 성립하지 않는 것**이다

계정이 없으면 로그인이 안 되고, 로그인이 안 되면 **출퇴근 시각을 찍을 수단 자체가 없다.**
⇒ 자동 근태는 **기능을 막는 게 아니라 물리적으로 불가능**하다.

```
계정 없는 사원
 → 자동 출퇴근 기록: 물리적 불가능 (찍을 수단이 없다)
 → 근태 화면: 결근만 기록된다
 → 계정 발급되는 순간부터 정상 근태 시작
```

🟢 **설계가 단순해진다.** 기능을 차단하는 로직이 아니라,
**성립하지 않는 것을 성립하지 않는 대로 표시**하는 것이다.

⚠️ **PM 오독 기록**: PM 이 *"없앤다"* 를 **기존 데이터 삭제**로 읽고
근로기준법 3년 보존 의무·헌법 #1 을 들어 말리려 했다. **사장님 뜻은 그게 아니었다.**
⇒ **기존 근태 데이터는 삭제 대상이 아니다.** 이 건은 닫힘.

### ✅ 사장님 확정 — **예외만 기록한다**

> *"**결근, 지각 만 관리자가 체크**할수 있는 구조로 가는거지.
>  그럼 **체크이슈가 없는 날은 반대로 정상출근**이라는거잖아."*

```
계정 있는 직원   → 로그인이 곧 출근 기록 (자동)
계정 없는 사원   → 관리자가 결근·지각만 체크
                   체크 없는 날 = 정상출근
```

🟢 **관리자가 매일 30명을 찍는 게 아니라 문제 있는 사람만 찍는다.**
30명 중 결근 1명이면 **하루 한 번** 누르면 끝난다.
⇒ 레거시 히트판이 살아남은 이유 그대로다 — *"쓰기가 겁나 쉬웠기 때문이다."*

**⇒ PM 이 제안하던 `결근(계정없음)` 표기는 필요 없어졌다.**
결근은 이제 **관리자가 직접 판단해 찍은 것**이다. 시스템이 추측해 붙인 게 아니므로
이유를 덧붙일 게 없고, 급여·징계로 이어져도 **찍은 사람이 명확**하다.
⚠️ PM 이 *"시스템이 자동으로 결근을 붙인다"* 는 **한 단계 앞선 전제**로 고민하고 있었다.

### 🔴 ⬜ 이 방식의 구멍 — **아무도 안 찍으면 전원 정상출근**

*"체크 없음 = 정상출근"* 은 뒤집으면 **관리자가 잊어버린 날도 전원 정상출근**이 된다.

실제로 결근한 사람이 있었는데 아무도 안 찍었으면 기록상 **정상 출근**이 되고 급여가 그대로 나간다.
분쟁이 나면 **회사가 반박할 근거가 없다.**

> **김삼성 상무**: *"예외 기록 방식은 삼성도 씁니다. 다만 **월말 마감**을 반드시 둡니다.
>  인사담당자가 한 달치를 확인하고 닫습니다. 닫기 전엔 언제든 고칠 수 있고,
>  닫은 뒤엔 이력이 남습니다. 그게 없으면 **아무도 안 본 달**이 생깁니다."*

### ✅ 사장님 확정 — **월마감을 결재로 닫는다**

> *"**월마감에 인사기록에 대한 결재를 인사담당자, 대표 결재라인으로 받고 최종 반영**"*

🔴 **이것이 ④ 일상과 ⑥ 결재를 잇는 고리다.**

```
① 계정 → ② 신분 → ③ 계약 → ④ 일상(근태) → ⑤ 신청 → ⑥ 결재
                                └──────── 월마감이 이 둘을 잇는다 ────────┘
```

지금까지 결재는 **연차·경비 같은 개별 건**만 돌았고, **근태는 근태대로 쌓이고 결재는 결재대로** 돌았다.
월마감 결재가 그 사이를 닫는다. ⇒ 김삼성 상무가 지적한 **"아무도 안 본 달"** 이 사라진다.
**닫으려면 반드시 누군가 봐야 하기 때문이다.**

**확정 흐름**
```
한 달 동안   관리자가 결근·지각만 체크 (안 찍은 날 = 정상출근)
월말         인사담당자가 한 달치 확인 → 결재 상신
             대표 승인
승인 후      최종 반영 — 이 달의 근태가 확정된다
```

🟢 **새로 만들 게 아니다.** 이미 있는 결재 기능(`approval_documents` 등 7테이블)에
**문서 유형 하나를 추가**해 근태를 결재 문서로 올리는 것뿐이다.

### ✅ 사장님 확정 — **(나) 고칠 수 있되 이력이 남는다**

> *"**(나) 고칠 수 있되 이력이 남는다 — 누가 언제 뭘 바꿨는지 기록**"*

```
승인 후에도 수정 가능
 → 단, 누가 · 언제 · 무엇을 · 왜 바꿨는지 전부 기록
 → 승인 당시 숫자와 현재 숫자를 대조할 수 있다
```

🔴 **핵심은 "못 바꾸게" 가 아니라 "몰래 못 바꾸게" 다.**
승인 시점 값이 남아 있으면 대표가 승인한 숫자와 지금 숫자를 언제든 맞춰볼 수 있다.

⚠️ **PM 은 (가) 잠금을 권했다. 사장님 판단이 맞다.**
**인사 정정은 실제로 자주 일어난다** — 결근으로 찍었는데 병가였다, 지각이 아니라 외근이었다.
(가)로 잠그면 그때마다 **취소 결재 → 재상신**이라 히트판이 이기는 방식이 아니다.

> **김삼성 상무**: *"삼성도 정정을 막지 않았습니다. 막으면 사람들이 **결재를 안 올리고 버팁니다** —
>  틀린 걸 알면서도 고치기 번거로우니까요. 그게 더 위험합니다.
>  고칠 수 있게 하되 흔적을 남기면 **오히려 정직하게 고칩니다.**"*

🟢 **히트판이 이미 쓰는 방식과 같은 결** — 원장은 지우지 않고 **반대 기록을 쌓아** 바로잡는다(헌법 #3).
근태도 같은 결로 간다. ⇒ **수정 이력 테이블 필요**(승인 시점 스냅샷 + 변경 이력).

## 3-4. 🆕 인사문서 관리 (사장님 신규 지시)

> *"그리고 **인사문서 관리**도 하나 추가해야해. 이력서 / 재직증명서 / 사직서 / 퇴사증명서 등등"*

**김삼성 상무 정리 — 성격이 세 갈래다. 이게 설계를 가른다.**

### ① 회사가 **발급**하는 것 (증명서 — 직원이 요청)

| 문서 | 언제 |
|---|---|
| **재직증명서** | 대출·비자·자녀 학교 — **가장 많이 요청** |
| **경력증명서** | 이직할 때 |
| **퇴직증명서** | 퇴사 후 |
| **원천징수영수증** | 연말정산·이직 — 🔴 **법정 발급 의무** |
| 근로소득 지급명세서 | 연말정산 |
| 재직·급여 확인서 | 대출 심사 |
| 4대보험 가입확인서 | 공단 발급이나 회사가 대행 |

### ② 직원이 **제출**하는 것 (입사·퇴사 서류)

| 문서 | 언제 |
|---|---|
| **이력서·자기소개서** | 입사 |
| 주민등록등본 · 통장사본 | 입사·급여계좌 |
| 자격증·졸업증명서 | 입사 |
| **사직서(사표)** | 퇴사 |
| 서약서·보안서약서 | 입사 |

### ③ 양쪽이 **맺는** 것 (계약)

| 문서 | 비고 |
|---|---|
| **근로계약서** | 🟢 **이미 있다** — 전자근로계약서 + 전자서명 이력 |
| 연봉계약서 | 매년 |
| 비밀유지서약(NDA) | |

### 🔴 짚어야 할 것 3가지

**1. 근로계약서는 이미 돈다.** 인사문서 관리를 새로 만들면 **같은 문서가 두 군데** 생긴다.
⬜ 흡수할지 나란히 둘지 정해야 한다 (헌법 #1 — 기존 것을 덮지 않는다).

**2. ①과 ②는 완전히 다른 기능이다. 같은 화면에 넣으면 헷갈린다.**
- ① 발급 = **우리가 만들어서 준다** → 양식 · 직인 · 발급번호 · **발급대장**
- ② 보관 = **받아서 저장한다** → 파일 업로드 · 개인정보

**3. 🔴 ②는 민감정보 — 헌법 #5 정면.**
주민등록등본·통장사본은 **암호화 필수 컬럼** 대상. **보안 매니저 검토 필요.**

### ✅ 사장님 확정 — 발급 결재는 **(나) 인사담당자 승인 한 단계**

```
직원 요청 → 인사담당자 승인 → 발급
```

**왜 (다) 대표까지가 아닌가**: 재직증명서는 **자주 나간다.**
대표까지 가면 대표가 하루에 몇 번씩 눌러야 한다 — 히트판이 이기는 방식이 아니다.

⬜ **다만 확인 필요**: **급여가 찍히는 문서**(원천징수영수증·급여확인서)도 같은 한 단계인가,
아니면 이것만 대표까지 가나. 문서 종류별로 결재 단계가 갈릴 수 있다. → 김삼성 상무 검토.

### 🔴 발급대장 (상무님 강조)

> *"증명서는 **누구에게 언제 무엇을 떼어줬는지** 남아야 합니다.
>  나중에 위조된 재직증명서가 돌아다니면 **우리가 뗀 것인지 아닌지** 확인할 방법이 있어야 합니다."*

⇒ 발급 시 **발급번호 부여 + 발급 이력 기록**. 조회로 진위 확인.

## 4. 재점검 판정 기준 — 13화면 각각에 질문 하나

> **"이 화면이 다루는 사람은 직원계정에서 왔나, 계정 없이도 존재하나?"**

계정 없이 존재할 수 있으면 **거기가 끊기는 자리**다.
⚠️ 근태·휴가·전자근로계약서가 특히 의심 — 사람 단위로 도는데 계정 연결이 안 보인다.

## 5. 결재 현황

### ✅ 사장님이 닫아주신 것 (8/11 새벽) — 7건

| # | 항목 | 확정 내용 |
|---|---|---|
| 1 | 계정 없는 사원 | **막지 않는다** — 막으면 MDB 마이그 직원이 전부 못 들어온다(§3-1) |
| 2 | 연결 방향 | **양방향** — *"계정추가→직원등록 도, 역으로 직원등록→계정등록도 되야 정합"*(§3-2) |
| 3 | 계정 발급 | **수동** — *"그 계정을 사용하고자 하는 직원이 결정해야지"*(§3-2) |
| 4 | 계정 없는 사원 근태 | **자동기록 물리적 불가** — 삭제가 아니다(§3-3) |
| 5 | 근태 기록 방식 | **예외만 체크** — 결근·지각만, 안 찍은 날 = 정상출근(§3-3) |
| 6 | 월마감 | **인사담당자 → 대표 결재 후 최종 반영**(§3-3) — ④일상과 ⑥결재를 잇는 고리 |
| 7 | 확정 후 수정 | **(나) 고칠 수 있되 이력이 남는다**(§3-3) — *"몰래 못 바꾸게"* |
| 8 | 인사문서 발급 결재 | **(나) 인사담당자 승인 한 단계**(§3-4) |

### ⬜ 아직 안 닫힌 것 — 5건 (내일 김삼성 상무 검토)

| # | 질문 | 왜 필요한가 |
|---|---|---|
| 1 | **결재선 = 직급** 으로 가나 | 상무님 권고. *"사람으로 짜면 퇴사하는 날 모든 결재가 멈춘다"* · 기존 결재 데이터 처리 동반 |
| 2 | **입사일 → 연차 자동계산** 붙이나 | 법정 기준이라 안 붙이면 **숫자가 틀린다** → 노동법 문제. 법무팀장 교차 확인 |
| 3 | 메신저 **결재알림 먼저 / 채팅 나중** | 범위 확정 |
| 4 | 계정 **체크박스 일괄 발급** UI | 50명이면 50번 누르는 부담 해소(§3-2) |
| 5 | 급여 관련 문서도 **한 단계**인가 | 원천징수영수증·급여확인서는 대표까지 가나(§3-4) |
| 6 | 근로계약서 **중복** 처리 | 이미 도는 전자근로계약서를 흡수하나 나란히 두나(§3-4) |
