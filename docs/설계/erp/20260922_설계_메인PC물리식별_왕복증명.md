## 2. 왜 지금 방식이 안 되는가 (요약 · 상세는 [1-V])

```csharp
// MainPcOnlyAttribute.cs:38 — 현행
return !viaTunnel && isLoopback;        // 터널 헤더가 있으면 무조건 false
```

고객은 **도메인으로 접속한다.** 도메인 접속은 Cloudflare 가 `CF-Connecting-IP` 를 반드시 붙인다.
⇒ **첫 조건에서 항상 탈락한다.**

그리고 IP 로는 영영 못 가린다 — cloudflared 가 **그 PC 안에서** 히트판을 다시 부르므로
서버가 보는 소켓 주소는 **외부 접속이든 메인PC든 항상 `127.0.0.1`** 이다.
같은 사무실이면 공인 IP 도 같다(실측 `124.194.59.154`).

> **그러므로 판정의 축을 「어디서 왔나(IP)」에서 「무엇을 증명할 수 있나」로 옮긴다.**

## 3. 설계 — 「왕복 증명」

### 3-1. 한 줄 요약

> **브라우저가 자기 PC 안의 히트판을 두드려 증표를 받아 온다.**
> 받아 오면 메인PC, 못 받아 오면 클라이언트. **고객은 아무것도 하지 않는다.**

### 3-2. 무엇이 증거인가

메인PC 와 클라이언트 PC 의 차이는 **터널을 지나와도 사라지지 않는다**:

| | 메인PC | 클라이언트 PC |
|---|---|---|
| 그 PC 안에 히트판 본체 | 🟢 있다 | 🔴 없다 |
| 그 PC 안에 `hitpan-keys.conf` | 🟢 있다 | 🔴 없다 |
| `http://127.0.0.1:5257` 를 두드리면 | 🟢 **자기 히트판이 답한다** | 🔴 **아무도 없다** |

⚠️ API 는 **루프백 전용 바인딩**이다(실측: `LocalAddress = 127.0.0.1`).
즉 클라이언트 PC 가 이 주소를 두드리면 **자기 PC 를 두드리는 것**이고, 거기엔 히트판이 없다.
**남의 메인PC 를 두드릴 방법이 없다.** 이것이 이 설계의 물리적 근거다.

### 3-3. 흐름 (3왕복)

```
 브라우저(도메인)                 서버 = 히트판 본체 (같은 프로세스)
      |
 (1)  |-- POST /api/devices/mainpc-challenge --------->  1회용 표 N 발급
      |   (터널 경유)                                     · 60초 유효 · 1회 사용
      |<-------------- { challenge: N } ---------------|  · 세션(JWT jti)에 묶는다
      |
 (2)  |-- POST http://127.0.0.1:5257/api/devices/mainpc-proof  { N }
      |   🔴 터널을 안 지난다 — 브라우저가 자기 PC 로 직접 보낸다
      |   ⚠️ 서버는 이 요청을 「CF헤더 없음 + 루프백」으로 받는다 = 진짜 로컬
      |<------ { proof: HMAC(설치키, N + tenantId + 만료) } ------|
      |
 (3)  |-- POST /api/devices/mainpc-verify { N, proof } ->  자기 키로 재계산해 대조
      |   (터널 경유)                                     · N 미사용·미만료·세션 일치
      |<------------ { isMainPc: true } ---------------|  · 통과 → 세션에 메인PC 표식
```

**클라이언트 PC 는 (2)에서 끝난다.** 두드릴 히트판이 없어 연결 자체가 실패한다.
⇒ 증표를 못 얻고, (3)을 못 한다. **거짓말할 여지가 없다.**

### 3-4. 🔴 최초 등록 — 「메인PC 등록」 (사장님 결재 2026-09-22)

> *"히트판 첫 설치후 접속때 … 그때 **메인PC등록** 이라는 팝업을 만들었으면 좋겠어"*
> *"아니면 **최초 로그인후 메인PC등록을 먼저** 해."*

**이 설계에는 순환 문제가 있었다** — 키를 만들려면 메인PC 를 알아야 하고,
메인PC 를 알려면 키가 필요하다. **사장님의 등록 팝업이 그 고리를 끊는다.**

```
메인PC 가 아직 등록되지 않은 회사 · 부모계정이 로그인하면
   ↓
[메인PC 등록] 팝업 — 사람이 누르는 건 여기 한 번뿐이다
   ↓
 (1) 브라우저가 자기 PC 안의 히트판을 두드린다        ← 🔴 키가 없어도 이건 된다
 (2) 응답이 오면 = 이 PC 안에 본체가 있다 = 메인PC
 (3) MAINPC_PROOF_KEY 생성 → TpmKeyService.SealKey() 로 봉인
 (4) tenant_devices 에 메인PC 등록 (is_main_pc=1)
   ↓
이후로는 사람을 안 묻는다 — §3-3 왕복 증명이 매번 자동으로 돈다
```

⚠️ **클라이언트 PC 에서 이 팝업을 눌러도 안전하다.** (1)에서 두드릴 히트판이 없어 실패한다.
*"이 컴퓨터는 메인PC 가 아닙니다"* 로 끝난다. **자칭할 방법이 없다.**

### 🔴 팝업은 딱 한 번만 보인다 (사장님 결재 2026-09-22)

> *"다음 접속부터는 메인PC등록 팝업이 안보이고, **바로 접속**되도록"*

```
로그인 직후 — 화면 뒤에서 조용히 왕복을 먼저 돌려 본다 (고객은 모른다)
   │
   ├─ 이미 메인PC 가 등록돼 있다   → 팝업 없음. 바로 들어간다
   ├─ 미등록 + 왕복 성공(= 이 PC 가 메인PC)  → 🔵 [메인PC 등록] 팝업 1회
   └─ 미등록 + 왕복 실패(= 클라이언트 PC)    → 팝업 없음. 바로 들어간다
```

⚠️ **팝업은 메인PC 에서만 뜬다.** 클라이언트 PC 직원은 이 팝업을 **평생 못 본다** —
누르고 실패하는 경험조차 만들지 않는다. *"고객은 인증키가 도는지 안 도는지 모르게"* (사장님).

⚠️ 등록이 끝나면 그 회사에는 `is_main_pc=1` 줄이 생기므로, **누가 어디서 로그인하든 팝업은 다시 안 뜬다.**

🔴 **반자동 원칙이 제자리로 돌아온다** — 사람이 정하는 것은 **최초 1회 등록**뿐이다.
현행 결함(매 접속마다 누구나 자칭)과 여기서 갈린다.

⚠️ **온보딩 화면(환영·사용방법)은 이 작업 범위가 아니다.** 나중에 온보딩이 생기면
이 팝업을 그 안으로 옮긴다. **신규 고객도 기존 고객도 「최초 로그인 후」 한 경로로 처리된다** —
이미 설치된 고객(사장님 PC 포함)은 온보딩을 거친 적이 없기 때문이다.

### 3-5. 🔴 메인PC 변경 — 되돌릴 수 있어야 한다 (사장님 결재 2026-09-22)

> *"되돌리는 기능도 있어야됨. 고객사가 컴퓨터를 새로 구입해서 메인PC를 변경할수도 있으니까."*
> *"백업 데이터베이스는 히트판의 자료관리→자료백업/복구 기능에서 **고객사가 알아서 복구**를 하겠지."*

**없으면 구멍이 된다**: 새 PC 로 옮겨도 DB 에 옛 메인PC 등록이 남아 있으면
*"이미 등록됨"* 으로 판정돼 팝업이 안 뜬다 ⇒ **새 PC 가 영원히 메인PC 가 못 된다.**
옛 PC 가 고장 나 꺼져 있으면 해제할 방법도 없다.

#### 갈래 ① 자동 — 히트판이 스스로 안다

🟢 **물어볼 필요가 없다.** 봉인은 **그 PC 에서만 풀린다.**
풀리지 않으면 그것이 곧 *"이 컴퓨터는 등록된 그 컴퓨터가 아니다"* 라는 뜻이다.
`TpmKeyService.IsSealedKeyValid()` 가 이미 그 용도로 있다(*"마더보드 교체·BIOS 리셋 감지"*).

```
새 PC 에서 로그인
  → 왕복은 성공한다 (본체가 이 PC 에 있으니까)
  → 그런데 봉인이 안 풀린다 = 등록된 그 PC 가 아니다
  → 🔵 "메인PC 를 이 컴퓨터로 변경하시겠습니까?" (부모계정)
  → [예] → 새 키 생성·봉인 → 🔴 기존 줄을 **갱신**한다 (새 줄을 만들지 않는다)
```

⚠️ **옛 PC 가 죽어 있어도 된다.** 새 PC 가 스스로 증명하기 때문이다.

#### 갈래 ② 수동 — 고객이 **[메인PC 연결]** 로 시작한다 (사장님 결재 2026-09-22)

> *"메인pc연결 → 변경하실 메인PC에 히트판이 설치되어 있습니까 (y/n)
>   y : 자동연결 / n : 설치후 연결"*

고객은 **[메인PC 연결] 하나만** 누른다. 그 뒤는 히트판이 길을 알려 준다.

```
[메인PC 연결]  (설정 · 부모계정)
   ↓
"변경하실 메인PC에 히트판이 설치되어 있습니까?"
   ├─ [예] → 🟢 자동 연결
   │         "그 컴퓨터에서 히트판에 접속하시면 자동으로 연결됩니다"
   │         → 새 PC 에서 로그인하는 순간 갈래 ①이 돈다 (봉인 불일치 감지)
   │
   └─ [아니요] → 설치 후 연결
             설치파일 내려받기 안내 → 고객이 받은 파일 실행 → 설치
             → 그 PC 에서 접속하면 갈래 ①이 돈다
```

🔴 **[아니요] 갈래의 한계를 고객에게 숨기지 않는다** — 브라우저는 받은 프로그램을
**자동으로 실행할 수 없다**(Windows 차단 · 우회로 없음). *"받은 파일을 한 번 눌러 주세요"* 가 필요하다.
**고객 손은 그 한 번뿐**이고, 그 뒤 설치·연결은 전부 자동이다.

⚠️ 설치파일은 **랜딩페이지가 배포한다**(3시스템 분리 — 랜딩 = 가입·결제·**다운로드**).
   ERP 는 그리로 보내기만 한다. ERP 가 설치본을 들고 있지 않는다.

⚠️ **연결이 끝나면 옛 등록은 자동으로 정리된다**(갈래 ①이 기존 줄을 갱신한다).
   고객이 따로 해제할 일이 없다 — **해제 버튼을 먼저 찾게 만들지 않는다.**

⚠️ **해제해도 위험하지 않다.** 등록은 여전히 **물리 증명이 있어야** 한다.
외부 PC 가 남의 등록을 지운 뒤 자기를 등록하는 일은 성립하지 않는다(두드릴 히트판이 없다).

#### 🔴 실제 이전 절차 — 팝업이 두 번 뜨는 것은 정상이다

자료 이전은 **기존 자료관리(백업/복구)가 한다** — 사장님 결재. 새로 만들지 않는다.

```
① 새 PC 에 히트판 설치 (DB 가 비어 있다)
② 미등록이므로 [메인PC 등록] 팝업 → 등록          ← 팝업 1회차
   🔵 등록 직후, DB 가 비어 있으면 **「자료 복구」 안내 팝업** (사장님 결재)
      *"기존에 쓰시던 자료가 있으면 [자료관리 → 자료복구] 에서 가져오세요"*
      ⚠️ 이 안내가 없으면 고객이 **빈 화면을 보고 자료가 날아간 줄 안다.**
         갈 곳을 알려 주지 않는 안내는 흐름이 끊긴 것이다(#20)
③ 자료관리 → 자료복구 → 옛 백업본 복원
④ 🔴 복원이 옛 DB 를 덮어쓴다 ⇒ 옛 메인PC 등록이 되살아난다
⑤ 봉인 불일치 감지 → [메인PC 변경] 팝업 → 재등록   ← 팝업 2회차
```

⚠️ **④는 버그가 아니라 복원의 정의다**(옛 DB 를 그대로 되살리는 것).
   ⑤가 그것을 받아 정리한다. **이 두 번을 설계에 적어 두지 않으면
   다음 사람이 *"왜 두 번 뜨지?"* 하고 ⑤를 없애 버린다** — 그러면 갈래 ①이 통째로 죽는다.

⚠️ 새 PC 에 히트판이 **아직 없는 경우**(클라이언트로 접속해 이전을 시작)는 **이 작업 범위 밖**이다 —
   설치파일 내려받기 안내가 필요하고, 🔴 **브라우저는 프로그램을 자동 실행할 수 없다**(Windows 차단).
   고객이 받은 파일을 한 번 눌러야 한다. 별도 작업으로 뺀다(§11).

### 3-6. 키를 훔쳐가도 못 쓴다 — `TpmKeyService`

> 사장님: *"키는 **복호화** 시키는건?"*

히트판에 이미 [`TpmKeyService`](../../../src/HitPan.Application/Services/Security/TpmKeyService.cs) 가 있다. **새로 만들 것이 없다.**

- **TPM 2.0 칩에 봉인** (`NCRYPT_PLATFORM_KEY_FLAG`) — *"PC 외부 추출 불가"*
- TPM 없는 PC 는 **DPAPI 폴백** (`DataProtectionScope.LocalMachine` — 그 PC 에서만 풀린다)
- **마더보드 교체·BIOS 리셋 감지** (`IsSealedKeyValid` · 워치독 WS-23 연계)

⇒ `hitpan-keys.conf` 를 통째로 복사해 다른 PC 에 심어도 **봉인이 안 풀린다.**
   §5 에 적은 구멍(파일 탈취 → 메인PC 복제)이 이것으로 닫힌다.

### 3-7. 왜 (2)가 「물리적」인가

(2)는 **네트워크를 타고 나가지 않는다.** 브라우저가 자기 컴퓨터 안에서 자기 컴퓨터에게 묻는다.
이 요청은 Cloudflare 를 거치지 않으므로 서버가 **CF헤더 없음 + 루프백**으로 받는다 —
현행 판정이 유일하게 믿을 수 있다고 본 바로 그 조건이다.

즉 **현행 판정을 버리는 게 아니라, 그 판정이 성립하는 통로를 따로 열어 주는 것**이다.

## 4. 왜 이 형태인가 — 기각한 안들

| 안 | 기각 사유 |
|---|---|
| **IP·헤더로 판정** (현행) | 🔴 터널이 소켓 주소를 지운다. 같은 사무실이면 공인 IP 도 같다 → **원리적으로 불가** |
| **장치 이름으로 판정** | 🔴 브라우저가 장치 이름을 서버에 못 보낸다(보안상 차단). 그리고 *"이 PC의 이름 바꾸기"* 로 바뀐다 |
| **브라우저에 증표를 저장** | 🟡 되지만 **브라우저를 바꾸면 깨진다.** 사장님 요구(*"어떤 브라우져로 접속을 해도"*)를 못 지킨다 |
| **클라이언트 PC 에 프로그램 설치** (A안 2번) | 🔴 *"온전한 웹 SaaS 로 보이게"* 와 충돌. ActiveX 는 실행할 브라우저가 이미 없다 |
| **사람이 [이 컴퓨터가 메인] 선택** (현행 우회로) | 🔴 **누구나 자칭 가능.** 사장님 판정: 반자동 원칙의 오용 |
| **🟢 왕복 증명** (본 설계) | 브라우저 무관 · 설치 0 · 고객 조작 0 · 자칭 불가 |

## 5. 보안 — 공격 시나리오와 방어

| # | 공격 | 방어 |
|---|---|---|
| A-1 | 외부 PC 가 `isMainPc=true` 를 본문에 실어 보냄 | 🟢 서버가 **본문을 안 읽는다.** 증표만 본다 |
| A-2 | 메인PC 에서 받은 증표를 복사해 외부에서 씀 | 🟢 표 N 은 **1회용 · 60초 · 그 세션(jti)에만** 유효 |
| A-3 | 표 N 을 미리 잔뜩 받아 둠 | 🟢 증표 만료가 N 발급 시각에 묶인다. 세션이 바뀌면 무효 |
| A-4 | 같은 PC 에 가짜 서버를 5257 로 띄워 증표를 위조 | 🟢 **HMAC 을 위조하려면 `hitpan-keys.conf` 의 설치키가 있어야 한다.** 그 파일은 메인PC 에만 있다 |
| A-5 | 다른 회사 히트판이 그 PC 에 깔려 있음 | 🟢 증표에 `tenantId` 를 섞는다. 남의 회사 키로는 우리 서버 검증을 못 통과 |
| A-6 | 대표 계정 비번 탈취 후 외부 접속 | 🟢 **자료관리가 안 열린다** — (2)를 못 하므로 메인PC 가 못 된다 (**현행은 열린다**) |
| A-7 | 브라우저 확장·악성 스크립트가 로컬 통로를 두드림 | 🟡 CSP 를 **그 주소 하나로만** 연다(§6-2). 그 PC 에 이미 악성코드가 있으면 이 설계 밖의 문제 |

### ⚠️ 이 설계가 막지 못하는 것 (정직하게 적는다)

- **메인PC 그 컴퓨터 앞에 앉은 사람**은 당연히 메인PC 로 인정된다. 그건 설계 의도다
- 메인PC 에 원격데스크톱으로 들어온 사람도 메인PC 로 보인다 — **원격 접속 통제는 이 설계 밖**
- `hitpan-keys.conf` 를 통째로 훔쳐 다른 PC 에 심으면 그 PC 가 메인PC 가 된다
  ⇒ 🔴 **이 파일의 접근 권한은 별도 확인이 필요하다** (§10 D-3)

## 9. 순서 (P 단계)

```
P1  MainPcProofService + API 3개          ← 서버만. 화면 무변경. 여기까지는 아무 영향 없다
P2  CSP 한 줄 + 브라우저 JS               ← 왕복이 실제로 도는지 실측 (G-1·G-2)
P3  [메인PC 등록] 팝업 (§3-4)             ← 최초 1회 · 키 생성 + TPM 봉인 + 기기등록
P4  MainPcOnly 두 곳에 갈래 추가          ← 자료관리가 열린다
P5  DeviceAuthGate 자칭 경로 차단         ← 결함 봉합 (G-7)
P6  메인PC 변경·해제 (§3-5)               ← 새 PC 이전 · 되돌리기 (G-14~G-19)
```

🔴 **P6 를 빼고 내보내면 안 된다.** 없으면 고객이 컴퓨터를 바꾸는 순간
**메인PC 를 영영 못 옮긴다** — 옛 등록이 남아 팝업이 안 뜨기 때문이다.

⚠️ **설치본에 키를 미리 심지 않는다.** 사장님 결재로 **키는 P3 등록 시점에 생성**된다.
⇒ 이미 깔린 고객도 **다음 로그인에 팝업 한 번**으로 끝난다.
⇒ 🟢 **설치본·업데이트 흐름을 건드리지 않는다**(#43 워치독 로직 불변).

⚠️ **P3 는 P1·P2 가 돌아야 성립한다** — 팝업이 누르는 것이 곧 왕복의 첫 바퀴이기 때문이다.
