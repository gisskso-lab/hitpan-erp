## 0. 설계 원칙 — 이번 봉합의 성격

> **고칠 것은 「계산」이 아니라 「닿는 범위」다.**

실측 결과 계산 로직은 전부 살아 있다. 틀린 것은 세 가지다.

| # | 무엇이 | 실제 |
|---|---|---|
| 1 | **반품·취소가 재고·회계·원장 세 곳에 고르게 닿는가** | 🔴 안 닿는다 |
| 2 | **가드가 고객이 지나가는 경로에 있는가** | 🔴 없다 (다른 경로에 있다) |
| 3 | **화면이 맞는 표를 보는가** | 🔴 안 본다 |

⇒ **계산 로직을 다시 짜지 않는다.** 전달 경로와 범위를 맞춘다.

### 🔴 설계 대원칙 — 막지 말고 없애라

가드는 *"넘으려는 시도"* 를 막는다. 하지만 **진입점이 늘면 가드는 반드시 한쪽에만 붙는다**
— P0-1 이 정확히 그 사고다(가드는 실재하는데 화면 경로엔 없었다).

**화면이 잔량만큼만 채우면 넘을 경로 자체가 사라진다.**
이 설계는 가능한 한 **가드 대신 구조**를 쓴다.

## 1. 도메인 모델 — 상태 정의 (결재 7)

### 1-1. 상태 전이도

```
수주서      수주완료 ─┐
                      ├→ 판매완료 → 판매확정 → 계산서발행 → 전자발행
거래명세서            ┘     │           │                      │
                          삭제        취소                 반품완료 → 반품확정
                    (원장 무접촉) (원장 역기록)         (마이너스 전표)  (국세청 발송)
```

### 1-2. 상태 사전

| 상태 | 뜻 | 원장 영향 | 되돌리기 |
|---|---|---|---|
| 수주완료 | 수주 완료 (수주서 전용) | 무접촉 | 삭제 |
| 판매완료 | 거래명세서 작성·저장 | 무접촉 | **삭제** |
| **판매확정** | 판매확정 버튼 | 🔴 **재고 OUT · 미수금 ↑ · 분개** | **취소** |
| 계산서발행 | 계산서 발행(일괄 대기 포함) | 세금 문서만 | **취소** |
| 전자발행 | 국세청 전송 완료 | — | 🔴 **마이너스만** |
| **반품완료** | 마이너스 전표 O · 국세청 미발송 | 🔴 **재고 IN · 미수금 ↓ · 역분개** | — |
| **반품확정** | 마이너스 전표 O · 국세청 발송 | 상계 완결 | — |
| 취소 | 판매확정 이후 되돌림 | 원장 역기록 | — |

### 1-3. 설계 결정 4건 (결재 7 추가결정)

| # | 결정 | 설계 반영 |
|---|---|---|
| ① | **워딩만 변경** | DB enum 값 **불변**. 표시 계층에서만 한글 매핑 ⇒ **마이그 부담 0** |
| ② | **분할출고는 상태가 아니라 뱃지** | `판매완료 [분할출고]` — 파생 표시값. **컬럼 신설 없음**. 거래조건 다양성으로 상태화 시 **조합 폭발** |
| ③ | **마이너스 명세서는 같은 상태 + 부호** | 별도 상태 안 만듦. 부호로 구분 |
| ④ | **취소 상태 유지** | 계산서는 2단(삭제/마이너스), **명세서는 3단**(삭제/취소/마이너스) — 판매확정 시점에 **이미 재고가 움직여서** |

🔴 **①이 이 설계에서 가장 중요한 판단이다.** DB 값을 안 건드리므로
기존 데이터·인덱스·통계·리포트가 **전부 그대로 산다.**

### 1-4. 되돌리기 3단 — 판정 기준은 「원장에 무엇이 갔느냐」

```
원장에 아무것도 안 갔다     →  삭제      (흔적 없이. 사슬 자체 삭제)
원장에 갔지만 내부에만 있다  →  취소      (INSERT ONLY #3 ⇒ 역기록으로 상계, 상태로 남김)
원장에 갔고 국세청까지 갔다  →  마이너스   (물리적으로 못 지움 ⇒ 마이너스 전표로 상계)
```

⚠️ **「삭제」는 사슬 자체 삭제**다 — 목록·현황·분석·통계에서 전부 빠진다.
🔴 다만 **원장 무접촉 상태에서만** 허용한다. 원장이 움직인 뒤엔 절대 삭제 경로가 없다(#3).

## 2. 잔량 기준 — P0-1·P0-2 동시 해결 (결재 4)

### 2-1. 판정식

```
출고 가능량 = 수주 주문수량 − 기출고수량      →  0 이면 차단
반품 가능량 = 판매수량     − 기반품수량      →  0 이면 차단
```

🔴 **이 한 줄이 P0-1(명세서 중복)과 P0-2(반품 무제한)를 동시에 푼다.**
별개 봉합 2건으로 본 것이 **같은 원리의 양면**이었다.

### 2-2. 왜 지금 안 되고 있나

| P0 | 현재 |
|---|---|
| P0-1 | `delivered_qty` 가 **확정 시점에만** 오른다 ⇒ draft 재전환으로 뚫린다 |
| P0-2 | **기반품수량을 아예 안 본다** |

### 2-3. 🔴 8/27 작11 가드와의 관계

⚠️ **현재 작11 가드가 정상 분할출고를 막고 있다.**

코드는 원래 잔량 로직(`OrderedQty − DeliveredQty`)을 **갖고 있었는데 가드가 덮었다.**

⇒ **가드를 지우는 게 아니라 잔량 기준으로 되돌린다.**
🔴 게이트가 내 봉합과 충돌하면 **지우기 전에 왜 있었는지 읽는다** — 작11 가드는
*중복생성 절대금지* 오더의 산물이다. 잔량 기준이 그 목적을 **더 정확히** 달성한다.

### 2-4. 반품 누적은 품목 단위 (결재 6)

```
명세서: A 10개 · B 5개

A −7 OK  →  A −2 OK(누적 9)  →  A −1 OK(누적 10 소진)  →  A −1 차단
B −5 OK                                                    ← A 와 무관
```

전량 소진 명세서 ⇒ **[반품하기] 버튼 자체 비활성**.

## 3. 마이너스 전표 사슬 (결재 2·3)

### 3-1. 왜 반품 메뉴가 아니라 마이너스인가

| 근거 | 내용 |
|---|---|
| 법정 방식 | **국세청 이세로에 「수정」 개념이 없다.** 마이너스 상계 + 재발행뿐 |
| 원장 정합 | `stock_ledger`·`journal_lines` 는 **INSERT ONLY**(#3). 마이너스가 구조와 맞는다 |
| 기결재 정합 | 8/25 결재(매출 반품확인 메뉴 전부 제거)와 **같은 방향** |

### 3-2. 🔴 사슬 근거는 선택이 아니다

> **사장님**: *"이 마이너스 전표의 근거가 뭔지는 **분명하게 사슬로 연결**을 시켜야해."*

**근거 없는 마이너스는 장부를 못 읽게 만든다.** 「왜 −100만원인가」에 답이 없으면 세무 대응 불가.

### 3-3. 층 전파 — 마이너스는 수주까지 올라간다

```
수주      1 + (−1) = 0
명세서    1 + (−1) = 0     ← 쌍둥이로 묶여 따라다닌다
```

🔴 **설계상 이것이 핵심이다.** 명세서 층에서만 상계하면
**수주 잔량이 안 돌아와** 그 위에 또 만들 수 있다 ⇒ P0-1 이 되살아난다.

⇒ **마이너스 전표는 잔량을 되돌리는 장치이기도 하다.** 결재 3 과 결재 4 는 한 몸이다.

### 3-4. 표기

```
목록 조회:   명-001     1,000,000
             └ 명-001R   −1,000,000   ← 원전표 바로 아래
```

- 원전표 번호 + `R` 접미 — 눈으로 짝이 보인다
- **원전표 바로 아래 배치** ⇒ 목록 자체가 **경리의 대사 화면**이 된다

## 4. 화면 설계 — 신설하지 않는다 (결재 5)

### 4-1. 진입점 2곳

```
판매목록 그리드 ─ [반품하기]
거래명세서 작성 ─ [세금] [반품하기]
```

### 4-2. 도착 화면 = 같은 거래명세서 화면

```
같은 거래명세서 화면 — 수량·금액이 (−)로 전량 채워진 상태
  · 반품 안 할 품목은 줄을 지운다
  · 수량 수정 가능
  · 이미 반품된 품목은 잔량만큼만
  · 거기서 마이너스 계산서까지 끊는다
```

### 4-3. 이 설계가 한 번에 푸는 것 4가지

| 효과 | 설명 |
|---|---|
| **히트판 정신** | 담당자가 **이미 아는 화면**. 교육 0 — *"처음 보는 사람이 혼자 쓸 수 있냐"* 통과 |
| **근거 연결 자동** | **원전표에서 눌러 들어오니** 사슬이 저절로 걸린다. 사람이 고를 일이 없다 |
| **수량 상한 자동** | 잔량이 채워지니 **가드로 막는 게 아니라 넘을 경로가 사라진다** |
| **경리 검증 화면** | 목록 배치(원전표 아래 (−))가 그대로 대사 화면 |

🔴 **새 화면 0개** — 새 화면은 곧 **새 진입점**이고, 진입점이 늘면 **가드가 또 한쪽에만 붙는다**(P0-1 재발).

## 5. 명세서 취소 → 사슬 삭제 (P0-3 봉합)

### 5-1. 현재 결함

`SalesService.cs:1181` 이 `total_sales` 를 **`sales_deliveries` 의 confirmed 합계로 통째로 재계산**한다.
🔴 **`sales_returns` 를 빼지 않는다.**

```
4월   반품 200만원 처리          → 미수 정상 차감
5월   전혀 다른 오타 명세서 1장 취소
        ↓  total_sales 재계산 = 명세서 합계만
      🔴 4월 반품이 사라지고 미수가 1,000만원으로 부활
```

🔴 **조용하다.** 오류도 경고도 로그도 없다.

### 5-2. 설계 방향

| 원칙 | 내용 |
|---|---|
| **재계산이 아니라 증감** | 통째로 다시 쓰는 방식 자체가 위험원. 취소된 그 건만 차감 |
| **재계산이 불가피하면 반품을 반드시 포함** | `SUM(명세서 확정) − SUM(반품 확정)` |
| ⚠️ **매입 코드 복붙 금지** | 매출반품은 **매출·미수** 축이다. 매입채무 ≠ 외상매출금 |

🔴 **매입엔 이 코드가 없다** — 매입에서 가져올 것이 없으므로 **신규 설계**다.

## 6. 업체별 원장 (P0-4 봉합)

### 6-1. 현재 결함

`GetStockLedgerAsync`(`ReportService.cs:2532~2590`)가
view=item 과 view=partner 를 **같은 `stock_ledger` 에서 GROUP BY 만 바꿔** 읽는다.

| 있어야 할 것 | 현재 |
|---|---|
| 잔량 = **금액** | 🔴 **개수** |
| 부가세 · 미수금 잔액 · 전표별 줄 · 이월잔액 | 없음 |

### 6-2. 🟢 계산은 이미 맞다

**`partner_balance.balance` 는 정확하다.**
고칠 것은 계산이 아니라 **화면이 어느 표를 보느냐**다.

### 6-3. 설계 방향

```
상품별 원장  →  stock_ledger    (수량 축 — 지금 그대로 맞다)
업체별 원장  →  금액 축으로 분리  (미수금 대사 화면)
                · 전표별 줄
                · 이월잔액
                · 부가세
                · 잔액 = partner_balance.balance 와 일치
```

⚠️ **상품별 원장은 건드리지 않는다.** 수량 축이 맞는 화면이다.

### 6-4. 🔴 영업 근거

더존·이카운트에서 「거래처원장」은 **미수금 대사 화면**이다.
**데모에서 수량이 나오면 제품 카테고리 자체를 의심받는다** — 기능 결함이 아니라 **영업 사고**.

## 7. 확정 건 삭제·수정 2단 통제 (결재 8)

```
1단  권한 검사        ← 이미 동작 중 (신설 아님)
2단  패스워드 재입력   ← 이번에 신설
```

| 항목 | 내용 |
|---|---|
| 대상 상태 | **판매확정 · 반품확정** + 이후(계산서발행 · 전자발행) |
| 대상 행위 | **삭제 · 수정 둘 다** |

🔴 **착수 전 실측 필수** — *"1단은 당연히 지금 동작하고 있는 거지"* 라는 전제를
**실측으로 확인**한다. 오늘 하루에만 *"이미 되어 있다"* 가 **두 번 틀렸다**.

⚠️ 참고: 8/21 실측에서 **확정 엔드포인트 5개 중 4개에 개별 권한 검사가 없었다**.
작11 에서 봉합했으나 **이번에 다시 확인한다**.

🔴 **미결 1건 (사장님 답 필요)**
- 패스워드는 **로그인한 본인** 것인가
- **유효시간**을 둘 것인가 (연속 작업 시 매번 물으면 번거롭다)
- **이력**을 남길 것인가

## 10. 🟢 게이트 설계 — 사장님 판정식이 그대로 게이트

결재 1 이 **글자로는 절대 못 만드는 게이트**를 준다.

`GetStockLedgerAsync` 는 view=item 과 view=partner 가 **같은 표를 GROUP BY 만 달리** 읽는다.
⇒ **같은 사실의 두 절단이니 총합이 반드시 같아야 한다.**

### 10-1. 교차검산 등식

```
G-1   Σ(상품축 수량)  ==  Σ(업체축 수량)
G-2   Σ(회계 매출)    ==  Σ(명세서 확정 − 반품 확정)
G-3   Σ(재고 OUT)     ==  Σ(명세서 확정 수량 − 반품 확정 수량)
G-4   partner_balance.balance  ==  업체별 원장 잔액
G-5   수주 잔량 0  ⇒  추가 명세서 생성 거부
G-6   품목 반품 잔량 0  ⇒  추가 반품 거부
G-7   명세서 취소 후  total_sales  ==  (명세서 확정 − 반품 확정)   ← P0-3
```

🔴 **G-1·G-2·G-3 은 봉합이 깨지면 재고는 2배 빠지는데 회계는 1배라 반드시 FAIL 한다.**
문자열 검사로는 흉내 낼 수 없다.

### 10-2. 게이트 규율 (검증축 요구 — SoD)

| # | 규율 |
|---|---|
| 1 | 🔴 **게이트는 봉합자가 짜지 않는다** — 자기가 고친 자리만 검사하게 된다 |
| 2 | 🔴 **짜면 곧바로 봉합 빼고 FAIL 확인** — 초록이면 가짜 |
| 3 | 🔴 **글자검사 금지** — 파일 읽어 문자열 찾기는 게이트가 아니다 |
| 4 | 🔴 **실제로 불러 봐라** — 로직을 죽여도 통과하면 가짜 |
| 5 | **대조군 필수** — 없는 경로와 비교 |
| 6 | 🔴 **질문을 *"고쳤나"* 가 아니라 *"갔나"* 로** — 만드는 쪽만 재면 전부 통과하고도 반려난다 |
