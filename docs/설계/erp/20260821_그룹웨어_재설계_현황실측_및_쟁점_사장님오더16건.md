## 2. 🔴 실측 중 발견한 결함 2건 — 오더보다 먼저 봉합해야 한다

### 결함① 휴직 결재는 **구조적으로 절대 안 올라간다**

사장님 오더 9번은 *"휴직관리 존치"* 다. 그런데 **휴직 결재는 지금 100% 실패한다.**

추적한 사슬 (전부 실제 파일 확인):
```
AbsenceService.cs:42   const string DocType = "absence";
                       → TryCreateApprovalAsync(... "absence" ...)   (363줄)

ApprovalTriggerHelper  if (!setting.IsEnabled) return;   ← 조용히 종료
                       (approval_settings 에 absence 행이 있어야 IsEnabled 가 참)

ApprovalService.cs     GetSettingsAsync:
                         foreach (var (docType, label) in DocTypeLabels)   ← 설정행을 여기서 생성
                       DocTypeLabels 에 "absence" 없음   (grep 실측 0건)
```

⇒ **설정화면에 "휴직" 행이 아예 안 뜬다 → 켤 방법이 없다 → 상신은 항상 조용히 실패.**

> 🔴 **화면은 "결재상신" 버튼을 보여준다.** 눌러도 아무 일이 안 일어난다.
> 이건 **화면이 사용자에게 거짓말하는** 구조다 — 어제 기본창고(`_selectedWarehouseId`)와 **같은 종류**다.
> `ApprovalTriggerHelper.cs:225` 주석이 *"두 곳을 함께 고쳐야 하며, 빠뜨리면…"* 이라고 **경고해 놓고
> 정작 `absence` 에서 빠뜨렸다.** 어제 교훈 그대로다 — **기록은 봉합이 아니다.**

### 결함② 초과근무는 **설정만 있고 트리거가 없다**

- `DocTypeLabels["overtime"] = "초과근무"` → 설정화면에 **뜬다. 켤 수 있다.**
- `HrService.CreateOvertimeAsync` → INSERT 만 하고 **결재 호출 0건** (grep 실측)
- 대신 `ApproveOvertimeAsync` 라는 **결재와 무관한 자체 승인** 경로

⇒ 고객이 결재설정에서 "초과근무" 를 켜고 결재선까지 짜도 **아무 일도 안 일어난다.**
사장님 오더 7번(*"초과근무신청서 작성시 결재메뉴로 보이도록"*)이 정확히 이 자리다.

> 결함①과 ②는 **정반대 방향의 같은 병**이다:
> ① 코드는 부르는데 설정이 없다 / ② 설정은 있는데 코드가 안 부른다.
> **양쪽 다 화면은 정상으로 보인다.**

## 4. 🔴 결재 화면 — 오더 1번의 실체

현재 결재는 **목록 3화면**(대기·보낸·완료)뿐이고:

| 실측 | 내용 |
|---|---|
| 필터 | **0개.** `MudSelect`·날짜·검색 전무 |
| API | `GetPending/GetSent/GetCompleted` 가 **쿼리 파라미터를 하나도 안 받는다** |
| 상신 화면 | **없다.** `POST /api/approval/documents` 를 부르는 페이지 0개 |

사장님 오더 1번(콤보 2개)은 **필터축을 이렇게 바꾼다:**

```
[전] 메뉴 3개 = 대기 / 보낸 / 완료          ← 상태가 '메뉴'였다
[후] 메뉴 1개 + 콤보1(상태) × 콤보2(문서종류) ← 상태가 '필터'가 된다
```

🔴 **이건 단순 필터 추가가 아니라 메뉴 3개가 1개로 합쳐지는 구조 변경**이다.
오더 15번(메뉴 재배치)에서 결재가 1개인 것과 정확히 일치한다 — **사장님 오더 1과 15는 한 몸이다.**

⚠️ 다만 **콤보2(문서종류)** 는 `doc_type` 이 15종인데 사장님이 5종(보고서·휴가·휴직·경비신청·입사퇴사)만
드셨다. **"입사퇴사" 는 지금 결재 문서종류에 없다** — 신규 정의가 필요하다(§6 질의).
