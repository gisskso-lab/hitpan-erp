## 2. 🔴 사장 직권 (최우선)

> 상무님: *"오늘 사장님이 하신 말 중 **제일 값어치 있다.**
> 내가 8/21에 '최우선' 이라 해놓고 **답을 못 냈던 자리**다.
> 나는 교과서(전결·대결·회수·결재선변경)만 읊었지, **한국 중소기업이 실제로 뭘 하는지**는 못 말했다."*

### 2-1. 🟢 사장님 확정 — **반자동**

> 사장님: *"**=반자동원칙 사장이 아무때나 누를수있게**"*

🔴 **자동 판정을 만들지 않는다.** 히트판 대원칙과 같다:

> **100% 자동화는 없다. 무조건 반자동** — 제안값 → 사람이 확정

| | |
|---|---|
| 시스템이 하는 것 | **공석을 알아보고 묻는다**(제안) — *"결재자가 00중입니다"* |
| 사람이 하는 것 | **[Y] 변경 / [N] 유지** 를 고른다(확정) |
| 시스템이 안 하는 것 | 🔴 **저 혼자 결재하지 않는다 · 저 혼자 결재자를 바꾸지 않는다** |

⇒ 조건 판정으로 **막지 않는다.** 공석 3사유(§2-2)가 아니어도
   **부모계정·권한자는 결재설정에서 언제든 결재자를 바꿀 수 있다.**
   다만 **공석일 때는 시스템이 먼저 알려준다**(§6-3).

### 2-2. 🟢 사장님 확정 — 공석 사유 **3가지**

> 사장님 지시 B-2: *"**휴가, 퇴사, 휴직**"*

| 사유 | 어떻게 아나 | 성격 |
|---|---|---|
| **퇴사** | `employees.is_resigned` / `is_active=0` | 영구 |
| **휴직** | `employees.work_status = 'leave_of_absence'` | 기간 |
| **휴가** | `leave` 승인 건의 기간에 오늘이 들어감 | 단기 |

🔴 **이 3가지는 "버튼을 띄우는 근거" 이지 "자동 결재 조건" 이 아니다.**
   ⇒ 셋 중 아무것도 아니어도 **사장은 누를 수 있다**(§2-1).
   ⇒ 셋 중 하나면 화면이 **"부장 공석 — 직권 결재"** 라고 **먼저 알려준다.**

### 2-3. 🟢 사장님 확정 — 이력에 **"부장공석"** 으로 남긴다

> 사장님 지시 B-1: *"**부장공석 으로 남겨**"*

상무님: *"그냥 사장이 승인한 걸로 보이면 **나중에 감사에서 못 푼다.**
**감추지 말고 흔적을 남겨라** — 8/21 자체승인 버튼 때 내가 한 말과 같다."*

**남기는 방법** — 표 신설 없이 기존 칸을 쓴다:

```
approval_history
  approver_id           = 사장 employee_id      (실제 누른 사람)
  original_approver_id  = 공석인 부장 employee_id (원래 결재자)
  is_delegated          = 1                      (대신 결재했다)
  comment               = "부장공석 — 직권결재" + 사유(퇴사/휴직/휴가)
```

🟢 **Q1 확정 — `is_delegated` 를 그대로 쓴다**(§6-1, 사장님 *"델리게이트로"*).
   대결과 직권은 **같은 성격**이다 — *남의 자리를 대신 눌렀다*.
   구분은 `original_approver_id`(누구 자리) + `comment`("부장공석 — 직권결재") 로 된다.
   ⇒ 🔴 **DDL 변경 0건.**

### 2-4. 🟢 사장님 확정 — 권한은 **"부모계정이 주는 권한까지"**

> 사장님 지시 D-3: *"**부모계정이 주는 권한까지**"*

⇒ **부모계정 전용이 아니다.** 부모계정이 **권한으로 열어주면 관리자도 쓴다.**
   ⇒ 헌법 #11 정합 — *권한은 어드민이 직접 설정*. 우리가 역할을 코드에 박지 않는다.

🔴 **새 권한 항목 필요** — `HR_PROXY` 와 같은 방식(5축 밖 별도 항목):

```
menu_code = APPROVAL_OVERRIDE   "직권 결재"
기본 OFF — 고객사가 켠다
🔴 EnforcedMenus 등록 필수 (안 하면 체크박스가 화면에 안 뜬다 = 1.2.74 P0 재발)
```

## 3. 🔴 전결

> 상무님: *"전결이 없으면 **100만원짜리 경비도 사장까지 올라간다.**
> 그러면 사장이 **결재기계**가 되고, 결국 대충 누른다. **그게 결재가 무너지는 방식**이다."*

### 3-1. 🟢 사장님 확정 — **고객사가 알아서 설정**

> 사장님 지시 D-2: *"이것도 **금액, 문서종류 다 고객사가 알아서 설정**하게"*

🔴 **우리가 기준을 정하지 않는다.** 금액도, 문서종류도 **고객사가 넣는다.**
   ⇒ 헌법 #11(업종·규모별 템플릿 제공 금지) 정합.
   ⇒ *"300만원 이하 부장 전결"* 같은 **기본값을 코드에 박지 않는다.**

### 3-2. 설정 표 (신규)

```
approval_final_rules        (사장님 확정 §6-2)
  tenant_id
  doc_type          어떤 문서에
  max_amount        얼마 이하면            (NULL = 금액 무관)
  final_step_order  몇 단계에서 끝내나
  is_active
```

🔴 **값을 코드에 넣지 않고 표에서 읽는다** — `labor_policy_settings` 와 같은 방식.
   ⇒ 나중에 기준이 바뀌면 **행만 갈아끼운다.** `switch` 로 박으면 코드 수정이 된다.

### 3-3. 🟢 금액 칸은 이미 있다 (DESCRIBE 완료 — 헌법 #13)

`approval_documents` 실측:

```
amount   decimal(15,2)  NOT NULL DEFAULT 0.00   '금액'
```

🟢 **상신 시점에 이미 금액이 박힌다.** 전결 판정은 이 값을 그대로 읽으면 된다.
- 🟢 `decimal` 이라 헌법 #4(금액은 decimal) 정합 — 새로 만들 필요 없다
- 🟢 **원본이 나중에 바뀌어도 결재 판단은 상신 당시 금액**이다(#6 정합)

⇒ **전결에 필요한 금액 축은 표 변경 0건.** 신설은 규칙 표(§3-2) 하나뿐이다.

## 4. 🟡 상신 결재라인 배선

> 상무님: *"표는 제대로 만들어 놨다. **직책으로도 사람으로도** 걸 수 있게 해뒀다 —
> 작은 회사는 사람으로, 큰 회사는 직책으로 건다. **이게 실무에서 맞는 설계**다."*
>
> 🔴 *"문제는 8/12 흐름설계서가 이미 적어놨다 — **'표는 있는데 결재 엔진이 안 읽는다'**.
> 만들어 놓고 안 쓰는 것이다. 이건 사장님 탓이 아니라 **우리가 보고를 잘못한 것**이다."*

### 4-1. 지금 구조

```
approval_line_steps   step_order · position_id · employee_id   ← 있는데 엔진이 안 읽음
approval_doc_lines    doc_type 단위 전역 마스터 1행             ← 엔진이 읽는 것
```

⇒ **두 축이 따로 논다.** 배선 = `approval_line_steps` 를 상신 시점에 읽어
   `approval_doc_lines` 로 펼치는 일이다.

### 4-2. 🔴 직책으로 걸었을 때가 진짜 값어치다

`position_id` 로 걸면 **사람이 바뀌어도 결재선이 안 죽는다.**
⇒ 부장이 바뀌면 **새 부장이 자동으로 그 자리**에 온다.
⇒ 🟢 **이게 §2 직권의 필요를 줄인다** — 퇴사해도 후임이 있으면 선이 안 끊긴다.

⚠️ 다만 **후임이 없으면** 여전히 공석이다 ⇒ **직권이 그때 필요하다.**
   ⇒ **직권과 배선은 서로를 대체하지 않는다. 둘 다 필요하다.**

## 5. 세 가지가 어떻게 다른가 (혼동 방지)

> 상무님: *"사장 직권과 전결은 **방향이 반대**다. 헷갈리면 안 된다."*

```
전결  =  위로 안 올라간다      부장이 끝냄            (단계를 줄인다)
직권  =  아래를 대신 눌러준다   사장이 부장 자리를 누름  (사람을 대신한다)
대결  =  옆으로 넘긴다         부장 대신 차장          (미리 걸어둔다)
```

| | 언제 정하나 | 누가 | 지금 |
|---|---|---|---|
| 전결 | **미리**(설정) | 고객사 | 🔴 없음 |
| 대결 | **미리**(기간) | 결재자 본인 | 🟢 있음 |
| **직권** | **그때 묻고 고른다** | 사장·권한자 | 🔴 없음 |

🟢 **사장님 의중(지시 C) = 직권.** 상무님도 같은 판정:
> *"셋 다 필요하지만 **직권이 제일 급하다** — 없으면 **회사가 선다.**
> 전결은 없어도 굴러는 간다(느릴 뿐)."*

## 6. 🟢 사장님 확정 — Q1·Q2·Q3 (2026-08-22)

### 6-1. Q1 🟢 **델리게이트로 간다** (PM 권고 물림)

> 사장님: *"**델리게이트로**"*

PM 은 *"새 칸을 파자"* 고 권고했으나 **사장님이 물리셨고, 그게 맞다.**

| PM 권고(폐기) | 사장님 확정 |
|---|---|
| 직권용 새 칸 신설 | 🟢 **기존 `is_delegated` 재사용** |

**왜 사장님 안이 맞나**:
- 대결도 직권도 성격이 **같다** — *남의 자리를 대신 누른다*
- 구분은 **이미 있는 칸으로 된다** — `original_approver_id`(누구 자리) + `comment`("부장공석 — 직권결재")
- 🔴 **DDL 변경 0건** — 헌법 #1(추가만) 부담도 없다
- PM 이 든 근거(*"대결 몇 건인지 못 센다"*)는 **`comment` 로 갈린다** — 셀 수 있다

⇒ 🟢 **`approval_history` 표 변경 없음. `approval_doc_lines` 도 그대로.**

### 6-2. Q2 🟢 표 이름 = **`approval_final_rules`**

> 사장님: *"전결 `approval_final_rules`"*

```
approval_final_rules
  tenant_id
  doc_type          어떤 문서에
  max_amount        얼마 이하면        (NULL = 금액 무관)
  final_step_order  몇 단계에서 끝내나
  is_active
```

⚠️ §3-2 의 가칭 `approval_delegation_rules` 는 **폐기.**
   (*delegation* 은 대결을 뜻해 전결과 헷갈린다 — 사장님 이름이 정확하다)

### 6-3. Q3 🟢🟢 **묻고 고른다** — PM 안보다 낫다

> 사장님: *"**부모계정, 권한가진자 계정으로 메신저, 로그인후 대쉬보드팝업으로**
> ***"결재자가 00중입니다. 변경하시겠습니까? 유지하시겠습니까?"* → y/n"*

**PM 안은 이랬다**: *사장이 알아서 직권 버튼을 누른다.*
**사장님 안은 이렇다**: **시스템이 먼저 물어본다.**

| | PM 안 | 사장님 안 |
|---|---|---|
| 누가 먼저 아나 | 사장이 **찾아봐야** 안다 | 🟢 **시스템이 알려준다** |
| 언제 아나 | 결재함에 들어가야 | 🟢 **로그인하자마자 / 메신저로** |
| 무엇을 고르나 | 누른다/안 누른다 | 🟢 **변경 / 유지** 두 갈래 |

> 상무님: *"이게 **반자동 원칙의 정확한 모습**이다. 시스템이 판단은 안 하고 **알려만 주고**,
> **사람이 고른다.** 내가 8/21에 말한 '갓길' 이 이걸로 생긴다."*

#### 알리는 경로 2개 — 🟢 **둘 다 이미 있다**

| 경로 | 실측 | 근거 |
|---|---|---|
| **로그인 후 대시보드 팝업** | 🟢 **자리 있음** | `Dashboard.razor:216` — 5/26 사장님 결재 *"9시 출근 첫 로그인 1회 브리핑"* |
| **메신저 결재 안내** | 🟢 **자리 있음** | `ChatPage.razor:166` — *결재봇* + **딱지**(메시지인지 결재안내인지 구분) |

🔴 **새 알림 구조를 만들지 않는다.** 있는 자리에 **얹는다.**

#### 받는 사람

> 사장님: *"부모계정, 권한가진자 계정으로"*

⇒ **부모계정 + `APPROVAL_OVERRIDE` 권한 보유자**(§2-4 와 같은 축).
   ⇒ 권한 없는 직원에게는 **안 뜬다** — 남의 회사 인사 사정이 새면 안 된다.

"결재자가 00중입니다. 변경하시겠습니까? 유지하시겠습니까?"
                  ↓                        ↓
              [Y] 변경                  [N] 유지
                  ↓                        ↓
      🔴 결재설정 화면으로 링크 이동        🔴 상태 유지
         (/settings/approval)               (아무것도 안 바꾼다)
```

> 사장님 확정(2026-08-22): *"**Y선택시 결재설정으로 링크이동 n선택시 상태유지**"*

⚠️ `00` 자리 = **휴가중 / 휴직중 / 퇴사** (§2-2 세 사유)
🔴 **개발용어 금지** — *"공석"*·*"delegate"* 같은 말이 고객 화면에 나가면 안 된다.

#### 🔴🔴 [Y] 는 "그 자리에서 결재" 가 아니다 — PM 초안 정정

PM 초안은 *"[변경] 이면 사장이 그 자리에서 직권으로 누른다"* 였다. **틀렸다.**

| PM 초안(폐기) | 사장님 확정 |
|---|---|
| 팝업에서 **바로 결재** | 🟢 **결재설정 화면으로 보낸다** |
| 그 **한 건**만 넘어간다 | 🟢 **그 사람 자리를 정리한다** |

**왜 사장님 안이 근본인가**:
- 팝업에서 한 건 결재하면 **다음 문서도, 그 다음 문서도 또 막힌다**
- 결재설정에서 **결재자를 바꾸면 그 자리가 풀린다** — 뒤에 밀린 것까지 한 번에
- 🟢 **[Y]=이동** 이므로 팝업은 **알림 역할만** 한다 — 결재 로직이 팝업에 안 들어간다(단순)

🟢 **목적지 실측**: `/settings/approval`(`ApprovalSettingsPage.razor`) 에
   **결재자 · 위임결재자 지정 칸이 이미 있다**(`:99`·`:101`·`:109`).
   ⇒ 🔴 **새 화면을 만들지 않는다. 링크만 건다.**

#### 🔴 [N] 을 고르면 어떻게 되나

- **상태 유지** — 문서도 결재선도 **아무것도 안 바꾼다**
- **다음 로그인에 다시 묻는다** — 업데이트 팝업 *[나중에]* 와 같은 방식(#43 정신)
- 🔴 **한 번 [N] 했다고 영영 안 뜨게 만들지 마라** — 그러면 **그 문서가 잊힌다**

### 6-4. 🔴 그래서 Q3 원래 물음(전결+공석)의 답

*"부장 전결인데 부장이 공석"* ⇒

```
1. 시스템이 묻는다      "결재자가 휴가중입니다. 변경/유지?"
2. [Y] 결재설정으로 이동 → 그 자리 결재자를 바꾼다
3. 🟢 전결은 유지된다     단계가 안 늘어난다 — 위로 안 올라간다
```

⇒ 🔴 **바뀌는 것은 "누가" 뿐이다. "몇 단계" 는 안 바뀐다.**
   전결 규칙(`approval_final_rules`)은 **`final_step_order`(단계)** 로 걸리고,
   결재자 교체는 **그 단계에 앉는 사람**을 바꿀 뿐이라 **서로 안 부딪힌다.**

⚠️ **[N] 이면 그 문서는 계속 대기**한다 — 전결이든 아니든 같다.
