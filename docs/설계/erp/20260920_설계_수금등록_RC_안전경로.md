### 결정: **서버 설정을 보고 두 경로로 가른다. 둘 다 같은 정확성 계약을 지킨다.**

| 축 | 내용 |
|---|---|
| 판정식 | `SELECT @@log_bin,@@binlog_format` → **위험 = log_bin=ON AND STATEMENT**, 그 밖은 안전 |
| 안전 경로 (RC) | 지금 3판 그대로 — RC + 거래처 행 `FOR UPDATE` + 일반 읽기로 R 재계산 (교착 0 실측 · G8-w) |
| 위험 경로 (RR) | RR + 거래처 행 잠금 + **R 재계산·전표 남은금액을 잠금 읽기(`LOCK IN SHARE MODE`)** + 교착(1213/1205) **트랜잭션 통째 짧은 재시도** |
| 기본값(조회 실패) | 🔴 **RR 경로** — RR 경로는 두 서버 **모두에서 돈다**. RC 는 안전 서버에서만 돈다 → 모르면 도는 쪽 (#20) |
| 캐시 | 프로세스 1개 값 + TTL 5분 · 1665 를 실제로 만나면 즉시 무효화 · 재기동 시 초기화 |

| 등록 차단 | **없다.** 재시도 소진 시에만 「잠시 후 다시 저장」 문구(고객어) — 마지막 수단 |
| 갈래 | S1 판정·경로(파일 4) · S2 게이트·CI(파일 3) — 2갈래 |

## 본문

## §1 [문제] 무엇이 왜 막히나

선행검증 확정 사실만 쓴다(재측정 금지).

- `log_bin=ON` **AND** `binlog_format=STATEMENT` → RC 트랜잭션의 `FOR UPDATE`·INSERT 가 **ERROR 1665**. `BEGIN`·일반 `SELECT`·`LOCK IN SHARE MODE` 는 통과.
- RC 를 쓰는 곳은 `CollectionService.cs:132`(수금)·`:301`(지급) 2곳뿐. 매출·매입·재고·BOM·회계는 무영향.
- 그 서버에서는 **수금·지급 등록 3경로(이월잔액 매칭 · 명세서/전표 지정 · ref 없는 순수 등록)가 전부** 막힌다 = #20 흐름 끊김 P0.
- `SET SESSION binlog_format='ROW'` 는 BINLOG ADMIN 권한 필요 → 응용 계정 불가.
- **RR 단순 폴백은 대안이 아니다**: 1665 는 사라지지만 G8-u 최종 R −20,000 · G8-x 초과 매칭 미거절 = 조용한 잔액 오류.

### §1-1 RR 이 왜 틀렸나 — 원인을 한 줄로

RR 은 트랜잭션 첫 읽기에서 스냅숏이 고정된다. 거래처 행을 잠근 뒤에도 **R 재계산이 「일반 SELECT」라서 옛 스냅숏**을 본다.
InnoDB 에서 **잠금 읽기(`FOR UPDATE`·`LOCK IN SHARE MODE`)는 RR 에서도 최신 커밋을 읽는다.**
→ RR 이 틀린 것이 아니라 **RR 에서 일반 읽기로 판정한 것**이 틀렸다. 고칠 자리는 격리수준이 아니라 **R 재계산 문장**이다.

## §2 [축] 경로를 가르는 기준

| 판정 | log_bin | binlog_format | 경로 | 근거 |
|---|---|---|---|---|
| 안전 | OFF | 무엇이든 | **RC** | 1665 조건은 AND (선행 §3) |
| 안전 | ON | MIXED · ROW | **RC** | 대조군 통과 (선행 §3) |
| 위험 | ON | STATEMENT | **RR** | 1665 재현 (선행 §1) |
| 알 수 없음 | 조회 실패·권한거절·타임아웃 | — | **RR** | RR 경로는 두 서버 모두에서 돈다 |

🔴 **왜 RC 를 기본으로 남기나**(반증 답): RC 경로는 3판에서 교착 0 으로 실측되고 이미 main 에 있다. RR 경로는 파생표 공유잠금이 넓어 교착을 재시도로 삼킨다 — 지연과 드문 재시도 소진을 안고 간다.
검증된 경로를 버릴 이유가 없으므로 **안 되는 서버에서만** RR 로 간다. 「코드 하나로 통일(항상 RR)」은 더 단순하지만 전 고객에게 재시도 경로를 강제한다 → **결재 안건 A-3 으로 올린다**(설계 기본안 아님).

## §3 [판정] 시점 · 캐시 · 실패

- **시점**: 등록 트랜잭션을 **열기 직전**. 캐시 히트면 DB 왕복 0.
- **범위**: 프로세스 단위 값 1개(ERP 는 고객 PC 1 프로세스). 연결마다 재조회하지 않는다.
- **수명**: TTL **5분**. 근거 — `SET GLOBAL binlog_format` 은 재기동 없이도 바뀌고, 세션값은 연결이 새로 맺힐 때 따라간다. 5분이면 「고객이 설정을 고친 뒤 다시 저장」이 사람 시간 안에 반영된다. (상수 한 곳 · 값은 PM 재량)
- **즉시 무효화**: ① 프로세스 재기동 ② **실행 중 1665 를 만나면** 캐시를 버리고 다시 판정 → 그 요청은 RR 로 재시도(재시도 조건에 1665 포함 · §4-3).
- **조회 실패**: 예외를 삼키지 않고 `LogWarning` 한 줄(#15) + **RR 경로**. 실패가 등록을 막지 않는다.
- 판정 문장은 시스템 변수 조회 — 테이블·잠금 접근 0 (선행 F8).

## §4 [RR 경로] 정확성을 어떻게 지키나

### §4-1 거래처 직렬화 — G8-x

`SELECT balance_id FROM partner_legacy_balances … FOR UPDATE` **그대로 둔다**. 1665 는 RC/RU 한정이므로 RR 에서는 허용된다(⚠️ §10-1 미실측 · 0단계 확인).
뒤 연결은 앞 연결 커밋까지 이 잠금에서 기다린다 → G8-x 의 「기다렸다 거절」이 성립.

### §4-2 R 재계산 — G8-u · G8-x

`GetForUpdateAsync` 의 두 번째 문장(파생표 R 조회)을 **모드에 따라** 바꾼다.

```
RC 모드 : SELECT … FROM (공용식) x WHERE x.partner_id = @PartnerId
RR 모드 : SELECT … FROM (공용식) x WHERE x.partner_id = @PartnerId LOCK IN SHARE MODE
```

- 공용 식(`ReceivableRemainingSql`·`PayableRemainingSql`) **본문은 한 글자도 안 바꾼다** — 11곳 소비자와 같은 식이어야 한다(3판 계약).
- 잠금절은 **꼬리 한 줄**만 모드로 갈린다. 붙이는 자리는 `GetForUpdateAsync` 한 곳.
- 근거: 3판 1차안(R1b)이 이 방식으로 G8-u·G8-x 를 통과했다(현행 `MatchIsolation` 주석에 폐기 사유가 **교착**이라고만 적혀 있다 = 정확성은 통과했다는 기록). ⚠️ STATEMENT 인스턴스에서는 미실측 → **G-RC3·G-RC4 가 실측한다**(가정으로 넘기지 않는다).

### §4-3 교착 — G8-w · 재시도

1차안이 폐기된 이유가 여기다. 파생표 공유잠금이 회사 범위를 훑어 **다른 거래처 동시 매칭에서도 교착**(G8-w).
RR 경로에서는 교착을 없애는 대신 **삼킨다**.

- **재시도 범위 = 트랜잭션 통째.** 부분 재시도 금지 — INSERT·`partner_balance`·자동기표가 한 트랜잭션이라 중간 재개는 이중 반영이 된다.
- 구현 자리: `CreateCollectionAsync`/`CreatePaymentAsync` 의 **본문을 내부 메서드로 빼고 얇은 재시도 껍질**을 씌운다. 커밋 **뒤**의 감사로그는 껍질 밖(재시도에 안 섞인다).
- **재시도 조건(화이트리스트)**: `MySqlException` 번호 **1213**(교착) · **1205**(잠금 대기 초과) · **1665**(캐시가 낡아 RC 로 갔을 때 · §3).
  `InvalidOperationException`(고객 문구 거절)·그 밖의 예외는 **절대 재시도 안 한다** — 거절을 재시도로 뒤집으면 잔액이 틀어진다.
- **상한·간격**: 총 3회 시도(원 1 + 재시도 2) · 50ms → 150ms + 지터 0~50ms. 사용자 체감 상한 약 0.5초. 값은 상수 한 곳 · 근거는 체감 기준이지 실측 아님(⚠️ §10-3) → G-RC5 가 실제 시도 횟수를 잰다.
- **소진 시 문구**(고객어 · 개발용어 금지 #23):
  > 지금 다른 사용자가 같은 거래처의 수금을 처리하고 있습니다. 잠시 후 다시 저장해 주세요.
  (지급은 "수금"→"지급") — 문구 상수는 `CollectionService` 문구 모음 한 곳.

### §4-4 D1 — 설계가 새로 찾은 구멍

`EnsureCollectionTargetAllowedAsync`(`:782`)·`EnsurePaymentTargetAllowedAsync`(`:820`) 의 **남은금액 SUM 은 일반 읽기**다.
RC 에서는 문장마다 최신이라 맞지만, **RR 에서는 옛 스냅숏** → 같은 명세서에 동시 수금이 들어오면 **합이 전표금액을 넘어도 통과**한다.
선행검증(이월잔액 축)·PM 추천안에 없던 항목이다. RR 경로에서 같은 처방을 쓴다.

```
RR 모드 : SELECT COALESCE(SUM(amount),0) FROM collections … LOCK IN SHARE MODE
          (지급 = payments + purchase_returns 합산 문장 · 같은 모양)
```

전표 행 `FOR UPDATE` 는 이미 있으므로 같은 전표 동시 등록은 직렬화된다. 잠금 읽기는 **그 뒤에 최신 합을 읽게** 한다. 게이트 G-RC6.

## §5 [가드] `LegacyBalanceMatching.cs:185` 를 어떻게 바꾸나

지금: `tx.IsolationLevel != MatchIsolation → NotSupportedException`. RR 을 허용하면 이 방어선이 무너진다. **격리수준을 느슨하게 푸는 게 아니라, 모드를 선언받는다.**

### §5-1 계약

```csharp
public enum LegacyMatchMode { ReadCommittedFresh, RepeatableReadLocking }
public static IsolationLevel IsolationFor(LegacyMatchMode mode);   // RC↔ReadCommitted · RR↔RepeatableRead
```

호출자는 트랜잭션과 **모드를 같이** 넘긴다. 가드는 두 가지를 본다.

1. 모드가 **선언됐나**(기본값 없음 — 인자 필수).
2. `tx.IsolationLevel == IsolationFor(mode)` 인가.

둘 중 하나라도 어긋나면 지금과 같은 `NotSupportedException`. `Serializable`·`ReadUncommitted`·`Snapshot`·`Unspecified` 는 **어느 모드로도 통과 못 한다** = 「아무 격리 수준이나」가 되지 않는다.

### §5-2 모드가 SQL 을 고른다

같은 `mode` 값이 §4-2·§4-4 의 잠금절을 고른다. → **격리수준과 잠금식이 한 값에서 갈린다.**
「RR 로 열고 일반 읽기로 판정」하는 조합은 코드로 표현할 수 없다(3판이 밟은 그 사고를 구조로 막는다).

### §5-3 상수

- `MatchIsolation` 은 **남긴다** — 뜻을 「RC 경로의 격리수준」으로 좁히고 주석 갱신. 외부 참조(게이트 `MatchIsolation`)가 깨지지 않는다.
- `MatchIsolationFallback = IsolationLevel.RepeatableRead` 신설.
- ⚠️ §10-1 이 틀리면(RR+STATEMENT 에서도 `FOR UPDATE` 가 1665) → RR 모드의 거래처 행 잠금도 `LOCK IN SHARE MODE` 로 내리고, 같은 거래처 동시는 **교착으로만 갈린다** = §4-3 재시도가 그 자리를 메운다. 이 분기는 작지 §8 에 미리 적어 둔다.

### §6-2 사례 (신설 `RcSafePathGate`)

카드 기대값 표 9건이 정본. 요지만 다시 적는다.

## §10 [⚠️ 미실측] 추측을 사실로 쓰지 않는다

2. **파생표 `LOCK IN SHARE MODE` 가 STATEMENT 서버에서 최신 커밋을 읽는가** — 3판 1차안 기록이 근거일 뿐, 이 조합은 미실측. G-RC3·G-RC4 가 판정한다.
3. **교착 빈도·재시도 성공률** — 미실측. 상한 3회는 체감 기준이지 실측 근거가 아니다.
4. **고객 PC·사장님 PC 의 `log_bin`/`binlog_format` 분포** — 안 봤다. 「모른다」가 사실이다. 빈도를 숫자로 말하면 받아쓰기(#32).
5. **D1(명세서·전표 SUM 스냅숏 오염)이 현장에서 실제로 났는지** — 모른다. RR 경로를 새로 여는 이번 작업이 **만들지 않게** 막는 것이지, 과거 사고 보고가 있는 게 아니다.

### §11-2 (다)를 기각하는 이유 — 코드로 못 막는다

(다)는 「이 트랜잭션에 **앞선 일반 읽기가 하나도 없었다**」가 전제다. 이 전제를 코드가 강제하려면 그 연결에서 지금까지 나간 문장을 전부 알아야 한다. 우리 코드의 읽기는 **호출자마다 Dapper 를 직접** 부른다 — 관문이 없다. 결국 「먼저 잠그고 나서 읽어라」는 **사람이 지키는 호출 순서 규칙**으로만 남고, 이건 3판 병렬이슈44 가 밟은 바로 그 함정이다. 게다가 어긋나도 예외가 아니라 **조용히 옛 금액**이다(돈이 틀린다).
→ 성립 조건이 맞아떨어지는 경우가 있더라도(⚠️ §11-6) **처방으로 삼지 않는다.**

### §11-4 RR 재계산의 모양 (실측된 모양만 쓴다)

- L0·base_date 는 **이미 있는 첫 문장**(`… FROM partner_legacy_balances … FOR UPDATE`)에서 같이 받는다 — 잠금 읽기라 최신이고 **잠금이 늘지 않는다**.
- M 은 **실테이블 직접 · 거래처 1건 필터 · 꼬리 `LOCK IN SHARE MODE`** 문장으로 나눠 읽는다(미수 2문장 · 미지급 3문장). 공용 식의 각 `LEFT JOIN` 하위질의 술어를 **그대로** 옮긴다(별칭 `lc·ec·lp·ep·rt/rti/pr` 유지).
- ❌ **금지**: `SELECT SUM(..) FROM (… UNION ALL …) t` · `SELECT (SELECT …), (SELECT …)` — 파생표·스칼라 하위질의는 이번에 **안 서는 것으로 실측된 모양**이다. 같은 이유로 #16(`UNION ALL` 권장)은 여기서는 **적용 예외**다(한 연결·순차 · `Task.WhenAll` 아님).
- R = `GREATEST(L0,0) - ΣM` 을 **C# decimal** 로(#4) — SQL 의 산술과 같은 식, 같은 자릿수.
- 🔴 **§4-4(D1) 지급 쪽 재점검**: 현행 지급 합산은 **스칼라 하위질의 2개** 안에 잠금절이 있다(`CollectionService.cs:851·855`). S1 이 실측한 것은 **수금 쪽 단일 직접 문장**뿐이다 → 같은 함정일 수 있다. **직접 문장 2개로 분리**하고 G-RC6 에 매입 축을 실측으로 넣는다.

### §11-5 안전 경로(RC) 는 무변경

### §11-6 ⚠️ 2판이 안 잰 것

1. **(다)의 갈림** — 「앞선 일반 읽기가 없으면 일반 읽기도 최신인가」는 **안 쟀다.** 기각 사유는 실측이 아니라 **강제 불가**다. (나)를 채택하므로 재지 않는다.

**EXPLAIN 을 게이트에 넣는 방법**(구현 지시는 작지 §16):
`EXPLAIN ` + 제품 SQL 상수를 그대로 이어 붙여 Dapper `Query<ExplainRow>` 로 읽는다(`Table`·`Key`·`KeyLen`·`Rows` — Dapper 는 대소문자 무시로 `key`→`Key` 를 맞춘다). `rows` 는 **추정치**이므로 단언은 「같다」가 아니라 **「상한 이하」 + 「무관 행을 10배 늘려도 안 커진다」 대조군** 두 개로 건다. 추정치 하나만 단언하면 옵티마이저 통계 갱신에 흔들린다.

🔴 **갭 잠금은 게이트로 못 지운다** — RR 의 next-key 잠금은 스캔 범위에 **인접한 간극**도 잠근다. 인덱스로 범위가 좁아져도, 그 간극에 떨어지는 **다른 거래처의 INSERT** 는 여전히 막힐 수 있다. G-RC12 ②(INSERT)가 이걸 실제로 재는 자리다. **⚠️ 인덱스만으로 100% 사라진다고 쓰지 않는다** — G-RC12 가 초록이면 「이 사례에서는 안 막혔다」까지가 사실이다.

### §12-8 재시도 — 문구 정정 · 그래도 남는다

**문구**(`CollectionService.cs:702·703`) — 「같은 거래처」는 **사실이 아니다**(#25 · 헌법 「쉽게」).

1. **같은 거래처 동시 매칭** — 설계가 의도한 직렬화다(G-RC4 가 「기다렸다 거절」을 잰다). 1205 가 여기서 난다.

3. **갭 잠금**(§12-6) — 좁힌 범위에 인접한 간극. ⚠️ 미실측.
→ 상수(3회·50/150ms)는 **그대로**. 바꾸는 건 문구 하나다(#33 범위 최소).

### §13-2 문제 정의 — 무엇이 진짜 고장인가

**L2·L4·L5 는 같은 모양의 문장이다.** 거래처 조건이 **잠그려는 표가 아니라 조인되는 전표 표**에 붙어 있다.

```
L2  FROM collections ec       JOIN sales_deliveries  sd ...  WHERE ec.tenant_id=@T AND sd.partner_id=@P
L4  FROM payments    ep       JOIN purchase_receipts pr ...  WHERE ep.tenant_id=@T AND pr.partner_id=@P
L5  FROM purchase_returns rt  JOIN rti JOIN purchase_receipts pr ... WHERE rt.tenant_id=@T AND pr.partner_id=@P
```

⇒ 옵티마이저가 **거래처 조건이 없는 쪽(ec·ep)을 구동표로 고르면** 그 표에 걸린 조건은 `tenant_id` 뿐이고, 한 DB 한 회사이므로 그것은 **표 전체**다. 그래서 `ALL 107,653` · `ALL 2,196` 이 나온다.

**행이 많아서가 아니다.** [1-V] §2-3: 2,060행까지 고르게 뿌리면 계획이 안 뒤집힌다. 뒤집는 것은 **거래처 편중 + 타입 칸 선택도 0**(그 회사 payments 100% `purchase` · collections 100% `sales_delivery`)이다.
⇒ **「데이터가 커지면 생기는 문제」로 다루면 틀린다. 이관 직후에 바로 난다.**

**그리고 이 문장들은 RR 경로에서만 돈다** (`GetForUpdateAsync` 의 `mode == RepeatableReadLocking` 분기 · `LockTailFor` 는 RC 에서 빈 문자열). RC 경로는 애초에 아무것도 안 잠근다.
⇒ 폭발 반경은 **「log_bin=ON + STATEMENT」 서버 + 판정 실패 시 기본값(RR)**(§9)이다. 범위는 좁지만 **기본값이 RR 이므로 실사용에서 흔하다고 봐야 한다.**

| 원인 | 정체 | 인덱스로 고쳐지나 | 언제 나나 |
|---|---|---|---|
| **A** | 구동표를 잘못 골라 표 전체를 훑는다 → `PRIMARY` 위에 전 행 X 잠금 | 🔴 **아니다** — 지목해야 쓴다 | 실물 분포에서만 |
| **B** | RR 의 next-key — 범위 끝의 **간극**이 다음 거래처의 삽입 지점을 막는다(`insert intention waiting`) | 🔴 **아니다** — 간극 잠금은 인덱스 모양과 무관하게 남는다 | 시험 시드에서도 |

🔴 **B 는 「없앤다」가 아니라 「줄이고 잰다」가 정직한 목표다.** 지금은 구동표 전체 스캔이라 **모든 간극**이 잠긴다. 계획을 고정하면 **그 거래처 범위의 끝 한 칸**으로 줄어든다. **한 칸은 0 이 아니다** — 그 잔여를 T1 이 수치로 재고, 수용 여부는 PM 이 판정한다(P-5).

### §13-3 L2 를 어떻게 좁히는가 (1순위 · §23-3-2)

**계획을 못 박는다.** 구동표를 `sales_deliveries sd` 로 고정하고, 두 표의 접근 인덱스를 지목한다.

- `sd` → `idx_tenant_partner (tenant_id, partner_id)` — **이미 있다**(출하 DDL 실측). 거래처 1건으로 좁혀진다.
- `ec` → `idx_coll_tenant_doc (tenant_id, ref_doc_type, ref_doc_id)` — **DB-124 로 이미 있다.** `ec.ref_doc_id = sd.delivery_id` 등치 ⇒ 전표당 rows 1.

**바꾸는 것은 `FROM` 의 순서와 힌트뿐이다. 술어·별칭·`WHERE`·`COALESCE`·`SUM` 대상은 한 글자도 안 바꾼다.**
INNER JOIN 의 순서 변경과 접근 인덱스 지정은 **결과집합을 바꿀 수 없다** ⇒ 「덜 세는」 위험 = **구조적으로 0**. 이것이 §17 이 기각한 처방 (가)(문장 재작성)와 갈라지는 지점이다.

**덜 세게 될 위험 평가**: 🟢 **없다.** 힌트는 접근 경로만, `STRAIGHT_JOIN` 은 조인 순서만 바꾼다. 술어 무접촉.
**다만 ⚠️ 새 위험이 하나 생긴다** — 인덱스가 없는 DB 에서 힌트는 **오류 1176** 이다. 등록이 깨진다(#20). ⇒ **⚠️-3(마이그가 요청 처리 전에 끝나는가)을 T1 이 실측하기 전에는 T3 착수 금지.**

⚠️ **아직 안 쟀다**: 편중 거래처(전체의 40%)는 이관 명세서가 매우 많다. **계획이 좋아도 잠기는 행 수 자체가 클 수 있다.** 그래서 게이트가 **계획이 아니라 잠금 행 수를 직접 재야** 한다(§13-6). 수치는 T1 이 먼저 낸다.

### §13-5 원인 B — 이웃 간극 (§23-3-1 · 자백 C·D)

**실측된 모양**: A 가 L3 을 `LOCK IN SHARE MODE` 로 잡고 있으면 → `idx_pay_partner` 의 **바로 다음 거래처**(`aaaa-p-0001x`) INSERT 가 `lock_mode X locks gap before rec insert intention waiting` 로 1205. **먼 거래처는 통과.**

| 후보 | 내용 | 판정 |
|---|---|---|
| **B-1** | 회사 접두 인덱스를 **타게 만든다**(§13-4 L3·L4) | 🟡 **부분만.** 회사 경계는 막지만 **V5 에 따르면 회사는 하나**다 ⇒ 실익은 축 통일. **같은 회사 다음 거래처는 여전히 막힌다** |
| **B-2** | 계획 고정으로 **잠기는 간극의 개수를 줄인다**(표 전체 → 범위 끝 한 칸) | 🟢 **채택.** 지금은 전체 스캔이라 **모든 간극**이 잠긴다 |
| **B-3** | 잠금 읽기를 없애고 **이미 잡은 `partner_legacy_balances` 행 잠금만 믿고 일반 읽기** | ⚠️ **보류(기각 아님).** 이론상 성립한다(FOR UPDATE 가 첫 문장이면 읽기뷰가 그 뒤에 서고, 같은 거래처 경쟁자는 행 잠금에 막힌다). **그러나** S1 §3-2 에서 **앞선 일반 읽기가 이미 읽기뷰를 세워 옛 값을 돌려준 사고**가 실측됐다. 「앞선 일반 읽기 금지」를 **코드로 강제할 방법을 아직 못 찾았다** ⇒ **P-6 으로 PM 에** |
| **B-4** | 거래처마다 보초 행을 심어 꼬리 간극을 자기 것으로 만든다 | 🔴 **기각.** 금액 표에 가짜 행을 넣는다(#4 · #3) |
| **B-5** | 이 문장들만 READ COMMITTED 로 | 🔴 **기각.** 격리수준은 문장 단위로 못 바꾼다. RR 경로가 있는 이유 자체가 STATEMENT 서버에서 RC 가 거절되기 때문이다(§9) |
| **B-6** | `LOCK IN SHARE MODE` 제거·약화 | 🔴 **기각.** 정확성 계약이 깨진다. [1-V] §3-7: **좁은 계획이면 아무도 안 막힌다** — 잠금절 자체는 죄가 없다 |

🔴 **채택 = B-2 (+B-1). 그리고 잔여를 반드시 잰다.**
**「한 칸으로 줄었다」를 말로 하지 않는다.** T1 이 실물 분포 시드에서 N1/N2/N3 형 이웃 프로브를 **봉합 전/후로** 돌려 **막히는 거래처 수**를 센다. 봉합 후에도 0 이 아니면 그 수치를 **P-5** 로 PM 에 올린다(수용 / B-3 승격).

### §13-6 🔴 감시자 — 게이트가 실물 문제를 보게 만든다 (§23-3-3)

**지금 게이트는 세 겹으로 못 본다.**

| 못 보는 이유 | 근거 | 고치는 법 |
|---|---|---|
| ① **시드 분포가 다르다** — 무관 행 30~300, 거래처 고름 ⇒ L2·L3·L4 가 **안전 판정을 통과**한다 | [1-V] §2-7-2 · 자백 F | **실물 분포 시드**를 새로 만든다 |
| ② **계획만 재고 잠금을 안 잰다** — 계획이 좋아도 잠금이 넓을 수 있다 | §13-3 ⚠️ | **잠금 행 수를 직접 잰다** |
| ③ **`MatchLockIndexes` 가 손으로 적은 이름 목록** — `PRIMARY`·`uq_*_source` 가 없어 실제 매칭 잠금을 못 본다 | [1-V] 반증 ③ | **이름 목록을 버리고 성질을 잰다** |

**실물 분포 시드(`RealDistributionSeed`) 요건** — 「크게」가 아니라 **「같은 모양으로」**:

| 요건 | 값 | 왜 |
|---|---|---|
| 타입 칸 선택도 0 | `payments.payment_type` 100% `purchase` · `collections.ref_doc_type` 100% `sales_delivery` · `source_type` 100% `migration` | **이것이 방아쇠다**([1-V] §2-3) |
| 거래처 편중 | 한 거래처가 전표의 **40% 이상** | 고르게 뿌리면 2,060행까지 계획이 안 뒤집힌다 |
| 규모 | 편중만으로 160행에서 뒤집힌 실측이 있다 ⇒ 상한 `payments ≈ 2,000` · `collections ≈ 10,000`, **뒤집히는 최소 규모를 T1 이 찾아 고정** | 시험 시간 |
| `purchase_returns` | 🔴 **반드시 채운다**(이관 매입의 일부에 확정 반품 · 편중 거래처에 몰아서) | L5·D1-c 를 잴 수 있는 유일한 길(⚠️-1) |
| 🔴 음성 대조군 | **봉합 전 코드에서 이 시드가 `type=ALL` 을 재현하는 것**을 T1 이 확인하고 수치를 남긴다 | **재현 못 하는 시드는 감시자가 아니다** |

**새 게이트 3종** (기존 G-RC1~13 은 그대로 둔다):

| 게이트 | 무엇을 재나 | 기대값 | 무력화(봉합 빼면) |
|---|---|---|---|
| **G-RC14 계획** | 실물 분포 시드에서 L1~L5·D1-a/b/c 의 `type`·`key` | **어느 문장도 `type=ALL` / `key=NULL` 이 아니다** | 힌트 한 줄 제거 → 그 문장 빨간불 |
| **G-RC15 잠금 범위** 🔴 | RR 트랜잭션에서 각 문장을 잡은 채 `information_schema.innodb_trx.trx_rows_locked` | **시드가 아는 「그 거래처 몫」에서 계산한 상한 이하.** 🔴 **고정 상수 금지**(반증 ③ 죽은 단언) | 힌트 제거 → 잠금 행 수가 표 전체로 튄다 |
| **G-RC16 이웃 프로브** 🔴 | 문장을 잡은 채 **무관한 거래처**의 UPDATE·INSERT 4종을 `innodb_lock_wait_timeout=1` 로 시도 | **4종 전부 성공**(원인 A 해소) · 이웃 한 칸 잔여는 **건수를 출력**하고 상한은 T1 수치로 정한다 | 힌트 제거 → 1205 |

**`MatchLockIndexes` 교체**: 이름 목록을 지우고, 막은 인덱스를 `information_schema.statistics` 에서 **첫 칸이 `tenant_id` 인가**로 **재서** 판정한다. **모르는 인덱스가 나오면 통과가 아니라 실패**다 — 「성질을 재고, 모르면 막는다」.

**G-RC13 음성 대조군 수리 — ④-7 채택** (§23-4-4 의 불일치를 설계가 이렇게 판정한다):
지금의 빨간불은 **정당한 빨간불이 아니라 시험 자체의 결함**이다. 대조군이 `payments` 에 **한 줄만** 심어 「두 회사 걸침」을 만들지 못한다(그 시드에서 `PB` 는 `payments` 에 행이 없다). `PB` 의 `payments` 행을 **양쪽 테넌트에 각각** 심으면 해소된다 — **제품 무변경 · 게이트를 무르게 하지 않는다.**
증거(실패 메시지 · `:1299` 위치 · 시드 추적)가 붙은 ④-7 을 채택하고, 「무르게 해야 초록」이라는 반대 서술은 **채택하지 않는다.**

### §13-7 원인 미상의 잔여 차단 — 규명이 1단계다 (§23-3-4)

옛 이름 「수기 등록 유니크 간극」은 **뺀다.** 수기 등록 둘만으로는 NULL/NULL 도 다른 값도 **둘 다 통과**했다 — 원인 서술이 증명되지 않았다.
🔴 **없는 원인을 고치러 가지 않는다.** T1 의 첫 과제는 **규명**이다.

1. 실물 분포 시드에서 **등록 경로 전체**(`CollectionService` RR 흐름)를 두 연결로 동시에 돌린다 — 문장 단위가 아니라 **흐름 단위**([1-V] §5-6 한계).
2. 차단이 나면 `SHOW ENGINE INNODB STATUS` 로 **대기 상대 인덱스와 잠금 모양**을 찍는다.
3. **격리**: 원인 A 를 봉합한 상태(힌트를 켠 사본)에서 다시 돌려 **남는 것이 무엇인지** 가른다. 두 원인은 서로를 가린다(자백 C).
4. 결과가 「원인 A·B 로 전부 설명된다」면 **별건 ②를 닫는다.** 남는 것이 있으면 **그때 이름을 붙이고** 처방은 별도 결재.

⛔ **규명 전 처방 금지.** 이 트랙에서 이름부터 붙였다가 두 번 틀렸다(자백 C·H).

### §13-9 고른 안과 근거 (한 줄씩)

1. **㉦ 계획 고정.** 「인덱스를 더 단다」가 아니라 **「어느 표부터 볼지, 어느 인덱스로 볼지를 문장이 지시한다」**.
2. 근거는 실측 하나다 — `FORCE INDEX(fk_pr_partner) + FORCE INDEX(idx_pay_tenant_type_ref) + STRAIGHT_JOIN` 조합에서만 좋은 계획이 나왔다([1-V] §2-3).
3. 금액 불변은 **약속이 아니라 구조**다. 힌트·조인 순서는 술어를 못 바꾼다. 그래도 **G-RC10 값 동등성 7사례 · G-RC11 공용 식 SHA-256 앵커**가 회귀로 지킨다(무변경 초록이어야 한다).
4. 원인 B 는 **줄이고 잰다.** 「없앴다」고 쓰지 않는다.
5. **감시자가 먼저다.** 시드가 봉합 전 코드에서 빨간불을 못 내면, 그 게이트는 아무것도 증명하지 못한다.

### §14-2 [D-4] 🔴 문장별 처방 — 한 처방을 8문장에 일괄 적용하지 않는다

**㉪ 의 정당성(왜 「덜 세는 재작성」이 아닌가)**
`FROM A JOIN B ON B.k = A.x` 에서 `A.x IS NULL` 인 행은 등치 비교가 **UNKNOWN** 이라 **조인이 절대 못 맞춘다.** 따라서 `AND A.x IS NOT NULL` 은 **조인 조건이 이미 함의하는 술어**다. 함의된 술어를 더하는 것은 **결과집합을 바꿀 수 없다** — ㉣(`ec.partner_id = @P` 추가)가 기각된 이유(두 칸이 어긋난 행을 잃는다)와 **종류가 다르다.**
⚠️ 그래도 **WHERE 를 손대는 변경**이므로 **PM 결재 안건(P-10)** 으로 올린다. 설계가 혼자 「안전하다」고 넘기지 않는다.

#### §14-2-1 L5 후보와 기각 사유 (확정은 T2-A 가 한다)

| # | 후보 | 판정 | 사유 |
|---|---|---|---|
| **L5-㉭** | 4판대로 `pr` 구동(`STRAIGHT_JOIN`+`FORCE INDEX(fk_pr_partner)`) | 🔴 **기각** | 실측 **+5.5% 악화** · **D-6 를 만든다**(같은 거래처 매입전표 INSERT 1205 · #20) |
| **L5-㉫** | `AND rt.partner_id = @PartnerId` 추가 (`purchase_returns.partner_id` 는 **NOT NULL · 존재**) | 🔴 **기각(기본안 제외)** | **㉣ 와 같은 종류다.** `rt.partner_id` 와 `pr.partner_id` 가 어긋난 행이 있으면 **금액 과소 계상**(#4). 함의된 술어가 **아니다**. 불변 보장 장치(제약·단일 등록 경로)가 증명되면 **재상정** |
| **L5-㉪** | `AND rt.receipt_id IS NOT NULL` (`idx_rt_tenant_receipt` 범위) | ⚠️ **후보 — 이득 미측정** | 함의된 술어라 **안전**하나, 실사용에서 `receipt_id` 없는 반품(전표 없는 직접반품) 비율을 **아무도 모른다**(T1 Z-13: 반품 분포는 계측자가 만든 것) |
| **L5-㉬** | 인덱스 신설 `purchase_returns (tenant_id, status, is_deleted, receipt_id)` | ⚠️ **후보 — 선택도 미측정** | 확정 반품이 대다수면 안 좁혀진다. **선택도 0 인 칸을 접두로 두는 실수**(3판 DB-124 의 재발) |
| **L5-㉮** | **현상 유지 + 감시** — 처방 없이 G-RC15 가 L5 의 잠금 행 수를 재고 상한 초과 시 빨간불 | 🟢 **잠정 채택(T3 기본값)** | **모르는 것을 봉합하지 않는다.** L5 는 실물에서 `purchase_returns` **0행**이라 지금 당장의 피해가 없다. 반품이 쌓이면 게이트가 먼저 운다 |

🔴 **L5 에 대한 설계의 답**: **지금은 고치지 않는다. 대신 「pr 구동 금지」를 못 박고, 게이트로 감시한다.** ⚠️ 이 판단의 전제는 「실물 `purchase_returns` 0행」이다 — **다른 고객사에서 반품이 많으면 전제가 깨진다**(범위 밖 · §14-9).

### §14-3 [D-6] 🔴 「구동표 이전 차단」 — **수용이 아니라 처방 변경으로 없앤다**

| 물음 | 답 |
|---|---|
| 수용인가, 처방 변경인가 | 🔴 **처방 변경.** ㉪ 는 구동표를 `ec`·`ep` 에 그대로 두므로 **`purchase_receipts` 를 범위로 잡지 않는다** ⇒ 차단이 **생기지 않는다** |
| 왜 수용하면 안 되나 | 막히는 것이 **「같은 거래처의 매입전표 등록」**이다. 매칭 한 건이 도는 동안 **매입 등록이 3초 뒤 1205** — #20(흐름은 안 끊긴다) 정면이다. **봉합이 없던 차단을 새로 만드는 것**은 봉합이 아니다 |
| 원리로 말하면 | 거래처로 `pr` 를 **범위 스캔**하면 그 거래처 구간의 **간극 전부**가 잠긴다 ⇒ 그 거래처의 새 매입전표는 반드시 그 간극 중 하나에 들어간다 ⇒ **인덱스를 어떻게 바꿔도 못 피한다.** 「`pr` 를 거래처로 훑지 않는다」가 유일한 해법이다 |
| 그래서 규칙으로 | 🔴 **「`purchase_receipts`·`sales_deliveries` 를 거래처 범위로 구동표 삼지 않는다」를 T3 의 불변 규칙으로 박는다.** `pr`·`sd` 는 **PK 등치(eq_ref)로만** 만진다 |
| 게이트 | **G-RC16 에 「같은 거래처 `purchase_receipts` INSERT」·「같은 거래처 `purchase_returns` INSERT」를 사례로 넣는다.** 4판 처방을 되살리면 이 게이트가 **빨간불**이 된다 |

⚠️ **미실측**: ㉪ 적용 후 Q2·Q3 프로브를 **안 돌렸다.** 「생기지 않는다」는 **원리에서 나온 추론**이다 — T2-A 가 재서 확인한다.

### §14-4 [D-1] 🔴 인덱스 부재 시 1176 — **힌트를 안 쓰면 이 구멍이 닫힌다**

| 경로 | 인덱스 없을 때 | 판정 |
|---|---|---|
| **힌트 있음**(4판) | `FORCE INDEX` 가 없는 인덱스를 가리키면 **오류 1176 → 등록이 통째로 죽는다**(#20) | 🔴 **위험** |
| **㉪ 만**(5판 기본안) | 힌트가 없다. 인덱스가 없으면 옵티마이저가 **`ALL` 로 떨어진다** — 느리고 넓게 잠그지만 **등록은 산다** | 🟢 **고장이 나도 죽지 않는다 — #30 자가회복과 같은 방향** |

🔴 **설계의 답: 1순위는 「판정기도 두 경로도 만들지 않는 것」이다.** ㉪ 만으로 잠금이 충분히 줄면 **D-1 자체가 소멸한다.** 이것을 T2-A 가 먼저 잰다.

**2순위(㉪ 만으로 부족해 `FORCE INDEX` 를 써야 하는 문장이 나오면)** — 그때만 두 경로를 연다:

| 항목 | 내용 |
|---|---|
| 판정 시점 | **부팅 1회**(`LegacyMatchMode` 선례 그대로 — 서버 성질을 보고 경로를 고른다) |
| 판정 방법 | `information_schema.statistics` 에서 **그 문장이 요구하는 인덱스 이름이 실재하는가** 1회 조회 → 캐시 |
| 두 경로 | **같은 SQL 의 힌트 있는 판 / 없는 판.** 술어는 한 글자도 다르지 않다 ⇒ **값은 같다**(G-RC10 이 양쪽을 다 돈다) |
| 실패 시 기본값 | **힌트 없는 판**(느리지만 산다). 「모르면 안전한 쪽」 |
| 로그 | 힌트 없는 판으로 떨어지면 **`LogWarning` 한 줄**(#15) — 조용히 느려지지 않게 |
| ⛔ 안 하는 것 | 기동 시 인덱스를 **자동 생성**하지 않는다(#29 · 마이그 밖에서 DDL 금지) |

⚠️ **미확인**: 「㉪ 만으로 옵티마이저가 DB-124 를 고르는가」가 **안 재졌다.** 이 한 값이 1순위/2순위를 가른다 ⇒ **T2-A 의 첫 항목.**

### §14-5 [D-7] 🔴 G-RC15 의 상한 — 시드에서 계산하는 식 · 죽은 단언 방지

**규칙 3개**
1. 🔴 **고정 상수 금지.** 상한의 모든 입력은 **시드가 심은 수**(`RealDistributionSeed` 의 필드)여야 한다.
2. 🔴 **살아있음 증명이 먼저다.** 게이트는 상한을 쓰기 **전에** `Assert(상한 < 봉합_전_실측값)` 를 돌린다. 이것이 거짓이면 **그 단언은 죽어 있다** → 게이트 실패. (`MaxCrossTenantBlocked=4` 사고의 재발 방지)
3. 🔴 **문장마다 연결을 새로 연다.** 한 연결에서 잇달아 재면 `trx_rows_locked` 가 앞 값에 물든다(T1 §4-1).

| 문장 | 상한 식 | 봉합 전 실측(비교값) |
|---|---|---|
| **L1 · L3** | `seed.LegacyMatchedRows(partner) + 2` | 1 → ⚠️ 상한이 실측보다 크다 ⇒ **규칙 2 에 걸린다** ⇒ **L1·L3 은 「상한 감시」가 아니라 「회귀 감시」**(값이 커지면 알린다)로 분류. 봉합 대상이 아니므로 **죽은 단언이 아니라 회귀 경보**임을 주석에 명시 |
| **L2** | `seed.NonNullRefCollections + seed.MatchedDeliveries + 2` | **112,019** |
| **L4** | `seed.NonNullRefPayments + seed.MatchedReceipts + 2` | **2,274** |
| **L5** | ⚠️ **미확정** — 처방이 정해진 뒤에 세운다. 잠정 `seed.ConfirmedReturnsOfPartner * (1 + seed.AvgReturnItems) + 2` | **3,124** |
| **D1-b** | `2 * seed.PaymentsPerReceipt + 3` (T1 §4-5-4 의 관측식) | 1 (현재) |

`+2` 는 **범위 양 끝 간극** 몫이다 — 임의 상수가 아니라 **InnoDB 넥스트키 구조에서 나오는 값**이므로 그렇게 주석에 쓴다.
⚠️ **미실측**: `seed.PaymentsPerReceipt` 의 실사용 상한을 아무도 모른다(T1 Z-5). 시드가 **정하는 수**이므로 게이트는 성립하지만 **실물 상한의 근거는 아니다.**

### §14-6 [D-8] 게이트 사례는 **경로 끝 INSERT** 로

🔴 **읽기끼리는 안 막는다**(A·B 둘 다 `LOCK IN SHARE MODE` = S · T1 §8-1). 읽기 프로브로 만든 게이트는 **영원히 초록**이다.

| 역할 | 무엇 |
|---|---|
| **보유자** | 문장 하나(또는 경로 전체)를 `LOCK IN SHARE MODE` 로 잡고 유지 · **다른 연결에서 `innodb_trx` 로 생존 확인**(T1 절차 그대로) |
| **프로브(빨간불을 내야 하는 쪽)** | **경로 끝 INSERT** — ① 무관 거래처 `collections` INSERT ② 무관 거래처 `payments` INSERT ③ **같은 거래처 `purchase_receipts` INSERT**(D-6 감시) ④ **같은 거래처 `purchase_returns` INSERT** ⑤ **다른 거래처의 지급 등록 경로 전체**(T1 §8-2 의 B 경로) |
| **대조군(항상 통과해야 하는 쪽)** | 보유자 없이 같은 5종. 읽기 프로브 4종은 **「S 끼리 양립」 확인용**으로만 남기고 **판정에 쓰지 않는다**(주석 명시) |
| **함정** | UPDATE 프로브는 **대상 행을 PK 리터럴로 지목**한다. 하위질의로 찾으면 **프로브가 스스로를 막아 가짜 빨간불**(T1 §4-3④) |
| `innodb_lock_wait_timeout` | 프로브 연결에서 **1~3초**로 낮춘다(게이트가 멈추지 않게) |

### §14-7 [D-3] 두 칸 100% NULL — **채우는 길은 기각한다**

| 물음 | 답 |
|---|---|
| 검토했는가 | **했다. 기각한다.** |
| 기각 사유 ① | `collections.ref_doc_id` 가 NULL 인 것은 **결함이 아니라 설계다.** 레거시는 「이 수금이 어느 명세서에 붙었는지」를 **안 갖고 있다.** 이월잔액 매칭 기능 자체가 **그 없는 연결을 사후에 사람이 맞추는 장치**다. 채운다 = **추측으로 연결을 만든다** ⇒ 금액이 틀린다(#4) |
| 기각 사유 ② | 채우려면 `collections`·`payments` 의 **금액·멱등 키 근처를 UPDATE** 해야 한다 — `uq_collections_source`·`uq_payments_source`·`migrated_source_hash` 에 닿는다. **범위 밖**이고 마이그 무결성 예외(레거시 그대로)와 정면이다 |
| 기각 사유 ③ 🔴 | **채우는 것은 이번 처방과 반대 방향이다.** ㉪ 는 그 칸이 **비어 있다는 사실을 범위로 쓴다.** 채우면 ㉪ 의 이득이 그만큼 줄어든다 |
| 그럼 시간이 지나면 | ERP 에서 등록한 수금·지급은 그 칸이 **채워진다** ⇒ ㉪ 의 범위가 **실제로 합산해야 할 행 수만큼** 자란다. **이것은 정상이다** — 표 크기가 아니라 **일한 만큼** 자란다. 자라는 속도는 **G-RC15 가 본다** |

### §14-8 [D-5] `MaxCrossTenantBlocked` 대체 · [D-9] T2 시드 기준

**D-5** — 죽은 단언을 살리는 두 줄(의미만 적는다 · 구현은 T2):

- ① `seed.CrossTenantCaseCount > 0` 을 **먼저** 단언한다 — 사례가 0 건이면 게이트가 죽은 것이다.
- ② 막힌 건수가 **`seed.CrossTenantCaseCount` 와 같다**고 단언한다.

🔴 **`4` 라는 숫자를 코드에서 지운다.** 사례 수는 **시드 객체가 안다.** ①이 없으면 시드가 0 건이 돼도 ②가 `0 == 0` 으로 초록이 된다 — 그것이 이번에 난 사고다.

**D-9** — T2 시드 기준(`dp_full` 을 본뜨지 않는다):

| 요건 | 값 | 왜 |
|---|---|---|
| 토대 | **출하 DDL(`installer/hitpan_db_clean.sql`) 로 새로 만든 빈 DB** | `dp_full` 은 시험 인덱스 2개 + `ref_order_id` 1,365행으로 **오염**(T1 §4-4) |
| 🔴 두 칸 | `collections.ref_doc_id` **100% NULL** · `payments.ref_order_id` **100% NULL** | 실물 그대로. ㉪ 의 이득이 여기서 나온다 |
| 타입 칸 | `payment_type` 100% `purchase` · `ref_doc_type` 100% `sales_delivery` · `source_type` 100% `migration` | 방아쇠 |
| 거래처 편중 | 한 거래처가 전표의 **40% 이상** | 고르게 뿌리면 계획이 안 뒤집힌다 |
| 규모 | T1-1(계획이 뒤집히는 최소 규모)이 정한다 — **남은 일** ⇒ 그 전까지는 `payments ≈ 2,000` · `collections ≈ 10,000` 잠정 | 시험 시간 |
| `purchase_returns` | 채운다(확정 반품 · 편중 거래처) ⚠️ **비율은 실물 근거가 없다**(T1 Z-13) — 시드가 **정하는 수**임을 주석에 쓴다 | L5 측정의 유일한 길 |
| 🔴 **둘째 시드** | **「등록 누적 상태」** — 두 칸이 **채워진 행 N개**를 가진 변형 | ㉪ 의 범위가 자라는 것을 재고, **G-RC10 값 동등성이 죽은 단언이 아님을 증명**한다(§14-9 ⚠️-2) |
| 음성 대조군 | 봉합 **전** 코드에서 이 시드가 **L2 112,019 · L4 2,274 급의 수치를 재현**하는 것을 먼저 확인 | 재현 못 하는 시드는 감시자가 아니다 |

**㉪ 가 왜 「덜 세는 재작성」이 아닌가** (§14-2 의 논거를 그대로 유지한다):
`FROM A JOIN B ON B.k = A.x` 에서 `A.x IS NULL` 인 행은 등치 비교가 **UNKNOWN** 이라 **조인이 절대 못 맞춘다.** 따라서 `AND A.x IS NOT NULL` 은 **조인이 이미 함의하는 술어**이고 결과집합을 바꿀 수 없다.
🔴 **그리고 이번엔 그것이 실제로 시험됐다** — [1-V] 가 20행 진실집합을 심어 **36칸 전부 `2,082,000.00`** 으로 확인했다(§21-2 ②). 5판까지의 「값 동등 ✅」는 양쪽 다 0 을 센 **죽은 확인**이었다.

### §15-4 🔴 C4 를 왜 넣는가 — **[5] 임원이 판정할 수 있게 세운다**

### §15-7 검증 방법 — **계획이 아니라 잠금 행 수와 이웃 프로브로 판정한다**

**판정 원칙 4개** (하나라도 깨지면 게이트가 아니다)

1. 🔴 **EXPLAIN 으로 판정하지 않는다.** 계획은 **대리물**이다 — L5 에서 `ALL`→`ref; Using index` 로 글자가 바뀌고도 잠금은 −0.26%, **이웃은 그대로 막혔다.** 판정값은 `information_schema.innodb_trx.trx_rows_locked` 와 **실제 프로브 결과** 둘뿐이다.
2. 🔴 **프로브는 경로 끝 INSERT 다.** 읽기끼리는 안 막힌다(양쪽 `LOCK IN SHARE MODE` = S). **읽기 프로브로 만든 게이트는 영원히 초록**이다. 읽기 4종은 「S 끼리 양립」 확인용으로만 남기고 **판정에 안 쓴다**(주석 명시).
3. 🔴 **고정 상수 상한 금지 · 상한을 사례 수와 같게 걸지 않는다.** `MaxCrossTenantBlocked=4` 사고가 그 모양이었다 — 시드가 0건이 되면 `0 == 0` 으로 **절대 실패 불가 단언**이 된다. ⇒ **① 사례 수 > 0 을 먼저 단언 ② 상한은 시드 필드에서 계산 ③ `Assert(상한 < 봉합_전_실측)` 로 살아있음을 먼저 증명**.
4. 🔴 **문장마다 연결을 새로 연다.** 한 연결에서 잇달아 재면 `trx_rows_locked` 가 앞 값에 물든다.

## §17 🔴 정정 (PM 브라운킴 · 2026-09-21) — **§16-2 의 「조회 실패 = 실패」를 V-2 fail-open 으로 교체한다**

> 🔴 **§16 을 지우지 않는다.** 아래 두 줄만 이 절이 **대체**하고, §16 의 나머지는 **그대로 산다**.
> 근거: **사장님 오더**(작2 §16 — *"워크플로우흐름, 현 기능에 절대 침해되선 안되"*) → PM 이 **§16-4 V-1~V-7** 로 옮겼고, **§16-2 는 그 오더보다 먼저 쓰였다.**

### 17-1. 무엇이 어떻게 바뀌나

| 어디 | §16 원문 | **§17 정정** |
|---|---|---|
| `:1347` | *"모르면 통과는 절대 없다" — **조회 실패도 통과가 아니라 실패**다* | 🔴 **조회 실패는 통과다.** 「확실히 없다」(`information_schema.statistics` 를 **읽어서 0행 확인**)일 때만 차단한다 |
| `:1355` | *조회 실패 = `null` = 판정 불가 = **안전측*** | 🔴 **여기서 「안전측」은 통과 쪽이다.** 차단이 아니다 |

### 17-2. 🔴 왜 뒤집었나 — **어느 쪽이 「현 기능 침해」인가**

| | 닫는 것 | 여는 것 |
|---|---|---|
| **fail-closed**(§16 원안) | 조용한 부분 적용 | 🔴 **판정을 못 했다는 이유로 멀쩡한 업데이트를 되돌린다** |
| **fail-open**(§17) | 조용한 부분 적용 (판정이 된 경우) | 판정 불가 시의 부분 적용 |

🔴 **잘못된 롤백은 고객이 쓰던 버전을 뺏는다.** 그건 구멍을 메우려다 **현 기능을 깨는 것**이고 오더 정면 위반이다.
반면 **부분 적용은 다음 회차에 롤백으로 복구되고**, 그 사이의 피해는 **잠금이 넓어지는 것**이지 업무 중단이 아니다.
**두 위험의 크기가 다르다 — 그래서 맞바꾼다.**

⚠️ **이것이 구멍을 다시 연 것이라는 읽기를 막아 둔다**: 닫는 범위가 「판정이 되는 모든 경우」이고, 판정 불가는 **드물고 로그·본사 통지로 드러난다.** **조용한 것을 시끄럽게 만든 것**이 이번 장치의 핵심이다.

### 17-3. 🟢 이 정정은 기존 관용구와 **같은 편**이다
