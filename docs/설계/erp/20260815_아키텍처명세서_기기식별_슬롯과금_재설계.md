## §0. 30초 요약

**무엇이 고장났나** — 한 대의 기기가 여러 슬롯을 먹는다. 브라우저를 바꾸면 새 슬롯, 메인PC에서 접속하면 또 새 슬롯.
**고객이 쓰지도 않은 자리에 돈을 낸다.**

**왜** — 기기를 **생김새(지문)로 알아맞히려 하기** 때문이다. 생김새는 브라우저마다 다르고 언제든 변한다.
7/2 에도 같은 증상이 났고 지문을 정교하게 만들어 봉합했다. **한 달 반 만에 재발했다**(§13).

**어떻게 고치나 — 🔴 알아맞히기를 그만둔다.**
> 사장님: *"**자동화보단 물리적으로 수동으로.** 클라이언트 인증요청 → 메인PC 인증수락·슬롯추가 → 클라이언트 인증등록"*

**슬롯은 기기가 접속했다고 늘지 않는다. 대표가 수락 버튼을 누를 때 늘어난다.**
승인 안 한 기기는 세어지지 않으므로, 지문이 아무리 흔들려도 요금이 흔들리지 않는다.

**제어는 한 곳에서 한다** — 로그인과 업무 화면 **사이에 화면 하나**를 둔다(§14).
> 사장님: *"지금까지 슬롯에 관한 개발이 이뤄진 흐름을 살리면서 기능까지 안정적으로 구현하기 위해선
> **로그인과 히트판ERP 사이에 화면을 넣고 그 화면으로 제어를 하는게 가장 자연스러울듯**"*

**한 번 승인되면 영구다** — 대표가 슬롯을 지우기 전까지. 다시 묻지 않는다(§15).

## §1. 사장님이 그리신 구조

```
                    ┌──────────────┐
                    │   Accounts   │   계정 — 무제한
                    │ A · B · C …  │
                    └──────┬───────┘
                           │  Account-Device 관계 (N:M)
                           ▼
                    ┌──────────────┐
                    │   Devices    │   기기 — 변하지 않는 PK
                    │ 01 · 02 · 03 │
                    └──────┬───────┘
                           │  Slot 할당 (1:1)
                           ▼
                    ┌──────────────┐
                    │ Device Slots │   슬롯 — 과금 단위
                    └──────────────┘

Account A ──┐
Account B ──┼── Device 01 ── Slot 01
Account C ──┘
```

**과금 단위는 계정이 아니라 기기다.** 사무실 PC 한 대를 경리·구매·창고 담당 셋이 번갈아 써도 슬롯 1개다.
이것이 ERP 현장과 맞는다 — 창고 PC 한 대를 여러 직원이 교대로 쓰는 것은 흔한 일이고,
그때마다 슬롯을 먹으면 고객이 납득하지 못한다.

## §2. 현행 실측 — 무엇이 있고 무엇이 없나

### §2-1. 기기를 찾는 열쇠

**네 곳 전부 지문 단독이다.**

```sql
SELECT device_id, status, COALESCE(is_main_pc,0)
FROM tenant_devices
WHERE tenant_id = @TenantId AND fingerprint = @Fp
LIMIT 1
```

| 위치 | 용도 |
|---|---|
| `TenantDeviceService.cs:141-148` | 로그인 시 기기 조회 |
| `TenantDeviceService.cs:580` | QR 모바일 등록 멱등 검사 |
| `MainPcRegistrationService.cs:150-151` | 메인PC 자기 등록 |
| `DeviceRegistrationController.cs:82-85` | 백오피스 경로 (여기만 `status='approved'` 추가) |

🔴 **`device_id` 도 `auth_key_hash` 도 조회 열쇠가 아니다.**

### §2-2. 장비넘버는 있는데 안 보낸다

| 있는 것 | 위치 | 상태 |
|---|---|---|
| `device_id` 컬럼 (PK, varchar(36)) | `hitpan_db_clean.sql` | ✅ 있음 |
| 서버가 발급 (`Guid.NewGuid()`) | `TenantDeviceService.cs:297` | ✅ 발급됨 |
| 기기가 저장 (`hitpan_device_id`) | `AuthService.cs:89-93` | ✅ 저장됨 |
| 읽는 함수 `getDeviceId()` | `device-fingerprint.js:234` | ✅ 만들어짐 |
| **로그인 때 서버로 보냄** | — | 🔴 **없음 — 호출처 0곳** |

로그인이 보내는 것은 **셋뿐**이다 (`AuthService.cs:43-60`):
```
DeviceFingerprint · DeviceType · DeviceName
```
`LoginRequest` DTO (`LoginRequest.cs:17-25`)에도 `DeviceId` · `AuthKey` 필드가 **없다.**

🔴 **서버가 장비넘버를 내려주고, 기기가 저장하고, 다음 접속에 도로 안 보낸다.**
사장님이 *"인증하면 백 번 접속해도 한 번"* 이라 하신 것이 안 되는 이유가 정확히 이 자리다.

### §2-3. 지문이 세 갈래로 갈려 있다

같은 `tenant_devices.fingerprint` 한 컬럼에 **서로 다른 산식 셋**이 들어온다.

| 만드는 곳 | 형식 | 재료 |
|---|---|---|
| `device-fingerprint.js:66` | `HFPv2-` + FNV-1a | 브라우저 환경 특성 + UA |
| `MainPcRegistrationService.cs:230-239` | `MAINPC-` + SHA-256 | `MachineName` + TENANT_CODE + SLOT_INDEX |
| `UserInfoPage.razor.cs:116-117` | (eval 조립) | UA + screen + timezone |

🔴 **접두어부터 다르므로 서로를 절대 찾지 못한다.**
메인PC가 자기를 `MAINPC-…` 로 등록하고, 그 PC에서 사람이 브라우저로 접속하면 `HFPv2-…` 로 조회한다 →
없다고 판단 → **새 기기 등록 → 슬롯 하나 더.**
**이것이 사장님이 실측하신 "메인PC를 자동으로 잡고, 그 PC에서 접속하면 또 슬롯을 잡는" 증상의 원인이다.**

### §2-4. 슬롯을 세는 방법

SELECT device_type AS t, COUNT(*) AS c

WHERE tenant_id = @TenantId AND status = 'approved'

## §4. 재설계 — 무엇을 바꾸나

### §4-1. 원칙

> **기기는 자기 생김새를 신고하지 않는다. 서버가 준 이름표를 들고 온다.**

브라우저에게 *"이 기계가 무엇이냐"* 를 물으면 영원히 답을 못 한다 — 하드웨어 정보 접근이 막혀 있고,
앞으로도 열리지 않는다. **묻는 대상을 바꾼다.**

### §4-2. 기기 식별 — 두 갈래, 저장은 한 자리

| 기기 | 히트판 서버가 도나 | 식별 방법 |
|---|---|---|
| **메인PC** (본체·DB 보유) | ✅ 돈다 | **서버가 OS 에서 하드웨어 값을 읽는다** — 사장님: *"장치관리자에 찍히는 고유 장비넘버"* |
| **직원 PC · 휴대기기** | ❌ 브라우저만 | **서버가 발급한 장비넘버 + 인증키를 들고 온다** |

🔴 **두 갈래로 식별하되, 결과는 `tenant_devices` 한 줄로 모인다.**
지금은 `MAINPC-` 와 `HFPv2-` 가 형식부터 달라 못 만나서 한 PC 가 두 줄이 됐다(§2-3).

> **MAC 주소를 1차 재료로 쓰지 않는 이유** — 사장님 지적대로 여러 개이고(유선·무선·가상 어댑터),
> 랜선을 뽑거나 VPN·가상머신을 켜면 목록이 바뀐다. 무엇보다 **직원 기기에서는 서버가 없어 읽을 방법 자체가 없다.**
> 메인PC 재료로는 검토 대상이며(§10-2), 그 경우도 **여러 값을 묶어** 하나가 바뀌어도 견디게 한다.

### §4-3. 찾는 순서를 뒤집는다

| 순서 | 열쇠 | 잡히는 기기 |
|---|---|---|
| ① | **장비넘버 + 인증키** | 인증받은 기기 — **백 번 와도 이 줄** |
| ② | **장비넘버** 단독 | 인증 전 기기 |
| ③ | 지문 | 옛 기기 (장비넘버 없던 시절) — **호환 전용** |
| ④ | 없음 | **그때만** 새 슬롯 |

현행은 ③만 있다. ①②를 앞에 놓으면 —
브라우저를 바꿔도 · 메인PC 에서 접속해도 · 창을 몇 개 열어도 · 주소가 달라져도 **한 줄이다.**

### §4-4. 로그인이 장비넘버를 보낸다

**이 설계의 핵심 한 줄.** 지금 없는 것은 이것 하나다.

```
LoginRequest 에 DeviceId · AuthKey 를 추가한다
AuthService 가 getDeviceId() · getAuthKey() 를 호출해 함께 보낸다
```

함수는 이미 있다(`device-fingerprint.js:234,253`). **부르는 쪽만 없다.**

### §4-5. 메인PC 가 자기 장비넘버를 브라우저에 내려준다

메인PC 는 서버와 브라우저가 **같은 PC** 에 있다. 서버가 자기 장비넘버를 화면에 내려주면
브라우저가 그것을 저장하고, 다음부터 그 값으로 조회된다 → **`MAINPC-` 행에 그대로 붙는다.**

🔴 **이 한 가지가 지금 새고 있는 슬롯을 막는다.**

### §4-6. 슬롯 계산을 한 곳으로

네 번 복제된 COUNT 를 **단일 메서드**로 모은다. 한 곳만 고치면 전부 반영되게.

### §4-7. 요금 기준값을 설정으로

| 항목 | 지금 | 바꿀 것 |
|---|---|---|
| 요금제별 기본 슬롯 | 코드 `switch` | **설정에서 읽는다** (본사 마스터 화면) |
| 추가슬롯 산식 | 코드 `extra * 2` | **설정에서 읽는다** |
| 추가슬롯 가격 | 코드에 없음 | **설정** — 확정: **1만원 / PC 1 + 모바일 1** |

⚠️ **가격을 바꾸는 데 코드 배포가 필요하면 그것은 설계 결함이다.**

## §5. 과금 규칙 (사장님 확정 2026-08-15)

| 항목 | 값 | 출처 |
|---|---|---|
| 과금 단위 | **기기 1대 = 슬롯 1개** | 사장님 확정 |
| 계정 수 | **무제한** | 사장님 그림 |
| 메인PC | **슬롯을 센다** (면제 아님) | 사장님 확정 — 주석 `:165` 는 틀림 |

⚠️ **현행 추가슬롯 산식은 PC 1 + 모바일 2** 다(`extra * 2`). 사장님 확정(1+1)과 **다르다.** 설계는 1+1 을 따른다.

⚠️ **기본 제공 슬롯 수는 이 문서에서 확정하지 않는다.** 코드의 `(5,3)` · `(10,8)` 은 근거가 없다.
설계는 *"본사가 화면에서 정한다"* 로 짜고, 실제 숫자는 사장님이 나중에 넣으신다.

## §5-A. 🔴 과금 정합 — 촘촘하게 (사장님 강조 2026-08-15)

> 사장님: *"특히나 강조하는것은, **과금에 연결된거니 더욱 촘촘하게** 신경쓰도록"*
>
> 🔴 **슬롯 계수가 틀리면 두 방향 모두 사고다.**
> 많이 세면 **고객이 쓰지도 않은 자리에 돈을 낸다**(지금 나고 있는 사고).
> 적게 세면 **요금정책이 샌다**. 어느 쪽도 나중에 조용히 고칠 수 없다 — 이미 청구된 돈이다.

### §5-A-1. 계수 불변식 — 구현이 반드시 지켜야 할 것

| # | 불변식 | 어기면 |
|---|---|---|
| **I-1** | **한 물리 기기 = `tenant_devices` 한 줄.** 브라우저·창·주소·로그인 계정이 달라도 늘지 않는다 | 고객 과다 청구 (**현행 위반 중**) |
| **I-2** | 같은 기기가 **재접속·재로그인·재설치**해도 새 줄이 생기지 않는다 | 고객 과다 청구 |
| **I-3** | **폐기된 기기는 슬롯을 물지 않는다.** 폐기 즉시 반환된다 | 고객 과다 청구 |
| **I-4** | 슬롯을 세는 코드는 **한 곳뿐이다** | 네 곳이 갈려 서로 다른 답 (**현행 위반 중** — §2-4) |
| **I-5** | 요금 기준값(슬롯 수·가격)은 **설정에서만** 읽는다. 코드에 숫자를 적지 않는다 | 가격 변경에 전 고객 배포 필요 (**현행 위반 중** — §2-5) |
| **I-6** | 기기 종류를 모르면 **싼 칸**으로 보낸다 | 고객 과다 청구 |
| **I-7** | 계수 대상은 **`status='approved'`** 뿐. `pending`·`revoked` 는 세지 않는다 | 승인 전 기기가 과금됨 |

🔴 **I-1 · I-4 · I-5 는 지금 깨져 있다.** 이 설계의 존재 이유다.

### §5-A-2. 계수 게이트 — 시험 없이 배포 금지

현행 기기·슬롯 시험은 **0건**이다(§2-6). 과금이 걸린 자리에 게이트가 없다.
아래는 **구현과 함께 반드시 만들고, 반증까지 확인**한다(빼면 FAIL 하는지).

| 게이트 | 검사 내용 |
|---|---|
| G-1 | 같은 장비넘버로 **100회 로그인** → `tenant_devices` **1줄** (사장님 원문: *"100번을 접속해도 한번만"*) |
| G-2 | 같은 기기 · **다른 브라우저** 3종 → 1줄 |
| G-3 | 같은 기기 · **다른 주소**(도메인/localhost) → 1줄 |
| G-4 | 메인PC 자동등록 + **그 PC에서 브라우저 접속** → 1줄 (§4-5) |
| G-5 | 계정 3개가 같은 기기로 로그인 → **1줄 · 슬롯 1개** (사장님 그림 §1) |
| G-6 | 폐기 → 슬롯 즉시 반환 (I-3) |
| G-7 | 슬롯 계산이 **단일 메서드**를 통과하는지 (I-4 · 복제 재발 차단) |
| G-8 | 요금 기준값이 **코드 리터럴에 없는지** (I-5) |
| G-9 | 옛 지문 기기 → 장비넘버 승격, **새 줄 안 생김** (§7 재매핑) |
| G-10 | 한도 초과 경계 — 정확히 한도에서 막히고 한 대 아래에서 통과 |

⚠️ **G-1 · G-4 · G-9 는 지금 나고 있는 사고 그 자체다.** 이 셋이 통과하지 않으면 배포하지 않는다.

### §5-A-3. 청구 대조 — 사람이 확인할 수 있어야 한다

🔴 **고객이 "왜 이만큼 나왔나"를 물으면 답할 수 있어야 한다.**

- 등록기기 화면에 **어느 기기가 몇 슬롯을 쓰는지** 그대로 보인다 (현행 `DeviceManagePage` 확장)
- 슬롯이 늘어난 **시점과 이유**가 기록에 남는다 (`device_login_logs` 활용 검토)
- 헌법 #24 — 가르치지 않고 넘기는 것은 거짓말이다. **고객이 자기 청구를 검증할 수 있어야 한다**

⚠️ [[feedback_semi_auto_principle]] — *"히트판에 100% 자동화는 없다. 무조건 반자동."*
슬롯 계산은 자동으로 하되 **본사가 조정할 수 있어야 하고, 조정 이력이 남아야 한다.**

| # | 원칙 | 근거 |

## §7. 되돌릴 수 없는 위험 — 기존 고객 재매핑

> ✅ **2026-08-15 사장님 확인: 아직 실사용 고객이 없다.**
> ⇒ **지금은 망가질 기기가 없다.** 이 절의 위험은 **현재 시점에는 실재하지 않는다.**
> 🔴 **그래서 지금이 구조를 깔끔하게 잡을 수 있는 유일한 창이다. 베타가 나가면 이 창은 닫힌다.**
> 아래는 **베타 이후를 위해 지금 만들어 두는 것**이다 — 나중에 만들려면 고객을 세워두고 만들어야 한다.

🔴 **베타 출시 후에는 이 설계에서 가장 위험한 자리가 된다.**

식별 방식을 바꾸면 이미 등록된 기기가 **전부 새 기기로 잡힌다.**
→ 슬롯이 두 배 → **한도 초과 → 로그인 차단**(§10-1 결재로 확정: 한도 초과는 막는다).

`device-fingerprint.js:15-16` 이 이미 경고하고 있다:
> *"지문 산식을 바꾸면 기존 등록 기기(옛 난수)와 안 맞아 재인식될 수 있다 → 마이그레이션은 서버측 유예·재매핑으로 처리"*

**따라서 §4-3 의 ③(지문 호환 경로)은 선택이 아니라 필수다.**
옛 기기가 지문으로 걸리면 **그 자리에서 장비넘버를 발급해 붙인다**(승격). 새 줄을 만들지 않는다.

⚠️ 재매핑 설계가 없는 구현은 **배포 즉시 전 고객 장애**다. 작업지시서에 반드시 포함한다.

## §14. 🔴 제어의 중심 — 로그인과 업무 화면 사이의 한 화면

> 사장님 (2026-08-15): *"**로그인과 히트판ERP 사이에 화면을 넣고 그 화면으로 제어**를 하는게 가장 자연스러울듯"*
> *"401로 가지 않게, 로그인과, 히트판화면 중간에 화면을 하나 두자고 한거야"*
> *"중간 화면에서 **인증키 등록을 하는 장치**가 되는거지"*

### §14-1. 왜 화면 하나로 모으나

지금 기기 판정이 **세 군데로 흩어져 있다.**

| 자리 | 무엇을 하나 | 문제 |
|---|---|---|
| `AuthController.cs:101-105` | 로그인에서 **401** | 🔴 토큰을 못 받아 **아무 화면도 못 뜬다** |
| `DeviceAuthMiddleware.cs:98-124` | API 마다 **403** | 화면이 뜨려면 먼저 403 을 맞아야 한다 |
| `MainLayout.razor:52` | 인증 화면 | **업무 레이아웃 안**이라 "들어왔는데 왜 또 막나" |

셋이 각자 판단하니 흐름이 안 맞는다. **한 곳으로 모은다.**

### §14-2. 흐름

```
[로그인]  ← 401 을 내지 않는다. 정상으로 끝난다
   ↓
[기기 확인 화면]  ← 🔴 제어는 여기서만
   │
   ├ 승인됨 + 인증키 보유    → 그냥 지나간다 (다시 안 뜬다)
   │
   ├ 미승인                  → "미승인기기입니다. 승인요청 하시겠습니까?"  Y / N
   │     ├ N → 요청 안 함. 이 화면에 머문다
   │     └ Y → 메인PC(대표)에게 승인 요청 알림 (§14-4)
   │
   ├ 요청함 · 대기 중        → "관리자 승인을 기다리는 중입니다"
   │                            승인 알림이 오면 자동 전환
   │
   ├ 🔴 승인됨 · 인증키 없음 → **여기서 번호를 입력받아 저장한다** (§14-3)
   │
   └ 거부됨                  → "관리자가 등록기기 승인을 거부하였습니다.
                                관리자에게 문의하세요"
                                → 🔴 **영구 거부 아님. 다시 처음으로 돌아간다**
   ↓
[히트판 업무 화면]
```

**대표 쪽 분기** (승인 요청을 받았을 때)
```
[승인 요청 알림]  → Y → 슬롯 여유 있음 → 승인 · 슬롯 +1 · 인증번호 발급
                    │
                    └→ 슬롯 초과 → "슬롯기기 구독을 하시겠습니까?"  Y / N
                          ├ Y → 랜딩페이지로 이동 (결제)
                          └ N → 슬롯기기 추가로 등록되지 않습니다
                  → N → 클라이언트에 거부 안내 (위 흐름의 마지막 갈래)
```

### §14-3. 🔴 이 화면이 인증키를 등록하는 장치다

대표가 수락하면 번호가 나온다. **그 번호를 이 화면에서 바로 넣는다.** 별도 화면으로 빠지지 않는다.
입력하면 장비넘버·인증키가 기기에 저장되고 통과한다.

⇒ **이 화면이 장비넘버가 기기에 심어지는 유일한 자리다.**
다음 접속부터는 `device_id AND auth_key_hash` 로 조회되고, 승인은 영구이므로(§15) **이 화면을 다시 볼 일이 없다.**

🔴 **번호는 사람이 옮겨 적는다.** 대표가 읽고 → 직원에게 알려주고 → 직원이 입력한다.
알림에 번호를 실어 보내면 편하지만 **옆에서 화면을 보면 그대로 새어나간다.**
사장님: *"자동화보단 물리적으로 수동으로."* **편의보다 확실함을 택한다.**

### §14-4. 승인 요청 알림 — 기존 배관을 그대로 쓴다

> 사장님: *"이미 메신저 통해 알림창을 만들어뒀음"* → **실측 확인 완료.**

### §14-5. 401 을 걷어낸다

🔴 **`AuthController.cs:101-105` 가 흐름을 막는 단 하나의 자리다.**
`allowed=false` 면 pending 이든 한도초과든 구분 없이 `401 Unauthorized` 를 던진다.
⇒ 토큰이 없으니 SignalR 에 못 붙고, **승인돼도 클라이언트가 모른다.** 화면이 뜰 자리조차 없다.

**로그인은 정상으로 끝낸다.** 기기 상태는 응답에 실어 보내고, 판단은 §14-2 화면이 한다.

⚠️ **이것은 보안을 무르게 하는 것이 아니다.**
`DeviceAuthMiddleware` 가 여전히 `/api/*` 전부를 막는다(승인된 기기만 통과).
**업무 데이터는 그대로 잠겨 있고, 열리는 것은 로그인과 이 화면뿐이다.**
문은 열리되 방에는 못 들어간다.

⇒ **§3 모순 #2 판정 정정**: `:271` **주석이 맞고 코드가 틀렸다.** (1차 초안은 ⚠️미결로 두었다)

### §14-6. 기존 흐름을 살린다 — 새로 만드는 것은 최소

> 사장님: *"**지금까지 슬롯에 관한 개발이 이뤄진 흐름을 살리면서** 기능까지 안정적으로 구현"*

| 이미 있는 것 | 어떻게 하나 |
|---|---|
| `pending/approved/revoked` 상태 | **그대로.** 화면이 이 상태를 읽어 분기 |
| 승인 API (`tenant_admin` 전용) | **그대로.** 대표가 누르는 버튼이 이미 있다 |
| 인증키 발급·검증 | **그대로.** 승인 시 발급되는 흐름 유지 |
| SignalR 알림 배관 | **연결만.** 배관은 있고 부르는 쪽이 없다 |
| `DeviceAuthGate.razor:107-117` (번호 입력) | **옮긴다.** 레이아웃 안 → 이 화면 |
| `AuthController.cs:101-105` 401 | **걷어낸다.** 유일하게 막는 자리 |

🔴 **되돌리기 쉽다** — 이 화면이 통과만 시키면 지금과 똑같이 동작한다.
문제가 나면 화면에서 판단을 끄면 된다. **서비스 로직을 헤집지 않는다.**

🔴 **과금 판정이 한 곳에 모인다** — 슬롯이 늘어나는 순간이 **"대표가 수락할 때"** 하나로 좁혀진다.
흩어져 있으면 숫자가 틀렸을 때 어디서 샜는지 못 찾는다.

## §15. 승인은 영구다

> 사장님: *"승인된 기기는 **영구(메인에서 슬롯삭제 하기 전까지)**적으로 쓸수 있게"*

**실측 — 현행이 이미 영구다.**

| 항목 | 실측 |
|---|---|
| 인증키 만료 | **없음** |
| 승인 상태 만료 | **없음** |
| `last_seen_at` 기반 자동 정리 | **없음** |
| 자동 폐기 스케줄러 | **없음** |
| 10분 만료가 걸린 것 | **QR 등록 토큰만** — 등록용 일회용 코드라 맞다 |

⚠️ **다만 지금은 "우연히" 영구다.** 만료 코드가 없어서 그런 것이지 지켜지고 있는 것이 아니다.
누가 나중에 *"오래 안 쓴 기기는 정리하자"* 를 넣으면 **조용히 깨진다.** 슬롯이 줄어 요금 정산에도 걸린다.

🔴 **설계 확정**:
> **승인은 영구다. 만료 · 자동정리 · 재인증 요구를 두지 않는다.**
> 승인이 풀리는 유일한 길은 **대표의 명시적 폐기**뿐이다.

게이트 — **G-18**(§16). 승인 후 시간이 지나도 유효한가 · 오래 안 쓴 기기가 자동으로 사라지지 않는가.

## §17. [3-V] 병렬검증 P0 반영

### §17-1. 🔴 열쇠는 AND 다 (PI-08)

1차 초안이 1순위 열쇠를 *"장비넘버 + 인증키"* 라고만 쓰고 **AND 인지 OR 인지 정하지 않았다.**
§3 서문에 *"정하지 않으면 구현자가 임의로 고른다"* 고 스스로 경고해 놓고 같은 실수를 했다.

```sql
WHERE tenant_id = (JWT 클레임)
  AND device_id = @Id
  AND auth_key_hash = @Hash
  AND status = 'approved'
```

🔴 **인증키만으로는 찾지 못하게 한다.** OR 로 읽으면 인증키를 옮겨 적은 기기가 남의 줄에 붙어 **요금이 샌다.**
그리고 인증키 공유는 **대표가 번호를 알려주는 구조상 자연스러운 행동**이라 실제로 일어난다.

⇒ `VerifyAuthKeyAsync:479` · `DeviceAuthMiddleware:107` 도 같이 고친다 —
지금은 `auth_key_hash` 만 보고 `device_id` 를 안 본다. **문 여는 것도 "이 기기의 열쇠인가"를 물어야 한다.**

### §17-2. 🔴 DDL 에 장비넘버 칸을 따로 만든다 (PI-09)

현행: `UNIQUE(tenant_id, fingerprint)` + `fingerprint NOT NULL`.
**지문 칸이 하나뿐이라 `MAINPC-` 와 브라우저 접속을 한 줄에 담을 자리가 없다.**
⇒ **§4-5 메인PC 합류가 물리적으로 성립하지 않는다.** 1차 초안은 DDL 을 아예 언급하지 않았다.

**칸을 나눈다** — 서버가 읽는 하드웨어 식별값을 담을 컬럼을 추가하고, `fingerprint` 는 **옛 기기 호환 전용**으로 남긴다.
- 헌법 #36 — 출하 DDL(`hitpan_db_clean.sql`) 편입
- 헌법 #13 — 새 SQL 전 `DESCRIBE tenant_devices`
- 🔴 마이그레이션은 **`src/HitPan.API/Migrations/SQL/DB-NN_*.sql` 에만** ([[project_migration_real_path]])

### §17-3. 계수는 4곳이 아니라 **5곳** (P0 실측)

1차 초안 "4곳" 은 부정확하다. **5곳이고 모양이 서로 다르다.**

| 위치 | 모양 |
|---|---|
| `TenantDeviceService.cs:97 / :245 / :410` | `GROUP BY` 전체형 |
| `TenantDeviceService.cs:597` | 단일 COUNT · **모바일만** |
| 백오피스 `DeviceRegistrationController.cs:98-101` | `device_type = @Type` **등호** → 🔴 **`tablet` 이 어느 칸에도 안 잡힌다** |

백오피스 등호가 특히 나쁘다 — **공짜로 쓰이는 기기**가 생긴다(→ G-13).

### §17-4. `enterprise` 정정 (PI-14)

코드만 `premium`, **DDL · 시리얼 발급 · 백오피스는 전부 `enterprise`.**
⇒ 값이 안 맞아 `_ => (5,3)` 으로 떨어져 **최상위 고객이 basic 한도를 받는다.** 지금도 나고 있는 사고다.
⚠️ §10-4 미결이 *"premium 이 들어오면"* 이라는 **틀린 질문**을 하고 있었다. `enterprise` 로 정정한다.

### §17-5. `?? "pc"` 는 **두 곳** (P0 실측 D-9)

`AuthController.cs:93` **와** `TenantDeviceService.cs:260`. 한 곳만 고치면 아무것도 안 바뀐다.

### §17-6. ⚠️ 구현자 함정 — `:165` 주석 (P0 실측 D-3)

`TenantDeviceService.cs:165` 주석이 *"메인PC 는 슬롯을 안 센다"* 고 말한다.
🔴 **그 주석을 보고 SQL 에 `is_main_pc = 0` 을 넣으면 요금정책이 샌다.**
사장님 확정은 **"메인PC 포함"** ⇒ **코드가 맞고 주석이 틀렸다. 고칠 것은 주석이다.**
