## §0. 30초 요약

**무엇이 고장났나** — 한 대의 기기가 여러 슬롯을 먹는다. 브라우저를 바꾸면 새 슬롯, 메인PC에서 접속하면 또 새 슬롯.
**고객이 쓰지도 않은 자리에 돈을 낸다.**

**왜** — 기기를 **생김새(지문)로 알아맞히려 하기** 때문이다. 생김새는 브라우저마다 다르고 언제든 변한다.
7/2 에도 같은 증상이 났고 지문을 정교하게 만들어 봉합했다. **한 달 반 만에 재발했다**(§13).

**어떻게 고치나 — 🔴 알아맞히기를 그만둔다.**
> 사장님: *"**자동화보단 물리적으로 수동으로.** 클라이언트 인증요청 → 메인PC 인증수락·슬롯추가 → 클라이언트 인증등록"*

**슬롯은 기기가 접속했다고 늘지 않는다. 대표가 수락 버튼을 누를 때 늘어난다.**
승인 안 한 기기는 세어지지 않으므로, 지문이 아무리 흔들려도 요금이 흔들리지 않는다.

**제어는 한 곳에서 한다** — 로그인과 업무 화면 **사이에 화면 하나**를 둔다(§14).
> 사장님: *"지금까지 슬롯에 관한 개발이 이뤄진 흐름을 살리면서 기능까지 안정적으로 구현하기 위해선
> **로그인과 히트판ERP 사이에 화면을 넣고 그 화면으로 제어를 하는게 가장 자연스러울듯**"*

**한 번 승인되면 영구다** — 대표가 슬롯을 지우기 전까지. 다시 묻지 않는다(§15).

## §1. 사장님이 그리신 구조

```
                    ┌──────────────┐
                    │   Accounts   │   계정 — 무제한
                    │ A · B · C …  │
                    └──────┬───────┘
                           │  Account-Device 관계 (N:M)
                           ▼
                    ┌──────────────┐
                    │   Devices    │   기기 — 변하지 않는 PK
                    │ 01 · 02 · 03 │
                    └──────┬───────┘
                           │  Slot 할당 (1:1)
                           ▼
                    ┌──────────────┐
                    │ Device Slots │   슬롯 — 과금 단위
                    └──────────────┘

Account A ──┐
Account B ──┼── Device 01 ── Slot 01
Account C ──┘
```

**과금 단위는 계정이 아니라 기기다.** 사무실 PC 한 대를 경리·구매·창고 담당 셋이 번갈아 써도 슬롯 1개다.
이것이 ERP 현장과 맞는다 — 창고 PC 한 대를 여러 직원이 교대로 쓰는 것은 흔한 일이고,
그때마다 슬롯을 먹으면 고객이 납득하지 못한다.

### §2-1. 기기를 찾는 열쇠

### §2-2. 장비넘버는 있는데 안 보낸다

|---|---|---|

로그인이 보내는 것은 **셋뿐**이다 (`AuthService.cs:43-60`):

🔴 **서버가 장비넘버를 내려주고, 기기가 저장하고, 다음 접속에 도로 안 보낸다.**
사장님이 *"인증하면 백 번 접속해도 한 번"* 이라 하신 것이 안 되는 이유가 정확히 이 자리다.

### §2-3. 지문이 세 갈래로 갈려 있다

같은 `tenant_devices.fingerprint` 한 컬럼에 **서로 다른 산식 셋**이 들어온다.

| 만드는 곳 | 형식 | 재료 |
|---|---|---|
| `device-fingerprint.js:66` | `HFPv2-` + FNV-1a | 브라우저 환경 특성 + UA |
| `MainPcRegistrationService.cs:230-239` | `MAINPC-` + SHA-256 | `MachineName` + TENANT_CODE + SLOT_INDEX |
| `UserInfoPage.razor.cs:116-117` | (eval 조립) | UA + screen + timezone |

🔴 **접두어부터 다르므로 서로를 절대 찾지 못한다.**
메인PC가 자기를 `MAINPC-…` 로 등록하고, 그 PC에서 사람이 브라우저로 접속하면 `HFPv2-…` 로 조회한다 →
없다고 판단 → **새 기기 등록 → 슬롯 하나 더.**
**이것이 사장님이 실측하신 "메인PC를 자동으로 잡고, 그 PC에서 접속하면 또 슬롯을 잡는" 증상의 원인이다.**

## §4. 재설계 — 무엇을 바꾸나

### §4-1. 원칙

> **기기는 자기 생김새를 신고하지 않는다. 서버가 준 이름표를 들고 온다.**

브라우저에게 *"이 기계가 무엇이냐"* 를 물으면 영원히 답을 못 한다 — 하드웨어 정보 접근이 막혀 있고,
앞으로도 열리지 않는다. **묻는 대상을 바꾼다.**

### §4-2. 기기 식별 — 두 갈래, 저장은 한 자리

| 기기 | 히트판 서버가 도나 | 식별 방법 |
|---|---|---|
| **메인PC** (본체·DB 보유) | ✅ 돈다 | **서버가 OS 에서 하드웨어 값을 읽는다** — 사장님: *"장치관리자에 찍히는 고유 장비넘버"* |
| **직원 PC · 휴대기기** | ❌ 브라우저만 | **서버가 발급한 장비넘버 + 인증키를 들고 온다** |

🔴 **두 갈래로 식별하되, 결과는 `tenant_devices` 한 줄로 모인다.**
지금은 `MAINPC-` 와 `HFPv2-` 가 형식부터 달라 못 만나서 한 PC 가 두 줄이 됐다(§2-3).

> **MAC 주소를 1차 재료로 쓰지 않는 이유** — 사장님 지적대로 여러 개이고(유선·무선·가상 어댑터),
> 랜선을 뽑거나 VPN·가상머신을 켜면 목록이 바뀐다. 무엇보다 **직원 기기에서는 서버가 없어 읽을 방법 자체가 없다.**
> 메인PC 재료로는 검토 대상이며(§10-2), 그 경우도 **여러 값을 묶어** 하나가 바뀌어도 견디게 한다.

### §4-3. 찾는 순서를 뒤집는다

| 순서 | 열쇠 | 잡히는 기기 |
|---|---|---|
| ① | **장비넘버 + 인증키** | 인증받은 기기 — **백 번 와도 이 줄** |
| ② | **장비넘버** 단독 | 인증 전 기기 |
| ③ | 지문 | 옛 기기 (장비넘버 없던 시절) — **호환 전용** |
| ④ | 없음 | **그때만** 새 슬롯 |

현행은 ③만 있다. ①②를 앞에 놓으면 —
브라우저를 바꿔도 · 메인PC 에서 접속해도 · 창을 몇 개 열어도 · 주소가 달라져도 **한 줄이다.**

#### §4-45-2. 🔴 `hardware_id` 는 **당분간 비워 둔다** (헌법 #9)

봉합안이 채택한 결론을 따른다 — **억지로 채우면 그것이 새 결함이다.**

| 선택지 | 판정 | 이유 |
|---|---|---|
| 서버가 OS 하드웨어 값을 읽어 `hardware_id` 에 넣는다 | ⏸ **보류** | 메인PC 에서만 가능. 직원 기기는 브라우저뿐이라 원천적으로 못 읽는다 |
| 하드웨어 값을 **브라우저에 내려주고 받는다** | 🔴 **폐기** | 내려주는 순간 **아무 기기나 그 값을 들고 와** 남의 줄에 붙는다 (개발팀 축 A — 철회 유지) |
| **판별을 아예 안 한다** (§4-45-3) | 🟢 **채택** | 판별이 없으면 오판도 없다 |

⇒ 🔴 **컬럼은 남기되 배선은 하지 않는다.** 단 **DDL 주석의 거짓말은 지금 고친다** —
*"격하됐다"* 가 아니라 *"⏸ 미사용. `fingerprint` 가 여전히 옛 기기 조회 열쇠"* 로.
⚠️ 칸을 지우는 선택지는 **택하지 않는다**(헌법 **#9** — *"DB는 미리 다, 코드는 필요할 때만"*).

> 🔴 **PM 근거 정정 (2026-08-18)** — 초안은 이 자리에 **헌법 #37**(*"안 읽힌다 ≠ 잔재"*)을 근거로 적었다. **조항 오용이다.**
> #37 원문(`헌법원문_1-43.md:193`)의 덩어리2는 *"**쓰기(수신 INSERT/UPSERT)는 살아 작동하지만** SELECT 하는 코드가 0건"* 인 컬럼이다(`reseller_id` 등).
> `hardware_id` 는 **쓰는 코드도 0건** — 값이 들어온 적이 없다. **다른 상태다.**
> ⇒ 존치 근거는 **#9**(미리 만들어 둔 자리는 정상)이지 #37 이 아니다.
> 결론(남긴다)은 같으나, **근거를 틀리게 남기면 다음 사람이 *"#37 이라 못 건드린다"* 로 잘못 인용한다.**

#### §4-45-3. 🟢 채택안 — 메인PC 를 **판별하지 않는다**

> **메인PC 는 이미 자기 줄이 있다**(`is_main_pc=1, status='approved'`).
> 문제는 **브라우저가 그 줄을 못 찾아서 새 줄을 만드는 것**이었다.
> ⇒ **찾게 해 주면 끝이다. 판별할 일이 없다.**

```
[메인PC 서버 기동]
   MainPcRegistrationService 가 BuildServerFingerprint() 로 MAINPC-… 생성
   → tenant_devices 에 is_main_pc=1, status='approved' 로 자기 등록
        │
        │  🔴 지금은 여기서 끊긴다 — DB 에만 넣고 브라우저에 안 준다
        ▼
[같은 PC 에서 브라우저 로그인]
   서버가 자기 지문을 LoginResponse 에 실어 내린다        ← 🆕 이 한 줄이 없다
   → 브라우저가 저장 → 다음부터 1순위 조회로 그 줄에 붙는다
   ⇒ 같은 PC 가 두 줄이 되지 않는다
```

**실측 근거**:

| 항목 | 실측 |
|---|---|
| `BuildServerFingerprint()` 존재 | ✅ `src/HitPan.API/HostedServices/MainPcRegistrationService.cs:230-238` — `"MAINPC-" + SHA256(MachineName…)[..16]` |
| 자기 등록 시 사용 | ✅ 같은 파일 `:145` |
| **브라우저로 내려주는 자리** | 🔴 **없음** — `LoginResponse.cs` 에 서버 지문 필드가 없다 (`DeviceId`·`DeviceAwaitingApproval` 등만 존재) |

🔴 **새로 만들 것은 두 자리뿐이다.**
1. `LoginResponse` 에 **서버 지문 필드 1개** 추가 (메인PC 에서 로그인했을 때만 채움)
2. 브라우저가 그 값을 저장하고 **다음 로그인에 되보낸다**

⚠️ **왜 이것이 하드웨어 값을 내려주는 것과 다른가** — 서버 지문은 **그 서버가 도는 PC 에서 로그인해야만** 받는다.
남의 PC 브라우저는 이 값을 받을 경로가 없다. 하드웨어 값을 API 로 조회하게 만들면 **아무나 물어볼 수 있다.**

⚠️ **loopback 판정은 여기에 쓰지 않는다.** 2026-08-10 에 *"고객사에서는 항상 참"* 임이 드러나 걷어낸 축이다
(터널이 고객 PC 안에서 localhost 를 다시 부른다 — `DeviceAuthMiddleware.cs:152-160` 주석이 그 경위를 남기고 있다).
loopback 은 **자료관리 화면 잠금**(8/11 사장님 지시)에만 쓴다.

| **G-1a** | 격리DB + 실서비스 | `device_id` 고정 · **지문을 매회 바꿔** 100회 → `COUNT(*)==1` | 미구현 |
| **G-1b** | 〃 | `device_id` 없음 · 지문 고정 100회 → `COUNT(*)==1` | 미구현 |
| **G-4** | + `MainPcRegistrationService` | 메인PC 자기등록 후 브라우저 3종 접속 → `COUNT(*)==1` | 🔴 FAIL 예상 |
| **G-9** | 격리DB | 옛 지문 기기 재접속 → 번호 승격, **새 줄 0** | 미구현 |
| **G-31** | 실제 `verify-key` | 기기 B 가 A 의 키 입력 → **A 의 번호 반환되면 FAIL** | 🔴 **FAIL** |
| **G-32** | 실제 미들웨어 | `is_main_pc=0` 행의 `device_id` 헤더 → **통과하면 FAIL** | 🔴 **FAIL** |
| **G-13b** | 종류 승격 | `mobile→pc` 승격 시 `pcUsed <= pcLimit` | 🔴 **FAIL** |

🔴 **G-1a 와 G-1b 를 나눈 이유** — 사장님 원문 *"100번을 접속해도 한번만"* 은 **두 방향**이다.
번호는 같은데 지문이 흔들리는 경우(브라우저 갱신)와, 번호가 없어 지문으로 찾는 경우(옛 기기).
**하나만 시험하면 나머지 방향으로 샌다.**

##### ⑤ ⚠️ 게이트로 만들 수 없는 것 — 약속하지 않는다

**origin 격리 시험은 서버측 게이트로 불가능하다.** localStorage 가 origin 별로 갈리는 것은
**브라우저 동작**이라 xUnit 에서 재현할 수단이 없다.
⇒ **Playwright 실측 시나리오로 분류한다.** 🔴 **게이트로 약속하면 못 지킨다** —
못 지킬 약속을 문서에 적는 것이 거짓 완료의 시작이다.

### §5-A-3. 청구 대조 — 사람이 확인할 수 있어야 한다

🔴 **고객이 "왜 이만큼 나왔나"를 물으면 답할 수 있어야 한다.**

- 등록기기 화면에 **어느 기기가 몇 슬롯을 쓰는지** 그대로 보인다 (현행 `DeviceManagePage` 확장)
- 슬롯이 늘어난 **시점과 이유**가 기록에 남는다 (`device_login_logs` 활용 검토)
- 헌법 #24 — 가르치지 않고 넘기는 것은 거짓말이다. **고객이 자기 청구를 검증할 수 있어야 한다**

⚠️ [[feedback_semi_auto_principle]] — *"히트판에 100% 자동화는 없다. 무조건 반자동."*
슬롯 계산은 자동으로 하되 **본사가 조정할 수 있어야 하고, 조정 이력이 남아야 한다.**

## §14. 🔴 제어의 중심 — 로그인과 업무 화면 사이의 한 화면

> 사장님 (2026-08-15): *"**로그인과 히트판ERP 사이에 화면을 넣고 그 화면으로 제어**를 하는게 가장 자연스러울듯"*

> *"중간 화면에서 **인증키 등록을 하는 장치**가 되는거지"*

### §14-1. 왜 화면 하나로 모으나

지금 기기 판정이 **세 군데로 흩어져 있다.**

| 자리 | 무엇을 하나 | 문제 |
|---|---|---|
| `AuthController.cs:101-105` | 로그인에서 **401** | 🔴 토큰을 못 받아 **아무 화면도 못 뜬다** |
| `DeviceAuthMiddleware.cs:98-124` | API 마다 **403** | 화면이 뜨려면 먼저 403 을 맞아야 한다 |
| `MainLayout.razor:52` | 인증 화면 | **업무 레이아웃 안**이라 "들어왔는데 왜 또 막나" |

셋이 각자 판단하니 흐름이 안 맞는다. **한 곳으로 모은다.**

### §14-2. 흐름

```
[로그인]  ← 401 을 내지 않는다. 정상으로 끝난다
   ↓
[기기 확인 화면]  ← 🔴 제어는 여기서만
   │
   ├ 승인됨 + 인증키 보유    → 그냥 지나간다 (다시 안 뜬다)
   │
   ├ 미승인                  → "미승인기기입니다. 승인요청 하시겠습니까?"  Y / N
   │     ├ N → 요청 안 함. 이 화면에 머문다
   │     └ Y → 메인PC(대표)에게 승인 요청 알림 (§14-4)
   │
   ├ 요청함 · 대기 중        → "관리자 승인을 기다리는 중입니다"
   │                            승인 알림이 오면 자동 전환
   │
   ├ 🔴 승인됨 · 인증키 없음 → **여기서 번호를 입력받아 저장한다** (§14-3)
   │
   └ 거부됨                  → "관리자가 등록기기 승인을 거부하였습니다.
                                관리자에게 문의하세요"
                                → 🔴 **영구 거부 아님. 다시 처음으로 돌아간다**
   ↓
[히트판 업무 화면]
```

**대표 쪽 분기** (승인 요청을 받았을 때)
```

                    │

                  → N → 클라이언트에 거부 안내 (위 흐름의 마지막 갈래)
```

### §14-3. 🔴 이 화면이 인증키를 등록하는 장치다

대표가 수락하면 번호가 나온다. **그 번호를 이 화면에서 바로 넣는다.** 별도 화면으로 빠지지 않는다.
입력하면 장비넘버·인증키가 기기에 저장되고 통과한다.

⇒ **이 화면이 장비넘버가 기기에 심어지는 유일한 자리다.**
다음 접속부터는 `device_id AND auth_key_hash` 로 조회되고, 승인은 영구이므로(§15) **이 화면을 다시 볼 일이 없다.**

🔴 **번호는 사람이 옮겨 적는다.** 대표가 읽고 → 직원에게 알려주고 → 직원이 입력한다.
알림에 번호를 실어 보내면 편하지만 **옆에서 화면을 보면 그대로 새어나간다.**
사장님: *"자동화보단 물리적으로 수동으로."* **편의보다 확실함을 택한다.**

## §15. 승인은 영구다

> 사장님: *"승인된 기기는 **영구(메인에서 슬롯삭제 하기 전까지)**적으로 쓸수 있게"*

**실측 — 현행이 이미 영구다.**

| 항목 | 실측 |
|---|---|
| 인증키 만료 | **없음** |
| 승인 상태 만료 | **없음** |
| `last_seen_at` 기반 자동 정리 | **없음** |
| 자동 폐기 스케줄러 | **없음** |
| 10분 만료가 걸린 것 | **QR 등록 토큰만** — 등록용 일회용 코드라 맞다 |

⚠️ **다만 지금은 "우연히" 영구다.** 만료 코드가 없어서 그런 것이지 지켜지고 있는 것이 아니다.
누가 나중에 *"오래 안 쓴 기기는 정리하자"* 를 넣으면 **조용히 깨진다.** 슬롯이 줄어 요금 정산에도 걸린다.

🔴 **설계 확정**:
> **승인은 영구다. 만료 · 자동정리 · 재인증 요구를 두지 않는다.**
> 승인이 풀리는 유일한 길은 **대표의 명시적 폐기**뿐이다.

게이트 — **G-18**(§16). 승인 후 시간이 지나도 유효한가 · 오래 안 쓴 기기가 자동으로 사라지지 않는가.

## §17. [3-V] 병렬검증 P0 반영

### §17-1. 🔴 열쇠는 AND 다 (PI-08)

1차 초안이 1순위 열쇠를 *"장비넘버 + 인증키"* 라고만 쓰고 **AND 인지 OR 인지 정하지 않았다.**
§3 서문에 *"정하지 않으면 구현자가 임의로 고른다"* 고 스스로 경고해 놓고 같은 실수를 했다.

```sql
WHERE tenant_id = (JWT 클레임)
  AND device_id = @Id
  AND auth_key_hash = @Hash
  AND status = 'approved'
```

🔴 **인증키만으로는 찾지 못하게 한다.** OR 로 읽으면 인증키를 옮겨 적은 기기가 남의 줄에 붙어 **요금이 샌다.**
그리고 인증키 공유는 **대표가 번호를 알려주는 구조상 자연스러운 행동**이라 실제로 일어난다.

⇒ `VerifyAuthKeyAsync:479` · `DeviceAuthMiddleware:107` 도 같이 고친다 —
지금은 `auth_key_hash` 만 보고 `device_id` 를 안 본다. **문 여는 것도 "이 기기의 열쇠인가"를 물어야 한다.**

---

#### 🔴 §17-1-A. 【정정】 왜 이 절이 5개월간 구현되지 않았나 (2026-08-18 설계팀장 자백)

> **근거** 봉합안 §0 수확1 · §2 의제1. **이 절은 지우지 않고 정정으로 남긴다** —
> 틀린 이유를 지우면 다음 사람이 같은 자리에서 같은 실수를 한다.

##### ① 실측 — 위 §17-1 은 한 글자도 구현되지 않았다

| 설계가 지목한 자리 | 2026-08-18 실측 |
|---|---|
| `VerifyAuthKeyAsync` | 🔴 **`auth_key_hash` 단독.** `src/HitPan.Infrastructure/Services/TenantDeviceService.cs:589-607` — `WHERE tenant_id AND auth_key_hash AND status='approved'`. **`device_id` 절이 없다** |
| `DeviceAuthMiddleware` | 🔴 **AND 가 아니라 3중 OR.** `src/HitPan.API/Middleware/DeviceAuthMiddleware.cs:109-172` — ①authKey 단독 → ②실패 시 deviceId 단독 → ③그래도 실패 시 `account_type=="tenant_admin"` 이면 **무조건 통과** |
| 1순위 열쇠 "장비넘버 + 인증키" | 🔴 **`device_id` 단독.** `TenantDeviceService.cs:209-219` — 인증키 절 없음 |
| `LoginRequest.AuthKey` | 🔴 **필드 자체가 없다** (`LoginRequest.cs` — `DeviceId`:45 만 있음) |

⚠️ **③ `tenant_admin` 갈래는 PR#169(대표 자기 화면 잠김 봉합)가 만든 것이다.**
막다른 길 하나를 닫으면서 **AND 원칙을 정면으로 어겼는데, 그 사실이 어느 문서에도 없었다.**
🔴 봉합이 새 구멍을 뚫었을 때 **그것을 적는 자리**가 우리 절차에 없다는 뜻이다.

##### ② 🔴 진짜 이유 — 태만이 아니라 **논리적 순환**(닭과 달걀)

1차 설계(위 §17-1)는 AND 를 이렇게 적었다:

```sql
WHERE device_id = @Id AND auth_key_hash = @Hash    ← 둘 다 "보내라"
```

**그런데 인증키를 넣으러 온 브라우저는 아직 `device_id` 가 없다.** 번호를 **받으러** 온 것이다.

```
설계: "device_id 와 키를 둘 다 보내라"
현실:  키를 넣는 그 순간이 device_id 를 처음 받는 순간이다
       ⇒ 보낼 수 있으면 넣을 필요가 없고, 넣어야 하면 보낼 게 없다   ← 닭과 달걀
```

🔴 **구현자는 이 SQL 을 쓸 수 없었다.** 쓰면 아무도 인증을 통과하지 못한다.
그래서 옛 SQL 이 그대로 남았고, **"AND 로 고쳤다"는 보고만 문서에 남았다.**
⚠️ **설계서가 만든 순환이다. 구현팀 태만이 아니다.**

##### ③ 🟢 해법 — 키는 **판정만** 하고, **무엇을 열지는 결정하지 않는다**

```
지금 (틀림):  키를 준다 → 그 키를 가진 줄을 찾아 준다
              ⇒ 키를 검색 열쇠로 쓰고 있다. 남의 키를 넣으면 남의 줄이 열린다

바꿈 (맞음):  ① 서버가 이 세션이 신청한 줄을 먼저 잡는다   ← 클라이언트가 못 고른다
              ② 그 줄에 저장된 키와 대조한다               ← 키는 맞나/틀리나만 답한다
              ③ 맞으면 그 줄만 연다
              ⇒ 남의 줄에 닿을 길이 구조적으로 없다
```

🔴 **번호를 클라이언트가 보내지 않는다. 서버가 세션에서 정한다.** 순환이 사라진다.
남의 키를 넣어도 **자기 줄에서 대조되어 "틀림"으로 끝난다** — 남의 줄이 열리지 않는다.

| 무엇이 | 어디서 정하나 | 왜 |
|---|---|---|
| **어느 줄을 여나** | 🔴 **서버** (JWT 테넌트 + 이 세션의 신청 이력) | 클라이언트가 고르게 두면 남의 줄을 고른다 |
| **그 키가 맞나** | 저장된 해시와 대조 | 판정만 한다. 검색하지 않는다 |
| **번호(`device_id`)** | 🔴 **서버가 발급해 내려준다** | 들고 오라고 하면 닭과 달걀 |

⚠️ **키 소멸(1회용화)만으로는 못 닫힌다** — 개발팀 지적을 수용한다.
소멸은 **두 번째 사람**만 막는다. **첫 번째 사람이 남의 `device_id` 를 받아오는 경로**는 그대로 열려 있다.
⇒ 🔴 **1회용화와 "줄을 서버가 정한다"는 둘 다 해야 닫힌다.** 하나만 하면 초록불만 켜진다.

##### ④ AND 를 거는 자리는 **둘로 갈린다** — 같은 규칙을 두 곳에 쓰면 또 막힌다

| 자리 | 브라우저가 `device_id` 를 갖고 있나 | 규칙 |
|---|---|---|
| **인증키 입력**(`VerifyAuthKeyAsync`) | ❌ **없다** (지금 받으러 왔다) | 🔴 **서버가 줄을 정하고 키를 대조.** AND SQL 을 쓰지 않는다 |
| **평상시 문 통과**(`DeviceAuthMiddleware`) | ✅ **있다** (인증 때 받아 저장했다) | 🔴 **`device_id` AND `auth_key_hash` 진짜 AND** |

🔴 **1차 설계는 이 둘을 하나로 봤다.** 그래서 "AND 로 고쳐라"가 앞 자리에서 성립하지 않았다.

⚠️ **미들웨어 ③ `tenant_admin` 무조건 통과 갈래는 지워야 하지만, 지우기 전에 답해야 한다** —
*"대표가 막히면 누가 풀어주나?"* (그 갈래가 답한 질문이다).
⇒ 봉합안 1-3 대로 **경로 화이트리스트로 좁힌다** (`/api/devices` · `/api/auth` 만).
**전 API 통과를 없애되 막다른 길은 다시 만들지 않는다.**

##### ⑤ 게이트 — 이것이 통과하지 않으면 "AND 로 고쳤다"고 말하지 않는다

### §19-3. 🔴 `rejected` 를 `revoked` 에서 분리한다

**실측 — 지금은 반려가 폐기와 같은 칸에 들어간다.**

| 뜻 | 상태 | 다음에 무엇이 되나 |
|---|---|---|
| **"이번엔 아니다"**(반려) | 🆕 **`rejected`** | 🔴 **직원이 [확인] → 미등록으로 회귀 → 다시 신청 가능** |

🔴 **왜 결함인가** — 같은 칸에 넣으면 화면이 둘을 구분할 수 없다.

⚠️ **재신청을 막지 않는다** — 사장님 판정 §18: *"고객사 실수로 생기는 일로, 오히려 반복요청 막을시 그게 더 불편"*.

⚠️ **`rejected` 는 계수하지 않는다**(S-3). 반려가 슬롯을 물면 대표가 거부할수록 요금이 오른다.

### §19-4. 전이 ② — 대표 알림이 없으면 이 기계가 멈춘다

**실측**: `TenantDeviceService` 생성자(`:83-95` 부근)에 `INotificationService` 주입이 없고,
`role='tenant_admin'` 조회도 pending INSERT 직후 알림 호출도 **0곳**이다.

§14-4 가 *"새로 만들 것은 둘뿐"* 이라 적은 그 둘이 아직 없다.

🔴 **알림은 3중으로 건다**(봉합안 1-6) — 실시간(SignalR) + **로그인 시 배지** + 3일 후 재알림.
실시간 하나만 두면 **대표가 그때 로그인해 있지 않으면 영영 못 본다.**

⚠️ **알림에 인증번호·인증키를 싣지 않는다** (§14-3 · §18 유지 — 옆에서 화면을 보면 새어나간다).

### §20-1. 결재 1 — 🔴 결제는 **관문이 아니라 판단 재료**다

팀은 *"수동 인증 = 결제 확인"* 으로 **추론**했다. 🔴 **그 추론은 폐기한다.**

```
                              (그 화면에 결제 상태가 보인다) ← 결제는 사람이 보는 정보
```

| | 팀 안 (폐기) | 🔴 사장님 확정 |

🔴 **왜 사장님 안이 옳은가** — 결제를 관문으로 만들면 **대리점이 먼저 열어주고 나중에 정산**하는 실제 영업 흐름이 막힌다.
그리고 결제 확인이 자동이면 **결제 시스템이 흔들릴 때 슬롯도 같이 멈춘다.** 사람이 보고 판단하면 안 멈춘다.

⚠️ **전제조건이 붙는다** — 결제 전에 승인하면 **다음 웹훅에 값이 덮여 사라질 수 있다**(절대값 덮어쓰기).

| **저장** | 🔴 **`tablet` 으로 갈라 둔다** (팀 안 유지 — 결재와 상충 0) |

**왜 칸을 안 늘리나** — 사장님 확정 가격표가 이미 2칸이다(*"추가슬롯 1만원 / PC 1 + 모바일 1"*).
칸을 늘리면 **가격표가 깨진다.** 그리고 현장에서는 폰 자리가 남는데 태블릿 자리가 없어 못 쓰는 일이 생긴다 —
**칸을 나눌수록 고객이 손해다.**

**왜 저장은 가르나** — 지금은 저장까지 `mobile` 로 뭉갠다. 나중에 사장님이 *"태블릿은 따로 받자"* 하시면
**과거 자료가 없어 갈 수가 없다.** ⇒ **저장은 세밀하게, 과금은 단순하게.**

✅ **계수는 이미 맞다** — `MobileUsedFrom` 이 `tablet` 을 휴대기기 칸에 합산한다(G-13 통과 확인).

## 🔴 §21. 설계 규칙 신설 — 이 문서 자신에게 거는 규칙 (2026-08-18)

> **근거** 봉합안 §0 수확2. 🔴 **설계서가 실패하게 되어 있던 구조를 고친다.**

### §21-1. 🔴 규칙 1 — **값을 읽는 조항과 그 값을 처음 만드는 조항은 한 항목으로 묶어 적는다**

**나눠 적으면 읽는 쪽만 구현되고 게이트는 초록이 된다.** `hardware_id` 가 정확히 그렇게 죽었다(§4-45-1).

| 갈라 적으면 | 왜 반쪽만 되나 |
|---|---|
| §4-4 (읽는다 · 쉬움) | 먼저 한다. **값이 비어도 오류가 안 난다** |
| §4-5 (만든다 · 어려움) | 나중으로 밀린다. **안 해도 아무 불이 안 켜진다** |

🔴 **한 항목으로 묶으면 "반쯤 했다"가 존재할 수 없다.** 만드는 쪽 없이 읽는 쪽만 내면 항목이 안 닫힌다.

### §21-2. 규칙 2 — 조항에 **무게를 매긴다**

봉합안 §0: *"726줄에 §4-3·§4-4·§4-5·§14·§17 이 **전부 같은 무게**로 적혀 있어
구현자가 **쉬운 것부터** 했고 **어려운 것만 정확히 빠졌다.**"*

⇒ 🔴 **모든 절은 P0/P1/P2 와 "이것 없이 다른 것을 해도 되나"를 명시한다.**
평평하게 적으면 구현 순서를 구현자가 정하고, 사람은 쉬운 것부터 한다.

### §21-3. 규칙 3 — **봉합이 새 구멍을 뚫으면 그 사실을 설계서에 되올린다**

PR#169(대표 잠김 봉합)가 미들웨어를 **3중 OR** 로 만들어 §17-1(AND)을 정면으로 어겼는데,
**어느 문서에도 그 기록이 없었다**(§17-1-A ①).
⇒ 🔴 **원칙을 어기며 봉합했으면 어긴 절에 한 줄을 남긴다.** 남기지 않으면 다음 사람이 그것을 정상으로 읽는다.

### §21-4. 규칙 4 — **자기 반증을 흡수하지 않은 절은 "반영 완료"라 적지 않는다**

§17 제목이 *"[3-V] 병렬검증 P0 반영"* 인데, 그 P0(PI-08)를 **반증한 PI-15 가 흡수되지 않은 채**
결재선을 통과했다. ⇒ 🔴 **반증 문서가 열려 있으면 그 절은 "반영"이 아니라 "반영 중"이다.**

## ⏸ §22. 추가슬롯 — **후행** (2026-08-18 신설 · 상세는 후속 설계서)

> 🔴 **사장님 순서 정정 (2026-08-18)**:
> **"추가슬롯 구현보다 먼저 선행되야 할 것은, 아직 봉합되지 않은 기기슬롯 승인추가임"**

### §22-1. 🔴 이 절은 자리만 잡는다. 착수하지 않는다

```
기기 접속 → 승인 요청 → 대표 승인 → 슬롯 +1 → (슬롯이 차면) → 추가슬롯 구매
             ↑                                                    ↑
        🔴 지금 여기가 끊겨 있다                          이 절이 다루는 자리
```

⇒ 🔴 **승인이 안 되면 슬롯이 늘지 않고, 슬롯이 늘지 않으면 "부족"에 도달하지 않는다.**
**아무도 안 가는 길을 먼저 포장하지 않는다.**

그리고 **사장님 실측 3증상(2026-08-16)이 하나도 안 닫혔는데 전부 §19·§20-2 영역이다.**
추가슬롯은 **증상 목록에 없다** — 고객이 지금 겪는 것이 아니다.

### §22-2. 후행 조건

| 조건 | 판정 기준 |
|---|---|
| §19 상태 기계 + §17-1-A AND | [4] 검증 통과 |
| 🔴 **사장님 실측으로 증상 ②③ 닫힘** | 백지 환경 실측 (개발PC 정상은 검증이 아니다) |

⇒ 위 둘이 확인된 **뒤에** 후속 설계서를 발행한다.

### §22-3. 후속 설계서가 다룰 것 (목록만 · 상세 금지)

| 항목 | 상태 |
|---|---|
| ① ERP 부모계정 요청 → ② 백오피스 승인 → ③ 슬롯 반영 (사장님 3단 설계) | ①② 미구현 |
| 🔴 결재 1 반영 — 승인 화면에 **결제 상태 표시** (관문 아님, §20-1) | 신설 |
| 🔴 **3-1 nonce 이력 + 순번 역행 차단** — 결재 1 의 전제조건 | **의제3 착수일의 첫 작업** |
| Push vs Pull — ERP 는 백오피스 URL 을 알지 않는다 (헌법 #35 · #30) | Pull 채택 |
| 별건 P0 — 웹훅 `iat` 고정(재시도 21분 후 영구 401) | 슬롯 밖 **모든 웹훅**에 걸린다 |

### §22-4. 헌법 정합 — 무엇을 보내고 무엇을 안 보내나

**#18 은 "업무 데이터 전송 금지"지 "아무것도 보내지 마라"가 아니다.** 구독·과금은 백오피스 소관(#35).

| 보낸다 (4개뿐) | 절대 안 보낸다 |
|---|---|
| 라이선스 키(대조용, **저장 금지**) | 기기 이름 · 지문 · 장비넘버 |
| 현재 쓰는 자리 수 | 직원 이름 · 계정 |
| 요청 수량 | 거래처 · 상품 · 금액 |
| 요청 시각 | DB 내용 일체 |

🔴 **기기 목록은 백오피스 화면에도 안 띄운다**(#22). 담당자가 궁금해도 안 준다.
🔴 **요청 사유는 자유 텍스트 금지, 고정 선택지** — 자유 입력이면 고객이 업무 내용을 쓴다.
**#18 위반이 사용자 손으로 일어난다.**

### §22-5. ⚠️ [[project_fixed_vs_delivered_gap]] 5차 방지

> **백오피스 화면에 "승인함"이 떠도 고객 PC 는 3자리 그대로일 수 있다.**
> 담당자는 끝났다고 믿고 고객은 안 늘었다고 전화한다. **양쪽 다 자기가 맞다고 믿는 상태가 최악이다.**

⇒ 🔴 **게이트는 "승인했나"가 아니라 "고객 PC 숫자가 바뀌었나"를 본다** — 보내는 쪽이 아니라 **받는 쪽.**
