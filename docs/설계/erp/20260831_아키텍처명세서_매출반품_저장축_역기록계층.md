## 4. 🔴 결정적 제약 — 원장 두 계층이 음수를 안 받는다

이것이 아키텍처 판정의 **단일 최대 근거**다.

### 4-1. `journal_lines` — DB 가 음수를 물리적으로 거부

```sql
-- hitpan_db_clean.sql:1916
CONSTRAINT `chk_jl_debit_or_credit` CHECK (
  `debit_amount` > 0 AND `credit_amount` = 0
  OR `debit_amount` = 0 AND `credit_amount` > 0)
```
> 테이블 주석: *"복식부기 분개 라인 — INSERT ONLY, CHECK로 차변·대변 배타"*

**복식부기에서 반품은 음수가 아니라 「차·대 반대편 양수」(역분개)로 표현한다.**

### 4-2. `stock_ledger` — 부호 대신 두 칸으로 방향 표현

```sql
-- hitpan_db_clean.sql:3625
`qty_in`  decimal(15,3) NOT NULL,
`qty_out` decimal(15,3) NOT NULL,
UNIQUE KEY `uq_stock_ledger_source` (tenant_id, source_type, source_id, item_id, move_type)
```
잔고 = `SUM(qty_in) − SUM(qty_out)`. **음수 컬럼이 없다.**

### 4-3. 그래서 확정 단계에 이미 방어벽이 서 있다

```csharp
// SalesService.cs:400 — 20260828작14 이전부터 존재
// 합계 0원 판매는 확정 금지 — journal_lines CHECK 제약 위반 방지(§20 워크플로우 오염 차단)
if (delivery.TotalAmount + delivery.VatAmount <= 0m)
    throw new InvalidOperationException("합계가 0원인 거래명세서는 확정할 수 없습니다.");
```

🔴 **음수 명세서는 저장돼도 「확정」이 안 된다. 확정이 안 되면 재고도 원장도 안 움직인다.**
⇒ **B안은 반품으로서 아무 일도 못 한다.** 이 가드를 걷어내면 확정 순간 **DB 가 거부**한다.

> **B안의 실제 크기**: `[Range]` 하나 푸는 일이 아니라 **복식부기 분개 구조를 바꾸는 일**이다.

## 6. 현장·세무·레거시 축 검증

### 6-1. 세무 — 설계서(0828) §3-1 주장은 **절반만 사실**

🟢 사실: 이세로에 「수정」 개념이 없고 **수정세금계산서를 새로 발행해 상계**한다.
🔴 **정정**: 법정 명칭은 「마이너스 전표」가 아니라 **「수정세금계산서」**이고 **수정사유 코드**가 붙는다
(부가가치세법 시행령 §70).

| 수정사유 | 코드 | 작성일자 | 결과 |
|---|---|---|---|
| **환입(반품)** | **1** | **반품한 날** | 반품한 달 매출에서 차감 |
| 계약 해제 | 2 | 해제일 | — |
| 착오정정 | 6 | **원 계산서 날짜** | 🔴 과거 기수 **수정신고 + 가산세** |

⇒ 4월 매출을 5월에 반품하면 **5월에 (−)로** 잡아야 한다.
🔴 **B안이 "원전표에 붙는" 인상을 주면 이 구분이 흐려진다.**
현행 `TaxInvoiceService.cs:359` 는 `BusinessDate.Today` 로 채번해 **이미 반품일 기준으로 맞게 짜여 있다**(다만 §1-1 때문에 불리지 않는다).

### 6-2. 매입매출장 — 매출만 행이 없다

```
4/10  매출     명-20260410-001   삼성전자   10,000,000  1,000,000
5/03  매출반품 반-20260503-001   삼성전자   -2,000,000   -200,000   ← 별도 행·별도 번호
```
매입은 이미 이 모양이다 — `FinanceService.cs:143~157` 이 `'매입반품'` 을 별도 DocType 으로 UNION.
🔴 **매출만 이 행이 없다.** 세무사가 *"반품 건만 뽑아 주세요"* 할 때 **매출은 못 뽑는다.**

### 6-3. 창고 — B안이면 **불량반품이 사라진다**

`sales_returns.return_reason`(`customer_return`/`defect`/`exchange`) · `sales_return_items.is_loss`(DB-108).
🔴 **불량 반품은 재고에 안 넣고 폐기한다.** 거래명세서에는 그 칸이 **없다** ⇒ 음수 명세서로는 표현 불가.

### 6-4. 세금계산서 코드는 **이미 A안을 전제**한다

```csharp
// TaxInvoiceService.cs:383
// 🔴 음수로 뒤집는다. sales_returns 금액은 양수로 저장돼 있다.
var negAmount = -Math.Abs(ret.TotalAmount);
```
- `:299` — `FROM sales_returns WHERE return_id = @ReturnId` (독립 행 전제)
- `:311` — `"확정된 반품만 마이너스 계산서를 발행할 수 있습니다"` (**반품 자신의 상태** 전제)

🔴 이는 0828 설계서 §1-3 ③ *"별도 상태 안 만듦"* 과 **정면충돌**한다.
⇒ B안 채택 시 **이미 동작하는 마이너스 계산서 코드를 버리고 다시 짜야 한다.**

### 6-5. 레거시 — 🔴 내가 앞서 보고한 것이 틀렸다

**종전 보고**: *"레거시는 음수 방식 ⇒ B안이 자연스럽다"* — **추정이었고 실측하니 반대였다.**

```
docs/mdb-mapping-spec.md:99   IJ_IO = 'I' 입고 / 'O' 출고
```
DOCFB 18컬럼에 `IJ_GUSU`·`IJ_GU` 는 **없다**(`docs/mdb-schema-dump.md:266~284`).
`docs/개발/erp/W2_RETURNS_DESIGN.md:96` 이 `IJ_GUSU` 를 전제로 변환 룰을 짰는데 **그 컬럼은 실재하지 않는다** ⇒ 별건 정정 대상.

⇒ **레거시는 부호가 아니라 방향 코드(I/O)로 구분했고 수량 `IJ_QTY` 는 양수다.**
**그것이 A안 방식이다.** 20년 쓴 경리 손에 밴 것은 *"반품은 별도 전표 · 수량은 양수"* 다.

### 7-4. 목록 표기 — `명-001R` 이 아니라 `반-…`

```
명-20260410-001    10,000,000
 └ 반-20260503-001  -2,000,000   ← 원전표 아래 배치 · 표시상 (−)
```
근거: ①세무사·거래처가 보는 문서라 **종류가 이름에 보여야** 한다 ②매입이 이미 `매반-` 이라 **대칭**
③사장님 의도(*"원전표 바로 아래 = 대사 화면"*)는 `delivery_id` 조인으로 **그대로 달성**된다.
