## 0. ⭐ 사장님 오더 (Q5 확정)

> PM 물음: *"직책에 재직자가 여럿일 때 누구를 결재자로 하나요? (예: 부장이 2명일 때)"*
>
> ## 사장님: **"권한설정 한 자"**

### 0-1. 🟢 PM 권고를 물리셨고, 사장님이 맞다

| PM 권고(폐기) | 사장님 확정 |
|---|---|
| 직급 높은 순 → 입사일 순 | 🟢 **권한 설정한 자** |

**왜 사장님 안이 맞나**:
- PM 안은 결국 **시스템이 사람을 고르는 것** ⇒ 헌법 #11(권한은 어드민이 직접) 위반 소지
- 부장이 2명이면 **회사마다 답이 다르다** — 우리가 정할 수 없다
- 🟢 **이미 있는 축(권한)을 쓴다** — 새 개념을 안 만든다

> 상무님: *"맞다. 삼성에서도 **결재권은 직급이 아니라 발령**이었다.
> 같은 부장이어도 **결재권을 받은 사람**과 아닌 사람이 있다.
> 직급으로 자동 판정하면 **발령이라는 개념이 사라진다.**"*

## 1. 🔴 실측 — 착수 전에 확인한 것

### 1-1. 🟢 `APPROVAL` 권한이 이미 있다 (신규 0)

```
PermissionService.cs:35        ("APPROVAL", "결재")
PermissionPage.razor.cs:54     ("APPROVAL", "결재")
PermissionPage.razor.cs:86     EnforcedMenus 에 포함  ← 🟢 화면에 이미 뜬다
```

⇒ 🟢 **새 권한 항목을 만들지 않는다.** *"권한 설정한 자"* = **`APPROVAL` 권한 보유자**.
⇒ 🟢 **`EnforcedMenus` 등록도 이미 돼 있다** — 1.2.74 P0 위험 **없음**.

### 1-2. 🔴🔴 그런데 직책과 사원이 FK 로 안 이어져 있다

```
positions             position_id · code · name · sort_order
employees             position  varchar(30)   ← 🔴 이름 문자열이다
```

- `employees` 에 **`position_id` 컬럼이 없다**(실측: 0건)
- 실제 값 = **`"대표이사"`** (T-004 실측) — **이름이 그대로 들어 있다**

🔴 **`approval_line_steps.position_id` 로 직책을 걸어도, 그 직책의 사람을 찾을 길이
   이름 문자열 대조뿐이다.** 이름을 고치면 연결이 끊긴다.

### 1-3. 🔴 결재 엔진은 `approval_line_steps` 를 안 읽는다

| 축 | 표 | 누가 읽나 |
|---|---|---|
| 엔진 축 | `approval_doc_lines` | `ApprovalTriggerHelper:37`·`:115` · `ApprovalService` |
| 직책 축 | `approval_line_steps` | `ApprovalLineService` · `PositionService` **뿐** |

⇒ 화면에서 직책으로 짜도 **실제 결재는 사람 고정 1행**으로 돈다.

## 2. 🟢 설계 — 사장님 확정을 어떻게 담나

### 2-1. 결재자 결정 규칙 (사장님 *"권한설정 한 자"*)

```
approval_line_steps 한 단계를 펼칠 때

 ├ employee_id 가 있으면   → 그 사람 그대로              (사람으로 건 경우)
 └ position_id 가 있으면   → 그 직책 재직자 중
                              🟢 APPROVAL 권한 보유자를 결재자로
```

| 그 직책에 권한자가 | 어떻게 |
|---|---|
| **1명** | 🟢 그 사람이 결재자 |
| **여럿** | 🟢 **전원을 그 단계에 넣는다**(§2-2) |
| **0명** | 🔴 **막는다 · 사람에게 알린다**(§2-3) |

### 2-2. 🔴 여럿이면 — 병렬인가 순차인가

**권고: 병렬(누구든 한 명이 결재하면 그 단계 통과).**

> 상무님: *"부장이 둘인데 **둘 다 결재해야** 넘어가면, 한 명이 휴가만 가도 선다.
> 실무에서 같은 직급 둘은 **누구든 한 명**이 처리한다. 그게 **결재권을 나눠준 이유**다."*

⇒ ⚠️ **다만 이건 상무 권고이지 사장님 확정이 아니다** — **§6 Q5-1**.

### 2-3. 🔴 권한자가 0명일 때 — 조용히 실패하면 안 된다

가장 위험한 자리다. 직책은 걸어놨는데 **그 직책에 `APPROVAL` 권한자가 없으면**:

```
❌ 나쁜 동작   상신이 조용히 실패 / 결재선 0줄로 통과
🟢 옳은 동작   상신을 막고 사람에게 알린다
              "○○ 직책에 결재 권한자가 없습니다. 권한설정에서 지정해 주세요."
              → 권한설정 화면으로 링크 (사장님 원칙 ③ — 새 화면 안 만든다)
```

🔴 **결재선 0줄로 통과시키면 결재를 켠 의미가 사라진다**(무통제 승인).

### 2-4. 🟢 무엇을 건드리나 — 표 신설 0

```
상신 (TryCreateApprovalAsync)
 └→ ① approval_line_steps 조회 (step_order 순)
 └→ ② 각 단계를 사람으로 펼침 (§2-1)
 └→ ③ approval_doc_lines 로 기록
 └→ ④ 기존 엔진이 그대로 돈다        ← 🟢 엔진 무변경
```

| | |
|---|---|
| 🟢 표 신설 | **0건** |
| 🟢 엔진 변경 | **0건** — 계속 `approval_doc_lines` 만 본다 |
| 🔴 새 코드 | 펼치는 로직 1개(`ApprovalTriggerHelper` 안) |

## 3. 🔴 미해결 — 직책·사원 FK 부재 (1-2)

`employees.position` 이 **이름 문자열**이라 직책으로 사람을 찾으려면 이름 대조뿐이다.

### 3-1. 세 가지 안

| 안 | 방법 | 평가 |
|---|---|---|
| **A** | `employees.position` 이름 ↔ `positions.name` **문자열 대조** | 🔴 이름 바꾸면 끊긴다 · 동명이 직책이면 오작동 |
| **B** | `employees` 에 **`position_id` 추가**(#1 추가만) + 마이그로 이름→ID 채움 | 🟢 **근본** · ⚠️ DDL 1건 |
| **C** | G1 은 **`employee_id` 로 건 경우만** 지원, 직책은 다음 차수 | 🟡 범위 축소 · **직책 축의 값어치를 못 씀** |

**PM·상무 권고 = B.**

> 상무님: *"A 는 **이름이 열쇠**가 되는 설계다. 인사에서 직책 이름은 자주 바뀐다 —
> '팀장' 이 '파트장' 이 되는 일이 실제로 있다. 그때마다 **결재선이 조용히 죽으면**
> 아무도 모른 채 결재가 안 간다. **B 가 맞다.**"*

⚠️ **B 는 DDL 이라 사장님 결재 사항** — **§6 Q5-2**.
