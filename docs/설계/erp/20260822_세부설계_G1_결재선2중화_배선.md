## 0. ⭐ 사장님 확정 (2026-08-22)

> **Q5** *"직책에 재직자가 여럿일 때 누구를 결재자로?"* → **"권한설정 한 자"**
>
> **축 정정** → *"결재라인에 그래서 **pk를 직책으로 두는것이 아니라 사원이름이나 계정으로** 두는게 맞지"*
>
> ## **최종 확정** → *"**대표이사 마지막 결재 외는 권한가진자가 하는걸로.**"*

### 0-1. 🟢 규칙 (이것이 전부다)

```
최종 결재 단계   =  대표이사        (고정)
그 외 모든 단계  =  APPROVAL 권한 가진 자
```

🔴 **직책(`position`)을 보지 않는다.**

### 0-2. 🔴 PM v1 안 폐기 기록 (반복 금지)

PM 이 v1 에서 **직책 축을 세우자**고 했다. 사장님이 두 번 물리셨고 **사장님이 맞다.**

| PM v1 (폐기) | 사장님 확정 |
|---|---|
| 결재선 PK 를 **직책**으로 | 🟢 **사람(사원·계정)으로** |
| `employees` 에 `position_id` **DDL 추가** | 🟢 **DDL 0건** |
| 이름→ID **마이그레이션** | 🟢 **0건** |
| 직책→사람 **펼치는 로직** | 🟢 **불필요** |
| 권한자 0명·여럿 **분기 처리** | 🟢 **불필요** |

**PM 이 무엇을 놓쳤나**:
1. `approval_doc_lines` 가 **이미 `approver_id`(사원)로 돌고 있었다** — 있는 축을 두고 새 축을 만들려 했다
2. 사장님 원칙 ②(**있는 걸 쓴다**)에 어긋났다
3. *"직책으로 걸면 사람이 바뀌어도 안 죽는다"* 는 곧 **자동 승계**인데,
   이는 **100% 자동화**라 히트판 반자동 원칙에 어긋난다

🟢 **사람이 바뀌는 문제는 사장님이 이미 푸셨다** —
   *"결재자가 00중입니다. 변경하시겠습니까?"* → **[Y] 결재설정으로 링크이동**
   ⇒ **시스템이 알려주고 사람이 바꾼다.** 이것이 반자동이다.

> 상무님: *"PM 이 교과서를 따라갔다. 대기업은 직책으로 건다 — **인사발령이 시스템에 들어오니까.**
> 히트판 고객사는 **발령 시스템이 없다.** 그러면 직책으로 걸어도 **그 직책에 누가 있는지를
> 결국 손으로 넣어야** 한다. **한 번 더 돌아가는 것뿐**이다."*

### 0-3. 🟢 그래서 직책관리 메뉴가 필요 없다 (사장님 확정)

> 사장님: *"그래서 **직책관리 메뉴가 굳이 필요 없눈거야**"*
> *"**사원관리나 계정관리에서 등록한 직원의 직책이 자동으로 올라가도 되고**"*

🟢 **실측 — 이미 그렇게 돌고 있다**: `EmployeeService.EnsurePositionExistsAsync`(`:275`)

```
사원 등록·수정 시 직책 이름을 넣으면
  → positions 에 있나 확인 (이름 대조)
  → 없으면 자동 등재
  → 쓰레기 값은 거른다  (주석 실측: "12명 중 8명 직급 없음 · 그중 '0' 이 1건")
```

**직책관리 메뉴가 필요했던 유일한 이유는 결재선이었다.** 결재선을 사람으로 짜기로 한 이상
그 이유가 사라졌고, 직책 등재는 **사원관리가 알아서 한다.**

🔴 **없애는 것은 메뉴뿐이다. 표(`positions`)는 살린다** — 다른 3곳이 쓴다(실측):

| 쓰는 곳 | 무엇 |
|---|---|
| `CompanyBootstrapProvisioner` | 신규 고객사 설치 시 **기본 직책 시드** |
| `EmployeeService` | **자동 등재**(위 로직) |
| `SerialIssueService` | 참조 |

⇒ 헌법 #37(*"안 읽힌다 ≠ 잔재"*) · 사장님 원칙 ②(**기능은 안 없어지고 녹아들어감**) 정합.
⇒ 🟢 **메뉴가 하나 더 준다** — 3번 사원관리가 직책을 흡수한다.

## 2. 🟢 설계 — 무엇을 하나

### 2-1. 결재선 구성

```
approval_doc_lines  (doc_type 단위)
  seq_no 1..N-1   →  APPROVAL 권한 가진 자   (고객사가 결재설정에서 지정)
  seq_no N (최종) →  대표이사 (is_parent=1)
```

### 2-2. 🔴 그래서 G1 이 하는 일은 **배선이 아니라 가드다**

v1 은 *"직책을 사람으로 펼친다"* 는 **배선 작업**이었다.
사장님 확정 후에는 **펼칠 것이 없다** — 이미 사람으로 돌고 있다.

⇒ 🔴 **G1 의 실제 내용이 바뀐다**:

| | 무엇 |
|---|---|
| ① | **최종 단계 = 대표이사** 를 보장한다 |
| ② | **그 외 단계는 `APPROVAL` 권한자만** 지정 가능하게 막는다 |
| ③ | 권한 없는 사람이 결재선에 있으면 **알린다** |

### 2-3. ① 최종 단계 = 대표이사

| 경우 | 어떻게 |
|---|---|
| 결재선 마지막이 **대표가 아님** | 🔴 결재설정에서 **경고**하거나 자동으로 대표를 마지막에 둔다 → **§6 Q1** |
| 대표가 **여럿** | `is_parent=1` 중 고객사가 **고른다**(#11) |
| 단계가 **1개뿐** | 그 하나가 곧 대표 |

### 2-4. ② 권한 없는 사람을 결재자로 못 넣게

🔴 **지금은 아무나 결재자로 지정할 수 있다**(결재설정 화면이 사원 목록에서 고름).
⇒ `APPROVAL` 권한 **없는** 사람을 넣으면 — 그 사람은 **결재함에 들어가지도 못한다**
   (`ApprovalController` 가 `[RequirePermission("APPROVAL","view")]`) ⇒ **결재가 영영 막힌다.**

⇒ 🟢 **결재설정에서 권한자만 고르게** 하거나, 고를 때 **경고**한다 → **§6 Q2**

### 2-5. ③ 권한이 나중에 꺼지면

결재선에 넣을 때는 권한이 있었는데 **나중에 관리자가 꺼버리면** 같은 일이 생긴다.
⇒ 🟢 **사장님이 이미 푸신 방식으로 알린다** —
   *"결재자가 권한이 없습니다. 변경하시겠습니까?"* → **[Y] 결재설정으로 링크이동**
   (오늘 확정한 공석 알림과 **같은 자리·같은 문구 틀**)
