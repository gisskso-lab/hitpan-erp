## §3 [핵심] 「[예] 한 번 = 시도 한 번」

**규칙 C (워치독 소비)** — 버전 V 에 대해:

```
latest  = local_update_consents 에서 V 의 최신 1건 (종전 정렬 그대로: consented_at DESC, id DESC)
used    = local_update_apply_status 에서 V 행의 consent_id (행 없음·NULL = 0)
latest.action = reject                  → 종전 Reject 분기 그대로 (적용 안 함 · 보고 · 펜딩 해제)
latest.action = approve, latest.id > used → 새 [예]: ① in_progress 행(consent_id=latest.id) 먼저 기록
                                              ② 기록 성공했을 때만 ApplyUpdateAsync
                                              ③ 기록 실패 → 적용 안 함 · 펜딩 유지(다음 루프)
latest.action = approve, latest.id ≤ used → 이미 쓴 [예]: 적용 안 함 · 펜딩 해제 · 보고 0 (「다시 물어야 함」)
없음 / 조회 실패                          → 종전 None / Error 그대로
```

- 인메모리 `_consentAppliedVersions`(`:102`) 는 **남기되 키를 버전 → 동의 id 로 바꾼다**(같은 수명 안 이중 안전장치 · #1 수정 허용). 버전 키를 그대로 두면 B-1 이 남는다.
- 왜 시각이 아니라 id 인가: `consented_at` 은 API 프로세스 시계(`DateTime.Now`), `applied_at` 은 DB `NOW(3)` — 두 시계를 비교하지 않는다. id 는 한 표 안의 순번이라 비교가 정확하다.
- NULL(옛 행) = 0: 새 워치독이 도는 시점엔 설치버전보다 높은 버전의 옛 행이 있을 수 없다(워치독 자기교체는 **성공 뒤**에만 — `UpdateOrchestrator.cs:996-1012`). 있더라도 결과는 종전과 같은 1회 재시도 = 무회귀.
- #43 대조: [예]=즉시 적용 · [나중에]=적용 안 함 **둘 다 그대로**. 바뀌는 것은 「실패한 [예]는 다 쓴 것」 하나 — 더 묻는 쪽이지 건너뛰는 쪽이 아니다(2차 §6 #43 행).
- 🔴 in_progress 를 **적용 전에** 쓰는 이유: 다운로드 실패·슬롯 실패·예외·전원 종료(B-8)도 「이 [예]는 썼다」가 남는다 ⇒ 재기동 뒤 무질문 재시도(B-3)가 원리적으로 사라진다.

## §4 [판정] ERP 「미완료」 판정식 (API · 읽기만)

입력: 설치버전 `I`(VersionInfo) · 최신 발견 `L`(`local_update_status` 최신) · `L` 의 최신 동의 `C` · `L` 의 결과행 `A`.
`I ≥ L` 이거나 `L` 없음 → **none**(종전 `UpdateAvailable=false` 그대로).

| 종류(kind) | 조건 | 팝업(메인PC) | 사이드바 |
|---|---|---|---|
| `first` | `C` 없음 | 종전 문구 「새 버전 … 업데이트하시겠습니까?」 | 「새 버전 {L} 있음」 |
| `later` | `C`=reject | **사장님 문구** | 「업데이트 미완료 · 나중에 선택」 |
| `requested` | `C`=approve · `C.id > A.consent_id` · 경과 < **T1** | 없음 | 「업데이트 준비 중」 |
| `not_started` | 위와 같고 경과 ≥ T1 | 사장님 문구 | 「업데이트가 시작되지 않았습니다」 |
| `in_progress` | `A.consent_id = C.id` · `A.result=in_progress` · 경과 < **T2** | 없음 | 「업데이트 진행 중」 |
| `interrupted` | 위와 같고 경과 ≥ T2 | 사장님 문구 | 「업데이트 중 중단됨」 |
| `failed` | `A.consent_id = C.id` · result ∈ blocked·rolled_back·failed·rollback_failed·success(인데 `I<L`) | 사장님 문구 | 사유 매핑(§7) |

- 경과: `requested` = `C.consented_at` 과 API `DateTime.Now`(같은 시계) · `in_progress` = SQL `TIMESTAMPDIFF(SECOND, applied_at, NOW(3))`(같은 DB 시계). **T1 = 10분 · T2 = 30분**(설계값 · ⚠️ 워치독 루프 60초·펜딩 재적재 ~2분·백업 소요 미실측 ⇒ [4] 실측 후 PM 확정 P-2).
- `A.consent_id < C.id` 이고 `C`=approve 인 경우는 `requested`/`not_started` 로 간다(앞 시도 실패 뒤 새 [예]).
- 조회 실패: 종전처럼 `UpdateAvailable=false` 폴백 + LogWarning(#15·#20). 🔴 「계속 떠야 함」과 부딪히는 유일한 자리 — API 가 DB 를 못 읽으면 ERP 자체가 못 쓰는 상태라 받아들인다(⚠️ 리스크 표).
- 응답 계약(`UpdateStatusDto` **추가만** · 기존 5필드 불변): `IssueKind`(string) · `IssueText`(고객 문구 · §7 매핑 결과만) · `CanRespond`(bool = `MainPcOnlyAttribute.IsMainPc(HttpContext)` **같은 함수 호출** — 복붙 금지) · `NeedsPrompt`(bool = kind ∈ first·later·not_started·interrupted·failed).
- 판정은 **순수 함수 한 곳**(입력 5값 → kind)으로 뺀다 — 게이트가 컨트롤러 없이 표를 전부 돌릴 수 있게.

## §5 [워치독] 변경 (갈래 W)

> ⬛ **9/30 개정 — 이 절의 표 자리는 §12 로 대체.** `local_update_apply_status.consent_id` 칸 · 자가생성 `ADD COLUMN` · apply_status 에 `in_progress`/`failed` 기록 · 판독 SQL 의 apply_status JOIN 은 **폐기**(사장님 9/30 「1번으로」). 규칙 C 의 흐름(§3)·기동 정리·폴더 복원(§6)·보고 수 불변(5번)은 **유지** — 적는 표만 바뀐다.

1. **소비 규칙 C**(§3) — `ConsumeConsentForMajorAsync`. 판독은 `WatchdogConsentReader` 에 **새 메서드 추가**(`ReadLatestAsync` 는 남긴다 · #1): `SELECT c.id, c.action, COALESCE(a.consent_id,0) FROM local_update_consents c LEFT JOIN local_update_apply_status a ON a.applied_version=c.update_version WHERE c.update_version='{V}' ORDER BY c.consented_at DESC, c.id DESC LIMIT 1` (버전 문자열 검사 `IsSafeVersionLiteral` 그대로).
2. **in_progress 기록** — `WatchdogStatusWriter.WriteApplyStatusAsync` 에 선택 인자 `consentId` 추가. 값이 있으면 `ON DUPLICATE KEY UPDATE … consent_id=VALUES(consent_id)`, 없으면(종점 기록들) consent_id **안 건드림**. 자가생성 DDL 문자열에 `consent_id` 칸 + `ALTER TABLE … ADD COLUMN IF NOT EXISTS consent_id` 한 줄(표만 있고 칸 없는 옛 DB 대비).
3. **행 안 남던 종점 3곳에 `failed` 기록** — 다운로드·Sha256 실패(`UpdateOrchestrator.cs:163-167`) · 슬롯 판정 실패(`:188-192`) · Approve 분기 예외(`Worker.cs` catch). detail 은 §7 매핑이 알아보는 고정 문구.
4. **기동 시 정리** — `ExecuteAsync` 기동 복원 블록(`Worker.cs:195`) **앞**: ① 폴더 복원(§6) ② `result='in_progress'` 행 → `failed` · detail 「업데이트 중 중단」(기동 시점엔 적용이 돌 수 없다 — 적용은 이 프로세스 안에서만 돈다). 실패는 LogWarning 후 진행(#15·#20).
5. **R-1 보고 수**: Reject 분기 무접촉 ⇒ 보고 빈도 **불변**. 「이미 쓴 [예]」 분기는 `ReportConsentRejected` 를 부르지 않는다 ⇒ **증가 0**. (줄이는 것은 N-UPD3 별건.)

## §6 [전원종료] 폴더 복원 (갈래 W · 새 파일 1개)

워치독 기동 때 `{app}` 아래 폴더 모양만 보고 판정(DB 무관 · 순서 R1→R2→R3):

| # | 모양 | 뜻 | 동작 |
|---|---|---|---|
| R1 | `web` 없음 · `web.old` 있음 | web 밀어낸 직후 중단 | `web.old` → `web` |
| R2 | `api` 없음 · `api.old` 있음 | api 밀어낸 직후 중단 | `api.old` → `api` |
| R3 | `web.old` 있음 · `api.old` 없음 · `web`·`api` 있음 | web 만 신버전(혼합) | `web` → `web.failed`, `web.old` → `web` |
| R4 | `web.old`·`api.old` 둘 다 · `web`·`api` 있음 | 교체 끝 · 검증 중 중단 | **손대지 않음**(로그만) — 범위 밖 §0 |

- `:351` 가드: `TryDeleteDir(appWebOld/appApiOld)` 앞에서 R1·R2 모양이면 **지우지 않고 먼저 복원**(유일한 구버전 보호). 대조군: 가드 빼면 `web.old` 가 지워져야 FAIL.
- 복원했으면 in_progress 행을 `rolled_back` · 「업데이트 중 중단 — 이전 버전으로 되돌림」으로 기록(§5-4 보다 먼저).
- 이동 실패(파일 잠김 등): 로그 + 계속 · **프로세스를 죽이지 않는다**(종전 정지 함수 밖에서 새 kill 경로를 만들지 않는다).
- **#43**: 흐름 불변 — 동의 없는 신버전 적용 0, 「실패 시 롤백」을 부팅 때 마저 하는 것. **#29**: 사람이 고객 PC 를 조작하는 것이 아니라 게시물(팝업 동의로 들어간 워치독)의 자가 회복(#30). 🔴 **시험은 임시 폴더·샌드박스만** — 이 PC 설치본·demo 접촉 금지(#39).
- ERP 자체가 못 뜨는 경우(`rollback_failed` · R4 뒤 기동 실패)는 **ERP 안내가 원리적으로 불가** — 워치독 긴급통지(`UpdateOrchestrator.cs:963`)의 몫. 이 설계는 경계만 적는다.

## §7 [문구] 고객 문구 매핑 (detail 원문은 화면에 안 낸다 · #23 개발용어 금지)

| 결과 · detail 머리 | IssueText |

- **이름 판정**: 보호 3표 이름 중 어느 것도 이 이름의 부분 문자열이 아니다 ⇒ 두 게이트 정규식(`…TABLE\s+`?{t}`?\b`)에 원리적으로 안 걸린다. `local_update_apply_status_*` 류(보호 이름을 머리로 가진 이름)는 금지 — `\b` 한 글자에 기대게 된다.
- **한 시도 = 한 행**: `in_progress` 는 **INSERT(UPSERT 아님)** — 같은 [예]를 두 번 쓰면 UNIQUE 위반 = 기록 실패 = 적용 안 함(DB 가 막는다).
- **종점 결과 자리**: ① 시도 행 — 모든 종점이 `UPDATE … SET result, detail, ended_at=NOW(3) WHERE update_version=V AND result='in_progress'` 로 닫는다(동의 없는 경로는 0행 = 무해). ② apply_status — **종전 그대로**(옛 4종점 · 옛 어휘 · 칸·호출 수 불변). `in_progress`·`failed` 는 apply_status 에 **쓰지 않는다.** ③ 본사 보고 — 종전 깔때기(`RecordApplyStatusAsync`) 호출 수 불변. 새 종점(다운로드·슬롯·예외)과 기동 정리는 깔때기를 **거치지 않고** 시도 행만 닫는다(§0 R-1 「늘지도 줄지도 않는다」).

**12-2 규칙 C · 판정식의 출처만 바뀐다** (흐름은 §3·§4 그대로)
