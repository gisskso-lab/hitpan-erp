## 2. 사장님 7단계 흐름 — 판정

| 단계 | 판정 | 사유 |
|---|---|---|
| 1. 회계장부 | 🟢 **정확** | 실무 중심축이 맞습니다 |
| 2. 수금 (+) | 🟢 정확 | |
| 3. 지급·급여·경비 (−) | 🟡 **계정과목만 위치 이동** | 아래 ① |
| ↳ "2-3을 한번에 = 매입매출장" | 🔴 **다릅니다** | 아래 ② |
| 4. 부가세 | 🟢 정확 | |
| 5. 어음·카드·은행 = "+/−의 유형" | 🟢 **표현이 특히 정확** | 돈의 **수단**이 맞습니다 |
| 6. 월마감 | 🟢 정확 | |
| 7. 손익·세무사 | 🟢 정확 | |

### ① 계정과목은 3번이 아니라 **맨 앞(0번)** 입니다
> **계정과목** = 돈에 붙이는 **이름표 목록**. "이건 식대, 저건 매출" 하고 분류하는 사전.

마이너스 전용이 아닙니다 — 매출(+)도 씁니다. 그리고 **이게 없으면 1~7번이 전부 작동 안 합니다.**
더존·이카운트도 「기초정보」에 두지 「지급」 옆에 두지 않습니다.

### ② 매입매출장은 "수금+지급을 한번에" 가 **아닙니다**

| 구분 | 무엇 | 시점 |
|---|---|---|
| 매입매출장 | 물건을 **팔았다/샀다** (세금계산서) | 물건 나간 날 |
| 수금·지급 | 그 **돈을 받았다/줬다** | 돈 들어온 날 |

100만원 팔고 다음달에 받으면 — 매입매출장은 **이번달**, 수금은 **다음달**. 다른 장부입니다.
✅ 히트판 코드(`FinanceService.cs:113`)도 **이미 맞게** 되어 있습니다(수금·지급 안 봄).

⇒ **수금+지급을 한번에 보는 자리 = 매입매출장이 아니라 「회계장부」(1번)입니다.**
   사장님이 찾으시던 게 정확히 그것입니다.

### 수정된 실무 순서
```
0. 계정과목 (기준 세팅)
1. 회계장부  ← 모든 게 모이는 중심
2. (+) 수금    3. (−) 지급·급여·경비
   ↳ 별개 장부: 매입매출장 (세금계산서)
4. 부가세   5. 어음·카드·은행 (수단)   6. 월마감   7. 손익·세무사
```

## 3. 「회계장부」는 실무에서 무엇인가 — 4탭

경리가 기대하는 건 한 화면이 아니라 **세트**입니다. 더존·이카운트 공통.

| 탭 | 쉬운 말 | 경리가 언제 쓰나 |
|---|---|---|
| ① 분개장 | 돈 움직임 **전부 시간순** | "어제 뭐뭐 있었지?" |
| ② 총계정원장 | **이름표별로 모아본 것** | "외상매출금 지금 얼마?" |
| ③ 거래처원장 | 거래처별 받을/줄 돈 | "A사에 얼마 남았지?" |
| ④ **합계잔액시산표** | 전체 **한 장 요약 + 검산** | 🔴 **월마감 직전 필수** |

> **시산표** = 좌우(차변·대변) 합계가 **딱 맞는지 확인하는 검산표**. 복식부기는 항상 좌우가 같아야 하고, 안 맞으면 어딘가 틀렸다는 뜻.

🔴 **사장님의 "전체 돈 숫자가 모이는 곳" = ④ 시산표**가 정확히 그것입니다.

### 13개와 겹치나 — 안 겹칩니다
| | 기존 13개 | 회계장부 |
|---|---|---|
| 보는 것 | 업무별로 **따로** | **전부 한곳에** |
| 근거 | 원본 전표 | **분개** |
| 답하는 질문 | "이번달 수금 얼마?" | 🔴 **"지금 우리 회사 현금 얼마, 받을 돈 얼마냐"** |

마지막 질문에 답하는 화면이 **지금 없습니다.**

## 6. 🔴 PM 판정 — 두 전문가 의견이 갈렸습니다

| | ERP매니저 김 | 설계팀장 존 |
|---|---|---|
| 순서 | **계정과목·기표 먼저** → 회계장부 | **회계장부 먼저** → 기표 |
| 이유 | 지금 만들면 **빈 화면** | 만들면 **누락이 눈에 보인다** |

### PM 결론: **설계팀장 안(회계장부 먼저)** 을 권합니다

근거 4가지:
1. **위험**: 회계장부는 읽기 전용 ⇒ **DDL 0 · 원장 무접촉 · 위험 0**.
   기표 추가는 트랜잭션·원장·FK 를 건드립니다(헌법 #3 INSERT ONLY 영역).
2. **"빈 화면" 우려는 과장**입니다 — 매입·판매·BOM·계산서 기표는 **이미 돌고 있습니다.**
   빈 게 아니라 **일부만 찬 상태**로 보입니다.
3. 🔴 **그 "일부만 참" 이 곧 근거가 됩니다** — 화면에 "수금 100건인데 장부엔 0건" 이 뜨면,
   그게 기표 봉합의 **실측 근거**입니다. 지금은 아무도 그걸 볼 수 없습니다.
4. 계정과목 확장은 **기존 고객 DB 마이그**를 부릅니다 — 무거운 걸 먼저 하면 오래 막힙니다.

⚠️ 단 ERP매니저 지적도 유효합니다: **1차에서 "이 화면은 아직 매입·판매만 보입니다" 를 화면에 명시**해야
   담당자가 "고장났나" 하지 않습니다. 이건 1차 범위에 넣겠습니다.

### 5번 파이프라인 — DDL 0 으로 이미 가능 (실측)

`bank_transactions` **DESCRIBE 실측 결과 필요한 컬럼이 이미 있습니다**:

| 컬럼 | 현재 | 파이프라인에서 쓰는 법 |
|---|---|---|
| `imported_from` | `varchar(20)` NOT NULL **DEFAULT `'manual'`** | 🔴 **바로 이 자리** — `manual` → 나중에 `toss` / `openbanking` |
| `source_type` · `source_id` | `varchar(30)` · `varchar(80)` | 외부 거래 원본키 보관 (멱등 재수집) |
| `partner_id` | nullable | 자동 매칭 시 채움. 지금은 사람이 지정 |
| `card_payments.source_id` | `varchar(80)` | 카드도 동일 |

⇒ **지금은 `imported_from='manual'` 로만 들어옵니다.** 연동 시 값만 바뀌고
   **표·화면·회계장부는 한 줄도 안 바뀝니다.** 이것이 "파이프라인을 미리 만든다"의 실체입니다.

**설계 원칙 3가지 (연동 시점에 지킬 것)**
1. 🔴 **자동 수집 ≠ 자동 기표** — 헌법 *"100% 자동화는 없다"*.
   외부에서 거래를 **가져오는 것까지가 자동**, **기표는 사람이 확인 후 확정**(반자동).
2. 🔴 **멱등** — 같은 거래를 두 번 받아도 두 번 기표되면 안 된다.
   `(tenant_id, source_type, source_id)` 로 막는다. `journal_entries.uq_je_source` 와 같은 방식.
3. 🔴 **원본 보존** — 외부에서 받은 값을 고쳐 저장하지 않는다. 매칭·분류는 **별도 칸**에.

### 🔴🔴 범위 재확정 (사장님 지시 2026-08-27, 최종)

> *"saas결재는 지금 하지마"* · *"완벽한 회계 워크플로우 구축에 집중해"*

| 축 | 이번 차수 |
|---|---|
| **A. SaaS 구독결제** (`billing_*`·`IBillingProvider`) | ❌ **손대지 않는다.** 이미 동작 중인 것을 건드리지 않는다 |
| **B. 고객사 업무 회계** (`card_payments`·`bank_transactions`) | ✅ **여기에만 집중** |

⇒ 아래 파이프라인 설계는 **B(회계) 축만** 해당합니다.
   A 는 *"같은 패턴이 이미 있다"* 는 **참고 근거**로만 인용하고, **코드는 한 줄도 안 건드립니다.**

### 파이프라인 설계 — B(회계) 축

```
        법인카드 · 법인통장 (고객사 업무)
                    ↓
        수집기 (지금은 사람이 입력 = manual)
        ├ imported_from = 'manual'   🟢 지금
        └ imported_from = 'toss'     🟡 추후 (컬럼만 준비)
                    ↓
        card_payments · bank_transactions
                    ↓  🔴 사람이 확인 후 확정 (반자동)
                회계장부 (분개)
```

| 대상 | 현행 | 추후 |
|---|---|---|
| 카드 (`card_payments`) | 사람이 입력 | `source_id` 로 외부 원본 연결 |
| 계좌 (`bank_transactions`) | `imported_from='manual'` | `imported_from='toss'` |

🔴 **패턴은 A(구독결제)의 `IBillingProvider` 를 그대로 본뜹니다** — `ProviderCode` 로 갈아끼우는 방식.
   이미 레포에 있는 방식이라 **같은 것을 두 번 배우지 않아도 됩니다**(히트판 정신: 쉬움).
   ⚠️ 단 **A 의 코드는 읽기만 하고 수정하지 않습니다.**

**규약**
| 규약 | 내용 |
|---|---|
| 수단 구분 | `imported_from` = `manual` → 나중에 `toss` |
| 멱등키 | `(tenant_id, source_type, source_id)` — 같은 거래 두 번 받아도 한 번만 |
| 키 보관 | 🔴 고객 PC 에 외부 비밀키 **0건** |

⚠️ **B 의 키 보관은 A 와 갈릴 수 있습니다** — 고객사 법인계좌 인증정보를 본사가 들면
   헌법 #18·#22(본사가 안 가지면 안 털린다)와 충돌합니다.
   ⇒ **연동 착수 시 사장님·보안상무 결재 필요** (이번 차수 범위 아님).

**⚠️ 이번 차수에 하지 않는 것**: 토스 API 호출·토큰·스케줄러·실제 수집.
**인터페이스와 컬럼 규약만 확정**하고 실제 연동은 별건 결재.
(지금 만들면 쓰지도 않는 코드가 보안 표면만 넓힌다 — 헌법 #34 뼈대 먼저)
