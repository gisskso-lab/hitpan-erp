## §1 [W-1] 보호대 한 점 통합 + 음성 대조군 재측정

**사실** 🟢 — `AuthService.RefreshAsync` 안에서 `CompensateNewSessionRowAsync` 를 부르는 곳은 셋이고 인자 식이 **세 번 복사**돼 있다: `isNewSession && sessionRecorded ? sessionId : null`
- ③ 회전 준비(연결 열기·`BeginTransaction`) `catch` · ① 단일사용 거부 `catch (UnauthorizedAccessException)` · ② 회전 중 예외 `catch (Exception)`
- 게이트 `G_B13d_이어받은_세션의_갱신이_터져도_일하는_세션_행은_살아남는다` 는 **③ 만** 탄다(Q7).

**처방** (CTO K-8 채택안 그대로)
1. `if (isNewSession) { … InsertSessionAsync … }` 블록 **바로 뒤**, `CreateLoginResponse(...)` **앞**에 지역변수 1개를 선언한다.
   - 이름: `sessionIdCreatedHere` — 받는 쪽 매개변수(`CompensateNewSessionRowAsync` 의 `sessionIdCreatedHere`)와 같은 이름으로 해 둘을 잇는다.
   - 값: 지금 식 그대로(`isNewSession && sessionRecorded ? sessionId : null`). **식은 바꾸지 않는다.**
2. 세 호출의 인자를 그 변수로 바꾼다. 다른 줄은 건드리지 않는다(#1).
3. 세 자리 주석 중 *"인자가 `null` 이 되어"* 류 서술은 **변수 이름**을 가리키게 고친다. 옛 서술은 ⬛낡은 줄로 남긴다(문서는 지우지 않는다).

**효과와 한계**
- 🟢 보호대가 한 글자열이 되므로 G-B13d 의 음성 대조군이 **세 자리를 함께** 잰다(보호대를 지우면 세 자리가 동시에 빠진다).
- 🔴 그래도 ①② **경로 실행**은 여전히 0 이다(Q7). "보호대가 같다"는 잰다, "①② 에서 보상이 실제로 불린다"는 못 잰다.
- 선택 W-1b(② 게이트 신설 — 트랜잭션 안 실패 주입 헬퍼 신규)는 CTO 가 "더 크다"고 적었다. **기본 안 함** · 넣을지는 PM(§7 P-2).

**음성 대조군 재측정 (W-2 · CI 가 유일한 계측 경로)**
- 개발 PC 는 `CREATE DATABASE` 거부 ⇒ DB 게이트는 `[SKIP]`. 로컬 초록은 증거가 아니다.
1. W-1 커밋 위에 **버리는 가지**를 만든다: 선언의 `isNewSession &&` **한 조각만** 지운다(호출부는 안 건드린다 — 한 점이 진짜 한 점인지가 이 대조의 목적).
2. draft PR 로 올려 `db-gate` 잡을 깨운다(선례 #428·#429). 통과 = **`G_B13d` FQN 이 Failed** + 실패 문구 *"보상 삭제가 이어받은(일하고 있는) 세션 행을 지웠다"*.
3. 본 가지 W-1 커밋: 같은 잡에서 `G_B13d`·`G_B13`·`G_B13b`·`G_B13c` **FQN Passed** + `HITPAN_REQUIRE_DB: true` + 이 넷의 `[SKIP]` 0.
4. 버리는 가지는 PR 닫고 삭제(머지 0). 두 run ID 를 개발명세서에 적는다.
- 🔴 판정은 **FQN** 으로 한다 — `--verbosity normal` 은 한글 DisplayName 만 찍어 FQN 이 없다(9/22 사고). 대조 두 쪽을 같은 파서로 읽지 않는다.

**[4] 리뷰 확인 (게이트 아님 — 글자 확인은 리뷰 몫)**: `AuthService.cs` 안 `isNewSession && sessionRecorded` 출현 **1회** · `CompensateNewSessionRowAsync(` 호출 3곳의 두 번째 뒤 인자가 모두 그 변수.

## §2 [R-1] 갱신이 「행 없는 `sid`」를 만났을 때 — 갇힘

**현행 흐름** 🟢 코드 / ⚠️ 화면 실행 미측정
```
화면 요청(sid=X, 행 없음) ─▶ SessionValidityMiddleware: 행 없음 → 401
  ─▶ HitPanApiAuthHandler: 401 → TryRefreshAsync
       ─▶ RefreshAsync: isNewSession=false → GuardExpiredPcSessionRevivalAsync
            「② 행 없음 — 현행 유지」 return → 회전 성공 → UPDATE user_sessions 0행 → 200 (sid=X 그대로)
  ─▶ 재시도 → 또 401 → 핸들러는 「갱신 성공」 갈래라 토큰을 안 지운다
⇒ 로그인 화면으로도 안 가고 모든 화면 401 · 요청마다 refresh 토큰 회전 (= 갇힘)
```
탈출 🟢: 화면 로그아웃은 서버 응답과 무관하게 저장 토큰을 지운다(Web `AuthService.LogoutAsync`). ⚠️ 그러나 서버 쪽 `/api/auth/logout` 은 미들웨어에서 401 로 끊겨 **refresh 토큰 폐기가 안 돈다**(회전된 토큰이 7일 남는다). 모든 화면이 401 인 채 로그아웃 버튼을 찾을 수 있는지는 미측정.

**이 입구를 타는가 — 코드로 확인** (「행 없는 `sid`」 + 「DB 에 살아 있는 refresh 토큰」 두 조건이 함께 서야 갇힌다)

| 경로 | 타나 | 근거 |
|---|---|---|
| 밀어내기 `ForceSignOutOtherPc` | 🟢 **안 탄다**(정상 시) | `EnforceSinglePcLoginAsync` 가 PC 행을 지운 뒤 같은 `LoginAsync` 가 `DELETE FROM refresh_tokens WHERE user_id` ⇒ 밀린 PC 의 갱신은 `RefreshAsync` 초입 *"로그아웃된 토큰"* 401 → 핸들러가 토큰을 지운다 → 로그인 화면. 또 축 B 기본 끔(DB-128)이면 이 경로 자체가 안 돈다 |
| 밀어내기 **도중 예외** | 🟢 **탄다**(축 B 켬일 때만) | 행 삭제와 refresh 전삭 **사이**(`_unitOfWork.SaveChangesAsync` · `TenantConfigReader.GetRequired("JWT_SECRET")` · `CreateLoginResponse`)에서 터지면 밀린 PC 는 행 없음 + 토큰 생존 |
| 로그아웃 (`AuthController.Logout`) | 🟢 **안 탄다** | 그 계정 refresh 토큰 전부 `is_revoked = 1` ⇒ 어느 기기든 다음 갱신은 401 → 로그인 화면 |
| 데이터 초기화 (`DataResetService`) | 🟢 **안 탄다** | 지우는 표 목록에 `refresh_tokens`·`user_sessions` 가 **함께** 있다 |
| DB 복원 (`BackupService.RestoreAsync`) | 🟢 **지금은 안 탄다** | `RestoreTemporarilyClosed = true` 로 복원이 닫혀 있다. ⚠️ 다시 열리면: 두 표가 같은 시점으로 함께 돌아가 대개 토큰이 없어 401(로그인) — 단 백업 파일이 두 표를 함께 담는지는 미확인 |
| 보상 삭제가 이어받은 행을 지움 (K-8 보호대 빠짐) | 🟢 **탄다** | 행은 지워지고 refresh 회전은 롤백돼 옛 토큰이 산다 — CTO *"즉시 쫓아낸다"* 보다 나쁜 R-1 그 자체 |
| 수동 DB 수술 (`user_sessions` 만 지움) | 🟢 **탄다** | 운영은 #39 로 금지 · CS 현장 조치로 생길 수 있다 |
| 만료 행 정리 | 해당 없음 | 코드에 만료 행을 지우는 곳 0(`DELETE FROM user_sessions` 는 밀어내기·보상·로그아웃 3곳뿐). 만료 행은 미들웨어 401 → 갱신이 되살린다(정상) |

**선택지** — 🔴 **선택은 PM·사장님**(§7 P-1). 설계는 대가와 권고만.

| 안 | 무엇을 하나 | 대가 |
|---|---|---|
| **A 현행 200** | 그대로 | 갇힘 유지. 위 「탄다」 네 경로가 전부 갇힘으로 끝난다. **K-8 보호대가 나중에 빠지면 아무도 모르는 채 고객이 갇힌다**(W-1 이 유일한 방어선). 코드 0줄 |
| **B 401 로 재로그인** | `GuardExpiredPcSessionRevivalAsync` 의 「② 행 없음」 **한 갈래만** `return` → 거절(`UnauthorizedAccessException`, 고객 문장 — 기존 ⑦ 과 같은 문장 재사용 여부는 PM). **`enforce_session_validity` 가 켜진 테넌트에서만**(행 없음·NULL = 끈 쪽 — 미들웨어와 같은 방향) | 그 사용자는 **재로그인 1회**. 거절이 회전 **앞**이라 옛 refresh 토큰은 폐기되지 않고 남는다(화면이 지우므로 실제 피해는 없다고 본다 ⚠️ · 행이 없는 한 다시 써도 401). 갱신마다 스위치 조회 1회 추가(8h 주기). 새 SQL 이므로 DESCRIBE 선행(#13). 게이트 1건 신설 |
| **C 새 세션 발급** | 행이 없으면 `isNewSession` 처럼 새 `sid`·새 행 | 작1 절C 결정 *"밀어내기로 이미 지워진 세션은 되살리지 않는다"* 를 정면으로 뒤집는다. K-8 회귀를 **완전히 숨긴다**(행이 다시 생겨 흔적 0). `isNewSession` 판정이 토큰에서 오는 구조라 손댈 곳이 넓다(M) |

**권고: B (스위치 연동)** — 근거 셋.
1. 미들웨어는 이미 *"행 없음 = 죽은 세션 = 401"* 로 답한다. 갱신이 같은 사실에 **다른 답(200)** 을 주는 것이 갇힘의 원인이다. 두 판정이 같은 답을 내게 한다.
2. 작1 절C 의 의도(*"되살리지 않는다"*)는 그대로다 — 되살리지도, 새 토큰을 굽지도 않는다.
3. K-8 보호대가 나중에 빠져도 결과가 「조용한 갇힘」에서 「재로그인 1회」로 내려간다. W-1 이 유일한 방어선이 아니게 된다.
- 스위치 연동 이유: `enforce_session_validity = 0` 이 **종전 동작 완전 복귀**여야 비상 스위치 의미가 산다(끈 테넌트에선 미들웨어도 통과시키므로 B 가 끼어들 이유가 없다).
- 판정 자리를 새로 만들지 않는다 — 「② 행 없음」 한 갈래만 바꾼다. 그 함수의 `catch (Exception)` 폴백(판정 실패 = 진행)은 그대로다 ⇒ `user_sessions` 가 없는 DB(기한 없는 갈래)는 영향 0.

**B 채택 시 게이트 G-B15 (동작으로 잰다)**: 로그인(`sid` 실림) → 그 행만 삭제 → 갱신 ⇒ 스위치 1: 401 · refresh 토큰 **회전 안 됨** / 스위치 0: 200(종전). 양성 조건 = 토큰에 `sid` 가 실렸다 · 행 삭제 1건. 음성 대조군 = 「② 행 없음」을 `return` 으로 되돌리면 FAIL. CI `db-gate` 등록.

**참고 — 오더 3안 밖(확인 필요)**: 화면 핸들러에서 *"갱신 성공 뒤 재시도도 401 이면 토큰을 지운다"*(`HitPanApiAuthHandler` 재시도 갈래). 원인 무관하게 갇힘을 푼다. 오더에 없으므로 넣지 않았다 — 원하면 PM 이 사장님께 여쭌다(#33).

🔴 **순서**: R-1 은 W-1 과 **같은 [3] 차수**여야 한다. 실측 뒤에 고치면 그 실측이 무효다(CTO K-8 논리 동일).

## §3 [K-4ⓐⓑⓒ] 돌아가는 서버에서 재는 절차 (§5 실측에 편입)

**ⓒ 비상 스위치 1→0 → 10초** — 사실 🟢: TTL `SessionCacheTtl = 10초` · 캐시 키 `session-validity:{tenant}` · 스위치 판독이 생존 조회 **앞**. 🔴 돌아가는 서버에서 바꿔 본 적 0(G-B14 는 매 호출 새 캐시·빈 DB).
1. 시험 PC 브라우저 X 로 로그인(`sid` 실림 확인 — §5 M-3 방법).
2. 시험 DB 에서 X 의 세션 행만 삭제 → X 화면이 401 이 되는 것을 F12 Network 로 확인(= 죽은 세션 상태). ⚠️ A 안이면 여기서 갇힘(R-1)이 함께 관측된다 — 그 자체가 M-9 기록.
3. `UPDATE tenant_settings SET enforce_session_validity = 0 WHERE tenant_id = …` 실행 시각 T0 기록.
4. X 에서 1초 간격으로 같은 조회 화면 요청(사람 손 · F12 Network 타임스탬프). **첫 200 시각 T1**.
5. 통과: `T1 − T0 ≤ 10초 + 요청 간격 1초`. **API·서비스 재시작 0회**(작업 관리자 PID 불변으로 확인).
6. 되돌리기 0→1 → 같은 방법으로 **10초 안에 다시 401** 확인(끄기만 되고 켜기가 안 먹으면 비상 스위치가 아니다).
7. 스위치 행이 없는/NULL 인 테넌트는 끈 쪽(Q2 🟢) — 실측은 안 하고 선행검증 근거로 둔다.

**ⓐ 막히면 안 되는 경로** (죽은 `sid` 를 쥔 브라우저로) — 로그인 화면 표시·로그인 · 업데이트 확인(`update-status-local`) · `mainpc-proof` · 문서 다운로드 링크 · 워치독 `/health`. 전부 401 이 **아니어야** 통과. 근거 Q1 🟢, 실측은 처음.

**ⓑ DB 가 잠깐 끊길 때** — 사실 🟢 fail-open 두 겹(Q2). 잴 것은 *"DB 가 돌아온 뒤 재로그인 없이 계속 쓰나"*: 끊긴 동안 응답이 **401 이 아니고**(500/503 류) 핸들러가 토큰을 안 지웠는지. 🔴 MariaDB 서비스 정지는 **#29 서비스 조작**이다 — 시험 PC 라도 사전 승인 대상인지 **확인 필요**(§7 P-5). 승인이 없으면 ⓑ 는 선행검증 코드 근거로만 두고 실측표에 「미측정」으로 적는다.

## §4 [K-7] 게시 첫날 창 · 기한 없는 갈래

**사실** 🟢 — `AccessTokenLifetime = 8h` · `RefreshTokenLifetime = 7일`. 업데이트 순간 기존 토큰은 `sid` 가 없다 → 미들웨어 통과 → 첫 갱신(access 만료 401)에서 `isNewSession` → 새 행 + `sid`. ⇒ **기기마다 최대 8h** 창. `AuthExtensions` 의 15분/7일 상수는 참조 0곳(R-2) — 창을 15분으로 적으면 틀린다.

첫날 창 안에서 달라지는 것(🟢 코드):
- 옛 토큰 기기는 세션 행이 없어 로그아웃·밀어내기의 **즉시 반영 대상이 아니다**(축 B 가 꺼져 있어 밀어내기는 애초에 안 돈다).
- 옛 토큰 기기가 로그아웃하면 `AuthController.Logout` 의 `sid` 없음 갈래가 **그 계정 세션 행 전삭** ⇒ 이미 새 토큰을 받은 같은 계정의 다른 기기(모바일 포함)가 **10초 안에** 401 → 로그인 화면. 종전(#427 이전)엔 access 만료(≤8h) 뒤였다 — 창 안에서만 생기는 변화.

**선택지** — 🔴 사장님(§7 P-3)

| 안 | 내용 | 대가 |
|---|---|---|
| (가) 수용 | 인계서·CS 메모에만 적는다 | 고객 체감 변화는 위 둘째 항목뿐 · 8h 안에 저절로 닫힌다. 비용 0 |
| (나) 고지 | 업데이트 안내에 *"업데이트 후 한 번 다시 로그인해 주세요"* | 고객 노출 문구(개발용어 금지) · 안 따라도 8h 뒤 같은 결과. 업데이트 안내 문구가 #43 흐름 변경에 해당하는지 **확인 필요** |
| ~~(다) 강제~~ | `sid` 없는 토큰 거절 | **제외** — 20260927작2 작지 §3 금지 #1b(*"배포 순간 전 고객이 튕긴다"*) |

권고: (가). 근거 — 창 안의 "미반영"은 종전과 같은 동작이지 회귀가 아니고, 스스로 닫힌다.

**기한 없는 갈래** 🟢 — `InsertSessionAsync` 가 계속 실패하는 DB(예: DB-127 미적용으로 `device_kind` 칸 없음)는 로그인·갱신마다 `sid` 를 안 실어 **영원히** 세션 생존 확인 밖이다. 결과는 #427 이전과 같다(fail-open · 회귀 아님). 흔적은 남는다 — 매 실패마다 `security_alerts` 에 `alert_type = 'session_insert_failed'` 1행.
- 처리안 ① (권고) **게시 전 실측 항목으로 막는다**: 마이그된 고객 DB 에서 로그인·갱신 뒤 `session_insert_failed` **0건**(§5 M-10). 흔한 원인(마이그 미적용)을 게시 전에 잡는다.
- 처리안 ② 게시 후 감지: 그 표는 고객 PC 로컬에만 있다 — 본사로 올리지 않는다(#18·#22). 고객 화면에서 이 흔적을 보는 곳이 있는지 **확인 필요**.

## §5 [실측] 백지 PC 재현 계획 (초안)

**전제** — Q8 🟢: 시험 채널이 없다 ⇒ 시험 게시 = 정식 게시. 결재 4-4 는 ⏳(경로를 다시 여쭌다). 이 절은 **③ 게시 없이 재현** 안의 초안이다. 실측 대상 빌드는 **W-1 + R-1 처방이 [4] 를 통과한 커밋**이다.
