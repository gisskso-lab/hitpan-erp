## §3. 🔴 P0 — 조립 전에 먼저 정리해야 할 것 3건

### P0-1. 결재선 시스템이 **2개**이고 서로를 모른다

| | 실제 도는 것 | **죽어 있는 것** |
|---|---|---|
| 테이블 | `approval_doc_lines` | `approval_lines` + `approval_line_steps` |
| 화면 | 결재 설정 (`/settings/approval`) | 결재라인 설정 (`/settings/approval-lines`) |
| 직급 지원 | ❌ 사람(`approver_id`)만 | ✅ **`position_id` 있음** |
| 결재 엔진이 읽나 | ✅ | 🔴 **안 읽음** |

**고객에게 무슨 일이 나나**: 관리자가 직급으로 결재선을 짜면 저장도 되고 화면에도 뜨는데
**결재는 그 설정을 전혀 안 본다. 조용히 무시된다.**

> 🔴 **김삼성 상무 조언의 난이도를 바꾸는 지점.**
> 상무님: *"사람 이름으로 결재선을 짜면 **그 사람이 퇴사하는 날 회사의 모든 결재가 멈춥니다.**"*
> 그런데 직급을 지원하는 쪽이 **죽어 있다.** 상무님 조언을 살리려면 **죽은 쪽을 엔진에 붙여야** 한다.

**⛔ 어느 쪽을 정본으로 삼을 것인가는 설계 판단이지 개발 판단이 아니다 — 사장님·상무님 결재 사항.**
설계팀 권고안은 §7-A.

### P0-2. 경비 신청이 완전한 막다른 길

| | ERP 경비 | **그룹웨어 경비** |
|---|---|---|
| 결재 트리거 | ✅ | 🔴 **없음** |
| 월마감 체크 | ✅ | 🔴 없음 |
| 감사로그 | ✅ | 🔴 없음 |
| 승인 엔드포인트 | ✅ | 🔴 **없음** |

직원이 경비를 신청하면 **결재가 안 올라가고, 그룹웨어 안에서 승인할 방법도 없다. 영원히 "대기".**
유일한 우회 경로에서는 **승인자 자리에 테넌트 ID를 넣는다** — 누가 승인했는지 영영 모른다.

⇒ **사장님 신규요청 5번(경비·지출결의서 ↔ 회계 연결)이 정확히 이 봉합이다.**

### P0-3. 근로계약서가 신분 축과 완전 단절

서명해도 `employees` 를 **한 줄도 안 건드린다.**
계약서의 입사일·연차·급여가 사원 정보로 **전혀 흘러가지 않는다.**
**같은 사람 입사일이 두 곳에 따로 있고 대조 장치가 없다.**

⇒ 급여명세서(신규요청 6)를 지으려면 **급여 기준값이 어디서 오는지**가 먼저 정해져야 한다.

## §3-5. 🔴🔴 축(PK) 확정 — **사원(`employees`)이 축이다**

> 사장님 질문(2026-08-12): *"결국 프라이머키 역할로 워크플로우의 축이 되는건 직원계정이지?
> 직원계정이 아닌 사원으로 잡아야 하나?"*

**답: 사원(`employees`)이 축이다.** 계정(`users`)이 아니다. 실측 근거 둘.

### 근거 1 — 그룹웨어가 이미 전부 사원을 가리키고 있다

| 표 | 가리키는 것 |
|---|---|
| `attendance`(근태) · `leave_requests`(휴가) · `overtime`(초과근무) · `hr_expense_requests`(경비) · `labor_contracts`(계약서) | **`employee_id`** |
| `approval_documents`(결재문서) | **`requester_id`** — DDL 주석 *"기안자 **사원** ID"* |
| `approval_doc_lines`(결재선) | `approver_id` |
| `esign_records`(전자서명) | 🔴 **`user_id`** ← **유일한 예외** |

**8개 중 7개가 사원을 가리킨다.**

### 근거 2 — 실제 데이터가 결정적이다 (개발DB 실측)

```
사원 12명  →  계정 있음 1명 · 계정 없음 11명
```

**계정을 축으로 잡으면 11명이 그룹웨어에서 사라진다.** 근태도 휴가도 결재도 못 한다.
⇒ 사장님 8/11 결재 #1 *"계정 없는 사원을 막지 않는다 — 막으면 MDB 마이그 직원이 전부 못 들어온다"* 와 정확히 일치.

### 그럼 "직원계정 = 마스터"는 틀린 말인가 — 아니다, **층이 다르다**

| 축 | 역할 | 없으면 |
|---|---|---|
| **사원** `employees` | **업무의 주체** — 근태·휴가·결재·급여의 주인 | 그룹웨어 자체가 성립 안 함 |
| **계정** `users` | **로그인 수단** — 시스템에 들어오는 열쇠 | 남이 대신 처리 가능 |

사장님 못박음 *"HR과 인사, 그룹웨어는 직원계정으로부터 모든 연결이 돼"* 는
**"직원이라는 존재가 축"** 으로 읽는다. 로그인 계정이 축이라는 뜻이 아니다.

> 현실 비유: 입사하면 **사번**이 먼저 생기고 사내 **아이디**는 나중에 받는다.
> 아이디가 없어도 그 사람은 직원이고, 월급도 나오고 연차도 쌓인다.

### 축 확정이 낳는 결론 3가지

```
employees (사원) ★축 — 모든 그룹웨어가 여기 매달린다
    │
    ├─ user_id ────→ users (계정)    … NULL 허용 (있을 수도 없을 수도)
    ├─ position_id → positions (직급) … 결재선이 여기 걸린다 (상무님 조언)
    └─ dept_id ────→ departments(부서) … 부서방이 여기 걸린다
```

1. 🔴 **전자서명이 `user_id` 를 쓰는 것은 예외 = 봉합 대상.**
   계정 없는 사원은 근로계약서에 **서명을 못 한다.** 사원 기준으로 바꿔야 한다

### 🔴 다만 메신저는 예외다 — **계정 있는 사원만** (사장님 결재 2026-08-12)

> 사장님: *"그룹웨어의 마스터는 사원. 하지만 **메신저는 계정이 있는 사원에게만 권한**을.
> **물리적으로 그렇게 될 수밖에 없으니**"*

**축 결정과 모순이 아니라, 원칙을 완성하는 결재다.** 판정 기준이 여기서 나온다:

| 기능의 성격 | 축 | 왜 |
|---|---|---|
| **남이 대신 해줄 수 있는 것** | **사원** | 근태·휴가·경비·급여·계약… 인사담당자가 대신 등록해도 **사실이 성립**한다 |
| **본인이 직접 해야만 하는 것** | **계정** | 메신저·로그인·전자서명… **대신 말해줄 수 없다.** 물리적으로 불가 |

⇒ 메신저는 **실시간으로 접속해 본인이 말하는 것**이라 로그인이 전제다.
계정 없는 사원에게 메신저 권한을 준다는 말은 **접속할 수단이 없는 사람에게 채팅을 시키는 것**과 같다.

**설계 반영**
- 메신저 참여자·메시지는 **`user_id` 기준**(축 예외 — 근거 명시)
- 메신저 UI 는 **계정 있는 사원에게만** 노출. 없으면 안내: *"메신저는 로그인 계정이 필요합니다"*
- 🔴 **부서방 인원 = 그 부서 사원 중 계정 있는 사람**. 부서 사원 전원이 아니다
- 🔴 **결재 알림도 계정 기준** — 알림은 로그인한 화면에 뜨는 것이므로
- ⇒ **결재선에 계정 없는 사원이 있으면 그 사람은 알림을 못 받는다.**
  이건 결함이 아니라 **구조상 당연**이며, 대신 **인사담당자·대표가 대리 처리**하는 경로가 있어야 한다
- 반대로 **근태·휴가·경비·급여·계약은 계정 없어도 전부 된다**(인사담당자 대행)

> 이 구분이 8/11 사장님 결재 #1(*"계정 없는 사원을 막지 않는다"*)과 정합한다.
> **막지 않는다 = 업무에서 배제하지 않는다**는 뜻이지, **로그인이 필요한 기능까지 준다는 뜻이 아니다.**
2. 🔴 **결재선은 직급(`position_id`)에 건다.** 사람에 걸면 퇴사 시 멈춘다(상무님).
   직급은 사원에 붙어 있으므로 축과 정합한다 → §3 P0-1 권고안의 근거
3. **계정 발급은 부가 기능**이므로 순서를 미룰 수 있다(8/11 결재 #3 "수동 발급")

⛔ **이 축 결정이 ERD 전체의 전제다.** 바뀌면 짝 문서 4종을 다시 써야 한다.

## §4. 흐름 설계 — 물 흐르듯

> 사장님: *"물흐르듯 자연스러운 워크플로우 흐름과 동시에 꼼꼼하고 촘촘한 기능으로"*
> 김삼성 상무: *"부품은 다 있다. **조립 순서**를 잡는다."*

### 4-1. 축① 직원의 일생 (입사 → 재직 → 퇴사)

```
[입사]
 사원 등록 ──────→ 계정 발급 ──────→ 직급·부서 배정
   employees          users            positions/departments
      │                 │
      │  🔴 지금 끊김: 사원→계정 링크 없음(user_id NULL 하드코딩)
      │     사장님 결재(8/11 #2): 연결은 **양방향**
      ↓
 근로계약서 작성 → 전자서명 ──→ ● employees 갱신 ←🔴 지금 끊김(P0-3)
   labor_contracts   esign         (입사일·연차·급여 기준값이 여기서 확정)
      │
      ↓
[재직]  근태 · 휴가 · 초과근무 · 경비 · 보고서 · 급여
      │
      ↓
[퇴사]  퇴직 처리 → 결재선에서 자동 제외 → 인수인계
                      🔴 지금: 결재선이 사람 기반이라 퇴사 시 결재 정지(P0-1)
```

**설계 원칙 (김삼성 상무)**
1. **직원계정 = 마스터** — 사장님 못박음: *"HR과 인사, 그룹웨어는 직원계정으로부터 모든 연결이 돼"*
2. **계정 없는 사원을 막지 않는다**(8/11 결재 #1) — 막으면 MDB 마이그 직원이 전부 못 들어온다
3. **연결은 양방향**(8/11 결재 #2) — 계정→직원, 직원→계정 둘 다
4. **계약서 서명이 신분을 확정한다** — 입사일·연차·급여가 **한 곳으로 모이는 지점**

### 4-2. 축② 하루 업무 (신청 → 알림 → 결재 → 반영)

```
 ┌─ 입구 3개 ──────────────────────────────┐
 │  ① 화면에서 신청   ② 메신저에서 작성      │  ← 신규요청 2
 │  ③ 캘린더에서 클릭                        │
 └──────────────┬───────────────────────────┘
                ↓  (입구가 달라도 여기서 하나로 합쳐진다 ★핵심)
        ┌───────────────────┐
        │  결재 문서 생성    │  approval_documents
        │  doc_type 으로 구분│
        └────────┬──────────┘
                 ↓
        결재선 결정 (직급 기반)  ←🔴 P0-1
                 ↓
        🔔 알림 (실시간)         ←🔴 지금 없음. 상무님 "결재 알림부터"
                 ↓
        결재함 → 승인/반려
                 ↓
   ┌─────────────┴─────────────┐
   ↓                           ↓
 원본 상태 갱신            ● 회계 반영          ←🔴 신규요청 5·7
 (연차 차감·근태 반영)      (경비·급여)
   ✅ 연차는 이미 됨          🔴 지금 끊김
```

🔴 **이 그림의 핵심은 "입구가 달라도 한 흐름으로 합쳐진다"** 는 것이다.
사장님 지시 *"채팅창으로 작성시 워크플로우 로직에 자동추가"* 가 정확히 이 뜻이고,
그래서 **메신저는 별개 기능이 아니라 결재 워크플로우의 또 다른 입구**다.

### 4-3. 축③ 돈 (그룹웨어 → 회계)

> 사장님 지시: *"경비신청, 지출결의서는 회계관리와 연결"* · *"급여명세서도 회계관리와 연결"*

```
그룹웨어(사람이 쓰는 곳)              회계(돈이 쌓이는 곳)
──────────────────────────────────────────────────────
경비신청 ─[영수증첨부]→ 지출결의서 ─결재→ ●━━━━→ 경비처리/전표
                                          🔴 지금 끊김(P0-2)

급여명세서 ──────────────────────결재→ ●━━━━→ 인건비/전표
                                          🔴 완전 신규

초과근무 승인 ────────────────────────→ ● 급여 계산 근거
                                          🔴 지금 결재도 안 탐
```

**설계 원칙**
- 그룹웨어는 **신청·승인**까지. 회계는 **금액 확정·전표**. 경계를 섞지 않는다
- 회계 반영은 **결재 승인 시점에만**(헌법 #6 — 확정은 사람이)
- 원장은 **INSERT ONLY**(헌법 #3)
- 월마감 이후 소급은 차단(ERP 경비의 `EnsureNotClosedAsync` 패턴 재사용)

### 4-4. 축④ 소통 (메신저 — 신규)

> 김삼성 상무: *"메신저는 **'결재가 올라왔습니다' 알림부터** 붙이세요.
> 그러면 직원이 메신저를 켤 이유가 생깁니다."*
> 사장님: *"히트판ERP내 알림되도록(인스타나페이스북처럼), 팝업형태로 별도 창"*

```
1단계  🔔 결재 알림      ← 상무님 조언. 배관(SignalR)이 이미 있어 가장 쌈
2단계  💬 1:1 · 전체 채팅
3단계  👥 부서방          ← 🔴 부서 축 정리가 선행조건
4단계  📝 채팅창에서 양식 작성 → 결재 상신 (사장님 지시 핵심)
```

**🟢 최대 수확 — SignalR 이 이미 완비돼 있다**
서버·클라이언트·**WebSocket 인증 난제 봉합**까지 종단으로 실재한다(마이그레이션 진행률용).
⇒ 메신저 실시간은 **신규 인프라가 아니라 검증된 패턴 복제**다.

**🔴 그러나 두 가지가 걸린다**
1. **부서가 두 갈래** — 코드는 `dept_id`(마스터)를 읽는데 **실제 데이터는 자유문자 칸에만** 있다.
   마스터 표 0행. ⇒ **지금 부서방을 만들면 방이 0개 생긴다.**
2. **터널 경유 WebSocket 미실측** — 기존 SignalR 은 마이그(수분간 1회)용이라 **상시 연결과 성격이 다르다.**
   장애격리 PRD 에도 *"실측 필요"* 로 남아 있다 ⇒ **네트워크 매니저(마이클) 실측 선행**(헌법 #27)

**🔴🔴 보안 — 두 채팅을 절대 UI 로 합치면 안 된다**
AI 챗봇은 대화를 **외부(클로드·챗GPT·제미나이)로 보낸다.** 사내 메신저는 **회사 안에만** 있어야 한다.
UI 를 합치면 **사내 대화가 실수로 외부에 나가는 경로**가 생긴다(헌법 #18·#22 위반).
⇒ 아이콘·명칭·위치를 설계 단계에서 가른다: AI = 로봇(`SmartToy`, 기존 유지) / 메신저 = 사람·말풍선.

## §5. 🔴 조립 순서 — 무엇부터 해야 다음이 쉬워지나

> 김삼성 상무: *"부품은 다 있다. **조립 순서**를 잡는 분이다."*
> 원칙: **선행조건이 있는 것을 뒤로, 다른 것을 쉽게 만드는 것을 앞으로.**

| 단계 | 무엇 | 왜 이 순서인가 | 비용 |
|---|---|---|---|
| **0** | 🔴 **P0-1 결재선 정본 결정** | 이게 안 정해지면 **보고서·경위서·급여 전부 결재선을 못 짠다.** 모든 흐름의 병목 | **결재 사항** |
| **1** | 숨은 7화면 **메뉴 등재** + 초과근무 3종 분리 | 있는 걸 보이게. 신규요청 3번이 여기서 **거의 끝난다** | 낮음 |
| **2** | 🔔 **결재 알림**(SignalR 로 뱃지 실시간화) | 상무님 조언 1순위. 배관이 이미 있어 최저비용 · **이후 모든 흐름이 살아난다** | 낮음 |
| **3** | **보고서 4종**(일일·주간·월간·경위서) | 토대 최상 — DDL 변경 0, 딕셔너리 4줄 + 화면 | 중 |
| **4** | 🔴 **P0-2 경비 → 회계 연결** + 영수증 첨부 | 신규요청 4·5. ERP 경비에 **검증된 패턴이 있어 복제** | 중 |
| **5** | 🔴 **P0-3 계약서 → 사원 연결** + 연차 자동계산 | 한 몸이다. 입사일이 한 곳으로 모여야 연차·급여가 선다. **법무 교차확인 필수** | 중 |
| **6** | **급여명세서** + 회계 연결 | 5단계가 선행(급여 기준값). **법정 영역 — 상무님·법무팀장 필수** | 높음 |
| **7** | **부서 축 정리** | 메신저 부서방의 선행조건 | 중 |
| **8** | **메신저** 1:1·전체 → 부서방 → 채팅창 양식작성 | 7단계 + 터널 WebSocket 실측 선행 | 높음 |

> ⚠️ **단계 0 은 사장님·상무님 결재 없이 넘어갈 수 없다.**
> 단계 1·2 는 결재선과 무관해 **병행 가능**하다.

## §6. 꼼꼼함 — 놓치면 안 되는 것 (촘촘한 기능)

> 사장님: *"꼼꼼하고 촘촘한 기능으로"*
> 실측에서 나온 **"조용히 틀리는" 결함**들. 500 이 안 나서 더 위험하다.

| # | 무엇 | 지금 상태 | 심각도 |
|---|---|---|---|
| 1 | 근로계약서 **급여가 항상 0원** | API 이름 불일치로 값이 안 들어옴 | 🔴 문서 신뢰도 |
| 2 | **무효화된 전자서명이 "유효"로 표시** | 같은 이름 불일치. 무효 건에 [무효화] 버튼 계속 노출 | 🔴 감사추적(5년 보관 의무) |
| 3 | **"무효화" 버튼이 아무것도 안 함** | 확인창까지 띄우고 스낵바만. 실제 API 는 있는데 안 부름 | 🔴 **"되는 척"** |
| 4 | **신청 사유가 어디서도 안 보임** | DB 엔 저장되는데 조회 SQL·DTO 에 누락 | ⚠️ |
| 5 | **연차 15일 하드코딩** | DB 실값 무시. 전 직원 공통 15일 | 🔴 **법정 기준과 다름** |
| 6 | 휴가 화면 KPI 가 **음수**가 됨 | 전 직원 신청을 모아놓고 개인 기준 15일로 계산 | ⚠️ |
| 7 | **결재선 없는 사원 상신 = 조용히 무시** | 신청자는 올라간 줄 안다 | 🔴 |
| 8 | **초과근무 승인이 결재선을 안 탐** | 문서유형은 정의돼 있는데 트리거 없음 | ⚠️ |
| 9 | **근태↔휴가 상호 인지 0** | 휴가 낸 날이 근태에서 결근 | ⚠️ |
| 10 | HR 계열 **빈 catch** | API 500 과 "데이터 0건"이 화면상 구분 안 됨 | ⚠️ 헌법 #15 |
| 11 | `employees` 참조 **FK 0건** | 고아 행이 DB 차원에서 안 막힘 | ⚠️ |

> 🔴 3번은 어제 AI 연동에서 잡은 *"안 보내면서 성공 반환"* 과 **같은 종류**다.
> **"되는 척하는 버튼"은 없는 버튼보다 나쁘다.** 고객이 됐다고 믿기 때문이다.

## §7. 설계팀 권고 (결재 필요 사항)

### A. P0-1 결재선 정본 — 권고안

**권고: 죽어 있는 쪽(`approval_lines`+`approval_line_steps`)을 정본으로 삼고 엔진에 붙인다.**

| | 근거 |
|---|---|
| 찬성 | 상무님 조언(직급 기반)을 살리는 **유일한 길**. `position_id` 가 거기 있다 |
| 찬성 | 퇴사 시 결재 정지 문제가 구조적으로 해결된다 |
| 반대 | 지금 도는 쪽을 바꾸는 것이라 **회귀 위험**이 있다 |
| 완화 | 기존 표를 **지우지 않는다**(헌법 #1·#37). 사람 지정은 **대결(대리결재)** 용으로 남긴다 |

⛔ **최종 판단은 사장님·상무님.** 설계팀은 근거만 제시한다.

### B. 결재받아야 할 나머지

| # | 안건 | 누가 |
|---|---|---|
| 1 | 결재선 정본(위 A) | 사장님·상무님 |
| 2 | **연차 산정 기준** — 현재 15일 하드코딩이 법정과 다름 | 상무님 + **법무팀장** |

| 5 | 터널 WebSocket 실측 착수 | 네트워크 매니저(마이클) |
