## §1. 스케줄 한눈에

```
P0  현행 봉인 + 실측     ─ ✅ 완료 (2026-08-15)
      ↓
┌─ 1차 ────────────────────────────────────────────┐
│ P1  계수 단일화 (5곳 → 1곳)  ※백오피스 정렬 제외  │
│ P2  기준값 설정화 (enterprise 정정 포함)          │
│ P2.5 🔴 DDL 칸 분리 — 장비넘버 자리를 만든다      │
└──────────────────────────────────────────────────┘
      ↓  검증 통과 후에만
┌─ 2차 ──────────── 🔴 여기서 3증상이 닫힌다 ──────┐
│ P3  열쇠 AND 교체 (장비넘버 + 인증키)             │
│ P4  메인PC 합류 · 옛 기기 승격                    │
│ P5  🔴 중간 화면 — 제어의 중심 (승인 3단 + 알림)  │
│     + 401 걷어내기 + 백오피스 정렬(여기서)        │
└──────────────────────────────────────────────────┘
      ↓
P6  종단 검증           ─ 백지 설치 실측. 게이트 18개 전부
```

**순서를 바꾸면 안 되는 이유**
- **P1·P2 가 1차인 이유** — 계수가 5곳으로 갈리고 한도 값이 흔들리는 채로 열쇠를 바꾸면
  숫자가 틀렸을 때 **어디가 틀렸는지 못 찾는다.** 과금이라 이게 결정적이다
- **P2.5 가 1차인 이유** — 🔴 DDL 에 장비넘버 칸이 없으면 **P3·P4 가 물리적으로 성립하지 않는다**
  (`UNIQUE(tenant_id, fingerprint)` · 지문 칸 하나뿐 — PI-09)
- **P3~P5 를 2차로 묶은 이유** — 셋이 **한 흐름**이다. 열쇠를 바꿔도 화면이 없으면 승인할 길이 없고,
  화면이 있어도 열쇠가 그대로면 여전히 슬롯이 샌다. **따로 내면 둘 다 반쪽이다**
- **백오피스 정렬을 2차로 미룬 이유** — 🔴 PI-12. 모바일 한도(3)가 PC 한도(5)보다 **작아서**
  지금 옮기면 **차단이 빨라진다.** 과다청구를 피하려다 더 아픈 것을 부른다.
  열쇠가 바뀌어 계수가 정확해진 다음에 옮긴다

### 🔷 P2 — 요금 기준값 설정화

#### 왜 하는가
```csharp
"basic" => (5, 3), "pro" => (10, 8), ...   // 코드에 박혀 있다
pcLimit += extra; mobileLimit += extra * 2;
```
🔴 **가격을 바꾸려면 코드를 고쳐 전 고객에게 배포해야 한다.**
헌법 #11 · [[project_pricing_admin_managed]] (*"가격·리워드는 본사 마스터 화면에서, 코드 금지"*) 위반.
🔴 **불변식 I-5 위반 — 지금 깨져 있다.**

#### 무엇을 만드나
| 항목 | 지금 | 바꿀 것 |
|---|---|---|
| 요금제별 기본 슬롯 | `GetLimitsForTier` switch | **설정에서 읽는다** |
| 추가슬롯 산식 | `extra * 2` (모바일 2대) | **설정** — 사장님 확정 **1+1** 로 정정 |
| 추가슬롯 가격 | 코드에 없음 | **설정** — **1만원** |
| 진실원 | ERP switch ↔ 백오피스 `plans` 테이블 (**둘**) | **하나로** |

#### 🔴 확정된 값 (사장님 2026-08-15)
- 추가슬롯 = **1만원 / PC 1대 + 모바일 1대**
- ⚠️ **현행은 PC 1 + 모바일 2** 다. 사장님 확정과 **다르다** → 1+1 로 고친다

#### ⚠️ 이 단계에서 확정하지 않는 것
**기본 제공 슬롯 수.** 코드의 `(5,3)`·`(10,8)` 은 근거가 없다.
**설정에서 읽는 구조만 만들고, 실제 숫자는 사장님이 나중에 넣으신다**(명세서 §10-5).

#### 완료 기준
- [ ] 요금 기준값이 **코드 리터럴에 없다** (게이트 **G-8**)
- [ ] ERP 와 백오피스가 **같은 값**을 본다 (이중 진실원 해소)
- [ ] 값을 바꾸는 데 **코드 배포가 필요 없다**
- [ ] 조정 이력이 남는다 ([[feedback_semi_auto_principle]] — 반자동 원칙)

#### 위험
⚠️ 헌법 #21 — `appsettings.json` 은 건드리지 않는다. 설정 저장 위치를 별도로 정한다.
⚠️ 본사↔ERP 전달 경로(`WebhookInboundController`)가 이미 있다. **새로 만들지 말고 그 길을 쓴다.**

### 🔷 P2.5 — 🔴 DDL 칸 분리 (1차 · [3-V] PI-09 로 신설)

#### 왜 하는가
현행 `tenant_devices` 는 `UNIQUE(tenant_id, fingerprint)` + `fingerprint NOT NULL`.
🔴 **지문 칸이 하나뿐이라 `MAINPC-` 와 브라우저 접속을 한 줄에 담을 자리가 없다.**
⇒ **P3·P4 가 물리적으로 성립하지 않는다.** 1차 초안이 DDL 을 아예 언급하지 않아 병렬검증이 P0 로 적발했다.

#### 무엇을 만드나
- 서버가 읽는 **하드웨어 식별값 컬럼** 추가 (메인PC 용)
- `fingerprint` 는 **옛 기기 호환 전용**으로 남긴다 — 새 조회 경로에서는 3순위
- UNIQUE 제약 재설계 — 한 줄이 장비넘버와 지문을 **동시에** 가질 수 있게

#### 헌법
- **#36** 출하 DDL(`hitpan_db_clean.sql`) 편입 — 신규 설치 단일 진실원
- **#13** 새 SQL 전 `DESCRIBE tenant_devices` 선행
- **#17** 신규 테이블이면 `ENGINE=InnoDB` 명시
- 🔴 마이그레이션은 **`src/HitPan.API/Migrations/SQL/DB-NN_*.sql` 에만** ([[project_migration_real_path]])
  → 다른 자리에 두면 **배포본에 안 실려 고객 화면이 죽는다**(8/12 실사고)

#### 완료 기준
- [ ] `DESCRIBE` 결과가 설계와 일치
- [ ] clean DDL 편입 + `ddl-smoke` 통과
- [ ] 마이그레이션 파일이 **올바른 경로**에 있다 (`MigrationLocationGuardTests`)
- [ ] 기존 데이터가 깨지지 않는다 (실사용 고객 0 이지만 demo·테스트 데이터 보존)

#### 위험
⚠️ **UNIQUE 제약 변경은 되돌리기 어렵다.** 변경 전 백업 필수.
⚠️ 헌법 #37 — *"안 읽힌다 ≠ 잔재"*. **기존 컬럼을 지우지 않는다.** 추가만 한다(#1).

### 🔷 P3 — 🔴 장비넘버 열쇠화 (이 설계의 본체)

#### 왜 하는가
> 사장님: *"기기슬롯 인증을 하면 그 기기는 **100번을 접속해도 한번만** 그 기기를 잡아야해"*

장비넘버는 **이미 있고, 이미 발급되고, 이미 기기에 저장된다.**
🔴 **그런데 로그인할 때 아무도 그것을 보내지 않는다**(명세서 §2-2). 호출처 **0곳**.
🔴 **불변식 I-1 위반 — 지금 깨져 있다.**

#### 무엇을 만드나

**① 로그인이 장비넘버를 보낸다**
```
LoginRequest  ← DeviceId · AuthKey 필드 추가
AuthService   ← getDeviceId() · getAuthKey() 호출해서 함께 전송
```
함수는 이미 있다(`device-fingerprint.js:234,253`). **부르는 쪽만 없다.**

**② 찾는 순서를 뒤집는다** (명세서 §4-3)
| 순서 | 열쇠 | 잡히는 기기 |
|---|---|---|
| ① | **장비넘버 + 인증키** | 인증받은 기기 — **백 번 와도 이 줄** |
| ② | **장비넘버** 단독 | 인증 전 기기 |
| ③ | 지문 | 옛 기기 — **호환 전용** |
| ④ | 없음 | **그때만** 새 슬롯 |

#### 완료 기준
- [ ] 🔴 **같은 장비넘버로 100회 로그인 → 1줄** (게이트 **G-1** · 사장님 원문)
- [ ] 다른 브라우저 3종 → 1줄 (**G-2**)
- [ ] 다른 주소(도메인/localhost) → 1줄 (**G-3**)
- [ ] 계정 3개가 같은 기기로 → **1줄 · 슬롯 1개** (**G-5** · 사장님 그림)
- [ ] 폐기 → 슬롯 즉시 반환 (**G-6** · I-3)
- [ ] 한도 경계 — 정확히 한도에서 막히고 한 대 아래에서 통과 (**G-10**)

#### 위험
🔴 **여기가 가장 위험하다.** 조회 순서를 잘못 짜면 **모든 기기가 한 줄로 합쳐지거나**(과소 계수),
**아무것도 안 걸려 매번 새 줄**(과다 계수)이 된다. 둘 다 과금 사고다.
⚠️ 장비넘버는 localStorage 에 있어 **지울 수 있다.** 지워지면 ③ 지문 경로로 떨어지게 설계한다 — 새 줄이 아니라.
⚠️ 헌법 #2 — 기기 조회에 `tenant_id` 를 **파라미터로 받지 않는다.** JWT 클레임에서만.

### 🔷 P4 — 메인PC 합류 + 옛 기기 재매핑

#### 왜 하는가
**메인PC 2슬롯 사고**(사장님 실측)의 봉합이다.
`MAINPC-…` 와 `HFPv2-…` 는 접두어부터 달라 **서로를 절대 못 찾는다**(명세서 §2-3).

#### 무엇을 만드나

**① 메인PC 가 자기 장비넘버를 브라우저에 내려준다** (명세서 §4-5)
메인PC 는 서버와 브라우저가 **같은 PC** 에 있다. 서버가 자기 장비넘버를 화면에 내려주면
브라우저가 저장하고, 다음부터 그 값으로 조회된다 → **`MAINPC-` 행에 붙는다.**

**② 옛 기기 승격** (명세서 §7)
지문으로 걸린 옛 기기는 **그 자리에서 장비넘버를 발급해 붙인다.** 새 줄을 만들지 않는다.

**③ 메인PC 하드웨어 재료 결정** (명세서 §10-2)
현행 `MachineName` 은 **사용자가 바꿀 수 있다.** 후보(메인보드 UUID · 디스크 일련번호 등)를
**실측 비교**해 근거를 만든 뒤 결정한다. 🔴 **짐작으로 고르지 않는다.**
⚠️ 여러 값을 묶어 **하나가 바뀌어도 견디게** 한다.

#### 완료 기준
- [ ] 🔴 메인PC 자동등록 + **그 PC에서 브라우저 접속 → 1줄** (게이트 **G-4**)

### 🔷 P5 — 🔴 중간 화면 = 제어의 중심 (2차 · 전면 개정)

> 사장님: *"**로그인과 히트판ERP 사이에 화면을 넣고 그 화면으로 제어**를 하는게 가장 자연스러울듯"*
> *"401로 가지 않게"* / *"중간 화면에서 **인증키 등록을 하는 장치**가 되는거지"*
> 상세 흐름 → 명세서 **§14** (참조식)

#### 왜 하는가
기기 판정이 **세 군데로 흩어져** 있다 — 로그인 401 · 미들웨어 403 · 레이아웃 안 화면.
셋이 각자 판단하니 흐름이 안 맞는다. **한 곳으로 모은다.**

#### 무엇을 만드나

**① 중간 화면 (명세서 §14-2 흐름)**
승인됨 → 지나감 / 미승인 → 요청 Y·N / 대기 중 → 승인 알림 대기 /
🔴 승인됨·인증키 없음 → **여기서 번호 입력·저장** / 거부됨 → 안내 후 **다시 처음으로**

**② 401 걷어내기** — `AuthController.cs:101-105`
🔴 **흐름을 막는 단 하나의 자리.** 로그인은 정상으로 끝내고 기기 상태만 실어 보낸다.
⚠️ 보안을 무르게 하는 것이 아니다 — `DeviceAuthMiddleware` 가 `/api/*` 를 그대로 막는다.
**문은 열리되 방에는 못 들어간다.**

**③ 승인 요청 알림** — 기존 SignalR 배관 재사용 (명세서 §14-4)
새로 만들 것은 **둘뿐**: 대표 `employee_id` 조회 한 줄 + `INotificationService` 주입.

**④ 슬롯 초과 시 구매 경로**
대표 화면에서 *"슬롯기기 구독을 하시겠습니까?"* → Y 면 **랜딩페이지로 이동**.
🔴 막는 것이 목적이 아니라 **파는 것**이 목적이다.

**⑤ 백오피스 "싼 칸" 정렬** — 1차에서 미룬 것을 여기서 (PI-12)

#### 완료 기준
- [ ] **G-14** 대표 수락 없이 `approved` 가 되지 않는다
- [ ] **G-15** 슬롯 초과 상태에서 승인이 통과하지 않는다
- [ ] **G-17** 거부 후 재요청이 슬롯을 두 번 먹지 않는다
- [ ] 미승인 기기가 **401 을 맞지 않는다** — 토큰을 받고 화면에 도달한다
- [ ] 승인 알림이 **대표에게만** 간다 (다른 직원에게 안 감)
- [ ] 승인되면 클라이언트 화면이 **자동 전환**된다 (SignalR 수신)
- [ ] **F-1** 처음 보는 직원이 물어보지 않고 넘어간다 (CLAUDE.md 최종 통과 기준)
- [ ] **F-2** 개발용어·영어 0 (*"인증키"·"디바이스"* 금지)
- [ ] **F-3** 번호를 어디서 받는지 화면이 알려준다 (헌법 #24)
- [ ] **F-4** 슬롯 초과면 그렇다고 말하고 **구매 경로**를 준다
- [ ] **F-5** 이 단계가 **처음 한 번뿐**임을 알 수 있다 (승인은 영구 — 명세서 §15)

#### 하지 않는 것 (사장님 판정 — 명세서 §18)
- ❌ 대표 부재 시 대기 처리 — *"업체가 고민할 일"*
- ❌ 반복 요청 차단 — *"막을시 그게 더 불편"*
- ❌ 인증번호를 알림에 실어 보내기 — 옆에서 보면 새어나간다. **사람이 전달한다**

#### 위험
⚠️ **판정은 사장님이 하신다.** 수석 웹디자이너 목업 → 결재 → 구현.
⚠️ 로그인 흐름을 건드리므로 **기존 로그인 회귀**를 함께 시험한다.
🔴 **되돌리기 쉽게 만든다** — 이 화면이 통과만 시키면 지금과 똑같이 동작해야 한다.
문제가 나면 화면에서 판단을 끈다. **서비스 로직을 헤집지 않는다.**
