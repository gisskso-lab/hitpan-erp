## §2 [주체] 되돌림 일꾼 — 누가 [예]를 받고 누가 실행하나

```
메인PC 화면 [예] ─▶ API(N+1 · 살아 있음)  ─▶ ① 전제 P-a~P-f 재판정(화면 값 불신)
                                         ② request.json 쓰기(%ProgramData%\HitPan\rollback\)
                                         ③ 스크립트를 run\ 로 복사(api 폴더는 곧 바뀐다)
                                         ④ 1회용 SYSTEM 작업 HitPan-LocalRollback 등록·실행 → 202
                   되돌림 일꾼(스크립트) ─▶ §4 순서 — 워치독 서비스는 **멈출 대상**일 뿐 주체가 아니다
```
- **왜 API 인가**: 전제 상황에서 살아 있는 것은 ⓐ화면·ⓑAPI 다(고장은 ⓒ). API 는 SYSTEM 예약작업으로 돈다(선행 P4) ⇒ SYSTEM 작업을 걸 수 있다. 자기 폴더는 못 바꾸므로 **밖의 작업**이 한다 — 워치독 자기교체(`UpdateOrchestrator.cs:1149-1323`)와 같은 모양, 단 **워치독이 아니라 API 가 건다.**
- **[예] 는 동의 표에 안 쓴다**: `local_update_consents` 는 워치독이 소비하는 표 ⇒ 쓰면 고장 난 소비 경로와 섞인다. [예] 의 기록 = `request.json`(요청자 사용자 id · 시각 · from/to · 재료 경로 · 1회용 번호) + 스크립트 로그 + 이벤트로그(원천 `HitPanWatchdog` · 새 EventId 대역 28040~ · 새 원천 등록 = 레지스트리라 안 만든다).
- **1회용 번호**: 작업 명령줄과 `request.json` 에 같은 번호 — 다르면 스크립트 즉시 종료(묵은 요청·손으로 돌린 스크립트 거부 ⇒ 「사람 손 수술」 통로가 되지 않는다).
- **폴더 권한**: `%ProgramData%\HitPan\rollback\` 은 SYSTEM·Administrators 만 쓰기(일반 사용자 쓰기 0) — 요청 파일 바꿔치기 차단.
- **슬롯 번호**: API 가 `TenantConfigReader.Get("SLOT_INDEX")`(`MainPcRegistrationService.cs:305` 와 같은 출처)로 읽어 `request.json` 에 싣는다 ⇒ 스크립트는 `db.conf` 를 **열지 않는다.**
- **익명 금지**(⬛「로그인창 버튼」 부분만 §13-4 로 대체 — 버튼은 생기되 익명 API 는 여전히 0): `[AllowAnonymous]` 변형·로그인창 버튼·`TenantMiddleware` 화이트리스트 추가 **0**(병렬이슈 03 — 로그인창 승인이 메인PC 판단을 뒤집은 전례).

## §3 [재료] 옛 프로그램은 어디서

**3-1 순위**: ① `{app}\rollback\prev\{api,web,watchdog}` + `version.txt` + `sha256.txt` → ② SYSTEM 프로필 `…\HitPan\Updates\staging\hitpan-{V}.zip`(API 도 SYSTEM ⇒ 같은 경로 · ⚠️U-2) → ③ 없음 = 버튼 비활성 「되돌릴 이전 버전이 이 컴퓨터에 없습니다」 ⇒ 작3 탈출 §4 J-3(사장님 판단).

**3-2 보존(갈래 W) — 성공 뒤 지우던 것을 옮긴다**
| 지금 | 바꾼 뒤 |
|---|---|
| `CleanupAfterSuccess` 가 `api.old`·`web.old` 삭제(`UpdateOrchestrator.cs:1094-1095`) | `rollback\prev\` 로 **이동**(같은 볼륨 = 복사 0). 이동 전 `prev` 를 비운다 = **1세대만** |
| 자기교체 스크립트가 성공 시 `watchdog.old` 삭제(`:1320`) | `rollback\prev\watchdog` 로 이동 · 이어서 `version.txt`(옛 판 번호)·`sha256.txt`(세 벌 파일 해시) 기록 |
- 🔴 **효력 시점**: 보존 코드는 **그 판의 워치독이 다음 판을 적용할 때** 돈다. N+1 을 적용하는 것은 1.3.48 워치독(삭제하는 옛 코드) ⇒ **N+1→1.3.48 에는 효과 0.** N+1 워치독이 N+2 를 적용할 때부터 생긴다.
- 보존 실패는 적용 성공을 뒤집지 않는다(종전 best-effort 원칙 그대로 · 로그만).
- 디스크: 상시 +1세대(개발 PC 기준 ≈200MB ⚠️). 이동이라 교체 순간 추가 사용 0.
- 곁: `staging\*.zip`·`pre-update-backup\*.sql` 누적(선행 §1 곁 발견)은 **이 트랙에서 안 건드린다**(zip 은 이 트랙의 재료 · 정리 정책은 별건).

**3-3 「바로 앞 판」 판정** — 여러 판 건너뛰기를 막는 유일한 문
- ①: `prev\version.txt` 가 곧 바로 앞 판(보존은 직전 교체에서만 생긴다).
- ②: staging zip 중 **현재보다 낮은 최고 판** V 이고, 업데이트 이력(`local_update_apply_status` **읽기만** · 칸은 [3] 착수 시 `DESCRIBE` #13)에 「V 성공 → 현재 성공」이 **이어서** 있을 때만. 이력이 V 를 못 보여 주면(설치 EXE 로 깐 V · 이력 끊김) **거부.**
- 설치본으로 깐 판은 zip 이 없다 ⇒ 그 판으로는 못 돌아간다(선행 P3). N+1 에서 이 경우가 사장님 PC 면 R-2.

**3-4 재료 검사(스크립트 S1)**: 세 벌 폴더 존재 · `HitPan.API.dll`·`HitPan.Web` 주 dll·`HitPan.Watchdog.exe` FileVersion = 대상 판 · ① 은 `sha256.txt` 대조 · ② 는 zip 해제 성공 + FileVersion(다운로드 때 해시는 PC 에 남지 않는다 — 선행 P3-2 · 한계로 기록).

## §4 [순서] 세 벌 되돌림 · 재시작 · 실패 처리

스크립트 `local-rollback.ps1` — **ASCII 만**(PS 5.1 한글 깨짐 전례) · `$ErrorActionPreference='Stop'` · 모든 단계 로그.

| 단계 | 하는 일 | 실패 시 |
|---|---|---|

| S2 | 부팅 복원 안전망 — `HitPan-ERP-keepalive-restore` 존재 확인, 없으면 `UpdateProcessGate` 와 **같은 이름·같은 동작**으로 등록 후 `/Query` 확인 | `refused` · 아무것도 안 멈춤 |

| S4 | 교체 — 세 벌 각각 `X → X.rbk` 이름 바꿈 → `stage\X → X` 이동. **목적지를 먼저 비운 뒤 옮긴다**(A-1 중첩 전례 `:1123-1125`) | S7 |

| 성공 | `X.rbk`(N+1)·`stage` 삭제 · S2 에서 **새로 만든** 안전망만 삭제 · 상태 `success` · 이벤트로그 | — |
| S7 | 원위치 — 다시 정지(S3) → `X.rbk → X` 복귀(목적지 선비움) → S5 → `version` = from 확인 → 상태 `reverted` | 복귀도 실패 = `broken` · 이벤트로그 Error · keepalive 는 S2 안전망이 부팅 때 되살린다 ⇒ 작3 §4 J-4 |

- **순서 이유**: S1·S2 는 아무것도 멈추기 **전** — 실패해도 ERP 는 그대로 돈다(바닥 없이 떨어지지 않는다 · `UpdateProcessGate` 0번 원칙과 같다). 워치독을 **먼저** 멈춘다 — 고장 난 워치독이 교체 중 끼어들지 않게.
- **K-2 · #29**: 서비스·예약작업 조작은 사장님 9/30 「서비스도 재시작」 사전 승인 범위. MariaDB·cloudflared·방화벽·레지스트리 **무접촉**(`UpdateProcessGate.cs:29-30` 과 같은 경계).
- **고객 PC 파일 수술 금지와의 관계**: 금지 대상은 **사람(팀·사장님)이 손으로** `Program Files` 를 옮기는 일이다. 이 경로는 **고객이 제품 안에서 누른 [예]로 제품이 하는 동작**이다(업데이트 교체와 같은 성질). ⇒ 팀은 스크립트를 손으로 돌리지 않는다 · 1회용 번호가 손 실행을 거부한다(§2).
- 화면: 202 뒤 「되돌리는 중 — 약 5분 뒤 다시 로그인해 주세요」 · API 가 곧 멈추므로 결과는 **재로그인 후** 사이드바 한 줄로 알린다(API 가 기동 때 `request.json` 결과를 읽음 — 1.3.48 판은 이 코드가 없다 ⇒ 1.3.48 로 되돌린 성공은 「버전 줄이 1.3.48」 로만 보인다 · ⚠️ R-1 과 함께 확인).

## §5 [불변] 고객 데이터를 절대 안 건드린다는 보장

**5-1 구조** — 되돌림 경로에 DB 에 닿는 부품이 **없다.**
- 컨트롤러·서비스(갈래 A)는 DB 연결을 **주입받지 않는다**(생성자 인자에 `IDbConnection`·`DbContext`·Dapper 저장소 0). 전제 P-b 의 이슈 판정·P-c 이력은 **기존 읽기 서비스 호출**로 받는다(SELECT 만 · 새 SQL 0).
- 스크립트는 `mariadb`·`mysql`·`mysqldump`·`db.conf`·`.sql`·`pre-update-backup`·MariaDB 데이터 폴더를 **글자로도** 가지지 않는다.

- 선행 P1: 지금 자동 롤백도 DB 복원 0(결재 #3 `UpdateOrchestrator.cs:873-874`) — 같은 원칙을 새 경로로 넓힐 뿐.

**13-2 [구조] 워치독과 독립된 수동 모듈 — 기존은 안 뜯는다**
```
[자동] 로그인 팝업 → update-consent → 워치독 한 루프(동의 소비·백업·교체·검증·자동 롤백)      ← diff 0
[수동] 자료관리 메뉴 / 로그인창 버튼(관리자 로그인 뒤)
   → API 수동 모듈 (워치독 프로세스 실행 0 · 동의 표 0)
       업데이트: 피드 확인·서명·다운로드·해시 → 자료 백업   |   되돌리기: 재료 판정(§3)
   → request.json(mode=update|rollback) → 1회용 SYSTEM 작업 HitPan-LocalSwap
   → 교체 일꾼 local-swap.ps1 -Mode … : §4 S0~S7 그대로 · 워치독은 「멈출 대상」 · 실패 시 원위치
```
- **한 틀 공유(채택 권고)**: §2·§4 「되돌림 일꾼」을 **교체 일꾼**으로 넓혀 두 모드가 같은 스크립트·작업 이름·`request.json` 을 쓴다. 이유 ① 작업 이름 하나 = 두 수동 동작이 겹치지 않는 자물쇠(P-f) ② 정지·교체·원위치(S3~S7) 한 벌 — 복붙 0 ③ G-S1~S3 가 두 모드를 함께 잰다. 모드 차이는 두 곳뿐: **S1 재료**(update = zip 해시를 `request.json` 값과 다시 대조 → 해제 → FileVersion = to / rollback = §3) · **성공 정리**(update = 옛 세 벌 `.rbk` → `rollback\prev\` 1세대 보존 + `version.txt`·`sha256.txt` · zip 삭제 / rollback = `.rbk` 삭제).
- **다운로드·서명 재사용 = 링크 컴파일**: 워치독 원본 `UpdateChannel.cs`·`UpdateManifestSigning.cs`·`UpdateSignatureVerifier.cs`·`UpdateClient.cs`(`GetLatestManifestAsync` 안에서 서명검증 `:90` · `IsNewerVersion :137` · `DownloadAsync :205` · `VerifySha256Async :224`)·`UpdateDiskSpaceGuard.cs`·`DbConfReader.cs` 를 API csproj 에 `<Compile Include=… Link=…>` 로 넣는다 — **파일 복사 0 · 워치독 파일·csproj 수정 0**. 공용 라이브러리로 **옮기지 않는다**(= 워치독을 뜯는 일). ⚠️ API 에서 그대로 빌드되는지(워치독은 `ProjectReference` 0 · `net8.0-windows`) [3] 첫 행동 U-8.
- **백업**: API 의 기존 `IBackupService`(자료관리 「자료 백업·복구」와 같은 기능)로 교체 **전** 백업 · 실패 = 작업 등록 0(업데이트 백업 원칙 「백업 실패 시 업데이트 차단」 그대로). 백업이 API 쪽이라 일꾼은 두 모드 모두 **DB 글자 0**(G-D1 유지). 되돌리기는 백업·DB 둘 다 0(§5).
- **받는 폴더** `%ProgramData%\HitPan\manual\staging\` — 워치독 staging 과 따로(서로의 정리가 안 닿는다).
- **자동과의 경합**: API 판정(P-d) ~ S3 정지 사이에 워치독이 자동 적용을 시작하는 틈 ⇒ S0 이 워치독의 `UpdateLockFile` 을 **먼저 잡는다**(워치독 코드 무변경 · 그 잠금 규칙을 따를 뿐) ⚠️ 묵은 잠금 판정 규칙 U-9.
- **효력 시점**: 메뉴·로그인창 동작·일꾼은 **N+1 부터** 있다. 1.3.48 로 되돌린 PC 에는 없다 ⇒ 그 PC 는 자동(옛 워치독 팝업)만.

|---|---|---|---|---|
| 워치독 서비스 정지 | ❌ 적용 주체 없음 | ✅ 워치독은 멈출 대상 · S5 가 새 판 워치독을 켠다 | ✅ | ✅ |
| 워치독 동의 소비 결함(9/30 ⓒ) | ❌ | ✅ 동의 표 안 씀 | ✅ | ✅ (L-1 (나)면 ❌) |
| API 불능 | ❌ 팝업·동의 입구가 API | ❌ | ❌ | ❌ ⇒ 전부 워치독 자동복구·작3 §4 J-4 영역 |
| 피드 불능(`updates.hitpan.kr`) | ❌ | ❌ 같은 피드 — 불가피 | ✅ PC 안 재료 | ❌ |

- **요약**: 자동 **고유** 고장(워치독 정지·동의 소비)은 수동이 산다 = 사장님 「자동이 막혀도 수동」 목적 충족. 피드·디스크·서명은 수동 업데이트도 같이 막힌다(바깥 재료·보안 문) ⇒ 그때가 **수동 되돌리기** 차례(§9 단계 ③). API 불능은 세 경로 모두 못 산다(화면이 없다).
- 코드 차원 공유: 링크 파일에 버그가 나면 자동·수동 업데이트가 함께 깨진다(보안 검증을 한 벌로 두는 대가) — 수동 되돌리기는 이 파일들을 안 쓴다.

**13-4 [입구] 재배치**
- **자료관리**: `Sidebar.razor` 자료관리 그룹(`:325-333`)에 링크 2줄 **추가** · 새 화면 `/data/update`·`/data/rollback`. 문 = 컨트롤러 `[Authorize(Policy="TenantAdminOnly")]` + `[MainPcOnly]`(`BackupController.cs:16·:23` 과 같은 두 줄). 메뉴 숨김은 편의 · 막는 것은 서버.
