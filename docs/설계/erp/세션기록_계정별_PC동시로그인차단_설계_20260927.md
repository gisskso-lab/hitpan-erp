## 0. D-1 판정 (사장님 전결 2026-09-27)

> **기존 「테넌트 총량 동시세션 제한」을 살릴 것인가 버릴 것인가**

### 🟢 판정: **살린다. 버리지 않는다.**

| 근거 | 내용 |
|---|---|
| #1 | 수정은 OK, **삭제·덮어쓰기 금지**. 기존 코드는 추가만 한다 |
| #37 정신 | *"안 읽힌다 ≠ 잔재"* — 안 도는 것과 필요 없는 것은 다르다 |
| 실무 | **새 기능이 세션 행을 어차피 만든다.** 행이 생기면 기존 제한은 **공짜로 되살아난다** — 따로 살릴 일이 없다 |
| 역할 | 둘은 **다른 축의 다른 안전장치**다. 하나가 다른 하나를 대신하지 못한다 (선행검증 §4) |

### 🔴 그런데 이 판정이 곧 이번 설계 최대 위험이다

세션을 넣기 시작하는 순간, **한 번도 돈 적 없는 테넌트 총량 제한이 소리 없이 켜진다.**
한도를 넘는 고객은 그날부터 **429 를 맞는다.** 아무도 그 코드가 실제로 도는 걸 본 적이 없다.

⇒ **§4 안전장치(킬스위치 + 점등 전 실측)를 이 설계의 필수 구성으로 둔다.**
⇒ 이 위험을 안 달고 세션 INSERT 만 넣는 작업지시서는 **반려 사유**다.

## 1. 무엇을 만드나 — 한 줄

**로그인·갱신 때 세션 행을 남기고**(지금 0건), 그 위에서 **같은 계정의 PC 동시 로그인을 막는다.**
모바일은 FREE 이므로 세지 않는다.

## 2. 두 축을 섞지 않는다

| | 축 A — 기존 (살림) | 축 B — 신설 |
|---|---|---|
| 세는 단위 | 테넌트 안 **서로 다른 사용자 수** | **한 계정**이 동시에 붙은 **PC 수** |
| 판정식 | `COUNT(DISTINCT user_id) … tenant_id=?` | `COUNT(*) … user_id=? AND device_kind='pc'` |
| 한도 | `SlotPolicyDefaults` (기기한도×1.5, 바닥 8/20/…) | **1** (같은 계정 PC 1대) |
| 자리 | `SessionLimitMiddleware` (**무접촉**) | 로그인·갱신 2곳 + **신설 미들웨어**(§4-6) |
| 막는 법 | 429 | 로그인 **거절** + 사용자 확정 밀어내기 (§4-4) |

🔴 **축 B 를 `SessionLimitMiddleware` 안에 넣지 않는다.** 축 A 의 식과 뒤엉키면
이번 트랙이 고치려는 혼선을 그대로 재생산한다.
⇒ 즉시 차단이 필요해 요청 경로를 타야 하지만(§4-6 갈래 나), **기존 미들웨어를 고치는 게 아니라
`SessionValidityMiddleware` 를 새로 추가한다** (#1 — 추가만).

### 3-1. `device_kind` — 왜 컬럼을 새로 만드나

`user_sessions` 에 `user_agent VARCHAR(500)` 이 이미 있다. 그런데 **UA 문자열 추론으로 모바일을 가르지 않는다**:

- UA 는 사용자가 바꿀 수 있다 ⇒ **FREE 인 모바일로 위장하면 과금이 뚫린다**
- UA 규칙은 브라우저 개편마다 깨진다 ⇒ 조용히 오판정
- 메인PC 트랙에서 이미 겪었다 — **브라우저가 말해주는 것에 정책을 얹으면 안 된다**

⇒ `device_kind ENUM('pc','mobile') NOT NULL DEFAULT 'mobile'` 를 **서버가 판정해 적는다.**
UA 는 **사람이 읽는 기록**으로 남기되, 신고값 단독 판정은 하지 않고 **서버가 읽은 UA 로 교차검증**한다
(8/18 V-05 · 판정 자리 하나 = `HitPan.Application/Common/DeviceTypeResolver.cs`).

🟢 **기본값은 `'mobile'` 이다 — 「모르는 것은 싼 칸으로」** (2026-09-27 작2 §7 로 정정)

⬛ **낡은 줄** — ~~`DEFAULT 'pc'`~~ / ~~*"🔴 기본값이 `'pc'` 인 이유: 모르면 과금되는 쪽으로 떨어뜨린다.
반대로 두면 판정 실패가 곧 매출 누수다."*~~

🔴 왜 뒤집혔나 — 히트판에는 이미 판정이 끝난 원칙이 있다:

- **"모르는 것은 싼 칸으로"** — 모르는 값 → `mobile` (20260815 아키텍처명세서 §3 #4 *"ERP 가 맞다"* 로 판정 완료 · 백오피스가 ERP 규칙에 맞춰졌다: `DeviceRegistrationController.cs:89-96`)
- 근거가 된 **실제 사고**: 백오피스가 모르는 값을 `'pc'` 로 보내 **고객이 쓰지도 않은 비싼 자리에 돈을 냈다.** `?? "pc"` 폴백도 같은 이유로 걷어냈다 (20260815작3 P1 I-6 · `AuthController.cs:99-111`)
- **8/16 CR2-2 최종 판정**: *"이 폴백은 결함이 아니다"* ⇒ `'pc'` 로 되돌리면 **P0**
- 차단 축에서도 `mobile` = 「안 막힘」 = 고객에게 유리한 쪽이라 **방향이 같다**. 규칙을 두 개 만들지 않는다.

⚠️ 남는 한계는 숨기지 않는다 — 신고값을 안 보내는 클라이언트는 `mobile` 로 떨어져 축 B 차단을 안 받는다.
UA 교차검증이 그 폭을 좁히지만 **위조를 막은 것은 아니다.** ⇒ 매출 누수가 아니라 **차단 누락**이고, 게이트 G-3·G-B1·G-B11 이 그 값을 지킨다.
근거 주소: [`DB-127_user_sessions_device_kind.sql`](../../../src/HitPan.API/Migrations/SQL/DB-127_user_sessions_device_kind.sql) 머리말 *"왜 기본값이 'mobile' 인가"* · [`20260927작2_축B봉합_작업지시서.md`](../../운영기록/20260927작2_축B봉합_작업지시서.md) §7 · [`축B봉합_기기종류판정_서버판정복귀_설계_20260927.md`](축B봉합_기기종류판정_서버판정복귀_설계_20260927.md) §7

## 4. 🔴 안전장치 — 없으면 이 설계는 반려다

### 4-1. 킬스위치

축 A·축 B 각각 **설정 한 줄로 끌 수 있어야 한다**(`tenant_settings` 또는 `appsettings` — ⚠️ #21 로 `appsettings.json` 은 못 건드리니 **DB 설정값**으로 간다).

고객 화면에서 사고가 나면 **배포 없이** 꺼야 한다. 게시 1회에 372MB·수십 분이다.

### 4-2. 점등 전 실측 — 축 A 를 켜기 전에 반드시

```sql
-- 테넌트별 "동시에 붙을 수 있는 사용자 수" 상한 추정
SELECT tenant_id, COUNT(*) AS active_users
  FROM users WHERE is_active = 1 GROUP BY tenant_id ORDER BY 2 DESC LIMIT 20;
```

이 값이 축 A 한도(basic **8** / pro **20** / default **50**)를 **넘는 테넌트가 하나라도 있으면**,
세션 INSERT 를 켜는 순간 그 고객은 **429** 다.

| 결과 | 조치 |
|---|---|
| 전부 한도 미만 | 🟢 축 A 그대로 켠다 |
| 넘는 테넌트 있음 | 🔴 **켜지 않는다** — 한도 조정 결재 먼저 |

⚠️ **PM 은 이 값을 못 쟀다** — `hitpan` GRANT 가 4개 DB 에만 걸려 있어 실물 DB 에 못 닿는다
(선행검증 §6). **[3] 착수 전 사장님 1회 측정이 필요하다.**

### 4-3. 실패해도 조용한 구조를 물려받지 않는다

기존 미들웨어의 `catch` 는 예외를 삼키고 통과시킨다(가용성 우선). 그래서 **아무도 안 도는 걸 몰랐다.**
신설 코드는 다르게 간다:

- 축 B 판정 실패 시 → **로그인은 통과**(가용성) + `LogError` + **`security_alerts` 에 행을 남긴다**
- 즉 **눈에 보이는 흔적**을 남긴다. 로그만으로는 또 못 본다

## 4-4. 🟢 A-1 전결 판정 (사장님 전결 2026-09-27)

> **같은 계정 2번째 PC 로그인 — 거절인가 밀어내기인가**

### 🟢 판정: **거절이 기본. 밀어내기는 사용자가 확정할 때만.**

```
2번째 PC 로그인 시도
   → 거절 + "이미 다른 PC에서 사용 중입니다 (마지막 사용: HH:mm)"
   → [그 PC 접속을 끊고 여기서 사용하기] 버튼
   → 사용자가 누르면 → 기존 세션 끊고 로그인
```

| 근거 | 내용 |
|---|---|
| **반자동 원칙** | *"100% 자동화 없음 — 제안값 → 수정 → 확정"*. 자동 밀어내기는 사용자가 확정한 적 없는 동작이다 |
| **ERP 는 입력 중심이다** | 넷플릭스식 자동 밀어내기는 **보는** 서비스라 괜찮다. 히트판은 **입력하는** 서비스다. 전표 쓰던 화면이 예고 없이 튕기면 **입력이 날아간다** |
| **히트판 정신** | *"처음 보는 사람이 혼자 쓸 수 있냐"*. 거절은 원인이 화면에 보인다. 튕김은 원인을 짐작할 수 없다 |
| **CS** | *"왜 안 되지"* 는 화면이 답한다. *"왜 갑자기 튕겼지"* 는 전화가 온다 |

### 🔴 이 판정이 만드는 위험 — 반드시 같이 푼다

**거절만 두면 영영 못 들어가는 경우가 생긴다.** PC 가 꺼지거나 브라우저를 그냥 닫으면 로그아웃 `DELETE` 가 안 돈다 ⇒ 죽은 세션이 남아 본인 계정을 스스로 잠근다.

⇒ **밀어내기 버튼은 선택이 아니라 필수 구성이다.** (자동이 아니라 **사용자 확정**이라는 점이 A-1 의 핵심)
⇒ 추가로 `expires_at` 만료로도 풀린다 — 만료 시간은 절C 에서 정한다.

## 4-5. 🟢 B-2 차단 해소 — 축 A 킬스위치 **기본 OFF** 로 출발한다

B-2(테넌트별 활성 사용자 수 측정)는 **PM 이 못 잰다**(GRANT 밖). 이것 때문에 [3] 이 멈추지 않도록 설계를 바꾼다:

| | 값 |
|---|---|
| 축 A (테넌트 총량 제한) | **기본 OFF** 로 출하 |
| 축 B (계정별 PC 동시) | 기본 ON |

⇒ 세션 INSERT 를 켜도 **축 A 는 안 켜진다** ⇒ **429 위험 0** ⇒ B-2 없이 [3] 착수 가능.
⇒ B-2 측정은 **축 A 를 켜는 날**에만 필요하다. 그날까지 미룬다.

> 🔴 **"있는데 꺼져 있다"를 문서에 남긴다.** 안 그러면 다음 사람이 §0 의 「살린다」만 읽고
> 켜져 있다고 믿는다 — 이번 트랙이 바로 그 사고(넣는 곳 없는데 돈다고 믿음)로 시작했다.

## 4-6. 🟢 즉시 차단 — 갈래 「나」 채택 (사장님 결재 2026-09-27)

### 먼저: 실측으로 드러난 현재 동작 (설계 초안이 몰랐던 것)

```
AccessToken 8시간 · RefreshToken 7일
로그인하면 그 계정의 refresh_tokens 를 전부 DELETE 한다  (AuthService.cs:117)
```

⇒ **지금도 PC2 로그인이 PC1 의 refresh 토큰을 지운다.** 그런데 PC1 의 **access 토큰은 JWT 라 상태가 없다** — 서버가 DB 를 안 본다. PC1 은 **최대 8시간 그대로 쓰다가** 갱신 시점에 조용히 튕긴다.

🔴 **지금이 최악의 조합이다**: 동시 로그인은 사실상 되고, 나중에 예고 없이 한쪽이 튕긴다.

⇒ 세션 행만 지우는 밀어내기(갈래 가)는 **눌러도 PC1 이 안 끊긴다.** 고객은 끊었다고 믿는다.

### 🟢 채택: 갈래 「나」 — 요청 경로에서 세션 유효성을 확인한다

| 버린 갈래 | 사유 |
|---|---|
| 가 (세션만 삭제) | 최대 8시간 안 끊긴다. **끊었다고 믿는데 안 끊긴 상태**가 더 위험하다 |
| 다 (토큰 수명 단축) | 🔴 8시간으로 올린 이유가 **근무 중 끊김**이다(#19·#27). 되돌리면 그 사고 재발 |

### 🔴 「미들웨어 무접촉」은 유지한다 — 새 미들웨어를 **추가**한다

`SessionLimitMiddleware` 는 **여전히 한 줄도 안 건드린다.** 축이 다른 판정을 그 안에 섞으면
이번 트랙이 고치려는 혼선을 그대로 재생산한다. 대신 **신설**한다 (#1 — 추가만):

```
TenantMiddleware
  → SessionValidityMiddleware  ⬅ 신설 (축 B 즉시 차단)
  → SessionLimitMiddleware     ⬅ 무접촉 (축 A · 기본 OFF)
```

### 이걸 하려면 JWT 에 세션 번호가 있어야 한다

지금 토큰에는 `user_id`·`tenant_id` 만 있다. 그것만으로는 **PC1 과 PC2 를 못 가른다** —
"이 사용자 세션이 있나"는 답해도 **"이 PC 의 세션이 살아 있나"**는 못 답한다.

⇒ `CreateLoginResponse`([`AuthService.cs:434~485`](../../../src/HitPan.Application/Services/AuthService.cs#L434-L485))에 **`sid` 클레임**을 넣는다.
⇒ 미들웨어는 `SELECT 1 FROM user_sessions WHERE session_id=@sid AND expires_at>NOW()` 로 판정한다.

### ⚠️ 「즉시」의 정직한 정의 — 최대 10초

매 요청 DB 조회는 부담이라 **10초 캐시**를 둔다. 따라서 밀어내기는 **즉시가 아니라 최대 10초**다.
사람 체감으로는 즉시지만, **문서에 10초라고 적는다** — "즉시"라고 적어두면 다음 사람이 0초로 믿는다.

### 🔴 옛 토큰 호환 — 이게 빠지면 배포 순간 전원 로그아웃이다

이미 발급된 access 토큰에는 `sid` 가 **없다**. 없는 토큰을 "세션 없음"으로 판정하면
**배포 즉시 전 고객이 튕긴다.**

⇒ **`sid` 가 없는 토큰은 통과시킨다.** 8시간 뒤 자연히 새 토큰으로 갈린다.
⇒ 게이트 G-7 로 시험한다.
