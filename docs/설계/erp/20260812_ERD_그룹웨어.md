## §1. 전체 관계도

```
                    ┌─────────────┐
                    │   users     │  계정 (로그인 수단)
                    │  user_id PK │
                    └──────△──────┘
                           │ user_id (NULL 허용)
                           │ ※ 실측: 사원 12명 중 1명만 보유
        ┌──────────────────┴──────────────────┐
        │           employees  ★축            │
        │           employee_id PK            │
        │  user_id · dept_id · position(문자) │
        │  join_date · resign_date            │
        └──┬────┬────┬────┬────┬────┬────┬───┘
           │    │    │    │    │    │    │
     ┌─────┘    │    │    │    │    │    └─────────┐
     ↓          ↓    ↓    ↓    ↓    ↓              ↓
 attendance  leave  over  hr_exp  labor_    approval_documents
  (근태)     _req   time  _req    contracts   (requester_id)
                                     │              │
                                     ↓              ↓
                              esign_records   approval_doc_lines
                              🔴 user_id 기준      (approver_id)
                                (축 예외 — 봉합대상)

  departments ──dept_id──→ employees      🔴 마스터 0행 (§4-1)
  positions   ──?────────→ employees      🔴 연결 컬럼 없음 (§4-2)
```

### 신규 영역 (이번 설계)

```
employees ──→ 🆕 reports          (보고서 4종)
employees ──→ 🆕 payslips         (급여명세서)
hr_expense_requests ──→ 🆕 expense_attachments (영수증)

users ──→ 🆕 chat_rooms / chat_members / chat_messages / chat_reads   (메신저)
users ──→ 🆕 notifications                                            (알림)
          ↑ 🔴 계정 기준 — 사장님 결재
```

## §3. 🔴 구조적 결함 (설계 전 정리 필요)

### 3-1. 결재선 2중화 — GW-001

```
[실제 도는 것]                    [죽어 있는 것]
approval_doc_lines                approval_lines
  approver_id (사람)                └─ approval_line_steps
  🟢 엔진이 읽음                        ├ employee_id
                                        └ position_id  ← 직급 지원
                                     🔴 엔진이 안 읽음
```

⛔ **정본 선택은 사장님·상무님 결재.** 설계팀 권고 = 직급 쪽을 엔진에 연결(흐름설계서 §7-A).
🚨 어느 쪽이든 **기존 표 삭제 금지**(헌법 #1·#37).

### 3-2. 부서 축 2갈래 — GW-040

| | `departments.dept_id` (마스터) | `employees.department` (자유문자) |
|---|---|---|
| 코드가 읽는 곳 | 🟢 **여기** | ❌ |
| 실제 데이터 | 🔴 **0행** | 🟢 **10건** |
| 인덱스 | — | `idx_employees_dept` |

⇒ **화면엔 "부서 없음", 사원엔 부서명 10건.** 지금 부서방을 만들면 **방이 0개** 생긴다.
+ `users` 에도 `dept_id` 가 **또** 있다(3중화). 축은 사원이므로 **`employees` 기준으로 통일**.

### 3-3. 🔴 직급도 같은 문제 (신규 발견)

```
positions (마스터)  ←──?── employees.position varchar(30)  자유문자
                            🔴 position_id 컬럼이 없다
```

**`employees` 에 `position_id` 가 없다.** 자유문자 `position` 만 있다.
⇒ **직급 기반 결재선(상무님 조언)을 걸려면 이 연결부터 만들어야 한다.**
GW-001 의 **숨은 선행조건**이다.

### FK 정책 — 🔴 결정 필요

**현상**: `employees` 를 참조하는 **FK 0건**(전부 인덱스만). 고아 행이 DB 차원에서 안 막힌다.

| 안 | 장점 | 단점 |
|---|---|---|
| **A. FK 추가** | 무결성 보장 | MDB 마이그 시 순서 제약 · 기존 데이터 정리 필요 |
| **B. 현행 유지**(앱 검증) | 마이그 유연 | 고아 행 위험 지속 |

⛔ **DB 매니저 + 사장님 결재.** 설계팀 의견: **신규 표는 FK 부여**, 기존 표는 현행 유지(리스크 격리).
