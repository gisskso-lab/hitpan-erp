## §1. 목적 · 범위

### 목적
자동배포(GitHub Actions)가 NCP 에서 **root 로 임의 셸을 돌릴 수 있는 현 구조**를, **비특권 전용 계정 + 최소 sudoers 화이트리스트**로 가둔다. 20260723작1 §2 G-B 의 보안목표를 실측 기반으로 실제 달성한다.

### 범위 (IN)
1. NCP: 비특권 계정 `hitpan-deployer` 신설 (셸 有, sudo그룹 **미포함**).
2. NCP: 전용 SSH 키쌍 신설 → 공개키를 `hitpan-deployer` authorized_keys 에 등록.
3. NCP: `/etc/sudoers.d/hitpan-deployer` — **자동업데이트용 1줄 + 웹CD용 N줄** 최소 화이트리스트. `visudo -c` 검증 필수.
4. NCP: `/opt/hitpan/installer/updates/` 상주 스크립트 = `hitpan-deployer` **읽기·실행만**(쓰기 불가 = 바꿔치기 차단). 소유 root, others r-x.
5. GitHub: `deploy-update.yml`·`deploy-ncp.yml` 의 `NCP_USER` = root → `hitpan-deployer`. `NCP_SSH_PRIVATE_KEY` = 신규 개인키.

## §2. 🔴 CTO·사장님이 반드시 볼 핵심 리스크 (받아쓰기 차단)

### 리스크 R-1 (BLOCKING) — 웹CD sudo 가 화이트리스트로 잘 안 가둬진다
실측: deploy-ncp.yml 이 쓰는 sudo (line 102·103·104·114·115·116·117·118·119·151·152·154·155·156·208·209·210·211):
- `sudo cp -r /opt/hitpan/* ...` (백업)
- `sudo rsync -a --delete ... /opt/hitpan/*` (배포 — **임의 소스**)
- `sudo systemctl restart hitpan-{backoffice-api,backoffice-web,landing}`
- `sudo systemctl daemon-reload`
- `sudo mkdir -p /etc/systemd/system/$SVC.service.d`
- `printf ... | sudo tee /etc/systemd/system/.../release-version.conf` (**systemd 파일 생성**)

**문제:** `sudo rsync`(임의 소스→/opt)·`sudo tee`(임의 파일 쓰기)를 NOPASSWD 로 열면, 그 계정은 **사실상 root 와 동급**이 된다(예: rsync 로 /root/.ssh 덮기, tee 로 sudoers 추가). 화이트리스트가 형식만 남고 실질 보안이 약해진다.

**→ CTO 판단 필요:** 웹CD 를 화이트리스트로 가두는 3안 중 택:
- **(a) 래퍼 스크립트화** — 웹CD sudo 블록을 NCP 상주 `deploy-web.sh`(root 소유, 인자 없음, 고정 경로만) 1개로 만들고 sudoers 는 `deploy-web.sh` **인자 0개만** 허용. rsync 소스·타겟이 스크립트에 하드코딩 → 임의쓰기 봉인. **가장 안전. 권장.**
- (b) 개별 명령 화이트리스트 — systemctl restart 3개·daemon-reload 만 NOPASSWD, rsync/cp/tee 는 **/tmp→/opt 이동을 배포계정 홈 기반으로 재설계**. 복잡·깨지기 쉬움.
- (c) 웹CD 는 이번 범위서 빼고 root 유지 — 사장님 "웹CD도 비특권화" 결재와 배치. 재확인 필요.

> **PM 소견:** (a) 래퍼가 정석. 단 래퍼 신설 = 웹CD 로직을 NCP 상주 스크립트로 옮기는 것 = **추가 작업·추가 검증**. CTO 가 (a) 승인 시 본 작지서에 deploy-web.sh 명세 추가.

### 리스크 R-2 — 전환 중 배포 중단 창(window)
`NCP_USER` 를 root→hitpan-deployer 로 바꾸는 순간, sudoers·authorized_keys 가 아직이면 **다음 배포가 인증/권한 실패**. → **순서 강제**(§4): 계정·키·sudoers 를 NCP 에 **먼저 완비**하고, GitHub Secret 은 **맨 마지막**에 교체. 교체 직후 dispatch 로 1회 검증.

### 리스크 R-3 — sudoers 문법 오류 = sudo 전체 마비
`/etc/sudoers.d/` 파일 문법 틀리면 sudo 가 통째로 거부될 수 있음. → **`visudo -cf <파일>` 통과 못 하면 배치 안 함**(§3-3 게이트). 기존 sudoers 는 절대 편집 안 함(신규 파일만, `/etc/sudoers.d/hitpan-deployer`).

### 리스크 R-4 — 개인키 노출 경로 재확인
현재 `/var/hitpan/update-keys/` = root 600. `hitpan-deployer` 는 여기 **읽기 불가**여야 함(핵심 목표). publish-update.sh 는 `sudo` 로 실행되니 스크립트 내부에선 root 로 개인키 접근 OK. **계정 자체는 개인키 못 봄** = 정상. 배치 후 `sudo -u hitpan-deployer cat /var/hitpan/update-keys/update_private.pem` → **Permission denied 확인**(§5 DoD).

## §3. 작업 명세

### §3-1. 계정 신설 (NCP)
```
useradd -m -s /bin/bash hitpan-deployer      # 홈 有, 로그인셸 有
# sudo/admin 그룹 미포함 (id 로 확인)
```

### §3-2. SSH 키쌍 (신규 전용)
```
# 로컬(또는 NCP)에서 ed25519 키쌍 생성 (기존 키 재사용 금지 — 계정 전용)
ssh-keygen -t ed25519 -f hitpan-deployer-key -C "hitpan-deployer@cd" -N ""
# 공개키 → NCP /home/hitpan-deployer/.ssh/authorized_keys (600, 소유 hitpan-deployer)
# 개인키 → GitHub Secret NCP_SSH_PRIVATE_KEY (§3-5). 로컬 개인키는 등록 후 파기.
```

### §3-3. sudoers 화이트리스트 (`/etc/sudoers.d/hitpan-deployer`)
> **CTO R-1 결정 반영 후 확정.** (a) 래퍼 채택 가정 초안:
```
# 자동업데이트 CD — publish-update.sh 2인자만
hitpan-deployer ALL=(root) NOPASSWD: /opt/hitpan/installer/updates/publish-update.sh --zip * --manifest *
# 웹 CD — 래퍼 1개 인자0 (R-1 (a)) — deploy-web.sh 명세는 CTO 승인 후 추가
hitpan-deployer ALL=(root) NOPASSWD: /opt/hitpan/deploy/deploy-web.sh
```
- **`--webroot`·`--private`·`--feed-url`·`--allow-republish` 는 화이트리스트에 없음** = 넘기면 거부(20260723작1 §2 G-B 정신).
- 배치 전 `visudo -cf /etc/sudoers.d/hitpan-deployer` **통과 필수.**
- ⚠️ sudoers 와일드카드 `*` 주의: `--zip *` 는 공백 포함 임의문자 매칭. **경로에 공백·`;`·`&&` 주입 방어** = publish-update.sh 가 인자를 파일존재검사(`[[ -f "$ZIP" ]]`)로 이미 검증(실측 line 86-87). 그래도 CTO 가 와일드카드 안전성 최종 판정.

### §3-4. 상주 스크립트 권한 (바꿔치기 차단)
```
chown root:root /opt/hitpan/installer/updates/*.sh
chmod 755 /opt/hitpan/installer/updates/*.sh     # others r-x (실행 O, 쓰기 X)
# hitpan-deployer 는 쓰기 불가 → CI 가 스크립트 바꿔치기 물리 차단
```

### §3-5. GitHub Secret 교체 (맨 마지막)
- `NCP_USER`: root → **hitpan-deployer**
- `NCP_SSH_PRIVATE_KEY`: 기존 → **신규 hitpan-deployer 개인키**
- (두 워크플로우 공용 Secret 이면 한 번, 분리면 각각)

## §4. 착수 순서 (R-2 배포중단 방지 — 순서 강제)
```
[NCP 먼저 완비 — GitHub 안 건드림]
 1. hitpan-deployer 계정 신설 (§3-1)
 2. SSH 키쌍 생성 + authorized_keys 등록 (§3-2) → 신규키로 SSH 접속 성공 확인

 4. /etc/sudoers.d/hitpan-deployer 배치 + visudo -c 통과 (§3-3)
 5. 상주 스크립트 권한 755 root (§3-4)
 6. sudo -u hitpan-deployer 로 화이트리스트 명령 OK / 오버라이드 거부 / 개인키 읽기 거부 실측 (§5)
    ↓ 여기까지 GitHub 미변경 = 기존 root 배포 계속 정상
[GitHub 교체 — 마지막]
 7. Secret NCP_USER·NCP_SSH_PRIVATE_KEY 교체 (§3-5)
 8. deploy-ncp.yml workflow_dispatch 1회 → 웹배포 정상 확인 (전환 검증)
```

## §5. 검증 DoD (검증팀 SoD — 만든 사람 ≠ 검증)
> 완료 = "돌려봤더니 됐다" 금지. 아래 **실측 반증**.

1. **화이트리스트 발동**: `sudo -u hitpan-deployer sudo publish-update.sh --zip a.zip --manifest b.json` → 통과(파일없음 에러는 무관, sudo 인증은 통과). `--webroot /x` 추가 → **sudo 거부**.
2. **개인키 격리(핵심)**: `sudo -u hitpan-deployer cat /var/hitpan/update-keys/update_private.pem` → **Permission denied**.
3. **스크립트 바꿔치기 차단**: `sudo -u hitpan-deployer sh -c 'echo x >> /opt/hitpan/installer/updates/publish-update.sh'` → **Permission denied**.
4. **임의 셸 불가**: `sudo -u hitpan-deployer sudo bash` / `sudo -u hitpan-deployer sudo systemctl restart sshd` → **거부**(화이트리스트 밖).
5. **웹CD 전환**: Secret 교체 후 deploy-ncp dispatch → 랜딩·백오피스·API **3서비스 정상 재기동**(systemctl is-active).
6. **sudoers 무결성**: `visudo -c` 전체 통과(기존 규칙 안 깨짐).
7. **롤백 경로**: 문제 시 Secret 을 root 로 되돌리면 즉시 복구 가능함을 명시(계정·sudoers 는 남겨둬도 무해).
