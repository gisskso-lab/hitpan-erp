### 1-2. 게이트를 여닫는 지점 전수 (`Worker.cs`)

| `:119` | 기동 시 로컬 Major 펜딩 발견 → `null` | 열기 (W4-6 펜딩 소실 복원) |

| `:335` | 평가 후 `= today` | 닫기 |
| `:389` | 평가 중 예외 → `null` | 열기 (헌법 #15) |

**핵심 [확인]**: 이 필드를 파일·DB에 쓰는 코드는 전 리포에 없다. 즉 **프로세스가 죽으면 게이트도 같이 죽는다.**

### 1-3. 지금 "재시작하면 풀린다"는 의도된 설계가 아니다

`:26-28` 주석은 게이트의 목적을 이렇게만 밝힌다 — *"매 루프 60초마다 manifest 조회 방지"*.
**재시작 시 초기화된다는 성질은 어디에도 설계 의도로 기술되어 있지 않다.** [확인]

- 반대 방향의 성질은 **명시되어 있다** — `:110-113` (W4-6 펜딩 소실 복원)은 `_pendingConsentUpdate` 가 인메모리라 **재시작 시 날아가는 것을 결함으로 보고** 복원 코드를 넣었다.
- 즉 팀은 "인메모리 = 재시작 시 소실"을 **문제로 인식했고**, 같은 파일의 `_lastUpdateCheckDate` 에 대해서는 그 인식을 적용하지 않았다.

**설계팀 판정**: 2026-08-06 19:34 에 사장님의 `sc start` 가 통한 것은 **봉합의 작동이 아니라 부작용의 우연한 이득**이다. 이 사실을 문서에 남긴다 — 3안 검토의 존재 이유이자, 향후 누군가 "재시작하면 되니까 괜찮다"고 오판하는 것을 막기 위해서다.

### 1-4. manifest 1회 조회의 실제 비용 [확인]

| 항목 | 값 | 근거 |
|---|---|---|
| 요청 | `GET https://updates.hitpan.kr/manifest.json` | `UpdateClient.cs:72-73` |
| 응답 크기 | JSON 9필드 — **1KB 미만** | `installer/updates/manifest-sample.json` |
| 타임아웃 | 30초 | `UpdateClient.cs:71` |
| 클라이언트 CPU | JSON 역직렬화 + Ed25519 서명 1회 검증 | `:72`, `:90` |
| 새 버전 없을 때 | `IsNewerVersion` false → `LogDebug` 후 `null` 반환. **다운로드 없음** | `:97-104` |
| **엣지 캐시** | **manifest.json 에 no-cache 가 걸려 있다** | `deploy-update.yml:19` — *"manifest.json no-cache 헤더 확인 — Cloudflare 엣지 경유. ✅ 이미 no-cache 걸림"* |

> 🔴 **마이클(네트워크) 지적 — 이 마지막 줄이 이번 검토의 숨은 축이다.**
> manifest 는 게시 직후 옛 버전이 서빙되면 안 되므로 **의도적으로 no-cache** 다. 그래서 Cloudflare 가 앞에 있어도 **폴링 1건 = NCP 오리진 요청 1건**이다. CDN이 흡수해 주지 않는다.
> 주기를 N배로 올리면 **오리진 요청도 그대로 N배**가 된다. "Cloudflare 뒤라 괜찮다"는 직관은 이 파일에 대해서는 **틀렸다.**

## 2. 왜 `4cc5842` 는 반쪽 봉합이 되었나 — 설계 관점 분석

> 임무 §추가 3에 대한 답이다. 새 안이 같은 함정을 피하는지 판정하는 기준이 된다.

### 2-1. 그 봉합이 실제로 한 일

`Worker.cs:296-308` 주석이 스스로 밝힌 대상은 **"[나중에] 를 눌러 펜딩이 비워진 뒤"** 한 가지다.
봉합 위치도 그에 맞춰 **`if (_pendingConsentUpdate is { } consentPending)` 블록 안**(:293~311)이다.

즉 **그 블록에 진입한 경우에만** 게이트가 풀린다. [확인]

### 2-2. 그래서 어디를 못 덮었나

| 상태 | 그날 재발견 가능? | 이유 |
|---|---|---|
| Major 펜딩 있음 → 해소됨 | ✅ 된다 | `:306` 이 게이트를 연다 |
| **펜딩이 애초에 없음**(발견만 하고 Major 아님 / 그날 새 버전 없었음) | ❌ **안 된다** | `:293` 조건 자체가 false — 봉합 코드에 도달하지 않는다 |
| Normal 야간 보류 중 | ❌ 안 된다 | `:314` 분기에서 return, 게이트 해제 없음 |
| 평가했으나 새 버전이 없었음 → 그 뒤 게시됨 | ❌ **안 된다 ← 이번 N-10** | `:340-344` 는 `_lastUpdateCheckDate = today`(`:335`) 를 이미 찍은 뒤 return |

**이번 사장님 사례는 4번째 줄이다.** 19:30에 1.2.54까지 평가를 마쳤고, 그 뒤 1.2.55가 올라왔다. 펜딩 블록에 진입할 일이 없으니 봉합 경로에 걸릴 수 없다.

### 2-3. 설계 관점의 진짜 원인 — **증상에 붙인 봉합**

`4cc5842` 는 **"게이트가 문제다"** 가 아니라 **"[나중에] 를 눌렀는데 그날 재발견이 안 된다"** 는 **하나의 재현 시나리오**를 고쳤다.

> 설계 원칙: **"이 증상이 나는 경로가 여기 하나뿐인가"를 묻지 않고 봉합하면 반드시 두 번째 얼굴이 온다.**

`_lastUpdateCheckDate` 는 **평가 경로의 전역 스위치**인데, 봉합은 **한 분기 안쪽**에 들어갔다. 스위치를 여는 조건이 스위치가 닫히는 조건보다 좁으면 반드시 틈이 남는다. `:119`·`:306`·`:389` 세 개의 해제 지점이 전부 **특정 사건 뒤에 붙은 땜질**이고, "정상적으로 하루가 지나면 열린다" 외에는 **주기적·구조적 해제 지점이 없다.** [확인]

### 2-4. 이 분석이 새 안에 거는 조건 (합격 기준)

새 안은 다음을 만족해야 세 번째 얼굴을 막는다.

| 조건 | 내용 |
|---|---|
| **G-1** | 게이트 해제가 **특정 사건이 아니라 시간(주기) 기반**이어야 한다. 어떤 분기를 타든 일정 시간이 지나면 반드시 재평가된다. |
| **G-2** | 게이트를 건너뛴 사실이 **로그에 남아야** 한다. 지금 `:326` 의 조용한 return 이 원인 규명을 반나절 지연시켰다(채증 500건 중 0건 — 작1 §2-3). |
| **G-3** | 해제 지점이 **한 곳으로 모여야** 한다. `:119`·`:306`·`:389` 처럼 흩어지면 다음 사람이 전부를 못 본다. |
| **G-4** | 재시작으로 우연히 풀리는 성질에 **의존하지 않아야** 한다. |

## 3. 3안 각각 — 동작 · 장단점

### 3-1. 1안 — 확인 주기 단축

**동작**: `_lastUpdateCheckDate`(DateOnly) 를 시각 기반 판정으로 바꾼다. 마지막 확인 후 N시간이 지나면 재평가.

**핵심 성질**
- 게이트 해제가 **시간 기반**이 된다 → **G-1 충족.**
- 판정 자리가 `:325-327` 한 곳이므로 해제 로직도 그 한 곳에 모인다 → **G-3 충족.**
- 기존 60초 루프 안에서 판정만 바뀌므로 **새 인프라 0**. 본사 서버·방화벽·인증서 어느 것도 안 건드린다.

**장점**
| | |
|---|---|
| 구조 변화 최소 | 판정식 하나. 검증 표면이 작다 |
| 실패 모드 없음 | 못 받는 신호도, 못 읽는 파일도 없다. 최악이 "N시간 늦음" |
| 헌법 #30 정합 | 본사가 죽어도 고객 PC 가 스스로 주기 도래를 판단한다. 본사 의존 0 |
| 개발 사이클 | N=1h 이면 사장님 3단계가 **평균 30분 / 최대 1시간**으로 성립 |

**단점**
| | |
|---|---|
| 오리진 부하 선형 증가 | no-cache 라 CDN 흡수 없음(§1-4). N을 너무 짧게 잡으면 그대로 청구서가 된다 |
| 여전히 지연이 있다 | 게시 직후 즉시는 아니다. 최대 N시간 |
| **재시작 폭주를 못 막는다** | 인메모리를 그대로 두면 서비스가 자주 재기동되는 PC(Guardian 5분·sc failure 5초 — `Worker.cs:98-100` 참조)에서 매 기동마다 조회가 1회씩 추가된다 → **G-4 미충족** |

**N 후보별 실측 산정** (고객사 1,000곳 가정 — 베타 이후 목표치)

| N | PC당 1일 조회 | 전체 1일 오리진 요청 | 전송량(1KB 기준) | 개발 사이클 |
|---|---|---|---|---|
| 24h (현행) | 1 | 1,000 | 1MB | ❌ 최대 24h |
| **6h** | 4 | 4,000 | 4MB | 🟡 최대 6h |
| **1h** | 24 | 24,000 | 24MB | ✅ 최대 1h |
| 15m | 96 | 96,000 | 94MB | ✅ 최대 15m |
| 60s (게이트 없음) | 1,440 | 1,440,000 | 1.4GB | ✅ 즉시 |

> 백엔드 매니저 소견: **1시간(24,000 req/일 ≈ 0.28 req/s)은 nginx 정적 파일 서빙 기준 부하라고 부르기 어려운 수치다.** 문제는 요청 수가 아니라 **디스크**였다(eaba641 — 게시본 무한누적 730MB/회). manifest 폴링은 디스크를 늘리지 않는다. 다만 **access.log 는 늘린다** — eaba641 당시 *"nginx access.log write alert"* 가 동반 증상이었다는 사실을 기억해야 한다. [확인]

### 3-2. 2안 — 게시 신호 즉시 확인 (푸시)

**동작**: 게시(`deploy-update.yml`)가 완료되면 본사가 고객 PC 에 "새 버전 있음"을 알리고, 워치독이 그 신호를 받아 즉시 manifest 를 조회한다.

**구현 가능한 형태 3가지와 각각의 벽**

| 형태 | 내용 | 벽 |
|---|---|---|
| (a) 본사 → 고객 PC 직접 호출 | 백오피스가 각 고객 터널로 POST | 🔴 **헌법 #30 정면 위반.** 본사가 고객 PC 주소록을 갖고 능동 접속하는 구조 — *"본사가 안 가지면 털릴 일 없다"*(#22)와 반대. 터널 다운 시 신호 소실 |
| (b) 상시 연결(WebSocket/SSE) | 워치독이 본사에 연결을 열어두고 대기 | 🟡 고객사 수만큼 상시 연결 유지. 방화벽·프록시 환경에서 끊김 → **재연결 로직이 곧 새로운 워치독**. 끊긴 동안 신호 소실 → **폴백 폴링이 어차피 필요** |
| (c) 메타핑 응답에 실어 보냄 | 이미 도는 5분 주기 `SendMetaPingAsync`(`Worker.cs:148-149`, `MetaPingIntervalMinutes=5`)의 **응답**에 `latestVersion` 을 담아 내려보낸다 | 🟡 **이게 유일하게 현실적이다.** 다만 §3-2-1 |

**3-2-1. (c)안의 실제 상태 [확인 — 이것이 2안의 결정타]**

`WatchdogOptions.cs:12` → `MetaPingEndpoint = "https://back.hitpan.kr/watchdog/ping"`
같은 파일 `:16-17` 주석이 스스로 기록하고 있다:

> *"⚠️ 위 MetaPing 2개와 **다른 경로**다. `/watchdog/*` 수신부는 백오피스에 아직 **0건**이라 지금도 400 이 난다(실측 2026-08-06)."*

코드리뷰서도 같은 항목을 **범위 밖**으로 명시한다 — *"`/watchdog/ping` 경로 복구 ⬜ 범위 밖(명시)"*.

**즉 2안(c)이 올라탈 메타핑 경로는 지금 백오피스에 존재하지 않는다.** 2안을 채택하면 순서가 이렇게 된다:

```
백오피스 /watchdog/ping 수신부 신규 구축
  → 응답 스키마 설계(latestVersion 필드)
  → 워치독 응답 처리 코드 신규
  → 본사 장애 시 폴백 폴링 설계(어차피 필요)
  → 종단 실측
```

**장점**
| | |
|---|---|
| 지연 최소 | (c) 기준 최대 5분. 개발 사이클로는 최상 |
| 평상시 오리진 부하 최저 | 새 버전이 없으면 manifest 를 아예 안 두드린다 |

**단점**
| | |
|---|---|

### 3-3. 3안 — 게이트 영속화 (디스크/DB 저장)

**동작**: `_lastUpdateCheckDate` 를 파일 또는 로컬 DB 에 기록하고 기동 시 읽어 복원한다.

**⚠️ 방향 판정 — 단독 채택 시 현상은 나빠진다**

| | 현행 | 3안 단독 |
|---|---|---|
| 그날 이미 평가함 + 새 버전 게시됨 | 최대 24h 지연 | 최대 24h 지연 (동일) |
| 위 상태에서 서비스 재시작 | ✅ **즉시 발견**(우연) | ❌ **여전히 안 발견** |
| 사장님의 `sc start` 우회로 | 통한다 | **막힌다** |

**즉 3안 단독은 이번 실측에서 유일하게 통했던 탈출구를 없앤다.** 개발 사이클은 24시간에 **완전히 고정**된다.

**그럼에도 검토 대상인 이유 (사장님 지시 §3안 주의)**

1. **"재시작하면 풀린다"는 우연이다**(§1-3). 우연에 기대는 설계는 문서에 남기지 않으면 다음 사람이 **기능으로 오인**한다. 실제로 CS 매뉴얼에 *"서비스를 재시작해 보세요"* 가 들어가면, 그건 헌법 #30("고객 손 0번")을 CS 절차로 위장해 위반하는 것이다.
2. **3안이 푸는 진짜 문제는 따로 있다** — *재시작 폭주*. 워치독은 Guardian(5분)·sc failure(5초)로 되살아나는 구조다(`Worker.cs:98-100`). 크래시 루프에 빠진 PC 는 **기동마다 manifest 를 1회씩** 두드린다. 지금은 하루 1회 게이트가 인메모리라 **이 폭주를 막는 장치가 없다.**
   → **주기를 짧게 하면(1안) 이 폭주는 그대로 남는다. 3안의 영속화가 그것을 막는다.** [추정 — 크래시 루프 실측 사례는 확보하지 못했다. 구조상 가능하다는 판정이다]
3. **W4-6 펜딩 복원(`:110-121`)이 이미 같은 문제를 인정했다.** 인메모리 상태의 재시작 소실을 결함으로 보고 복원 코드를 넣은 전례가 있다.

**장점**
| | |
|---|---|
| 재시작 폭주 차단 | 유일하게 이걸 막는 안 |
| 우연 제거 | 동작이 재시작 여부에 안 흔들린다 → **G-4 충족** |
| 진단 가능 | 파일을 열면 "마지막으로 언제 확인했나"가 보인다. 지금은 프로세스 안에만 있어 CS 가 볼 수 없다 |

**단점**
| | |
|---|---|
| 🔴 **단독이면 개발 사이클 24h 고정** | 사장님 오더에 정면으로 반한다 |
| 새 실패 모드 | 파일 손상·권한·시계 역행 시 "영영 안 열림". 읽기 실패 = **열림(fail-open)** 이 안전 기본값 |
| 저장 위치 결정 필요 | §6-2 |

## 5. 🏆 설계팀 권고 — 4안(혼합)

### 5-1. 권고안 정의

> **주기 기반 게이트(1안)를 뼈대로 하고, 그 마지막 확인 "시각"을 디스크에 남긴다(3안의 메커니즘).**
> **단, 영속화의 목적은 "게이트 유지"가 아니라 "재시작 폭주 상한"이다.** N시간이 지났으면 재시작 여부와 무관하게 열린다.

**한 줄 근거**: 3축 중 어느 하나도 희생하지 않는 유일한 조합이며, §2-4 합격 조건 **G-1~G-4 를 전부 충족하는 유일한 안**이다.

### 5-2. G-조건 대조

| 조건 | 1안 | 2안 | 3안 | **4안** |
|---|---|---|---|---|
| G-1 시간 기반 해제 | ✅ | 🟡 신호 의존 | ❌ | ✅ |
| G-2 건너뜀 로그 | (같이 넣으면) | (같이 넣으면) | (같이 넣으면) | ✅ **필수 포함** |

| G-4 재시작 우연 제거 | ❌ | ❌ | ✅ | ✅ |

### 5-3. 왜 1안 단독이 아닌가

1안 단독이면 재시작마다 조회가 1회 추가된다. 지금은 하루 1회라 **재시작 폭주의 영향이 하루 1회 → 하루 M회**로 그친다. N=1h 로 바꾸면 정상 PC 는 24회지만 **크래시 루프 PC 는 상한이 없다.** eaba641(디스크 100%)이 가르친 것은 *"1회당 비용이 작아도 회전이 없으면 반드시 죽는다"* 이다. **상한 없는 반복은 그 자체가 설계 결함이다.**

### 5-4. 왜 2안이 아닌가 (지금은)

세 가지가 겹친다.
1. **헌법 #30** — 발견의 성립 조건에 본사를 넣으면 자가회복이 아니다. 1PC 24시간 지연을, 전 고객 무기한 정지 위험과 바꾸는 거래다.
2. **선행 공사** — `/watchdog/*` 수신부 0건(`WatchdogOptions.cs:16-17` 실측 주석). 백오피스 신규 개발이 앞에 선다.
3. **어차피 폴백이 필요** — 2안을 넣어도 1안을 같이 넣어야 한다. **2안은 1안의 대안이 아니라 후속 가속기다.**

> **2안은 폐기가 아니라 보류다.** `/watchdog/*` 수신부가 복구되고 메타핑 종단이 실측되면, **4안 위에 얹는 3단계**로 재상신한다(§7-3).

### 5-5. 왜 3안 단독이 아닌가

§3-3 방향 판정 그대로 — 개발 사이클이 24h 로 고정되고, 이번 실측에서 유일하게 통했던 우회로까지 막힌다. 사장님 오더에 정면으로 반한다.
**다만 3안의 메커니즘(영속화)은 4안 안에서 살아 있다.** 3안이 틀렸던 것은 **저장하는 것**이 아니라 **저장한 값을 날짜로 해석하는 것**이다.

### 5-6. §2-4 합격 조건에 대한 자기검증

| 조건 | 4안이 어떻게 만족하나 |
|---|---|

| G-2 | 게이트 통과·차단 양쪽에 흔적을 남긴다. 이번 원인 규명이 반나절 걸린 이유가 `:326` 의 침묵이었다 |
| G-3 | 판정을 한 지점으로 모은다. 기존 `:119`·`:306`·`:389` 는 **제거하지 않는다**(헌법 #1) — §6-4 |
| G-4 | 마지막 확인 시각이 디스크에 있으므로 재시작해도 판정이 동일하다 |

### 6-3. 🟡 [결재-3] 야간 창 정책과의 관계

`IsNightWindow` 는 **3시대 1시간뿐**이다(`UpdateOrchestrator.cs:1423-1424` — `Hour >= 3 && Hour < 4`). [확인]
N=1h 면 **3시대에 반드시 1회 이상 평가**가 보장되어 Normal 채널 야간 적용이 지금보다 안정된다.
반대로 **N을 6h 이상으로 잡으면 3시대를 건너뛸 수 있다** — `_pendingNightUpdate` 로 낮에 들고 있다가 적용하는 경로(`:314-323`)가 있어 치명적이지는 않으나, **N 값 결정에 이 제약이 있다는 사실을 결재에 포함한다.**

> 설계팀 판정: **N ≤ 1h 이면 야간 창 1시간을 반드시 덮는다.** 이것도 1h 권고의 근거 하나다.

### 6-4. 🟡 [결재-4] 기존 3개 해제 지점의 처리

`:119`(펜딩 복원) · `:306`(4cc5842) · `:389`(예외)를 **제거하지 않는다** — 헌법 #1(수정은 OK, 제거 금지).
4안이 들어와도 이들은 "즉시 열기" 로 여전히 유효하다(N시간을 안 기다리고 바로 연다).
**단 의미가 바뀐다** — 지금은 "날짜 게이트 해제", 4안 이후는 "주기 게이트 즉시 만료". **주석 갱신이 필요하다는 사실만 결재에 올린다.**

## 8. W4-6 정지공격 감지와의 상호작용 — 🔴 **주기를 바꾸면 이 계수가 깨진다**

> 임무 §추가 1에 대한 답이다. **이번 검토에서 확인한 것 중 가장 중요한 부수 발견이다.**

### 8-1. 현행 계수 로직 [확인]

`Worker.cs:483-508` `TrackUpdateStallAsync(DateOnly today, ct)`

```
:485  if (!_update.LastFetchFailed) { 카운터 0 리셋; return; }
:496  if (_lastFetchFailCountedDate == today) return;   // 같은 날 중복 집계 방지
:497  _lastFetchFailCountedDate = today;
:498  _updateFetchFailStreakDays++;
:502  if (_updateFetchFailStreakDays >= UpdateStallNotifyDays)  // 7
          → 본사 긴급 통지 "update_feed_stalled"
```

주석(`:50-55`)이 밝힌 의도: *"조회 실패한 **날짜**를 세어 임계(**7일**) 연속이면 본사에 통지"*.

**이 로직은 "하루 1회 평가"를 전제로 설계되어 있다.** `_lastFetchFailCountedDate == today` 중복 방지가 있어서 **하루 안에 몇 번을 실패하든 카운터는 +1** 이다.

### 8-2. 주기를 1h 로 바꾸면 무슨 일이 나나

**결론: 계수 자체는 안 깨진다. 하지만 의미가 왜곡되고 감지가 늦어진다.** [확인 — 코드 로직상 확정]

| 항목 | 현행(하루 1회) | N=1h 적용 후 | 판정 |
|---|---|---|---|
| 카운터 증가 | 하루 최대 +1 | **하루 최대 +1** (`:496` 날짜 중복방지가 그대로 산다) | 🟢 폭주 없음 |
| 7일 도달 시점 | 실패 7일째 | **실패 7일째** (동일) | 🟢 |
| 🔴 **카운터 리셋** | 하루 1회 성공하면 리셋 | **1시간에 1번이라도 성공하면 즉시 리셋**(`:485-492`) | 🔴 **문제** |

**🔴 진짜 문제 — 간헐 장애가 영영 감지되지 않는다**

현행에서는 하루 1회 조회가 마침 장애 구간에 걸리면 그날은 실패로 집계된다. **N=1h 면 하루 24번 중 1번만 성공해도 카운터가 0으로 리셋된다.**

- 하루 23시간 feed 가 죽고 1시간만 살아나는 간헐 장애 → **현행: 실패로 셀 가능성 있음 / 4안 이후: 영원히 0. 7일 통지가 절대 발화하지 않는다.**
- W4-6 이 잡으려던 것은 *"feed 가 끊겨 고객이 영영 옛 버전에 고정되는 것"* 인데, **간헐 장애에서는 실제로 옛 버전에 고정되면서도 카운터는 깨끗하다.**

> **설계팀 판정: 이것은 4안이 만드는 새 결함이 아니라, 4안이 드러내는 기존 설계의 전제 붕괴다.**
> `TrackUpdateStallAsync` 는 **"조회를 하루 1번만 한다"** 는 전제 위에 서 있다. 그 전제를 바꾸는 순간 "날짜 단위 계수"는 더 이상 의미 있는 지표가 아니다.

### 8-3. 두 번째 문제 — 통지 지연

`TrackUpdateStallAsync` 는 `:338` 에서 **`_lastUpdateCheckDate = today`(:335) 직후에만** 호출된다. 즉 게이트를 통과한 평가에서만 계수한다. 주기가 짧아지면 호출 빈도는 24배가 되지만 `:496` 이 하루 1건으로 묶으므로 **감지 속도는 전혀 빨라지지 않는다.** 하루 24번 실패해도 7일을 기다린다.

### 8-4. 권고 — **분리 판정**

**N-10 봉합에 W4-6 계수 개편을 끌어들이지 않는다.** 근거:

1. 4안을 넣어도 **W4-6 이 즉시 깨지지는 않는다**(§8-2 — 카운터·임계·통지 전부 동작). 지금 당장 터지는 결함이 아니다.
2. 계수 축을 "날짜" 에서 "연속 실패 횟수 + 최근 성공 시각" 으로 바꾸는 것은 **정지공격 감지 정책의 재설계**다. 임계값(7일)의 의미도 다시 정해야 한다 — **사장님 결재 사안**이다.
3. 한 판에 섞으면 N-10 봉합의 검증 표면이 커져 사장님 3단계가 그만큼 늦어진다.

> **단, 4안 작업지시서에 "W4-6 계수 전제가 무효화된다"는 사실을 명시적으로 기록하고, 후속 과제로 등록한다.** 기록 없이 넘기면 §2-3 과 똑같은 반쪽 봉합이 된다. 🔴 **[결재-5] 로 §11 에 올린다.**

## 9. 개발팀 코드리뷰서 P1-1 과의 관계 — **별도 판정**

> 임무 §추가 2에 대한 답이다.

### 9-1. 두 건의 대조

| | **N-10** (이 문서) | **P1-1** (코드리뷰서 §3) |
|---|---|---|
| 증상 | 새 버전을 **발견하지 못한다** | 거부한 버전을 **계속 재발견한다** |
| 방향 | 게이트가 **너무 오래 닫혀 있다** | 게이트가 **너무 자주 열린다** |
| 코드 위치 | `Worker.cs:325-327` (게이트 판정) | `Worker.cs:304-308` ↔ `:450-457` (거부 처리 ↔ 해제) |
| 원인 | `_lastUpdateCheckDate` 의 해제 조건이 좁다 | 거부 사실을 기억하지 않는다(`_consentAppliedVersions` 에 Approve 만 등록 — `:442`) |
| 피해 | 개발 사이클 24h · 고객 최대 24h 미수신 | 60초마다 저비용 재조회 + 본사 중복 보고 가능 |
| 등급 | P1 (우선순위 높음) | P1 |

### 9-2. 판정: **같은 코드 영역이지만 별개 결함. 봉합은 따로 간다.**

**근거 1 — 진범이 다르다.**
N-10 은 **게이트 자체**의 문제다. P1-1 은 **거부 상태를 기억하지 않는 것**이 문제이며, 게이트 해제(`:306`)는 그 결함을 **드러내는 조건**일 뿐이다. P1-1 을 제대로 고치는 방법은 게이트를 건드리는 게 아니라 **거부 버전 집합을 두는 것**이다(코드리뷰서 §3 권고와 동일).

**근거 2 — 4안이 P1-1 을 악화시키지 않는다.** [확인 — 코드 경로 대조]
P1-1 의 고리는 `:306` 이 "펜딩 해소 즉시" 게이트를 여는 데서 발생한다. 4안은 그 **즉시 해제 경로를 건드리지 않는다**(§6-4 — 헌법 #1 로 존치). 4안이 바꾸는 것은 `:325-327` 의 **대기 상한**이다.
- P1-1 고리 주기: 60초(즉시 해제 → 다음 루프) — **4안 적용 후에도 60초. 변화 없다.**
- 즉 **N 값을 아무리 조정해도 P1-1 의 회전 속도는 안 바뀐다.** 두 건은 독립적이다.

**근거 3 — 4안이 P1-1 을 가리지도 않는다.**
4안은 P1-1 을 고치지도 악화시키지도 않으므로, P1-1 봉합은 언제 해도 된다. 순서 의존이 없다.

**근거 4 — 한 판에 묶으면 검증이 얽힌다.**
P1-1 검증은 "거부 후 60초 관찰 + 본사 중복 행 확인"(코드리뷰서 V-7)이고, N-10 검증은 "N시간 대기 후 재발견 확인"이다. 관측 창이 60초 대 1시간으로 두 자릿수 차이라 **한 실측에 담기 어렵다.**

### 9-3. 단, 두 가지 공동 제약

1. **같은 함수를 만진다** — 둘 다 `EvaluateUpdateOncePerDayAsync` 안이다. **동시 작업은 충돌한다. 순서를 정해야 한다.**
   > 설계팀 권고 순서: **N-10(4안) 먼저 → P1-1 나중.** 이유: N-10 이 사장님 3단계를 막고 있어 우선순위가 높고, N-10 이 끝나면 P1-1 검증을 그 짧아진 사이클로 더 빨리 돌릴 수 있다.
2. **함수명이 사실과 어긋나게 된다** — `EvaluateUpdateOncePerDayAsync` 는 4안 이후 "하루 1회"가 아니다. **이름 정정이 필요하다는 사실을 작업지시서에 남긴다**(구현 지시는 아님).

## 10. 개발용/고객용 분리안 — **반려 기록** (채택 안 함)

> 임무 §추가 4에 대한 답이다. 사장님이 선택지로 보셨던 안이며, 채택하지 않되 **왜 반려했는지를 남긴다.**

**안의 내용**: 개발 PC·샌드박스에서는 주기를 짧게(예: 1분), 고객 PC 에서는 하루 1회를 유지한다. 환경변수·설정으로 분기.

### 10-1. 반려 사유

| # | 사유 |
|---|---|
| R-1 | 🔴 **"개발 PC 에선 됐는데" 를 구조로 만든다.** 사장님 확정(2026-07-06, `feedback_dev_pc_proves_nothing`) — *"개발환경 PC 정상작동은 큰 의미 없다"*. 발견 경로는 자동업데이트의 **첫 관문**인데, 그 관문을 개발/고객이 다르게 타면 **우리가 검증한 경로와 고객이 타는 경로가 영영 다르다.** 이번 N-10 이 바로 "고객 경로를 안 밟아서 몰랐던 것" 이다 |
| R-2 | 🔴 **고객 문제가 안 고쳐진다.** 고객은 여전히 최대 24h 미수신이다(작1 §5-2 — P0 긴급 봉합이 그날 안에 안 내려감). 개발팀만 편해지고 **고객 영향은 그대로 남는다** |
| R-3 | 🟡 **분기 자체가 새 결함면이다.** "지금 이 PC 는 개발인가 고객인가" 를 판정하는 코드가 늘고, 오판 시 **고객 PC 가 1분 폴링을 돈다**(자해) 또는 **개발 PC 가 24h 를 돈다**(검증 무의미) |
| R-4 | 🟡 **헌법 #34 위반 소지** — *"인프라는 베타부터 정식 완성도"*. 발견 경로는 인프라다. 개발용 우회로를 두는 것은 "베타니까 임시로" 의 형태다 |

### 10-2. 다만 살릴 것 하나

**N 값을 설정으로 두는 것 자체는 유효하다**(§6-1). 분리안이 틀린 것은 *설정 가능성*이 아니라 **개발과 고객이 서로 다른 값을 쓰는 것**이다.
4안에서는 **개발도 고객도 같은 N 을 쓴다.** 우리가 겪는 지연을 고객도 똑같이 겪고, 우리가 답답하면 그건 고객도 답답한 것이다 — **이 정렬이 유지되어야 한다.**
