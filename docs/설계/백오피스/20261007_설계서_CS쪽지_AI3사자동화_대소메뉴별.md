## §1 [대메뉴 4. CS 관리 ▸ 고객사 CS 요청사항]

**ⓐ 왜**: 고객 쪽지가 도착해 쌓이는 본사·대리점의 책상이다. 지금은 껍데기 화면(`AdminCsListPage.razor:112` — API 호출 0줄)뿐이라, 쪽지가 와도 받을 사람이 볼 곳이 없다. 그리고 현장(강지원)이 경고한 대로 **입구를 열면 양이 2~3배로 뛴다(⚠️추정)** — 밀려올 때 안 무너지는 장치(약속 시계·내 응대함·30초 전화 틀)를 같은 책상에 둔다.

**ⓑ 화면·API·테이블**
| 것 | 내용 | 근거 |
|---|---|---|
| 목록 화면 | `/admin/cs` 실결선(껍데기→API 연결) + 열: 남은 시간(N-1)·상태·유형(7모양)·접수경로 · 목록 위 신호 2칸 「지난 건 N / 2시간 내 N」 | F-14 · N-1 |
| 내 응대함 | 🆕소메뉴(결재된 신설 1줄) — 담당 배정 1동작 + 「내 것/안 맡은 것/지난 것」 3탭 · 대리점판은 자기 범위만 | N-4 |
| 전화 접수 단추 | 고객사·유형·한 줄·즉결/미해결 — **네 동작**. `received_channel='phone'` 으로 들어간다 | N-5 · Q-4(전화 전건 기록) |
| 수신 API | 🆕`Backoffice.API` CS 컨트롤러 **신설**(교정② — 수신·저장·백엔드·화면은 전부 백오피스 몫) — **수신·인증 = 3중 일치 대조**(사장님 10/8): **테넌트넘버·시리얼넘버·부모계정 셋이 전부 맞아야 접수** · 하나만 맞는 요청 = 거부 + 거부 로그 · 🔴멱등키(`client_ticket_uid`)와는 **별개 축**(멱등은 중복 방지, 3중 일치는 신원 검증) · 멱등 `UNIQUE(tenant_id, client_ticket_uid)` + **필드 화이트리스트 밖 거부**(문③) · 자식계정 식별자는 화이트리스트에 없다 — 오면 거부 | 사장님 10/8 · 개발 §2-4·§5-1 |
| 시리얼 보관 | 🔴**발급한 시리얼 행 삭제 금지 — 상태만 변경**(폐기·만료도 행 보존 · #3 동원리). **폐기 시리얼로 인증 시도 = 거부** + 거부 로그. ⚠️**시리얼 발급 방식 자체는 무접촉**(사장님 「잘 돌고 있으니 건들지 마」 — 이 설계서는 발급 코드를 한 줄도 제안하지 않는다) | 사장님 10/8 |
| 시리얼 축 판단 | CS 티켓이 시리얼을 싣고 오므로 **시리얼 축 판단 3종**(①정상설치 됐나 ②잘 돌고 있나 ③계정과금 이슈 없나)과 같은 축으로 묶인다 — 운영현황(🆕C)·결제구독(🆕B)과의 연결 고리는 **2차 범위로만 표기**(이 설계서에서 화면·테이블 신설 없음) | 사장님 10/8 |

| 상태 전이 | F-15 고정목록·서버 1곳. 「고객 답 대기」 1칸 추가는 **결-1**(결재 전 안 넣음) | R-4(상태는 더 안 늘림) |

**ⓓ 게이트(동작 + 음성 대조군)**: ⓪**3중 일치**: 테넌트·시리얼·부모계정 중 **하나만 틀린** 요청 3종 각각 → 거부 + 거부 로그 · **폐기 시리얼**로 시도 → 거부 · 셋 다 맞으면 접수(양성 대조군) ①같은 쪽지 2회 송신 → 티켓 **1건**(멱등 — 시간창 아닌 키) ②화이트리스트 밖 필드 실은 payload → **거부 + 거부 로그 실존** ③A대리점 토큰으로 B대리점 티켓 조회 → 403/빈값 ④상태 전이를 다른 경로로 시도 → 거부 로그 ⑤전화 접수를 처음 쓰는 직원이 **30초 안에**(N-5 기준) ⑥음성 대조군: 멱등 UNIQUE 를 빼면 2건이 되는 것을 먼저 확인(게이트는 글자가 아니라 동작 — 소요시간·DB유무 판별 포함).

**ⓔ 하지 않는 것**: 상태 칸 추가(결-1 전) · 결제 수정 액션(F-18 읽기전용 유지) · 대리점의 공통장애 **선언**(R-10 — 신고만) · 만족도 묻기(R-9 보류) · 티켓 삭제(상태만 바꾼다).

## §2 [대메뉴 4. CS 관리 ▸ CS 누리집]

**ⓐ 왜**: 해결한 일이 사람 머릿속에서 끝나면 같은 일을 100번 다시 푼다. 누리집은 「이 증상엔 이렇게」가 쌓이는 창고이고, §8-2 고리(접수→정리→해결→재사용)의 심장이다. 파일(cs.md) 하나로 두면 누가 언제 왜 고쳤는지가 안 남으므로 **DB 에 저장하고 md 로 쓰고·보여주고·내보낸다**(IA §5-ⓓ 결재 그대로 — 쓰는 사람에겐 md 와 똑같다).

**ⓑ 화면·API·테이블**
| 것 | 내용 | 근거 |
|---|---|---|
| 테이블 | 🆕`bo_kb_docs`(doc_id·title·body_md·status 초안/승인/폐기·approved_by·approved_at·source_ticket_id·version) — **UPDATE 없이 version 증가로 새 행** + `bo_kb_doc_logs`(INSERT ONLY) — **채택** | 개발 §3-2 · IA §5-ⓓ |
| 승격 초안 | 티켓 완료 → 초안 **자동 생성 · 등재는 CS팀장 승인**(§8-6 결재 그대로). 생성 쿼리가 tenant_id·상호·담당자 칸을 **SELECT 자체를 안 한다**(화이트리스트 — 가져오지 않은 값은 잊을 수도 없다) | 개발 §5-2(1) |
| 승인 API | status→'승인' 전 **본문 재스캔**(식별정보·금지필드) — 걸리면 승인 거부 + 자리 표시. 화면 검사만으론 안 됨(API 직접 호출 우회) | 개발 §5-2(2) |
| 승인 체크리스트 | 「그 회사의 모양」(직원 수·창고 수·BOM 단수 같은 희귀 조합) 금지 — 증상·재현 조건·해결 순서만 | 개발 §5-3 #2(희귀성도 신분) |
| 답장 문구 틀 | 누리집 안 「답장 문구」 묶음 — 이름·금액은 빈 칸으로만 · 자동 채움 발송 없음 | N-7(2차) |
| 틀린 답 신고 | 문서마다 「쓰인 N / 틀림 신고 N / 마지막 고친 날」 3숫자 — F-22 통계가 처음 쓸 수 있는 화면이 된다 | N-10(2차) |

**ⓒ 순서**: 1차 = bo_kb_docs·md 입출력·승격 초안+승인. 2차 = 답장 문구·틀린답 신고 3숫자·초안 생성 조건(「같은 증상 N번 이상」만)·하루 상한·승인자 1~2명 지명(R-3 — CS팀장 한 명에게 초안 50장 몰림 방지). 3차 = 공개 도움말(N-9 — 내부가 두꺼워진 뒤 · CS팀장 승인 + 마케팅 확인 한 단계 더 + #23 금지어·식별정보 검사 통과 시만).

**ⓓ 게이트**: ①승인 안 된 문서(status≠'승인')가 어벤져스팀 호출 재료로 나가는지 → **0건**(WHERE 절 자체에서 배제 — if 분기 금지) ②식별정보 품은 초안 승인 시도 → **거부 로그** ③version 올려도 옛 판이 남는지(이력) ④음성 대조군: 재스캔을 빼면 승인이 **통과해 버리는 것**을 먼저 확인.

**ⓔ 하지 않는 것**: 외부 지식 긁어오기(CS팀장 직접 정의) · 자동 승격(사람 승인 없이 등재 0건) · 다른 테넌트 **티켓 원문**을 문서 근거로 저장 · 파일 cs.md 를 진실원으로 두기(내보내기용일 뿐).

## §3 [대메뉴 4. CS 관리 ▸ CS 현황]

**ⓐ 왜**: 자동화는 「몇 건 처리했나」로 재면 거짓말을 낳는다(숫자 올리려 애매한 것도 보냄). 봐야 할 숫자는 **①초안 그대로 나간 비율 ②사람이 고쳐 나간 비율 ③고객이 「이게 아니에요」 한 비율** — ③이 오르면 끄는 게 맞고, 끌 수 있어야 한다(§4 끄는 단추와 짝).

**ⓑ 화면·API·테이블**: F-20(대리점 CS현황·시각화)에 얹는 열 — 위 3비율 · `received_channel` 별 건수(쪽지가 전화를 줄였나) · 공지별 「보낸 날 / 그 뒤 7일 같은 유형 문의 변화」(N-13). 새 테이블 없음 — `bo_cs_tickets`·`bo_cs_ticket_logs`·호출 장부(§6)에서 집계만.

**ⓒ 순서**: 전부 2차(⑥사이클) — 셀 데이터가 쌓인 뒤에 뜻이 있다.

**ⓓ 게이트**: ①집계값 = 원본 티켓 수 검산 일치(F-20 완료 기준 그대로) ②통계에 본문·고객사 식별자 0건(F-22) ③음성 대조군: 「고객 답 대기」·중복 합침·장애 묶음 3건이 미처리 집계에서 **분리되는지**(R-11 — 하나라도 빠지면 대리점 평가가 분쟁이 된다).

## §5 [ERP 쪽 — CS 요청 보내기 · 받은 답 보기 · 로컬 큐 (백오피스 메뉴 아님 · 한 장)]

**ⓐ 왜**: 고객이 쓰는 입구다. **ERP 의 역할은 두 가지뿐 — 쪽지를 보내는 것과 받은 답을 보는 것**(교정② — 저장·분석·AI 는 전부 백오피스 몫). 실측상 ERP 에는 CS 화면 0건·본사행 HTTP 0건·큐 테이블 0건 — **길을 새로 낸다**. 그리고 쪽지는 핑이 아니다: 한 건이 사라지면 **고객이 쓴 글이 사라진다**. 그래서 기존 송신 코드(실패 시 버림)를 안 쓰고 DB 큐로 간다. 마지막으로 **「답 왔음」이 ERP 화면에 안 보이면 이 오더 전체가 역효과다**(R-7 — 우리가 1시간에 답해도 체감은 3일) — N-8 을 1차에 묶는다.

## §9 [입력과 달리 정한 것 · ⚠️미확인]

**입력과 달리 정한 것 (전부 「무엇을 왜」)**
1. **분류 5종 → 현장 7모양 교체 제안**(결-9) — DB명세서 §3 `category` 고정 목록과 다르다. 현장 피드백 우선 원칙 + 구현 0건인 지금이 유일하게 싼 시점. 단 **내가 확정하지 않고 결재로 올림**(결재본 갱신은 같은 결재로 — 10/7 작12 「쪼갠 조건을 뒤 문서에서 넓힘」 사고 재발 방지).
2. **IA §5-ⓓ「(가) 무경유부터」 권고의 지위** — §8-1 사장님 오더가 이미 갱신했다(어벤져스팀 연결이 목표). 이 설계서는 그 갱신을 따르되, 1차/2차 경계는 **법무 4건**이 긋는다(내 재량 아님).
3. **교차확인(§3-2ⓑ)을 2차·설정값으로** — 현장은 「답 갈리면 사람」을 1번 아래 2번으로 꼽았지만 비용 2배 결정이 결-7 에 달려 있어 결재 틀에 묶었다.
4. **개발 피드백의 「어댑터 3개는 그대로 쓴다」(§4-1)를 사장님 교정 ①로 대체** — Backoffice 2프로젝트가 ERP 를 ProjectReference 0건(PM csproj 실측)이라 재사용이 물리적으로 불가. **패턴만 본뜬다.** 같은 이유로 PM 사실목록의 「3사 어댑터 재사용」 표현도 이 판에서 폐기.
