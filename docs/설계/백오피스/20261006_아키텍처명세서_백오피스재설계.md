## §1 [ⓐ 3시스템 흐름도 — 무엇이 흐르고, 무엇이 절대 안 흐르나 (본오더 1항)]
```
[랜딩 landing.hitpan.kr · NCP]           [백오피스 back.hitpan.kr · NCP]          [ERP {고객사ID}.hitpan.kr · 고객 PC 로컬]
 가입·결제·다운로드만                      프로비저닝·고객·대리점 관리만              업무 처리만
   │ 가입서(이메일·추천코드·유입경로) ──Push──▶ │                                        │
   │ 결제(토스) ────────즉시 Push──────▶ │ 개통(설치·인증번호·연결) ──────────────▶ │ 설치
   │                                    │ ◀──Pull(5분)·보고── 직원 수·기기·버전·연결 신호 │
   │                                    │ ◀──개통 후 첫 보고── S-2 대표 아이디(화이트리스트) │
   │                                    │ ◀──일 단위 Push── 챗봇 메타(건수·유형·응답시간만) │
   │                                    │ ──공지·알림(F-38)·차단/해제(F-26)──────▶ │
```
- **절대 안 흐르는 화살표(#18·#22)**: ERP→백오피스 로 거래·금액·거래처명·BOM·재고·회계 등 **업무 데이터 일체 ✕** · 챗봇 **대화 본문 ✕** · 직원 개인정보 ✕ · 비밀번호·해시·토큰 ✕(#40). 백오피스→ERP 로 원격 조작 ✕(#30 — 관찰·공지·차단 신호만). 랜딩↔ERP 직접 연결 ✕(백오피스 경유).
- 영업 귀속 사슬(기능정의서 F-5·F-8): 백오피스(코드 발급) → 랜딩(가입서 코드칸) → 백오피스(tenant FK 귀속) — 상호명 글자 조인 대체(Z2 · ⓪사이클).

## §2 [ⓑ 권한 2갈래 서버 강제 구조 (회의록 §3 안철수 ②)]
- **격리는 화면이 아니라 서버.** 대리점 토큰의 모든 조회에 JWT 클레임의 reseller_id 를 **서버가 WHERE 주입** — 파라미터 수신 즉시 반려(#2 의 백오피스판).
- 주입 지점은 **한 곳**(베이스컨트롤러 또는 미들웨어 공통 필터) — 컨트롤러마다 따로 금지. 근거: 9/22 `TenantMiddleware` 화이트리스트 3연발(기억 메모 `project_mainpc_physical_id_roundtrip_20260922`) — 경로마다 따로 등록하는 구조가 세 번째 재발의 뿌리였다.
- 미들웨어 화이트리스트(익명 허용 경로)는 **신설 라우트 추가 시 명시 등록 + 음성 대조군 게이트**(미등록 경로 401 FAIL 을 실제로 봄)를 짝으로 — 등록 없는 추가 금지.
- 역할 = 단일 enum·단일 컬럼(F-1 · 값은 Q-1). 본사 마스터도 대리점 데이터 **조회만**(「접근」≠대필 · 안철수 ②). 게이트 = A 토큰→B 데이터 403/빈집합 실측(기능정의서 §0 공통 기준).
- 구조 게이트 1건 추가(안철수 권고 · 2차): **`reseller/v2` 전 라우트를 열거해 공통 필터 통과 여부를 자동 대조** — 필터를 안 지나는 라우트가 하나라도 있으면 FAIL(새 라우트 추가 시 자동으로 걸린다 · 9/22 「미들웨어를 지나가 보지 않는 게이트」 재발 방지).

## §3 [ⓒ api/reseller/v2 신설 라우트 체계]
- 현행: `reseller/v2` 라우트 0(선행검증 B) — 대리점 화면이 없는 API 를 부른다(B 2-15·16). 신설 원칙:
| 묶음 | 라우트 줄기 | 받침 F | 공통 |
|---|---|---|---|
| 영업 | `api/reseller/v2/sales/*`(현황·추천코드) | F-5·F-6 | 전 라우트 §2 공통 필터 통과 |
| CS | `api/reseller/v2/cs/*`(티켓·인계·현황) | F-14~F-20 | 금지필드 검사(DB명세서 §4) |
| 구독·정산 | `api/reseller/v2/subscription/*` · `/settlement/*` | F-29·F-32·F-34·F-35 | confirmed 만 집계(Z3) |
| 본사 전용 | `api/admin/*`(기존 줄기 유지 — 승인·차단·이관·정산 확정·관찰) | F-3·F-26·F-30·F-36~F-42 | 민감 작업 = 감사 기록(F-42) 경유 |
- 본사/대리점 라우트 줄기를 섞지 않는다 — 같은 데이터라도 범위가 다르면 다른 문(#7 혼용 금지의 백오피스판). 상태 전이(결제·티켓·차단)는 라우트가 몇 개든 **전이 로직은 서버 한 곳**(안철수 Z3).

## §5 [ⓔ ERP→백오피스 신설 송신 — payload 화이트리스트 원칙 (안철수 ③)]
- 신설 송신 2줄기: **S-2 대표 아이디**(개통 후 첫 보고 · F-10) · **챗봇 메타**(일 단위 · F-19) — **ERP 쪽은 한 송신 모듈**(클라이언트·인증·재시도 공용 · 2차 조건) — 줄기마다 복제하면 봉합도 두 번(「고쳤다≠갔다」 자리).
- 원칙: payload 는 **필드 화이트리스트로 못 박고, 서버가 초과 필드를 거부**(S-3 텔레메트리 금지필드 검사와 같은 축). 허용 목록 = DB명세서 §2(tenants 4칸)·§3(`bo_cs_chatbot_meta` 5칸) — 목록 밖 필드 도착 = 거부+로그.
- 게이트는 글자가 아니라 동작: 금지 필드를 실은 시험 payload 가 **실제로 거부된 로그**를 보고 통과(음성 대조군) — 통과 로그만 보는 게이트 금지.
- 송신 실패는 ERP 쪽에서 재시도·보류(고객 업무 비차단 — #30 자가 회복 원리) · 본사 수신부는 멱등(같은 보고 2회 = 1건).
