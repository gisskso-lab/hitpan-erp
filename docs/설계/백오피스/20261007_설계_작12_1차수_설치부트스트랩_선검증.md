## §1 [흐름] 지금 → 바꾼 흐름 (요청 1건이 지나가는 길)

### 지금 (`InstallerBootstrapController.cs:45-235`)

```

② 빈 값 검사 → 400
③ DB 열기 · License:Pepper 로 licenseKey HMAC
④ tenants WHERE license_key_hash=@Hash AND status='active'  (+ landing_signups LEFT JOIN)
⑤ 못 찾으면 → LogWarning + 401            🔴 여기서 끝 — 실패가 어디에도 기록되지 않는다
⑥ 도메인 문자열 조립
⑦ 🔴 if (_cfDomain.IsConfigured) → IssueAsync(DNS) → IssueTunnelAsync(터널 발급)
       → UpdateDnsTunnelTargetAsync(DNS CNAME PATCH) → UpdateTunnelIngressAsync(ingress PUT)   [:117-149]
⑧ 부트스트랩 토큰 생성 · HITPAN_BOOTSTRAP_TOKEN_KEY 취득
⑨ INSERT serial_verify_attempts (result='installer-bootstrap')   ← 성공에서만 돈다

🔴 **④ 를 통과하면 ⑦ 이 무조건 돈다.** 즉 **유효 라이선스 키 1개 = Cloudflare DNS·터널을 몇 번이든 흔들 수 있는 권한**이고,
**틀린 키는 횟수 제한 없이 무한히 시도**할 수 있다(⑤ 가 기록조차 안 하므로 잠금 기계가 깨어날 재료가 없다).

```

### ⇒ 「요청에 사업자번호를 추가로 요구한다」가 깨뜨리는 것

3. ⇒ **#27·#28·#30 위반** — 고객 PC 가 스스로 못 살아난다. **작11 식 봉합과 결과가 같아진다.**

## §3 [ⓐ] 선검증 설계 — 갈래 A 채택 · 갈래 B 는 결재 올림

### §3-1 갈래 A (1차수 채택) — 서버측 2중 조건

| 중 | 조건 | 재료 | 지금 있나 |
|---|---|---|---|
| 1중 | `tenants.license_key_hash` 일치 **AND** `status='active'` | 요청의 `licenseKey` | 🟢 있다 (`:88`) |
| 2중 | 그 **테넌트에 2중 일치가 성립할 가입서가 실재** — `landing_signups` 에 `tenant_id = t.tenant_id` 로 묶인 행이 있고 그 행이 `biz_no_hash` 를 보유 | **서버 DB 만** | 🟢 재료 있다 (`biz_no_hash NOT NULL` · Z2 가 `tenant_id` 키를 붙였다) |

- **읽기 전용 · 쓰기 0 · DDL 0.** 이미 ④ 가 같은 두 표를 조인한다 ⇒ **새 표 접근 없음.**
- 🔴 **2중 조건을 「회사명 글자 폴백」으로 성립시키지 않는다.** Z2(`20261006작8`)가 글자 조인을 **키 조인으로 바꾼 이유**가
  「동명 타사 가입서 해시로 남의 라이선스가 통과」였다(`31_backoffice_z2_...sql:55`). 글자 폴백을 **인프라 발동 조건**으로 쓰면
  그 구멍을 CF 조작 권한에 다시 연결한다. ⇒ **키로 묶인 행만 2중 재료로 센다.**
- ⚠️ **이 조건이 막는 것과 못 막는 것을 정직하게 적는다.**
  - 막는다: 테넌트 행만 있고 **가입 사슬이 없는** 행(수동 생성·마이그 잔재·시험 행)으로 CF 를 흔드는 것.
  - **못 막는다**: 공격자가 **정상 고객의 유효 라이선스 키를 쥔 경우.** 그건 ⓐ 의 사정권이 아니다 — 그 경우를 줄이는 것은 **ⓑ(무차별 대입 차단)** 와 **ⓒ(응답에서 비밀값 축소)** 다. 🔴 **「ⓐ 로 막았다」고 적으면 다음 사람이 속는다.**

### §3-2 갈래 B (1차수 밖 · 결재 올림)

요청에 사업자번호를 추가하고, **워치독만 다른 증표**(설치 때 받은 `bootstrap.token` 재제시)로 분기한다.
설치 EXE·워치독·`db.conf`·토큰 수명·재사용 방지(jti)가 전부 걸리고, **구 설치본·구 워치독 하위호환 경로**가 추가로 필요하다.
⇒ **규모가 1차수를 넘는다.** 정식 출시 전 「테넌트별 파생키 전환」(`:127-130` 주석의 기결재 항목)과 **같은 묶음**으로 가는 것이 맞다 — **확인 필요**.

### §3-3 🔴 갈래 A 의 최대 위험 (C-3)

갈래 A 는 「정상 신규 고객에게는 2중 재료가 **항상** 생긴다」를 전제한다.
그 전제는 **「가입→결제확인→부트스트랩」 사슬 종단이 미측정**이라 **지금은 가설이다**([1-V] §8).
⇒ **게이트 G-2 양성 경우(정상 사슬 테넌트는 CF 가 돈다)를 CI DB 에서 반드시 세운다**(§6).
⇒ 🔴 **게시 전 조건으로 「실제 가입 1건이 2중 재료를 만드는가」 1회 실측을 추가한다**(§8 R-3).
만약 운영에 **키 미연결 옛 테넌트**가 많다면 갈래 A 는 그 고객들의 터널 자동 발급을 끈다 ⇒ **C-1 읽기 결과가 선행 조건**이다.

## §4 [ⓑ] 잠금 정책 — 숫자와 그 근거

### §4-1 숫자 (🔴 발명 0 — 기존 값을 그대로 쓴다)

| 항목 | 값 | 출처 |
|---|---|---|
| 실패 허용 N | **5회** | `SerialVerifyController.cs:25` `MaxFailedAttempts = 5` (사장님 헌법 「5회 실패 시 잠금」 `:16`) |
| 실패 집계 창 | **60분** | `SerialVerifyController.cs:26` `FailWindowMinutes = 60` |
| 잠금 유지 | **60분 → 자동 해제** 🆕 | 창과 같은 값. **기존 기계는 영구+본사 수동 해제**(`:72-79`)라 그대로 쓰면 재설치가 영구 차단된다 |
| 잠금 **키 단위** | **`client_fingerprint` 해시 단위만** | `serial_verify_locks` 의 `UNIQUE KEY uk_fingerprint` 가 그 하나다 (출하 DDL `:493`) |
| IP | **기록만** (`serial_verify_attempts.client_ip` — 이미 한다) | 잠금 키로 쓰지 않는다 — 근거 §4-2 |

### §4-2 왜 IP·라이선스 키를 잠금 키로 쓰지 않나 (결재문 ⓑ 는 「키·IP」라 적혀 있다 — **확인 필요**)

1. 🔴 **IP 로 잠그면 한 사람의 오타가 옆 사람 설치를 막는다.** 한 고객사·한 건물의 여러 PC 는 NAT 뒤에서 **같은 공인 IP** 로 보인다. 모바일 통신사 대역이면 전혀 무관한 고객끼리 겹친다.
2. 🔴 **키·IP 단위 집계는 DDL 변경을 부른다.** `serial_verify_attempts` 의 인덱스는 `(tenant_id,attempted_at)` · `(client_fingerprint,attempted_at)` · `(result,attempted_at)` **셋뿐**이고 `submitted_hash`·`client_ip` 에는 **인덱스가 없다**(출하 DDL `:471-473`). 키·IP 단위로 세려면 **INSERT ONLY 로 계속 자라는 표를 full scan** 하거나 **인덱스를 추가**해야 한다 ⇒ **1차수의 「DDL 0」 제약(§8 되돌림)과 충돌.**
3. ⇒ **1차수는 지문 단위.** 키·IP 단위 가산은 **인덱스 추가와 함께 2차수 이후** — 사장님 결재문 문구와 다르므로 **PM 이 확인해 올린다.**

### §4-3 🔴 정상 재설치가 잠기지 않는 근거 (사장님 PC 재설치가 막히면 P0)

| # | 근거 | 코드 사실 |
|---|---|---|
| 1 | **카운터는 「키 불일치」에서만 오른다** | ⑤ 는 `tenant is null` 일 때만 돈다. **본사 장애·DB 오류·CF 실패는 catch → 500** 이라 카운터에 안 닿는다 ⇒ **본사가 아파도 고객이 잠기지 않는다** (G-6 이 이걸 잠근다) |
| 2 | **정상 재설치는 같은 유효 키를 쓴다** ⇒ 실패 0 ⇒ 가산 0 | ④ 가 그 테넌트를 찾는다 |
| 3 | **성공이 카운터를 0 으로 리셋한다**(⑧-b) | 기존 `serial/verify` 성공 경로와 동일(`:135-139`) ⇒ 이전 오타가 다음 설치로 넘어가지 않는다 |
| 4 | **재설치는 같은 PC = 같은 지문**(`{computername}-{username}`) | 전 설치가 성공했다면 그 지문 카운터는 이미 0 |
| 5 | **워치독은 실패 경로에 들어가지 않는다** | 유효 키를 `db.conf` 에서 읽는다. **키가 없으면 요청 자체를 안 보낸다**(`TunnelTokenRecovery.cs:78-85` 가 먼저 return) ⇒ 무인 반복 호출이 카운터를 밀어 올릴 길이 없다 |
| 6 | **브라우저 시리얼 검증 실패가 설치를 잠그지 않는다** | 같은 표를 쓰지만 **지문 입력값의 종류가 다르다** — `serial/verify` 는 「user-agent+해상도+timezone」(`:52-53`), 부트스트랩은 「컴퓨터명-사용자명」 ⇒ 해시가 겹치지 않는다 |
| 7 | 🔴 **5회를 넘겨도 60분 뒤 스스로 열린다** | 신설. 기존 기계의 영구 잠금을 **이 설계가 되돌려 푼다** ⇒ 봉합 후가 봉합 전보다 **덜** 막는 유일한 지점 (G-4) |

- `result` 값은 **구분해서** 남긴다 — `installer-mismatch` · `installer-locked` · `installer-no-biz-proof` · (성공) `installer-bootstrap`.
  같은 표를 두 문이 공유하므로 **구분 없이 남기면 추적이 섞인다.** `result` 는 `varchar(20)` ⇒ 🔴 **값 길이 20자 이내** 확인 필요(`installer-no-biz-proof` = 22자 ⇒ **`installer-nobizproof`(20자)** 로 줄인다).

**워치독이 읽는 항목은 `domain.tunnelToken`·`domain.tunnelId`·`domain.tunnelTokenIssued` 셋뿐이다**(전수 grep 실측).
⇒ **단계 2 에서 비밀값성 4항목 중 2개(`bootstrap.token`·`bootstrap.tokenKey`)를 뺀다** ＋ `tenant.*` 5항목(연락처 2개 포함)도 뺀다.
⇒ 🔴 **터널 2항목은 두 단계 모두 필요하므로 못 뺀다** — 그 사실을 숨기지 않고 적는다. 1차수로 비밀값성 4항목 중 **2개**가 줄어든다.

### §5-2 단계를 서버가 어떻게 가르나

- 요청에 **선택 필드 1개**를 더한다(`BootstrapRequest` 에 nullable 추가 · #1 추가만). 값 2종: 생략 / 「터널 복구」 의미의 값 1개.
- 🔴 **생략 = 지금과 똑같은 18항목 전체 응답**(기본값). **절대 반대로 만들지 마라** — 기본을 축소로 잡으면 **이미 고객 PC 에 깔린 구 설치본·구 워치독이 전부 깨진다**(G-8 이 이걸 잠근다).
- `installerVersion` 으로는 **가를 수 없다** — 설치 EXE 는 `{#AppVersion}`, 워치독은 `VersionInfo.Current` 로 **둘 다 제품 버전**이라 모양이 같을 수 있다. 추측으로 가르면 조용히 틀린다.
- **워치독 1곳만** 그 필드를 보내게 바꾼다. 설치 EXE 무변경.
- ⚠️ **단계적 발효**: 고객 PC 의 **구 워치독**은 필드를 안 보내므로 전체 응답을 받는다(안 깨진다). 자동 업데이트로 새 워치독이 깔린 PC 부터 축소가 발효. ⇒ 「게시 직후 전 고객 축소」가 아니다. 그렇게 적어야 다음 사람이 안 속는다.

### §5-3 🔴 응답 항목 **이름**을 새로 추가하지 않는다

구 설치본의 `ExtractJsonValue(RawResponse, 'tokenKey')` 는 **평면 이름 검색**이다(`iss:612-621`).
`domain`·`bootstrap` 안에 이름이 겹치는 새 항목을 더하면 **구 설치본이 엉뚱한 값을 집는다.**
⇒ **ⓒ 는 빼기만 한다. 더하지 않는다.** (`purpose` 는 **요청** 필드라 무관.)

## §6 [게이트] 판정 게이트 — 전부 동작 · 각 게이트의 FAIL 재현법

이름: `InstallerBootstrapPreverifyGateTests` (`src/HitPan.Tests/Integrity/`) · CI 등록 = `.github/workflows/build-and-test.yml` **`db-gate` 잡의 `GATES` 변수에 `|InstallerBootstrapPreverifyGate` 추가**(작11 `BackofficeAnonymousAdminApiGate` 와 같은 방식).
🔴 **DB 게이트는 `db-gate` 잡에서만 계측된다** — 개발 PC 는 `hitpan` 계정이 `CREATE DATABASE` 를 거부한다. 로컬 전체 회귀는 `HITPAN_GATE_SKIP_OK=1` 이 필요하다.
🔴 **조용히 초록인지는 소요시간으로 가른다**(10/7 작10 사고: DB 없이 `Passed 10/Skipped 0/1초`, DB 있으면 30초). `[SKIP]` 0건 검사는 기존 단계가 이미 한다.

## §7 [경계] B4 와의 선 — 1차수에서 어디까지 손대나

| 항목 | 1차수 (B3) | 3차수 (B4) |
|---|---|---|
| `InstallerBootstrapController.cs` | **수정** (ⓐⓑⓒ) | 무접촉 |
| `LandingPublicController.cs` (`license/claim`) | 🚫 **무접촉** | 수정 |
| `landing_signups.biz_no_hash` · `tenant_id` | **읽기만** (존재 여부 판정) | 2중 일치 비교 |
| 실패 문구가 키↔사업자번호를 가르는 oracle | 🚫 **손대지 않는다** — `:185`·`:211` 두 분기 문구 통일은 B4 | **봉합 대상** |
| 부트스트랩 401 문구·상태코드 | 🚫 **그대로 둔다** (근거 아래) | — |

🔴 **부트스트랩 401 을 1차수에서 바꾸지 않는 이유 2개**
1. 워치독이 **401 을 「시리얼 무효/미승인」으로 해석해 로그 문구를 가른다**(`TunnelTokenRecovery.cs:103-110`). 상태코드를 바꾸면 그 진단이 거꾸로 된다.
2. 문구 oracle 봉합은 **B4 와 같은 판정**이다. 두 차수가 같은 자리를 따로 고치면 뒤 차수가 앞 차수를 덮는다(#1 위반 경로).

**신설 423 은 안전한가** — 워치독은 `!IsSuccessStatusCode` 로 떨어져 「본사 응답 오류(일시 장애면 다음 사이클 재시도)」로 로그하고 **다음 사이클에 재시도**한다(코드 경로 확인). ⇒ **동작이 깨지지 않는다.** 단 워치독은 유효 키를 쓰므로 **애초에 423 에 닿지 않는다**(§4-3 5번).
