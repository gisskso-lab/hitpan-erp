## §1 [C-5 행 범위 강제 — 1순위 · 이 사이클의 핵심]

### 1-1 왜 「컨트롤러마다」가 아니면 안 되는가
지금 36엔드포인트의 유일한 장벽은 본사가 화면에서 고치는 `bo_permissions.allowed_roles` CSV 1개다(선행검증 §2-3-c). CSV 는 **키 단위 통과/거부**라 구조적으로 행을 못 자른다(`BoPermissionService.cs:66` — `reseller_id` 를 아예 안 읽는다). 컨트롤러마다 손으로 `WHERE` 를 넣는 설계는 **9/22 `TenantMiddleware` 화이트리스트 3연발**과 같은 모양이다(아키 §2 · 기억 `project_mainpc_physical_id_roundtrip_20260922`) ⇒ 금지.

### 1-2 구조 — 거부 기본값(deny-by-default) 1곳
```
대리점 토큰 요청
   │
   ├─ ① ResellerScopeGuard  (전역 IAsyncAuthorizationFilter · 등록 1줄)
   │      · reseller_id 클레임 있나? 없으면 통과(본사·익명은 이 필터 소관 아님)
   │      · 이 엔드포인트에 [ResellerScoped] 가 있나?
   │           없다 → 403 (**기본값**)      ← 36엔드포인트가 여기서 한 번에 닫힌다
   │           있다 → HttpContext.Items["bo.reseller_scope"] = 클레임값
   │
   ├─ ② ResellerScopeArgumentFilter (같은 등록 · IAsyncActionFilter)
   │      · ActionArguments 안의 resellerId / reseller_id 를 **클레임값으로 덮어쓴다**
   │        (비어 있으면 채우고, 남의 값이면 바꾼다 — 클라이언트 입력은 신뢰하지 않는다)
   │
   └─ ③ IResellerScope (주입 서비스) — SQL 의 @Rid 는 **이 서비스에서만** 온다
          · Current() 는 HttpContext.User 만 읽는다. 쿼리·바디·헤더 경로 0
          · 대리점 토큰인데 값이 없으면 throw (fail-closed)
```
- **적용 범위**: `HitPan.Backoffice.API` 의 **모든** 컨트롤러. 등록 지점 = `src/HitPan.Backoffice.API/Program.cs:23` `AddControllers()` 에 필터 2개 추가 — **파일 1개 · 줄 2개.**
- **기존 10컨트롤러 36엔드포인트는 손대지 않는다**(#1 추가만). 대리점 토큰이 거기 닿지 못하게 되는 것으로 봉합이 끝난다.
- **대리점이 실제로 쓸 라우트만** `[ResellerScoped]` 를 붙인다 — 이번 사이클은 `ResellerPortalController`(`api/reseller-portal/*` 3개) 와 신설 `api/reseller/v2/*`(아키 §3). 붙이는 순간 ②③ 이 범위를 강제한다.
- **익명 입구**는 이 필터가 건드리지 않는다(클레임 없음) — 익명 4개는 작11 P0 소관.

### 1-3 `[FromQuery] resellerId` 처분
| 자리 | 지금 | 설계 |
|---|---|---|
| `ResellerSerialController.cs:39,46` | `[FromQuery] string? resellerId` · 비우면 `WHERE` 미부착 = 전건 | 라우트는 **본사 전용**(`[ResellerScoped]` 없음) ⇒ 대리점은 403. 본사에게는 「필터」로서 정당 ⇒ **파라미터 유지** · ② 가 대리점 토큰일 때만 덮어쓴다 |
| `ResellerSettlementController.cs:44,52` | 같음 | 같음 |
| `ResellerPortalController.cs:156-166` | 이미 클레임만 읽음(정상) | `IResellerScope` 로 **교체**해 범위 출처를 1개로 모은다. 동작 동일 |
⇒ 「비우면 전건」이 위험한 이유는 **대리점이 그 라우트에 닿을 수 있다는 가정** 때문이었다. 닿지 못하게 하는 것이 봉합이고, 파라미터 제거는 본사 기능을 깎는 일이라 하지 않는다(#33 — 오더에 없는 요구 금지).

### 1-4 `bo_permissions` CSV 와 행 범위 분리
- CSV 는 **기능 접근**만 정한다. 행 범위는 ①②③ 이 정한다 ⇒ **CSV 에 대리점 역할을 체크해도 본사 엔드포인트는 여전히 403**(①이 CSV 를 안 본다). 이것이 게이트 G-4 의 음성 대조군이다.
- 추가 방어: `BoPermissionService.UpdateAllowedRolesAsync` 에 **역할 화이트리스트**(4값만) + **본사 전용 키에 대리점 역할 저장 거부**. 저장 거부 시 400 + 사유 문장(한글).

## §2 [역할 enum 4값 — 값·표·토큰]

### 2-1 4값과 화면 표시
| 내부값(단일 컬럼) | 화면 표시 | 범위 |
|---|---|---|
| `platform_owner` | 본사 대표 | 전체 + 설정·권한·감사 |
| `platform_admin` | 본사 관리자 | 전체(설정·권한 제외) |
| `reseller_admin` | 대리점 관리자 | **자기 것만** |
| `reseller_user` | 대리점 담당자 | 자기 것만(읽기 중심) |
- 내부값은 **기존에 코드가 이미 읽고 있는 철자**를 쓴다(`platform_owner` 5곳·`reseller_admin` 발급값) ⇒ 전환 시 깨지는 자리가 17줄에서 줄어든다. 새 철자(`owner`·`admin`)를 만들면 죽은 분기가 또 생긴다.
- `role` **단일 컬럼 1개**가 축이다. 본사/대리점 갈래는 `bo_users.reseller_id` **NULL 여부**로 파생한다(계층 추가 아님 — 두 갈래 그대로).

### 2-2 담는 표 — C-1 ⓐ (실제 `DESCRIBE` 2026-10-07 · 로컬 `hitpan_backoffice`)
```
bo_users   user_id char(36) PRI · email varchar(255) UNI · password_hash varchar(255)
           name varchar(100) · role varchar(32) MUL · reseller_id char(36) NULL MUL
           is_active tinyint(1)=1 · failed_login_cnt int(11)=0 · last_login_at
           created_at · updated_at                                    [0행]
bo_permissions  permission_key varchar(80) PRI · … · allowed_roles varchar(200)   [17행]
platform_admins.role  enum('super_admin','billing_admin','cs_admin','readonly')
```
🟢 **`bo_users` 에 칸 추가 0 · ALTER 0.** 로그인에 필요한 칸(`password_hash`·`is_active`·`failed_login_cnt`·`last_login_at`)이 전부 있다.
🟢 **ENUM 2표 ALTER 는 필요 없다.** 선행검증 §2-4-가의 「ENUM 2표 ALTER 필수」는 **ⓑ(2표 유지) 전제**였다. ⓐ 채택으로 `platform_admins`·`reseller_accounts` 는 **읽기 전용 동결**(파일·표·행 보존 — #1·#37). 값을 새로 넣지 않으므로 ENUM 을 건드릴 이유가 없다.

### 2-3 마이그 — `installer/backoffice/40_bo_users_role4_auth.sql` (신설 · 멱등)
| 단계 | 내용 | 안전장치 |
|---|---|---|
| ㉠ | `platform_admins` 중 `role='super_admin'` → `bo_users` INSERT(`role='platform_owner'`, `reseller_id=NULL`, `password_hash`·`email` 그대로 이관) | `INSERT … SELECT … WHERE NOT EXISTS`(email 기준) = 재실행 안전 |
| ㉡ | `reseller_accounts`(있으면) `reseller_admin`→`reseller_admin` · `reseller_user`→`reseller_user` 이관 | 표 부재 시 건너뜀(로컬에 표 없음 — `information_schema` 확인 분기) |
| ㉢ | **`readonly`·`reseller_readonly`·`billing_admin`·`cs_admin` 행은 이관하지 않는다** | 행수를 `bo_migration_notes` 성격의 로그로 남기고(또는 마이그 출력), 그 계정은 **기존 입구 폴백으로 계속 로그인된다**(끊기지 않음). PM 이 집계를 보고 사장님께 올린다 ← **C-3 「운영에 행이 있으면 보류」 분기의 실체** |
| ㉣ | `bo_permissions` 32행 **UPSERT** — `allowed_roles` 를 4값으로 재작성. 단 **`updated_by IS NOT NULL` 행(본사가 손으로 고친 행)은 덮지 않는다** | 17행→32행 보강 · 32행이면 값만 교정 ⇒ C-8 미확인 흡수 |
| ㉤ | `bo_users.role` **CHECK 제약** 4값 (MariaDB 11.4) | enum 대신 varchar+CHECK — 값 추가 시 ALTER 1줄 |
🔴 `bo_users.reseller_id` → `resellers.reseller_id` FK 는 **이번에 걸지 않는다**(본사 계정은 NULL · 기존 데이터 미확인). ⚠️ 다음 사이클 DB매니저 판정.

## §3 [전환 순서 — 지금 들어오는 사람이 안 끊긴다 · 작11 과 충돌 없음]

### 3-1 토큰 발급을 한 함수로 모은다 (= 「역할 판정 서버 한 곳」)
```
POST api/backoffice/auth/login   (신설 · 단일 입구)
   1) bo_users 조회  → 있으면 4값 그대로
   2) 없으면 폴백: platform_admins → 매핑(super_admin→platform_owner)
                  reseller_accounts → 매핑(reseller_admin/reseller_user)
   3) IssueTokens(role=4값,
                  reseller_id=bo_users.reseller_id(대리점만),
                  account_type=파생값)   ← 한 함수. 다른 발급 경로 0
```
- `account_type` **파생 규칙**: `role∈{platform_owner,platform_admin}` → `"platform_admin"` · `role∈{reseller_*}` → `"reseller_admin"`. **작11 이 세운 `account_type` 축 방어가 그대로 유효**하고, 동시에 `platform_owner` 역할이 처음으로 발급된다 ⇒ Owner 7줄·`OwnerOnly` 5화면이 열린다(C-2).
- 🔴 `OwnerOnly` 정책은 지금 `RequireClaim("role","owner")`(`src/HitPan.Backoffice/Program.cs:61-62`) 다. 4값에 `owner` 는 없으므로 **`platform_owner` 로 교정**해야 열린다 — 교정 없이 「owner 가 생겼다」고 보고하면 「고쳤다 ≠ 갔다」다.

### 3-2 2단 전환
| 단 | 하는 일 | 끊김 |
|---|---|---|
| **1단 (작10)** | 단일 입구 신설 · 기존 2입구(`:32`·`:85`) **살려 둔다**(#1) · Web `signin` 은 단일 입구만 부른다 · 정책·사이드바·가드를 4값으로 교정 | 0 — `bo_users` 에 없는 계정도 폴백으로 같은 범위로 들어온다 |
| **2단 (다음 사이클)** | 폴백 사용 0건을 로그로 확인한 뒤 기존 2입구 비활성(파일·라우트 보존 · 410 안내) | 폴백 0건 확인이 조건 |
- Web 쪽은 이미 API 응답의 `role`·`accountType` 을 그대로 쿠키 클레임에 담는다(`src/HitPan.Backoffice/Controllers/BackofficeAuthController.cs:67,85`) ⇒ **API 가 4값을 주면 Web 은 자동으로 4값이 된다.** Web 에서 고칠 것은 ① 단일 입구 호출 ② 정책 3개 ③ 로그인 성공 후 이동 경로(지금 대리점도 `/admin/dashboard` 로 보낸다 — `:94` 계열) 세 자리뿐.
- 「역할 지정 → 즉시 반영」은 **상향과 하향을 나눠** 설계한다 ⇒ **§3-3**(PM 조건부 반려 반영 · 10/7).

### 3-3 상향은 재로그인 · **하향·차단은 즉시 끊긴다** (PM 조건부 반려 보강 · 10/7)

🔴 **반려 사유가 맞다.** 권한을 **낮추거나 끄는 것**이 재로그인까지 미뤄지면 그 계정은 토큰 수명(쿠키 8시간 — `src/HitPan.Backoffice/Program.cs:51` `ExpireTimeSpan`) 내내 계속 들어온다. 이 레포는 같은 구멍을 **이미 적발하고 못 봉합한 상태**다(작3·작4 병렬검증 P1-01 — 「계정을 끈 뒤에도 8시간 토큰 유효 · 차단 수단 0」). 백오피스에 같은 구멍을 새로 파면, 이 사이클의 질문(「권한이 실제로 강제되는가」)에 **아니오**가 된다.

#### (가) 채택 방안 — **후보 1(매 요청 라이브 판독)** + 「좁은 쪽 우선」 규칙
후보 2(권한변경 시각 비교)는 **요청당 읽기가 똑같이 생기는데**(시각을 어딘가서 읽어야 한다) 캐시를 두면 그 TTL 만큼 차단이 늦는다 — 캐시가 쉬운 것이 장점이 아니라 **차단 지연이 설계에 들어오는 것**이 단점이다. 후보 3(폐기 목록)은 상태를 따로 관리해야 해 이 사이클에 무겁다(PM 판단과 동일). ⇒ **후보 1 채택.**

강제 지점은 **늘리지 않는다.** §1-2 의 전역 필터가 이미 한 곳이므로 그 앞에 단계 ⓞ 를 넣는다(필터 1개가 `BoAccessGuard` 로 역할이 하나 늘 뿐, 등록 줄·파일 수는 그대로):
```
ⓞ 라이브 계정 판독 (전역 필터 안 · 요청당 1회 · 캐시 없음)
     SELECT role, reseller_id, is_active  (토큰 sub = 키)
       FROM platform_admins  WHERE admin_id=@Sub
     UNION ALL                                    ← #16 (연결 1개 · 왕복 1회)
     SELECT role, reseller_id, is_active
       FROM bo_users         WHERE user_id=@Sub
   ├ 행 0건           → 403 (계정 삭제·이관 미완 = fail-closed)
   ├ is_active = 0    → 403 「계정이 비활성화되었습니다」          ← 즉시 차단
   ├ 갈래 변경(본사↔대리점) → 403 「소속이 변경되었습니다. 다시 로그인해 주세요」
   ├ reseller_id 불일치     → 403 (같은 문장)                      ← 소속 변경 즉시 차단
   └ 유효역할 = **좁은 쪽**(토큰 역할, DB 역할 중 낮은 등급)
        본사 사다리   platform_owner(2) > platform_admin(1)
        대리점 사다리 reseller_admin(2) > reseller_user(1)
   이후 ①②③ 은 토큰 역할이 아니라 **유효역할·DB reseller_id** 로 판정한다
```
| 변경 | 언제 먹히나 | 왜 그렇게 두나 |
|---|---|---|
| **하향**(역할 낮춤) | **다음 요청부터** — DB 가 좁으면 좁은 쪽이 이긴다 | 반려 요구 그대로 |
| **비활성**(계정 끔) | **다음 요청부터** 403 | 작3·작4 P1-01 과 같은 구멍 차단 |
| **소속 변경**(대리점 이동) | **다음 요청부터** 403 + 재로그인 안내 | 옛 소속 데이터가 한 요청도 더 안 나간다(fail-closed) |
| **상향**(역할 올림) | **재로그인 시** — 토큰이 좁으므로 그대로 좁다 | PM 요구 ①. 그리고 **메뉴는 토큰 클레임에서 그려진다** ⇒ 상향을 즉시 먹이면 「API 는 되는데 메뉴에 없다」가 되어 **G-6(메뉴↔진입 일치)이 깨진다** |
🟢 이 비대칭은 공짜가 아니라 **G-6 을 지키기 위한 선택**이다. 올리는 쪽만 재로그인을 요구하므로 안전한 방향으로만 느리다.

#### (나) 비용 — 실측 숫자
- **실측**(2026-10-07 · 로컬 `hitpan_backoffice` · MariaDB 11.4.10 · `SHOW PROFILES` 6회): 위 `UNION ALL` 1왕복 **0.82 / 0.82 / 0.84 / 1.09 / 1.39 / 2.46 / 3.65 ms**, 중위 **≈1.2ms**. 두 조회 모두 **PK 점 조회**(`platform_admins.admin_id` PK · `bo_users.user_id` PK).
- 지금 상태와의 차이: `[BoPermission]` 32엔드포인트는 `bo_permissions` 를 **60초 캐시**로 읽어(`BoPermissionService.cs` `CacheTtl=60s`) 요청당 DB 읽기가 사실상 0 이다 ⇒ ⓞ 는 **요청당 왕복 1회를 새로 만든다.**
- 규모: 백오피스 사용자는 본사 계정 **2행**(실측) + 대리점(로컬 0행) ⇒ ⚠️**가설** — 동시 사용자 10명 미만, 화면 전환당 요청 수 개. 하루 수천 요청 규모이면 추가 부하는 **초당 1왕복 미만**이다. ⚠️ NCP 운영은 네트워크 왕복이 더해지고 **미측정**(#39).
- ⚠️**캐시를 넣지 않는다.** TTL 을 두는 순간 「즉시」가 그 TTL 만큼 거짓이 된다. 성능 문제가 실제로 측정되면 그때 **별건**으로 올린다(선반영 금지 — #33).

#### (다) 구현 범위
🟢 **이 사이클에 포함한다.** 갈래 ㄱ 이 어차피 새로 쓰는 필터 안에 쿼리 1개·분기 5개가 늘어난다 — 새 표·새 상태·새 배경작업 **0**. 별건으로 뗄 근거가 없다.
⚠️ 2단 전환 중에는 `bo_users` 와 기존 2표에 같은 사람이 있을 수 있다 ⇒ ⓞ 는 `bo_users` 행을 **우선**으로 쓰고(이관 완료분), 없으면 `platform_admins` 행을 쓴다. 두 행이 다 있고 역할이 다르면 **좁은 쪽**을 쓴다(fail-closed).
🔴 `reseller_accounts` 는 로컬에 표가 없어(선행검증 §2-1-나) ⓞ 의 `UNION ALL` 에 **조건부로** 넣는다 — 표 부재 시 그 갈래를 뺀 쿼리를 쓴다(기동 시 1회 판별 · 요청당 판별 금지).

## §5 [게이트 — 전부 동작형 · 봉합 전 FAIL 재현 포함]

> CI 「권한 메뉴 정합」은 **ERP 전용**이라 백오피스 역할명을 바꿔도 초록이다(선행검증 §2-5) ⇒ 작10 게이트를 새로 세운다.
> 측정 경로: **CI `db-gate` 잡**(`HITPAN_REQUIRE_DB=true` · `[SKIP]` 1건이면 실패). 개발 PC 는 `CREATE DATABASE` 거부 ⇒ **PR 에서만 깨어난다.**

| 게이트 | 무엇을 재나(동작) | 봉합 전 FAIL 재현 |
|---|---|---|
| **G-1** 라우트 버킷 전수 | 리플렉션으로 `HitPan.Backoffice.API` 의 **모든** 액션을 열거 → ⓐ익명 허가목록 ⓑ본사전용(무표식) ⓒ`[ResellerScoped]` 중 **정확히 하나**에 속하는지. 어디에도 등록 안 된 신설 라우트 = FAIL | 필터 등록 줄을 빼면 ⓐⓒ 판정 근거가 사라져 36엔드포인트가 「미결정」으로 FAIL |
| **G-2** A→B 격리 (양성) | 격리 DB 에 대리점 A·B + 고객사 각 2행 시드 → **A 토큰**으로 `api/backoffice/tenants`·`resellers`·`reseller-settlements`·`reseller-serials` 요청 → **403** | 필터 제거 후 같은 요청 → `bo_permissions` CSV 에 `reseller_admin` 1회 추가로 **200 + 전 고객사 반환**을 실제로 찍는다 |
| **G-2음** 음성 대조군 | **본사 토큰**은 같은 엔드포인트 **200** · **A 토큰**은 `api/reseller-portal/*` 에서 **자기 행만 200**(B 행 0건) | 스코프 서비스를 쿼리값 읽기로 되돌리면 B 행이 섞여 FAIL |
| **G-3** `resellerId` 입력 무시 | A 토큰으로 ⓐ `resellerId` **비움** ⓑ `resellerId=B` → 두 경우 모두 **A 행만**(또는 403). 전건 0 | 지금 코드에서 ⓐ 를 호출하면 **전건**이 나오는 것을 먼저 찍는다(이게 FAIL 모양) |
| **G-4** CSV 가 행 범위를 못 넓힌다 🔴 | `bo_permissions.allowed_roles` 에 `reseller_admin`·`reseller_user` 를 **강제로 넣고** G-2 를 다시 돈다 → **여전히 403** · 그리고 저장 API 가 본사 전용 키에 대리점 역할을 **거부**(400) | 필터 없는 상태에서 같은 CSV 를 넣으면 200 ⇒ CSV 가 유일 장벽이었음을 증거로 남긴다 |
| **G-5** 로그인 축 단일 | ⓐ `bo_users` 로 만든 계정이 **실제로 로그인된다**(지금은 불가 — 인증 경로 0) ⓑ 폴백 계정(`platform_admins.super_admin`)도 **`role=platform_owner`** 토큰을 받는다 ⓒ 발급 경로가 **1개**(IL/리플렉션으로 토큰 생성 지점 개수 단언) | 봉합 전에는 ⓐ 가 401 로 FAIL(선행검증 §2-7 「`bo_users` 로는 로그인이 안 된다」의 자동 재현) |
| **G-6** 메뉴↔진입 일치 | 역할별 사이드바가 내보내는 링크 집합 ⊆ 그 역할이 **실제 진입 가능한** 라우트 집합 · 역방향도(실물 있고 진입 가능한데 메뉴에 없는 화면 = 보고) · **가드 없는 `@page` 0개** | 지금 돌리면 ⓐ 대리점 링크가 `/admin/dashboard`(본사 라우트) ⓑ 무가드 8화면 ⓒ Owner 7줄 진입자 0 — 3건 FAIL |
| **G-8** 🔴 **하향·차단 즉시성** (§3-3) | 격리 DB · 대리점 A 계정으로 로그인 → 토큰 T 획득 → `[ResellerScoped]` 요청 **200**. **T 를 그대로 쓰면서** ⓐ `UPDATE bo_users SET role='reseller_user'` → 상위 역할 전용 요청 **403** ⓑ `UPDATE … SET is_active=0` → **모든** 요청 403 ⓒ `UPDATE … SET reseller_id='B'` → 403 + 재로그인 안내. **재로그인·토큰 재발급 0회**로 잰다 | ⓞ 판독 줄을 빼면(= 토큰 역할만 믿는 지금 구조) ⓐⓑⓒ 가 **전부 200** 으로 나온다 — 그 200 을 먼저 찍는 것이 FAIL 재현이다. 계정을 끈 뒤에도 쿠키 수명 8시간 내내 통과하는 모양(작3·작4 P1-01)과 **같은 증거**다 |
