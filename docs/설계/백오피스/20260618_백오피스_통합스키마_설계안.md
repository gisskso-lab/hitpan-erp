## 0. 이 설계안이 푸는 문제 (사장님 데이터 흐름도 반영)

사장님 데이터 흐름도 + 두 반박으로 확정된 원칙:
1. **백오피스(NCP)는 고객사 최소정보만** — 계정·이메일·전화번호 + 구독/라이선스 메타. 민감정보(사업자번호·법인번호 등)는 ERP 로컬에만. (헌법 #22, 개인정보보호법 리스크)
2. **백오피스 스키마는 ERP 의존 없이 NCP에서 자립** — 현재 `LIKE hitpan_erp.tenants`는 "한 서버 가정"이라 클라우드 분리 시 깨짐.
3. **결제·토스 = 모듈처럼 붙였다 뺐다** — 베타는 결제 없이 완주, 8월 토스 가맹 시 파일+환경변수만 추가. 베타 임시방편 0, 정식 완성도(헌법 #34).

## 1. 핵심 결정 3가지

### 결정 A — 백오피스 tenants 다이어트 (민감정보 제거)

현재 백오피스 tenants는 ERP tenants를 `LIKE`로 100% 복제 → 민감정보 8개 보유 = 사장님 지시 위반.
ERP 로컬 `local_company`(PK=tenant_id)에 회사 민감정보 원본이 **이미 전부 보관**됨(`hitpan_db_clean.sql:2641-2656` 확인) → 백오피스에서 빼도 **데이터 손실 0**.

**백오피스 tenants 최종 컬럼:**

| 남길 것 (A — 운영/구독/연락처) | 뺄 것 (B — 민감정보, ERP 로컬에 원본 존재) |
|---|---|
| tenant_id, platform_id, tenant_code | **biz_no** (사업자등록번호) |
| tel, email | **ceo_name** (대표자명·개인정보) |
| reseller_id, reseller_tier | **address, zip_code** (사업장주소) |
| max_users, status, subscription_tier | **corp_no** (법인등록번호) |
| is_locked_from_landing, bootstrap_at, trial_ends_at | **subsidiary_no** (종사업장번호) |
| db_host, db_name | **biz_type, biz_item** (업태·종목) |
| **license_key_hash** (HMAC만) | **🔴 license_key_plain** (평문키 — 폐기 1순위) |
| domain_alias, serial_verified(+at,+fingerprint) | fax, logo_url, homepage, tax_type, fiscal_month, initial_date, e_invoice_* (회사설정 — local_company에 있음) |
| ai_mode, ai_token_*, anthropic_api_key_encrypted(+last4,+status) | |
| extra_device_slots, created_at, updated_at | |
| **company_name** (보유 유지 — 사유 아래) | |

- **company_name 보유 유지**: 현재 signup↔tenant 매칭이 company_name 조인키에 의존(`SignupsAdminController.cs:73,117,249` 등). 당장 빼면 매칭 깨짐. tenant_id 기반 조인 리팩터는 별건. → 이번엔 보유.

### 결정 B — license_key_plain 폐기 (평문→해시만)

- 현재: 백오피스가 평문 시리얼키 영구 저장(`SignupsAdminController.cs:143`). 자기모순(주석 :131 "1회 노출만"). 헌법 #18·#22 위반.
- 봉합: license_key_hash(HMAC)만 보유. 시리얼 **재발송** 기능은 평문 의존이라 → "발급 직후 1회 노출 후 폐기" 또는 "신규 키 재발급" 방식으로 코드 변경.
- 영향 코드: `SignupsAdminController.cs:67,143,247`.

### 결정 C — 결제·토스 모듈 분리 (이미 됨 — 유지·정리만)

전수조사 결과 **이미 모듈로 완성·휴면 상태**. 추가 작업 거의 없음:
- `tenant_payments` = FK 0개, core와 독립. 별도 파일 유지.
- 토스 가드 503(키 없으면 잠) 이미 구현. `IBillingProvider` 추상화 + ManualBillingProvider만 등록.
- 베타 우회: `VerifyPage.razor:61` 결제 건너뜀.
- **8월 부활 = TossBillingProvider 파일 1개 + 환경변수 2개 + NavigateTo 한 줄.** 코드 재공사 0.
- → **이번 스키마에서 결제는 "연결고리(tenant_payments, FK 0)만 정식 포함, 알맹이 0".** 지금 손댈 것 없음.

## 2. 백오피스 통합 스키마 파일 구조 (신설)

ERP 의존(`LIKE hitpan_erp`) 제거 → 자립형 `CREATE TABLE`. 모듈 분리 위해 파일 다층화:

```
installer/backoffice/                         (신규 폴더 — 형상관리 정식)
├── 00_backoffice_core.sql        ← 계정·구독·CS·대리점 (자립형 CREATE)
│     tenants(다이어트), landing_signups, resellers, reseller_accounts,
│     reseller_applications, platform_admins, bo_users, bo_permissions,
│     bo_audit_log, bo_approval_queue, bo_user_mfa, tenant_domains,
│     promotions, promotion_usages, pricing_plans, pricing_history,
│     tenant_rewards, serial_verify_attempts, serial_verify_locks,
│     webhook_outbox, beta_signups, reseller_serials,
│     reseller_settlements, reseller_settlement_lines, tenant_settings 등
├── 10_backoffice_payment.sql     ← 결제 모듈 (지금은 tenant_payments만, 알맹이 0)
│     tenant_payments (FK 0, 연결고리 자리)
│     [8월 추가 예정: toss_* 테이블은 이 파일에 떨궈넣으면 자동 결합]
└── (자동실행기가 번호순 적용)
```

- 누락이던 7테이블(pricing_plans, pricing_history, tenant_rewards, serial_verify_attempts, serial_verify_locks, beta_signups, reseller_accounts) → core에 자립형으로 흡수.
- 누락이던 6컬럼(license_key_plain은 폐기, domain_alias, serial_verified* 등) → tenants CREATE 본문에 포함(license_key_plain 제외).
- `DB-60_backoffice_v1.sql`은 코드와 테이블명 불일치(폐기) — 기준으로 안 씀.

## 3. 자동실행기 설계

백오피스 `Program.cs`에 시작 시 마이그 적용기 추가 (현재 없음 — 전체 110줄 확인):
- 앱 기동 시 `installer/backoffice/` 폴더의 `.sql`을 **번호순 순차 적용**.
- 적용 이력 테이블(`_schema_migrations`)로 멱등성 — 이미 적용한 파일은 skip.
- `CREATE TABLE IF NOT EXISTS` + `ALTER ... IF NOT EXISTS`로 재실행 안전.
- 효과: 8월 결제 파일 1개 떨궈넣으면 **다음 기동 때 자동 결합**. 코드 재공사 0.
- ⚠️ 실제 NCP DB에서 실행은 사장님 영역(헌법 #29). 자동실행기는 "앱이 자기 DB 스키마를 보장"하는 코드일 뿐, DB 인스턴스 생성은 사장님.

## 5. ⚠️ 설계안 미해결 — 사장님 결재 필요 지점

1. **company_name 보유** — 매칭 조인키라 당장 못 뺌. 보유 유지 OK? (아니면 tenant_id 매칭 리팩터 별건 발주)
2. **가입 시 사업자정보 ERP 전달 경로** — 현재 백오피스 tenants 경유. 사장님 흐름도("ERP 직행, 백오피스 미경유")대로 하려면 이 경로 재설계 필요. 이번 범위에 포함할지, 별건으로 뺄지.
3. **license_key_plain 재발송 방식** — "1회 노출 후 폐기" vs "신규 키 재발급" 중 사장님 선호.
4. **스키마 실행 경계** — PM은 파일·코드만, NCP 실행은 사장님. 확인.
5. **작업 범위** — 이번에 (스키마 신설 + 자동실행기 + 다이어트 코드봉합) 전부 한 번에 갈지, 단계 분할할지.
