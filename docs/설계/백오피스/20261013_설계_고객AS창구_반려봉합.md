## 3. 서버 — 6건 (전부 추가형 · #1)

### S-1 응대유형 값 **넓히기** (삭제 0)

```
AllowedHandledVia       = { message, phone, remote }            ← 기존 3값 그대로 산다
                        + { as_center, email, sns, etc }        ← 더한다
AllowedHandledViaManual = { phone, remote, email, sns, etc }    ← 🔴 사람이 고를 수 있는 값
```

🔴 **`as_center` 는 `Manual` 집합에 넣지 않는다.** 서버만 앉히는 값이다 —
넣으면 본사 담당자가 수기건을 「히트판 A/S센터로 응대했다」로 꾸밀 수 있다(작1 S-1 과 같은 함정 · L-3 계열).
🔴 기존 `message` 도 Manual 에 넣지 않는다 — 쪽지 응대는 이제 `as_center` 가 정본이고,
**옛 값 `message` 는 읽을 때만 산다**(지우지 않는다 · #1).

### S-2 쪽지건은 응대유형을 **사람이 못 바꾼다**

`SetHandledVia` — `received_channel = 'erp_message'` 이면 400:
> 「쪽지로 들어온 A/S 는 히트판 A/S센터 응대로 고정입니다」

수기건만 `AllowedHandledViaManual` 로 받는다.

### S-3 완료 전이 — 쪽지건은 서버가 채우고 통과

```
if (to == "완료")
{
    쪽지건(erp_message) :  UPDATE … SET handled_via = 'as_center' WHERE id=@Id AND handled_via IS NULL
                           ⇒ 🔴 빈 칸만 채운다. 이미 값이 있으면 **덮지 않는다**(U-2 · #1)
                           ⇒ 거부하지 않는다
    수기건              :  handled_via 비면 종전처럼 400 (약속 보존)
}
```

🔴 **왜 수기건은 그대로 막나**: 손으로 적은 건은 **어떻게 응대했는지를 사람만 안다.**
비워 두면 나중에 CS 실적을 만들 때 소급이 안 된다 — 작1 이 이 칸을 막은 원래 이유가 수기건에는 그대로 유효하다.

### S-4 수기건 상태는 **접수·완료 2종**

```
수기건(erp_message 아님) && to ∉ { 접수, 완료 }  →  400
  「손으로 적은 A/S 는 접수와 완료만 기록합니다 — 처리 과정은 고객사에 보이지 않습니다」
```

🔴 **U-1 보존 조건**: 막는 것은 **새로 고르는 것**뿐이다.
이미 `처리중`·`보류`·`고객답대기` 로 앉은 수기건이 운영에 있으면 **그 값을 UPDATE 하지 않고 그대로 읽어 보여준다.**
(지우면 사실이 사라진다 · #1 · 작1 「모르는 값은 아는 척 안 한다」와 같은 줄)

### S-5 상세 SELECT 에 **4칸 추가** (추가만)

```
+ k.rating, k.rated_at AS ratedAt, k.rating_comment AS ratingComment, k.read_at AS readAt
```

⇒ 상세에서 **고객평가 ★ 가 처음으로 보인다** · 「안 읽음」이 늘 뜨던 거짓도 같이 사라진다.

### S-6 상세 응답에 **처리 과정** 더하기 (엔드포인트 0건 신설)

```
SELECT from_status AS fromStatus, to_status AS toStatus, actor_id AS actorId, acted_at AS actedAt
  FROM bo_cs_ticket_logs WHERE ticket_id = @Id ORDER BY acted_at      ← 인덱스 (ticket_id, acted_at) 그대로 탄다
```

응답 모양: `{ success, ticket, replies, logs }` — **기존 두 칸은 모양 변화 0**(하위호환).

🔴 **폐기건에도 과정은 보인다** — 전이 기록에는 몸통이 없다(상태값·시각·누가). 작1 V-3 의 「몸통은 비우고 사실은 남긴다」와 같은 선이다.
🔴 `bo_cs_ticket_logs` 는 **INSERT ONLY** — 이 설계는 읽기만 더한다(L-5).

## 4. 화면 — 사장님 결재대로

### 4-1 상태변경 자리 = **목록 행에서 바로 + 오른쪽 칸 펼침** (사장님 결재)

```
목록 ─ 상태 칸
  [접수 ▾]  ← 누르면 그 자리에서 메뉴. 고르면 바로 서버로 간다
            🔴 메뉴 클릭이 행 클릭(상세 열기)을 타지 않게 stopPropagation
            🔴 값 목록이 건마다 다르다 — 쪽지건 5종 / 수기건 2종(접수·완료)
            🔴 지금 값이 목록 밖(옛 수기건 '처리중')이면 **그 값을 맨 위에 그대로 보여주고 비활성**
               ⇒ 아는 척도, 지우기도 안 한다
오른쪽 ─ 처리 칸
  기본 **펼침**(IsInitiallyExpanded) — 작1 에서 접은 것을 되돌린다
```

### 4-2 응대유형 — 건의 성격에 따라 **다른 것이 보인다**

| 건 | 보이는 것 |
|---|---|
| 쪽지 | 🔴 콤보 **없음** · 고정 글자 **「응대유형 · 히트판 A/S센터」** + 한 줄 설명 「쪽지로 들어온 A/S 는 히트판 A/S센터가 받습니다」 |
| 수기 | 콤보 **5종**(전화 · 원격지원 · 이메일 · SNS · 기타) + 「응대 저장」 |

### 4-3 쪽지건 상세 — 세 가지가 한눈에 (사장님 2)

```
┌ [접수] [분류 통신] [★ 좋아요]        ← 상태 · 분류 · 고객평가 세 칸이 머리에 나란히
│ 응대유형 · 히트판 A/S센터
├ 고객이 보낸 글
├ 주고받은 답 N건
└ ▼ 처리 과정  (기본 펼침)
     10-13 21:04  접수 → 처리중   (담당 u-…)
     10-13 21:30  답 보냄
     10-13 22:11  처리중 → 완료   (담당 u-…)
```

🔴 **대화와 전이를 한 줄기에 섞어 시간순으로 놓는다** — 사장님 1)의 「어떤 대화를 했고 어떻게 처리했는지」는
두 자료가 **따로 있으면 안 읽힌다.**

### 4-4 목록 — 사장님 2)의 세 칸을 앞으로

칼럼: `고객사 · 분류 · 응대유형 · 상태(+안읽음·★평가) · 접수 · 답`
🔴 「접수 경로」 칼럼은 **「응대유형」으로 바뀌는 것이 아니다** — 두 축이 다르다(선행검증 §7).
접수 경로는 **상세 머리줄에 그대로 남긴다**(정보 손실 0 · 작1 과 같은 약속).
