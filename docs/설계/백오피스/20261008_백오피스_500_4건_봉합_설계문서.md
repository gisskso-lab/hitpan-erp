## §1 [왜] 이 사고가 난 한 문단 — 다음 사람이 같은 자리에서 안 넘어지게

한 뜻의 표가 **두 벌**로 레포에 들어왔다(`promotions` admin 모양 · `promotions_legacy` legacy 모양).
들어온 날 작성자는 둘의 충돌을 알고 있었고, 주석으로 「통합은 별건 todo(사장님 결재 2026-06-18)」라 적어 두었다
(`installer/backoffice/00_backoffice_core.sql:370`·`:502-503`). **주석은 코드가 아니다.**
그 뒤 컨트롤러는 legacy 칸 이름을 **admin 표 이름(`promotions`)으로** 읽는 상태로 넉 달을 살았다.
요금제 쪽은 더 단순하다 — 컨트롤러가 읽는 칸 3개의 정의가 6/11 커밋에서 **모양이 틀렸다는 이유로** 지워졌고,
같은 커밋이 **그 칸들을 그대로 쓰는 시드를 남겼다**(= 작성자는 운영에 그 칸이 있다고 믿었다). 아무도 대조하지 않았다.
그리고 이 두 어긋남은 **운영에서 화면을 처음 열기까지 아무 소리도 내지 않았다** — 레포에 「코드가 읽는 칸이 표에 있는가」를
묻는 장치가 **0건**이기 때문이다. 헌법 #13(새 SQL 전 DESCRIBE 의무)은 사람의 의무로만 있었고 **한 번도 코드로 집행된 적이 없다.**
10/8 R-1 로 SQL 이 처음 서버에 실려 갔지만, 그것은 **실려 간 것**이지 **맞는 것**이 아니다. 어긋남은 그대로 있다.
⇒ 봉합 둘(§3·§4) + 재발 차단 하나(§6 G-COL-1). **셋 중 하나라도 빠지면 이 문서는 실패다.**

## §4 [요금제] 세 칸을 어떻게 되살리나

### §4-1 6/11 에 왜 지워졌나 — `git show 82091fb7` 직독

- 바뀐 파일은 **`scripts/pricing_plans_seed.sql` 하나뿐**(`installer/backoffice/` 무접촉).
- 커밋 메시지 그대로: 「NCP에 pricing_plans 테이블 이미 존재 · 기존 스키마는 plan_id(VARCHAR PK) · 본 SQL이 plan_code 라서 Unknown column 사고 → plan_code→plan_id 정정 · **CREATE TABLE 제거(이미 존재 보존)**」
- 🔴 **즉 「세 칸을 폐기한다」는 결재가 아니다.** 지운 것은 **PK 모양이 틀린 CREATE** 다.
- 🔴 결정적: **같은 커밋이 `price_display`·`max_pc_devices`·`max_mobile_devices` 를 그대로 INSERT 하는 시드를 남겼다**
  ⇒ 작성자는 운영에 세 칸이 **있다고 믿었다**. 되살리면 안 되는 이유는 커밋 어디에도 **없다**.
- ⚠️ 그 시드 자체는 「결재 전 실행 금지」로 묶여 있고 실행 여부 미확인 ⇒ 운영에 세 칸이 **있을 수도** 있다. `ADD COLUMN IF NOT EXISTS` 가 양쪽을 다 흡수한다.

### §4-2 🔴 함정 둘 — 기본값을 잘못 주면 동작이 바뀐다

1. **`0` 을 기본값으로 주면 기기 등록 상한이 0 이 된다.** `DeviceRegistrationController:65-66` 은 `COALESCE(p.max_pc_devices, 5)` —
   `COALESCE` 는 **NULL 만** 막는다. `0` 이면 폴백이 안 돌고 상한 0 이 되어 **등록이 전부 막힌다.**
   ⇒ 두 칸은 **`NULL DEFAULT NULL`** 로 더한다. 기존 행은 NULL = 「미설정」 ⇒ 폴백 5/3 이 그대로 산다.
2. **NULL 을 `int` 로 받으면 다시 500 이다.** `PlanRow.MaxPcDevices`/`MaxMobileDevices` 가 `int`(`PricingAdminController:257-258`)
   ⇒ `int?` 로 바꾼다. `UpdatePlanRequest` 쪽도 `int?` 로 하고 UPDATE 는 `COALESCE(@MaxPcDevices, max_pc_devices)` —
   화면이 값을 안 보내도 **기존 값이 0 으로 덮이지 않게** 한다(#1 정신).

### §4-3 🔴 칸을 더하는 것은 「기기 슬롯 과금」 부활이 **아니다**

9/25 결재로 슬롯 과금은 폐기되고 과금 축은 **계정 수**다. 이 설계는 **코드가 읽는 칸을 있게만 한다** — 값은 NULL(미설정)이고
과금·동시로그인 판단은 이 칸을 **안 본다**. 두 칸을 **코드에서 빼는 쪽**(슬롯 폐기 정합)은 동작 변경이고
`DeviceRegistrationController` 영향 분석이 필요하므로 **2차 별건**으로 올린다(§8 사장님-2).
이번에는 500 을 멈추는 데까지만 간다(#33 · 오더 범위).

## §5 [기동거부] 재기동 위험을 설계가 낮출 수 있는 자리 — 있다(3건) · 없는 것도 있다(1건)

### §5-1 🟢 있다 ① — `31:42` FK 의 errno 1452 는 **설계로 없앤다**

`31` 파일의 문장 순서는 `ADD COLUMN tenant_id` → `ADD KEY` → **`ADD CONSTRAINT … FOREIGN KEY`** → backfill 이다.
칸이 **그 파일에서 처음 생기는 경우**엔 FK 시점에 전 행이 NULL ⇒ 1452 **불가**. 위험은 **칸이 이미 있고 값이 들어 있는 경우**뿐이다.
⇒ **FK 문장 바로 앞에 고아 복원 1문장을 추가한다**(담당 #8).
🔴 **새 파일로는 못 한다** — 칸이 없는 DB 에서 그 UPDATE 를 먼저 돌리면 `Unknown column` 으로 **그 파일이 기동을 거부한다**.
그래서 `31` 안, `ADD COLUMN` **뒤**에 들어가야 한다. 기존 줄은 한 줄도 지우지 않는다(#1 추가만).

| # | 누가 | 어느 파일 | 무엇을 |
|---|---|---|---|
| 8 | DB 매니저 | `installer/backoffice/31_backoffice_z2_landing_signups_tenant_fk.sql` | `ADD CONSTRAINT` 문장 **앞**에 `UPDATE landing_signups SET tenant_id = NULL WHERE tenant_id IS NOT NULL AND tenant_id NOT IN (SELECT tenant_id FROM tenants);` **1문장 + 사유 주석 1줄** 추가. 기존 줄 삭제·수정 0건 · 멱등 · `tenant_id IS NOT NULL` 행만 건드린다 |

### §5-2 🟢 있다 ② — `43`·`44` 는 실패 경로를 애초에 안 만든다
전 문장 `IF NOT EXISTS` · 신규 FK 0개(`43` 의 자기 참조 1개는 `CREATE` 안쪽) · 인덱스 변경 0개 · `INSERT` 0건
⇒ 콜레이션(150)·고아FK(1452)·중복(1062) 경로가 **구조적으로 없다**.

### §5-3 🟢 있다 ③ — 되돌림이 환경변수 한 글자다
적재 실패로 기동이 거부되면 `HITPAN_BO_AUTO_MIGRATE=0` 으로 재기동 ⇒ **즉시 직전 상태**(§2-7).
이 경로를 작업지시서에 **사장님용 한 줄**로 싣는다.

### §5-4 🔴 없다 — 콜레이션 불일치(errno 150)
운영 `landing_signups`·`tenants` 의 실제 콜레이션을 못 봤다(#39). `31` 의 FK 는 피할 수 없다 — 적재기는 번호순 전부를 돈다.
`_schema_migrations` 에 `31` 을 「적용됨」으로 미리 적는 우회는 **운영 DB 직접 수술(#39)** 이라 금지.
⇒ **사장님이 재기동 전에 읽을 한 줄**:
> 「재기동 중 로그에 `[SchemaMigrator] 적용 실패 31_…` 이 보이면, 환경변수를 `0` 으로 되돌려 한 번 더 재기동하면 직전 상태로 돌아옵니다. 데이터는 변하지 않습니다.」

## §6 [게이트] 각 게이트가 **동작**을 무는지 (누적 26번 지적 · 봉합 빼고 FAIL 확인 의무)

### §6-1 1차 — 이번 차수 (전부 신설)

| 게이트 | 무는 **동작** | DB | 봉합 빼면 |
|---|---|---|---|
| **G-COL-1** 🔴 **코드가 읽는 칸이 표에 있나** | 시험이 `installer/backoffice/*.sql` 을 파싱해 **표→칸 색인**을 만든다(`CREATE TABLE` 본문 + `ALTER TABLE … ADD COLUMN`). 대상 컨트롤러의 SQL 문자열에서 `FROM`/`JOIN`/`INSERT INTO`/`UPDATE` 뒤 표 이름과 그 문장의 식별자를 뽑아 **색인에 없는 칸이 하나라도 있으면 FAIL**. 「글자가 있나」가 아니라 **색인 대조** | 아니오(`build` 잡에서 먼저 소리) | 지금 코드로 돌리면 `price_display`·`max_pc_devices`·`max_mobile_devices`·`promo_code`·`title`·`use_count`·`target_plan`·`status` 가 **전부 잡힌다** — [3] 은 이 FAIL 목록을 **먼저 캡처**하고 봉합한다 |
| **G-COL-1n** 음성 대조군 | `44` 에서 `price_display` 한 줄을 지운 사본으로 G-COL-1 을 돌려 **FAIL** 하는지 | 아니오 | 파서가 죽어 있으면 여기서 드러난다 |
| **G-PROMO-1** | 시험 DB 에 `00`+`43` 적재 후 `PromotionController` 의 **실제 SQL 3개**(목록·생성·redeem)를 실행 → 성공 + `promotion_usages` 행 1건 | **예** | 표 이름이 `promotions` 로 남아 있으면 Unknown column 으로 FAIL |
| **G-PRICE-1** | 시험 DB 에 `00`+`44` 적재 후 `PricingAdminController` 의 `plans` SELECT 실행 → 두 칸이 **NULL 로 읽히고 `int?` 로 매핑**된다. 같은 시험이 `DeviceRegistration` 의 `COALESCE` 가 **5/3** 을 돌려주는지 본다(§4-2 의 0 사고를 무는 자리) | **예** | 기본값 0 으로 쓰면 5/3 대신 0 이 나와 FAIL |
| **G-MIG-1** | `43`·`44` 를 **같은 DB 에 2회** 적재해 2회 모두 성공(멱등 실측) | **예** | `IF NOT EXISTS` 를 빼면 2회차 1050/1060 으로 FAIL |
| **G-MIG-2** | `31` 적재 전에 고아 `tenant_id` 1건을 **심고** 적재 → 성공 + 그 행이 NULL 로 복원. 고아 복원 줄을 빼면 **1452 로 FAIL** | **예** | §5-1 이 실제로 1452 를 막는지 |
| **G-SHIP-4** | 기존 `BackofficeSchemaShipGateTests` G-BO-SHIP-2(레포↔산출물 SQL 집합 동일)가 `43`·`44` 를 자동 포함하는지 확인 | 아니오 | 새 파일이 배포에 안 실리면 FAIL |

🔴 **판별 규칙(10/7 교훈)**: DB 게이트는 DB 없이 **조용히 초록**일 수 있다 ⇒ `[SKIP]` 표시 + **소요시간**으로 가른다.
CI `db-gate` 잡의 초록만 증거로 인정한다.

### §6-2 2차 — 별건 (이번에 하지 않는다)
G-COL-1 범위를 **백오피스 컨트롤러 전체**로 넓힌다. 1차에서 전체를 켜면 파서 오탐(동적 `sql +=`·별칭·서브쿼리)으로 CI 가 못 선다
⇒ 1차는 **이번 사고의 5개 컨트롤러**(`Promotion`·`PromotionsAdmin`·`PricingAdmin`·`LandingPublic`·`DeviceRegistration`)로 고정하고,
2차에서 화이트리스트를 지우며 오탐을 하나씩 닫는다. 2차 착수는 PM 결재(§8 PM-6).

## §9 못 잰 것 (설계가 여기에 기대지 않는다)

1. 운영 DB 의 실제 표·칸 모양(#39) — 그래서 **모양 무관 설계**로 갔다(§3-3).
2. 운영 콜레이션 ⇒ `31` FK 의 errno 150 가능성(§5-4) — **되돌림 경로로만** 대비.
3. 랜딩 공개 요금표가 지금 실제로 깨져 있는지(§2-5) — ⚠️추론. `44` 가 맞으면 같이 풀린다.
4. `scripts/pricing_plans_seed.sql` 이 운영에서 실행된 적 있는지 — `IF NOT EXISTS` 가 양쪽을 흡수한다.
5. CS 2건(확정 3)은 이 설계가 코드로 건드리는 것이 **0건**이다 — 재기동 1회로 끝난다. 이 문서의 역할은 그 재기동을 **안전하게 만드는 것**(§5)뿐이다.
