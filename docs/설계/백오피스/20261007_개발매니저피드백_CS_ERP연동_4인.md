## §1 【풀스택 매니저】 ERP 쪽에 손대야 하는 영역 — 전부

### §1-1 한눈에: 지금 끊긴 그림

```
[ERP 고객 화면]  ← 🔴 없다 (0-10)
      │
      ▼  🔴 보낼 통로가 없다 (0-5: ERP API 는 본사로 HTTP 를 안 쏜다)
      │
   [로컬 큐]     ← 🔴 없다 (0-7: 쌓아 둘 표가 없다)
      │
      ▼
[백오피스 수신 API] ← 🔴 없다 (0-2)
      │
      ▼
[bo_cs_tickets]    ← 🔴 없다 (PM 실측)
      │
      ▼
[/admin/cs 화면]   ← 🟡 껍데기만 있다 (0-1)
```

**5칸 중 4칸이 없다. 1칸은 껍데기다.** "쪽지 연결" 은 기존 길에 얹는 일이 아니라 길을 새로 내는 일이다.
🔴 **"쉽다" 는 말을 쓰지 않는다** — 반증: 비슷하게 생긴 워치독 송신부가 **백오피스 수신부가 없어 3개월간 허공으로 갔다**(`TelemetryController.cs` 머리글 주석, 실측 2026-08-06 기록). 송신만 만들면 "고쳤다 ≠ 갔다" 가 8차로 재발한다.

### §1-5 🔴 설계서끼리 부딪히는 자리 — 우리가 못 정한다 (결재 필요)

**본문(자유 입력) 칸을 1차에 두는가?**

|---|---|
| §5-ⓒ | "CS 티켓 **본문**은 고객이 자유롭게 쓴다" — 금지필드 검사로 막되 받는다 |

🔴 **우리는 이걸 넓히지 않는다.** 10/7 작12 에서 쪼개 놓은 조건을 뒤 문서에서 되돌려 적어 사장님 손을 네 번 묶은 사고가 있었다. 그러니 **그대로 쪼갠 채 올린다** — 사장님 결재 사항:

- **갈래 ㉯**: 1차에 본문 포함. ⇒ DB명세서 쟁점-3 을 **같은 결재로 갱신**해야 하고, 금지필드 거부 로그 FAIL 게이트가 **같은 커밋**에 들어가야 한다(DB명세서가 못 박은 조건).

### §1-6 🔴 아무도 아직 안 정한 자리 — "답이 ERP 안에서 어디로 도착하나"

§5-ⓑ 그림은 "ERP 가 Pull → 고객 화면에 「답 왔음」 알림" 까지만 그려 놨다. **그 알림이 뜨는 자리가 코드에 없다.**

- 후보 A: 사내 메신저(`chat_messages`)에 본사 답을 한 줄로 꽂는다. ⚠️ 그러면 `sender_id` 가 **사원 ID 여야 하는데**(DDL 주석: "🔴 결재 안내도 결재한 사람 ID — 봇 이름으로 가리지 않는다") 본사 직원은 그 테넌트의 사원이 아니다. ⇒ **FK·의미 둘 다 안 맞는다. 추천하지 않는다.**
- 후보 B: 전용 `cs_*` 표 + 전용 화면(§1-2 C). 깔끔하지만 화면 하나가 더 생긴다.

⇒ **후보 B 를 권고**하되, 근거는 "A 가 DDL 주석과 정면으로 부딪힌다" 는 실측 하나다. C 는 재 봐야 한다.

## §2 【네트워크 매니저 마이클】 끊기는 자리 — 쪽지가 사라지지 않게

### §2-1 지금 있는 본사-송신 코드는 **실패하면 버린다** (실측)

| 코드 | 실패하면? | 근거 |
|---|---|---|
| `MetaPingClient.cs` | Polly 재시도 3회(2초 지수백오프) + 회로차단기(50% 실패·60초 차단) + 30초 타임아웃 → **그 뒤 끝. 로그만 남고 내용은 사라진다** | `src/HitPan.Watchdog/Telemetry/MetaPingClient.cs:43-62` — 큐에 쌓는 코드 **0줄** |
| `UpdateHistoryClient.cs` | 🔴 **재시도조차 안 붙였다.** 자기 주석: "⚠️ 재시도(Polly)를 붙이지 않는다 — 재시도가 업데이트 흐름을 붙잡으면 그 자체가 위반이다" | `:20` |
| `TelemetryController` (수신측) | 워치독은 fire-and-forget. "이 엔드포인트의 어떤 응답도 고객 PC 의 업데이트를 막지 않는다" | 머리글 주석 |

**이 설계는 그 용도로는 맞다.** 핑 한 번 잃어도 다음 핑이 온다. **그런데 CS 쪽지는 다르다 — 한 건이 사라지면 고객이 쓴 글이 사라진다.** 즉 **기존 송신 코드를 그대로 쓰면 안 된다.** 이게 네트워크팀의 1번 피드백이다.

### §2-2 4가지 끊김에서 쪽지가 어떻게 되나 (설계 요구)

| 상황 | 지금 그대로면 | 반드시 이렇게 |
|---|---|---|
| **고객 PC 가 꺼져 있다** | 애초에 ERP 가 안 돌아서 쪽지를 쓸 수도 없다. 문제는 **쓰고 나서 바로 끈 경우** — 메모리 큐면 소실 | 🔴 **큐는 DB 표**(메모리·파일 금지). ERP 로컬 MariaDB 에 `INSERT` 가 끝난 뒤에 화면이 "접수됐습니다" 를 띄운다. 송신은 그 뒤 비동기 |
| **터널이 끊겼다** | 송신 실패 → 지금 코드면 버림 | 큐 행이 `pending` 으로 남고 워커가 다음 주기에 다시 집는다. **고객 업무는 전혀 안 멈춘다**(#30) |
| **Windows Update 직후** | 서비스 재기동 중 워커가 안 돌 수 있다. ⚠️ 9/29 실측 이력: **워치독 멱등이 재시도를 막아 재기동이 필요**했던 사고가 있다 | 워커는 **기동 시 큐를 먼저 쓸어본다**(`OutboxPollerWorker` 는 기동 후 1분 대기 — 이 패턴 재사용 가능). 🔴 **"보낸 적 있나" 판정은 로컬 큐 상태가 아니라 `sent_at IS NULL` 로** — 멱등이 재시도를 삼키는 자리를 안 만든다 |
| **본사가 500 이다** | 재시도 3회 뒤 버림 | 🔴 **4xx 와 5xx 를 가른다.** 5xx·타임아웃·네트워크 = 재시도 대상(큐 유지). 400/422(금지필드 거부 등) = **재시도하면 영원히 안 들어간다** ⇒ `rejected` 로 종결 + **고객 화면에 사유 표시**. 지금 어느 코드도 이걸 안 가른다 |

### §2-3 🚨 가장 큰 발견 — `OutboxPollerWorker` 는 **고객 PC 가 본사 DB 에 직접 접속한다**

```
src/HitPan.API/BackgroundServices/OutboxPollerWorker.cs:56
    var connStr = _config["Outbox:BackofficeConnectionString"];
  주석(:28-31)
    "BackofficeConnectionString": "Server=...;Database=hitpan_backoffice;..."
  :86-96  await using var conn = new MySqlConnection(connStr);
          SELECT ... FROM messaging_outbox WHERE processed_at IS NULL
  :122    UPDATE messaging_outbox SET processed_at = NOW(6) ...
```

즉 **고객사 PC 안에 본사 백오피스 DB 의 접속 문자열이 들어가고, 고객 PC 가 NCP DB 를 직접 SELECT·UPDATE 한다.**

- 🔴 이건 "본사가 고객을 두드리지 않는다" 는 §5-ⓑ 제약은 지키지만, **고객 PC 하나가 털리면 본사 DB 자격증명이 털린다**(보안 매니저 §5-4 와 같은 사고).
- 🔴 자기 주석이 **"본사 ERP → 백오피스 INSERT 금지"** 라 못 박아 놨다 ⇒ **이 길로 CS 쪽지를 올릴 수 없다.** 올리면 자기 규칙 위반이다.
- 🟡 **지금 꺼져 있다**: `Outbox:Enabled` 기본값 `false`, `appsettings*.json` 에 `Outbox` 항목 **0건**(grep 결과 Program.cs 만 걸림) ⇒ 실제로는 안 돈다. ⚠️미확인: 고객 PC 실물 `appsettings` 에 이 값이 있는지는 **못 쟀다**(이 PC 는 `api` 폴더 읽기 거부 이력).

⇒ **CS 쪽지는 반드시 HTTPS API 로 간다.** DB 직결은 늘리지 않는다. (이 워커 자체의 처분은 **별건 트랙** — 우리 범위 밖이고, #37 "안 읽힌다 ≠ 잔재" 가 걸린다. **지우자고 제안하지 않는다.**)

### §2-4 멱등키 — 어떻게 잡나

- 키 = `tenant_id` + ERP 가 만든 **티켓 UUID**(ERP 가 발급, 본사가 아님). 송신 때 `Idempotency-Key` 헤더 또는 payload 필드로 같이 보낸다.
- 본사 수신부는 `UNIQUE(tenant_id, client_ticket_uid)` 로 **같은 쪽지 2회 = 1건**(아키텍처명세서 §5 가 이미 "본사 수신부는 멱등" 을 요구한다).
- ⚠️ 주의: `TelemetryController` 는 멱등을 **"1분 내 같은 내용"** 시간창으로 잡는다(`DuplicateWindowSeconds = 60`). 🔴 **쪽지에 시간창 멱등을 쓰면 안 된다** — 터널이 10분 끊겼다 복구되면 창 밖이라 중복이 들어온다. **키 멱등**이어야 한다.

### §2-5 재시도 한도 — "포기" 를 어떻게 다루나

- 지수백오프 + 상한(예: 24시간 후 10분 간격 고정). 🔴 **"재시도 횟수 다 쓰면 삭제" 금지.** 큐 행은 지운다는 개념이 없다 — `failed` 로 멈추고 **사람이 볼 수 있어야 한다**.
- 🔴 #26 정신: 목표 시간과 타임아웃을 분리한다. "5분 안에 가야 한다" 가 "5분 지나면 버린다" 로 변하면 사업 실패다.
- 화면에 **"아직 본사에 안 갔음"** 상태가 고객에게 보여야 한다. 안 보이면 고객은 답을 기다리고 우리는 못 받은 걸 모른다 — "고쳤다 ≠ 갔다" 가 여기서 난다.

### §2-6 17시나리오 중 다시 재야 할 것

| 번호 | 영역 | 왜 다시 재나 |
|---|---|---|

🔴 **게이트는 글자가 아니라 동작**(누적 26번 지적). 위 재측정은 **대조군 필수** — 터널을 실제로 끊고 쪽지가 큐에 남는지, 본사를 500 으로 만들고 재시도가 도는지. `EXIT=0` 은 통과가 아니다. 개발 PC 정상은 검증이 아니다.

## §4 【풀스택 매니저】 AI 3사 연동 구조

### §4-1 "3사를 한 인터페이스로" — 🟢 **이미 있다. 새로 만들지 마라**

실측한 살아 있는 축:

```
IChatCompletionProvider                         ← src/HitPan.Infrastructure/Services/AnthropicChatProvider.cs:69
  ├─ CompleteAsync(decryptedApiKey, systemPrompt, userMessage, history, ct)
  └─ CompleteWithToolsAsync(decryptedApiKey, systemPrompt, messages, tools, ct)
        │
        ├── AnthropicChatProvider   (클로드AI)
        ├── OpenAiChatProvider      (챗GPT)
        └── GeminiChatProvider      (제미나이)
                │
        IAiProviderFactory.Resolve(providerId)   ← src/HitPan.Infrastructure/Services/Ai/AiProviderFactory.cs:109
          모르는 값·빈 값 = 전부 anthropic 으로 떨어진다 (예외 안 던진다)
```

🔴 **핵심: `decryptedApiKey` 가 메서드 인자다.** 공급자 어댑터는 키를 자기 안에 안 들고 있다 ⇒ **같은 어댑터에 본사 풀 키를 넣어도 그대로 돈다.** 이게 "재사용 가능한가" 의 답이다: **어댑터 3개는 그대로 쓴다. 키를 어디서 꺼내는지만 다르다.**

🚫 **`IAiProvider`(`src/HitPan.Application/Interfaces/IAiProvider.cs`) 에는 얹지 마라** — 구현체 0개(0-3). 단 **지우자고도 하지 않는다**(#37·#1).

### §4-2 🔴 그런데 지금 구조를 CS 자동화에 그대로 못 쓰는 이유 2개

| | 실측 | 왜 막히나 |
|---|---|---|
| ① 키가 **고객사 것**이다 | 키 보관 = 고객 PC 로컬 DB `local_subscription.{anthropic,openai,google}_api_key_encrypted varchar(512)` (AES-256) · 저장 API 는 `AiSettingsController` (`[Authorize(Policy="TenantAdminOnly")]`) | §8-7 ⓐ(본사 부담)로 결재되면 **키가 본사 NCP 에 있어야 한다.** 고객 PC 의 BYOK 칸은 CS 자동화와 **다른 물건**이다 ⇒ 백오피스 쪽에 **별도 키 저장소**가 필요(§5-4) |
| ② **장애 전환이 없다** | `AiProviderFactory.Resolve()` 는 **한 곳을 고르고 끝**이다. 실패 시 다른 공급자로 넘기는 코드 **0줄**(파일 전문 읽었다) | "어느 쪽이 죽어도 돌아가는가" → 🔴 **지금은 안 돈다.** 주석은 "한 곳이 장애·한도 초과일 때 키를 다시 넣지 않고 갈아탄다" 고 적었지만 **그건 사람이 화면에서 갈아타는 얘기**다. 자동 전환이 아니다 |

### §4-3 장애 전환 — 우리가 권고하는 모양

```
CsAutoDraftService (백오피스 · 신규)
   │ 1. 누리집에서 근거 문서 N장 찾기   ← 외부 호출 0 · 여기까지는 AI 없이도 값을 한다
   │ 2. 순서표(본사 설정값)대로 공급자 호출
   │       1순위 → 실패/타임아웃/한도초과 → 2순위 → 3순위
   │       🔴 "실패" 판정: 5xx · 타임아웃 · 429(한도) = 다음 공급자
   │                      4xx(키 틀림·요청 잘못) = 다음 공급자로 넘기지 말고 멈춤 + 알림
   │                        (틀린 요청을 3사에 3번 보내면 돈만 3배 쓴다)
   │ 3. 셋 다 실패 → 🔴 "초안 없음" 으로 끝낸다. 사람이 손으로 쓴다
   └─ 어느 경우에도 고객 응대는 멈추지 않는다 — 초안은 거드는 것일 뿐
```

- 순서표는 **본사 설정 화면**(🆕E)에서 사람이 정한다. 🔴 **코드에 1순위를 박지 않는다** — 100% 자동화 없음(반자동 원칙).
- 🔴 `Resolve()` 의 "모르는 값은 anthropic 으로 조용히 떨어진다" 동작은 **BYOK 무회귀용으로는 옳지만 전환 체인에서는 위험하다** — 2순위를 "openaii" 로 잘못 적으면 1순위와 같은 곳을 두 번 부른다. ⇒ 전환 체인은 **목록 검증을 따로** 한다(`AiProviderIds.All` 과 대조).

### §4-4 비용·토큰·속도

| 축 | 지금 있는 것 | 더할 것 |
|---|---|---|
| 토큰 집계 | `ai_usage_logs`(`charge_mode varchar(20)`) · `AiUsageDto`(Ym·입력·출력·합계·한도·잔여) — **테넌트 단위**로 이미 센다 | 🔴 **본사 풀은 테넌트 단위가 아니다.** 본사 전체 월 상한 + **티켓 1건당 상한** 두 개가 필요하다. 티켓당 상한이 없으면 긴 본문 하나가 하루 예산을 태운다 |
| 한도 | `MonthlyLimit`·`ExtraTokens`·`Remaining` 틀이 있다 | 본사 풀 장부는 **처음 생긴다**(§8-7: 지금껏 `hitpan_pool` 은 거짓 장부였고 작8 에서 `byok` 로 교정했다) ⇒ **거짓 장부를 되살리지 말고 새로 짠다** |
| 속도 | ⚠️미확인 — 재지 않았다 | 🔴 **CS 화면이 AI 응답을 기다리게 하지 않는다.** 초안 생성은 **비동기**(티켓 열면 "초안 준비 중")로 간다. 동기면 외부 지연이 백오피스 화면 지연이 된다 |
| 돈 | — | `cs_ai_calls` 류 호출 장부(공급자·입력·출력·추정비용 **DECIMAL(18,2)** #4 · 티켓ID) 를 **처음부터** 넣는다. 안 넣으면 "얼마 썼나" 를 영원히 못 센다 |

### §4-5 🔴 반자동 — "사람 확정 전 고객 발송 0건" 을 **어디서** 강제하나

이게 사장님 오더 중 가장 조용히 깨지는 자리다. 코드로 강제할 자리를 **세 겹**으로 지정한다:

1. **구조로** — 🔴 초안을 만드는 서비스와 고객에게 보내는 서비스를 **서로 모르게** 짠다. `CsAutoDraftService` 는 발송 함수를 **참조조차 안 한다**(DI 로 안 받는다). 호출할 수 없으면 사고가 날 수 없다.
2. **데이터로** — `bo_cs_replies`(백오피스 측 답) 에 `approved_by` · `approved_at` 를 **NOT NULL** 로. 🔴 **승인자 없이는 행이 안 생긴다** ⇒ 발송 큐는 그 표만 읽는다. 사람이 안 거친 글은 **물리적으로 보낼 몸통이 없다.**
3. **게이트로** — 시험이 **"초안을 승인 없이 발송 시도 → 실제로 거부된 로그"** 를 본다(음성 대조군). 🔴 통과 로그만 보는 게이트는 금지(누적 26번). **봉합을 빼고 FAIL 이 나오는지 먼저 확인**한다.

🔴 그리고 §8-6 의 **"승인 전 초안은 어벤져스팀에 안 넘어간다"** 도 같은 방식 — `bo_kb_docs.status='승인'` 아닌 행을 **쿼리 단계에서** 배제한다. 코드 분기(`if`)로 하면 새 호출자가 우회한다. 🔴 **WHERE 절에 박아야 한다.**

## §5 【보안 매니저】 보안·격리 — 5개 질문에 하나씩

### §5-1 ① 금지필드 **송신 단계 거부** — 어디서

🔴 **세 군데에 다 넣는다(심층방어).** 한 곳만 넣으면 새 호출자가 우회한다.

| 문 | 어디 | 근거 |
|---|---|---|
| 문① **ERP 입력 시점** | `CsRequestController` — 저장 **전**에 검사. 걸리면 **400 + 고객에게 "주민번호는 넣지 마세요"** | 고객이 고칠 기회를 준다. 저장 후 막으면 금지필드가 ERP DB 에 남는다 |
| 문② **ERP 송신 시점** | 큐→본사 송신 직전 한 번 더. 걸리면 `terminal_reason='rejected'` (재시도 안 함 — §2-2) | 문①을 우회한 경로(마이그·수동 INSERT)를 막는다 |
| 문③ **본사 수신 시점** | 🔴 **여기가 진짜 문이다.** 백오피스 수신 API 가 **화이트리스트 밖 필드를 거부**한다 | 아키텍처명세서 §5: *"payload 는 필드 화이트리스트로 못 박고, **서버가 초과 필드를 거부**"*. 구버전 ERP 가 돌아다닐 수 있으므로(워치독 선례 — `TelemetryController` 가 송신측·서버측 2중으로 막았다) **서버가 최종 판정자**다 |

**검사 규칙** — 쓸 수 있는 선례 2개를 실측했다. **새 기법 만들지 말고 이걸 따른다**:
- `src/HitPan.API/Services/Messaging/OutboxPublisherService.cs:30-40` — 사업자번호 정규식 `\b\d{3}-?\d{2}-?\d{5}\b` + 금지 JSON 키 8개(`business_number`·`company_name`·`representative_name`·`address`·`phone`·`mobile`·`email`·`resident_number`). 🔴 걸리면 **`InvalidOperationException` 강제 발생**(조용히 넘기지 않는다).
- `src/HitPan.Watchdog/Telemetry/MetaPingClient.cs:19-27` — 금지 필드명 집합 17개(`revenue`·`sales`·`purchase`·`transaction`·`invoice`·`item`·`customer`·`employee` 포함). 걸리면 **송신 자체를 중단**.

🔴 **다만 위 두 선례는 "JSON 키 이름" 을 본다. CS 본문은 자유 글이라 키 이름으로 못 막는다** ⇒ 본문용으로 **패턴 검사가 추가로 필요**하다:
주민번호(13자리·YYMMDD-NNNNNNN) · 카드번호(13~19자리 + Luhn) · 계좌(은행별 길이 — ⚠️ 오탐 위험 높다) · 사업자번호(위 정규식).
🔴 **"쉽다" 를 쓰지 않는다. 반증을 먼저 쓴다**: 숫자 패턴 검사는 **오탐으로 정상 문의를 막는다**(예: "전표번호 1234567890 이 안 열려요" 가 사업자번호로 잡힌다). ⇒ **거부가 아니라 "이 부분을 지워 주세요" 로 되돌려 주는 UX**가 필요하고, 그 판정의 정확도는 ⚠️**실측 전엔 모른다**. 규칙별 FAIL/오탐을 `cs_forbidden_rejects`(DB-142) 로 세어 **CS팀장이 규칙을 조정**한다(반자동).

### §5-2 ② 누리집 승격 시 고객 식별정보 제거 — **사람이 잊어도** 막는 장치

🔴 사람의 성실성에 기대는 설계는 설계가 아니다. **3겹**:

1. **초안 생성 단계에서 애초에 안 넣는다** — §8-6 이 요구한 "고객 식별 정보 제거된 상태" 를 **필드 화이트리스트로** 구현한다. 초안을 만드는 쿼리가 `tenant_id`·상호·담당자 칸을 **SELECT 하지 않는다.** 🔴 **가져오지 않은 값은 잊을 수도 없다.** 이게 가장 강한 장치다.
2. **승인 버튼 앞에 서버 검사** — `bo_kb_docs.status` 를 '승인' 으로 바꾸는 API 가 **본문을 다시 스캔**한다. 걸리면 승인 거부 + 어디가 걸렸는지 표시. 🔴 화면 검사만으로는 안 된다(API 를 직접 부르면 통과).
3. **어벤져스팀에 넘기는 입구에서 한 번 더** — `status='승인'` + 스캔 통과, 둘 다 **WHERE 절**에서(§4-5).

### §5-3 ③ 🚨 **A사 이슈가 B사 응대에 노출되는 길** — CS 지식에서 테넌트 격리가 새는 자리

§8-5 가 "안 하면 A사 이슈가 B사 응대 중에 노출된다" 고 한 줄로 적었는데, **우리가 새는 구멍을 구체적으로 세어 봤다. 4개다.**

| # | 새는 자리 | 어떻게 새나 | 막는 법 |
|---|---|---|---|
| 1 | **본문 그대로 승격** | A사가 "(주)대한상사 3월 매출" 이라 썼고 그게 누리집 문서가 되면, B사 응대에서 그 문서가 근거로 **인용**된다 | §5-2 (1)(2)(3) |
| 2 | 🔴 **희귀성 자체가 신분이다** | 식별정보를 다 지워도 "직원 3명 · 창고 2개 · 반제품 BOM 7단" 같은 조합은 **그 회사 하나뿐**이다. CS 담당자는 누군지 안다 | 🔴 승격 문서는 **증상·재현 조건·해결 순서만.** "그 회사의 모양" 을 적지 않는다. CS팀장 승인 체크리스트에 이 항목을 넣는다 |
| 3 | 🚨 **AI 호출에 "비슷한 이슈" 를 근거로 붙일 때** | §8-2 ④ 가 바로 이것이다. 근거로 붙는 게 **승인된 누리집 문서**면 안전하지만, **다른 테넌트의 티켓 원문**이 섞이면 그 순간 격리가 끝난다 | 🔴 **근거 출처를 `bo_kb_docs`(승인본) 하나로 제한**한다. `bo_cs_tickets` 를 근거로 쓰는 코드는 **쓰지 않는다**. 이것도 분기가 아니라 **쿼리 자체**로 |
| 4 | **백오피스 화면 권한** | `/admin/cs` 는 `[Authorize(Policy="PlatformOnlyV2")]` — **본사 전원**이 본다. 대리점이 열면 남의 고객사 티켓이 보일 수 있다 | `AdminCsListPage.razor:14` 가 본사용이다. **대리점용은 별 화면 + `reseller_id` 강제 필터.** 🔴 필터는 화면 파라미터가 아니라 **서버가 토큰에서 꺼낸 `reseller_id`** 로 — #2 와 같은 원리다. 파라미터로 받으면 바꿔서 보낸다 |

🔴 그리고 **ERP 쪽**: `cs_requests`·`cs_replies` 조회 쿼리는 **전부 `WHERE tenant_id = @TenantId`**, 그 값은 **JWT 에서만**(#2). 파라미터로 받는 코드가 들어오면 즉시 반려.

### §5-4 ④ 외부 API 키 보관 위치

| 어디 | 가능한가 |
|---|---|
| ERP 설치 EXE 안 | 🚫 **절대 금지.** 고객 PC 는 우리 손이 아니다. "Cloudflare API 토큰은 본사 서버에만(EXE 포함 금지)" 와 같은 원리 |
| 레포 · `appsettings.json` | 🚫 금지. 🔴 그리고 **문서·커밋메시지에도 값의 "모양" 조차 쓰지 않는다** — TruffleHog 가 **가짜 값도 잡고**, PR 스캔은 커밋 범위를 훑어 "나중에 지움" 으로는 안 지워진다(10/7 하루 두 번 사고) |
| 고객 PC 로컬 DB(`local_subscription`) | 🟡 **BYOK(고객 키)는 거기가 맞다 — 지금 그렇게 돈다.** 하지만 **본사 풀 키는 거기 두면 안 된다**(고객 PC 에 본사 돈 쓰는 키를 두는 것) |
| 🟢 **본사 NCP 백오피스 서버만** | ✅ 여기다. 환경변수 또는 NCP 비밀 저장소. 🔴 그리고 **어벤져스팀 호출은 백오피스 서버에서만 나간다** — §8-5: *"어벤져스팀이 DB 를 직접 보지 않는다. 백오피스 API 가 필요한 조각만 뽑아 넘긴다(권한은 서버 한 곳에서만 강제)"* |

🔴 **ERP(고객 PC)에서 본사 풀 AI 를 직접 부르는 길은 만들지 않는다.** 만들면 ① 키가 고객 PC 로 가고 ② 호출 장부를 본사가 못 센다 ③ 금지필드 검사를 우회할 수 있다. **CS 자동화는 전부 본사 쪽 일이다.**

### §5-5 ⑤ 작9 동의 게이트와의 접점

- 🔴 **ERP 쪽 게이트(`ExternalAiGate`)는 CS 자동화와 상관없다.** 실측: 그 게이트는 `hitpan_erp`(고객 PC 로컬 DB)의 `ai_export_consents` 를 보고, 막는 문은 **ERP 챗봇·AI직원**(`ChatbotService.cs:181·448`)이다. 어벤져스팀 호출은 **본사 NCP 에서 나가므로 이 게이트를 지나가지 않는다.**
- ⇒ 🚨 **그래서 백오피스 쪽에 같은 게이트를 **새로** 세워야 한다.** 안 세우면 §8-4 의 "지금 잠가 둔 자리가 그대로 어벤져스팀 연결 지점이 된다" 가 **사실이 아니게 된다** — ERP 게이트는 본사 호출을 막을 수 없다. 이게 보안팀의 1번 발견이다.
- **백오피스 게이트 모양** (ERP 쪽 fail-closed 원리를 그대로 복제):
  - `bo_ai_export_consents`(또는 `tenants` 의 동의 참조) 에 해당 테넌트 기록이 **있을 때만** 그 테넌트 티켓이 어벤져스팀 호출에 쓰인다. 표 부재·예외·0건 = **전부 닫힘**.
  - 🔴 **테넌트 단위다.** A사가 동의했고 B사가 안 했으면, B사 티켓은 초안을 못 받는다. 전역 on/off 스위치로 만들면 안 한 집 데이터가 나간다.
  - 🔴 **INSERT ONLY**(동의 기록은 증거 — DB-138 주석 그대로).
  - 🔴 **동의 기록을 임의로 INSERT 하지 않는다.** 작9 §7(법무 계약·국외이전 고지·대리점 위탁계약 + **사장님 결재**) 전에는 **동의 수집 화면 선개발도 금지**라고 DB-138 주석에 못 박혀 있다.
- 🟢 **그래서 §8-9 의 "법무가 늦어도 ⑤는 돈다" 는 기술적으로 맞다.** 누리집 검색 + 규칙 기반 제안은 외부로 안 나가므로 게이트와 무관하다. **우리도 그 순서를 지지한다.**
- ⚠️미확인: 백오피스 측 동의 표가 지금 있는지 **안 쟀다**(백오피스 DB DDL 전수 미확인).

## §8 4인 서명 — 각자 1번 걱정

- **풀스택 매니저**: 🔴 "AI 코드가 이미 있다" 는 말에 속으면 안 된다. **살아 있는 축은 `IChatCompletionProvider` 하나**고 `IAiProvider` 는 구현체 0개다. 그리고 **장애 전환은 없다** — "3사 지원" 은 사람이 화면에서 갈아타는 것이지 자동 전환이 아니다. 그걸 "이미 된다" 로 올리면 정정이 또 난다.
- **백엔드·DB 매니저**: 🔴 **DB-139 부터 네 장(139~142) 을 한 묶음으로 미리 다 짠다**(#9). 번호는 **머지 직전에 전 브랜치로 다시 센다** — DB-121/123 중복 사고가 이미 났고 겹치면 뒤가 **조용히 skip** 된다. `tenant_id` 는 `varchar(36)` + `utf8mb4_unicode_ci` 로 **못 박는다**(DB-138 주석이 혼재를 경고했다). 출하 DDL 동반을 **같은 커밋**에(#36 · DB-126 사고).
- **네트워크 매니저 마이클**: 🔴 지금 본사로 가는 코드는 **전부 실패하면 버린다**(큐 0줄). 쪽지에 그걸 쓰면 고객이 쓴 글이 사라진다. **DB 큐 + 키 멱등 + 4xx/5xx 구분 + 상한 있는 백오프, 그리고 "안 갔음" 이 고객 화면에 보이기.** 17시나리오 #1·#2·#4 는 **반드시 다시 잰다** — ERP 본체가 바깥으로 나가는 건 **이번이 처음**이다.
- **보안 매니저**: 🚨 **ERP 게이트는 본사 호출을 막지 못한다.** "작9 가 잠가 뒀으니 안전하다" 는 틀린 안심이다 — `ExternalAiGate` 는 고객 PC 로컬 DB 를 보고 ERP 챗봇만 막는다. **백오피스 쪽 fail-closed 게이트를 1차에 신설**해야 "닫혀 있다" 가 사실이 된다. 그리고 테넌트 격리는 **희귀성으로도 샌다**(§5-3 #2) — 식별자를 지우는 것만으로는 부족하다.
