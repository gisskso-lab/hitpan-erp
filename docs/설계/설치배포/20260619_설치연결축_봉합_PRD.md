**연결축 코드는 14단계 거의 완비. 설치 후 "첫 로그인까지 도달"을 막던 진범은 빌드게이트 숫자 불일치(137/8 기대 vs clean 실제 121/3) → 빌드 영구 차단. FK 위반은 이미 clean에서 봉합됨. A안 = 게이트 숫자 2줄 정정으로 빌드 해제 → E2E 검증.**

### 2-2. 설치 후 첫 로그인 — 진범 [실측 확정]
**증상**: 빈 PC에 EXE 설치 → /setup/license Step3 "부모계정 생성" 클릭 → 500 → 로그인 불가.

**진범 (2겹)**:
1. **(이미 봉합됨) FK 위반**: 과거 번들 DB에 `fk_users_tenant` 등 tenants 참조 FK가 살아있어, tenants 비어있으면 users INSERT가 ERROR 1452. → **현재 `installer/hitpan_db_clean.sql`에서 tenants 참조 위험 FK 18개 전원 비활성화 완료**(주석 처리). hitpan_db_clean.sql:3598 등. **추가 작업 불필요.**
2. **(진짜 살아있는 차단) 빌드게이트 숫자 불일치**: clean 파일을 번들로 만들려면 build-installer.ps1 게이트 3을 통과해야 하는데:
   - `$ExpectedTables = 137` (build-installer.ps1:212) vs clean 실제 **121** → `-ne`로 즉시 차단(:214-216)
   - `$ExpectedTriggers = 8` (build-installer.ps1:213) vs clean 실제 **3** → `-lt`로 차단(:218-220)
   - → **clean 파일은 멀쩡한데 게이트가 옛 숫자(137/8)라 빌드를 영구 차단.** 이게 봉합 안 된 진짜 P0.

**왜 137/8이 틀렸나 [실측]**:
- clean은 본사 HQ/대리점/플랫폼/랜딩 테이블 16개를 제거한 121테이블판(헌법 #18·#22·#35 부합). 제거 16개 = reseller_*(9)+platform/HQ(6)+landing(일부). 
- 트리거 8개 중 5개는 그 제거된 본사 테이블(platforms, reseller_*) 전용 UUID 트리거 → 동반 소멸. **ERP 필수 트리거 3개는 정확히 보존**: trg_psp_ratio_insert/update(거래처 특별단가 비율), trg_tax_invoices_issued_lock(세금계산서 발행 후 변조 차단). hitpan_db_clean.sql:2243·2258·3232.
- 즉 121/3이 올바른 값이고 137/8은 계층제거 이전 옛 기준.

### 2-3. 트리거 성격 [실측 — 안심 근거]
- 재고/원장/회계 자동반영 트리거는 **0개**. 핵심 무결성은 앱 서비스 계층이 담당.
- 8개 = UUID자동채움 6 + 비율계산 1 + 세금계산서잠금 1, 전부 부수적. 버린 5개는 본사 전용이라 ERP 로컬에 무의미. → **트리거 3개로 줄어도 ERP 기능 손상 없음.**

## 3. 구현 설계 (A안 — 사장님 결재 2026-06-19)

### 3-1. 봉합 작업 (최소 변경)
**파일 1개 수정: installer/build-installer.ps1**
- :212 `$ExpectedTables = 137` → `121`
- :213 `$ExpectedTriggers = 8` → `3`
- :175·:208 주석 "137 테이블 + 8 트리거" → "121 테이블 + 3 트리거" 동기화(문서 정합)
- (게이트 4 common_codes-only, 게이트 1·2 백도어·금지구문은 clean 이미 통과 — 손 안 댐)

**clean 파일(installer/hitpan_db_clean.sql): 수정 없음**
- FK 18개 이미 비활성화, 트리거 3개 보존, INSERT common_codes만 — 현 상태로 게이트 통과 가능(숫자 정정 후).
- 단 헤더 주석(:5 "137 테이블 + 8 트리거")은 실제(121/3)와 불일치 → 주석만 동기화 권장(빌드 영향 없으나 혼선 방지).

### 3-2. 봉합 안 하는 것 (이번 범위 밖, 별건)
- 트리거 8개를 clean에 억지로 채우기 → ✗ (본사 테이블이 없어 불가능, 불필요)
- FK를 유지하고 tenants INSERT 추가(B안) → ✗ (사장님 A안 채택, 계층제거 방향과 어긋남)
- 백오피스 promotions/promotions_legacy 통합, CS·대리점 기능 추가 → 별건(2026-06-19 사장님 지시)

## 4. 배포·검증 설계

### 4-1. 빌드 → 배포 절차 (헌법 #29 — 실행은 사장님)
1. build-installer.ps1 게이트 숫자 정정 커밋(개발팀, 사장님 결재 후).
2. 빌드 재실행 → 게이트 4/4 통과 확인(이전엔 게이트 3에서 차단).
3. **실토큰 EXE 빌드** — 테스트 토큰 아닌 운영 Cloudflare 토큰으로(헌법 #34). (토큰 주입은 사장님 영역 #29)
4. 빈 PC(또는 sandbox-test.wsb)에 설치 → E2E.

### 4-2. E2E 검증 시나리오 (이게 통과해야 P0 종결)
**빈 PC에 EXE 설치 → 로그인까지 무중단:**
1. EXE 실행(관리자) → 시리얼 입력
2. MariaDB 설치 → DB 생성 → 스키마 import(121테이블·3트리거) → **테이블 91+ 검증 게이트 통과**
3. cloudflared 터널 기동 → 외부 도메인 200(실토큰)
4. ERP API/Web 기동 → 브라우저 자동 오픈
5. /setup/license Step1~4: 시리얼+사업자번호 → 회사정보 → **부모계정 생성(500 안 나야 함 ← 핵심)** → 로그인 링크
6. 로그인 성공 → 대시보드

**판정**: 5번 부모계정 생성이 200이면 P0 봉합 확정. (FK 제거가 실제 빈 DB 설치에서 작동하는지 = 진짜 증명)
