## 1. 왜 이 설계가 필요한가 — 실측 채증

### 1-1. main 푸시 시크릿 스캔이 11건 전부 실패했다

```
$ gh run list --workflow=trufflehog.yml --branch main --limit 12
failure push 2026-07-31 bc51f1d
failure push 2026-07-31 2a45143
failure push 2026-07-30 90fffbd
... (11건 전부 failure, 7/21~7/31 성공 0건)
```

### 1-2. 그런데 시크릿이 검출된 게 아니었다

```
##[error]BASE and HEAD commits are the same. TruffleHog won't scan anything.
##[error]Process completed with exit code 1
```

**스캔이 시작조차 못 했다.**

### 1-3. 원인 — base 가 항상 'main' 고정

```yaml
base: ${{ github.event.repository.default_branch }}   # → 항상 "main"
head: HEAD
```

main 에 푸시되면 `base == HEAD` → 액션 가드에 걸려 죽는다.

**액션 내부 동작 (로그 실측)**:

| base/head | 동작 |
|---|---|
| 하나라도 값 있음 | 그 값으로 비교. **같으면 exit 1** |
| 둘 다 비어 있음 | 이벤트별 자동 분기 (`push`=`before..after`, `pull_request`=PR base) |

⇒ **값을 넣는 행위 자체가 자동 분기를 막고 있었다.**

### 1-4. 주석과 코드가 달랐다

> 종전 주석: *"PR이면 base..HEAD, push면 before..after"*

코드는 그렇게 동작하지 않았다. **작10 P0 와 같은 종류** — 주석이 실동작을 잘못 서술했고 아무도 반증하지 않았다.

---

## 2. 왜 P0 인가 — 침묵보다 나쁘다

PR 스캔은 정상 작동한다(main 유입은 전부 PR 경유). **따라서 실제 유출 가능성 자체는 낮다.**

문제는 **빨간 X 가 상시화**된 것이다:

```
늘 실패하는 체크  →  아무도 안 본다  →  진짜 유출이 나도 같은 빨간 X  →  구분 불가
```

오늘 아침 [main Ruleset 이 일주일간 꺼진 채 방치된 것](../../운영기록/20260731_사고기록_main보호_일주일_무방비_재잠금.md)과
**같은 구조**다. 못 지켜지는·늘 깨지는 장치는 **죽은 장치**다.

## 4. 설계 — 두 갈래로 나눈다

### 4-1. [본건] base·head 비우기 — G-1

```yaml
# 종전
base: ${{ github.event.repository.default_branch }}
head: HEAD

# 봉합 — 두 줄 제거. 액션이 이벤트별로 알아서 잡는다
(없음)
```

`fetch-depth: 0` 은 **유지**한다. `before` 커밋이 로컬에 있어야 diff 가 성립한다.

### 4-2. [오탐] SSH 룰 검출 **2건** (해당 파일 3개) — G-2

> ⚠️ 1차 작성분은 "3건"이라 적었으나 **실측 검출은 2건**이다(검증팀 P1-1).
> 파일 3개 중 1개는 검출되지 않았다 — 제외 3건 중 1건은 불필요할 수 있다(§7-1 에서 확인).

**검출 정체 (실측)**

| 파일 | 내용 | 키 본문 |
|---|---|---|
| `.github/trufflehog-config.yaml` | 룰이 **자기 자신의 패턴 문자열**에 매칭 | ❌ 없음 |
| `docs/개발/업데이트배포/20260724작1v2_…작업지시서.md` | 신설할 룰의 `regex:` 한 줄을 본문에 인용 — 룰을 만들라는 **지시문** | ❌ 없음 |
| `docs/개발/업데이트배포/20260724작3_…작업지시서.md` | 동일 | ❌ 없음 |

워킹트리 전체 검색에서도 **실제 키 본문(base64 블록) 0건**.

⇒ **순수 오탐.** 이 3파일만 스캔 대상에서 제외한다.

### 4-3. [진탐] 개발 DB 비밀번호 리터럴 — G-3, **제외하지 않는다**

> ※ 이 문서는 그 비밀번호 문자열을 **그대로 적지 않는다.** 적는 순간 이 설계서가
> `hitpan-db-password` 룰에 걸려 새 오탐이 된다(실측: 1차 작성분이 정확히 그랬다).
> 값은 `CLAUDE.md` 접속 정보와 `.github/trufflehog-config.yaml` 룰에 있다.

스캔이 돌자 드러난 **실제 문제**:

| 파일 | 형태 | 판정 |
|---|---|---|
| `installer/install.bat:51,85,92` | **MariaDB 계정을 이 비번으로 실제 생성** | 🔴 **진탐** |
| `scripts/backup-daily.ps1:7` | env 없으면 이 값으로 폴백 | 🟡 진탐 |
| `installer/HitPan-Universal.iss:1542` | 주석 | 오탐 |
| `src/HitPan.Application/Services/BackupService.cs:404` | 주석 | 오탐 |
| `src/HitPan.IntegrationTests/…/DbFixture.cs:15` | 로컬 테스트 픽스처 | 오탐(테스트) |
| `docs/**` 38건 | 문서 | 오탐 |

**`install.bat` 이 급소다.** 고객 PC 마다 **동일한 DB 비밀번호**로 계정을 만든다.
한 곳이 뚫리면 전 고객사가 같은 자격증명으로 열린다.

> `installer/hitpan-start.bat:20` 주석에 *"사고 #38 봉합: 폴백 비밀번호 제거"* 가 있다.
> **같은 문제를 한 번 잡았는데 `install.bat` 은 남아 있었다.**

⇒ **오늘 범위 밖.** 설치 흐름 전체(계정 생성·db.conf·백업·마이그레이션)를 건드려야 한다.
⇒ **덮지 않는다.** `hitpan-db-password` 룰을 유지해 빨간 X 로 남긴다.
⇒ **별건 작업지시서**로 문서화해 추적한다.

## 5. 이 봉합 후 스캔은 여전히 빨간 X 다 — 의도된 것이다

| | 봉합 전 | 봉합 후 |
|---|---|---|
| 결과 | 🔴 실패 | 🔴 실패 |
| **이유** | **설정 결함** (스캔 미수행) | **실제 하드코딩 비번** |
| 봐야 하나 | ❌ 볼 게 없다 | ✅ **봐야 한다** |

**증상은 같고 의미가 정반대다.** 봉합 전 빨간 X 는 무의미했고, 봉합 후 빨간 X 는 진짜 지적이다.

이걸 초록으로 만들려고 진탐을 제외하면 **오늘 작업이 무의미해진다**(G-4 위반).

### 6-1. R-6 은 예측이 아니라 실제로 일어났다 (1차 커밋 `575cc8f`)

제외 목록과 이 설계서의 1차 작성분이 **제외 이유를 설명하느라 탐지 패턴을 그대로 인용**했고,
그 결과 **새 오탐 3건**을 만들었다. 실측:

```
"base": "b073027", "head": "575cc8f"     ← 이번 푸시 2커밋만 스캔
"chunks": 4, "unverified_secrets": 3     ← 전부 방금 추가한 두 파일에서
```

| 파일 | 만든 오탐 |
|---|---|
| `.github/trufflehog-exclude-paths.txt` | SSH 헤더 1건 |
| 이 설계서 (1차분) | DB비번 2건 + SSH 헤더 1건 |

> **오탐을 없애러 온 파일이 오탐을 만들었다.**
> 작10 P1-3 *"침묵을 없애러 온 함수가 침묵을 만들었다"* 와 같은 구조다.

**봉합 방식**: 이 두 파일을 제외 목록에 추가하지 **않는다.**
제외 목록이 자기 자신을 제외하면 자기참조로 스캐너를 무력화하는 첫걸음이 된다.
⇒ **문서에서 패턴 문자열을 빼는 것**으로 해결한다. 제외 없이 오탐이 사라진다.

**규칙**: 시크릿 관련 문서는 **탐지 패턴을 그대로 적지 않는다.** 값이 필요하면 위치만 가리킨다.

## 8. [3-V] 병렬검증 반려 및 정정 (보안상무 안철수 · 2026-07-31)

작업 **도중** 독립 반증이 들어와 **P0 2건 · P1 2건**을 적발했다. 지적이 전부 옳았다.

### 8-1. 🔴 P0-1 — 제외 규칙이 한 번도 실동작 검증되지 않았다

§6 R-4 에 *"실측으로 검출 0건 확인 (추측 금지)"* 라고 적었으나 **그 실측은 존재하지 않았다.**

```
$ git diff --name-only main...HEAD
.github/trufflehog-exclude-paths.txt
.github/workflows/trufflehog.yml
docs/설계/보안/20260731_시크릿스캔_정상화_설계서.md
```

**제외 대상 3파일 중 어느 것도 브랜치 diff 에 없다.** 봉합 후 스캔은 전부 차등(`before..after`)이라
그 파일들을 **애초에 읽지 않았다.** 검출 0건은 제외가 작동한 증거가 아니라 **스캔 범위 밖**이었을 뿐이다.

> **이것이 이 프로젝트가 반복 지적해 온 "주석과 실동작 불일치"와 정확히 같은 구조다.**
> 작10 이 *"검증된 패턴이라 불렀지만 선례 0건"* 이었던 것과 같다.
> PM 이 **없는 실측을 있다고 문서에 적었다.**

**봉합**: §7-1 — 제외 대상 파일에 무해한 주석 1줄을 넣어 차등 스캔 범위에 올리고 실측한다.

### 8-2. 🔴 P0-2 — 채증 run 이 main 이 아니었다

§1-1 이 근거로 든 `30614738083` 은 **main 이 아니라 작업 브랜치**의 run 이다.

| run | 브랜치 | 성격 |
|---|---|---|
| `30614385889` | **main** (`bc51f1d`) | ✅ 봉합 전 main 실패 — **이것이 올바른 채증** |
| `30614738083` | `fix/trufflehog-…` (`b073027`) | ❌ 봉합 후 브랜치 푸시 |

원인 진단(`base==HEAD` → exit 1)은 액션 소스 로그로 확인되어 **맞다.** 그러나 채증이 어긋났으므로
**"main 푸시에서 스캔이 돈다"(G-1/V-1)는 아직 미증명**이다. main 실측은 머지 후에만 가능하다.

### 8-3. 🟡 P1-1 — SSH 검출은 3건이 아니라 2건

```
$ gh run view 30614738083 --log-failed | grep -c 'hitpan-ssh-private-key'
2
```
전체: `hitpan-db-password` 102 · `SQLServer` 8 · `hitpan-ssh-private-key` 2 = 117 (`unverified_secrets: 117` 일치).

**파일은 3개인데 검출은 2건이다.** 제외 3건 중 1건은 불필요할 수 있다 — §7-1 실측으로 확인한다.

### 8-4. 🟡 P1-2 — SQLServer 검출 8건을 분석하지 않았다

설계서에 이 검출 종류 언급이 **한 줄도 없었다.** OSS detector 라 custom 룰 제외 대상도 아니다.
접속 문자열(`Server=…;Password=…`) 패턴이며 개발 DB 비번과 같은 위치일 **가능성이 높으나 미확인**이다.

⇒ **추정으로 닫지 않는다.** `install.bat` 별건 작업지시서에 **함께 포함**해 분류한다.

### 8-6. 현재 PR 이 빨간 X 인 진짜 이유

진탐이 아니라 **히스토리 커밋 `575cc8f` 에 남은 패턴 인용문**이다.
