## 1. 증상 (실측)

`installer/updates/build-manifest.ps1`로 1.2.34 update zip을 만들려 하면 **호환성 게이트(88행)에서 빌드 실패**:
```
호환성 게이트 위반 — DB-82_watchdog_update_consents.sql 이 'local_update_' 를 건드립니다.
```
- 걸린 파일: `DB-82_watchdog_update_consents.sql`, `DB-83_local_update_status.sql`
- 둘 다 **2026-06-29 고리2 때 만든 기존 파일**(커밋 `c1221f9`). 이번 릴리스 신규 아님.
- 우리 W4-6 신규(`local_update_apply_status`)는 **zip에 없음**(clean DDL + 워치독 자가생성 설계라 정상).

## 2. 원인 (설계와 구현의 불일치)

### 작업지시서 원문 (20260715작1 §253·§263)
- §253: "B안 스캐너가 **zip 해제 후** `Migrations/SQL`에 신규 파일이 있으면 강제 중단" (워치독 런타임 게이트 — 이미 UpdateOrchestrator에 구현됨)
- §263: "스캐너가 `Migrations/SQL/*.sql`을 훑을 때 **`local_update_` 문자열이 걸리면 빌드 실패**" (build-manifest 빌드타임 게이트)

### 구현의 문제
build-manifest.ps1(85~101행)이 스캔하는 대상 = **api publish 산출물의 `Migrations/SQL/DB-*.sql` 전체**. 이 폴더엔 **과거 모든 마이그 이력이 항상 포함**된다(csproj가 전부 복사 — 20260716작1 W-0 봉합). 그 안에 `local_update_status`·`consents`를 **처음 생성한** DB-82/83이 항상 있으므로, `local_update_` 문자열이 **모든 릴리스에서 무조건 검출**된다.

### 결과
- **이 게이트 도입 후 build-manifest.ps1로 manifest를 성공 생성한 적이 0회**(git 이력 없음·생성된 manifest.json 없음 = 실측). 고리4 배포 파이프라인이 이 지점에서 처음부터 막혀 있었다.
- 게이트가 막아야 할 것("이번 릴리스가 local_update_ 스키마를 **바꾸는가**")과 실제 막는 것("payload에 local_update_ 문자열이 **존재하는가**")이 다르다. **존재는 정상, 변경이 위험**인데 존재를 막는다.

## 3. 왜 이게 위험한 게이트였나 (정당성은 유효)

게이트의 **목적 자체는 옳다**(CTO C-2): 구버전 워치독이 `local_update_status`·`consents`를 직접 SQL로 읽고 쓰므로, 릴리스가 그 **스키마를 바꾸면** 구버전 워치독이 깨진다(영구 고립). 막아야 할 건 "**변경**"이다. 지금 구현은 "존재"를 막아 목적을 초과 달성(=전면 차단)한 오탐이다.

## 4. 수정안 (3택, CTO 판단 요청)

### A안 — "변경" 판정으로 교체 (권장)
게이트가 "payload의 local_update_ SQL"이 **clean DDL(단일 진실원)과 스키마가 다른가**를 본다. 즉:
- update zip에 넣을 마이그 SQL 중 `local_update_` 관련 파일의 **CREATE/ALTER가 clean DDL의 해당 테이블 정의와 다르면** 빌드 실패.
- 같으면(=기존 스키마 재현일 뿐 변경 아님) 통과.
- 장점: 목적("변경 차단")에 정확. 단점: 스키마 비교 로직 필요(공수 증가).

### B안 — update zip에서 Migrations/SQL 자체를 제외 (가장 단순·안전)
자동업데이트(고리4)는 **파일 교체만** 하고 DB 마이그는 고리5 범위다(1차 릴리스는 마이그 없음 = B안 대전제). 그렇다면 **update zip에 `Migrations/SQL/*.sql`을 애초에 넣을 이유가 없다.**
- build-manifest가 zip을 묶을 때 api의 `Migrations/SQL` 폴더를 **제외**.
- 게이트는 "zip에 마이그 SQL이 있으면(=고리5 전인데 마이그 동반) 실패"로 **의미가 명확**해짐.
- 장점: 게이트 목적과 완전 정합, 공수 최소. 신규설치는 clean DDL, 업데이트는 파일교체 — 마이그 SQL이 update 경로에 낄 자리가 없음.
- 단점: 나중 고리5(마이그 지원) 설계 시 zip에 SQL 넣는 방식 재설계 필요(그때 정식 설계).
- ⚠️ 확인 필요: 워치독 런타임 게이트(UpdateOrchestrator의 zip 해제 후 Migrations/SQL 검사)가 이 제외와 정합하는가 — zip에 SQL이 없으면 런타임 게이트는 "신규 마이그 0"으로 정상 통과. 정합.

### C안 — 기존 파일 화이트리스트
DB-82/83처럼 **이미 출하된 local_update_ 파일 목록을 화이트리스트**로 두고, 그 외 새 파일만 차단.
- 단점: 화이트리스트 유지보수 = "사람의 약속을 코드로"라던 C-2 정신에 역행. 새 컬럼을 기존 파일에 추가하면 못 잡음(파일명은 그대로). **반려 예상.**

## 5. PM 의견
**B안 권장.** 게이트 목적(변경 차단)과 자동업데이트 설계(파일교체만, 마이그는 고리5)가 만나는 지점이 "update zip엔 마이그 SQL이 없어야 정상"이다. A안은 정확하나 스키마 비교 공수가 크고, 지금 1차 범위(마이그 없는 릴리스)엔 과설계. C안은 C-2 정신 역행.
