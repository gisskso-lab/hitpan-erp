## 3. ② CI 실행 (1.2.35 / Emergency)

머지 후 GitHub Actions 에서 **Build Installer EXE** 워크플로를 `workflow_dispatch` 로 실행한다.

| 입력 | 값 | 사유 |
|---|---|---|
| version | **1.2.35** | 현 설치본(1.2.34)보다 높아야 워치독이 감지한다 |
| channel | **Emergency** | 아래 게이트 표 참조 |

### ⚠️ 채널 선택이 실측 성패를 가른다

| 채널 | 워치독 동작 | 오후 실측 |
|---|---|---|
| **Emergency** | 안내 후 **즉시 적용**(시간 무관) | ✅ **바로 관측 가능** |
| Normal | 야간(새벽 3시대)에만 적용 | ❌ 새벽까지 대기 |
| Major | 로그인 Y/N 동의 + **영업시간 외**에만 적용 | ❌ 밤까지 대기 |

**Major·Normal 로 올리고 낮에 "보류" 로그가 뜨는 것은 정상 동작이다.**
이것을 "업데이트 실패"로 읽으면 2026-07-20 의 오판이 그대로 재발한다.
관련 코드: `Worker.cs:398`(영업시간 게이트) · `Worker.cs:307`(하루 1회 게이트).

### CI 가 하는 일 (오늘 배선분)
1. API·Web·**워치독** publish (`-p:HitPanVersion` 주입 — 버전 갈라짐 차단)
2. 의존성 번들 5종 다운로드 + clean DDL 배치
3. 인스톨러 컴파일 (`/DBundleDir=payload` 주입)
4. **`build-manifest.ps1`** → `hitpan-1.2.35.zip` + `manifest-1.2.35-unsigned.json`
   - 버전은 api EXE 의 FileVersion 에서 **단방향**으로 읽는다(사람이 두 번 입력하지 않음)
   - 워치독/api 버전 불일치 시 즉시 실패
   - `local_update_*` 스키마 변경 게이트 (사전 점검 결과 **ALTER 0건 = 통과 예상**)
5. 산출물 업로드: `HitPanUpdate-1.2.35`, `HitPanInstaller-1.2.35`

> ⚠️ 이 워크플로는 **오늘 처음 완결된 것**이라 첫 실행에서 실패할 수 있다.
> 실패 시 로그의 실패 스텝명을 PM 에게 전달하면 봉합한다(오늘 CI 봉합도 3라운드 걸렸다).

## 5. ④ NCP 배포 (사장님, sudo 1회)

두 파일을 NCP 서버로 옮긴 뒤:

```bash
sudo bash publish-update.sh \
  --zip      hitpan-1.2.35.zip \
  --manifest manifest-1.2.35-unsigned.json
```

이 스크립트가 원자적으로 수행하는 것:
1. 입력 검증 (zip 실측 sha256 == manifest.sha256, 파일명 대조)
2. **다운그레이드 게이트** (현 manifest 1.2.34 보다 높은 버전만 허용)
3. zip 배치 → `packages/hitpan-1.2.35.zip`
4. **서명** (개인키는 NCP `/var/hitpan/update-keys/` 600 root 에만 존재)
5. **원자 교체** (tmp → mv, 옛것은 `.bak` 백업)
6. **자기검증** (curl 로 서빙본 재취득 → 버전·서명·zip 200 확인)
   → 하나라도 실패 시 `.bak` 자동 롤백 (옛 manifest 유지 = 전 고객 정지 아님)
