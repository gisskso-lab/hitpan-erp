> 헌법 #20(워크플로우 무결성)·#33(의중 재확인 후 코드)·#36(출하 DDL 단일 진실원) 정합.

## 1. 문제 (전수조사 + SoD 반증 확정)

`BomService.AssembleAsync`(생산)·`DisassembleAsync`(해체) 의 stock_ledger INSERT 4곳(547·559·709·774)이
**서버에서 매 호출 `productionRunId = Guid.NewGuid()`(:439)를 source_id 로 생성**한다.
- 정상 반복생산(같은 BOM 10회) = 매번 다른 GUID → 다 통과(정상, 유지해야 함).
- **사고성 중복(더블클릭·네트워크 재시도로 같은 1회가 2번 전송)** = 서버가 매번 새 GUID → UNIQUE 회피 → **둘 다 INSERT 성공 → 재고 2배**(헌법 #20 오염).

판매·매입·반품 9개 경로는 `status != Draft/confirmed` 가드(SalesService:273 등)로 **이미 멱등** — 보존(점검 완료).
→ **BOM 4곳만 근본해결 대상.**

## 2. 근본 원인

서버가 멱등키를 만들면(매번 새 GUID) 클라이언트의 "같은 1회"를 식별할 길이 없다.
**멱등키는 클라이언트가 한 호출당 하나 생성해, 재시도 시 같은 키를 재전송**해야 서버가 중복을 판정할 수 있다(표준 idempotency 패턴).

## 3. 해결 설계 — ⭐정정: 멱등 인프라가 이미 있다. "살려서 BOM에 적용"이 근본해결

### ⚠️ 전수조사 재확인 (받아쓰기·과설계 차단)
새 테이블을 만들 뻔했으나 실측 결과 **멱등 인프라가 이미 완성돼 작동 중**이다(사장님 "이미 있다면 살려라"의 정확한 지점):
- `idempotency_keys` 테이블 — clean DDL:1414 (요청해시+응답캐시+TTL, 이미 존재)
- `IdempotencyMiddleware.cs` — `Idempotency-Key` 헤더 처리(헤더누락 400 / 같은키+다른본문 409 / 캐시적중 재응답 / fail-open)
- `[IdempotencyKey]` 속성 — 옵트인 데코레이터
- `IdempotencyCleanupService.cs` — TTL 1h 정리
- **이미 적용된 곳**: SalesController:140(deliveries/confirm), PurchaseController, TaxInvoiceController

→ **근본해결 = 새 코드/테이블 0건. BOM 두 엔드포인트에 기존 인프라를 적용(누락 메꿈).**

### 3-1. 서버 — BOM 엔드포인트에 `[IdempotencyKey]` 부착 (SalesController:140 패턴 그대로)
- `BomController.cs:135` `[HttpPost("assemble")]` 바로 아래 `[IdempotencyKey]` 추가.
- `BomController.cs:152` `[HttpPost("disassemble")]` 바로 아래 `[IdempotencyKey]` 추가.
- 미들웨어가 자동으로: 같은 키+같은 본문 = 캐시 재응답(재고 무변경) / 다른 키 = 정상 통과(반복생산 보존).
- DDL·서비스·DTO 변경 **0건**(BomService.AssembleAsync 무손상, productionRunId 유지).

### 3-2. 클라이언트 — `Idempotency-Key` 헤더 전송 (필수 — 안 보내면 400)
- ⚠️ 속성 부착 시 헤더 없으면 미들웨어가 **400**(BomService.cs Web:218·239 현재 헤더 미전송 → 그대로면 생산 400 = 헌법 #20 역위반). **반드시 같이 수술.**
- `AssembleWithErrorAsync`·`DisassembleWithErrorAsync`(Web BomService.cs:214·235)에서 `Idempotency-Key` 헤더 추가.
- 키 = `Guid.NewGuid().ToString("N")` (TaxInvoiceApiService:17 패턴). 메서드 1회 호출 = 키 1개 → HttpClient 동일요청 재전송(타임아웃 재시도)은 같은 키 유지 → 중복 차단. 새 생산 클릭 = 새 호출 = 새 키 → 반복생산 보존.
- `PostAsJsonAsync` → `HttpRequestMessage` 로 바꿔 헤더 부착(DeliveryService:179 패턴).

### 3-3. DDL
- **변경 없음.** idempotency_keys 이미 clean DDL:1414 존재. 헌법 #36 동기화 불필요.

## 6. 절대 보존 (받아쓰기 차단)
- **정상 반복생산을 막으면 안 된다**(헌법 #20 역위반). 멱등키가 다르면 무조건 통과.
- DDL은 clean DDL 먼저(헌법 #36). 마이그/운영DB 직접 ALTER 금지(B-1 배포가 정합 반영).
