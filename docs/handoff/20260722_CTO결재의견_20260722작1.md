## 🔴 BLOCKING (해소 후 착수)

### B-1 — 게이트가 매 페이지 이동마다 팝업을 재조회·재노출하는 무한 안내 위험
`MainLayout` 은 로그인 후 **모든 화면의 껍데기**다. `UpdateConsentGate` 를 여기 넣으면
페이지를 옮길 때마다 `OnInitializedAsync` 가 재실행될 수 있다. 가드가 없으면:
- 고객이 [나중에]를 눌러도 다음 화면에서 또 뜸 → **업무 방해**(헌법 #20 워크플로우 끊김).

**해소 요구**:
- 게이트는 **레이아웃 생명주기 1회만** 조회한다(페이지 이동마다 재조회 금지).
- [나중에] 거부는 **이 세션 동안 재노출 안 함**(sessionStorage 플래그 등). 다음 로그인엔 재안내 OK.
- 작지서 W-2 의 "한 세션에 1회만" 을 **구현 방법까지** 명시(플래그 키·저장 위치).

### B-2 — 신규 GET `api/auth/update-status` 인증 가드 명시 누락
작지서 W-1 이 "인증 필요"라고만 썼다. 실측 확인 결과 `update-consent` 는 `[Authorize]`(L223)이고
`local_update_status` 조회는 tenant 필터 불요(로컬 단일 테넌트). 신규 GET도 **반드시 `[Authorize]`**
로 달아야 한다 — `[AllowAnonymous]` 로 잘못 달면 미인증자가 버전 정보를 긁는다(경미하나 원칙 위반).

**해소 요구**: W-1 에 `[Authorize]` 명시. 미인증 401 시 게이트는 조용히 스킵(W-2 방어와 정합).

## 🟡 권고 (착수 가능, 반영 권장)

### A-1 — 로그인 응답 기존 필드 제거 금지 재확인
작지서가 "로그인 응답 기존 필드 유지"라 썼다. **정확하다.** `LoginApiResponse` 의
`UpdateAvailable`·`LatestVersion` 등을 제거하면 회귀 위험. 게이트는 신규 GET만 쓰되,
**기존 필드는 dead 라도 남겨둔다**(하위호환). 다음 정리는 별도 안건.

### A-2 — 조회 로직 추출 시 동작 동일성 보장
W-1 이 `EnrichUpdateConsentInfoAsync` 로직을 private 추출해 공용화한다. 추출 후
**로그인 경로의 기존 동작이 1비트도 안 변해야** 한다(SemVer 비교·폴백 포함). 검증 게이트 8에 포함됨 — 확인.
