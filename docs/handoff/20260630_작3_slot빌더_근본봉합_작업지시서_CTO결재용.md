## 2. 사고의 정확한 원인 (코드 실측)

### M2 — slot 빌더가 운영 db.conf 경로에 씀
- **파일**: `tests/scenarios/comms-integrity/Build-TestSlot.ps1`
- **봉합점**: `$DbConfPath = 'C:\Program Files\HitPan\db.conf'` (param 기본값, 약 라인 58) → Step [4] db.conf 생성(약 라인 343~366)이 **이 운영 경로에 테스트값을 씀**.
- **실측 피해**: 오늘 demo의 `C:\Program Files\HitPan\db.conf`가 `PRIMARY_DOMAIN=e2e-comms.hitpan.kr / DB_NAME=hitpan_e2e`로 덮임. demo API(TenantConfigReader가 이 파일 읽음)가 **재시작 시 인증 깨짐 잠복**.
- **근본 원인**: 테스트 슬롯의 db.conf를 **격리 경로(C:\HitPanTest\)가 아니라 운영 공유 경로**에 둔 설계 결함.

### M3 — demo 보호 가드가 "서비스명"만 봐서 같은 인스턴스 demo를 못 막음
- **파일**: 같은 파일, `Test-DemoServiceRunning`(약 라인 178~192)
- **봉합점**: 가드가 `Get-Service 'cloudflared'/'MariaDB'`(서비스명)만 Running 체크 → **WARN만** 하고 진행.
- **실측 피해**: demo는 **MariaDB 11.4(3306) 인스턴스의 `hitpan_erp` DB**로 살아있는데, 서비스명 가드는 이를 "테스트 PC면 정상"으로 통과시킴. 결과로 운영 인스턴스(3306) 안에 `hitpan_e2e`를 만듦(129만 행 demo 옆에).
- **근본 원인**: "운영 존재 판정"을 *서비스명*으로 했지 *DB 존재*로 안 함.

## 3. 봉합안 (구현은 결재 후)

### M2 봉합 — db.conf를 격리 경로로
1. `$DbConfPath` 기본값을 **`C:\HitPanTest\db.conf`**(격리 루트 하위)로 변경. 운영 경로(`C:\Program Files\HitPan\`)에 **절대 쓰지 않음**.
2. 만약 운영 경로에 쓰는 옵션이 필요하면, **운영 db.conf 존재 시 abort**(덮어쓰기 물리 차단).
3. Run-CommsScenarios.ps1 등 소비처가 db.conf를 어디서 읽는지 grep 후 격리 경로 정합 확인(헌법 #12 — 모든 소비처 확인).

### M3 봉합 — 가드를 "DB 존재"로 강화
1. `Test-DemoServiceRunning`에 **DB 레벨 가드 추가**: 대상 인스턴스(3306)에 **`hitpan_erp`(운영 DB)가 존재하면** "이 인스턴스는 운영과 공유 = 테스트 슬롯 생성 abort".
2. 즉 "같은 인스턴스에 운영 DB 있으면 hitpan_e2e 만들지 않음" — WARN이 아니라 **ABORT**.
3. (권장) 테스트 슬롯은 **별도 인스턴스/포트**를 요구하도록 안내 메시지(→ M4로 연결).

### 봉합 후 불변식 (검증 기준)
- slot 빌더 실행 시: 운영 db.conf **미터치** + 운영 DB(hitpan_erp) 있는 인스턴스면 **abort**.
- 즉 "오늘 같은 사고가 코드 레벨에서 물리적으로 불가능"해짐.
