## 1. 문제 정의 (어제 "자동 업데이트 실패"의 정체)

어제 자동 업데이트는 **실패한 게 아니라 끝까지 돌 수 있는 물건이 아니었다.** 4단계 중 마지막이 빈 자리다:

| 단계 | 코드 | 실측 |
|---|---|---|
| ① 새 버전 감지 (manifest, 하루 1회, 채널 3분기) | 있음 | 미실측 |
| ② 다운로드 + sha256 검증 | 있음 | 미실측 |
| ③ 적용 전 자동 백업 (mysqldump, 실패 시 물리 차단) | 있음 | 미실측 |
| ④ **실제 EXE·파일 교체 → 서비스 재시작 → 실패 시 롤백** | ❌ **미구현** | — |

④ = `src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs` **102~107행** 자리표시 — *"고리4 미구현 — 백업까지만 수행하고 적용 보류"*. `VelopackUpdaterStub`은 no-op이고 **DI 등록도 호출도 0건**, csproj에 **Velopack PackageReference 자체가 없다**.

**즉 지금 고객 PC는 새 버전을 받아놓고 적용을 못 한다.** 갱신 경로가 사실상 없으니 재설치밖에 남지 않았고, 그게 어젯밤 사고의 뿌리였다. **이것을 채우는 것이 본 작업의 전부다.**

## 2. 실측으로 드러난 것 (설계 근거 — 전부 코드 확인, 2026-07-16)

회의(하브루타·레드팀·법무·현장)가 지적한 3건이 **전부 사실로 확인**됐고, 조사 중 **더 나쁜 것 3건**이 추가로 나왔다.

### 2.1 회의 지적 — 확인됨

1. **keepalive가 교체를 방해한다** — `HitPan-ERP-{API|WEB}-keepalive-{slot}` 예약작업이 **1분마다**(`/SC MINUTE /MO 1`, SYSTEM) 생사 검사 없이 무조건 `schtasks /Run`. 파일 교체하려고 프로세스를 죽이면 **1분 안에 부활해 파일을 잠근다**. (`installer/HitPan-Universal.iss:1722-1726`)
   - `.iss:1719-1721` 주석은 keepalive가 "무해"하다고 적었다. 그 근거("살아있으면 no-op")는 **프로세스가 살아있을 때만** 참이다. 교체 시나리오에서 전제가 깨진다.
2. **`/local-update` 라우트가 없다** — `installer/web-server.ps1`(HttpListener, 5234) 라우트는 정확히 3개: ① canonical 301 ② `/api/*` → `localhost:{apiPort}` 프록시 ③ 그 외 = 정적파일, 없으면 SPA 폴백. **없는 경로는 404가 아니라 200 + index.html**(폴백 분기 `:152-163`, `:156-159` StatusCode 미지정 = 기본값 200). → "200 왔으니 성공"으로 판정하면 **영구 오진**.
3. **적용 엔진이 빈 껍데기** — Velopack PackageReference 0건, stub은 no-op·미배선.

8. **`/health` 판정 경로는 설정 1줄·배포 형태에 좌우된다 — 단일 실패점** (CTO 처방 2의 근거) — `HealthIpWhitelistMiddleware`(`Program.cs:367`, 인증 미들웨어보다 **앞**)가 루프백만 허용하고(`:40-42`) 워치독은 로컬이라 통과한다. **그러나 이 판정은 다음 3가지에 묶여 있다**:
   - **설정 1줄로 열린다** — `HealthCheck:AllowedIps`(`HealthIpWhitelistMiddleware.cs:43-50`). 운영 편의로 IP를 추가하면 W4-5 판정이 외부 응답에 좌우된다.
   - **`UseForwardedHeaders` 배선 0건** — 프록시 경유 시 `RemoteIpAddress`가 프록시 IP(127.0.0.1)가 된다. 지금은 `web-server.ps1:89`가 `/api/*`만 프록시해 `/health`가 안 새지만, **터널 ingress가 5257 직결인 배포가 실재한다**(`build-installer-universal.ps1:125-126` — *"ingress origin=http://localhost:5257(API) 직결… /health 200=API전용"*). **그 경로에선 화이트리스트가 프록시 IP를 보고 통과시킨다.**
   - **주석이 실제 동작과 정반대** — `HealthController.cs:8-13`은 *"익명 접근(공개). Grafana/Uptime Robot/AWS ELB 헬스 프로빙용"*이라 선언한다. 코드를 읽는 사람을 오도한다.

   → **주석 정정(W4-0)만으론 부족하다.** 판정은 **EXE FileVersion 2중 판정**(CTO 처방 2)으로 구제한다. `/health` 단독 의존 금지.
   ※ v3 작성 시 PM이 *"CTO가 주석에 속아 오판했다"*고 서술했으나 **사실이 아니다** — CTO는 화이트리스트 존재를 읽고 인용한 뒤 그것을 단일 실패점으로 지적했다. PM이 하지 않은 주장을 반박한 것. 이 문장이 남으면 다음 세션이 "health 노출은 검토 끝"으로 오독한다 — **검토는 끝나지 않았다.**

### 서명 · manifest 위조 차단 — **W4-2의 blocker** (동시 착수)

- manifest에 `signature`·`kid` **2필드 추가**(9→11, 추가만) — `AutoUpdate/UpdateChannel.cs:21-32`
- **서명 대상 = manifest 본문 정규화 JSON 전체**(sha256 필드 포함) → 자기참조 고리를 끊는다. sha256 = zip 무결성 / 서명 = manifest 진위, **2층**.
- 검증 위치 = `UpdateClient.GetLatestManifestAsync`. **실패 = manifest null 반환**(다운로드 진입 금지).
- 워치독엔 `HitPan.API` 참조가 없으므로 `SerialProofVerifier`의 **ECDSA 부분만 이식**(~40줄, `System.Security.Cryptography` = BCL). **HMAC 2-part 경로는 가져오지 않는다** — manifest는 신규 스키마라 하위호환 부채가 0이다(여기서만은 대칭키 금지가 공짜).
- **워치독 kid는 시리얼과 분리**(`upd-v1`) — 시리얼 개인키 유출이 코드 실행으로 번지면 안 된다(권한 분리).
- 개인키 = NCP `/var/hitpan/serial-keys/`(600 root)와 동일 정책. **채팅·문서 노출 절대 금지**(헌법 #23·#29).
- **키 생성·NCP 배치 = 헌법 #29 사전 승인 대상** (CTO 처방 8) — kid 분리는 **새 키쌍을 세우는 것**이다. "키 인프라 완성형"이 아니다. §8 작업 순서에 결재 단계 명시.

#### 🔴 서명 수행 위치 = NCP 전용. CI 서명 금지 (CTO 최종 처방 1 / C-1 — 착수 차단 사유였음)

v4 초안은 §9에 *"manifest 생성 파이프라인(`.github/workflows/`)"*, §4에 *"개인키는 NCP 600 root"*라 썼다. **두 문장은 양립 불가능하다** — CI가 manifest를 만들고 서명까지 하려면 개인키가 GitHub Secrets에 있어야 한다.

**왜 금지인가**: 전 고객 SYSTEM 코드 실행 권한을 **본사가 통제 못 하는 제3자(GitHub)**에 두는 것 = 헌법 #22·#29 위반. 2026-07-07 시리얼 개인키를 NCP 600 root에 가두고 채팅에도 안 올린 결정과 **정면 모순**이다.
> **위력 비교 (CTO)**: 시리얼 키 유출 = 가짜 라이선스. **업데이트 키 유출 = 전 고객 PC 임의 코드 실행.** 더 센 키를 더 약한 곳에 두는 셈.

**분리 설계 (1차 확정)**:
```
CI (GitHub Actions)   : zip 빌드 + sha256 + manifest 본문 생성 (서명 없음) → 아티팩트
                          ↓ (사람이 받아 NCP로 반입)
NCP (600 root, 오프라인) : manifest 본문 → 개인키 서명 → signature·kid 추가 → 배포
```
- **개인키는 NCP를 떠나지 않는다. GitHub Secrets 반입 0건.**
- **서명 = 릴리스 1건당 사장님 결재 1회** — 부담이 아니라 **기능**이다. 전 고객 코드 실행 트리거에 사람 결재가 붙는다(헌법 #29 정신).
- 자동화(NCP 서명 전용 엔드포인트 + mTLS + 감사로그)는 정공법이나 **1차 범위 밖**. 베타는 릴리스 빈도가 낮아 수동 서명으로 충분.
- **`HITPAN_UPDATE_FEED`는 Production에서 무시**(개발 전용).
- **서명이 막는 것과 못 막는 것 (CTO B-4 검증 결과 — 반은 v3가 맞았다)**:
  - ✅ **다운그레이드는 막힌다** — 서명이 manifest 본문(sha256 포함) 전체를 덮으므로 "1.2.34인 척하는 옛 zip"은 version·sha256 동시 위조가 필요 = 개인키 없이 불가. + W4-0 SemVer 비교 = **이중 방어**.
  - ❌ **서명된 옛 manifest 통째 재생(replay)은 안 막힌다** — 1.2.34 서명 manifest를 보관했다 1.2.35 배포 후 다시 물리면 서명·sha256 전부 유효. 유일한 방어가 SemVer 비교인데 **이건 워치독 자기 버전이 정확할 때만 작동** → **W4-0 ⓑ가 빠지면 워치독은 영원히 1.0.0 → 모든 서명 manifest가 "새 버전" → replay 방어 0.** W4-0과 서명은 곱해진다.
  - ❌ **정지 공격**(manifest를 아예 안 주기) — 하루 1회 조회(`Worker.cs:264-266`)라 **feed를 조용히 끊으면 고객은 영원히 옛 버전에 고정되고 아무도 모른다.** Emergency 채널(보안 패치)이 이 경로로 무력화. → **W4-6에 "N일 연속 조회 실패 = 메타 ping 통지" 추가 (CTO 처방 7), §7에 G-S2 신설.**

### W4-1 · 교체 대상 정지 (keepalive 부활 차단) — **신규 설계** (CTO 처방 3)

> v3는 이 순서를 "`.iss:1171-1175` 재사용"이라 썼으나 **허위였다**(§2.3 삭제 항목 참조). 실제 `.iss` 코드는 순서가 반대이고 `/End`를 쓴다. **아래는 신규 설계다.**

정지 순서:
```
0. HitPan-ERP-keepalive-restore ONSTART 작업 등록
   → schtasks /Query 로 존재 확인
   → 확인 실패 시 업데이트 전체 중단 (스왑 진입 금지)     ★ 바닥 없이 떨어지지 않는다
1. keepalive API  /Change /DISABLE   ← /End 아님. /End는 인스턴스만 죽이고 트리거는 살아 1분 뒤 또 돈다
2. keepalive WEB  /Change /DISABLE
3. tenant API  /End
4. tenant WEB  /End
5. taskkill /F /IM HitPan.API.exe   (End 불응 대비)
6. 잔존 프로세스 확인 폴링(최대 10초)
```

**cloudflared·MariaDB 불가침** — 교체 대상 아님. 터널 유지 = CS 접근 경로 유지, DB 유지 = 롤백 자산 보존.

**"keepalive가 영영 disabled로 남는" 위험 = 이 설계의 최대 급소.** 워치독이 스왑 중 죽으면 **업데이트가 ERP를 영구 정지시킨다.** v3는 3중이라 썼으나 **CTO 검증 결과 실질 1~2중이었다.** 보강한 3중:

| 층 | 보장 | v3의 구멍 → v4 보강 |
|---|---|---|
| ① | `try/finally` 무조건 `/ENABLE` | (유지) 정상·예외·롤백 경로. 강제종료·정전은 못 막음 |
| ② | `HitPan-ERP-keepalive-restore` ONSTART 작업을 **`/DISABLE` 전에 등록** → **재부팅 1회로 100% 복구** | 🔴 **v3는 등록 반환코드를 검사하지 않았다** — 등록이 실패해도 그대로 `/DISABLE`로 진행 = **바닥 없는 걸 모른 채 떨어짐.** → **`schtasks /Query` 성공 확인 전엔 `/DISABLE` 금지** (위 0단계) |
| ③ | 워치독 기동 시 자가 점검 — keepalive가 disabled면 `/ENABLE` | 🔴 **v3는 "업데이트 진행 표식"의 저장 위치를 안 적었다.** DB에 두면 **워치독이 스왑 중 죽었을 때 표식이 남아** 자가점검이 "업데이트 중이구나" 하고 **영원히 `/ENABLE`을 안 한다** → ①죽음 + ③무력화 = **②만 남는 1중.** → **표식 = TTL 15분 파일**(DB 아님 — DB는 워치독이 죽으면 못 지운다). 자가점검은 **표식이 있어도 TTL 만료면 무조건 `/ENABLE`** |

②가 바닥, ③이 실질 복구 경로(`sc failure` 5초·Guardian 5분이 워치독을 되살리므로 **재부팅 없이 최대 5분**), ①이 정상 경로. **셋 중 하나만 살아도 ERP는 돌아온다** — 이제 진짜로.

**③ 표식 파일 상세 (CTO 재심사 Q2 답변 — 착수 전 확정)**

- **경로 = `{app}\update.lock`.** **`%LOCALAPPDATA%` 금지** — 워치독은 SYSTEM이라 `C:\Windows\System32\config\systemprofile\...`로 숨어 **사람이 못 본다.** `{app}` 루트를 쓰는 이유 3가지: ① 사람이 보는 곳(CS가 "이 파일 지우세요" 안내 가능) ② db.conf 등이 이미 있어 **ACL·백신 예외가 설정된 경로**(헌법 #31) ③ 진단 시 한곳에서 보인다.
- **TTL 판정은 mtime이 아니라 파일 내용의 UTC 타임스탬프로.** 시계 변경은 **공격이 아니라 사고로 깨진다** — 공격자가 시계를 바꿀 수 있으면 이미 SYSTEM이라 논할 실익이 없다. 진짜 위험은 **정상 시나리오**: NTP 동기화·수동 시간 변경으로 mtime이 미래가 되면 **TTL이 영원히 만료 안 됨 → ③ 무력화.**
- **fail-safe 판정**: `now - written > 15분`(만료) **또는** `now < written`(미래 표식 = 말이 안 됨 = 손상) → **둘 다 즉시 `/ENABLE`.** 원칙 = *"만료됐거나, 말이 안 되면 푼다."* 판정 실패 시 기본값은 항상 ENABLE.
- **별건 백로그**: `_stagingDir`(`UpdateOrchestrator.cs:28-30`)도 `%LOCALAPPDATA%`를 쓴다 → SYSTEM 프로파일로 숨는다. 본건 범위 밖이나 §11 기록.

### W4-2 · 파일 교체 (best-effort 스왑 + 즉시 복원)

**"원자적" 표현 폐기** — Windows 폴더 리네임은 핸들 하나만 열려 있어도 실패한다. 정직한 이름 = **best-effort 스왑 + 실패 즉시 복원**.

```
staging\hitpan-{V}.zip → 해제 → staging\extract\{api,web,watchdog}
web 먼저 → api 나중            ★ v3는 api 먼저였다. CTO 처방 5로 교정 (아래 근거)
  {app}\web → {app}\web.old      (리네임)
  extract\web → {app}\web        (리네임)
  → 이어서 api 동일
실패 시 즉시 역리네임. 부분 성공도 전부 되돌림.
```

**스왑 순서를 web → api로 뒤집은 근거 (CTO 처방 5 / B-5)**: v3는 *"api 먼저 → 헬스 확인 → web"* 이었다. 그러면 api가 신버전으로 뜬 뒤 web 스왑이 실패할 때, **신버전 api가 처리한 거래를 구버전 api가 이어받는 창**(수초~수십초)이 생긴다. 1차는 마이그 없음(B안)이라 스키마가 같아 대부분 무해하나 — **그 전제가 사람 손에 달려 있다**(아래 B안 게이트). **web을 먼저 스왑하면 web 실패 시 api는 아직 기동 전 = 그 창이 아예 없다.**

> ⚠️ **스왑 구간 전체가 W4-1 정지 상태 안이다** (CTO Q1 — 오독 방지). 이 구간에는 api·web 어느 것도 실행 중이 아니다(keepalive DISABLE + tenant End + taskkill 완료). *"web 스왑 중 web이 살아있나?"* 로 읽으면 안 된다. **스왑 순서(web→api)와 기동 순서(api→web)가 다른 건 의도된 비대칭**이다 — 스왑은 "실패 시 노출창 최소화", 기동은 "API가 서야 ERP가 산다"로 **기준이 다르다.** G-4가 검증한다.

- **설정파일은 `{app}` 루트에 있어 api/web 스왑 대상 밖**(구조적으로 안전 — 실측 확인). 그래도 `db.conf`·`hitpan-keys.conf`·`bootstrap.conf` 사본을 스왑 전 `pre-update-backup`에 남긴다(비용 0, 헌법 #20).
- **열린 핸들 진단**(헌법 #15 침묵 금지): `IOException` HRESULT(32=공유위반 / 5=액세스거부) 구분 + `tasklist` 잔존(HitPan.API.exe·powershell.exe) + keepalive 작업 상태를 함께 기록. 이 둘이면 실무상 원인의 99%(= keepalive 부활)가 특정된다. (`handle.exe`는 미설치 전제라 불가)

**B안 게이트 — 사람 손에서 뗀다 (CTO 처방 4 / B-2)**

v3는 *"`RequiresMigration=true`면 정지"*라 썼으나, **그 플래그는 write-only 필드이고 검사 코드가 0건**이며 **manifest 생성 파이프라인 자체가 없어 손으로 써왔다**(§2.2 #7). 즉 "1차는 DB 안 바꾸는 것만"이라는 안전장치가 **코드가 아니라 사람의 약속**이었다. 릴리스 담당자가 `false`를 한 번 오타하면 → 신버전 api가 구 스키마에서 500 → 롤백 → **DB는 이미 신버전이 건드린 상태인데 DB 자동복원은 안 함(결재 #3)** → 구버전 + 오염 DB = **되돌려도 안 살아난다.** 헌법 #19(*"어 어젠 됐는데"가 있어선 안 됨*) 정면 위반.

2중 방어:
1. **릴리스 파이프라인이 자동 산출** — zip 안의 `Migrations/SQL/*.sql` 목록을 스캔해 `requiresMigration`을 **기계가 결정**. 손입력 금지.
2. **워치독이 교차검증** — zip 해제 후 `Migrations/SQL`에 신규 파일이 있으면 **`RequiresMigration=false`여도 강제 중단**. 사람 실수를 코드가 잡는다.

게이트 위치: 다운로드·백업 **후** / W4-1 **전**. 중단 시 `local_update_status`에 "CS 필요" 기록. 백업까지 하는 이유 = 고리5(마이그 지원)가 그 백업을 그대로 쓴다.

**워치독↔릴리스 호환성 — 문서가 아니라 코드로 (CTO 처방 6 → 최종 처방 2 / C-2)**

W4-3 제외로 **구버전 워치독 + 신버전 api/web** 조합이 정상 상태가 된다. 워치독은 `local_update_status`·`local_update_consents`를 직접 SQL로 읽고 쓰므로, 릴리스가 그 스키마를 바꾸면 **구버전 워치독이 깨진다 = 업데이트 주체가 죽는다 = 그 PC는 영구 고립**(재설치 외 복구 불가 = 사장님이 없앤 그 경로).

> ⚠️ **v4 초안의 자기모순 (CTO 적발)**: 초안은 *"계약: 1차 릴리스는 `local_update_*` 스키마 불변"* 문장 하나 + G-5 수동 게이트로 끝냈다. **바로 위 B안 게이트에서 "사람의 약속을 코드로 옮긴다"고 진단해놓고, 같은 문서에서 같은 실수를 반복한 것.** 6개월 뒤 `local_update_status`에 컬럼을 추가하는 사람은 **이 문서를 안 읽는다.** G-5는 릴리스 시점 수동 게이트라 그때 작동하지 않는다.

**코드 게이트**: 위 B안 스캐너가 `Migrations/SQL/*.sql`을 훑을 때 **`local_update_` 문자열이 걸리면 빌드 실패.** 어차피 만들 스캐너에 **grep 한 줄 추가 = 추가 공수 0.** 사람의 약속이 코드가 된다. G-5는 그대로 유지(2중).

### W4-4 · 재시작

`WS28I_FourProcess.TryRestartTask`(:92) **그대로 재사용**(신규 코드 0).

순서: API 기동 → 헬스 확인 → Web 기동 → **keepalive `/ENABLE` 복원** → ② ONSTART 복원작업 삭제.
복원은 헬스 검증 통과 후가 아니라 **기동 직후** — 롤백에 들어가도 keepalive는 살아 있어야 구버전을 지킨다.
(스왑은 web→api 순, 기동은 api→web 순. 스왑은 "실패 시 노출창 최소화", 기동은 "API가 서야 ERP가 산다"로 기준이 다르다.)

### W4-5 · 검증 게이트 + 롤백

**`schtasks /Run` 반환코드는 검증이 아니다** — "작업을 시작했다"는 뜻이지 "ERP가 산다"가 아니다(비동기). → 헬스폴링.

- API `/health` **2초 간격 × 최대 60초**. 판정 = **HTTP 200 + 응답 본문의 버전이 신 버전**. **200만으론 불통과** — 구버전이 살아 있어도 200이다.
  - ⚠️ **W4-0 ⓐ 없이는 이 게이트가 100% 실패한다** — `HealthController.cs:44`가 `"1.0.0-beta"` 리터럴이라 정상 업데이트도 "신 버전 아님"으로 읽힌다(CTO B-1).
  - **판정 2중화 (CTO 처방 2)**: `/health` 본문 버전 **+ 교체된 EXE의 FileVersion 직접 확인**. `/health` 단독은 미들웨어 설정 하나(`HealthIpWhitelistMiddleware`, 루프백 전용)에 판정이 묶인다.
- **Web(5234)은 200으로 판정 금지** — 없는 경로도 200+index.html이라(`web-server.ps1:152-163`) **항상 성공으로 오진**한다. Content-Type + 실제 바이트로만 보고, **진짜 판정은 API에 맡긴다**(API가 죽으면 ERP는 못 쓴다).

롤백 순서:
```
1. W4-1 재실행 (keepalive DISABLE 먼저)
2. 파일 복원  api.old → api,  web.old → web
3. keepalive ENABLE + schtasks /Run
4. 헬스폴링(구버전) 통과 = 롤백 성공
5. 롤백까지 실패 = 메타 ping 긴급 통지 + local_update_status 기록 (헌법 #30 — 본사는 통지만)
```

**DB 자동 복원은 하지 않는다 (사장님 결재 #3)** — 1차는 마이그 없는 릴리스만(B안)이라 스키마가 안 바뀐다. DB를 되돌리면 **업데이트 시도 중 들어온 정상 거래를 지운다.** 백업은 **보험으로 존재만** 한다. 자동 DB 복원은 고리5에서 마이그와 함께 설계.

### W4-6 · 상태 기록·멱등

- `local_update_status`에 `applied_version`·`applied_at`·`result` 기록(`WatchdogStatusWriter` 확장). **멱등 키 = 버전.**
- **인메모리 펜딩 소실 버그 동시 해결** — `_pendingConsentUpdate`가 인메모리 필드(`Worker.cs:40`)라 워치독 재시작 시 펜딩이 날아가고, 하루1회 게이트(`Worker.cs:264-266`) 때문에 **다음날까지 동의 폴링이 죽는다**. 펜딩을 `local_update_status`에서 복원. 같은 테이블·같은 라이터를 건드리므로 **여기 끼우는 게 맞다**(분리하면 두 번 손댄다).
- **정지 공격 게이트 (CTO 처방 7 / B-4)** — **manifest 조회 N일 연속 실패 = 메타 ping 통지**(±10줄). 지금은 feed를 조용히 끊으면 **고객이 영원히 옛 버전에 고정되고 아무도 모른다** — Emergency 채널(보안 패치)이 그 경로로 무력화된다. 본사는 **통지만** 받는다(헌법 #30, 업무 데이터 0건).
- **mysqldump PATH 탐색 봉합** — `WatchdogStatusWriter.cs:149`·`WatchdogConsentReader.cs:155`가 `where`로 PATH를 **먼저** 뒤진다 → PATH 심기로 SYSTEM 실행 가능. 고정 경로(`C:\Program Files\MariaDB 11.4\bin`) 우선 → PATH 폴백으로 **순서 뒤집기**. 같은 파일을 건드리는 김에.
- 성공 시 staging·`.old`·`watchdog.new`·② ONSTART 복원작업·③ TTL 표식 정리.

## 5. 후속으로 빼는 것 (사장님 결재 완료)

### W4-3 · 워치독 자기 교체 — 제외

감시자 2중(Guardian 5분 + `sc failure` 5초)을 **동시에 무력화**해야 하는데, 그 창에서 워치독이 죽으면 **되살릴 주체가 없다**(`sc failure reset`은 서비스 설정 변경이라 프로세스가 죽어도 남는다 = 영구 무방비). keepalive 문제는 ERP가 죽는 것이지만 이건 **자가복구 인프라 자체가 죽는 것**이다 — CS 원격도 못 들어간다. 그리고 **없어도 1차 목표가 달성된다**(고객이 체감하는 건 api/web, 워치독은 변경 빈도가 낮다).

1차 처리: zip의 `watchdog/`을 `{app}\watchdog.new`에 풀어두고 **스왑하지 않는다**. 워치독 버전이 바뀐 릴리스면 `local_update_status` 기록 + 메타 ping 통지 → 본사 인지. **고리5 별건.**

### W4-7 · 로그인 전 "버전 업데이트하기" 버튼 — 고리4 실증 후로

사장님 제안이었으나, 아래 근거로 **연기 결재**(2026-07-16):

1. **고리4 없으면 버튼은 거짓말** — 지금 누르면 백업만 하고 아무 일도 안 일어나는데 `ApplyUpdateAsync`는 `true`를 반환한다. "업데이트했습니다"가 뜨는데 버전은 그대로 = **표시광고법 §3 거짓 표시를 우리 손으로 만든다.** CS를 줄이려던 버튼이 CS를 만든다.
2. **버튼의 목적이 고리4로 이미 달성된다** — 사장님 목적은 "재설치하세요 대신 이 버튼 누르세요". 고리4가 서면 워치독이 **알아서** 갱신한다 = 고객 손 **0번**. 버튼은 고객 손 1번이라 오히려 후퇴. 버튼이 진짜 필요한 건 "야간창을 못 기다리는 급한 CS"뿐인데 그건 **Emergency 채널이 이미 담당**한다.
3. **서명이 선행** — 인증 0의 트리거 = SYSTEM 코드 실행 표면.

**후속 승인 시 이 형태로** (회의 4진영 제약 전부 반영):

- **경로**: 브라우저 → **web-server.ps1 신규 `/local-update` 라우트**(같은 출처) → `local_update_requests` INSERT → 워치독 폴링. **워치독은 포트를 열지 않는다**(SYSTEM 미인증 로컬 포트 = 권한상승 표면). `local_update_consents`(DB-82)와 **동일한 검증된 중간자 패턴 재사용**. 엔진은 고리4와 공유(중복 구현 금지).
- 라우트는 **정적 서빙보다 앞**에 — 뒤에 두면 SPA 폴백이 200+index.html로 먹는다.
- **2단계 옵트인**(정보통신망법 §50조의5) — 클릭=즉시실행 금지. ① 버튼 → ② 설명 화면 + "동의하고 시작" 별도 클릭.
- **클릭 전 고지**: "작성 중인 화면이 있으면 저장해 주세요 / 3~5분 접속 불가 / **다른 직원과 함께 쓰는 PC면 미리 알려주세요**" (ERP매니저 지적 = 동시 사용. 재시작이 동료의 작성 중 전표를 날린다)
- **"자료 유지" 문구는 롤백이 Sandbox에서 실증되기 전까지 금지**(표시광고법 §3 — 사실주장). 실증 후 "기존 자료는 그대로 있습니다"로 해제.
- 금지어: **자동·완벽·100%·무중단**. 포괄 면책 금지(약관규제법 §7). 약관·SLA 개정 필요.
- **진행 표시 필수** — 멈춘 듯 보이면 강제종료 → 데이터 사고.
- 실패 화면 = **한국어 안심 문구 우선**, 에러코드·영어 금지.
- 화면 노출은 **버전번호만** — 테넌트코드·시리얼·서버주소 금지(헌법 [[feedback_tenant_code_internal_only]]).
- **`ConsentMessage` 화면 표시 금지**(저장형 XSS) — 표시하려면 텍스트 노드로만.
- 미인증이라 **rate limit 필수**(예: 10분 1회).
- 화면 문구는 **CS 스크립트와 정확히 일치**(강지원 팀장 지적).

## 6. 안전 원칙 (절대)

- **덮어 재설치 아님** — 워치독이 파일만 교체(고객 손 0번, [[feedback_no_overwrite_reinstall]]). 고객 EXE 재실행 0.

- **동의 채널 정합** — Major는 로그인 Y/N 동의 후에만. Normal은 야간창. Emergency는 안내 후.

## 10. 리스크 (사장님 보고용)

- **W4-0이 이 작업의 생사** — v3는 이걸 "버전 붙이기"로 얕봤다가 blocking을 만들었다. **`HealthController.cs:44` 하나 빠지면 고리4는 단 한 번도 성공하지 못한다**(정상 업데이트를 실패로 오판 → 무한 롤백). 그리고 **본사가 지금 보는 고객사 버전은 전부 가짜다**(인스톨러 1.2.13 ↔ 메타핑 1.0.0) — 업데이트 성공률 집계 자체가 불가능한 상태.
- **W4-1 3중 보장이 생명선** — 뚫리면 "업데이트가 고객 ERP를 영구 정지"시킨다. **재설치를 없애려다 재설치를 강제하는 최악.** v3는 3중이라 썼으나 실은 1~2중이었다(② 등록 미검증 · ③ 표식 위치 미정). G-1이 형식적 통과로 끝나면 안 된다.
- **B안이 코드가 아니라 사람의 약속이었다** — `RequiresMigration` 검사 코드 0건, manifest는 손으로 씀. 담당자 오타 한 번 = 롤백해도 안 살아남(DB 자동복원 안 함 결재). **자동 산출 + 교차검증 2중으로 사람 손에서 뗀다.**
- **서명 개인키 = 코드 실행 권한** — 유출 시 전 고객 SYSTEM 코드 실행. 시리얼 키와 kid 분리는 최소 방어. 베타는 서버격리+ACL / 정식은 HSM·KMS(헌법 #23·#29). **키 생성·배치는 헌법 #29 사전 결재 대상**(§8 순서 0단계).
- **정지 공격은 서명으로 못 막는다** — feed를 조용히 끊으면 고객이 옛 버전에 영구 고정되고 아무도 모른다. 보안 패치 경로가 죽는다. → 통지 게이트 필수.
- **schtasks 기동은 서비스보다 검증이 까다롭다**(비동기) → W4-5 헬스폴링에 충분한 대기·재시도.
- **Web 5234 슬롯 무관 하드코딩** — 한 PC 멀티슬롯 시 두 Web이 같은 포트를 다툰다(`web-server.ps1:4`). **본건 범위 밖**이나 별도 백로그.
- 테스트는 **Windows Sandbox(휘발성)** 에서만 — demo 운영 불가침(헌법 #39).
