## 0. 한 줄 요약

업데이트가 **새 EXE 적용 + DB 스키마 마이그(ALTER)** 를 동반할 때, 마이그가 실패하면 지금 구조는 **DB만 되돌리고 EXE는 새 버전인 채** 남아 스키마 미스매치로 ERP가 안 뜬다(반쪽 롤백 = 더 위험). 본 설계는 **DB와 EXE를 한 단위로 묶어, 실패 시 둘 다 직전 버전으로 동시 복원하고 구버전으로 재기동**하는 상태머신을 정의한다.

## 1. 현황 파악 (코드 실측)

### 1-1. BackupService.RestoreAsync — DB만 복원, EXE 롤백 0건
`src/HitPan.Application/Services/BackupService.cs`
- `RunBackupAsync` : `mysqldump --single-transaction` 로 `.sql` 한 파일 생성 → 1차/2차(미러) 폴더 저장. **DB 덤프만**. EXE·바이너리·설정파일 백업 0건.
- `RestoreAsync` :
  1. 복원 대상 `.sql` 결정(이력 backup_id 또는 외부경로)
  2. 회사명 일치 확인(오복원 방지)
  3. restore_history INSERT('running')
  4. **안전망 — 복원 직전 자동 `pre_restore_*.sql` 덤프** (이게 핵심 자산: "복원하다 실패하면 직전 상태로 되돌릴 덤프"가 이미 존재)
  5. `mysql.exe < sourceFile` 임포트
  6. 성공/실패 이력 UPDATE
- **결론: RestoreAsync 는 DB 한 축만 안다. EXE/버전 개념이 코드에 전혀 없다.** 마이그 실패 후 EXE를 되돌릴 주체가 시스템 어디에도 없음.
- §#3 정합 확인: backup_history/restore_history 는 INSERT/UPDATE만, DELETE 없음(주석 명시). 보관정책 `ApplyRetention` 은 `.sql 파일`을 지우지 별 **DB 행을 지우지 않음**.

### 1-2. VelopackUpdaterStub — 순수 stub (no-op)
`src/HitPan.Watchdog/AutoUpdate/VelopackUpdaterStub.cs`
- `CheckForUpdatesAsync` : 환경변수 `HITPAN_AUTO_UPDATE_ENABLED != "true"` 면 즉시 false. true 라도 "would check" 로그만 찍고 false 반환. **실제 Velopack 호출 0건.**
- `IntegrationPseudoCode()` 에 정식 통합 의사코드만 문자열로 보관: `VelopackApp.Build().Run()` → `UpdateManager` → `CheckForUpdatesAsync` → `DownloadUpdatesAsync` → `ApplyUpdatesAndRestart`.
- **Velopack NuGet 패키지 미참조. 이전버전 보관정책 미정.**

### 1-3. RequiresMigration 플래그 — 정의만 있고 소비처 0건
- 정의: `src/HitPan.Watchdog/AutoUpdate/UpdateChannel.cs` `UpdateManifest.RequiresMigration (bool)` + `ConsentMessage`. 주석: "Major 채널 전용 — DB 스키마 변경 여부".
- 소비처 grep 결과: **읽는 코드 0건.** `UpdateOrchestrator.EvaluateAsync` 는 `manifest.Channel` 만 분기(Emergency/Normal/Major)하고 `RequiresMigration` 은 보지 않음.
- `UpdateOrchestrator` 자체도 `Worker.cs` 가 호출하지 않음(DI 와이어링 없음). 워치독 정기 루프는 통신 복구(WS-28-A~I)만 돌고 자동 업데이트는 아직 결선 안 됨.
- **즉, 업데이트 파이프라인 전체가 "설계만 있고 미가동" 상태.** 고리4는 이 미가동 파이프라인 위에 롤백을 얹는 작업.

### 1-4. DB 마이그레이션 적용 경로 — 업데이트 시 ALTER 를 실행하는 자동 주체가 **없다**
- `src/HitPan.API/Migrations/SQL/DB-*.sql` (81개+) = ALTER 이력 모음. **API 시작 시 자동 적용 안 함** (Program.cs 에 마이그 러너·EnsureCreated·.sql 실행 0건 — grep 무매치).
- `installer/install.bat` : 신규설치만 — `hitpan_db.sql`(clean DDL) 한 번 import. 기존 운영 데이터 있으면 import 건너뜀(데이터 보호). **install.bat 에 DB-*.sql ALTER 루프 없음** (헌법 #36: install.bat 에 migrations 루프 금지).
- `installer/migrations/20260619_ai_chatbot_byok_memory.sql` 1개 존재하나 적용 루프 없음.
- `MigrationController` 는 **레거시 MDB(Access) → ERP 데이터 이관**이지 스키마 ALTER 가 아님. (용어 충돌 주의: "마이그레이션"이 두 의미)
- **결정적 사실: 업데이트가 DB 스키마를 바꾸려면 ALTER 를 실행할 주체를 고리4에서 새로 만들어야 한다.** 현재는 사람이 손으로 DB-*.sql 을 돌리는 구조 → 헌법 #39(운영 손수술) 위반 위험의 근원. 고리4 = 이 손수술을 검증된 자동 트랜잭션으로 대체.
- **스키마 버전 추적 테이블 없음** (schema_version/migration_history 류 grep 무매치). 어떤 ALTER 가 적용됐는지 DB가 모름 → 롤백 판단의 기준점이 없음. **고리4의 선결 과제.**

## 2. Velopack 롤백 능력 — 가정 + 검증 필요 항목

> 코드에 stub뿐이라 아래는 Velopack 공식 동작에 대한 **설계 가정**이다. 별표(⚠️검증)는 PoC 로 실측 확인해야 머지 가능.

### 2-1. 가정 (Velopack 공식 동작으로 알려진 것)
- **A1. 이전 버전 로컬 보관**: Velopack 은 앱을 `%LocalAppData%\<AppId>\` 아래 `app-<version>\` 폴더로 버전별 설치하고 `current` 가 활성 버전을 가리키는 구조. `ApplyUpdatesAndRestart` 는 새 `app-<new>\` 로 전환 후 재기동. **이전 `app-<old>\` 폴더는 즉시 삭제되지 않고 일정 기간 남음** → 롤백의 물리적 토대.
- **A2. 적용은 재시작 시점에 일어남**: `DownloadUpdatesAsync` 는 패키지를 staging 에 받기만 하고, `ApplyUpdatesAndRestart`(또는 `WaitExitThenApplyUpdates`) 가 실제 파일 교체 + 재기동을 수행. 즉 **"다운로드 완료 ≠ 적용"** — 적용 직전까지는 구버전이 그대로 살아있음.

### 2-2. ⚠️검증 필요 (불확실 — PoC 없이 머지 금지)
- **V1. 자동 롤백 API 존재 여부**: `ApplyUpdatesAndRestart` 가 "적용 후 새 버전이 부팅 실패하면 자동으로 이전 버전으로 되돌리는" 내장 API가 있는가? → **확실치 않음.** Velopack 의 자동 롤백은 주로 "새 버전 EXE 실행 자체가 깨졌을 때"를 다루며, **"EXE는 멀쩡히 떴지만 DB 마이그가 실패한" 우리 시나리오는 Velopack 의 관심사 밖**일 가능성이 높다. → 우리가 직접 롤백 상태머신을 들고 있어야 한다(§3).
- **V2. 특정 버전으로 강제 다운그레이드 API**: `UpdateManager` 로 "지정한 구버전으로 되돌리기"가 1급 API로 지원되나, 아니면 `app-<old>\current` 포인터를 우리가 직접 다뤄야 하나? ⚠️실측.
- **V3. 이전버전 보관 개수/기간 설정**: 몇 개·며칠 보관하는지 설정 가능한가? 고리4는 **최소 직전 1버전 무손상 보장**이 필수. ⚠️실측 + 명시 설정.
- **V4. 서비스(워치독)/콘솔 앱 호환**: Velopack 은 데스크톱 앱 가정이 강함. 우리 구성(HitPan.API + HitPan.Web + Watchdog Windows 서비스 + cloudflared + MariaDB 5조각)에서 EXE만 Velopack 으로 교체할 때 **다른 4조각과의 버전 정합**을 Velopack 은 모름. → §3의 "묶음 단위"를 우리가 정의해야 함.

**검증 산출물 요구**: 위 V1~V4 를 다루는 격리 PoC(테스트 환경, 헌법 #39 — 운영 금지)에서 실측 후 본 설계의 가정을 확정/수정한다.

## 3. 원자적 롤백 설계 — 상태머신

### 3-1. 핵심 원칙 (사장님 요구 직역)
1. **묶음 단위 = {DB 스키마 + EXE(API/Web/Watchdog 번들)} 한 단위**. 둘은 절대 따로 안 움직인다(헌법 #20: 끊기면 무결성 깨짐).
2. **"적용 전 완전 백업" → "적용" → "검증" → 실패 시 "묶음 전체 원복"**.
3. **전원차단(원자성) 대비**: 어느 순간 죽어도, 재부팅 후 워치독이 상태를 읽어 **자동으로 끝내거나(roll-forward) 되돌린다(roll-back)**. 사람 손 0번(헌법 #30).
4. **운영 직접 수술 금지(헌법 #39)**: 모든 전환은 검증된 단일 스크립트/서비스가 수행. 손 ALTER 금지.

### 3-2. 상태 영속화 — 신규 상태파일 (DB 밖에 둔다)
DB 안에 상태를 두면 "DB 롤백 시 상태도 같이 롤백"되는 자기참조 함정에 빠진다. 따라서 **업데이트 진행 상태는 DB 밖 JSON 파일**에 둔다:

```
%LocalAppData%\HitPan\Updates\update-state.json   (예시)
{
  "updateId": "guid",
  "fromVersion": "1.2.0",
  "toVersion": "1.3.0",
  "requiresMigration": true,
  "state": "MIGRATING",          // 아래 상태 enum
  "dbBackupFile": "...\\pre_update_20260629_xxx.sql",
  "exeOldVersionPath": "...\\app-1.2.0",
  "exeNewVersionPath": "...\\app-1.3.0",
  "migrationFiles": ["DB-82_xxx.sql", ...],
  "startedAt": "...", "updatedAt": "..."
}
```
- 멱등 키 `updateId`. 매 단계 전이마다 파일을 **먼저 갱신(fsync)하고** 다음 작업 수행 → 전원차단 복구 기준점.

### 3-3. 상태 enum 과 전이

```
IDLE
 └▶ (업데이트 결정: manifest.RequiresMigration=true, 동의/야간조건 충족)
BACKING_UP        : pre_update DB 덤프(mysqldump) + 현재 EXE 버전 경로 고정 보관 확인
 └ 성공 ▶ APPLYING_EXE
 └ 실패 ▶ ABORTED (아무것도 안 바꿈 — 가장 안전. 구버전 그대로 가동)

APPLYING_EXE      : Velopack 새 버전 적용 + (재기동 필요)
 └ 성공 ▶ MIGRATING
 └ 실패 ▶ ROLLBACK_EXE

MIGRATING         : 새 EXE 가 새 ALTER(DB-*.sql 묶음)를 트랜잭션으로 실행
 └ 성공 ▶ VERIFYING
 └ 실패 ▶ ROLLBACK_DB_THEN_EXE   ★핵심: 반쪽 롤백 금지

VERIFYING         : 정합 스모크(로그인200 / /me 200 복호화 / 캘린더 JSON / 대시보드 / 재고·매입·판매 핵심 1개씩 — 헌법 #39 deploy-demo.ps1 게이트 재사용)
 └ 성공 ▶ COMMITTED (완료. 구버전 EXE·pre_update 덤프는 보관정책따라 N일 후 정리)
 └ 실패 ▶ ROLLBACK_DB_THEN_EXE

ROLLBACK_DB_THEN_EXE :
   1) DB: pre_update 덤프로 복원(mysql.exe < dump)  → 스키마·데이터 구버전으로
   2) EXE: Velopack 으로 구버전(app-<old>) 활성화 + 재기동
   3) 재검증 스모크(구버전 기준)
 └ 성공 ▶ ROLLED_BACK (구버전 무손상 가동 + 사용자 안내 "업데이트 보류, 기존 버전 유지")
 └ 실패 ▶ NEEDS_OPERATOR (본사 비상 통지 — 헌법 #30 통지만, 본사 데이터 0)

ROLLBACK_EXE      : EXE 적용 단계에서 실패(아직 DB 안 건드림) → EXE만 구버전 복귀 + 재기동
 └▶ ROLLED_BACK
```

### 3-4. 안전 순서의 핵심 = "DB 마이그를 EXE 적용보다 **뒤에**, 그러나 백업은 둘 다 **앞에**"
- **백업(DB덤프 + 구EXE경로 고정)** 을 제일 먼저, 둘 다.
- EXE 적용을 DB 마이그보다 먼저 하는 이유: 새 ALTER 는 **새 코드가 실행**해야 코드-스키마가 같은 세대로 맞는다(헌법 #36 정신). 구코드가 새 ALTER 돌리면 또 미스매치.
- DB 마이그 실패 시 **반드시 DB 먼저 복원 → 그 다음 EXE 구버전 복귀** (순서 중요: 구버전 EXE 가 깨질 수도 있는 새 스키마를 보면 안 됨).

### 3-5. 전원차단(crash) 복구 — 워치독이 부팅 후 update-state.json 을 읽고 결정
| 죽은 시점 state | 부팅 후 워치독 행동 |
|---|---|
| BACKING_UP | 미완 백업 폐기 → ABORTED (구버전 그대로). 아무 변경 없었음 |
| APPLYING_EXE | Velopack 적용이 원자적이라 가정(V1⚠️). 미완이면 구버전 활성 확인 → ROLLBACK_EXE→ROLLED_BACK |
| MIGRATING | **가장 위험**. DB가 일부만 바뀌었을 수 있음 → 무조건 ROLLBACK_DB_THEN_EXE(pre_update 덤프가 진실원) |
| VERIFYING | 검증 미완 = 신뢰 불가 → ROLLBACK_DB_THEN_EXE (보수적) |
| ROLLBACK_* | 롤백 재개(idempotent: 덤프 복원은 몇 번 돌려도 동일 결과) |
| COMMITTED/ROLLED_BACK | 종결. 정리만 |

- **MIGRATING 의 부분적용 위험 완화**: 각 ALTER 묶음을 **가능한 한 단일 트랜잭션**으로. 단, MariaDB 의 DDL(ALTER TABLE)은 **암묵 커밋**되어 롤백 불가 → 트랜잭션으로 묶어도 DDL 은 안 돌아온다. **따라서 DDL 실패 시 의지처는 트랜잭션이 아니라 pre_update 전체 덤프 복원**이다. 이 점을 설계 전제로 못박는다(⚠️중요 리스크 §5).

## 4. BackupService 확장안

### 4-1. 무엇을 더 보관/복원해야 하나
현재 BackupService 는 **DB .sql 한 축만** 안다. 고리4는 EXE 축을 추가해야 한다. 단, **EXE 물리 보관은 Velopack 책임(app-<old> 폴더)** 으로 두고, BackupService 는 **"어느 버전이 직전이었나"의 메타와 DB 덤프**만 책임지게 분리하는 것이 깔끔하다(SoC).

### 4-2. 권고 — RestoreAsync 에 끼워넣지 말고 별도 오케스트레이터
- `RestoreAsync` 는 **사용자가 자료관리에서 수동 복원**하는 경로다(회사명 확인 등 UX 포함). 여기에 EXE 롤백을 섞으면 의미가 오염된다.
- 대신 **신규 `UpdateRollbackOrchestrator`(Watchdog 측)** 를 두고, 그 내부에서 BackupService 의 **재사용 가능한 조각**을 부른다.

### 4-3. BackupService 확장 시그니처(설계안 — 구현 아님)
```
// IBackupService 에 추가(인터페이스 확장 → 헌법 #12: 모든 구현체 grep 필수)
Task<string> DumpForUpdateAsync(string tenantId, string label, CancellationToken ct);
   // pre_update_*.sql 생성, 경로 반환. RunMysqldumpAsync 재사용. retention 제외(자동삭제 금지).
Task RestoreFromFileAsync(string tenantId, string dumpFile, CancellationToken ct);
   // 회사명 확인을 '시스템 트리거(updateId 검증)'로 대체한 내부 복원. RunMysqlImportAsync 재사용.
```
- 기존 `RunBackupAsync`/`RestoreAsync`/`mysqldump`/`mysql import` 헬퍼는 **그대로 재사용**(덮어쓰기 금지 — 헌법 #1). 추가만.
- §#3 정합: 새 메서드도 backup_history/restore_history 에 INSERT/UPDATE만. DELETE 0.

### 4-4. 신규 컴포넌트 목록(설계상 필요, 구현은 결재 후)
1. **스키마 버전 추적 테이블** `schema_migrations(version PK, applied_at, update_id, checksum)` — **clean DDL(hitpan_db.sql)에도 편입**(헌법 #36). 롤백 판단·재적용 멱등의 기준점. 현재 전무 → 선결.
2. **`MigrationRunner`**(새 EXE 측, API): DB-*.sql 묶음을 schema_migrations 기준으로 순서대로·멱등 적용. 손수술 대체(헌법 #39). 적용 전 DESCRIBE 확인(헌법 #13).
3. **`UpdateRollbackOrchestrator`**(Watchdog): update-state.json 상태머신 운전. 부팅 시 crash 복구 진입점.
4. **Velopack 실통합**(VelopackUpdaterStub 대체): NuGet 참조 + UpdateManager 결선 + app-<old> 보관정책 명시(§2 V3).

```
// UpdateRollbackOrchestrator.RunUpdateAsync(manifest)  ※Velopack V1~V4 검증 후 확정
state = BACKING_UP;  save();

// ── 새 EXE 부팅 직후 ──
if (manifest.RequiresMigration) {
  state = MIGRATING; save();
  try { migrationRunner.ApplyPending(updateId); }            // schema_migrations 기준 멱등
  catch { goto ROLLBACK; }
}
state = VERIFYING; save();

ROLLBACK:
  state = ROLLBACK_DB_THEN_EXE; save();
  backup.RestoreFromFileAsync(tenant, dbDump);               // ①DB 먼저
  velopack.RollbackTo(oldVer); restart();                    // ②EXE 구버전 (V2⚠️)
  if (smoke.AllPass(oldVer)) { state = ROLLED_BACK; notifyUser("기존 버전 유지"); }
  else { state = NEEDS_OPERATOR; meta.NotifyEmergency(); }   // 헌법 #30 통지만
```

## 8. 정합성 자가검토

- **헌법 #3**: 롤백은 원장 UPDATE/DELETE 아님 = 전체 덤프 스냅샷 복원. backup/restore 이력은 INSERT/UPDATE only. (R6 사장님 확인 단서)
- **헌법 #20**: DB+EXE 묶음 단위로만 전이 → "확정했는데 안 맞음" 끊김 차단. 반쪽 롤백 금지가 본 설계 핵심.
- **헌법 #34**: 연결축·업데이트 워크플로우 = 정식 완성도. 미가동 stub 을 정식으로 끌어올림.
- **헌법 #36**: schema_migrations + 신규 컬럼은 clean DDL 편입. install.bat 에 ALTER 루프 추가 금지(MigrationRunner 가 업데이트시 담당, 신규설치는 여전히 clean DDL 단일 import).
- **헌법 #39**: 모든 전환은 검증된 단일 오케스트레이터/스크립트. 손 ALTER·운영 직접수술 0. PoC 는 테스트 환경 한정.
- **헌법 #29·#33**: 본 문서는 설계까지. 코드 0건. 결재 후 SOP [6]~[7] 진입.
