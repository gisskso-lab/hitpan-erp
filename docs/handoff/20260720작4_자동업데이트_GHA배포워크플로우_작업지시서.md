## 1. 문제

자동업데이트 zip·manifest·EXE 를 `updates.hitpan.kr` 에 올리는 **GHA 경로가 없다**(실측: `.github/workflows/` 에 deploy-ncp.yml=백오피스·랜딩만, build-installer.yml=GitHub Release만). 그동안 updates 업로드는 사장님이 손으로 했다. 이제 push 한 번으로 자동업데이트 배포가 되게 한다.

## 2. 재사용할 기존 자산 (추측 0 — 이미 있는 것)

- **NCP 접속** = GitHub Secrets `NCP_SSH_PRIVATE_KEY`·`NCP_HOST`·`NCP_USER` (deploy-ncp.yml:87-97 에서 이미 사용 중). 개인키는 GHA Secrets 에만, PM PC·레포에 없음(헌법 #22·#29 정합).
- **publish-update.sh** (커밋 85206e3) — NCP 안에서 zip 배치·서명·원자교체·자기검증·롤백. 이번 워크플로우가 SSH 로 이걸 호출한다.
- **sign-manifest.sh** — 서명 규격 단일출처(publish 가 source). 서명 개인키 = NCP `/var/hitpan/update-keys/update_private.pem` (600 root).
- **build-manifest.ps1** — zip·unsigned manifest 산출(BOM 없음, 커밋 46234a0).

## 3. 설계 — `.github/workflows/deploy-update.yml`

### 트리거
- `workflow_dispatch` (수동, inputs: version·channel) — 실측·정식 배포 공통. 태그 자동 트리거는 **범위 밖**(오배포 위험, 사장님 결재 후 별건).

### 잡 흐름
```
[build] windows-latest
  1. checkout
  2. dotnet publish api/web/watchdog (-p:HitPanVersion=<version>)  ← 버전 단일주입(W4-0)
  3. build-manifest.ps1 로 hitpan-<version>.zip + manifest(unsigned) 산출
  4. 산출물 artifact 업로드
[deploy] ubuntu-latest  (needs build, environment: production)
  5. artifact 다운로드
  6. SSH 키 셋업 (deploy-ncp.yml 과 동일 패턴)
  7. zip·unsigned manifest 를 NCP /tmp 로 rsync
  8. NCP 안에서 publish-update.sh 실행 (SSH):
       sudo bash /opt/hitpan/installer/updates/publish-update.sh \
         --zip /tmp/hitpan-<ver>.zip --manifest /tmp/manifest-<ver>-unsigned.json
     → NCP 안에서 서명(개인키 NCP)·원자교체·자기검증·롤백. 개인키 GHA 로 안 나옴.
  9. 배포 후 curl 로 updates.hitpan.kr/manifest.json 최신 확인(이중).
```

### ⭐ 핵심 안전 원칙
- **서명은 NCP 안에서만.** GHA 는 unsigned manifest 까지만 만들어 NCP 로 넘기고, 서명은 publish-update.sh 가 NCP 개인키로 수행. **개인키는 GHA Secrets 에도 안 둔다**(CTO C-1 기존 처방 유지 — 업데이트 개인키 유출 = 전 고객 코드 실행).
- **publish-update.sh 가 NCP 에 배포돼 있어야 한다.** 현재 이 스크립트는 레포에만 있고 NCP 엔 없다 → 워크플로우가 실행 전 `installer/updates/*.sh` 를 NCP 로 rsync 하는 단계 필요(또는 deploy-ncp 처럼 /opt/hitpan/installer 에 상주).
- **updates 웹루트 경로**(예: `/var/www/updates.hitpan.kr`) = publish-update.sh 의 `--webroot` 기본값. NCP 실제 경로와 일치하는지 **사장님 확인 1회 필요**(추측 금지).

## 6. CTO 처방 — 착수 조건 (2026-07-20 부분수정후승인)

> ⭐ 핵심 인식: 개인키가 GHA 로 새는 건 이 워크플로우의 진짜 위험이 아니다(서명은 NCP 안에서만 = 맞음).
> **진짜 위험 = GHA runner 가 NCP 에서 sudo 로 스크립트를 실행한다는 것.** 스크립트를 바꿔치기하면
> NCP 에서 SYSTEM 권한 획득 → 개인키로 뭐든 서명 가능 → C-1 처방 무의미. 아래 B-1~4 가 이걸 막는다.

### B-1 (blocking) — 실행 스크립트는 NCP 상주본만, GHA 가 rsync 로 올려 실행 금지
- publish-update.sh·sign-manifest.sh 는 **NCP `/opt/hitpan/installer/updates/` 에 사전 상주**(사장님 sudo 1회 배치).
- 워크플로우는 **상주본을 호출만** 한다. GHA 가 옮기는 것은 **zip·unsigned manifest 데이터뿐, 실행 코드 아님.**
- 상주본 갱신(스크립트 수정 시)은 **별건 결재**로 사장님이 배치. 레포→NCP 자동 rsync 로 실행 스크립트를 밀어넣지 않는다.

### B-2 (blocking) — sudo 대상을 publish-update.sh 하나로 sudoers 화이트리스트
- 배포 계정(NCP_USER)이 임의 `sudo bash` 를 못 돌리게, `/etc/sudoers.d` 에 **"이 스크립트, 이 인자 형태만 NOPASSWD"** 화이트리스트(사장님 NCP 작업, 헌법 #29).
- 공급망 침해 시 폭발 반경을 zip 배치·manifest 교체로 물리적으로 가둠.

### B-3 (blocking) — fork PR·브랜치 보호·dispatch 권한 명시
- ① `deploy` 잡 `environment: production` 에 **required reviewer(사장님) 승인 게이트** 실제 설정.
- ② fork PR 에서 이 워크플로우 secrets 접근 불가 확인(pull_request 트리거 없음 유지).
- ③ dispatch 권한 = **레포 write 권한자로 제한**.
- ④ 워크플로우 파일·`installer/updates/*.sh` 변경은 **CODEOWNERS + 브랜치 보호 필수 리뷰**.

### B-4 (blocking) — NCP 실제 경로 4종 사장님 확인 = 착수 게이트
- publish-update.sh `--webroot` 기본값·FEED_URL 이 실제 nginx 서빙 경로와 다르면 자기검증이 옛 파일을 받거나 롤백 루프.
- 4종: ① 웹루트 ② 스크립트 상주 위치 ③ update_public.pem 존재 ④ manifest no-cache.
- **확인 회신 전에는 워크플로우 활성화 금지** — `.disabled` 로 둔다.
- ✅ 사장님 확인 완료(2026-07-20): ① `/var/www/updates.hitpan.kr` ② update_public.pem 존재. 남은 것: 스크립트 상주 위치(B-1 대로 /opt/hitpan/installer/updates/ 배치 여부)·manifest no-cache.

### N-1 (non-blocking) — dispatch input 버전 3자 정합 fail-closed
- build 잡 첫 스텝에서 version input == -p:HitPanVersion == manifest·zip 파일명 검증. 오타를 build 진입 즉시 세움.

### N-2 (non-blocking) — 다운그레이드 방어는 publish-update.sh 게이트로 이미 커버
- cmp_three + ALLOW_REPUBLISH=0 가 동일·하향 die. GHA 중복 게이트 불필요.

### N-3 (non-blocking) — GHA 자기검증 curl 은 이중 안전망으로 유지, 실패 시 "이미 롤백됨" 로그 명시
