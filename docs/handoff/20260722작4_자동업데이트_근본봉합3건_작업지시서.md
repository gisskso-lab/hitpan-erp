## §1. 봉합 #1 (P0 최중요) — 신규설치 schema_migrations 자동 시드

### 진범
`installer/hitpan_db_clean.sql`은 `schema_migrations` **테이블만 CREATE**(L3030)하고, "이 clean DDL엔 DB-02~DB-84가 이미 반영됨"이라는 **시드 INSERT가 없다**. 그래서:
- 구설치(ALTER 누적) DB → schema_migrations에 이력 쌓임 → 게이트 통과
- **신규설치(clean DDL) DB → schema_migrations 0행 → 첫 자동업데이트 무조건 차단** ← 전 신규 고객 영향 P0

clean DDL은 이미 DB-02~DB-84가 반영된 **최종 스키마**다. 논리상 그 마이그들은 "이미 적용됨"이 맞다. 시드가 빠진 게 결함.

### 봉합
`installer/hitpan_db_clean.sql`의 schema_migrations CREATE 직후에 **시드 INSERT 추가**:
```sql
-- 신규설치 시드 (20260722작4): clean DDL 은 아래 마이그가 이미 반영된 최종 스키마다.
--   신규설치 DB 는 이 이력이 없어 첫 자동업데이트가 교차검증 게이트에 전량 차단됐다(2026-07-22 실측).
--   clean DDL 이 담고 있는 마이그를 success=1 로 시드해 "이미 적용됨"을 명시한다(헌법 #36 정합).
INSERT INTO `schema_migrations` (`migration_id`, `success`) VALUES
('DB-02',1),('DB-03',1),...,('DB-84',1);   -- 실측 55개 전체
```
**시드 목록 = 실측 확정된 55개**: DB-02, DB-03, DB-04, DB-05, DB-06, DB-07, DB-08, DB-08b, DB-09, DB-10, DB-11, DB-12, DB-13, DB-14, DB-15, DB-16, DB-18, DB-19, DB-20, DB-21, DB-22, DB-23, DB-24, DB-25, DB-26, DB-27, DB-28, DB-29, DB-30, DB-31, DB-32, DB-33, DB-34, DB-35, DB-36, DB-37, DB-38, DB-39, DB-50, DB-60, DB-70, DB-71, DB-72, DB-73, DB-74, DB-75, DB-76, DB-77, DB-78, DB-79, DB-80, DB-81, DB-82, DB-83, DB-84.

### ⚠️ CTO 검토 요청 (동기화 보증)
- 이 시드 목록은 **clean DDL 안의 Migrations/SQL과 동일해야** 한다. 다음 릴리스에 DB-85가 추가되면 시드도 갱신돼야 함. **수동 목록은 갈라질 표면.**
- 대안: 시드를 손 목록이 아니라 **빌드타임에 Migrations/SQL 폴더를 스캔해 자동 생성**하거나, ddl-smoke CI가 "clean DDL의 SQL 파일 수 == schema_migrations 시드 행수"를 검사. → CTO가 동기화 방식 확정.
- **함정**: 시드에 없는 마이그(진짜 신규)는 여전히 게이트가 차단해야 정상. 시드가 과하면(존재 안 하는 마이그까지) 진짜 필요한 마이그를 놓친다.

## §2. 봉합 #2 — API 프로세스 30초 종료 지연

### 증상 (1.2.38 실측 로그)
```
23:55:15  ERP API 강제 종료: 30초 안에 끝나지 않아 중단했습니다.
```
`UpdateProcessGate.RunProcess`가 taskkill을 30초 타임아웃(L306)으로 기다리다 강제 중단. **교체는 됐지만(느리게 죽음) 30초 지연**은 정상 아님.

### 규명 필요 (봉합 전)
- `schtasks /End`는 "성공" 찍히는데 프로세스가 왜 즉시 안 죽나 — API가 graceful shutdown(DB 연결 정리·요청 대기)에 시간 걸리는지, taskkill이 뭔가에 막히는지.
- **어제 손으로 띄운 Session 1 유령**의 잔재 가능성도 배제 못 함(Sandbox 오염). 1.2.39 백지설치 실측으로 재현되는지 먼저 확인.

### 봉합 방향 (규명 후 택1)
- taskkill 전 API에 graceful stop 신호를 먼저 주고 짧게 대기 후 /F
- 또는 WaitUntilProcessGone 폴링을 종료 직후로 당기고 taskkill 재시도 루프

**이건 규명 우선. 재현 안 되면(오염이면) 기록만.**

## §3. 봉합 #3 — 교체 후 검증 대상 파일 오류 (.dll 못 찾음)

### 증상 (1.2.38 실측 로그)
```
23:55:21  파일 교체 완료(web→api) — .old 롤백용 보존 (1.2.38)
23:55:22  🛑 교체된 API 파일을 찾지 못했습니다: C:\Program Files\HitPan\api\HitPan.API.dll
```
파일 교체는 성공했는데, **사후 검증이 `HitPan.API.dll`을 찾는다.** 그런데 API는 **단일파일 publish(PublishSingleFile=true)** 라 `.dll`이 없고 **`HitPan.API.exe`만** 있다. 검증 코드가 옛 구조(.dll)를 기대 → 검증 실패 로그.

### 봉합
UpdateOrchestrator의 교체 후 검증에서 **`HitPan.API.dll` → `HitPan.API.exe`** 로 대상 정정(단일파일 구조 정합). FileVersion 읽기도 exe 기준.
- 규명: 이 검증 실패가 교체 자체를 롤백시키는지(치명), 로그만 남기는지(경미). 로그 순서상 교체는 완료됐으니 경미로 보이나, 검증 실패가 apply_status를 rolled_back으로 기록하면 본사 집계가 틀림.
