```
① 터널 죽음(cloudflared EventLog 레지스트리 잔재) → setup 요청이 ApiBaseUrl(=test1.hitpan.kr 터널)로 나갔다 530 실패

③ [②뚫으면] BOOTSTRAP_TOKEN_KEY 불일치 401 (본 작지서 A안 대상) ← 아직 실제 발생한 적 없음, 예측
```

- **핵심**: setup 은 `ErpApi`(BaseAddress=`appsettings.ApiBaseUrl`=`https://test1.hitpan.kr`, 터널 경유)로 호출됨(`LicenseSetupPage.razor` L289·348). loopback CORS 회피 설계(`HitPan.Web/Program.cs` L28~35). **즉 터널이 부모계정 생성의 전제.**
- **A안(키 불일치)은 ②·① 때문에 아직 키 검증까지 도달을 못 해 발생 관측이 0건.** 코드상 키 불일치는 실재(백오피스=실키 / ERP=DEV폴백, 실측)하나, **"진짜 401을 낸다"는 종단 재현으로만 확정.**
- **결론**: A안 봉합은 정당(코드상 키 불일치 실재). 단 **종단 재현에서 실제 키 401 관측 후 "진범 확정"** 처리. 오늘 "예측했는데 다른 게 진범" 반복 방지.

## 3. 🔴 보안상무(안철수) 결재 필요 — 공용키 vs 테넌트별 파생키
- (a)는 **서명키가 각 고객 PC db.conf 에 존재.** icacls(Administrators·SYSTEM only, `.iss` L1036) + 본사 미전송(#22)으로 보호되고, 이는 **기존 JWT_SECRET·ERP_ENCRYPTION_KEY 가 이미 수용한 리스크와 동급**(설계팀장·백엔드·네트워크 공통).
- **단 차이**: JWT_SECRET 은 PC별 난수(로컬전용)인데, BOOTSTRAP_TOKEN_KEY 는 **백오피스와 공유하는 대칭키.** 전 고객 **공용 단일키**면 한 PC 유출 시 임의 테넌트 토큰 위조 가능(횡적 위험, 단 tenantId·biz해시 매칭이 앞단 방어).
- **설계팀장 권고**: 백오피스가 `HMAC(마스터키, tenant_id)` 로 **테넌트별 파생키** 생성→그 PC db.conf 에만 내림+서명도 동일 파생키. PC 유출이 해당 테넌트로만 국한 = JWT 격리 수준과 동일.
- **결재 논점**: 공용키(구현 단순, 기존 리스크 수용) vs 파생키(안전, 백오피스 서명·발급 로직 추가). **보안상무·사장님 결정.**
