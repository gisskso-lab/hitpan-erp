# §1. 오늘의 확정 팩트 (사장님 못박음 2026-07-22 밤)

## 1-1. 🔴 핵심 팩트 — 복구설치가 진범
```
최초 설치 (백지)   → 잘 됨 ✅
복구 설치 (재설치) → 안 됨 ❌
```
**변수는 딱 하나 = "복구설치냐 아니냐."** 같은 EXE·같은 계정·같은 Sandbox인데
복구설치 경로만 달라서 결과가 갈렸다. **∴ 진범 = 복구설치 경로.** (사장님 논리, 실측 확정)

증상(복구설치 후):
- API 를 손으로 띄우면 **포트 5000(기본값)으로 뜸** — 5257 이 아님(실측: `Now listening on: http://localhost:5000`)
- **`test1.hitpan.kr` = 404** (로컬 `localhost:5234` 는 정상 로그인·작동)
- 즉 **db.conf 설정값(API_PORT=5257·TUNNEL_TOKEN 보존됨)은 맞는데 실제 실행상태가 어긋남**
  → "설정 ≠ 실행" 괴리 = **침묵 고장**(로컬만 되고 외부 터널 죽음). 검증하는 사람도 속는다.

**이게 사장님 헌법 [[feedback_no_overwrite_reinstall]] "덮어 재설치는 존재하지 않는 경로"가
왜 필요한지 오늘 실측이 증명한 것이다.** 복구설치는 최초설치와 달리 실행상태를 틀어놓는다.

## 1-2. ⚠️ 실측 스냅샷 (복구설치 완주 후 db.conf — 이건 "맞게" 들어감)
```
API_PORT=5257 / SLOT_INDEX=1 / PRIMARY_DOMAIN=test1.hitpan.kr
TUNNEL_ID=b8efde38-c50b-49ac-91bc-5abf3cfce753 / TUNNEL_TOKEN=eyJ...(살아있음)
schtasks: HitPan-ERP-API-tenant-1·keepalive·WEB 전부 등록됨
cloudflared: RUNNING, 올바른 토큰으로 tunnel run
```
**중요**: db.conf·작업·터널토큰은 완주 후엔 "맞게" 들어간다. 그런데도 **실행상태(뜬 포트·외부접속)는
틀어져 있다.** 파일만 보면 정상이라 오판하기 쉽다(§5 PM 오판이 정확히 이것). test1 404 의 남은
후보 = Cloudflare 클라우드 ingress(public hostname→service 매핑)인지, 로컬 실행 괴리인지 **미확정.**

## 5-2. "지금 db.conf 맞으니 괜찮다"로 틀어진 상태를 덮음 (반복된 오판)
API 가 5000 으로 떴던 **사실**을, "지금 db.conf 는 5257 이니 아까 건 미완성"이라며 덮으려 함.
사장님: *"뒤집힌 게 아니지. 이미 포트설정부터 틀어져 있었는데."*
→ **틀어진 상태가 발생한 사실 자체가 결함이다.** 나중에 우연히 맞아도 "틀어질 수 있는 구조"가
   복구설치의 치명성. 현재값이 정상이라고 과거 고장을 없던 일로 만들지 말 것.

경로" 위반. 그 복구설치가 오늘 모든 증상(포트·터널 틀어짐)의 원인. **정상은 백지 설치뿐.**
