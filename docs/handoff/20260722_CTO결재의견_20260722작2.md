## 🔴 BLOCKING — A안 원안의 치명적 전제 오류

### B-1 — 워치독은 DB 마이그를 적용하지 않는다 (고리5 미구현)
[`Worker.cs:280`](../../src/HitPan.Watchdog/Worker.cs#L280) 명시:
> "실제 EXE 교체·재시작·검증·롤백(고리4)은 ApplyUpdateAsync 가 수행한다. **DB 마이그 자동적용은 고리5 범위.**"

즉 **워치독은 EXE만 교체하고, DB 스키마는 건드리지 않는다.** 게이트 ①은 겉보기엔 "오타 방지"
문구지만, 실질은 **"마이그가 필요한 릴리스를 아예 못 들어오게 막는 거친 방패"**였다.
고리5(마이그 자동적용)가 없는 현재, 게이트 ①을 순진하게 풀면:

- 새 코드(신버전 EXE)가 새 컬럼/테이블을 요구 → **DB에는 그 스키마가 없음**(적용 주체 부재)
- → 신버전 ERP 가 500 → 롤백해도(구 EXE 복원) 이미 늦을 수 있음 = **헌법 #20 워크플로우 파괴 P0**

**게이트 ①은 "고리5가 생길 때까지 마이그 릴리스를 막는 임시 안전벽"이었다.** 이 맥락을 작지서가 놓쳤다.

### B-2 — A안이 기대는 "schema_migrations 로 신규 판정"은 절반만 맞다
`schema_migrations` 는 실재하고 `MigrationRunner`(API)가 채운다(확인됨). 하지만:
- 워치독이 "zip 의 .sql 중 schema_migrations 에 없는 것"을 신규로 판정하는 것 자체는 타당하나,
- **신규가 없을 때만 통과**시켜도, 그 "신규 없음"이 **정말 스키마 무변경**을 보장하려면
  zip 의 DB-*.sql 집합이 이미 적용 완료임을 신뢰해야 한다. 누적 이력이라 대개 참이나,
  **clean DDL 과 어긋난 케이스(헌법 #36 갭)**에선 거짓일 수 있다.

## ✅ 채택안 — A'안 (수정)

게이트 ①을 **"존재"에서 "신규 마이그 유무"로 정밀화하되, 방향을 뒤집는다**:

```
현재 ①:  SQL 존재 + RequiresMigration=false  → 차단   (누적 이력에 항상 걸림 = 오탐)
A'안 ①:  zip 에 schema_migrations 미적용 신규 .sql 이 있는가?
          · 신규 없음                          → 통과 (누적 이력만 = 정상 릴리스)  ← 오탐 제거
          · 신규 있음 + RequiresMigration=false → 차단 (진짜 오타, 방어 유지)
          · 신규 있음 + RequiresMigration=true  → 차단 (고리5 미구현이라 적용 주체 없음!) ← B-1 반영
```

**핵심(B-1 반영)**: 신규 마이그가 있으면 `RequiresMigration` 값과 **무관하게 차단**한다.
고리5(마이그 자동적용)가 생기기 전까지, 마이그가 필요한 릴리스는 자동업데이트로 내보내지 않는다.
이건 제약이 아니라 **정직**이다 — 적용할 수 없는 마이그를 "통과"시키는 게 사고다.

→ 결과: **누적 이력만 있는 릴리스(대부분의 코드 수정 배포)는 통과**해 자동교체된다(오탐 해소).
   마이그가 진짜 필요한 릴리스는 고리5 완성 전까지 수동 경로(재설치 등)로 간다(현 단계 정직).
