## 2. 자유 반박 토론 — PM이 사장님 안에 제기한 우려 6건

### 반박 ① — "고객은 DB 모름" 안의 2가지 함정

**함정 A — 마케팅 vs 기술 분리 함정**
- 사장님 안: *"고객은 DB 엔진 모름, 그냥 히트판"*
- PM 우려: 마케팅·고객 카피 = 100% 정합. **그러나 본사 CS·기술 진단 영역에서는 DB 차이가 사라지지 않음.** MDB(단일 사용자·파일잠금) vs MariaDB(멀티 사용자·트랜잭션) = 마이그 사고 시 진단 시 결국 DB 엔진 차이로 돌아옴.
- PM 대안: **두 트랙 분리** — 고객 카피 = "히트판 신버전" / 본사 CS·기술 매뉴얼 = DB 엔진 차이 명시.

**함정 B — "이관 안 되면 이상함"의 책임 함정**
- 사장님 안: *"버전업에서 데이터 이관 안 되는 자체가 이상함"*
- PM 우려: 고객 입장 = 정당한 기대 동의. **하지만 ERP 업계 현실에서 100% 자동 마이그는 사실상 존재 안 함.** 더존 V10→V12도 일부 수동, SAP S/4HANA는 컨설팅 6개월~1년.
- PM 진짜 우려: "자동 99% 보장" 카피 + 1% 강제 조정으로 마케팅 → **마이그 사고 시 고객이 본사 책임 주장 가능** (헌법 #24 책임 분산 위반 위험).
- PM 대안: 자동 마이그를 **"best effort"** 표현 + 강제 조정을 **"정합성 검증 기능"** 으로 명세. *"99% 보장"* 직접 표현 회피.

### 반박 ② — "99% + 1% = 100% 봉합" 안의 2가지 위험

**위험 A — "1%"의 진짜 크기**
- 사장님 안: *"99% 자동 + 1% 강제 조정 = 100% 봉합"*
- PM 우려: 1%는 통계적 수사. **실제로는 한 고객당 0.1% ~ 30% 변동** 가능. 100,000건 거래 중 30%면 30,000건 = 어드민이 수동 조정 불가능한 양.
- PM 대안: *"1%"* 추상 표현 대신 **"건수 기반 한도"** — *"불일치 100건 이하 = 강제 조정 가능 / 100건 초과 = 본사 컨설팅 필수"*

**위험 B — "워크플로우 차이 = 물리 법칙" 의 자기방어 함정**
- 사장님 안: *"워크플로우·기능 차이는 물리 법칙처럼 항상 발생 = 1% 강제 조정 = 결함 아닌 설계"*
- PM 우려: 우아한 명제. **그러나 이 논리는 자기방어 함정** — 우리 마이그 코드 버그(오늘 진범 9건) 도 "물리 법칙"으로 정당화 가능 = 코드 품질 책임 회피 위험.
- PM 진짜 의견: 1% 강제 조정 = 안전망 ✅ (사장님 맞음) **+ 동시에** "마이그 코드 99% 달성 책임" 도 본사가 짐 ✅ (헌법 #19 errors 0 정합). 둘은 따로 관리. 같은 논리로 묶으면 안 됨.

### 반박 ③ — PM이 추가로 제기하는 의문 3건

**의문 A — 강제 조정 권한자 = 누구?**
- 사장님 안: *"마스터 어드민이 임의 조정"*
- PM 의문: 마이그 시점 = 신규 ERP 첫 진입 = **어드민 권한 부여 전 가능성**. 어드민 계정이 아직 안 만들어졌는데 누가 강제 조정? 첫 가입자 자동 = 어드민?

**의문 B — 강제 조정 후 검증자 = 누구?**
- PM 의문: 어드민이 직접 조정 + 직접 확인 = **self-audit (자기 검증)**. 외부 검증자 부재. 사장님 헌법 #challenge_owner 정합 시 *"어드민도 검증 받아야"* = 본사 또는 대리점이 사후 검증 기능 필요?
- 헌법 #24(책임 분산) 정합 시 = 본사는 검증 안 함 (사장님 데이터 주권). 그러면 self-audit이 최선?

**의문 C — 1% 강제 조정 이력 보관**
- PM 의문: 강제 조정 = **감사 추적 영구 보관 필수** (세무·법적 분쟁 대비). 어디 보관?
  - 본사 보관: 헌법 #22 (본사 데이터 최소주의) 위반
  - 고객 PC 보관: PC 잃어버리면 감사 이력 사라짐 = 분쟁 시 본사 패소 위험
  - 클라우드 백업: 사장님 데이터 주권 vs 본사 클라우드 = 또 다른 분쟁
