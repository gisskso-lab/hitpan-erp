## 📚 Chapter 2 — 박사논문 학술 근거

### 2.1 Brewer's CAP Theorem (PODC 2000)

**Eric Brewer**, *"Towards Robust Distributed Systems"*, PODC 2000.

분산 시스템 = Consistency · Availability · Partition Tolerance 중 2개만 가능.

**히트판 적용:**
- AP 시스템 (Availability + Partition Tolerance 우선)
- 네트워크 파티션 시 가용성 유지 → 일관성은 eventual

**증명:** Gilbert & Lynch (MIT 2002), *"Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services"*, ACM SIGACT News.

### 2.2 PACELC Theorem 확장

**Daniel Abadi (Yale 2012)**, *"Consistency Tradeoffs in Modern Distributed Database System Design: CAP is Only Part of the Story"*, IEEE Computer.

- Partition 발생 시 → Availability vs Consistency
- 정상 시 → Latency vs Consistency

**히트판 적용:** 정상 시에도 latency 영역 = 5234 → 5257 → MariaDB localhost = sub-10ms. 클라우드 ERP 대비 우위.

### 2.3 Recovery Oriented Computing (Berkeley 2002)

**David Patterson et al.**, *"Recovery Oriented Computing (ROC): Motivation, Definition, Techniques, and Case Studies"*, UC Berkeley CSD-02-1175.

**핵심:** `Unavailability ≈ MTTR / MTTF`
- MTTR 10배 단축 = MTTF 10배 늘림과 동일 효과
- *"하드웨어 결함·소프트웨어 버그·운영자 실수 = 해결 대상이 아닌 수용 대상"*

**히트판 적용:** 워치독 영역 = MTTR 최소화 전략. 5분 → 1분 → 30초 = 가용률 직접 향상.

### 2.4 Google SRE Book (O'Reilly 2016)

**Beyer et al.** (Google SRE), *"Site Reliability Engineering"*, O'Reilly.

**Chapter 3 - Embracing Risk:**
- 99.9% = 연 8.76시간 다운타임
- 99.99% = 연 52.56분
- 99.999% = 연 5.26분 (비용 100배)
- *"Extreme reliability comes at a cost"*

**히트판 적용:** 99.99%가 cost·feasibility 최적.

**Chapter 5 - Eliminating Toil:**
- *"Toil = 수동 반복 작업 = 자동화 대상"*
- 워치독 = toil 자동화

### 2.5 Netflix Chaos Engineering (2017)

**Casey Rosenthal et al.** (Netflix), *"Chaos Engineering"*, arXiv:1702.05843.

**5 Principles:**
1. Build a hypothesis around steady state
2. Vary real-world events
3. Run experiments in production
4. Automate continuously
5. Minimize blast radius

**히트판 적용:** 20개 시나리오 시뮬레이션 = Chaos Monkey 패턴.

### 2.6 Resilience Engineering (Hollnagel 2006)

**Erik Hollnagel et al.**, *"Resilience Engineering: Concepts and Precepts"*, Ashgate Publishing.

**핵심:**
- 시스템 = 실패 수용 + 적응
- Recovery 능력 = Resilience 본질

### 2.7 Tanenbaum Distributed Systems (Pearson 2017)

**Andrew Tanenbaum & Maarten Van Steen**, *"Distributed Systems: Principles and Paradigms"*, 3rd Edition, Pearson.

**Chapter 8 - Fault Tolerance:**
- Failure detection: ping 주기 = trade-off
- 1분 주기 = 일반 표준

### 2.8 Polly 라이브러리 (.NET)

**Microsoft Resilience Documentation:**
- Circuit Breaker pattern (Michael Nygard, *"Release It!"*, Pragmatic Bookshelf 2007)
- Retry pattern
- Timeout pattern

**히트판 적용:** Watchdog C# 구현 = Polly 패턴 활용.

### 2.9 Stuart Cheshire "Latency Lags Bandwidth" (CACM 2005)

**Stuart Cheshire**, *"It's the latency, stupid"*, CACM January 2005.

**경고:** 자동 봉합 무한 반복 = 시스템 안정성 0. Cool down 필수.

**히트판 적용:** Cool down 5회/시간 → 본사 알림.

### 2.10 Yair Stark "Error Budget Is All You Need" (2024)

**Medium**, *"Error Budget Is All You Need - Part 1"*.

**핵심:** 99.99% SLO = 0.01% error budget = 분기당 약 13분 다운 허용.

**히트판 적용:** 분기 13분 = 일 평균 8.6초. 사고 1건 = 분기 budget 즉시 소진 위험.
