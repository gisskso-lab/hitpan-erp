## 📋 안건 1 — "연결 이슈 100% 가능한가?"

### 사장님 출발점
> *"99~100%는 되야됨"*

---

### Round 1.1 — PM 1차 안건 제시

**박사논문 근거:**

| 저자·연도 | 핵심 주장 |
|---|---|
| Brewer (2000, PODC) | CAP Theorem — 분산 시스템은 C·A·P 중 2개만 가능 |
| Gilbert & Lynch (MIT 2002) | CAP 수학적 증명 |
| Patterson (Berkeley 2002) | ROC — Unavailability ≈ MTTR/MTTF. MTTR 10배 단축 = MTTF 10배 늘림과 동일 |
| Google SRE Book Ch.3 (Beyer et al. 2016) | 99.99% = 연 52.56분. 99.999%는 비용 100배 |
| Rosenthal et al. (Netflix 2017) | Chaos Engineering — *"Build confidence by experimenting in production"* |
| Hollnagel (2006) | Resilience Engineering — 실패 수용 |

**비즈니스 사례:**

| 사고 | 날짜 | 다운타임 | 원인 |
|---|---|---|---|
| AWS US-EAST-1 | 2017-02-28 | 4시간 | S3 명령어 오타 1개, 손실 1.5억 달러 |
| Cloudflare Argo | 2022-06-21 | 1.5시간 | BGP 설정 오류 |
| Facebook | 2021-10-04 | 6시간 | BGP 라우팅 |
| KT 한국 전국 | 2021-10-25 | 40분 | BGP 설정 오류 |
| SKT | 2024-04 | 수시간 | 인증 시스템 |
| Nabu Casa (HA) | 상시 | 인터넷 끊김 시 원격 불가 | 본질적 한계 |

**PM 1차 결론:**

100% 영구 보장 = **수학적 불가능**. 이유:
1. 외부 의존: Cloudflare(99.99%) × 통신사(99.5%) × 전기(99%) × HW(99%) = **약 97.5% 상한**
2. CAP 정리상 파티션 발생 시 가용성·일관성 중 하나 포기
3. Patterson ROC — 실패는 해결 대상이 아닌 수용 대상
4. **사장님 본인 헌법 #27 명문화:** *"SLA 99.99% 정직. '100% 무결성' 약속 금지"*

→ **사장님 격언과 헌법 #27이 충돌**. 사장님이 *"99~100%"*라 하셨지만 헌법 #27은 *"100% 금지"*. PM은 헌법 우선으로 해석 = **목표 99.99%**.

### Round 1.2 — 보안 매니저 2 반박

> *"PM. 박사논문 인용은 정합. 단 '사용자 시선 100%'와 'SLA 시선 100%' 구분 필요.*
>
> *사용자 시선 100% = 본인 PC 켜져있는 동안 ERP 작동 = 본사 책임 99.99% 가능. 통신사 정전은 고객 자기 회사 사고 → 본사 책임 0 (헌법 #24 책임 분산).*
>
> *사장님 격언 '99~100%' = 본사 책임만 99.99% = 사용자 인지 100%."*

**핵심:** PM의 *"97.5% 상한"* = 외부 포함 수치. **본사 책임만 분리하면 99.99% 가능**.

---

### Round 1.3 — 백엔드 매니저 재반박

> *"보안2 의견 부분 정합. 본사 책임만 99.99% 가능. 단 검증 = 1만 고객사 4주 베타 필수.*
>
> *Brewer CAP — 분산 환경 시뮬레이션 의무. Netflix Chaos (Rosenthal 2017) — Production 실험 필수.*
>
> *본사 PC 검증 ≠ 고객사 검증. 베타 단계 발진 안 거치면 99.99% 주장 = 거짓.*"

**핵심:** 숫자 자체보다 **실측이 본질**.

---

### Round 1.4 — DB 매니저 재반박

> *"백엔드 의견 정합. 추가 사항: 헌법 #22 본사 데이터 최소주의 위반 위험.*
>
> *99.99% 검증 위해 본사 메타 ping 영역 필요. 단 메타 = up/down 핑만, 업무 데이터 0. 이 선 안 지키면 클라우드 ERP가 됨.*
>
> *추가: 데이터 유실 0이 99.99%보다 우선. 헌법 #22 v3 — '백업조차 E2E 암호화 본사가 내용 모르게'. 이게 빠지면 99.99% 무의미.*"

**핵심:** 99.99% 가용성보다 **데이터 무결성 100%가 선행**.

---

### Round 1.5 — 검증팀장 재반박

> *"전원 의견 정합. 단 검증 방법 미합의.*
>
> *Netflix Chaos Monkey — random 인스턴스 강제 종료. 본 시스템 적용 = cloudflared 강제 종료·Windows Update 시뮬레이션·백신 격리·전원 차단·인터넷 차단 17개 시나리오.*
>
> *각 시나리오 5분 이내 자동 복구 안 되면 99.99% 거짓. 17/17 PASS 후만 99.99% 주장 가능.*
>
> *현 상태 = 17개 시나리오 실측 0건. 즉 현재 SLA = '모름'. 95%·97%·99% 모두 추정.*"

**핵심:** 실측 전엔 숫자 무의미. **17/17 PASS 후에야 숫자 박제 가능**.

---

### Round 1.6 — 설계팀장 재반박

> *"검증팀장 정합. 추가: 다중 이중화 없이 99.99% 불가.*
>
> *현재 = cloudflared 단일. SPOF(단일 장애점). Cloudflare 자체 다운 = 즉시 0%.*
>
> *Tailscale·WireGuard 다중 백업 = 99.99% 도달의 유일 경로. 단일 터널로 99.99% 주장 = 박사논문 수준 거짓.*"

**핵심:** **다중 이중화 없으면 99.99% 도달 불가**.

---

### Round 1.7 — 본부장 재반박

> *"설계팀장 정합. 단 사업·법무 측면 추가.*
>
> *마케팅 영역에서 '99.99% 보장' = 광고법 정합 위험. 약관에 SLA 명시 + 위반 시 환불 조항 필요.*
>
> *법무팀장 확인 필수. 헌법 #24 책임 분산 — 약관에 본사 책임 영역 명문화.*
>
> *결론: 99.99% 마케팅 메시지 → 약관 SLA → 위반 시 환불. 이 3단 정합 없으면 광고법 위반.*"

**핵심:** 숫자뿐 아니라 **약관·법무 정합 필수**.

---

### Round 1.8 — 외부 AI 의견 (OpenAI 시각, PM 시뮬레이션)

> *"PhD 수준 분석: 본 아키텍처(로컬 PC + cloudflared 단일)는 본질적으로 95~98%가 상한. 99.99% 도달은 다중 이중화 필수.*
>
> *Home Assistant Nabu Casa 사례: 같은 아키텍처(로컬 + 터널). 공개 SLA 없음. 실측 95~98% 추정.*
>
> *Korean ERP 비교: 이카운트 = AWS 클라우드 = 99.9% SLA 가능. 더존 = 하이브리드. 히트판 = 로컬 단일. **셀링 포인트(데이터 주권)와 SLA(99.99%)는 trade-off**.*
>
> *권고: 99.5% SLA로 정직 마케팅 + 데이터 주권 강조. 99.99%는 다중 이중화 후 6개월 실측 후 주장."*

**핵심:** **셀링 포인트와 SLA는 trade-off**. 99.5%로 정직이 99.99% 거짓보다 강함.

### Round 1.9 — 외부 AI 의견 (Gemini 시각, PM 시뮬레이션)

> *"OpenAI 의견 부분 동의. 단 99.5%는 한국 시장에서 약함.*
>
> *더존 99.9%·이카운트 99.95% 마케팅. 99.5% = 영업 패배.*
>
> *대안: '본사 책임 영역 99.99% 보장 + 고객 인터넷 영역 별도'로 분리. 약관 명문화 + 헌법 #24 가르침 매뉴얼(LTE 백업 라우터 권고)로 보완.*
>
> *Brewer CAP 정합: 본 시스템 = AP. 일관성보다 가용성 우선. 다중 이중화 = AP 강화 경로."*

**핵심:** **본사 책임 99.99% vs 외부 책임 분리** = 정직 + 영업 가능.
