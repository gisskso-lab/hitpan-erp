### 2.3 ERP 계정 계층 (헌법 #38 — 절대, 외우기)

```
부모계정 = tenant_admin = 백오피스에서 등록(가입시 발급) = 계정ID가 라이선스
자식계정 = tenant_user = 부모가 ERP 안에서 직접 생성 = 백오피스에 안 남음
```

- **ERP가 발급하는 account_type 은 tenant_admin·tenant_user 둘뿐.** 다른 값 존재 불가.
- `platform_admin`·`reseller_admin` = **백오피스 계층**. ERP에 있던 건 잘못 나눈 것 → 청소 대상 (12차 후속 a0e8327에서 죽은 분기 제거).
- 2026-06-18 보안 격벽: ERP JWT에 platform_id·reseller_id 식별자 미발급 (고객사 PC 뚫려도 본사·타 고객사 노출 방지, 헌법 #22).

### 2.4 ⚠️⚠️ 덩어리2 = 절대 건들지 말 것 (헌법 #37)

> **차기 세션이 코드조사 돌릴 때 이걸 "잔재·오류"로 오판하고 제거할까봐 사장님이 헌법으로 못박음.**

- **덩어리2 정의:** 백오피스→ERP **단방향 수신**해서 ERP 로컬에 보관하는 메타데이터 컬럼. **쓰기(수신 UPSERT)는 살아있는데 ERP가 그 값을 SELECT·소비하는 코드는 아직 0건** 상태 (자리 선점).
- **대표:** `local_subscription`·`tenants`·`subscriptions` 의 `reseller_id`·`reseller_tier` (= 어느 대리점이 이 고객사를 영업했는지 = **영업 출처 메타데이터**).
- 출처: 부트스트랩 토큰 클레임(`CompanyBootstrapController` local_subscription UPSERT) + 백오피스 웹훅(`WebhookInboundController`).
- **"SELECT 0건 = 정상"이며 제거 근거 아님.** 헌법 #18/#22 위반 아님 (수신 방향이지 전송 아님).
- **핵심 인과 (사장님 못박음):** ERP 계층이 부모/자식 2개뿐이라는 사실 때문에 reseller_id를 "계층에 안 맞는 잔재"로 오판하기 쉬운데, reseller_id는 *계정 계층*이 아니라 *영업 출처 메타*다. **계층 정의를 근거로 덩어리2를 만지면 안 됨.**
- 만질 일 생기면 **코드 손대기 전 사장님 결재** (헌법 #33). `tenants.reseller_tier`는 NOT NULL DEFAULT 없어서 컬럼만 떼면 부모계정 가입 500.

### 2.5 출하 DDL = 신규설치 단일 진실원 (헌법 #36)

- 코드가 SELECT/INSERT/UPDATE 하는 **새 테이블·컬럼은 반드시 `installer/hitpan_db_clean.sql` 에 먼저 편입** (DESCRIBE 후, 헌법 #13).

## 3. 전수조사 체계 — 가장 중요 (이 방법론을 그대로 이어받을 것)

### 3.1 왜 전수조사인가

> 사장님 격언: *"테스트 100% = 실제 70~80%. 바이브코딩 한계."* ([[owner_quote_vibecoding_limit_20260515]])
> 헌법 #23: AI 협업 코드 5중 검증 의무. 헌법 #19: errors 0 + warnings 0 = 무결성.

EXE 빌드(고객 첫 등장) 전에 **극한 환경에서 검증**한다 (사장님 품질 헌법, EVF 6대 영역).

### 3.2 전수조사 표준 방법론 (사장님이 확정한 형식)

```
① N병렬 실측 조사  (9축 또는 5축, 에이전트 동시 fan-out)
② 1단 교차검증 (정합) — 검증팀: 검증팀장 + 검증팀원
③ 2단 교차검증 (적대) — 임원팀: PM + CTO + 설계팀장 + 검증팀장
④ P0만 즉시 봉합, 나머지(P1·P2·P3)는 사장님 보고 후 결재받아 봉합
```

- **1단 = 정합 검증** (찾은 결함이 진짜인가 file:line 실측).
- **2단 = 적대 검증** (봉합이 진짜 봉합인가, **거짓봉합 색출**). ← **이게 핵심.**

### 3.3 9축 정의 (13·14차 동형 — 사장님 지정)

| 축 | 영역 |
|---|---|
| 1 | 통신 이슈 / 워치독 |

| 3 | 회계 무결성 |
| 4 | 재고 무결성 |
| 5 | 프론트 계약 (프론트↔백엔드 DTO 불일치) |

> 5축 버전(10·11·12차)도 있었으나, 통합 9축이 사장님 최종 지정 형식.

### 3.4 ⭐ 거짓봉합 자가발견 — 이 프로젝트의 시그니처

**매 차수(7~14차) 봉합 직후 2단 적대검증이 거짓봉합을 잡아냈다.** 누적:

| 차수 | 거짓봉합 사례 | 원인 |
|---|---|---|
| 7차 | REGRESSION (봉합이 새 버그 도입) | — |
| 8차 | created_by/created_at 거짓봉합 | 교차검증 거짓전제 |
| 10차 | P0-4 직접매입 (REGRESS) | 봉합 후 자가발견 |
| 11차 | 반품사유 유실 (백엔드 컬럼 누락) | 교차검증 적발 |
