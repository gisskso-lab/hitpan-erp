## 1. 배경 (Why)

### 1.1 사장님 확정 설계 — 3계층 세금계산서 (DESIGN_PRINCIPLES §7)

```
거래명세서 확정
    ↓
[계산서 발행] 버튼        ← 1계층 (이번 라운드 구현)
    ↓
[전자세금계산서 발행] 버튼  ← 2·3계층 (별도 라운드)
```

### 1.2 현재 상태 (코드 기준 4/25 확인)

- `TaxInvoicePage.razor` — UI는 있으나 **"계산서 발행" vs "전자세금계산서 발행" 버튼 의미 분리 부재**
- `SalesListDialog.razor` — "계산서 발행" 버튼이 실제로는 **거래명세서 확정**만 수행 (4/24 핸드오프 §75 알려진 이슈)
- 백엔드: `SalesController` / `SalesService`에 `invoice` 관련 엔드포인트·DTO **전혀 없음**
- DB: 별도 `tax_invoices` 테이블 미존재 (DB-16 마이그레이션은 전자세금계산서 영역만)

→ **1계층(내부 마킹) 인프라 자체가 없다.** 이번 작지서로 신설.

### 1.3 왜 1계층부터 — 사장님 결정

- 전자발행(자체 vs 외주)은 **별도 결정 사항**
- 1계층 = 사내 회계·세무 전 단계로 **거래 확정 → 계산서 마킹** 흐름 완결
- 베타 체험단 20곳 첫 사용 시점에 1계층까지 동작 = 핵심 셀링 포인트

## 2. 목표 산출물 (What)

### 2.1 DB (신규 테이블 1개 + 인덱스)
- `tax_invoices` 테이블 신설 (1계층 마킹용)
- 컬럼: id / tenant_id / delivery_id / invoice_no / issued_at / issued_by / amount_total / vat_total / status (`issued`/`canceled`) / etax_status (`pending`/`issued`/`failed` — 2계층 연결용 placeholder) / etax_issued_at / created_at / updated_at
- ENGINE=InnoDB, utf8mb4_unicode_ci
- 인덱스: tenant_id+issued_at / delivery_id (UNIQUE) / invoice_no (UNIQUE)
- FK: delivery_id → deliveries.id

### 2.2 백엔드 (Contract-First — 옵션 C 첫 적용)

신규 프로젝트 또는 임시 폴더에 DTO 배치:
- `HitPan.Contracts/Sales/IssueTaxInvoiceRequest.cs` (Idempotency-Key 헤더 수신)
- `HitPan.Contracts/Sales/TaxInvoiceResponse.cs`
- `HitPan.Contracts/Sales/CancelTaxInvoiceRequest.cs`

> ⚠️ **`HitPan.Contracts` 프로젝트 신설 자체가 첫 번째 작업.** 마커스 리(DevOps)와 상의해 솔루션 구조 정리.

신규 엔드포인트:
- `POST /api/sales/tax-invoices` — 계산서 발행 (Idempotency-Key 필수)
- `GET /api/sales/tax-invoices/{id}` — 단건 조회
- `GET /api/sales/tax-invoices?from=&to=&partnerId=` — 목록
- `POST /api/sales/tax-invoices/{id}/cancel` — 취소 (역분개 동반)

서비스:
- `TaxInvoiceService.IssueAsync(deliveryId, idempotencyKey)` — UoW로 다음 처리:
  1. delivery 상태 검증 (`confirmed` 만 가능)
  2. `tax_invoices` INSERT
  3. `delivery.tax_invoice_id` 갱신 (역참조)
  4. 자동 분개 호출 (`AutoJournalHelper`)
  5. 멱등키 충돌 시 기존 결과 반환

## 6. 구현 가이드

### 6.1 DB

```sql
-- DB-17 발췌 (전체는 마이그레이션 파일에)
CREATE TABLE IF NOT EXISTS tax_invoices (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id BIGINT UNSIGNED NOT NULL,
  delivery_id BIGINT UNSIGNED NOT NULL,
  invoice_no VARCHAR(32) NOT NULL,
  issued_at DATETIME NOT NULL,
  issued_by BIGINT UNSIGNED NOT NULL,
  amount_total DECIMAL(18,2) NOT NULL,
  vat_total DECIMAL(18,2) NOT NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'issued',
  etax_status VARCHAR(16) NOT NULL DEFAULT 'pending',
  etax_issued_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tax_invoices_delivery (delivery_id),
  UNIQUE KEY uk_tax_invoices_invoice_no (tenant_id, invoice_no),
  KEY idx_tax_invoices_tenant_issued (tenant_id, issued_at),
  CONSTRAINT fk_tax_invoices_delivery FOREIGN KEY (delivery_id) REFERENCES deliveries(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

> §절대원칙 #13: DESCRIBE deliveries 먼저 확인 후 FK 작성.
> §절대원칙 #17: ENGINE=InnoDB 명시 ✅
> §절대원칙 #3: 원장 INSERT ONLY는 journal_lines/stock_ledger — tax_invoices는 status 변경 가능 (issued/canceled)

### 6.2 백엔드 (Contract-First 첫 적용)

- `HitPan.Contracts` 프로젝트 신설 (마커스 리와 솔루션 구조 협의 후 진행)
- DTO는 record로 작성 (immutable)
- `IssueAsync`는 EF+Dapper UoW 사용 (브라운킴 PoC 결과 적용 예정 — PoC 완료 전이면 명시적 트랜잭션 fallback)
- 멱등키 처리:
  - Header `Idempotency-Key` 수신
  - `idempotency_keys` 테이블(P0-4에서 신설)에 키 + 결과 캐시
  - 24h TTL
- `AutoJournalHelper`로 자동 분개 (매출/부가세 분리 — 베티 박 검증)

### 6.3 프론트

- `TaxInvoicePage.razor`:
  - 3개 버튼 시각 분리 (DESIGN_PRINCIPLES §7 명명 규약)
  - 1계층 버튼만 활성, 2·3계층은 disabled + 툴팁
- `SalesListDialog.razor`:

  - 발행 결과 Snackbar에 발행번호 표시

### 6.4 보안

- §절대원칙 #2: tenant_id JWT 클레임에서만
- 발행 권한: `sales.tax-invoice.issue` 정책 (Authorization Policy)
- 취소 권한: `sales.tax-invoice.cancel` (어드민·경리만)
- 감사 로그: 발행·취소 시 `audit_logs`에 user_id+action+before/after

### 6.5 테스트·검증

- 단위: `TaxInvoiceService.IssueAsync` — 정상 / 중복 / 미확정 delivery / 멱등키 재요청 / 권한 미보유
- 통합: API → DB → 분개 흐름 (BK 검증)
- 회귀: 기존 거래명세서 확정 흐름 깨지지 않음

## 7. EVF 검증 계획

| 영역 | 검증 시나리오 | 책임자 | 통과 기준 |
|---|---|---|---|
| ④ 혼돈 | 같은 delivery에 발행 버튼 100회 동시 클릭 → invoice 1건만 생성 | DV-D | 멱등키 작동 / `uk_tax_invoices_delivery` 유니크 보장 / journal_lines 1쌍만 |
| ⑤ 무지 | 신입 경리 5명 무설명 → "계산서 발행" vs "전자세금계산서" 버튼 의미 혼동률 < 20% | ERP | 무지 테스트 통과 |
| ② 장애 | 발행 중 DB 끊김 → 트랜잭션 롤백, invoice 미생성, 분개 미반영 | BK | UoW 트랜잭션 정합성 |

> ① 부하 / ③ 악의 / ⑥ 노후는 영향 적음 — 일반 회귀 테스트로 갈음.
