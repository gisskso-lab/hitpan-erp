## 1. 배경 (Why)

결재 #11·#12 사장님 일괄 승인 (2026-05-13):
- 임계치: 1분 100건(Warning) + 1시간 1000건(Critical)
- 발행 시점: Critical 즉시 / Warning 즉시 / 일/주/월 배치
- 채널: SMS·이메일·Slack·대시보드·보고서 PDF

W3 sensitive_access_log 적재 → W5 알람 발행. 베타 출시(7/15) 전 작동 필수.

## 2. 목표 산출물

### 서비스
- `AlertThresholdEvaluator` — sensitive_access_log 조회 + 임계치 비교
- `AlertDispatcher` — 5채널 통합 발송 (SMS/Email/Slack/Dashboard/PDF)
- `AlertScheduler` — 일/주/월 배치 (Quartz.NET 또는 Hosted Service)

### 5 채널 구현
| 채널 | 라이브러리 | 비고 |
|---|---|---|
| Critical 즉시 SMS | 알리고/네이버 클라우드 SENS | 본사 1개월 비용 ~50만원 (Phase 2) |
| Warning 즉시 Email | 기존 SmtpClient | 즉시 도입 |
| Slack | Webhook | 즉시 도입 |
| 일/주 대시보드 | 백오피스 SignalR | W4 백오피스 의존 |
| 월 PDF | QuestPDF | 기존 활용 |

### DB
- `alert_history` 신규 (id, tenant_id, alert_type, channel, recipient, sent_at, status)
- `alert_recipient` 신규 (tenant_id, role, channel, address, active)

### API
- `GET /api/audit/alerts` (tenant_admin)
- `POST /api/audit/alerts/{id}/acknowledge`
- `PUT /api/audit/alert-recipients`

### 테스트
- 단위 5 + 통합 5 = 10 케이스

## 6. 구현 가이드

### 6.1 DB
- `alert_history` RANGE(YEAR) 파티션 5년 (결재 #7 일관)
- INSERT ONLY (헌법 #3) — UPDATE는 status 1컬럼만 허용

### 6.2 백엔드
- AlertThresholdEvaluator는 Hosted Service 1분 주기 polling (Phase 2 → SignalR push)
- 채널 발송 실패 시 재시도 3회 + dead letter queue
- 본사 ↔ 고객사 알림 분리 (헌법 #18 v3)

### 6.3 프론트
- 백오피스 대시보드 위젯 (W4 의존)
- 알림 수신자 관리 화면 (tenant_admin)

### 6.4 보안
- SMS 수신자 전화번호 → AES-256 암호화 (`alert_recipient.address_encrypted` VARBINARY)
- 약관 동의 항목 추가: "보안 알림 SMS 수신 동의" (법무팀장 검토)
- 첫 로그인 약관 동의 미체크 시 SMS 채널 비활성화

### 6.5 테스트
- 임계치 트리거 시뮬레이션 (1분 101건 → Warning 발송)
- 5채널 동시 발송 멱등성
- 약관 미동의 시 SMS 차단
