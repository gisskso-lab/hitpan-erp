## 1. 작업 사이클 (사장님 확정 2026-07-28 / 2026-08-28 개정 — [1]~[7] + [★])

> ### 🔴 2026-08-28 개정 (사장님 오더) — **검증 - 설계 - 개발 - 검증(동시)**
> **맨 앞에 검증을 다시 넣는다. 설계보다 검증이 먼저다.**
> 이유: 8/27 작7→작8 사고. 게이트 9건이 **전부 통과하고도 반려**났다.
> 게이트가 잰 건 *"서버가 만드는가"* 였고 **그건 사실**이었는데, 화면은 받지도 보여주지도 않았다.
> **틀린 전제 위에 설계문서를 쓰면 그 아래가 전부 틀린다.** 그래서 설계 앞에 검증을 세운다.

```
[1] 사장 오더
      ↓
[1-V] 🔴 선행검증 — 검증팀장 데이비드 박          ⭐2026-08-28 신설
    · 오더에 깔린 **전제가 사실인지 실측**으로 확인
    · "이미 되어 있다" 도 반증한다 — 되어 있다는 말은 근거가 아니다
    · 전제가 깨지면 → [1] 사장님께 되묻는다. 설계 착수 금지
    · 선행검증서 작성                  → 📄 검증/선행/
      ↓  ⛔ 전제 미확인 상태로 설계 금지
[2] 설계팀 — 설계팀장 존
    · 설계문서 작성                    → 📄 설계/{영역}/
    · 작업지시서(PRD) 작성             → 📄 운영기록/
    · → 개발팀에 넘김
    · → PM 결재 OR 반려                → 📄 운영기록/ (결재의견)
      ↓  ⛔ 결재 없으면 코드 금지
[3] 개발팀 — PM(개발팀장) 지휘        ⟷  [3-V] 동시 병렬검증 — 안철수 상무
    · 역할분배 (매니저·서브에이전트)        · 작업과 **동시**에 실시간 반증
    · 코딩                                   · 적발 즉시 반려·재작업
    · 개발명세서 작성                  → 📄 개발/{영역}/
                                            → 📄 검증/병렬이슈/  ⭐별도 폴더
      ↓
[4] 검증팀 — 검증팀장 데이비드 박            🔴개발과 **동시 착수** (2026-08-28)
    · 개발명세서 검토 + 코드리뷰
    · 최종 결재 OR 반려
    · 작업리뷰서 작성                  → 📄 검증/{영역}/
    · 🔴 [3] 이 끝나기를 기다리지 않는다 — 코드가 나오는 대로 붙는다
      ↓
[5] 최종 결재
    · CTO 래리 결재                    → 📄 운영기록/ (CTO 결재의견)
    · 사장님 최종 결재                 → 📄 (작업지시서에 결재 상태 기록)
      ↓
[6] 🔴 커밋 — 무조건                   ← 사장님 결재 = 커밋 트리거
    · 사장님 결재 + [4] 검증 완료 건은 **예외 없이 커밋**
    · 미커밋으로 남기지 않는다
      ↓
[7] 일일작업보고서 (하루 끝)           → 📄 운영기록/  ← 사장님이 "오늘 뭐했나" 보시는 문서
      ↓
[★] 인수인계서                         → 📄 운영기록/  ← 세션·컨텍스트 만료 전 필수
```

> ## ⭐ [7]과 [★]은 **언제 참조하느냐**로 갈린다 (사장님 정의 2026-07-28)
>
> | 문서 | 언제 참조하나 | 무엇이 들었나 |
> |---|---|---|
> | **[★] 인수인계서** | **세션이 끝나 새 창을 열 때** (같은 날, 이어서) | 지금 상태·함정·다음 첫 행동 |
> | **[7] 일일작업보고서** | **다음날 컴퓨터 켜고 새 창 열 때** | 어제 이슈·작업·수정 내용 |
>
> **인수인계서 = 세션 단위 이어받기 / 일일작업보고서 = 날짜 단위 이어받기.**
> 하루에 세션을 3번 열면 인수인계서는 3번 쓰고, 일일작업보고서는 1번 쓴다.

### 🔴 [6] 커밋 규칙 (사장님 확정 2026-07-28)

> **"최종 내가 결재하고, 작업·검증 완료된 건에 대해선 무조건 커밋!!!!"**

| 조건 | 커밋 |
|---|---|
| [5] 사장님 결재 ✅ + [4] 검증 통과 ✅ | **무조건 커밋** |
| 검증 미통과 / 사장님 결재 전 | 커밋 안 함 — [3]·[4]로 되돌림 |

**왜**: 결재·검증까지 끝난 작업이 워킹트리에 남아 있으면 다음 세션이 그 상태를 모른다.
"어제 됐는데?" 사고의 원인이고, 여러 세션이 겹치면 유실된다.

**커밋에 남길 것** (참조식 — 문서 주소만):
```
{타입}({영역}): {한 줄}

작업지시서: docs/운영기록/{파일}
개발명세서: docs/개발/{영역}/{파일}
작업리뷰서: docs/검증/{영역}/{파일}  판정 ✅통과
병렬이슈:  docs/검증/병렬이슈/{파일}  ✅봉합완료
결재: PM {날짜} → 검증팀 {날짜} → CTO {날짜} → 사장님 {날짜}
```

**세션 종료 시 `git status --porcelain --untracked-files=no` 가 0이어야 한다.**
0이 아니면 → 결재 안 난 작업이 남았거나, [6]을 빼먹은 것이다.

**각 단계에 📄가 붙어 있다 = 그 단계는 문서를 남긴다.**
문서가 없으면 그 단계는 **하지 않은 것**이다. (헌법 #42)

| 단계 | 누가 | 무엇 |
|---|---|---|
| **[1-V] 선행검증** | **검증팀장 데이비드 박** | 🔴 오더의 **전제 실측**. 깨지면 설계 착수 금지 — 사장님께 되물음 |
| [2] 작성 | **설계팀장 존** | 설계문서 + 작업지시서(PRD) |
| [2] 결재 | **PM 브라운킴** | 결재 OR 반려 — 작성자와 다른 사람(SoD) |
| [3] 지휘 | **PM(개발팀장)** | 역할분배·코딩·개발명세서 |
| [3-V] 병렬검증 | **안철수 상무** | 작업과 동시에 반증. 이슈는 `검증/병렬이슈/` 별도 관리 |
| [4] 검증 | **검증팀장 데이비드 박** | 개발명세서 + 코드리뷰 → 작업리뷰서. 🔴**[3] 과 동시 착수** |
| [5] 최종 | **CTO 래리 → 사장님** | 팀 최종 결재권은 임원이 갖는다 |

## 4. 세션 루틴

### 세션 시작 — **두 갈래** (사장님 정의)

**A. 같은 날 이어서 (세션만 끝나서 새 창)**
```
1. docs/START_HERE.md                  ← 지형 파악
2. §0-1 🟢진실원 인수인계서 1개         ← 지금 상태·함정·다음 첫 행동
3. 인수인계서 §9 "다음 세션 첫 행동" 대로 시작
```

**B. 다음날 (컴퓨터 켜고 새 창)**
```
1. docs/START_HERE.md                  ← 지형 파악
2. 어제 일일작업보고서                  ← 어제 뭐 했나·이슈·결재 대기
3. 그다음 인수인계서                    ← 마지막 세션 상태·다음 행동
```

> **왜 다른가**: 같은 날은 맥락이 이어져 인수인계서만으로 충분하다.
> 다음날은 하루가 통째로 비었으니 **어제 전체를 먼저 봐야** 한다.

### 작업 중
```
· 코드 고치기 전 → START_HERE §2 판단 트리거에서 헌법 확인
· 🚨 #29·#33·#37·#39·#40 에 걸리면 → 원문 필독 (요약 신뢰 금지)
· 문서 만들기 전 → CATEGORIES.md 판정 + 저장 위치 결재
· 에이전트 띄우기 전 → 헌법/AI협업_토큰절약_에이전트투입_매뉴얼.md §0 카드 · §4-1 판정 트리
```

### 세션 끝 (컨텍스트 만료 전)
```
1. 🔴 결재·검증 완료 건 전부 커밋 ([6] — 무조건)
2. 일일작업보고서 작성 ([7] — 사장님이 "오늘 뭐했나" 보시는 문서)
3. 인수인계서 작성 ([★] — 다음 세션 AI 가 이어받는 문서)
4. START_HERE §0-1 진실원 주소 갱신
5. 운영기록 INDEX 🟢진실원 절 갱신 + 옛 문서 ⬛흡수
6. git status --porcelain --untracked-files=no | wc -l  →  0 이어야 함
```

## 6. 이 원칙을 어겼을 때

| 상황 | 조치 |
|---|---|
| 문서 없이 코드부터 나옴 | **즉시 중단.** [2] 작업지시서(PRD)부터 만든다 |
| PM 결재 없이 코딩 시작 | **즉시 중단.** [2] 결재 벽을 우회한 것 |
| "대화에서 합의했으니 됐다" | 대화는 근거가 아니다. 문서로 남긴다 (헌법 #42) |
| "급하니까 나중에 문서" | 그게 두더지잡기의 시작이다 (헌법 #39 사고 원인) |
| **선행검증 없이 설계 착수** | 🔴 **즉시 중단.** [1-V] 로 돌아간다. 전제가 틀리면 그 아래 전부 틀린다 |
| **[4] 검증을 개발 끝난 뒤로 미룸** | [4]는 **동시**다. 끝나고 하면 이미 쌓인 위에서 찾게 된다 |
| 병렬검증을 작업 후로 미룸 | [3-V]는 **동시**다. 끝나고 하면 거짓봉합을 못 잡는다 |

| 세션 끝났는데 미커밋 남음 | 결재 안 난 작업이거나 [6] 누락. 둘 중 뭔지 확인하고 처리 |

## 7. 🔴 동시 세션 — 한 작업 트리를 두 창이 쓸 때 (2026-10-26 실측 사고 반영)

> **루틴 [1]~[7] 은 바뀌지 않는다.** 아래는 **같은 폴더를 두 창이 동시에 쓸 때만** 더 붙는 규율이다.
> 근거: 2026-10-26 ERP 작1(양식지·워터마크) 창과 외부검증 도입 창이 **같은 작업 트리**를 썼고 **실제로 섞였다.**

### 7-1 무엇이 터졌나 (실측)

작1 창이 인수인계서를 커밋(`a191d321`)할 때 **다른 창이 `docs/운영기록/INDEX.md` 에 적어 둔 한 줄이 그 커밋에 함께 들어갔다.**
파일 단위로 `add` 했기 때문이다. 그 결과 **HEAD 에 깨진 링크 1건**(아직 untracked 인 파일을 INDEX 가 가리킴)이 남았다.

🔴 **커밋을 피하는 것만으로는 부족하다. 쓰기(파일 생성·편집)만으로도 남의 커밋에 섞인다.**

### 7-2 규율 — 다음부터 이렇게 한다

| # | 규율 | 까닭 |
|---|---|---|
| 1 | **세션 시작 때 직전 창이 살아 있나부터 본다** — 살아 있으면 **머지·게시 금지** | 10/6 두 창이 동시에 머지·게시한 사고 |
| 2 | 🔴 **공용 파일(`INDEX.md`·`START_HERE.md`)은 그 창이 끝난 뒤에 적는다** | 7-1. 양쪽이 같은 파일을 고치면 먼저 커밋한 창이 삼킨다 |
| 3 | 🔴 **`git add` 는 경로를 하나하나 적고, `git diff --cached` 로 남의 변경이 섞였나 본다** | 레포 루트 `git add -A` 금지(10/7 2,473개 사고)와 한 몸 |
| 4 | 🔴 **남의 커밋을 고쳐 바로잡지 않는다** — `amend`·`rebase`·`reset` 금지 | 다른 세션이 그 브랜치를 쓰고 있다. **자기 몫을 커밋하면 깨진 링크는 저절로 성립한다** |
| 5 | **계열이 둘이면 진실원도 둘** — 문서 머리에 *"이 문서는 어느 계열의 진실원인가"* 를 적고 **섞지 않는다** | 10/26 ERP 작업 계열 ↔ 외부검증 계열 |
| 6 | **`git worktree add` 로 피하려 하지 않는다** | worktree 가 쌓여 9/29 에 `C:` 디스크가 모자라 업데이트가 막혔다 |
| 7 | **한쪽 창이 게시(배포)를 하면 끝난 사실을 상대 창에 넘긴다** | 상대 창의 다음 첫 행동이 「게시 종료 확인」일 수 있다 |
| 8 | 🔴 **공용 INDEX 를 줄 번호로 고치지 않는다**(`awk NR==N`·`sed '332d'` 금지) — **앵커 문자열**로 고치고 **고치기 직전에 다시 읽는다** | 2026-10-26 실측: 한 창이 331행을 읽고 332행을 지웠는데 그 사이 다른 창이 같은 구역을 고쳤다 ⇒ **어느 줄이 지워졌는지 아무도 구별할 수 없었다** |
| 9 | 🔴 **게시(dispatch) 전에 상대 창에 먼저 말한다** | 2026-10-26: 같은 입력으로 **14초 차이**로 게시 런이 **두 개** 떴다(하나 취소). 10/12 묵은 승인대기 런 사고와 같은 입구 |
