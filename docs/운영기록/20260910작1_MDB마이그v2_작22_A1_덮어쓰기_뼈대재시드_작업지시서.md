## 0. 왜 이 작업인가 (한 줄)

**「모두 지우고 새로 가져오기」를 누르면 히트판이 갓 설치한 상태로 돌아간 뒤 레거시를 다시 읽어야 한다.** 그런데 지금의 초기화는 회사 뼈대까지 지우고 **되살리는 코드가 한 줄도 없다** — 그래서 덮어쓰기를 못 열고 있었다. 사장님이 *"넣어"* 로 뼈대 재시드를 허락하셨으므로 이제 연다.

---

## 1. 무엇이 지워지고, 무엇을 다시 까는가 (실측 근거)

초기화(`DataResetService`)는 **보존 화이트리스트(6/23 사장님 결재) 밖의 모든 표**를 테넌트 범위로 비운다. 부모계정(`users`)·회사정보·로그는 보존되지만, 신규 설치 때 `CompanyBootstrapProvisioner.CreateParentAsync` 가 **같은 트랜잭션에서 깔아 주던 5종은 전부 지워진다.**

| 지워지는 뼈대 | 몇 개 | 없으면 무슨 일이 나나 |
|---|---|---|
| `accounts` 표준 계정과목 | **27** | 이관 뒤 첫 판매확정·수금·경비·급여가 **기표되지 못한다** — `journal_lines → accounts` FK(`fk_jl_account`) 로 죽는다 |
| `employees` 대표 사원 1행 | **1** | 대표가 사원관리·직원현황에서 사라지고 **결재선에서 못 고른다** |
| `positions` 기본 직급 | **6** | 대표 사원의 직급 「대표이사」가 **마스터에 없는 값**이 된다(직급으로 짜는 결재선이 깨진다) |
| `labor_policy_settings` 근로 기준값 | **16** | 연차가 15일이 아니라 **0일**로 나오고 휴직은 *"기준이 정해져 있지 않습니다"* 만 뜬다 |
| `warehouses` 기본창고 MAIN | **1** | 창고를 안 쓰는 다수 경로(상품마스터 「미지정」)가 착지할 자리가 없다 |

> 🔴 **뼈대의 정의 = 새로 만들지 않는다.** `CompanyBootstrapProvisioner` 가 **신규 설치 때 까는 그 5종 그대로**다. 목록·값·이름을 하나도 새로 고안하지 않는다. 사장님 결재 문언은 *"표준 계정과목과 대표 사원 자리"* 였고, 직급·근로기준값·기본창고는 **그 둘이 실제로 동작하기 위한 같은 트랜잭션의 나머지**다(직급이 없으면 대표의 직급이 허공을 가리키고, 계정과목만 있고 사원이 없으면 기표 주체가 없다).
>
> 🔴 **보존 목록(6/23 결재)은 한 글자도 안 바꾼다.** 초기화가 무엇을 지우는지는 그대로 두고, **지운 뒤에 다시 까는 단계만 뒤에 붙인다**(헌법 #1 추가만).

## 2. 순서 (별지 §1-1 — 설계 대비 1건 정정)

```
[모드=덮어쓰기]  대표계정 비번 + 확인문구 "덮어쓰기"  (MainPcOnly · TenantAdminOnly)
   → ①②  IDataResetService.ResetAllAsync(...)        ← 비번확인·강제백업·삭제·감사기록을 이미 한 몸으로 한다
   → ③   뼈대 재시드  CompanyBootstrapProvisioner.ReseedCompanySkeletonAsync(tenantId)
   → ④   잡 생성      MigrationJobStore.CreateAsync    ← 반드시 ② 뒤 (migration_jobs 도 초기화 대상)
   → ⑤   이관(1단계 → 다이얼로그 → 2단계) → ⑥ 대사표
```

> **설계 정정 1건 (PM 전결)**: 별지 §1-1 은 ① 백업을 **따로** 부르라고 했으나, `ResetAllAsync` 가 **이미 내부에서 강제 백업(`before_data_reset`)을 돌리고 실패 시 중단**한다(실측 `DataResetService.cs:95-107`). 따로 부르면 **백업이 두 번** 돌아 큰 DB 에서 시간만 두 배가 된다. ⇒ **`ResetAllAsync` 하나로 ①②를 대신한다.** 백업 없이 지우는 일은 없으므로 안전 요건은 그대로다.

## 3. 만들 것 (추가만 · 신설 표 0 · DDL 0)

### 3-1. `CompanyBootstrapProvisioner` — 메서드 경계만 세운다 (헌법 #1)

`CreateParentAsync` 안의 시드 블록 5개를 **본문을 옮기지 않고** 메서드로 잘라낸다. 잘라낸 뒤 `CreateParentAsync` 는 그 메서드들을 순서대로 부른다 — **결과가 종전과 한 글자도 달라지면 안 된다.**

| 새 메서드 | 무엇 | 멱등 |
|---|---|---|
| `SeedOwnerEmployeeAsync` | 대표 사원 1행(`emp_no '0001'` · `position` = 대표이사 · `user_id` = 부모계정) | `NOT EXISTS` 추가 |
| `SeedDefaultWarehouseAsync` | MAIN 기본창고 | 이미 `NOT EXISTS` |
| `SeedStandardPositionsAsync` | 직급 6 | 이미 `NOT EXISTS` |
| `SeedLaborPolicyAsync` | 근로 기준값 16 | 이미 `NOT EXISTS` |
| `SeedStandardAccountsAsync` | 표준 계정과목 27 | 이미 `NOT EXISTS` |

### 3-2. `ReseedCompanySkeletonAsync(tenantId, ct)` — 재시드 진입점 (신설)

- 자기 커넥션을 열고 **한 트랜잭션**으로 위 5개를 순서대로 실행한다.
- 대표 사원은 **부모계정(`users.is_parent=1 AND is_deleted=0`)에서 이름·아이디를 읽어** 만든다. 부모계정이 없으면 사원만 건너뛰고 나머지는 깐다(초기화는 부모계정을 보존하므로 정상 경로에선 항상 있다).
- **되살리는 것이지 덮어쓰는 게 아니다** — 전부 `NOT EXISTS`. 이미 있으면 손대지 않는다(대표가 고친 값을 우리가 되돌리지 않는다 · `SeedDeviceSlotPolicyAsync` 주석의 원칙과 같다).

### 3-3. 두 경로가 **같은 재시드**를 탄다

| 경로 | 어디 | 무엇 |
|---|---|---|
| 초기화 화면 | `DataResetController.ResetAll` | `ResetAllAsync` 성공 뒤 `ReseedCompanySkeletonAsync` 호출 |
| 덮어쓰기 가져오기 | `MigrationController` 덮어쓰기 분기 | 같은 메서드 호출 |

> 🔴 **두 경로가 갈리면 그게 다음 사고다.** 초기화만 고치고 덮어쓰기를 안 고치거나 그 반대면, *"한쪽 사고는 반대쪽에 같은 코드가 있는지 그 자리에서 확인"* 을 또 어긴 것이다(작21·작15 재발 계통).

### 3-4. `MigrationController` — 덮어쓰기 분기 열기

- `RejectUnsupportedMode` 의 **덮어쓰기 400 을 없앤다**(잘못된 모드값 400 은 남긴다).
- 덮어쓰기는 **`/start` 에서만** 받는다. 동기 `POST legacy-mdb` 와 `continue` 는 **병합만** — `continue` 는 이미 지운 뒤 이어받는 것이라 또 지우면 1단계 결과가 날아간다.
- 확인 2단: `Password`(대표계정 비번 — `ResetAllAsync` 가 검증) + `ConfirmText` 가 **"덮어쓰기"** 와 일치. 불일치면 400, 문구는 개발용어 0.
- 실패 시 잡을 만들지 않는다(초기화가 실패했는데 잡만 남으면 화면이 헷갈린다).

### 3-5. 화면 (`MdbMigration.razor`) — 방식 선택 열기

- 방식 선택 2개: **「기존 자료는 두고 없는 것만 보태기」**(기본) / **「기존 자료를 모두 지우고 새로 가져오기」**.
- 덮어쓰기를 고르면 경고 + 대표계정 비번 + 확인문구 **"덮어쓰기"** 입력칸(초기화 화면과 같은 2단 확인).
- 경고문에 **지워질 건수**를 보여준다: 히트판에서 직접 입력한 거래 N건(`source_type <> 'migration'` 인 명세서·매입·수금·지급 합). 미리보기 응답에 실어 보낸다.
- ⚠️ 개발용어 0 — 「초기화」·「마이그레이션」·「덮어쓰기 모드」 같은 말 대신 위 문안 그대로.

## 4. 게이트 (글자검사 금지 · 봉합 빼고 FAIL 먼저 본다)

| ID | 무엇을 재나 | 어디서 |
|---|---|---|
| **G-OW1** | 덮어쓰기 뒤 `accounts` 27 · `employees` 대표 1 · `positions` 6 · `labor_policy_settings` 16 · `warehouses` MAIN 1 이 **다시 있다** | e2e (실 DB) |
| **G-OW2** | 재시드는 **멱등** — 두 번 불러도 행수가 안 늘고, 사람이 고친 값(계정과목 이름 등)을 **되돌리지 않는다** | e2e |
| **G-OW3** | 덮어쓰기 이관 뒤 **첫 판매확정·수금이 기표된다**(`journal_lines` FK 1452 가 안 난다) — 뼈대 재시드의 존재 이유 그 자체 | e2e |
| **G-OW4** | 재시드를 **빼면** G-OW1·G-OW3 이 **FAIL 한다**(무력화 시험 · 대조군) | e2e |
| **G-OW5** | 확인문구 불일치·비번 불일치면 **아무것도 지워지지 않는다**(행수 불변) | e2e |
| **G-OW6** | `continue`·동기 `legacy-mdb` 는 덮어쓰기를 **안 받는다**(400) | xUnit(리플렉션 아님 — 실제 분기 호출) |
| **G-OW7** | 초기화 화면 경로도 **같은 재시드**를 탄다(`DataResetController` 가 그 메서드를 부른다) | xUnit + e2e |

> 🔴 **G-OW4 가 이 판의 핵심 게이트다.** 나머지가 다 초록이어도 봉합을 뺐을 때 빨간불이 안 뜨면 그 게이트는 가짜다(누적 24번 반복된 사고).
