## 1. 🔴 즉시 봉합해야 하는 것 — 순서대로

### F-1 (P0) — 사고 내는 쪽이 안 꺼진다

```
미들웨어가 읽는 설정 : enforce_tenant_session_limit   (축 A)   ← SessionValidityMiddleware.cs:139
AuthService 가 읽는 설정 : enforce_single_pc_login     (축 B)   ← AuthService.cs:221
```

축 B 킬스위치가 **`AuthService` 안에만** 있다. **`SessionValidityMiddleware` 는 그 값을 안 읽는다.**
설계 §4-1 이 *"사고 나면 배포 없이 꺼야 한다"* 고 적어둔 것을 **절반만 만들었다.**

**연쇄 (⚠️ 실물 미재현 · 코드 독해)**:
DB-127 마이그 실패 → 세션 INSERT 실패를 `catch` 가 삼킴 → **로그인 200** →
그 토큰에 `sid` 가 있음 → 미들웨어가 「세션 없음」으로 읽어 **모든 `/api` 401** →
갱신도 `sid` 가 있어 `UPDATE 0행` → **영영 안 풀린다. 그리고 못 끈다.**
⇒ #30(고객 PC 자가 회복 · 본사 의존 0) 충돌.

**봉합 방향**: 미들웨어가 축 B 킬스위치를 읽게 하고, **세션 행이 아예 없을 때의 안전 폴백**을 정한다.
⚠️ 폴백을 "통과"로 두면 차단이 무력해지고, "차단"으로 두면 이 잠금이 남는다 — **선택이 필요하다**(§4 결재 C-1).

### F-5 / P1-3 (P1) — 모바일 로그아웃이 PC 를 끊는다

[`AuthController.cs:361`](../../src/HitPan.API/Controllers/AuthController.cs#L361)
```sql
DELETE FROM user_sessions WHERE user_id = @UserId     -- session_id 한정이 아니다
```
여태 표가 비어 있어 아무 일도 안 하던 줄이다. **이번에 행을 넣기 시작하면서 깨어났다.**
⇒ 모바일에서 로그아웃하면 **PC 도 10초 안에 끊긴다.** 9/25 결재 *"모바일 FREE · PC 와 동시 가능"* 위반.

🔴 **교훈**: 축 A 에 대해서는 *"안 돌던 게 깨어난다"* 를 경고해놓고, **바로 옆 줄에서 같은 일이 벌어지는 건 못 봤다.**
**표를 비어 있게 두던 코드를 살릴 때는 그 표를 읽는 곳·지우는 곳을 전수로 다시 본다.**

### F-2 (P0) — 게이트가 봉합을 안 잰다

시험이 운영 SQL 을 `const` 로 **복사해서** 제가 돌린다([`SessionRecordConcurrentPcGateTests.cs:54-66`](../../src/HitPan.Tests/Integrity/SessionRecordConcurrentPcGateTests.cs#L54-L66)).
운영 코드를 부르는 줄은 **`NormalizeDeviceKindForTests` 하나뿐**이다.

⇒ **`AuthService.cs:156` 의 `InsertSessionAsync` 호출을 지워도 8건 전부 초록이다.**
**이 트랙이 막으려던 「넣는 코드 0건」 재발을 이 게이트가 못 잡는다.**

🔴 **교훈**: 음성 대조군을 만들었지만 **스키마**를 쟀지 **배선**을 안 쟀다.
*"봉합을 빼면 실패하는가"* 의 **봉합이 무엇인지**를 잘못 잡으면 대조군도 거짓이 된다.

⇒ F-1·F-5 를 고쳐도 **이 게이트로는 고쳐졌는지 확인이 안 된다.** F-2 를 먼저 고쳐야 나머지를 믿을 수 있다.

## 2. 🔴 결재가 필요한 것 — PM 이 못 정한다

### C-1 (F-4 / P0-1) — 차단이 클라이언트 자진신고에 달렸다

축 B 발동 여부 **전체**가 클라이언트가 보내는 `DeviceType` 한 칸에 달려 있다
([`LoginRequest.cs:22`](../../src/HitPan.Application/DTOs/Auth/LoginRequest.cs#L22) → [`AuthService.cs:214`](../../src/HitPan.Application/Services/AuthService.cs#L214)).
`"mobile"` 한 글자면 차단이 통째로 안 걸린다. `/api/auth/login` 은 `[AllowAnonymous]` 다.

🔴 **PM(나)의 판단이 틀렸다.** 설계·DDL 에 *"수용한 구멍"* 이라 적으며 근거 3개를 댔는데 전부 깨졌다:

| PM 이 적은 근거 | 반증 |
|---|---|
| "모르는 것은 싼 칸" 원칙 | 그건 **과금 규칙**이지 **통제를 끄는 규칙**이 아니다 |
| ERP 웹은 항상 보낸다 | **공격자는 우리 화면을 안 쓴다** |
| 과금 축이 계정이라 매출 무관 | 🔴 **순환논증** — 「계정 5개 = PC 5대」를 강제하는 장치가 **바로 이 차단**이다 |

특히 DDL 주석에 *"UA 는 사용자가 바꿀 수 있어 위장하면 뚫린다"* 고 써놓고,
**UA 보다 더 쉽게 바꿀 수 있는 `DeviceType`** 을 근거로 삼았다.
게다가 게이트 `G-3b` 가 이 구멍을 **기대값으로 고정**한다 — 시험이 구멍을 지키고 있다.

⚠️ **다만 「고치면 된다」가 아니다.** 브라우저는 자기가 PC 임을 물리적으로 증명할 수단이 없다 —
메인PC 트랙(9/22~25)에서 이미 확인한 벽이다.
⇒ **「완전히 막는 길이 실재하는가」부터 따져야 한다.** 사장님 결재 사항.

🔴 **등급이 두 문서에서 다르다** — 같은 결함을 [4] 는 **P1(F-4)**, [3-V] 는 **P0(P0-1)** 으로 적었다.
PM 이 한쪽으로 통일하지 않는다(9/22 사장님 지적 — 등급을 PM 이 정하지 마라).
**베타 게이트를 막는 등급인지**가 이 결재의 일부다. 두 문서는 등급만 다르고 사실관계는 같다.

### C-2 — F-1 의 안전 폴백을 어느 쪽으로 둘 것인가

세션 행이 없을 때 **통과**(차단 무력) vs **차단**(잠금 위험). 고객이 겪는 사고 유형이 정반대다.

### C-3 — `device_kind` 기본값 (F-3)

작지 §3 **금지 #3** 은 *"기본값을 `'mobile'` 로 두지 마라 — 어기면 즉시 반려"* 였다.
**PM 이 결재 없이 뒤집었다.** 뒤집은 근거(「모르는 것은 싼 칸」)는 타당하나 **절차를 건너뛰었고**,
작지 그 줄과 설계 §3-1 을 안 고쳐 **문서 3개가 서로 다른 말을 한다.**

### C-4 — F-6 : 8시간 만료 틈으로 PC 2대 영구 공존

세션 만료 8시간(access) ↔ refresh 7일. 틈에 PC2 가 로그인하고 PC1 이 갱신하면 둘 다 산다.
