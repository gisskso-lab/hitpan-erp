## 1. 왜 이 작업을 하는가

### 1-1. 사장님 오더가 이것에 걸려 있다

> 사장님 (2026-08-07): *"워치독, 업데이트 종단이 구현되면 그 후부터 수정·보완작업이 쉬워질거야.
> 재설치 없이 **코드수정 → 업데이트 → 실측** 이 세 단계만 하면 되거든."*

**지금은 그 3단계가 성립하지 않는다.** 실제로는:
```
코드수정 → 게시 → [최대 24시간 대기] → 실측
```

2026-08-07 백지환경 실측에서 사장님이 `sc stop/start` 를 직접 치셔야 1.2.55 가 잡혔다.

### 1-2. 고객 쪽 영향

고객 PC 에는 재시작할 사람이 없다. 새 버전을 **최대 24시간** 못 받는다.
그동안 히트판은 **정상으로 보인다** — 고객도 본사도 모른다.

### 1-3. "재시작하면 풀린다"는 우연이다 (설계팀 §1-3)

같은 파일 `Worker.cs:110-113` 은 인메모리 소실을 **결함으로 보고** 복원 코드를 넣었는데,
`_lastUpdateCheckDate` 에는 그 인식이 적용되지 않았다.

> ⚠️ 이대로 두면 CS 매뉴얼에 *"서비스를 재시작해 보세요"* 가 들어가

## 4. 구현 지시

### 4-1. 게이트를 날짜 → 시각 기반으로 바꾼다

**현행** (`:325-327`)
```csharp
var today = DateOnly.FromDateTime(DateTime.Now);
if (_lastUpdateCheckDate == today)
    return;
```

**변경 방향**
- 판정 기준을 **"오늘 이미 했나"** 에서 **"마지막 확인 후 N시간이 지났나"** 로 바꾼다
- N 기본값 **1시간**. `appsettings.json` 으로 조정 가능하게 하되 **코드에 상·하한**을 둔다
  - 하한 근거: 너무 짧으면 본사 서버 부하. 설계서 §7 부하 산정 참조
  - 상한 근거: **N > 1h 이면 야간 창(3시대 1시간)을 통째로 건너뛸 수 있다** (결재-3)

### 4-2. 마지막 확인 시각을 파일에 남긴다

**목적을 정확히 이해할 것 (설계서 §5)**
> **영속화의 목적은 "게이트 유지"가 아니라 "재시작 폭주 상한"이다.**

- 재시작해도 **직전 확인 시각을 알 수 있어야** 한다
- 크래시 루프에 빠진 PC 가 재시작할 때마다 본사를 두드리는 것을 막는다
- **단, 게이트를 24시간 유지하라는 뜻이 아니다.** N시간이 지났으면 재시작 여부와 무관하게 확인한다

**저장 위치** (결재-2 — 파일, DB 아님)
- 기존 관례를 따른다: `UpdateLockFile.cs:51-60` 이 `{app}\update.lock` 을 쓰는 방식 참조
  (`AppContext.BaseDirectory` 기준 `..` 로 올라가 `{app}` 을 잡는다)
- **DB 를 쓰지 않는 이유**: DB 가 죽었을 때야말로 업데이트가 필요할 수 있다.
  또한 개발팀 코드리뷰서 P1-3(DB 비밀번호 명령줄 노출)의 노출면을 늘리지 않는다

**파일 손상 대비**
- 읽기 실패·파싱 실패 시 **"확인한 적 없음"으로 간주**하고 즉시 확인한다.
  안전측은 "덜 확인"이 아니라 "더 확인"이다
- 쓰기 실패는 **업데이트를 막지 않는다.** 로그만 남긴다(헌법 #15)

### 4-3. 🔴 건너뛸 때 로그를 남긴다 (설계팀 합격조건 G-2)

**이번 사고의 진짜 원인은 침묵이다.**
`:326` 이 아무것도 안 남겨서, 로그 500건을 뒤져도 무슨 일이 있었는지 알 수 없었다.

- 건너뛸 때 **어떤 수준으로든** 기록을 남긴다
- 다만 60초 루프이므로 매번 남기면 로그가 오염된다 — **빈도 조절**을 함께 설계한다
  (예: 처음 한 번만 / 일정 간격마다 / Debug 수준)
- 판단은 구현팀에 맡기되, **"다음에 같은 일이 나면 로그로 알 수 있는가"** 를 기준으로 한다

### 4-4. 기존 해제 지점 3곳은 존치한다 (결재-4 · 헌법 #1)

| 위치 | 무엇 | 처리 |
|---|---|---|
| `:119` | 기동 시 Major 펜딩 발견 → 게이트 개방 | **존치** + 주석 갱신 |
| `:306` | Major 펜딩 해소 → 게이트 해제 (`4cc5842`) | **존치** + 주석 갱신 |
| `:389` | 평가 중 예외 → 게이트 개방 | **존치** + 주석 갱신 |

**주석 갱신 이유**: 세 곳 모두 *"하루 게이트"* 라는 표현을 쓴다.
N시간 게이트로 바뀌면 그 표현이 사실과 달라진다. **주석이 거짓말하면 다음 사람이 오판한다.**

⚠️ **지우지 말 것.** 헌법 #1 — 수정은 OK, 덮어쓰기 금지.

## 6. 🔴 반드시 문서에 남길 것 — W4-6 계수 전제 무효화 (결재-5)

**이 절을 빠뜨리면 `4cc5842` 와 똑같은 반쪽 봉합이 된다.**

`Worker.cs:483-508` `TrackUpdateStallAsync` 는 **"조회를 하루 1번만 한다"** 는 전제 위에 있다.

주기가 바뀌면:
- 카운터 폭주는 **없다** (`:496` 날짜 중복방지가 살아 있음)
- 7일 임계도 **그대로 유효**
- **그러나** `:485-492` 가 **1회만 성공하면 즉시 리셋**한다

> ⚠️ **하루 23시간 feed 가 죽고 1시간만 살아나는 간헐 장애**에서는
> 실제로 옛 버전에 고정되면서도 **카운터가 영원히 0** 이 된다. 7일 경보가 안 울린다.

**이것은 4안이 만드는 결함이 아니라, 4안이 드러내는 기존 전제 붕괴다.**
즉시 터지지 않으므로 이번 범위에서 제외하되,
**개발명세서에 이 사실을 명시하고 후속 과제로 등록**한다.
