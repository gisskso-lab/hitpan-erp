## 2. 퇴직서 500 — 원인 2개였다 (종결)

### 🔴 왜 중요한가 — 기존 관문이 **전부 통과**시켰다

| 관문 | 왜 못 잡았나 |
|---|---|
| 빌드 0/0 | **파일 이름 문제**라 컴파일러가 볼 수 없다 |
| 게시 게이트 | *"새 SQL 인데 requiresMigration=false"* 만 보지 **번호는 안 봤다** |
| 로컬 실측 | 빈 DB 엔 `DB-100` 기록이 없어 그냥 실행된다 |

> 🔴 **"빈 DB 에서 된다" 는 "고객 DB 에서 된다" 가 아니다.**
> 기적용 상태를 재현하지 않은 것이 검증의 구멍이었다.

### 원인 ① 마이그 번호 충돌 (기존 고객)

`DB-100` 을 **두 파일**이 썼다.

```
DB-100_payroll.sql              8/14 · 고객 DB 에 이미 적용됨
DB-100_resignation_letters.sql  8/24 · 이번 작업
```

`MigrationRunner` 는 파일명이 아니라 **번호로 식별자를 만들고**(`:70-76`),
`schema_migrations` 에 `success=1` 인 ID 는 건너뛴다(`:103-107`).
⇒ 퇴직서 SQL 이 **한 줄도 실행되지 않고 skip** 됐다.

### 원인 ② clean DDL 누락 (신규 고객) — DDL Smoke 가 잡음

①만 고쳤으면 **신규 고객에서 같은 500 이 재발**했다. 표가 clean DDL 에 없었다(헌법 #36).

### 재발 차단 — CI 게이트를 만들었다

`scripts/check-migration-id-collision.sh` → CI 잡 「마이그레이션 번호 충돌 (DB-NN 유일성)」

🔴 **게이트를 먼저 실패시켜 확인했다**:

| 실험 | 기대 | 결과 |
|---|---|---|
| 현재 상태 | PASS | 🟢 종료 0 |
| **사고 상태 복원**(DB-100 2개) | **FAIL** | 🔴 **종료 1** · 파일명+해결법 출력 |
| `DB-08b` 접미사 | PASS(오탐 없어야) | 🟢 `DB-08` 과 구분 |

⇒ **다음에 번호를 겹치면 머지가 막힌다.**

## 3. 결재설정 ① 자동승인 제거 (완결)

### 🔴 화면만 뺀 게 아니라 **서버 로직을 껐다** (사장님 결재)

종전엔 금액이 기준 미만이면 **결재선을 통째로 건너뛰고 승인**됐다.
⇒ **결재선에 이름이 올라간 사람이 보지도 못한 문서가 승인된 것으로 남는다.**
실무에선 *"내가 결재한 적 없는데 내 이름으로 승인돼 있다"* — 감사 추적이 깨진다.

**두 곳**을 껐다:

| 위치 | 종전 동작 | 위험도 |
|---|---|---|
| `ApprovalService.cs:496` | `status = "approved"` | 승인된 문서는 남음 |
| `ApprovalTriggerHelper.cs:130` | `return` | 🔴 **결재 문서 자체가 안 생김** — 이력이 아예 없다 |

### 🔴 컬럼·DTO 는 안 지웠다 (헌법 #37)

*"안 읽힌다 ≠ 잔재"*. 이미 값을 넣어 둔 고객사 기록이다.
저장 시 **서버가 준 값을 그대로 되돌려 보낸다** — 빼면 **남의 저장값을 지우게 된다.**

### 대조실험으로 실증

6조건 중 **정확히 1건만** `approved`→`pending`. 나머지 5건 무변화 = **회귀 0**.

## 4. 🔴 미해결 — ② 결재라인 스크롤 (다음 사람이 읽을 것)

### 증상

결재설정에서 「설정」 아이콘을 눌러도 **아래 결재라인 영역으로 화면이 안 내려간다.**
편집 영역은 표 아래에 나타나는데 문서유형이 10줄이라 **화면 밖**이다.

> 사장님: *"고객입장에서 «설정 아이콘 눌렀는데, 결재설정 어떻게 해요?» 라고 오해할수도"*

히트판 통과 기준(**"처음 보는 사람이 혼자 쓸 수 있냐"**)에 걸리는 자리다.

### 시도 1 (1.3.6) — MudBlazor `IScrollManager` ❌

```csharp
await ScrollManager.ScrollToAsync($"#{LineEditorAnchorId}", 0, 0, ScrollBehavior.Smooth);
```

**실패.** 원인은 찾았다 — `ScrollToAsync` 는 **창(window)** 을 스크롤하는데
이 앱은 창이 스크롤되지 않는다:

```
MainLayout.razor:69   <main class="hitpan-content mud-px-4 mud-py-4">
hitpan.css:70-74      .hitpan-content { flex:1; overflow:auto; min-height:0; }
```

창은 이미 끝까지 있는 상태라 **아무 일도 안 일어났다. 오류도 안 났다.**

### 시도 2 (1.3.7) — `scrollIntoView` ❌ **← 여기서 멈춤**

```javascript
// wwwroot/js/hitpan-scroll.js
toElement: function (elementId) {
    var el = document.getElementById(elementId);
    if (!el) return false;
    el.scrollIntoView({ behavior: 'smooth', block: 'start' });
    return true;
}
```

**또 실패.** 사장님: *"결론은 안됨."*

### 🔴 다음 사람에게 — 여기까지는 확인됐다

배포는 **정상**이다. 파일이 없어서 실패한 게 아니다:

| 확인 | 결과 |
|---|---|
| `http://127.0.0.1:5234/js/hitpan-scroll.js` | 🟢 **200 · 내용 정상** |
| `index.html` 이 JS 를 부르나 | 🟢 **1건** |
| `toElement` 함수 정의 | 🟢 **1건** |
| C# 호출 `hitpanScroll.toElement` | 🟢 main 에 실림 |
| 옛 `IScrollManager` 주입 | 🟢 **0건** (정확히 교체됨) |

⇒ **파일·로딩·배포는 다 맞다. 실패는 다른 층이다.**

### 아직 안 재본 것 (여기서 시작할 것)

1. 🔴 **브라우저 콘솔** — `hitpanScroll` 이 `window` 에 실제로 붙었나?
   개발자도구(F12) → Console → `window.hitpanScroll` 쳐보면 즉시 안다.
   `undefined` 면 **JS 로딩 순서·캐시** 문제다.
2. 🔴 **`toElement` 반환값** — 코드가 `false` 를 받으면 경고 로그를 남기게 해 뒀다.
   콘솔이나 로그에 *"결재라인 영역(id=approval-line-editor)을 찾지 못해"* 가 뜨는지 본다.
   뜨면 **렌더 시점** 문제(`Task.Yield()` 로 부족), 안 뜨면 **스크롤은 됐는데 안 보이는** 것.
3. **브라우저 캐시** — WASM 은 캐시가 강하다. `index.html` 에 강제 해제 스크립트가 있지만
   JS 파일 자체는 버전 쿼리(`?v=`)가 없다. 다른 js 는 붙어 있다
   (`hitpan-signup.js?v=20260601a`) — **이것만 없다.** 유력한 후보다.
4. **`block:'start'` 가 먹히는 위치인가** — 컨테이너가 여럿 겹쳐 있으면
   `scrollIntoView` 가 엉뚱한 조상을 잡을 수 있다.

### 🔴 이번 실패에서 배운 것 (코드에 남겨 뒀다)

1.3.6 은 **아무 일도 안 일어났는데 오류도 안 났다.**
사장님이 화면을 보고 말씀해 주시기 전까지 몰랐다.
⇒ 그래서 `toElement` 가 **`true`/`false` 를 반환**하게 하고 호출부가 로그를 남기게 했다.
**조용히 실패하는 코드를 그대로 두면 같은 사고를 또 못 잡는다.**

## 6. 오늘 사고에서 나온 교훈 (다음에도 유효)

### ① 브랜치는 **머지된 main 위에서** 딴다

PR #258 이 충돌해 닫고 #259 로 다시 올렸다.
머지 **전** main 에서 딴 브랜치는, 스쿼시 머지 후 **같은 내용이 다른 커밋**이 되어 부딪힌다.
⇒ 앞 PR 머지 확인 → `git fetch` → **거기서** 브랜치.

### ② Blazor 정적 자산은 `publish` 에서 확인한다

`build` 산출물엔 `wwwroot/js/*` 가 **없다.** publish 시점에 모인다.
⇒ JS·CSS 를 추가하면 **반드시 `dotnet publish` 로 실렸는지 본다.**
이번에 이걸 안 봤으면 파일 없는 채로 배포될 뻔했다.

### ③ 게이트는 **먼저 실패시켜** 확인한다

CI 게이트를 만들면 통과만 보지 말고 **사고 상황을 복원해 빨간불이 뜨는지** 본다.
안 그러면 아무것도 안 하는 가짜 게이트를 만들고 안심하게 된다.

### ④ `git add scripts/` 같은 폴더 단위 add 를 하지 않는다

무관한 파일(`_truncate-only.sql` 등)이 딸려 온다. **경로를 명시**한다.
