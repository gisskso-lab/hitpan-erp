## [2] 원인 — 가드가 확정 한 곳뿐이었다

| 동작 | 종전 상태 | 결과 |
|---|---|---|
| 확정 | 진입 가드 + 플래그 + `finally` **완비** | 정상 |
| **저장** | **플래그 자체가 없음** | 연타 시 **반품 전표 중복 생성** |
| **삭제** | **플래그 자체가 없음** | 같은 문서에 삭제 요청 두 번 |
| **확정취소** | 플래그를 **세우기만** 하고 진입 체크 없음 | 연타 그대로 뚫림 |

🔴 **확정취소가 특히 교훈적이다.** `_isConfirming = true` 는 있는데
`if (_isConfirming) return;` 이 없었다. **가드가 있는 것처럼 보이지만 아무것도 막지 못한다.**
20260825작3 의 "필터가 헛돈다" 와 같은 모양의 사고다.

### 저장이 왜 위험한가

`_isNew` 는 **서버 응답이 도착한 뒤에야** false 로 바뀐다.
응답 오기 전 두 번째 클릭이 들어오면 `_isNew` 가 아직 true 라
**POST 가 한 번 더 나가 반품 전표가 두 장 생긴다.**

## [3] 봉합

확정 함수의 기존 패턴(진입 가드 → 플래그 → `try`/`finally`)을 그대로 따랐다.

```
if (_isSaving) return;      ← 진입 가드 (없으면 아무것도 못 막는다)
...
_isSaving = true;
try { ... }
finally { _isSaving = false; }   ← 안 풀면 버튼이 영영 죽는다
```

| 동작 | 추가한 것 |
|---|---|
| 저장 | `_isDeleting` 과 별개인 `_isSaving` 플래그 신설 + 진입 가드 + `finally` |
| 삭제 | `_isDeleting` 플래그 신설 + 진입 가드 + `finally` |
| 확정취소 | **진입 가드 한 줄** (플래그·`finally` 는 이미 있었다) |

### 손대지 않은 것 — 서버 멱등 (사장님 결재)

- **확정·취소·삭제는 서버가 이미 상태로 막는다** — `draft` 가 아니면 확정 불가,
  `confirmed` 가 아니면 취소 불가. 연타해도 두 번째는 서버에서 튕긴다.
- **생성만 서버 방어가 없다.** 서버는 **연타와 진짜 두 번째 반품을 구분할 수 없다**
  (매번 새 ID 라서). 잘못 막으면 정당한 반품을 반려하게 된다.
  → 사장님 결재: **화면 가드만**. 서버 멱등키는 범위 밖.
