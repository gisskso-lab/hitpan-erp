## 1. 🟢 오더 1 — 회계 배선 (완료)

### 무엇이 문제였나

**수금·지급·경비·급여가 분개를 한 줄도 안 만들고 있었다.** 화면·저장은 정상인데
회계로 넘기는 문이 없었다. 판매·매입·BOM 10경로는 정상 기표 중이었다
⇒ **회계장부가 절반만 채워지고 있었다.**

### 착수 블로커였던 것 — 계정과목

`journal_lines → accounts` FK 때문에 **없는 계정에 기표하면 FK 1452 로 죽는다.**
계정이 **8개뿐**이고 현금·급여·예수금·경비계정이 전부 없었다.

⇒ **DB-111 로 21개 추가 (8 → 27).**

> 🟢 **사장님 지시 반영** — *"현금은 수기로!!!!"*

> 복식부기는 차·대가 반드시 짝이라 계정 **행 자체**는 있어야 FK 를 통과한다.

아직 신고가 없는 건 BOM 쓰는 고객이 없어서로 추정. DB-111 이 둘 다 심어 일치시켰다.

### 기표 시점 — 매입·판매의 「확정」과 같은 축

| 업무 | 시점 | 왜 |
|---|---|---|
| 수금·지급 | 생성 즉시 | **같은 트랜잭션 안** — 저장만 되고 분개가 빠지는 일이 없게 |
| 경비 | **승인 시점** | 대기·반려분이 비용으로 남으면 손익이 틀어진다 |
| 급여 | **지급 시점** | 확정은 *"명세를 잠갔다"*, 지급이 *"돈이 나갔다"* |

### 급여는 3줄 분개

차변 급여(총지급) / 대변 예수금(공제) + 예금(실지급).
차액은 회사가 대신 보관했다 나라에 내는 돈이라 **부채**다. 안 나누면 인건비가 과소계상되고
원천세 신고와 장부가 안 맞는다.

> ⚠️ **금액은 시스템이 계산하지 않는다** — 이미 사람이 확정한 숫자를 옮길 뿐.

## 2. 🔴 오더 2 — 매입라인 전수조사 (조사 완료 · 코드 미착수)

### 사슬은 안 끊겼다

발주→매입은 **헤더·라인 양쪽**이 이어져 있고(`po_id`·`po_item_id`), 초과입고 가드·PO 상태 롤업에
**실제로 쓰이고 있다.** 매입→반품도 `receipt_id` 로 이어져 있다.

### 그런데 문제가 3건 있다

#### ① 🔴 철자가 갈려 있다 — 이미 사고 난 자리

| 표 | 철자 |
|---|---|
| `purchase_orders` · `purchase_receipts` | **`cancelled`** (l 2개) |
| `purchase_returns` · `sales_returns` · `tax_invoices` | **`canceled`** (l 1개) |

**원장문서는 `cancelled`, 반품문서는 `canceled`.** 매입 사슬 안에서 5단계↔6단계에 철자가 뒤집힌다.
레포 시험이 직접 기록: *"종전 `<> 'cancelled'` 는 실제 기록값 `canceled` 와 절대 안 맞아 무의미했다."*
`varchar(20)` 에 enum 제약이 없어 **DB 가 두 철자를 다 받는다.**

#### ② 🔴 발주 상태 — C# enum 과 DB enum 이 안 맞는다

- DB: `enum('draft','ordered','partial','received','cancelled')`
- C#: `Draft, Confirmed, Partial, Closed, Cancelled`

**`Confirmed`·`Closed` 는 DB 에 없는 값이다.** 코드가 직 SQL 로 우회 중이고,
`ParsePurchaseOrderStatus` 는 DB 의 `ordered`·`received` 를 못 읽어 **전부 `Draft` 로 떨어뜨린다.**
⇒ **EF 로 읽으면 입고완료 건이 임시저장으로 보인다.**

> 📌 **앞서 주신 그리드 오더의 상태 4종**(임시저장/입고완료/반품중/반품확정)과 **정면으로 얽힌다.**
> 표시층(그리드 색·열)을 고치기 전에 **이 축부터 정리해야 한다.** 안 그러면 어긋난 값을 예쁘게 칠하는 셈이다.

#### ③ 반품 라인 링크가 없다 (비대칭)

`purchase_return_items` 에 `receipt_item_id` 가 **없다.** 어느 매입 **라인**을 반품했는지 추적 불가.
매입 쪽엔 `po_item_id` 가 있는데 반품 쪽만 빠졌다.

## 3. 🔴 오더 3 — 창고 (조사 완료 · **구조적 블로커 발견**)

### 🔴 DB 열쇠 하나가 다창고를 막고 있다

`stock_ledger` UNIQUE 키에 **`warehouse_id` 가 없다**:
```
uq_stock_ledger_source (tenant_id, source_type, source_id, item_id, move_type)
```

⇒ 전표 1장·품목 1개 = **원장 행 1개까지만.**
⇒ 같은 품목을 두 창고로 나눠 받으면 **행을 2개 못 만든다.**
⇒ 그래서 코드가 품목 단위로 합쳐 넣고 **창고는 첫 라인 것만** 쓴다.

**결과: `stock_ledger` 와 `item_stock` 이 창고별로 어긋난다.**
`item_stock` 은 (품목,창고)로 올바른데 원장은 전량을 첫 창고에 몰아 적는다.
⇒ **원장으로 창고별 재고를 뽑으면 틀린 값이 나온다.** 지금은 아무도 안 뽑아서 안 드러났다.

### 🟢 스위치가 이미 있는데 아무 데도 안 붙어 있다

`use_multi_warehouse` — **설정 화면에 토글까지 있다.**
전 소스 12곳 나오는데 **전부 설정 저장·조회 배관뿐**, 재고·매입·판매·BOM 로직에 **읽는 곳 0건.**

⇒ **사장님 오더 3번의 「미지정/지정」 스위치가 이미 만들어져 있고 연결만 안 돼 있다.**
새로 만들 게 아니라 **배선할 자리**다.

### 현재 동작은 오더와 반대다

- **오더**: 창고 미지정 = 모든 재고 통합
- **현재**: 창고 미지정 = **MAIN 창고로 강제 배정** (4단 폴백)

⇒ **「통합 재고」라는 개념 자체가 없다.**

### 그 밖

- 잔액 조회 **13곳 전부 창고 무시** (`GROUP BY tenant_id, item_id`)
- 음수재고 가드 **3곳도 전 창고 합산** ⇒ A창고 0인데 B창고에 있으면 A 출고가 통과
- 발주·매입·반품 **세 표 모두 헤더에 창고 컬럼 없다** — 매입 화면의 「입고창고(기본)」은 **화면 안에서만 사는 값**, DB 에 안 남는다

> 📌 **앞서 주신 그리드 오더의 「입고창고」 열**이 여기 걸린다. 헤더에 값이 없어 **라인에서 끌어올려야** 한다.
