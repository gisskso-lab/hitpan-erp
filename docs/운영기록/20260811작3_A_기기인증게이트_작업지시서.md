# §-1. 🔴 PM 이 어제 합의를 빠뜨렸다 — 사장님 지적으로 정정

PM 이 1차안에서 기기 식별을 **JWT 클레임**으로 짜서 올렸다. 사장님 지적:

> *"**인증 슬롯을 식별할 수 있도록 슬롯인증 절차에서 인증키 같은 걸 심자**고 어제 얘기했을텐데."*

**맞다.** 어제 작업지시서는 **제목부터** *"기기 인증키 + 슬롯 판매 경로"* 이고,
사장님 원문이 §맨 앞([20260811작1:15-16](20260811작1_챕터4_기기인증_슬롯판매_작업지시서.md))에 있다:

> *"1. 사용PC에는 **물리적으로 간단한 인증서 같은 인증키를 부여.**
>  2. 사용 모바일에는 QR로 모바일기기 인증키를 부여."*

그리고 **왜 인증키인지**까지 적혀 있다([:42-46](20260811작1_챕터4_기기인증_슬롯판매_작업지시서.md)):

> *"지금은 **브라우저에게 '너 누구냐'** 를 묻는다(지문). 브라우저는 자기 안에만 흔적을 남기니
> Edge 와 Chrome 이 각자 다른 답을 하고, **같은 PC 가 2대로 세어진다.**
> 사장님 안은 묻는 대상을 **기기에 발급한 인증키**로 바꾼다.
> 추측을 정교하게 하는 게 아니라 **애초에 추측을 안 하게** 만든다."*

## 왜 PM 안이 틀렸나 — 단순 누락이 아니다

JWT 안은 **추측(지문)을 토큰에 실어나르는 것**이다.
⇒ 바꾸라고 하신 방식을 **그대로 유지**하는 셈이고,
⇒ 지금 겪는 **"같은 PC 가 2대로 세어지는"** 문제가 **안 풀린다.**

| | PM 1차안 (폐기) | **사장님 안 (채택)** |
|---|---|---|
| 서버가 묻는 것 | *"이 브라우저 지문이 뭐냐"* | **"네가 받은 인증키를 내놔라"** |
| 근거 | 추측 (환경 해시) | **발급 사실** |
| Edge·Chrome | 🔴 **각자 다른 답 = 2대** | 🟢 같은 키 = 1대 (§2-1) |

## 실측 — 인증키는 **합의만 있고 구현이 0이다**

| 확인 | 결과 |
|---|---|
| `tenant_devices` 에 인증키 컬럼 | 🔴 **없다** |
| `UNIQUE KEY` | 🔴 `(tenant_id, **fingerprint**)` — **여전히 지문이 주(主)** |
| 코드에 `auth_key`/`device_key` | 🔴 **0건** (토스 `authKey` 는 결제용 · 무관) |

⇒ 어제 지시서 `:167` 이 예고한 그대로다:
*"**인증키가 주(主), 지문은 보조로 남긴다.**"* — 그 전환이 **아직 시작 안 됐다.**

# §0. 🔴 실측이 서버 안의 모순을 잡았다 — 이게 (A) 의 진짜 첫 일감

[`TenantDeviceService.cs:255`](../../src/HitPan.Infrastructure/Services/TenantDeviceService.cs) 주석에
**어제 사장님 지시가 그대로 적혀 있다**:

> *"allowed=false 이지만 **로그인 거부가 아니다.** 사장님: **'일단 로그인, 접속까지는 가능하게 해.'**"*

그런데 [`AuthController.cs:101-105`](../../src/HitPan.API/Controllers/AuthController.cs) 는 그 값을 받아 **로그인을 거부한다**:

```csharp
if (!allowed)
    return Unauthorized(new { message = reason });
```

🔴 **(A) 의 전제가 서버 최상류에서 이미 깨져 있다.**
인증 안 된 기기는 **게이트 화면에 도달조차 못 하고** 로그인 폼에서 튕긴다.
그래서 *"인증기기 한도초과"* 문구도 게이트 안내문이 아니라 **로그인 실패 빨간 글씨**로 뜬다.

⚠️ 지금 `DeviceApproval:Enabled = false` 라 아무도 안 겪는다. **스위치를 켜는 순간 드러난다.**

⇒ **사장님 결재: 주석대로 간다.** 로그인은 통과시키고 메뉴만 잠근다.

# §1. 사장님 결재 2건 (이번 작업의 뼈대)

## 결재 1 — 승인 시 **인증키를 발급**하고, 기기는 그것을 내민다

```
대표가 승인  →  서버가 인증키 발급  →  기기에 저장
                                        ↓
        이후 모든 요청  →  기기가 인증키 제시  →  서버가 대조
```

🔴 **서버는 추측하지 않는다.** *"네가 받은 키를 내놔라"* 한 마디만 한다.
어제 사장님 원문 — *"물리적으로 간단한 **인증서 같은 인증키**를 부여"*.

⚠️ **인증키는 지문을 대체한다. 다만 지문을 지우지는 않는다**([20260811작1:167](20260811작1_챕터4_기기인증_슬롯판매_작업지시서.md)):
> *"기존 지문 산식 제거 — **인증키가 주(主), 지문은 보조로 남긴다.** 제거는 별건"*

지문은 *"키를 처음 받기 전"* 단계와 **키 분실 시 같은 기기임을 알아보는 보조**로 남는다.

## 결재 2 — 로그인은 **통과**시키고 메뉴만 잠근다

직원이 *"왜 안 되는지 모른 채"* 막히지 않게 한다.
어제 사장님 정정(*"직원에게 직원이 할 수 없는 일을 시키지 마라"*)과 같은 계통이다.

# §2. 인증키 설계 — 결정할 것 3가지

## 2-0. 🔴 전체 흐름 (사장님 확정 — 이것이 정본)

> *"인증요청을 메인PC에 하면, 그 요청을 **승인하는건 대표**야"*
> *"메인PC에서 인증키가 생성되면, **요청한 클라이언트PC에서 입력하는 방식.**
>  그 메인PC에서 키를 주는 방식은 **대표 마음이지.**"*

```
직원 PC                          메인PC (대표)
   │                                  │
   │ ① 로그인 → 화면 비활성화            │
   │   "인증된 기기가 아닙니다.          │
   │    히트판 관리자에게 문의하세요."    │
   │                                  │
   │ ────── ② 인증요청 ──────────────▶ │
   │                                  │ ③ 대표가 승인
   │                                  │   → 인증키 생성·화면에 표시
   │                                  │
   │        ④ 대표가 키를 알려준다        │
   │        (구두·메신저·메모 — 대표 마음) │
   │ ◀────────────────────────────────│
   │                                  │
   │ ⑤ 직원이 그 키를 **입력**           │
   │   → 이 PC 에 저장 → 화면 열림       │
```

🔴 **이 방식이 "직원인지 해커인지" 를 푼다.**
키를 **아는 사람만** 입력할 수 있고, 그 키는 **대표가 직접 건넨 것**이다.
서버가 추측할 일이 없다.

⚠️ **키를 전달하는 방법은 우리가 정하지 않는다.** 사장님: *"대표 마음이지."*
우리는 **화면에 보여주는 것**까지만 한다.

## 2-1. 🔴 인증키는 **슬롯을 세는 도구가 아니다** — PM 정정

PM 이 인증키에 *"지문을 대체한다"*, *"같은 PC 가 2대로 세어지는 걸 푼다"* 를 붙여
설계를 어렵게 만들었다. 사장님 지적:

> *"인증키 발급으로 대조검사로 슬롯을 구분 하지 않더라도,
>  **장치ID나 장치이름으로 단순하게 슬롯관리를 할 수 있는 거잖아.**"*
> *"**왜 어렵게 생각하는거지??**"*

**맞다. 두 가지는 별개다.**

| | 무엇으로 | 이미 되나 |
|---|---|---|
| **슬롯 관리 (몇 대냐)** | `tenant_devices` 의 **행**. `device_id`·`device_name` | 🟢 **이미 된다** |
| **인증 (문을 여느냐)** | **인증키** | 🔴 이번에 만든다 |

⇒ 기기 목록에 행이 하나면 한 대다. **세면 그만이다.**
⇒ 인증키는 *"이 기기가 승인받은 그 기기냐"* 만 본다.

🔴 **PM 은 인증키를 슬롯 식별에까지 끌어들이지 않는다.** 지문 산식·2겹 문제는
**이번 범위가 아니다**(어제 지시서 `:224` 가 이미 별건으로 남겼다).

## 2-1b. 저장 위치

인증키는 직원이 **입력**한 뒤 그 PC 브라우저에 보관한다(`localStorage`).
다음부터는 직원이 다시 입력하지 않는다.

## 2-2. 어떻게 실어 보내나

```
요청 헤더  X-HitPan-Device-Key: {인증키}
```

⚠️ 사용자가 값을 고쳐 보낼 수 있다 ⇒ **서버가 DB 와 대조**한다(추측이 아니라 조회).
키는 **긴 무작위 값**이라 찍어 맞힐 수 없고, 남의 키를 알아낼 경로가 없다.

⚠️ **JWT 에는 넣지 않는다.** 토큰 수명이 **8시간**([`AuthService.cs:21`](../../src/HitPan.Application/Services/AuthService.cs))이라
대표가 폐기해도 **최대 8시간 살아 있다** — 근무 하루가 통째로 들어간다.
헤더+DB 대조는 **다음 요청에 즉시** 반영된다.

## 2-3. 저장 방식 — 🔴 원문을 넣지 않는다

`device_register_tokens` 의 선례를 따른다(`token_hash` 만 저장, 평문 미저장).

| 컬럼 | 내용 |
|---|---|
| `auth_key_hash` | 🔴 **SHA-256 해시만.** 원문은 발급 순간 한 번만 보여주고 안 갖는다 |
| `auth_key_issued_at` | 발급 시각 |

⚠️ DB 가 통째로 새도 **남의 기기로 접속할 수 없다.** 헌법 #5 계통.

# §4. 게이트 화면 — 무엇을 보여주나

## 🔴 사장님 원문 (2026-08-11, 이것이 정본)

> *"인증키가 없어 인증할 수 없는 슬롯은*
> *  **로그인만 되고 화면은 비활성화** 그리고*
> *  비활성화된 화면에 **"인증된 기기가 아닙니다. 히트판 관리자에게 문의하세요."** 안내*
>
> *그리고 **메인PC 에선** "인증되지 않은 기기가 접속하였습니다. 슬롯을 추가하시겠습니까?" Y/N*
> *  **Y** : 랜딩페이지 연결*
> *  **N** : "인증기기를 변경하시겠습니까?" Y/N"*

## 4-1. 직원 쪽 — 화면 하나, 문구 하나

```
┌──────────────────────────────────────────┐
│  (메뉴 전부 비활성화)                       │
│                                           │
│  "인증된 기기가 아닙니다.                    │
│   히트판 관리자에게 문의하세요."              │
│                                           │
│  (버튼 없음)                               │
└──────────────────────────────────────────┘
```

🔴 **경우를 나누지 않는다.** 승인대기든 한도초과든 미등록이든 **직원에게는 같은 말**이다 —
직원이 할 수 있는 일이 어차피 하나(관리자에게 문의)뿐이기 때문이다.

⚠️ **PM 정정**: PM 1차안은 화면을 3분기(승인대기/미등록/한도초과)로 짰다.
사장님 안은 **하나**다. 직원에게 원인을 설명해봐야 **직원이 할 수 있는 게 달라지지 않는다.**

⚠️ 문구는 **"인증된 기기가 아닙니다. 히트판 관리자에게 문의하세요."** 로 통일한다.
(사장님: *"그거나 저거나"* — 어제 문구와 뜻이 같다. 하나로 맞춘다)

🔴 **버튼을 두지 않는다.** [기기 인증하기] 도 없다 — 직원이 눌러도 대표 승인을 못 앞당긴다.
슬롯 추가는 **메인PC(대표) 화면**에서 판다(4-2).

## 4-2. 🔴 메인PC 쪽 — 파는 자리 (사장님 (C))

```
메인PC 화면
┌────────────────────────────────────────────────┐
│  "인증되지 않은 기기가 접속하였습니다.              │
│   슬롯을 추가하시겠습니까?"          [예]  [아니오] │
└────────────────────────────────────────────────┘
        │                          │
        │ 예                        │ 아니오
        ↓                          ↓
   랜딩페이지 연결          "인증기기를 변경하시겠습니까?"  [예] [아니오]
     (슬롯 구매)                    │
                                   │ 예 → 등록기기 관리 (기존 기기 해제 → 새 기기 승인)
```

🔴 **막는 김에 판다.** 어제 지시서 §의중 ③ — *"차단 장치가 아니라 판매 경로다"*.

⚠️ **"인증기기를 변경"** 은 슬롯을 안 사고도 새 기기를 쓰게 하는 길이다
(안 쓰는 기기를 빼고 그 자리에 넣는다). 돈을 안 쓰는 선택지를 반드시 함께 준다.

⚠️ **결제 미준비** — 사장님 확인(2026-08-11 *"아직"*). 토스는 공영정보(주) 명의 신청 예정.
⇒ **[예] → 랜딩페이지 연결까지만.** 결제 자체는 이번 범위 밖.

## 4-3. 문구 원칙

🔴 **사장님이 주신 문구를 그대로 쓴다.** PM 이 다듬지 않는다.
*"인증된 기기가 아닙니다. 히트판 관리자에게 문의하세요."*

⚠️ **"슬롯"** 은 메인PC(대표) 화면에만 쓴다 — 돈을 내는 사람이 보는 말이라 통한다.
직원 화면에는 안 쓴다.

⚠️ 등록 자체는 **로그인이 이미 한다**
([`TenantDeviceService.cs:281`](../../src/HitPan.Infrastructure/Services/TenantDeviceService.cs)
`_approvalEnabled ? "pending" : "approved"`). 직원이 누를 버튼이 필요 없는 이유다.

# §5. 🔴 승인제 스위치를 켤 때 함께 봐야 하는 것

[20260811작2 검증](../개발/erp/20260811_PI-04_기기유형오판_봉합_개발명세서.md) 이 넘긴 선결 항목이다.

[`ApproveAsync:404-407`](../../src/HitPan.Infrastructure/Services/TenantDeviceService.cs) 이
승인 시점에 **한도를 다시 검사**한다. 이 재검사 자체는 **옳다** —
대기 3대·남은 1칸이면 첫 승인만 되고 나머지는 막혀야 한다(`:381-383` 주석).

**문제는 대표가 무엇을 해야 하는지 모른다는 것이다.**

```
"인증기기 한도초과. 슬롯을 추가하거나 사용하지 않는 기기를 해제해 주세요."
```

⇒ 이 문구가 뜰 때 **그 자리에서 할 수 있게** 해야 한다 —
(C) 판매 알림·기기 해제로 잇는다. 문구만 띄우고 끝내면 어제와 같은 지적을 받는다.

⚠️ PM 정정: 검증팀이 이를 *"잠복 결함"* 으로 올렸으나, [`ApproveAsync:377`](../../src/HitPan.Infrastructure/Services/TenantDeviceService.cs)
이 `approved` 면 **즉시 return** 하므로 **이미 승인된 기기는 재검사에 안 걸린다.**
`pending` 은 스위치가 켜져야 생긴다 ⇒ **현재 발생 불가.** 스위치 ON 과 **동시에** 열린다.

# §6. 검증 — [7-V] 검증팀장 데이비드 박

🔴 **빌드 0/0 은 검증이 아니다.** 스위치를 켜고 **직접 막혀 봐야** 한다.

| # | 관문 | 확인 |
|---|---|---|
| 1 | 빌드 errors 0 + warnings 0 | ⬜ |
| 2 | 스위치 **ON** 후 새 기기 로그인 → **로그인은 되나** | ⬜ |
| 3 | 로그인 후 **메뉴가 잠기나** (사이드바 + **모바일 하단바**) | ⬜ |
| 4 | 🔴 **주소창에 URL 직접 입력** → 뚫리나 | ⬜ |
| 5 | 대표 승인 → **인증키가 발급되고** 잠금이 풀리나 | ⬜ |
| 5b | 🔴 **인증키 없이 헤더만 위조**해서 보내면 막히나 | ⬜ |
| 5c | 🔴 **남의 인증키**를 넣으면 그 기기로 인정되나 (되면 안 된다) | ⬜ |
| 5d | 인증키를 지우면(브라우저 정리) **다시 승인대기로 가나** | ⬜ |
| 6 | 🔴 **폐기 즉시 반영되나** (8시간 안 기다리고) | ⬜ |
| 7 | 게이트 화면이 부르는 API 가 **게이트에 막히지 않나** (데드락) | ⬜ |
| 8 | 미들웨어 고장 시 **통과되나** (fail-open) | ⬜ |
| 9 | 🔴 **스위치 OFF 로 되돌리면 원래대로 도나** | ⬜ |

🔴 **9번이 안전장치다.** 켰다가 문제가 생기면 되돌릴 수 있어야 한다.

⚠️ **실측 전 확인**: 검증팀 보고 — `hitpan_erp` 에 **DB-86 `is_main_pc` 미적용**.
이 DB 로 API 를 띄우면 기기목록 화면이 **500** 이다. 마이그레이션부터 확인할 것.
