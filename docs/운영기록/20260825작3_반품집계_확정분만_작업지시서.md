## [2] 원인 — 전수조사로 확정

**"데이터 분석이 안 된다"의 원인 중 하나가 반품 집계였다. 숫자 자체가 틀렸다.**

### 사고 ① 매입반품 — 필터가 헛돌았다

| 자리 | 값 |
|---|---|
| 실제 기록 (`PurchaseService` 취소 UPDATE) | `status='canceled'` — **L 하나** |
| 리포트 필터 (`ReportService` 4곳) | `status <> 'cancelled'` — **L 둘** |

두 문자열은 절대 같지 않다 → 조건이 **항상 참** → **취소분이 100% 집계에 남았다.**
필터가 있는 것처럼 보이지만 아무것도 거르지 못하는 상태였다.

### 사고 ② 매출반품 — 상태 조건이 아예 없었다

`sales_returns` 를 조회하는 SQL 2곳에 status 조건 자체가 없었다.
`is_deleted = 0` 만 봤다.

🔴 **판매종합현황(반품포함)이 특히 위험했다** — 취소·미확정 반품이
`-COALESCE(SUM(...))` **음수로 매출에서 계속 차감**되어 **매출이 실제보다 적게** 나왔다.

### 폭발 반경 — 리포트 한정

재취소 방지 가드는 `!= "confirmed"` **양성 비교**라 철자와 무관하게 정상 작동한다.
원장·회계는 안전하다. **틀린 것은 현황 숫자뿐이다.**

### 기존 데이터

git 이력상 반품 취소 기능은 처음부터 `canceled` 하나로만 만들어졌다
(`cancelled` 를 쓴 코드가 존재한 흔적 없음). 두 철자가 섞여 있을 가능성은 낮아
**데이터 정정 없이 코드만 고치면 된다.**

## [3] 봉합 — 부정(`<>`)이 아니라 양성(`=`)

사장님 결재대로 **철자는 건드리지 않고 리포트만** 고쳤다.

```
종전: WHERE ... AND rt.status <> 'cancelled'   ← 철자 안 맞아 항상 참
종전: WHERE ... (매출반품은 조건 자체가 없음)
봉합: WHERE ... AND status = 'confirmed'
```

**양성 비교를 쓴 이유** — `canceled`/`cancelled` 혼재와 **무관**해지고,
draft(미확정)도 **함께** 빠진다. 재고·회계가 confirmed 에만 반응하므로
현황 숫자도 같은 잣대여야 한다 (헌법 #6).

### 고친 6곳

| 리포트 | 위치 |
|---|---|
| 매입반품현황 — 기간별·업체별·품목별·사원별 | `ReportService.cs` 4곳 |
| 매출반품현황 | `ReportService.cs` `SALES_RETURN` |
| 판매종합현황(반품포함) 반품 leg | `ReportService.cs` `SALES_TOTAL_INCLUDING_RETURN` |

### 손대지 않은 것

- **판매종합현황의 매출 leg** (`sd.status <> 'cancelled'`) — `sales_deliveries` 는
  기록·조회가 L 둘로 **정상 매칭**된다. 멀쩡한 필터를 깨뜨리지 않았다.
- 취소 상태값 철자 자체 (사장님 결재 — 안 건드림)
- 수주·발주·매입 등 다른 계열 리포트
