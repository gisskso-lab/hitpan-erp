## 1. 🔴 종전 전제가 틀렸다 — 정정

### 1-1. 무엇이 틀렸나

지금까지 팀이 여러 문서에 이렇게 적어 왔다:

> ❌ *"사장님 사업자등록 = 베타 이후(8월 말). 실업급여 수급 중.
> 사업자 회원·세금계산서·토스 가맹·법인카드 권장 절대 금지"*

**이 전제는 "사장님 개인 명의"를 가정한 것이었다.**
실제 구조는 **기존 법인 공영정보(주)에 귀속**이다.

### 1-2. 그래서 무엇이 달라지나

| 항목 | 종전 (틀린 전제) | 실제 |
|---|---|---|
| 사업자 신원 | 없음 (등록 전) | ✅ **공영정보(주) 있음** |
| 토스페이먼츠 | 🚫 가맹 권장 금지 | ✅ **공영정보(주)로 신청 예정** |
| 전자세금계산서 | 🚫 보류 | ✅ **메이크빌(주) ↔ 공영정보(주) 계약** |
| SNS 비즈니스·광고 계정 | ⚠️ 사업자 정보 요구 우려 | ✅ **공영정보(주) 명의로 가능** |
| 사업자 회원 가입 | 🚫 금지 | ✅ **가능** (공영정보 명의) |
| 계약 주체 | 없음 | ✅ **공영정보(주)** |

### 1-3. ⚠️ 다만 여전히 조심할 것

**"사장님 개인" 과 "공영정보(주)" 는 다르다.**

- 계약·가맹·계정은 **공영정보(주) 명의**로 한다
- **사장님 개인 명의로 하라고 권하지 않는다** (종전 원칙은 이 부분에서 유효)
- 실업급여 관련은 **사장님 개인 사정**이므로 PM 이 판단하지 않는다

## 1-4. 🔴 이 구조의 진짜 의미 — 사장님 추가 지시 (2026-08-07)

> **"일단 레거시히트판업체인 공영정보(주)에서 히트판을 운영할 거면,
> 기존의 직원들이 익숙했던 히트판체계에서 바로 뉴히트판ERP 영업,마케팅,CS체계에
> 적응 할 수 있는 업무환경을 만드는게 중요함.
> 그래서 미리 준비하고 기획하며, 업무 워크스페이스를 구축하는거임."**

### 이 한 문단이 오늘 지시 전부를 꿰맨다

공영정보(주) 귀속은 **서류상 절차가 아니다.**
**그 회사에는 이미 직원이 있고, 그들이 새 체계로 갈아타야 한다.**

### 무엇이 바뀌는가 — 프로그램만이 아니다

| | 레거시 히트판 | 새 히트판 |
|---|---|---|
| 파는 것 | 설치해서 파는 프로그램 | **구독 SaaS** |
| 고객 관리 | 고객 명부 | **백오피스** |
| CS | 전화 받고 방문 | **원격 + 터널·자동업데이트** |
| 영업 | 직접 방문 | **대리점 + 랜딩** |
| 자료 | Access 파일 | **고객 PC MariaDB + 터널** |

**직원 입장에서는 일하는 방식이 통째로 바뀐다.**

### ⭐ 그래서 오늘 지시들이 전부 이어진다

| 오늘 지시 | 왜 그렇게 말씀하셨나 |
|---|---|
| **CS 3축 — "Access DB 20년, 터널링 지식 0"** | 🔴 **그 사람들이 바로 공영정보 직원이다.** 가상의 인물이 아니었다 |
| **"초등학생도 할 수 있는 매뉴얼"** | 새로 공부시킬 게 아니라 **바로 쓸 수 있어야** 한다 |
| **"교육이 필요함"** | 갈아타는 사람에게는 교육이 필수다 |
| **백오피스 = 영업·CS 집합체** | 🔴 **그들이 매일 앉아서 일할 곳**이라서 |
| **"미리 준비하고 기획"** | 직원이 앉기 전에 **자리가 준비돼 있어야** 한다 |
| **CS 챗봇 (API 없이)** | 모르는 걸 매번 물어볼 사람이 없다 |

### 🔴 그래서 백오피스의 정의가 다시 바뀐다

| 단계 | 정의 |
|---|---|
| 종전 | 본사 관리 도구 |
| 8/07 오전 | 영업·CS 영역의 집합체 |
| **8/07 최종** | 🔴 **공영정보(주) 직원들의 업무 환경** |

**"이 화면 처음 보는 사람이 혼자 쓸 수 있냐"** 가 백오피스에도 그대로 적용된다.
지금까지 그 기준은 **고객용 화면**에만 쓰였다.

### ⭐ 히트판의 존재 이유와 정확히 같다

> *"레거시 히트판이 VB + Access + 낡은 UI로도 살아남은 이유는 딱 하나.
> **쓰기가 겁나 쉬웠기 때문이다.**"*

**고객에게만 쉬우면 안 된다. 파는 직원에게도 쉬워야 한다.**
공영정보 직원이 새 백오피스 앞에서 헤매면, 레거시가 이겼던 그 이유를 새 히트판이 잃는 것이다.

### ⚠️ 아직 모르는 것 (착수 전 확인)

| # | 항목 |
|---|---|
| 1 | 공영정보(주) 직원이 **몇 명**인가 · 어떤 일을 하나 (영업/CS/관리) |
| 2 | 그들이 **언제** 새 체계로 옮기나 (베타 전/중/후) |
| 3 | 레거시 히트판 운영을 **병행**하나 |
| 4 | 교육을 **누가** 하나 |

> 🚫 **PM 은 위 4건을 추측하지 않는다.** 사장님만 아는 정보다.
> 오늘 *"사업자등록 전"* 을 확인 없이 인용해 틀린 것과 같은 실수를 반복하지 않는다(§6).

## 1-5. 🔴🔴 사업 규모와 셀링포인트 — 사장님 추가 지시 (2026-08-07)

> **"본사고객이 백오피스와 영업환경, cs환경에 익숙해져야, 대리점 사장들한테 교육이 가능함.
> 그래야 영업에 이어질 수 있고.
> 기존의 레거시 히트판의 대리점 영업망은 탄탄해서, 이 워크스페이스에 적응하면
> 매출을 올리기엔 매우 쉬울거임.
> 전국의 10개가 넘는 대리점 영업망을 통한 기존 5만고객사의 전환고객, 신규고객 유입이
> 베타배포 이후 첫 정식배포의 셀링포인트임"**

### 🔴 규모가 달랐다 — PM 이 자릿수를 잘못 알고 있었다

| | PM 이 알고 있던 것 | 실제 |
|---|---|---|
| 대리점 | 베타1에 5곳 | **전국 10곳 이상 (기존 영업망)** |
| 고객사 | 베타 5~10곳 | 🔴 **기존 5만 고객사** (전환 대상) |
| 성격 | 신규 개척 | **이미 있는 영업망 + 이미 있는 고객** |

> ⚠️ 오늘 CS팀이 *"5곳은 되나 50곳은 불가능"* 이라고 쓴 대목이 있다.
> **자릿수가 두 개 더 크다.** 그 전제로 다시 봐야 한다.

### 🔗 교육 체인 — 끊기면 영업이 안 된다

사장님이 순서를 명시하셨다:

```
본사 직원이 익숙해진다
        ↓  (익숙해져야 가르칠 수 있다)
대리점 사장들에게 교육
        ↓  (교육이 돼야 팔 수 있다)
영업 → 매출
```

**첫 단계가 백오피스다.** 본사 직원이 백오피스·영업환경·CS환경에 익숙하지 않으면
**대리점 교육 자체가 불가능하고, 체인이 거기서 끊긴다.**

⇒ 백오피스는 "관리 도구"도, "직원 업무 환경"에서 끝나는 것도 아니다.
🔴 **대리점 교육의 교재이자 실습 환경이다.**

### 🔴 그래서 CS 3축의 무게가 달라진다

| 축 | 종전 이해 | 지금 |
|---|---|---|
| ① 매뉴얼 | 상담원용 | **대리점 사장 교육 교재** |
| ② 교육 | 직원 몇 명 | **본사 직원 → 대리점 10곳 → 그 아래** |
| ③ 워크스페이스 | 편의 | 🔴 **영업 체인의 첫 단추** |

**"초등학생도 할 수 있는" 기준이 왜 그렇게 강했는지 이제 이해된다** —
본사 직원만 쓰는 게 아니라 **전국 대리점 사장들이 각자 배워서 써야** 한다.

### ⭐ 이것이 셀링포인트다 (사장님 명시)

> *"베타배포 이후 첫 정식배포의 셀링포인트"*

| 셀링포인트 | 내용 |
|---|---|
| **전환 고객** | 기존 5만 고객사가 레거시 → 새 히트판으로 |
| **신규 고객** | 대리점 10곳 영업망을 통한 신규 유입 |

⇒ 🔴 **MDB 마이그레이션이 셀링포인트의 심장이다.**
[ERP 화면 일정 §2-8](20260807_일정기록_ERP화면별_수정보완_9대영역_사장님지시.md) 에서
*"신규 고객의 첫인상을 좌우한다"* 고 적었으나, 실제로는 그 이상이다 —
**전환이 안 되면 5만 고객사가 움직이지 않는다.**

### 🔴 베타 대상 확정 — 기존 대리점 (사장님 지시 2026-08-07)

> **"일단 베타버전으로 테스트 배포는 기존 대리점들을 통해 할 것임."**

**베타 고객 = 일반 고객사가 아니라 기존 대리점이다.** 성격이 완전히 다르다.

| | 일반 고객 베타 (PM 이 가정하던 것) | 실제 — 대리점 베타 |
|---|---|---|
| 쓰는 사람 | 처음 보는 고객 | **레거시 히트판을 팔던 사람** |
| 목적 | 기능 검증 | 🔴 **기능 검증 + 대리점 교육 1회차** |
| 피드백 성격 | *"이거 안 돼요"* | *"이걸로 팔 수 있겠나"* — **영업 관점** |
| 실패 시 | 고객 1곳 이탈 | 🔴 **영업망 신뢰 훼손** |

### ⭐ 이 결정이 좋은 이유 (PM 소견)

| 이유 | 내용 |
|---|---|
| **관대한 첫 고객** | 레거시를 팔던 사람이라 맥락을 안다. 낯선 고객보다 오류를 견딘다 |
| **베타가 곧 교육** | §1-5 교육 체인의 *"대리점 교육"* 단계가 베타와 겹친다 — **두 번 안 해도 된다** |
| **피드백 질이 다르다** | *"이게 팔리냐"* 를 실제 판매자가 답한다. 기술영업팀장 기준 그대로다 |
| **전환 고객 접점** | 대리점이 기존 고객사를 안다. 5만 전환의 실마리가 여기서 나온다 |

### 🔴 그러나 위험도 다르다

| 위험 | 내용 |
|---|---|
| **신뢰가 걸린다** | 일반 고객 1곳이 아니라 **영업망 전체가 본다.** 첫인상이 나쁘면 팔 마음이 안 생긴다 |
| **입소문이 빠르다** | 대리점끼리 통한다. 사고 하나가 10곳에 즉시 퍼진다 |
| **8/02 전례** | 대리점 설치 실패 → **사장님께 직접 연락**이 유일한 경로였다. 그 구조가 아직 그대로다 |

⇒ 🔴 **사장님 최우선 지시 ①(베타 배포가 기능상 안전한가)의 무게가 여기서 확정된다.**
베타 대상이 영업망이므로, 4팀 "조건부 합격"을 그대로 내보내면 안 된다.

| 4 | 전환을 **어느 속도**로 하나 |
| 5 | 대리점 10곳의 **역할** — 영업만인가, 1차 CS 도 하나 |
| 6 | 대리점 교육을 **누가 언제** 하나 (베타와 겹치나) |
| 7 | 레거시 히트판 **운영 종료 시점**이 있나 |

### ✅ 확인됨 — 대리점이 **자기 회사에** 설치한다 (사장님 2026-08-07)

> **"대리점이 자기 회사에 설치해서 테스트 하는거임"**

**위험도가 크게 낮아진다.** 대리점의 고객사 자료가 걸리지 않는다.

| 항목 | 뜻 |
|---|---|
| **실제 고객사 자료 노출** | ✅ **없다.** 대리점 자기 회사 자료만 |
| 실패 시 피해 | 대리점 자기 업무 — **남의 사업이 멈추지는 않는다** |
| 헌법 #18·#22 | 여전히 적용되나, 3자 자료가 얽히지 않아 단순해진다 |
| 자료 손실 시 책임 | 대리점 본인 자료 — 3자 배상 문제가 아니다 |

### 🔴 그래도 가벼워지지 않는 것

| 항목 | 왜 |
|---|---|
| **영업망 신뢰** | 자기 회사 자료라도 **망가지면 안 판다.** 오히려 자기 일이라 더 예민하다 |
| **대리점 사장이 직접 겪는다** | 남의 PC 가 아니라 **자기 PC 에서 겪는 고장**이다. 인상이 깊게 남는다 |
| **입소문** | 대리점끼리 통한다. *"내 회사에 깔았다가 이랬어"* 가 가장 강한 말이다 |

### ✅ 자료 손실 위험 — 사장님 정정 (2026-08-07)

> **"이미 레거시 히트판을 메인으로 쓰고 있고, 뉴히트판ERP는 말그대로 테스트임"**

PM 이 *"대리점이 자기 레거시 자료를 옮겨보다 잃을 수 있다"* 고 적었던 것은 **틀렸다.**

| 항목 | 실제 |
|---|---|
| 대리점의 **메인 업무 시스템** | 🔴 **레거시 히트판.** 계속 그것으로 일한다 |
| 뉴 히트판 ERP 의 위치 | **테스트.** 업무를 옮겨오는 게 아니다 |
| 자료 원본 | 🔴 **레거시 쪽에 그대로 있다.** MDB 마이그레이션은 **복사**지 이전이 아니다 |
| 마이그레이션 실패 시 | 뉴 히트판 쪽만 비거나 틀린다. **원본은 무사하다** |

⇒ **자료를 잃는 경로가 없다.** 마이그레이션이 실패해도 대리점은 레거시로 계속 일한다.

### 그래서 MDB 마이그레이션의 성격이 바뀐다

**"자료를 잃느냐"가 아니라 "옮겨온 자료가 맞느냐"의 문제다.**

| | |
|---|---|
| 🔴 진짜 위험 | **틀린 채로 옮겨지는 것** — 건수는 맞는데 금액이 틀리다, 거래처가 누락됐다 |
| 왜 위험한가 | 대리점이 **레거시와 대조**해 본다. 안 맞으면 *"이건 못 판다"* 가 된다 |
| 판정 기준 | **원본 대조 가능성** — 레거시가 살아 있으니 대조가 실제로 일어난다 |

⇒ 마이그레이션의 합격선은 **"안 잃었다"가 아니라 "레거시와 숫자가 맞는다"** 이다.

### ⭐ 그리고 이 방식이 좋은 이유가 하나 더 있다

**대리점 사장이 자기 회사에서 직접 써 본다** = 판매자가 사용자가 된다.
- 팔기 전에 **자기가 먼저 써 보므로** 설명이 진짜가 된다
- *"이걸로 팔 수 있겠나"* 를 자기 업무로 판단한다
- **교육이 곧 실습**이다 — §1-5 교육 체인과 정확히 맞물린다

**PM 이 추측하지 않는다.** 오늘 *"사업자등록 전"* 을 확인 없이 인용해 틀린 것과 같은 실수를 반복하지 않는다(§6).

### 2-1. 공영정보(주)가 기존 히트판 업체라는 점

> *"기존 레거시 히트판 업체인 공영정보(주)"*

**우연이 아니라 자연스러운 귀속이다.**
- 레거시 히트판(VB + Access)을 팔던 곳이 새 히트판도 판다
- **기존 고객·영업망이 이미 있다**
- MDB 마이그레이션([ERP 화면 일정 §2-8](20260807_일정기록_ERP화면별_수정보완_9대영역_사장님지시.md))이
  왜 중요한지도 여기서 설명된다 — **그 회사의 기존 고객이 옮겨 탄다**

📌 ⚠️ 위 세 줄은 **PM 해석**이다. 사장님이 명시하신 것은 "귀속" 사실까지다.

## 6. PM 정정 기록

**PM 이 종전 전제를 잘못 유지했다.** 오늘 하루에도 여러 문서에
*"사업자등록 전이라 못 한다"* 를 근거로 적었다.

**왜 틀렸나**: 메모리에 남은 4월 기록(*"사업자등록 = 베타 이후"*)을
**확인 없이 계속 인용**했다. 사장님께 여쭙지 않았다.

**교훈**: 사업 구조는 **사장님만 아는 정보**다. 코드나 문서로 확인되지 않는다.
⇒ 제약을 근거로 무언가를 막을 때는 **그 제약이 지금도 유효한지 먼저 확인**한다.
