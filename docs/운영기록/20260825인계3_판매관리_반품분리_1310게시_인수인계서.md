## [2] 🔴 사장님이 정의하신 것 — 다음 세션 필독

### 매출반품 vs 매입반품 (2026-08-25 원문)

> **매출에 있는 반품** = 사용자의 고객사가 반품처리한 품목관리
> **매입에 있는 반품** = 사용자가 반품처리할 품목관리
>
> **매입의 반품처리(명세서)** = 내가 반품처리해서 고객에게 보낼 명세서 → **지급금액 −, 재고 −**
> **매출의 반품확인(확인서)** = 고객이 반품한 것에 대한 확인서 → **미수금액 −, 재고 +**
>
> **매입은 반품처리 / 매출은 반품확인** — 메뉴명도 명확하게 나눈다

⇒ 코드는 이 방향을 **이미 정확히** 지키고 있다(실측 확인). 화면만 묶여 있던 것.

### 매출반품 처리 규칙 (2026-08-25 원문)

> 1. 매출에서의 반품 = 판매한 물건이 고객사의 반품으로 재입고된 경우
>    = **파손이면 로스로 정의, 파손이 아니면 재입고(재고반영)**
> 2. **로스일 경우 로스율에 반영** = 로스율 판매수익성분석에, 이익률 감소반영(**그리드에 로스율추가**)
> 3. **판매순위표, 판매통계, 판매현황에는 반영빠지고**
> 4. **수주서, 수주현황, 거래명세서는 해당거래에 반품**(파손에는 파손이라고 표기)
>
> **회계에도 반영할 것(미수에서 −처리)**
> **세금계산서도 반영할 것** — 마이너스 계산서를 끊던, 계산서를 삭제를 하던

⇒ **1번·회계는 작6에서 완료.** 2·3·4·세금계산서는 **미착수**.

### 로스 판정은 고객사가 정한다

> **"로스판정 기준은 고객사가 정하는거지, 너가 왜 정해."**
> **"사유도 콤보박스로 두지 말고 텍스트박스로 자율적 기입하도록 하고,
>   자율적으로 기입한걸 텍스트박스로 선택하도록 해"**

⇒ 작6 반영 완료. 우리가 사유 코드를 깔지 않는다(헌법 #11 과 같은 축).

### 4-A. 판매목록 조회 버튼 개편 (1.3.10 반려 2번 + 추가 지시)

> **판매목록 조회에서 계산서 발행 버튼을 "판매확정" 버튼으로 변경**
> **전자발행 버튼을 "계산서 발행" 버튼으로 변경 → 계산서 발행버튼 클릭시, 전자발행으로 버튼상태가 변경되도록**
> **판매확정버튼 누르기 전에는 계산서 발행버튼 비활성화**

🔴 **실측으로 드러난 것 (중요):**
- 현 「계산서 발행」 버튼 → 실제로는 **`BulkConfirmAsync` = 판매확정**.
  다이얼로그 문구도 *"확정 처리하시겠습니까?"* ⇒ **이름만 틀렸다. 사장님 지시가 맞다.**
- 현 「전자발행」 버튼 → **아무 일도 안 한다.** 확인창 띄우고 `Search()` 로 목록 새로고침만.
  서버 호출 0. ⇒ **가짜 버튼.** 이름만 바꾸면 「계산서 발행」이라는 가짜 버튼이 된다.
- 상태 라벨은 **이미 사장님 표현과 일치** — `confirmed`="판매확정", `invoiced`="계산서발행"

⇒ **착수 전 결재 필요**: 이름만 바꿀지, 실제 발행 동작까지 만들지.
   (세금계산서 차수와 한 몸이라 함께 볼 것)

### 4-B. 반품 연결 버튼 (1.3.10 반려 2번) — **결재 완료, 구현만 남음**

> **판매목록 불러오는 버튼이 있어야 됨. 거래명세서 판매목록조회에도 반품으로 상태변경하는
> 버튼이 있어야됨. → 당연히 반품확인서에 자동반영**

**착수 전 결재 완료:**
- 판매목록 「반품」 → **반품확인서 초안 생성 후 열기** (사용자가 수량·로스 고친 뒤 확정)

- 거래명세서 상세 조회 `DeliveryService.GetAsync` 가 품목까지 가져온다
