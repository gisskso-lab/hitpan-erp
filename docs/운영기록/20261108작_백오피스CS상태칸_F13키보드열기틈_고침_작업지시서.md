## §2 [범위]
### 하는 것
- ① 틈 안 Enter · Space 다시 누름 → 끝 초점 = 그 줄 단추 · 목록 닫힘 · 고름 0.
- ② 틈 안 Tab · Shift+Tab → 끝 = 목록 닫힘 · 초점 그 줄 단추(9.3 목록 안 Tab 의 끝과 같게).
- 둘 다 **키보드(Enter · Space)로 연 목록에만**. 마우스로 연 목록의 다시 클릭 · Tab 은 지금 판 그대로.

### 하지 않는 것 (범위 밖 · 기록)
- **③ 키보드로 열고 바깥 클릭** — 끝 상태(`BODY`)가 마우스 · 지연 0 대조와 같다([1-V] §4 ③). 빈 곳 클릭 → `BODY` 는 브라우저 표준. 칸에서 단추로 돌리면 「키보드로 연 경우만 단추 · 마우스는 BODY」 로 **갈라져** 대표 · ERP 매니저 결정이 생긴다 → 손대지 않음. 남는 것 = 중간에 목록 안 초점이 0.6~1.2초 생겼다 사라지는 것 하나(후보 3 JS 로만 막힘 · 후순위). 개발명세서 §10 · [4] 리뷰서에 「③ 범위 밖 · 대조와 같음」 한 줄.
- 9.3 쪽 첫 항목 초점 늦음 자체 = 라이브러리 몫(F12 §13-7 그대로) · 판 올림 · 하위 메뉴 도입 = 재검 대상.
- [1-V] 후보 3(JS 덧대기) — §4 꼴이 [4] 에서 빨강일 때만 설계 보고(만들지 않음).
- 순수 빈 곳 클릭 · 화면읽기 프로그램 · Linux · 2번 줄 이하 = [1-V] §7 미측정 그대로 · 이 문서가 넓히지 않음.

## §3 [다시 누름의 바른 결과]
[1-V] §4 덧붙임: 같은 다시 누름이 틈 안에서는 「닫기」, 첫 항목 초점 뒤에는 「첫 항목 고르기」 다. 갈림을 무엇으로 정하나:

| 초점 자리(누르는 순간 · 브라우저) | 바른 결과 | 근거 |
|---|---|---|
| **그 줄 단추**(틈 안) | **닫기 · 초점 그 줄 단추 · 고름 0** | 9.3 단추 `OnClick=ToggleMenuAsync`(L625~655 · 열렸으면 `CloseMenuAsync`) = 메뉴 단추 토글. 마우스로 다시 클릭한 끝(단추)과 같다. 지금 `BODY` 인 것은 늦은 첫 항목 초점이 목록과 함께 지워져서 — 토글 뜻은 맞고 끝 자리만 틀림 |
| **첫 항목**(초점 표시가 목록 안에 보인 뒤) | 그 항목 고르기 · 닫힘 · 초점 단추 | 9.3 표준(목록 항목 Enter = 고르기 · `MudMenuItem` L150~155 `CloseAllMenusAsync`) · [1-V] §3-2 고름 15/15. **손대지 않는다** |

- 왜 하나로 합치지 않나: 「둘 다 고르기」 는 틈 안 다시 누름이 **사용자가 못 본 항목으로 상태를 바꾼다**(서버 쓰기 · 되돌리기 어려움) → 금지. 「둘 다 닫기」 는 9.3 목록 항목의 Enter 를 바꿔야 해 칸 밖 · 표준 위반 → 범위 밖.
- 고름이 일어나는 길은 **목록 안에 초점 표시가 생긴 뒤** 하나뿐이다(키 사건이 목록 항목에서 난다 — 팝오버는 칸 DOM 밖이라 칸 `@onkeydown` 까지 안 온다). 이 문서의 고침은 그 길에 손을 대지 않는다 → 고침이 만드는 고름 = 0.
- 오히려 줄어드는 위험: 지금 ② 끝 상태(목록 열린 채 · 초점 1번 줄 첫 항목)에서 사용자가 「2번 줄에 왔다」 고 믿고 Enter 를 누르면 **1번 줄 상태가 한 번에 바뀐다**. 고침 뒤에는 닫힌 단추라 Enter 가 목록을 여는 데서 멈춘다(바뀌려면 한 번 더 눌러야 하고 그 사이 열린 목록이 보인다).
- 확인 필요(낮음 · 기록 추천): 느린 회선에서 「단추에 초점 / 첫 항목에 초점」 을 눈으로 가르기 어려운 0.5~1.3초 구간은 9.3 표준 그대로 남는다. 이 문서의 범위는 「틈 안 결과가 `BODY` · 열린 목록이 아니게」 까지.

    //    · 열림은 9.3 OpenChanged 로만 안다(L53~56 WithEventCallback · L525 · L586 SetValueAsync) — _menu.Open 은 늘 false(위 E1-a 주석).
    //    · 받는 쪽 없는 EventCallback = 이 칸을 다시 그리지 않는다. 다시 그리면 MudMenu 도 다시 그려지고, 열린 동안
    //      _focusedIndex == -1 이면 L1016~1027 이 래퍼 초점 · 첫 항목 초점을 또 보낸다.
    //    · 칸 @onkeydown 은 단추에 초점이 있을 때만 키를 받는다 — 목록(팝오버)은 칸 DOM 밖이라 항목 위 Enter(고르기)는 여기 안 온다.
    //    · 🔴 9.3 판 올림 · 하위 메뉴 도입 시 재검 — L53~56 · L495~554 · L625~655 · L981~1029 의존(20261108작 F13 지시서 §4).
    private bool _open;          // 9.3 이 알려 준 열림
    private bool _openedByKey;   // 이번 열림이 칸에 온 엔터·스페이스 뒤에 열렸나(마우스로 연 목록은 손대지 않는다)
    private bool _keyArmed;      // 단추에서 엔터·스페이스 keydown 이 칸까지 올라왔다
    private EventCallback<bool> MenuOpenChangedNoRender => new(null, (Func<bool, Task>)OnMenuOpenChangedAsync);

    private async Task OnMenuOpenChangedAsync(bool open)
    {
        _open = open;
        if (open) { _openedByKey = _keyArmed; _keyArmed = false; return; }
        // ① 키보드로 연 목록을 단추 다시 누름(엔터·스페이스 → 9.3 토글 L653~654 CloseMenuAsync)으로 닫았다.
        //    바깥 클릭(R L128 OnClosed) · Esc(위 고침 A) · 항목 고르기(MudMenuItem L155)는 _keyArmed 가 거짓 → 손대지 않음.
        var restore = _openedByKey && _keyArmed;
        _openedByKey = false; _keyArmed = false;   // 🔴 await 전에 비운다 — 아래 호출이 이 손잡이를 다시 불러도 거기서 끝난다
        // 닫힌 뒤 부름 = L525 같은 값(전이 0 · 콜백 0) + L553 FocusActivatorAsync → 늦은 첫 항목 초점 → 목록 제거 → 단추 초점 순서.
        if (restore && _menu is not null) await _menu.CloseAllMenusAsync();
    }

    private async Task OnGapKeyAsync(KeyboardEventArgs e)
    {
        if (_menu is null) return;
        if (e.Key is "Enter" or " ") { _keyArmed = true; return; }
        // ② 키보드로 연 목록이 열린 채 단추에서 Tab · Shift+Tab — 9.3 목록 안 Tab 길(L986~988)과 같은 끝(닫힘 · 단추).
        if (e.Key == "Tab" && _open && _openedByKey) await _menu.CloseAllMenusAsync();
    }

### §5-2 「Tab 이 한 번 안 먹힘」 체감
| | 틈 안 Tab 끝 | 사용자가 보는 것 |

| 지금 | 1번 줄 목록 열린 채 · 초점 첫 항목 | 2번 줄로 간 듯하다 약 0.3초 뒤 1번 줄 목록 안으로 끌려감 · Enter 한 번 = 1번 줄 상태 바뀜(§3) |

- B 의 끝 = 9.3 이 지연 0 에서 이미 내는 끝. 「Tab 이 한 번 안 먹힘」 은 고침이 새로 만드는 것이 아니라 **9.3 표준 체감을 느린 회선에도 똑같이** 주는 것. 「Tab 이 간 자리를 지킴」 은 B 로 불가(서버가 Tab 이 간 곳을 모름) → E(JS)만 가능 · 후순위.

### §5-3 `Open` 매개 양방향 처리 (원문 확인)
- `Open` = `[Parameter, ParameterState]`(L401~403) · `OpenChanged` = `EventCallback<bool>`(L408~409) · 생성자 L53~56 `RegisterParameter(nameof(Open)).WithParameter(() => Open).WithEventCallback(() => OpenChanged).WithChangeHandler(OnOpenChanged)`.
- `OnOpenChanged`(L482~486)는 **부모가 넘긴 `Open` 이 바뀔 때** 열기/닫기를 부르는 손잡이다. B 는 `Open` 을 **넘기지 않는다** → 부모 쪽 값 변화 0 → L482 안 불림 → 9.3 내부 상태(`_openState`)와 다툼 0. `OpenChanged` 만 받으면 9.3 이 L525(`false`) · L586(`true`) 에서 `SetValueAsync` 할 때 알림만 온다.
- 🟡 확인 필요(원문 사본 밖): `ParameterState<T>.SetValueAsync` 가 **① 값이 바뀔 때만 ② 값을 먼저 넣고 콜백**을 부르는지. 사본 `mudsrc93/` 에 파일 없음 → §8 멈춤 1([3] 착수 전 원문 확인). 순서가 반대여도 B 는 플래그를 `await` 전에 비우므로 재귀는 한 번에서 끝난다(§6 ⑤) — 다만 그 경우 키 가로채기 해제가 두 번 불려 `JSException`(L513~523 잡힘) 가능 → [4] C7 로 잰다.

### §5-4 F12 와 겹침 정리
- **고침 A(Esc 줄)**: 글자 무변. B 의 (나) 한 줄은 그 위에 끼운다 → Esc 는 `OnGapKeyAsync` 를 지나 아무것도 안 하고 고침 A 로 간다. Esc 로 닫힐 때 `OnMenuOpenChangedAsync(false)` 가 불리지만 `_keyArmed` 거짓 → 복원 이중 0.
- **A2(F12 C1 빨강일 때 · 미발생)**: F12 §13-5 A2 꼴은 람다 `OpenChanged` + `_open` 이다. B 가 먼저 들어가면 A2 = Esc 줄에 `|| !_open` 조건 하나(B 의 `_open` 재사용 · 새 `OpenChanged` 0). F12 [4] 가 C1 빨강을 먼저 내면 A2 는 **B 의 받는 쪽 없는 꼴로** 만들고 F13 [3] 이 그 필드를 재사용 → §9 D24.
