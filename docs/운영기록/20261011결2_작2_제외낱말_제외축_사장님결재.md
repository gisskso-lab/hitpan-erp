## §2 결재 ① — 「제외」는 **낱말 교체 + 등록 입구 신설**로 간다 🟢 승인

### 올린 내용 (PM)
사장님 오더는 *「요금제 넣고, 요금제 제외 버튼을 추가로 넣을것」* 이었다.
실측해 보니 **기능은 `main`(`16669004`)에 이미 있었고 낱말이 「비활성화」였다.**
없던 것은 기능이 아니라 **사장님이 쓰신 말**이었다. ⇒ 범위를 이렇게 좁혔다.

| | 전 | 후 |
|---|---|---|
| 상태 표시 | 활성 / 비활성 | **판매중 / 제외됨** (아이콘 + 색) |
| 버튼 | 비활성화 / 활성화 | **제외 / 포함** |
| 설명 | 없음 | **「지워지지 않습니다 · 다시 포함할 수 있습니다」** 를 화면이 직접 말한다 |

🔴 **진짜로 없던 것은 등록 입구**였다 — 운영 `pricing_plans` 가 **0행**인데 종전 화면에는
**고치는 입구만** 있어서 **첫 등록 자체가 불가능**했다. 그것을 새로 냈다(`POST api/admin/pricing/plans`).

### 승인된 결론
- **별도 버튼을 더 넣지 않는다.** 「제외 / 포함」 한 쌍이 정본 낱말이다.
- 호출 경로·서버 코드는 **무접촉**(`ToggleActive` 한 글자도 안 바뀜) — 승인된 상태 그대로.
- 🚫 **다음 사람이 「제외 버튼이 없다」고 다시 신설하지 마라.** 이 결재가 그 자리의 근거다.
  🔴 교훈: **사장님 낱말과 코드 낱말이 다를 수 있다.** 「없다」고 말하기 전에 **다른 낱말로 한 번 더 찾아라.**

## §3 결재 ② — 「제외」 축은 **과금 축(`is_active`) 단독** 🟢 승인

### 올린 내용 (PM)
지금 「제외」는 **요금제를 안 팔리는 상태로** 만든다(`is_active = 0`). **랜딩 노출(`is_visible`)은 안 건드린다.**
사장님 이유에 「베타 테스트시 필요」가 있어, **「랜딩에서만 감추고 과금은 유지」**가 필요하면
**다른 축**이 맞다고 올렸다. 과금 축이 둘로 갈라지면 **나중에 돈 계산이 어긋나므로** 임의로 안 건드렸다.

### 🔴 2026-10-11 정정 — 내가 「과금」이라고 쓴 것이 틀렸다 (추가 결재 1건 올림)

[4] 독립검증이 `pricing_plans` **소비처 7곳을 전수로** 재서 뒤집었다(리뷰서 §5-1ⓑ):

| 「제외」가 막는가 | 실측 |
|---|---|
| 공개 요금표·랜딩 노출 | 🟢 **막는다** (`LandingPublicController` · `PromotionsAdmin` 둘 다 `is_active=1 AND is_visible=1`) |
| 신규 **가입 입구** | 🔴 **안 막는다** — 요금제 존재·`is_active` 확인이 **0건**. 그 코드로 가입 요청은 그대로 들어간다 |
| 쓰고 있는 고객사 **과금** | 🔴 **안 막는다** — 구독·청구 경로에서 `is_active` 를 읽는 코드 **0건** |
| 기기 상한 | 🔴 **안 막는다** — `DeviceRegistration` 의 JOIN 이 `is_active` 를 **무조건 무시** |

⇒ **지금 「제외」의 실효 범위는 「새 고객에게 안 보인다」 하나다.**
내가 §3 에 쓴 「**과금·판매 축**을 내린다」는 **코드가 뒷받침하지 않는 서술**이었다. 그대로 두면
다음 사람이 「제외했으니 과금이 멈췄다」고 읽는다 ⇒ 아래로 바꿔 적고, 화면 문구도 고쳤다(V-10).

🔴 **추가 결재 올림**: 사장님이 쓰신 이유가 「베타 테스트시 필요」였습니다.
- ㉮ **「새 고객에게 안 보이게」** 면 → **지금 구현으로 충족.** 추가 작업 0건
- ㉯ **「그 요금제 과금을 멈춰라」** 면 → **별건 트랙 필요**(구독 축 · §4-3 대리점 면제와 같은 자리)

### 승인된 결론
- **축은 하나다 — `is_active`.** 「제외」는 **요금제 안내(랜딩·공개 요금표)에서 뺀다.**
  🔴 과금·기기상한까지 멈추는 것은 **지금 구현에 없다**(위 정정 · ㉯ 결재 대기).
- **랜딩 노출(`is_visible`)은 이 버튼이 건드리지 않는다.** 종전 동작 그대로.
- 🔴 **등록 입구가 `is_active` 를 입력으로 받지 않는 것도 승인된 설계다** —
  받으면 포함/제외가 **두 입구로 갈라져** 과금 축이 둘이 된다. 새 요금제는 출하 DDL 기본값(=포함)으로 선다.
- 🚫 **앞으로 「제외」에 `is_visible` 을 끼워 넣는 변경은 별건이고 사장님 결재 대상이다.**
  필요가 생기면 **「랜딩에서만 감추기」라는 다른 이름의 기능**으로 올린다 — 같은 버튼에 섞지 않는다.
  근거: 계정 과금 축을 둘로 가르지 않는다는 기존 방침과 한 몸이다.

## §4 🚫 이 결재에 **포함되지 않은 것** (범위 확장 금지)

| # | 포함 안 됨 | 왜 |
|---|---|---|
| 1 | **머지** | 머지 결재(오더 ②)는 별도이고 **조건 2건**이 남아 있다 — ⓐ CI 초록 ⓑ [4] 독립검증 판정. 이 결재는 그 조건을 면제하지 않는다 |
| 2 | **운영에 요금제를 실제로 넣는 것** | 화면에서 넣을 수 있게 된 것까지가 작2 다. **무엇을 얼마로 넣을지는 사장님 결재** |
| 3 | **대리점 구독요금 면제정책** | 요금제(상품) 축이 아니라 **고객사·대리점 속성** 축 ⇒ **별건 트랙**(인계2 §4-4) |
| 4 | **게시(배포)** | `production` 승인은 사장님 손. 🚫 PM 임의 금지 |
| 5 | **ERP 쪽 변경** | 작2 는 ERP 무접촉. 전달 통로는 **다음 작업**(인계2 §6) |
