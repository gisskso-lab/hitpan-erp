## 1. 오더를 이렇게 이해했다 (명문화)

### 사장님 의중

**① 판정 대상을 바꾼다 — 이것이 설계의 핵심**
지금은 **브라우저에게 "너 누구냐"** 를 묻는다(지문). 브라우저는 자기 안에만 흔적을 남기니
Edge 와 Chrome 이 각자 다른 답을 하고, **같은 PC 가 2대로 세어진다.**
사장님 안은 묻는 대상을 **기기에 발급한 인증키**로 바꾼다. 추측을 정교하게 하는 게 아니라
**애초에 추측을 안 하게** 만든다.

**② 막되 가두지 않는다**
로그인·접속은 열고, 메뉴만 잠근다. 화면이 "기기인증을 먼저 진행하세요"라고 말해준다.
로그인부터 막으면 고객은 뭐가 잘못됐는지 모르고 전화한다 — 혼자 풀 수 있어야 한다(히트판 정신).

**③ 차단 장치가 아니라 판매 경로다**
한도가 차면 직원에게는 "관리자 문의", **대표계정에는 슬롯 구매 제안**이 뜬다.
슬롯 1개 = 1만원. 막는 김에 판다. 등록기기 관리가 곧 과금 화면이 된다.

**④ 승인 권한은 대표계정에**
슬롯이 남든 없든 **모든 기기는 대표계정을 거쳐** 들어온다. 돈이 걸린 자원이라 문지기가 필요하다.

**⑤ 기존 사용자를 막지 않는다 + 개발 중 끌 수 있어야 한다**
사장님 지적: *"개발하면서 슬롯을 다 써서 테스트도 못하는 상황이 올수 있음"*
→ 우리가 만든 기능 때문에 우리가 테스트를 못 하는 자리다. **끄는 스위치를 처음부터 넣는다.**
급할 때 코드를 뒤져 주석 처리하는 게 아니라 **설정 한 줄**로 끈다.

## 5. 검증 방법 (SoD)

**[3-V] 동시 병렬검증** — 보안상무 안철수
- 최우선 반증: **"기존 기기가 안 막히나"** (F 가 진짜 동작하나 — 4차 사고 계통)
- 차순위: **"스위치를 끄면 정말 다 열리나"** (개발 자기잠금 방지)
- 적발 → `docs/검증/병렬이슈/`

**[4] 최종 검증** — 검증팀장 데이비드 박
- [ ] 빌드 errors 0 + warnings 0
- [ ] ddl-smoke (DDL 변경 시)
- [ ] 독립 반증 3건 이상
- [ ] **실측 (Sandbox `test1.hitpan.kr`)**:
  1. 🔴 **스위치 꺼짐 상태에서 기존 계정 4개 로그인·메뉴 정상** (최우선 회귀)
  2. 스위치 켜고 → 기존 기기 **안 막힘**(F)
  3. 새 브라우저 접속 → 로그인 되나 / 메뉴 잠기나 / 안내문 뜨나
  4. [기기 인증하기] → 대표계정 승인함에 뜨나 → 승인 → 메뉴 열리나
  5. 슬롯 채운 뒤 → 직원 "한도초과" / 대표 "슬롯 추가?" 양쪽 다 뜨나
  6. Y → 랜딩 이동 / N → 변경·차단 선택지
