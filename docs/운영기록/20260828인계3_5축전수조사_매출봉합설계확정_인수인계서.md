### 현장팀 신규 발견 P0 2건 (아무도 안 본 자리)

**명세서 취소 → 과거 반품 증발** (`SalesService.cs:1181`)
```sql
SET total_sales = (SELECT SUM(total_amount) FROM sales_deliveries WHERE ... status='confirmed')
```
- `sales_returns` 를 안 뺀다. 매출을 **명세서만 보고 통째로 다시 쓴다**
- 시나리오: 4월 200만원 반품 → 5월 **전혀 다른 오타 명세서 1장 취소** → 미수가 1,000만원으로 **부활**
- 🔴 조용하다. 오류도 경고도 없다. **매입엔 이 코드가 없다 — 또 매출만**

**업체별 원장이 「돈 원장」이 아님**
- `stock_ledger` 단일 테이블을 읽음. 상품별 원장과 **완전히 같은 쿼리**, `GROUP BY` 만 다름
- 「잔량」이 금액이 아니라 **개수**. 부가세·미수금 잔액·전표별 줄·이월잔액 **전부 없음**
- 🟢 다만 `partner_balance.balance` 는 **정확하다** — 고칠 것은 계산이 아니라 **화면이 어느 표를 보느냐**
- 영업: 더존·이카운트에서 「거래처원장」은 **미수금 대사 화면**. 데모에서 수량이 나오면 **제품 카테고리를 의심받는다**

## 4. 🔴 사장님 결재 8건 — 이번 봉합의 뼈대

### 결재 1 — 기본 로직 (판정 기준)
> "워크플로우 흐름으로 **금액값은 회계로, 상품재고값은 재고로 정합하게** 나와야 하고,
> 이 값을 **상품이냐, 업체냐의 필터링으로 원장이 정확하게** 나와야 되."

```
매입 → 재고 IN  + 지급금 ↑     지급 시 → 지급금 ↓
매출 → 재고 OUT + 미수금 ↑     수금 시 → 미수금 ↓ · 현금 ↑ · 부가세는 매출 시점 기입
원장 → 위 둘을 반영 · 상품 축 / 업체 축
```
⇒ 조사 결과 **이 로직 자체는 코드에 살아 있다.** 틀린 건 **반품·취소가 세 곳에 고르게 안 닿는 것**.

### 결재 2 — 매출반품 메뉴가 아니라 마이너스 전표
> "전자발행이 이미 되고 월마감이 되서 손대지 못하는 건에 대해선 매출반품이라는 메뉴를 만드는 것보다
> **마이너스 전표처리를 하는 게 가장 깔끔해.** 하지만 이 마이너스 전표의 근거가 뭔지는
> **분명하게 사슬로 연결**을 시켜야해."

**국세청 이세로 방식과 동일** — 계산서에 「수정」 개념이 없고 **마이너스 상계 + 재발행**만 있다.
8/25 결재(매출 반품확인 메뉴 전부 제거)와 **같은 방향**.

### 결재 3 — 마이너스가 수주까지 올라간다
```
수주      1 + (-1) = 0
명세서    1 + (-1) = 0     ← 쌍둥이로 묶여 따라다닌다
```
🔴 **PM 판단 정정**: "마이너스는 되돌리는 장치일 뿐 중복 생성은 못 막는다"고 본 것이 **틀렸다.**
마이너스를 명세서 층에만 두고 생각해서였다. **사슬 위로 올리면 층마다 0이 된다.**

### 결재 4 — 잔량 기준 (분할출고 허용)
```
출고:  수주 잔량 = 주문수량 − 기출고수량   →  잔량 0 이면 차단
반품:  품목 잔량 = 판매수량 − 기반품수량   →  잔량 0 이면 차단
```
🔴 **이 한 줄로 P0-1과 P0-2가 동시에 풀린다.** 별개 봉합 2건으로 본 것이 같은 원리의 양면.
⚠️ **현재 8/27 작11 가드가 정상 분할출고를 막고 있다.** 코드는 원래 잔량 로직(`OrderedQty - DeliveredQty`)을 갖고 있었는데 가드가 덮었다.

### 결재 5 — 화면을 새로 만들지 않는다
```
판매목록 그리드 ─ [반품하기]
거래명세서 작성 ─ [세금] [반품하기]
        ↓
같은 거래명세서 화면 — 수량·금액이 (−)로 전량 채워진 상태
  · 반품 안 할 품목은 줄을 지운다   · 수량 수정 가능
  · 이미 반품된 품목은 잔량만큼만   · 거기서 마이너스 계산서까지 끊는다

목록 조회:   명-001    1,000,000
             └ 명-001R  -1,000,000   ← 원전표 바로 아래
```
- 담당자가 이미 아는 화면 → 히트판 정신 통과
- 원전표에서 눌러 들어오니 **근거 연결 자동**
- 잔량이 채워지니 **수량 상한 자동** — 가드로 막는 게 아니라 **넘을 경로가 사라짐**
- 목록 배치가 **경리의 검증 화면**이 됨

### 결재 6 — 반품 누적은 품목 단위
```
명세서: A 10개 · B 5개
A -7 OK → A -2 OK(누적9) → A -1 OK(누적10 소진) → A -1 차단
B -5 OK  ← A와 무관
```
전량 소진된 명세서면 **버튼 자체가 비활성**.

### 결재 7 — 상태 한글 통일
```
수주서    수주완료 → 판매완료 → 판매확정 → 계산서발행 → 전자발행
거래명세서          판매완료 → 판매확정 → 계산서발행 → 전자발행
                      │          │                    │
                    삭제        취소              반품완료 → 반품확정
              (원장 무접촉) (원장 역기록)      (마이너스 전표) (국세청 발송)
```

| 상태 | 뜻 | 이 시점에 일어나는 일 |
|---|---|---|
| 수주완료 | 수주 완료 (수주서 전용) | 원장 무접촉 |
| 판매완료 | 거래명세서 작성·저장 | 원장 무접촉 |
| **판매확정** | 판매확정 버튼 누름 | **재고 OUT · 미수금 ↑ · 분개** |
| 계산서발행 | 계산서 임의발행 (일괄발행 대기 포함) | 세금 문서만 |
| 전자발행 | 국세청 전송 완료 | 되돌릴 수 없음 |
| **반품완료** | 마이너스 전표 O · 국세청 **미발송** | **재고 IN · 미수금 ↓ · 역분개** |
| **반품확정** | 마이너스 전표 O · 국세청 **발송** | 상계 완결 |
| 취소 | 판매확정 이후 되돌림 | 원장 역기록 |

**추가 결정**:
- **① 워딩만 변경** — 상태 개수 그대로, 이름만 한글로 (마이그 부담 감소)
- **② 「분할출고」는 상태가 아니라 표시(뱃지)** — `판매완료 [분할출고]`. 거래조건이 다양해서(잔금까지 받은 경우·계약금만) 상태로 쪼개면 조합 폭발
- **③ 마이너스 명세서는 같은 상태 + 부호로 구분** — 별도 상태 안 만듦
- **④ 취소 상태 유지** — 계산서는 2단(삭제/마이너스)인데 **명세서는 3단(삭제/취소/마이너스)**. 판매확정 시점에 이미 재고가 움직여서

|---|---|---|
| 판매완료 | **삭제** | 흔적 없이. 목록·현황·분석·통계에서 전부 빠짐 — **사슬 자체 삭제** |
| 판매확정 · 계산서발행 | **취소** | 원장 INSERT ONLY(#3)라 **역기록으로 상계**하고 상태로 남김 |
| 전자발행 | **마이너스** | 국세청에 갔으니 물리적으로 못 지움. 마이너스 전표로 상계 |

### 결재 8 — 확정 건 삭제·수정은 2단으로
> "권한가진자만 **확정** 상태를 삭제, 수정할 수 있도록 — 이건 **당연히 지금 동작하고 있는 거지.**
> 권한가진자 **패스워드 한번 더 입력.**"

```
1단  권한 검사        ← 이미 동작 중 (신설 아님)
2단  패스워드 재입력   ← 이번에 신설
```
**다이얼로그 문구(사장님 지정)**: `"확정된 거래 입니다. 취소하시려면 패스워드 입력이 필요합니다"`

- 대상: **판매확정 · 반품확정** + 그 이후 단계(계산서발행 · 전자발행)
- **삭제뿐 아니라 수정도** 대상
- 🔴 **1단이 정말 동작 중인지 실측 필요** — 오늘 하루에만 "이미 되어 있다"가 두 번 틀렸다

## 5. 이번 작업 범위

### 🟢 이번에 한다 — 매출라인
- **명세서 중복 · 반품 상한** — 잔량 기준 통일
- **마이너스 전표 사슬** — 명세서 +1/-1 · 수주까지 전파 · 원전표 아래 배치
- **반품하기 버튼 2곳** — 판매목록 그리드 · 거래명세서 `[세금]` 옆
- **명세서 취소 → 사슬 삭제** — 목록·현황·분석·통계에서 전부 빠짐
- **상태 한글 전환** — 판매라인 모든 버튼·전표작성칸·목록
- **확정 건 삭제·수정 시 패스워드 재입력**
- **업체별 원장** — 쓸 수 있는 화면으로
- **전표 생성 배선** — 사장님 승인, **매출 쪽에 넣음**

### ⏸ 다음 차례 — 계산서 파트
- 마이너스 계산서 **화면** (서버 API 있으나 Web에서 부르는 코드 **0건**)
- **국세청 전송** (`etax_status` 움직이는 코드 없음)
- **부가세 신고 상계** (매출측 `sales_returns` UNION 누락)
- **매입매출장 매출반품 행**
- **매입라인 상태 한글 전환** — 이번엔 판매만. 매입·매출이 한동안 다른 어휘를 쓰게 됨

## 6. 🔴 착수 순서 (검증팀 권고 반영)

| 단계 | 내용 | 왜 이 자리인가 |
|---|---|---|
| **1** | 🔴 **CI에 DB 잡 신설** | 없으면 새 게이트도 전부 SKIP. **안 고치면 오늘 일이 반복** |
| **2** | **탐지 먼저** — 정합성 검사 매출 대칭 + 오염 건수 확정 | 대조군 없이 고치면 봉합 후 "0건"이 증거가 안 됨 |
| **3** | 🔴 **게이트를 봉합 전에 짜서 빨간불 확인** | 초록이면 가짜. **게이트는 봉합자가 짜지 않는다**(SoD) |
| **4** | **상태 한글 전환 + 봉합** | 상태가 먼저 서야 버튼·목록을 한 번에 맞춤 |
| **5** | 교차검산 등식 + 무력화 시험(봉합자 아닌 사람이) | 하나라도 초록이면 그 게이트는 가짜, 미완료 |

### 🟢 사장님 판정식이 그대로 게이트가 된다
`GetStockLedgerAsync` 는 `view="item"` 과 `view="partner"` 가 **같은 `stock_ledger` 를 읽고 GROUP BY만 다르다**(`ReportService.cs:2532~2590`).
⇒ **같은 사실의 두 절단이니 총합이 반드시 같아야 한다.** 봉합이 깨지면 재고는 2배 빠지는데 회계는 1배라 **반드시 FAIL**. 글자로는 절대 못 만드는 게이트.

## 7. 🔴 착수 전 확인 4건

1. **패스워드 재입력 방식** — **로그인한 본인** 비밀번호로 맞는지 / 유효시간 둘지(연속 작업 시 매번 물으면 번거로움) / 이력 남길지. **1단 권한검사가 실제로 동작하는지 실측 선행**
2. **수주 `closed` 2건** — 새 정의에 그 이름이 없음. 진행 단계에 따라 재분류 필요
3. **기존 매출반품 데이터** — PM 의견: **과거분 그대로, 신규만 마이너스 축**. 전환하면 원장에 세 겹이 쌓여 장부를 못 읽게 됨 (원장 INSERT ONLY)
4. **철자 갈림** — 매출반품 `canceled` / 명세서 `cancelled`. 한글 전환으로 자연 해소되나 마이그 시 양쪽 다 봐야 함

**2·3·4는 PM 판단으로 작업지시서 초안에 넣고 결재받는 것이 빠름. 1만 사장님 답 필요.**
