## §0. 사장님 확정 (토론 대상 아님 — 작7 §0 원문)
1. 백오피스 존재 이유 = ① 본사·대리점의 고객 구독관리·고객 CS관리·영업 ② 본사의 대리점 실적·수수료 정산. **이 둘뿐.**
2. 두 목적을 **하나의 일관된 워크플로우**로 잇는다.
3. 계층관리 정의 전부 = **본사(마스터: 모든 고객사·모든 대리점 영업현황·CS현황 접근) / 대리점(자기 영업현황·CS현황만)**.
4. 설계의 첫 축 = 워크플로우 흐름. 7개 영역은 흐름 위에 얹는다.
5. 현상 인식: "지금은 설치·인증번호·연결 정도만 하고 있지 빈 껍데기" — 선행검증 A·B·C 가 실측으로 확인(작동 15 / 부분 3 / 권한 막힘 5 / 고아 4 · API 0 화면 18 · 없는 API 부르는 화면 6).

## §2. R1 현장팀 의견 (각자 사실 A·B 만 읽고 작성 · 원문 그대로)
### ERP 매니저

|---|---|---|---|---|
| 1 결재과금 | 본사 결제담당 · 매달 정산 마감 전 대리점별 금액 확인 | 결제상태 · 대리점 정산합계 · 수수료율 | 숫자 틀려도 모르고 송금 — 정산 사고 | `confirmed` 저장 vs `approved` 집계(A②) ⇒ 화면이 떠도 0원 · 수수료 0.15 고정(B 3-5) |

**7개 밖 제안(결정은 사장님)**: CS 화면에서 그 고객사의 **결제 상태를 같이** — 결제 사고가 CS 문의로 들어오는 게 현장 패턴. 1번+2번을 한 화면에 묶는 설계 요청(#20 흐름).

**사장님께 여쭐 것**: ① 정산 집계 기준 `approved`/`confirmed` 통일 ② 권한 역할명을 실무 기준 하나(본사관리자/대리점관리자/대리점직원 등)로 정리 · 이번 범위 포함 여부 ③ CS 기록의 #18·#22 경계(처리상태·요약 같은 메타만인지).

### 마케팅팀장

**① 30초 설명 테스트 — 7개 전부 🔴**: 지금 설명하면 **전부 거짓말**이 된다. 결재과금(`/admin/billing` 빈 화면 · 토스 금액 서버 대조 0) · CS기록(테이블 없음) · 권한계층(실동작 역할 `super_admin` 하나) · 영업현황(`sales-stats` 서버 없음 — 대리점 첫 화면이 깨진다) · 영업순위·매출순위(계산 0 · 원천이 상호명 조인) · CS현황(0). ⇒ 베타 피치에 이 7개를 넣으면 허위광고.

**② 순위**: 공개 순위는 상위 자극 / 꼴찌 낙인 → 이탈. 더 큰 문제 = **숫자 자체를 못 믿는다**(0.15 고정 · 상호명 조인 · varchar 날짜) — 본사가 먼저 틀린 숫자로 대리점을 줄 세우는 사고. ⚠️가설: 전체 순위 대신 「내 등급 밴드(상위 10% 식)」 노출이 안전.

**③ 가입 깔때기(업무 데이터 제외)**: 가입신청 수 → 결제완료 수 → 설치완료(워치독 첫 신호) → 활성 사용(최근 신호·로그인 유무). 금액·상품명·거래내역 같은 ERP 업무 데이터는 절대 제외.

**④ 프로모션↔과금**: 프로모션이 편집하는 건 `max_users`/`max_devices` 뿐 · 계정 과금 어휘 0 ⇒ 「계정 추가 할인」을 팔 길이 없다.

**⑤ 사실 충돌**: 「등등」은 다듬는 투였지만 실제는 4개 영역 신설 · 계정 과금 전환은 결재됐는데 백오피스 흔적 0 — 영업이 계정 기준으로 팔아도 본사 화면에 안 잡힌다.

**사장님께 여쭐 것**: ① 순위를 대리점에 공개 vs 본사 내부용(숫자 신뢰 전엔 공개 위험) ② 「계정 추가 프로모션」을 이번 범위에 넣을지 ③ CS기록·CS현황을 홍보 문구에 쓸 수 있는 시점.
### 기술영업팀장

**① 매일/매달 보고 싶은 것**: 대리점 사장 = 「이번 달 내 몫」 — 신규 계약 건수 · 구독 금액 · 정산 예정액 3개(더존·이카운트 대리점 포털 첫 화면). 본사 영업담당 = 「어느 대리점이 식고 있나」 — 이번 달 신규 0건 · 재계약 이탈 순. 지금 대리점 화면 중 서버가 붙은 건 고객사 목록·정산 2개뿐(B 2-17) — 「이번 달 실적」 화면 없음.

**② 순위 기준 장단점**
- 신규 고객사 수: 영업 체감에 가장 가깝다 / 큰 1건과 소형 10건을 못 가른다.
- 유지율(해지율): CS·온보딩 품질을 더 반영 — 대리점 탓하면 반발 · CS현황이 0(B 2-8)이라 해지 이유 설명 불가.
- 구독 금액 합계: 금액 = 수수료라 공정해 보이나 산출이 상호명 문자열 조인(B 3-2) — 순위를 매길 만큼 안 믿긴다.
- 계정 수: 과금 단위와 직결되나 「계정 늘리기」 유도 → 고객사 과금만 오른다 — 순위 기준 부적절.
→ 1차 제안 = **신규 고객사 수 + 구독 금액(정산 확정분)** · 확정 단계 숫자만(취소 건이 순위를 흔들지 않게).

**③ 공개 범위**: 1차는 **본사만 전체 순위 · 대리점은 자기 등수만**(이카운트 방식). 수수료 0.15 고정인데 순위 공개 시 민원 유발 ⚠️가설.

**④ 사실 충돌**: 계정 과금 어휘 0건(A②) — 영업이 「계정당 1만원」을 설명할 화면이 없다 · `approved`/`confirmed` 불일치(A②) — 결제돼도 정산 0원 가능 → 순위·수수료를 매기면 대리점 신뢰가 먼저 깨진다 · 수수료 0.15 상수(B 3-5) — 등급별 차등 보상 수단 없음 · 대리점 실적은 **구독 결제 금액으로만**(고객사 업무 데이터 끌어오기 = 반려 · #18·#22).

**사장님께 여쭐 것**: ① 수수료 0.15 고정 유지 vs 등급별·순위 연동 차등 ② 순위를 대리점끼리 공개 vs 본사만 ③ 신규 수 vs 구독 금액 가중치(1차 단순 합산 제안).

### CS팀장 강지원

**① CS 기록 한 건의 최소 칸**: 고객사(tenant 식별자 · 대리점 소속 — 담당자 이름·연락처는 ERP 로컬) · 유형(설치/오류/사용법/결제/기타 — 현장 표현 그대로) · 상태(접수→처리중→**보류**→완료 — 즉시 안 닫히는 건이 30%) · 처리자(대리점 1차 / 본사 2차 구분 필수) · 접수·완료 시각(평균 처리시간의 재료). 거래 내용·금액·거래처명은 **담지 않는다**(#18·#22).

**② 백오피스에 기록돼야 할 길**: 전화(대리점 1차 응대가 대부분 — 본사가 몰라선 안 됨 · 메타만) · 챗봇(ERP 로컬 — 백오피스로는 건수·유형 요약만 · 지금 「넘어가는 길 없음」 유지) · 대리점 자체 접수(본사 조회 가능해야 2차 이관 때 백지에서 시작 안 함) · 원격지원(**했다는 사실과 소요시간만** — 화면 내용 저장 금지).

**③ 대리점 CS현황 숫자**: 미처리 건수 · 평균 처리시간 · **재문의율**(같은 건 재접수 — 진짜 품질 신호). 대리점 평가 연동은 **보류** — 1~2개월 쌓기 전 점수화 = 점수 받아쓰기 사고. 먼저 보여주기 → 사장님 재확인 후 연동.

**④ 챗봇 vs CS기록 경계**: 챗봇(`ai_conversations`) = ERP 로컬 1차 응대 로그 · 본사 불필요. CS기록 = **사람이 개입한 건의 메타**. 경계 = 챗봇이 못 풀고 사람에게 넘어간 순간(`cs_handoff_tickets` · 6/19 설계 · 미구현).

**⑤ 사실 대조**: CS 테이블 0 · 순위·CS현황 집계 0(B) 과 합치 — 세워야 한다. `PRD_AI_CS_SYSTEM.md:74-75`(처리 메타만 Push) · FN-32/FN-33(본사 인계 API · CS 큐→전화) · `20260807_CS보강제안서` 제안B(백오피스 문의 기록 화면)가 같은 방향 — **이미 합의된 설계였는데 구현이 안 남았다**(⚠️가설).

**사장님께 여쭐 것**: ① 대리점 CS현황을 평가에 바로 쓸지, 몇 개월 지켜볼지 ② 전화 응대(대리점 1차)도 백오피스 **의무 기록**인지, 시스템이 자동으로 남기는 것만 우선인지 ③ `cs_handoff_tickets` 를 되살릴지 새로 설계할지.
### AI수석

**① 용어 고정(설계 전 결재 없이 넘어가면 개발 엇나간다)**
- 「결재과금」: 사실은 결제(토스)·요금제편집·대리점정산 3갈래가 섞여 있다(A-②). "결재"가 승인절차(4-eyes)를 뜻하는지, 단순 "결제"의 오타인지부터 고정. 나는 "결제·과금"으로 읽는다.
- 「권한계층」: A-③에서 어휘가 6갈래다. 설계서에는 **단 하나의 enum**과 그걸 담는 **단 하나의 컬럼**만 쓴다고 못 박아야 한다. "본사owner/본사admin/대리점admin/대리점user" 4값 고정 제안.
- 「대표 아이디」≠「로그인 이메일」≠「랜딩 가입 이메일」: A-④ — 설계서 표에 3칸을 분리된 컬럼으로 명시하지 않으면 개발자가 하나로 합쳐버린다.
- 「CS기록」: PRD에 CS 절 자체가 없다(B-④). "기록"이 티켓인지 메타통계인지 용어부터 정의.

**② 설계보다 먼저 고칠 끊김 (우선순위)**
1. 권한 어휘 4~6갈래(A-③) — 이 위에 CS·순위 화면을 올리면 전부 403 재발.
2. `owner` 역할이 DB에 없어 OwnerOnly 화면 5개 진입 불가(A-③) — S-2 가 OWNER 라인에 얹히면 똑같이 막힌다.
3. 웹훅이 `ExtraDeviceSlots` 를 보내고 `ExtraAccounts` 0건(A-②) — 화면을 계정 과금으로 짜도 전송이 옛 슬롯이면 숫자가 안 맞는다.
4. 정산 집계 `'approved'` vs 결제 저장 `'confirmed'`(A-②) — 매출순위가 처음부터 0원.
5. `tenant_payments`↔`tenants` 상호명 문자열 조인(B-3-2) — 매출·영업 숫자의 원천이 흔들린다.

**③ CS 챗봇(ERP 로컬) 경계**
- 될 것: 대화·사용량은 고객사 로컬 DB에만(이미 그렇다). 본사로는 메타 통계만(PRD_AI_CS_SYSTEM.md:74-75) — 건수·응답시간류, 본문 제외.
- 안 될 것: 질문 본문이 외부 AI 로 나갈 때 업무 데이터가 실리는지 미확인 — 설계 전에 메울 구멍. 백오피스 CS 화면의 자동판정 노출은 CS팀장 승인 먼저 · 외부 노출 금지어(#23).

**④ 설계 순서(의존순)**: 권한계층(3) → 결제과금(1) → 대리점 영업현황(4) → 영업·매출순위(5·6) → CS기록(2) → 대리점 CS현황(7).

**사장님께 여쭐 것**
1. 권한 어휘를 무엇으로 통일할지(사장님 결재 사안).
2. 「결재과금」이 승인절차 포함인지, 단순 결제·과금인지.
3. 백오피스로 넘길 챗봇 「메타 통계」 범위를 CS팀장과 몇 개 필드로 못 박을지.

## §5. 보안·법무 피드백 (사장님 추가 지시 "CS 강화 · 법적 이슈는 법무팀장·보안상무")
#### 보안상무 안철수 (보충 — CS 강화·자동화 지시에 대한)

**① Z7ⓒ 한계선 vs CS 강화·자동화 — 양립한다. 자동화에 업무 데이터는 필요 없다.**
- 자동 분류·재문의 연결·응대 제안은 전부 메타(유형·상태·시각·재문의 키·요약)로 돈다. 한계선 유지.
- 추가 허용 필드(전부 코드값/ID 형): 발생 메뉴·화면 식별자 · ERP 버전 · 해결 지식문서 ID · 자동분류 결과·신뢰도. 자유 텍스트는 기존 문의요약 1칸으로 한정(입력 경고 + 서버 금지필드 검사) — 자유 텍스트 칸 추가 설계는 반려.
- 자동 응대는 **「제안 → 사람 확정 → 발송」 반자동 원칙**(100% 자동화 없음) — 확정 전 고객 발송 금지 + 수정 이력 기록.

**② CS기록의 자동화 지식 재사용**
- 지식 정본은 CS팀장이 직접 정의한 문서뿐 — CS기록은 **「어느 지식문서가 어느 유형을 풀었나」 라우팅 통계로만**. 본문의 지식문서 자동 승격 금지(사람 검수 없는 승격 = 외부 긁기와 같은 오염 · CS팀장 승인 필수).
- 금지: CS기록 원문의 외부 AI 프롬프트·학습 투입(본사 쪽에 새 반출 구멍) · 고객사 식별자 붙은 채 지식화.
- 익명화: 지식화 시 tenant 식별자·처리자 ID·시각 제거 + 문의요약은 **사람이 일반화해 다시 쓴 문장만**(자동 익명화 신뢰 금지 — 요약 속 고유명사를 기계가 못 가른다).

**③ 보관 강화 vs #22 — 늘리는 것은 필드가 아니라 기간 통제**
- 필드 한계선 유지 + 보유기간 통제: 티켓 메타 3년 · 자유 텍스트 요약은 완료 후 1년 경과 시 삭제(유형·통계만 잔존) · 해지 고객사는 해지 후 90일 내 tenant 연결 해제·통계화 · 파기 분기 배치 + 파기 로그 의무.
- 수치는 제안값 — 보유기간·파기 주기는 개인정보처리방침 기재 사항 ⇒ **법무팀장 공동 판정 + 사장님 결재**. 「법적 분쟁」 1순위는 본판정 ⓐ 외부 AI 반출(처리위탁 미비)임을 재확인.
### 법무팀장 (개인정보·보안 법무 검토)

**1. CS기록 보관**
- 보안상무 ⓒ 허용필드는 저위험(담당자 개인정보는 ERP 로컬). 단 법인 「대표」는 자연인 — 대표 아이디·이메일은 개인정보 맞음.
- 수집근거: §15①4(계약이행)로 커버 가능 — 별도 동의 불요 가능성 높음. 단 **자유텍스트 문의요약**은 서버 금지필드 검사 가동 전엔 근거 약함 — 조건부 허용이 맞다.
- 보유기간·파기 숫자 미기재 = §21 위반 소지 — 설계 확정 시 반드시 숫자 명문.
- 본사는 CS메타의 **독자 처리자**(수탁자 아님) — 사고 시 본사 1차 책임. 설계서에 성격 명문화.

**2. CS 자동화**
- 과금·해지 등 「권리·의무에 중대한 영향」 자동판정이면 자동화된 결정 권리 조항(§37의2 ⚠️조번호확인필요) 적용 — **이번 CS 자동화에 과금·해지 자동판단을 넣지 말 것**. 단순 분류·라우팅은 소지 낮음.
- CS기록의 챗봇 학습 직접 투입 = 목적외이용 소지 — CS팀장 방침(직접 정의·자동 투입 금지)이 법적으로도 맞다. 설계서 명문화.

**3. 외부 AI 반출(ⓐ) — 분쟁위험 1위**
- 계약·고지 0으로 외부 AI 전송 = **그 자체로 위법 상태**. §17 또는 §26 + 국외 소재면 §28의8.
- `hitpan_pool`(본사 키)이면 본사가 홀로 전체 책임 — 가장 위험.
- 법인명·사업자번호는 원칙상 개인정보 아님이나 1인사업자 거래처는 개인정보일 수 있음(구분 로직 0 ⚠️) — 일괄 금지가 안전.
- 별건 P0·베타 Tool 노출 금지 판정에 전적 동의. 추가: (a) 처리위탁계약/국외이전 고지 선체결 전 노출 금지 (b) pool 키 책임귀속 조항 명문화.

**4. S-2 대표 아이디·이메일**
- 근거 §15①4 가능성 높음. 첫 로그인 약관 4종에 수집·이용 고지 문구 유무 ⚠️확인필요(없으면 추가).
- 3칸 분리는 중복 고지 불요 — 단 각 시점(가입/개통)의 첫 수집 칸 고지는 필요. 비번 0건 방침 유지.

**5. 대리점 관계**
- 대리점의 본사 DB CS·영업정보 조회 = §17 제공 소지 — 대리점 계약서(유무 ⚠️확인필요)에 접근 목적·범위·재위탁 금지를 §26 위탁 구조로 명문화 권고.
- 폐업·교체: 본사 DB 원본 + 대리점 조회권만이면 이전 불요 · 대리점 사본(엑셀) 있으면 파기확인서 수취.

**ⓐ 설계 반영 필수 6건**: ① 자유텍스트 요약은 금지필드 검사 가동 전 비허용 ② 보유기간·파기 숫자 명문 ③ 외부AI Tool 은 계약·고지 체결 전 베타 노출 금지 ④ 첫 로그인 약관 고지 삽입(선확인) ⑤ 대리점 위탁계약서 명문화 ⑥ CS 자동화에서 과금·해지 결정 배제.
