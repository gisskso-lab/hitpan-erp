## 3. 🔴 핵심 반려 1 — "침해 흔적 0"은 말할 수 없다

**보안상무·검증팀장이 독립적으로 같은 결론.**

| 반증 | 내용 |
|---|---|
| `last`/`lastb` 는 **root 가 편집 가능한 파일** | wtmp/btmp 기반. 침해자가 root 를 먹었다면 **가장 먼저 지우는 대상**. 침해된 서버의 로그가 깨끗한 건 오히려 정상 시나리오 |
| **키가 이미 심겼다면 실패 로그에 안 남는다** | `authorized_keys` 에 공개키가 들어갔으면 정상 성공으로 기록되거나, SFTP·포트포워딩은 wtmp 에 안 남음 |
| `last` 는 **대화형 세션만** 기록 | `ssh host 'command'`(CI 가 쓰는 방식)·scp·리버스셸은 안 남음. **7/24~7/28 CI 게시 접속이 성공 목록에 없다** = 그 목록이 전체집합이 아니라는 증명 |
| SSH 만이 침입 경로가 아님 | nginx 로 랜딩·백오피스·updates 3개가 외부 노출. 웹 취약점 경유는 `last` 에 한 줄도 안 남음 |

> ### 결론: **"침해 없음"이 아니라 "침해 여부 미상(unverified)"**
> **PM 은 증거 부재를 부재 증거로 오독했다.** (검증팀장 지적 원문)
>
> 판정 기준을 *"침해 증거가 있나"* → **"침해 없음을 증명할 수 있나"** 로 올려야 한다. (보안상무)

**긍정 신호도 정직하게 기록**: `pubkeyauthentication` 이 켜져 있고 사장님이 키로 접속해 왔으며,
공격 패턴이 **자동화 봇넷의 통상 배경 소음**(계정명 사전 대입)이라 표적 공격 징후는 아니다.
실제 뚫렸을 확률은 **낮다**. 아래 채증이 그 "낮다"를 "확인했다"로 바꾸는 절차다.

## 4. 🔴 핵심 반려 2 — 조치 순서가 뒤집혔다

### 4-1. 보안상무: **채증이 조치보다 먼저**

PM 의 3순위(로그 정리)가 **증거를 지운다.** 순서를 바꾸면 되돌릴 수 없다.

### 4-2. 검증팀장: **`permitrootlogin` 을 건드리면 배포가 죽는다** ⭐

PM 은 *"root+비밀번호+fail2ban 3중 위험"* 이라 진단해 놓고 조치엔 root 항목을 안 넣었다.
그 흐름에서 보안팀이 `permitrootlogin no` 를 추가하는 건 거의 필연인데 —

| 실측 (레포) | 사실 |
|---|---|
| `deploy-ncp.yml:103·108-110` | `NCP_USER` 로 SSH·rsync. **그 값이 root** |
| `20260724_인수인계서:167` | 대체 계정 `hitpan-deployer` = **uid999·nologin** |
| `20260724작1:78` | Secret 교체는 계정·키·sudoers 완비 **후 맨 마지막** — 미완 |

> **⇒ 지금 root 로그인을 끄면 배포 경로가 0개가 된다.**
> 랜딩 404 봉합도, 자동업데이트도, 사장님 수동 SSH 도 전부. **보안 조치가 아니라 자해다.**
>
> 계정 비특권화는 이미 [`20260724작1`](../설계/업데이트배포/20260724작1v2_배포계정_비특권화_6관점종합_작업지시서.md) 에 순서가 설계돼 있다. **오늘 할 일이 아니다.**

### 4-3. 두 사람 순서 대조

| 순위 | 보안상무 | 검증팀장 |
|---|---|---|
| 0 | **IoC 채증** | NCP 콘솔 접속 실측(백도어 확보) |
| 1 | 두 번째 SSH 세션 확보 | **로그 오프서버 백업**(증거보존) |
| 2 | **`PasswordAuthentication no`** ⭐ | **authorized_keys 3개 지문 대조** ⭐ |
| 3 | `PermitRootLogin prohibit-password` | btmp truncate + logrotate(디스크) |
| 4 | fail2ban | fail2ban (ignoreip **/24**) |
| 5 | 로그 정리 | `PasswordAuthentication no` |
| 6 | **authorized_keys 3개 확인** | ⛔ `permitrootlogin` **손대지 않음** |
| 7 | NCP ACG 로 22번 IP 제한 | [별건] 계정 전환은 오늘 금지 |

**차이**: 보안상무는 *"진행 중 공격의 결정타(비번차단)를 빨리"*, 검증팀장은 *"키 정체 확인이 먼저"*.

> **PM 통합 제안**: 검증팀 순서를 기본으로 하되, 보안상무의 **"두 번째 세션 확보"** 를 0번에 넣는다.

## 6. 게시 중단 판단 — **3인 전원 동의**

보안상무 근거 3가지:

1. **게시 = 개인키로 서명하는 행위다.** 서버 무결성 미확인 상태에서 서명하면, 만에 하나 침해 시
   **우리 손으로 악성 페이로드에 정품 서명을 찍어 전 고객에게 배포**하게 된다.
   `publish-run.sh` 의 B-4 독립 재조회는 *러너 침해* 방어용이지, **NCP 자신이 침해된 경우는 설계상 못 막는다**
   — 그 스크립트가 침해된 호스트에서 돌기 때문이다.
2. **상주본 갱신 절차서가 `publish-run.sh` 를 덮어쓴다.** 그 파일은 **변조 확인의 핵심 증거물**이다.
   지금 덮으면 **변조 여부를 영원히 알 수 없다.**
3. **랜딩 404 는 P0 이나 급성이 아니다.** 1.2.29~1.2.41 전부 404 였고 = 한 번도 작동한 적 없었다.
   고객 0명. 몇 시간 미뤄 잃을 게 없다. 반면 침해 서버에서 서명하면 **제품 신뢰 전체**를 잃는다.

> **조건부 해제**: 채증 4개(키 지문·개인키 짝·sudoers·게시물 전수)가 깨끗하고 비번차단이 끝나면
> **오늘 안에 게시 재개 가능.** 무기한 동결이 아니라 **약 1시간짜리 선행 조건**이다.

## 8. 완료 관문 (검증팀장 3관문)

**관문 1 — 접근성 (잠김 0)**
- **새 터미널** 신규 SSH 접속 성공 (기존 세션 살아있음은 **증명 아님**)
- 그 세션에서 `sudo -n true` 성공
- **NCP 콘솔 접속 실측 1회** (SSH 죽어도 살아나올 경로)

**관문 2 — 보안 실효 (설정 아닌 동작)**
- `systemctl is-active` 는 **증명 아님** → 밴 IP ≥1 **AND** 커널 룰에 실재 **AND** 5분 후 `Total banned` 증가
- 외부에서 `ssh -o PreferredAuthentications=password` → **프롬프트 없이** `Permission denied (publickey)`
- authorized_keys 3개 **전부 소유자 확정**
- 디스크 < 75% + logrotate 자동 회전 설정

**관문 3 — 파이프라인 무손상** ⭐
- `NCP_USER` = **root 유지** (Secret 미변경)
- **실측 게시 1회 종단 완주** — EXE 260MB rsync + 래퍼 + HTTP 200
- 그 게시 중 사장님·CI IP 가 **밴되지 않음**

> **"설정 다 했다"는 통과가 아니다.** (검증팀장)

## 13. 보안매니저 2 (인프라·OS) 의견 — 실무 실행 계획

> 총괄 판단이 아니라 **손에 잡히는 명령**을 책임지는 자리. 핵심 결론이 앞 두 사람과 또 달랐다.

### 13-1. 핵심 판단

> **"fail2ban 만 켠다. SSH 하드닝은 `PasswordAuthentication no` 한 줄까지만 하고,
> 포트 변경·소스IP 제한·`PermitRootLogin no` 는 전부 하지 않는다."**

이유: `deploy-ncp.yml` 이 **GitHub 호스티드 러너에서** 이 서버로 SSH·rsync 를 들어온다.
포트 22 고정, 계정 root. **셋 중 하나라도 건드리면 CD 가 그 자리에서 죽는다.**

### 13-2. 🔴 PM 이 놓친 것 — 가장 급한 2건

| # | 지적 | 채증 결과 |
|---|---|---|
| **E-7** | **디스크 87% 가 이미 배포 게이트를 넘었다.** `deploy-web.sh:44` `MIN_FREE_MB=2048` — **여유 1.3G < 2G → 지금 배포하면 거부된다.** 보안 이슈가 아니라 **가동 중단 이슈** | ✅ 확인됨. 정리로 2.2G 복구 |
| **E-1** | **다른 포트를 아무도 안 봤다.** MySQL 3306 외부 개방이면 SSH 보다 급하다 | ✅ **외부 노출 없음** (로컬 전용) |
| E-2 | 공개키 3개 정체 미확인 | ✅ **전부 신원 확인** (채증 B-3) |
| E-4 | `lastb` 는 실패만 — 침해 판정 근거 부족 | ✅ 채증으로 보강 |
| **E-6** | **fail2ban 이 도는 줄 알고 쓴 문서 2건이 그대로** — 거짓 안전감 | 🔴 §13-5 정정 |
| E-8 | **모든 서비스가 `User=root`** — 백오피스 API 취약점 1개면 곧바로 root → **서명 개인키 접근** | ⬜ 별건 |
| E-9 | NCP 콘솔 OS 비밀번호 보유 여부 미확인 | ⬜ 미확인 |

### 13-3. 사장님 IP 를 `ignoreip` 에 넣을 것인가 — **넣지 마십시오**

PM 이 물었고, 매니저2 가 정면으로 답했다.

> **넣으면 안 되는 이유**: `124.194.59.154` 는 한국 ISP **동적 할당** 가능성이 높다.
> 공유기 재부팅·임대 갱신 시 바뀌고, **그 IP 는 다음 가입자에게 넘어간다.**
> 즉 ignoreip 는 "사장님 면제"가 아니라 **"모르는 남 하나를 무기한 fail2ban 면제"** 로 변한다.
>
> 게다가 사장님은 **키 인증**으로 들어온다 — 키가 맞으면 실패 카운트가 안 오른다. 면제 이득이 없다.

**"오타 몇 번에 잠기나"에 대한 정확한 답**: 비밀번호 오타로는 **안 잠긴다**(프롬프트 자체가 안 뜸).
잠기는 경로는 **키가 잘못됐을 때** — 10분 내 5회 실패 시 1시간. **연속 2회 실패하면 세 번째를 치지 말고 원인부터 볼 것.**

밴돼도 자력 탈출: `fail2ban-client set sshd unbanip <IP>` / 재부팅하면 전부 해제(nftables 런타임 상태)

### 13-4. NCP 고려사항

| 항목 | 판단 |
|---|---|
| ACG 로 22번 IP 제한 | **원리적으로는 fail2ban 보다 낫다**(패킷이 서버에 닿기 전 차단). **그러나 못 쓴다** — CD 가 GitHub 러너에서 들어오고 그 IP 는 수천 CIDR·주 단위 변동 |
| ACG 로 할 일 | **SSH 말고 다른 포트를 잠그는 데 쓸 것.** 22·80·443 외 열린 게 있는지 확인 |
| NCP 콘솔 구제 | **부분적.** VNC 콘솔은 **OS 비밀번호를 요구**한다. 모르면 구제 수단이 아니다 → **하드닝 전 확인 필요** |
| 비용 | **추가 0원.** fail2ban·sshd·logrotate 전부 OS 기본. 유료 보안상품 불필요 — *"상품으로 살 게 아니라 설정 안 한 것뿐"* |
