## 3. 🔴 상태 칸은 하나 — PM 이 한 번 틀렸다

사장님 지시는 처음부터 **"상태처리를 「반품」이라고 표기할것"** = **상태를 바꾸라**였다.

그런데 PM 이 *"매입확정 사실이 사라지면 안 된다"* 는 걱정을 앞세워 **칩을 나란히 붙이는**(`매입확정`＋`반품`) 다른 물건을 만들었다.

> 사장님: *"반품 했다고 매입이 지워지는게 아니라, **전표 상태가 변경되면 됨. 이 방법이 가장 쉬움**"*
> 사장님: *"내가 작업명령 할때도 **상태변경**을 이야기 했는데 지금 뭐한거지"*

🔴 **무엇이 잘못이었나** — PM 의 걱정은 **DB** 얘기였고 사장님은 **화면 표기**를 말씀하신 것이다.
**섞으면 안 되는 둘을 섞어** 있지도 않은 문제를 만들고 설계를 비틀었다.
⇒ DB `status` 는 안 건드리고(원장·부가세 안전) **화면 표기만 「반품」**. 둘은 애초에 충돌하지 않았다.

⚠️ 칩을 둘로 늘리지 않는다 — 화면이 복잡해지면 현장에서 안 읽힌다(**히트판은 쉬움으로 이겼다**).

### 🔴 워크플로우 정합성 — 이게 근거다

사장님이 정리해 주신 데이터 흐름:

```
매입확정 → 재고 +  ·  지급금 +
반품     → 재고 −  ·  지급금 −
```

> *"전표상에는 마이너스 전표를 끊지 않지만 **데이터 흐름상 반품처리시 마이너스 처리를 함으로 데이터 정합성이 맞춰짐**"*
> *"재고, 회계에 반품도 워크플로우 흐름에 맞춰져야지. **그래야 전표가 의미가 있지**"*
> *"**반품전표 끊는데, 재고, 회계에 반영이 안되면 그게 무슨의미가 있어**"*

🟢 **재고·회계 반영은 이미 되고 있다**(작16 에서 확인 — 정방향과 완전 대칭·단일 트랜잭션). 실물 확인:

| 축 | 코드 |
|---|---|
| 재고 − | `stock_ledger` Reverse **OUT** INSERT + `item_stock.current_qty - @Qty` |
| 지급금 − | `partner_balance` 차감 + 분개 `amount: -totalAmount`(외상매입금) |
| 마이너스 전표 | 끊지 않는다 — 전표는 `purchase_returns` 별도 문서, **원장만 역산** |

⇒ 숫자는 이미 맞고 있었는데 **화면만 「매입확정」이라 말하고 있었다.** 그 어긋남을 없앤 것이 이번 작업이다.

### 최종 표기 — 칸 하나
| 상황 | 상태 칸 |
|---|---|
| **반품 확정** | 🔴 **반품** |
| 반품 없음 · 매입확정 | 🟢 매입확정 |
| 미확정 | 임시저장 등 |

⚠️ **확정된 반품만** 상태가 바뀐다. 반품확정이라야 재고−·지급금−가 실제로 일어나기 때문이다
(`ConfirmPurchaseReturnAsync` 는 `draft` 만 확정 대상으로 받고, 원장 반영은 confirmed 에만 — 헌법 #6).
**돈과 재고가 실제로 움직인 건만** 「반품」이다.

## 4. 봉합 — 쓰지 않고 되짚는다

`PurchaseService.GetReceiptsAsync` 목록 SQL 에 **상관 서브쿼리** 추가:

```sql
(SELECT MIN(r.status)
   FROM purchase_returns r
  WHERE r.receipt_id = pr.receipt_id
    AND r.tenant_id  = pr.tenant_id
    AND r.is_deleted = 0
    AND r.status <> 'canceled') AS ReturnStatus
```

🔴 **쓰기 경로는 한 줄도 안 건드렸다.** `purchase_receipts` 에 저장하지 않고 **조회 시점에 되짚는다** —
원장·확정 로직에 손대지 않으므로 회귀 위험이 없다(#3 INSERT ONLY 정신).

### 세 가지 판단
| 선택 | 이유 |
|---|---|
| **JOIN 아닌 서브쿼리** | JOIN 하면 반품서가 둘 이상일 때 **매입명세서 행이 늘어난다**(같은 전표가 두 번). 지금은 중복가드(작18 W5-2)가 막지만 **그 가드가 바뀌어도 목록이 안 깨지게** 여기서부터 막는다 |
| **`canceled`·`is_deleted` 제외** | 되돌린 반품이 「반품」으로 남으면 담당자가 **살아있는 것으로 오인**한다 |
| **`MIN()`** | `'confirmed' < 'draft'` 라 **확정이 우선**한다(실측 확인). 반품서가 여럿이어도 확정된 게 있으면 확정으로 보인다 |

## 5. 실측 — 4가지 경우를 심어서 확인

로컬 `hitpan_e2e` 에 매입명세서 4건 + 반품 3건(확정·작성중·취소)을 심고 실행:

| 전표 | 매입상태 | 반품 | `ReturnStatus` | **화면** |
|---|---|---|---|---|
| 매입-001 | confirmed | 없음 | `NULL` | 매입확정 |
| 매입-002 | confirmed | **확정** | `confirmed` | 🔴 **반품** |
| 매입-003 | draft | 작성중 | `draft` | 임시저장 |
| 매입-004 | confirmed | **취소됨** | `NULL` | 매입확정 |

- 매입-002 — 매입확정이던 전표가 **「반품」으로 바뀐다**(이번 지시의 본안)
- 매입-004 — 되돌린 반품은 **세지 않는다**(살아있는 것으로 오인 방지)
- 매입-003 — 반품서는 있으나 **확정 전**이라 재고−·지급금−가 아직 없다 ⇒ 「반품」 아님

🔴 **행 증식 반증**: 매입-002 에 반품서를 **하나 더** 넣어도 **목록 행수 4개 그대로** · 값은 `confirmed` 유지.
(JOIN 이었으면 매입-002 가 두 줄로 떴다.)
