## 3. 🔴 왜 `status` 를 덮지 않는가 — 두 축이다

*"반품이니 `status='returned'` 로 바꾸면 되지 않나"* 가 가장 쉬운 길이지만 **틀렸다.**

**반품했다고 매입이 취소된 게 아니다** — 샀다가 돌려준 것이지 **안 산 게 아니다.**
`status` 를 덮으면 **매입확정 사실이 사라져** 원장·집계·부가세가 어긋난다
(작17 에서 *"매입반품인데 매출에 영향이 있나"* 로 정리된 축과 같다 — **매입은 매입 논리로**).

⇒ **두 축을 각각 보여준다**: `매입확정` **＋** `반품`

| 화면 표기 | 뜻 |
|---|---|
| `매입확정` | 반품 없음 |
| `매입확정` + 🔴`반품` | 반품 **확정** |
| `매입확정` + 🟡`반품작성중` | 반품서는 있으나 **아직 확정 전** |

⚠️ **작성중과 확정을 구분한다.** 「반품」 하나로 뭉치면 아직 확정 안 한 반품이 이미 처리된 것처럼 보여 **담당자가 확정을 건너뛴다**.

## 4. 봉합 — 쓰지 않고 되짚는다

`PurchaseService.GetReceiptsAsync` 목록 SQL 에 **상관 서브쿼리** 추가:

```sql
(SELECT MIN(r.status)
   FROM purchase_returns r
  WHERE r.receipt_id = pr.receipt_id
    AND r.tenant_id  = pr.tenant_id
    AND r.is_deleted = 0
    AND r.status <> 'canceled') AS ReturnStatus
```

🔴 **쓰기 경로는 한 줄도 안 건드렸다.** `purchase_receipts` 에 저장하지 않고 **조회 시점에 되짚는다** —
원장·확정 로직에 손대지 않으므로 회귀 위험이 없다(#3 INSERT ONLY 정신).

### 세 가지 판단
| 선택 | 이유 |
|---|---|
| **JOIN 아닌 서브쿼리** | JOIN 하면 반품서가 둘 이상일 때 **매입명세서 행이 늘어난다**(같은 전표가 두 번). 지금은 중복가드(작18 W5-2)가 막지만 **그 가드가 바뀌어도 목록이 안 깨지게** 여기서부터 막는다 |
| **`canceled`·`is_deleted` 제외** | 되돌린 반품이 「반품」으로 남으면 담당자가 **살아있는 것으로 오인**한다 |
| **`MIN()`** | `'confirmed' < 'draft'` 라 **확정이 우선**한다(실측 확인). 반품서가 여럿이어도 확정된 게 있으면 확정으로 보인다 |
