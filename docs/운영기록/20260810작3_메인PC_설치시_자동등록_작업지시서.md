> CS: *"어느 컴퓨터에서 쓰시나요?"*
> 고객: *"그냥… 회사 컴퓨터요."*

**CS 가 그 PC 가 메인PC 인지 클라이언트인지 알 방법이 없다.** 기기 목록이 전부 `(이름없음)` 이고

| **메인PC** | 히트판 본체·DB·터널이 그 PC 에 있다 | 그 PC 를 살려야 한다. 재부팅·서비스 확인 |

⇒ **구분이 없으면 CS 가 첫 질문을 못 던진다.** 이건 기능 누락이 아니라 **운영 불능**이다.

### 3-3. ⚠️ 설치마법사가 지문을 만들 수 없다 — 이 작업의 핵심 제약

지문은 **브라우저 JS**(`device-fingerprint.js:29-54`)가 화면 해상도·브라우저 종류·시간대로 만든다.
설치마법사(Inno Setup)는 브라우저가 아니다. **같은 값을 만들 방법이 없다.**

🔴 **따라서 "설치마법사가 tenant_devices 에 INSERT" 를 곧이곧대로 하면 안 된다.**
지문 없는 행을 넣으면(`fingerprint` 는 `NOT NULL`) 첫 로그인 때 지문이 안 맞아
**새 기기로 또 등록된다 ⇒ 메인PC 1대가 슬롯 2개를 먹는다.** 요금정책 사고다(방향만 반대).

⇒ **등록 시점(설치)과 지문 결합 시점(첫 로그인)을 나눈다.** §4 설계.

## 3-4. 🔴 사장님 추가 지적 — 메인PC 는 "사람이 쓰는 PC" 가 아니다

> *"고객사 입장에서 메인PC를 **반드시 대표자나 ERP담당자가 쓴다는 보장이 없어.**
> **24시간 켜있는 윈도우10환경의 가장 적절한 PC환경**을 히트판 본사에서는 메인PC로 추천할 것이기 때문이야.*
>
> *그렇다면 **최초 ERP 설치 할때 담당했던 직원이 없을경우**, 히트판CS이슈가 터졌을 땐
> 메인PC와 클라이언트의 구분이 없다면 고객사는 대응하기가 힘들거야. 그래서 필요해."*

**이 지적이 설계를 하나 바꾼다.**

| 종전 전제 (틀림) | 실제 |
|---|---|
| 메인PC 에서 사람이 로그인한다 | 🔴 **아무도 로그인 안 할 수 있다.** 서버 성격의 PC — 창고·구석에 24시간 켜두는 PC |
| 설치한 사람이 어느 PC 인지 안다 | 🔴 **그 직원이 퇴사하면 아무도 모른다** |

⇒ 🔴 **"메인PC 에서 첫 로그인이 일어나면 확정" 에 기대면 안 된다. 그 로그인이 영영 없을 수 있다.**

⇒ **판정은 로그인과 무관하게, 서버가 기동할 때 스스로 끝내야 한다.** §4 가 이 방식이다.

### 🔴 계정 축과 기기 축은 별개다 (사장님)

> *"그렇지 **부모계정을 반드시 메인PC에서 쓴다는 보장이 없거든.** **계정은 계정일 뿐이니까.**"*

이것이 이 설계의 근거다. 두 축을 섞으면 안 된다.

| 축 | 무엇 | 어디에 |
|---|---|---|
| **계정** | 누가 로그인하나 (부모/자식) | 사람을 따라다닌다. 노트북·집·휴대폰 어디서든 |
| **기기** | 어느 컴퓨터에서 접속하나 | 슬롯을 세는 단위. **과금 근거** |

**부모계정이 메인PC 에서 로그인해야 할 이유가 전혀 없다.**
사장이 자기 노트북에서 부모계정을 쓰고, 메인PC 는 창고에서 아무도 안 건드린 채 도는 것이 정상이다.

⇒ 🔴 **기기 등록을 계정 로그인에 묶는 순간 이 정상 상태가 등록 실패가 된다.**
   그래서 §4 는 등록 주체를 **브라우저(계정)가 아니라 서버 자신**으로 둔다.

## 4. 구현 방식 — 서버가 기동할 때 스스로 등록한다 (로그인 불필요)

> ⚠️ **이것은 새 설계가 아니다.** 사장님: *"이게 새 설계가 아니라니까. 원래 그렇게 하기로 한 건데
> 그동안 빼먹은 거야."* — 기기 기준·메인PC 구분·설치 시 등록은 **처음부터 정해져 있었다.**
> 아래는 그 결정을 **어떻게 코드로 넣느냐**일 뿐이다. 결정을 다시 하는 자리가 아니다.

```
[설치마법사]  db.conf 에 MAIN_PC=1 을 남긴다         ← 자기 PC 라는 걸 판정 없이 안다
      ↓
[API 기동]    HostedService 가 tenant_devices 에
              메인PC 행을 스스로 넣는다 (없으면)      ← 🔴 사람이 로그인하지 않아도 등록된다
      ↓
[등록기기]    is_main_pc=1 · 이름 "회사 서버 (자료 보관)" · 슬롯 1개 소모
      ↓
[CS]         고객이 화면에서 어느 PC 가 메인PC 인지 본다
```

🔴 **핵심 — 등록 주체가 브라우저가 아니라 서버 자신이다.**
API 는 메인PC 에서만 돈다(`.iss:2359` schtasks + `:1825` `DB_HOST=localhost`).
그 API 가 기동할 때 자기를 등록하므로 **사람의 로그인이 전혀 필요 없다.**

### 4-1. 지문(fingerprint) 을 무엇으로 하나

`fingerprint` 는 `NOT NULL` 이고 `UNIQUE(tenant_id, fingerprint)` 다. 서버는 브라우저 지문을 만들 수 없다.
⇒ **서버 전용 지문을 쓴다.** 브라우저 지문(`HFPv2-`)과 **네임스페이스가 겹치지 않게** 한다.

```
MAINPC-{SHA256(MachineName + TENANT_CODE + SLOT_INDEX) 앞 16자}
```

- `Environment.MachineName` 은 이미 워치독이 쓰는 기존 패턴(`TunnelTokenRecovery.cs:92`)
- 브라우저 지문은 항상 `HFPv2-` 로 시작하므로 **충돌하지 않는다**
- 같은 PC 에 멀티슬롯이 있어도 `SLOT_INDEX` 로 갈린다

⚠️ **그래서 메인PC 행은 브라우저 로그인 행과 별개다.** 메인PC 에서 사람이 로그인하면
그 브라우저는 **자기 지문으로 별도 등록**된다 — 슬롯을 하나 더 먹는다.
🔴 **이것은 결함이 아니라 정의다.** 사장님 결재는 *"메인PC 도 슬롯을 소모한다"* 이고,
메인PC(서버)와 그 위에서 일하는 사람의 브라우저는 **다른 용도**다.
⚠️ 다만 **고객에게 이 사실이 보여야 한다** — T4 에서 목록에 성격을 구분해 표시한다.

### 4-2. 왜 이게 안전한가

| 축 | 근거 |
|---|---|
| 사람 없이도 등록됨 | 🔴 **서버 기동만으로 등록된다.** 24시간 켜둔 무인 PC 라도 반드시 잡힌다 |
| 판정이 흔들리지 않음 | db.conf 는 **그 PC 에만** 있다. 클라이언트PC 에는 히트판이 설치돼 있지 않다 |
| 접속 경로와 무관 | loopback·Host·XFF 를 **아예 보지 않는다.** 오늘 두 번 무너진 축을 안 쓴다 |
| 설치 담당자 퇴사에 강함 | 화면에 표식이 남아 **누구든 목록만 보면 안다** (사장님 CS 지적) |
| 재설치에 안 흔들림 | db.conf 는 재설치에도 살아남고, `MAIN_PC` 는 **항상 1** 이라 값 보존 로직 불필요.<br>지문도 MachineName 기반이라 재설치 후 **같은 값** ⇒ 중복 행이 안 생긴다 |
| 위조 불가 | 클라이언트 브라우저는 서버 db.conf 에 영향을 못 준다. **서버가 자기 파일에서 읽는다** |

⚠️ **환경변수 폴백** — `TenantConfigReader.Get()` 은 db.conf 에 없으면 환경변수를 본다(`:24-25`).
`MAIN_PC` 는 **서버 프로세스 환경**이라 원격 위조 경로가 아니다. 그 PC 관리자만 바꿀 수 있고,
그 사람은 이미 DB 파일에 접근 가능하다 ⇒ **권한 상승이 아니다. 허용.**

⚠️ **`TenantConfigReader` 는 프로세스당 1회만 읽는다**(`:38`). 기존 고객이 업데이트로 db.conf 에
`MAIN_PC` 를 받으면 **API 재시작 후** 반영된다. 업데이트는 서비스 재시작을 동반하므로 문제없다.

- 값이 항상 `1` 이므로 `ReadDbConfValue` 보존 로직 **불필요**

### T3 — 서버가 기동할 때 스스로 등록 (🔴 로그인 불필요)

**신규** `src/HitPan.API/HostedServices/MainPcRegistrationService.cs`

기존 HostedService 패턴을 따른다 (`IdempotencyCleanupService` · `IntegrityCheckService` 참고).

동작:
1. `TenantConfigReader.Get("MAIN_PC")` 가 `1` 이 아니면 **아무것도 안 하고 끝낸다**
2. 서버 지문 생성 — `MAINPC-{SHA256(MachineName + TENANT_CODE + SLOT_INDEX) 앞 16자}` (§4-1)
3. 그 지문으로 이미 등록된 행이 있으면 **`is_main_pc=1` 로 승격만** 하고 끝낸다 (재설치·업데이트 대비)
4. 없으면 INSERT — `is_main_pc=1`, `device_type='pc'`, `status='approved'`
5. 🔴 **테넌트당 1건 보장** — 이미 다른 메인PC 가 있으면 **INSERT 하지 않는다**

⚠️ **한도를 넘어도 이 등록은 막지 않는다.** 이것은 로그인 차단이 아니라 **사실 기록**이다 —
그 PC 는 실제로 존재하고 실제로 히트판을 돌리고 있다. 목록에 안 보이면 CS 가 못 쓴다(§2).
🔴 **단, 사람 로그인 경로(`RegisterOrRefreshAsync`)의 한도 검사는 절대 손대지 않는다.**

⚠️ **기동 실패가 API 를 못 죽이게 한다** — DB 가 아직 안 올라왔을 수 있다.
예외는 잡아 로그만 남기고 다음 기동에 다시 시도한다(멱등이라 안전).

`src/HitPan.API/Controllers/AuthController.cs`

- 🔴 **손대지 않는다.** `RegisterOrRefreshAsync(..., isMainPc: false, ...)` 를 **그대로 둔다** —
  브라우저 로그인은 계정 축이고, 메인PC 는 기기 축이다(§3-4). 섞지 않는다
- `BuildMainPcName`(`:531`)은 **HostedService 가 쓰지 않는다**(이름을 서버가 직접 만든다).
  ⇒ dead code 로 남으면 정리하거나, 이름 생성을 여기로 모을 것 — 둘 중 하나. **양쪽에 두지 말 것**

`src/HitPan.Infrastructure/Services/TenantDeviceService.cs`

- 🔴 **`RegisterOrRefreshAsync` 는 손대지 않는다.** 한도·`revoked` 거부 전부 종전대로
- dead parameter `isMainPc`(`:103`) — 이번 설계에서 쓰지 않는다. **제거하거나 그대로 둔다**(호출부 1곳)
- 신규 메서드 추가: 메인PC 등록/승격 (HostedService 가 부른다)
- 기기 목록 조회에 `is_main_pc` 를 실어 보낸다 (T4 용)

### T4 — 화면에 구분이 보이게

`src/HitPan.Web/Pages/Settings/` 등록 기기 관리 화면
