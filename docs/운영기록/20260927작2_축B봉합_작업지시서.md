### 🔴 착수 전 반드시 알 것 — 3줄

1. **`ResolveDeviceType` 을 그 자리에서 부를 수 없다.** 계층이 반대다(설계 §2-1). **Application 으로 옮긴다.**
2. **`sid` 미탑재는 호출 순서를 바꿔야 성립한다** — 지금은 토큰이 INSERT 보다 먼저 만들어진다(설계 §4-2).
3. **축 B 판정은 `tenant_devices` 를 읽지 않는다**(설계 §3). 지문 없는 로그인이 실재한다.

### 이 차수가 하지 않는 것

- 🚫 **위조를 막지 않는다.** ⬛ *"도달 목표는 8/18 V-05 수준(헤더까지 함께 위조해야 됨)"* — **낡은 줄**(사유: 9/27 [3-V] V-B1 실측 반증 · 20260927작2 **2차**에서 정정). 🔴 정정: **「서버가 이긴다」는 UA 가 말을 할 때만이다** — UA 를 생략·공백으로 두거나 Mac 을 사칭하면 판정이 성립하지 않고 신고값이 이긴다(`DeviceTypeResolver.cs:176`·`:191-197`). 닫히는 것은 *"UA 가 PC 라고 말하는데 신고값만 mobile"* 경로 하나다. *"막았다"* 고 쓰면 거짓봉합.
- 🚫 **축 B 를 켜지 않는다.** 기본 OFF 로 출하한다. 켜는 것은 별도 결재(전결 §6).
- 🚫 범위 밖: F-7 경주 · F-8 서버측 방어 · F-9 만료행 청소 · P1-1 · P2-1 · P2-3 · 계정 수 상한(5/8).

### 🔴 조건 C-5 (신설) — 갱신 경로가 만드는 새 세션의 기기 종류

🟢 **PM 실측**: `AuthService.cs:479` 가 갱신 경로에서
`InsertSessionAsync(conn, sessionId!, user, NormalizeDeviceKind(null))` — **항상 `'mobile'`** 을 적는다.

- `NormalizeDeviceKind` 를 없애면(절A) 이 자리에 **무엇을 넣을지 반드시 정해야 한다.** 안 정하면 구현이 또 자기 판단으로 메운다.
- 지금 상태 그대로면 **옛 토큰으로 `/refresh` 한 번 = 축 B 영구 회피**다. 그 행은 `device_kind = 'pc'` 조회(`:226-229`)에 안 잡히므로 로그인을 거치지 않고 차단 밖으로 나간다.

**결정**: `ResolveDeviceType(null, 서버가 읽은 User-Agent)` 를 쓴다. 갱신 요청에는 신고값이 없으므로 **UA 단독 판정**이다.
- 무조건 `'mobile'` 보다 엄격해진다. ⬛ *"도달 수준은 8/18 선례와 같다(헤더를 위조해야 값을 고른다)"* — **낡은 줄**(사유: V-B1 실측 · 2차 정정). 🔴 UA 를 **생략·공백**으로 두면 위조 없이 판정을 비켜간다 ⇒ 갱신은 신고값도 없으니 `?? "mobile"` 로 떨어진다. 이 경로를 막는 것은 다음 차수(장비넘버) 몫이다.
- 🚫 여기에 신고값 칸을 새로 만들지 마라 — 자진신고 입구를 하나 더 파는 일이다.

**게이트 G-B12 신설** (절I) — (양) PC UA 로 갱신 ⇒ 새 세션 `device_kind='pc'` / (음) UA 판정을 지우고 `null` 폴백으로 되돌리면 `'mobile'` 로 적혀 **FAIL**.
