## 1. 🔴 P0-1 — 모든 고객 PC 가 동일한 DB 비밀번호를 쓴다

### 1-1. 실측


`installer/install.bat` 최종 수정 `09369f8` (2026-04-28) — **3개월간 아무도 못 봤다.**

### 1-2. 🔴 사장님 결재 — **공통 비밀번호 유지 (확정 2026-07-31)**

> **사장님 지시:**
> 1. 고객사 PC 에 MariaDB 가 설치되지 않은 경우 → **동일한 패스워드로 사용할 것**
> 2. 고객사 PC 에 별도로 MariaDB 가 이미 있는 경우
>    (한 PC 에서 히트판 ERP 를 두 개 쓰는 업체, 다른 프로그램이 MariaDB 를 쓰는 경우)
>    → **히트판 ERP 접근 DB 도 동일한 패스워드로 사용할 것**
>
> **결정적 근거 (사장님):** *"DB 가 다르면 CS 를 해줄 수가 없어."*

**PM 이 아침에 올린 '고객사별 랜덤 생성' 안은 폐기한다.** 교과서만 보고 현장을 안 본 제안이었다.

#### 왜 랜덤 생성이 틀렸나 — CS 가 불가능해진다

| 상황 | 공통 비번 | PC 마다 다른 비번 |
|---|---|---|
| "히트판이 안 켜져요" | 원격 붙어 즉시 DB 확인 | **그 PC 비번부터 찾아야** 함 |
| 백업 복구 요청 | 즉시 처리 | 비번 모르면 복구 불가 |
| 업데이트 실패 | 로그 보고 조치 | DB 접근 자체가 막힘 |
| **고객 PC 고장 · 디스크만 생존** | 새 PC 에 그대로 붙임 | **비번이 그 PC 에만 있었으면 데이터 이관 불가** |
| 한 PC 에 ERP 2개(본점·지점) | 계정 1개 | 계정 2개로 갈림 |
| 기존에 MariaDB 쓰던 업체 | 관리 일관 | 그 회사 DBA 가 낯선 계정 발견 |

마지막에서 두 번째 줄이 가장 무겁다. **디스크만 살아있는데 비번이 그 PC 에만 있었으면
백업 파일이 있어도 복원할 DB 에 못 붙는다.**

CS 팀장(강지원) 관점 — 동종업계 20년에서 *"비밀번호가 뭐예요"* 는 **실제로 들어오는 문의**다.
우리가 답을 모르면 원격 접속 예약을 잡아야 하고 그동안 고객 업무가 멈춘다.
**히트판이 이긴 이유("쓰기가 겁나 쉬웠다")의 정반대다.**

#### 실측 — 18개 파일이 이 비번 하나에 묶여 있다

```
$ git grep -ln 'Hitpan2025' HEAD -- '*.cs' '*.ps1' '*.bat' '*.sh' '*.iss' '*.yml' '*.sql'
→ 18개 파일 (BackupService.cs · backup-daily.ps1/.sh · MigrationSmokeTest ·
   설치 스크립트 5종 · hitpan-start.bat · Sandbox·통합테스트 등)
```

PC 마다 다른 비번이면 이 전부가 "비번을 읽어오는" 구조로 바뀌어야 한다.
**한 곳만 놓쳐도 그 고객사는 백업이 조용히 실패하거나 업데이트가 죽는다.**
백업 실패는 당장 안 보인다 — 필요할 때 없다는 걸 안다.

### 1-3. 그렇다면 실제 위험은 무엇인가 — 재평가

PM 이 아침에 *"고객사 A 비번을 알면 B·C·D 전부 열린다"* 고 적은 것은 **과장이었다.**

정확히는 이렇다:

```
비번을 안다  →  그 PC 에 물리적·네트워크 접근이 가능해야  →  DB 접근
```

히트판 DB 계정은 **`'hitpan'@'localhost'`** — 원격 접속 계정이 아니다.
비번을 알아도 **그 PC 앞에 앉거나 그 PC 를 장악해야** 의미가 있다.
그 시점이면 이미 `db.conf` 도 파일도 읽힌다 — **공통이든 랜덤이든 차이가 없다.**

⇒ 공통 비번의 **실질 위험 증가는 제한적**이다. 사장님 판단이 옳다.

### 1-3-1. 🔴 공통 DB 비번은 "비밀번호"가 아니라 **제품 설정값**이다 (혼동 금지)

> **이 구분을 먼저 못 짚어 2026-07-31 실제 사고가 날 뻔했다.** §7 참조.

| 성격 | 내용 |
|---|---|
| 공개 값에 가깝다 | 설치 EXE(`install.bat`) 에 **평문**으로 들어가 전 고객사에 배포된다 |
| 비밀이 아니다 | 숨기는 게 목적이 아니라 **CS 가 알고 있어야** 하는 값이다 |
| 안전한 이유 | 비밀이라서가 아니라 **`localhost` 바인딩**이라 원격 접근이 불가능해서다 |
| 추측 난이도 | **의미 없다.** 어차피 배포되는 값이라 강도를 높여도 얻는 게 없다 |

⛔ **절대 금지**: 본사·개인 자격증명(마스터 계정·메일·은행·NCP·클라우드)과 **같거나 유사한 값 금지.**
설치본을 받은 누구나 메모장으로 열어보면 그 값이 보인다.

### 1-3-2. 확정값 — `HITPAN2026!` (사장님 결재 2026-07-31)

| 항목 | |
|---|---|
| 값 | `HITPAN2026!` |
| 근거 | 제품명 기반 — 개인·본사 자격증명과 무관 |
| 적용 시점 | **지금** — 기존 설치본 0건(사장님 확인). 베타 출시 후엔 못 바꾼다 |
| 종전값 | `Hitpan2025!` → 전량 교체 (18개 파일) |

> **왜 지금인가**: 기존 설치본이 없으므로 "업데이트 후 DB 접속 불가" 사고 위험이 0 이다.
> 고객 PC 에 한 대라도 깔리면 그 순간부터 교체 비용이 폭증한다.

### 1-4. 선례 — 사고 #38 은 다른 건이다

```
installer/hitpan-start.bat:20
::   사고 #38 봉합: 폴백 <비번> 제거 — 잘못된 자격증명 사용 차단
```

이는 *"잘못된 자격증명으로 접속을 시도하는 폴백"* 을 없앤 것이지
공통 비번 정책 자체를 부정한 것이 아니다. 혼동하지 않는다.

## 2. 🔴 P0-2 (진짜 P0) — `GRANT ALL ON *.*` 이 남의 DB 까지 전권을 준다

### 2-1. 실측

```
installer/install.bat:85
  CREATE USER IF NOT EXISTS 'hitpan'@'localhost' IDENTIFIED BY '<비번>';
  GRANT ALL ON *.* TO 'hitpan'@'localhost';
              ↑↑↑ 서버의 모든 데이터베이스에 대한 전권
```

### 2-2. 사장님 케이스 2 에서 정확히 사고가 된다

사장님이 지목하신 *"고객사 PC 에 별도로 MariaDB 가 설치되어 있을 경우"* 다.

| 상황 | `GRANT ALL ON *.*` 의 결과 |
|---|---|
| 그 회사가 MariaDB 로 다른 ERP·쇼핑몰 DB 운영 중 | 히트판 계정이 **남의 DB 까지 읽고 쓰고 지울 수 있다** |
| 히트판에 SQL 인젝션 취약점 1개라도 있으면 | 피해가 히트판 DB 를 넘어 **그 회사 전체 DB 로 번진다** |
| 우리 마이그레이션 스크립트 버그 | 남의 DB 를 건드릴 수 있는 권한이 있다 |

> **남의 집에 들어가면서 집 전체 마스터키를 만드는 격이다.**
> 비밀번호가 공통인 것보다 이쪽이 실제 위험이 크다.

### 2-3. 봉합

```sql
GRANT ALL ON hitpan_erp.* TO 'hitpan'@'localhost';
```

`*.*` → `hitpan_erp.*` — **한 글자 차이**다. 히트판은 자기 DB 만 쓰므로 기능 영향 0.

⚠️ **실측 확인 필요**: 마이그레이션·백업·워치독이 `hitpan_erp` 외 다른 스키마를 건드리는지
(`information_schema` 는 별도 권한 불필요). 건드린다면 그 대상만 개별 GRANT.

## 3. 🔴 P0-3 (진짜 P0) — 기존 MariaDB 가 있으면 침묵 실패한다

### 3-1. 실측

```
installer/install.bat:85
  mysql -u root -p%ROOT_PW% -e "CREATE USER ..." >nul 2>&1
                                                  ↑↑↑ 에러가 삼켜진다
```

### 3-2. 사장님 케이스 2 의 다른 얼굴

이미 MariaDB 가 깔린 PC 에서는 **그 회사 root 비밀번호를 우리가 모른다.**
`%ROOT_PW%` 는 우리 기본값이므로 접속이 실패하고, `>nul 2>&1` 이 에러를 삼킨다.

```
설치는 "성공"으로 끝난다  →  계정이 안 만들어졌다  →  로그인 단계에서 죽는다
```

**작10 에서 봉합한 것과 정확히 같은 구조다** — 침묵 실패.
[작10 설계서](../설계/설치배포/20260730_설치6단계_관측성_설계서.md) §1-3 *"로그가 침묵했다"* 와 동일.

### 3-3. 봉합 방향

1. `>nul 2>&1` 제거 → 종료코드·출력 로그 기록 (작10 `ExecLogged` 패턴 준용)
2. 기존 MariaDB 감지 시 **설치 마법사가 root 비밀번호를 묻는다**
   — 헌법 #20(워크플로우 안 끊김) · 히트판 정신(*"처음 보는 사람이 혼자 쓸 수 있냐"*)
3. 실패 시 고객이 읽을 수 있는 안내 (개발용어 금지 — 헌법 CS 원칙)

## 7. 🔴 아차사고 기록 — 마스터 계정 비밀번호가 배포될 뻔했다 (2026-07-31)

**실제로 배포되지는 않았다.** 그러나 한 단계만 더 갔으면 전 고객사 PC 에 들어갔다.
같은 일이 반복되지 않도록 경위를 그대로 남긴다.

### 7-1. 경위

```
PM: "공통 DB 비밀번호 값을 확정해주십시오"   ← 값의 성격을 설명하지 않고 물었다
사장님: (히트판 마스터 계정 비밀번호를 제시)
PM: 확인 요청 → 사장님 "히트판 마스터계정 패스워드야"
PM: 즉시 중단 · 사용 불가 사유 설명 · 마스터 계정 비번 변경 요청
사장님 결재: HITPAN2026! 로 확정
```

### 7-2. 만약 그대로 갔다면

`install.bat` 은 **평문 배치 파일**이고 설치 EXE 에 담겨 고객에게 배포된다.
메모장으로 열면 그대로 보인다.

⇒ **히트판 마스터 계정 비밀번호가 전 고객사 PC 에 배포된다.**

### 7-3. 원인 — PM 이 값의 성격을 먼저 설명하지 않았다

"비밀번호"라는 단어가 붙어 있으니 **실제 비밀번호를 떠올리는 것이 자연스러운 흐름**이었다.
이것은 사장님 실수가 아니라 **PM 의 질문 설계 결함**이다.

§1-3-1 을 먼저 설명했어야 했다 — *"이건 비밀이 아니라 배포되는 제품 설정값입니다."*

### 7-4. 후속 조치

| # | 조치 | 담당 | 상태 |
|---|---|---|---|
| 1 | **히트판 마스터 계정 비밀번호 변경** (대화에 평문 노출됨) | 사장님 | 🔴 **당일 처리 요청** |
| 2 | 같은 값을 다른 곳에 재사용 중이면 함께 변경 | 사장님 | 🔴 확인 필요 |
| 3 | §1-3-1 "제품 설정값이지 비밀이 아니다" 명문화 | PM | ✅ 완료 |
| 4 | 앞으로 시크릿 값을 물을 때 **성격·노출 범위를 먼저 고지** | PM | ✅ 본 문서에 규범화 |

> **노출된 자격증명은 실제 유출 여부와 무관하게 폐기한다.** 이것이 원칙이다.

### 7-5. 규범 — 시크릿 값을 물을 때 (헌법 #22·#33 파생)

값을 요청하기 **전에** 반드시 고지한다:

1. **어디에 들어가는가** (평문 배포되는가, 서버에만 있는가)
2. **누가 볼 수 있는가** (고객 전원인가, 본사만인가)
3. **본사·개인 자격증명 재사용 금지**를 명시적으로 경고

이것 없이 *"값을 정해주십시오"* 라고 묻는 것은 **PM 의 직무유기**다.
