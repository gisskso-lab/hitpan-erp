## 0. 사장님 지시

> *"반품은 조회전용이 아니라, **워크플로우의 한 축**이지. 따라서, **매입목록이나, 매입관련 현황·분석·통계자료·순위표 에도 반영**되야 하고, **회계·재고에도 자동반영**되야 함."*
> *"판매는 전표를 삭제하면 되지만, **매입은 워크플로우 축으로 유기적으로 작동**하는게 맞지. **애초에 그렇게 설계하기도 했고**"*
> *"워크플로우 흐름에 따라 데이터 **재고·금액의 정합성은 무조건 맞아야됨**."*

**작업 중 사장님이 세 번 방향을 잡아 주셨다** — 그때마다 내 판단이 틀렸다(§6).

---

## 1. 무엇이 틀렸나

매입 리포트 **20종이 `purchase_returns` 를 아예 안 봤다**(참조 SQL **0건**).

### 사장님 설명이 이걸 정확히 짚는다

> *"불량100개가 들어왓다고 해도, **100개를 반품하고 재주문 하겠지**"*

| 단계 | 실제 |
|---|---|
| 불량 100개 매입 | 매입 100 |
| 100개 반품 | 매입 0 (안 산 것과 같다) |
| 100개 재주문 | 매입 100 |
| **실제로 산 것** | **100개** |
| **화면에 보이던 것** | 🔴 **200개** |

⇒ **반품을 전액 되돌린 업체도 순위 1위로 남았다.** 순위표가 거짓말을 했다.

---

## 2. 🔴 왜 유형 추가가 아니라 SQL 자체를 바꿨나

처음엔 판매쪽이 「판매종합현황(반품포함)」을 **별도 유형**으로 뒀다는 이유로
매입도 「매입종합현황(반품포함)」을 **추가**하려 했다.

**사장님이 바로잡으셨다** — *"**매입을 매출에 맞춰서 하지 않잖아.**"*

⇒ **매입은 매입 논리로 판단한다.** 유형을 따로 만들어 고르게 하는 것은
*"불량도 매입에 넣고 볼까요, 뺄까요"* 를 묻는 셈인데 **답은 하나뿐이다.**

만들었던 「매입종합현황」·「반품포함 순위」는 **전부 되돌리고** 기존 SQL 자체를 고쳤다.

## 3. 바꾼 것

### 리포트 18종 — `UNION ALL` 음수 합산

| 구분 | 종수 | 상수 |
|---|---|---|
| 매입현황 | 5 | `PR_BY_PERIOD` · `PR_BY_PARTNER` · `PR_BY_ITEM` · `PR_MONTHLY` · `PR_PARTNER_YEARLY` |
| 매입순위표 | 5 | `PRR_BY_PARTNER` · `PRR_BY_ITEM` · `PRR_BY_PERIOD` · `PRR_BY_REGION` · `PRR_BY_EMPLOYEE` |
| 매입통계 월별 | 4 | `PRSTATS_*_MONTHLY` |
| 매입통계 전년동기 | 4 | `PRSTATS_YOY_*` |

공통 조건: `rt.is_deleted = 0 AND rt.status = 'confirmed'` (헌법 #6) · 날짜축은 **`rt.return_date`**

### 회계·자금 6곳

| 자리 | 처리 |
|---|---|
| **부가세 신고** `FinanceService` | 🔴 **차감** — 안 산 물건의 매입세액을 국세청에 공제 신청하던 상태 |
| **미지급금** KPI | 🔴 **차감** — 돌려준 물건 값은 줄 돈이 아니다 |
| **미지급 aging** `CollectionService` | 전표별 차감 — 안 빼면 돌려준 값이 90일 초과로 늙어간다 |
| 대시보드 이달매입 | 차감 |
| 손익 월별추이 | 차감 |
| 6개월 추이 | 차감 |
| **매입매출장** | 🟢 **빼지 않고 반품을 음수 「행」으로 추가** |

⚠️ **매입매출장만 다르게 처리한 이유** — 여기는 **집계가 아니라 전표 목록**이다.
빼서 없애면 *"매입은 있는데 돌려준 기록이 없는"* 장부가 되어 세무사·거래처가 대사할 수 없다.

## 4. 안 바꾼 것

| 대상 | 이유 |
|---|---|
| **매입단가 변동현황** `PR_PRICE` | 최저·최고·**평균 단가**라 *"반품분을 뺀 단가"* 가 성립하지 않는다 |
| **발주현황** `PO_*` | 발주 단계엔 반품이 없다 |
| **판매(Sales) 전 영역** | 🔴 **매입반품은 매출에 영향이 없다** — 사장님 확인 |

### 🔴 판매를 건드리려다 멈춘 경위

내가 *"판매 순위표도 반품을 안 뺀다 = 양쪽 공통 문제"* 라고 보고드려
사장님이 *"모두 적용"* 지시를 주셨다. 그런데 사장님이 되물으셨다 —
***"근데 매출에 영향이 있나?? 매입반품인데?"*** · ***"판매에 영향을 주지 않아"***

**맞다.** 매입반품은 매입 숫자만 줄인다. 매출반품(판매반품)과는 **다른 축**이고 서로 안 섞인다.
⇒ 판매쪽(매출반품이 매출 순위·통계에 안 빠지는 문제)은 **별도 차수**로 올린다.

## 5. 🔴 실측 — 로컬 MariaDB 에 사장님 시나리오를 넣고 20종 전부 실행

**불량 100개 매입 → 100개 반품 → 100개 재주문** (단가 1,000원)

| 항목 | 봉합 전 | 봉합 후 |
|---|---|---|
| 매입현황 | **200개 / 200,000원** 🔴 | **100개 / 100,000원** 🟢 |
| 부가세 매입세액 | 20,000원 🔴 | **10,000원** 🟢 |
| 미지급금 | 220,000원 🔴 | **110,000원** 🟢 |
| YoY 전년(매입 30만·반품 10만) | 300,000원 🔴 | **200,000원** 🟢 |
| **재고** | 100개 🟢 | 100개 🟢 |

🟢 **SQL 20종 실행 성공 20 / 실패 0**

⚠️ **재고는 원래 맞았다** — 사장님이 *"재고에만 영향이 있겠지"* 라고 하신 그대로다.
반품확정이 `stock_ledger` OUT + `item_stock` 차감을 이미 정확히 하고 있었다.
틀렸던 건 **화면 숫자**뿐이다.

### 실측 중에 더 찾은 것 2건

**① 전량 반품된 건이 목록에서 통째로 사라졌다.**
순액도 0, 건수도 0(매입 1 + 반품 −1)이라 `HAVING` 을 못 넘었다.
🔴 사장님 헌법 — *"목록에서 숨기면 사라지는 게 아니라 안 보이는 채로 쌓인다."*
⇒ **절대값 기준**으로 바꿔 **0원으로 보이게** 했다. *"샀다가 다 물렸다"* 도 사실이다.

**② YoY 는 당해·전년 <u>양쪽</u> 반품을 다 빼야 한다.**
한쪽만 빼면 전년이 부풀려져 **증감률이 거짓**이 된다.

## 7. 게이트

**`PurchaseReturnInReportsGateTests` 신설 99건** — 18종 × 5축 + 회계 4 + 단가 제외 1

| 지키는 것 |
|---|
| 반품 테이블을 보는가 (`UNION ALL`) |
| 확정 반품만 빼는가 (`is_deleted=0` · `status='confirmed'`) |
| 날짜축이 `return_date` 인가 |
| **모든** 집계 컬럼이 음수인가 |
| YoY 가 전년 구간도 빼는가 |
| 전량반품이 `HAVING` 에 안 걸리는가 |
| 회계 4곳(부가세·미지급금·aging·매입매출장) |
| 단가는 **안 건드렸는가** |

### 반증 4건 실측
부호 제거 · YoY 전년구간 제거 · 미지급금 차감 제거 · `HAVING` 되돌림
→ **각각 정확히 그 항목만 FAIL**, 되돌리면 통과.

🔴 **첫 반증에서 게이트 하나가 가짜였다.** 마이너스가 *"하나라도"* 있으면 통과하게 짜서
`qty` 부호만 떼도 **초록불**이 나왔다 ⇒ **집계 컬럼 수만큼 세도록** 고쳤다.
*"낱말 하나로 검사 금지"* 를 또 되밟았다.
