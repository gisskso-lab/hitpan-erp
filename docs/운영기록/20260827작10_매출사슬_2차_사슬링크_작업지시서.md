## 1. W1 — 🔴🔴 명세서 수정이 수주 링크를 끊고, **삭제 가드가 뚫린다**

### 증상 (실측 · main `34dd5acd`)

`SalesService.UpdateDeliveryAsync` — `sales_delivery_items` 전량 DELETE 후 재INSERT 하는데
`order_item_id` 에 **하드코딩 `NULL`** 이 들어간다.

```
DELETE FROM sales_delivery_items WHERE delivery_id = @DeliveryId ...   (:924)
INSERT INTO sales_delivery_items
    (delivery_item_id, delivery_id, tenant_id, order_item_id, item_id, ...)
VALUES
    (@DeliveryItemId, @DeliveryId, @TenantId, NULL, @ItemId, ...)      (:934-939)
```

⇒ **draft 거래명세서를 한 번만 수정 저장하면 모든 라인의 수주라인 링크가 영구히 NULL 이 된다.**
생성 경로(`:274`)는 값을 넣는데 **수정 경로만 NULL 로 덮는다.**

### 🔴 왜 이게 단순 데이터 손실이 아닌가 — **가드가 뚫린다**

`DeleteSalesOrderAsync` 의 "판매전환된 라인 차단" 가드가 **`order_item_id` 로 판정한다** (:1625-1637):

```sql
SELECT COUNT(*) FROM sales_delivery_items di
  JOIN sales_deliveries sd ON ...
 WHERE di.order_item_id IN (SELECT order_item_id FROM sales_order_items WHERE order_id=@Id ...)
   AND sd.status <> 'cancelled'
```

링크가 NULL 이면 이 COUNT 가 **0** 이 된다.
⇒ 🔴 **이미 출고된 수주서가 삭제 가능해진다.** 조용한 어긋남이 아니라 **가드 무력화**다.

### 🔴 왜 화면이 다시 보내면 되는 게 아닌가

- `UpdateDeliveryAsync` 가 받는 `DeliveryItemDto` 에 **`OrderItemId` 가 없다**
- 조회 SQL 이 `order_item_id` 를 **한 번도 읽지 않는다**(실측 — 전 파일 grep)
  ⇒ **화면은 받은 적이 없는 값을 되돌려줄 수 없다.**
- ⚠️ 이건 작7 이 겪은 것과 **같은 모양**이다 — `DeliveryItemDto` 주석이 그 사고를 적어놨다:
  *"`sales_return_items.delivery_item_id` 는 컬럼·FK·DTO 가 전부 있었는데 **화면에 값이 안 와서** 채울 수가 없었다."*
  **한 계층 위에서 같은 일이 벌어지고 있다.**

### 봉합 방침 — **서버가 보존한다** (화면에 의존하지 않는다)

DELETE 전에 `(delivery_item_id → order_item_id)` 를 읽어두고, 재INSERT 시 되붙인다.
- 🔴 **화면 수정 없이 서버만으로 닫는다** — 화면을 고치는 방식은 *"화면이 보내주면"* 이라는
  전제에 기대는데, 그 전제가 바로 이번에 깨진 것이다.
- 매칭 키: `delivery_item_id`(화면이 보내는 값 — `DeliveryItemDto.DeliveryItemId` 는 **있다**)
- 새로 추가된 라인은 `order_item_id` 가 없는 게 정상 ⇒ NULL 유지
- ⚠️ **확정 후엔 이 경로가 안 돈다**(`:809-812` draft 만 허용) — draft 구간의 문제다

## 2. W2 — 견적→수주 링크가 **컬럼째 없다**

### 증상
- `sales_orders` 에 **`quotation_id` 컬럼이 존재하지 않는다**(DDL·엔티티·EF 매핑 전부)
- 유일한 흔적 = `QuotationService.cs:326` 의 **memo 자유텍스트** `"견적서 전환: {QuoteNo}"`
  ⇒ 사용자가 수주서를 수정하면 `memo` 가 화면 값으로 **덮어써져 연결이 소멸**한다
- 역방향 `quotations.converted_order_id` 는 있으나 **`order_id`(UUID)가 아니라 `order_no`(번호)** 가 들어간다
  (`:350-353`). 컬럼명과 내용이 어긋나고, **JOIN 하는 코드는 0곳**(에러메시지 표시용뿐)

### 봉합
- **DB-114**: `sales_orders.quotation_id varchar(36) NULL` + 인덱스 신설
- 견적→수주 전환 시 **`quotation_id` 저장**
- `converted_order_id` 에 **`order_id` 를 넣도록 교정** — ⚠️ 기존 행은 번호가 들어있으므로
  **마이그로 되짚어 채운다**(`order_no` 로 조인해 `order_id` 로 치환). 못 찾으면 그대로 둔다
- 🔴 **memo 문자열은 지우지 않는다** — 사람이 읽는 흔적으로 그대로 두고, 기계가 되짚는 축만 추가한다
  (1차에서 사장님께 보고한 원칙: *"비고는 사람이 읽는 용도, 되짚는 축은 컬럼으로"*)

## 3. W3 — 수주 자동생성 **Y/N 반자동** (사장님 결재①)

### 🔴 PM 정정 — **Y/N 은 이미 있었다**

착수 전 이 문서에 *"사용자에게 묻지 않고 조용히 만든다"* 고 적었는데 **틀렸다.**
**서버만 보고 화면을 안 봤다.**

실제로는 `DeliveryPage.razor:322-334` 에 **Y/N 다이얼로그가 이미 있다**(20260825작5).
- `_isNew` 이고 수주 연결이 없으면 `ShowMessageBoxAsync` 로 확인을 받고,
  **취소하면 저장이 중단된다**(`proceed != true` → return)
- 자동생성분 **`is_auto=1` 표식**도 이미 들어간다
- 1차(작9 W4)에서 **멱등 가드**까지 붙어 중복생성도 막혔다

⇒ **사장님 결재 ①(Y/N 반자동)·②(표식)은 이미 충족돼 있다.**

### 남은 것 — **문구 하나**

사장님이 지시한 문구와 화면 문구가 다르다.

| | 문구 |
|---|---|
| 사장님 지시 | **"수주서가 없는 거래입니다. 수주서를 자동 생성합니다"** |
| 현재 화면 | "이 판매거래의 수주서가 없습니다. 수주서는 자동으로 생성됩니다." |

⇒ **지시 문구 그대로** 맞춘다. 그 외 동작은 손대지 않는다(이미 맞다).

⚠️ **흐름을 끊지 않는다**(헌법 #20) — Y 면 그대로 저장, N 이면 사용자가 수주를 먼저 만들 수 있다.

## 4. W4 — MDB 마이그 소급분 (사장님 결재①②)

### 증상 (실측)
- `MdbMigrationService` 의 `DeliveryHeaderRow` 에 **`OrderId` 필드가 아예 없다**(:4814-4831)
- 마이그된 거래명세서는 **전량 `order_id = NULL`**, `status='confirmed'`
- 원인: 수주는 **DOCFO/DOCF2**, 명세서는 **DOCFB** — 서로 다른 원본이라 조인이 없다

### 봉합 방침
- **소급 도구**로 만든다(마이그 코드 자체를 바꾸지 않는다)
  - 🔴 마이그는 **레거시 그대로**가 원칙(헌법 #26). 없는 수주서를 만드는 건 레거시에 없던 데이터 생성이다
  - 사장님 지시가 명시적이므로 진행하되 **반드시 구분 가능해야** 한다
- **Y/N 확인 후 실행** — 실행 전 **대상 건수를 먼저 보여준다**(되돌리기 어렵다)
- 🔴 **`is_auto=1` 표식 필수** — 레거시 실데이터와 구분(사장님 *"중요함"*)
- 🟢 `sales_orders.is_auto` 는 **현재 아무도 쓰지 않는다**(INSERT 3곳 전부 미설정=0) ⇒ 충돌 없이 전용 가능
- ⚠️ **범위 결정 필요** — 이번 차수에 넣을지, 별도 화면으로 뺄지는 W1~W3 완료 후 판단.
  **W1~W3 이 먼저다**(신규 경로가 안 새야 소급이 의미가 있다)
