**이 아래는 위 오더를 명문화한 것이다.** 오더에 없던 요구를 넣지 않는다(#33).

### §1-1 이해
- 「별건 작업」 = G1-3 H 화면 장치가 드러낸 **제품 결함**(약관 미동의 「나」 가 약관 화면이 아니라 본 화면에 자리 잡음)을 장치 작업과 떼어 따로 고친다.
- 「장치는 분리」 = 장치는 결함을 `H-OBS-TERMS`(관찰 · 빨강 아님)로 적고 초록으로 갔다. 이 작업은 결함을 고친 뒤 **그 관찰 줄을 다시 빨강 게이트로 되돌리는 것**까지 한다(G1-3 H 개발명세서 §9 · 「결함이 고쳐지면 이 줄을 지우고 H-D2 를 다시 [장치] 빨강으로」).
- 「기존 흐름에 영향 0」 = 동의 끝난 사용자의 로그인·본 화면·업데이트 팝업(#43)은 **지금과 똑같아야** 한다.
- 안 하면: 처음 로그인한 직원이 약관 화면 대신 본 화면 + 「권한이 없습니다」 알림 두 개를 본다(§2 S-2). 물어보지 않고는 못 쓴다.

### §1-2 해석이 갈리는 자리
- [1-V] §4 의 **잠복 결함**(판정 기준 세 곳 어긋남)이 「약관 결함」 에 들어가나? [1-V] 는 「이번 원인 아님 · 별건 등록 권고」. 존은 **넣자**고 권고(§4-2 — 안 B 를 안전하게 하려면 C 가 필요). 빼라면 §4 의 C 갈래와 T-1 을 걷는다 → §10 Q-2.

### §4-2 권고 — **B + C 묶음**
- 까닭 ① B 는 결함이 「어떤 순서로」 생기든 막는다 — §2-2 의 추정에 기대지 않는다.
- 까닭 ② A 는 동의 끝난 모든 사용자의 로그인 줄기를 건드린다 — 대표 「기존 흐름에 영향 0」 과 정면으로 부딪힌다.
- 까닭 ③ B 와 약관 화면(S-10)은 **같은 status** 를 읽는다. 기준이 하나면 「관문은 미동의 · 약관 화면은 동의함」 핑퐁이 원리상 안 난다. C 를 빼고 B 만 하면 지금 기준(아무 행)으로 같게 읽으니 핑퐁은 없지만 잠복 결함이 남는다.
- 🔴 금지 조합: **관문은 엄격 기준 · 약관 화면은 느슨한 기준** — `/terms`↔`/` 무한 왕복. 두 화면은 반드시 같은 끝점을 읽는다.
