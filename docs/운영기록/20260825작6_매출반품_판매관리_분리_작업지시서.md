## [2] 원인 — 백엔드는 분리돼 있는데 화면만 묶여 있다

### 🟢 백엔드는 두 업무를 정확히 구분한다

| 구분 | 확정 시 재고 | 검사 |
|---|---|---|
| **매출반품** (고객 → 우리) | `move_type='in'` **증가** | 재고 초과 검사 **없음** (받는 것이니 당연) |
| **매입반품** (우리 → 공급처) | `move_type='out'` **감소** | **재고 초과 검사 있음** ("반품 수량이 현재 재고를 초과합니다") |

회계도 대칭이다 — 매출반품은 매출 역분개, 매입반품은 매입 차감.
**엔드포인트 7개·프론트 서비스 5메서드 모두 완비.**

### 🔴 화면만 한 곳에 묶여 있다

| 메뉴 | 위치 | 실제 대상 |
|---|---|---|
| 반품 처리 | **매입관리** | 화면 안 콤보로 매입/**매출 둘 다** |
| 반품현황 | **매입관리** | **매입반품만** (`purchase_returns` 3곳 하드코딩) |

⇒ **판매 담당자가 매입관리로 들어가 콤보를 바꿔야 자기 업무를 본다.**
⇒ **매출반품 현황은 어디에도 없다.** 사장님 2번 반려가 정확하다.
⇒ 3번(더블클릭)이 "확인안됨"인 것도 **같은 뿌리** — 전표를 판매관리에서 못 찾으셨다.

## [3] 작업 범위

### ① 판매관리에 매출반품 전표 신설

- 새 라우트 · `WorkDocumentKind.SalesReturn` 추가 · 탭 매핑
- **매출 전용 고정** — 반품유형 콤보 제거
- 20260825작4 의 더블클릭 가드(진입 가드 + `finally`) **그대로 계승**
- 확정 다이얼로그 문구는 매출 방향(Reverse IN, 재고 증가)

### ② 판매관리에 매출반품현황 신설

- `SR_BY_PERIOD` / `SR_BY_PARTNER` / `SR_BY_ITEM` / `SR_BY_EMPLOYEE` 4종 신설
  — 매입반품현황 `RT_*` 4종과 **대칭**
- 20260825작3 결재 계승: **확정분(`status = 'confirmed'`)만 집계**
- 작성자 조인은 20260825작5 결재 계승: **`ec.user_id = sr.created_by`**
- 조회유형 재조회는 20260825작2 봉합 계승: `ValueChanged` + 검색어 초기화

### ③ 기존 매입 화면을 매입 전용으로 고정

- 반품유형 콤보 제거 · `_returnType` 을 `purchase_return` 고정
- ⚠️ **잘못 골라 반대 방향으로 재고가 움직이는 사고를 구조적으로 차단**

### 손대지 않을 것

- 백엔드 반품 로직(확정·취소·재고·회계) — 이미 정확하다
- 매입반품현황 `RT_*` 4종 — 매입 쪽은 그대로
- 반품 API 계약 — 화면만 가른다
