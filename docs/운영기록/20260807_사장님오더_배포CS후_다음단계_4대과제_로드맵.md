## 1. 전제 — "배포·CS 영역 기본 틀"이 먼저다

4대 과제는 **배포·CS 틀이 선 다음**이다. 사장님이 순서를 명시하셨다.

### 1-1. 왜 이 순서인가 (2026-08-07 실측 근거)

오늘 배포 종단 검증에서 드러난 것:

- **고칠 수는 있는데 고객에게 도달하지 않는다** — 새 버전 확인이 하루 1회 + 그 기억이 메모리(N-10)
- **고객이 막혀도 우리가 모른다** — 백오피스에 고객 버전 조회 화면 없음(설계팀 P1-6)
- **고객이 물어볼 곳이 없다** — 고객센터 연락처 미정 (D안 결재 완료, 개설 대기)

즉 **1~4번을 아무리 잘 해도, 배포·CS 틀이 없으면 그 결과가 고객에게 안 간다.**
사장님 순서가 옳다.

### 1-2. 사장님이 그린 그림 (같은 날 오더)

> *"워치독, 업데이트 종단이 구현되면, 그 후부터는 수정·보완작업이 쉬워질거야.
> 왜냐하면 **재설치 없이 코드수정 → 업데이트 → 실측** 이 세 단계만 하면 되거든."*

**이 3단계 사이클이 서는 것이 곧 "기본 틀"이다.**
1~4번은 전부 "수정·보완"이므로, 사이클이 느리면 네 과제 전부가 느려진다.

### 과제 1 — 히트판 ERP 기능 하나하나 찍어보며 수정·보완

> 사장님 원문: *"히트판ERP 기능하나하나 찍어보며 수정, 보완사항 수정"*

**성격**: 전수 점검. 화면·기능을 실제로 눌러보며 잡는 작업.

**연결되는 기존 원칙**
- 헌법 #8 — 6단계 워크플로우 순서 (설정 → 마스터 → 매입 → 판매 → 현황 → 재무)
- 헌법 #10 — 한 화면씩 완성 → 사장님 확인 → 승인 → 커밋
- **"이 화면, 처음 보는 사람이 혼자 쓸 수 있냐?"** — 모든 화면의 최종 통과 기준
- ERP 매니저 임무 — *"실제 경리·구매담당이 3분 안에 쓸 수 있는지"*

**착수 전 정해야 할 것**
- 점검 순서 (6단계 워크플로우 순서를 그대로 따를지)
- 판정 기준 (무엇을 "보완 필요"로 볼지)
- 기록 방식 (화면당 1건인지, 묶음인지)

## 3. 과제 간 관계 — PM 소견

사장님이 1→2→3→4 순으로 적으셨으나, **완전한 직렬은 아니다.**

```
[배포·CS 기본 틀]  ← 지금 여기
        │
        ├──→ 과제1 (ERP 전수점검) ──┐
        │                            ├──→ 과제2 (CS 챗봇)
        └──→ 과제3 (랜딩·백오피스) ─┘     ※ 1·3의 결과가 챗봇 지식이 된다
                    │
                    └──→ 과제4 (요금정책)
                          ※ 백오피스 마스터 화면이 있어야 요금을 넣는다
```

**근거**
- **과제 2는 1·3 뒤가 자연스럽다** — 챗봇이 답할 내용이 1·3에서 나온다. 먼저 만들면 바뀐 기능을 다시 학습시켜야 한다
- **과제 4는 과제 3과 묶인다** — 가격은 코드가 아니라 **백오피스 마스터 화면**에서 관리하기로 이미 정해져 있다
- **과제 1·3은 병행 가능** — 서로 다른 시스템이다

⚠️ **이건 PM 소견이지 결정이 아니다.** 순서는 사장님이 정하신다.
