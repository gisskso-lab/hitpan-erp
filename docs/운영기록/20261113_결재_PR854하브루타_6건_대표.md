## 6. 1번 실행 기록 (#29 사전 승인 = §5 · 설정만 · 코드 0)

### 6-1. 실행 직전 새로 드러난 사실 — [1-V] 가 놓친 것
- **N4** `build-installer.yml` 도 `environment: production` 을 쓴다. 트리거 = **태그 `v*.*.*` push** + 수동 실행. [1-V] A-4 ④ 는 「표본 배포 2건 모두 main」 으로 판단했는데 이 워크플로를 세지 않았다. 마지막 실행 = 8/20 · 수동 · **`fix/installer-root-unify` 가지**에서(main 아님).
- ④ 를 「branch = main」 만으로 걸면 **태그로 도는 설치기 빌드가 승인 단계에서 거절된다**(태그는 가지가 아니다). → 배포·설치 경로 무접촉 원칙(10/8)에 따라 **태그 `v*.*.*` 를 함께 허용**한다. 가지 수동 실행(8/20 모양)은 ④ 의 뜻대로 막힌다 — 앞으로 설치기 수동 빌드는 main 에서 돌린다.
- 태그 허용은 「아무 커밋에 태그를 달면 운영 job 까지 간다」 는 뜻이다. 다만 운영 job 앞에는 그대로 **대표 계정 승인 1명**(required reviewer)이 있다 — 바꾸기 전과 같은 방어. ⚠️ 이 계정은 PM 도구와 같은 계정이고 `can_admins_bypass=true` · `prevent_self_review=false` 다(§6-3 · [4] R4). 태그 보호 ruleset 은 별건 후보로 남긴다(이번 결재 범위 밖).
- **N5 (11/13 [4] R1 · 실행 뒤 적발)** `deploy-update.yml`(ERP 업데이트 게시)도 `production` 환경을 쓴다(수동 실행만). 9/22 `release/*` 가지에서 게시 2회(되돌림 게시 1회 포함). S3 뒤로는 **main 이 아닌 가지에서 ERP 게시 · 되돌림 게시를 하면 승인 단계에서 거절**된다 — main 에서 실행하면 그대로 된다. 태그로 실행하면 통과하지만 태그 push 는 build-installer 도 함께 돌린다. 1-나 질문(develop · 백오피스 배포 맥락)에서 **대표께 묻지 않은 범위**다 → 설정은 그대로 두고 대표께 사후 보고 · 확인(§6-5). `release/*` 허용 추가는 대표 결정(#29) 뒤에만. 고객 PC 의 되돌리기 화면(워치독)은 게시가 아니라 이 설정과 무관.
