## 3-1. 🆕 사업자등록증 **파일** 처리 규칙 (사장님 결재 2026-08-10)

### 결재된 것

> **"심사 중만 보관 후 폐기"** — 가입 승인 심사가 끝나면 파일을 파기한다.

### 사장님 추가 발언 (판단 근거)

> "보통은 사업자등록증 제출까지도 하거든"
> "사장이 제안한게 더 타이트 한거지"
> "사업자등록증 제출 요구 안하고, 사업자 정보만 제공받는거니"
> "기존 레거시 히트판은 사업자등록증 팩스로 받고 보관했거든"

### ⭐ 정책 위치 — 히트판은 스탠다드보다 **덜 가져간다**

| | 업계 일반 | **레거시 히트판** | 🆕 **새 히트판** |
|---|---|---|---|
| 등록증 파일 | 받아서 **영구 보관** | 팩스로 받아 **보관** | **심사 중만 보관 → 폐기** |
| 사업자 정보 | 보관 | 보관 | **보관** (세금계산서용) |

⇒ **§0 판정표의 "사장님 범위 < 스탠다드 → 그대로 간다" 에 해당한다.**
덜 가져가는 것은 리스크가 아니라 **셀링포인트**다(`architecture_local_db_tunnel` 과 같은 논리).

⚠️ **설계팀 오판 정정 기록** — 설계팀이 "업계 스탠다드를 따르자"는 지시를 *"업계만큼 가져오자"* 로
읽고 파일 보관 쪽으로 여쭸다. 사장님 지적대로 **사장님 안이 더 타이트한 쪽**이었다.
스탠다드는 **상한이지 목표가 아니다.**

### 구현 규칙

- [ ] 파일은 **심사 종료 시점에 파기** — 승인·거부 **양쪽 모두**
- [ ] 파기 = 실제 삭제 (soft delete 금지, 백업본 포함)
- [ ] 보관 중에도 **암호화** + 접근 로그 (헌법 #5)
- [ ] 파기 **실행 기록**을 남긴다 (언제 무엇을 지웠나 — 파기 자체가 입증 대상)
- [ ] 심사 없이 자동 승인되는 경로에서는 **OCR 직후 즉시 파기**

### ⚠️ 레거시 전환 시 별도 쟁점 (이번 범위 밖 — 기록만)

기존 5만 고객사는 공영정보(주)가 **팩스 원본을 이미 보관**하고 있다.
전환 시 그 보관본을 어떻게 할지는 **별도 결재 사항**이다(새 정책은 폐기인데 기존은 보관 중).
→ R5(기존 가입자 소급 수집)와 함께 판단.

## 7. ⬜ 미결 — 사장님 결재 필요

### OCR 엔진 선택

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A** | 외부 OCR (네이버 클로바 등) | 정확도 높음·즉시 | 🔴 **사업자등록증 이미지가 외부로 나간다** — 위탁 동의 필수, 약관 문안 추가 |
| **B** | 본사 서버 내부 처리 | 이미지 외부 유출 0·위탁 동의 불필요 | 개발 부담·정확도 낮음 |
| **C** | OCR 없이 **수기 입력 + 국세청 진위확인** | 가장 단순·**지금 당장 가능** | 사장님 오더의 "OCR 자동등록" 아님 |

**설계팀 의견**: 오더는 A/B 중 하나를 요구한다. 다만 **C 를 1단계로 먼저 열면** 세금계산서 발행이
막히지 않는다(수집은 되니까). OCR 은 편의 기능이고, **막혀 있는 것은 수집 자체**다.

⇒ 권고: **T2(수집)를 먼저, T3(OCR)를 뒤에.** 오더 순서와 다르므로 **사장님 판단 필요**.
