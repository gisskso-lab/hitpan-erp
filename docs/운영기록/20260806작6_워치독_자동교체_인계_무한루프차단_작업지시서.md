## 2. 봉합 설계 — 옛 워치독을 고치지 않고 우회

옛 워치독은 이미 고객 PC 에 있어 고칠 수 없다. 대신 **그가 원래 하는 일**에 올라탄다.

```
installer/HitPan-Universal.iss:2354
  schtasks /Create /TN "HitPan-ERP-API-tenant-{slot}"
           /TR "{app}\api\HitPan.API.exe ..." /RU SYSTEM /RL HIGHEST

UpdateOrchestrator.cs:952  RestartErp → TryRestartTask(ApiTask(slot)) → schtasks /Run
```

⇒ **업데이트가 api 폴더를 통째로 교체한 뒤, SYSTEM 권한으로 새 API 를 실행한다.**
그 새 API 가 우리 코드다. 여기서 인계받는다.

### 2-1. 흐름 (고객 조작 0)

```
1.2.52 워치독이 1.2.55 를 받음
   → api·web 교체 → schtasks /Run 으로 새 API 기동
   → ★ 새 API 가 watchdog.new 를 watchdog.handoff 로 복사 (구버전이 모르는 이름)
   → ★ 2분 뒤 교체 예약 등록
   → (구버전 워치독이 watchdog.new 를 지움 — 우리 복사본은 무사)
   → 2분 뒤: 워치독 멈춤 → 교체 → 재시작
   → 워치독도 1.2.55  ⇒ 이후로는 워치독이 스스로 교체(W4-3 내장)
```

### 2-2. 타이밍 — 왜 "복사"가 필수인가 ([3-V] C5 적발)

1.2.52 실제 순서(`UpdateOrchestrator.cs:207~237`):
```
RestartErp(:207) ── 새 API 기동 ── VerifyNewVersion(:221, 첫 성공 즉시 반환)
                                 └→ CleanupAfterSuccess(:237) → watchdog.new 삭제
```
새 API 기동 후 **5~60초 안에** 재료가 삭제된다. **2분 뒤 예약만 걸면 그때는 재료가 없다.**
⇒ 예약 **전에** 별도 폴더로 복사한다. 이 봉합이 없으면 A안 전체가 무효.

## 3. 구현

**신규** `src/HitPan.API/Startup/WatchdogHandoffBootstrap.cs`
**수정** `src/HitPan.API/Program.cs` (app.Run() **직전** 호출 — Run 은 블로킹이라 뒤에 두면 실행 안 됨)

| 안전 장치 | 근거 |
|---|---|
| 백그라운드 실행 + 전 구간 try/catch | ERP 기동을 1ms 도 늦추지 않고, 어떤 실패도 기동을 막지 않음 (#20) |
| 재료 판정 = **EXE 존재** (폴더 존재 아님) | 빈 폴더로 교체하면 그 PC 는 워치독을 잃음 |
| 부팅 복구 안전망을 **교체보다 먼저** 등록, 실패 시 교체 미시작 | 바닥 없이 뛰지 않음 |
| 버전 동일 시 아무것도 안 함 | 무한 재교체 차단 |
| 실패 시 구버전 복원 (`watchdog.bak`) | 새 워치독이 고장나도 그 PC 는 살아야 함 (#30) |
| 예외는 삼키되 **전부 로그** | #15 침묵 금지 |

## 4. [3-V] 동시 병렬검증 적발 — P0 2건 / P1 3건 (전부 봉합)

> 검증은 구현이 **끝난 뒤가 아니라 도는 중에** 돌렸다. PM 은 적발 내용을 **전부 직접 재현**해 사실 확인했다.

### P0-1 예약작업 이름 충돌 — **PM 자충수**

```
UpdateOrchestrator.cs:1016  "HitPanWatchdogSelfReplace"          (워치독 본체)
WatchdogHandoffBootstrap.cs:44  "HitPanWatchdogSelfReplace"      ← PM 이 그대로 씀
```

사고: 교체로 올라온 신버전 워치독이 기동 시 `CleanupStaleSelfReplaceArtifacts`(`Worker.cs:108`)를 도는데,
그건 `watchdog.new` 존재만 본다(`:1268`). 우리 재료는 `watchdog.handoff` 라 **안 보인다** → "잔재"로 오판해
**부팅 복구 안전망을 삭제**(`:1273`). 아직 교체 완료 판정 전인데 안전망이 사라진다 = 그 순간 정전이면 **영구 고립**.

**봉합**: `HitPanWatchdogHandoffSwap` / `HitPanWatchdogHandoffRecover` 로 이름 공간 분리.
PM 확인: 산출물에서 옛 이름 **0건**.

### P0-2 Guardian 부재 PC 가 실재 — **영구 사망 경로**

`git show 6aeb72b:installer/scripts/InstallWatchdog.ps1` — PM 확인:
```
:9   $ErrorActionPreference = 'Stop'
:36  sc.exe failure ... restart/5000
:39  Start-Service $ServiceName        ← 여기서 실패하면 즉사
:66  Register-ScheduledTask ...        ← Guardian 등록에 도달 못 함 (게다가 CIM 기반)
```
⇒ 1.2.52 고객 PC 에 Guardian 이 **없을 수 있다**(봉합은 2026-08-04 `ae18dc0`, 1.2.52 는 07-31).
그런데 `sc failure` 는 **비정상 종료에만** 반응한다 — 우리가 `Stop-Service` 로 정상 정지시킨 서비스는
되살려 주지 않는다. **재기동 실패 시 재부팅 전까지 아무도 살리지 않는다.**

**봉합**: 교체 전 `schtasks /Query` 로 Guardian 실재 확인 → 없으면 **직접 등록**(schtasks.exe, CIM 회피) →
등록조차 실패하면 **교체를 시작하지 않는다**(구버전 유지).
