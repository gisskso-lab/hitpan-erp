## 6대 정공법 축 (구조 변경 only)

### 축 1. 마이그 1분 절대 (헌법 #26 정공법 5축 통합)

**현재 봉합 상태:**
- Row-by-row INSERT (60만 = 10~30분)
- 청크 INSERT IGNORE (60만 = 5~10분)
- 둘 다 1분 격언 위반

**정공법:**
- **1-1. MySqlBulkCopy + LOAD DATA LOCAL INFILE**
  - `OleDbDataReader` → CSV 임시 파일 stream
  - `LOAD DATA LOCAL INFILE 'tmp.csv' INTO TABLE ...`
  - 1000만 행 ≈ 5~10초
- **1-2. OLEDB 병렬 SELECT (3 MDB 동시)**
  - PYOJUN·PANDATA·POTHER 별도 OleDbConnection
  - Task.WhenAll (헌법 #16 준수 — 각 MDB 별도 connection)
- **1-3. Stream 처리 (DataTable 폐기)**
  - 메모리 사용량 일정 (수 MB), 1000만 행 OOM 0
- **1-4. 인덱스 DISABLE → 마이그 → ENABLE KEYS**
  - 11개 대상 테이블 인덱스 일괄 재구축
- **1-5. 테이블별 병렬 마이그 (Task.WhenAll)**
  - 각 테이블 독립 connection (마이그 전용 풀, 축 3과 연계)
  - PANDATA 11개 테이블 동시

**측정 기준:** PYOJUN + PANDATA + POTHER 3 MDB 총 ≤ 60초 (60만/100만/1000만 동시 통과)

### 축 2. 멱등성 영속 키 — source_hash (CODE-06 정공법)

**현재 봉합 상태:**
- partners: `partner_code` SELECT 선조회 (race condition 가능)
- collections: `source_id = "mig-{S_YMD}-{S_BUY}-{rowIdx:D6}"` rowIdx 의존 (재정렬 시 깨짐)
- INSERT IGNORE 봉합 — silent swallow 위험 (DB-03)

**정공법:**
- **모든 마이그 테이블에 `migrated_source_hash CHAR(64)` 컬럼 + UNIQUE**
- `SHA256(buy_code + S_YMD + S_BUY + S_SEQ + ...)` 결정적 해시
- 정렬·rowIdx 의존성 0 — 어떤 순서로 읽어도 같은 row = 같은 hash
- INSERT IGNORE 대신 `ON DUPLICATE KEY UPDATE updated_at = VALUES(updated_at)`로 명시적 멱등
- SHOW WARNINGS 청크별 수집 → migration_errors 저장 (DB-03 silent 차단)

**대상 테이블 (12종):**
partners, items, employees, sales_orders, purchase_orders, stock_ledger, collections, cashbook, expenses, tax_invoices, bills, card_payments, bank_transactions

### 축 3. 마이그 전용 connection 풀 분리 (SEC-04/SET SESSION 정공법)

**현재 봉합 상태:**
- catch swallow + Dispose 강제 (반쪽 봉합)
- 마이그 connection이 일반 풀과 공유 → SET SESSION 누수 위험 잔존

**정공법:**
- **IMigrationDbConnection 인터페이스 신규** (IDbConnection과 분리)
- `MigrationDbConnectionFactory` — 마이그 전용 connection string + 별도 풀
- DI 등록: `AddScoped<IMigrationDbConnection>(...)`
- 마이그 풀은 SET SESSION (fk_checks=0, unique_checks=0, innodb_flush=2) 가져도 일반 컨트롤러 connection과 0 공유
- 일반 connection은 그대로 IDbConnection 사용 (영향 0)

**효과:** 마이그 후 PartnerController·CollectionController가 FK 우회 INSERT할 가능성 = 0 (구조적으로 차단)

### 축 4. 진행률 백엔드 분리 (CODE-01 정공법)

**현재 봉합 상태:**
- static ConcurrentDictionary 트릭 + Scoped store
- 폴링 2초 간격 (30분 = 900회 호출)

**정공법:**
- **SignalR Hub 신규** (`MigrationProgressHub`)
  - 마이그 진행 상태 → push 즉시
  - 폴링 폐기, 30분 마이그 = 0회 폴링
- **MigrationProgressService (Singleton)** — IDbConnection 의존 0
  - in-memory ConcurrentDictionary
  - SignalR 연동
- **MigrationJobStore는 DB INSERT 전용으로 분리** (Scoped)
  - jobId persistence만 담당
- 진행률 = SignalR push, persistence = DB INSERT, 둘 다 독립

**효과:**
- 폴링 0
- 베타 후 SaaS 클러스터 진입 시 SignalR backplane(Redis) 교체만으로 다중 서버 지원
- 백오피스 모니터링 (헌법 #22 위반 0, push 메타정보만)
