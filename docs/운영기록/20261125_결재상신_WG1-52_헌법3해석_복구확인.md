## 1. 무엇을 왜 대표께서 정하셔야 하나

### 1-1. 헌법 #3 원문 (한 글자도 안 바꿈)

> 3. **INSERT ONLY 원장** — stock_ledger, journal_lines UPDATE/DELETE 금지
> — `docs/헌법/헌법원문_1-43.md` :20 · 통합본 `docs/헌법/HITPAN_CONSTITUTION.md` :352 · :375(원장에 손댈 때 → #3·#6)

쉬운 말: **재고 장부(stock_ledger · 재고 들고 난 기록)와 회계 장부(journal_lines · 분개 줄)는 「새 줄 추가」만 된다. 이미 적힌 줄을 고치거나(UPDATE) 지우면(DELETE) 안 된다.** 틀린 거래는 지우지 않고 반대 전표(역전표)를 새로 써서 바로잡는다. 원문에는 **예외 조항이 없다.**

### 1-2. 왜 지금 부딪히나

10/27 대표께서 베타에 **「최소 복구」**를 넣기로 결재하셨다 — 부모계정 전용 한 화면 · 고객 손 = 확인·동의 버튼뿐 · 명령줄 0 · **「착수 전 헌법 #3 해석」** 조건이 붙었다(`20261027_결재_베타로드맵_사장님최종_기준선_G0착수.md` :13 · CTO 결재문 `20261027_결재_베타로드맵공동최종보고서_CTO1차.md` :27).
- 「부모계정 전용」은 처음 나온 말이 아니다: 코드 주석에 8/11 「🔴 2026-08-11 (사장님 지시): 자료관리는 **부모계정 + 메인PC 환경에서만**.」(`src/HitPan.API/Controllers/BackupController.cs` :17 · 초기화 문 `DataResetController.cs` :18 도 같은 글) — **PM 기록**(대표 원문은 이번에 찾지 않음). 지금 코드는 「메인PC」(:23)만 지키고 「부모계정」은 안 지킨다(:16 · §3 ④). ⇒ §2-1 조건 1 은 새 조건이 아니라 **미이행분**이다(보안상무 S-5).

「복원」은 백업 파일 하나로 **자료 전체를 그 백업을 뜬 시점으로 통째로 되돌리는 일**이다. 백업 파일은 표마다 「표를 지운다 → 다시 만든다 → 백업 때 내용을 채운다」 꼴로 되어 있다(§3 ⑧ · [1-V] §1-1 확정). 그래서 복원하면:
- 백업 **뒤에** 적힌 재고·회계 장부 줄은 **사라지고**, 백업 **앞의** 줄은 백업 속 내용으로 **다시 깔린다**(= 지움 + 덮어씀).
- 장부만이 아니다. 같은 방식으로 다음도 **백업 시점으로 돌아간다**([1-V] §1-2 확정 · 코드 읽기 · 실행 0):
  - 「누가 언제 무엇을 했나」 감사 기록 — 초기화 직후 그 직전 백업으로 되돌리면 **초기화했다는 기록까지 지워진다**(6/23 명세 「로그는 초기화 안 함」과 부딪힘).
  - 복원 기록 자신 — 지금 코드대로면 **「성공」이라고 답하면서 복원 기록은 0** 이 된다(§3 ⑤).
  - 직원 계정 · 비밀번호 · 권한 · 약관 동의 기록(일시 · IP · 버전 — 법정 보관 기록일 수 있음 · 법무 확인 거리 · ⚠️추론) · 기기 등록 · 구독 받은 내용.
- 백업 **뒤에** 업데이트로 새로 생긴 표는 지워지지 않고 남는다 → 자료 꼴이 반쪽이 될 수 있다(설계 몫).
- **보안 뜻**(보안상무 3인 검토 S-1 ~ S-3 · 코드 읽기 · 실행 0):
  - **흔적 지우기 도구가 된다** — 지금 복원 문은 관리자 역할 직원도 통과한다(§3 ④). 부정 거래 → 그 전 백업으로 복원 → 거래 · 감사 기록 · 복원 기록이 함께 사라지고 응답은 「성공」(§3 ⑤). **누가 되돌렸는지 증명할 길이 없다.** 남는 단서는 사전 백업 파일 하나(`BackupService.cs` :367-372 · 보관정책은 이 파일을 지우지 않는다 — :595-598 이 `hitpan_backup_*.sql` 만 셈).
  - **보안 상태가 거꾸로 돈다** — 퇴사·잠금 처리한 계정이 다시 활성 · 유출 의심으로 바꾼 비밀번호가 옛것으로 · 줄인 권한이 다시 커짐 · 분실·차단한 기기가 다시 허용 · 로그아웃·강제 만료한 로그인이 「폐기 안 됨」으로 돌아감(로그인 유지 기록은 DB 표 `refresh_tokens` 의 `is_revoked` 칸 · `AuthService.cs` :253 · 만료 전이면 다시 쓰임 = ⚠️추론).
  - **대표 비밀번호도 백업 시점 것으로 돌아간다** — 백업 뒤 바꾸고 옛것을 잊었으면 복원 직후 대표가 잠긴다. 헌법 #40(본사 비번 0건)이라 본사도 도울 수 없다(#40 의 뜻대로 정상 — 대신 화면에서 미리 알려야 함 · §2-1-2 ⓓ).

즉 복원은 그 성질상 #3 이 막는 「지우기 · 고치기」를 장부에 하고, 장부 밖 기록까지 되돌린다. #3 을 글자 그대로 읽으면 **백업 파일 하나로 통째 되돌리는 방식의** 복원은 만들 수 없다(장부는 남기고 나머지만 되돌리거나 반대 전표로 바로잡는 복원은 가능 — §2 (다)). 그래서 **대표 해석이 먼저**다(헌법 판단 서열: 통합본 → 원문 → 그래도 애매하면 대표 결재).

## 5. 쟁점 ③ — 「복구 확인」 실물 1건의 내용

- 「복구 확인」 원문은 60_2 :89 「대표 실물」 칸의 네 글자뿐 — **무엇을 확인하는지 정의는 없다**(⚠️ 아래 내용은 PM 해석).

- PM 안 = 화면이 다 되면 대표께서 **시험 환경에서 한 번 눌러 보시고** 「처음 보는 사람이 버튼만으로 할 수 있나」를 확인(헌법 #10 「한 화면 완성 → 사장님 확인 → 승인 → 커밋」). G1 증거기준은 「관찰 + CI(동작 정본은 G3)」(증거기준안 :91).
- 숫자가 맞는지 재는 진짜 시험은 G3 에 이미 따로 있다: W-G3-02 「복원 뒤 숫자 대조」(`60_3_갈래E3_G2G5공휴일자원.md` :40) · W-G3-07 「복원 안전 4조건」(:45) · W-G3-08 「최소 복구 = 부모계정 한 화면 확인·동의 버튼만 · 대표(정본) · PC1」(:46 · 증거기준안 :117).
- 참고(고르는 안이 아님): 「G1 확인 없음」은 결재된 판 1.1 을 바꾸는 일이고, 「G1 에서 숫자 대조까지」는 G3 W-G3-02·07·08 과 같은 일을 두 번 하는 것이라 올리지 않았다.
