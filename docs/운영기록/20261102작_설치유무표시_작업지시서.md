## §0 [카드] 대표 오더 · 결론 · 다음 행동

**대표 오더 원문 (11/2)** — 이 문서의 원본이다.

> 일단 스케쥴표 대로 가고, 로그기록 보는 부분은 별건으로 처리하자. 그런데 설치유무는 이미 있는기능에서 동작이 안되는거니 처리 하고 가는게 맞을듯

> 표시 상태 : ⓑ — 깔다 멈춘 고객을 찾을 수 있습니다
> 시각 문구 : ⓐ — 쓰기 경로를 건드리지 않습니다
> 프로그램을 삭제해도 「완료」로 남음 : ⓐ — ⓑ는 무접촉 규칙에 걸리고 ERP 게시 보류에도 막힙니다
> 운영 DB 읽기 1회 : 승인 — 표·칸·문자 규칙·건수만 읽습니다. 고객 값은 읽지 않습니다

주소: [결재 기록](20261102_결재_설치유무표시_오류로그별건_대표.md) · 설계: [설계문서](../설계/백오피스/20261102_설치유무표시_설계문서.md) · 전제: [1-V](../검증/선행/20261102_1V_설치유무표시_전제실측.md)

**결론**: 고객사 목록 · 상세의 「ERP 설치」 칸이 설치 성공에도 전부 「미설치」로 나온다. 쓰는 곳이 없는 칸을 보고 있어서다. 이미 쌓이는 재료를 읽어 **완료 / 설치 시작 / 미설치** 로 고친다.

| 고정 | 내용 |
|---|---|
| 판정 | 설계 §2 · 읽기 판정 안 A |
| 첫 읽기 보호 | 🔴 생략 안 함. 기존 SELECT 불변 + 둘째 문장 + 실패 시 목록 생존 (설계 §3) |
| 무접촉 | DDL 0 · ERP · 워치독 · 설치 · 시리얼 · 배포 경로 |
| 유지 | `is_locked_from_landing` · `bootstrap_at` · API `IsLocked` · `BootstrapAt` |

**다음 행동**: ① PM 이 §9 쟁점을 판정하고 결재 ② [3]·[3-V]·[4] 동시 착수 ③ 머지 · 배포는 대표 결재를 따로 받는다.

**코드 수정 · 배포 승인이 아니다.** 결재 기록 「이 결재가 뜻하지 않는 것」 그대로다.

## §1 [이해] 오더를 이렇게 이해했다

- 대표 의중: 있는 기능이 동작하지 않는 건이니 일정과 별개로 고치고 간다. 2상태가 아니라 3상태로 해서 **깔다 멈춘 고객을 찾을 수 있게** 한다.
- 안 하면: 본사 화면이 전 고객 「미설치」로 남아 CS · 영업이 설치 여부를 고객에게 물어야 한다.
- 🔴 대표가 받아들인 한계: 프로그램을 지워도 「완료」로 남는다. 고치려면 ERP · 설치 변경이 필요하다.
- **실측 근거**
  - 쓰는 곳 0 · 재료별 증명 범위 · 안 되는 경우 = [1-V] §1 · §2.
  - 운영 표 · 칸 · 문자 규칙 · 인덱스 · 옛 칸 값 = 결재 기록 「운영 읽기 결과」. 건수는 공개 문서에 적지 않는다.
  - 코드 위치 재확인(이 문서 작성 시): `AdminTenantDetailV2.razor:84` · `AdminTenantsV2.razor:81` · `TenantsAdminController.cs:70` · `:103` · 재료 쓰기 `InstallerBootstrapController.cs:297` · `TelemetryController.cs:272` · `:164`.

🔴 고침 1 의 근거: 대표에게 ⓐ · ⓑ · ⓒ 를 올렸고 대표 답은 「규칙대로, 루틴대로 처리해」 다. 선택을 고른 답이 아니다. [4] 기준 판정식은 PM · [2] 판단 + 대표 인지 사안이므로 PM 이 추천안 ⓐ 로 판단했고, 머지 상신에 다시 적는다. 대표가 바꾸면 따른다.

🔴 머지 상신에 적을 잔여: 옛 판 ERP 가 실제로 도는 고객도 「실행 기록 없음」 문구를 받는다(옛 판 안내 문장이 덮는다) · 업데이트 실패 보고만 있는 고객은 설치 시작으로 남는다 · 프로그램을 지운 고객의 보고 행이 남아 「설치 시작」 일 수 있다(대표 수용 원문은 「완료」 잔존 기준이라 범위가 다르다).
