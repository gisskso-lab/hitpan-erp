## 1. 🔴 반려 ②③ — **증상 2개, 원인 1개**

### 무엇이 일어났나

사장님이 두 줄로 적으셨지만 **한 사고다.**

```
Authorization requires a cascading parameter of type Task<AuthenticationState>.
Consider using CascadingAuthenticationState to supply this.
```

버튼이 **안 보인 게 아니다.** 목록이 **렌더 도중에 죽었다.**
죽은 화면엔 버튼도 없으니 사장님 눈에는 "확정버튼 없음"(②)으로 보였다.

### 진짜 원인 — 자리(位置) 문제

[`App.razor`](../../src/HitPan.Web/App.razor) 를 보면 답이 나온다.

| 행 | 내용 |
|---|---|
| 8 | `<MudDialogProvider />` ← **캐스케이드 밖** |
| 10 | `<CascadingAuthenticationState>` |
| 11~ | `<Router>` … 라우팅되는 **페이지**들 |

`DialogService.ShowAsync<T>` 로 뜨는 컴포넌트는 8행 아래에 붙는다.
⇒ 다이얼로그 안에는 `Task<AuthenticationState>` 가 **없다.**
⇒ 그 안에서 `AuthorizeView` 를 만나면 즉시 `InvalidOperationException`.

`PurchaseReturnList` 는 **페이지가 아니라 다이얼로그**다:
- [`SalesReturnPage.razor.cs:648`](../../src/HitPan.Web/Pages/Sales/SalesReturnPage.razor.cs#L648)
- [`ReturnPage.razor.cs:366`](../../src/HitPan.Web/Pages/Purchase/ReturnPage.razor.cs#L366)

작9 가 **전표 화면**(라우팅 페이지 = 캐스케이드 안)에 `AuthorizeView` 를 넣은 건 정상 동작했다.
작10 이 그 코드를 **목록(다이얼로그)에 그대로 옮기면서** 자리가 바뀐 걸 못 봤다.

### 🔴 이미 겪고, 이미 적어놨던 함정

[`SalesListDialog.razor:112-115`](../../src/HitPan.Web/Components/Sales/SalesListDialog.razor#L112-L115) 에 **그대로 적혀 있다**:

> `AuthorizeView` 는 MudDialog 캐스케이드 밖에서 `Task<AuthenticationState>`를 못 받아
> "Authorization requires a cascading parameter" 오류 발생.
> 권한 검증은 백엔드 `[Authorize(Policy = "SalesManager")]` 가 강제하고
> UI 는 항상 노출 → 권한 없으면 서버가 403 반환, 사용자에게 안내.

**답이 레포 안에 주석으로 있었는데 작10 이 되밟았다.**
⇒ 사람 기억에 기대던 것을 **게이트로 바꾼다**(3장).

### 봉합

[`PurchaseReturnList.razor`](../../src/HitPan.Web/Components/Purchase/PurchaseReturnList.razor) — `AuthorizeView` 제거, 버튼은 그대로.

**권한이 사라지는 게 아니다.** 서버가 강제한다 —
`POST sales/returns/{id}/confirm` 은 `[Authorize(Policy = "SalesManager")]`.
권한 없이 누르면 403 이 내려오고 `ConfirmOneAsync` 가 그 문장을 화면에 보여준다.
화면은 **서버보다 관대해도 인색해도 안 된다**(작9 원칙)는 그대로다 — 다만 **판정 주체가 서버**일 뿐이다.

## 2. 반려 ① — **결함이 아니다**

`api/auth/update-status-local` 은 [`AuthController.cs:504`](../../src/HitPan.API/Controllers/AuthController.cs#L504) 에 **있다.**
404 는 **설계대로 나온 것**이다:

```csharp
if (viaTunnel || remote is null || !IPAddress.IsLoopback(remote))
    return NotFound();   // 바깥에서 온 요청 — 있는지 없는지도 알려주지 않는다
```

로그인 **전** 업데이트 안내는 *"그 컴퓨터 앞에 앉은 사람"* 만 쓸 수 있다.
사장님은 **터널**(`demo.hitpan.kr`)로 들어오셨다 ⇒ `CF-Connecting-IP` 헤더가 붙는다 ⇒ 404.

그리고 이 404 는 **로그인을 막지 않는다** — `LoadUpdateNoticeAsync` 가 예외를 삼키고
콘솔에만 한 줄 남긴다(헌법 #15·#20). 사장님이 보신 건 **그 로그 한 줄**이다.

🟡 **다만 사장님께 여쭐 것**: 콘솔에 빨간 줄이 남는 것 자체가 불편하시면,
터널 접속일 때는 **조회를 아예 시도하지 않게** 할 수 있다(1줄). 기능 변화는 없고 로그만 조용해진다.

## 5. 🔴 남은 것 — 사장님 결재/실측 필요

### ④ 반품확정 500 — **미규명**
작10 봉합(`HasSalesReturnLossColumnAsync` + 1054/1146 → 안내문)은 `origin/main` 에 **확인했다.**
그런데도 500 이면 **다른 예외**다. 500 은 `is_loss` 말고 다른 자리에서 났다는 뜻이다.

🔴 **개발PC 정상은 검증이 아니다.** 단정하지 않는다. 필요한 단서:
- API 기동 로그 `[Startup/Migration]` 줄
- 확정 눌렀을 때 **API 로그의 예외 스택 첫 줄**

②③ 봉합 후 목록이 살아나면 ④ 재현 경로 자체가 바뀔 수 있어, **먼저 게시하고 재실측**을 제안드린다.

### ⑤ 조회유형 "사원별" — **임의로 못 지운다**
매입 반품현황([`ReturnStatusPage.razor:23`](../../src/HitPan.Web/Pages/Purchase/ReturnStatusPage.razor#L23))에 **똑같이 있다.**
서버도 `SR_BY_EMPLOYEE` 로 **정상 동작**한다(집계축 = `created_by` 전표작성자).

⇒ 세 갈래 중 사장님 결재 필요:
1. **매출만** 뺀다 (매입과 비대칭이 됨)
2. **매출·매입 둘 다** 뺀다 (← 매입 영역 침범, 별도 결재 필요)
3. **라벨을 고친다** — "사원별" 이 아니라 **"전표작성자별"** 이 실제 의미다

> PM 판단: ③이 가장 유력하다. 사장님이 "사원별"에서 **영업사원 실적**을 기대하셨다면
> 지금 숫자(전표 친 사람)는 **다른 것**이고, 그게 어긋나 보이신 것일 수 있다.
> **다만 이건 추측이라 여쭙는다.**
