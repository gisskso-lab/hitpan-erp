## 2. 원인의 원인 — 게시본 무한누적

### 2-1. 채증

| 위치 | 크기 | 내용 |
|---|---|---|
| `/tmp` | **1.6G** | EXE 4개(1.2.42~45) + ZIP 4개 — **게시 스테이징 잔재** |
| `/var/www/updates/packages` | **1.3G** | EXE 3개(각 270MB) + ZIP 5개(각 102MB) |
| `/var/log` | 558M | 로그 |

**오늘 하루 5회 게시**(`1.2.41`→`1.2.45`)했고 **한 번도 회수되지 않았다.**

### 2-2. 왜 안 지워졌나 — 구조적 누락

`publish-update.sh` 를 실측한 결과:

```bash
BACKUP_KEEP=10        # ← manifest .bak 만 회전한다
...
# N-3: 백업 회전 — 최근 BACKUP_KEEP 개만 유지
if (( ${#BAKS[@]} > BACKUP_KEEP )); then
  for old in "${BAKS[@]:$BACKUP_KEEP}"; do rm -f "$old"; done
fi
```

**`manifest.json.bak` 회전 로직은 있는데, 패키지 본체(ZIP·EXE) 회전 로직이 없다.**

- ZIP: 3-a 에서 `cp -f` 로 배치 → **회수 없음**
- EXE: 3-b 에서 원자 배치(`cp`→`mv`) → **회수 없음**
- `/tmp` 스테이징: GHA 가 rsync 로 올림 → **게시 후 삭제 없음**

### 2-3. 왜 하필 오늘 터졌나

**게시 1회당 영구 증가량:**

```
EXE 270MB (packages) + ZIP 102MB (packages)
+ EXE 259MB (/tmp)   + ZIP 98MB  (/tmp)
─────────────────────────────────────────
= 약 729MB / 게시 1회
```

9.8G 디스크에서 **13회 게시하면 반드시 사망**한다. 오늘 5회 게시가 마지막 방아쇠였다.

### 2-4. PM 오판 자기채증 (헌법 #32 — 받아쓰기 금지)

오늘 오전 PM 은 다음과 같이 판단했다:

> *"옛 버전이 3세대만 남아 있습니다 (`1.2.40` 은 이미 회수됨) — 자동 정리가 도는 것 확인. 디스크 압박 없습니다."*

**이 판단은 오판이었다.**

- 근거로 삼은 것: `1.2.40` ZIP 이 404 였음
- 실제: `1.2.40` ZIP 은 **회수된 것이 아니라** 그 시점 게시 이력·보존 정책상 존재하지 않았을 뿐
- **EXE 는 단 하나도 지워진 적이 없었다** — EXE 를 확인하지 않고 ZIP 만 보고 "자동 정리가 돈다"고 단정
- 그 오판 때문에 디스크 압박을 과소평가하고 `1.2.45` 를 추가 게시 → **DB 사망**

> 🔴 **교훈**: "안 보인다"를 "회수됐다"로 읽었다. **없어진 이유를 확인하지 않은 추정**이었다.
> 오늘 작8 에서 확정한 관통 원인 *"만들었는지만 보고 되는지를 안 봤다"* 와 **같은 형태의 오류**다.
> 이번엔 *"지워졌는지 확인하지 않고 지워진다고 믿었다."*

응급 복구는 **시간을 벌었을 뿐이다.** 2.0G 로는 **게시 2~3회면 다시 100%** 가 된다.

### 4-1. P0-A · 게시 스크립트에 패키지 회전 추가 (핵심)

**대상**: `/opt/hitpan/installer/updates/publish-update.sh` (NCP 상주본)
**위치**: §5 원자 교체·백업 회전 **직후** (= 서빙 검증 통과 후)

```bash
# ── 6) 패키지 회전 (20260730작9 P0-A — 디스크 100% 사망 재발 방지) ──────────────
#   ■ 왜 필요한가
#     BACKUP_KEEP 은 manifest .bak 만 회전한다. 패키지 본체(ZIP 102MB·EXE 270MB)는
#     한 번도 회수되지 않아 게시 1회당 372MB 가 영구 누적됐다 →
#     2026-07-30 실측: 9.8G 디스크 100% → MySQL 기동 불가 → 가입·설치 전면 마비.
#   ■ 왜 여기인가
#     서빙 검증(§5)을 통과한 뒤여야 한다. 검증 전에 지우면 롤백 대상이 사라진다.
#   ■ 왜 2세대인가
#     현행(N) + 직전(N-1). 직전은 롤백 대상이라 반드시 남긴다. 3세대 이상은 실익 없다.
#   ■ 실패해도 게시는 성공으로 둔다
#     회전 실패가 게시를 되돌리면 본말전도다. 경고만 남긴다(헌법 #15 — 침묵은 아니다).
PKG_KEEP="${HITPAN_PKG_KEEP:-2}"

rotate_pkg() {
  local pattern="$1" label="$2"
  # 최신순 정렬 → KEEP 개 이후를 삭제. mtime 기준(버전 문자열 정렬은 1.2.9 > 1.2.10 오류)
  local files=()
  while IFS= read -r f; do files+=("$f"); done < <(
    find "$PACKAGES_DIR" -maxdepth 1 -type f -name "$pattern" -printf '%T@ %p\n' 2>/dev/null \
      | sort -rn | awk '{ $1=""; sub(/^ /,""); print }'
  )
  if (( ${#files[@]} > PKG_KEEP )); then
    for old in "${files[@]:$PKG_KEEP}"; do
      # 현행 게시본은 절대 지우지 않는다(이중 안전망 — mtime 이 꼬여도 방어)
      if [[ "$(basename "$old")" == "$ZIP_BASENAME" || "$(basename "$old")" == "${EXE_BASENAME:-}" ]]; then
        warn "회전 대상에 현행 게시본이 들어왔다 — 건너뜀: $(basename "$old")"
        continue
      fi
      rm -f "$old" && log "$label 회전 삭제: $(basename "$old")" \
                   || warn "$label 회전 삭제 실패(무시): $(basename "$old")"
    done
  fi
}

rotate_pkg 'hitpan-*.zip'            'ZIP'
rotate_pkg 'HitPan-ERP-Setup-*.exe'  'EXE'
log "패키지 회전 완료(KEEP=$PKG_KEEP) — 잔여: $(du -sh "$PACKAGES_DIR" 2>/dev/null | cut -f1)"
```

**설계 판단 근거:**

| 판단 | 이유 |
|---|---|
| `mtime` 정렬, 버전 문자열 정렬 아님 | `sort -V` 없이 문자열 정렬하면 `1.2.9 > 1.2.10` 오류. `1.2.100` 도달 시 잘못된 파일 삭제 |
| 현행 게시본 이름 이중 확인 | `mtime` 이 꼬여도(수동 `touch` 등) 방금 올린 것은 절대 안 지운다 |
| 검증 통과 후 위치 | 검증 전 삭제 시 롤백 불가 |
| 실패해도 게시 성공 유지 | 회전 실패로 정상 게시를 되돌리면 본말전도 |
| `HITPAN_PKG_KEEP` 환경변수 | 비상시 사람이 조절 가능. 기본 2 |

### 4-4. P1-D · 랜딩 WebSocket 500 (별건, 오늘 발견)

**증상** (nginx error.log, `15:26`~`15:56` **64초 주기 반복**):

```
upstream timed out (110) while reading response header from upstream,
request: "GET /_blazor?id=...", upstream: "http://127.0.0.1:5260/_blazor?..."
```

**원인**: `/etc/nginx/sites-enabled/landing.hitpan.kr.conf`

```nginx
proxy_set_header Connection keep-alive;   # ❌ WebSocket 업그레이드 원천 차단
# proxy_read_timeout 없음 → 기본 60초 → 로그의 64초 주기와 일치
```

→ WebSocket 실패 → Blazor 롱폴링 폴백 → nginx 가 장애로 오판 → **500**

**봉합** (헌법 #29 — 사장님 결재·실행):

```nginx
# http 블록
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

# landing 블록
proxy_set_header Connection $connection_upgrade;   # keep-alive → 교체
proxy_read_timeout  3600s;                          # 신규
proxy_send_timeout  3600s;                          # 신규
```

> 이것이 **사업자등록증 업로드 `미리보기 생성 실패: 500`** 의 원인이다.
> 롱폴링은 대용량 스트림에 취약해 업로드에서 특히 터진다.


**화면은 "OCR 완료"로 보이지만 실제로는 아무것도 읽지 않는다.** 껍데기다.
7행 주석이 *"실제 OCR·검증 API 연결은 P1 후속 작지에서"* 라고 명시하고 있다.

**추가 결함** — 코드와 서버 설정 불일치:

| | |
|---|---|
| 컴포넌트 선언 | `MaxBytes = 5MB` |
| 서버 실제 한도 | **SignalR 기본 32KB** (`Program.cs:13` 에 `MaximumReceiveMessageSize` 없음) |

**처음부터 통과할 수 없는 조합**이다. P1-D 를 고쳐도 큰 파일에서 또 터진다.

## 5. 재발 방지 — 프로세스

### 5-1. 게시 전 필수 확인 (I-3 규율에 추가)

기존 I-3: *"게시할 커밋이 `build-and-test` 초록인지 확인"*
**추가**: *"NCP 디스크 여유가 1.2G 이상인지 확인"* — P1-C 가 자동 강제.

### 5-2. "지워진다"를 믿지 않는다 (헌법 #32 확장)

> **PM 오판 재발 방지**: 회수·정리·자동화가 "돈다"고 말하려면 **그 코드를 읽었거나 전후를 실측**해야 한다.
> "파일이 안 보인다"는 **회수의 증거가 아니다.** 오늘 오전 PM 이 정확히 이 오류를 저질렀다.

### 5-3. NCP DB 서비스명 정정

| 대상 | DB | 서비스명 |
|---|---|---|
| 고객사 ERP (로컬) | MariaDB 11.4.10 | — |
| **NCP 백오피스** | **MySQL 8.0.45** | **`mysql`** (❌ `mariadb` 아님) |

장애 복구 시 `systemctl start mysql`. 이 오인이 오늘 복구를 지연시켰다.

## 7. 검증 기준 (검증팀장 데이비드 박)

| # | 기준 | 방법 |
|---|---|---|
| V-1 | 게시 후 `packages/` 에 ZIP·EXE 각 2개 이하 | 게시 1회 후 `ls` 실측 |
| V-2 | 게시 후 `/tmp` 에 해당 버전 잔재 0 | 게시 1회 후 `ls /tmp` |
| V-3 | 현행 게시본 무손상 | manifest 버전 EXE·ZIP HTTP 200 + 크기 일치 |
| V-4 | 직전 버전 ZIP 보존(롤백 가능) | `ls` 확인 |
| V-5 | 디스크 여유 부족 시 게시 중단 | `HITPAN_PKG_KEEP` 조작 재현 |
| V-6 | 랜딩 `/_blazor` 타임아웃 0 | nginx error.log 10분 관찰 |
| V-7 | 사업자등록증 업로드 성공 | 실제 2MB 파일 업로드 |

**⚠️ V-1·V-2 는 다음 게시 때 실측해야 확정된다.** 코드만 넣고 "됐다"고 하지 않는다 —
오늘 작8 에서 확정한 *"만들었는지만 보고 되는지를 안 봤다"* 를 반복하지 않는다.
