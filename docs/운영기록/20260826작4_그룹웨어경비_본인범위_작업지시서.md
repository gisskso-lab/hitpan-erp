## 1. 🔴 실제로 뚫려 있었다

`GET /api/hr/expense-requests` 가 화면이 보내온 `employeeId` 를 **그대로 서비스에 넘겼다.**
안 보내면 `WHERE` 에 조건이 안 붙어 **전 직원 경비가 다 나온다**
(`HrService.GetHrExpensesAsync` 는 `employeeId` 가 비면 필터를 안 건다).

🔴 **그런데 화면은 그 값을 한 번도 보낸 적이 없다** — `Web/Services/HrService.cs:108` 은 `api/hr/expense-requests` 를 **맨 URL 로만** 부른다.

⇒ **일부 경로가 아니라 모든 실사용 호출이 전 직원 경비를 조회하고 있었다.**

### 권한 속성은 이걸 못 막는다
`[RequirePermission("HR","view")]` 는 **"HR 화면을 볼 수 있나"** 이지 **"누구 것을 볼 수 있나"** 가 아니다.
경비를 올리는 직원은 **당연히 이 권한을 갖는다** ⇒ 그 직원이 그냥 화면을 열면 남의 경비가 보였다.

### 🔴 급여는 진작 막고 있었다 — 비대칭
`PayrollController.ResolveScopeAsync` (8/13 사장님 지시 *"a직원 급여를 b직원이 볼수 없어야해"*) 는
요청값을 **무시하고 본인으로 덮는다.** **같은 회사에서 급여는 막고 경비는 뚫린 자리**였다.

## 2. 봉합

`src/HitPan.API/Controllers/HrController.cs`

```
- public async Task<IActionResult> GetHrExpenses([FromQuery] string? employeeId, CancellationToken ct)
-     if (string.IsNullOrEmpty(tid)) return Forbid();
-     return Ok(await _svc.GetHrExpensesAsync(tid, employeeId, ct));
+ public async Task<IActionResult> GetHrExpenses(CancellationToken ct)

+     if (string.IsNullOrEmpty(tid) || string.IsNullOrEmpty(eid)) return Forbid();

```

🔴 **파라미터를 아예 없앴다.** 받아서 무시하면 다음 사람이 *"왜 안 먹지"* 하고 되살린다.
**주소창에 남의 id 를 넣을 자리를 남기지 않는 것**이 요점이다.

### ⚠️ 급여와 다른 점 — 여기는 가르지 않는다
급여는 경리(`PAYROLL` 권한)가 전 직원을 봐야 해 세 갈래로 갈랐지만, 경비는 **권한을 보지 않는다. 무조건 본인이다.**
경리가 전건을 보는 자리는 **회계 「경비 처리」 화면**이다
(`FinanceService.GetExpensesAsync` 가 두 표를 `UNION ALL` 로 합쳐 보여준다 — **그건 그대로 둔다**).

## 3. 🔴 앞선 판단 2개가 뒤집혔다

PM 이 8/26 스케줄표·작3 초안에서 올린 것이 **둘 다 틀렸다.**

| PM 판단 | 실제 | 왜 틀렸나 |
|---|---|---|
| *"급여·경비 신설은 이미 있는 화면과 **중복**"* | **의도된 분리** | 쓰임새·권한이 다르다 |
| *"표를 신설하고 UNION 을 **끊어야** 한다"* | **둘 다 안 한다** | 같은 데이터를 **다른 역할로 보는 것**이었다 |

🔴 **"쓰임새가 다르다" 를 "데이터가 다르다" 로 읽은 것이 오독이었다.**
사장님 설명(*"회계=경리가 명세서 작성 / 그룹웨어=직원이 조회·다운로드"*)은
**같은 명세서를 양쪽이 다른 역할로 본다**는 뜻이다. 표를 갈랐으면 **직원이 자기 명세서를 영영 못 본다.**

⇒ 할 일은 복사도 표 신설도 아니고 **범위 판정 한 자리**였다.
