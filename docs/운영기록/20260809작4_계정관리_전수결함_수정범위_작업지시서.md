## 4. 🔴 사장님 결재 요청 — 어디까지 고칠까

**PM 이 임의로 정하지 않는다.** 범위에 따라 작업량이 크게 다르다.

### 4-1. 순서 (PM 권장)

| 순위 | 항목 | 이유 |
|---|---|---|
| **1** | 권한 메뉴코드 정합 (2-1) | 권한이 안 먹히면 **다른 모든 화면 검증이 무의미** |
| **2** | "실패를 0건으로 위장" 공통 봉합 (2-5) | 한 규칙으로 5화면이 동시에 낫는다 |
| **3** | 설정 덮어쓰기 차단 (2-3) | 데이터 사고 경로 |
| **4** | 삭제 확인 2곳 (2-4) | 손 적게 들고 사고 큰 것 |
| **5** | 사장님 지적 3건 (§1) | 우편번호·출력이미지·중복제거 |
| **6** | 결재라인 이원화 (2-2) | **설계 판단 필요** — §4-3 |

### 4-2. 출력이미지 저장 범위

| 안 | 범위 | 결과 |
|---|---|---|
| (가) | 버튼→파일선택 연결 + 로고만 저장 | 로고만 됨. 인장·헤더는 **컬럼이 없어 여전히 안 됨** |
| **(나) 권장** | (가) + `tenants` 에 인장·헤더 컬럼 ALTER | 3종 다 됨. DDL 변경 → 헌법 #36·#9 결재 |
| (다) | 버튼을 감춘다 | 안 되는 걸 "된다"고 말하지 않게 됨. 기능은 나중 |

**PM 의견 (나)** — 인장은 거래명세서·견적서에 찍혀야 하는 것이라 ERP 에서 빠질 수 없다.
⚠️ 단 **인쇄 양식이 인장을 참조하는 코드를 아직 못 찾았다**(`grep "인장"` → 0건).
저장만 되고 안 찍히면 반쪽이라 **인쇄 쪽까지 같이 봐야 완결**이다.

### 4-3. 결재라인 이원화 — 어느 쪽을 살릴까

| 안 | 내용 |
|---|---|
| (가) | "결재라인 설정" 화면을 **살아있는 표(`approval_doc_lines`)로 연결** |
| (나) | "결재라인 설정" 메뉴를 **감추고** "결재 설정" 하나로 통일 |
| (다) | 그대로 두고 화면에 안내만 |

**PM 은 여기서 의견을 내지 않습니다.** 결재는 업무 흐름이라 **사장님이 어떻게 쓰실지가 먼저**입니다.
"결재라인을 문서유형과 별개로 이름 붙여 관리하고 싶다"면 (가), "문서유형별이면 충분"이면 (나)입니다.

### 4-4. §2-5 공통 봉합 방식

| 안 | 내용 |
|---|---|
| (가) | 화면 하나씩 개별 봉합 |
| **(나) 권장** | 공통 규칙 — ① 조회 실패 시 **저장 잠금** + 사유 표시 ② catch 로그 의무 ③ 삭제 확인 의무 ④ 저장 후 재조회 |

⚠️ **(나)①은 사용성과 충돌**합니다 — 서버가 잠깐 죽으면 설정을 못 고칩니다.
다만 **틀린 값으로 덮어쓰는 것보다 못 고치는 게 낫다**는 판단입니다. 이 부분 결재를 청합니다.
