## §1. 무엇이 문제인가 — 한 파일이 두 갈래로 갈라졌다

`deploy-update` 워크플로가 **브랜치마다 다른 파일명으로 각자 진화**했다.

| 브랜치 | `deploy-update.yml` (**GitHub 이 실행**) | `deploy-update.yml.disabled` (**실행 안 함**) |
|---|---|---|
| **main** | ✅ **367줄** `d80d2491` — 1.2.40·1.2.41 을 실제로 게시한 것 | 339줄 `83e44d4a` — **방치된 잔재** |
| **develop** | ❌ **없음** | 🟢 **525줄** `a694f260` — 7/29·7/30 봉합분 전부 여기 |

> 표의 줄 수는 **비어있지 않은 줄** 기준이다. `wc -l` 실측은 각각 **392 / 363 / 558**.
> 🔴 **검증 시 줄 수로 대조하지 말고 blob 해시로 대조할 것** — 기준이 둘이라 오판정이 난다.

### 계보 (실측)

```
400c291  ← merge-base(main, develop).  이 지점에 deploy-update.yml 이 **없다**
c1b917b  .disabled 계보의 뿌리
   ├── main    9ec0e2d  .disabled 를 '복사해' deploy-update.yml **신규 생성**(363 insertions)
   │           435debe  active 만 수정 (strip 봉합)  ← .disabled 는 그대로 방치
   └── develop 5d8c534 → d1dff9d → 0cd19bf   ← .disabled 만 계속 발전
```

> ⚠️ **`9ec0e2d` 는 rename 이 아니라 복사·신규생성**이다. 그래서 main 활성본에는 rename 이력이 없다.
> 그리고 **merge-base(`400c291`)에 `deploy-update.yml` 경로가 없다** — 이 두 가지가 §3 충돌의 원인이다.

### 그래서 무슨 일이 생기나

**develop → main 을 그대로 병합하면** (실측 `git merge-tree --write-tree`, exit=0 충돌 없음):

1. main 의 `deploy-update.yml`(367줄 `d80d2491`)은 **develop 에 대응 파일이 없으므로 그대로 생존**
2. 525줄은 `.disabled` 로 들어가 **GitHub 이 무시한다**
3. 1.2.42 게시 → **구버전 워크플로가 돈다** → EXE 빌드 스텝 없음
4. → **랜딩 다운로드 404 그대로.** 작3 코드가 통째로 사표(死票)

> 🔴 **오늘 작3 으로 짠 EXE 배선이 한 줄도 실행되지 않는다.**

**그리고 develop 에서 `git mv` 로 이름만 맞춰도 자동 교체되지 않는다.**
merge-base 에 그 경로가 없어 git 이 rename 으로 잇지 못하고 **add/add 충돌**로 판정한다

## §3. 조치 — develop 에서 파일명을 정본화

### 왜 develop 에서 하나

main 에서 고치면 develop 이 또 `.disabled` 를 들고 있어 **다음 병합 때 같은 사고가 재발**한다.
갈라짐은 **원류(develop)에서 봉합**해야 끝난다.

### 실행 — 2단계다. **3-1 만 하면 실패한다**

**[3-1] develop: 파일명 정본화**

```bash
git switch develop
git mv .github/workflows/deploy-update.yml.disabled \
       .github/workflows/deploy-update.yml
git commit -m "ci(작4/[3]): deploy-update 워크플로 파일명 정본화 — .disabled 갈라짐 봉합"
git push origin develop
```

**[3-2] 🔴 필수 — main 의 구버전을 '먼저 삭제'한 뒤 병합**

3-1 만 하고 PR 을 올리면 **add/add 충돌 8 hunk** 가 난다 (§1 참조).
merge-base 에 `deploy-update.yml` 이 없어 **rename 추적이 원리적으로 불가**하기 때문이다.
손으로 풀다 한 hunk 라도 잘못 고르면 **문법 깨진 워크플로가 main 에 올라가 게시가 시작조차 못 한다.**

```bash
git switch -c merge/develop-to-main-20260730 main
git rm .github/workflows/deploy-update.yml
git rm .github/workflows/deploy-update.yml.disabled   # 잔재 동시 소멸 (아래 표 참조)
git commit -m "ci(main): deploy-update 구버전 active/disabled 제거 — develop 정본 수용 준비"
git merge develop          # 실측: 충돌 0
git push -u origin merge/develop-to-main-20260730
```

> ✅ **실측 근거**: `git merge-tree --write-tree <main-구버전삭제> <develop+mv>` → **exit=0**,
> 결과 트리에 `deploy-update.yml`(`a694f260`) **1개**, `.disabled` **0개**. 원하는 최종 상태와 정확히 일치.

> ⚠️ **`git rm` 은 헌법 #1 위반이 아니다** — §2 에서 develop(525) ⊃ main(367) 을 실측 확인했다.
> 지우는 것은 **하위 사본**이고, 상위본이 같은 커밋에서 그 자리에 들어온다.

### ⛔ 하지 않는 것

| 안 하는 것 | 왜 |
|---|---|
| main 에서 워크플로 **내용** 수정 | 재발 원인. 내용은 원류(develop)에서만 고친다. 3-2 는 **삭제**만 한다 |
| 워크플로 **내용** 수정 | 이번은 **파일명·배치만.** 내용은 `0cd19bf` 에서 이미 결재됨 |
| 충돌을 손으로 해소 | 병합본이 YAML 파싱 실패한다. **3-2 로 충돌 자체를 없앤다** |

### 🔄 방침 변경 — main `.disabled`(339) 삭제를 **이번 PR 에 포함**

당초 §7 별건으로 미뤘으나 **포함으로 바꾼다.**

| 이유 | 내용 |
|---|---|
| 어차피 손댄다 | 3-2 에서 main 쪽 워크플로 파일을 건드려야 충돌이 없어진다 |
| `name:` 중복 | 3파일 전부 `name: Deploy Auto-Update (자동업데이트 영구 CD)`. 이름 기반 `gh workflow run` 이 모호해진다 |
| **재발 씨앗** | §6 교훈 2번이 지목한 원인 그 자체. 남기면 다음에 또 갈라진다 |

> 실행은 위 3-2 의 `git rm … .disabled` 한 줄. 실측상 이걸 포함해도 충돌 0.

## §6. 이 사고가 준 교훈

**1. "역류시켰다"가 안전을 보장하지 않았다.**
7/29 `5d8c534` 는 develop 의 `.disabled` 에 봉합을 역류시켜 *"main 과 동형"* 을 만들었다.
내용은 동형이 됐지만 **파일명이 달랐다.** 동형성 검사를 **내용만** 하고 **경로는 안 봤다.**

**2. `.disabled` 를 남긴 것이 화근이었다.**
활성화(`9ec0e2d`)할 때 복사하고 원본을 지우지 않아 **한 워크플로에 파일이 2개**가 됐다.
이후 두 브랜치가 서로 다른 쪽을 고쳤다.

**3. 실행되는 파일이 무엇인지부터 확인해야 한다.**
작3 은 코드를 정확히 짰지만 **안 도는 파일**에 짰다. 구현 전 *"이 파일이 실제로 실행되나"* 확인이 없었다.

**4. PM 이 "그대로 교체된다"고 단정한 것이 틀렸다 — 검증팀이 반증했다.**
초판 §3 은 `git mv` 한 줄이면 된다고 썼다. 검증팀이 `git merge-tree` 로 **실제 시험 병합**을 돌려
**add/add 충돌 8 hunk · 병합본 YAML 파싱 실패**를 실측했다.
PM 은 *"이름이 같아지면 git 이 알아서 잇겠지"* 라고 **추측**했고, **merge-base 를 확인하지 않았다.**
merge-base `400c291` 에 그 경로가 없다는 사실 하나가 계획 전체를 뒤집었다.

> **교훈: 병합 결과는 추론하지 말고 `git merge-tree` 로 미리 돌려본다.** 비파괴로 확인 가능하다.

**5. 줄 수를 검증 기준으로 삼은 것도 오판정 씨앗이었다.**
"525줄" 은 비어있지 않은 줄 기준인데, 검증자가 `wc -l` 로 재면 **558** 이 나온다.
→ **blob 해시로 판정한다.**
