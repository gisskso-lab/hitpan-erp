## 1. 🔴 500 의 진짜 원인 — 세 번의 봉합이 **전부 거꾸로**였다

### 원인

`(int)(it.is_loss ?? 0)` 가 **`RuntimeBinderException: Cannot convert type 'bool' to 'int'`** 로 터졌다.

MySqlConnector 는 `TINYINT(1)` 을 **`Boolean`** 으로 돌려준다
(연결문자열에 `TreatTinyAsBoolean=false` 가 없어 기본값 `true` 적용 —
[`InfrastructureExtensions.cs:55`](../../src/HitPan.Infrastructure/Extensions/InfrastructureExtensions.cs#L55)).
`dynamic` 캐스팅은 런타임 실제 타입이 **정확히** 맞아야 하므로 `bool → int` 는 예외다.

### 🔴 왜 세 번을 틀렸나

| 차수 | 고친 것 | 실제 |
|---|---|---|
| 작10 | 1054 — "마이그 안 들어간 DB" | 🔴 그쪽은 **원래 정상**(폴백 `0 AS is_loss` → `Int32`) |
| 작12 | 1054 폴백을 5경로로 확대 | 🔴 같은 자리를 더 넓혔을 뿐 |
| 작13 | 1062 원장중복 | 🔴 원장이 **애초에 안 남는다**(아래 참조) |

**고친 쪽은 멀쩡했고, 안 고친 쪽이 터지고 있었다.**
사장님 PC 는 DB-108 이 적용돼 있어(= 실컬럼 `TINYINT(1)` → `Boolean`) 계속 500 이 났다.

### 증상 모양 대조

`RuntimeBinderException` 은
`InvalidOperationException`(→400)도 `MySqlException`(1054/1146/1062→400, 1451/1452→409)도 아니라
미들웨어 마지막 `catch(Exception)` 으로 떨어져 **정확히 500**.

**실측 재현:**
```
DB-108 적용됨 (실컬럼 TINYINT(1)) → is_loss = Boolean → 🔴 RuntimeBinderException
DB-108 미적용 (폴백 0 AS is_loss) → is_loss = Int32   → 🟢 정상
```

⚠️ 이 예외는 트랜잭션 **안**에서 터져 롤백된다 ⇒ **원장이 안 남는다** ⇒
작13 이 넣은 "이미 재고에 반영됨" 가드에도 안 걸린다.
**그래서 몇 번을 눌러도 똑같이 500** 이었다. 작13 가설이 왜 빗나갔는지도 이걸로 설명된다.

🔴 **사장님 확인과 일치한다** — *"여태 500이 떠서 반품확정된 건은 단 한건도 없어"*.
롤백되므로 원장도, 확정 건도 남을 수 없다.

### 봉합 (기능은 뺐지만 코드는 고쳐 둔다)

`IsLossValue(object?)` 헬퍼 신설 — `Convert.ToInt32` 로 **`bool`·`sbyte`·`int`·`long` 전부** 받는다.
🔴 타입을 하나로 못박지 않는다. 연결문자열·DB 버전·컬럼 정의에 따라 무엇이든 올 수 있다.

**실측**: 봉합 후 양쪽 DB 조건 모두 통과, 로스 판정도 정확(`is_loss=1` 제외 확인).

## 2. 반품확인 메뉴 제거 — **진입점 전부**

| # | 자리 | 처리 |
|---|---|---|
| 1 | 사이드바 「반품확인서」·「반품확인현황」 | **제거** |
| 2 | 판매목록 「반품」 버튼 | **제거** |
| 3 | `CanCreateReturn` · `CreateReturnAsync` | **제거** |
| 4 | `@inject WorkTabService` (판매목록) | **제거**(더는 안 쓴다) |
| 5 | `@page "/sales-returns"` | **제거** |
| 6 | `@page "/sales-return-status"` | **제거** |

🔴 **입구가 둘이면 한쪽만 막아도 소용없다.** 메뉴만 빼면 주소를 직접 치거나 즐겨찾기로 들어온다.
그러면 **만들 수는 있는데 열 수는 없는 문서**가 쌓인다 — 사장님 헌법(*"안 보이는 채로 쌓인다"*) 그 자리다.

⚠️ **화면·API·서버 로직은 남아 있다.** 지운 것은 **진입점**뿐이다.
되살릴 때는 결재 후 주석만 풀면 된다(500 봉합이 포함된 상태로).

### 대체 경로 (사장님 지시)

## 3. 게이트 — 6건을 **정반대로 뒤집었다**

기능을 뺐으므로 *"있어야 한다"* 게이트가 **제거를 막는다.** 작11·작12 에서 겪은 그 자리다.

| 종전 | 지금 |
|---|---|
| `판매관리_메뉴에_반품확인서와_반품확인현황이_있어야_한다` | `사이드바에_반품확인_메뉴가_되살아나면_안_된다` |
| `판매목록조회에_반품_버튼이_있어야_한다` | `판매목록에_반품_진입점이_없어야_한다` |
| — | `반품화면_라우트가_살아있으면_안_된다` **신설** |
| `반품버튼이_원거래_상태를_바꾸지_않아야_한다` | **삭제**(없어진 메서드를 검사) |
| `반품버튼은_확정하지_않고_초안만_열어야_한다` | **삭제**(동상) |
| `파손_로스는_재고에_반영하지_않아야_한다` — 리터럴 `it.is_loss ?? 0` 요구 | **동작 검사**(`IsLossValue`)로 교체 |

🔴 마지막 것이 특히 중요하다 — **그 리터럴이 바로 500 의 원인**이었는데,
게이트가 그걸 **강제하고 있었다.** 글자를 보고 동작을 안 본 게이트다.

신설 `DynamicCastSafetyGateTests` — `is_loss` 를 `(int)` 로 직접 캐스팅하면 FAIL.

⚠️ **남긴 게이트**: 매출반품 SQL 4종·확정분만 집계·서버 정책 등은 **그대로 살아 있다.**
되살릴 때 기능이 온전한지 보증한다.
