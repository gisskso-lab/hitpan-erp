## 2. 작10 — 500 의 원인과, 그것을 어떻게 잡았나

### 재현으로 확정했다

로컬에 같은 조건을 만들어 실제로 돌렸다:

```
MySqlException: Unknown column 'is_loss' in 'SELECT'
```

`ConfirmSalesReturnAsync` 가 작6의 **DB-108** 컬럼을 읽는데 **그 컬럼이 고객 DB 에 없었다.**

### 🔴 중간에 세운 FK 가설을 버린 과정 — 이게 오늘의 교훈이다

처음엔 `journal_lines.fk_jl_account`(계정과목 미시드) 를 의심했고 **실제로 1452 를 재현까지 했다.**
그런데 `GlobalExceptionMiddleware` 를 읽어보니:

```
InvalidOperationException → 400
FK (1451·1452)           → 409   ← FK 였다면 여기
그 외                     → 500   ← 사장님이 받은 것
```

**사장님이 받은 건 500 이다. 그러므로 FK 가 아니다.**
⇒ 재현했다는 이유만으로 원인이 되지 않는다. **증상의 모양까지 맞아야 한다.**

### 봉합 두 겹

| | |
|---|---|
| ① 코드 | 확정·취소가 **스키마를 먼저 확인**(헌법 #13). 컬럼 없으면 0(정상품)으로 읽는다 |
| ② 게시 | **`requiresMigration:true`** 로 내보내 DB-108 을 밀어 넣는다 |

🔴 **①은 로스 기능을 끄는 게 아니다.** 컬럼이 생기면 그대로 동작한다.
마이그가 늦게 도착한 DB 에서도 **반품확정 자체는 되게** 하는 것이다(헌법 #20).

## 3. 🔴 아직 모르는 것 — 반드시 이어서 볼 것

### DB-108 이 왜 안 들어갔나

- 1.3.10 은 **`requiresMigration:true`** 로 나갔다
- 워치독은 신규 마이그가 있으면 **경고 후 통과**시킨다
- 적용 주체는 **HitPan.API 기동 시 `MigrationRunner`**(고리5)

**정상이라면 그때 들어갔어야 한다.**

**단정하지 않았다** — `schema_migrations` 를 볼 수 없다(이 PC 는 운영기가 아니다).

⚠️ **1.3.14 로 증상은 사라져도, 원인이 마이그 경로 자체면 다음에 또 나온다.**

**다음 세션이 확인할 것** — 사장님께 여쭙거나 실측으로:
1. `schema_migrations` 에 **DB-108 이 success=1 로 있나**
2. 1.3.10 을 **건너뛰고** 1.3.11 이후로 오셨나
3. `MigrationRunner` 가 SQL 폴더를 못 찾는 경우 — 배포 레이아웃에서 폴더가 실제로 잡히나
   (`MigrationRunner.cs:55` `ResolveMigrationsDirectory`, 후보는 `{baseDir}/Migrations/SQL` 1순위)

> ⚠️ **여기서 PM 판단을 한 번 정정한다.**
> 처음엔 *"폴더를 못 찾으면 조용히 넘어간다"* 고 적었는데, **코드를 확인하니 아니다.**
> 폴더를 못 찾으면 `Success=false` + `LogError` 이고, `Program.cs:464` 가 그걸 받아
> **🛑 로 시작하는 에러 로그**를 남긴다(헌법 #15 지켜지고 있다).
> ⇒ **조용히 넘어가는 구조는 아니다.** 다만 **그 로그를 아무도 안 본다면** 결과는 같다.
> **API 기동 로그에서 `[Startup/Migration]` 을 찾는 것이 가장 빠른 단서다.**

**추가된 규칙:**
- 🔴 **낱말 하나로 검사하지 마라** — `private void X()` **정의**와 `OnClick="X"` **배선**을 **따로**
- 🔴 **구간을 자르면 자른 밖도 봐라** — 금지패턴은 **파일 전체**에도
- **여러 줄 주석의 이어지는 줄은 `CodeLines` 가 못 거른다** — 속성 자체를 봐라
- **문자열 슬라이스는 오프셋을 의심하라** — `i + 10` 같은 어림수가 여는 `"""` 안에 걸린다
