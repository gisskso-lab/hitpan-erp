## §0 카드 (≤40줄)

### 결론: **L2 는 「인덱스 2개 + 술어 한 줄」이 한 묶음일 때만 봉합된다. 셋 중 하나를 빼면 어느 구간에선가 지금보다 나빠진다.**

| 축 | 내용 |
|---|---|
| 넣는 것 | **DB-125 = C2 + C4**(인덱스 2개) · **제품 SQL 1줄**(L2 의 ㉪) |
| 이미 승인된 것 | **L4 의 ㉪ 한 줄**(§17 J-2 · 되돌리지 않는다) ⇒ **제품 SQL 총 2줄** |
| C2 | `sales_deliveries (tenant_id, partner_id, source_type)` — 커버링 · L2 **3,122→2,013 (−36%)** · **힌트 없이** 채택 |
| C4 | `collections (tenant_id, ref_doc_type, ref_doc_id, is_active, source_type, amount)` — 단독 **−1.5%** · **존재 이유 = ㉪ 의 2~4% 함정 제거** ⇒ **[5] 안건** |
| 🔴 묶음 근거 | 9구간(0·1·2·3·4·5·10·50·100%) **전부 기준선 이하** · 최악 칸 2%: **2,241**(−26%) · 0%: **41**(기준선 112,040) |
| 🔴 술어를 못 빼는 이유 | 인덱스만으로는 **0% 구간을 못 고친다**(110,863). 0% = **이관 직후 = 모든 고객의 출발점** |
| 🔴 인덱스를 못 빼는 이유 | ㉪ 단독은 2~4% 에서 **+116~182%**(3/3 재현). 모든 고객이 0%→5% 를 **반드시 통과**한다 |
| 🔴 L5 | **처방 없다 — 못 고친 채 닫는다.** 남은 위험(지급 등록 중 그 회사 반품 등록이 **거래처와 무관하게 전부 막힌다**)은 열린 채로 보고한다 |
| 힌트 | 🔴 **0개**(B-3). 인덱스 없는 구버전 DB 는 **느릴 뿐 등록은 산다** ⇒ 1176 위험 소멸 |
| 부작용 | 8문장 전수 **악화 0건** · **D1-a 3→2 개선** · 값 8/8 동일 |

| 결재 | **[5] 3건**(C4 채택 · B-4 해석 · L5 무처방) · **PM 4건**(L2 ㉪ 묶음 재승인 · 게이트 2개 · DB-125 번호 · ALGORITHM 표기) |

### 이 지시서를 읽는 사람이 절대 하면 안 되는 것
- **묶음을 쪼개 배포하는 것** — C2·C4·㉪ 중 하나만 넣으면 **지금보다 나쁜 구간이 산다**
- 힌트(`FORCE INDEX`·`STRAIGHT_JOIN`) **재도입** — 인덱스 없는 DB 에서 **1176 으로 등록이 죽는다**

- **L5 에 처방을 얹는 것** · **`rt.partner_id` 술어 추가**(금액을 덜 센다 — 기각됨)
- 컬럼 추가·삭제 · 데이터 변경 · 기존 인덱스 삭제 · **`tenants` 조인** · **DB-121·122 번호 사용**
