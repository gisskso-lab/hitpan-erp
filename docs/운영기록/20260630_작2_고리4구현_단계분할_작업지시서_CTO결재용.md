## 3. PM 권고 — 단계 분할 (설계서 §6-1 정합, 위험도 높아 한 번에 금지)

설계서가 단계 권장: **②a 스키마버전+MigrationRunner배선 → ②b Velopack PoC(V1~V4 실측) → ③ 롤백상태머신.**
②a는 어제 ①에서 절반(테이블+클래스) 했으니, 실제 작업은 아래 3단계:

### 단계 P1 — MigrationRunner 앱시작 배선 (가장 안전, 의존 0)
- **무엇**: 이미 있는 `MigrationRunner.cs`(클래스)를 Program.cs에 DI 등록 + 앱 시작 시 `schema_migrations` 기준 미적용 DB-*.sql 멱등 적용 호출.
- **왜 먼저**: Velopack·롤백과 독립. **이것만으로도 "손 ALTER 운영수술"(헌법 #39 사고 근원)을 검증된 자동 적용으로 대체**.
- **리스크**: 낮음. 단 기존 운영 DB에 이미 적용된 ALTER를 재적용 안 하도록 schema_migrations 시드 정확성 필수(헌법 #13 DESCRIBE).
- **검증**: B갈래 hitpan_e2e 빈 DB에 적용 → 124테이블 + DB-*.sql 순차적용 → 멱등(2회 실행=동일) 확인.

### 단계 P2 — Velopack PoC (실측, 머지 전 필수)
- **무엇**: 설계서 §2 V1~V4 격리 PoC 실측 — ①자동롤백 API 존재? ②특정버전 다운그레이드 API? ③이전버전 보관 개수/기간? ④서비스/콘솔 앱 호환?
- **왜 PoC 먼저**: 설계서가 "Velopack 가정은 ⚠️검증 없이 머지 금지"로 못박음. 가정 위에 롤백 쌓으면 사상누각.
- **리스크**: 🔴 R2(자동롤백 API 미확인). PoC 결과로 ③ 설계 확정/수정.
- **검증**: B갈래 테스트 환경(헌법 #39 — 운영 절대 금지).

### 단계 P3 — 원자적 롤백 상태머신 (P1·P2 결과 위에)
- **무엇**: `UpdateRollbackOrchestrator` + `update-state.json` 상태머신(설계서 §3). BACKING_UP→APPLYING_EXE→MIGRATING→VERIFYING→COMMITTED / 실패시 ROLLBACK_DB_THEN_EXE.
- **왜 마지막**: P1(마이그 적용)·P2(Velopack 실동작) 둘 다 확정돼야 그 위에 롤백을 얹음.
- **리스크**: 🔴 R1(MariaDB DDL 트랜잭션 롤백불가 → pre_update 전체덤프 복원이 유일 의지처), R3(5조각 버전정합), R4(롤백 중 사용자 입력).
- **검증**: B갈래에서 의도적 마이그 실패 주입 → DB·EXE 동시 구버전 복원 + 스모크 PASS 실측.
