## 1. 🔴 사장님이 정의해주신 것 — 이것부터 읽어라

> *"사실 대부분 고객사들은 창고를 사용하지 않을거야. 이유는 도소매 업체들은 대부분 사업장에서 상품을 보관하고 출고하기 때문이야."*
> *"미지정 그게 상품마스터의 기본 디폴트 값이야. 창고는 물류까지 돌리는 중형이상의 유통업장을 운영하는 사장들에게 필요한 **기능**이야."*
> *"메인창고 하나만 설정되어 있는거 자체가 어떻게 보면 미사용이랑 같은 기능을 하기때문에"*

🔴 **PM 이 "옵션" 이라 적자 "옵션이 아닌 기능" 으로 정정하셨다.**

### 왜 이 낱말이 중요한가

**「옵션」이라 부르면 부가물로 취급해 대충 다뤄도 된다고 읽힌다.** 기능이므로:

- 중형 이상 유통업장에서 **제대로 서 있어야** 한다
- **동시에** 안 쓰는 다수는 **존재를 몰라도** 재고가 정상으로 돌아야 한다

**둘 중 하나만 만족하면 실패다.**

### 「창고를 안 쓴다」의 실제 DB 모양 (실측)

창고가 **0개가 아니다**:

| 확인한 것 | 근거 |
|---|---|
| 회사 생성 시 `MAIN` 1행 자동 생성 | `CompanyBootstrapProvisioner:280-287` |
| 사용자는 그 존재를 모른다 | 상품등록 화면에 「미지정」이 기본 |
| 화면 안내문 | *"비워두면 회사 기본창고로 입고됩니다"* (`ItemDetail.razor:103`) |
| `warehouse_id` 는 NOT NULL | `item_stock`·`stock_ledger`·`stock_adjust_logs` 셋 다 |

⇒ **창고 1개 + `items.default_warehouse_id` 전부 NULL** 이 다수 고객의 상태다.
⇒ 창고결정 3단의 **③(테넌트 MAIN)은 「최후 폴백」이 아니라 다수의 정상 경로다.**

🔴 **사장님 결정**: MAIN 으로 들어가는 것으로 확정. **추가 수술 없음.**
(PM 이 "화면만 미사용 / 스위치 신설 / `warehouse_id` NULL 허용" 3안을 여쭸고 1안 확정)

### 2-1. 작20 봉합 — 두 축이었다

**① 창고결정 3단이 BOM 에만 없었다**

매출(작19)·매입은 3단인데 BOM 은 ③ 하나뿐. 상품마스터에 A창고를 지정해도
MAIN 에서 빼려다 **A창고에 자재가 100개 있는데 "재고 부족"으로 생산이 막혔다.**

⇒ `WarehouseResolver` 를 BOM 도 부르게 했다. **해체(`DisassembleAsync`)도 같이** —
생산만 고치면 완제품은 A창고에 쌓이는데 해체는 MAIN 을 뒤져 또 막힌다.

**② 과차감 — 별개 축이고 더 무겁다**

`GetAsync` 의 `LEFT JOIN item_stock` 에 창고 필터·합산이 없어 자재가 2창고면
목록이 2행이 됐고, **10개 생산에 자재 20개**가 빠졌다. 창고 3개면 30개.
원장·원가·분개까지 부푼다.

🟢 **같은 파일 `GetListAsync`(:73-76) 는 이미 창고합산을 쓰고 주석까지 이 사고를 설명하고 있었다.**
`GetAsync` 만 안 고쳐져 있었다.

**곁가지**: `stock_adjust_logs` 의 before/after 를 읽는 SELECT 에 `warehouse_id` 필터가 없어
기록 창고와 다른 창고 수량을 적고 있었다. 생산·해체 4곳 모두 넣었다.

### 2-2. 사본을 늘리지 않았다

같은 SQL 이 매출·매입에 **따로 두 벌** 있었다. BOM 에 세 번째를 만들면 또 한쪽만 고쳐진다.

⇒ `WarehouseLookup` 신설. **판정**(`WarehouseResolver`, 순수함수 — 시험이 DB 없이 돈다) / **조회**(`WarehouseLookup`)
