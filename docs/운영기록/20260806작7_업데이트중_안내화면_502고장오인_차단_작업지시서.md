## 0. 사장님 오더 (원문)

실측 도중 502 를 직접 겪으신 뒤:

> "히트판 접속이 끊어지고 502에러 떴다고"
> "고객이 보기에 업데이트 중 오류로 인식하지 않게 화면에 안내문구를 하나 쓰자."
> "히트판 업데이트 중입니다. 업데이트가 끝나면 컨트롤+시프트+R을 눌러주세요 라고 나가면 어때?"
> "업데이트 완료시 완료 메시지 띄우고"
> (30초 후 F5 안내안에 대해) "이것도 좋네 이게 더 낫겠다"
> (완료 후 처리) "자동으로 넘어감이 더 좋다" / "오케이"

**근거의 무게**: 이건 가정이 아니라 **오늘 실측에서 실제로 발생한 현상**이다.
그리고 **히트판을 만든 사장님이 직접 "오류"로 읽었다.** 만든 사람이 그렇게 읽으면 고객은 100% 전화한다.

## 1. 확정된 사양 (사장님 결정)

### 1-1. 업데이트 중
```
┌────────────────────────────────────┐
│                                    │
│         히트판 업데이트 중          │
│                                    │
│    잠시만 기다려 주세요.            │
│    끝나면 자동으로 돌아옵니다.      │
│                                    │
│           ● ● ●                    │
│                                    │
│    창을 닫지 마세요.                │
└────────────────────────────────────┘
```

### 1-2. 30초 경과해도 미복귀 시 — 아래에 조용히 한 줄 추가
```
       오래 걸리면 F5 를 눌러 주세요
```

> **PM 원안 `Ctrl+Shift+R` 은 사장님이 F5 안으로 교체 확정.**
> 사유: 현장 직원은 `Ctrl+Shift+R` 을 평생 쓰지 않는다. 잘못 눌러 `Ctrl+R` 이 되면 옛 화면이 그대로 나와
> "또 안 되네"가 된다. F5 는 비개발자가 아는 유일한 새로고침 키다. (히트판 정신 — *"설명서 없이 그냥 됐다"*)

### 1-3. 완료 시
```
┌────────────────────────────────────┐
│    ✅  업데이트가 끝났습니다        │
│                                    │
│        히트판 1.2.55                │
│        잠시 후 화면이 열립니다      │
└────────────────────────────────────┘
        ↓ 2~3초 뒤 **자동 이동** (사장님 확정)
      히트판 정상 화면
```

**고객 조작 0회.** 자동 복귀가 실패할 때만 F5 한 번.

## 2. 기술 전제 — 왜 히트판 안에 넣으면 안 되는가

`installer/HitPan-Universal.iss:1134`:
> "터널 — ingress origin = http://localhost:5257(API)"

터널이 **히트판 API 에 직결**돼 있다. 업데이트 중에는 그 API 가 꺼진다.
⇒ **502 를 내는 주체는 히트판이 아니라 터널(cloudflared)이다.**
⇒ 히트판 안의 코드·페이지는 그 순간 **아무것도 실행되지 않는다.** 안내화면을 API 에 넣는 설계는 원천 불가.

## 3. 구현 방안 3안 — PM 비교

| | 방안 | 어디에 두나 | 장점 | 단점 |
|---|---|---|---|---|
| **A** | **브라우저가 미리 안다** | 히트판 web (사전 로딩) | 인프라 무손상(#29). 히트판 끊겨도 이미 브라우저에 있음 | [예] 를 누른 그 창에서만 유효. 다른 PC/탭은 여전히 502 |
| **B** | 터널 ingress 이중화 | cloudflared 설정 | 모든 접속자에게 유효 | **터널 설정 변경 = 헌법 #29 사전승인 대상.** 통신 무결성 리스크. 안내용 상주 프로세스 필요 |
| **C** | A + B 병행 | 양쪽 | 완전 | 범위 과대. 오늘 범위 아님 |

### PM 권고 — **A안**

근거:
1. **사장님이 겪으신 시나리오가 정확히 A안 범위다.** [예] 를 누른 그 창에서 502 를 보셨다.
   업데이트를 시작한 사람이 그 화면을 보는 것 — 이게 압도적 다수 경우다.
2. **헌법 #29** — 터널·ingress 조작은 사전승인 대상이고, 오늘 자동업데이트가 막 정상화된 시점에
   통신 계층을 건드리는 건 리스크 대비 실익이 낮다.
3. **B안은 별건으로 분리**해 다중 사용자 환경을 별도 설계한다(아래 §7).

**A안 동작 원리**
```
[예] 클릭
  → 브라우저가 안내화면을 **먼저 화면에 띄운다** (이미 로딩된 상태 = 히트판이 꺼져도 살아있음)
  → 5초마다 /health 를 두드린다
  → version 이 새 버전으로 바뀌면 → 완료 메시지 → 2~3초 → 자동 이동
  → 30초 지나도 미복귀 → "오래 걸리면 F5" 한 줄 추가
```
`Ctrl+Shift+R` 을 **사람 대신 페이지가 하는 것**이다.

## 4. 30초 기준의 근거 (실측 기반)

오늘 실측에서 히트판이 실제로 꺼져 있던 시간을 근거로 확정한다.
`/health` 응답 `uptime_sec: 134` 는 재기동 후 경과이므로, 정확한 다운타임은 **증거수집 로그에서 산출**한다.

> **원칙**: 너무 짧으면 매번 뜨고, 그러면 고객이 "또 F5 눌러야 하나"를 학습한다.
> 그건 자동 복귀를 만든 이유를 없애는 것이다. **평소보다 확실히 오래 걸릴 때만** 떠야 그 문구가 의미를 갖는다.
> 실측 다운타임의 **2~3배**를 기준으로 잡되, 최소 30초 이상.

## 5. 설계 리스크 (구현 전 반드시 해결)

| # | 리스크 | 대응 |
|---|---|---|
| R1 | **폴링이 히트판 재기동을 방해** | `/health` 만 두드린다(가벼움). 5초 간격. 최대 10분 후 폴링 중단 + 안내 유지 |
| R2 | **완료 판정 오류** — 옛 프로세스가 아직 살아 옛 버전 200 응답 | `/health` 의 **version 이 새 버전과 일치**할 때만 완료. 200 만으론 불통과 (W4-5 게이트와 동일 기준) |
| R3 | **끝없이 도는 화면** | 10분 초과 시 "예상보다 오래 걸립니다. F5 를 눌러 주세요" 로 전환. 무한 대기 금지 |
| R4 | **롤백된 경우** — 옛 버전으로 돌아옴 | version 이 **옛 버전 그대로**면 완료 메시지 없이 조용히 복귀(고객에게 실패를 굳이 알리지 않되, 거짓 성공도 표시하지 않는다) |
| R5 | **[나중에] 누른 사람** | 안내화면 안 뜸. 업데이트 진입 시에만 |
| R6 | **개발용어 노출** (헌법: 고객 노출 영역 개발용어 금지) | "502", "서버", "프로세스", "API" 등 금지. "히트판", "업데이트", "화면" 만 사용 |
| R7 | **창을 닫아버림** | 문구로 명시("창을 닫지 마세요"). 닫아도 업데이트 자체는 워치독이 진행하므로 데이터 위험 없음 — 다시 접속하면 됨 |
