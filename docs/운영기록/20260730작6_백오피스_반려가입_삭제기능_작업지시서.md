## 1. 무엇이 문제인가 (실측)

### 1-1. 반려는 되는데 삭제가 없다

`SignupsAdminController.cs` 현행 엔드포인트:

| 엔드포인트 | 줄 | 있나 |
|---|---|---|
| `GET /api/admin/signups` | — | ✅ |
| `POST /api/admin/signups/{id}/approve` | 90 | ✅ |
| `POST /api/admin/signups/{id}/reject` | 316 | ✅ (`status='rejected'` 저장) |
| **`DELETE /api/admin/signups/{id}`** | — | ❌ **없음** |

`AdminSignups.razor` 화면:

- `반려` 필터 탭 존재(33행) → **반려 목록을 볼 수는 있다**
- 그 행에 대한 조작 버튼: `submitted` 상태만 `승인`(100행)·`반려`(102행)
- `rejected` 행 → **아무 버튼도 없다.** 목록에 영구히 남는다

### 1-2. ⭐ 왜 단순 "지저분함" 문제가 아닌가 (급소)

`landing_signups` 스키마 (`installer/backoffice/00_backoffice_core.sql`):

```sql
signup_token   varchar(64)  NOT NULL,
biz_no_hash    varchar(128) NOT NULL,
...
UNIQUE KEY uk_signup_token (signup_token),
KEY ix_biz_no_hash (biz_no_hash),
```

`uk_signup_token` = **유니크 제약**. 그리고 `biz_no_hash` 로 사업자번호를 식별한다.

> ⚠️ **반려 건이 남아 있으면 같은 업체의 재가입이 막힐 수 있다.**
> 랜딩 가입 로직이 `biz_no_hash` 중복을 검사한다면(→ [3] 선행 확인 필수),
> 잘못 반려한 업체는 **영구히 가입 불가**가 된다. 이는 영업 차단이다.
> ⇒ 삭제 기능은 편의가 아니라 **가입 흐름 복구 수단**이다(헌법 #20).

### 1-3. ⭐⭐ 사장님 실측 제보로 드러난 **고아 tenants 행** (2026-07-30 추가)

> **사장님 제보**: *"백오피스에 내가 반려한 「히트판비즈텍」 이라는 업체는 테넌트코드도 생성이 안되었음 확인바람"*

**PM 확인 결과 — 테넌트코드 미생성은 정상이다. 그러나 그 확인 과정에서 별개 결함이 드러났다.**

#### (1) 테넌트코드가 없는 것 자체는 정상

| 시점 | `tenants` 상태 |
|---|---|
| 랜딩 가입 | 행 저장, `status='pending'` (코드 미활성) |
| **승인**(`approve` 137-141행) | `UPDATE tenants SET status='active'` + 라이선스 발급 → 코드 유효 |
| **반려**(`reject` 322-326행) | **`landing_signups.status='rejected'` 만 변경** |

⇒ 승인을 안 했으니 발급이 안 된 것. **버그 아님.**

#### (2) 🔴 그런데 반려가 `tenants` 를 방치한다

`Reject` 는 `landing_signups` 만 UPDATE 하고 **`tenants` 의 `pending` 행을 그대로 남긴다.**
지우지도, 상태를 바꾸지도 않는다. ⇒ **고아(orphan) `pending` 행이 영구 누적.**

#### (3) 그래서 작6 을 그대로 만들면 **반쪽 삭제**가 된다

| 작6 원안대로 지우면 | 결과 |
|---|---|
| `landing_signups` 행 삭제 | `tenants` 의 `pending` 행 **그대로 방치** |

목록 조회(`List` 41-46행)는 `tenants` 를 이렇게 매칭한다:

```sql
LEFT JOIN tenants t ON t.tenant_id = (
    SELECT t2.tenant_id FROM tenants t2
    WHERE t2.company_name = s.company_name    ← 회사명 문자열 매칭
    ... status='pending' … submitted_at 근접순 1건
```

**회사명 + 시각 근접**으로 붙이는 구조다(주석에 *"사고 #5 봉합 2026-06-10 — signup ↔ tenant 1:1 매칭"* 이
있는 것이 이 매칭의 취약성을 이미 한 번 앓았다는 증거다).

> 🔴 **위험**: 반려·삭제 후 같은 회사명으로 **재가입하면, 남아 있던 고아 `pending` 행에 잘못 붙을 수 있다.**
> 그 상태로 승인하면 **엉뚱한 tenant 가 활성화**된다. 사고 #5 의 재발 경로다.
> ⇒ 삭제는 **`landing_signups` 와 `tenants`(pending) 를 한 단위로** 처리해야 한다.

## 2. 무엇을 하는가 (범위)

**`rejected` 상태 건만** 삭제할 수 있게 한다.

| 대상 | 변경 |
|---|---|
| `SignupsAdminController.cs` | `DELETE /api/admin/signups/{id}` **추가** — `landing_signups` + **고아 `tenants`(pending) 동시 정리** |
| `AdminSignups.razor` | `rejected` 행에 `삭제` 버튼 + 확인 대화상자 **추가** |

### 2-0. 🔴 삭제는 **한 트랜잭션 · 두 테이블** (1-3 근거)

```
BEGIN
  1) landing_signups  : status='rejected' 확인 후 DELETE
  2) tenants          : 그 signup 에 매칭되는 status='pending' 행 DELETE
COMMIT
```

**규칙**:
- `tenants` 는 **`status='pending'` 인 것만** 지운다. `active` 는 🔴 **절대 건드리지 않는다**(승인 완료 고객).
- 매칭은 `List` 41-46행과 **같은 규칙**을 쓴다(회사명 + `submitted_at` 근접 1건). 규칙이 갈라지면 엉뚱한 행을 지운다.
- 매칭 결과가 **2건 이상이면 삭제하지 말고 중단**한다 — 어느 것인지 모르는 상태에서 지우면 사고 #5 재발.
- `tenants` 행이 **0건이어도 `landing_signups` 삭제는 진행**한다(이미 정리됐거나 애초에 없던 경우).
- 지운 `tenant_id` 를 **로그에 남긴다**(헌법 #15·#24).

> ⚠️ **[3] 착수 전 필수 확인**(헌법 #12·#13): `tenants` 를 FK 로 참조하는 자식 테이블이 있는지
> **전수 grep** 하라(`devices`·`subscriptions`·`licenses` 등). 있으면 FK 제약으로 DELETE 가 실패하거나
> 연쇄 삭제가 일어난다. **결과를 개발명세서에 기록**하고, 자식 행이 있으면 **삭제를 중단**하는 쪽으로 간다
> (모르는 것을 지우지 않는다 = fail-closed).

### 2-1. 🔴 삭제 허용 범위 — 절대 규칙

```
status = 'rejected'                → 삭제 허용
status = 'submitted'               → 거부 (아직 판단 전 — 반려부터 하라)
status = 'approved' / 'active'     → 🔴 절대 거부
```

**`approved`·`active` 를 지우면 안 되는 이유**: 승인 건은 이미 `tenants` 저장 + 라이선스 발급 +
ERP webhook 발송이 끝난 상태다(`approve` 126-152행). 가입 원본을 지우면
**대금·라이선스·테넌트의 근거가 사라진다.** 법무·회계 추적 불가(헌법 #24 책임 3축).

⇒ **컨트롤러에서 상태를 다시 검사한다.** 화면이 버튼을 숨기는 것만으로는 부족하다
(API 직접 호출 가능 — 보안 매니저 1 검토 대상).

### 2-2. 물리 삭제인가 논리 삭제인가 — ⭐ 판단 필요

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 물리 삭제** (`DELETE FROM`) | 행 제거 | `uk_signup_token`·`biz_no_hash` 즉시 해제 → **재가입 가능** | 기록 소멸 |
| **B. 논리 삭제** (`status='deleted'`) | 상태만 변경 | 기록 보존 | **유니크 제약 그대로 → 재가입 여전히 막힘** |

**설계팀 권고 = A(물리 삭제) + 삭제 이력 로그.**

근거: 사장님 목적이 *"삭제"* 이고, B 는 1-2 의 재가입 차단을 **해결하지 못한다**(문제가 그대로 남는다).
단 헌법 #41·문서보관 정신에 따라 **누가·언제·무엇을 지웠는지 감사 로그는 남긴다**
(`_logger.LogWarning` 최소 + 기존 감사 테이블 있으면 그쪽 — [3] 이 grep 후 결정, 헌법 #12).

> ⚠️ **[3] 개발 착수 전 확인 의무**: 랜딩 가입 API 가 `biz_no_hash` / `signup_token` 중복을
> 실제로 어떻게 검사하는지 **먼저 grep 하라**(헌법 #13 — 새 SQL 전 DESCRIBE 의무 정신).
> 검사하지 않는다면 재가입은 애초에 막히지 않으므로 A/B 판단 근거가 달라진다.
> **그 결과를 개발명세서에 기록한다.**

## 4. 어떻게 하는가 ([3] 개발팀용)

### 4-1. API (담당: 백엔드 개발자 1 · 보안 개발자 1 검토)

```
DELETE /api/admin/signups/{signupId}
```

절차:
1. 현재 `status` 조회
2. `rejected` 아니면 → `400` + 사유 반환 (**서버에서 재검사**, 2-1)
3. `DELETE FROM landing_signups WHERE signup_id=@Id AND status='rejected'`
   (WHERE 에 status 를 **한 번 더** 넣는다 — 경합 방어)
4. 영향 행 0 → `400` "삭제 대상이 없습니다"
5. 감사 로그: 누가·언제·`signup_id`·`company_name`
6. 기존 `Approve`/`Reject` 의 예외처리·응답 형식 **패턴 그대로** 따른다(헌법: 기존 패턴 준수)

### 4-2. 화면 (담당: 프론트 개발자 1 · UX 1)

- `rejected` 행에만 `삭제` 버튼 (`context.Status is "rejected"`)
- **확인 대화상자 필수** — 되돌릴 수 없는 작업
  > "○○○ 업체의 가입 신청을 삭제합니다. 삭제하면 되돌릴 수 없습니다. 진행하시겠습니까?"
- 성공 → `Snackbar` 안내 + 목록 새로고침
- 개발용어 금지(헌법 #23·#24)

### 4-3. 하지 말 것

- ❌ `approved`·`active` 삭제 허용 (2-1)
- ❌ 화면에서만 막고 API 는 열어두기
- ❌ 확인 대화상자 없이 즉시 삭제
- ❌ `landing_signups` 스키마 변경 (컬럼 추가·제거 — 이번 범위 아님, 헌법 #37)

## 5. 검증 방법 (SoD — 만든 사람 ≠ 검증하는 사람)

| # | 게이트 | 기준 |
|---|---|---|
| V1 | 빌드 | errors 0 + warnings 0 (헌법 #19) |
| V2 | 정상 삭제 | `rejected` 건 삭제 → 목록에서 사라짐 |
| V3 | **거부 검증** | `submitted`·`approved`·`active` → **API 직접 호출로도 거부**(화면 우회) |
| V4 | 재가입 복구 | 삭제 후 **같은 사업자번호로 재가입 가능** (1-2 목적 달성 확인) |
| V5 | 감사 로그 | 삭제 기록(`signup_id`·회사명·`tenant_id`)이 로그에 남는가 |
| V6 | 회귀 | 승인·반려 기능 무손상 |
| **V7** | **고아 tenants 정리** | 삭제 후 `tenants` 에 그 회사의 `pending` 행이 **0건** (1-3) |
| **V8** | **active 보호** | `active` tenant 는 **절대 삭제되지 않음** — 승인 완료 고객 1건 두고 반려건 삭제해도 무손상 |
| **V9** | **재가입 오매칭 없음** | 삭제 → 같은 회사명 재가입 → 승인 → **새로 만든 tenant 가 활성화**(옛 고아 행에 안 붙음, 사고 #5 재발 0) |

> **V3·V4·V7·V8·V9 가 핵심이다.**
> V3 없으면 보안 구멍 · V4 없으면 문제 미해결 · **V7 없으면 반쪽 삭제** ·
> **V8 은 실고객 데이터 보호** · **V9 는 사고 #5 재발 차단**.
> V8·V9 는 **실제로 데이터를 만들어 놓고** 검증한다(코드 읽기만으로 통과 금지 — 검증팀 SoD).
