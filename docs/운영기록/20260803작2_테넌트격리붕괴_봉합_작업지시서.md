## 2. 사고 — 사실

### 2-1. 실측 채증 (2026-08-03 Windows Sandbox, test1.hitpan.kr)

브라우저 콘솔:
```
POST https://api-demo.hitpan.kr/api/auth/login   net::ERR_FAILED
Access to fetch at 'https://api-demo.hitpan.kr/api/auth/login'
from origin 'https://test1.hitpan.kr' has been blocked by CORS policy
```

게시본 확인 (외부 조회):
```
https://test1.hitpan.kr/appsettings.json
  → "ApiBaseUrl": "https://api-demo.hitpan.kr"
https://test1.hitpan.kr/appsettings.Local.json
  → "ApiBaseUrl": "https://api-demo.hitpan.kr"
```

### 2-2. 진범

레포 원본 `src/HitPan.Web/wwwroot/appsettings.json` 이 **본사 데모 서버**를 가리켰다.
이 파일은 출하 EXE·업데이트 패키지에 **그대로 실린다.**

⇒ **어느 고객사에서 접속하든 화면이 한 곳으로 로그인을 보낸다.**
  고객사 100곳이면 100곳이 같은 곳을 본다 = **회사별 격리가 구조적으로 부재.**

### 2-3. 왜 지금까지 안 드러났나

```
설치 시    FixupBlazor 가 고객 도메인으로 덮어씀  → 가려짐
업데이트   web/·api/ 폴더 통교체 → 원본 부활      → 드러남
```

**7/01(작7)·7/07(작2 W2-1)에도 같은 사고**가 났다. 매번 **정정 로직만 덧대고
원본은 안 고쳐** 재발했다. 이번이 세 번째다.

### 2-4. 피해 범위

| 항목 | 판정 |
|---|---|
| 실제 자격증명 유출 | **없음** — `api-demo.hitpan.kr` 이 현재 미존재라 CORS 가 차단 |
| 구조적 위험 | 🔴 **있음** — 그 주소가 살아나면 그대로 나간다. **우연히 막힌 것이지 설계가 막은 게 아니다** |
| 고객 영향 | 현재 실고객 0 → 실피해 0. **베타 시작 후였으면 즉시 사업 중단 사안** |
| 법적 | 개인정보보호법 안전조치 의무 · 고객사 간 데이터 혼입 시 손해배상 |

## 4. 구조적 교훈 — 정정은 업데이트를 이길 수 없다

전수 감사 결과:

```
UpdateOrchestrator.cs:333-340
  Directory.Move 로 web/·api/ 를 폴더째 통교체. 파일 단위 보존 로직 전무.
     ↓
FixupBlazor 가 설치 시 정정하는 5개 파일 전부가 업데이트 때 원본값으로 되돌아간다.
```

7/01·7/07 봉합이 재발한 이유가 이것이다. **정정 로직을 아무리 덧대도 업데이트가 이긴다.**

(`.iss:1047,1059`). **터널 접속은 `api/wwwroot` 를 본다**(7/22 작3 '터널 404 진범' 경로).
⇒ 터널 경로는 애초에 한 번도 정정된 적이 없다. 원본을 비우면 이 구멍도 함께 막힌다.

"고쳤다고 생각하는 상태"다. 오늘 PM 이 ⑥ 자동업데이트를 "PASS" 라 보고했다가
