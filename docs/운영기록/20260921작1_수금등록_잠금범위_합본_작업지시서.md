## §2 사실 목록 — 이 위에서만 일한다 (선행검증 §3 · 작지 §23-2)

1. 표적은 **회사 경계가 아니라 거래처·전표 경계**다. 실제 고객 설치는 **한 DB 한 회사**(V5).
2. **제일 나쁜 자리는 L2**(`collections ALL 107,653` · 112,019행 잠금). 트랙 이름이 「수금등록」인데 수금 축이 제일 나쁘다.
3. **DB-124 는 실물 분포에서 옵티마이저가 안 고른다** — 접두 선택도 0.
4. **행 수는 방아쇠가 아니다** — 2,060행까지 고르게 뿌리면 좋은 계획 유지.
5. **통계 갱신으로 안 고쳐진다**(실측). 6. **조인 순서만으로도 안 고쳐진다**(실측) — **인덱스 강제까지 같이** 줘야 한다.
7. **좁은 계획이면 아무도 안 막힌다**(대조군 D1-b) ⇒ 고칠 것은 **범위**다.
8. 🔴 **`purchase_returns` 는 실물 사본에서 0행** — L5·D1-c 의 계획은 **아직 아무도 못 쟀다.**
9. 🔴 **원인은 둘이고 서로를 가린다.** 한쪽을 봉합하면 나머지를 **격리해서 다시 재야** 한다.
10. 🔴 **기존 게이트는 둘 다 못 잡는다** — 시드 분포 + 이름 목록.

### 이 트랙에서 비싸게 배운 것 (구현자도 지킨다)
- **기대는 실측 전까지 사실이 아니다** (PM 이 4번 틀렸다)
- **대조군은 「넣었다」로 부족하다** — 가르는 변수가 **관측된 잠금이 있는 인덱스 안에** 있어야 한다
- **빈 표의 EXPLAIN 은 근거가 못 된다**
- **이름 목록 예외는 감시자를 지운다**

### 12-1. 🔴 진짜 뿌리가 바뀌었다 — 「타입 칸 선택도 0」이 아니다

§0 카드·§2 사실목록 4번은 방아쇠를 **「거래처 편중 + 타입 칸 선택도 0」**이라고 적었다. **검증팀장이 스스로 그것을 정정했다**(선행검증 §2-3-1) — 비교한 두 DB 가 다른 변수까지 같이 달랐다(교란변수).

**실측된 뿌리**:
> **실물 이관 데이터는 `collections.ref_doc_id` 가 100% NULL(109,822/109,822) · `payments.ref_order_id` 가 100% NULL(2,228/2,228)** 이다.
> 그 칸이 DB-124 세 칸 인덱스의 **마지막 칸**이라 `mysql.index_stats` 의 `prefix_arity 3` 이 **NULL** 로 남는다(= 선택도 없음).
> **강제로 태워도 `rows` 추정이 접두 범위 전체(10.7만)로 찍힌다.**

⇒ **「인덱스를 넣었으니 됐다」가 아니라, 데이터가 그 인덱스를 못 쓰게 생겼다.** 설계 §13 과 이 지시서 §2-4 의 「타입 칸 선택도 0」 서술은 **이 문장으로 대체**한다.
⚠️ 경계까지가 실측이다 — 키당 1행이면 좋은 계획, 키당 10.7행이면 나쁜 계획. **그 사이 어디인지는 안 쟀다.**

### 12-2. 🔴 설계 후보 ⓐ·ⓒ 는 **실측으로 기각됐다** · `USE INDEX` 로는 부족할 수 있다

검증팀장이 실물 사본에서 직접 걸어 봤다(선행검증 §2-3-3):

| 시험한 것 | 결과 |
|---|---|
| ⓐ 인덱스 신설 `payments(tenant_id, ref_order_id)`·`collections(tenant_id, ref_doc_id)` | 🔴 L2·L4 **그대로 `ALL`** |
| ⓒ `STRAIGHT_JOIN` 만 | 🔴 안쪽이 `ALL` + `BNL join` |
| ⓒ + `join_cache_level=0` | 🔴 여전히 `ALL` |
| **ⓒ + `FORCE INDEX` 까지** | 🟢 **좋은 계획** (`pr ref fk_pr_partner 57` · `ep ref idx_pay_tenant_type_ref`) |
| `ANALYZE … PERSISTENT FOR ALL` | 🔴 안 듣는다 |

⇒ **P-1ⓑ 에 답이 나왔다**: 내가 「`USE INDEX` 는 권고다 · 안 바뀌면 `FORCE INDEX` 로 올릴지 되묻겠다」고 걸어 둔 조건의 실측 답은 **「`FORCE INDEX` 가 필요하다」**이다.
⇒ 처방 ㉦ 의 **방향은 맞다**(힌트 조합). 다만 **문구를 `USE INDEX` 로 적어 둔 부분은 설계가 다시 정해야 한다.**
⇒ **DB-125 단독으로는 안 된다**(ⓐ 기각). DB-125 는 힌트가 가리킬 대상으로서만 의미가 있다.

검증팀장 ④-10: **`MaxCrossTenantBlocked = 4` 는 죽은 단언이다** — `crossOps` 가 **정확히 4건**이라 `crossBlocked.Count <= 4` 는 **절대 실패할 수 없다.**
나는 같은 문서(작지 §16-2 · §19)에서 **「고정 상수 상한을 박지 마라 · 절대 실패 불가가 되는 것을 보이라」**고 적어 놓고 **내가 그걸 했다.**
⇒ **T2 에서 제거한다.** 대체는 「건수 고정」이 아니라 **「어느 것이 막혔는지」를 이름으로 고정**하거나, **막힌 상대가 매칭 잠금이 아님을 증명**하는 쪽이다. 설계·구현이 정한다.
같은 이유로 `MaxCrossTenantUnnamed = 2` 도 다시 본다.

## §15 🟢 PM 결재 — 설계 5판 (브라운킴 · 2026-09-21)

**결재: 조건부 승인.** 처방 ㉪ 의 방향은 옳고, **4판보다 위험이 낮다.**

### 15-1. PM 이 직접 확인한 것 (받아쓰지 않았다)

설계의 핵심 주장은 *「`IS NOT NULL` 한 줄은 INNER JOIN 이 이미 함의하므로 결과집합을 바꿀 수 없다」*이다. **제품 코드로 확인했다** —

| 문장 | 조인 | 확인 |
|---|---|---|
| **L2** `LegacyBalanceMatching.cs:273~282` | `FROM collections ec **JOIN** sales_deliveries sd ON sd.delivery_id = ec.ref_doc_id …` | `ec.ref_doc_id` 가 NULL 이면 등치가 **UNKNOWN** → INNER JOIN 이 그 행을 **이미 버린다.** `AND ec.ref_doc_id IS NOT NULL` 은 **결과에 대해 항등**이다 ✅ |
| **L4** `:295~304` | `FROM payments ep **JOIN** purchase_receipts pr ON pr.receipt_id = ep.ref_order_id …` | 같은 구조 ✅ |

⇒ **성립한다.** 이것이 §17 에서 기각한 처방 (가)(`partner_id` 직접 술어)와 **종류가 다른 이유**도 분명하다 —
(가)는 조인이 함의하지 **않는** 술어라 **덜 셀 수 있었고**, ㉪ 는 조인이 **이미 함의하는** 술어라 **덜 셀 수가 없다.**

### 15-2. 🔴 5판이 4판보다 나은 진짜 이유 — 구멍 하나가 닫힌다

| | 4판(힌트) | 5판(㉪) |
|---|---|---|
| 인덱스가 없을 때 | **1176 → 등록 사망**(#20 위반) | `ALL` 로 떨어질 뿐 **등록은 산다** |
| 마이그 실패 허용 정책(#30)과 | **정면 충돌** | 충돌 없음 |
| 판정기·두 경로 | 필요 | **불필요** |
| DB-125 | 필요 | **불요 가능** |

내가 P-1ⓐ 에 걸어 둔 조건(「1176 은 지금 고치려는 병과 같은 병이다」)이 **설계를 더 나은 답으로 밀었다.** 조건을 건 값을 했다.
