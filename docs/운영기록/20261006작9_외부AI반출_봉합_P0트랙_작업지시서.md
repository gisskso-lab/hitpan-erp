## 0. 무엇이 문제인가 (선행검증 C-③ 실측)
- ERP 의 AI Tool 이 **거래처명·사업자번호·전화번호·매출이익**을 외부 AI 에 전송한다(PartnerSearchTool.cs:63-71 · SalesProfitabilityTool). 본사 경유는 아니나 처리위탁·국외이전 계약·고객 고지가 0.
- ⬛기각(10/6 [1-V] §3) — ~~`ai_mode` 기본 `hitpan_pool` 이면 **본사 계정 키**로 나가는 구조 ⚠️미확인~~ : pool(본사) 키는 코드·설정 어디에도 실재하지 않음. 실제 호출 키는 전부 고객이 직접 넣은 테넌트 소유 BYOK — 키 없으면 외부로 아예 안 나간다.

## 1. 결재된 방침 (Q-7 · 변경 불가)
- **봉합 전 베타에 이 Tool 노출 금지**(안철수·래리·법무 일치).
- 처리위탁 계약 또는 약관 내 국외이전 고지 **선체결 전 노출 금지** · pool 키 책임귀속 조항 명문화(법무).
- 약관 개정 초안·대리점 위탁계약은 이 트랙의 법무 묶음(구 Q-8·Q-9).

## 2. [1-V] 선행검증이 잴 것 (작7 트랙과 분리 · 이 트랙의 첫 걸음)
1. 외부 AI 로 나가는 **모든 길 전수**: Tool 목록 · 각 Tool 이 싣는 필드 · X-2(OpenAI/Gemini) 경로 · `hitpan_pool` 키의 출처·소유.
2. 노출 상태: 이 Tool 들이 지금 실물 ERP(1.3.53)에서 고객에게 **켜져 있나** — 켜짐이면 차단이 봉합 1순위.
3. 법인/개인사업자 구분 로직 유무(법무 — 1인사업자 거래처는 개인정보).

## 3. 하지 않는 것
- 작7 백오피스 트랙과 섞지 않는다(래리: 품으면 영역 이탈) · 운영 DB·고객 PC 직접 수술 금지(#39) · Tool 코드 삭제가 아니라 **노출 차단 + 계약·고지 후 재개**가 방침.

## 4. [2] 봉합 설계 (설계팀장 존 · 2026-10-06) — 켜는 조건 = 「고지·동의 기록 존재」 서버 검사

### 4-1. 차단 조합 판정 — A+B 만으로는 X-2 가 남는다 ⇒ **D 포함 확정** (단, 삭제가 아니라 게이트로 잠근다)
- [1-V] §5 주의 그대로: A(Tool 등록부)+B(엔진 입구)는 ②(AI직원)만 닫는다. ①(일반 챗봇 폴백)은 **사용자 질문 + 직전 8턴 history 를 3사로 내보내는 그 자체가 반출**이고, X-2(②답이 history 에 실려 ①로 재반출)도 ①이 열려 있는 한 남는다.
- 단 D 를 「폴백 제거」(코드 삭제)로 하면 재개 경로가 죽는다(§3 방침 위배 + §5 대조군 불능). ⇒ **삭제 0건 · 단일 게이트를 문 3곳에 건다.**

### 4-2. 게이트 1개 · 문 3개 (fail-closed)
- 신설 `IExternalAiGate.IsOpenAsync(tenantId)` — 서버 단일 판정: `ai_export_consents`(§4-3)에 해당 테넌트 유효 동의 기록이 **존재**할 때만 열림. 테이블 부재·조회 예외·기록 0건 = 전부 **닫힘**(fail-closed). 지금은 그 기록 자체가 없으므로 사실상 전면 차단. tenant_id 는 JWT 클레임에서만(#2).
- **문①** ChatbotService.cs:159 외부 폴백 분기 — 닫힘이면 ① 진입 0, KB-only 응답 + 안내 한 줄(§4-4). → D 효과 · **X-2 봉합**
- **문②** ChatbotService.cs:412 AI직원 엔진 분기 — 닫힘이면 ② 진입 0. → B
- **문③** AiAgentService.CompleteWithToolsAsync 입구 — 닫힘이면 차단 반환. → A 의 런타임 등가물(문②를 우회하는 새 호출자가 생겨도 Tool 반출 0 — 심층방어)
- Program.cs:300-305 등록부 3줄 **정적 제거는 안 한다**: 등록은 테넌트 무관 기동 시점이라 「동의 기록 존재」 조건을 걸 수 없고, 제거하면 §5 G-5 대조군(재개 경로 생존 증명)이 죽은 문이 된다. — 확인 필요: PM 결재 §8-1.
- ③ 핑(CheckConnectionAsync:1384)은 업무 데이터 0([1-V] §1 ③) — **차단하지 않는다**(키 사전 점검용 "OK" 왕복뿐). — 확인 필요: PM 결재 §8-2.

### 4-3. 동의 기록 — `ai_export_consents` 테이블 신설 (마이그 DB-NN)
- InnoDB 명시(#17) · INSERT ONLY 운용: id · tenant 식별 · terms_version · agreed_by · agreed_at · agreed_ip. **시드 0건.**
- 마이그는 `src/HitPan.API/Migrations/SQL/DB-NN_*.sql` + **출하 DDL `hitpan_db_clean.sql` 동시 반영**(#36 — DB-126 누락 사고 재발 금지).
- 스키마는 최소: 법무 약관 체계(별도 진행)가 확정되면 동의 화면·버전 체계가 이 테이블을 그대로 쓴다. **동의 기록을 쌓는 화면·API 는 이번 봉합에서 만들지 않는다** — 재개는 §7 결재 후.

### 4-4. 화면 안내 (ⓑ /settings/ai-assistant · AiAssistantPage.razor)
- 게이트 닫힘 상태 안내 문구(상시 노출) 초안: **「외부 도우미 연결은 이용 안내 동의 절차가 마련된 뒤 열립니다. 지금은 연결 정보를 저장해도 회사 자료가 밖으로 나가지 않습니다.」** — 업체명·개발용어 0(#23 검토 완료 · 「게이트」「API」「키」「차단」 등 미사용). 최종 문구는 고객 노출 어휘이므로 사장님 결재 상신(§8-4).
- 챗봇 쪽: 미동의로 외부 폴백이 막혀 KB-only 로 답한 경우 같은 어휘 기준의 안내 한 줄.
- SaveApiKeyAsync 「저장 즉시 status='valid'」([1-V] §2)는 이번 범위 밖 — 게이트가 상류에서 막으므로 반출 위험 아님. §7 후속으로 기록.

### 4-5. 장부 바로잡기 (ⓒ charge_mode)
- ChatbotService.cs:236·484·566 의 `charge_mode='hitpan_pool'` 하드코딩 → **실제 키 출처 기록**. 현 구조는 BYOK 단일이므로 'byok' — 단 상수 재하드코딩이 아니라 키 출처 판정 한 곳을 경유(향후 pool 실구현 시 그 자리만 바뀜).
- 기존 적재 행은 손대지 않는다(로그 불변 · 거짓 구간의 경계는 본 문서가 기록: 봉합 배포 이전 행의 'hitpan_pool' 은 전부 BYOK 였음 — [1-V] §3).

## 6. 갈래 — **1갈래** (한 사슬)
- 게이트 서비스·문 3개·마이그·화면·장부가 전부 한 판정(`IExternalAiGate`)을 공유한다. 쪼개면 반쪽 봉합(X-2 잔존) 상태가 중간에 생긴다 ⇒ 1갈래.
- 구현 순서: (1) DB-NN 마이그 + 출하 DDL → (2) IExternalAiGate + 문①②③ → (3) 화면 문구 → (4) charge_mode → (5) G-1~G-8 + CI 등록.
