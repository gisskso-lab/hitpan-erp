## [2] 🔴 인계3 의 범위 판정이 틀렸다 — 실측으로 정정

인계3 [4-B] 에 **"🟢 새 API 불필요 — 화면 배선만 하면 된다"** 라고 적었다.
착수 전 실측하니 **틀렸다.** 서버를 두 군데 손대야 한다.

### 정정 ① — 거래명세서 상세가 `delivery_item_id` 를 안 준다

[SalesService.cs:671-691](../../src/HitPan.Application/Services/SalesService.cs#L671-L691) 품목 SQL:

```
SELECT di.item_id, it.item_name, ..., di.qty, di.unit_price, ...
FROM sales_delivery_items di
```

**`di.delivery_item_id` 도 `di.warehouse_id` 도 SELECT 목록에 없다.**
[DeliveryItemDto](../../src/HitPan.Web/Models/DeliveryModels.cs#L180) 에도 두 필드가 없다.

⇒ 품목을 불러와도 **어느 판매 줄에서 왔는지 못 적는다.**
`sales_return_items.delivery_item_id` 는 컬럼·FK·DTO 가 다 있는데 **채울 값이 화면에 안 온다.**

### 정정 ② — 화면 저장 payload 에 링크가 아예 없다

[SalesReturnPage.razor.cs:181-190](../../src/HitPan.Web/Pages/Sales/SalesReturnPage.razor.cs#L181-L190) 저장 payload:

```
partnerId · returnDate · memo · returnReason · returnReasonMemo · items
items: itemId · warehouseId · qty · unitPrice · supplyAmount · vatAmount · isLoss
```

**`deliveryId` 도 `deliveryItemId` 도 없다.** 화면 코드 전체에 그 낱말이 0건이다.

⇒ 백엔드 `CreateSalesReturnAsync` 는 `@DeliveryId` 를 **정상적으로 INSERT 한다.**
받을 준비는 돼 있는데 **화면이 안 보낸다.** 지금 만드는 반품확인서는 전부 `delivery_id = NULL` 이다.

### 정정 ③ — 수정 저장하면 링크가 날아간다

[SalesService.cs:2019-2030](../../src/HitPan.Application/Services/SalesService.cs#L2019-L2030) `UpdateSalesReturnAsync` 의 UPDATE 문:

```
SET partner_id, return_date, total_amount, vat_amount, memo,
    return_reason, return_reason_memo, updated_at
```

**`delivery_id` 가 없다.** 품목 줄도 지웠다 다시 넣으므로 `delivery_item_id` 가 같이 날아간다.

⇒ 불러와서 저장(생성)까지는 링크가 남아도, **한 번 더 고쳐 저장하면 끊긴다.**
사장님이 *"당연히 반품확인서에 자동반영"* 이라 하신 그 연결이 **두 번째 저장에서 조용히 사라진다.**

> 🔴 **이것이 [[project_fixed_vs_delivered_gap]] 의 그 자리다.**
> 컬럼도 있고 DTO 도 있고 INSERT 도 있다 — **"다 있으니 잇기만 하면 된다"** 로 보인다.
> 실제로 끊긴 곳은 **전달 경로**였고, 이번에도 **끊기는 자리가 옮겨가 있었다**(생성→수정).
> [[feedback_easy_claim_needs_refutation]] — 쉽다고 판단한 순간 반증부터 돌린 결과다.

## [3] 작업 범위

### 3-1. 서버 — 거래명세서 상세에 링크 필드 추가

| 파일 | 내용 |
|---|---|
| `SalesService.cs` 품목 SQL | `di.delivery_item_id AS DeliveryItemId` · `di.warehouse_id AS WarehouseId` **추가** (헌법 #1 추가만) |
| `DeliveryModels.cs` `DeliveryItemDto` | `DeliveryItemId` · `WarehouseId` 속성 추가 |

⚠️ **SELECT 에 컬럼을 더하는 것뿐.** 기존 필드·WHERE·ORDER BY 무변경.

### 3-2. 서버 — 수정 저장이 링크를 보존

| 파일 | 내용 |
|---|---|
| `UpdateSalesReturnRequest` | `DeliveryId` 수용 |
| `UpdateSalesReturnAsync` | UPDATE 에 `delivery_id=@DeliveryId` 추가 · 품목 재삽입에 `delivery_item_id` 보존 |

### 3-3. 화면 — 반품확인서 「판매불러오기」

| 파일 | 내용 |
|---|---|
| `SalesReturnPage.razor` | 「판매불러오기」 버튼 (「목록」 옆) |
| `SalesReturnPage.razor.cs` | `LoadFromDeliveryAsync()` — `SalesListDialog` 열고 → `DeliveryService.GetAsync` → 품목 채움 |
| 저장 payload | `deliveryId` · 줄마다 `deliveryItemId` **전송** |

**채울 때 지킬 것:**
- 업체·일자는 원 거래명세서 값으로 채운다 (사용자가 고칠 수 있다)
- 단가는 **원 판매단가 그대로** — 반품은 판 값으로 돌려준다
- 로스 체크는 **전부 해제 상태로 시작** — 파손 판정은 고객사가 한다 (사장님 지시)
- 이미 입력된 줄이 있으면 **덮어쓰기 전에 묻는다** (헌법 #1)

### 3-4. 화면 — 판매목록조회 「반품」 버튼

| 파일 | 내용 |
|---|---|
| `SalesListDialog.razor` | 「반품」 버튼 추가 — 확정된 건에만 활성 |
| 동작 | 선택 1건 → 반품확인서 초안 생성 → 탭으로 열기 |

**활성 조건:** `Status == "confirmed"` 또는 `"invoiced"` 인 건 **1건만** 선택.
- `draft` 는 아직 판 것이 아니다 → 반품 대상이 아니다 (헌법 #6)
- 여러 건 동시 반품은 **이번 범위 밖** — 한 반품확인서는 한 거래명세서에 붙는다(`delivery_id` 단일 FK)

## [5] ⚠️ 결재 필요 — 반품하면 원 거래명세서는 어떻게 되나

사장님 오더에 *"거래명세서 판매목록조회에도 **반품으로 상태변경**하는 버튼"* 이라 하셨다.
이 **"상태변경"** 을 두 가지로 읽을 수 있어, 잘못 고르면 회계가 어긋난다.

| 읽기 | 뜻 | 결과 |
|---|---|---|
| **A. 표시만** | 거래명세서는 `confirmed` 그대로, 「반품있음」 만 표시 | 원 매출 남고 반품이 별도 차감 — **회계 정합** |
| **B. 상태 자체 변경** | `status = 'returned'` 로 바꿈 | 원 매출이 현황·통계에서 빠질 수 있음 — **이중차감 위험** |

🔴 **PM 판단: A 가 맞다.** 근거:
- 반품확정이 **이미** 매출·미수를 차감한다(작6 실측). B 로 원 거래까지 빼면 **두 번 빠진다**
- 사장님이 4-C 에서 *"수주서, 수주현황, 거래명세서는 해당거래에 **반품**(파손에는 파손이라고 표기)"* 이라 하셨다 — **표기**라는 말씀
- 부분반품(3개 중 1개)이면 원 거래를 통째로 `returned` 로 바꿀 수 없다

⇒ **이번 차수는 「반품」 버튼으로 반품확인서를 여는 데까지만 한다.**
   원 거래 표기는 **4-C 반품 표기**에서 함께 — 그때 부분/전체를 같이 본다.

| G3 | 줄마다 `deliveryItemId` 가 실린다 | 줄 매핑 빼면 FAIL |
| G4 | **수정 저장해도 `delivery_id` 가 남는다** | UPDATE 에서 빼면 FAIL |
| G5 | 「판매불러오기」 버튼이 있다 | 버튼 빼면 FAIL |
| G6 | 「반품」 버튼이 확정건에만 활성 | 조건 빼면 FAIL |
| G7 | 불러온 로스는 전부 해제 상태 | 기본값 바꾸면 FAIL |
| G8 | **매입 반품화면 무변경** | 매입 파일 손대면 FAIL |

🔴 **G4 가 이번 차수의 핵심.** 나머지가 다 통과해도 G4 가 없으면
*"불러왔는데 두 번째 저장에서 링크가 사라지는"* 거짓봉합이 된다.

⚠️ **게이트는 글자가 아니라 동작을 봐야 한다** ([[feedback_gate_must_test_behavior]]).
글자검사만으로 끝내지 말고, **봉합을 빼고 FAIL 을 눈으로 확인**한 뒤 커밋한다.
