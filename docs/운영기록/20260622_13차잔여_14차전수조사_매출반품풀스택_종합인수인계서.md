## 2. 개발 작업 — 13차 잔여봉합 (커밋 `812ce86`)

> 사장님 "13차 후순위 6건 봉합 후 14차" 지시. 실측 결과 후순위 분류보다 무겁게 나옴(계통 P0 + 미구현 기능 포함).

### 2-A. [계통 P0] PdfRenderService 6개 문서 PDF/메일첨부 전체 DOA
- **증상**: 견적·수주·거래명세서·세금계산서·매입발주·매입명세서 **PDF/이메일 첨부 전부 런타임 500**.
- **근본**: head/line 쿼리가 실제 DDL과 다른 컬럼명을 조회 — 계통 drift.
- **파일**: `src/HitPan.Application/Services/PdfRenderService.cs`
- **정정 매핑표** (반드시 기억):

| 쿼리가 읽던 것 | 실제 DDL |
|---|---|
| `p.business_no` | `p.biz_no` |
| `p.contact_name` | `p.manager_name` (partners엔 contact_name 없음) |
| `quotation_no/date/id` | `quote_no/quote_date/quote_id` |
| `so_no/so_date/so_id` | `order_no/order_date/order_id` |
| `total_supply` | `total_amount` (=공급가액. 부가세는 `vat_amount` 별도) |
| `total_vat` | `vat_amount` |
| `remark` | `memo` |
| `item_name`/`spec` (각 _items) | **items JOIN** (items.item_name·items.spec) |
| tax_invoices: `invoice_date·supply_amount·tax_invoice_id` | `issued_at·amount_total·invoice_id` |
| tax_invoices partner | `delivery_id → sales_deliveries.partner_id → partners` 2단 JOIN |

- **핵심 교훈**: **`total_amount` = 공급가액**, 총액 = `total_amount + vat_amount`. (SalesService 저장부에서 교차검증 완료 — 이중계산 아님)

### 2-B. [P1] SalesService 다창고 폴백 비대칭
- **파일**: `src/HitPan.Application/Services/SalesService.cs` (CreateDelivery·UpdateDelivery 2곳)
- **정정**: `ORDER BY warehouse_id` → `ORDER BY (CASE WHEN wh_code IN ('MAIN','WH-MAIN') THEN 0 ELSE 1 END), wh_code`
- **대칭 확인**: 매입3 + BOM3 + 판매2 = **8곳 전부 동일 패턴**.

### 2-C. [A — 미구현→풀스택 백엔드] 매출반품 write 경로
- **발견**: sales_returns·sales_return_items DDL은 있으나 **코드가 통째로 없음**(서비스·컨트롤러·DTO·역분개 0건).
- **신설** (매입반품 대칭):
  - DTO: `src/HitPan.Application/DTOs/Sales/CreateSalesReturnRequest.cs`, `SalesReturnDtos.cs`
  - 인터페이스: `ISalesService` 6메서드 추가
  - 서비스: `SalesService` 6메서드 (`GetSalesReturns`·`GetSalesReturnDetail`·`CreateSalesReturn`·`UpdateSalesReturn`·`ConfirmSalesReturn`·`DeleteSalesReturn`)
  - 컨트롤러: `SalesController` 5엔드포인트 (`api/sales/returns` GET/GET{id}/POST/PUT/confirm/DELETE)
- **회계**: `RecordSalesDeliveryCancelAsync` 재사용 (매출↓·부가세예수금↓·외상매출금↓)
- **재고**: `move_type='in'` (매출반품 = 고객 반납 = 재고 증가)
- **⚠️ 이때 빠진 것**: **프론트 배선** — 14차에서 P0로 적발됨.

### 2-D. [P3] status longtext→varchar(20)
- **파일**: `installer/hitpan_db_clean.sql`
- `purchase_receipts.status`·`sales_deliveries.status`: `longtext` → `varchar(20) NOT NULL DEFAULT 'draft'`
- sales_deliveries `idx_tenant_status (status(32))` prefix 잔재 → 일반 인덱스로 정리.

### 2-E. [E — 거짓봉합 2회 자가발견·정공법 재봉합] emp_no 백필
- **파일**: `src/HitPan.Application/Services/AuthService.cs` (`BackfillParentEmployeeAsync`)
- **원버그**: emp_no = Count()+1 → 비연속(0001·0003·0005) 시 0004 충돌.
- **1차 거짓봉합**: catch에서 `Remove(실패엔티티)`로 detach 의도 → 그런데 **`Repository.Remove`는 소프트삭제**(IsActive=false+Update)라 Modified로 잔류 → 다음 SaveChanges 미커밋행 UPDATE → `DbUpdateConcurrencyException` 로그인 차단(**원버그보다 악화**).
- **2차 거짓봉합**: "재조회만 하면 무해" 전제가 거짓 — 실패 Added 엔티티가 **공유 DbContext에 잔류**, 호출부 `SaveChanges(LastLoginAt)`가 좀비 재flush → 두번째 1062 → 로그인 500.
- **정공법 재봉합(3차, 통과)**:
  - `IRepository.Detach(T)` 신설 → 구현체 `Repository.cs` 1개뿐(헌법 #12 grep 확인) → `Context.Entry(entity).State = EntityState.Detached`
  - catch에서 **1062·비1062 무조건 Detach** 후 분기 (1062→재조회, 비1062→throw)
  - 호출부 2곳(login·refresh) try/catch로 백필 실패가 로그인 미차단
  - emp_no = **MAX(파싱)+1** (비연속에도 충돌 안 함)
- **최종 적대검증 통과 근거**: EF `State=Detached`가 Added 엔티티 추적 해제 + Employee 네비게이션 0개(그래프 완전성) + 6경로 전부 안전.

## 4. 개발 작업 — 14차 봉합 (미커밋, 커밋 대기)

### 4-1. [P0] 매출반품 프론트 풀 배선 (B안) ⭐ 핵심
- **사장님 결재**: "B안으로 모두 봉합" (A안=선택지 숨김은 회피라 기각, B안=근본 배선 선택)
- **변경 파일 3개**:

| 파일 | 변경 |
|---|---|
| `src/HitPan.Web/Pages/Purchase/ReturnPage.razor.cs` | `_returnType=="sales_return"`이면 `api/sales/returns`로 6경로 분기 |
| `src/HitPan.Web/Services/DeliveryService.cs` | 매출반품 4메서드 추가(`GetSalesReturnList`·`GetSalesReturnDetail`·`DeleteSalesReturn`·`ConfirmSalesReturn`) |
| `src/HitPan.Web/Components/Purchase/PurchaseReturnList.razor(.cs)` | `IsSalesReturn` 파라미터 → 목록·삭제 분기 |

- **6경로 분기 전수**(둔갑저장 잔존 0 확인):
  1. `SaveAsync` POST(신규) → basePath 분기
  2. `SaveAsync` PUT(수정) → 동일 basePath
  3. `DeleteAsync` → deletePath 분기
  4. `ConfirmReturnAsync` → 다이얼로그 문구(IN/OUT) + 확정 API 분기
  5. `LoadReturnAsync(id, isSalesReturn)` → 상세 조회 API 분기 + `_returnType` 세팅
  6. `OpenListAsync` → 목록 다이얼로그 `IsSalesReturn` 전달
- **모델 재사용**: `PurchaseReturnDetailModel`을 매출반품에도 재사용(DeliveryId 미매핑이지만 프론트가 안 읽어 무해).

### 4-2. [P1] 매출반품 return_reason NULL 폴백
- **파일**: `src/HitPan.Application/Services/SalesService.cs` (Create·Update 2곳)
- **이유**: `sales_returns.return_reason`은 **NOT NULL DEFAULT 'customer_return'**(매입반품은 NULL 허용 — 비대칭). 화면이 사유 안 보내면 NULL→1048(500).
- **봉합**: `ReturnReason = request.ReturnReason ?? "customer_return"` (DDL DEFAULT와 동일 값)

### 4-3. [P1] BOM 마이그 source_id 해시 고정폭화
- **파일**: `src/HitPan.Application/Services/MdbMigrationService.cs:1205`
- **원버그**: `sourceId = $"DOCRT-{productKey}"`, productKey=`pumName|spec`(무제한) → `bom_headers.source_id varchar(80)` 초과 → ERROR1406 → BOM이 마스터 단계(`continueOnFail:false`)에 묶여 **partners·items·accounts 마스터 전체 롤백** → 긴 품명+사양 제조 고객 마이그 전량 실패.
- **봉합**: `sourceId = $"DOCRT-{ComputeSourceHash($"bom:{productKey}")}"` → "DOCRT-"6자 + SHA256 64자 = 70자 ≤ 80.
- **멱등성 유지**: SHA256 결정적 → 같은 productKey→같은 source_id (재마이그 UPSERT 정합).
- **bom_items 영향 없음**: items는 `BomId` 직접 참조(source_id 매칭 아님).

### 4-4. [P2] 결재 docType 분리
- **파일**: `src/HitPan.Application/Services/ApprovalService.cs` `DocTypeLabels`
- **원버그**: 트리거는 `sales_return`·`purchase_return` docType 사용하는데, 라벨엔 `'return'`만 있어 결재선 설정 화면에 못 떠 → 트리거 조회 `lineCount=0` → 반품 결재 영영 미생성.
- **봉합**: `["return"]` 제거, `["sales_return"]="매출반품"`·`["purchase_return"]="매입반품"` 추가.
- **워크플로우 비차단 근거**: 트리거는 confirmed 사후 + lineCount=0이면 throw 없이 return → 재고·회계는 안 끊김(그래서 P0 아닌 P2).

### 4-5. [코스메틱] 2건
- 매출반품 원장 memo `'매출반품 (Reverse OUT)'` → `(Reverse IN)` (실제 동작은 IN)
- PurchaseReturnList NoRecords 문구 `IsSalesReturn` 분기("매출반품/매입반품 없음")

> **왜 90이 아닌 89**: 매출반품 풀 배선의 **실기기 E2E 검증 미수행**(빌드0/0+적대검증통과는 "코드가 맞다"까지, "실제 화면 저장→확정→재고IN 눈 확인"은 미완). 헌법(테스트100%=실제70~80%)대로 **실측 1회 전엔 90 못 박음**. 남은 1점은 코드가 아니라 **실기기 E2E 1회**가 채운다.
