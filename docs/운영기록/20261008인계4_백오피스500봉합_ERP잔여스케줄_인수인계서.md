### 재기동 위험 — 데이터가 아니라 **기동 거부**
🟢 출하 SQL 12개에 파괴적 구문 **0건** · `INSERT` 있는 3개(`31`·`90`·`91`)는 전부 `INSERT IGNORE`/`IF NOT EXISTS`/`WHERE … IS NULL` ⇒ **중복으로 안 터진다**(파일 직독).
🔴 다만 `SchemaMigrator.cs:122-127` 은 한 파일만 실패해도 예외를 던져 **백오피스 전체가 기동을 거부**한다(지금 도는 고객·결제 화면까지).
**재기동 전 읽기 한 줄** — 0 이면 안전:
```sql
SELECT COUNT(*) FROM landing_signups s LEFT JOIN tenants t ON t.tenant_id = s.tenant_id
 WHERE s.tenant_id IS NOT NULL AND t.tenant_id IS NULL;
```

### 🔴 3-6 실측이 설계를 뒤집었다 — 「조용한 0」

설계는 *"NULL 을 `int` 로 받으면 **500**"* 이라 적었는데 **틀렸다.** 실측하니 **Dapper 가 NULL 을 조용히 `0`** 으로 둔다.
⇒ 화면에 0 이 뜨고 **그 0 이 저장돼 기기 등록이 전부 막힌다.** **500 보다 덜 시끄럽고 더 위험하다.**
🔴 이것이 이번 사고의 **두 번째 뿌리**이고, **`G-COL-1` 은 이걸 못 본다**(아래 §4-A-3 B-7).

새 게이트는 「칸이 없다」를 문다. **아래는 그 그물을 빠져나가는 구멍**이다. 2차 과녁의 정본.

| # | 못 보는 것 | 왜 위험한가 |
|---|---|---|
| **B-1** 🔴최상 | **표 자체가 색인에 없으면 그 문장을 통째로 건너뛴다** — `unjudgeable` 로 **세기만 하고 단언이 없다** | 「칸이 없다」는 잡고 **「표가 없다」는 못 잡는다**. 다음에 표를 통째로 빠뜨리면 아무도 안 잡는다 ⇒ **`unjudgeable == 0` 단언 신설** |
| **B-2** 🔴 | **별칭을 실제로 안 가른다** — 문장에 나온 **모든 표의 칸 합집합**으로 본다 | 다중 조인에서 **엉뚱한 표의 칸**이 통과한다. 🔴 **PM 이 오늘 `t.` 를 잘못 읽은 것과 똑같은 실수**를 게이트도 한다 |
| **B-3** 🔴 | **동적 SQL 조각이 버려진다** — `^(SELECT\|INSERT\|UPDATE\|DELETE)` 로 시작하지 않으면 검사 대상 밖 | 실제로 **이번 사고 당사 컨트롤러**의 `where = "WHERE status = @Status"` 조각이 **안 검사된다** |
| **B-7** 🔴 | **NULL 가능성 축이 원리적으로 없다** | 이번 사고의 **두 번째 뿌리**(NULL ↔ 비널 `int` = 조용한 0)를 못 본다. 지금은 `G-PRICE-1` 이 한 컨트롤러만 덮는다 ⇒ **POCO 정합 게이트 신설** |
| B-4 | 대문자가 섞인 토큰은 무조건 건너뜀 | 대문자 칸은 영영 안 걸린다 |
| B-5 | `SELECT *` 는 칸 토큰 0개인데 「판정함」으로 센다 | 판정한 척하는 숫자가 된다 |
| B-6 | 파생표·서브쿼리(`FROM (SELECT…) x`)는 표·별칭 미등록 | 그 안의 칸은 안 본다 |
| B-8 | `ADD <칸>`(COLUMN 생략)·`MODIFY`·`CHANGE` 미인식 · `ALTER` 파싱이 첫 `;` 에서 끊김 | 그 방식으로 생긴 칸이 색인에서 빠진다 |

⚠️ **추가 발견**: `G-MIG-1`(2회 적재)의 2회차 목록에 **`00` 이 없다.** 지금 `00` 은 `CREATE TABLE IF NOT EXISTS` 28개뿐이라 안전하지만(PM·[4] 직독 확인), **다음에 누가 `00` 에 `INSERT` 한 줄 넣는 날 아무도 안 잡는다.**
⚠️ `G-MIG-1` 은 **`43`·`44` 축을 못 문다**(구현자 자기신고 · [4] 확인). `00` 이 같은 커밋에 같은 것을 만들어 1회차부터 no-op 이라 「그 게이트만 FAIL」이 성립하지 않는다. **43·44 의 2회 적재 안전을 실제로 보증하는 것은 게이트가 아니라 「전 문장 `IF NOT EXISTS` · FK·INSERT 0」이라는 문장 모양**이다 — 사람이 지켜야 한다.
#### 4-A-4 아직 아무도 확인 못 한 것

- 🔴 **운영 DB 의 실제 표·컬럼 모양** — 모든 판정의 분기점인데 **아무도 못 봤다**(#39). 작16 은 **그걸 몰라도 맞게** 설계했지만, 확인되면 더 좁힐 수 있다.
- ⚠️ 운영에 **살아 있는 프로모션 데이터**가 있나(사장님 확인사항 ⑴).

| 1 | **배포가 SQL 을 한 번도 안 실었다** | 「스위치만 켜면 된다」는 처방이 **무효**였다. 적재기는 폴더가 없으면 **예외 없이 조용히 통과**한다 ⇒ **「고쳤다」와 「갔다」 사이에 배포 경로가 있다.** 로그에 `.sql` 0줄을 보고서야 알았다 |
| 2 | **코드가 읽는 칸이 표에 있는지 아무도 안 봤다** | 헌법 #13 이 **코드로 집행된 적이 없었다**. 그래서 화면 둘이 **처음부터 500** 이었는데 아무도 몰랐다 ⇒ `G-COL-1` 신설(1차) |
| 3 | **같은 뜻의 표가 두 벌** | `promotions` / `promotions_legacy` 가 공존했고 코드가 **섞어 읽었다**. 파일 자신이 주석으로 *"통합은 별건 todo"* 라 경고했는데 **그 별건이 500 으로 터졌다** ⇒ 「나중에」라고 적어 둔 todo 는 **언젠가 사고로 돌아온다** |
| 4 | 🔴 **PM 이 컬럼을 세다가 두 표를 합쳐 셌다** | 검색 범위가 `promotions` 와 `promotions_legacy` 를 **한 덩어리로** 긁어 「전부 있다」고 **틀린 보고**를 했다. [1-V] 가 반증했다 ⇒ **범위를 긋는 검색은 끝 경계를 눈으로 확인**하라 |
| 5 | 🔴 **PM 이 별칭을 잘못 읽었다** | SQL 안 `t.` 를 `bo_cs_tickets` 로 봤는데 실제로는 `tenants` 였다 ⇒ **별칭 선언을 먼저 보고** 칸을 세라. **게이트도 같은 실수를 한다**(§4-A-5 B-2) |
| 6 | 🔴 **PM 이 파일 하나를 빼고 셌다** | `promised_at` 이 없다고 봤는데 `41` 이 `ADD COLUMN` 으로 더하고 있었다 ⇒ **한 표의 칸 = 생성 파일 + 그 뒤 모든 `ADD COLUMN` 파일** |
| 7 | **설계가 「500 이 난다」고 했는데 실측은 「조용한 0」** | NULL 을 `int` 로 받아도 터지지 않고 **0 이 저장된다** ⇒ **덜 시끄러운 쪽이 더 위험하다.** 설계의 「~하면 터진다」도 **실측 전엔 가설**이다 |
