## 0. ⭐ 사장님 오더 (원문 그대로 — 이 문서의 원본)

> **Q5** *(직책에 재직자가 여럿일 때 누구를 결재자로?)* → *"**권한설정 한 자**"*
>
> **축 정정** → *"결재라인에 그래서 **pk를 직책으로 두는것이 아니라 사원이름이나 계정으로** 두는게 맞지"*
>

**이 아래 모든 내용은 위 오더를 명문화한 것이다.** 오더에 없던 요구를 넣지 않는다.

## 1. 오더를 이렇게 이해했다 (명문화)

```
결재선 = 사람으로 짠다 (직책 아님)
  최종 단계   →  대표이사        고정
  그 외 단계  →  APPROVAL 권한 가진 자
```

- **안 하면 무슨 일이 나는가**: 권한 없는 사람이 결재선에 들어가면
  그 사람은 결재함에 **진입 자체가 막혀**(`[RequirePermission("APPROVAL","view")]`)
  ⇒ **그 문서가 영영 안 간다.** 아무도 모른 채 일이 선다.
- **실측 근거**(헌법 #32): 설6 §1 참조. 요약:
  - 🟢 `APPROVAL` 권한 **이미 있음** + `EnforcedMenus` **등록됨** ⇒ 신규 0
  - 🟢 대표 = **`is_parent=1`** (T-004 실측: `position` 이 `null` 인데도 대표)
  - 🟢 `approval_doc_lines` 가 **이미 `approver_id`(사원)** 로 돈다
  - 🟢 직책 자동 등재 **이미 있음** — `EnsurePositionExistsAsync:275`

## 2. 무엇을 하는가 (범위)

### [A] 최종 단계 = 대표이사 보장

- [ ] 결재선 마지막 단계가 대표가 아니면 **결재설정에서 경고**
- [ ] 대표 판정은 🔴 **`is_parent = 1`** — `position` 으로 판정 **금지**(실측 `null`)
- [ ] 대표가 여럿이면 **고객사가 고른다**(#11)
- [ ] 🔴 **자동 배치하지 않는다** — 경고만. 자동은 반자동 원칙 위반

### [B] 그 외 단계 = `APPROVAL` 권한자만

- [ ] 결재설정 결재자 목록에 **`APPROVAL` 권한자만** 보이게
- [ ] 🔴 **새 권한 만들지 마라** — `APPROVAL` 이 이미 있다
- [ ] 🔴 `EnforcedMenus` 손대지 마라 — 이미 등록돼 있다

### [C] 권한이 나중에 꺼지면 알린다

- [ ] 결재선에 있는 사람의 `APPROVAL` 권한이 꺼지면 **알린다**
- [ ] 🟢 **오늘 확정한 공석 알림과 같은 틀** — 문구·자리 재사용
      *"결재자가 권한이 없습니다. 변경하시겠습니까? 유지하시겠습니까?"*
      **[Y]** → `/settings/approval` **링크이동** · **[N]** → 상태유지
- [ ] 🟢 알림 자리 **기존 것** — `Dashboard.razor:216` · `ChatPage.razor:166`

### [D] 직책관리 메뉴 내림

- [ ] 사이드바에서 **직급 관리 메뉴 제거**
- [ ] 🔴 **표는 살린다** — `positions` 를 3곳이 쓴다(프로비저너 시드 등 · #37)
- [ ] 🔴 **주소는 리다이렉트로 살린다** — 404 금지(8/13 원칙)
- [ ] 🟢 직책 등재는 **그대로 자동**(`EnsurePositionExistsAsync` 무변경)

### 하지 않는 것 (명시)

- 🔴 **`position_id` DDL 추가** — PM v1 안, 사장님이 물리심
- 🔴 **직책→사람 펼치는 로직** — 결재선이 사람이라 불필요
- 🔴 **`approval_line_steps` 표 삭제** — #37(안 읽힌다 ≠ 잔재)
- 🔴 **대결 손대기** — 이미 돈다
- 🔴 **자동 승계·자동 배치** — 100% 자동화 금지(반자동 원칙)
- ⏸ 직권·전결 → **G2** · 사직서·계약서 → **G3**

| **Q2** | 결재자 목록에 누가 보이나? | 권한자만 | 🔴 **부모계정, 그리고 권한자만** — 권고 정정 |

### 🔴 Q2 — PM 권고가 틀렸고 사장님이 잡으셨다

PM 은 *"권한자만"* 이라 권고했다. 그대로 짰으면 **대표가 결재자 목록에서 사라진다.**

**실측 근거** — `PermissionService.HasPermissionAsync` Layer 0:

```
// Layer 0 — 부모계정(tenant_admin)은 항상 전권 (락아웃 방지)
if (userId == _currentTenant.UserId &&
    _currentTenant.AccountType == "tenant_admin")
{
    return true;
}
```

부모계정은 `user_permissions` 표를 **아예 안 본다.** 여기서 바로 `return true` 다.

⇒ 목록을 `user_permissions` 에서 APPROVAL 가진 사람으로 뽑으면
   **대표는 그 표에 줄이 없어서 안 잡힌다.**
⇒ 그런데 [A] 의 규칙이 *"최종 단계 = 대표이사"* 다.
⇒ **결재선 마지막에 반드시 넣어야 할 사람을 목록에서 빼버리는 화면**이 될 뻔했다.
   G1 이 자기 자신과 충돌하는 자리였다.

**PM 오판의 종류**: 있는 구조(Layer 0 바이패스)를 안 보고 권고부터 냈다.
8/22 인수인계서 §4 에 적은 오판 6건과 **같은 병**이다.

⇒ 조회 조건은 **`is_parent = 1` OR `APPROVAL` 권한자** 두 갈래다.---
