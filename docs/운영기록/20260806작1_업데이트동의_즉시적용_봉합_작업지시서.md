## 0. PM 자기 적발 — 무엇을 잘못 보고했나

2026-08-06 10:57, PM 은 팝업이 뜬 것을 근거로 **"오더 ① 종단 실증"** 이라고 보고했다.
사장님이 즉시 바로잡으셨다: *"팝업이 뜨는게 중요한게 아니라 뜬 팝업으로 옵션을 선택할때, 제대로 동작하느냐가 중요한거지."*

**사장님이 맞다.** 실측된 것은 여기까지다:

## 1. 진범 — 영업시간 게이트가 '수동 동의'까지 막는다

`Worker.cs:396-402` (ConsumeConsentForMajorAsync)

```csharp
case ConsentDecision.Approve:
    // Major 는 동의했어도 영업시간엔 미룬다
    if (_update.IsBusinessHour(DateTime.Now))
    {
        _logger.LogInformation("... 영업시간이라 적용 보류(영업시간 외 자동 적용)");
        return;   // ← 펜딩 유지, 아무 일도 안 함
    }
```

`UpdateOrchestrator.cs:982-983`
```csharp
public bool IsBusinessHour(DateTime now)
    => now.Hour >= 9 && now.Hour < 18 && now.DayOfWeek != Saturday && != Sunday;
```

실측: 목요일 10:57 → 영업시간 → **[예] 를 눌러도 18시까지 보류.**
화면에는 진행 표시도, 안내도 없다. 팝업만 사라진다 ⇒ **고객은 고장으로 인식한다.**

### 1-1. 왜 이 설계가 틀렸나

영업시간 보호 자체는 옳다 — **업무 중 프로그램이 꺼지면 안 된다.**
그러나 그것은 **자동 적용(Normal 채널)** 에 필요한 것이다.

**Major 는 고객이 직접 "지금 하겠습니까?" 에 [예] 라고 답한 건이다.**
본인이 명시적으로 선택한 행위를 8시간 미루면서 **아무 안내도 하지 않는 것**은
- 헌법 #24 (가르침 의무 — 가르치지 않고 넘기는 건 거짓말)
- 헌법 #25 (쉽게 — "이 화면, 처음 보는 사람이 혼자 쓸 수 있냐")
양쪽에 어긋난다. 고객은 왜 안 되는지 알 방법이 없다.

### 1-2. 사장님 용도(테스트 배포)와의 충돌
사장님 오더 ②는 *"수정건이 있을시 바로 수정해서 다시 띄운다"* 다.
낮에 [예] 를 눌러도 8시간 뒤 적용이면 **개발 사이클 자체가 안 돈다.**

## 2. 봉합 설계

### 2-1. 원칙
| # | 원칙 |
|---|---|
| 1 | **고객이 직접 [예] 를 누른 건은 즉시 적용한다** — 본인 의사가 영업시간 규칙보다 앞선다 |
| 2 | **자동 적용(Normal)의 야간 창은 그대로 둔다** — 묻지 않고 바꾸는 것은 계속 보호 |
| 3 | 삭제 아닌 추가 — `IsBusinessHour` 는 남긴다(Normal 이 계속 쓴다). 헌법 #1 |
| 4 | 팝업 문구가 사실과 일치해야 한다 — "지금 진행" 이라고 물었으면 지금 해야 한다 |

### 2-2. 변경
`Worker.cs` `ConsumeConsentForMajorAsync` 의 `Approve` 분기에서
**영업시간 보류를 제거**하고 바로 적용에 진입한다.

근거: 이 분기는 `ConsentDecision.Approve` — 즉 **고객이 [예] 를 누른 경우에만** 도달한다.
[나중에]는 `Reject` 로 별도 처리되고, 자동 적용은 이 함수를 타지 않는다.

⚠️ **`IsBusinessHour` 자체는 삭제하지 않는다.** Normal 채널 판정에 계속 쓰인다.

### 2-3. 하지 않을 것
| 항목 | 사유 |
|---|---|
| `IsNightWindow`(Normal) 변경 | 자동 적용은 야간 유지가 옳다 |
| `IsBusinessHour` 삭제 | Normal 이 쓴다(헌법 #1) |
| 팝업 UI 에 진행률 표시 추가 | 별건. 이번 범위는 "눌렀을 때 되게" |
