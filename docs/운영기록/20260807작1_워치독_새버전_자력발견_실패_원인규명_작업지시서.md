## 0. 한 줄

**워치독이 새 버전을 스스로 발견하지 못했다. 사람이 재시작한 뒤에야 발견했다.**
고객 PC 에는 재시작할 사람이 없다.

## 1. 왜 이 지시서가 나왔나

2026-08-07, 사장님이 백지환경(Windows Sandbox, TEST1)에서 워치독 자기교체(C-1) 채증을 실행했다.
**C-1 자체는 통과**했다. 그런데 그 과정에서 통과와 무관한 사실이 하나 드러났다.

### 1-1. 실측 경과 (원본 — 가공 없음)

| 시각 | 사건 | `local_update_status.latest_version` |
|---|---|---|
| 2026-08-06 19:30:01 | 워치독이 기록한 발견값 | **1.2.54** |
| — | 사장님이 조회를 **13회 반복** — 값이 계속 1.2.54 | 1.2.54 (변화 없음) |
| — | 사장님이 `sc.exe stop HitPanWatchdog` → `sc.exe start HitPanWatchdog` **직접 실행** | — |
| 2026-08-06 19:34:27 | 재시작 직후 조회 | **1.2.55** |

조회에 사용된 명령(사장님 실행 원본):
```
& "C:\Program Files\MariaDB 11.4\bin\mariadb.exe" -u hitpan_t001 "-p<생략>" \
  -e "SELECT latest_version, discovered_at FROM local_update_status;" hitpan_erp_t001
```

### 1-2. 이 사실의 무게

히트판의 자동 업데이트는 **"고객 손 0번"**을 전제로 설계되어 있다(헌법 #30 — 고객 PC 자가 회복, 본사 의존 0).
그런데 이번 실측에서는 **사람이 서비스를 재시작해야** 새 버전이 잡혔다.

- 사장님은 히트판을 만든 사람이라 재시작을 떠올렸다.
- **고객은 떠올릴 수 없다.** 서비스라는 개념 자체를 모른다.
- 즉 고객 PC 에서 같은 일이 나면 **업데이트가 영영 안 잡힌 채 방치**된다.

이것은 "업데이트가 실패한다"보다 조용하고 나쁘다.
실패는 로그에 남고 재시도가 돈다. **발견 자체를 못 하면 아무 일도 일어나지 않는다.**

## 2. 원인 규명 결과 — 🔴 **유력 확정** (2026-08-07 추가)

> **최초 발행 시점에는 "원인 미상"이었다.** 같은 날 코드 정독 + 추가 채증으로 원인이 좁혀졌다.
> 아래는 **유력**이며, 확정은 §2-4 의 잔여 반증을 거친 뒤에 한다.

### 2-1. 진범 후보 — `_lastUpdateCheckDate` 는 **메모리 변수**다

`src/HitPan.Watchdog/Worker.cs:324-326`

```csharp
var today = DateOnly.FromDateTime(DateTime.Now);
if (_lastUpdateCheckDate == today)
    return;                    // ← 로그도 남기지 않고 그냥 나간다
```

`Worker.cs:334`
```csharp
// 평가 자체는 하루 1회만(성공·새버전없음 모두). manifest 조회 실패는 다음날 재시도.
_lastUpdateCheckDate = today;
```

**새 버전 확인은 하루에 한 번뿐이고, 그 사실을 기억하는 변수는 디스크가 아니라 메모리에 있다.**

### 2-2. 실측이 이것과 정확히 맞아떨어진다

| 시각 | 무슨 일이 있었나 | 근거 |
|---|---|---|
| 19:30 이전 | 그날 1회 확인 완료 → **1.2.54** 발견, `_lastUpdateCheckDate = 오늘` | `local_update_status` 19:30:01 |
| 그 뒤 | 1.2.55 가 게시됨 | — |
| 19:30~19:34 | 사장님 13회 조회 — 값 불변. **워치독은 매 루프 `return` 만 했다** | §2-3 로그 침묵 |
| — | `sc stop` → `sc start` = **프로세스 재시작 = 메모리 초기화** | 사장님 실행 |
| 19:34:27 | 게이트가 풀려 재조회 → **1.2.55** 발견 | `local_update_status` |

**재시작이 통한 이유는 무언가를 고쳐서가 아니라, 메모리가 날아가 게이트가 풀렸기 때문이다.**

### 2-3. 로그의 침묵이 증거다 (2026-08-07 추가 채증)

샌드박스 Windows 이벤트 기록(`Application` / `HitPanWatchdog`)을 조회한 결과:

| 조회 | 결과 |
|---|---|
| 전체 기록 | **500건** (Information 493 · Warning 7) |
| **19:25 ~ 19:40 구간** | **0건** |
| `[Update` / `manifest` / `W4-` / `1.2.5` 키워드 | **0건** |

**기록이 500건이나 있는데 업데이트 관련은 한 줄도 없다.**
한글 깨짐 탓도 아니다 — 검색어가 영문·숫자라 깨질 수 없다.

즉 워치독은 **새 버전을 못 찾은 게 아니라, 찾으려는 시도조차 하지 않았다.**
`:326` 의 `return` 은 아무것도 기록하지 않으므로 침묵이 남는다.
**이 침묵이 곧 그 경로를 탔다는 증거다.**

### 2-4. 3자 정합

| 근거 | 내용 | 상호 모순 |
|---|---|---|
| 코드 | 하루 1회 게이트 + 조용한 `return` | 없음 |
| 로그 | 문제 구간 침묵 · 업데이트 키워드 0건 | 없음 |
| 재시작 효과 | 메모리 초기화 → 즉시 발견 | 없음 |

셋이 서로 모순 없이 같은 지점을 가리킨다.

### 2-5. 이것은 **같은 벽에 다시 부딪힌 것**이다

`4cc5842 fix(업데이트/P0): 재배포 사이클이 하루 1회에 묶여 있던 문제 — [3-V] 병렬검증 적발`

이 봉합의 주석(`Worker.cs:298-300`)이 이미 같은 현상을 적어 두었다:

> *"사장님이 [나중에] 를 눌러 펜딩이 비워져도 **그날 안에는 새 버전을 다시 발견하지 못한다.**
> 수정 → 재게시 → 재확인 사이클이 하루 1회로 묶였다."*

**그런데 그 봉합은 "동의 팝업이 떴다가 해소된 경우"에만 게이트를 푼다**(`:302-308`).
이번 사장님 사례는 **팝업이 뜨기 전, 발견 단계**여서 그 경로에 걸리지 않았다.

즉 **같은 진범의 다른 얼굴**이다. 개발팀 코드리뷰서 P1-1(거부 후 재무장 고리)과도 같은 코드 영역이다.

최초 발행 시 세웠던 가설 중 다음은 위 증거로 사실상 배제되었다.

### 2-7. 🚫 그래도 지금 코드를 고치지 않는다

원인이 유력해졌을 뿐 **확정이 아니다.** 그리고 봉합 방향은 PM 이 정할 사안이 아니다.

- 확인 주기를 짧게 할 것인가
- 게시 신호를 받으면 즉시 확인할 것인가
- 게이트를 디스크에 저장할 것인가(재시작해도 유지 — 지금과 **반대 방향**)

셋은 고객 PC 부담·본사 서버 부하·개발 사이클 속도가 각각 다르다.
**설계팀 검토 → 결재 후 별도 작업지시서**로 간다(헌법 #29·#33·#42).

### 4-1. 잔여 반증 (확정 전 해야 할 것)

**증거 회수 상태**: 샌드박스에서 이벤트 기록 500건을 파일로 회수했으나
**샌드박스 밖으로 꺼내지 못했다**(격리 정책). 콘솔 조회 결과만 확보되어 있다(§2-3).

따라서 다음은 **아직 안 했다**:

- [ ] 500건 전수를 시계열로 훑어 **다른 원인이 섞여 있지 않은지** 확인
- [ ] Warning 7건의 내용 확인 — 이 중 업데이트 관련이 있는지
- [ ] 19:30 이전에 "1.2.54 발견" 기록이 실제로 있는지 (있으면 §2-2 표가 완성된다)

**단, 이것들이 결론을 뒤집을 가능성은 낮다.** 코드·로그침묵·재시작효과 3자가 이미 정합하기 때문이다(§2-4).
다음 차수 샌드박스에서 회수 방법을 바꿔(공유폴더 마운트 등) 확보한다.

### 4-2. 재현 절차 (다음 차수용)

1. 워치독이 그날 1회 확인을 마친 상태를 만든다 (기동 후 1루프 경과)
2. 새 버전을 게시한다
3. **재시작하지 않고** `local_update_status` 를 관찰한다 → 갱신되지 않아야 한다(현상 재현)
4. `sc stop/start` → 다음 루프에서 갱신되면 원인 확정

**주의**: 3번에서 **날짜가 바뀌면** 자동으로 풀리므로, 자정을 넘기지 않는 구간에서 해야 한다.

**4번 주의**: 이 지시서는 규명까지다. **봉합 구현은 별도 작업지시서 + 결재 후**에 한다(헌법 #29·#33·#42).

## 5. 등급 판단 — 🟡 **P1** (2026-08-07 조정)

최초 발행 시 **P0 후보**로 두었고, 원인 규명 후 **P1** 으로 조정한다.

### 5-1. P0 가 아닌 이유

**날짜가 바뀌면 게이트가 저절로 풀린다**(`Worker.cs:324` — `DateOnly.FromDateTime(DateTime.Now)`).
영구 고립이 아니고 고객 자료도 안전하다. 최악이 "하루 늦게 받는다"이다.

### 5-2. 그래도 가볍지 않은 이유

| 관점 | 영향 |
|---|---|
| 고객 | 새 버전을 **최대 24시간** 못 받는다. 그동안 히트판은 **정상으로 보인다** — 고객도 본사도 모른다 |
| 긴급 봉합 | P0 를 급히 고쳐 올려도 **그날 안에 안 내려간다.** 긴급성이 무의미해진다 |
| 개발 사이클 | **하루 1회로 묶인다.** 아래 §5-3 |
| 재발 | 같은 벽에 두 번째다(§2-5). 세 번째가 없다는 보장이 없다 |

### 5-3. 사장님 오더와의 관계 (2026-08-07)

> 사장님: *"워치독, 업데이트 종단이 구현되면 그 후부터는 수정·보완작업이 쉬워질거야.
> 재설치 없이 **코드수정 → 업데이트 → 실측** 이 세 단계만 하면 되거든."*

**이 항목이 그 3단계를 막고 있다.** 실제로는 이렇게 된다:

```
코드수정 → 게시 → [최대 24시간 대기] → 실측
```

오늘 사장님이 `sc start` 를 직접 치신 것이 그 증거다.
**즉 이 건은 고객 영향보다 우리 개발 속도에서 더 무겁다.**
등급은 P1 이나 **우선순위는 높게** 둔다.

### 5-4. 등급 재조정 조건

- **P0 로 올라갈 경우**: 날짜 경계에서도 안 풀리는 경로가 발견되거나, 다른 게이트와 겹쳐 영구 고립이 성립할 때
- **P2 로 내려갈 경우**: 실사용에서 하루 지연이 문제되지 않음이 확인될 때(현재로선 개발 사이클 때문에 불가)

## 6. 함께 처리할 부수 항목 2건

채증 과정에서 같이 드러난 것으로, 이 건과 별개지만 같은 실측에서 나왔다.

### 6-1. 로그 한글 깨짐 (개발팀)
콘솔 출력에서 `?좊쾭???뚯튂?낆쓣` 형태로 깨진다. 원문은 "워치독 설치본을 watchdog.handoff 로 확보했습니다".
**기능 결함은 아니나** 상담원이 원격지원 중 로그를 읽어야 할 때 판독 불가가 된다.

### 6-2. 예약작업 조회 접근 거부 (CS·개발팀)
```
Get-ScheduledTask : Cannot connect to CIM server. 액세스가 거부되었습니다.
```
관리자 권한인데도 실패. 기지 사고(`ae18dc0` — CIM 회피)이나 **CS 진단 절차에는 미반영**이었다.
CS 매뉴얼은 `schtasks /query` 로 교체하도록 이관 완료.
제품 코드 측에 추가 조치가 필요한지는 개발팀 판단.
