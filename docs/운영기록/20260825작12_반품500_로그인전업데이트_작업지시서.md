## 1. 🔴 ④ 반품 500 — 작10 은 **읽는 자리만 막고 쓰는 자리를 안 막았다**

### 원인

작10 은 *"확정 시 500"* 을 `ConfirmSalesReturnAsync` **안으로 좁혀 읽고**, 확정·취소의 **SELECT 2곳**만 폴백을 걸었다.
그런데 사용자는 확정 버튼을 누르기 **전에** 상세조회·저장을 먼저 지나간다.

| # | 자리 | SQL | 엔드포인트 | 작10 |
|---|---|---|---|---|
| ① | `SalesService.cs:1923` | `sri.is_loss AS IsLoss` (상세조회) | `GET returns/{id}` | ❌ **try/catch 자체가 없었다** |
| ② | `SalesService.cs:1982` | `INSERT … is_loss)` (생성) | `POST returns` | ❌ |
| ③ | `SalesService.cs:2054` | `INSERT … is_loss)` (수정) | `PUT returns/{id}` | ❌ |
| ④ | 확정 SELECT | 폴백 있음 | `POST …/confirm` | ✅ |
| ⑤ | 취소 SELECT | 폴백 있음 | `POST …/cancel` | ✅ |

⇒ 마이그(DB-108) 안 들어간 DB 에서 문서를 **여는 순간**·**저장하는 순간** `1054` 로 죽었다.

### 증상 모양 대조 (500 인 이유)

`GlobalExceptionMiddleware` 분기:

| 예외 | HTTP |
|---|---|
| `InvalidOperationException` | 400 |
| `MySqlException` **1451/1452**(FK) | 409 |
| **그 외 전부 (1054 포함)** | **500** |

`1054` 는 FK 필터도 400 필터도 통과 못 하고 마지막 `catch(Exception)` → **정확히 500**.
🔴 **증상의 모양이 맞다** — 사장님이 받으신 것과 같다.

### 🔴 대조 실험 (같은 DB, 같은 조건)

```
봉합 전 SQL : SELECT sri.is_loss …   → ERROR 1054  (= 500)
봉합 후 SQL : SELECT 0 AS IsLoss …   → 정상 반환
봉합 전 INSERT (is_loss 포함)         → ERROR 1054  (= 500)
봉합 후 INSERT (is_loss 제외)         → 1054 사라짐
```

재현 조건은 실측으로 만들었다 — `is_loss` 컬럼을 지우고 `schema_migrations` 에 DB-108 을 "적용됨"으로 표시(= 사장님 DB 와 동일: **마이그는 적용됐다는데 컬럼은 없다**).

### 봉합

- **5개 경로 전부**에 `HasSalesReturnLossColumnAsync` 대칭 적용 (작7 의 *"생성은 넣고 수정은 안 넣던 비대칭"* 재발 방지)
- 컨트롤러 `1054/1146` catch 를 **조회·저장·확정·취소 5곳** 으로 확장 — 사람 말로 안내(개발용어 금지)

⚠️ **폴백은 마이그 대체가 아니다.** 근본은 DB-108 적용이고, 폴백은 마이그가 늦게 온 DB 에서도 **흐름을 안 끊기** 위한 것이다(헌법 #20).

### 🔴 덤 — 인계5 의 "미규명" 이 풀렸다

실측 중 `schema_migrations` 를 직접 봤다:

```
DB-105  clean-ddl   2026-08-20 18:16
DB-106  1.2.40.0    2026-08-25 16:24   ← 내가 기동한 순간
DB-107  1.2.40.0    2026-08-25 16:24
DB-108  1.2.40.0    2026-08-25 16:24
```

⇒ **DB-106·107·108 은 그 전까지 안 들어가 있었다.** 기동해야 들어간다.
즉 *"게시했다 ≠ 고객 DB 에 적용됐다"* — **API 가 재기동돼야** 마이그가 돈다.
🔴 인계5 에 *"DB-108 이 왜 안 들어갔는지 모른다"* 고 남긴 자리의 답이다.

## 2. 🔴 ① 로그인 전 업데이트 — **탈출구가 그려져만 있고 막혀 있었다**

### 사장님 오더

> ① *"설계대로라면 **로그인 전에 업데이트를 먼저 받을 수 있도록** 하자고 해서 이렇게 된거 같은데, 그럼 **그렇게 구현이 되야지**"*
> ② *"**수동업데이트로 받을 수 있도록 로그인 아래에 「최신버젼업데이트」 라는 버튼**을 만들어."*

### 🔴 실측 — 조회는 되는데 실행이 401 이었다

```
GET  update-status-local   → 200
POST update-consent-local  → 401   ← loopback 인데도!
```

작10 이 `TenantMiddleware` 면제에 **조회(GET)만 넣고 실행(POST)을 빠뜨렸다.**
⇒ 「지금 업데이트」 버튼은 **배포 이후 한 번도 눌린 적이 없다.**
안내는 떴는데 눌러도 아무 일이 안 났다. **터널에서도, 로컬에서도 안 됐다.**

### 사장님 결재 — **B안**

> *"1. 터널에서 실행까지 허용할 것인가 … **사장소견 = B안으로**"*
> *"2. 로그인 전에 강제 업데이트 창구를 만드는 이유는 **로그인에서 갇히는 경우를 실제 경험**했음.
>     **테스트 계정이라 망정이지 고객사였으면 대형사고**"*

🔴 **갇힌 사람은 터널로 들어온다.** loopback 제한은 정작 **구조받아야 할 그 사람**을 막고 있었다.

### 봉합 (B안 = 표시·실행 모두 터널 허용 + 멱등 + rate limit)

| # | 무엇 | 어디 |
|---|---|---|
| 1 | 실행 경로 인증 면제 | `TenantMiddleware` — `/api/auth` 통째 개방 금지, **이 주소 하나만** |
| 2 | 터널 404 차단 제거(조회·실행) | `AuthController` |
| 3 | **멱등** — 같은 버전 재승인은 새 INSERT 안 함 | `AuthController` (DoS 1차 방어) |
| 4 | **전용 rate limit** 5분 5회 | `RateLimitMiddleware` (2차 방어) |
| 5 | 미인증 원격엔 **필드 축소** | `UpdateChannel`·`ConsentMessage` 는 loopback 만 |
| 6 | 경로(터널/로컬) 로그 | 누가 어디서 눌렀는지 |

**남은 위험은 DoS 뿐**이다 — 가짜 버전 설치는 불가능하다(워치односн 적재본 대조 + 서명·SHA256 검증). 그 DoS 를 멱등이 막는다.

### 🔴 종단 실측 (새 빌드로 API 기동)

| 경로 | 종전 | 봉합 후 |
|---|---|---|
| 로컬 POST 실행 | **401** | **400**(로직 도달) |
| 터널 GET 조회 | **404** | **200** |
| 터널 POST 실행 | **404** | **400**(로직 도달) |
| 5회 초과 연타 | — | **429** ✅ |

*(400 = "준비된 업데이트가 없습니다" — 이 환경엔 적재된 새 버전이 없다. **미들웨어를 통과해 컨트롤러 로직까지 갔다**는 뜻이고, 그게 이번에 고친 것이다.)*

### 「최신버젼업데이트」 버튼 (사장님이 그린 순서)

```
-아이디-
-비밀번호-
-로그인(버튼)-
-최신업데이트(버튼)-   ← 배너 대체가 아니라 병행
```

🔴 **상시 노출**이다. 종전 배너는 `_updateAvailable` 일 때만 떠서, 조회가 실패하면(터널 404) **화면에 탈출구가 하나도 안 보였다.** 이 버튼은 항상 있고 문구만 바뀐다:

| 상태 | 문구 |
|---|---|
| 새 버전 있음 | 「최신버젼업데이트 (1.3.15)」 |
| 최신 | 「최신버젼업데이트」 + *현재 버전 1.3.14 — 최신입니다* |
| 조회 실패 | 「최신버젼업데이트 **(확인 실패 — 다시 시도)**」 |

덤으로 고친 것: `_updateStarting` 이 성공 후 복원 안 돼 버튼이 *"준비 중…"* 으로 굳던 것 · *"잠시 후"* → **"1분 이내"**(워치독 폴링 60초라 그 사이 고장으로 오해).
