## 3. 🔴 가장 뼈아픈 것 — 우리가 예언하고 우리가 재발시켰다

`SignupsAdminController.cs` 7/16 주석 원문:

> *"종전엔 이 메일 본문에 1.2.28 이 세 곳에 손으로 적혀 있었다. 실배포가 1.2.33 으로
> 올라가는 동안 이 값은 그대로 남아, 가입 승인 메일을 받은 고객이 1.2.28 을 설치했다.
> **버전을 코드에 적는 한 같은 사고가 반복되므로**, 배포 때 바뀌는 값은 설정에서 읽는다."*

**코드 → 설정으로 옮겼을 뿐, 여전히 사람이 손으로 적는 값이었다.**
진짜 원인은 "어디에 적혀 있느냐"가 아니라 **"사람이 옮겨 적어야 하느냐"**였다.

| | 1차 사고 (7/16) | 이번 사고 (8/02) |
|---|---|---|
| 메일 | 1.2.28 (코드) | 1.2.33 (설정) |
| 실배포 | 1.2.33 | 1.2.46 |
| 증상 | 옛 EXE 설치 → 로그인 500 | **404 → 설치 불가** |
| 원인 | 손으로 적음 | **손으로 적음 (동일)** |

**교훈: "설정으로 뺐다"는 봉합이 아니다. 사람 손이 남아 있으면 같은 사고가 난다.**

## 4. 봉합 (PR #34)

### 4-1. 진범 — manifest 단일 진실원으로 통일

랜딩은 **2026-07-21 사장님 결재**로 이미 전환돼 있었다:
> *"랜딩은 무조건 최신 설치파일"* (`DownloadPage.razor:126`)

**메일만 그 봉합에서 빠져 있었다.** 같은 축으로 통일했다.

```
manifest(updates.hitpan.kr/manifest.json) → 설정값 → null(미발송)
```

manifest 는 **게시와 동시에 갱신**되므로 사람이 옮겨 적는 단계가 사라진다.
⇒ 같은 사고가 **구조적으로 불가능**해진다. 이게 3번 교훈의 유일한 해법이다.

폴백 설정값도 1.2.33 → 1.2.46 으로 정정(manifest 가 죽어도 404 로 안 떨어지게).

### 4-2. 함께 잡은 P0 2건 (조사 중 발견)

| # | 내용 |
|---|---|
| **인가 부재** | `SignupsAdminController` 가 `[Authorize]` 단독 = "JWT 만 있으면 누구나". 백오피스 JWT 는 **대리점에도 발급**된다. 남의 가입 승인·시리얼 발급·평문 시리얼 탈취가 가능했다. 2026-06-11 봉합 때 Pricing·Promotions 엔 붙고 **이것만 빠짐** → `[Authorize(Policy="PlatformAdmin")]` |
| **채번 결함** | `tenant_code` 가 `COUNT(*)+1`. 하나 지우면 번호가 되돌아가 다음 가입이 UNIQUE 위반으로 죽는다. **삭제 기능의 선행 조건** → `MAX+1` |

### 4-3. 사장님 요청 — 삭제 기능

`DELETE /api/admin/signups/{id}` + 화면 [삭제] 버튼(상태 무관).
상세는 PR #34 / 커밋 `ff3ee8d`.

## 7. 교훈

1. **"설정으로 뺐다"는 봉합이 아니다.** 사람이 옮겨 적어야 하면 같은 사고가 난다.
   진짜 봉합은 **사람 손을 제거**하는 것이다(manifest 자동 조회).
2. **한 봉합이 다른 곳을 부순다.** 디스크 봉합이 배포 링크를 죽였다.
   봉합할 때 *"이걸 참조하는 데가 어디냐"* 를 반드시 훑어야 한다.
3. **화면이 전부 초록이어도 고객은 못 쓸 수 있다.** 이 사고는 우리 화면 어디에도
   안 보였다. **고객 신고가 유일한 발견 경로였다.**
4. 🔴 **고객 한 줄이 P0 3건을 끌어냈다.** *"설치가 안 됐다고 하더라고"* 한마디가
   진범 + 인가 구멍 + 채번 결함을 드러냈다. **현장이 답이다.**
