## 1. 🔴 작12 봉합이 그 자리가 아니었다

작12 에서 스키마 폴백(1054)을 5경로에 깔았는데 **여전히 500** 이었다.
⇒ **1054 가 아니었다.** 다른 예외다.

### 어떻게 찾았나 — 추측을 멈추고 전 구간을 실제로 태웠다

확정 경로가 건드리는 **모든 테이블·컬럼을 실물 스키마와 대조**했다:

| 테이블 | 결과 |
|---|---|
| `sales_returns` · `sales_return_items` | ✅ |
| `stock_ledger` · `item_stock` | ✅ |
| `partner_balance` · `monthly_summary` · `monthly_summary_sources` | ✅ |
| `journal_entries` · `journal_lines` | ✅ |

**전부 정상이었다.** 스키마는 원인이 아니었다.

그래서 확정 SQL 12단계를 **순서대로 그대로 실행**하는 프로그램을 짜서 돌렸다.
전 구간이 통과했다 — 즉 **정상 데이터에서는 확정이 된다.**

그 다음 UNIQUE 제약을 봤고, 거기서 나왔다.

### 🔴 진짜 원인 — 원장의 UNIQUE 제약

```
stock_ledger    : uq_stock_ledger_source (source_type · source_id · item_id · move_type)
journal_entries : uq_je_source           (tenant_id · source_type · source_id)
```

**원장이 이미 남아 있는 반품을 다시 확정하면 MySQL 1062(Duplicate entry).**

**실측 재현:**
```
1회차 INSERT 성공
🔴 중복 INSERT → MySQL 1062:
   Duplicate entry 'T1-sales_return-DUPTEST-…-I1-in' for key 'uq_stock_ledger_source'
```

### 🔴 증상 모양 대조 — 왜 500 인가

`GlobalExceptionMiddleware` 분기:

| 예외 | HTTP |
|---|---|
| `InvalidOperationException` | 400 |
| `MySqlException` **1451/1452**(FK) | **409** |
| **그 외 전부 (1062 포함)** | **500** |

1062 는 스키마(1054/1146)도 아니고 FK(1451/1452 → 409)도 아니라
마지막 `catch(Exception)` 으로 떨어져 **정확히 500** 이다.

🔴 **레포 전체에서 1062 를 잡는 곳이 한 군데도 없었다**(grep 0건).

### 어떻게 그 상태가 생기나

상태 전환(6단계)은 **트랜잭션의 마지막**이다.
앞 단계가 커밋된 뒤 뒤에서 실패하면 **상태는 `draft` 로 남고 원장만 남는 창**이 생긴다.
그 뒤로는 몇 번을 눌러도 1062 → 500 이 반복되고, **누르는 사람은 이유를 알 수 없다.**

사장님은 1.3.13~1.3.15 에서 확정을 **여러 번** 시도하셨다. 그 사이에 생긴 자국이다.

## 5. 세 번 연속 같은 모양이었다

| | 작11 | 작12 | **작13** |

작10 은 1054 를 잡았고, 작12 는 그 1054 를 5경로로 넓혔다.
그런데 **정작 나던 것은 1062** 였고, 그건 **아무도 안 잡고 있었다.**

🔴 **교훈**: 에러번호로 예외를 가를 때는 **그 경로에서 날 수 있는 번호를 전부 세어봐야** 한다.
하나를 잡으면 나머지가 전부 500 으로 샌다. 그리고 **500 은 원인을 안 알려준다.**

⚠️ **더 큰 교훈** — 작12 에서 나는 *"e2e DB 에서 확정 전 구간이 통과한다"* 를 보고
*"스키마는 정상"* 까지만 결론 내고 멈췄다. **정상 데이터로만 시험했기 때문이다.**
