## 2. P0-1 — 디스크 여유공간 검사 0건

### 2-1. 실측

```
grep -rniE "DriveInfo|AvailableFreeSpace|TotalFreeSpace|여유공간|freespace" --include=*.cs src/
  → 0건
```

**소스 전체에 디스크 여유공간을 보는 코드가 하나도 없다.** 인수인계서 지적이 정확하다.

### 2-2. 왜 P0 인가 — 안전망이 같이 무너진다

3팀이 독립으로 지목한 근거가 이것이다:

> **롤백도 디스크를 쓴다.** 부족한 순간 **안전망까지 무너진다.**

업데이트 흐름을 보면 디스크를 세 번 쓴다:

| 단계 | 디스크 사용 |
|---|---|
| 1 | 패키지 ZIP 다운로드 — **약 100MB** (실측: `hitpan-1.2.55.zip` = 102,720,238 bytes) |
| 2 | 백업 (`WatchdogBackupRunner`) — DB 크기에 비례 |
| 3 | 압축 해제 + 슬롯 교체 |

**디스크가 2단계에서 차면** 백업이 실패하고, [업데이트 워크플로우 결재](../../CLAUDE.md)의
*"백업 실패 시 업데이트 물리적 차단"* 이 작동해 그나마 막힌다.

🔴 **문제는 3단계다.** 백업은 성공했는데 해제 중 디스크가 차면 —
**옛 버전은 이미 지워졌고 새 버전은 안 풀렸다.** 그리고 **롤백도 디스크를 쓴다.**

### 2-3. 봉합 방향 (결재 후 착수)

| 항목 | 제안 |
|---|---|
| 검사 시점 | 다운로드 **전** (받고 나서 알면 이미 100MB 를 썼다) |
| 필요량 산정 | `sizeBytes`(manifest 에 이미 있다) × 안전계수 + 백업 예상량 |
| 부족 시 | **업데이트를 시작하지 않는다** + 본사 보고 + 고객 안내 |
| 🔴 결재 필요 | **안전계수·최소 여유(GB)를 몇으로 할 것인가** |

> 💡 manifest 에 `sizeBytes` 가 **이미 있다**(실측 확인). 새 통신 없이 계산 가능하다.

## 4. 🔴 P0-3 — 야간창 3~4시 1시간뿐 (셋 중 가장 어렵다)

### 4-1. 먼저 오해를 푼다 — N-10 이 이것을 고친 게 아니다

`WatchdogOptions.cs:36-39` 가 *"상한 60분이라야 3시대에 반드시 1회 이상 평가가 걸린다"* 고 적었고,
검증리뷰서 §2-7 이 시뮬레이션으로 **위상 60종 전수 통과**를 확인했다.

**그것은 사실이나, 이 P0 를 해소하지 않는다.**

| | 보장하는 것 | 보장 못 하는 것 |
|---|---|---|
| N ≤ 60분 | **PC 가 켜져 있으면** 3시대에 평가가 걸린다 | 🔴 **PC 가 꺼져 있으면 아무 일도 안 일어난다** |

### 4-2. 실측한 구조

`Worker.cs:485-498`

```csharp
case UpdateAction.ApplyAtNight: // Normal
    if (_update.IsNightWindow(DateTime.Now))   // Hour >= 3 && Hour < 4
        await _update.ApplyUpdateAsync(m, ct);
    else
        _pendingNightUpdate = m;               // 들고만 있는다
```

`UpdateOrchestrator.cs:1423-1424`

```csharp
public bool IsNightWindow(DateTime now)
    => now.Hour >= 3 && now.Hour < 4;          // 1시간뿐
```

### 4-3. 🔴 사무실 PC 는 밤에 꺼진다

> 인수인계서: *"사무실 PC 는 밤에 끔 → **구조적으로 업데이트 0회**인데 **오류가 안 남**"*

**히트판의 설치 대상이 무엇인지 생각하면 이것이 예외가 아니라 기본값이다.**
고객사 사무실 PC 는 퇴근 때 끈다. 새벽 3시에 켜져 있는 쪽이 드물다.

⇒ **Normal 채널 업데이트는 그 고객에게 영원히 도달하지 않는다.**

### 4-4. 🔴 더 나쁜 것 — 경보도 안 울린다

`Worker.cs:638-642` `TrackUpdateStallAsync`

```csharp
if (!_update.LastFetchFailed)
{
    // 조회 성공 = feed 정상. 그동안의 연속 실패를 푼다.
```

**이 함수가 보는 것은 "feed 조회가 성공했는가" 뿐이다.**

| 실제 상태 | 워치독이 보는 것 |
|---|---|
| feed 조회 ✅ 성공 (낮에 잘 된다) | **정상** |
| 야간창 도달 ❌ 0회 (밤에 PC 가 꺼짐) | **보지 않는다** |
| 고객 버전 🔴 옛 버전 고정 | **카운터 0 → 7일 경보 발화 안 함** |

> 🔴 **고객도 본사도 모른다.** 화면은 정상으로 보이고, 로그도 정상이고, 경보도 안 운다.
> 이것이 이 P0 의 진짜 무게다 — **침묵하는 실패**다.

`Worker.cs:464-472` 가 이미 이 전제 붕괴를 주석으로 적어놨다(작2 §6 이행).
**적어놨을 뿐 고쳐지지 않았다.**

### 4-5. 🔴 왜 이번에 코드를 안 고치는가

**이것은 정책 재설계이지 봉합이 아니다.** `Worker.cs:469-471` 이 그 이유를 정확히 적었다:

> *"계수 축을 '날짜'에서 '연속 실패 횟수 + 최근 성공 시각'으로 바꾸는 것은
> 정지공격 감지 **정책의 재설계**이고 임계 7일의 의미도 다시 정해야 하는 **사장님 결재 사안**이다."*

**PM 이 임의로 정할 수 없는 것들:**

| # | 결정 사항 | 왜 사장님 |
|---|---|---|
| 1 | 야간창을 넓힐 것인가 (3~4시 → 예: 0~6시) | 고객 업무 시간과 충돌 판단 |
| 2 | PC 가 켜진 시각에 적용을 시도할 것인가 | **영업 중 재기동 위험** vs 미도달 |
| 3 | 며칠 미도달이면 경보인가 | 임계 정책 |
| 4 | 미도달 시 고객에게 무엇을 보여줄 것인가 | CS 정책 |

> ⚠️ **2번이 특히 위험하다.** 야간창을 두는 이유가 *"영업 중에 히트판을 끄지 않기 위해"* 다.
> 그것을 풀면 **낮에 업무 중 재기동**이 일어날 수 있다. `IsBusinessHour` 가 별도로 있는 이유다.

**정책을 정하기 전에, 이 일이 실제로 얼마나 일어나는지 모른다.**
