> "그 확인은 사장의 SSH 몫으로 남기지 말고, AI를 이용해, CS의 새로운 인력이 대응 할수 있도록 메뉴얼을 만들어"

## 1. 무엇이 문제인가

### 1-1. 지금은 CS 가 원인을 못 본다

통신 문의가 오면 원인 확인 수단이 **사장님 SSH 뿐**이다.

| 확인 항목 | 지금 누가 | 문제 |
|---|---|---|
| 계정이 승인됐나(`tenants.status`) | 사장님 SSH → DB | CS 대기 |
| Cloudflare 설정 켜졌나(환경변수 3종) | 사장님 SSH → systemd | CS 대기 |
| 터널·DNS 가 발급됐나 | 사장님 SSH → 로그 | CS 대기 |

⇒ **CS 신입은 아무것도 판정할 수 없다.** 고객은 기다리고, 사장님이 병목이 된다.

### 1-2. 백오피스에 진단 API 가 없다 (실측)

컨트롤러 27개 전수 확인 — **진단·헬스체크 전용 엔드포인트 0건.**
`TenantsAdminController` 로 테넌트 목록은 보이지만, **"이 고객이 왜 1033 인가"** 를 답해주는 것은 없다.

### 1-3. ⭐ 실측으로 이미 좁혀진 것 (진단 API 가 자동화해야 할 판정)

PM 실측 2026-07-30:

| 호스트 | HTTP | 해석 |
|---|---|---|
| `demo.hitpan.kr` | **502** | DNS ✅ + 터널 ✅ + **연결만 끊김**(PC 꺼짐) — 발급 정상 |
| `test1.hitpan.kr` | **530** | **터널 없음 또는 ingress 비어 있음** — 발급 실패 |
| `test2.hitpan.kr` | **530** | 동일 |

> ⭐ **502 vs 530 이 결정적 판별식이다.** 이 한 줄이 "PC 를 켜면 되는 문제"와
> "본사 발급이 안 된 문제"를 가른다. **진단 API 는 이 판정을 자동으로 내려야 한다.**

## 2. 무엇을 만드는가

**`GET /api/backoffice/diagnostics/tenant/{시리얼 또는 회사명}`** — CS 가 백오피스 화면에서 1클릭.

### 2-1. 응답 설계 (CS 가 읽는 말로)

```jsonc
{
  "판정": "미승인",                    // 승인대기 | 정상 | 본사설정누락 | 발급실패 | 고객PC꺼짐
  "고객안내문": "가입 승인이 아직 완료되지 않았습니다. 승인 후 설치하시면 정상 작동합니다.",
  "다음조치": "백오피스 → 가입관리에서 승인 처리",
  "담당": "CS 자체 처리 가능",          // CS 자체 | 개발팀 이관 | 사장님 결재
  "근거": {
    "계정상태": "pending",
    "본사설정": "정상",
    "도메인응답": 530,
    "터널발급": false
  }
}
```

**핵심**: CS 가 `pending`·`530` 같은 값을 해석하지 않는다. **`판정`·`고객안내문`·`다음조치` 3줄만 읽고 응대**한다.

### 2-2. 판정 규칙 (§1-3 실측 기반)

| 계정상태 | 본사설정 | 도메인 | **판정** | 담당 |
|---|---|---|---|---|
| `pending` | — | — | **승인대기** | CS 자체 (승인하면 끝) |
| 없음 | — | — | **시리얼 오류** | CS 자체 (시리얼 재확인) |
| `active` | 누락 | 530 | **본사설정누락** | 사장님 결재 (환경변수) |
| `active` | 정상 | 530 | **발급실패** | 개발팀 이관 |
| `active` | 정상 | **502** | **고객PC꺼짐** | CS 자체 ("컴퓨터를 켜주세요") |
| `active` | 정상 | 200 | **정상** | 재확인 요청 |

### 2-3. 🔴 절대 규칙 — 무엇을 반환하지 않는가

| 금지 | 왜 |
|---|---|
| **Cloudflare API 토큰·Zone ID·Account ID 값** | 헌법 #22 — 존재 여부(`true/false`)만 |
| 라이선스 키 평문 | 해시 비교만. 응답에 시리얼 원문 금지 |
| 고객 업무 데이터 | 헌법 #18 — 진단은 메타·상태만 |
| 사업자번호·대표자명 | 백오피스는 평문 미보유(결재 2026-06-18 "길 B") |
| DB 예외·스택트레이스 | 내부 구조 노출 |

## 4. 어떻게 하는가 ([3] 개발팀용)

### 4-1. `DiagnosticsController.cs` 신규 (담당: 백엔드 1 + 보안 1)

```
[ApiController]
[Route("api/backoffice/diagnostics")]
[Authorize]
public class DiagnosticsController : ControllerBase
```

- `[BoPermission("diagnostics.read")]` — 기존 `BoPermission` 패턴 그대로(TenantsAdminController:45 참조)
- 권한 신설 시 **권한 목록·시드에 등록**(헌법 #11 — 어드민이 직접 설정)
- 조회 항목:
  1. `tenants` 상태·`domain_alias`·`tenant_code` (시리얼 해시 또는 회사명으로)
  2. `_cfDomain.IsConfigured` (**bool 만**)
  3. `https://{domain}` HTTP 상태 코드 (서버에서 1회, 타임아웃 10초)
  4. `serial_verify_attempts` 최근 시도 이력(있으면 — 설치 시도 흔적)
- 판정은 **2-2 표를 코드로 옮긴다.** 판정 로직을 CS 문서와 **같은 출처**로 유지

### 4-2. 백오피스 화면 (담당: 프론트 1 + UX 1)

- 위치: 가입관리·테넌트관리 화면에 **`진단` 버튼**
- 입력: 시리얼 또는 회사명 1칸
- 출력: **판정 / 고객안내문 / 다음조치** 3줄을 크게. `근거` 는 접어두기(펼치면 보임)
- **복사 버튼** — 고객안내문을 그대로 복사해 붙여넣게

### 4-3. 하지 말 것

- ❌ 진단 API 가 터널·DNS 를 **발급·수정**하는 기능 겸용 (헌법 #29 — 조회 전용 유지)
- ❌ 토큰·키 값 반환 (2-3)
- ❌ 인증 없이 열기 (`[Authorize]` 필수 — 고객 상태 조회는 내부 정보)
- ❌ 판정 규칙을 코드에만 두고 CS 문서와 갈라지게 하기

## 5. 검증 방법 (SoD — 만든 사람 ≠ 검증하는 사람)

| # | 게이트 | 기준 |
|---|---|---|
| V1 | 빌드 | errors 0 + warnings 0 (헌법 #19) |
| V2 | **판정 6종 전부** | 2-2 표의 6가지 경우를 **실제 데이터로 만들어** 각각 올바른 판정 |
| V3 | **502 vs 530 구분** | `demo`(502) → "고객PC꺼짐" · `test1`(530) → "발급실패/설정누락" (§1-3 실측 재현) |
| V4 | 비밀 미노출 | 응답 전문에 토큰·Zone·Account·시리얼 평문 **0건** (문자열 검사) |
| V5 | 권한 | 미인증·권한없는 계정 → **거부** |
| V6 | 판정 불능 | DB 다운·타임아웃 시 `"확인불가"` + 사유 (조용한 성공 0) |
| V7 | **CS 신입 실사용** | CS 담당이 **매뉴얼만 보고** 판정→응대까지 도달 (문서 없이 코드 읽지 않아도 됨) |

> **V3·V7 이 핵심이다.** V3 는 이 API 의 존재 이유(판별식)이고,
> **V7 은 사장님 오더의 목적** — CS 신입이 사장님 없이 대응하는 것.
