## 0. PM 자기 적발 — 왜 지시가 이행 안 됐나

**사장님 지적 3건 모두 사실이다. 코드가 없어서가 아니라 PM 이 안 쓰거나 안 만들었다.**

| 지시 | 실제 상태 | PM 잘못 |
|---|---|---|
| ① Y/N 동의 업데이트 | **기능 전부 존재**(팝업·API·워치독 적재) | PM 이 게시할 때마다 `channel=Emergency` 를 넣어 **그 경로를 통째로 우회**했다 |
| ② 테스트배포 사이클 | ①의 결과로 불가 | Emergency 는 묻지 않고 즉시 적용 → 사장님이 확인할 새가 없다 |
| ③ 백오피스 업데이트 기록 | **워치독 송신부만 있고 백오피스 수신부 0건** | 만들지 않았다 |

**①이 핵심이다.** 2026-08-03~04 PM 이 게시한 1.2.49·1.2.52 는 **전부 Emergency** 였다.

```
Emergency  → 워치독이 묻지 않고 즉시 적용   ← PM 이 이것만 써 왔다
Normal     → 야간 조용히 적용
Major      → Y/N 팝업                      ← 사장님이 지시하신 것
```

`Worker.cs:351-360` 은 **`RequireConsent`(=Major) 일 때만** `UpsertLatestAsync` 로 팝업용 데이터를 적재한다.
Emergency 는 그 줄에 도달조차 안 한다 ⇒ **팝업이 구조적으로 뜰 수 없었다.**

2026-08-03 사장님이 "업데이트 안 뜨네" 하신 것도 이 때문이다.
PM 은 그때 워치독 일일 게이트만 설명하고 **채널이 원인이라는 것을 못 짚었다.**

## 1. 대상 ① — Y/N 동의 배포 (코드 변경 0, 운영 규칙)

### 1-1. 이미 완성된 사슬 (실측 확인)

```
게시(channel=Major)
   ↓
워치독 발견 → Worker.cs:351 RequireConsent → 즉시 적용 안 함
   ↓
WatchdogStatusWriter.UpsertLatestAsync → 로컬 DB local_update_status 적재
   ↓
ERP 로그인 → UpdateConsentGate.razor:44 → GET api/auth/update-status
   ↓
AuthController.ComputeUpdateStatusAsync → IsNewerVersion 비교
   ↓
"새 버전 {V} 이(가) 나왔습니다. 업데이트하시겠습니까?"  [예] / [나중에]
   ↓
SubmitUpdateConsentAsync → 워치독 ConsumeConsentForMajorAsync 가 읽어 적용
```

**코드는 손댈 것이 없다.** 게시 채널만 `Major` 로 하면 된다.

### 1-2. 확정 운영 규칙 (사장님 오더 ②)

| 상황 | 채널 | 근거 |
|---|---|---|
| **평시 수정 배포·테스트 배포** | **Major (기본)** | 사장님이 Y/N 로 받아 확인 — 개발 사이클의 전제 |
| 보안·데이터 손상 등 즉시 강제 | Emergency | 사장님 사전 결재 시에만 |
| 야간 조용히 | Normal | 현재 미사용 |

> 🔴 **PM 금지**: 사장님 별도 결재 없이 `Emergency` 로 게시하지 않는다.
> Emergency 는 **고객 의사를 묻지 않고 바꾸는 것**이다 — 사장님 지시(①)의 정반대다.

### 1-3. 검증
- 1.2.53 을 **Major** 로 게시 → 샌드박스(1.2.52) 로그인 → **팝업 노출 + [예] 적용 실측**
- 팝업 문구에 개발용어·영어 0건(2026-06-05 사장님 명령)

## 2. 대상 ② — 백오피스 고객사 업데이트 기록 (신규 구현)

### 2-1. 실측된 결손

| 구간 | 상태 |
|---|---|
| 워치독 송신 `MetaPingClient.SendAsync` (164줄) | ✅ 구현됨 |
| 페이로드 `MetaPingPayload` (66줄) | ✅ 구현됨 |
| **백오피스 수신 엔드포인트** | ❌ **0건** (`meta-ping` grep 0) |
| **기록 테이블** | ❌ **0건** |
| 백오피스 조회 화면 | ❌ 없음 |

⇒ **워치독이 보내는 것이 허공으로 간다.** 사장님이 고객사 업데이트 현황을 볼 방법이 없다.

### 2-2. 설계 — 헌법 #18·#22 절대 준수

> **본사로 고객사 업무 데이터 전송 절대 금지.** 업데이트 기록은 *운영 메타데이터*이지 업무 데이터가 아니다.
> `MetaPingClient.ValidateMinimalism`(:155-163)이 이미 금지 필드를 차단한다 — **그 검사를 절대 우회·완화하지 않는다.**

**수집 항목 (이것만)**

| 필드 | 예 | 사유 |
|---|---|---|
| `tenant_id_hash` | `sha256:...` | 고객사 식별(원문 아님) |
| `from_version` / `to_version` | 1.2.52 → 1.2.53 | 업데이트 기록의 본체 |
| `channel` | Major | 어떤 방식으로 갔나 |
| `result` | success / failed / rejected | 성공·실패·고객이 [나중에] |
| `occurred_at` | UTC | 시점 |
| `failure_reason` | 문자열(선택) | 실패 원인 |

**금지 항목**: 거래처·상품·금액·직원명·DB 내용 등 업무 데이터 일체.

**테이블**: `tenant_update_history` (백오피스 DB, `ENGINE=InnoDB` 명시 — 헌법 #17)

### 2-3. 구현 범위

| # | 항목 | 파일(예정) |
|---|---|---|
| 1 | 수신 엔드포인트 `POST /api/telemetry/update-history` | `Controllers/TelemetryController.cs` (신규) |
| 2 | 테이블 DDL | 백오피스 마이그레이션 |
| 3 | 워치독 송신 지점 배선 (적용 성공/실패/거부 3시점) | `UpdateOrchestrator.cs` |
| 4 | 백오피스 조회 화면 | 별건 — **본 지시서 범위 밖** |

### 2-4. 보안
- 인증: 기존 `GetBearerToken` 방식 유지 (`MetaPingClient:79`)
- 헌법 #2: `tenant_id` 를 파라미터로 받지 않는다 — 해시로만
- 실패해도 **고객 ERP·업데이트를 절대 막지 않는다**(헌법 #20·#30, fire-and-forget)

## 2-B. 대상 ③ — 사이드바 버전 표기 (사장님 오더 ⑤)

> *"현재 히트판 버전이 어떻게 되는지 자료관리 탭 밑에 작게 버전도 표기해."*

### 2-B-1. 왜 필요한가 (단순 표시가 아니다)
Y/N 업데이트를 도입하면 **고객·사장님이 "지금 내 버전이 뭔지" 를 볼 수 있어야** 한다.
그게 없으면 [예] 를 눌러도 **바뀌었는지 확인할 방법이 화면에 없다.**
2026-08-03~04 PM 이 매번 `curl .../health` 로 확인한 것을 **고객은 할 수 없다.**
⇒ 오더 ②(테스트배포 사이클)의 **확인 수단**이다.

### 2-B-2. 위치
`src/HitPan.Web/Layout/Sidebar.razor` — 11.자료관리 `</MudNavGroup>`(:161) 바로 아래,
`</MudNavMenu>` 앞. 사이드바 최하단이다.

### 2-B-3. 요건
| # | 요건 |
|---|---|
| 1 | **작게** 표기(사장님 명시) — 메뉴를 가리지 않는다 |
| 2 | 값은 **실제 실행 중인 버전** — 하드코딩 금지(과거 8곳 하드코딩 사고 이력) |
| 3 | 조회 실패해도 **사이드바·ERP 를 절대 안 막는다**(헌법 #20) — 실패 시 표기 생략 |
| 4 | 개발용어·영어 금지(2026-06-05) — "버전 1.2.53" 형태 |
| 5 | 헌법 #14 — `.razor` 에 raw string(`"""`) 금지 |

### 2-B-4. 출처
`GET /api/auth/update-status` 가 이미 `CurrentVersion` 을 돌려준다
(`AuthController.ComputeUpdateStatusAsync`, `GetCurrentErpVersion()`).
**새 API 를 만들지 않는다** — 기존 단일 진실원 재사용.

### 2-B-5. 합격 기준
- 사이드바 최하단에 현재 버전이 작게 보인다
- 업데이트 적용 후 값이 **바뀐다**(1.2.52 → 1.2.53 실측)
- API 실패 시에도 사이드바 정상 동작

## 3. 우선순위 — 사장님 오더 ② 가 최우선

**대상 ①(Y/N 배포)이 먼저다.** 그게 막혀 있으면 수정→배포→확인 사이클 자체가 안 돈다.
대상 ②(백오피스 기록)는 그 다음이며, 없어도 개발 사이클은 돈다.

```
[1단계] 1.2.53 Major 게시 → 팝업 실측        ← 즉시
[2단계] 백오피스 수신부 + 테이블 구현         ← 1단계 확인 후
[3단계] 백오피스 조회 화면                    ← 별건
```

## 4. 합격 기준

### 1단계
1. 1.2.53 이 **Major** 로 게시된다
2. 샌드박스 ERP 로그인 시 **"업데이트하시겠습니까"** 팝업이 뜬다
3. **[예]** 누르면 적용되고, **[나중에]** 누르면 적용 안 된다
4. 적용 후 버전이 1.2.53 으로 바뀐다

### 2단계
5. 워치독이 업데이트 결과를 백오피스로 보내고, **백오피스 DB 에 행이 쌓인다**
6. 업무 데이터 0건(헌법 #18·#22) — 페이로드 검사로 확인
7. 백오피스가 죽어도 고객 ERP·업데이트는 정상(헌법 #30)

> ⚠️ **"코드 고쳤다"는 봉합이 아니다.** 샌드박스 실측으로만 판정한다.
