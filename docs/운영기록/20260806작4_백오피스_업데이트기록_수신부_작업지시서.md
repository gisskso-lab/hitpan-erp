## 1. 진범 — 코드 버그가 아니라 "받을 문이 없다"

### 1-1. 실측 확정 (2026-08-06)

인수인계서는 `MetaPing HTTP 400` 을 미해결로 남겼다. **원인을 실측으로 확정했다.**

```
POST https://back.hitpan.kr/watchdog/ping        -> HTTP 400
GET  https://back.hitpan.kr/healthz              -> HTTP 404   ← 코드엔 있는데 404
GET  https://back.hitpan.kr/aaa-nonexistent-xyz  -> HTTP 404
POST https://back.hitpan.kr/aaa-nonexistent-xyz  -> HTTP 400   ← ★ 아무 경로나 POST 하면 400
```

⇒ **400 은 `/watchdog/ping` 고유 증상이 아니다.** 라우팅 안 되는 POST 에 대한 일반 응답이다
   (응답 헤더 `blazor-enhanced-nav: allow`, `Server: nginx/1.24.0` — Blazor 서버가 처리).

**즉 페이로드 검증 실패가 아니라 경로 자체가 없다.** 스키마를 아무리 고쳐도 400 은 안 사라진다.

> - CS팀장 강지원 "MVP 에 꼭": **(현재버전 + 마지막보고시각 + 업데이트 성공/실패)** 세트.
>   *"로컬 ERP는 '업데이트했다'가 '업데이트됐다'를 보장 안 한다. 실패 여부 없으면 CS가 눈 감고 일한다."*

## 3. 설계

### 3-1. 헌법 #18·#22 — 무엇을 받고 무엇을 안 받나

> **본사로 고객사 업무 데이터 전송 절대 금지.** 업데이트 기록은 *운영 메타데이터*지 업무 데이터가 아니다.
> `MetaPingClient.ValidateMinimalism`(:154-163)이 이미 금지 필드를 차단한다 — **완화·우회 금지.**

**받는 것 (이것만)**

| 필드 | 예 | 사유 |
|---|---|---|
| `tenant_id_hash` | `sha256:a938…` | 고객사 식별(원문 아님) |
| `from_version` / `to_version` | 1.2.52 → 1.2.53 | 기록의 본체 |
| `channel` | Major / Normal | 어떤 방식으로 갔나 |
| `result` | success / failed / rejected | 성공·실패·고객이 [나중에] |
| `occurred_at` | UTC | 시점 |
| `failure_reason` | 문자열(선택) | 실패 원인 |

**금지**: 거래처·상품·금액·직원명·DB 내용 등 업무 데이터 일체.

### 3-2. 고객사 식별 — 해시로 조인한다 (실측 확인)

워치독은 `SHA256(TENANT_CODE)` 를 보낸다(`MetaPingClient.cs:126-142`). **salt·pepper 없음.**

실측:
```
T-001 -> sha256:a938512bd32f1ec15eac4af291ae9e2da4956cff404b907fff39bd7def608bfc
T-002 -> sha256:a1994385fee87ad6e5ebf17c4be60917e27d10947265fc6f375d0f26199d8836
```
⇒ 같은 입력이면 항상 같은 해시 ⇒ 백오피스가 `tenants.tenant_code` 로 **재계산해 대조**할 수 있다.

⚠️ **백오피스에 해시 컬럼이 없다**(실측: `tenant_code_hash` 0건).
`tenants` 에 **컬럼을 추가하지 않는다**(기존 테이블 변경 최소화 — 헌법 #1·#37).

**⇒ 그런데 §3-5 에서 인증 방식이 바뀌어 이 대조는 주 경로가 아니게 됐다.**
신원은 **라이선스 키로 확정**하고, `tenant_id_hash` 는 **기록·표시용**으로만 저장한다.
(해시 재계산 대조는 구현하지 않는다 — 불필요해졌다)

### 3-5. 인증 — 라이선스 키로 진짜 검증한다 (PM 결재 시 정정)

> ⚠️ **초안은 "검증 불가라 검증하지 않는다"로 썼다. PM 검토에서 뒤집혔다.**
> 레포에 **이미 같은 문제를 푼 코드가 있다** — 먼저 찾았어야 했다(헌법 #42).

**성립 근거 (실측)**

| 쪽 | 가진 것 | 근거 |
|---|---|---|
| 워치독 | `LICENSE_KEY` **원문** (`db.conf`) | `MetaPingClient.cs:146` |
| 백오피스 | `License:Pepper` + `tenants.license_key_hash` | `DeviceRegistrationController.cs:56,70` |

⇒ 워치독이 **라이선스 키를 보내면**, 백오피스가 `HMAC-SHA256(key, pepper)` 로 해싱해
   `tenants.license_key_hash` 와 대조할 수 있다. **`DeviceRegistrationController` 가 이미 그렇게 한다.**

**채택 방식** — 선례를 그대로 따른다(새 기법 금지):
```
워치독 → 본문에 license_key 동봉 (HTTPS/TLS1.2+, MetaPingClient.cs:38)
백오피스 → HMAC(key, pepper) == tenants.license_key_hash 조회
           매칭 O → 그 tenant_id 로 적재 (신원 확정)
           매칭 X → 401. 적재하지 않는다
```

**이 방식이 초안보다 나은 점 2가지**
1. **진짜 인증이 된다** — 위조 행이 안 쌓인다
2. **고객사 신원이 확정된다** — §3-2 의 해시 재계산 대조가 **불필요**해진다
   (해시는 기록·표시용으로만 남긴다)

> 🔴 **평문 저장 금지**(헌법 #22): 받은 `license_key` 는 **대조에만 쓰고 절대 저장하지 않는다.**
> 로그에도 남기지 않는다(마스킹). `DeviceRegistrationController` 와 동일 원칙.

**미상 고객사 처리 변경**: 인증이 되므로 **미상은 401 로 거절**한다.
§3-3 의 `tenant_id` NULL 허용은 **유지**하되(설치 직후 등록 지연 대비) 정상 경로에서는 채워진다.

### 3-6. 워치독 송신 배선

`UpdateOrchestrator` 의 **3시점**에서 fire-and-forget 송신:
1. 적용 성공 확정 후 → `result=success`
2. 적용 실패·롤백 후 → `result=failed` + `failure_reason`
3. 고객이 [나중에] 선택 → `result=rejected`

> 🔴 **송신 실패가 업데이트를 절대 막지 않는다**(헌법 #20·#30). 예외를 삼키되 로그는 남긴다(#15).
