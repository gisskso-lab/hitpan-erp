## 0. 왜 이게 1차인가

> 사장님: **"사슬의 정합률 100%가 목표임. 그리고 가장 중요한거 사슬동작중 중복생성 절대금지"**

중복생성은 **사슬 정합률을 근본에서 무너뜨린다.** 번호가 겹치거나 문서가 두 장 생기면
그 뒤 2·3차에서 아무리 링크를 이어도 **무엇에 이어야 하는지가 모호**해진다.
그래서 링크(2차)·회계(3차)보다 **먼저** 간다.

## 1. 범위 — W1~W5

### 🔴 W1. 매출반품 번호가 **저장 자체를 못 한다** (신규 발견)

**증상 (실측)**

| | 번호 | 길이 | 컬럼 | 결과 |
|---|---|---|---|---|
| 매입반품 | `매반-20260827-001` | 19 | varchar(20) | 🟢 |
| **매출반품** | `매출반품-20260827-001` | **25** | **varchar(20)** | 🔴 **초과 5자** |

- `ApprovalService.cs:118` 이 이 배포가 **`STRICT_TRANS_TABLES`** 임을 기록(과거 ERROR 1406 사고).
- ⇒ **`ERROR 1406 Data too long` 으로 매출반품 생성이 터진다.**
- 매입은 `매반-`(2글자)로 19자에 맞췄는데 **매출만 `매출반품-`(4글자)**.

**사장님 지시 (비고 표기 형식)**
> 매출반품에 마이너스 전표면 비고란에 **"반품전표 : 반-(전표번호)"** 라고 표기하면 될듯

⇒ **prefix 를 `반-` 으로 바꾼다.** 길이 문제가 **같이 해소**된다.

| 안 | 예시 | 길이 | 판정 |
|---|---|---|---|
| 현행 | `매출반품-20260827-001` | 25 | 🔴 |
| **채택 `반-`** | `반-20260827-001` | **18** | 🟢 |

**작업**
- `SalesService.cs:1958` prefix `매출반품-` → `반-`
- 🟢 **읽는 쪽 의존 0 확인 완료** — `매출반품-` 문자열을 쓰는 곳은 이 1곳뿐
  (나머지 grep 결과는 전부 주석·설명문)
- 기존 행 마이그: `DB-113` 에서 `매출반품-` 로 시작하는 `return_no` 를 `반-` 으로 UPDATE
  ⚠️ **기존 행은 이미 잘렸거나 저장 실패했을 수 있다** — 마이그는 있으면 고치고 없으면 넘어간다(멱등)

### 🔴 W2. COUNT+1 채번 5곳 → MAX+1

`DocumentNumberHelper.cs:6-9` 주석이 COUNT+1 을 **"진범"** 으로 지목:
> EF `Repository.FindAsync(StartsWith).Count + 1` 패턴은 동시 호출 시 같은 번호 생성 →
> `(tenant_id, doc_no)` UNIQUE 충돌 → **4/28 174건 자동 사슬 중 71건 stock_ledger 누락.**

**그 진범이 5곳에 그대로 남아 있다.**

| # | 위치 | 대상 | 비고 |
|---|---|---|---|
| 1 | `QuotationService.cs:404` `GenerateQuoteNoAsync` | 견적 `견-` | |
| 2 | `QuotationService.cs:306` | 견적→수주 전환 `수-` | 🔴 `DateTime.UtcNow` — 아래 W2-b |
| 3 | `TaxInvoiceService.cs:85` | 계산서 `세-` | 🔴 `DateTime.UtcNow` — 아래 W2-b |
| 4 | `SalesService.cs:1958` | 매출반품 `반-` | 🔴 `DateTime.UtcNow` · W1 과 같은 자리 |
| 5 | `PurchaseService.cs:981`·`:1109` | 매입반품 `매반-` | 2군데 |

**작업**: 전부 `DocumentNumberHelper.NextNumberAsync` 로 교체.
- 트랜잭션 안에서 도는 호출은 `transaction:` 인자 전달 (헬퍼가 이미 지원)
- 🔴 **COUNT+1 의 진짜 위험은 동시성만이 아니다** — 소프트삭제 시 COUNT 가 줄어
  **이미 쓴 번호를 재발급**한다. MAX+1 은 삭제된 번호를 건너뛴다.

### W2-b. 채번 일자가 **매출만 UTC** (같은 자리라 함께 고친다)

- 🟢 매입은 이미 **`BusinessDate.Today`** 를 쓴다 (`PurchaseService.cs:1109`, 20260825작18 W4 봉합)
- 🔴 **매출 3곳만 `DateTime.UtcNow` 로 남았다** (위 표 2·3·4)
- `BusinessDate` 의 doc 주석이 용도를 명시한다:
  *"업무 기준 '오늘' — **전표 일자·문서번호 채번**에 쓴다"* (`BusinessDate.cs:33-34`)
  ⇒ **이 헬퍼는 바로 이 용도로 만들어졌는데 매출이 채택을 안 했다.**
- **증상**: KST 09:00 이전에는 UTC 날짜가 **전날**이라 `세-20260826-…` 이 8/27 에 발급된다.
  전표 일자와 번호의 날짜가 **하루 어긋난다.**
- **조치**: 매출 3곳 `DateTime.UtcNow` → `BusinessDate.Today` (채번 라인 한정)
  ⚠️ 채번 외 용도의 `UtcNow`(`created_at` 등)는 **건드리지 않는다** — 저장 시각은 UTC 가 맞다

### 🔴 W4. 수주 자동생성 멱등 가드 (사장님 "가장 중요" 핵심)

**현황** — `SalesService.cs:160-211`
- `OrderId` 가 비었는지**만** 검사하고 수주서를 만든다.
- **같은 거래명세서 저장을 두 번 타면 수주서가 2장 생긴다.**
- `POST /api/sales/deliveries` 에 **`[IdempotencyKey]` 가 없다** (confirm 엔 있음 — `SalesController.cs:142`).
- 🔴 메모리의 자동발주 중복사고(*"is_auto=1 은 쓰기만 하고 읽지 않았다"*)와 **완전히 동형**.
  매입은 그 사고 후 `po.is_auto = 1` 을 **읽는** 멱등 필터를 넣었는데, 매출 수주 자동생성은 **그 봉합을 안 받았다.**

**작업**
1. `POST /deliveries` 에 `[IdempotencyKey]` 부여 (confirm 과 대칭)
2. 자동생성 직전 **멱등 조회**: 같은 tenant·partner·date 로 이미 만들어진
   **`is_auto=1` 수주서가 있으면 재사용**하고 새로 만들지 않는다
   → 🔴 **`is_auto` 를 쓰기만 하지 말고 읽는다** (자동발주 사고의 교훈 그대로)
3. 채번·INSERT 를 **같은 트랜잭션** 안에서 (W2 의 `transaction:` 인자)

### 🔴 W5. 매출반품 중복발행 차단

**현황**: `CreateSalesReturnAsync:1944-2011` 에 **같은 `delivery_id` 중복 검사가 없다.**
매입은 `PurchaseService.cs:1092-1105` 에 있다 — **비대칭.**

**매입 동작 — 실측 확인 완료** (`PurchaseService.cs:1091-1106`)
```sql
SELECT return_no FROM purchase_returns
 WHERE receipt_id=@Rid AND tenant_id=@Tid
   AND is_deleted=0 AND status <> 'canceled'
 LIMIT 1
```
- **살아있는 반품 1건이면 막는다** — 부분반품 복수 허용이 **아니다**
- **취소분은 제외** (`status <> 'canceled'`) — 주석: *"취소분은 다시 만들 수 있어야 하므로 제외"*

**작업**: 위 쿼리를 `sales_returns`·`delivery_id` 로 **그대로 대칭 이식**.
- 🔴 **에러 메시지에 기존 반품번호를 반드시 담는다** — 작8 교훈: *"막는 것 ≠ 알려주는 것."*
  `"이미 반품전표({dupNo})가 발행된 거래명세서입니다. 기존 반품전표를 수정하세요."`
**🔴 철자 — 실측 확인 완료. 여기서 틀리면 가드가 조용히 안 먹는다**

같은 `SalesService.cs` 안에서 **철자가 갈린다**:

| 줄 | 테이블 | 저장값 |
|---|---|---|
| :955 · :1155 | `sales_deliveries` | **`cancelled`** (2L) |
| **:2508** | **`sales_returns`** | **`canceled`** (1L) |

⇒ W5 가드는 **`canceled`(1L)** 를 써야 한다. 매입(`purchase_returns`)과 같다.
🔴 **옆줄의 `sales_deliveries` 코드를 보고 `cancelled` 로 복사하면 가드가 영원히 안 걸린다** —
막는 것처럼 보이면서 **아무것도 안 막는다.** 게이트 G-5 가 이걸 잡아야 한다.
*(철자 통일 자체는 P2 ⑦ 별건 — 마이그 동반이라 여기서 안 건드린다)*

## 3. 게이트 — 가짜 게이트 21회 방지

| G | 검사 | 반드시 |
|---|---|---|
| G-1 | `반-yyyyMMdd-NNN` 이 **varchar(20) 에 실제로 INSERT 된다** | 🔴 **DB 에 넣어라.** 길이 계산으로 판정 금지 |
| G-2 | 같은 명세서 2회 저장 → **수주서 1장** | 🔴 실제로 2번 불러라. `if(false&&…)` 로 죽여도 통과하면 가짜 |
| G-3 | 동시 채번 2회 → **번호 2개가 다르다** | 반환값 판정 금지 — **DB 행을 세라** |
| G-4 | 소프트삭제 후 채번 → **삭제된 번호를 재발급하지 않는다** | COUNT+1 이 지는 자리 |
| G-5 | 같은 명세서 2번째 반품 → **거부 + 기존 반품번호가 메시지에 담긴다** | 🔴 *"막는 것 ≠ 알려주는 것"* — **번호가 갔는지** 확인 |
| G-6 | 자동생성 수주서에 **`is_auto=1` 표식** | 사장님 "중요함". 표식 없으면 **FAIL** |
| G-7 | **대조군**: 봉합 빼면 G-1~G-6 이 **FAIL 로 바뀐다** | 🔴 초록불이 어디서 오는지 확인 |

🔴 **질문은 "고쳤나" 가 아니라 "갔나"** — 작7→작8 에서 게이트 9건 전부 통과하고도 반려났다.
서버가 맞는 값을 만드는지가 아니라 **화면·DB 까지 갔는지**를 재라.
