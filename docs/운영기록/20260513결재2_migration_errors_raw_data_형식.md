# 결재 안건 #2 — migration_errors.raw_data 컬럼 형식

> **상신:** 2026-05-13 PM 닥터스트레인지
> **수신:** 사장님
> **긴급도:** P2 (W3 청크 처리 도입 전 결재 필요)
> **담당 매니저 리뷰:** DB 매니저 (1차) + 보안 매니저 (2차)

## 1. 배경

W2 D2에서 `migration_errors` 테이블 신설 (실패 행 추적용). `raw_data` 컬럼 형식은 W2 D2 시점에 미결로 남김 (헌법 #22 데이터 최소주의 + 형사영역 정책 충돌 우려).

### 컬럼 후보
- 마이그 실패 시 원본 MDB 행 데이터를 어떤 형식으로 보존할 것인가
- 이 데이터에는 **주민번호·급여·계좌 등 형사영역 데이터가 평문으로 포함될 가능성**

## 2. 핵심 갈등

| 요구 | 충돌 |
|---|---|
| **운영 편의** — 사람이 읽고 원인 파악 가능해야 함 | **헌법 #18 v3** 형사영역 9개 법령 차단 |
| **재처리 가능** — 실패 행 복구 자동화 | **헌법 #22** 데이터 최소주의 |
| **감사 추적** — 누가 언제 어떤 데이터로 실패했는지 | **개인정보보호법 §29** 안전성 확보조치 |

## 3. 선택지

### A안: JSON TEXT (운영 편의 우선)
```sql
raw_data JSON NULL
```
- 장점: 사람이 읽고 즉시 디버깅 가능. SQL 인덱싱 가능 (`JSON_EXTRACT`)
- 단점: **평문 형사영역 데이터 노출** → 헌법 #18 위반 가능성. DBA가 접근 시 즉시 사고
- 비고: tenant 격리만으로는 부족 (본사 DBA도 못 보게 해야 함)

### B안: VARBINARY 암호화 (보안 우선)
```sql
raw_data VARBINARY(8000) NULL  -- AES-256 암호화
raw_data_format VARCHAR(10) NULL  -- 'JSON' 등 메타
```
- 장점: 형사영역 보호 완벽. 복호화 키 보유자만 조회 가능
- 단점: 디버깅 시 매번 복호화 필요. SQL 검색 불가
- 비고: 기존 `IBinaryCryptoService` 재사용 가능

### C안: 하이브리드 (민감 필드만 마스킹된 JSON)
```sql
raw_data JSON NULL  -- 민감 필드는 사전 마스킹
raw_data_full VARBINARY(8000) NULL  -- 평문 백업 (선택적)
```
- 장점: 일상 디버깅은 JSON으로 빠르게. 필요 시만 VARBINARY 복호화
- 단점: 컬럼 2개. 코드 복잡. 마스킹 규칙 누락 위험
- 비고: `SensitiveFieldMasking` 헬퍼 이미 존재

### D안: 외부 분리 저장
- raw_data 자체를 DB에 안 넣고, 별도 암호화 파일 시스템 (`/var/hitpan/migration_errors/{job_id}/{row_id}.aes`)
- 장점: DB 백업에 형사영역 안 섞임 (헌법 #22 강력 준수)
- 단점: 파일·DB 동기화 운영 부담. 베타 D-63 일정에 무리

## 4. 어벤져스 리뷰

| 매니저 | 의견 | 추천 |
|---|---|---|
| DB 매니저 | JSON이 운영상 압도적. 다만 형사영역 직격탄 | C안 |
| 보안 매니저 | 헌법 #18 절대 우선. **JSON 평문은 불가**. B안 또는 D안 | **B안** |
| 법무팀장 | 개인정보보호법 §29 + 신용정보법 §19 — DB 평문 저장 시 행정처분 리스크. 형사영역 0건 평문 원칙 | **B안** |
| 백엔드 매니저 | C안 매력적이나 마스킹 누락 시 사고. 작업량 대비 위험 | B안 |
| 본부장 춘식 | 베타 D-63. C안 일정 부담. B안 안전 + 단순 | **B안** |
| AI수석 | C안 매스킹 자동화 어려움. raw 데이터 컬럼 셋이 매번 다름 (partners/items/employees/거래/원장…) | B안 |

**다수 의견: B안 (VARBINARY 암호화)** — 보안·법무·일정 3축 일치.
