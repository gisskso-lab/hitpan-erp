## 1. 무엇이 고장났나 (검증팀 실측)

격리 DB 에 출하 DDL 을 그대로 넣어 신규 설치를 재현한 결과:

| 확인 | 결과 |
|---|---|
| `device_slot_policy_settings` 행 수 | **0행** |
| `schema_migrations` 의 DB-104 | **이미 `success=1`** (`hitpan_db_clean.sql:3354`) |
| `MigrationRunner.cs:91-104` | `success=1` 이면 **건너뛴다** |

⇒ **신규 고객은 정책 표가 영원히 비어 있고 항상 `FallbackLimits`(코드 상수)로 돈다.**
⇒ **작3 의 목적이 신규 고객에게 무력하다.** 그리고 신규 설치와 업데이트가 서로 다르게 동작한다.

### 🔴 진짜 원인 — 시드가 아직 없는 것을 기준으로 돈다

DB-104 시드의 기준:
```sql
FROM (SELECT DISTINCT tenant_id FROM local_subscription) AS t
```
**신규 설치 시점에는 `local_subscription` 이 0행이다.** 회사가 아직 만들어지기 전이기 때문이다.
그 뒤 회사가 만들어져도 DB-104 는 이미 성공 표시라 다시 돌지 않는다.

⚠️ **회귀가 아니다.** 숫자는 종전(코드 상수)과 같으므로 지금 당장 요금이 틀리지는 않는다.
다만 **설정화가 실제로는 안 된 것**이고, 대표가 화면에서 고쳐도 반영될 표가 없다.

### 🔴 게이트가 없던 자리다

게이트 13/13 이 **전부 통과했는데도 남았다.** 게이트가 틀린 게 아니라 **없었다.**
더 나쁜 것은 `ddl-smoke` 가 오히려 그 시드 줄을 **요구**해서 결함을 만드는 방향으로 작용했다.

## 2. 어떻게 봉합하나 — 선례가 바로 옆에 있다

**`CompanyBootstrapProvisioner.cs:340-375` 가 `labor_policy_settings`(DB-96)를 같은 방식으로 시드한다.**
DB-96 도 같은 구조(테넌트별 기준값 표)이고 같은 문제를 이미 이렇게 풀었다.

⇒ **같은 자리에 같은 방식으로 붙인다.** 새 구조를 만들지 않는다.

### 하는 것
- [ ] `CompanyBootstrapProvisioner` 회사 생성 경로에 **기기 슬롯 기준값 시드** 추가
- [ ] 시드 값은 **DB-104 와 한 글자도 다르지 않게** (basic 5/3 · pro 10/8 · enterprise 100/80 ·
      premium 100/80 · trial 10/5 · default 5/3 · 추가슬롯 1+1 · 가격 10000)
- [ ] **멱등** — `INSERT … WHERE NOT EXISTS` (DB-96 선례와 동일). 두 번 돌아도 안 늘어난다
- [ ] 🔴 **이미 손댄 회사는 건드리지 않는다** — DB-104 의 `WHERE NOT EXISTS (… p.tenant_id = t.tenant_id)`
      의도를 그대로 유지 (헌법 #1 · #11)
- [ ] 🔴 **게이트 신설** — 신규 설치 후 정책 표가 **비어 있지 않은지** 검사 (아래 §4)

### 하지 않는 것
- ❌ **DB-104 파일 수정** — 이미 적용된 고객이 있을 수 있다. 마이그는 되돌리지 않는다
- ❌ **clean DDL 의 `('DB-104','clean-ddl',1)` 제거** — `ddl-smoke` 가 그 줄을 요구한다.
      건드리면 다른 게이트가 깨진다. **회사 생성 경로에서 채우는 쪽이 옳다**
- ❌ **숫자 변경** — 값은 그대로. 이 봉합으로 한도가 하나도 안 바뀌어야 한다
- ❌ 백오피스 동기화 (2차) · 열쇠 교체 · 중간 화면 (2차)
- ❌ 검증팀이 새로 찾은 별건들 (§6) — **이번 범위 아님**

## 4. 🔴 게이트 — 이번 봉합의 핵심

**R-1 은 게이트가 없어서 살아남았다.** 봉합보다 게이트가 더 중요하다.

| 게이트 | 검사 | 반증(빼면 FAIL 하는가) |
|---|---|---|
| **G-19** | 회사 생성 후 `device_slot_policy_settings` 가 **비어 있지 않다** | 시드 호출을 빼면 FAIL |
| **G-20** | 시드된 값이 **`FallbackLimits` 와 일치**한다 | 값을 하나 바꾸면 FAIL |
| **G-21** | 회사 생성을 **두 번** 돌려도 행이 **안 늘어난다**(멱등) | `WHERE NOT EXISTS` 를 빼면 FAIL |
| **G-22** | 이미 값을 고친 회사는 **덮어쓰지 않는다** | 덮어쓰게 바꾸면 FAIL |

🔴 **글자만 검사하는 게이트를 만들지 마라.** 검증팀이 `P25` 를 **가짜 게이트**로 판정했다 —
인덱스 이름 문자열만 봐서 `NOT NULL DEFAULT ''` 로 바꿔도 초록불이었고, 그 DDL 이면 두 번째 기기부터 1062 로 죽는다.
**동작을 검사해라.** 실제로 회사를 만들고, 표를 읽고, 행이 있는지 본다.
