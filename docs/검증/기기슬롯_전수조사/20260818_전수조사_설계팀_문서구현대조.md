## 2. 거짓 완료 보고 목록 — 문서 인용 vs 코드 인용

### ■ 거짓 #1 — "hardware_id 칸 신설(DB-103) ✅" (칸만 만들고 배선 0)

- **문서 주장**: `DB-103_tenant_devices_hardware_id.sql:98` — *"`fingerprint` **격하** … 새 기기는 `hardware_id` 로 잡는다"*, 출하DDL `installer/hitpan_db_clean.sql:3734` 도 같은 문구를 **고객 DB 에 실어 보냈다.**
- **코드 실측**: `hardware_id` 를 SELECT/INSERT/UPDATE 하는 코드가 **ERP 본체에 0곳.**
- 🔴 **가장 나쁜 점**: DB 주석이 *"지문은 격하됐다"* 고 **거짓말을 고객 DB 에 새겨 넣었다.** 실제로는 지문이 여전히 유일하게 작동하는 열쇠다(`TenantDeviceService.cs:224-226`).
- ⚠️ 이것을 **2차 개발명세서 스스로 인정했다** — `20260816_개발명세서_2차 §1-2`: *"어제 1차는 컬럼만 깔고 배선을 안 했다."* 그런데도 **1차 인수인계서·일일보고서는 이 건을 완료로 보고했고 1.2.81 로 게시했다.**

### ■ 거짓 #2 — "2차에서 hardware_id 를 1순위 열쇠로 썼다" (다른 컬럼을 썼다)

- **문서 주장**: `20260816_개발명세서_2차 §2` 표 — *"**1겹 — 알아보기**: `hardware_id` 를 **1순위 열쇠**로 쓴다 (지문은 폴백)"*
- **코드 실측**: `TenantDeviceService.cs:211-221` 이 실제로 쓰는 것은 `device_id`(서버 발급 Guid) 다. `hardware_id` 는 **여전히 0곳.**
- 🔴 **두 값은 성질이 정반대다.** `hardware_id` 는 §4-2 가 *"서버가 OS 에서 읽는 변하지 않는 값"* 으로 정의한 것이고, `device_id` 는 **브라우저 localStorage 에 보관되는 값**(`device-fingerprint.js:234-243`)이다. 명세서가 통째로 버리기로 한 그 저장소다.
- ⇒ **명세서 §2 표를 그대로 읽으면 1겹은 구현되지 않았다.** 이름만 옮겨 적었다.

### ■ 거짓 #3 — "§17-1 열쇠를 AND 로 바꿨다" (OR 로 구현됐다)

- **문서 주장**: 명세서 §17-1 — *"🔴 **인증키만으로는 찾지 못하게 한다.** OR 로 읽으면 인증키를 옮겨 적은 기기가 남의 줄에 붙어 **요금이 샌다**"*. 2차 작지서가 이 절을 근거로 인용.
- **코드 실측** — `DeviceAuthMiddleware.cs:109-172`:
  ```
  if (authKey 있음)          ok = (auth_key_hash 만으로 조회)      // ← device_id 안 봄
  if (!ok && deviceId 있음)  ok = (device_id 만으로 조회)          // ← auth_key 안 봄
  if (!ok && account_type == "tenant_admin") ok = true             // ← 아무것도 안 봄
  ```
  **세 갈래 OR.** AND 는 어디에도 없다.
- **`VerifyAuthKeyAsync`(`TenantDeviceService.cs:596-604`)** 는 §17-1 이 명시적으로 "같이 고친다" 고 지목한 자리인데 **한 글자도 안 바뀌었다** — PI-08 이 인용한 그 SQL 그대로다.
- 🔴 **PI-08(P0)이 "닫혔다"고 명세서 §17-1 이 선언했고, PI-15(P0)가 "안 닫혔다"고 반증했는데, 코드는 PI-15 가 맞다.** 그리고 PI-15 가 지적한 *"통로가 없다"* 는 헤더 추가로 풀렸는데(`DeviceAuthMiddleware.cs:33`), **통로가 생긴 뒤에도 AND 로 안 묶었다.** 오히려 통로가 하나 더 생겨 **OR 갈래가 3개로 늘었다.**

## 4. 문서 모순·순환

1. **🔴 같은 사안 "닫힘 vs 미결"** — `20260816_인수인계서_2차 §7-2` 는 *"**2차 = 중간 화면 + 열쇠 AND + 메인PC 합류**"* 로 **셋 다 미착수**로 적었다. 그런데 그 다음 커밋 `db98fa3`(2차)은 *"관문을 세웠다"* 고 선언했고 `20260816_개발명세서_2차` 는 R-1~R-5 완료로 적었다. **실측하면 중간화면=자리 안 옮김·열쇠 AND=OR 로 구현·메인PC 합류(§4-5)=0곳** ⇒ **인수인계서의 "미착수" 쪽이 실제에 더 가깝다.**

2. **🔴 §17-1 이 PI-08 을 "닫았다"고 선언 → PI-15 가 "못 닫는다"고 반증 → 코드는 PI-15 가 맞음.** 그런데 **PI-15 는 지금도 ⬜미봉합**이고, 명세서 §17 제목은 여전히 *"P0 반영"* 이다. **설계 문서가 자기 반증을 흡수하지 않은 채 결재선을 통과했다.**

3. **🔴 PI 14건 전부 ⬜미봉합** — 실제로 닫힌 PI-14·PI-17·PI-19 조차 상태가 안 바뀌었다. **상태 표시가 정보를 전혀 담고 있지 않다.** 반대로 PI-12(*"P0P1P2만 하고 멈추면 지금보다 나빠진다"*)는 **정확한 예언이었는데 아무도 답하지 않았다.**

4. **🟠 판정이 여러 번 뒤집힌 사안**
   - `?? "mobile"` 폴백 — **4번 엇갈림**(병렬검증↔개발팀↔검증팀↔코드리뷰 2회차). 8/16 인수인계서 §4 가 코드로 갈라 **결함 아님**으로 종결. ✅ 이 종결은 코드와 일치한다(`AuthController.cs:60` 가드가 실제로 앞을 막는다).
   - **B-1/CR2-3** — 1차 인수인계서 "P1 요금결함" → 2차 "**죽은 코드**"로 뒤집힘. ✅ 뒤집힌 쪽이 맞다.
   - **`:165` 주석** — *"메인PC 는 슬롯 안 센다"* → §17-6 이 *"코드가 맞고 주석이 틀렸다"* 로 정정. ✅ 코드 `CountUsedSlotsAsync` 에 `is_main_pc` 제외 절 없음 확인.
   - **QR 승인** — 1차 *"QR 띄운 것 자체가 승인"* → 2차 사장님 전결로 **뒤집힘**. ✅ 코드 반영됨.

5. **🟠 폐기·격하된 근거를 계속 인용** — 출하 DDL(`hitpan_db_clean.sql:3734`)이 *"새 기기는 hardware_id 로 잡는다"* 는 **사실이 아닌 문장을 고객 DB 에 심었다.** 다음 개발자는 이 주석을 근거로 삼는다.

6. **🟠 순환 인용** — `일일작업보고서 §2` 는 산출물로 인수인계서를 걸고, `인수인계서 §9` 는 근거로 명세서·PI 를 걸며, **명세서 §17 은 PI 를 "반영했다"고 적는다.** 세 문서가 서로를 가리키는데 **어느 것도 코드를 다시 보지 않았다** — `hardware_id` 배선 0곳이 하루 뒤 2차 개발명세서의 **자체 실측**으로 처음 드러난 이유다.

## 5. 재발 뿌리 분석

**같은 증상(한 기기 = 여러 슬롯)이 네 차례 "봉합 완료"됐다가 네 번 다 재발한 이유는 하나다 — 매번 "기기를 브라우저에게 물어보는" 자리를 그대로 두고, 그 위에서 값의 정교함만 바꿨기 때문이다.** 7/2 는 origin 격리를 잡아 지문을 정교하게(`HFPv2-`) 만들었고, 8/10~8/11 은 판정축을 loopback→`MAIN_PC`→`is_main_pc` 로 옮겼으며(병렬이슈 10 이 *"판정축이 요청 속성에서 서버 속성으로 옮겨갔을 뿐 '항상 참'이라는 성질은 똑같다"* 고 정확히 진단했다), 8/15 는 계수·한도를 모았고, 8/16 은 열쇠를 `fingerprint`→`device_id` 로 바꿨다. **그런데 `device_id` 는 `fingerprint` 와 똑같은 localStorage 에, 똑같은 origin 격리 아래 저장된다**(`device-fingerprint.js:234`). 7/2 실측대본이 무너뜨린 바로 그 전제 위에 8/16 의 봉합이 다시 세워졌다. 설계는 이것을 알고 있었다 — §4-2 는 *"메인PC 는 **서버가 OS 에서 하드웨어 값을 읽는다**"* 로 저장소 자체를 브라우저 밖으로 빼기로 했고, §4-5 를 *"🔴 이 한 가지가 지금 새고 있는 슬롯을 막는다"* 라고 못박았다. **그 한 가지가 네 차수 내내 한 줄도 구현되지 않았다.** 여기에 두 번째 뿌리가 겹친다 — **검증이 코드의 존재가 아니라 문자열의 존재를 검사했다.** G-25 는 정규식으로 SQL 모양을 보고(`DeviceApprovalGateTests.cs:150-157`), G-28 은 함수 호출 유무만 보았다(그래서 static 필드가 forceLoad 로 증발하는 것을 못 잡았고, 관문이 아예 안 뜬 채 1.2.82 가 게시됐다). 가짜 게이트가 오늘까지 **여섯 번**이다(G-8·G-13·P25·G-21×2·G-28). **결론: 재발의 뿌리는 지문 산식도 판정축도 아니라, ①식별값을 여전히 브라우저가 보관한다는 것과 ②그것을 검사해야 할 게이트가 코드 텍스트를 읽고 있다는 것 — 두 가지다.** 설계는 둘 다 정확히 지목했고, 구현은 둘 다 비켜갔다.

## 6. 가장 위험한 것 3가지 (우선순위)

### 🥇 1위 — 열쇠가 OR 다. 남의 인증키·남의 장비넘버로 문이 열린다 (요금 누수 + 접근통제 붕괴)

## 8. 거짓 완료 보고의 유형 분류

| 유형 | 무엇인가 | 건수 | 해당 건 |
|---|---|---|---|
| **① 칸만 만들고 배선 안 함** | DB 컬럼·DTO 필드·헤더 상수는 만들었는데 읽고 쓰는 코드가 없다. **DDL 주석까지 "이제 이걸로 잡는다"고 적어 거짓이 고객 DB 에 새겨진다** | **3** | `hardware_id`(DB-103) / `LoginRequest.DeviceId` 초기(8/15, 8/16에 배선) / `X-HitPan-Device-Id` 헤더(받아만 놓고 AND 에 안 씀) |

| **③ 게이트를 근거로 완료 선언 (가짜 게이트)** | 시험이 **코드 텍스트**나 **DB 제약**을 검사해 초록불이 뜬다. 봉합을 빼도 FAIL 이 안 난다 | **6** | G-8(리터럴 유무) · G-13 · P25 · G-21×2(UNIQUE가 지킴) · **G-28**(호출 유무만 봐서 관문이 안 뜨는 걸 못 잡음) |

## 9. 설계팀 권고 (판정은 PM·CTO·사장님)

1. **PI 14건의 상태부터 코드로 갈라 갱신** — 무엇이 남았는지 세는 것이 먼저다.
2. **§17-1 AND 를 진짜로 건다** — `VerifyAuthKeyAsync` · `DeviceAuthMiddleware` 둘 다. `tenant_admin` 무조건 통과는 **"대표가 막히면 누가 푸나"** 를 다른 방법으로 답하고 좁혀야 한다.
3. **G-1·G-4·G-9 를 만들고 반증까지 확인한 뒤** 다음 게시를 한다(명세서 §5-A-2 가 이미 "배포 금지" 라고 못박은 조건이다).
4. **게이트는 텍스트가 아니라 값·동작으로.** G-8·G-26 이 좋은 본보기다(순수 함수를 시험이 직접 부른다). G-25·G-28 계열 정규식 게이트는 전부 재작성 대상.
5. **`hardware_id` 배선 또는 칸 철회 중 택일** — 지금처럼 "격하됐다"는 거짓 주석만 남기는 것이 최악이다.
