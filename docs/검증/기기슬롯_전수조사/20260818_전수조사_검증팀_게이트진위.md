# 🔴 가짜 판정 9건 — 상세

## 1. B-4 (`DeviceSlotGuardTests.cs:559`) — **산술적으로 실패가 불가능하다**

### 왜 가짜인가
게이트는 `sessions >= devices` 를 주장한다. 그런데 **두 값이 같은 뿌리에서 나온다.**

`SessionLimitMiddleware.cs:51-68`:
```
var pc     = SlotPolicyDefaults.Value($"tier.{tier}.pc_limit", 0);
var mobile = SlotPolicyDefaults.Value($"tier.{tier}.mobile_limit", 0);
var fromDevices = (int)Math.Ceiling((pc + mobile) * SessionHeadroom);  // SessionHeadroom = 1.5
var limit = Math.Max(fromDevices, floor);
```
시험도 같은 `SlotPolicyDefaults` 에서 `devices = pc + mobile` 을 만든다.
⇒ 주장은 `max(ceil(d*1.5), floor) >= d` 이고, **d ≥ 0 이면 `ceil(d*1.5) >= d` 는 항상 참**이다.

**실측 반증**: pc 0~500 × mobile 0~500 × floor 5종 전수 대입 → **반례 0건.**
어떤 요금제 숫자를 어떻게 바꿔도 이 시험은 빨간불이 될 수 없다.

### 봉합을 어떻게 빼면 통과하는가
**뺄 봉합이 없다.** `enterprise` 를 `LegacyFloor` 에서 빼도, `SlotPolicyDefaults` 숫자를 아무렇게나 바꿔도 통과한다.
게이트가 지킨다고 적은 그 결함(`enterprise` 누락)은 **`Math.Max` + `*1.5` 구조가 이미 구조적으로 불가능하게 만들었고**, 시험은 그 구조를 재확인할 뿐이다.
🔴 유일한 실패 조건은 **`SessionHeadroom` 을 1.0 미만으로 낮추는 것** 하나뿐 — 즉 이 시험은 사실상 `SessionHeadroom >= 1.0` 게이트다.

### 무엇을 검사해야 진짜가 되는가
- 시험이 **자기 기대값을 하드코딩**해야 한다: `enterprise` → 최소 180, `basic` → 최소 8 … 을 시험 파일에 적고 대조.
- 또는 `SessionHeadroom` 이 **1.0 이상인지**를 별도 게이트로 명시하고, B-4 는 **tier 목록 자체의 누락**(`LegacyFloor` 와 `SlotPolicyDefaults` 의 tier 집합이 같은가)을 본다.

## 2. B-3 (`DeviceSlotGuardTests.cs:598`) — **고객에게 가지 않는 파일을 검사한다**

### 왜 가짜인가
게이트가 읽는 것은 `scripts/pricing_plans_seed.sql` **파일**이다.
그런데 이 값을 실제로 쓰는 것은 **NCP 백오피스 DB 의 `pricing_plans` 테이블**이다
(`src/HitPan.Backoffice.API/Controllers/DeviceRegistrationController.cs:65-69` 가 그 테이블을 조회한다).

🔴 **이 스크립트는 아직 NCP 에서 실행되지 않았다** (사장님 결재 대기 중 — 인수인계 기록).
⇒ **파일은 옳고 DB 는 틀린 상태에서 게이트가 초록불**이다. 이것은 [[project_fixed_vs_delivered_gap]] 의 정확한 재발이다 —
**"고쳤나"는 보는데 "갔나"는 안 본다.**

### 봉합을 어떻게 빼면 통과하는가
NCP `pricing_plans` 의 `basic.max_mobile_devices` 를 0 으로 되돌려도 **이 시험은 초록불**이다.
파일만 맞으면 되기 때문이다. 그리고 그 0 이 바로 게이트 주석이 스스로 적은 결함
(*"typeCount >= 0 이 항상 참 ⇒ 한 대도 등록 못 한다"*)이다.

### 무엇을 검사해야 진짜가 되는가
- 파일 대조는 유지하되, **판정 대상을 실제 테이블로 옮긴다** — 격리 DB에 백오피스 DDL + 이 시드를 넣고 `DeviceRegistrationController` 의 조회 SQL 을 실제로 돌려 한도 값을 읽는다(`DeviceSlotSeedGateTests` 방식).
- 최소한 **"이 스크립트가 NCP 에 적용되었는가"** 를 별도로 기록·확인하는 절차 게이트가 있어야 한다.

## 3. G-24 (`DeviceApprovalGateTests.cs:87`) — **식별자 이름만 보면 우회된다**

### 왜 가짜인가
두 assert 가 전부 텍스트다:
```
code.Contains("deviceAwaitingApproval")            // 낱말이 있나
Assert.False(Regex.IsMatch(code, @"if\s*\(\s*!\s*allowed\s*\)"))   // 이 정확한 모양이 없나
```

### 봉합을 어떻게 빼면 통과하는가 — **실측 반증 성공**
`AuthController.cs:138` 의 한 줄을 이렇게 바꾸면 **승인 대기 기기가 다시 401 로 막히는데 게이트는 초록불**이다:
```
if (!allowed && !deviceAwaitingApproval)   →   if (!allowed && deviceAwaitingApproval is bool)
```
`deviceAwaitingApproval` 낱말은 **그대로 남아** 첫 assert 통과, `if (!allowed)` 라는 **정확한 모양은 아니므로** 둘째 assert 통과.
그런데 `is bool` 은 항상 참이라 **`!allowed` 인 모든 요청이 401** — P0 가 그대로 되살아난다.
(같은 효과: `if (!allowed && true)` · `if (allowed == false)` · `if (!(allowed))`)

# 🔴 가짜 게이트가 반복 생산되는 구조적 이유 — 방법의 결함

G-8 · G-13 · P25 · G-21 · G-28 이 **사람이 게을러서** 반복된 게 아니다.
다섯 건을 나란히 놓으면 **같은 방법론적 결함 다섯 개**가 보인다.

### (1) 🔴 **게이트를 봉합과 같은 시각에, 같은 사람이, 같은 머릿속 모형으로 짠다**
봉합을 막 끝낸 사람은 *"내가 무엇을 고쳤는지"* 를 안다. 그래서 게이트가 **고친 것을 확인**한다.
그런데 게이트의 임무는 정반대다 — **고쳐지지 않은 경우를 찾는 것**이다.
⇒ *"내가 `MarkAwaitingApproval` 을 붙였으니 그게 있는지 보자"* 는 **확인**이고, G-28 은 정확히 그렇게 짜였다.
**확인은 반증이 아니다.** 검증팀 SoD(작성자 ≠ 검증자)가 게이트 자체에는 적용되지 않고 있다.

### (2) 🔴 **"검사하기 쉬운 것"이 "검사해야 하는 것"을 밀어낸다**
동작 검사는 대상 코드를 부를 수 있게 열어야 하고(내부 메서드 `internal`, DI 가짜 주입, 격리 DB), 시간도 든다.

⇒ 마감이 걸리면 **언제나 텍스트가 이긴다.** 그리고 텍스트 게이트는 **처음엔 진짜처럼 초록불이 뜬다** — 차이가 안 보인다.
`DeviceSlotSeedGateTests`(격리 DB·실 Provisioner, 게이트당 6~9초)가 가장 건강하고,
`DeviceApprovalGateTests`(전부 밀리초 단위 텍스트)가 가장 병든 것은 **우연이 아니다.**
🔴 **실행 시간이 곧 게이트의 깊이다** — 밀리초로 끝나는 게이트는 대개 글자만 본다.

공정에는 *"통과했나"* 를 묻는 단계는 있는데 *"무엇이 통과시켰나"* 를 묻는 단계가 **없다.**

`var ok = true;` 는 알아도 `bool ok = true;` 는 모른다.
⇒ 코드가 **정상적으로 진화하기만 해도** 게이트는 조용히 아무것도 안 지키게 된다.
그리고 **아무것도 안 지키게 된 순간에도 초록불**이라 아무도 모른다.
**부패해도 경보가 없는 안전망**이다.

### (5) 🔴 **"칸을 만드는 것"과 "배선하는 것"의 경계에 게이트를 세우지 않는다**
반복 사고의 형태가 매번 같다 — 1차 `hardware_id`(컬럼만·배선 0), G-28c `getDeviceId`(함수만·호출 0),
G-28 `MarkAwaitingApproval`(호출은 함·값은 증발), B-3(파일은 옳음·DB 는 안 감).
전부 **A 는 있는데 A→B 가 없는** 형태다.
그런데 텍스트 게이트는 **A 의 존재만 본다.** 구조적으로 이 계열의 결함을 **볼 수 없는 도구**로
이 계열의 결함을 막으려 하고 있다. [[project_fixed_vs_delivered_gap]] 이 4차까지 반복된 것과 **같은 병**이다.

> **한 줄 요약**: 게이트를 *만든 것을 확인하는 도구* 로 쓰고 있다.
> 게이트는 *만든 것이 무너지는 경우를 찾는 도구* 여야 한다. 도구의 용도를 잘못 잡았기에 사람을 바꿔도 재발한다.

# ✅ 앞으로 게이트를 짤 때의 판정 규칙 (5줄)

1. **짜자마자 봉합을 빼고 빨간불을 눈으로 본다.** 빨간불을 못 본 게이트는 **짜지 않은 것**이다. (반증 실패 시 그 게이트는 폐기)
2. **"초록불이 어디서 오나"를 적는다** — 내 코드 / DB 제약 / 프레임워크 / 산술. **내 코드가 아니면 그 게이트는 가짜다.**
3. **`Contains`·정규식으로 소스를 읽지 않는다.** 값·응답코드·반환타입·DB 행을 본다. 텍스트가 불가피하면 **부정형**(있으면 안 되는 것)에만 쓴다.
4. **A 의 존재가 아니라 A→B 의 도달을 검사한다** — 컬럼이 아니라 저장된 값, 호출이 아니라 살아남은 값, 파일이 아니라 적용된 DB.
5. **게이트는 봉합한 사람이 아닌 사람이 판정한다**(SoD를 게이트에도 적용). 그리고 **밀리초로 끝나는 게이트는 일단 의심한다.**
