# 발견 상세

## [P0-1] 관문이 업무 화면을 덮지 않는다 — 증상③ 직접 원인

**파일:** `src/HitPan.Web/Layout/MainLayout.razor:52` (그리고 `:54~66` 의 `<main>`)

### 무엇이 났나 (코드가 실제로 하는 일)

`DeviceAuthGate` 는 `<main>` 을 **감싸지 않고 그 위에 형제로 놓여 있다.**

```razor
<DeviceAuthGate />

<main class="hitpan-content mud-px-4 mud-py-4">
    <ErrorBoundary>
        <ChildContent>@Body</ChildContent>
```

`DeviceAuthGate.razor` 는 `_awaitingApproval` 이 참일 때 `<div class="hp-device-gate">` 를 하나 그릴 뿐이고, **`@Body` 를 자기 안에 받지 않는다.** 즉 관문이 떠도 그 아래에 사이드바·헤더·업무 화면이 **정상적으로 함께 렌더링된다.** 관문이 `@Body` 를 가리는지는 전적으로 `hp-device-gate` CSS 가 화면 전체를 덮는 오버레이인지에 달려 있는데, 컴포넌트 자체에는 그 보장이 **한 줄도 없다.**

### 왜 결함인가

사장님 설계는 *"로그인 → [디바이스 인증] → 히트판 ERP"* 로 **관문을 통과해야 ERP 가 나오는** 순서다. 지금 구조는 **ERP 와 관문이 동시에 존재**하고 관문은 그 위에 얹힌 딱지다. 승인 안 난 기기가 화면을 스크롤하거나 오버레이를 우회하면 업무 화면에 그대로 닿는다. 사장님이 *"다른기기 로그인 → 요청, 승인 흐름 실패"* 라고 보신 자리가 여기다 — 관문이 뜨긴 하는데 **흐름이 관문에서 멈추지 않는다.**

### 근거

```razor
@* MainLayout.razor:49-54 *@
<DeviceAuthGate />

<main class="hitpan-content mud-px-4 mud-py-4">
    <ErrorBoundary>
        <ChildContent>@Body</ChildContent>
```

`DeviceAuthGate.razor` 전체에 `@Body` · `ChildContent` · `RenderFragment` 가 **0회** 등장한다(파일 317줄 전량 확인).

### 주석 주장 vs 실제

- **주석 주장** (`DeviceAuthGate.razor:10`): *"🔴 로그인은 막지 않는다. **화면만 덮는다.**"*
- **실제**: 화면을 덮는 코드가 없다. 형제로 그려질 뿐이며 덮개 여부는 CSS 에 위임돼 있고 그 CSS 는 컴포넌트가 보증하지 않는다.

## [P0-2] 승인 대기(pending) 기기가 재로그인마다 새 슬롯을 먹을 수 있다 — 증상② 유력 원인

**파일:** `src/HitPan.Infrastructure/Services/TenantDeviceService.cs:209-230`, `:417-444`

### 무엇이 났나

`RegisterOrRefreshAsync` 는 1순위로 `req.DeviceId` 로 기존 기기를 찾고, 없으면 2순위로 지문(`fingerprint`)으로 찾는다. **둘 다 못 찾으면 새 행을 INSERT 한다.**

그런데 **1순위 조회는 `req.DeviceId` 가 비어 있으면 아예 실행되지 않는다**(`:209` 의 `if (!string.IsNullOrWhiteSpace(req.DeviceId))`). 그러면 **지문 하나에만 의존**하게 되고, 지문은 `device-fingerprint.js:48` 의 `_envSeed()` 가 `userAgent` 를 씨앗에 포함하므로 **브라우저·버전이 달라지면 달라진다.**

`req.DeviceId` 가 비는 경로가 실제로 존재한다:

1. **localStorage 가 비어 있는 첫 접속** — 정상. 그러나 그 첫 접속이 `pending` 으로 들어가면 아래 3번과 결합한다.
2. **`hitpanDevice.setDeviceId` 저장 실패** — `device-fingerprint.js:238-241` 이 예외를 통째로 삼킨다(`catch (e) { }`). 사생활보호모드·저장소 가득참·사이트 데이터 차단이면 **조용히 저장이 안 되고 아무도 모른다.**
3. **다른 origin 으로 접속** — `localStorage` 는 origin(scheme+host+port)별로 격리된다. `localhost:5234` ↔ `127.0.0.1:5234` ↔ `{고객사ID}.hitpan.kr` 은 **서로 다른 저장소**다. 이 사실은 같은 파일 `:7-11` 주석이 스스로 인정하고 있다 — 지문은 그 문제를 피하려고 환경해시로 만들었지만, **`hitpan_device_id` 는 그 대책이 없는 순수 localStorage 값**이다.

⇒ 이 경우 서버는 매번 "처음 보는 기기"로 판정해 `:418` 에서 `Guid.NewGuid()` 로 **새 device_id 를 발급하고 새 행을 INSERT** 한다.

### 왜 결함인가

`_approvalEnabled = true`(`appsettings.json:22` 실측 확인)이므로 새 행은 `pending` 으로 들어간다. `CountUsedSlotsAsync` 는 `status='approved'` 만 세므로 **요금은 당장 안 샌다.** 그러나 대표 화면의 승인 대기 목록에 **같은 PC 가 접속할 때마다 한 줄씩 쌓인다.** 사장님이 보신 *"엣지에서 엣지로 띄워도 슬롯 추가됨"* 이 정확히 이 모습이다 — 사장님이 보신 "슬롯"은 **기기 목록의 줄**이다.

### 근거

```csharp
// TenantDeviceService.cs:209
if (!string.IsNullOrWhiteSpace(req.DeviceId))
{
    existing = await _db.QueryFirstOrDefaultAsync<...>(  // ← DeviceId 없으면 통째로 건너뜀
```

```javascript
// device-fingerprint.js:238-241 — 저장 실패를 아무도 모른다
setDeviceId: function (id) {
    try { if (id) localStorage.setItem('hitpan_device_id', id); }
    catch (e) { /* private 모드 등 */ }
},
```

### 주석 주장 vs 실제

- **주석 주장** (`AuthService.cs:60`): *"이 한 줄이 사장님 오더 **'100번을 접속해도 한번만'** 을 성립시킨다."*
- **실제**: 그 한 줄은 **localStorage 가 살아 있을 때만** 성립한다. 저장 실패·origin 변경 시 아무 신호 없이 종전(지문 단독) 동작으로 되돌아간다. 되돌아갔다는 사실을 알려주는 로그도 없다.
- **주석 주장** (`DeviceDtos.cs:87`): *"같은 PC 에서 Edge ↔ Chrome 을 오가도 **한 줄**이다."*
- **실제**: Edge↔Chrome 은 **애초에 localStorage 를 공유하지 않는다.** Chrome 에는 `hitpan_device_id` 가 없으므로 `req.DeviceId=null` → 지문으로 떨어지는데 지문도 UA 가 달라 다르다 ⇒ **반드시 새 줄이 생긴다.** 이 주석은 성립할 수 없는 주장을 하고 있다.

## [P0-3] `gate-status` 는 deviceId 가 없으면 무조건 "통과"를 돌려준다

**파일:** `src/HitPan.API/Controllers/DeviceController.cs:109-110`

### 무엇이 났나

```csharp
if (string.IsNullOrWhiteSpace(deviceId))
    return Ok(new { approved = true, confirmCode = (string?)null });
```

`DeviceAuthGate.razor:202-205` 는 `hitpanDevice.getDeviceId()` 로 읽은 값을 쿼리로 붙이는데, **그 값이 비면 `deviceId` 파라미터 없이 호출**한다. 서버는 그것을 **승인됨으로 답한다.**

### 왜 결함인가

관문의 유일한 진실원이 이 API 다(`DeviceAuthGate.razor:155-158` 이 스스로 그렇게 선언한다). 그런데 **localStorage 가 비면 관문이 스스로 열린다.** P0-2 와 같은 뿌리다 — 저장 실패·다른 origin·사생활보호모드면 미승인 기기가 관문을 그냥 통과한다. 쿼리 파라미터를 지우는 것만으로 통과되므로 **우회 난이도도 사실상 0**이다.

### 근거

주석은 *"deviceId 가 없으면 = 기기 등록 자체를 안 거친 접속(지문 미지원 등). **종전대로 통과시킨다**"* 라고 적혀 있다. 그러나 이 판단은 **로그인 응답이 `DeviceAwaitingApproval=true` 를 준 기기에도 똑같이 적용된다** — 서버는 그 맥락을 여기서 다시 보지 않는다. JWT 로 사용자를 알고 있으므로 `user_id` 로 대기 중인 기기가 있는지 되물을 수 있는데 **묻지 않는다.**

## [P0-4] 대표계정은 기기 인증을 전면 우회한다 — 대표 PC 에서는 승인제 자체가 없다

**파일:** `src/HitPan.API/Middleware/DeviceAuthMiddleware.cs:168-173`

### 무엇이 났나

```csharp
if (!ok)
{
    var accountType = context.User?.FindFirst("account_type")?.Value;
    if (string.Equals(accountType, "tenant_admin", StringComparison.Ordinal))
        ok = true;
}
```

`tenant_admin` 이면 **기기와 무관하게 모든 API 를 통과**한다. 장비넘버도, 인증번호도, `status='approved'` 도 보지 않는다.

### 왜 결함인가

사장님 증상②의 실측 조건이 **"한 PC 에서 엣지에서 엣지로"** 다. 사장님은 대표계정으로 시험하신다. 즉 **사장님이 어떤 브라우저로 접속하든 미들웨어는 100% 통과**시키고, 기기는 조용히 `pending` 으로 계속 쌓인다. 관문(`DeviceAuthGate`)은 화면단이라 이 우회와 별개로 뜰 수 있지만, **API 가 다 열려 있으므로 업무 화면은 정상 동작한다.** ⇒ 사장님 눈에는 *"막히지도 않는데 슬롯만 늘어난다"* 로 보인다.

주석은 *"이 예외가 새로 열어주는 권한은 없고, **막다른 길만 없앤다**"* 라고 주장한다. 그러나 이것은 **메인PC 를 구제하려던 것인데 계정 축으로 구제**해서, 대표가 **집·카페·폰 어디서 접속해도** 기기 검사가 사라진다. 메인PC 축(`is_main_pc` 또는 장비넘버)으로 좁히지 않은 것이 결함이다.

### 주석 주장 vs 실제

- **주석 주장**(`:161`): *"⚠️ **직원 계정(tenant_user)은 그대로 막힌다.** 요금·접근 통제는 유지된다."*
- **실제**: 직원은 막힌다는 말은 맞다. 그러나 **"요금 통제가 유지된다"는 거짓**이다. 대표는 몇 대의 기기로 접속하든 검사받지 않으며, 그 기기들은 `pending` 으로 목록만 늘린다.

### 왜 결함인가

`RegisterMobileByTokenAsync` 는 `deviceId` 를 만들어 돌려주는데(`TenantDeviceService.cs:727`, 반환값 3번째) **폰이 그것을 안 받는다.** ⇒ 그 폰이 다음에 로그인하면 `req.DeviceId=null` 이라 **지문으로만 찾는다.** QR 등록 때 저장한 지문과 로그인 때 만드는 지문은 같은 함수라 대개 맞지만, **폰 브라우저를 바꾸면(사파리로 QR 찍고 크롬으로 로그인) 새 기기가 된다.** P0-2 와 같은 병이 모바일에서 반복된다.

### 주석 주장 vs 실제

- **주석 주장**(`DeviceAuthMiddleware.cs:32`, `AuthController.cs:112`): *"⚠️ **칸만 만들고 넘기지 않으면 아무것도 안 바뀐다** — `hardware_id` 가 1차에서 딱 그렇게 됐다."*
- **실제**: 그 교훈을 적어 놓고 **모바일 경로에서 똑같은 일을 반복했다.** 서버는 deviceId 를 돌려주는데 클라이언트가 안 받는다.

# 증상②·③의 확정 원인

## 증상② — "한 PC 에서 엣지에서 엣지로 띄워도 슬롯 추가됨"

**부분 확정.** 배선 자체는 이번엔 끊긴 곳이 없다 — `device-fingerprint.js:234` → `AuthService.cs:61` → `LoginRequestDto.DeviceId`(`AuthModels.cs:26`) → `LoginRequest.DeviceId`(`:45`) → `AuthController.cs:114` → `RegisterDeviceRequest.DeviceId`(`:92`) → `TenantDeviceService.cs:209` 까지 **이름이 전부 `DeviceId` 로 일치**하고 한 칸도 비지 않는다. 되돌려 저장하는 쪽도 `AuthService.cs:104-108` 에 있고, **pending 이어도 저장된다**(서버가 `AuthController.cs:144` 에서 `response.DeviceId = deviceId` 를 승인 대기 여부와 무관하게 채우기 때문). `Login.razor:231` 의 `forceLoad` 는 저장이 **끝난 뒤**에 일어나므로(저장은 `LoginAsync` 안, 이동은 그 반환 후) **순서 문제는 없다.**

그래서 **"엣지→엣지"가 문자 그대로 같은 프로필의 같은 브라우저였다면, localStorage 는 공유되므로 새 행이 생길 수 없다.** 코드상 그 경로는 닫혀 있다. 새 행이 실제로 생겼다면 남는 가능성은 셋이고, 전부 **P0-2 의 갈래**다: ①두 번째 엣지가 **InPrivate 창**이었다(별도 저장소 → `getDeviceId()=null` → 지문도 UA 가 같아 맞을 수는 있으나, 첫 등록이 `pending` 이면 2순위 지문 조회는 `pending` 행도 찾아내므로 이 경우는 새 행이 **안** 생겨야 한다) ②**접속 주소가 달랐다**(`localhost` vs `127.0.0.1` vs `*.hitpan.kr` — origin 격리로 `hitpan_device_id` 가 안 보이고, 지문은 `_envSeed` 가 origin 을 안 쓰므로 같아서 역시 2순위가 잡아야 한다) ③**저장이 조용히 실패했다**(`device-fingerprint.js:239` 의 삼킨 catch).

🔴 **여기서 코드만으로는 확정이 끊긴다.** 이유는 **2순위 지문 조회(`:222-229`)에 status 조건이 없어 `pending` 행도 찾아내기 때문**이다 — 즉 지문만 같으면 새 행이 생기지 **말아야** 한다. 그런데도 사장님 화면에서 행이 늘었다면, **지문 자체가 두 번 다르게 나왔다**는 뜻이다. 그 경우 원인은 `_envSeed()` 가 쓰는 값 중 **창 크기에 따라 변하는 `screen.availWidth/availHeight`**(`device-fingerprint.js:41`)일 수 있다 — 다중 모니터에서 창을 다른 화면으로 옮기거나 작업표시줄 상태가 바뀌면 이 값이 달라진다. **이것이 가장 유력한 미확정 후보다.** 실측 필요(아래 참조).

## 증상③ — "다른기기 로그인 → 요청, 승인 흐름 실패"

**확정.** 원인은 **P0-1** 이다. `MainLayout.razor:52` 의 `<DeviceAuthGate />` 는 `<main>`(`:54`) 과 **형제**이고 `@Body` 를 자기 자식으로 받지 않는다. 관문이 뜨더라도 그 아래 업무 화면이 함께 렌더링되므로 **"로그인 → 인증 → ERP" 순서가 성립하지 않는다.** 덮개 역할은 전적으로 `hp-device-gate` CSS 에 위임돼 있고 컴포넌트는 그것을 보증하지 않는다.

여기에 **P0-4** 가 겹친다. 사장님은 대표계정으로 시험하시므로 `DeviceAuthMiddleware:168-173` 이 **모든 API 를 통과**시킨다 ⇒ 화면 아래 ERP 가 **데이터까지 정상으로** 그려진다. 관문이 막는 시늉만 하고 실제로는 아무것도 안 막는 상태다.

승인 쪽 흐름 자체(대표 목록 → `pending` 추출 → `approve` → 인증키 발급 → 폴링 3초 → `location.reload`)는 코드상 이어져 있다. 다만 **P1-9**(한도 초과 시 pending 영구 고아)와 **P1-8**(static 상태 공유)이 승인이 안 먹히는 것처럼 보이게 만들 수 있다.
