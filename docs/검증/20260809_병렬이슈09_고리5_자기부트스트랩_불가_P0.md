## 2. 왜 이렇게 됐나

| | 값 |
|---|---|
| 고객 PC 워치독 | **1.2.57** (옛 규칙 — 신규 마이그 = 차단) |
| 1.2.59 패키지 안 워치독 | 1.2.59 (새 규칙 — 경고 후 통과) |
| zip 의 DB-*.sql | 56개 |
| 로컬 `schema_migrations` | 55건 (DB-85 없음) |
| 차집합 | **DB-85 1건 → 차단** |

```
새 규칙을 받으려면  →  옛 규칙을 통과해야 하는데
옛 규칙이 막는 이유가 →  바로 그 새 규칙이 풀려던 것
```

**자기 자신을 배달할 수 없는 구조다.**

---

## 3. 🔴 PM 이 무엇을 놓쳤나

게시 전에 게이트를 **로컬에서 전부 미리 돌려봤다** — migsmoke·시드정합·컬럼·권한정합·빌드·테스트.
전부 통과였다. 그런데 **정작 중요한 하나를 안 봤다**:

> **"지금 고객 PC 에 깔린 버전이, 이 패키지를 어떻게 볼 것인가"**

CI 게이트는 **만드는 쪽**을 검사한다. 이 결함은 **받는 쪽**에 있었다.
빌드가 아무리 초록이어도 잡히지 않는 자리다.

> ⭐ 메모리에 적어둔 *"고쳤다 ≠ 고객에게 갔다"* 의 **4차 재발**이다.
> 이번에 끊긴 자리는 **"게시본과 설치본의 버전 차이"** 였다.
> 1·2차=커밋~main / 3차=main~서버 / **4차=서버~설치본**.

---

## 4. 🟢 다만 안전장치는 설계대로 작동했다

이건 정직하게 기록한다 — 시스템은 옳게 행동했다.

| 단계 | 동작 |
|---|---|
| 백업 | ✅ 교체 전 705KB 덤프 확보 |
| 차단 | ✅ 위험을 감지하고 **교체하지 않음** |
| 복원 | ✅ ERP 되살림 — 39초 만에 서비스 복귀 |
| 기록 | ✅ `blocked` 로 DB 에 남김 |
| 데이터 | ✅ **손상 0** |

**차단이 없었다면** DB-85 컬럼 없이 새 코드가 깔려 회사정보 화면이 500 이었을 것이다.

## 5. 응급 조치 (Sandbox 에 적용함)

게이트는 `schema_migrations` 에 DB-85 가 **있으면 통과**시킨다.
⇒ DB-85 를 **먼저 적용**해 두면 옛 워치독도 "신규 없음"으로 본다.

```sql
ALTER TABLE local_company
  ADD COLUMN IF NOT EXISTS address_detail VARCHAR(200) NULL DEFAULT NULL,
  ADD COLUMN IF NOT EXISTS seal_url VARCHAR(200) NULL DEFAULT NULL,
  ADD COLUMN IF NOT EXISTS header_url VARCHAR(200) NULL DEFAULT NULL;
INSERT IGNORE INTO schema_migrations (migration_id, app_version, success)
VALUES ('DB-85','manual-gate-open',1);
```

실측 결과: 컬럼 3종 생성 확인 · DB-85 success=1 등록 확인 · 워치독 재시작.

새 코드의 고리5 는 **이미 적용된 것을 건너뛰므로**(멱등) 충돌하지 않는다.

⚠️ **이건 이번 한 번뿐이다.** 1.2.59 가 깔리면 새 워치독이 게이트를 통과시킨다.

## 6. 🔴 근본 봉합 — 결재 요청

응급 조치는 **이번 Sandbox 한 대**만 푼 것이다. 실제 고객 PC 는 전부 같은 벽에 막힌다.

| 안 | 내용 | 평가 |
|---|---|---|
| **(가)** | **워치독만 먼저 배달하는 경로**를 만든다 — 워치독은 마이그와 무관하므로 게이트를 안 탄다 | 근본. 다만 새 배포 경로 설계 필요 |
| **(나)** | 설치 프로그램(EXE) 재설치로 1.2.59 를 깐다 | 사장님 *"덮어 재설치는 존재하지 않는 경로"*(2026-07-15) 에 어긋남 |
| **(다)** | 게시 전 **로컬 DB 에 마이그를 미리 적용**하는 절차를 CS 매뉴얼화 | 고객 손이 들어간다 — 헌법 #30(고객 손 0) 위반 |
| **(라)** | 옛 워치독이 **DB-85 만 예외 통과**하도록 서버가 신호를 준다 | manifest 로는 불가(옛 코드가 그 필드를 안 읽음) |

**PM 의견은 (가)입니다.** 이유는 —
워치독은 **DB 스키마와 아무 상관이 없다**. 그런데 지금은 ERP 와 한 zip 에 묶여 같은 게이트를 탄다.
워치독만 따로 갱신할 수 있으면 이런 교착이 구조적으로 사라진다.

⚠️ 단 (가)는 **새 배포 경로**라 설계·검증이 필요하다. 오늘 밤 일이 아니다.

### 그 전까지의 현실적 순서

1. **Sandbox 에서 1.2.59 를 먼저 통과시킨다**(응급 조치 완료 — 지금 진행 중)
2. 1.2.59 가 깔리면 **그 워치독은 새 규칙**을 갖는다
3. 이후 게시부터는 **DB 가 바뀌어도 팝업 한 번**으로 간다
4. (가)는 별도 작업지시서로 올린다
