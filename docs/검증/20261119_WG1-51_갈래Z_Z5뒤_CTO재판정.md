## §1 분류 행 j 유권해석 (CTO 자기 규칙 · 전결)
- **기록(공식) = ⓓ 미분류(장치 탓으로 셈).** 행 j 는 7차 §5-3 · 8차 0단에서 런 전에 고정했다. 결과를 본 뒤 칸을 새로 만들거나 ⓐ · ⓑ 조건을 넓혀 맞추면, 결과에 맞춰 규칙을 고치는 꼴이 된다(갈래로 쪼갠 조건은 뒤에서 넓히지 않는다).
- **덧붙임(재설계 방향용) = 「ⓓ-R1 CI 환경 글꼴 겹」**: 「T8 빨강(글꼴 칸 Lato) + 제품 기본 폼 글꼴 칸 한글 0 · 같은 대체 글꼴 이름」. 「장치 탓으로 셈」 의 뜻은 측정 환경(리눅스 러너)이 고객 환경(윈도우 · 맑은 고딕 있음)과 달라서 생긴 실패라는 것이다. 그래서 **제품 판정 = 0 · 이 런을 제품 결함 근거로 쓰지 않는다.** 대표 §50 W5 셋째 줄 「장치 탓으로 멈추면 Z 시험은 끝내고 장치를 다시 설계해 원인 자료와 함께 보고」 가 그대로 적용된다.
- **F-Z5-1 = 내 잘못.** ⓐ 「사유 = 자체시험**만**」 과 ⓑ 「**T8 초록**」 이 둘 다 이 꼴을 막는 조건이었다. 그래서 7차 §3 본문에서 예상했던 「같은 글꼴 이름이라 제품 PDF 와 함께 무너짐」 이 행으로 옮겨지지 않았다.
- **메우는 법(앞으로 · 재설계 분류표)**: T8 {초록 · 빨강} × 제품 기본 폼 {한글 낱말 있음 · 없음} **2×2 네 칸을 먼저 다 채우고**, 그 밖의 경우만 ⓓ 로 둔다. 네 칸 = ⑴ 빨강+없음 = 환경 글꼴 겹 ⑵ 빨강+있음 = T8 하네스 결함 ⑶ 초록+없음 = 단계 차례 · 제품만의 글꼴 길(R2) ⑷ 초록+있음 = 좌표 규칙(R3) 또는 그 밖. 「없음」 칸은 글꼴 칸 이름(T8 과 같은 대체 글꼴인지)으로 가른다. 재설계 첫 런 전에 명세서에 고정한다. **완비 검사는 작성자가 아닌 [4] 가 네 칸을 세어서 확인한다**(진입 조건 C9 · §3).

### 2-2 추천 = (가) 필수 · (나) 별건 · (다) 예비
- **(가) 가 필수인 까닭**: 비교 기준(main)은 고치기 전 판이라 제품 코드를 넣을 수 없다. 리눅스에서 main 칸을 읽을 수 있게 하는 길은 러너 환경을 고치는 것뿐이다((다) 제외). 고객 PC 는 윈도우이고 맑은 고딕이 있다. 러너를 고객 환경 쪽으로 맞추는 것이 「실사용 경로부터」 에 맞는다.
- **맑은 고딕 파일은 어디에도 두지 않는다**(러너 · 공개 저장소 · 산출물 · 설치본). 윈도우에 딸려 오는 글꼴이라 재배포 허락이 없다고 본다(【확인 필요 · 법무팀장 1줄】). 대체 글꼴은 OFL 만 쓴다.
- **7차 §4-3 「글꼴 설치는 main 기대 행 비교 기준을 흔듦」 은 뒤집는다**(CTO 자기 규칙). 그 걱정은 Z4 환경과 이어지는지였는데, Z 트랙이 main 칸 판정 0 으로 끝나 지킬 기준선이 없다. 두 판이 한 런 · 한 환경에서 함께 차려지면 비교 기준은 선다.
- **(가) 의 조건(반증)**
  - **G1 별칭이 먹나 = 【가설】.** Z5 에서 `fonts-wqy-zenhei` 를 깐 뒤에도 T8 은 Lato 였다. 렌더 라이브러리가 글꼴을 이름으로만 찾고 운영체제의 대체 규칙을 따르지 않을 수 있다. → **런 자리를 쓰기 전에 이 PC 안 리눅스 상자(컨테이너)에서 T8 하네스만 돌려 확인한다**(앱 · DB · 5257/5234 0 · 디스크는 PM 이 판단). 안 먹으면 차례로 ⓐ 별칭을 다른 꼴로(강한 묶음) ⓑ 이름을 바꾼 OFL 글꼴 파일을 러너에만 둠(법무 1줄 · 상표 · OFL 수정본 조항) ⓒ (다) 로 다시 여쭘.
  - **G2 단계 차례**: 별칭이 먹어도 API 가 글꼴보다 먼저 뜨면 옛 목록으로 그릴 수 있다(7차 §9-3 미확인 · Z5 에서 API 10:21:00 기동 → 글꼴 10:21:41). → 글꼴 · 별칭 · 글꼴 목록 갱신을 API 기동 앞에 둔다.
  - **G3 글자 폭**: 대체 글꼴은 맑은 고딕과 글자 폭이 달라 줄바꿈 · 잘림 · 좌표(R3 ±1.5mm)가 고객 출력과 다를 수 있다. → 그런 칸에는 「대체 글꼴 기준」 꼬리표를 단다. 판정은 같은 글꼴끼리 두 판을 비교한 것만 쓴다. 절대 좌표 확인은 이 PC(윈도우 · 실물 맑은 고딕 · C3 충족)에서 한다.

## §3 갈래 A~F 계속 여부 · 머지 · R1
- **멈춤 ⓐ ⓑ 「판단 불가」 → §5-4 「A~F 전부 멈춤」 에 해당하지 않는다.** §5-4 와 대표 §39 Q2 답(「비교 시험에서 원인이 다르다고 나오면 그때 멈춤」)의 걸쇠는 **원인이 다르다는 증거**다. Z5 의 판정 칸은 0이라 그런 증거도 0이다.
- **반증 — 판단 불가는 안전하다는 뜻이 아니다.** 전제를 검사할 장치가 사라졌을 뿐이다. 전제가 틀릴 위험(8/27 작7 꼴)은 Z5 전과 그대로이고, 검사 시점만 R1 로 밀렸다. **손실 상한이 「Z5 한 바퀴 코딩분」 에서 「재설계 + R1 한 바퀴 코딩분」 으로 늘어난다**(【가설】 +2~3일). 대표께 보고하고 Q-Z1 에서 함께 고르시게 한다.
- **갈래별**
  - **계속**: A · B · D · E⑴⑶(화면 두 파일) · E⑵ · F-1 · F-2(P-4 뒤 그대로). 이들의 근거는 대표 결재(Q3 · Q8 · Q9 · Q11 · Q12 · Q13)이지 Z 측정이 아니다.
  - **막힘 유지**: **C**(고칠 자리 = main 경우표 ⓔ 의 빨강 칸 · 측정 0) · **E 의 `DocumentController.cs` 부분**(「Z 가 쓰임 확인 뒤」). 둘 다 R1 의 main 칸 경우표가 나온 뒤로 미룬다. C 는 R1 결과를 보고 고쳐 R2 이후에 잰다.
- **머지 = 0 유지 → R1 통과(+ 평소 관문) 뒤.** 대표 Q2 의 「Z5 [4] 결과 뒤」 는 글자로는 풀렸다. 하지만 측정 전에 머지하면 검증 전 머지가 되고, R 판의 main 칸이 가지 이름을 따른다면 비교 기준(고치기 전 판)이 지워진다. 확인 필요: R 판의 「main」 칸이 SHA(`75ed728b`)로 고정돼 있는지. 대표 결재를 조이는 쪽이라 CTO 판정으로 하고 대표께 보고한다.
- **R1 = 지금 금지 → 재설계 + 진입 판정 뒤.** 지금 쏘면 같은 글꼴 때문에 또 0칸이 나와 R 한 자리를 버린다. R 0/6 · 합계 4/10.

  - **C9 분류표 2×2 완비**: [4] 가 센다(§1).

## §5 대표 보고 줄(쉬운 한글)
1. 고치기 전 판과 비교하는 시험(Z5)도 시험 장치 쪽 문제로 결과를 하나도 내지 못했습니다. 결재하신 대로 Z 시험은 여기서 끝냅니다(Z 4번 다 씀 · 전체 10번 중 4번 씀 · 고친 판 시험 6번은 그대로 남음).
2. 원인은 하나로 확인했습니다. 리눅스 시험 PC 에 「맑은 고딕」 글꼴이 없어서, 시험 장치와 히트판 인쇄물이 둘 다 한글을 빈칸으로 그렸습니다. 고객 PC(윈도우)에는 맑은 고딕이 있으므로 고객에게 같은 일이 생긴다는 근거는 아닙니다. 원인 자료는 Z5 직접 대조 리뷰서 · 이 재판정서 · 시험 런 44504346338 기록에 있습니다.
3. 장치는 이렇게 다시 짭니다. 시험 PC 에 무료 공개 한글 글꼴을 깔고 「맑은 고딕」 이름으로 잡히게 합니다. 제품 코드와 설치 파일은 바꾸지 않고, 맑은 고딕 파일은 재배포가 안 되므로 쓰지 않습니다. 시험 자리를 쓰기 전에 이 PC 안에서 먼저 확인합니다.
4. 인쇄를 고치는 개발(A~F)은 계속합니다. 원인이 다르다는 증거는 나오지 않았습니다. 다만 비교 확인이 첫 고친 판 시험(R1)으로 밀려서, 그때 원인이 다르다고 나오면 버리는 작업이 2~3일 치로 늘 수 있습니다. 합치기(머지)는 R1 통과 뒤에 합니다.
5. 거래명세서 시험 칸 39개는 세 번 연속 목록이 비어 시험 준비가 안 됐습니다. 코드를 읽어 원인을 먼저 가르고, 제품 문제로 나오면 바로 보고드리겠습니다. 덧붙여, 글꼴이 없을 때 히트판이 경고 없이 한글을 비운 채 인쇄하는 것을 찾았습니다. 고객 PC 에서 생길 가능성은 낮아 보여 따로 적어 두고, 크기를 확인한 뒤 여쭙겠습니다.
