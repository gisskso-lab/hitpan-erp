## 0. 한 줄

**설정 조회가 실패하면 화면이 "하드코딩 기본값"을 진짜 설정처럼 보여주고,
사용자가 거기서 저장을 누르면 회사 전체 재고·단가·권한 정책이 그 기본값으로 덮어써진다.
오류 안내는 한 줄도 없다.**

## 1. 코드로 확인한 경로 (전 구간 실측)

### ① 실패를 삼킨다 — 로그조차 없다

`src/HitPan.Web/Services/SettingsService.cs:15-26`

```csharp
public async Task<TenantSettingsModel?> GetAsync(CancellationToken ct = default)
{
    try { return await http.GetFromJsonAsync<TenantSettingsModel>("api/settings", ...); }
    catch (Exception)
    {
        return null;          // 🔴 로그 0줄. 헌법 #15 정면 위반
    }
}
```

> 헌법 #15 — *"빈 catch 금지 — 최소 `_logger.LogWarning(ex, ...)` 한 줄"*
> 같은 파일에 이런 catch 가 **5곳**(`:22`, `:35`, `:50`, `:66`, `:89`).

### ② 실패를 정상처럼 그린다

`src/HitPan.Web/Pages/Settings.razor:331-352`

```csharp
var result = await SettingsSvc.GetAsync();
if (result != null)          // 🔴 null 이면 그냥 건너뛴다. else 가 없다
{
    _s = result;
    ...
}
_priceGrades = new List<PriceGradeModel> { new("A단가", _s.PriceARate), ... };
_loading = false;            // 🔴 로딩 끝. 화면은 "정상"으로 보인다
```

`_s` 는 필드 초기값 `new TenantSettingsModel()` — **하드코딩 기본값**이다.
사용자는 이것이 자기 회사 설정이라고 믿는다. **구분할 방법이 화면에 없다.**

### ③ 그 기본값을 서버로 전송한다

`src/HitPan.Web/Pages/Settings.razor:378-384`

```csharp
_s.AutoVatAdjust = !_autoVatOff;
_s.PriceARate = _priceGrades[0].Rate;   // ← 기본값 1.00
... B·C·D·E 동일
```

### ④ 서버가 전 컬럼을 덮어쓴다

`src/HitPan.Application/Services/SettingsService.cs:121-180+`

```sql
INSERT INTO tenant_settings (tenant_id, allow_force_price_input, ..., industry_type)
VALUES (...)
ON DUPLICATE KEY UPDATE        -- 🔴 27개 컬럼 전체 덮어쓰기
```

부분 갱신이 아니다. **화면이 들고 있던 값 전체가 진실이 된다.**

## 2. 사용자가 실제로 겪는 것

```
1. 서버 순단 · 토큰 만료 · 일시적 500  (드문 일이 아니다)
2. 직원이 사용환경 설정을 연다
3. 화면 정상. 로딩바도 정상적으로 사라진다. 오류 표시 0건
   → 실제 DB: "마이너스 재고 허용 = ON",  화면: OFF
4. 직원이 딴 항목 하나만 바꾸고 [저장]
5. 27개 컬럼 전부가 기본값으로 덮어써진다
```

**초기화된 것 중에는 이런 것들이 있다:**

| 컬럼 | 의미 | 잘못 초기화되면 |
|---|---|---|
| `allow_minus_stock` | 마이너스 재고 허용 | 재고 정책이 뒤집힌다 |
| `price_a_rate` ~ `price_e_rate` | 단가 등급 배율 | **판매 단가가 전부 틀어진다** |
| `credit_limit_amount` | 여신 한도 | 여신 관리가 무력화 |
| `force_edit_require_password` | 강제수정 암호 확인 | 통제가 풀린다 |
| `show_purchase_price` | 매입가 노출 | 직원에게 원가가 보인다 |

## 3. 왜 P0 인가

| 기준 | 판정 |
|---|---|
| 되돌릴 수 있나 | 🔴 **아니다** — 덮어쓰기라 이전 값이 남지 않는다 |
| 고객이 알아챌 수 있나 | 🔴 **아니다** — 아무 경고가 없다 |
| 자주 일어나나 | 🟠 서버 순단·토큰 만료면 발생. **로컬 PC 설치 구조상 순단은 일상** |
| 피해 범위 | 🔴 **회사 전체** — 테넌트 단위 정책 |

> **헌법 #25 3대 원칙 중 "안전하게" 위반.**
> 실패를 실패로 알리지 않는 것이 이 결함의 본질이다.

## 6. 🔴 사장님께 — 봉합 방향 (결재 요청)

개별 화면을 하나씩 고치면 **또 다른 화면에서 같은 게 나온다**(형제 결함 §4 가 증거다).
공통 규칙으로 잡는 것을 권합니다.

| 안 | 내용 | 범위 |
|---|---|---|
| **(가)** | `Settings.razor` 1화면만 봉합 | 작다. 하지만 §4 나머지는 남는다 |
| **(나) 권장** | ① 조회 실패 시 **저장 버튼을 잠근다** + 화면에 사유 표시<br>② 웹 서비스 catch 에 **로그 의무화**(헌법 #15)<br>③ 삭제는 **확인 다이얼로그 의무**<br>④ 저장 후 **재조회**해서 화면과 서버를 일치시킴 | 계정관리 9화면 공통 적용 |
| **(다)** | (나) + 나머지 8대 영역 전체 전수 적용 | 크다. 화면 56개 |

**PM 의견은 (나)입니다.** 이유는 —
지금 계정관리를 손대는 중이니 **같은 손질에 함께 넣는 것이 싸고**,
(다)는 아직 안 본 영역까지 건드려 **한 번에 검증할 수 없는 크기**가 됩니다.
나머지 영역은 그 영역 차례에 같은 규칙을 적용하면 됩니다.

⚠️ **(나)의 ①은 사용성과 충돌할 수 있습니다** — 서버가 잠깐 죽으면 설정을 못 고칩니다.
다만 **틀린 값으로 덮어쓰는 것보다 못 고치는 게 낫다**는 판단입니다. 이 부분 결재를 청합니다.
