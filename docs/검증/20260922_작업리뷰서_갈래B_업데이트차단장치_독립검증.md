## §1. 🔴 R-1 (반려) — **신설 게이트가 CI 에서 SKIP 초록이다**

### 1-1. [3] 의 주장

> 명세서 §5: *"b·c 는 실제 DB 를 워치독과 같은 경로로 읽는다 — 글자가 아니라 동작을 잰다.
> 못 붙으면 `HITPAN_REQUIRE_DB` 가 참인 잡에서 **FAIL**, 아니면 SKIP 사유를 남긴다(**SKIP 을 통과로 세지 않는다**)."*
> 명세서 §8: *"신설 게이트 **4 통과 / 0 실패 / 0 건너뜀**"*

### 1-2. 🔴 실측 — **그 「참인 잡」이 없다**

| 사실 | 근거 |
|---|---|
| 워치독 시험이 도는 곳은 `.github/workflows/watchdog-ci.yml` **하나뿐** | 워크플로 8개 전수 확인 |

## §3. 🔴 B-2 — fail-open 이 상시가 되는가 : 🟡 **조건부** + 🔴 **반대 방향 구멍 발견**

「드물다」를 아무도 잰 적이 없다. **내가 쟀다.** 프로브를 워치독과 **같은 경로**(`WatchdogStatusWriter.GetExistingIndexNamesAsync` → MariaDB CLI)로 돌렸다.

### 3-1. 판정 불가(Undetermined)를 만들기 — **쉽다. 7가지가 즉시 된다** (각 3회 중 3회 동일)

| 사례 | `present` | 판정 | 소요 |
|---|---|---|---|
| 없는 DB 이름 | `null` | `Undetermined` → **통과** | 0.13~0.31s |
| 포트 닫힘(33999) | `null` | `Undetermined` → **통과** | 2.14~2.21s |
| 잘못된 비밀번호 | `null` | `Undetermined` → **통과** | 0.20~0.30s |
| 없는 계정 | `null` | `Undetermined` → **통과** | 0.13~0.22s |
| 빈 사용자명 | `null` | `Undetermined` → **통과** | 0.13~0.20s |
| 응답 없는 호스트 | `null` | `Undetermined` → **통과** | **15.03~15.11s (상한 정각)** |
| 권한 전무(USAGE 만) | `null` | `Undetermined` → **통과** | 0.20~0.21s |
| MariaDB 클라이언트 부재 | `null` | `ResolveMariadbBinary` 가 `InvalidOperationException` → 바깥 catch → **통과** | — |

⇒ **판정 불가는 「드물다」가 아니라 「만들기 쉽다」.**
다만 **그중 어느 것도 정상 고객 PC 의 기본 상태는 아니다** — 정상 PC 는 db.conf 가 맞고 MariaDB 가 로컬에 있고 계정은 `GRANT ALL ON *.*` 이다.
⚠️**가설**: 정상 PC 에서 Undetermined 가 상시는 아니다. **⛔ 고객 PC 모집단에서 재 본 적은 없다**(§11 ⛔3). **진단은 실측 전엔 가설이다.**

### 3-2. 🔴 **반대 방향 구멍 — `information_schema` 는 권한으로 걸러진다** (V-1 전제가 깨진다)

[3] 의 V-1 핵심 주장(제품 주석 `UpdateOrchestrator.cs:686`·`WatchdogStatusWriter.cs:227` 에 그대로 있다):

> *"빈 집합(읽었는데 없다)과 null(못 읽었다)을 분리했다 — 빈 집합은 **확실히 없다**"*

**이 주장은 일반적으로 참이 아니다.** MariaDB 의 `information_schema.statistics` 는 **호출 계정의 권한으로 필터링**된다.
권한 없는 표는 **행이 아예 안 나온다** — 그런데 `exit=0` 이라 코드는 **「읽었다」**로 본다.

동일 DB(`hitpan_probe_ok`, 인덱스 2개 물리적으로 실재)를 **계정만 바꿔** 읽은 결과:

| 계정 | `present` 실측 내용 | 판정 | 회차 |
|---|---|---|---|
| `root`(전권) | `{collections.idx_coll_tenant_doc_cover, collections.primary, sales_deliveries.idx_sd_tenant_partner_src, sales_deliveries.primary}` (4개) | `Present` → 통과 | 5/5 |
| **1개 표만 SELECT** (`GRANT SELECT ON …sales_deliveries`) | `{sales_deliveries.idx_sd_tenant_partner_src, sales_deliveries.primary}` (2개) | 🔴 **`MissingConfirmed` → 롤백** | **5/5** |
| **컬럼 단위 SELECT** (`GRANT SELECT (id) ON …collections`) | `{collections.primary}` (1개) | 🔴 **`MissingConfirmed` → 롤백** | **2/2** |
| USAGE 만 | `null` | `Undetermined` → 통과 | 2/2 |

🔴 **인덱스는 DB 에 물리적으로 존재한다.** root 로 보면 4개 다 보인다.
그런데 권한이 좁은 계정으로 읽으면 **「읽어서 없음을 확인」**이 되어 **멀쩡한 업데이트가 롤백된다.**
이것은 fail-open 이 아니라 **fail-closed 오판**이고, 사장님 오더 §16-1 과 작지 §16-6 **중단조건 6** 이 정확히 금지한 모양이다.

**사이즈**: 정식 설치는 `installer/install.bat:85` 가
`CREATE USER 'hitpan'@'localhost' … GRANT ALL ON *.* TO 'hitpan'@'localhost'` 를 준다
⇒ **기본 설치 경로에서는 안 터진다.** 그래서 반려가 아니라 **조건부**다.

🔴 **다만 V-1 의 전제 — 「워치독 DB 계정이 스키마 전체에 SELECT 권한을 가진다」 — 가 코드·명세서·설계 어디에도 적혀 있지 않다.**
권한을 좁힌 고객사·수동 설치·DBA 가 손 댄 PC 에서는 전제가 깨진다. ⚠️**가설**(모집단 미측정 — ⛔3).

**→ 조건 C-1.**

### 3-3. 🟡 거짓 비상통지 한 자리

`PassesMigrationCrossCheckAsync`(`UpdateOrchestrator.cs:495`)는 `Migrations\SQL` 폴더가 없으면
**맨 앞 `:498` 에서 `return true`** 하고, 그때 `_declaredVerifyIndexes` 는 `:203` 에서 초기화된 **`null` 그대로** 남는다.
⇒ 3번째 조건이 `Undetermined` 로 떨어지고 **본사에 `update_index_verify_undetermined` 비상통지를 쏜다**(P4 실측, 4회 중 4회).

논리적으로는 「마이그가 없다 = 확인 대상 없음 = `NoDeclarations`」가 맞는 자리다.
⚠️**가설**: 해당 폴더는 누적 이력이라 항상 존재하므로 드묾(근거: 코드 주석 `:519` *"Migrations\SQL 은 누적 이력(DB-02~DB-84)이라 항상 존재한다"*). **⛔ 실기 미측정.**

**→ 조건 C-2.**

## §5. B-4 — 두 경로 동시 발화 : 🟢 **불가능하다. 항상 ①이 먼저 이긴다**

[3] 주장: *"①(스왑 전)은 null=차단, 3번째 조건(스왑 후)은 null=통과 — 의도적으로 반대"*
지시서 질문: *"같은 릴리스에서 동시에 발화하는 조합이 있나? 있으면 어느 쪽이 이기나?"*

호출 순서를 코드로 확정했다.

```
ApplyAsync  :203  _declaredVerifyIndexes = null;                         ← 매 적용 초기화
            :218  if (!await TrySwapFilesAsync(manifest, ct)) → return false;
                    └ :349  if (!await PassesMigrationCrossCheckAsync(...)) → return false;   ← 게이트 ① (스왑 前)
                              └ :548  _declaredVerifyIndexes = CollectDeclaredVerifyIndexes(...)
            :256  if (!await VerifyNewVersionAsync(...)) → FinishWithRollbackAsync(...)        ← 3번째 조건 (스왑 後)
```

- 게이트 ①이 `null`(`schema_migrations` 못 읽음)로 **차단**하면 `TrySwapFilesAsync` 가 `false` 를 내고 **스왑 자체가 안 일어나며 3번째 조건에 도달하지 않는다.**
- 따라서 **한 릴리스에서 둘이 동시에 발화하는 조합은 없다.** 순차이고, **이기는 쪽은 항상 ①** 이다.
- 반대 순서(①은 읽었는데 그 뒤 DB 가 안 읽힘)는 가능하고, 그때 3번째 조건은 `Undetermined` → 통과다. **비대칭은 의도대로 작동한다.**

**판정**: 🟢 **[3] 의 B-4 주장은 참이다. 반증 실패.**
