### 반증 1 — 경계값: `<` 인가 `<=` 인가 ✅ 안전

`Worker.cs:420`: `if (_lastUpdateCheckUtc is { } lastChecked && nowUtc - lastChecked < checkInterval) return;`

**차단 조건이 `<`** 이므로, 정확히 N분일 때는 `60분 < 60분` = false → **게이트를 통과한다.**

만약 `<=` 였다면 경과시간이 정확히 60분인 순간에 차단되지만, 다음 루프(60초 뒤)에 61분이 되어 통과한다 — **어느 쪽이어도 무한 대기는 생기지 않는다.** 다만 현재의 `<` 가 "지났으면 확인" 이라는 fail-open 정신에 더 부합한다. **결함 없음.**

### 반증 2 — 시계 변경 ✅ 안전 (이 항목이 가장 잘 만들어졌다)

| 시나리오 | 동작 | 근거 |
|---|---|---|
| 파일에 **미래 시각** | `null` 반환 → 즉시 확인 + 경고 로그 | `UpdateCheckStampFile.cs:93-98` |
| 시스템 시계를 **뒤로** 돌림 | 저장 시각이 상대적 미래가 됨 → 위와 동일하게 **즉시 확인** | 같은 곳 |
| 시계를 **앞으로** 돌림 | 경과시간이 커짐 → 즉시 확인 (fail-open 방향) | `:420` |

**미래 시각 방어가 없었다면** 그 시각이 지날 때까지 업데이트가 영영 막힌다 — 설계서 A-3 가 지적한 함정이며, 코드가 정확히 막았다. 이것은 **잘 된 설계**다.

### 반증 3 — UTC/로컬 혼재 ✅ 안전 (단, 조건부)

개발팀이 스스로 신고한 항목이다. **검증팀 판정: 현재 상태에서 안전하나, 이유는 개발팀 설명과 약간 다르다.**

| 축 | 사용처 | 시간대 |
|---|---|---|
| 게이트 판정 | `:418 DateTime.UtcNow`, 저장 `"O"` round-trip | **UTC** |
| 야간 창 | `:394 _update.IsNightWindow(DateTime.Now)` | **로컬** |
| W4-6 계수 | `:473 DateOnly.FromDateTime(DateTime.Now)` | **로컬** |

**혼재는 사실이다. 그러나 세 축이 서로 값을 주고받지 않는다** — 게이트는 UTC끼리만, 야간창은 로컬끼리만, 계수는 로컬끼리만 비교한다. **타입 경계를 넘는 지점이 없어** 오염이 전파되지 않는다.

- 게이트를 UTC 로 한 것은 **옳다.** 로컬로 재면 서머타임에 1시간이 통째로 뛰거나 되감긴다. 한국은 서머타임이 없지만, 사용자가 시간대를 바꾸면 로컬 판정은 즉시 깨진다.
- 야간 창이 로컬인 것도 **옳다.** "새벽 3시"는 고객 체감 시각이어야 한다.
- `ReadLastCheckedUtc` 가 `stamp.Kind != Utc` 일 때 `ToUniversalTime()` 으로 정규화한다(`:89`) — 파일을 시간대가 다른 PC 로 옮겨도 해석이 흔들리지 않는다.

> 🟡 **단, 이것은 "지금 안전"이지 "구조적으로 안전"은 아니다.** 한 함수 안에 두 시간축이 공존하는 상태(`:418` UTC 와 `:473` 로컬이 같은 try 블록 안)는 다음 사람이 둘을 섞을 위험을 남긴다. §6 후속 과제(W4-6 재설계)에서 반드시 함께 정리해야 한다. **이번 반려 사유는 아니다.**

### 반증 4 — 파일 I/O 실패 ✅ 안전 (🔴 P0 조건 미해당)

작업지시서 §8-1: *"파일 쓰기 실패가 업데이트를 막으면 P0."* **막지 않는다.**

| 실패 유형 | 동작 | 근거 |
|---|---|---|
| 파일 없음(첫 기동) | `null` → 즉시 확인, 조용히 | `:75-79` |
| 파싱 불가(손상) | `null` → 즉시 확인 + 경고 | `:82-87` |
| 읽기 예외(권한·잠금) | `null` → 즉시 확인 + 경고 | `:102-108` catch |
| **쓰기 실패(권한·디스크 가득)** | **예외를 삼키고 경고만** → 업데이트 계속 | `:118-127` catch |

**쓰기 실패 검증이 핵심이다.** `WriteCheckedNow` 는 `try/catch(Exception)` 으로 전부 삼키고 **예외를 재던지지 않는다**(`:122-127`). 호출부 `:460` 은 `_lastUpdateCheckUtc = nowUtc` **뒤에** 있으므로, 쓰기가 실패해도 인메모리 게이트는 이미 갱신됐고 업데이트 흐름은 그대로 진행된다.

> 즉 **디스크가 가득 차도 업데이트는 계속된다.** 잃는 것은 재시작 폭주 상한뿐이며, 그 사실이 경고 로그에 정확히 적혀 있다(`:126`). 헌법 #15(빈 catch 금지) 준수 — 4곳 전부 `LogWarning(ex, ...)` 이 있다.

**경로 권한 검증**: `ResolvePath()`(`:59-65`)는 `AppContext.BaseDirectory` 에서 `..` 로 올라가 `{app}` 을 잡고, 상위 폴더가 없으면 실행 폴더로 폴백한다. `UpdateLockFile` 과 동일 관례이며 워치독은 SYSTEM 으로 돌아 `{app}` 쓰기 권한이 있다. `%LOCALAPPDATA%` 를 피한 판단은 옳다(SYSTEM 계정에서는 `config\systemprofile` 로 숨어 CS 가 못 찾는다).

### 반증 5 — 연속 재시작 폭주 🟡 **P2 결함 1건 발견 (개발팀 미신고)**

**정상 경로는 안전하다.** 네트워크 장애로 manifest 조회가 실패해도 `UpdateClient.cs:110-116` 이 예외를 **삼키고 null 을 반환**하므로, `Worker.cs:452` 는 예외를 받지 않는다 → `:459-460` 이 정상 실행되어 **스탬프가 기록된다.** 따라서 feed 가 죽어 있어도 재시작 폭주 상한이 작동한다. 이 점은 잘 설계됐다.

**그러나 한 경로가 남는다.**

`Worker.cs:522-532` 의 catch 는 `EvaluateAsync` **이후** 단계(`ApplyUpdateAsync` · `_statusWriter.UpsertLatestAsync` · `IsNewerVersion` 내부 등)에서 예외가 나면 도달한다. 그때:

- `_lastUpdateCheckUtc = null` (`:531`) — 인메모리 게이트 해제
- **스탬프는 일부러 갱신하지 않음** (`:527-530` 주석이 의도를 명시)

→ 이 상태에서 예외가 **매번 재현되면**(예: `local_update_status` 테이블 손상으로 `UpsertLatestAsync` 가 항상 던짐), 게이트가 매 루프 열려 **60초마다 manifest 를 조회한다. 시간당 60회 = 의도한 1회의 60배.**

| 축 | 값 |
|---|---|
| 의도 | 60분당 1회 |
| 이 경로 | **60초당 1회 (60배)** |
| 지속 조건 | 결정론적으로 재현되는 예외 |

**등급 판정: 🟡 P2 (반려 사유 아님).** 이유:

1. **종전 코드도 동일했다.** 종전 `:389` 도 `_lastUpdateCheckDate = null` 로 똑같이 열었다. **이번 변경이 만든 결함이 아니다.**
2. 다만 **종전에는 이 폭주가 "하루 1회 → 60초 1회"였고 지금도 "60분 1회 → 60초 1회"** 로, 배수(60배)는 오히려 **줄었다**(종전 1,440배).
3. 도달 조건이 좁다 — 흔한 네트워크 장애는 `UpdateClient` 가 이미 삼킨다.

> **개발팀이 이 경로를 신고하지 않은 것은 지적한다.** `:527-530` 주석은 "스탬프를 안 지우는 이유"만 설명하고, **인메모리 해제가 만드는 루프당 재시도**는 언급하지 않았다. §5-2 권고로 남긴다.

### 자체신고 4 — 종전 지연이 "1분~24시간"으로 요동쳤다 → ✅ **주장 사실 확인. 기존 문서 표현이 부정확했다**

**주장은 사실이다.** 종전 지연은 고정 24시간이 아니라 **1분~24시간 사이에서 마지막 확인 시각에 따라 결정**됐다.

## 5. 검증팀 지적사항 (반려 사유 아님 · 후속 반영)

### 5-1. 🟡 야간 창 보장이 "값의 우연"에 걸려 있다 (P2)

§2-7 에서 확인했듯 `상한 60분 == 야간창 60분` 이라서 커버리지가 성립한다. **어느 한쪽만 바뀌어도 즉시 깨진다.**

- `IsNightWindow` 가 `Hour >= 3 && Hour < 4` 에서 30분으로 좁아지면 → 놓칠 수 있다
- 상한을 90분으로 올리면 → 놓칠 수 있다

현재 `WatchdogOptions.cs:40-43` 주석이 이 의존을 설명하고 있어 **최소 요건은 갖췄다.** 다만 `UpdateOrchestrator.IsNightWindow` **쪽에는 역방향 경고가 없다** — 그 함수를 고치는 사람은 워치독 옵션 주석을 볼 이유가 없다.

> **권고**: `UpdateOrchestrator.cs:1423` 에 *"이 창의 길이는 `WatchdogOptions.UpdateCheckIntervalMaxMinutes` 와 짝이다. 좁히면 야간 적용을 놓친다"* 한 줄 추가. **후속 과제로 충분하다.**

### 반려하지 않는 이유

검증팀은 **"됐다를 확인하는 게 아니라 안 되는 경우를 찾는" 조직**이다. 이번에 9종을 반증했고, **P0·P1 은 나오지 않았다.** 나온 P2 2건은 둘 다 **이번 변경이 만든 것이 아니라 이미 있던 성질**이다. 반려는 결함이 있을 때 하는 것이지, 실측이 남았다는 이유로 하는 것이 아니다.

**다만 "통과"라고 쓰지도 않는다.** §7-3 은 이번 작업의 존재 이유이고, 그것을 실측하지 않은 채 통과 도장을 찍으면 **개발 PC 정상작동을 검증으로 위장하는 것**(사장님 2026-07-06 지시 위반)이 된다.

### [5] CTO·사장님 결재로 올려도 되는가 — **의견: 올려도 된다**

**단, 다음 표현으로 올려야 한다:**

> *"코드 검증은 끝났고 결함 0건입니다. 다만 **핵심 항목(재시작 없이 발견)은 아직 실측하지 못했습니다.**

**커밋 시점 의견**: 워크플로우 [6]은 *"결재 + 검증 완료 = 무조건 커밋"* 이다. 검증팀 판정은 **조건부**이므로, 두 길 중 사장님 선택 사항이다.

|---|---|---|
| **(가) 실측 후 커밋** | §7-3 확정 후 커밋 — 가장 안전 | 60분 지연 |
| **(나) 지금 커밋 후 실측** | 워킹트리 미커밋 0 유지(세션 종료 대비) | 미실측분이 이력에 남음 |

> **검증팀 권고: (나)**. 이유 — ① 코드 결함 0건이 확인됐고 ② 실측하려면 **어차피 이 코드로 빌드·설치해야** 하므로 커밋이 실측의 전제다. ③ 워킹트리에 남기면 다음 세션이 상태를 모른다(SOP [6] 취지).
