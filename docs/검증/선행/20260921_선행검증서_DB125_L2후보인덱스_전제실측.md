| **C3** | `collections(tenant_id, partner_id, ref_doc_type, ref_doc_id)` | **3,125** | 🔴 **안 쓴다** | 🔴 **이득 0 — 반려** |
| **C2** 🟢 | `sd(tenant_id, partner_id, source_type)` | 🟢 **2,013** | 🟢 **쓴다** (`ref ix_c2 · Using index`) | 🟢 **채택** |

### 3-1. 🔴 1순위 후보가 이득 0 인 이유 — 이미 있는 인덱스다

`sales_deliveries` 에 **`idx_tenant_partner(tenant_id, partner_id)` 가 이미 있고**, InnoDB 는 **모든 2차 인덱스 뒤에 PK 를 붙인다.** `delivery_id` 가 PK 이므로

> `idx_tenant_partner` **≡** `(tenant_id, partner_id, delivery_id)` = **C1 과 물리적으로 같은 인덱스**

⇒ **넣어도 새 정보가 없다.** 실측이 그대로 보여 준다(3,125 → 3,125 · 계획 불변).

### 3-2. 🟢 `collections` 에 `partner_id` 를 넣는 안 — 실측으로 반증했다

L2 의 거래처 술어는 **`sd.partner_id`** 다(`LegacyBalanceMatching.cs:277`). C3 를 실제로 달고 재니 **옵티마이저가 한 번도 선택하지 않았고 잠금도 3,125 로 그대로**였다. **V-2 의 가설은 성립한다.**

### 3-3. 🟢 C2 가 듣는 이유

`tenant_id`+`partner_id`+`source_type` 이 전부 인덱스 안에 있어 **`Using index`(커버링)** 가 된다 ⇒ **클러스터 행을 안 집는다** ⇒ `sd` 2,235 → **1,123**. L2 전체 3,122 → **2,013**.

## §9 🔴 내가 못 잰 것 (추론과 실측을 섞지 않는다)

1. 🔴 **대량 `UPDATE` 직후 첫 측정은 부풀어 오른다 — 이번에도 당했다.** 0% 재현 1회차가 `③185,342 / ④220,364` 로 나왔고 2·3회차에 `122,451→110,623` / `41→41` 로 가라앉았다. **퍼지 지연으로 읽었지만 원인을 못 잤다.** §4-2 표의 0%·1% 값은 **가라앉은 뒤의 값**이다. **게이트 임계값을 세울 때 이 요동을 반영해야 한다.**
2. ⚠️ **채움 방식이 실제 사용 패턴과 같은지 모른다** — `_cmap.n ↔ _dmap.n` 순서로 붙였다. 실제로는 **거래처별로 몰려 붙는다.** 대상 거래처에 몰렸을 때 C2/C4 가 어떻게 되는지 **안 재 봤다.** (A-2 계측의 같은 미실측 항목이 그대로 남아 있다.)
3. ⚠️ **ALTER 6초는 이 PC 기준이다** — 고객 PC(느린 디스크 · 작은 버퍼풀 · 백신 실시간 검사)에서 몇 배가 될 수 있다. **B-6 을 완전히 닫으려면 저사양 실측이 필요하다.**
4. ⚠️ **쓰기 부하를 안 쟀다** — 인덱스 2개는 `collections`·`sales_deliveries` 의 **INSERT/UPDATE 를 느리게 한다.** 이관(수만 행 적재) 시간이 늘어날 수 있는데 **안 재 봤다.** C4 는 6칼럼이라 특히 그렇다.
5. ⚠️ **동시성 아래서 안 쟀다** — 전부 단일 연결 격리 측정이다. **실제 교착(deadlock)·대기가 줄어드는지는 이 수치로 못 말한다.** 잠금 행 수는 **대리물**이다.
6. ⚠️ **지급 축 V-8·V-9 는 이 문서 범위 밖이다** — 투입 카드가 V-1~V-7 만 지정했다. L5 의 `rt ALL` 3,124 는 **C2·C4 로 변화 0** 임만 확인했다(§5).
7. ⚠️ **`hitpan_v4_a` 는 `t1_base` 와 같은 규모(약 11만 행)다.** 공영정보 5만 고객사는 「DB 가 5만 개」라는 뜻이지 한 DB 가 더 크다는 뜻이 아니라고 읽었으나 — **이것은 추론이다.** 더 큰 단일 테넌트가 있는지 **확인 못 했다.**
