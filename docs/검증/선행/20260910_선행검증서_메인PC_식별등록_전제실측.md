### 결론 한 줄

🔴 *"디바이스 등록에서 메인PC 를 확실히 식별하면 마이그 실측이 풀린다"* 는 **절반만 맞다.**
「메인PC」는 코드에 **서로를 모르는 두 축**으로 있다.

| 축 | 무엇으로 판정하나 | 어느 주소에서 막나 |
|---|---|---|
| **문 A — 기기 문** (업무 API 전부) | `tenant_devices` 의 **열쇠(기계비밀)** 또는 **`is_main_pc=1` 줄 번호** (`DeviceAuthMiddleware.cs:128-194`) | **로컬**에서 막는다 (로컬은 다른 저장소 = 다른 기기 · §3) |
| **문 B — 자리 문** (찾아보기·지우고 가져오기·초기화·백업) | **요청 헤더·소켓만** (`MainPcOnlyAttribute.cs:37-49`) — 기기 표를 안 읽는다 | **도메인**에서 막는다 (터널 헤더가 붙는다) |

⇒ 어느 한 축만 고치는 설계는 **반대쪽 문에서 다시 막힌다.** ⇒ 설계 착수 전 **사장님 Q2(자료관리를 어느 주소에서 열 것인가) 결재가 선행**이다.

**게이트 요구 — 설계·개발이 새로 만들 게이트가 지킬 것**
1. 요청 파이프라인 전체(`Program.cs:574-617` 순서)를 태운다 — 기기 미들웨어(문 A) + 자리 필터(문 B)를 **한 요청**에서.
2. 사장님 경로 = `CF-Connecting-IP`·`X-Forwarded-For` 를 **붙이고** "열려야 할 것이 열리나"를 단언한다. 거부 단언만 있는 게이트는 판정 근거로 쓰지 않는다.
3. 로그인 직후 **업무 API 200** 까지 단언한다 (G-40 이 놓친 자리).
4. DB 게이트는 CI `GATES` 에 등록한다 — 기기 계열 제외 사유(권한 축)를 해소하고, 등록 안 된 게이트는 판정 근거로 쓰지 않는다.
5. 게이트 DB 스키마 = 고객 DB 스키마 (DB-89 처리 결정 후 동일화).
6. origin 분리·신분 유지는 Playwright 로 재고 결과를 문서에 남긴다 (8/20 이월분 포함) · 무력화 시험은 **"왜 FAIL 인지"** 까지 확인.
