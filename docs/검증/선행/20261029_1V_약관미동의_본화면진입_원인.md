## §3 ③ 경로 — 두 번의 「통째 새로 읽기」 중 뒤엣것이 이긴다
1. 로그인 성공 → `AuthService.cs:177~180` 세션 저장 → `NotifySessionChangedAsync()` → `HitPanAuthStateProvider.cs:69~73` 은 인증 상태 작업을 **던져 놓고 기다리지 않고** 바로 돌아온다.
2. `App.razor:13~18` `AuthorizeRouteView` 는 새 인증 작업이 끝나기 전까지 「확인 중」을 그리며 **열려 있던 `/login` 페이지를 내린다** — 이 현상은 `Login.razor:404~407` 주석(7/22 실측 「라우터가 /login 컴포넌트를 즉시 폐기」)에 이미 기록돼 있다.
3. 내려진 옛 Login 의 이어진 코드가 `Login.razor:397~402` → `/terms` 통째 새로 읽기(forceLoad) 를 **먼저** 건다.
4. 인증 작업(저장소 읽기 = 비동기)이 끝나면 라우터가 `/login` 을 **새로 만든다** → `Login.razor:198~204` `OnInitializedAsync` 가 「이미 인증됨」을 보고 `/` 통째 새로 읽기를 **나중에** 건다.
5. 브라우저는 마지막 주소 이동이 앞선 이동을 취소한다 ⇒ `/` 에 착지. 두 엔진 모두 같은 결과(런 5 Chromium·WebKit 동일)와 맞다.
6. 본 화면에는 약관을 **강제하는 관문이 없다** — `MainLayout` 은 안내 띠(`TermsConsentBanner`)만 띄우고 이동시키지 않는다(`TermsConsentBanner.razor:16~21` 버튼은 사용자가 눌러야 감). 화면 쪽 강제는 `Login.razor:397~402` 한 곳뿐인데 그 한 곳이 경합으로 덮인다.

⇒ 사람이 같은 버튼을 눌러도 같은 순서가 난다 = **제품 결함**(헌법 #24 · 「첫 로그인 약관 필수」 의 화면 쪽 강제가 깨짐). 서버 403(④)이 살아 있으면 업무 데이터는 막히나, 미동의자가 약관 화면 대신 본 화면 + 오류 알림을 보는 것은 「처음 보는 사람이 혼자 쓸 수 있냐」 기준 실패.
⚠️ 「유력」인 까닭: 3→4 의 순서는 코드로 설명했을 뿐 문서 이동 순서를 찍은 실측이 아직 없다(§5).

## §4 따로 적발 — 잠복 결함(이번 원인 아님 · 별건 등록 권고)
| 자리 | 기준 |
|---|---|
| 로그인 판정 `AuthController.cs:285~305` → `TermsConsentService.cs:83~100` | 테넌트+사용자+**판 v2.0.0**+**필수 4칸=1** |
| 서버 문 `TermsConsentMiddleware.cs:88~94` | 테넌트+사용자+**판 v2.0.0** |
| 화면 status `TermsConsentController.cs:20~54` | 테넌트+사용자 **아무 행이나**(판·필수칸 무시) · 예외 시 false |

세 곳이 서로 다른 기준이다. 옛 판 동의 행만 있는 사용자는 로그인=「동의 필요」 → `/terms` → status=「동의함」 → 800ms 뒤 `/`(②의 길)로 튕기고, 본 화면 띠도 안 뜨며, 서버 문은 403 — 동의할 길이 화면에서 사라진다. 약관 판이 바뀌는 날 전 고객이 밟는다. 판 문자열을 요청 본문에서 받는 저장 경로(`TermsConsentController.cs:80~90`)도 함께 볼 것.
