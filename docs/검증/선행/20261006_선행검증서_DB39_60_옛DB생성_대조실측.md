## §3 대조 실측 — 시험 DB `hitpan_e2e` (152표 · ERP 모양 · 본사 표 0 · 시드 행 있음)

### §3-0 재현 상태 편차 사유
카드는 「이력을 DB-38 까지만」이라 했으나, 현행 스키마에 DB-50 이후를 전부 재실행하면 비멱등 ALTER 충돌(별건 실패)이 섞여 판정 변수가 오염된다. 가설의 판정 변수는 **DB-39·DB-60 행의 부재** 하나이므로, 그 두 행만 지우는 통제 재현을 택했다. 러너는 번호순 실행이라 결과는 동일하다(DB-39 차례가 오면 돈다).

### §3-1 대조군 A — 시드 행 있는 그대로 실행
- `RESULT Success=True Applied=11 [DB-120…DB-137] Skipped=90` — DB-39·DB-60 은 skip. 본사 표 24종 조회 = **0건**.
- (부수 확인: e2e 가 DB-119 에서 멈춰 있어 밀린 11건을 정상 적용 — 러너 자체는 정상 동작.)

### §3-2 실험군 B — DB-39·DB-60 행만 삭제(= 시드 이전 옛 고객 DB) 후 같은 러너 실행
```
적용 완료: DB-39 (DB-39_backoffice_schema.sql)
마이그 실패 — 중단. 실패 마이그: DB-60. MySqlException: Can't create table
`hitpan_e2e`.`tenant_business_info` (errno: 150 "Foreign key constraint is incorrectly formed")
RESULT Success=False Applied=1 [DB-39] Skipped=38 Failed=DB-60
```
실측 결과(조회 확인):
1. 🔴 **본사 표 5개가 고객 DB 모양 안에 생겼다** — platform_admins · resellers · reseller_accounts · reseller_commissions · commission_settlements.
2. 🔴 **본사 super_admin 1행이 심어졌다** — `admin@hitpan.kr` / role=super_admin / 고정 bcrypt(원문 평문이 마이그 파일 주석에 있다). 고객 DB 에 본사 관리자 자격증명이 들어간 것(#18·#22 위반 모양 + 고정 비밀번호).
3. 🔴 **tenants 에 `fk_tenants_reseller` FK 가 되살아났다** — 출하 DDL 이 보안 격벽으로 제거한 FK 다.
4. 🔴 **DB-60 은 실패** — ERP tenants(`tenant_id varchar(36)`)가 IF NOT EXISTS 로 살아남고, tenant_business_info 가 `BINARY(16)` FK 로 그걸 참조(DB-60:56,68) → 형 불일치 errno 150. **25개 표는 안 생기는 대신 러너가 여기서 멈춘다.**

### §3-3 재시도(멱등 확인 2회차)
- `RESULT Success=False Applied=0 Skipped=39 Failed=DB-60` — DB-39 는 success=1 로 skip, **DB-60 은 매 기동마다 실패 반복**. 러너는 첫 실패에서 return 하므로(:154) **DB-60 보다 큰 번호의 미적용 마이그는 영영 안 돈다.** 진짜 옛 DB 라면 DB-70 이후(워치독 핑 · 약관 · 메인PC 가드 DB-120 · 봉인키 DB-126 … 봉합 전부)가 전부 막힌다.

### §3-4 판정 종합
| 가설 문장 | 판정 |
|---|---|
| 러너는 폴더 전부를 실행 대상으로 잡는다 | 🔴 확정 (§1) |
| 신규설치는 출하 DDL 시드가 막는다 | 🔴 확정 (§2 시드 + §3-1 대조군) |
| 옛 고객 DB 는 업데이트 한 번에 **본사 표 30개**가 생긴다 | 🟡 **수정 확정** — 생기는 건 사실이나 **5개 + FK 1 + 관리자 1행**에서 DB-60 이 실패. **진짜 P0 는 표 생성보다 「마이그 체인 영구 중단」** |

## §4 이미 깔린 고객 DB — 판정 불가 · 확인 조회문만 (읽기 전용)

운영 접근 금지(#39)라 실태는 못 쟀다. 생겼다면 아래 **SELECT 만으로** 확인 가능하다(고객 DB 에서, 본사 전송 없이):
```sql
-- ① 본사 표 존재 여부 (0건이어야 정상)
SELECT table_name FROM information_schema.tables
 WHERE table_schema = DATABASE()
   AND table_name IN ('platform_admins','resellers','reseller_accounts',
                      'reseller_commissions','commission_settlements');
-- ② 마이그 이력 — 행이 아예 없으면 '노출 대상 옛 DB', success=0 이면 '이미 중단 중'
SELECT migration_id, success, app_version, applied_at
  FROM schema_migrations WHERE migration_id IN ('DB-39','DB-60');
-- ③ 심어진 본사 계정 (①에서 platform_admins 가 있을 때만)
SELECT admin_id, email, role, is_active FROM platform_admins;
-- ④ 되살아난 FK
SELECT constraint_name FROM information_schema.table_constraints
 WHERE table_schema = DATABASE() AND table_name='tenants'
   AND constraint_name='fk_tenants_reseller';
-- ⑤ 체인 중단으로 밀린 마이그 (success=0 또는 DB-60 뒤 번호의 행 부재)
SELECT migration_id, success FROM schema_migrations WHERE success = 0;
```

## §6 시험 DB 잔재 (복구 결재 대기)

실험군 B 가 `hitpan_e2e` 에 남긴 것(복구 DROP 이 권한 분류기에 거절돼 **그대로 두고 보고**):
- 표 5개(platform_admins 1행 포함) · tenants 의 `fk_tenants_reseller` · `schema_migrations` DB-39 success=1(app_version=`1-V-harness`) / DB-60 success=0.
- 대조군 A 가 적용한 DB-120~137 11건은 러너의 정상 동작이라 복구 불요.
- 복구 SQL(결재 후 실행):
```sql
USE hitpan_e2e;
ALTER TABLE tenants DROP FOREIGN KEY fk_tenants_reseller;
DROP TABLE IF EXISTS reseller_accounts, reseller_commissions,
  commission_settlements, resellers, platform_admins;
DELETE FROM schema_migrations WHERE migration_id IN ('DB-39','DB-60');
INSERT INTO schema_migrations (migration_id, app_version, success)
VALUES ('DB-39','clean-ddl',1),('DB-60','clean-ddl',1);
```
- 하네스: 스크래치패드 `migharness/`(세션 종료 시 소멸) — 제품 코드·레포 수정 0건.
