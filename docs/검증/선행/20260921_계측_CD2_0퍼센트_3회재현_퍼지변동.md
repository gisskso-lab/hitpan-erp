## §4 🔴 `History list length` 는 **크기를 못 알려준다**

| 회차 | HLL | 봉합후 0% |
|---|---|---|
| R1 | **2** | 43 |
| R4 | 151 | 43 |
| R5 | 193 | 5,602 |
| R9 | 359 | **11,159** |
| R11 | **68** | 3,405 |

- HLL 이 **더 낮은** R11(68)이 HLL 이 **더 높은** R4(151)보다 **79배 큰** 잠금을 냈다. **상관이 없다.**
- 이유: MariaDB 의 `History list length` 는 **안 지워진 트랜잭션(언두 세그먼트) 개수**다. 11만 행을 한 문장으로 갈아엎어도 **1 만 오른다.** 우리가 다친 것은 **행 수**인데 HLL 은 **건수**를 센다.
- ⇒ **HLL 은 「0 이냐 아니냐」의 신호로만 쓸 수 있다.** 크기 보정에는 못 쓴다. (`INNODB_METRICS` 의 `purge_*` 카운터는 이 인스턴스에서 **비활성(0)** 이라 못 썼다 — §7-5)

## §5 🔴 2% 봉합전의 37배 플립은 **퍼지가 아니라 통계 낡음이다**

같은 데이터(2% · 채움 2,196)에서 `ANALYZE TABLE` **만** 달리해 격리 측정(M2). 긴 트랜잭션 없음.

| 통계 | EXPLAIN 구동 | **잠금** | 값 |
|---|---|---|---|
| 🔴 **낡음**(0% 에서 뜬 통계) | `ec` **ALL** / NULL / 107,653 → `sd` eq_ref PRIMARY | 🔴 **112,040** | 2,082,000.00 ✅ |
| 🟢 **신선**(2% 에서 `ANALYZE`) | `sd` **ref** / `fk_sd_partner` / 1,114 → `ec` ref `idx_coll_tenant_doc` / 48 | 🟢 **3,019** | 2,082,000.00 ✅ |

- **한 번의 `ANALYZE` 가 잠금을 37배 가른다.** 데이터는 한 행도 안 바뀌었다.
- ⇒ CTO 가 의심한 「퍼지 지연이 2% 칸을 깜빡이게 한다」는 **절반만 맞다.** 2% 칸을 실제로 흔든 것은 **통계 낡음**이고, 퍼지는 **0% 봉합후 칸**을 흔든다. **두 원인이 서로 다른 칸을 때린다.**
- 🔴 고객 PC 에서 통계가 낡는 것은 예외가 아니라 **기본값**이다(대량 이관 직후 · `innodb_stats_auto_recalc` 가 10% 변화에서만 돈다). **게이트가 `ANALYZE` 를 안 걸면 실운영에서 낡은 쪽이 정상이다.**

### 6-3. 권고 형태 (검증 의견 · 채택은 PM·CTO 결재)

```
같은 실행 · 같은 시드 안에서
  ① ANALYZE TABLE collections, sales_deliveries          ← 없으면 37배 거짓 빨간불 (§5)

```
- ④ 의 0.80 은 **관측 최악(0.7410)에 6%p 여유**다. 더 조이면 청정 2% 칸이 먼저 깨진다.
- ②를 CI 에서 못 지키면(공유 러너) **0% 칸은 게이트에서 빼고 2% 칸만 건다** — 2% 봉합후가 실측상 제일 단단한 칸이다(±7%).

## §7 🔴 내가 못 잰 것 (추론과 실측을 섞지 않는다)

1. 🔴 **`185,342` 를 재현 못 했다 — 16회 중 0회.** 청정에서도, 퍼지 지연을 일부러 만들어도 0% 봉합전은 **112,040 에서 1행도 안 움직였다.** ⇒ **그 값의 원인은 여전히 미확정**이다. 「퍼지 지연 때문」은 이 계측으로 **확인되지 않았다**(오히려 퍼지는 **봉합후**를 때렸다). 다른 원인(그때 인덱스 조합이 ③였다 · 그때 `ANALYZE` 가 안 돌았다)이 남아 있다 ⚠️.
2. 🔴 **100% churn(R11)이 3,405 로 역행한 이유를 모른다.** 5%→5,602 · 10%→11,159 는 정비례인데 100% 는 오히려 내려갔다. **비선형 구간이 있다** ⚠️. 최악 변동폭의 **상한을 못 말한다**.
3. ⚠️ **HLL 을 수천대로 못 올렸다.** 긴 트랜잭션 1개 + 대량 `UPDATE` 로는 HLL 이 **건수만** 센다(최대 359). 트랜잭션을 수천 개 쌓는 부하는 안 만들었다.
4. ⚠️ **동시성 아래서 안 쟀다.** 전부 단일 연결 격리다. `trx_rows_locked` 는 **대리물**이고 실제 대기·교착이 줄어드는지는 이 수치로 못 말한다.
5. ⚠️ **`INNODB_METRICS` 의 `purge_del_mark_records`·`purge_undo_no_pages` 는 이 인스턴스에서 비활성(0)** 이라 못 썼다. `SHOW ENGINE INNODB STATUS` 의 HLL 만으로 갈음했다.
6. ⚠️ **채움 분포가 실제와 같은지 모른다** — `_cmap.n ↔ _dmap.n` 순서다. 실제로는 거래처별로 몰린다(선행검증 §9-2 와 같은 미실측 항목이 그대로 남아 있다).
7. ⚠️ **고객 PC(느린 디스크·작은 버퍼풀·백신)에서 안 쟀다.** 이 PC 기준 수치다.
8. ⚠️ **`ALTER` 로 인덱스를 붙였다 뗐다 하는 방식 자체가 표를 재구축한다.** 봉합후 측정은 항상 **갓 만든 인덱스**에서 출발한다 — 실제 운영의 「오래 쓴 인덱스」와 다를 수 있다.

## §8 재현 방법

- 측정 DB 만들기: `mysqldump -h 127.0.0.1 -P 33306 -u root --single-transaction v125x collections sales_deliveries _cmap _dmap _tset` → 새 DB 적재
- 비율: `UPDATE collections c JOIN _cmap m ON m.collection_id=c.collection_id JOIN _dmap d ON d.n=m.n SET c.ref_doc_id = IF(m.n <= ROUND(109822*<pct>/100), d.delivery_id, NULL);` → `_tset` 20행 덮어쓰기
- 퍼지 지연 만들기: 별도 연결 `START TRANSACTION WITH CONSISTENT SNAPSHOT; SELECT COUNT(*) FROM _cmap; SELECT SLEEP(1500);` + **값이 실제로 바뀌는 churn**(예: `SETRATIO 5; SETRATIO 0;` ×3). **같은 비율 반복은 쓰레기를 안 만든다**
