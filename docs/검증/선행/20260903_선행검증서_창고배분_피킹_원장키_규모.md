> 사장님 지시 (2026-09-03): *"재고가 없으면 출고를 막아야 정상이지"* → **C안 확정**
> (C = 회사 합산으로 판매는 허용하되, **있는 창고에서 자동 배분**해 창고별 음수를 없앤다)

| 항목 | 실측 |
|---|---|
| `stock_ledger` UNIQUE 키 | `(tenant_id, source_type, source_id, item_id, move_type)` — 🔴 **`warehouse_id` 가 없다** |

⇒ **DDL 변경이 붙을 가능성이 높다.** 착수 전 배분 규칙 결재가 필요하다.

## 1. 왜 C안인가 — 두 지시가 충돌했고, C만 둘 다 지킨다

### 충돌한 두 지시

| 시점 | 사장님 지시 |
|---|---|
| **2026-04-26** | *"재고로 판매 흐름이 막히면 안 된다"* — 창고 1개 소기업 95%가 창고 단위로 막히면 판매를 못 친다 |
| **2026-09-03** | *"재고가 없으면 출고를 막아야 정상이지"* |

같은 자리를 가리킨다. 코드 주석(`SalesService.cs:440`)에 4/26 헌법이 그대로 남아 있다.

### 세 갈래

| 안 | 동작 | 판정 |
|---|---|---|
| A (현재) | 회사 합산으로만 검사 | 🔴 창고별 음수 발생 (9/3 지시 위반) |
| B | 창고 단위로 차단 | 🔴 다창고 고객이 창고 지정 실수로 판매 막힘 (4/26 헌법 위반) |
| **C** | 합산으로 허용 + **있는 창고에서 자동 배분** | 🟢 **둘 다 지킨다** |

🟢 **현장 논리로도 C** — 물건은 실제로 어딘가에 있다.
판매가 틀린 게 아니라 **없는 창고에서 뺐다고 적힌 장부가 틀린** 것이다.

🟢 코드 주석이 이미 C를 가리킨다 (`SalesService.cs:444`):
> *"다창고 고객용 **Picking Strategy** / 재고관리 모듈은 정식 버전 작지서로."*

⇒ **4/26 에 미뤄둔 그 작업이다.** 새로 만드는 게 아니라 예정돼 있던 것을 당기는 것.

## 2. 🔴 규모 — 원장 UNIQUE 키가 막고 있다

### 실측한 키 (출하 DDL · `installer/hitpan_db_clean.sql:3634`)

```sql
UNIQUE KEY `uq_stock_ledger_source` (`tenant_id`,`source_type`,`source_id`,`item_id`,`move_type`)
```

**`warehouse_id` 가 없다.** 그래서:
- 전표 1건 · 품목 1개 → 원장 **1줄만** 가능
- 5개를 A창고 3 + B창고 2 로 빼면 → **2줄 필요** → 🔴 **UNIQUE 위반**

### 이 키가 실제로 사고를 냈던 기록 (`SalesService.cs:464`)

> UNIQUE 위반 → 거래 전체 롤백(**"재고 안 빠짐"**, 헌법 #20).
> **표준 데모는 통과하나 실사용 첫날 터지는 잠복형.**
> 봉합: INSERT 전 `item_id` 로 합산해 **키당 1행만** 기록.

⇒ 6/23 에 **"품목당 한 줄"** 로 우회했다. C안은 그 우회를 되돌리는 방향이다.

### 이 키에 맞춰 설계된 코드 — 5곳

| 파일 | 자리 |
|---|---|
| `SalesService.cs:465` | 판매 확정 (OUT 합산) |
| `SalesService.cs:1132` | 판매 취소 (역행 합산 — 확정과 대칭) |
| `SalesService.cs:2457` | 매출반품 |
| `PurchaseService.cs:248`·`1309` | 매입·매입반품 |
| `BomService.cs:659`·`840` | BOM 전개·복귀 |
| `MdbMigrationService.cs:1923` | 마이그레이션 **멱등 키** |

🔴 **마이그레이션이 이 키를 멱등성 근거로 쓴다.** 키를 바꾸면 마이그 재실행 안전성에 영향.
⇒ 헌법 #26(마이그는 사업의 근간) 영역이다. **DB 매니저 감수 필수.**

## 3. 착수 전 필요한 것

### 🟡 결재 1건 — **배분 규칙** (사장님만 정할 수 있다)

두 창고에 나뉘어 있을 때 어디서 먼저 빼는가:

| 후보 | 규칙 |
|---|---|
| ① | 지정 창고에서 있는 만큼 → 부족분을 다른 창고에서 |
| ② | 재고 많은 창고부터 |
| ③ | 상품마스터 기본창고(`items.default_warehouse_id`) 우선 |
| ④ | 창고 코드 순 (MAIN 우선) |

🔴 **PM 이 정하면 받아쓰기다.** 현장에서 물건을 어느 창고부터 꺼내는지는 사장님 정보다.

⚠️ ③을 고르면 **매출이 `items.default_warehouse_id` 를 안 읽는 문제**(별건 선행검증서)가 선행 과제로 붙는다.

### 🟢 키 설계 판정 — 실측으로 정했다 (PM 판정 · DB 매니저 감수 필요)

**판정: UNIQUE 키에 `warehouse_id` 를 추가한다.**

```sql
-- 현재
UNIQUE KEY uq_stock_ledger_source (tenant_id, source_type, source_id, item_id, move_type)
-- 변경
UNIQUE KEY uq_stock_ledger_source (tenant_id, source_type, source_id, item_id, move_type, warehouse_id)
```

**근거 — 마이그 멱등성이 깨지지 않는다** (헌법 #26 확인):

| 확인 | 실측 |
|---|---|
| 마이그가 원장에 넣는 창고 | 🟢 **`wh-migration` 하나로 고정** (`MdbMigrationService.cs:226`) |
| 그래서 | 키에 창고가 붙어도 **값이 항상 같다** ⇒ `INSERT IGNORE` 멱등성 유지 |
| 마이그의 `item_stock` 생성 | 🟢 **이미 창고별 `GROUP BY`** (`:490`) — 창고축이 마이그에도 이미 살아 있다 |

⚠️ **대안(기각)**: `source_id` 에 창고를 접어 넣기(`{returnId}:{whId}`).
→ `source_id` 로 원전표를 되찾는 코드가 여러 곳에 있어(DB-116 소급복구가 그렇게 짜여 있다)
   문자열을 오염시키면 그 조회가 전부 깨진다. **키를 정직하게 넓히는 쪽이 맞다.**

### 착수 순서 (게이트 선행 · SoD)

1. 🟢 **키 설계 판정** — 위에서 완료 (DDL 1건 필요)
2. **게이트 선행 작성** → 봉합 전 🔴 빨간불 확인 (봉합자가 짜지 않는다)
3. **마이그 멱등성 반증** — 같은 마이그를 두 번 돌려 중복 0 확인 (헌법 #26)
4. 봉합 → 무력화 시험

## 4. 실측으로 확인한 사실 (근거 있음)

| 항목 | 결과 |
|---|---|
| 재고 검사가 실재하나 | 🟢 **있다** — `SalesService.cs:451` · `"재고가 부족합니다."` |
| 검사 기준 | 🔴 **회사 합산** (`SUM(qty_in)-SUM(qty_out)` · `warehouse_id` 조건 없음) |
| 그래서 생긴 것 | `1+1` 테스트1창고 **−15** (회사 합산 11개가 있어 검사를 통과했다) |
| 정합성 검사가 잡나 | 🟢 **잡는다** — 「음수 재고」 FAIL 1건 |
| 품목 합계 정합 | 🟢 유지 (기본창고 26 + 테스트1창고 −15 = 11) |

⚠️ **이 음수는 내가 만들었다.** 재고 0인 창고를 일부러 골라 3회 출고했다.
고객이 겪으려면 창고를 잘못 골라야 한다 — 다만 **막는 게 없다는 사실은 그대로다.**

## 5. 시산표 오진 정정 (내가 틀린 것)

6차 실측에서 *"시산표 차변 0 · 대변 0"* 으로 읽고 **PASS 를 줬다.**

**실제**: 차변 **171,748** · 대변 **171,748** · 차 **0** · 계정 9개 🟢

응답 필드가 `debitTotal`/`creditTotal` 인데 내 스크립트가 `debit`/`debitAmount` 만 찾아 0 으로 읽었다.

🔴 **두 겹으로 틀렸다**:
1. 필드명을 확인하지 않고 추측했다
2. **0 이 나왔는데 PASS 를 줬다** — 전표가 수십 건인데 시산표가 0 이면 그건 이상 신호다.
   *"0 = 0 이니 균형"* 이라고 읽은 게 아니라, **0 인 이유를 묻지 않은 것**이 잘못이다.

⇒ **규율 추가: 집계가 0 이면 PASS 가 아니라 UNKNOWN 이다.** 0 인 이유를 먼저 가른다.

## 6. 못 잰 축 (UNKNOWN — 「문제 없음」이 아니다)

| 축 | 상태 | 왜 못 쟀나 |
|---|---|---|
| **계산서 → 세금계산서 사슬** | 🔴 미검증 | **데이터 0건.** 재려면 전표를 만들어야 한다 |
| **BOM 전개 → 생산 → 재고** | 🔴 미검증 | BOM 4건 있으나 시나리오를 안 돌렸다 |
| **재고이송 out/in 짝** | 🔴 미검증 | 이력 2건 있으나 원장 대조를 안 했다 |

🔴 **이 셋은 「봉합 대상」이 아니라 「측정 대상」이다.**
계산서는 0건이라 시험 데이터를 만들어야 잴 수 있다 ⇒ **쓰기 결재가 별도로 필요하다.**

⚠️ **그리고 지금 규모로 잰 것은 규모로 인한 통과일 수 있다** (사장님 지적).
창고 3개·품목 15개·전표 수십 건이다. **5만 고객사 목표 대비 표본이 아니다.**
볼트너트 하나가 다창고였던 덕에 검사식 결함이 드러났다 — 품목이 수백 개면 무엇이 더 나올지 모른다.
