### 🔴 핵심 적발 — 승인된 전제가 DB-125 에서는 성립하지 않는다

`UpdateOrchestrator.cs:537-556` 에 이 구멍이 **글자로 적혀 있고**, 「실패해도 **새 컬럼을 쓰는 화면만** 오류가 나고 나머지는 돈다 ⇒ 재설치보다 피해가 작다」는 근거로 **2026-08-09 사장님 결재로 통과**가 됐다.
그 근거는 **컬럼 추가 마이그** 전제다. **DB-125 는 인덱스 마이그**라 실패해도 **오류가 0건**이고, 같은 zip 이 실어 온 **㉪ 한 줄은 그대로 켜진다**. 즉 **증상 없이 2~4% 구간에서 지금보다 1.5~2.8배 넓게 잠그는 상태**가 남는다.
같은 줄의 재결재 조건(`:555` 「마이그가 **데이터를 변형하는 종류**로 넓어지면」)도 **DB-125 에서는 안 걸린다** — 조건의 분류축이 틀렸다. 걸어야 할 축은 **「제품 코드의 동작이 그 마이그를 전제로 바뀌는 릴리스인가」**다.

### 게이트가 못 보는 이유
G-RC18 은 「인덱스 없는 DB 에서 **등록이 되는가**」를 본다. 이 상태는 **등록이 된다.** 그래서 초록이다. 게이트가 재는 축(가동 여부)과 사고의 축(잠금 범위)이 다르다.

## §1 A — 업데이트·설치 흐름에서 마이그 실패가 어떻게 처리되는가

## §2 B — 기존 「무엇이 실패하면 업데이트를 막는」 지점

### 2-1. 있다. 주소는 이것이다

| 차단 지점 | 주소 | 막는 것 | 스왑 기준 |
|---|---|---|---|
| 🟢 **백업 실패 차단** | **`src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs:172-181`** | `RunPreUpdateBackupAsync` 가 false → `blocked` 기록 + 본사 통지 + `return false` | **전** |
| 디스크 부족 | `:152-159` | `blocked`(fail-open) | 전 |
| 다운로드·해시 | `:162-167` | `return false` | 전 |
| 마이그 교차검증 | `:519-524` | `schema_migrations` **조회 불가**일 때만 `blocked` | 전 |
| 신버전 검증 | `:246-253` → `:661` | FileVersion·/health 불일치 → **롤백** | **후** |

백업 게이트 원문(`:172-181`) — 이것이 사장님이 말씀하신 「같은 자리」의 실체다:

    var (backupOk, backupFile) = await _backup.RunPreUpdateBackupAsync(ct);
    if (!backupOk || string.IsNullOrWhiteSpace(backupFile)) {
        _logger.LogError("[Update] 적용 전 백업 실패 — 업데이트 전 과정 물리적 차단({V}). 데이터 무결성 우선.", ...);
        await RecordApplyStatusAsync(manifest, "blocked", "적용 전 백업 실패 — 업데이트 차단(데이터 무결성 우선)", ct);
        await _meta.NotifyEmergencyAsync("update_backup_failed", $"pre-apply:{manifest.Version}", ct);
        return false; }

### 2-2. 🔴 그 자리에는 못 건다 — 시각이 다르다
백업은 **스왑 전**이고 마이그는 **스왑 후**다. 「같은 자리」를 찾으려면 **스왑 후에도 남아 있는 유일한 판정**을 봐야 하고, 그것이 **`VerifyNewVersionAsync`(`:661`)** 다. 이 자리는 이미 **「거짓 성공을 차단한다」**는 같은 목적으로 서 있고, 실패 시 갈 길(`FinishWithRollbackAsync` `:251`)도 이미 깔려 있다.

### 2-3. 🟢 제안 — `VerifyNewVersionAsync` 에 **3번째 조건**
현 2중 판정(② EXE FileVersion `:668-676` → ① /health 200+버전 `:678-706`) 뒤에 **③ 마이그 반영 확인**을 붙인다.

- **재료가 전부 이미 있다**: 스왑 전 `:526-533` 이 이 zip 의 **신규 마이그 ID 목록**(`newMigrations`)을 이미 만든다 — 필드로 들고만 있으면 된다. 읽는 수단도 `WatchdogStatusWriter.GetAppliedMigrationIdsAsync`(`src/HitPan.Watchdog/AutoUpdate/WatchdogStatusWriter.cs:170`)로 **이미 있다**.
- **판정**: 재시작·/health 통과 뒤 `GetAppliedMigrationIdsAsync` 를 **다시** 읽어 `newMigrations` 가 전부 들어왔는지 본다. 하나라도 빠졌으면 `FinishWithRollbackAsync(…, "마이그 미반영", ct)`.
- **롤백이 옳은 실패 모드인 이유**: ㉪ 한 줄과 DB-125 는 **같은 zip** 에 실려 온다. 롤백하면 ㉪ 도 같이 내려가 고객은 **현 기준선**으로 돌아간다 — 바로 이 구멍이 만드는 「㉪ 만 켜진 상태」가 사라진다.
- ⚠️ **추론**: 재시작 직후 워치독이 `db.conf` 로 DB 를 읽을 수 있다고 코드상 읽었으나(`ResolveDbCredentials`), **실행으로 확인하지 않았다**.

### 2-4. 🟡 대안 — 게이트 축을 바꾼다 (제품·워치독 코드 무수정)
G-RC18 을 「등록이 되는가」가 아니라 **「인덱스 없는 DB + ㉪ 에서 잠금 행 수가 기준선보다 크면 FAIL」**로 세운다. 이번 §4 표가 그 임계의 실측 근거다. 워치독을 안 건드리므로 **#43 무저촉**이나, **이미 나간 고객 PC 는 못 구한다** — CI 에서만 막는다.

## §3 C — `schema_migrations` 는 실패를 기록하는가 · 한 질의로 알 수 있는가

### 3-1. 🟢 실패도 기록한다
- 컬럼 정의 `src/HitPan.API/Migrations/SQL/DB-84_schema_migrations.sql:39` — `success TINYINT(1) … 1=성공(다음번 skip 대상). 0=실패(재적용 대상)`
- 기록 `src/HitPan.Application/Services/MigrationRunner.cs:206-223` — `INSERT … ON DUPLICATE KEY UPDATE`. 실패 경로 `:120`(파일 읽기 실패)·`:152`(실행 실패) 둘 다 `success: false` 로 **행을 남기고 즉시 중단**한다.
- ⇒ **한 질의로 알 수 있다**: `SELECT success FROM schema_migrations WHERE migration_id='DB-125';`(행 없음 = 시도조차 안 됨)

### 3-2. 🔴 그런데 `schema_migrations` 는 「인덱스가 있다」의 증거가 못 된다

| 새는 경로 | 근거 |
|---|---|
| **success=1 인데 아무 일도 안 한 전례** | `DB-124_lock_scope_indexes.sql:21-22` — 「DB-111/112 사고: `tenants` 를 조인한 마이그가 고객 PC 에서 **0행이라 "성공"으로 기록되고 아무 일도 안 했다**」 |
| **신규설치는 돌지도 않고 1 이 된다** | `installer/hitpan_db_clean.sql:3589·3604` 가 `('DB-124','clean-ddl',1)` 을 **시드**한다. DB-125 도 같은 줄에 들어갈 것이다 |
| 🔴 **CI 가 못 잡는다** | `scripts/ddl-smoke-test.sh:94-103` 은 **「소스 DB-*.sql 개수 == 시드 success=1 개수」만** 대조한다. **출하 DDL 의 `CREATE TABLE` 에 `KEY` 줄이 실제로 들어갔는지는 안 본다** ⇒ DB-125 를 시드에만 넣고 `KEY` 2줄을 빠뜨려도 **CI 는 초록**이고, 그 고객은 **신규설치부터 「인덱스 없음 + ㉪」** 상태로 출발한다 |
| DDL 부분 적용 | DB-125 는 인덱스 2개다. 첫째 성공·둘째 실패면 MariaDB 암묵 커밋으로 **첫째는 남은 채** `success=0` 이 된다 |

### 3-3. 🟢 런타임 한 질의의 정답은 `information_schema`
DB-124 가 스스로 쓰는 관용구(`DB-124_lock_scope_indexes.sql:30-39`)가 그대로 답이다.

    SELECT COUNT(DISTINCT index_name) FROM information_schema.statistics
     WHERE table_schema = DATABASE() AND index_name IN ('ix_c2','ix_c4');   -- 2 여야 한다

**권고**: §2-3 의 3번째 조건은 `schema_migrations` **와** `information_schema` **둘 다** 본다. 전자만 보면 3-2 의 네 경로가 전부 통과한다.

## §6 🔴 내가 못 잰 것 (추론과 실측을 섞지 않는다)

1. 🔴 **0% 의 ②㉪ 가 앞 문서(61)와 안 맞는다 — 2,266 이 나왔고 원인을 못 밝혔다.** 같은 사본 계보인데 갈렸다. 방향(㉪ 가 0% 에서 압도적으로 좋다)은 같으나, **0% 임계를 게이트에 쓸 거면 이 차이를 먼저 밝혀야 한다.**
