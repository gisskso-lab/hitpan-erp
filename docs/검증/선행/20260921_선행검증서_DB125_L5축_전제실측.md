## §5 🔴 전제 한 줄이 틀렸다 — `rt.partner_id` 는 **이미 있다**

T1-2 는 「`rt` 를 좁힐 술어가 `tenant_id`·`is_deleted`·`status` 뿐」이라 했다. **표를 열어 보니 아니다.**

### 5-1. 실측

| 확인 | 결과 |
|---|---|
| `purchase_returns.partner_id` 칸 | ✅ **존재** |
| NULL 개수 | **0 / 998** |
| `rt.partner_id <> pr.partner_id` 인 행 | **0 건** |
| `pr` 에 짝 없는 `rt`(고아) | **0 건** |
| 기존 인덱스 | **`idx_partner(partner_id)`** — 회사 접두 없는 단일칸(원인 B 의 모양) |
| 대상 거래처의 `rt` / `rti` | **98 / 495** |

⇒ **거래처 술어는 `pr` 에만 있는 게 아니다. `rt` 에도 있고, SQL 이 안 쓰고 있을 뿐이다.**

### 5-2. 값 동등 술어 1줄(⑤안)을 더했을 때

시험 문장에만 `AND rt.partner_id = @PartnerId` 추가.

| 안 | `rt` 계획 | `rt` rows | **잠금** | 기준선 대비 | **값** |
|---|---|---:|---:|---:|---|
| ① 기준선 | `ALL` | 998 | 3,124 | — | ✅ 3,666,200.00 |
| ④ 인덱스만(최선) | `ref ix_r3` | 998 | 3,116 | −0.26% | ✅ 3,666,200.00 |
| **⑤a 술어 1줄 · 새 인덱스 0** | 🟢 `ref` **`idx_partner`**(기존) | **98** | 🟢 **1,390** | 🟢 **−55.5%** | ✅ **3,666,200.00** |
| ⑤b 술어 + `ix_r4` | `ref idx_partner`(옵티마이저가 `ix_r4` 를 **안 고름**) | 98 | **1,390** | −55.5% | ✅ 3,666,200.00 |
| ⑤b′ 술어 + `FORCE ix_r4` | `ref ix_r4` | 98 | **1,389** | −55.5% | ✅ 3,666,200.00 |
| **⑤c 술어 + `ix_r5` 덮개** | 🟢 `ref ix_r5` `Using index` (**힌트 없이 자발 선택**) | **98** | 🟢 **1,292** | 🟢 **−58.6%** | ✅ **3,666,200.00** |

🔴 **읽는 법 — 이득의 출처를 헷갈리면 안 된다**
- **−55.5% 는 술어가 만든다. 새 인덱스 0개다.** 기존 `idx_partner` 가 이미 있다.
- **덮개인덱스 `ix_r5` 가 더하는 몫은 1,390→1,292 = 전체의 3.1%p 뿐.**
- ⇒ **「DB-125 같은 인덱스가 L5 를 구한다」는 서사는 성립하지 않는다.** 구하는 것은 술어다.
- ⇒ **B-4(제품 SQL 0줄)와 B-2(이득 있는 인덱스만)가 여기서 충돌한다. 검증이 정할 일이 아니라 설계·결재가 정할 일이다.**
- 참고: **1,292 는 T1-2 가 `purchase_returns` 98건 규모에서 쟀던 잠금값과 같다** — 술어가 「반품이 98건이던 시절」로 되돌린다는 뜻이다.

| ⑤-a | `rt.partner_id` 가 **항상** `pr.partner_id` 와 같다는 **보장 경로** — 누가 채우나, NULL 가능한가, 매입전표 거래처 변경 시 동기되나 | 본 검증은 **1회사·998행 이관 데이터**만 봤다. 운영 입력 경로는 안 봤다 |
| ⑤-b | `receipt_id IS NULL` 인 반품(전표 없는 반품)에서 `partner_id` 가 어떻게 되는가 | 이 DB 는 998/998 이 채워져 있다 |
| ⑤-c | **공용 식(`rm` 하위질의)과의 값 동등성** — 공용 식도 같이 고쳐야 두 식이 갈라지지 않는다 | **G-RC11 SHA 앵커**가 걸려 있다 |
| ⑤-d | `idx_partner` 가 **회사 접두 없는 단일칸**이라는 점(원인 B 의 모양) — 다회사 DB 에서 이 인덱스로 충분한가 | 이 DB 는 회사 1개라 구분이 안 된다 |

## §6 이웃 프로브 — **잠금이 줄어도 막힘이 그대로면 고친 게 아니다**

세션 A 가 L5 를 `LOCK IN SHARE MODE` 로 쥔 채 `SELECT SLEEP(9)`, 세션 B 가 `innodb_lock_wait_timeout=3` 으로 **다른 거래처(`91c9bfe2…`) 매입반품 INSERT**.
INSERT 칸: `return_id, tenant_id, return_no, partner_id, return_date`.

| 회차 | A 가 쥔 안 | A 보유 잠금 | B 결과 | 판정 |
|---|---|---:|---|---|
| **N-0 음성대조군** | (없음) | — | **성공** | 대조군 성립 |
| **N-1** | ① 기준선 (인덱스 없음) | 3,124 | **1205 timeout** | 🔴 막힘 (P-12 재현) |
| **N-2** | ④ 기준선 + `ix_r3`(최선 인덱스안) | **3,116**(프로브 중 실측) | **1205 timeout** | 🔴 **여전히 막힌다** |
| **N-3** | ⑤c 술어 1줄 + `ix_r5` | 1,292 | **성공** | 🟢 풀린다 |
| **N-6** | ⑤a 술어 1줄 · **새 인덱스 0** | 1,390 | **성공** | 🟢 풀린다 |
| **N-4·N-5·N-7 음성대조군** | (없음) | — | **성공** ×3 | 대조군 성립 |

🔴 **N-2 가 V-8 의 최종 못이다.** 잠금이 3,124→3,116 으로 줄어도 **이웃은 똑같이 막힌다. 고친 게 아니다.**

> ⚠️ **대조군에서 실제로 당한 것(기록)**: 1차 시도에서 보유 세션을 `kill` 로 끊었더니 Windows 의 `mysql.exe` 가 살아남아 **음성 대조군이 1205 로 나왔다.** `SLEEP` 을 짧게 잡고 `wait` 로 자연 종료시키도록 고친 뒤 대조군 4회가 전부 「성공」으로 섰다. **대조군이 없었으면 N-3·N-6 을 거짓으로 읽을 뻔했다.**

## §8 실물 규모 ALTER 비용 (B-6)

🔴 **33306 어디에도 「실물 규모 `purchase_returns`」가 없다** — `hitpan_v4_a.purchase_returns` 는 **0행**이다. 그래서 `t1_ret_scale` 을 만들어 998행을 **128배(127,744행 · 데이터 32.6MB)** 로 부풀려 쟀다.

| 인덱스 | 칸 수 | **ALTER 소요** | **인덱스 증가** |
|---|---:|---:|---:|
| `ix_r1(tenant_id,is_deleted,status)` | 3 | **1,756 ms** | +11.6 MB |
| `ix_r3(…,receipt_id,return_id)` | 5 | **2,829 ms** | +16.6 MB |
| `ix_r5(…,partner_id,…,return_id)` | 6 | **6,331 ms** | +22.7 MB |
| `ix_p1` on `purchase_receipts` @1,962행 | 3 | **316 ms** | (측정 생략 · 1MB 미만) |

- 전부 **C-1a 의 10초 문턱 아래**(127,744행 기준).
- ⚠️ 소요 시간에 `mysql.exe` **기동 시간(~0.3s)이 포함**돼 있다 — 실제 ALTER 는 이보다 짧다(보수적 수치).
- ⚠️ **인덱스 증가량이 크다.** `ix_r5` 는 **원본 데이터(32.6MB)의 70%**. 6칸 인덱스는 값이 확실할 때만 넣어야 한다.
- ⚠️ 5만 고객사 규모에서 `purchase_returns` 가 몇 행이 되는지는 **모른다** — 128k 는 내가 정한 가정이다.
