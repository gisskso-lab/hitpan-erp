## 2. 서버는 결백하다 — 브라우저 없이 왕복이 통과한다

브라우저를 완전히 빼고 `curl` 로 왕복 ①②③ 을 돌렸다.

```
① mainpc-challenge  (도메인 경유)   → 200 · 표 발급
② mainpc-proof      (127.0.0.1 직결) → {"confirmed":true}
③ mainpc-verify     (도메인 경유)   → {"outcome":"MainPcConfirmed","isMainPc":true,"pass":"..."}
```

⇒ **등록·봉인키·로컬직결·판정이 전부 정상이다.** 사장님이 등록하신 것은 살아 있다.
⇒ 고장은 **브라우저 구간 하나**로 좁혀졌다.

> ⚠️ 이 측정이 먼저였던 이유 — 서버를 의심한 채로 브라우저를 파면, 브라우저에서 무엇이 나와도
> 그것이 원인인지 증상인지 가를 수 없다. **결백한 쪽을 먼저 지운다.**

---

## 3. 증상 — 앱만 실패하고, 같은 페이지의 생짜 fetch 는 성공한다

실제 Chrome(153.0.8010.53)을 **화면 있는 상태로** 띄워 로그인시켰다.

| 무엇 | 결과 |
|---|---|
| `mainpc-challenge` | 200 |
| `mainpc-proof` (앱이 보낸 것) | **`net::ERR_ABORTED`** · 응답 없음 |
| 출입증 `sessionStorage` | `null` |
| 같은 페이지에서 **생짜 `fetch`** | **200 성공** (6~27ms) |

🔴 `ERR_ABORTED` 는 **차단이 아니라 요청자가 스스로 끊은 것**이다. 앱은 `AbortController` 로 1500ms 만 기다린다.

앱 함수(`hitpanMainPc.probe`)를 화면이 안정된 뒤 3회 불렀다 — **3회 모두 3027ms**(= 1500ms × 두 주소) 로 abort.

> ⚠️ **헤드리스로 재면 안 된다.** 이 왕복은 실물 브라우저 정책에 걸리는 축이라 결과가 뒤집힌다.

## 4. 🔴 브라우저 종류가 아니다 — 대조실험 4단계

### 4-1. Edge 도 똑같이 실패한다

새 프로필 Edge(153.0.4234.32) 3회 — `FAIL 1505ms · 1515ms · 1504ms`.
⇒ **P-3 반증.** Chrome 만의 문제가 아니다.

### 4-2. 기능을 하나씩 끄며 좁혔다 (Chrome · 변수 하나만 바꿈)

| 끈 기능 | 결과 |
|---|---|
| (없음 · 기본) | FAIL @1503 · 1514 · 1501ms |
| `PrivateNetworkAccessSendPreflights` | FAIL @1509 · 1505 · 1516ms ← **범인 아님** |
| **`LocalNetworkAccessChecks`** | **OK 200 @11 · 6 · 5ms** ← **범인** |

🔴 **preflight 계열이 아니라는 것이 핵심이다.** 서버에 `Access-Control-Allow-Private-Network` 헤더를
더하는 방식은 **이 차단에 닿지 않는다.** (그 가설로 착수했다면 헛수고였다)

### 4-3. 권한 저장시각이 사장님 관찰과 일치한다

브라우저는 이 권한을 `loopback_network` 라는 이름으로 **프로필마다** 저장한다.
(`%LOCALAPPDATA%\{Google\Chrome|Microsoft\Edge}\User Data\Default\Preferences` — **읽기만 함**)

| 브라우저 | `https://test1234.hitpan.kr` | 허용된 시각 |
|---|---|---|
| Edge | 허용 | **2026-09-23 01:31** ← 9/23 실물 실측을 한 그때 |
| Chrome | 허용 | **2026-09-25 01:09** ← 사장님이 *"인식 못하네"* 라고 하신 그 시각 |

### 4-4. 권한 한 줄만 넣으면 된다 (결정 실험)

새 프로필 두 개를 만들고 **`loopback_network` 허용 한 줄만** 달리 주입했다.

| 프로필 | 결과 |
|---|---|
| 권한 없음 | FAIL @1506 · 1516 · 1501ms |
| **권한만 미리 넣음** | **OK 200 @42 · 5 · 5ms** |

⇒ 코드·서버·브라우저 종류 전부 동일. **바뀐 것은 권한 한 줄뿐이다.**

### 4-5. 사장님 실물 확인

사장님 Chrome **새로고침 → 정상 인식**. (권한이 01:09 에 이미 저장돼 있었다)

## 5. 🔴 P-4 반증 — 1500ms 로 짧게 잡은 근거가 사실이 아니다

코드 주석: *"길게 잡으면 히트판이 없는 컴퓨터에서 로그인이 그만큼 느려진다"* (`hitpan-mainpc-proof.js:37`)

실측 — 히트판이 없는 자리(빈 포트)로 브라우저에서 요청:

```
실패 @1ms · 실패 @0ms
```

⇒ **연결 자체가 거부되어 즉시 끝난다. 기다릴 일이 없다.**
⇒ **시간제한을 늘려도 클라이언트 PC 는 전혀 느려지지 않는다.** 잃는 것이 없다.

| 상황 | 걸리는 시간 | 뜻 |
|---|---|---|
| 히트판 없는 PC | **1ms** | 연결 거부 — 즉시 |
| 메인PC · 권한 있음 | **5~42ms** | 정상 |
| 메인PC · 권한 팝업 대기 | **1500ms+ 매달림** | 지금 끊기는 자리 |
| 메인PC · 권한 **거부됨** | **1~3ms** | 즉시 차단 (매달림과 구별된다) |

## 6. 확정된 인과

```
새 브라우저로 처음 연다
   → 브라우저가 "이 사이트가 당신 컴퓨터 안을 봐도 됩니까" 팝업을 띄운다
   → 그동안 요청은 매달린다
   → 앱이 1500ms 에 스스로 끊는다  ⇒ "클라이언트 PC" 로 판정
   → 사용자가 [허용] 을 눌러도 그 왕복은 이미 죽어 있다  ⇒ 화면이 안 바뀐다
   → 새로고침해야 비로소 열린다
```

🔴 **고객 눈에는 "허용했는데도 안 되는 고장"으로 보인다.**

## 7. 🔴 9/23 「실물 실측 통과」가 틀렸던 이유

그날 Edge 에서 왕복이 돈 것은 **사람이 권한 팝업을 허용한 뒤의 결과**였다.
그 허용 동작이 측정에 들어가지 않았고, 인계서에는 *"브라우저 무관"* 으로 적혔다.

> **교훈**: 한 번 통과한 경로에 **사람 손이 하나 들어갔는지**를 세지 않았다.
> 브라우저를 안 바꿔본 것보다 이쪽이 더 큰 누락이다. → [[feedback_gate_must_test_behavior]]

## 8. 남은 미확정 (⚠️ 사실로 적지 말 것)

| # | 미확정 | 왜 못 닫았나 |
|---|---|---|
| U-1 | 권한 허용 **직후**, 새로고침 **없이** 같은 페이지에서 바로 되는가 | CDP `Browser.grantPermissions(localNetworkAccess)` 가 허용이 아니라 **즉시 거부(1~3ms)** 로 바뀌었다. 실물 팝업을 자동으로 누르는 길을 못 찾았다 |
| U-2 | 회사 정책(그룹정책)으로 이 권한이 막힌 PC 의 모양 | 그런 PC 가 없다. 다만 **[차단] 누른 것과 같은 1~3ms 즉시실패** 로 추정 (⚠️가설) |
| U-3 | Edge 가 이 정책을 언제부터 강제하는가 | 버전별 확인 안 함. 다만 **새 프로필 Edge 에서 이미 실패**하므로 이미 켜져 있다 |

## 9. 설계로 넘길 것

🔴 **이 봉합은 팝업 자체를 없애지 못한다.** 고객은 여전히 팝업을 한 번 본다 —
사장님 원칙 *"고객은 인증키가 도는지 안 도는지 모르게"* 와는 **충족되지 않은 채로 남는다.**
팝업이 아예 안 뜨는 길은 **별건 재설계**다 (사장님 2026-09-25 결재 시 봉합만 승인).

봉합 범위 두 가지:

| # | 무엇 | 근거 |
|---|---|---|
| ① | **기다려준다** — 팝업이 떠 있는 동안 포기하지 않는다 | §5 — 늘려도 잃는 것이 없다 |
| ② | **다시 돈다** — 자료관리에 들어갈 때 왕복을 조용히 재시도 | 사장님 제안. 화면 새로고침이 아니라 **왕복만** 다시 돈다(입력 중인 내용이 날아가지 않는다) |

⚠️ **[차단] 을 누른 고객의 길을 함께 설계하지 않으면 또 막다른 방이 된다** (§5 — 1~3ms 즉시실패).
