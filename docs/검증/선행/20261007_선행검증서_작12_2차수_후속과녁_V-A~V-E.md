### §0-1 🔴🔴 먼저 — **투입 전제가 틀렸다 (측정 트리)**

작지서·투입 카드는 작업 디렉터리를 `docs/20261007-work12-anon-kickoff` 로 지정하면서 동시에 「1차수는 머지 완료 ⇒ `origin/main` 이 운영과 같은 트리」라고 적었다. **둘이 동시에 성립하지 않는다.**

```
git merge-base --is-ancestor HEAD origin/main  →  NO (HEAD 는 main 에 없다)
git diff --stat HEAD origin/main -- src/       →  5파일 +1150/−1
```
그 1150줄이 **1차수 B3-1 전부**다 — `InstallerBootstrapController.cs`(+239) · `InstallerBootstrapPreverifyGateTests.cs`(+678) · `InstallerBootstrapReducedResponseGateTests.cs`(+218) · `TunnelTokenRecovery.cs`(+10/−1) · `DbConfReaderTests.cs`(+6).

**⇒ [2] 설계·[3] 구현은 `origin/main` 에서 갈라야 한다.** 이 문서의 모든 수치는 `git show origin/main:<경로>` 로 뽑은 것이다. 줄번호도 main 기준이다.

### §2-1 게이트 수 — 🟢 PM·CTO 가 맞다 (단 범위를 정확히 적어야 한다)

| 질문 | 수 | 근거 |

### §2-2 🔴 `tenants.status` 전수 — **DEFAULT 는 `'trial'` 이 맞다. 그런데 코드는 그 값을 한 번도 쓰지 않는다.**

**출하 DDL** `installer/backoffice/00_backoffice_core.sql:115`

🔴 **CHECK 0 · ENUM 아님 · 트리거 0** ⇒ **아무 문자열이나 들어간다.** (같은 파일 `:86` `resellers.status` 는 `enum('active','suspended','inactive','terminated')` — **두 표가 다른 규율**이다.)

### §2-3 ⇒ **T-3 은 P0 가 될 수 있다. 단 「될 수 있다」가 지금 말할 수 있는 전부다.**

### §2-4 🔴 **「가입 직후 고객이 부트스트랩에서 401 을 받나」 — 받는다. 그리고 1차수가 만든 문제가 아니다.**

**① 받는다 (코드로 따진 사슬)**
```
LandingSignupController.cs:310-315   INSERT INTO tenants (… status …) VALUES (… 'pending' …)
      ↓  (결제확인 :385  또는  관리자 승인 SignupsAdminController.cs:203 이 오기 전까지 'pending')
InstallerBootstrapController.cs:88   WHERE t.license_key_hash=@Hash AND t.status='active'   → 매칭 0행
InstallerBootstrapController.cs:94   401 "올바르지 않은 시리얼이거나 승인되지 않은 계정입니다"
```

🔴 **단 DEFAULT `'trial'` 때문이 아니다.** 유일한 `INSERT INTO tenants` 가 `status` 를 **명시**하므로 DEFAULT 는 안 쓰인다. 실제 초기값은 **`'pending'`** 이다.
🟢 그리고 이 401 은 **정상 동작**이다 — 결제·승인 전 고객이고, 시리얼 키(`license_key_hash`)도 결제확인(`:385`)·승인(`:204`) 때 비로소 들어간다(`INSERT` 때는 `''`). **키가 없는 고객은 애초에 설치를 시작할 수 없다.** ⇒ **「가입 직후」에는 피해자가 없다.**
🔴 **피해자가 생기는 자리는 「키를 이미 받은 뒤 `active` 가 아닌 고객」**이다 — `'suspended'`(`TenantsAdminController.cs:169`) 와 **`'trial'`**(§2-2 · 쓰는 코드 0건이지만 DDL DEFAULT 이고 UI 가 「체험」으로 렌더한다). 그 고객은 **설치도, 워치독 터널 자가복구도 401** 이다.

| 측정 | 결과 |

| 1차수 **이전** 트리(`HEAD`)에 그 조건이 있나 | 🟢 **있다** — `InstallerBootstrapController.cs:88` 같은 줄 |

## §3 V-C (T-4) — `SerialVerifyController` UPSERT · 호출자 0건인가

### §3-1 🔴 대조군 실험 — **PM 의 두 주장 모두 사실. 측정했다.**

**읽히는 사실 3개**
1. 🟢 **4회에 잠긴다** (결재 수치는 5회) — PM 이 맞다. 그런데 사용자 메시지는 `:72` *"시리얼 입력 **5회** 실패로…"* ⇒ **화면이 거짓을 말한다.**

## §5 V-E (T-6 · D-1) — 423 글자가 설치 화면까지 가나

### §5-1 🔴🔴 **답 = 가지 않는다. 0%. 고객이 보는 글자는 두 글자 `{\` 다.**

**실물 EXE 를 돌리지 않았다.** 코드 경로 + 설치본이 실제로 쓰는 런타임(Windows PowerShell **5.1.26100.9444**) 측정으로 닫았다.

**경로 (`installer/HitPan-Universal.iss`)**

| 단계 | 줄 | 일어나는 일 |
|---|---|---|
| ① | `:559` | `Invoke-RestMethod … /api/installer/bootstrap` · `$ErrorActionPreference='Stop'`(`:552`) ⇒ **423 은 throw** |
| ② | `:564-565` | `catch` → `$msg = $_.Exception.Message` → **`if ($_.ErrorDetails -and $_.ErrorDetails.Message) { $msg = $_.ErrorDetails.Message }`** |
| ③ | `:567` | `ResponseFile` 에 `'{"success":false,"message":"' + ($msg -replace '"','\"') + '"}'` 를 쓴다 |
| ④ | `:601` | `Pos('"success":true', RawResponse) = 0` → 실패 분기 |

**측정 1 — ② 의 분기가 어느 쪽으로 가나** (PS 5.1 · 로컬 `HttpListener` 로 423+한글 JSON 을 반환)

```
$_.ErrorDetails null?  : False
$_.ErrorDetails.Message: {"success":false,"locked":true,"message":"설치 시도가 … 60분 후 …"}
```
⇒ `ErrorDetails` 가 **채워진다.** 따라서 `$msg` = **서버 본문 JSON 전체**.

**측정 2 — ③ 의 이중 포장 + ⑤ 의 평면 파서** (`ExtractJsonValue` `:340-365` 를 그대로 옮겨 시뮬레이션)

`ResponseFile` 실제 내용:
```

```
`ExtractJsonValue` 는 첫 `"message":` 를 잡고(= **바깥 것**), 앞의 `"`·공백을 건너뛴 뒤 **`"` · `,` · `}` 중 아무거나 나오면 멈춘다**(`:359-360`). 바깥 값의 첫 두 글자는 `{` `\` 이고 그 다음이 `"` 다.

```
>>> 고객이 보는 글자 = [{\]   (길이 2)

MsgBox:
  시리얼 인증 실패:
  {\
```

**측정 3 — 🔴 대조군: 봉합 전 401 은 어땠나**
```
401 본문 {"success":false,"message":"올바르지 않은 시리얼이거나 승인되지 않은 계정입니다."}
  → 고객이 보는 글자 = [{\]      ← 똑같다
ErrorDetails 가 없었다면(가정)
  → [The remote server returned an error: (423) Locked.]
```

### §5-2 ⇒ **작지서 T-6 의 전제 「미해독 실패 화면이 1종→2종」이 틀렸다**

- **1종 → 1종**이다. **401 도 423 도 똑같이 `{\`** 를 띄운다.
- 🔴 **1차수가 만든 문제가 아니다.** `installer/bootstrap` 의 **모든 비-2xx 응답**이 이미 `{\` 로 표시돼 왔다. 시리얼을 잘못 입력한 고객은 **지금까지 쭉** `시리얼 인증 실패: {\` 를 봤다.
- 🔴 **원인은 423 이 아니라 이중 포장**이다 — 이미 JSON 인 본문(`$msg`)을 또 JSON `message` 에 문자열로 싸고(`:567`), 그걸 평면 스캐너(`:340`)로 읽는다. **401·423 을 한 번에 고치는 한 줄 자리**다.
- 🟡 **1차수 설계가 `ExtractJsonValue` 평면 검색을 걱정한 건 옳았다**(「더해진 이름 0개」) — 다만 **성공 경로만** 봤고 **실패 경로를 안 봤다.**

### §6-3 🔴 T-1 — 숫자 없이도 지금 정할 수 있는 것 (PM 이 조건을 또 넓혔다)

작지서 §3 은 *"T-1 은 S-2 숫자 없이 **처방을 설계하지 않는다**"* 라 적었다. **처방의 선택지가 숫자로 갈린다는 전제**인데, 코드가 그 전제를 깬다.

| 지금 정할 수 있는 것 | 근거 |
|---|---|
| 🔴 **「처음 보는 지문은 행을 만들지 않고 기존 행만 올린다」 단독으로는 못 막는다** | `serial/verify` 지문은 자유 문자열이라 **「처음 보는 지문」이 무한**이다. 그 처방은 *행을 안 만드는* 쪽이 아니라 *기존 행을 못 찾는* 쪽으로 간다 ⇒ **TTL/purge 는 숫자와 무관하게 필수** (§3-4) |

| 🔴 **잠긴 요청도 행을 쓴다는 사실** | `InstallerBootstrapController.cs:156` · `SerialVerifyController.cs:67` ⇒ **잠금이 증식을 멈추지 않는다** — 이게 TTL 이 필수인 두 번째 이유 |
| 🔴 **두 끝점을 같이 세어야 한다** | `installer/bootstrap`(PC당 1지문) vs `landing/serial/verify`(무한 지문) ⇒ S-2 ③ `result` 집계를 **끝점별로** 보라 |

⇒ **PM 은 「처방 선택」과 「긴급도(며칠)」를 한 칸에 넣었다.** 선택은 지금 할 수 있고, 숫자는 **일정**을 정한다.
