## §1. 한 줄 결론 + 판정표

> **한 줄**: PM 의 「L3·L4 가 실물에서 위험하다」는 **맞다 — 그리고 더 나쁘다.**
> PM 이 못 본 **L2(미수·수금 축)가 collections 10.7만 행을 통째로 훑으며 112,019 행을 잠근다.**
> **「계획이 나쁘다 ≠ 잠금이 넓다」는 추론이 아니라 사실로 확인됐다**(대조군으로 갈랐다).
> 🔴 **그리고 §21-1 이 기각한 F-1(인덱스 이웃 간극이 회사 경계를 넘는다)은 격리해서 재니 맞다.**
> ⇒ **원인은 하나가 아니라 둘이고, PM 은 그중 하나를 잘못 지웠다.** 설계는 **둘 다** 놓고 시작해야 한다.

| # | 재야 할 전제 | 판정 | 한 줄 |
|---|---|---|---|
| **V1** | L3·L4 실물 계획이 독립 재현되는가 | 🟢 **확인 + 🔴 확대** | 재현됨(L3 `idx_pay_type` · L4 `ALL 2,196`). **단 PM 의 측정용 DB `rc_l4_probe` 는 collections·sales_deliveries 가 0행이라 L1·L2 측정이 무효**였다. 전 표를 채워 재니 **L2 가 `ALL 107,653`** — PM 표에 아예 없던 항목이 제일 나쁘다. 🔴 **방아쇠도 찾았다: 실물 이관 데이터는 `ref_doc_id`·`ref_order_id` 가 100% NULL** 이라 DB-124 마지막 칸의 통계가 안 잡힌다(§2-3-1). **§21-3-2 의 후보 ⓐ·ⓒ 는 실측으로 기각**(§2-3-3) |

| **V6** | PM 의 §8·§21 숫자가 재현되는가 | 🟡 **숫자는 재현 · 🔴 이유가 반증됨** | **15사례 · 통과 14 · 실패 1 · skip 0 · 빌드 warning 0** — 숫자는 맞다. **전체 회귀 1,528 · 통과 1,523 · 실패 5 · skip 0**(PM 은 1,524). 🔴 **G-RC13 이 빨간불인 이유가 PM 이 말한 것과 다르다** — 계획 단언은 **통과**했고 **게이트 자신의 음성 대조군이 깨져 있다**(§2-7-1). 🔴 카드가 지정한 환경에서 **백업 게이트 4건도 같이 빨간불**(§2-7-4) |

### 🔴 설계 범위를 가르는 한 줄 (V5)

**한 DB 에 회사는 1개다.** 따라서 —
- 「**다른 회사가 막힌다**」는 **실제 고객 환경에서는 일어나지 않는다.** §21-3-5 의 심각도 상향(「남의 회사까지 막는다」)은 **시험 DB 안에서만 참**이다.
- 대신 **「다른 거래처가 막힌다」가 진짜 증상이고, 그것은 V2 에서 실측으로 확인됐다.** 설계는 **회사 경계가 아니라 거래처·전표 경계**를 목표로 잡아야 한다.

#### 🔴 2-3-1. 내 자신의 정정 — 「방아쇠 = 거래처 편중」은 **내가 성급했다**

위 표만 보고 나는 한 번 「방아쇠는 거래처 편중」이라고 적었다. **교란변수가 있었다.**
`dp_small` 은 `ref_order_id` 를 채워서 시드했고, `dp_full`(실물)은 **안 채워져 있다.** 두 변수가 같이 달랐다.
갈라서 다시 쟀다 —

```
SELECT SUM(ref_doc_id IS NULL), COUNT(*) FROM hitpan_v4_a.collections;  → 109822 / 109822   (100% NULL)
SELECT SUM(ref_order_id IS NULL), COUNT(*) FROM hitpan_v4_a.payments;   →   2228 /   2228   (100% NULL)
SELECT SUM(ref_order_id IS NULL), COUNT(*) FROM dp_small.payments;      →      0 /   2060
```
(원본 `hitpan_v4_a` 에서 직접 셌다. 내 복사본이 망가진 것이 아님도 확인했다 — 두 스키마의 열 순서 차이 **0건**.)

그 결과 MariaDB 의 통계가 이렇게 남는다:
```
mysql.index_stats · dp_full.collections.idx_coll_tenant_doc      prefix_arity 3 → avg_frequency NULL   🔴
mysql.index_stats · dp_full.payments.idx_pay_tenant_type_ref     prefix_arity 3 → avg_frequency NULL   🔴
mysql.index_stats · dp_small.payments.idx_pay_tenant_type_ref    prefix_arity 3 → avg_frequency 1.0000 🟢
```
`ANALYZE TABLE … PERSISTENT FOR ALL` 을 돌려도 **NULL 그대로**다(실측).
⇒ 옵티마이저는 **DB-124 의 마지막 칸에 선택도가 없다**고 보고, 강제로 태워도 `rows` 를 **접두 범위 전체**로 추정한다:
```
FORCE INDEX(idx_coll_tenant_doc) → ref = const,const,dp_full.sd.delivery_id · key_len 416 · rows 107653
```
**세 칸을 다 쓰는데도 추정이 10.7만 행이다.** 그래서 전체 스캔을 고른다.

#### 2-3-2. 그래서 방아쇠는 무엇인가 — **정직하게: 하나로 못 좁혔다**

| 잰 것 | 결과 |
|---|---|
| 행 수만 늘리기(고른 분포 · `ref` 채워짐) 60 → 2,060 | 🟢 **계획 안 뒤집힘** ⇒ **행 수는 방아쇠가 아니다**(확정) |
| `ref_order_id` 100% NULL (실물) | 🔴 통계 없음 → 전체 스캔 |
| 실물에 `ref_order_id` 를 채워 넣고 재측정 (`avg_frequency` 3칸 = **10.75** 로 복구) | 🔴 **그래도 `ALL 2,228`** |
| `dp_small` (`avg_frequency` 3칸 = **1.0**) | 🟢 좋은 계획 |

⇒ **마지막 칸의 선택도가 결정적이되, 「NULL 이라서」 하나만으로는 설명이 안 된다.**
키당 1행이면 좋은 계획, 키당 10.7행이면 나쁜 계획 — **경계는 1 과 10.7 사이**다. 거기까지가 내가 잰 것이다.
⚠️ **추론(실측 아님)**: 거래처 편중은 바깥 표의 행 수를 늘려 같은 방향으로 밀지만, **독립 방아쇠인지는 못 갈랐다.**

#### 2-3-3. 설계 후보 ⓐ·ⓒ 를 실물 사본에서 시험했다 — **둘 다 안 듣는다**

§21-3-2 가 적은 후보를 내 사본(`dp_full`)에서 직접 걸어 봤다:

| 후보 | 해 봤더니 |
|---|---|
| **ⓐ 인덱스 신설** `payments(tenant_id, ref_order_id)` · `collections(tenant_id, ref_doc_id)` 추가 | 🔴 **L2·L4 그대로 `ALL`** — 안 듣는다 |
| **ⓒ 조인 순서 고정** `STRAIGHT_JOIN` 만 | 🔴 바깥은 좋아지나(`fk_pr_partner` rows 57) **안쪽이 `ALL` + `Using join buffer (flat, BNL join)`** — 여전히 표 전체를 훑는다 |
| ⓒ + `join_cache_level=0` | 🔴 **여전히 `ALL`** |
| ⓒ + **`FORCE INDEX` 까지** | 🟢 `pr ref fk_pr_partner 57` · `ep ref idx_pay_tenant_type_ref` — **좋은 계획은 힌트를 다 줘야 나온다** |
| `ANALYZE … PERSISTENT FOR ALL` | 🔴 안 듣는다 |

🔴 **⇒ 설계는 「인덱스 하나 더」(ⓐ)나 「순서만 고정」(ⓒ)으로 끝나지 않는다.** 실측이 둘 다 기각했다.
⚠️ **추론(실측 아님)**: 남는 길은 **통계가 안 통해도 계획이 고정되는 방법**(힌트 명시 / 문장 구조 변경 / 잠금 대상 자체를 좁히기)인데, **그중 무엇이 맞는지는 설계팀장 몫**이고 나는 고르지 않는다.

⚠️ **`dp_full` 은 이 시험들로 내가 인덱스 2개를 더하고 `ref_order_id` 를 일부 채워 놓았다**(§2-3-2 실험). §2-2·§2-4 의 원표는 **그 전에** 잰 값이다.

### 2-4. V2 · V3 — 🔴 잠금 실측 (두 연결 · 대조군 포함)

절차: A 가 `REPEATABLE READ` 트랜잭션에서 제품 문장을 `LOCK IN SHARE MODE` 로 돌린 뒤 `SLEEP(30)` 으로 유지.
B 는 `innodb_lock_wait_timeout=3` 으로 무관한 행을 건드린다. 스크립트 `scratchpad/dp/lockprobe2.sh` · `trace.sh`.

| 보유자(A) | B1 다른거래처 payments UPDATE | B2 payments INSERT | B3 무관 collections UPDATE | B4 collections INSERT |
|---|---|---|---|---|
| **L4** (`ALL 2,196`) | 🔴 **1205** | 🔴 **1205** | 🟢 OK | 🟢 OK |
| **L2** (`ALL 107,653`) | 🟢 OK | 🟢 OK | 🔴 **1205** | 🔴 **1205** |
| **D1-b (대조군 · 좁은 인덱스)** | 🟢 OK | 🟢 OK | 🟢 OK | 🟢 OK |

🔴 **대조군이 원인을 갈랐다**: 같은 `LOCK IN SHARE MODE` 라도 **좁은 계획이면 아무도 안 막힌다.**
⇒ **「계획이 나쁘다 → 잠금이 넓다」는 이제 추론이 아니라 실측이다.** (§21-4 의 한계 1·2 해소)

## §3. 설계가 알아야 할 사실 (이것만 읽고 시작할 수 있게)

1. **표적은 회사 경계가 아니라 거래처·전표 경계다.** 실제 고객 설치는 **한 DB 한 회사**다(§2-5). 「다른 회사가 막힌다」는 시험 DB 안의 현상이다. **진짜 증상은 「같은 회사 안의 무관한 거래처가 막힌다」이고 그것은 실측됐다**(§2-4).
2. **가장 나쁜 자리는 L3·L4 가 아니라 L2 다.** `collections` 10.7만 행 전체 스캔 · **112,019행 잠금**. 이 트랙 이름이 「수금등록」인데 **수금 축이 제일 나쁘다.** PM 표에 없어서 아무도 안 보고 있었다.
3. 🔴 **DB-124 는 실물 분포에서 구조적으로 못 쓰인다.** 실물 이관 데이터는 **`collections.ref_doc_id` 가 100% NULL(109,822/109,822) · `payments.ref_order_id` 가 100% NULL(2,228/2,228)** 이다. 그 칸이 DB-124 세 칸 인덱스의 **마지막 칸**이라 `mysql.index_stats` 의 `prefix_arity 3` 이 **NULL** 로 남고(= 선택도 없음), 강제로 태워도 `rows` 추정이 접두 범위 전체(10.7만)로 찍힌다. **인덱스를 「넣었으니 됐다」가 아니다 — 데이터가 그 인덱스를 못 쓰게 생겼다.**
4. **행 수는 방아쇠가 아니다.** 고른 분포에서 2,060행까지 좋은 계획이 유지된다. ⇒ 「데이터가 커지면 생기는 문제」로 다루면 틀린다. **경계는 마지막 칸의 선택도**이고, 내가 좁힌 범위는 **키당 1행(좋음) ~ 키당 10.7행(나쁨)** 사이다. 하나로 못 좁혔다(§2-3-2).
5. 🔴 **§21-3-2 의 후보 ⓐ(인덱스 신설)·ⓒ(조인 순서 고정)는 실측으로 둘 다 기각됐다**(§2-3-3). `ANALYZE … PERSISTENT FOR ALL` 도 안 듣는다. 좋은 계획은 **순서 + 인덱스를 둘 다 강제해야** 나온다.
6. **이 문제가 가장 심한 시점은 「이관 직후, 수금 입력 0건」이다** — 바로 수금등록 화면을 처음 쓰는 그 시점이다. 사용자가 실제 수금을 넣기 시작하면 그 칸에 값이 차면서 선택도가 생긴다(⚠️ 그 전이가 어디서 일어나는지는 **못 쟀다**).
7. **좁은 계획이면 아무도 안 막힌다** (대조군 D1-b). 즉 **`LOCK IN SHARE MODE` 자체는 죄가 없다.** 고칠 것은 잠그는 **범위**다.
8. **`purchase_returns` 는 실물 사본에서 0행**이다. L5·D1-c 의 실물 계획은 **아직 아무도 못 쟀다** — 이 상태의 EXPLAIN 을 근거로 쓰면 안 된다.
9. 🔴 **잠금 문제의 원인은 둘이다. 하나만 고치면 다른 하나가 남는다.**
   - **원인 A — 계획이 넓다**: L2·L4 가 표를 통째로 훑으며 `PRIMARY` 위에 전 행 잠금(112,019 / 2,274). **같은 회사의 무관한 거래처가 막힌다.** 실물 분포에서만 난다.
   - **원인 B — 이웃 간극이 경계를 넘는다**: `idx_pay_partner` 처럼 **회사 접두가 없는 인덱스**를 고르면 `gap ... insert intention` 이 옆 회사/옆 거래처를 막는다. **시험 시드 규모에서도 난다.**
   - 두 원인은 **서로를 가린다**(§4-B 반증 ①). 어느 쪽을 봉합하든 **나머지 하나를 격리해서 다시 재야** 한다.
10. **기존 게이트는 이 둘 중 어느 것도 현재 못 잡는다.** 원인 A 는 시드 분포 때문에(§2-7-2), 원인 B 는 `MatchLockIndexes` 가 손으로 적은 목록이라 `PRIMARY`·`uq_*_source` 를 못 봐서(§4-B 반증 ③). **게이트 시드를 실물 분포로 바꾸는 일이 설계 범위에 들어가야 한다.**

| **④-10** 🔴 | §21-3-2 가 설계 후보로 적은 **ⓐ 인덱스 신설(DB-125)** · **ⓒ 조인 순서 고정** | 🔴 **내 사본에서 직접 걸어 보니 둘 다 안 듣는다**(§2-3-3). ⓐ 는 계획 무변경 · ⓒ 는 안쪽이 `BNL join` 으로 여전히 표 전체 스캔. **후보 목록을 그대로 들고 설계를 열면 두 번 헛다리를 짚는다** | 🔴 높음 |

### 🔴 내가 틀린 것 (나도 적는다)

- 나는 중간에 **「방아쇠는 거래처 편중」**이라고 한 번 적었다. **교란변수가 있었다** — 비교한 두 DB 가 `ref_order_id` 채움 여부까지 같이 달랐다. 갈라서 다시 재고 §2-3-1 에 정정했다. **PM 이 이 트랙에서 두 번 한 실수를 나도 한 번 했다.**

### 🔴 PM 이 맞은 것 (억지 반증 안 한다)

- **§21-2 의 L3 `idx_pay_type` · L4 `ALL 2,196` 은 내 독립 DB 에서 그대로 재현됐다.** 숫자까지 같다.

## §4-B. 반증 과제 3건 (카드가 지정한 것)

### 반증 ① — §21-1 의 대조군은 **원인을 가를 수 없는 설계였다** 🔴

§21-1 은 B7·B8(이웃) 과 B9·B10(멂) 을 비교해 「넷 다 막혔으니 이웃 간극(인덱스 축)이 원인이 아니다」라고 결론했다.

**측정한 사실** —
1. 대조군이 가른 변수는 **`partner_id` 의 정렬 거리**다 (`RcSafePathGateTests.cs:1021-1035`: `xPay = PB[..^1]+'z'` vs `fPay = "ff"+guid[2..]`).
2. §21-1 이 찍었다는 대기 상대는 **`uq_payments_source`** 이고, 그 인덱스의 칸은 **`(tenant_id, source_type, source_id)`** 다 (실측 · §2-6).
3. B7·B9 의 INSERT 문은 **`source_type`·`source_id` 를 아예 안 적는다**(`:1038`·`:1040`) → 둘 다 NULL. `tenant_id` 는 둘 다 같은 `otherT`.

**연역 (1+2+3 의 논리적 귀결)** — `uq_payments_source` 의 정렬에서 B7 과 B9 는 `(otherT, NULL, NULL)` **같은 자리**다.
**「이웃」과 「멂」이 아니라 같은 점이다.** 대조군이 가른 변수(`partner_id`)는 **잠금이 관측된 인덱스에 아예 들어 있지 않다.**

🔴 **⇒ 이 실험은 차이가 나올 수 없는 실험이었다.** 「넷 다 막혔다」는 이웃 가설을 기각하는 근거가 **못 된다.**
카드가 의심한 「멀다고 고른 id 가 실제로는 이웃이었을 가능성」보다 더 나쁘다 — **찍힌 잠금이 있는 인덱스에 거리 축이 아예 없었다.**

**빠진 것 ①: 음성 대조군.** 넷 다 「막혀야 할 이유가 있는」 쪽이었고, **「막히면 안 되는」 사례가 하나도 없었다.**
내가 §2-4 에서 넣은 **D1-b(좁은 계획) 보유자**가 그 자리다 — 4건 전부 통과했고, 그래서 원인이 갈렸다.

**빠진 것 ②: 격리.** PM 의 시나리오는 매칭 흐름 전체를 잡은 채 쟀다 = **잠금이 여러 개 동시에 걸려 있다.**
그중 하나(`uq_payments_source` 간극)가 **먼저 걸리면 뒤의 원인은 안 보인다.** 「넷 다 막혔다」는 **원인 하나가 다른 하나를 가린 결과**다.

🔴 **그래서 격리해서 다시 쟀다 — F-1 가설은 맞다(§2-6-1).**
L3 문장 **하나만** 잡고 재니 **이웃(다른 회사)은 1205, 먼 것(다른 회사)은 통과**했고,
대기 상대가 `index idx_pay_partner ... lock_mode X locks gap before rec insert intention waiting` 로 찍혔다.
⇒ **§21-1 의 「F-1 가설 기각」은 반증됐다. 원인은 둘이고, 인덱스 축도 그중 하나다.**

### 반증 ② — §21-2 의 「S3 실측은 시험 시드에서만 성립」은 **맞다**. 대표성은 실물 쪽이다

S3 0단계가 잰 것은 **게이트 시드(표당 30~300행 · 거래처가 고르게 분포)** 다. 내가 `dp_small` 로 같은 규모를 재현하니 L4 가 `fk_pr_partner → idx_pay_tenant_type_ref rows 1` 로 **좋은 계획**을 고른다(§2-3).
실물(`hitpan_v4_a`)은 **거래처 편중이 크고 타입 칸의 선택도가 0**이다 — 그쪽에서는 `ALL` 이다.

🔴 **대표성은 실물 쪽이다.** 이유는 「크다」가 아니라 **분포가 다르다**는 것이다(§2-3: 행 수를 2,060까지 올려도 고르게 뿌리면 계획이 안 뒤집힌다).
⇒ 설계는 **시험 시드에서 초록인 것을 근거로 쓰면 안 된다.** 게이트 시드를 실물 분포(편중 + 타입 선택도 0)로 바꾸지 않는 한, 그 게이트는 이 문제를 영원히 못 본다(§2-7-2).

### 반증 ③ — 고정값은 **문제를 덮는 장치가 맞다** 🔴

| 고정값 | 값 | 판정 |
|---|---|---|
| `MaxCrossTenantBlocked` | **4** | 🔴 **죽은 단언.** `crossOps` 가 **정확히 4건**이다(`:1036-1042`). `crossBlocked.Count <= 4` 는 **수학적으로 절대 실패할 수 없다.** 주석이 「현재 4(전부)」라고 스스로 적고 있다 — **상한을 가능한 최댓값에 못 박은 것은 아무것도 못 박은 것이다.** 감시자 0 |
| `MaxCrossTenantUnnamed` | 2 | 🟡 살아 있다(최대 4 중 2). 다만 「관측 실패 건수」를 고정한 것이라 **관측 장치가 더 망가지면** 빨간불이 난다 — 방향은 맞다 |
| `MaxNonMatchBlocked` | 1 | 🟡 살아 있다(6건 중 1) |

🔴 **더 근본적인 덮개 — `MatchLockIndexes` 가 손으로 적은 이름 목록이다.**
```
MatchLockIndexes = { idx_coll_tenant_doc, idx_pay_tenant_type_ref, idx_rt_tenant_receipt,
                     idx_tenant_partner, idx_pay_partner, idx_pay_tenant }      (:219-220)
```
「막힌 상대가 매칭 잠금인가」를 이 6개 이름으로만 판정한다. 그런데 —
- 내가 실측한 **실물 규모의 매칭 잠금은 `PRIMARY`(클러스터) 위에 있다**(§2-4 원자료). **`PRIMARY` 는 목록에 없다.**
- PM 자신의 §21-2 표에서 L1 이 고른 것은 **`uq_collections_source`** 다. **그것도 목록에 없다.**

⇒ **「상대가 매칭 잠금이 아니다」라는 단언은 매칭 잠금이 실제로 취하는 두 모양을 구조적으로 못 본다.**
§21-1 의 「위 단언이 통과했으니 매칭 잠금이 아니다」는 **순환 논증**이다.
그리고 이것은 §19-1 이 「손으로 적은 이름 목록은 삭제한다」며 `TenantPrefixExempt` 를 없앤 바로 그 함정인데, **여기서는 살아남았다.**

## §5. 못 잰 것 · 한계

1. **운영 DB `hitpan_erp_t004`(3306) 를 못 읽었다.** `hitpan` 계정에 `SELECT` 권한이 없고(`ERROR 1142`), root 자격증명 탐색은 하지 않았다. V5 는 **코드·DDL·출하물·실물 사본**으로 답했다 — 운영 실물 확인은 ⬜.
2. **`purchase_returns` 가 실물 사본에서 0행** — L5·D1-c 의 실물 계획·잠금은 **못 쟀다**.
3. **V6 는 부분만 잰다** — 게이트 15사례·빌드 warning 0·무력화 2건(①④)은 쟀다. **무력화 ②③⑤ 와 안전 33306 회귀 40 · 마이그·DDL 274 는 안 쟀다.** 전체 회귀는 마지막에 돌렸다(§2-7-4).
4. **`uq_*_source` 를 매칭 잠금이 고르는 분포는 재현 못 했다.** 내가 만든 `dp_gap` 에서는 L3 이 `idx_pay_partner` 를 골랐다. 그래서 PM 이 §21-1 에서 찍었다는 `uq_payments_source` 간극이 **어느 문장이 만든 것인지**는 여전히 미확정이다 — 다만 **`idx_pay_partner` 축이 독립적으로 성립한다는 것은 증명했다**(§2-6-1).
5. `dp_full` 은 `hitpan_v4_a` **한 고객사** 분포다. 다른 고객사 분포에서 방아쇠가 어떻게 달라지는지는 못 쟀다.
6. **잠금 실측은 내가 만든 사본(`dp_full`·`dp_gap`)에서 했다.** 실제 제품 코드 경로(`CollectionService` RR 흐름)를 통해 돌린 것이 아니라 **제품 SQL 상수를 그대로 옮겨** 두 연결로 돌린 것이다. 문장 단위 사실이고, 흐름 전체의 잠금 누적은 별도다.
7. **시험 서버가 검증 중 두 번 내려갔다**(33306·33406). 재기동 후 `dp_full`·`dp_small`·`dp_gap`·`rc_l4_probe` 전부 보존됐고(`rc_l4_probe.collections` 는 **여전히 0행** — §2-1 의 사실이 유지됨), 33406 은 `log_bin=1`·`binlog_format=STATEMENT` 로 복귀한 것을 확인했다.
