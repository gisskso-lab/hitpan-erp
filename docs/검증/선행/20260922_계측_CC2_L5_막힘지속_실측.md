## §2 M1·M2 — 잠금 보유 창 (L5 시작 → COMMIT)

실제 경로 그대로 재현: L5 → `INSERT payments` → `partner_balance` upsert → `journal_entries` → `journal_lines` → `COMMIT`
(근거 `CollectionService.cs:320-369` · 분개는 `AutoJournalHelper.cs:824,849`)

| DB | 회차 | L5 문장 (ms) | **보유 창 (ms)** | 잠금 행 | M③ 값 |
|---|---|---|---|---|---|
| `cc2_l5` (DB-124 **있음**) | **10회** | 3.1 ~ 12.8 | **6.7 ~ 25.4** | **1,703** | 1,309,010.00 **10/10 동일** |
| `cc2_noidx` (DB-124 **없음**) | **5회** | 4.4 ~ 10.4 | **9.3 ~ 27.3** | **2,789** | 1,309,010.00 **5/5 동일** |

🟢 **값 15/15 동일** — 인덱스 유무가 **금액을 안 바꾼다**(계획만 바꾼다).
🔴 **보유 창은 두 자릿수 ms 다.** 9/21 이 쓴 **인위 25초는 실제의 약 1,000배**였다.

## §3 M3 — 이웃이 실제로 무엇을 겪는가 (오류번호로 판정)

프로브: 같은 표 `purchase_returns` 에 INSERT · **`innodb_lock_wait_timeout=50`(기본값)**

| # | 조건 | 결과 | 뜻 |
|---|---|---|---|
| **음성 대조군** | 보유자 **없음** · 2회 | 🟢 **2/2 통과** · 0.6 · 0.6 ms | 표·제약 때문에 막히는 게 아니다 |
| **N-1** | `cc2_l5` · 보유 **1s** | 🟢 통과 · **0.6 ms** | 🔴 **아예 안 막힌다** |
| **N-2** | `cc2_l5` · 보유 **10s** | 🟢 통과 · **0.7 ms** | 🔴 **아예 안 막힌다** |
| **N-3** | `cc2_noidx` · 보유 **1s** · 2회 | 🟡 **막힘 — 551 ms · 582 ms 대기 후 성공** | **막힘 ≠ 실패.** 기다렸다가 됐다 |
| **양성 대조군** | `cc2_noidx` · 보유 **55s** | 🔴 **ERROR 1205** | **실험이 1205 를 만들 수 있다**(차이가 나올 수 있는 실험) |

⇒ 🟢 **1205 은 보유가 `innodb_lock_wait_timeout`(기본 50초)을 넘어야만 난다.**
⇒ 실측 보유 창 **6.7~27.3 ms** ⇒ **약 1,800 ~ 7,500 배 여유.**

🔴 **이 「배수」는 함정 §6-2 의 오독과 다르다.** 그때는 **잠금 대기 상한(3,000ms)** 과 **문장 수행시간(114ms)** 이라는 **다른 두 양**을 나눴다.
여기서는 **둘 다 「대기자가 기다려야 하는 시간」** 이다 — 보유 시간이 대기 상한을 넘느냐가 곧 1205 의 정의다. **같은 양끼리의 비교다.**

## §4 🔴 M4 — 진짜 위험은 1213 교착이다 (지속시간과 무관)

시나리오: 두 세션이 **같은 거래처**로 L5(공유잠금) → 각자 `purchase_returns` INSERT (잠금 승급)

| DB | 8회전 · 16세션 | **1213** | 1205 | OK |
|---|---|---|---|---|
| `cc2_noidx` (DB-124 **없음**) | | 🔴 **8** | 0 | 8 |
| `cc2_l5` (DB-124 **있음**) | | 🟢 **0** | 0 | 16 |

⇒ 🔴 **DB-124 없으면 매 회전마다 한 세션이 교착한다 — 8회전 8회(100%).**
⇒ 🔴 **교착은 기다려서 풀리지 않는다. 즉시 실패다.** 「보유가 짧으니 안전하다」는 **1213 에는 안 통한다.**
⇒ 🟢 **DB-124 가 있으면 같은 시나리오에서 0/8.**

**CTO N-3 이 옳았다** — PM 도 [4] 도 `1213` 을 한 번도 안 꺼냈는데, **재현해 보니 그쪽이 100% 였다.**

## §5 🔴 고객이 실제로 보는 것 — 재시도 정책을 빼고 말하면 안 된다

`CollectionService.cs:31-38, 928-964` 실측:

- 재시도 대상 `MatchTxRetryableErrors = { 1213, 1205, 1665 }`
- `MatchTxMaxAttempts = 3` · 백오프 `{50, 150}` ms + **지터 0~50ms**
- **3회 다 실패해야** 고객이 문구를 본다: *「지금 다른 사용자가 지급을 저장하고 있습니다. 잠시 후 다시 저장해 주세요.」*

⇒ **1213 한 번 = 고객 실패 아님.** 50~200ms 뒤 재시도한다.
⇒ 🔴 **그러나 「3연속 실패 확률」은 이번에 안 쟀다**(⛔ §7-5).

## §6 🔴 설계 전제와 부딪히는 발견 — **DB-124 가 이미 L5 를 건드린다**

설계 6판·작지 §17 은 **「L5 는 처방 없이 닫음(잔존 위험 그대로)」** 이다.
그런데 `idx_rt_tenant_receipt`(**DB-124 가 만드는 인덱스** · `DB-124_lock_scope_indexes.sql:93`) 유무로 L5 가 갈린다:

| | 계획 (EXPLAIN 구동표) | 잠금 행 | 이웃 막힘 | 1213 |
|---|---|---|---|---|
| **DB-124 없음** | 🔴 `rt` **ALL** (998) | 2,789 | 🔴 막힘 | 🔴 **8/8** |
| **DB-124 있음** | 🟢 `pr` **ref `fk_pr_partner`** (220) → `rt` **ref `idx_rt_tenant_receipt`** | 1,703 | 🟢 **안 막힘** | 🟢 **0/8** |

⇒ ⚠️ **가설(미확정)**: **L5 의 잔존 위험은 DB-124 로 이미 상당 부분 내려갔을 수 있다.**
🔴 **확정이 아니다.** 근거는 **이 PC 한 대 · 데이터 한 벌 · 시나리오 하나**다. §7 의 못 잰 축을 먼저 닫아야 한다.
🔴 **이 발견을 「L5 해결됨」으로 옮겨 적지 마라.** 9/21 이 *「원인은 다른 연결」* 을 규명됨으로 적고 틀린 자리가 바로 여기다(함정 §6-6).

## §8 판정 — **C-C2 의 재료는 채웠다. 다만 결론이 바뀔 수 있다**

1. 🟢 **「L5 가 얼마나 오래 막는가」의 답: 6.7~27.3 ms.** 인위 25초가 아니다. **수용의 재료가 생겼다.**
2. 🟢 **1205 은 실측 조건에서 안 난다** — 문턱이 50초다.
3. 🔴 **그러나 수용 논거를 「짧으니 안전하다」로 쓰면 안 된다** — **1213 은 시간과 무관하고 대조군에서 100% 였다.**
4. 🔴 **DB-124 ↔ L5 관계가 설계 전제와 다르다** — **[5] 안건**으로 올린다. ⚠️ 가설이다.
