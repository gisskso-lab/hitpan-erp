## §1 L — 로그아웃·로그인이 다른 기기의 refresh 토큰을 죽인다

### 1-1 증상이 코드에 있나 — 🟢 있다. 그리고 문이 둘이다

| 문 | 줄 | 하는 일 |
|---|---|---|
| 로그아웃 | `AuthController.cs:375-377` | `UPDATE refresh_tokens SET is_revoked = 1 WHERE user_id = @UserId` — 계정 전체 |
| 🔴 **로그인** | `AuthService.cs:189-191` | `DELETE FROM refresh_tokens WHERE user_id = @UserId` — 계정 전체. **오더에 없던 문** |
| (참고) 세션 행 | `AuthController.cs:391-397` | 로그아웃의 `user_sessions` 삭제는 이미 `sid` 단위다(작2 절F②). 옛 토큰만 전삭(`:398-403`) |

결과는 이렇게 나타난다. 휴대폰에서 **로그인하든 로그아웃하든** PC 의 refresh 행이 사라지거나 폐기된다.
PC 는 access 토큰(8h, `AuthService.cs:21`)이 끝날 때까지 정상으로 보인다. 그 뒤 401 이 나면 화면이 자동으로 갱신을 부른다(`HitPanApiAuthHandler.cs:65-74`).
그 갱신이 `AuthService.cs:573-579` 에서 `"로그아웃된 토큰입니다"` 401 로 막히고, 화면은 로그인 창으로 간다.
**반대 방향(PC 로그인 → 휴대폰)도 같다.**
- 코드 스스로 이 사실을 적어 두었다(`AuthService.cs:720-722`): *"현 정책은 사실상 '단일 활성 세션'이다 … 멀티기기 동시 세션을 의도한 것은 아니다"*. 이 문장은 9/25 결재(「모바일 FREE · PC와 동시」)보다 앞선 것이고 **결재와 정면으로 맞선다.**

### 1-2 세션 생존 미들웨어는 user 단위인가 — 🟢 세션 단위다

`SessionValidityMiddleware.cs:81-82·143-145` 는 `sid` 하나로만 조회한다(`WHERE session_id = @Sid`). user 단위로 죽이는 곳은 여기에 없다.
⇒ 로그아웃을 **즉시** 듣게 하는 것은 이 미들웨어(세션 단위)이고, **8시간 뒤에** 다른 기기를 끊는 것은 refresh 폐기(user 단위)다. 두 가지는 다른 축이다.

### 1-3 기기·세션 단위로 가를 열쇠가 DB 에 있나 — 🔴 refresh_tokens 에는 없다

- `installer/hitpan_db_clean.sql:3237-3250`: `refresh_tokens` 에 있는 열은 token_id · user_id · token_hash · ip_address · user_agent · expires_at · is_revoked · created_at 뿐이다. **session_id·device 열은 없다.**
  `ip_address`·`user_agent` 는 INSERT 가 채우지 않는다(`AuthService.cs:193·814`).
- 마이그 중 `refresh_tokens` 를 만지는 것은 `DB-04`(생성)·`DB-38`(엔진) 둘이다. `DB-129:84` 에는 *"표 모양 변경 없음"* 이라고 적혀 있다. 마지막 번호는 `DB-129` 다.
- 🟢 **다만 열쇠는 토큰 안에 이미 있다.** refresh JWT 에 `sid` 가 실린다(`AuthService.cs:1089-1092`). `user_sessions.session_id` 가 그 짝이다.
  ⇒ 가르는 방법은 셋 중 하나다. 이 중에서 고르는 것은 [2] 몫이다.
  - ㉠ 추가형 마이그로 `refresh_tokens.session_id` 를 넣는다. 출하 DDL(#36)도 함께 고친다. → 규모 **M**
  - ㉡ 로그아웃 본문에 refresh 토큰을 실어 해시로 한 줄만 폐기한다. → DDL 0
  - ㉢ 로그아웃은 세션 행만 지우고, 그 기기의 refresh 는 갱신 가드(`AuthService.cs:461-470`, 행 없음 → 401)에 맡긴다. → DDL 0
    ⚠️ ㉢ 는 `enforce_session_validity = 0`(비상)이거나 `sid` 없는 옛 토큰이면 **로그아웃한 기기의 refresh 가 살아남는다.** 쓰려면 이 퇴행을 결재로 수용해야 한다.
- 🔴 **로그인 쪽 `DELETE ... WHERE user_id` 를 바꾸면** 만료 행을 치울 곳이 필요하다. 회전 경로에는 이미 있다(`AuthService.cs:809-811`). 로그인 경로에는 없다.

### 1-4 「전 폐기가 맞는」 다른 경로와 섞여 있나 — 🟢 안 섞였다 (대신 곁가지 하나)

- refresh 를 계정 전체로 폐기·삭제하는 곳은 로그아웃(`AuthController.cs:376`)과 로그인(`AuthService.cs:190`) **둘뿐**이다. `grep` 으로 모든 코드를 확인했다(테스트 제외).
- ⬛ 곁가지(별건 · 이번 범위 밖). 전 폐기가 **있어야 할 것 같은** 경로에 폐기가 아예 없다.
  - `UserService.ResetPasswordAsync`(`:310`) — refresh·세션을 폐기하지 않는다 ⇒ 관리자가 비밀번호를 초기화해도 원래 기기는 **최대 7일** 갱신을 계속한다 ⚠️
  - `UserService.DeactivateAsync`(`:280`) — 폐기하지 않는다. refresh 는 `AppDbContext.cs:182-187`(is_active)이 막지만, **access 8h** 는 미들웨어에 활성 여부 검사가 없어 그대로 산다 ⚠️
  - ⇒ 1-3 에서 무엇을 고르든 이 두 경로를 **새로 섞지 않는다.** 넣을지 말지는 결재 포인트 L-④다.

### 1-5 이것을 지키는 게이트 — 🔴 없다. 초록인데 증상은 남아 있다

- `G-B7`(`SessionRecordConcurrentPcGateTests.cs:931-957`)은 로그아웃 뒤 **`user_sessions` 행만** 본다. refresh 토큰은 보지 않는다.
  게다가 준비 단계에서 휴대폰 로그인(`:941`)을 하는 순간 **PC 의 refresh 행이 이미 지워진다.** 게이트는 그 상태에서도 초록이다.
- 🔴 **`G-B6_음`(`:797-828`)은 잘못된 이유로 통과한다.** PC2 로그인(`:813`)이 `AuthService.cs:190` 에서 PC1 의 refresh 행을 지운다.
  그래서 PC1 갱신은 가드(`GuardExpiredPcSessionRevivalAsync`)에 **닿기 전에** `:578` 의 「로그아웃된 토큰」 401 로 끝난다.
  시험이 확인하는 것은 「401 이 났는가」와 「session 이라는 낱말이 없는가」(`:820-826`)뿐이라 이 차이를 가르지 못한다.
  ⇒ 주석에 적힌 음성 대조군(*"다른 PC 조회를 지우면 FAIL"*, `:793-794`)은 **거짓이다.** 가드를 통째로 지워도 이 게이트는 초록이다(⚠️ 실행 미측정 · 정적 판독).
  ⇒ L 을 고쳐 로그인이 전삭을 멈추면, 이 게이트는 그때 처음으로 가드를 **실제로** 잰다. [2] 는 여기에 메시지 단언(`"다른 컴퓨터에서 사용 중"`)을 넣어야 한다.
- 고치면 깨질 게이트는 **없는 것으로 보인다**(⚠️). `G-B13b`(`:1279-1325`)도 두 번째 로그인이 첫 토큰을 지우지만, 세션 행만 확인한다. `G-B16`(`:850-`)은 로그인 한 번 → 해시 전후가 같은지만 본다.
- 게이트 이름: `G-B1`~`G-B16` 은 이 파일 하나에만 있다. 다만 `BomWarehouseResolutionGateTests.cs` 에도 `G-B` 꼴 이름이 있다 ⇒ 새 게이트에 `G-B17` 같은 번호를 붙이기 전에 `grep` 으로 겹치는지 확인할 것.

## §2 F-4 — 새 세션 행을 넣은 뒤 예외가 나면 행이 남는다

### 2-1 갱신 경로 — 🟢 모양은 실재한다 · ⚠️ 실제로 터질 입력은 거의 없다

- `AuthService.cs:692`: 세션 INSERT(`isNewSession`)
- `AuthService.cs:708-709`: `CreateLoginResponse`. 이 줄은 보상 `try`(`:744-773`, `:794-841`) **앞**이다.
- 🟢 이 갈래에 들어오는 조건은 좁다. `sid` 가 **없는** refresh 토큰일 때만 `isNewSession` 이 된다(`:608-610`). 그런 토큰은 배포 전 발급분(7일이면 사라진다)이거나, 세션 기록에 실패해 `sid` 를 싣지 못한 토큰뿐이다.
- ⚠️ `CreateLoginResponse`(`:1027-1112`)가 던질 만한 것을 확인했다.
  - `Claim` 생성자는 값이 null 이면 던지지만, 원천이 `users.user_name`·`tenant_id` 라 `NOT NULL` 이다(DDL `:4297·4300`). Entity 기본값도 `string.Empty` 다.
  - 서명 키가 짧으면 서명 단계에서 던질 수 있다. 그러나 운영에서는 32자 이상을 강제하고(`AuthExtensions.cs:27`), 갱신 경로는 **같은 키로 검증을 이미 통과한 뒤**다.
  - ⇒ 현실적으로 터질 입력을 찾지 못했다. **구조 결함이지 발생 빈도가 있는 결함은 아니다.**

### 2-2 로그인 경로 — 🔴 같은 모양이고 더 넓다

- `AuthService.cs:178` 세션 INSERT → `:183` `CreateLoginResponse` → `:189-201` refresh_tokens DELETE·INSERT. 이 경로 전체에 **트랜잭션도 보상도 없다**(주석 `:168-170` 이 스스로 인정한다).
- 🔴 `CreateLoginResponse` 보다 **refresh_tokens 쓰기 두 줄**(연결 끊김·잠금 대기 초과 같은 DB 예외)이 실제로 터질 가능성이 더 높다 ⚠️. 코드는 이것을 이미 알고 수용했다(`:641-644` *"로그인 경로도 같은 모양 … 잔여 행은 expires_at 으로 자연 소멸"*).

### 2-3 영향 — 축 B 가 켜져 있을 때만 보인다

- 축 B 꺼짐(출하 기본, `DB-128`) → 남은 행은 아무것도 막지 않는다. 8h 뒤 저절로 사라진다.
- 축 B 켜짐 → 남은 `pc` 행이 `EnforceSinglePcLoginAsync`(`:252-263`)에 걸린다. 그래서 **자기 재로그인이 「다른 PC 사용 중」 409** 가 된다. `canForce = true`(`AuthController.cs:338`)라 [그 PC 끊기]로 빠져나올 수는 있다.
  갱신 쪽에서는 같은 오래된 토큰으로 재시도하면 `:680-689` 에서 「다른 컴퓨터에서 사용 중」 401 이 난다. 고객은 **있지도 않은 다른 PC** 이야기를 듣는다.
- 게이트: 갱신의 회전 실패 세 갈래는 `G-B13`·`G-B13b`·`G-B13c`·`G-B13d` 가 지킨다. **`CreateLoginResponse` 예외와 로그인 경로 잔여 행을 지키는 게이트는 0개다.**

## §3 R-3 — 다운로드 토큰이 일반 API 열쇠로 쓰인다

### 3-1 JwtBearer 가 `token_type` 을 거르나 — 🟢 **안 거른다**

- 일반 인증 설정은 `Program.cs` 가 아니라 `src/HitPan.API/Extensions/AuthExtensions.cs:50-87` 에 있다. `TokenValidationParameters` 는 서명·issuer·audience·수명만 본다. **`OnTokenValidated` 는 없다.**
- `token_type` 을 읽는 곳은 `AccessTokenValidator.cs:57·82`(다운로드 전용 경로)와 `AuthService.cs:553`(갱신) **두 곳뿐**이다. 일반 파이프라인에는 없다.
- 다운로드 토큰(`DocumentController.cs:67-81`)은 같은 비밀키·issuer·audience 로 서명된다. 여기에는 `tenant_id`·`user_id` 가 들어 있고, `role`·`account_type`·`employee_id`·**`sid`** 는 없다.

### 3-2 파이프라인을 끝까지 통과하나 — 🟢 통과한다 (정적 · 실행 ⚠️)

| 단계 | 줄 | 다운로드 토큰을 Bearer 로 보냈을 때 |
|---|---|---|
| 인증 | `AuthExtensions.cs:56-67` | 통과(검사 항목이 전부 맞는다) |
| `TenantMiddleware` | `:99-122` | `tenant_id` 가 있어 통과. role 은 `""` 이 된다 |
| `SessionValidityMiddleware` | `:81-82` | **`sid` 가 없어 통과** — 로그아웃·밀어내기를 모른다 |
| `TermsConsentMiddleware` | `:65-` | 동의 기록만 보므로 통과 |
| `DeviceAuthMiddleware` | `:121-194` | 승인제가 켜져 있다(`appsettings.json` `DeviceApproval:Enabled=true`). 원래 브라우저는 기기 헤더가 있어 통과한다. 다른 기기라도 **메인PC 기기번호**를 헤더에 넣으면 통과한다(비밀이 아니다 — 같은 파일 `:169-178` 이 스스로 적었다) |
| `PermissionFilter` | `:33-47` | **user_id 로 권한을 조회** ⇒ 그 사람이 가진 메뉴 권한 전부 |
| `[Authorize(Roles=…)]` | 5곳 | role 이 없어 막힌다(관리자 전용 5곳만) |

- 참고: refresh 토큰(7일)을 Bearer 로 보내면 `tenant_id` 가 없어 `TenantMiddleware:115-120` 에서 403 이 난다. **설계로 막은 게 아니라 우연히 막혔다.**

### 3-3 🔴 스스로 새 토큰을 뽑아 이어진다 (⚠️ 실행 미측정 — [3-V]/[2] 착수 전 1순위 실측)

`POST /api/documents/{type}/{id}/download-token`(`DocumentController.cs:45-85`)은 `[Authorize]` 만 요구한다. 다운로드 경로 예외(`TenantMiddleware.cs:127-137`)는 `/excel`·`/pdf` 로 끝나는 경로만이라 이 경로는 일반 파이프라인을 탄다.
⇒ **다운로드 토큰으로 새 다운로드 토큰을 받을 수 있다**(3-2 표를 그대로 통과한다). 2시간마다 다시 받으면 **끝이 없다.**
그리고 그 사슬은 로그아웃(`sid` 없음)·밀어내기(`sid` 없음)·계정 비활성(파이프라인에 is_active 검사 없음)을 모두 모른다.
⇒ 한 번 새어 나간 다운로드 링크 하나가 **퇴사자에게도 무기한 열쇠**가 될 수 있다. 이것이 P0 후보로 올린 이유다.

### 3-4 URL 로 다니나 — 🟢 다닌다

- 화면은 `?token=` 을 붙인 URL 을 만들고(`HitPan.Web/Services/DocumentService.cs:59`), 그 URL 을 `hitpan.openFile` 로 새 창·같은 창 이동으로 연다(`wwwroot/index.html:133-`). ⇒ **브라우저 방문 기록에 남는다.** 사용자가 주소를 복사해 메신저로 보내는 것도 막을 방법이 없다.
- 🔴 더 넓은 문이 있다. `AuthExtensions.cs:70-84` 의 `OnMessageReceived` 는 **모든 경로**에서 `?access_token=`·`?token=` 을 Bearer 로 받는다. 원래 필요한 곳은 SignalR 허브(`/hubs/migration`·`/hubs/notify`, `Program.cs:666·669`)뿐이다. ⇒ 일반 access 토큰도 URL 로 보내면 통한다.
- ⚠️ 서버 로그·터널 로그에 쿼리가 남는지는 **확인하지 못했다.** 우리 미들웨어에는 쿼리를 적는 코드가 0개다(`grep QueryString` 0건). 그러나 ASP.NET 호스팅 기본 로그와 cloudflared 로그 수준은 이 PC 설치본을 열어야 알 수 있다(#39 · 열지 않았다).
- 곁가지: `ValidateDownloadToken` 은 `doc_id` 만 묶고 `doc_type` 은 묶지 않는다(`AccessTokenValidator.cs:88-92`). 같은 id 를 다른 양식으로 받을 수 있다 ⚠️(영향 작음).

### 3-5 게이트 — 🔴 없다

`ValidateDownloadToken`·`download-token`·`AddJwtAuthentication` 을 부르는 시험은 0건이다(`src/HitPan.Tests` grep). 고친다고 깨질 게이트가 없고, 지키는 게이트도 없다.

## §5 결재 포인트 — 선택지만 적는다 (PM·설계가 정하지 않는다)

**L**
- **L-①** 휴대폰에서 로그아웃할 때 PC 도 끊어야 하나? — (가) 이 기기만 (나) 모든 기기 (다) 화면에서 [이 기기만 / 모든 기기] 중 고르게 한다
- **L-②** PC 에서 로그아웃할 때 휴대폰은? — ①과 같은 선택지. 두 방향을 따로 정할 수 있다
- **L-③** 🔴 **로그인이 다른 기기 refresh 를 지우는 것**(`AuthService.cs:190`)도 이번에 고치나?
  - (가) 고친다 — 모바일 FREE 약속과 일치한다. 대신 **축 B 가 꺼진 고객사에서는 PC 2대가 무기한 함께 쓰게 된다.** 지금은 8h 뒤 한쪽이 튕기는 「우연한 단일 세션」이 있다. 그 방식이 사라진다
  - (나) 로그아웃만 고친다 — 휴대폰 로그인은 여전히 PC 를 튕긴다
  - (다) 기기 종류로 가른다 — 예: 로그인은 **같은 종류** 기기의 refresh 만 지운다
- **L-④** 비밀번호 초기화·계정 비활성 때 모든 기기를 폐기하는 것을 이번에 함께 넣나, 별건으로 두나? (1-4 곁가지)
- **L-⑤** 가르는 방법 ㉠ DDL 추가 / ㉡ 본문 토큰 / ㉢ 세션 행 의존 — [2] 가 장단점을 정리하고 결재받는다(㉢ 의 비상 스위치 퇴행을 수용할지 포함)

**F-4**
- **F-④** 갱신 경로만 막나, 로그인 경로(refresh_tokens 쓰기 예외 포함)까지 막나?
- **F-⑤** 축 B 켜기 결재 **전에** 끝내야 하나, 켠 뒤에 해도 되나?

**R-3**
- **R-①** 다운로드 토큰은 다운로드에만 쓰게 한다(일반 인증에서 거부). — 대안 선택지는 없어 보인다. 결재가 필요한 것은 아래 두 가지다
- **R-②** URL 에 토큰을 싣는 방식 자체를 바꾸나?
  - (가) 유지 — 2h·doc 묶음은 그대로
  - (나) 수명을 짧게(예: 수 분) + 한 번만 쓰게
  - (다) URL 을 없앤다 — 화면이 fetch 로 파일을 받아 저장시킨다. 모바일 PDF 미리보기(`index.html:138-`)와 부딪히는지 확인이 필요하다
- **R-③** 모든 경로에서 `?access_token=`·`?token=` 을 받는 것(`AuthExtensions.cs:74-82`)을 허브 경로로 좁히나? — 좁히면 **쿼리로 토큰을 보내는 다른 화면이 있는지** 전수 확인이 선행돼야 한다(이번에 하지 않았다)
- **R-④** 발급 엔드포인트가 다운로드 토큰으로 호출되는 것을 막는 일(3-3)은 R-① 로 함께 닫히는가 — [2] 가 확인할 것
