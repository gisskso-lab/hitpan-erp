## §5 Q4 — 「미완료 업데이트 있음」 판정 재료

| 재료 | 어디서 | 지금 ERP 가 읽나 |
|---|---|---|
| 설치버전 | `VersionInfo.Current`(API 어셈블리) | 🟢 읽음 |

- 🟢 「미완료」 = `설치버전 < 최신` 은 **지금 값으로 충분**(= UpdateAvailable). 거부·차단·롤백·전원종료(교체 전) 전부 여기에 걸린다. 「실패」 문구는 결과행이 `blocked/rolled_back/rollback_failed` 일 때만 확정, 행 없음은 §2 의 N분 문턱으로만 추정.

- 🔴 ERP 가 못 뜨는 실패(`rollback_failed` · §2 2행)에는 **ERP 안내가 원리적으로 불가** — 워치독·본사 긴급통지(`:963`)의 몫. 설계가 이 경계를 적어야 한다.

## §8 Q7 — N-UPD2·N-UPD7 묶음 필요 여부

| 별건 | 이 요구에 필수? | 근거 |
|---|---|---|
| N-UPD2 | 🔴 **필수** | 실패 뒤 안내의 [예] 가 넣은 approve 를 `Worker.cs:602-607` 가 무시 — 워치독 재기동 전엔 「언제든지 정상적으로 마칠 수」가 **코드상 불가** |
| N-UPD4 | 🔴 필수 | 안내가 다시 받은 [예] 가 최신이 돼야 한다 — 로그인 후 경로는 이미 무조건 INSERT(1차 §2). 로그인창 경로의 「approve 존재 → 멱등」은 재시도를 막는다 |
| 옛 approve 자동 재시도 | 🔴 함께 정할 것 | 사장님 답(§1 ⚠️해석)이 「실패 → 다시 묻는다」면, 재기동 시 옛 approve 로 **묻지 않고** 재시도하는 현 동작(§3 A)과 어긋난다. 「결과행 시각보다 뒤의 approve 만 유효」 같은 기준이 필요 — N-UPD2 와 같은 자리 |
| N-UPD7 | 🟡 조건부 | 사장님 요구 두 곳(팝업·사이드바)은 JWT 경로라 `tenants` 를 안 본다. 그러나 로그인창(`Login.razor:236-245`)도 이미 새 버전 안내를 띄우고 그 버튼이 고객 PC 에서 400(1차 N-UPD7). 로그인창을 안내 입구로 **남기면 필수**, 안내만 두고 버튼을 걷으면 불요 — 설계 결정 |
| 🔴 보안(안철수) | 필수 제약 | 로그인창 `update-consent-local` 은 `[AllowAnonymous]` + 터널 허용(`AuthController.cs:724-725`). 그 멱등(`:778-795`)이 「미인증 원격자의 반복 호출 → 반복 교체·재기동」을 막는 **유일한 방어**다. N-UPD2/4 로 「실패 뒤 재시도」를 열 때 이 익명 입구에서 재시도가 열리면 **원격 반복 재기동(가용성 공격)** 이 된다 ⇒ 재시도 권한은 JWT 경로에만, 또는 익명 경로에 횟수 제한 |
