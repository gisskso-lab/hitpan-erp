### 2-2 🔴 설계가 알아야 할 사실 (처리 방법은 §7 결재)

- **퇴근 시각 = 퇴근 함수가 실행된 순간**(`HrService.cs:77·85`). 자동 로그아웃이 지금 로그아웃 경로를 그대로 타면 **설정 시각(정확히는 실행 시각)이 퇴근으로 찍힌다.** 18:00 에 나가며 로그아웃을 잊은 사람이 22:00 쿨타임에 걸리면 퇴근 22:00 · 근무시간 +4h 로 남는다.
- **하루 첫 로그아웃만 퇴근이 된다.** 두 번째부터는 `check_out IS NULL` 행이 없어 예외 → 경고 로그뿐. 뒤집어 말하면 **쿨타임은 그날 아직 퇴근이 없는 사람에게만** 근태를 바꾼다.
- **휴대폰 로그아웃도 퇴근을 찍는다** — 로그아웃 경로에 PC/휴대폰 구분이 없다(`AuthController.cs:359-364`). 점심에 휴대폰에서 로그아웃하면 그 시각이 퇴근이고, 저녁 PC 로그아웃은 무시된다. (쿨타임 이전부터 있는 사실)
- **하루 첫 로그인만 출근이 된다**(`HrService.cs:63` 예외 + UNIQUE).
- **날짜 경계**: 퇴근은 `work_date = 오늘` 만 찾는다(`HrService.cs:79`). 설정 시각이 자정을 넘으면(예 02:00) **전날 행의 퇴근은 안 찍힌다** — 경고 로그만.
- 🔴 **출근은 `/login` 에서만 찍힌다. 토큰 갱신은 출근을 안 찍는다.** 토큰은 `HitPanProtectedLocalStorage`(브라우저를 닫아도 남는 저장소 ⚠️파일 이름 기준) · 갱신 토큰 7일(`AuthService.cs:22`) · 화면은 시작할 때 만료 토큰이면 자동 갱신(`HitPanAuthStateProvider.cs:22-24`). ⇒ ⚠️ **로그아웃 안 한 사람이 다음 날 브라우저를 열면 로그인 화면 없이 들어오고 출근이 안 찍힐 수 있다.** 다만 PC 세션 행이 만료돼 있으면 갱신 가드(`AuthService.cs:434-438` `GuardExpiredPcSessionRevivalAsync` · 생존 확인 켬)가 401 로 막을 수 있어 실제 갈래는 **미측정.** 오더의 *"로그인을 하도록 유도"* 는 쿨타임이 **서버 쪽에서 로그인을 끝내야** 성립한다.
- (참고) `attendance.status` 의 `early_leave`·`late` 는 DDL 주석에만 있고 코드가 세팅하는 곳 0(`normal` 만).

## §3 전제 2 — 설정 시각을 어디에 두나

- 🟢 `tenant_settings`(`installer/hitpan_db_clean.sql:4115-4146`)에 **근무·퇴근·자동 로그아웃 시각 칸 없음.** 코드 전체 검색(`work_end`·`WorkEnd`·`퇴근시간`·`auto_logout`·`idle_timeout`)도 0 — `HrAttendancePage.razor:95` 「근무시간」은 표 머리글, `LaborContractCreatePage.razor` 는 근로계약서 문구.
- 🟢 회사 설정 화면 = `src/HitPan.Web/Pages/Settings.razor`(`tenant_settings` 칸들을 편집). `Pages/Settings/` 폴더에는 비슷한 칸 없음.
- 🟢 세션 스위치 3칸(`enforce_tenant_session_limit`·`enforce_single_pc_login`·`enforce_session_validity`)은 **화면이 없다** — 서버(`SessionValidityMiddleware`·`AuthService`)만 읽는다.
- 🔴 **행 없는 고객사**: `tenant_settings` 행은 설정 저장을 한 번 한 곳에만 있다(F4 설계 §5 · `SettingsService.cs:122`). 새 칸도 똑같이 「저장 안 한 회사 = 무엇으로 읽나」를 정해야 한다(§7 Q4). 비율은 여전히 미실측.
- 🟢 마이그 최신 = `DB-129` · 진행순서 1 이 `DB-130`·`DB-131` 을 잡아 두었다 ⇒ 쿨타임은 `DB-132` 이후.
- 🔴 **시간 기준이 섞여 있다**: `user_sessions` 는 UTC(`UTC_TIMESTAMP(6)`), `attendance` 는 서버 로컬(`DateTime.Now`). 설정 시각은 회사 벽시계로 입력될 것이므로 비교 기준을 설계가 명시해야 한다.

|---|---|

## §5 전제 4 — 로그아웃 실행

- 🟢 지금 로그아웃(`AuthController.cs:366-397`): `user_sessions` 는 **JWT `sid` 한 줄만** 지운다(`sid` 없으면 계정 전체). 🔴 그런데 `refresh_tokens` 는 `WHERE user_id` — **계정 전체(휴대폰 포함) 폐기**(`:375-377`). 진행순서 1 ㉠(`DB-130` `refresh_tokens.session_id`)이 이것을 고친다 ⇒ 쿨타임을 「PC 만」으로 하려면 **진행순서 1 이 먼저** 있어야 휴대폰이 같이 안 끊긴다.
- 🟢 **화면만 로그아웃하면 서버 세션은 남는다.** 화면 `Services/AuthService.cs:218-227` 은 서버 호출이 실패해도 저장소만 지우고 진행한다 ⇒ 서버 `user_sessions` 행은 `expires_at`(갱신 때 +8h · `AuthService.cs:21·864`)까지 살아 있고, 그동안 다른 PC 는 K-4 (다)로 막힌다. **서버가 세션 행을 끝내야 풀린다** — 확인.
  - (곁가지 · 기존 결함) `AuthService.cs:222` `catch { /* ... */ }` — 빈 catch(#15).
- 🟢 서버가 행을 끝내면 `SessionValidityMiddleware` 가 **최대 10초 뒤** 401(`SessionValidityMiddleware.cs:50` 캐시 10초 · 생존 확인 켬일 때) → 화면 자동 갱신 → 막히면 로그인 화면.
- 🔴 서버가 직접(로그아웃 API 를 거치지 않고) 끝내면 **퇴근 기록 함수가 안 불린다** — 부르지 않으면 `check_out` 이 빈칸으로 남는다. 부르면 §2-2 대로 실행 시각이 찍힌다. (§7 Q1)
- 🟢 PC/휴대폰 구분 재료는 있다 — `user_sessions.device_kind enum('pc','mobile')`(`hitpan_db_clean.sql:4243-`).
- ⚠️ 서버가 세션을 끝내도 이미 열린 SignalR 연결은 남는다(미들웨어는 연결 시점만 검사 추정 · 미측정).

| Q3 | **휴대폰으로** 들어와 있는 직원도 설정 시각에 로그아웃되나 | (가) PC 로 들어온 사람만 · (나) 휴대폰도 함께 |
| Q4 | 설정 시각을 **누가 정하고, 안 정한 회사는** | (가) 기본 꺼짐 — 관리자가 켜고 시각을 넣는다 · (나) 기본 켜짐(예 22:00) — 설정을 한 번도 저장 안 한 회사에도 적용 |
| Q5 | 화면을 닫았거나 PC 가 잠들어 **팝업을 볼 수 없는 직원**은 | (가) 설정 시각 + 60초에 서버가 로그인을 끝낸다(다음 날·다른 PC 가 풀린다) · (나) 화면이 깨어날 때 팝업 + 60초(그때까지 다른 PC 는 막힌 채) |
| Q6 | **작성 중이던 전표**가 있는 직원은 | (가) 팝업에 「저장 안 한 내용은 사라집니다」 안내만 · (나) 로그아웃 직전 입력을 임시로 남긴다(전 화면 손대야 해 규모 커짐) |
| Q7 | 설정 시각이 **자정을 넘는** 회사(예 새벽 2시) | (가) 허용 안 함(자정 전까지만) · (나) 허용 — 전날 퇴근 기록 처리를 따로 설계 |

## §8 미확정 ⚠️ 다음 사람에게

- 로그아웃 안 한 사람이 다음 날 브라우저를 열 때 **로그인 화면을 거치는지(출근이 찍히는지)** — 갱신 가드 갈래 실행 미측정(§2-2).
- 숨은 탭·절전에서 화면 타이머 동작 — 실물 브라우저 실측 필요(§4).
- 서버가 세션을 끝낸 뒤 열린 SignalR 연결이 계속 알림을 받는지(§5).
- `tenant_settings` 행 없는 고객사 비율(진행순서 1 과 같은 미실측).
