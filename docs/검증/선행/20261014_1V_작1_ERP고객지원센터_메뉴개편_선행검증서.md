## §6 새로 적발한 것

### §6-1 🔴 A-1 — `LIMIT 200` 을 공지와 내 문의가 **함께** 쓴다

`CsRequestController.cs:271-275`

```sql
FROM cs_requests r
LEFT JOIN cs_outbox o ON o.cs_request_id = r.cs_request_id
WHERE r.tenant_id = @TenantId
ORDER BY r.created_at DESC
LIMIT 200
```

- `origin` 으로 나누지 않고 **한 테넌트의 최근 200행**을 내린다.
- 본사 선발신(공지·과금안내·프로모션)은 `cs_requests` 에 **행을 만든다**(§7 ①). 매달 쌓인다.
- ⇒ 공지가 200건을 채우면 **고객이 쓴 문의가 목록에서 밀려 사라진다.** 화면을 둘로 갈라도 쿼리가 하나면 증상은 그대로다.
- 🔴 설계 조건: **분리는 화면만이 아니라 쿼리까지** 가야 한다(쪽별 `LIMIT`).

### §6-2 ⚠️ A-3 — 목록 API 에 `origin` 필터 매개변수가 없다

`[HttpGet("requests")] public async Task<IActionResult> List(CancellationToken ct)` (`:227-228`) — 매개변수가 토큰 하나뿐이다.
⇒ 화면 분리 방법이 **둘**이고, 어느 쪽이냐가 작업 규모를 가른다. **PM·설계 결재 사항**이다.

| 안 | 내용 | 값 |
|---|---|---|
| (가) 서버에 `origin` 질의칸 추가 | `List(string? origin, …)` · 쪽별 `LIMIT` | A-1 도 같이 풀린다 · 서버 변경 발생 |
| (나) 클라이언트에서 걸러내기 | 200행 받아 `Origin == "hq"` 로 두 화면이 나눠 그린다 | 서버 0변경 · **A-1 을 못 푼다** |

🔴 (나)만으로 끝내면 공지 쌓임 사고가 그대로 남는다 — 「된다」로 적지 않는다.
A-2 는 §2-2 에 적었다(`LocalSwapUiText.cs:66` 글자 교체 = 설계 항목).

## §7 P-6 — 본사 선발신이 `cs_replies` 행도 만드나 (🟢확인)

`src/HitPan.API/BackgroundServices/CsOutboxSenderWorker.cs` 수신 경로 — 한 트랜잭션 안에서 두 줄을 넣는다.

- ① `INSERT IGNORE INTO cs_requests (… status, origin, created_at) VALUES (… '답변도착', 'hq', @CreatedAt)`
  - `created_by = 'headquarters'` · `erp_version = 'hq'` · **`origin = 'hq'`** 🟢
  - 영향 행수 0이면 기존 행의 `origin` 을 확인하고, `'hq'` 가 아니면 **롤백 + ack 안 보냄**(남의 문의에 안 붙인다)
- ② `INSERT IGNORE INTO cs_replies (reply_id, tenant_id, cs_request_id, body, replied_by_kind, replied_at) VALUES (…, '본사', @At)`
  - 🔴 **`read_at` 칸을 넣지 않는다** ⇒ `NULL` 로 남는다

`unread-count` 의 `hq` 쿼리는 `p.read_at IS NULL` + `r.origin = 'hq'` 를 센다(`:496-501`).
⇒ **②가 넣은 그 행이 그대로 `hqCount` 로 올라간다.** 결-C 의 「공지 안읽음」 숫자는 **서버 쪽 재료가 이미 맞다.**
막힌 자리는 서버가 아니라 **사이드바 모델 칸**(§4-2)뿐이다.
