## 내가 측정하지 못한 것 (⚪ 미측정 — 설계가 메우거나 [3] 첫 행동으로 넘긴다)

1. ⚪ **Dapper 가 남는 칸을 어떻게 다루는지 실측 못 했다.** DTO 에서 `EmployeeId` 를 빼고 SQL 이 `AS EmployeeId` 를 계속 내보내면, record 생성자 매핑이 **그 칸을 조용히 무시하는지 / 예외를 던지는지** 모른다. 재려면 코드를 고쳐야 해서(코드 0줄 금지) **안 쟀다.** 추측을 사실로 적지 않는다 — `SyncService.cs:36` · `TenantSnapshotService.cs:32` 두 자리는 **고치는 쪽이 안전**하되, 고친 뒤 `/api/sync/employees` 가 **실제로 4칸 JSON 을 내는지 응답 본문으로** 재야 한다.
2. ⚪ **`/api/sync/employees` 실응답을 못 봤다.** 이 엔드포인트는 Sync 토큰 전용(`SyncController.cs:69-73`)이고 `TenantMiddleware` 화이트리스트에 없다는 선행 기록(`docs/설계/erp/20261005_설계_직원계정관리_계정과금.md:236`)이 **⚠️미실측**으로 남아 있다. **지금 4칸으로 줄었는지는 DTO 를 읽어 판정했을 뿐, 전선으로 확인하지 않았다.** 개발PC 정상은 검증이 아니다.
3. ⚪ **`tests/sandbox-m4/payload/app/MigrationIdempotencyCheck.exe`** 가 `tenant_employees_snapshot` 문자열로 적중했다. **바이너리라 못 읽었다.** 이 도구가 칸 수를 세는지 불명 — 세고 있으면 게이트가 하나 더 있다.
4. ⚪ **`tests/e2e/integration-20260615.spec.ts` B2·B3 는 `test.skip` 이라 안 돈다.** 되살렸을 때 통과할지 **미측정**. 그 주석의 칸 목록(`role` 등)이 실제 DDL 과 다르다는 사실만 확인했다.
5. ⚪ **운영(고객 PC)의 `tenant_employees_snapshot` 에 실제 행이 있는지 못 봤다.** #39 에 따라 운영은 안 건드렸다. 행이 0 이라는 보장도 내가 잰 게 아니다 — 「쓰는 코드 0건」에서 추론한 것이다.
6. ⚪ **백오피스 DB(MySQL 8) 쪽 표**를 직접 못 봤다. ERP 레포 안의 `src/HitPan.Backoffice.API` 코드만 쟀다. 백오피스 운영 DB 에 직원 복사본 표가 **이미 만들어져 있는지**는 레포로는 알 수 없다(판이 둘이다). 있으면 #37 정신의 「받는 쪽 칸」이 하나 더 늘어난다.
7. ⚪ **전체 빌드·전체 시험을 안 돌렸다.** `SyncTokenDtoTests` 필터 6건만 쟀다. 다른 영역이 이 DTO 를 간접 참조하는지는 grep 으로만 확인했다.

## 설계가 반드시 다뤄야 할 쟁점

| # | 쟁점 | 왜 설계가 답해야 하나 |
|---|---|---|
| **쟁-1** 🔴 | **어느 설계가 정본인가** — API 응답 4칸(`THREE_SYSTEM_ARCHITECTURE.md:115` 외 3곳) vs 받는 표 `employee_id` NOT NULL(`DB-77` · `랜딩/03:30-42`). 둘은 **동시에 참일 수 없다** | 「코드를 설계에 맞춘다」가 실행 가능해지려면 먼저 정해져야 한다. 설계끼리의 모순은 설계팀장·사장님 결재 사안 |
| **쟁-2** 🔴 | **snapshot UPSERT 의 유일키를 무엇으로 할 것인가** — 사원번호가 없으면 `uq_tenant_employee` 를 채울 수 없다. 이름+이메일로 바꾸면 **동명이인·이메일 변경·퇴사 후 재입사**에서 행이 갈라지거나 덮인다 | 지금 과금에는 영향 0이지만(§전제2), **Pull 을 만드는 날 바로 막히는 벽**이다. 「나중에 생각한다」로 넘기면 다음 사람이 혼자 만난다 |
| **쟁-3** 🔴 | **설계가 ID 를 가르는 기준이 글로 없다** — devices 는 `기기ID` 를 **허용**하는데(`:116`) employees 는 `사원번호`를 **금지**한다(`:115`). 같은 성격의 식별자인데 왜 한쪽만 되는지 근거가 설계에 없다 | 기준 없이 한 칸만 빼면, 다음에 같은 질문이 또 온다. #32(점수·판정 받아쓰기 금지) — 숫자가 아니라 **축**을 적어야 한다 |
| **쟁-4** | **ST-03 은 사원번호를 못 잡는다**(`:32` 금지어 6개에 없음). **칸이 늘어도 ST-01 만 잡고, ST-03 은 계속 초록**이다 | 「4칸 초과 = FAIL」 게이트를 **동작으로** 세워야 한다. 글자(숫자 4)만 바꾸면 다음에 `login_id` 가 끼어도 ST-03 은 통과한다 — 선행 기록 `docs/검증/erp/20261005_작업리뷰서_작5_사원계정연결.md:72` 가 이미 요구한 게이트다 |
| **쟁-5** | **ST-05 를 어떻게 고칠 것인가** — 「전체 필드 생성」 시험이니 4칸으로 줄이면 되지만, **`EmployeeId` 가 다시 들어오면 이 시험은 조용히 통과한다**(named 인자를 하나 더 안 쓰면 됨) | 회귀를 잡는 건 ST-01 쪽이다. ST-05 는 **컴파일만 되게 고치는 자리**임을 작업지시서에 명시해야 한다 |
| **쟁-6** | **SQL 별칭 두 자리를 같이 고치는가** — `SyncService.cs:36` · `TenantSnapshotService.cs:32`. 고치면 `TenantSnapshotService` 는 **자기 표의 NOT NULL 키를 안 읽는 조회**가 된다(쟁-2 와 한 몸) | PM 전제에 **이 소비자가 없었다.** 손대는 범위가 2배다 |
| **쟁-7** | **출하 DDL·마이그는 무접촉**을 작업지시서에 글로 못박을 것 (#36·#37 정신) | 「DTO 에서 뺐으니 표에서도 빼자」가 다음 차수의 오판 경로다. #37 원문 :198 이 바로 그 오판을 금지한다 |
| **쟁-8** | **문서 쪽 동시 교정 범위** — `DB-77` 주석(:3)이 자기 DDL 과 안 맞고, `tests/e2e/...:102` 의 칸 목록은 네 번째 정의다 | 틀린 주석은 **다음 사람에게 사실이 된다**. 다만 이 둘은 코드 동작이 아니라 글자 — 범위에 넣을지 PM 판단 |
| **쟁-9** | (별건 기록만 · 이번 범위 아님) `tests/e2e/...:102` 는 `name(암호화)` 라 적었는데 `installer/hitpan_db_clean.sql:4127` 은 `name varchar(50)` **평문**이다 | #5 암호화 필수 컬럼과의 정합 — 이번 오더와 무관하나 발견했으니 적는다. 별도 트랙 |
