## §1 검증 방법 — 글자가 아니라 동작으로 갈랐다

사유표는 `[AllowAnonymous]` 가 **붙어 있다**는 글자 사실이다. 그것으로는 세 가지를 못 가른다:
① 실제로 미들웨어를 통과하는가 ② DB 에 **쓰는가** ③ 응답에 어떤 **항목**이 실리는가.
그래서 두 가지를 직접 돌렸다.

| 장치 | 무엇을 하나 |
|---|---|
| **실요청 프로브** | 작11 게이트와 같은 harness(실제 인증·인가 파이프라인)를 띄워 후보 전건에 **토큰 0** 으로 요청을 보내고 ⓐ 상태코드 ⓑ 응답 JSON 의 **항목 이름만** ⓒ `message` 를 찍는다. **값은 찍지 않는다.** |
| **리플렉션 전수** | 컨트롤러 어셈블리를 전수 열거해 「익명으로 열린 **액션**」을 센다. 사유표의 「16건」이 전수인지 검산한다. |
| **쓰기 판정** | 요청 전후로 대상 테이블 행 수를 센다. 「썼다」를 코드 읽기로 말하지 않는다. |
| **호출자 전수 grep** | 각 라우트를 **누가 부르는가**를 레포 전체에서 찾는다 — 막으면 무엇이 깨지는지는 이것으로만 답할 수 있다. |

🔴 **쓰기가 실제로 났다** — 측정 중 `hitpan_trgtest` 에 들어간 행(reseller_applications 2 · beta_signups 2 · serial_verify_attempts 1 · 프로브 tenants 1)은 **측정 후 전건 삭제**했고 0 을 확인했다.

## §2 먼저 정정 — 익명 표면은 16건이 아니라 **22건**이다 (실측)

리플렉션 전수: **컨트롤러 32개 · 익명 액션 22건 · 무표시(암묵 익명) 액션 0건.**

사유표는 **클래스 1건 = 1줄**로 세어 액션 수를 줄였다. ⓐ(정당) 가 덮은 액션 10 + ⓑ(후보) 가 덮은 액션 9 = **19** 이고,
나머지 **3건은 ⓐ·ⓑ 어디에도 없다** — 즉 사유표는 「전수」가 아니다.

| 분류 없는 3건 (파일:줄 · 라우트 · 붙은 자리) | 실측 (토큰 0) |
|---|---|
| `LandingPublicController.cs:91` · `POST api/landing/beta-signup` · **클래스** `[AllowAnonymous]`(`:26`) | **200 OK** · `beta_signups` **1행 INSERT** (2회 보내 2행 — 중복차단·시도제한 0). 저장 항목: 회사명·담당자명·전화·이메일·인원·메시지·**접속 IP** |
| `LandingPublicController.cs:131` · `POST api/landing/signup/otp/send` · 클래스 | **400** (`SignupToken` 필수 모델검증) · DB 접촉 0 · **스텁**(본문이 「가도」) |
| `LandingPublicController.cs:138` · `POST api/landing/signup/otp/verify` · 클래스 | **202 Accepted** · 항목 `verified`·`paymentUrl`·`message` · **스텁**(코드가 `verified=false` 고정) · DB 접촉 0 |

`beta-signup` 은 B8 과 **같은 모양**(익명 무제한 INSERT)인데 개인정보를 더 담는다. 다음 차수 범위 판정에 넣어야 한다.

### §3-1 B3 — 응답에 실리는 **항목 이름**만 (질문 2 · 🔴 값 0건)

토큰 0 + 유효 라이선스 키 1개로 받은 **200 응답의 항목 전수** (18개):

```
success · source
tenant.tenantCode · tenant.companyName · tenant.tel · tenant.email · tenant.planType
domain.primary · domain.api · domain.tunnelTokenIssued · domain.tunnelToken · domain.tunnelId
bootstrap.token · bootstrap.expiresInSec · bootstrap.backofficeUrl · bootstrap.tokenKey
```

- **비밀값 성격 항목 4개**: `domain.tunnelToken` · `domain.tunnelId` · `bootstrap.token` · `bootstrap.tokenKey`.
- **고객사 연락처 2개**: `tenant.tel` · `tenant.email`.
- 🔴 1차 보고의 「**전 고객 공용** `tokenKey` 원문」은 **코드로 확인된다** — `bootstrapTokenKey` 는 환경변수 **1개**(테넌트별 분기 0, `InstallerBootstrapController.cs:131-136`). **다만 이것은 사고가 아니라 결재된 베타 전제다** — 같은 파일 `:127-130` 주석이 「베타=전 고객 공용키(보안상무 결재) · 정식 출시 전 = 테넌트별 파생키 전환 필수」라고 적어 둔다. 다음 차수가 「새로 발견된 구멍」으로 다루면 틀린다.
- ⚠️ 내 측정에서 `tunnelToken`·`tunnelId` 는 **Cloudflare 미구성이라 비어 있었다**(항목은 응답 규약에 있다). 구성된 환경에서 값이 실리는지는 **못 쟀다**(§6).
- 🔴 **같은 액션이 Cloudflare 를 바꾼다** — `IssueAsync`(DNS) · `IssueTunnelAsync`(터널 발급) · `UpdateDnsTunnelTargetAsync`(DNS PATCH) · `UpdateTunnelIngressAsync`(ingress PUT) 를 호출한다(`:117-146`). 즉 **토큰 0 요청이 인프라를 변경하는 경로**다(#29 계열). 내 측정에서는 자격증명 미설정으로 **미발동** — 발동 여부는 못 쟀다.

### §3-2 B4 — 2중 HMAC 은 실재하나, **어느 쪽이 틀렸는지 응답이 알려준다** (실측)

유효 라이선스 키 + **틀린** 사업자번호로 보냈을 때 응답이 「사업자번호가 가입 시 입력한 정보와 일치하지 않습니다」였다.
라이선스 키가 틀릴 때의 응답은 **다른 문구**다(`LandingPublicController.cs:37·58` 두 분기).
⇒ **라이선스 키 하나만의 유효/무효를 응답 문구로 가를 수 있다.** 실패 잠금 카운터는 이 액션에 없다(코드 읽기).

응답 형(`LicenseClaimResponse`)의 항목 이름: `valid`·`downloadUrl`·`companyName`·`message`·`tenantCode`·`bootstrapToken`·`signedProof`·`signedProofKid`.
2중 일치 시 `bootstrapToken`·`signedProof` 가 채워지는지는 **못 쟀다**(§6).

## §4 🔴 전제 반증 — B1·B5-register 는 **지금 쓰기가 안 된다** (출하 DDL 기준)

1차 보고의 B1 은 「DB 쓰기를 한다」가 근거였다. **실측은 500 이고 행이 0 이다.** 원인은 **스키마 두 판 공존**이다.

| | `PromotionController`(B1) 가 쓰는 컬럼 | 출하 DDL `installer/backoffice/00_backoffice_core.sql` 의 `promotions` |
|---|---|---|
| 코드 | `promo_code` · `use_count` · `target_plan` · `status` · BIGINT PK | `promotion_code` · `used_count` · `target_plan_id` · `is_active` · VARCHAR(36) PK (`:373-394`) |

- 출하 DDL `:369-371` 주석이 **이 불일치를 자백**하고, 레거시 정의를 **`promotions_legacy`** 로 따로 만든다(`:505-527`).
  그런데 **컨트롤러는 여전히 테이블명 `promotions`** 를 쓴다 ⇒ 출하 DDL 로 세운 DB 에서는 **SELECT 가 먼저 터져** INSERT·UPDATE 에 닿지 못한다.
  직접 SQL 로도 확인: `SELECT promo_code FROM promotions` → `Unknown column`.
- 덧붙여 `promotion_usages.promotion_id` 는 `bigint unsigned` + **FK → `promotions_legacy`** 다(`:538-541`) ⇒ SELECT 가 고쳐져도 FK 가 막는다.
- **B5-register** 도 같은 종류다: 코드가 `pricing_plans.max_pc_devices`·`max_mobile_devices` 를 읽는데(`DeviceRegistrationController.cs:65-66`) 출하 DDL 의 `pricing_plans` 에는 **`max_devices` 하나뿐**이다(`:407`).

🔴 **그러므로 B1·B5-register 의 「익명 쓰기」는 스키마에 달린 조건부다.** 운영(NCP) DB 가 어느 판인지는 **#39 로 못 쟀다**(§6).
참고로 이 PC 의 `hitpan_backoffice`(로컬 개발 DB)는 **레거시 판**(`promo_code`·`use_count`)이고 `pricing_plans` 테이블 자체가 **없다** — 세 판이 서로 다르다.

실패 잠금·시도 제한 / 응답 항목 최소화 / 서버측 금액·주문 바인딩 / 중복 접수 차단.
🔴 **이 구분을 설계가 놓치면 「막았다」가 「설치가 안 된다」로 돌아온다.**

## §6 질문 5 — 작10 교정②(`BoAccessGuard`)와의 상호작용

`src/HitPan.Backoffice.API/Filters/BoAccessGuard.cs:69`

```
if (context.ActionDescriptor.EndpointMetadata.OfType<IAllowAnonymous>().Any()) return;
```

- ⇒ **익명 표시가 있는 액션은 가드를 통째로 건너뛴다.** 바로 다음 줄(`:73-74`)은 **미인증 요청**도 면제한다.
  **그러므로 이 후보 22건은 어느 쪽으로도 가드가 막지 않는다** — 코드 그대로의 사실이다.

  작11 게이트는 `api/admin/*` **관리 표면만** 본다(그 파일이 자백).
  ⇒ **익명 액션이 22건에서 23건으로 늘어도 지금 게이트는 아무것도 안 깨진다.** 다음 차수가 세울 게이트의 자리가 여기다.

## §9 판정 — ⚠️ **조건부 (착수 가능 · 전제 3건 정정 후)**

**전제가 붕괴하지는 않았다.** 후보 9건은 모두 실재하고, 토큰 0 으로 **전건 인가 통과**가 실측됐다.
다만 설계가 그대로 받으면 틀리는 전제가 **3건**이다.

| # | 정정해야 할 전제 | 실측 근거 |
|---|---|---|
| 1 | 「**B1 이 익명으로 DB 를 쓴다**」 | 출하 DDL 기준 **500 · 0행**. 스키마 두 판 공존 + **호출자 0건**(§4·§4-1). 운영 DB 판은 **못 쟀다** |
| 2 | 「**사유표 16건이 전수**」 | 실측 **22건** · 분류 없는 3건(그중 `beta-signup` 은 **익명 INSERT 실측**) (§2) |
| 3 | 「**B3 의 공용 `tokenKey` 는 미발견 구멍**」 | 코드 주석이 **결재된 베타 전제**로 적어 둔다(§3-1). 새 사실은 ⓐ 실패 잠금 없음 ⓑ **토큰 0 요청이 Cloudflare 를 변경하는 경로** |

**설계 착수 전 반드시 반영할 것**
1. 봉합 축은 **인가가 아니다** — §5 를 넣지 않은 설계는 **설치·터널 자가복구·부모계정 생성·랜딩 가입을 깬다.**
2. 운영 DB 스키마 판(§8 1행)을 **사장님·PM 이 확인한 뒤** B1·B5-register 의 실제 위험을 정한다.
3. 익명 버킷을 **고정하는 게이트가 지금 없다**(§6) — 다음 차수가 세울 자리.
4. **순위·등급은 PM·사장님 결재 사항**이다. 이 문서는 사실만 적었다.
