## 2. 실측 — 매출의 창고 결정 순서

### 매입 (정상)

```
1. 라인에 지정한 창고
2. items.default_warehouse_id     ← 사장님이 말씀하신 그것
3. 테넌트 기본창고(MAIN 우선)
4. 없으면 명확한 오류
```
🟢 `LoadItemDefaultWarehousesAsync` — N+1 방지 일괄조회 + **`warehouses` 와 조인해 실재·활성 창고만** 인정
(창고가 지워진 뒤 남은 낡은 id 로 유령 창고에 쌓이는 사고를 10차 P0-4 가 막았다)

### 매출 (2단계가 없다)

```
1. 라인에 지정한 창고
   ❌ (마스터 기본창고 — 없음)
3. 테넌트 기본창고(MAIN 우선)
```

**`SalesService.cs:331`**
```csharp
var warehouseId = string.IsNullOrWhiteSpace(line.WarehouseId) ? defaultWarehouseId : line.WarehouseId;
//                                                              ↑ 테넌트 폴백. 마스터를 건너뛴다.
```

`defaultWarehouseId` 는 `warehouses` 만 조회한다 (`SalesService.cs:182-192`) — `items` 를 안 본다.

### 매출에서 창고를 정하는 자리 — 4곳 전수

| 위치 | 메서드 | 상태 |
|---|---|---|
| `:191` | `CreateDeliveryAsync` (판매 생성) | 🔴 마스터 안 봄 |
| `:926` | `UpdateDeliveryAsync` (판매 수정) | 🔴 마스터 안 봄 |
| `:2510` | `ConfirmSalesReturnAsync` (반품 확정) | 🔴 마스터 안 봄 |
| `:2681` | `CancelSalesReturnAsync` (반품 취소) | 🔴 마스터 안 봄 |

🔴 **4곳 전부 같은 폴백 SQL 을 복사해 갖고 있다.** 한 곳만 고치면 나머지가 어긋난다.

## 3. 실측 증거 — 대조군을 세워서 쟀다

⚠️ **1차 실측은 내가 받아쓰기했다.** 반품 4건이 판매와 같은 창고라 *"자동세팅 확인"* 이라 적었는데,
반증해보니 **판매가 창고 1곳(MAIN)만 쓰고 있었다** — 폴백이어도 같은 값이다. **대조군 없는 PASS 였다.**

⇒ 폴백창고(MAIN)와 **다른** 창고(001)로 판매를 만들어 반품시켰다. 이번엔 우연으로 통과할 수 없다.

| 단계 | 결과 |
|---|---|
| 001창고로 판매 생성 (`명-20260903-001`) | 🟢 `103fca06…` 정확히 저장 |
| 창고 미지정 반품 생성 (`반-20260903-003`) | 🔴 `warehouseId: null` |
| 반품확정 → 재고 | 🔴 **기본창고로 +1** (001창고 아님) |

`null` 이 조회 API 탓인지 확인 → **실제로 비어 저장됨**(같은 API 로 판매를 읽으면 창고값 정상).

**품목 `1+1` 기본창고 재고 25 → 26.** 001창고에서 나간 물건이 기본창고로 들어왔다.

## 4. 사장님 설계와 대조 — 걸리는 것 2건 중 1건은 내가 틀렸다

### ⭕ 걸리는것2 「반품이 다른 창고로 돌아오면 원장이 어긋난다」 → **내가 틀렸다**

사장님 답: *"재고메뉴에 재고이송이라는 것이 있음."*

실측 확인 — `StockService.cs:356-397`:
```
같은 source_id 로 묶어서
  나간 창고: move_type='out', source_type='transfer'
  받는 창고: move_type='in' , source_type='transfer'
```
🟢 **이송이 원장에 정직하게 두 줄로 남는다.** 사슬도 끊기지 않는다.

⇒ 반품이 기본창고로 받아도, 001창고로 **옮길 수단이 이미 있다.**
내가 **반품 한 단계만 보고** 결함이라 했다. 실무는 「반품 → 이송」 두 단계로 돈다.

### ✅ 걸리는것1 「원장은 합계로 못 적는다」 → **유효**

`stock_ledger.warehouse_id` 는 `NOT NULL` 이다. 원장에는 **반드시 어느 창고인지 적힌다.**
화면에서 합계로 보여주는 것과 별개로, **원장에 적히는 값은 정해져야 한다.**

지금 그 자리에 들어가는 값이 **「아무도 안 정한 값」**(테넌트 폴백)이다.
사장님 설계대로면 **마스터 기본창고**가 들어가야 한다.

⇒ 둘이 우연히 같으면 안 보이고, 다르면 **재고관리-창고관리 화면에서 어긋난다.**
   사장님이 창고별로 보시겠다고 한 바로 그 화면이다.

## 5. 사장님 설계를 코드로 옮기면

| 자리 | 창고를 아는가 |
|---|---|
| 판매·매입·반품 | ❌ 묻지 않는다 — 마스터 세팅 창고로 자동 |
| 재고이송 | ⭕ 명시적으로 지정 |
| 판매·매입 화면의 재고 | ❌ 전체 합계로 본다 |
| 재고관리-창고관리 | ⭕ 창고별로 본다 |

🟢 **창고를 아는 화면은 재고관리 하나.** 나머지는 몰라도 된다 —
현장 직원이 반품 치면서 *"어느 창고요?"* 를 답하지 않아도 되는 구조다(히트판 정신).

## 6. 🔴 착수 전 확인해야 할 것

1. **복붙 금지** — 매입은 **입고**(창고로 들어옴), 매출은 **출고**(창고에서 나감).
   출고는 **그 창고에 재고가 있느냐**가 걸린다. 매입에 없는 문제다.
   ⚠️ 8/27 *"판매 코드를 근거로 매입을 판단하지 마라"* 의 **반대 방향** — 같은 함정이다.
2. **4곳 동시** — 한 곳만 고치면 판매와 반품이 다른 창고를 쓴다.
   8/25 *"생성은 넣고 수정은 안 넣던 비대칭"* 사고 자리.
3. **헌법 #20 — 막지 말고 채운다.** 창고를 필수로 만들면 흐름이 끊긴다.
   마스터에 창고가 없는 품목은 **종전대로 테넌트 폴백**으로 가야 한다.
4. **게이트 선행** — 봉합 전에 짜서 🔴 빨간불 확인. 봉합자가 짜지 않는다(SoD).
5. **과거분 소급은 별건** — 이미 확정된 반품 4건은 원장이 움직인 기록이다(#3 INSERT ONLY).
   ⇒ **사장님 결재 없이 손대지 않는다.**

## 7. 미확인 (UNKNOWN — OK 아님)

| 항목 | 상태 |
|---|---|
| **화면으로 반품해도 `null` 인가** | 🔴 **안 쟀다.** 내 실측은 **API 직접 호출**이다. 화면(`DeliveryPage.razor:246`)이 채워주면 증상이 다를 수 있다 |
| 매입 반품에도 같은 구멍이 있나 | 🔴 **안 봤다** |
| `default_warehouse_id` 가 실제로 채워진 품목이 있나 | 🔴 안 쟀다 — 전부 비어 있으면 증상이 안 드러난다 |

🔴 **①이 이 건의 등급을 가른다.**
화면으로도 `null` 이면 **고객이 실제로 겪는 P0**, 화면은 정상이면 **API 직접 호출 시에만 나는 문제**다.
⇒ **설계 착수 전에 반드시 화면으로 잰다.**
