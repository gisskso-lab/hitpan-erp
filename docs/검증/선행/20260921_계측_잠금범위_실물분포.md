## 1. 계측 규칙 (이 트랙에서 비싸게 배운 것)

1. **빈 표의 EXPLAIN 은 근거가 못 된다** — 측정용 DB 는 전 표 행수를 먼저 찍고 시작한다.
2. **잠금은 격리해서 하나씩 잡고 잰다** — 동시에 잡으면 한 원인이 다른 원인을 가린다.
3. **대조군이 가르는 변수가 실제로 관측된 잠금이 있는 인덱스 안에 있는지** 확인한다.
4. **잰 것과 추론한 것을 섞지 않는다** — 명령과 출력이 있는 것만 「실측」.
5. MariaDB 11.4 에 `performance_schema.data_locks` 없음 · 1205 는 대기 중에만 보임 → 다른 연결에서 `SHOW ENGINE INNODB STATUS`.
6. 🔴 **남이 만든 측정 DB 는 깨끗하다고 가정하지 않는다** — 행수뿐 아니라 **인덱스 목록과 주요 칸의 NULL 비율**까지 찍고 시작한다. (이번에 §4-4 에서 실제로 걸렸다)
7. 🔴 **프로브 문장이 스스로 잠그지 않게 한다** — RR 에서 쓰기문 안의 하위질의는 공유 넥스트키 잠금을 잡는다. 대상은 **PK 리터럴**로 지목한다. (§4-3④)

### 4-3. 🟡 1차의 D1-b 재검토 (오염 DB 위에서 한 것 — **결론은 §4-5-3 에서 갱신**)

선행검증 §2-4 는 **D1-b 를 대조군**으로 썼고, 거기서 「같은 `LOCK IN SHARE MODE` 라도 좁은 계획이면 아무도 안 막힌다」를 끌어냈다. 설계 §13 과 작지 §2 사실목록 7번이 그 위에 서 있다.
내 측정에서 D1-b 가 **585행**을 잠갔으므로, 그 대조군이 여전히 성립하는지 **끝까지 찍었다.**

#### ① 585 는 무엇인가 — 규모에 비례하는가

```sql
SELECT COUNT(*) FROM payments WHERE ref_order_id='000ce2ec-…35a6b5';   → 291
SELECT ref_order_id, COUNT(*) c FROM payments GROUP BY ref_order_id ORDER BY c DESC LIMIT 3;
   → NULL 863 · '000ce2ec-…' 291 · '026686ac-…' 202
```

| 대상 전표의 지급 건수 | `trx_rows_locked` |
|---|---|
| 1건 (`03b54871-…`) | **3** |
| 291건 (`000ce2ec-…`) | **585** |

→ 대략 `2n + 3`. **표 전체(2,228)가 아니라 「그 전표의 지급 건수」에 비례한다.**
즉 585 는 **계획이 넓어서가 아니라 그 전표에 지급이 291건 달려 있어서**다. 선행검증이 잰 「rows 1」짜리 대조군은 **1건짜리 전표**를 골랐던 것이다 — 두 수치는 모순이 아니다.

#### ② 그래도 **585행이 남을 막는가** — 직접 프로브로 잰다 (추론 안 한다)

보유자 A: D1-b(291건 전표) `LOCK IN SHARE MODE` + `SLEEP(45)` (`hold_d1b.sql`)
프로브 B: `innodb_lock_wait_timeout=3` · 각 건 `START TRANSACTION … ROLLBACK` (`probe2.sql`)

| 프로브 | 보유자 **없을 때** | 보유자 **있을 때** |
|---|---|---|
| B1 무관 전표의 `payments` UPDATE (PK 리터럴) | 🟢 OK | 🟢 **OK** |
| B2 무관 거래처 `payments` INSERT | 🟢 OK | 🟢 **OK** |
| B3 무관 `collections` UPDATE (PK 리터럴) | 🟢 OK | 🟢 **OK** |
| B4 `collections` INSERT | 🟢 OK | 🟢 **OK** |
| B5 **같은 전표** `payments` INSERT (이웃) | 🟢 OK | 🔴 **1205** |

#### ③ 결론 — **대조군은 살아 있다. 재검토 결과 「아니다」**

- D1-b 가 585행을 잠가도 **무관한 거래처·무관한 전표는 한 건도 안 막힌다.**
- 막히는 것은 **같은 전표에 동시에 지급을 넣는 경우(B5)** 뿐이고, 이것은 **막으라고 만든 직렬화**다(같은 전표 초과지급 방지).
- ⇒ 선행검증 §2-4 의 「좁은 계획이면 아무도 안 막힌다」와 작지 §2 사실목록 7번은 **유지**. 설계 §13 을 고칠 사유 **없음**.
- 다만 **문구는 정밀해질 필요가 있다**: 「아무도 안 막힌다」가 아니라 **「그 전표 밖의 누구도 안 막힌다」**가 실측이 말하는 것이다. 같은 전표 안에서는 정확히 의도대로 막는다.

#### ④ 🔴 이 과정에서 **내가 만든 함정** (다음 사람이 또 밟는다)

프로브 1판에서 B1 을 이렇게 썼다가 **1205 가 났고, 하마터면 「D1-b 가 무관 전표를 막는다」로 보고할 뻔했다**:

```sql
UPDATE payments SET updated_at=NOW(6)
 WHERE payment_id=(SELECT payment_id FROM (SELECT payment_id FROM payments WHERE ref_order_id='026686ac-…') z);
```

원인은 보유자가 아니라 **프로브 자신**이다 — RR 에서 **쓰기문 안의 SELECT 는 공유 넥스트키 잠금을 잡는다.** 그 하위질의가 `payments` 를 훑으며 보유자가 쥔 행에 부딪혔다.
**PK 리터럴로 바꾸자 통과했다.** ⇒ **프로브는 대상 행을 PK 리터럴로 지목해야 한다. 하위질의로 찾으면 프로브가 스스로를 막는다.**
