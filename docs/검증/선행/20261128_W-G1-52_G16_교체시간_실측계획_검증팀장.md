## 2. 흐름 (표본마다 빈 datadir 에서 새로)

1. **root = 준비만**: 출하 DDL 적재 · 출하 GRANT 꼴 제한 계정 `hitpan_rs_t`@`localhost` + `GRANT ALL ON g16.*`(설계 §15-9 는 서비스 컨테이너라 `@'%'` 를 적었으나, 이 장치는 `docker exec` 소켓 접속이라 **출하와 같은 `@'localhost'`** 를 그대로 씀) · 가짜 업무 자료 붓기.
2. **G0**: 제한 계정 `CREATE DATABASE` → **1044 여야 초록**. 아니면 측정 무효로 멈춤. `SHOW GRANTS` 를 산출물에 남김.
3. **제한 계정**이 `rs_new__<표>` 만들기(`CREATE TABLE … LIKE` = 외래키 · 트리거 없는 표 · 외래키 0 을 따로 셈) → `INSERT … SELECT` 로 붓기(실제 덤프 붓기 시간은 아님 · 참고).
4. **대조군**: rs_new__ 쪽 잎 큰 표에서 1% 행을 뺌 → 교체가 실제로 일어났는지 행 수로 보임(라이브 == rs_new__ 이면 「됐다/안 됐다」 를 못 가름).
5. **설정마다 재기동 → 교체 트랜잭션**(제한 계정 · 한 세션): 첫 줄 엄격 `sql_mode` · `FOREIGN_KEY_CHECKS=1` · 자식 먼저 `DELETE` · 부모 먼저 `INSERT … SELECT`(칸 목록 명시 · 생성 칸 뺌) · `COMMIT` · 트랜잭션 안 DDL 0 · TRUNCATE 0.
6. **R11**(가장 큰 표본 · 설정 `bp1g_nobin`): 대조군 다시 갈라 둠 → 교체 시작 뒤 (앞서 잰 시간 × 0.6) 에 `docker kill` → `docker start` → 되돌림 끝 시각 · 행 수 · 체크섬(EXTENDED)을 「교체 전」 과 「새 값」 둘 다와 대조. kill 전에 끝나면 비율 0.3 으로 한 번 더.

## 4. 표본 고른 근거

- 표본(교체 대상 업무 자료 · 명목): **50MB · 250MB · 1GB · 2GB** (`G16_SAMPLES`).
- 근거 ① 고객 DB 크기 분포는 **없다**(설계 §15-9 「고객 DB 크기 = 확인 필요」). ② 옛 히트판이 Access 위에서 살아왔다 — Access 파일 하나 상한 2GB 이므로 옮겨 온 업무 자료 상한의 자릿수 근거로 2GB 를 위 끝에 둠(InnoDB 는 색인 · utf8mb4 로 같은 자료가 더 커질 수 있음 = 한계 §5). ③ 50MB = 막 쓰기 시작한 회사 · 250MB = 몇 해 쓴 소규모 · 1GB = 여러 해 쓴 중규모(가설 · 자릿수 표본).
- 표 분포: 큰 표 28개에 비중(`g16_gen.py` `WEIGHTS`) — 재고 원장 20 · 분개 줄 14 · 전표 5 · 납품 줄 9 · 수주 줄 6 · 입고 줄 6 · 발주 줄 4 · 계산서 줄 4 · 견적 줄 3 · 상태이력 3 · 수금 · 지급 · 통장 · 현금출납 각 2 … (머리 1 : 줄 3 ~ 5 · 원장 = 입출고 줄마다 1행 · 분개 = 전표마다 2행 이상). 나머지 교체 대상 표 = 표마다 30행. **이 비중은 업무 흐름 구조로 세운 가설**이다.
- 크기 맞추기: 먼저 보정 DB 에서 큰 표마다 2만 행을 붓고 `ANALYZE` 뒤 (자료 + 색인) ÷ 행 = 행당 바이트 → 표본마다 행 수를 셈 → 붓고 나서 **실제 크기를 다시 재어 표에 적음**(명목과 다를 수 있음 · 고유 칸이 짧은 표는 중복으로 행이 빠질 수 있음).
- 교체 대상 = 「지금 값」 근사 목록(설계 §5 ① ~ ④ + §15-4 추가 21) 밖 전부. ③-예외 3 · `idempotency_keys` 는 설계 추천대로 교체 대상. 분류 상수는 아직 코드에 없음([3] 몫) → 측정은 근사 목록으로 함. 지금 값 자식 → 교체 대상 부모 외래키가 나오면 그 자식을 교체 대상으로 옮기고 `plan.json` 메모에 남김(설계 판정 아님).
- 값: 한 PC = 한 회사라 `tenant_id` 는 모든 행 같은 값 · 글자 칸 일부 NULL(1/3) · 한글 섞음 · 외래키 칸은 부모 행을 가리키게 만듦(`INSERT IGNORE` + 외래키 검사 켠 채 붓기라 고아 0).

## 7. 측정 중 본 것 (발견만 · 고치지 않음 · 판정 아님)

- F1 교체 INSERT 때 출하 트리거 `trg_psp_ratio_insert`(DDL :2799)가 `vs_ratio` 를 다시 셈 → 백업 속 `vs_ratio` 와 다를 수 있음. 설계 G15 「`partner_special_prices` 붓기 전후 값」 이 이것을 재는 자리 — G15 에서 꼭 볼 것.
- F2 설계는 엄격 `sql_mode` 의 정확한 값을 적지 않음 — 이 장치는 `STRICT_ALL_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`. [3] 이 다른 값을 쓰면 다시 잴 것(NO_ZERO_DATE 등은 옛 자료를 거절할 수 있음).
- F3 교체 트랜잭션은 교체 대상 **모든 표의 행 잠금을 COMMIT 까지 쥔다** — 그 동안 같은 표 쓰기는 대기(잠금 대기 50초 기본 뒤 오류). 점검 상태(G17 · 503)가 이것을 앞에서 막는다는 전제를 [4] 에서 동작으로 확인.
- F4 R11 뒤 서버는 **되돌림이 끝나기 전에 접속을 받는다**(InnoDB 배경 되돌림) — 앱 기동 · 워치독이 그 사이 교체 대상 표를 쓰면 잠금 대기. 표의 「준비 초」 와 「잠금 탐침 초」 의 차이가 그 빈 창. 설계 §7 · R17 「⑤ 뒤 죽음」 과 함께 볼 것.
