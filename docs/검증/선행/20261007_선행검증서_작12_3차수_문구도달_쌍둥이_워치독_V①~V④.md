### §1-2 🔴 P1-①-1 (새로 발견) — **423 을 읽은 고객이 바로 다음 장에서 「로그인 불가 설치」를 권유받는다**

2차수 봉합은 `.iss:697-703` 에서 서버 문구를 띄운다. 그러나 `CallBootstrapApi` 가 `False` 를 반환하면 **호출부가 둘째 대화상자를 연달아 띄운다** — `installer/HitPan-Universal.iss:955-965`:

```
'시리얼 인증에 실패했습니다.' + ...
'로컬 단독 모드로 설치를 계속 진행하시겠습니까?' + ...
'  ✓ ERP 본체·데이터베이스·로그인 화면까지 정상 작동' + ...
'  ✗ 외부 도메인 연결은 안 됨 (시리얼 추후 입력 가능)'
```

세 가지가 동시에 틀린다.

1. **423 을 부정한다.** 서버는 「잠겼으니 1시간 뒤」라고 했는데 둘째 장은 「시리얼 **인증 실패**」라고 단정한다. 고객의 다음 행동이 **「기다린다」에서 「시리얼을 의심한다」로 뒤집힌다.** 2차수 봉합의 유일한 목적(423 의 가치 = 「1시간 뒤 열림」)이 **다음 장에서 지워진다.**
2. **🔴 「로그인 화면까지 정상 작동」은 거짓이다.** 이 분기에서 `[예]` 를 누르면 `:966-973` 이 `Result := True; Exit` 로 **즉시 빠져나가 `CallLicenseClaimApi`(`:982`)를 아예 호출하지 않는다** ⇒ `G_SignedProof = ''` ⇒ `ShouldSkipPage`(`:1076-1080`)가 부모계정 입력 페이지를 **건너뛴다** ⇒ `RunSeedParent` 미호출 ⇒ **부모계정 0건 = 로그인 불가.**
   **이 사실은 레포가 이미 글로 적어 뒀다** — `:1073-1074`:
   > 「증표 미취득(LOCAL·사업자번호 불일치 폴백)이면 … **폴백 기능 미구현 — 로그인 불가 상태로 설치됨**, 20260707작2 정정. **시리얼 미입력 LOCAL 모드도 동일.**」
3. **🔴 비대칭 — 같은 거짓을 셋째 대화상자에서는 이미 고쳤다.** `:996-1004` 가 바로 이 사죄문을 달고 문구를 고치고 기본 버튼을 `MB_DEFBUTTON2` 로 바꿨다:
   > 「종전 "로그인 화면 최초등록(P0-4)" 안내는 **실존하지 않는 기능을 약속한 거짓 안내였음**」
   그런데 **같은 거짓이 `:957`(부트스트랩 실패)과 `:902`(시리얼 미입력) 두 장에 그대로 남아 있다.** 세 장 중 한 장만 고쳤다.

**등급 P1.** 근거: ① 2차수가 423 문구를 닿게 한 **직후**라 피해자가 **지금 새로 생긴다** ② 「처음 보는 사람이 혼자 쓸 수 있냐」 정면 위반 ③ 결과가 **재설치**다(#20·#25).
**고쳐도 안전한가 — 🟢 안전하다.** 둘째 장은 **전부 설치본이 지어낸 고정 한글**이다. 서버·프록시 본문이 0글자 섞이지 않으므로 바꿔도 **새로 드러나는 정보가 없다**. 🔴 단 `[예]` 경로의 `G_LicenseKey := ''`(`:968`)·`G_TenantCode := 'LOCAL'` 은 **동작**이다 — 문구만 고치는지, 423 일 때 `[예]` 를 아예 안 주는지는 **설계 몫**이고 동작 변경이면 게이트가 붙어야 한다.

## §2 V-② — 401 문구 · 갈래별 대가를 숫자로 (🔴 PM 전제 「정면 충돌」을 깬다)

### §2-1 먼저 — **지금 401 이 나오는 경우 전수** (갈래 A 모집단의 코드적 정의)

`:123` `tenant is null` 이 되는 경우는 `:96-121` 쿼리 조건 **둘** 중 하나라도 빗나갈 때다.

| 경우 | 조건 | 고객이 할 일 |
|---|---|---|
| **a. 키 불일치** | `license_key_hash ≠ HMAC(입력키)` — 오타 · 다른 회사 키 · **재발급 후 옛 키**(`.iss:983` 「본사에서 새로 발급받은 시리얼 필요」가 재발급 실존을 증명) | 키를 다시 본다 |
| **b. 키는 맞고 `status≠'active'`** | `status ∈ {'pending','suspended'}` (`LandingSignupController.cs:386` · `TenantsAdminController.cs:169·196`) | **본사에 계약 문의** — 키를 다시 봐도 영원히 안 된다 |
| c. 그 밖 | 🟢 **없다** — 조회가 두 조건뿐이고, DB·CF·설정 실패는 모두 바깥 `catch` → **500** 이다(`:168-169` 주석이 명시 · 내가 코드로 확인) | — |

🔴 **b 에서 `'pending'` 은 사실상 0 이다**: `license_key_hash` 는 `status='active'` 로 바뀌는 **같은 UPDATE** 에서 들어간다(`LandingSignupController.cs:385-386` · `SignupsAdminController.cs:190-203`). 발급 전 `pending` 행은 해시가 NULL 이라 **입력 키와 절대 안 맞는다** ⇒ 경우 a 로 간다.
⇒ **경우 b 의 실체 = `'suspended'` 뿐**(한 번 active 였다가 본사가 정지한 고객).

### §2-2 🔴 갈래 B 의 「키 존재 노출」이 실제로 얼마나 나쁜가 — **거의 0이다. 근거 3개.**

**(1) 지금 붙은 시도 제한은 공격자를 못 막는다.** 잠금 키 단위는 `client_fingerprint` **하나뿐**이고(`:142-149` · UNIQUE `uk_fingerprint`), 그 값은 **요청 본문의 자유 문자열** `req.MachineFingerprint`(`:74`·`:89`)다. 공격자가 매 요청 지문을 바꾸면 **매번 새 행**이 되어 영원히 안 잠긴다. 보조 축도 없다:

| 축 | 상태 | 근거 |
|---|---|---|
| IP 단위 가산 | ❌ 없다 | `:87-88` 주석이 「`submitted_hash`·`client_ip` 에는 인덱스가 없다 … 2차수로」라고 **직접 적었고 2차수는 T-6 문구였다** ⇒ 안 됐다 |
| 키 단위 가산 | ❌ 없다 | 같은 자리 |
| 프레임워크 레이트리미터 | ❌ **0건** | `src/HitPan.Backoffice.API/Program.cs` 에 `AddRateLimiter`·`UseRateLimiter` **grep 0건** (미들웨어는 `UseHsts`·`UseHttpsRedirection`·`UseCors`·`UseAuthentication`·`UseAuthorization` 5개뿐 · `:141-147`) |

⇒ **「갈래 B 가 열거를 쉽게 만든다」는 전제가 성립하지 않는다.** 열거는 **이미 무제한**이다.

**(2) 더 강한 오라클이 원래 열려 있다.** 이 엔드포인트는 `[AllowAnonymous]`(`:28`)다. **HTTP 200 vs 401** 하나로 **「이 키는 유효하고 활성이다」** 가 드러난다 — 공격자가 갖고 싶은 **가장 값진 비트**다(200 이면 터널 토큰까지 받는다 · `:331-349`). 갈래 B 가 더하는 비트는 **「존재하나 설치 불가」** — **쓸 수 없는 키**를 가리키는, 전략적으로 **더 약한** 비트다.

**(3) 키는 추측할 수 없다 — 열거가 원리적으로 불가.** `SignupsAdminController.cs:632-644`:
- 알파벳 `"ABCDEFGHJKMNPQRSTVWXYZ23456789"` = **30자** (I·L·O·U 제외 Crockford 변형), 16자리.
- `RandomNumberGenerator.Fill` + `buf[i] % 30` ⇒ 30^16 ≈ **4.3×10^23 ≈ 2^78.5**.
- ⚠️ 모듈로 편향 있다(256 % 30 = 16 ⇒ 앞 16글자 10/256, 뒤 14글자 8/256). 손실은 자리당 **0.02 비트 미만** ⇒ 유효 엔트로피 **≈78비트**. 열거 판정은 바뀌지 않는다.

⇒ **갈래 B 의 노출은 「이미 진짜 시리얼을 손에 쥔 사람」에게만 닿는다.** 그 사람은 고객·전직원·메일 유출자다. 그에게 「이 시리얼은 존재하지만 계약 상태가 …」는 **그가 알 자격이 있는 정보**다.

### §5-1 🔴 묶음 반려 — **한 차수에 게시 경로가 3개다. 쪼개라.**

| V-① 서버 문구(①a·①c) · V-② 401·423 문구 | `InstallerBootstrapController.cs` (백오피스 API) | **NCP 배포 즉시 · 전 고객 · 고객 손 0번** | NCP 재배포 |

🟢 **권고 순서**(의존 없음 · 각자 독립 결재·독립 되돌림):
1. **V-② C-1 + C-3 + V-① ①a·①c** — 서버 문구 한 커밋. 코드 1파일 · 노출 0 · 운영 숫자 0 · **되돌림 1개** · 가장 많은 고객에 가장 빨리 닿는다.
2. **V-④ 로그 등급 + (측정 후) §4-4** — 워치독 1파일. 자동업데이트 경로.
3. **V-① P1-①-1 + V-③** — `.iss`. 🔴 **ISCC 게이트가 CI 에서 서는 것이 착수 조건**(2차수 §8-2 결재 그대로 · `LoadStringsFromFile` 인코딩을 ISCC 말고 잴 길이 없다).

### §5-2 🟡 「운영 읽기 숫자 없이도 진행된다」 — **절반만 맞다**

- 🟢 **V-①·③·④ 는 코드만으로 끝났다.** 운영 숫자 0건으로 이 문서의 모든 판정이 선다.
- 🔴 **V-② 는 아니다.** 갈래 A·B 의 **이득 크기**는 `'suspended'` 테넌트 수(= CS 모집단)다 ⇒ **S-2 읽기에 1건 추가 필요**: `SELECT status, COUNT(*) FROM tenants GROUP BY status`.
- 🟢 **단 그 숫자가 없어도 C-1·C-3 는 결재 가능하다** — 노출 0 · 구분 0 · 어느 쪽 숫자여도 이득이 양수다. **숫자를 기다리는 것은 B·C-2 뿐이다.**
  ⇒ 🔴 **「숫자 없이 설계 금지」를 V-② 전체에 걸면 과보수다**(PM 이 오늘 세 번 틀린 그 방향 · [[feedback_split_condition_must_stay_split]]).

### §5-4 🔴 새 과녁 제안 1건 — V-① P1-①-1 은 **지금 과녁 표에 없다**

세 대화상자 중 하나만 고쳐진 「로그인 불가 설치 권유」(§1-2)는 T-1~T-7 **어디에도 없다**. 2차수 봉합이 **방금 피해자를 만든 자리**이므로 3차수 과녁에 **P1 로 신설**해야 한다. 🚫 문구는 내가 쓰지 않는다 — `:996-1004` 가 **이미 본보기를 갖고 있다**는 사실만 넘긴다.
