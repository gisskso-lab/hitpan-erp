## 2. 실측 — 직접 본 것

### 2-1. 🟡 `return_id` 를 새로 만들 필요가 없다 — 범용 축이 이미 있다

`SHOW COLUMNS FROM tax_invoices` 실측:

| 컬럼 | 상태 |
|---|---|
| `source_type varchar(30)` | 🟢 **이미 있다** · 코드 참조 **0건** |
| `source_id varchar(80)` | 🟢 **이미 있다** · 코드 참조 **0건** |
| `amendment_of varchar(36)` | 있다 · 참조 0건 · **인덱스(MUL) 까지 있다** |
| `amendment_reason varchar(200)` | 있다 · 참조 0건 |

⇒ **전용 `return_id` 컬럼을 새로 만들면 축이 3개가 된다**(`source_*`·`amendment_*`·`return_id`).
🔴 헌법 #37 취지(있는 걸 잔재로 오판 금지)와 **#1**(덮어쓰기 금지, 추가만) 에 비춰
**이미 있는 `source_type`/`source_id` 를 쓰는 게 맞다.** `sales_return` 키는 8/28작12 에서 이미 세웠다.

⚠️ **단 `amendment_of` 는 국세청 「수정세금계산서」 축**이다. 반품 연결과 **의미가 다르다.**
둘을 섞으면 나중에 수정계산서를 넣을 때 충돌한다 ⇒ **분리 유지 권고.**

### 2-2. 🟢 매출 기표는 「계산서」가 아니라 「거래명세서 확정」에서 일어난다

| 시점 | 기표 |
|---|---|
| 거래명세서 확정 (`SalesService.cs:581`) | 🟢 `RecordSalesConfirmAsync` — 차변 외상매출금 / 대변 매출+부가세예수금 |
| **계산서 발행** (`TaxInvoiceService.IssueAsync` 43~188) | 🔴 **분개 0건** |
| 계산서 취소 (`TaxInvoiceService.CancelAsync:322`) | 🔴 **역분개 1건** (`sales_cancel`) |

**발행이 기표를 안 하는 것 자체는 정상이다** — 헌법 #6(원장 반영은 confirmed 시점에만).
매출은 이미 명세서 확정에서 잡혔으므로 계산서가 또 잡으면 **이중계상**이다.

🔴 **문제는 취소 쪽이다.**

## 3. 🔴🔴 P0 발견 — 계산서를 취소하면 매출이 장부에서 사라진다

### 3-1. 코드가 스스로 틀린 근거를 적고 있다

`TaxInvoiceService.cs:321` 주석:
> *"역분개 — **IssueAsync 기표의** 차/대변 반전"*

**IssueAsync 는 기표하지 않는다.** 43~188 행에 `AutoJournalHelper` 호출이 **한 건도 없다.**
`CancelAsync:268` 주석도 *"발행(IssueAsync:50)이 sales_deliveries 에서 읽어 **기표하던**"* 이라 적었는데,
**50행은 거래명세서 「검증」 쿼리**다. 기표가 아니다.

⇒ **주석을 읽고 주석을 믿었다.** 8/28작12 에서 [4] 가 잡은 것과 **같은 유형의 받아쓰기**다.

### 3-2. 실측 — 원장이 실제로 0 이 된다

로컬 MariaDB 에 시나리오를 넣고 돌렸다(명세서 확정 1건 + 계산서 취소 1건).

| 계정 | 취소 후 잔액 |
|---|---|
| 10800 외상매출금 | **0.00** |
| 40100 매출 | **0.00** |
| 25500 부가세예수금 | **0.00** |

🔴 **거래명세서는 여전히 `confirmed` 이고 재고도 이미 나갔는데 장부에서는 매출이 통째로 사라진다.**
`CancelAsync` 는 `sales_deliveries.tax_invoice_id` 만 NULL 로 되돌리고 **명세서 상태는 안 건드린다.**

⇒ **재고 ↔ 회계가 갈린다.** 헌법 #20(워크플로우 무결성) 위반.
⇒ 매출 누락 = **부가세 매출세액 과소신고**. (8/27 의 과대계상과 **반대 방향** 사고다)

### 3-3. 그리고 아무도 못 잡는다

`FinanceService` 에서 `sales_cancel` 낱말 **0건**.
정합성 검사(「확정전표 기표 누락」)는 *"확정인데 기표 없음"* 만 본다.
이 건은 **기표가 있다가 사라진 것**이라 그 검사에 안 걸린다.

## 5. 🔴 사장님께 여쭐 것 (설계 착수 전)

### ① P0(계산서 취소 역분개)를 이번에 같이 잡나

**같이 잡아야 하는 이유**: 마이너스 계산서를 만들면 **취소 경로를 반드시 지나간다.**
이걸 두고 마이너스 계산서만 얹으면 **새 기능이 기존 사고 위에 올라탄다.**

**따로 잡아야 하는 이유**: 오더는 *"빨리 봉합하고 머지, 게시"* 다. P0 를 붙이면 범위가 커진다.

> **PM 권고**: **같이 잡는다.** 마이너스 계산서와 **같은 코드 경로**라 따로 하면 두 번 손댄다.
> 다만 **봉합 범위는 「취소가 명세서 상태까지 되돌리게」가 아니라 「취소 역분개를 조건부로」** 로 좁힌다
> (헌법 #20 — 정합성 지키되 흐름은 안 끊는다).

### ② 마이너스 계산서를 「새 행」으로 끊나, 기존 행을 뒤집나

- **새 행(권고)**: 음수 금액의 새 `tax_invoices` 행. 국세청 전송 이력이 남고 원본이 보존된다.
- 기존 행 수정: 이력이 사라진다. 전자세금계산서 성격상 부적절.

### ③ 사슬연결도 표기 위치

비고 형식 `반품전표 : 반-(전표번호)` 를 **`remark1`**(varchar(100), 이미 있음)에 넣나,
아니면 별도 표시 컬럼을 두나. `remark1`·`remark2` 는 **레거시 마이그 축**이라 충돌 여부 확인 필요.
