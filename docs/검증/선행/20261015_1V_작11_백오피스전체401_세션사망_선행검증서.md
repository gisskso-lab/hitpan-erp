## §1. 신고된 증상

사장님 화면에 뜬 것(그대로):

```
목록 조회 실패: Response status code does not indicate success: 401 (Unauthorized).
A/S 목록을 불러오지 못했습니다 — 잠시 뒤 「조회」를 다시 눌러 주세요. (… 401 (Unauthorized).)
백과사전 조회 실패: … 401 (Unauthorized).
공지 목록을 불러오지 못했습니다 — … 401 (Unauthorized).
```

🔴 **한 화면이 아니다. 전부다.** 고객지원·A/S·백과사전·공지가 한꺼번에 같은 코드로 떨어졌다.

🔴 **그런데 화면은 떠 있었다.** 로그인 화면으로 밀려나지 않았다. 이 한 가지가 진범을 가른 열쇠다.

## §2. 실측 — 서버는 멀쩡하다

운영은 읽기만 했다(#39). 무엇도 고치지 않고 상태코드만 쟀다.

| 재 본 것 | 결과 | 무엇을 뜻하나 |
|---|---|---|
| `https://back.hitpan.kr/` | **200** | 화면 서비스 살아 있다 |
| `backoffice/login` | **200** | 로그인 화면 정상 |
| `admin/tenants` (쿠키 없이) | **302** | 🟢 **쿠키가 없으면 로그인으로 제대로 보낸다** |
| `api/admin/cs/outbound` (토큰 없이) | **401** + `WWW-Authenticate: Bearer` | 🟢 **API 가 살아서 인증을 보고 있다** |
| `api/backoffice/auth/admin/login` | **405** | 라우트 존재(POST 전용) — 로그인 경로 정상 |

🔴 **죽은 서비스는 401 을 주지 않는다.** 502·504 를 준다. API 는 살아서 **토큰을 보고 거절**하고 있었다.

🔴 **그리고 사장님은 302 로 로그인에 안 밀려났다** ⇒ 쿠키 `hitpan_bo` 는 **살아 있었다.**

⇒ 죽은 것은 서버가 아니라 **쿠키 안에 들어 있는 토큰**이다.

## §3. 진범 — 쿠키는 계속 사는데, 그 안의 JWT 는 8시간에 죽는다

흐름을 코드로 따라가면 이렇다.

| 단계 | 어디 | 무엇이 일어나나 |
|---|---|---|
| ① 로그인 | `HitPan.Backoffice.API` `BackofficeAuthController.IssueTokens` | JWT 발급. `exp` = **로그인 시각 + `Jwt:ExpiresHours`(8)** |
| ② 쿠키 굽기 | `HitPan.Backoffice` `BackofficeAuthController.SignInWithClaimsAsync` | 그 JWT 를 **`access_token` 클레임으로 쿠키에 굳혀** 넣는다 |
| ③ 쿠키 수명 | `Program.cs` 쿠키 설정 | `ExpireTimeSpan = 8h` + **`SlidingExpiration = true`** ⇒ 쿠키는 쓰는 동안 **계속 갱신된다** |
| ④ 화면이 API 호출 | `JwtFromCookieHandler` | 쿠키 클레임에서 토큰을 꺼내 `Authorization: Bearer` 로 붙인다 |
| ⑤ API 가 검사 | `HitPan.Backoffice.API` `Program.cs` | **`ValidateLifetime = true`** — 수명을 본다 |

🔴 **③ 은 갱신되고 ① 은 안 갱신된다.** 쿠키는 슬라이딩으로 계속 살지만, **그 안에 든 JWT 의 `exp` 는 로그인 시각에 멈춰 있다.** 8시간이 지나면:

- 쿠키는 유효 ⇒ 화면은 **로그인 상태**로 뜬다
- 토큰은 만료 ⇒ **모든 조회가 401**

그리고 **풀릴 길이 없다.**

### §3-1. 🔴 갱신(refresh) 경로가 0건이다

백오피스 API 인증 컨트롤러의 라우트를 전수로 세어 봤다.

| 라우트 | 있나 |
|---|---|
| `admin/login` | 있다 |
| `reseller/login` | 있다 |
| **토큰 갱신** | 🔴 **0건** |

`refresh_token` 은 발급돼 쿠키에 들어가지만, 코드에 「refresh: 단순 GUID (다음 단계 — DB 저장 + 만료·재발급)」라고 적혀 있고 **그것을 받는 엔드포인트가 없다.** 아무도 쓰지 않는다.

⇒ 8시간이 지난 세션은 **재로그인 말고는 되살릴 방법이 없다.** 그런데 화면이 로그인 상태로 보이니 **사용자는 재로그인할 생각을 하지 않는다.** 이것이 「전체가 죽었다」의 정체다.

### §3-2. 시각 대조

| 사건 | 시각 |
|---|---|
| `Deploy to NCP` 완주 (`3d88c467`) | 2026-10-14 23:32 KST |
| 토큰 수명 | 로그인 시각 + 8시간 |
| 신고 | 2026-10-15 아침 |

⇒ 밤에 로그인한 세션은 아침에 **반드시** 만료돼 있다. 증상과 어긋나는 데가 없다.

## §4. 🔴 내 머지가 원인인가 — 아니다. 그러나 변명하지 않는다

사장님 말씀 「되던걸 왜 망쳐놔?」에 정직하게 답한다.

**PR #550 이 백오피스에서 바꾼 것 전부**(`git diff 3d88c467^1 3d88c467` 실측):

| 파일 | 바뀐 것 |
|---|---|
| `Components/Pages/Platform/Components/CsVocab.cs` | 낱말 2곳 「요금 안내」→「과금결재 안내」 + 주석 |

인증·쿠키·토큰·HttpClient 를 건드린 줄은 **0건**이다. 이 구멍은 **그 전부터 있었다.**

🔴 **그러나 이것이 면죄부는 아니다.**

- 배포가 서비스를 **재기동**시켰다. DataProtection 키는 배포 폴더 **밖**(`/var/hitpan/backoffice-dp-keys`)에 있어 **쿠키가 재기동을 살아남았다.** 그래서 사장님은 로그인 화면으로 밀려나지 않고 **이 상태에 갇혔다.** 키가 날아갔다면 오히려 로그인 화면이 떠서 재로그인하고 끝났을 일이다.
- 🔴 **내가 「배포 완료 · 정상」이라고 보고했다.** 상태코드와 배포 로그만 보고 「정상」이라고 적었다. **로그인한 다음 화면에서 목록이 떠지나**는 재지 않았다. 사장님이 그 화면을 열었을 때 전체가 401 이었다. **보고가 앞서 나갔다.**

## §5. 봉합 — 쿠키가 그 안의 JWT 보다 오래 살지 못하게 한다

| 파일 | 한 일 |
|---|---|
| `src/HitPan.Backoffice/Services/BackofficeSessionGuard.cs` | **신설** — 판정 한 곳 |
| `src/HitPan.Backoffice/Program.cs` | 쿠키 `OnValidatePrincipal` 에서 그 판정을 부른다 |

동작: 쿠키를 검사할 때마다 안에 든 `access_token` 의 `exp` 를 읽는다. 죽었으면 **쿠키를 버리고(`RejectPrincipal` + `SignOutAsync`) 로그인 화면으로 보낸다.**

⇒ 「401 이 20곳에 뜨는 멀쩡해 보이는 화면」이 **「다시 로그인하세요」**가 된다.

### §5-1. 🔴 확실할 때만 버린다

멀쩡한 세션을 내 판단 착오로 끊는 쪽이 더 큰 사고다. 그래서 **버리는 경우를 하나로 좁혔다.**

| 판정 | 쿠키를 버리나 |
|---|---|
| `NoTokenClaim` — 클레임이 없다 | 아니다 |
| `Unreadable` — JWT 모양이 아니다 | 아니다 |
| `NoExpiry` — `exp` 가 없다 | 아니다 |
| `Alive` — 살아 있다 | 아니다 |
| **`Expired`** — 죽었다 | 🔴 **버린다** |

### §5-2. 🔴 판정을 왜 떼어냈나

`Program.cs` 람다 안에 두면 **게이트가 부를 수 없다.** 그러면 「그 글자가 파일에 있나」를 세는 **가짜 게이트**밖에 못 만든다 — 누적 30회+ 사고이고, 바로 어제(작9) 다섯 번째로 같은 사고를 냈다.

그래서 판정을 **Blazor·ASP.NET 의존 0 인 순수 C#** 파일로 떼고, `HitPan.Tests` 가 **소스만 링크**해 **값을 넣고 판정을 받아** 본다(`CsVocab.cs` 선례).

### §5-3. 꾸러미를 더하지 않았다

`exp` 를 읽으려고 `System.IdentityModel.Tokens.Jwt` 를 들이면 화면 프로젝트에 인증 꾸러미가 새로 붙어 **NU1903 표면이 늘고 #19(경고 0)가 흔들린다.** 필요한 건 숫자 하나뿐이라 **안에 있는 것**(`System.Text.Json` + base64url)으로 읽었다. 🟢 `PackageReference` 변경 **0줄**.

## §6. 게이트 G-W14-1~8 — 글자를 세지 않는다

실제 JWS 모양(머리.몸.서명) 토큰을 만들어 판정에 넣고 **돌아온 답**을 본다.

| 게이트 | 무엇을 재나 |
|---|---|
| G-W14-1 | 3시간 남은 토큰은 **안 끊는다**(양성 대조군) |
| **G-W14-2** | 🔴 10/14 23:30 로그인 + 8h ⇒ 10/15 09:00 에 **버린다** — 사고 그 모양 |
| G-W14-3 | 🔴 못 읽는 토큰 7종으로 **안 버린다** |
| G-W14-3b | `exp` 없는 토큰은 죽었다고 **말하지 않는다** |
| G-W14-4 | 경계 — `exp == 지금`은 죽은 것, 1초 남으면 산 것 |
| G-W14-5 | 유예 — 만료 직전 미리 끊는다 · **기본값에 유예가 켜져 있나** |
| G-W14-6 | `exp` 를 숫자로도 글자로도 읽는다 |
| **G-W14-7** | 🔴 `Program.cs` 가 이 판정을 **실제로 부르나** + 토큰을 로그에 안 적나(#22) |
| G-W14-8 | 🔴 갱신 경로가 **아직 0건**임을 고정 — 생기면 빨강 ⇒ 결-M 을 다시 보라 |

측정: **15/15 통과**(G-W14-3 은 7가지 입력으로 갈라져 15건).

### §6-1. 🔴 음성 대조군 — 봉합을 빼면 정말 빨강이다

「통과했다」만으로는 게이트가 무엇을 재는지 알 수 없다. 봉합을 하나씩 빼고 **실제로** 돌렸다.

| 대조군 | 뺀 것 | 결과 |
|---|---|---|
| NC-1 | `ShouldDropCookie` → `=> false` (봉합 제거) | 🔴 **G-W14-2·4·5 빨강** (3건) |
| NC-2 | 유예(`graceSeconds`) 무시 | 🔴 **G-W14-5 빨강** (1건) |
| NC-3 | 못 읽는 토큰을 `Expired` 로 판정 | 🔴 **G-W14-3 빨강** (4건) |
| NC-4a | 배선 이름을 바꿔 끊기 | 🔴 **G-W14-7 빨강** |
| NC-4b | 배선 블록을 통째로 삭제 | 🔴 **G-W14-7 빨강** |

### §6-2. 🔴 NC-4 가 내 게이트의 구멍을 먼저 잡았다

NC-4 를 처음 돌렸을 때 배선을 `OnValidatePrincipalDISABLED_NC4` 로 바꿨는데 **G-W14-7 이 통과했다.** `Contains("OnValidatePrincipal")` 이 **부분일치**로 걸린 것이다. 🔴 배선을 끊어도 초록인 게이트였다.

⇒ 대입문 모양(`o.Events.OnValidatePrincipal\s*=`)을 정규식으로 보게 고쳤다. 고친 뒤 NC-4a·4b 둘 다 빨강.

🔴 **그리고 그때 나는 `--no-build` 로 돌렸다.** 앞 대조군(NC-3)의 산물이 DLL 에 남아 있어 **결과 자체를 믿을 수 없었다.** 다시 빌드하고 기준선(15/15 초록)을 세운 뒤 재측정했다. 교훈: **대조군마다 빌드한다.**

## §9. 남은 결재 거리 — 결-M

🔴 **이 봉합은 8시간마다 재로그인을 만듭니다.** 조용히 죽던 것을 **소리내어 죽게** 바꾼 것이지, 안 죽게 만든 게 아닙니다.

없애려면 **토큰 갱신(refresh) 경로**를 만들어야 합니다. 그건 인증 설계 변경이라 사장님 결재 거리입니다.

| 안 | 무엇 | 비용 |
|---|---|---|
| ① 지금 이대로 | 8시간마다 재로그인 | 0 — 다만 하루 한 번 불편 |
| ② 수명을 늘린다 | `Jwt:ExpiresHours` 를 올린다 | 설정 한 줄 · 🔴 토큰이 오래 살면 털렸을 때 오래 쓰인다 |
| ③ 갱신 경로를 만든다 | `refresh_token` 을 DB 에 두고 재발급 | 설계·보안 검토 필요 |

**PM 추천 = ③ 이지만 지금은 아니다.** 사고 봉합과 설계 변경을 한 번에 하면 어느 쪽이 터졌는지 못 가립니다. ①로 두고 사장님이 「하루 한 번 재로그인이 불편한가」를 실제로 겪어 보신 뒤 결정하시는 게 맞습니다.

🔴 ② 는 **추천하지 않습니다.** 증상만 멀어지고 위험은 커집니다.
