## 1. 🔴 전제 반증 ① — "불안정하다"가 아니라 "도메인으로 열면 100% 안 된다"

**근거**: `src/HitPan.API/Security/MainPcOnlyAttribute.cs:38-50`

```csharp
var viaTunnel = req.Headers.ContainsKey("CF-Connecting-IP")
             || req.Headers.ContainsKey("X-Forwarded-For");
var isLoopback = remote is not null && IPAddress.IsLoopback(remote);
return !viaTunnel && isLoopback;
```

도메인(터널) 접속은 Cloudflare 가 `CF-Connecting-IP` 를 반드시 붙이므로 **첫 조건에서 무조건 탈락**한다.

| 여는 방법 | 메인PC 판정 |
|---|---|
| 그 PC 에서 `localhost` 로 열기 | 🟢 통과 |
| **도메인으로 열기** | 🔴 **항상 실패** |

사장님이 도메인으로 쓰시므로 **한 번도 성공한 적이 없다.** "됐다 안 됐다"로 보인 것은
localhost 로 열었을 때만 통과했기 때문이다.

**여기에 물려 있는 기능** — 셋 다 403 이 난다:
- 백업 `src/HitPan.API/Controllers/BackupController.cs:23`
- 데이터 초기화 `src/HitPan.API/Controllers/DataResetController.cs:19`
- **자료이관** `src/HitPan.API/Controllers/MigrationController.cs:438`

### 왜 IP 로는 영원히 못 가리는가 (실측)

터널(cloudflared)이 **그 PC 안에서** 히트판을 다시 부른다.
⇒ 서버가 보는 소켓 주소는 **외부 접속이든 메인PC 든 항상 `127.0.0.1`** 이다.

남는 단서는 Cloudflare 헤더뿐인데, 그 헤더는 **메인PC 가 도메인으로 접속할 때도 똑같이 붙는다.**

같은 사무실이면 공인 IP 도 같다 (실측: `124.194.59.154` / KR).

```
[사무실]
 ├ 메인PC      → 터널 → 서버가 보는 값: 소켓 127.0.0.1 · CF-IP 124.194.59.154
 └ 클라이언트PC → 터널 → 서버가 보는 값: 소켓 127.0.0.1 · CF-IP 124.194.59.154   ← 동일
```

⇒ **IP 축은 사망. 다른 증거가 필요하다.**

## 3. 🔴 신규 결함 — 외부 PC 가 "나 메인PC 야" 라고 거짓말하면 그대로 통과한다

**사장님 실측으로 발견** (PM 은 [1-V] 1차에서 못 봤다).

**위치**: `src/HitPan.Web/Components/Common/DeviceAuthGate.razor:618` `JoinServerRowAsync()`

```
① 기기 목록에서 is_main_pc=1 인 줄(메인PC)을 찾는다
② 그 줄의 인증키를 재발급받는다          ← 대표 계정이면 통과
③ 이 브라우저의 신분을 그 줄로 바꾼다     ← localStorage 에 메인PC 의 device_id 를 쓴다
④ 그 키로 verify → 🟢 메인PC 로 인정
```

**접속한 자리를 한 번도 확인하지 않는다.** 대표 계정으로 로그인만 하면
집·카페·외부 어디서든 메인PC 줄에 올라탈 수 있고, 그 순간 **백업·데이터 초기화·자료이관**이 열린다.

### 버그가 아니라 의도한 설계였다

같은 파일 `:609` 주석:

> *"같은 기계임을 서버가 증명할 길은 없으므로 (터널은 접속 경로를 지운다) **대표가 사람으로서 정한다**(반자동 원칙)."*

⇒ 당시엔 증명할 방법이 없다고 판정하고 판단을 사람에게 넘겼다.
**그 전제가 아래 §4 실측으로 깨졌다.**

### 🔴 사장님 판정 (2026-09-22) — 반자동 원칙을 오용했다

> *"이 반자동 원칙은 **메인PC라고 식별한 최초의 컴퓨터에 한한** 거지,
>  그렇게 치면 **모든 PC를 메인PC라고 무단접속 하는 구멍**을 주는 거."*
> *"오히려 더 꼬임."*
> *"**기기가 직접 인증키를 인식하고 메인PC로 알아보는 게 정확함.**"*

반자동 원칙(제안값 → 사람이 확정)은 **최초 1회 식별**에 적용되는 것이다.
그런데 이 코드는 **매 접속마다 누구나 "내가 메인PC다" 라고 선언할 수 있게** 만들었다.

⇒ **반자동 원칙을 구멍의 근거로 썼다.** 원칙의 오용이다. 결함의 성격은
   *"증명 못 해서 사람에게 맡김"* 이 아니라 **"막아야 할 자리를 원칙으로 정당화함"** 이다.

⇒ 그래서 [2] 설계의 방향은 **사람을 더 잘 묻는 것이 아니라, 사람을 안 묻는 것**이다.
   **기기가 인증키를 스스로 인식해 메인PC 를 알아본다. 사람 개입 0.**
   (반자동 원칙은 폐기가 아니다 — **최초 설치·최초 식별** 자리로 되돌려 놓는다)

## 4. 🟢 A안은 선다 — 실측으로 확인

### 무엇을 쟀나

> **터널(도메인)을 지나온 페이지가, 자기 PC 안의 히트판을 직접 두드릴 수 있는가?**

두드릴 수 있으면 메인PC, 못 하면 클라이언트다. 클라이언트 PC 에는 히트판 본체가 없기 때문이다.

### 재현 절차 (다음 사람이 그대로 재현할 것)

```
스크립트: scratchpad/pna-probe2.js (Playwright · chromium)
1. chromium.launch({ headless: false })        ← 🔴 headless: true 면 결과가 반대로 나온다(§4-3)
2. newContext({ bypassCSP: true })             ← 🔴 CSP 를 끄지 않으면 우리 설정에 먼저 막힌다(§4-2)
3. page.goto('https://test1234.hitpan.kr/')    ← 도메인 = 터널 통과 = 진짜 조건
4. page.evaluate → fetch('http://127.0.0.1:5257/health', { mode: 'cors' })
```

### 결과

```
페이지 출처(origin): https://test1234.hitpan.kr   (터널 통과)
🟢 http://127.0.0.1:5257/health → HTTP 200   {"status":"healthy","timestamp":"2026-09-22T11:55:47..."}
🟢 http://localhost:5257/health → HTTP 200   {"status":"healthy","timestamp":"2026-09-22T11:55:47..."}
--- 브라우저가 낸 차단 메시지: 없음 ---
```

**터널 뒤에서도 통과한다. 사장님 A안이 성립한다.**

### 4-1. 🟢 클라이언트 PC 는 물리적으로 못 붙는다

```
Get-NetTCPConnection -State Listen  ⇒  127.0.0.1:5257  (LocalAddress 가 127.0.0.1)
```

API 는 **루프백에만 바인딩**돼 있다. 외부 주소로는 아예 듣지 않는다.
⇒ 클라이언트 PC 에서 이 주소를 두드리면 **자기 PC 를 두드리는 것**이고, 거기엔 히트판이 없다.
⇒ **붙으면 메인, 안 붙으면 클라이언트.** 증거로 깨끗하다.

### 4-2. ⚠️ 막고 있던 것 ① — 우리가 건 CSP (우리 설정, 고칠 수 있다)

CSP 를 끄지 않고 실측하면 이렇게 막힌다:

```
Connecting to 'http://127.0.0.1:5257/health' violates the following Content Security Policy
directive: "connect-src 'self' https: wss:". The action has been blocked.
```

브라우저의 벽이 아니라 **히트판이 스스로 `http:` 연결을 막아 둔 것**이다.
⇒ [2] 설계에서 이 한 줄을 어떻게 열지 정해야 한다(무엇을 얼마나 열지는 보안 상무 검토 대상).

### 4-3. 🔴 함정 — headless 로만 재면 정반대 결론이 나온다

같은 스크립트를 `headless: true` 로 돌리면:

```
🔴 blocked by CORS policy: Permission was denied for this request to access the `loopback` address space.
```

**헤드리스 브라우저는 로컬 접근 권한을 자동 거부한다.** 실제 브라우저 창에서는 차단 메시지조차 없다.

⇒ 🚨 **헤드리스 결과만 보고 "브라우저가 막는다 = A안 불가" 로 보고할 뻔했다.**
   이 자리는 반드시 **실제 브라우저 창(headless:false)** 으로 재야 한다.

## 5. 🟢 직원 ≠ 계정 — 이미 분리돼 있다

사장님 확정: *"퇴사자 계정은 계정삭제로 -1. 직원등록과 계정등록은 다른 의미임."*

**DB 는 이미 그렇게 서 있다** (`installer/hitpan_db_clean.sql`):

| 테이블 | 확인된 것 |
|---|---|
| `employees.user_id` | `varchar(36) DEFAULT NULL` — **NULL 허용** ⇒ 계정 없는 직원이 성립한다 |
| `users.is_parent` | `1=부모계정(랜딩 가입자, tenant당 1명) / 0=자식계정(ERP 내 생성)` — 헌법 #38 그대로 |

⇒ 계정 과금 카운트는 `users WHERE tenant_id=? AND is_parent=0 AND is_deleted=0` 으로 선다.
⇒ **계정관리 기능 추가는 DB 를 갈아엎는 일이 아니다.** (다만 화면·서비스 계층이 직원과 계정을
   한 몸으로 다루는지는 **아직 안 봤다** — §7 미확인)

## 6. 사장님 설계 결재 사항 (2026-09-22 확정분)

| 항목 | 확정 |
|---|---|
| 기기 슬롯 과금 | **폐기.** 기존 "PC 5 + 모바일 3" 없앤다 |
| 기기 수 | **무제한.** 메인PC 1대 / 클라이언트 무제한 |
| 과금 단위 | **등록 계정 수** (동시 접속 아님) |
| 가격 | 5계정 3만 / 10계정 5만 / 1계정 추가 1만 (조합은 고객이 고른다 — *"개발자가 관여할게 아님"*) |
| 기기 등록 절차 | **제거.** 인증 등 절차 없앰 · **조회 기능만** 남김 |
| 기기 컬럼·코드 | **지우지 않는다** (#1 · #37) — 끄고 남긴다 |
| 백오피스 | 부모계정만 → **부모 + 자식계정 수**. 개인정보는 안 올린다 (#18 · #22) |
| 계정 한도 | 기본 5계정까지 ERP 에서 자유 생성. 초과는 **본사 문의·랜딩 연결**로 안내 |
| 작업 범위 | **(ㄱ) ERP 먼저.** 그 안에서 **메인PC A안이 선행** |

### 이 결재가 증상 ①을 없앤다

기기로 돈을 받지 않으면 줄이 늘어도 고객이 손해 보지 않는다.
⇒ **증상 ①은 고칠 대상이 아니라 증상이 아니게 된다.** (지저분한 것은 남지만 과금·차단과 무관)
