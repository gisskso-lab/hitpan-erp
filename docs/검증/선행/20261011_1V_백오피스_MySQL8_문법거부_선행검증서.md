## §1 한 줄

**운영 백오피스 DB(MySQL 8.0.45)는 `ALTER TABLE … ADD COLUMN IF NOT EXISTS` 를 문법 오류로 거부한다.**
적용기는 첫 실패에서 기동을 중단하므로 **`11` 번에서 멈췄고, 그 뒤 파일 전부가 운영에 없다.**
CS·요금제 500 은 증상 3개일 뿐 — 실제 공백은 **표 9개 + 칸 10개**다.

## §3 🔴 원인 — 서버가 직접 말했다 (가설 아님)

`journalctl -u hitpan-backoffice-api` 실측:

```
MySqlConnector.MySqlException (0x80004005): You have an error in your SQL syntax;
check the manual that corresponds to your MySQL server version for the right syntax
to use near 'IF NOT EXISTS approved_at_dt datetime NULL DEFAULT NULL
```

- `[SchemaMigrator] 적용 실패 11_backoffice_payment_z3_approved_at.sql — 기동 중단`
- 그 앞은 `skip (적용됨) 00_backoffice_core.sql` · `skip (적용됨) 10_backoffice_payment.sql` 둘뿐

`ADD COLUMN IF NOT EXISTS` 는 **MariaDB 전용 문법**이다. MySQL 8 은 모른다.

### §3-1 왜 게이트가 못 잡았나 — 판이 다르다

| | 종류 | 근거 |
|---|---|---|
| 운영 NCP 백오피스 | **MySQL 8.0.45** (`mysql.service`) | [20260730 일일작업보고서](../../운영기록/20260730_일일작업보고서.md) §발견정정 — 「문서·기억상 mariadb 로 알려져 있었으나 실제는 MySQL 8.0.45」 |
| CI `db-gate` 잡 | **MariaDB 11.4** | `.github/workflows/build-and-test.yml` — `image: mariadb:11.4` (2곳) |

⇒ 백오피스 스키마를 실제로 적재하는 게이트(`BackofficeRoleGateHarness` · `BackofficePromotionPricingDbGateTests` 등)는 **전부 MariaDB 에서만 돌았다.**
**게이트 개수와 무관하게 이 사고는 잡힐 수 없었다.** 재발 방지의 본체는 봉합이 아니라 **판을 하나 더 붙이는 것**이다.

🔴 PM 자기정정: 2026-10-08 절차서 §3 에서 「파일이 서버에 실리면 재기동 한 번으로 풀린다」고 적었다. **DB 종류 축이 빠져 있었다.** 10/11 배포로 파일은 실제로 실렸고(로그 15줄 확인), 그래도 안 풀렸다.

## §4 운영 DB 실측 — 무엇이 없나

### §4-1 적용이력표 (`_schema_migrations`)

```
00_backoffice_core.sql    | 2026-10-11 20:22:40.944443
10_backoffice_payment.sql | 2026-10-11 20:22:40.954149
```

🔴 **두 줄의 시각이 둘 다 10/11 밤** = **적용기가 운영에서 돈 것이 오늘이 처음**이다. 이력표 자체가 오늘 생겼다.
⇒ 운영 스키마는 여태 **이 경로로 관리된 적이 없다**. 10/8 절차서 §6 의 「과거에 사람이 놔둔 사본」 추측은 이렇게 결론났다.

### §4-2 표 — `SHOW TABLES` 30개

운영에 있는 것 = **`00`(28개) + `10`(1개) + `_schema_migrations`** = 30. 한 개도 안 틀리고 맞는다.

**없는 표 9개**

| 표 | 어느 SQL | 못 되는 일 |
|---|---|---|
| `tenant_update_history` · `tenant_update_state` | 20 | 고객사 업데이트 수신 기록 |
| `bo_cs_tickets` · `bo_cs_ticket_logs` · `bo_cs_replies` · `bo_cs_reject_logs` | 40 | CS 창구 |
| `bo_kb_docs` · `bo_kb_doc_logs` · `bo_ai_export_consents` | 41 | CS 백과사전 |

### §4-3 칸 — `information_schema.columns` 조회 17개 중 **1개만 존재**

나온 것: `tenants.tenant_id` (그 표의 원래 칸) — **그 밖에는 아무것도 안 붙어 있다.**

**없는 칸 10개**

| 칸 | 어느 SQL | 이 칸을 읽는 코드 (칸 이름으로 grep 실측) |
|---|---|---|
| `tenant_payments.approved_at_dt` | 11 | `ResellerSettlementCalculator` — **대리점 정산 날짜축** |

## §6 🟢 데이터 안전 — 오늘 밤 운영 데이터는 0줄 바뀌었다

| 근거 | 실측 |
|---|---|
| 오류가 **그 파일 첫 문장**(ALTER)에서 났고 거기서 멈췄다 | 오류 글자가 `approved_at_dt` 를 가리킨다 · 그 파일의 1번 문장 |
| 뒤의 `UPDATE tenant_payments` 2문장은 **실행되지 않았다** | 같은 배치에서 앞 문장 오류 → 중단 |
| 적용된 `00`·`10` 은 **순수 DDL** | `CREATE TABLE IF NOT EXISTS` 29개 · `INSERT`/`UPDATE`/`DELETE` **0개** (파일 전수 계수) |
| 되돌림 | drop-in 제거 + 재기동으로 `is-active=active` 복귀 확인 (사장님 실측) |

⇒ 오늘 밤 일어난 변화는 **「없던 표가 있으면 만든 것」** 뿐이다.

## §9 이 사고가 남기는 규칙 (다음 사람에게)

- 🔴 **운영 DB 종류를 모르고 DDL 을 쓰지 마라.** 백오피스=MySQL 8 / ERP=MariaDB — **두 판이다.**
- 🔴 **게이트가 한 판에서만 돌면 다른 판의 사고는 영원히 안 잡힌다.** 게이트 개수는 증거가 아니다.
- 🔴 **「파일이 서버에 갔다」 ≠ 「적용됐다」.** 10/11 배포 로그 15줄은 실렸음만 증명했다.
