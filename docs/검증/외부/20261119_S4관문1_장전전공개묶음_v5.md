## §0-1 [한계(v5)] — 장치 MAPPING §12 와 바이트가 같은 단락 (CTO A10-3 · 합격 근거 주장보다 앞 · v4 대비 새)

> **한계(v5).** 설치 뒤 단언(G1~G6)과 판독 직전 고정값 확인(`pin`)은 같은 실행기 안에서 도는 걸림줄이다. G1~G6 은 앞 단면(⑤ 바로 앞)과 M3 뒤 사이에 생긴 **우발** 변화(환경 변수 · git 설정 · 실행 파일 바이트 · 미리 읽는 라이브러리 설정(`/etc/ld.so.preload`) · 장치 나무(HEAD · 색인 표시 · replace 참조 포함))를 잡고, `pin` 은 M7 직전 판독 코드 4파일의 **디스크 위 바이트**가 워크플로 본문 고정값과 같음을 보인다. 둘 다 그 단계 셸이 깨끗하다는 전제 위에 선다. G5 가 대조하는 작업 나무는 장치 폴더(`tools/hqa-s4-measure`) · 측정 워크플로(`.github/workflows/hqa-s4-measure.yml`) 두 경로뿐이고(그 위 사이 폴더는 `.git` 이름 항목 · 링크인지만 본다), 그 밖 작업 나무(맨 위 `.gitattributes` 포함)의 창 안 변화는 G5 · M0 · M1 어디서도 대조하지 않는다. M1 의 소스 ↔ 나무 판정 칸은 작업 나무 속성(`.gitattributes` · `info/attributes`)을 탄 해시로 정한다 — 소스 묶음은 기대 sha256 대조를 거친 같은 파일을 풀어 해시하므로 묶음을 바꿔치는 길은 아니며, 속성이 바꿀 수 있는 것은 고정된 한 쌍(묶음 ↔ 장치 커밋 나무)의 판정 칸뿐이고 원 바이트 칸이 원자료(`m1-src-hashes.json`)에 함께 남는다(판정 칸이 속성을 타는 것 = 개발 PC 측정 · 순서 = 코드 읽기). guard(M3 뒤)부터 `pin` 사이 단계(M4 · 점검 · 항목 · run.json · M8 · M9)는 G 항목 밖이다 — 이 단계들은 고정된 코드만 돌리며, 다음 단계로 넘기는 실행기 환경 파일 쓰기는 M4 의 `HQA_BASE_URL` · `HQA_APP_DIR` 두 이름뿐이다(실행 경로 파일 쓰기 0). 표본 수집(항목 단계)도 같은 「셸이 깨끗하다」 전제 위에 있고, 다시 실행할 수 없어 추적성(잠금 무결성 · 설치 기록 · M3′)으로만 받친다. 같은 실행기에서 코드를 돌릴 수 있는 악의 있는 단계(예: 잡의 어느 단계 코드든 — 실행기 사용자는 암호 없이 관리자 권한을 쓴다 · 잡 끝까지 살아 있는 프로세스)는 앞 단면 · 검사 도구 · 셸 시작 변수(스스로 지우는 꼴 포함) · 실행기 환경 파일 · 저장소 내부(개체 저장소 · 손으로 만든 팩 위조 = 미측정)를 함께 바꿀 수 있어 이 확인으로 막지 못하며, 실행 중인 판독기가 바뀌지 않았다는 증명도 아니다. guard 가 PATH 로 찾아 돌리는 외부 명령은 `bash` · `dirname` · `mkdir` · `rm`(G1 전 · G5) · `node`(G1 · G5 · 원자료 쓰기) · `git`(G2 · G5) · `cmp`(G2~G4) · `readlink`(G3) · `sha256sum` · `cut`(G3 · G4) · `grep`(G5) 열하나다(guard 전체 · 코드 읽기 셈 · 미측정). 이 가운데 바이트를 확인하는 것은 G3 의 `node` · `git` · `bash` 셋뿐이고 그 셋도 자기 바이트 확인(G3) 전에 실행되며, 나머지 여덟은 확인 대상이 아니다. 잡 안에서 도는 코드는 장치 커밋 · 잠금 무결성 · 기대 해시 · 외부 액션 SHA 로 식별되며, 고정하지 못한 것은 실행기 이미지와 배포판 서명 꾸러미의 설치 스크립트(M2 · 판 + 서명 색인 · 설계 §1-1)뿐이다. 판독기 바이트의 독립성은 이 확인이 아니라 공개 원자료를 설치 없는 다른 환경에서 다시 판독해 대조하는 절차(설계 §1-2)가 진다. 판독 결과는 HQA 재판독이 일치한 회차만 합격 근거로 센다(설계 §1-2).
