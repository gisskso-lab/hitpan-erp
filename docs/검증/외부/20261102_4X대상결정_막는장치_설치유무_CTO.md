## §1 두 건 대상 / 제외

### 막는 장치 — 대상

> 근거 한 줄: 게시 보류 해제 조건에 든 신규 CI 장치 · 머지 차단 후보 · 필수 설정은 이 PR 밖 · 의뢰 범위 = PR 머리에 푸시된 고정 SHA 의 코드와 지시서 공개본

V-1 의 「잠재 심각도 P0 표기 건」 은 뺀다. 지시서 머리가 「위험 등급 확정과 별개」 다. 확정 전 등급을 공개 사유에 적을 까닭이 없고, 없어도 대상 근거가 선다.

### 설치 유무 — 제외

> 제외 사유 한 줄: 본사 권한 화면의 표시 교정 · DB 쓰기 0 · DDL 0 · ERP · 설치 · 시리얼 · 고객 PC 무접촉 · 설계 기준 새 수집 0 · 새 열람 1칸(저장된 고객 가동 시각이 처음 본사 눈에 간다) · 설계 기준 잠재 P0 미식별 · 남은 쟁점은 코드 읽기로 못 가르는 실물 대조 · 머지가 운영 배포 런을 띄우므로 배포 승인 별도

3인 문장에서 고친 곳:

| 3인 문장 | 고침 | 이유 |
|---|---|---|
| 「제품 쓰기 0」 | 「DB 쓰기 0」 | 막는 장치 지시서의 「제품 코드 0」 과 낱말이 겹친다. 설치 유무는 백오피스 제품 코드를 고친다 |
| 「새 수집 0(저장된 값 1칸 첫 열람)」 | 「새 수집 0 · 새 열람 1칸」 | 괄호에 넣으면 부가 설명으로 읽힌다. 수집과 열람은 다른 사실이다 |
| 「잠재 P0 없음」 | 「설계 기준 잠재 P0 미식별」 | 코드가 아직 없다. 없다고 단정할 시점이 아니다 |

🔴 **반증 — 위험 순서로 보면 대상과 제외가 거꾸로다.** 막는 장치는 제품 코드 0 · 운영 배포 런 0 이고, 설치 유무는 제품 코드 변경 · 머지가 곧 운영 배포 런 · 본사 화면 · 고객 가동 시각 첫 열람이다. 「외부 읽기로 더 얻을 것이 적다」 는 판정식 한 축에서만 참이다. 권한 범위 · 재료 출처 · 실패 시 생존은 코드 읽기로 가를 수 있다.

그래도 제외를 채택하는 근거는 셋이다.
1. 남은 가장 큰 쟁점(판정식 ↔ 실물)은 공개 코드로 답이 안 나온다. 배포 뒤 대표 눈 대조뿐이다.
2. 코드로 가를 수 있는 쟁점은 [3-V] 중점과 V 항목이 내부에서 덮는다. 🔴 **내부 눈만 본다는 뜻이다.** 상신에 그대로 적는다.
3. 두 PR 이 같은 파일을 고친다. 둘 다 의뢰하면 뒤 PR 의 의뢰 SHA 는 재정렬로 반드시 깨진다. 제외가 §4 를 풀어 준다.

제외의 뜻도 좁게 쓴다. **제외 = 의뢰서 미발행** 이다. 공개 레포라 외부가 스스로 읽고 지적할 수 있고, 지적이 오면 §8-1 #4 를 그대로 탄다.

**재심 조건** — 하나라도 걸리면 CTO → 대표로 다시 올린다. PM 단독으로 넣고 빼지 않는다.
① 대표 답(4 · 5 · 6번)이 쓰기 · DDL · ERP · 설치 · 시리얼 접촉을 부른다 ② 변경 파일이 설계 §8 표 밖으로 나간다 ③ [3-V] · [4] 에서 P0 후보가 나온다 ④ 법무 확인이 어긋남으로 나온다.

## §3 막는 장치 의뢰서 범위 · 회신 충돌

**준다 / 안 준다 = 3인 확인서 §2 표를 채택한다.** 아래 5곳만 고친다.

| # | 고칠 곳 | 왜 |
|---|---|---|
| 1 | 「뺀다」 표를 의뢰서에 옮겨 적지 않는다 → 「세부 설계 미제공」 한 줄 | 뺀 항목 목록이 곧 세부 설계의 목차다 |
| 2 | 🔴 질문을 「꼴을 적어 달라」 가 아니라 **「범주별로 있다 / 없다」** 로 묻는다 | 이 장치에 대한 좋은 회신은 곧 못 잡는 꼴의 예시다. **구체 회신은 드문 사고가 아니라 질문이 잘 먹힌 결과다.** 있다는 답을 받으면 구체화는 내부 [4] 가 로컬에서 한다 |
| 3 | 회신 표기 요청은 통제로 세지 않는다 | 부탁이다. 구속력이 없다. [5] 에는 「요청함」 까지만 적는다 |
| 4 | 🔴 공개 대응표의 근거 칸 | 지침 §1 · §8-1 #4 는 반박에 파일 · 줄을 요구한다. 근거가 제품 쪽이면 **대응표가 위치를 공개한다.** 3인이 다루지 않은 충돌이다. 대표 안건 3 에 함께 올린다 |
| 5 | [5] 표기 | 「[4-X] = 공개분 한정 · 로컬 세부는 내부 [4] 뿐」. 「외부 검증 완료」 로 넓히지 않는다 |

**회신 충돌의 실제 모양**

- 「3축 → 푸시」 순서는 **우리가 쓰는 글에만** 걸린다. 외부가 PR 댓글을 다는 순간 공개이고 우리 점검은 그 뒤다. 쟁점은 「보존 의무가 공개를 만드는가」 가 아니라 **「이미 공개된 것을 어떻게 다루나」** 다.
- 지침 §2-1 의 「전문 공개」 에는 예외 구조가 이미 있다 — 자격증명 · 토큰 · 고객 비밀정보까지 공개하라는 승인이 아니다. 제품 위치 · 재현 문장 · 못 잡는 꼴은 그 목록에 **없다.** 넣으면 예외가 늘고, 원문을 폴더 밖에 두는 일이 된다(「원문은 폴더로」). 그래서 PM · CTO 가 고를 수 없다.
- 한 가지 더. 지침 §2-1 은 「GPT 는 레포에 쓸 수 없다 · 왕복은 대화」 로 적혀 있어 지금 통로(PR 댓글)와 어긋난다. 안건 3 결정과 함께 본문을 맞춘다.

처리안은 §5 안건 3 ⓑ. 한계를 숨기지 않는다 — **가림은 회수가 아니다.** 내리기 전에 읽힌 것은 되돌리지 못한다. 그래서 본체는 위 2번(질문 설계)이고 가림은 뒷수습이다.

## §4 두 PR 순서 — 의뢰 SHA ≠ 머지 SHA

🔴 **기준부터 바꾼다.** 이 저장소의 머지 흐름(머지 커밋 · 스쿼시)에서는 머지 SHA 가 의뢰 SHA 와 같은 값이 될 수 없다. 「SHA 일치」 는 지킬 수 없는 기준이다. 재는 것은 **내용 일치**다.

> 합격선: `git diff {의뢰 SHA} {머지 직전 PR 머리} -- {막는 장치 코드 경로}` 0줄. 경로 = 3인 확인서 §3 「막는 장치 신규 · 수정」 묶음. 지시서 차이는 눈으로 본다.

**순서 = 막는 장치 먼저 · 설치 유무 뒤.** 🔴 근거는 기술 판단이다. 대표 원문은 「스케쥴표 대로」 이고, 「순서를 바꾸지 않는다」 는 PM 기록이며 머지 순서를 말하지 않는다. 3인의 「대표 결정대로」 를 그대로 옮기지 않는다.

| 단계 | 할 일 |
|---|---|
| 1 | 막는 장치 [3] 끝 → 3축 + 공개 범위 눈 대조 → PR 머리 푸시 → CI 초록 → **SHA 고정 · 의뢰 발행 · [4] 동시** |
| 2 | 의뢰 발행 ~ 막는 장치 머지 구간에 **겹침 두 파일을 고치는 머지 금지.** 설치 유무 PR 은 작업은 계속하되 머지하지 않는다 |
| 3 | 의뢰 뒤 더하는 문서는 코드 경로 밖으로만. 코드가 바뀌면 새 SHA + 차이 고정 링크로 의뢰를 갱신하고 대응표에 적는다 |
| 4 | 머지 직전 PR 머리 재확인 · 합격선 측정 · 결과를 [5] · 회의록에 적는다 |
| 5 | 머지 뒤 main 에서 전용 잡 1회 확인 |
| 6 | 설치 유무 재정렬 → **겹침 파일의 재정렬은 제외 건이 전부 흡수** → CI 재실행 · [4] 재측정 · 차이 재확인 → [5] → 머지 결재 · 배포 승인 |

- 음성 대조 런(상한 2회)은 재정렬 뒤에 쓴다. 앞에 쓰면 겹침 파일 변경으로 다시 재야 한다.
- 🔴 재정렬 뒤 설치 유무의 새 코드는 막는 장치 잡의 **첫 실전 대상**이 된다. 빨강이면 설치 유무를 고친다. 장치를 낮추지 않는다.
- 막는 장치가 지연되면 설치 유무도 같이 밀린다. 진행 / 대기는 §8-1 #6 대로 대표 판단이다. 대표가 앞지르기를 택하면 의뢰 전이어야 하고, 의뢰 뒤라면 의뢰 갱신이 따른다.

**안건에서 내린 것** — 약관 대조 법무 1건. 대표가 고를 것이 없다. PM 이 법무팀장을 불러 머지 결재 전에 닫고, 어긋남이 나올 때만 안건으로 올린다. 재심 조건 ④ 가 걸린다.
**새 안건이 아닌 것** — 설치 유무 4 · 5 · 6번은 이미 대기 중이다. 같은 보고에 다시 적되 답이 필요한 때를 나눈다.

**안건 2 추천 이유** — 대표 결정 1 이 이미 「필수」 다. 필수 설정은 새 일감이 아니라 정해진 단계를 해제 앞으로 옮기는 일이고, 왕복 실측은 어차피 머지 뒤다. ⓒ 는 공백이 끝나는 날이 없다. ⓑ 의 해제 순서: 머지 → main 잡 초록 → 필수 설정 재보고 · 결재 → **빨강 변이 PR 이 실제로 머지 못 하는 것 1회 실측** → 왕복 실측 → 해제. 설정만으로는 입증이 아니다. 늘어나는 일정은 ⚠️ 미측정.

**안건 3 ⓑ 절차** — 규칙은 미리 정하고, 들어오면 대표를 기다리지 않는다.
① 회신을 공개 문서로 옮기기 전에 멈춘다 ② **보안상무**가 구간을 판정한다(PM 아님). 대상 3범주뿐 — 제품 위치 · 재현 문장 · 못 잡는 꼴의 구체 예시 ③ 원문은 글자 그대로 로컬 보존 ④ 공개 원문본은 그 구간만 「가림 · 범주 · 판정자」 로 표시, 나머지 글자는 그대로 — **요약으로 바꾸지 않는다** ⑤ PR 댓글은 로컬 보존 뒤 내린다 ⑥ 회의록에 구간 수 · 범주 · 시각을 적고 같은 날 대표 보고 ⑦ 공개 대응표의 반박 근거는 장치 코드 파일 · 줄까지, 제품 쪽 근거는 로컬 대응표 + 공개본에 「근거 로컬 · 보안상무 대조」.

### 대표 보고 문안

> 대표님, 외부 검증 대상과 함께 결정 3건을 올립니다.
>
> **1. 외부 검증 대상**
> 막는 장치는 넣고 설치 유무 표시는 빼겠습니다.
> 위험이 낮아서 빼는 것이 아닙니다. 설치 유무는 머지하면 운영 배포 런이 뜨고, 본사 직원이 고객의 ERP 기동 시각을 처음 보게 됩니다. 그래도 빼는 까닭은 남은 쟁점이 「화면 표시가 실제 고객과 맞나」 이고, 이것은 코드를 읽어서 가릴 수 없기 때문입니다. 배포 뒤 대표님 눈 대조로 가립니다. 나머지는 내부 검증만 보고 나갑니다.
> ⓐ 이대로(추천) ⓑ 설치 유무도 외부 검증에 넣는다 — 의뢰 1건이 늘고, 두 건이 같은 파일을 고쳐 뒤 건은 의뢰를 다시 내야 합니다.
> 답이 필요한 때: 막는 장치 개발 착수 전.
>
> **2. ERP 게시 보류를 언제 풀까요**
> 막는 장치를 머지해도 그날은 막지 못합니다. 검사가 빨강이어도 머지 단추가 눌립니다. 필수 설정은 그 뒤에 따로 보고드리기로 했기 때문입니다. 지금 조건대로면 아직 막지 못하는 상태에서 보류가 풀릴 수 있습니다.
> ⓐ 조건 그대로 — 머지 + 테스트 PC 왕복 실측. 가장 빠릅니다. 설정 전까지 빨강 머지를 막는 것은 사람 눈뿐입니다.
> ⓑ 필수 설정까지 끝내고, 빨강 변경이 실제로 머지 못 하는 것을 1번 재 본 뒤 왕복 실측 후 해제(추천). 단계가 늘어납니다. 며칠인지는 아직 못 쟀습니다.
> ⓒ 조건은 그대로 두고, 설정 전까지 머지 결재 때마다 검사 결과를 적습니다. 일정은 그대로입니다. 공백이 끝나는 날이 없습니다.
> 답이 필요한 때: 막는 장치 최종 결재 올리기 전. 외부 회신 없이 머지하게 되면 「회신 없음 = 통과 아님」 으로 따로 적어 올립니다.
>
> **3. 외부 회신에 구체 내용이 공개로 달리면**
> 외부팀은 공개 PR 댓글로 답합니다. 댓글이 달리는 순간 공개이고 우리 점검은 그 뒤입니다. 장치가 못 잡는 예를 묻는 일이라 구체 내용이 올 수 있습니다. 범주로 써 달라고 묻되, 부탁일 뿐입니다.
> 대표님 규칙 두 개가 부딪힙니다. 「회신 원문 보존 · 전문 공개」 와 「세부는 로컬」 입니다.
> ⓐ 전문 공개 유지 — 규칙이 안 바뀝니다. 구체 내용이 공개로 남습니다.
> ⓑ 좁은 가림(추천) — 제품 위치 · 재현 문장 · 못 잡는 꼴의 예시 세 가지만. 원문은 글자 그대로 로컬에 두고, 공개본은 그 구간만 가렸다고 표시하고, 댓글은 내립니다. 판단은 보안상무가 하고 같은 날 보고드립니다. 내리기 전에 읽힌 것은 되돌리지 못합니다.
> ⓒ 이 건 회신만 비공개 통로로 — 공개 자체를 막습니다. 다만 10/30 에 정한 「대표 중간 전달 없음」 과 부딪혀 대표님 손이 다시 듭니다.
> 답이 필요한 때: 의뢰서를 내기 전.
>
> **기다리고 있는 답 3건 (설치 유무 4 · 5 · 6번)**
> 4번 「확인 불가」 는 개발 착수 전에, 5번 옛 설치본 · 6번 재설치 잔존은 배포 승인 전에 답이 필요합니다.
>
> **보고만** — 고객 기동 시각이 처음 본사 화면에 나오므로 약관 · 처리방침과 맞는지 법무팀장 확인 1건을 머지 전에 닫습니다. 어긋나면 그때 다시 올립니다.
> 두 건은 막는 장치를 먼저 머지합니다. 대표님이 머지 순서를 정하신 것은 아니고, 외부 의뢰 내용을 지키기 위한 기술 판단입니다.
