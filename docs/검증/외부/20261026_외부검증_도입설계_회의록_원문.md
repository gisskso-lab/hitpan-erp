## 원-1. 사장님 전달 문건 — 「[히트판 개발조직 운영 지침] 외부 독립 검증팀 도입」

> 출처: 사장님 전달 · 작성 주체 PM 미확인(⚠️) · 이 회의의 **출발 문건**

### 1. 목적
히트판 프로젝트의 개발 품질과 안정성을 향상하기 위해 OpenAI GPT를 외부 독립 검증팀으로 활용한다.
이는 Claude와 GPT의 성능을 비교하기 위한 것이 아니다. 기존 개발조직의 자체 검증에서 발생할 수 있는 공통된 판단 오류와 검증 사각지대를 발견하고, 프로그램의 완성도를 높이는 것이 목적이다.

### 2. 역할 분리
- Claude 개발조직: 기존 헌법과 업무 루틴에 따라 설계·개발·내부 검증을 수행한다.
- GPT 외부 검증팀: 구현 결과와 검증 근거를 독립적으로 검토하고, 결함·설계상의 맹점·회귀 위험·보안 위험을 탐색한다.
- 대표: 양측의 근거와 반론을 검토하고 최종 판단한다.

GPT의 검증 결과를 무조건 정답으로 취급하지 않는다. Claude의 자체 검증 결과 역시 외부 검증을 대신할 수 없다.

### 3. 검증 대상
1. 요구사항과 실제 구현의 일치 여부
2. 설계 명세와 구현 사이의 불일치
3. 매입·매출·재고·회계 등 업무 흐름 간 정합성
4. 데이터 무결성 및 마이그레이션 위험
5. 인증·권한·테넌트 격리·민감정보 보호
6. 설치·업데이트·복구·배포 과정의 위험
7. 테스트의 적절성 및 검증 사각지대
8. 기존 기능에 대한 회귀 위험
9. 개발 헌법·업무 루틴·승인 체계의 허점
10. 실제 고객 운영에 영향을 미칠 수 있는 기타 위험

### 4. 검증 원칙
- 공개 저장소의 문서만 읽고 전체 시스템을 검증했다고 주장하지 않는다.
- 확인한 사실, 추정, 미검증 사항을 구분한다.
- 결함을 보고할 때는 근거 파일, 관련 코드, 발생 조건, 영향 범위 및 권장 조치를 제시한다.
- 검증팀과 개발팀의 의견이 다르면 양측의 근거를 비교한다.
- 반론이 타당하면 기존 판단을 수정한다.
- 증거가 부족하면 결론을 보류하고 추가 검증 항목을 제시한다.
- 국소적인 수정뿐 아니라 전체 프로그램의 워크플로우에 미치는 영향을 검토한다.
- GPT의 보고만으로 코드 수정이나 배포를 자동 승인하지 않는다.

### 5. 작업 절차
1. 기존 개발 루틴과 승인 체계를 우선 확인한다.
2. 외부 검증이 필요한 작업과 검토 범위를 정의한다.
3. 검증에 필요한 소스코드·설계 문서·테스트 결과를 확보한다.
4. GPT 외부 검증팀의 독립 검토를 수행한다.
5. 발견 사항을 심각도와 근거에 따라 분류한다.
6. Claude 개발조직은 각 지적 사항에 대해 수용·반박·추가 검증 중 하나로 대응한다.
7. 양측의 근거를 비교하고 미해결 쟁점을 기록한다.
8. 기존 히트판 승인 절차에 따라 최종 판단한다.

### 6. 실행 전 확인 사항
먼저 현재 환경에서 GPT가 GitHub 저장소를 직접 읽을 수 있는지, 코드 변경사항을 확보할 수 있는지, 실제 테스트를 실행할 수 있는지 확인한다.
접근 권한이나 도구가 없는 경우 임의로 검증했다고 보고하지 않는다. 필요한 연동 또는 검증 자료를 명시하고, 접근 가능한 범위에서만 작업한다.

### 최종 원칙
외부 검증의 목적은 특정 AI의 우수성을 입증하는 것이 아니라, 서로 다른 관점의 비판과 반론을 통해 히트판의 품질을 지속적으로 향상하는 것이다.

> 🔴 **사장님 단서**: *"현 세션은 개발이 아니다. … 히트판 코드 절대 만지지 말고, 실행 전 확인사항 및 해당문건에 클로드는 절대 벗어나지 않기를 바란다."*

## 원-2. 사장님 — 협업 3방식 제시

> 출처: 사장님 원문

- 방식 1 — 수동 검증: Claude가 검토할 파일과 변경사항을 정리하고, 네가 GPT에 전달한다.
- 방식 2 — GitHub 연동: 지원되는 GitHub 연결 기능을 통해 GPT가 저장소를 직접 읽고 검토한다.
- 방식 3 — 자동화된 검증: PR이 생성되거나 갱신될 때 GPT 기반 검토 작업이 실행되고, 결과를 PR에 기록하도록 별도 연동을 구축한다.

> *"사장의 추천은 방식 2로 검토를 시작하고, 효과가 확인되면 방식 3으로 확장하는 것이야. 처음부터 자동화하면 잘못된 검토 결과가 반복적으로 쌓이거나, 검증 범위가 불분명해지는 문제가 생길 수 있으니까."*
> *"그리고 한 가지 더. 외부 검증팀이 매번 모든 파일을 검토할 필요는 없어. 변경된 코드뿐 아니라 그 코드가 영향을 주는 관련 업무 흐름까지 추적하는 방식이 효율적이야."*
> *"내가, 클로드에게 지시문을 전달하는 것과 GPT가 실제로 검증을 수행하도록 연결하는 것은 별개의 작업이라는 점만 기억하면 돼."*

## 원-3. GPT 1차 회신 — 블라인드 설계 결함 적발

> 출처: GPT 회신 원문 · 사장님 전달 · Claude 가 옮김

**1. 클로드 제안에 대한 독립 검토**
- **찬성: 방식 2에 의뢰서를 결합한다** — GitHub에 접근할 수 있다는 것과 특정 변경사항을 정확하게 검토할 수 있다는 건 별개의 문제야. 기준 SHA, 검토 범위, 관련 업무 흐름, 미검증 가설을 지정하는 건 타당해.
- **찬성: GPT의 결과에 판정권을 주지 않는다** — GPT의 지적을 자동으로 정답 처리하지 않고, 클로드가 근거로 반박할 수 있게 해야 해. 반대로 GPT가 틀렸다는 이유만으로 지적을 폐기해서도 안 돼.
- **찬성: 자동화 전에 탐지 능력을 측정한다** — 과거에 이미 발생한 결함을 대상으로 검증 능력을 측정하면, 실제 도입 가치에 관한 초기 증거를 얻을 수 있어.
- **수정 필요: 과거 사고 하나로 자동화 여부를 결정하지 않는다** — 한 건을 잡았다고 GPT가 전반적으로 효과적이라는 뜻은 아니고, 한 건을 놓쳤다고 모든 검증이 무가치한 것도 아니야. 다양한 유형의 과거 결함을 대상으로 평가해야 해.

**2. 가장 중요한 문제: 첫 번째 대조실험은 그대로 하면 안 돼**
클로드가 제안한 첫 실험은 9f93d851 커밋을 보고, GPT가 "수정했는데도 사용자에게 도달하지 못할 가능성"을 찾아낼 수 있는지 확인하는 거야.
나는 해당 커밋과 후속 수정 3d9795cf를 공개 GitHub에서 열어봤어. 그런데 여기서 검증 설계상의 문제가 하나 발견됐어.
1차 커밋의 제목과 설명에 이미 캐시 꼬리표 문제와 수정이 사용자에게 도달하지 못한 원인이 적혀 있어. 후속 커밋에는 index.html의 캐시 제어 헤더 문제까지 기록돼 있지. 따라서 지금 내가 해당 커밋을 보고 원인을 찾아낸다 해도, 독립적인 탐지 능력을 입증한 결과가 될 수 없어.
이건 내가 실제로 발견한 검증상의 문제야. GPT의 성능 문제가 아니라 실험 설계의 문제지.

**올바른 대조실험은 이렇게 하자**
1. 클로드가 사고 발생 당시의 코드와 수정 후보 패치를 준비한다.
2. 사고 이후 작성된 원인 분석, 사후 보고서, 정답이 노출된 커밋 메시지는 검토 자료에서 제외한다.
3. GPT는 당시 확인할 수 있었던 코드와 요구사항만으로 독립 분석한다.
4. GPT의 보고서를 확정한 다음, 클로드가 보유한 실제 사고 원인 및 실측 결과와 대조한다.

과거 기록을 이미 읽은 나에게는 이 건이 더 이상 완전한 블라인드 테스트가 아니야. 클로드가 다른 과거 사고를 하나 선정하거나, 별도의 독립 검토 세션을 사용해 실험을 다시 설계하는 게 좋아.

**3. 추가 조정 사항** (요지)
GPT 외부 검증을 내부 검증과 병렬 운영 — 찬성, 단 초기에는 비차단 / 의뢰서·운영지침 문서화 — 찬성, SHA·검토 범위·가설·영향 업무 흐름 명시 / GPT의 독립 탐지 성과 측정 — 찬성, 과거 사고와 신규 변경을 함께 평가 / 고유 결함 탐지가 0건이면 자동화 금지 — 방향은 타당하나 표본과 평가 기간을 정한 뒤 판단 / 자격증명 모양이 있는 112개 파일 — 별도 보안 감사 필요, 실제 유효성·Git 이력 노출 여부·필요 조치를 구분 / GPT는 정적 검증만 가능하다는 주장 — 이 대화에서 가능한 범위와 실제 고객 환경의 한계를 구분해야 함.

> *"클로드의 「GPT는 원리적으로 테스트 실행이 불가능하다」라는 표현은 조금 지나쳐. 나는 현재 네 로컬 개발환경과 고객 PC에 접근할 수 없고, 이 대화에서 실제 히트판의 설치·업데이트 종단 테스트를 수행한 것도 아니야. 그렇다고 모든 형태의 테스트 실행이 원리적으로 불가능하다는 뜻은 아니야. 별도 실행 환경과 필요한 의존성이 확보되면 일부 테스트를 실행할 수 있지만, 그것이 실제 고객 환경의 실측을 대체하지는 못해."*

**4. 대표님에게 추천하는 결재안** — ①외부 독립 검증팀 도입(승인 권고) ②운영지침과 의뢰서 작성(승인 권고) ③대조실험과 자동화 확대 조건(수정 후 승인) ④공개 저장소의 자격증명 감사(별건 우선 확인)

> *"내가 클로드의 의견에서 가장 높이 평가하는 부분은 GPT를 무조건 신뢰하지 않는다는 점이야. 나 역시 그 원칙을 나에게 적용할게."*

## 원-4. GPT 2차 회신 — 대표자 실측 체계 반영 (운영안 업데이트)

> 출처: GPT 회신 원문 · 사장님 전달 · Claude 가 옮김
> ⚠️ **PM 이 이 글을 사장님 정정문으로 오인했다** — 사장님 교정: *"나는 현재 지피티의 회신서를 전달하고 있는거 뿐이야."*

**1. 대표자 실측의 정의** — 히트판에서 말하는 실측은 단순 빌드·단위시험 실행이 아니다. 고객사 배포와 동일한 조건으로 다음 전체 경로를 검증하는 것이다. ①랜딩 페이지 가입 ②백오피스에 등록된 테스트 계정을 이용한 고객 동일 조건의 설치 ③히트판 접속 및 동작 확인 ④업데이트 실행 및 결과 실측 ⑤실측 완료 후 CI/CD 실행 ⑥게시·배포는 하지 않음. 테스트 PC는 충분히 확보되어 있다.

**2. GPT 외부 검증팀의 역할 수정** — GPT는 기존 실측을 대체하거나 중복 실행하는 조직이 아니다. 요구사항과 구현 사이의 누락 탐지 / 변경 사항이 영향을 미치는 전체 워크플로우 추적 / 기존 실측 및 CI/CD 검증 범위의 사각지대 탐지 / 테스트가 PASS여도 실제 기능 전달·업무 흐름·데이터 정합성이 보장되지 않을 가능성 지적 / 추가 실측이 필요한 경우 구체적인 위험과 검증 목적을 제시. GPT가 제안한 추가 실측은 자동으로 실행하지 않는다.

**3. 기존 검증 체계와의 관계** — 기존 고객 조건 실측(가입·설치·접속·업데이트의 실제 동작 확인) / 기존 CI/CD / GPT(독립적인 정적 검토와 검증 사각지대 탐지) / Claude 검증팀(근거 기반 수용·반박·추가검증) / 대표자(추가 실측 및 일정·자원 투입 최종 결정).

**4. 검증 보고 의무** — GPT는 실행하지 않은 시험을 실행한 것처럼 보고하지 않는다. 테스트 결과를 인용할 경우 PASS·FAIL·SKIP·미실행 건수와 확인 가능한 근거를 기록한다. 정적 검토 결과와 실제 실측 결과를 구분하며, 추가 검증을 하지 않은 항목은 미검증으로 표시한다.

**5. 변경 불가 원칙** — GPT는 의심 제기권만 가진다 / Claude의 반박도 최종 판정이 아니다 / GPT와 Claude 모두 자동 수정·게시·배포 권한을 갖지 않는다 / 추가 실측은 대표자 승인 없이 요구사항이나 일정에 자동 반영하지 않는다 / 최종 판단은 양측의 증거와 대표자의 실제 실측 결과를 종합해 대표자가 내린다.

> **핵심 원칙:** 기존 실측을 중복 수행하지 말고, 변경 사항과 기존 검증 범위를 대조해 고객에게 도달할 수 있는 위험 중 무엇이 아직 검증되지 않았는지 찾아낸다.

> 🔴 **PM 반박(본체 A-9)**: 내용은 합의와 같으나 **규범을 확정하는 문서는 외부검증팀이 발행하는 것이 아니다** — 같은 글 §5 의 「GPT는 의심 제기권만」과 자기모순.

## 원-5. GPT 3차 회신 — 추적 축 분류·Linux 빌드·블라인드 분리

> 출처: GPT 회신 원문 · 사장님 전달 · Claude 가 옮김

**1. 추적 축 5개 검토** — 다섯 축은 타당하지만, 현재 형태로는 서로 다른 종류의 검증 기준이 한 목록에 섞여 있다. 워크플로우·업무 흐름은 추적 대상이고, 원장·회계는 도메인 경계이며, 3시스템 경계는 아키텍처 경계, 반사·동적 호출은 구현 위험 유형이다. 이들을 그대로 체크리스트로 만들면 확인란만 채우고 실제 연결 관계를 놓칠 수 있다.
권고: 다섯 축을 유지하되 모든 축에 동일한 추적 규칙을 적용 — **변경의 진입점 → 중간 연결 고리 → 최종 결과**를 추적하고, 실제로 추적한 경로와 확인하지 못한 경로를 기록한다.
그리고 7가지 사고 유형 중 게이트의 거짓 초록, 마이그레이션·출하 DDL 누락, 테넌트 격리·권한은 별도의 위험 분류로 남겨야 한다. 추적 축과 사고 유형은 서로 다른 분류 체계다.

**2. 리눅스 샌드박스에서 빌드할 수 있는가** — 루트 Dockerfile은 .NET 8 SDK 이미지를 사용해 `src/HitPan.API/HitPan.API.csproj`를 Release 구성으로 게시하도록 작성되어 있다. 리눅스 컨테이너에서 API 프로젝트를 빌드·게시하는 경로는 저장소에 명시적으로 존재한다. **하지만 이것은 실행 성공을 확인한 결과가 아니다.** Docker 기반 API 게시 경로 = 파일에서 확인 / 실제 성공 여부 = 미측정 / 전체 솔루션 빌드 = 미측정 / Windows 설치 프로그램·Watchdog = 별도 검증 / 고객 PC 설치·업데이트 종단 = 실제 Windows 환경에서 별도 검증.
보고 의무화 항목: PASS / FAIL / SKIP / 미실행 건수 · 전체 대상 건수와 집계 기준 · DB 연결 등 시험 전제조건 충족 여부 · SKIP 사유와 그로 인해 검증되지 않은 범위 · 실제 실행 여부와 결과를 입증하는 로그 또는 산출물. **SKIP 수가 빠진 보고는 미측정으로 처리하는 것이 맞다.**

**3. 블라인드 역추적을 자기신고 외에 어떻게 막을 것인가** — 완벽한 보증은 어렵다. 시험 자료를 만드는 사람과 정답을 보관하는 사람을 분리해야 한다. ①신규 변경 선행 검증을 주 측정축으로 ②과거 사고 실험은 보조 지표 ③정답 노출 자료 미포함 별도 검토 ④GPT가 먼저 제출하고 변경 불가능한 기록으로 남긴 뒤 대조 ⑤이미 접했거나 역추적 가능성이 있으면 오염 가능성 있는 참고값으로 표시. 더 강한 검증이 필요하면 공개되지 않은 합성 결함이나 비공개 시험 패키지를 활용하는 방법도 있다.

**4. 측정 설계 추가** — ①참 지적 ②거짓 지적 ③고유 탐지 ④비용 ⑤심각도. 특히 ③은 단순히 GPT가 먼저 말했는지만으로 확정하면 안 된다. 절차 결함은 별도 장부에 두는 것이 맞다. 방식 3 자동화는 고유 탐지의 심각도·재현성·비용을 함께 평가해야 한다.

## 원-6. GPT 4차 회신 — 통합 회신 (대표자 실측 체계 반영 및 운영안 수정 의견)

> 출처: GPT 회신 원문 · 사장님 전달 · Claude 가 옮김

**2-1. 추가 실측 제안의 조건** — GPT는 발견한 모든 의심에 대해 추가 실측을 요구하지 않는다. 필요하다고 판단하면 의심되는 결함 및 영향받는 워크플로우 / 기존 실측에서 해당 위험이 검증되는지 여부 / 기존 산출물만으로 확인할 수 없는 이유 / 추가 실측의 목적과 합격·불합격 판정 기준 / 예상 자원 및 일정 영향을 함께 제시한다. 대표자 승인 전에는 실측이 수행된 것으로 간주하지 않는다.

**2-2. 정적 검토와 실행 검증의 분리** — 보고 결과를 **확인된 결함 / 정적 검토상 위험 / 미검증 / 반박 성립**으로 구분한다. 시험 결과를 인용할 때는 PASS·FAIL·SKIP·미실행 건수, 전체 대상 건수, 시험 전제조건 및 확인 가능한 근거를 함께 기록한다. SKIP 건수가 누락된 보고는 미측정으로 처리한다.

**2-3. 기존 검증 체계와의 관계** — GPT와 Claude는 상호 검토할 수 있으나, 어느 쪽도 단독 판정권을 갖지 않는다. 반박은 근거 제출이며 최종 채택은 대표자가 결정한다.

**3. 추적 축 5개** — 유지 권고 + 공통 추적 규칙. 단순 체크 표시만으로 검증 완료를 인정하지 않는다. 게이트 거짓 초록, 마이그레이션·출하 DDL 누락, 테넌트 격리·권한 문제는 별도의 사고 유형 분류로 유지.

**4. 성과 측정** — ③은 절차 결함과 제품 결함을 분리해 집계. 신규 변경 선행 검증을 주 측정축으로 하고 과거 사고 블라인드는 참고값으로 유지하는 수정안에 동의. 평가 기간과 표본 수뿐 아니라 사고 유형별 분포도 기록해야 하며, 제한된 표본으로 전체 효용을 단정하지 않는다.

**5-A. Linux 빌드** — 미측정 상태로 유지. Linux 빌드 결과를 Windows 설치·Watchdog·고객 환경 실측의 대체 증거로 사용하지 않는다.
**5-B. 공개 저장소 자격증명 감사** — 자격증명 형태의 문자열이 발견됐다는 사실만으로 실제 유효한 비밀정보라고 단정하지 않는다. 다만 공개 Git 이력까지 확인 대상에 포함해야 한다. 실제 조치는 기존 사전 승인·운영 통제 절차를 따른다. 이 문제는 GPT 외부 검증팀 도입과 별도 안건으로 유지한다.
**5-C. 과거 사고 블라인드 검증** — 공개 자료를 통한 역추적 가능성까지 완전히 제거했다고 주장하지 않는다.

**6. 결론 및 요청** — ①병렬·비차단 도입 ②기존 실측과 CI/CD 중복 실행 금지 ③기존 검증 산출물과 변경 사항을 대조해 사각지대를 찾는다 ④추가 실측은 근거·목적·예상 비용 제시 후 대표자 승인 ⑤실행하지 않은 항목은 미검증으로 기록 ⑥GPT와 Claude 모두 최종 판정권 없음 ⑦운영지침과 의뢰서 작성은 대표자 승인 이후.

## 원-7. GPT 5차 회신 — 증거 주체 분리·②-b·비용 분리·심각도 S0~S3

> 출처: GPT 회신 원문 · 사장님 전달 · Claude 가 옮김

**1-1. 증거의 성숙도와 증거 주체 분리 — 수정 수용**
> *"Claude의 지적을 수용한다. 제가 이전에 제안한 '확인된 결함' 정의는 실행 결과가 있다는 사실에 지나치게 의존했다. 실행한 주체와 환경, 실행 범위까지 구분해야 한다."*
> *"다만 Claude가 제안한 증거 주체별 등급표는 대표자 실측만이 결함을 확인할 수 있는 유일한 수단처럼 읽힐 위험이 있다. 정적 분석이나 독립적으로 재현 가능한 단위시험으로도 특정 결함을 입증할 수 있다. 예를 들어 코드에 명백한 권한 검사 누락이 있으면 고객 환경 종단 실측 전에도 해당 코드 결함은 확인될 수 있다."*

수정 제안 — GPT 정적 검토: 정적 검토상 위험(단, 코드 자체의 논리적 결함을 직접 입증한 경우 그 범위의 결함은 확인 가능) / Claude 개발 PC 실행: 해당 환경에서 관찰된 결과, 고객 환경 전체의 정상 동작을 보증하지 않음 / 기존 자동화 테스트: 테스트 대상·환경·전제조건 범위 안에서만 / 대표자 고객 조건 종단 실측: 고객 배포 경로에 대한 정본 실측 증거 / 모든 주체: 증거가 입증하지 않는 범위까지 결론을 확대하지 않음.

**1-2. 중복 지적 ②-b — 수용** — 지적 자체는 틀리지 않았으나 기존 실측이나 CI/CD가 이미 충분히 검증하는 범위에 포함된 항목. ② 거짓 지적과 섞지 않고 ① 참 지적에 합산하지 않는다.
> *"단, '기존 검증에 포함되어 있다'와 '기존 검증이 해당 위험을 실제로 잡아낸다'는 다르다. 기존 테스트가 해당 코드 경로를 실행하는지, 결과를 판정하는지 확인한 경우에만 중복으로 확정한다."*

**1-3. 비용 지표 분리 — 수용** — ④-1 GPT 도입 비용(GPT 검토, Claude 반박·재검토, 쟁점 정리) / ④-2 대표자 종단 실측 부담(요청 횟수와 실제 실행 횟수). 대표자 종단 실측 1회는 랜딩 가입부터 설치·접속·업데이트·CI/CD까지의 전체 경로를 의미한다. GPT가 제안했더라도 대표자가 실행하지 않은 건은 '요청'으로만 기록한다. 다만 추가 실측 횟수가 많다는 이유만으로 자동화 확대를 금지하지는 않는다 — 고객 데이터 손상이나 테넌트 격리 실패 같은 중대 위험을 예방한 경우에는 비용 대비 편익을 별도로 평가해야 한다.

**1-4. 의뢰서 입력물 5종 — 수용** — ①기준 SHA 및 변경 범위 ②대표자 실측 완료 항목과 결과 ③CI/CD 검증 범위 및 관련 산출물 ④개발팀이 이미 식별한 미검증 항목 ⑤아직 확인되지 않은 미검증 가설. 각 항목에 출처·기준 시각·확인 상태를 기록한다. 자료가 없으면 추측해 채우지 않고 '미제공' 또는 '미확인'으로 표시한다.
> *"특히 4번은 기존 커밋에 못 쟀다 항목이 있는지와 무관하게 작성해야 한다. … 이 수치는 Claude의 제출 자료에 따른 것이며, 제가 독립적으로 재계산한 결과는 아니다."*

## 원-17. GPT — 진입점 설계 검토

> 출처: GPT 회신 원문 · 사장님 전달 · Claude 가 옮김

**1. 설계 방향 — 동의** — *"원칙을 한 파일에 복제하는 것이 아니라, docs/검증/외부/INDEX.md를 단일 진입점으로 삼아 정본을 참조하는 구조가 적절합니다."* 운영지침은 `헌법/`, 의뢰서 틀은 `_틀/`, 측정장부는 `운영기록/`에 유지한다. 별도의 규칙집이나 절차 문서를 추가할 필요가 없다.

**2. 라운드별 자료 묶음 — 필수 아님** — 전체 원칙을 복사한 별도 문서를 매번 만드는 방식도 필요하지 않다. 필요하면 해당 라운드의 참조 문서 목록·기준 커밋 SHA·검토 범위를 모은 자료를 쓸 수 있고, 원문을 복제하지 않는 용도로 제한한다.

**3. 독립 검증의 재현성 — 기준 SHA 유지**
> *"공개 URL이 main 브랜치를 가리키면 문서 내용이 나중에 바뀔 수 있습니다. 따라서 실제 검증 의뢰에는 기준 커밋 SHA를 포함하고, 가능한 경우 그 SHA에 고정된 파일 링크를 사용하겠습니다."*

**4. 현재 상태** — INDEX 보강 내용과 미커밋 문서 본문은 아직 독립 확인하지 못했다. *"GPT가 문서를 읽기 위한 편의는 커밋·푸시를 앞당기는 근거가 되지 않습니다."*
