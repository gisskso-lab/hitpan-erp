## §4 [판정 ④] 실행기 이미지가 또 바뀌면 — 반복 위험과 막는 법

- **사실**: G1 은 같은 잡 안 두 단면(⑤ 와 M3 뒤)을 비교하므로, 이미지가 바뀌는 것만으로는 빨강이 안 된다. 빨강이 되는 것은 실행기(또는 서버 쪽 기능)가 **단계마다 바꾸는 새 이름**을 더할 때뿐이다.
- **고정 불가 한계**: GitHub 호스트 실행기는 `ubuntu-24.04` 라벨이 주마다 굴러가고 실행기 판 · 서버 쪽 기능은 우리가 못 묶는다. 자체 호스트 실행기는 「GitHub 서버 실측」 이라는 S4 전제를 바꾸므로 반려.
- **막는 법(장치 바이트 고침 없이)**
  1. 정상 대조군 → 심은 빨강을 같은 날 연달아 돌려 사이 변화 창을 줄인다.
  2. 결과 공유 댓글에 런 로그 머리(「Set up job」 의 실행기 판 · 이미지 판 · 프로비저너 판)를 옮겨 적는다 — 로그는 보존 기한이 지나면 사라지고 원자료 `run.json` 에는 실행기 판이 없다.
  3. 미리 정한 규칙: 실행기 단계별 이름 때문의 거짓 빨강이 **2회째** 나면 (가) 를 되풀이하지 않고 CTO 가 (다-2) 를 재판정한다(상한 · 재발행 비용 고리 끊기).
- **남는 위험(별건 · 중요)**: 이번 런은 G1 에서 멈춰 **G2~G5 는 GitHub 위에서 한 번도 안 돌았다.** 다음 런이 G2~G5 첫 실행이다. 이번 원자료 `m2-apt-history.txt` 에서 M2 가 올린 꾸러미는 mesa 셋뿐이고 node · git · bash 꾸러미 0 이라 G3 거짓 빨강 위험은 낮다고 본다 【가설】. G2(git 설정 출처) · G5(작업 나무)의 GitHub 첫 실행 결과는 미측정 — 또 빨강이면 §5 멈춤 ① 을 같은 방식으로 적용(즉석 봉합 0).
