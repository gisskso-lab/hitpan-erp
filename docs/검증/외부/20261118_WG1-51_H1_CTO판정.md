### §4-1 건별 근거

**① C2 구체화**
- ⑴ **앞 C2 의 구멍** — 설계 :242 「`/Encrypt` 글자 그대로 검사는 쓰지 않는다 — PDF 1.2+ 이름 문법상 `/Encr#79pt` 도 같은 이름」 은 맞다(스펙 7.3.5: 이름 안의 정규 글자는 `#` + 16진 두 자리로 써도 같은 이름). 해석기는 이름을 풀어서 비교하므로, 바이트 검사로는 「네이티브는 암호로 보는데 입구는 통과시키는」 꼴이 남는다. HQA ⑨ 「빠짐없이 식별한다는 독립 기준 없음」 도 바로 이 자리를 짚었다. 구체화는 같은 자리 · 관리 코드 · 새 의존 0 이므로 범위가 넓어진 것이 아니다.
- ⑵ **문법 대조** — 맞는 것: `#hh` 해독 · 잘못된 `#` 은 글자 그대로(해석기도 경고만 하고 글자 그대로 둠 · 정적) · 「풀린 이름 = `Encrypt`」 정확 일치(이름은 대소문자를 가린다 · `/encrypt` 는 다른 키라 해석기도 암호로 보지 않는다). **글자로 안 정해진 것(조건 1)**:
  - (가) **이름 끝** — 스펙의 끝 글자는 공백 6종(NUL · TAB · LF · FF · CR · SP)과 구분자 `()<>[]{}/%` 다. 공백만 끝으로 보면 값을 바로 사전으로 쓴 `/Encrypt<<…>>` 를 `Encrypt<<` 로 읽어서 놓친다.
  - (나) **끝 글자 `/` 를 먹는 구현** — 붙여 쓴 `/Type/XRef/Encrypt 5 0 R`(xref 흐름 사전에 흔한 꼴)에서 `/Encrypt` 를 놓친다.
  - (다) **16진 대·소문자** — `#6e` 와 `#6E` 는 같다. 그런데 E7 `/Encr#79pt` 는 숫자만 쓰므로 「대문자만 푸는」 결함을 잡지 못한다.
  - (라) **문맥 무시** — 「이름 토큰을 읽어」 를 주석 · 문자열을 건너뛰는 토크나이저로 구현하면, `(a%b) /Encrypt` 꼴에서 `%` 뒤를 줄 끝까지 건너뛰어 `/Encrypt` 를 못 본다. 그러니 문자열 · 흐름 · 주석 안까지 모든 `/` 바이트를 이름 시작 후보로 봐야 한다. 그 때문에 생기는 거짓 양성은 거절 쪽이라 받아들인다(:242 그대로).
- ⑶ **스펙상 선언 자리 논증(:243) — 선다.**
  - 증분 갱신: 덧붙인 xref · trailer 는 모두 파일 안 평문이라 파일 전체 검사가 모든 판을 덮는다. 옛 판의 trailer 까지 보지만, 그 결과는 과잉 거절 쪽뿐이다.
  - 혼합 참조(`/XRefStm`)와 선형화 첫쪽 trailer 도 평문이다.
  - 객체 흐름: 흐름은 객체 흐름에 들어갈 수 없으므로 xref 흐름은 늘 바깥에 있다. 암호 사전도 객체 흐름에 둘 수 없고(스펙 7.5.7), xref 흐름 사전은 압축 · 암호화 대상이 아니다.
  - → `/Encrypt` 키가 압축 자료 안에만 있는 꼴은 스펙상 없다.
  - 남는 것 = 망가진 파일 복구(해석기가 파일을 훑어 trailer 를 다시 세움) 같은 스펙 밖 관용. 설계 한계 ⒜ 와 같은 것이고, ㉡ 가 출구 쪽에서 받는다(②⑵).
- ⑷ **순서 ①~⑥ 의 우회 길 셋(조건 3 · 4)**
  - (가) **바꿔치기** — 묶음 입구가 파일 경로뿐이다(:225 S1). 검사한 파일과 네이티브가 여는 파일이 같다는 보장이 글자에 없다.
  - (나) **⑥ 이 「비었나 보기」 일 때** — 두 요청이 함께 ⑥ 을 지나면 동시에 둘이 해석된다 = h2 우회.
  - (다) **렌더 입구** — 「렌더는 정규화 사본만」(:241)은 원칙으로만 적혀 있고, ⓖ 는 TenantRoot 안 `.pdf` 면 통과시킨다. 양식이 격리 원본 · 처리 중 임시 원본 · 다른 기능이 만든 `.pdf` 를 가리키면 `UnderlayFile` 이 ①~⑥ 을 거치지 않고 네이티브로 연다.
- ⑸ **「판정 불능 = 거절」 이 정상 PDF 를 과잉 거절하나(#25)**
  - U 갈래로는 정상 PDF 가 걸리지 않는다. 올바른 PDF 에는 `trailer` 나 `/XRef` 가 반드시 있고, 20MB 를 훑는 데 15초 근처도 안 걸린다(U2 로 잰다).
  - 다만 사무 프로그램 PDF 저장이나 일부 복합기가 내는 흔한 꼴이 xref 흐름(P2)이다. 그런데 P2 는 지금 「E8 과 같은 길 · 못 만들면 미측정」(:252 · :254)이라, 과잉 거절이 가장 많이 날 꼴을 못 잴 수 있다 — 조건 7 이 닫는다.
  - 실제 과잉 거절의 주된 원천은 C2 가 아니라 앞서 정한 「권한 암호도 거절」(:241 ⓔ)이다. 공공기관 · 은행이 배포하는 양식 PDF 에는 권한 잠금이 흔하다. 정책은 그대로 두되, 직원이 혼자 다음 할 일을 알 수 있게 한다(조건 5).
  - 해독을 더해서 늘어나는 우연 일치(압축 자료 안 9바이트 꼴)는 무시할 수준이다.

**② 대안 ㉠ · ㉡ · ㉢**
- ⑴ **㉠ 반려** — 새 제품 의존(§8 :285)이 첫째 까닭이 아니다. 구조 해석은 trailer → xref 를 따라가므로 파일 전체 훑기보다 보는 범위가 좁다. 해석기는 망가진 파일을 훑어서 복구하기 때문에, 따라가는 검사는 해석기가 찾는 것을 놓칠 수 있다 — 놓치는 쪽으로 나빠진다. 놓침만 보면 훑기가 상위 집합이다. 직접 짠 해석기는 그 자체로 새 공격면이 된다.
- ⑵ **㉡ 채택(심층 방어)**
  - 해석기는 따로 지시하지 않으면 저장할 때 암호를 유지한다(정적 추론). 그러면 h4 가 스펙 밖 관용 때문에 놓친 파일은 정규화 사본도 암호 상태로 남고, **렌더할 때마다 네이티브가 암호 사본을 다시 연다**. 「자동 되풀이 0 · 렌더는 사본만」(:241)이 조용히 깨진다.
  - 같은 h4 함수로 사본을 한 번 더 보면 두 가지를 얻는다: 암호 사본 저장 0, 그리고 현장 경고 1줄. 이 경고로 설계 한계 ⒜ 가 처음으로 눈에 보이게 된다.
  - 「전 거절」 은 아니다(원본은 이미 한 번 해석된 뒤다). 설계에는 심층 방어로만 적는다.
  - 새 잡 0 — 심은 결함 ⓐ(h4 뺌) 잡이 곧 ㉡ 의 동작 증거 자리다. h4 가 빠지면 ㉡ 만 남기 때문이다.
- ⑶ **㉢ 채택(시험 쪽만) · 「유일한 길」 검토**
  - 원리상 유일하지는 않다. 시험 쪽에서 같은 묶음 해석기로 「비번 없이 열림 · 저장본에 암호 유지」 를 보는 길도 있다. 다만 저장 동작이 확인되지 않았고, 이 길로는 E8 · P2 를 만들지 못한다.
  - ㉢ 를 고르는 까닭은 E7 하나가 아니라 셋을 한 번에 닫기 때문이다:
    - (가) E7 계열 판정을 해석기 계열 자신이 한다. 위협 모델이 「네이티브가 암호로 보나」 이므로 가장 곧은 기준이다.
    - (나) E8 · P2 를 `--object-streams=generate` 로 만든다 — 지금 미측정 예정인 칸이다.
    - (다) 모든 행에 독립 기준 ⒞ 를 붙인다. `--is-encrypted` · `--requires-password` 종료 코드로 E1~E3(비번 필요)과 E4~E8(암호 · 비번 불요)을 가른다.
  - 바로잡을 글자: :243 ㉢ 「네이티브와 같은 해석기」 → CI 패키지 판은 묶음 판과 다를 수 있으므로 「같은 계열 · 판 기록」.
- ⑷ **런 상한**
  - Z 4 · 고침 6 · 합계 10 · R3 잡 11 · 심은 결함 17벌 그대로다(ⓐ · ⓑ 예상 사유 글자만 고친다).
  - 더해지는 것은 표본 행(E7a~c · 렌더 음성 1 · ㉡ 칸)과 잡 안의 단계(설치 · 표본 만들기)뿐이다 — 새 잡 0 · 새 런 0.
  - 설치 실패를 새 런으로 메우지 않는다(조건 7).
  - 앞서 열린 「`ui-browser.yml` matrix 수용」 확인 필요(작업지시서 §4-1)는 이 판정과 상관없이 그대로 남는다.

### §4-2 조건 (설계 고침 7차 · 재의뢰 SHA 에 함께 · 미반영이면 재의뢰 0)

1. **h4 이름 문법을 글자로**
   - 이름 시작 = 파일 안 모든 `/` 바이트(주석 · 문자열 · 흐름 안도 · 문맥 판별 0).
   - 끝 = 공백 6종 + 구분자 `()<>[]{}/%`. 끝 글자가 `/` 면 먹지 않고 다음 이름의 시작으로 본다.
   - `#` + 16진 두 자리(대 · 소문자 둘 다) = 그 바이트 · 잘못된 `#` = 글자 그대로.
   - 토큰을 끊은 **뒤** 해독하고, 풀린 바이트가 `Encrypt` 와 정확히 같으면(대소문자 가림) 거절.
   - ⑵ 근거에 한 줄 더함: 「증분 · 혼합(`/XRefStm`) · 선형화 첫쪽 trailer 는 모두 평문 · xref 흐름과 암호 사전은 객체 흐름에 못 들어감(스펙 7.5.7)」.
2. **E7 표본 넓힘(행만 · 잡 0)**
   - E7a 소문자 16진 `/E#6ecrypt` · E7b 전부 탈출 `/#45#6E#63#72#79#70#74` · E7c 붙여 쓴 이름 `/Type/XRef/Encrypt` 또는 trailer `/Foo/Bar/Encrypt`(E7c 는 ⓑ 결함에서도 거절되는 것이 정상).
   - E7 · E7a · E7b 는 만든 뒤 원시 바이트에 `/Encrypt` 부분 글자(`/EncryptMetadata` 포함)가 0 인지 확인한다. 있으면 그 표본은 무효다 — ⓑ 가 엉뚱한 사유로 거절하면 HQA ⑦ 기준상 검출이 아니다.
   - 심은 결함 ⓑ 예상 사유 = 「E7 · E7a · E7b 허용」 — 런 전에 고정.
3. **검사한 바이트 = 연 바이트 · ⑥ 원자적**
   - 올린 내용은 서버가 정한 이름의 임시 파일 1개에 쓰고 닫은 뒤에 ① 을 시작한다.
   - 네이티브가 끝날 때까지 그 파일의 내용 바꿈 · 이름 바꿈 0. h3 해시도 같은 바이트로 낸다.
   - ⑥ = 「비었나 보기」 가 아니라 **시도해서 차지**하는 것(실패하면 즉시 사람 말 거절). 네이티브가 끝날 때까지 쥐고 finally 에서 놓는다.
   - ⑦ 표지 생성 실패 = 판정 불능 = 거절.
4. **렌더 입구도 같은 문**
   - `UnderlayFile` 입력 = 정규화 사본 전용 폴더 · 서버가 만든 이름만.
   - 격리 원본 · 임시 원본 · 그 밖의 `.pdf`(TenantRoot 안이라도) = 바탕 0 · 오류 0 · 네이티브 0.
   - 음성 1행 측정(고침 R1 같은 잡 · 양성 대조 뒤).
5. **거절 말에 다음 할 일(#25)**
   - 잠긴 PDF 와 판정 불능 모두 「종이로 인쇄해 스캔하거나 그림으로 올려 주세요」 꼴의 대안을 함께 보여 준다.
   - 「암호화」 · 「Encrypt」 · 「판정 불능」 같은 개발 낱말 0(#23 점검과 함께).
   - 결과표에 과잉 거절 수(P4 · P2)를 따로 적는다.
6. **㉡ 정규화 사본 재검사**
   - 저장 뒤 같은 h4 함수로 사본을 본다. `Encrypt` 가 나오면 사본을 지우고 사람 말로 거절하며 경고 1줄(「입구 검사 누락 의심」 · 파일 해시)을 남긴다.

7. **㉢ 시험 쪽 qpdf 명령**

- **발행 전 보안상무 1줄 확인 = 필요** — 고침 7차가 조건 1~4 · 6 에 따라 보안 관문(h4 · ㉡ · 렌더 입구 · 표본) 줄을 다시 쓰므로, 작성자 ≠ 결재자를 한 번 더 지킨다. 범위 = 고친 줄이 이 조건과 맞는지 1줄 · PM 재결재 7차와 나란히 · 새 라운드 아님.
- **대표 발행 범위 재결재 = 불필요** — 재의뢰는 HQA 회신 6971724942 「이 PR에서 새 고정 SHA 재의뢰」 가 정한 같은 H1 의 연속이다. 같은 PR · 9문 · 범위 밖 · 기한 셈이 그대로면 앞 승인 범위 안이다. 재의뢰 댓글에 CTO 전결 1줄과 `20df5085..새 SHA` 바뀐 파일(설계 · 작업지시서 · 기록 문서뿐 · `src/` · `installer/` · `.github/` 0)을 적는다. 새 질문이나 범위 변경이 생기거나, 대표 결재 기록이 대상 SHA 를 글자로 묶어 두었다면(PM 확인) 대표에게 올린다.
