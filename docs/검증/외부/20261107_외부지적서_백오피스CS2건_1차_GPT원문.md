### ⓐ 인가·노출

- 새 counts/tenant와 목록은 클래스의 PlatformAdmin 정책 아래에 있고, 새 동작의 AllowAnonymous는 없었습니다. G-C-20도 메타데이터를 확인합니다. **정책 설정 자체 및 실제 HTTP 요청의 401/403을 시험한 증거는 아닙니다.**
- 새 숫자 입구는 빈/공백·36자 초과를 고정 오류 문구로 거부하고, 없는 고객사는 found=false/숫자 칸 없음, 존재하지만 쪽지 0인 고객사는 found=true/숫자 0으로 구분합니다. 새 응답 필드는 허용 설계와 대조했습니다.
- 두 거름 값은 Dapper 매개변수로 전달합니다. 목록 SQL에 더하는 것은 고정 조각이며 사용자 값을 SQL 글자로 이어 붙이지 않습니다.
- 이 변경에서 새로 추가한 원문 값 로그는 발견하지 못했습니다. 기존 전역 예외 처리/로그 경로 및 운영 오류 응답 전체를 검증한 것은 아닙니다.

### ⓑ 거름 정확성

- 기존 전체 StageCountSql은 바닥과 동일했습니다. 고객사 숫자는 같은 단계 CASE에 tenant_id=@TenantId를 더합니다. 목록도 같은 단계 우선순위 및 고객사 고유값 일치를 사용합니다. q가 함께 있으면 AND입니다.
- 목록의 빈/공백 tenant는 거름 없음, 새 숫자 입구의 빈 값은 400이라는 서로 다른 계약을 설계대로 구분했습니다.
- 주소 해석기의 상대 경로/앞 슬래시/대소문자, issue 제외, cs 질의, fragment 제거, query '+' 처리와 URL 해제를 코드 및 시험표로 대조했습니다.
- **추가 확인 경계:** 글자 주소 제외 비교는 URL 해제 *전*에 합니다. 예컨대 percent-encoded 글자 주소를 주면 해제된 글자 ‘issue’를 고객사값으로 반환하는 구조입니다. 실제 Blazor가 그 주소를 고정 화면으로 여는지, NavigationManager가 어떤 문자열을 넘기는지는 이번 범위에서 실행하지 못했습니다. 현재 화면 오동작 확정으로 세지 말고, 입력 정규화 계약/화면 경로와 내부 대조해 주십시오. 연속 슬래시도 RemoveEmptyEntries로 접히므로 같은 경계를 확인하면 됩니다.

### ⓒ 시험 실효 — 보강 후보 1건

**T1. 숫자 하위 질의만 '='에서 LIKE로 바꾸는 변이에 대한 빈틈(정적 후보)**

G-C-17의 %/_ 대조는 실제로는 회사명 존재 조회에서 먼저 found=false가 되어 숫자 하위 질의까지 가지 않습니다. 정상 시드는 GUID 모양 값이라, **존재 조회 '='는 그대로 두고 TenantStageCountSql만 LIKE로 바꾸면** 이 부분의 차이를 드러낼 값이 현재 새 시험에 없습니다. 현재 제품 SQL은 올바른 '='입니다. 현재 고객사 혼입이나 실제 결함을 발견했다는 뜻이 아닙니다.

HQA는 추출한 숫자 SELECT를 SQLite 메모리 DB와 가짜 값으로 보조 대조했습니다. 일반 GUID 값은 '='와 LIKE 변이 모두 total 1, 가짜 식별자 a_b 및 다른 값 acb를 함께 두면 '=' total 1 / LIKE total 3이었습니다. 이는 패턴 입력 대조군의 필요성을 보여 주는 **별도 SQL 모형**이며, 실제 MySQL/MariaDB·제품 C# 변이 시험이나 기존 시험 전체가 통과한다는 실행 증거가 아닙니다.

PM은 실제 식별자 허용 계약에 맞춰 ‘존재 조회를 지난 뒤 숫자 하위 질의에서 차이가 나는’ 대조군 또는 해당 변이 검사로 보강할지 판단해 주십시오. 현재 정책상 그 입력이 생성될 수 없다면 그 전제와 시험 보호 범위를 기록하면 됩니다.

기존 G-C-15/16의 상수 기반 시드·전체와의 차이·다른 고객사 증가 대조는 두 구현끼리만 비교하는 것보다 강한 검사입니다. CSBAR-5는 현재 형태의 @page 글자 목록을 찾는 정규식 검사이며 컴파일된 라우터 동작 전수 증거로 확대하지 마십시오. 숫자와 목록의 모든 q/mine/status 조합, 동시 변경 시점까지 실행 대조한 것은 아닙니다.
