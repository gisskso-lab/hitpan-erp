**판정 보류(P2).** 로그인 성공 뒤 이동을 요청했다는 표시와 목적 문서가 실제로 열린 상태를 구분할 수 없습니다. 목적 문서가 정상적으로 열리는 경로와, 이전 문서가 살아남는 경로를 나누어 판정했습니다.

| 질문 | 판정과 근거 |
|---|---|
| 1. 경합·안전망 | **P2.** Login.razor 502–630은 성공 후 NavigateTo를 호출하고 MarkNavigated를 설정하지만 성공 경로에서 정적 진행 표시를 해제하지 않습니다. 인증된 상태로 같은 런타임의 로그인 화면이 다시 초기화되면 251행에서 대기 화면을 켭니다. Next는 navigated를 시간보다 먼저 검사해 StandDown을 반환하고, WaitForInFlightLoginAsync는 대기 표시를 끄지 않고 돌아갑니다. 이 조건에서는 15초 뒤 홈으로 가지 않고 진행 막대와 비활성 버튼(28행)에 머뭅니다. 새 문서가 로드되어 런타임이 교체되거나 인증이 이미 해제된 경우에는 이 분기로 들어가지 않습니다. 취소·복원 캐시에서 조건이 실제 성립하는지는 미측정입니다. V3의 0초와 15초는 이동·입력 표시 전 Next가 호출되면 결과가 달라집니다. M3 성공은 측정한 순서에서의 일치만 지지합니다. |
| 2. 업데이트 안내 | 기존 성공·실패 호출 순서는 수용합니다. LoginUpdatePromptOrderGateTests 41–61은 성공 시 기억 지움과 방송을 각각 한 번 기록해 호출 순서를 비교하고 실패 시 둘 다 없음을 검사합니다. Major 팝업의 실제 Y/N 클릭까지 증명하는 시험은 아닙니다. |
| 3. approvalView | UserController 363–408은 서버 인증 문맥의 사용자·회사로 APPROVAL/view를 조회합니다. 실패 시 null이면 Sidebar 584–622에서 기존 조회를 시도하므로 서버 권한은 확대되지 않습니다. 다만 이때 서버가 거절하면 403 호출 자체는 남습니다. |
| 4. 대표 거름 | MainPcGate 143–175는 인증과 대표 여부를 먼저 확인한 뒤 확인 요청을 보냅니다. 직원 주체는 여기서 반환합니다. 같은 컴포넌트의 첫 렌더에서만 검사하므로 계정 전환 시 재생성 여부와 인증 상태 갱신 시점에 의존합니다. 이전 토큰이 남는 상황까지 해소됐다는 근거는 없습니다. |
| 5. 첫 화면 | 일반 직원의 판매·재무 조회 생략과 사용자용 오류 문구는 확인했습니다(Dashboard 471–481, 558–561, 620–637). 모든 실패가 안내 한 장으로 수렴하지는 않습니다. 권한 있는 사용자의 병렬 조회 두 개가 모두 실패하면 각 catch가 별도 안내를 낼 수 있고, 질문 3의 null 경로도 있습니다. 원 예외는 화면 문구 대신 로그에 기록합니다. |
