## §1 검증팀장 데이비드 박 — 조건부

### 막는 장치 = 대상. 단 문장 3곳이 사실과 어긋난다

| # | PM 안 문장 | 반증 | 고칠 문장 |
|---|---|---|---|
| V-1 | 「필수 검사가 머지를 막는 장치가 된다」 | 이 PR 은 필수 설정을 하지 않는다(지시서 §2 · 결재 기록 「뜻하지 않는 것」). 실측: 저장소 규칙 1개 · 활성 · 항목은 삭제 · 강제 푸시 · PR 3종이고 필수 상태 검사 없음 | 「잠재 심각도 P0 표기 건의 머지 차단 후보 · 신규 CI · ERP 게시 보류 해제 조건 ⓐ. 필수 설정은 이 PR 밖」 |
| V-2 | 「공개 레포에 머지되는 코드」 | §8-1 #2 · #6 = 푸시 → 의뢰 → [5]. 머지된 것을 보여 주면 [4-X] 가 [5] 뒤로 간다 | 「PR 머리에 푸시된 고정 SHA 의 코드 · 작업지시서」 |
| V-3 | 「정식 라운드로 일정을 늘리지 않는다」 | 지침 §2 일정 증가 0 은 맞다. 다만 대상이면 의뢰가 있어야 칸이 찬다 | 「의뢰는 [4] 와 동시 발행 · 미회신이면 칸에 「GPT 미회신」 · 진행/대기는 대표」 |

**PM 안이 놓친 것**
- 🔴 **해제 조건의 공백.** 게시 보류 해제 ⓐ 는 「막는 장치 머지」다. 머지 시점에는 아직 기계적으로 막지 않는다. [5] 상신에 「ⓐ 충족 = 머지까지 · 차단은 규칙 설정 뒤」를 적고 대표가 판단한다. 문구를 PM 이 넓히거나 좁히지 않는다.
- 🟡 **미회신 머지의 표기.** 「GPT 미회신」으로 머지하면 그것이 곧 해제 조건 충족이 된다. 「미회신 ≠ 통과」(§8-1 #6)를 상신본에 그대로 둔다.
- 🟡 **착수 순서.** 지시서 §0 은 「대상 결정 뒤 [3] 착수」다. 대표 결재까지 [3] 이 선다. 「일정 증가 0」과 부딪히므로 결재 요청 시점을 앞당기거나 PM 이 기다림을 명시한다.
- 🟡 **문서 불일치.** 두 지시서 머리는 결재 ⬜ · 진행 전부 ⬜ 인데 막는 장치 §0 은 🟢 PM 결재다. 설치 유무도 §9 는 PM 판정이 있다. 외부가 읽기 전에 맞춘다. §5 [4-X] 칸도 결정 뒤 갱신한다.
- 🟡 **두 PR 의 겹침.** 둘 다 `HitPan.Tests.csproj` · `build-and-test.yml` 을 고친다. 뒤 PR 은 재정렬이 생기고 의뢰 SHA ≠ 머지 SHA 가 된다. 머지 순서는 대표 결정대로 막는 장치 불변 · 재정렬 뒤 차이를 다시 확인한다.

**대조 — 안 걸린 것**: `deploy-ncp` 경로 필터 4개는 막는 장치 변경 경로와 겹치지 않는다(트리거 정의 기준). 머지로 운영 배포 런이 뜨지 않는다.

### 설치 유무 = 제외 동의. 외부 읽기로 더 얻을 것이 적다

- 잠재 P0 없음 · 제품 쓰기 0 · DDL 0 · 허용 밖 변경 0 (설계 §8).
- 🔴 남은 큰 위험은 **판정식이 실물과 맞는가**인데(설계 §10 ①), 공개 코드 읽기로는 답이 안 나온다. 유일한 실물 대조는 배포 뒤 대표 눈 대조다. 이것이 PM 사유보다 강한 제외 근거다.
- 사유 한 줄 — 형식은 충분하다(§8-1 #1). **내용이 모자란다.**

> 고칠 문장: 「본사 권한 화면 표시 · 읽기 전용 · 제품 쓰기 0 · DDL 0 · ERP · 설치 · 시리얼 · 고객 PC 무접촉 · 새 수집 0(저장된 값 1칸 첫 열람) · 잠재 P0 없음 · 머지는 운영 배포 런을 띄우므로 배포 승인 별도」

**제외 조건 (검증팀장)**
1. [5] 칸을 비우지 않는다 — 「[4-X] 제외 · 사유 · 대표 결재 위치」 (§8-1 #6).
2. 대표 상신 3건(지시서 §9 #1~#3)이 🔵 인 채로 제외를 확정하지 않는다. 「확인 불가」는 [3] 코드 분기라 착수 전에 답이 필요하다.
3. 🔴 **제외해도 지침 §9 는 걸린다.** 막는 장치 라운드가 열린 동안 설치 유무 머지로 뜬 배포 런은 「해당 변경과 무관해도」 전수 판정 대상이다. 라운드 기록에 함께 적는다. 11/2 조회 시점 `deploy-ncp` 최근 5런 전부 완료 · 대기 0(시점 값 · 머지 전 재조회).
