|---|---|
| 1. 계속·종료 경주 | 동일 물음에서는 Continue의 65초 미만 조건과 무응답 종료의 65초 이상 조건이 갈린다. 먼저 성공한 계속은 asked_at을 비우므로 후속 종료가 0행이 된다(Engine 262–311, 425–435). 다만 ‘놓침’ 종료에는 회사 설정을 다시 확인하는 조건이 없다(⑥). |
| 2. 근태·시각 | 자동 기록은 24시간 안의 최근 미퇴근 행을 잠그고, 출근 뒤 처음 오는 정시가 기준 순간보다 늦으면 시각을 비운다. 수동 UPDATE도 미퇴근 조건을 다시 검사한다(Engine 365–413, HrService 96–101). ⑥에서 잘못 선발된 세션도 이 기록 경로에 들어간다. 서버 PC 현지 시간대 변환(Engine 71–77)은 과거 근태 행의 시간대를 보존하지 않아 서버 시간대 변경 전후 정확성은 미검증이다. |
| 3. 권한·회사 | 팝업 신원은 서버 인증 문맥과 sid, 근태 수정·이력은 HR_PROXY/update와 HR/view, 좁은 설정은 TenantAdminOnly와 인증된 회사로 제한한다. Engine 285–311은 같은 거래에서 회사·sid로 잠근 행의 사용자와 sid로 토큰을 폐기한다. 해당 경로에서 타 회사 토큰 폐기 근거는 발견되지 않았다. |
| 4. 푸시 격리 | Hub 58–77이 인증 클레임 tenant_id·sid로 그룹을 구성하고 Pusher가 같은 키로 보낸다. NotificationClient의 연결 토큰 공급 시점 재조회가 최초 토큰 고정 문제를 방지한다. 연결 유지·만료가 겹친 실물 동작은 미측정이다. |
| 5. 주권·기록 | 세 이벤트의 본문은 남은 초, 종료 원인, 빈 본문이다(Pusher 48·65·82). 해당 전송은 고객 서버의 세션 그룹 대상이다. 로그에는 tenant·sid 및 일부 사용자·사원 식별자가 있고 접속기록에는 사용자·세션·user agent·종료 사유가 남는다(Engine 329–367). |
| 6. 기본 꺼짐·설정 저장 | **P1.** 최초부터 꺼진 회사는 Engine 106–111 조회에서 제외된다. 그러나 켜진 회사를 읽은 뒤 관리자가 끄기를 커밋하면 SettingsService 318–375가 PC의 asked_at과 snooze_until을 NULL로 만든다. 기존 주기는 이전 설정 시각으로 계속 진행한다. 로그인 시각이 그 전이고 5분이 지났다면 놓침 조회와 DELETE가 모두 참일 수 있다. DELETE는 설정의 현재 enabled·변경 시각을 확인하지 않는다. 결과는 세션 삭제·토큰 폐기·근태 기록이 같은 거래로 커밋될 수 있다는 것이다. 좁은 저장 자체는 다른 일반 설정 칸을 덮지 않는다. DB-132~134와 G-W13-7의 스키마 검사는 이 교차 순서를 다루지 않는다. |
| 7. 두 프로세스·재시작 | 같은 세션에 대한 묻기 UPDATE는 변경 1행일 때만 전송하고, 종료는 행 잠금 후 DELETE 성공자만 후속 쓰기를 한다. 주기 예외 기록과 교착 재시도가 있다. 이는 중복 쓰기를 줄이지만 설정 저장과 오래된 주기의 순서까지 직렬화하지 않는다. |
