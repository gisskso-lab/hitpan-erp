### Q1 — 🔴 (공개 출력 경로 P0 후보 1건, 안전성 미확정)

**[Q1-1] P0 — 탐지기 이름이 엔진 JSON에서 공개 `::error` 주석·잡 로그로 직행할 수 있는 길.**
- 위치: `scan.sh:122–125, 139–141` (보조 `:42–45`).
- 근거: **정적 확인**. `jq -r '.DetectorName // "unknown"'`으로 엔진 결과 JSON의 `DetectorName`을 읽어 문자열 제한 없이 `sort | uniq -c | awk`로 합친 뒤, `say_error "비밀 후보 찾음" "... 탐지기: ${detectors} ..."`에 그대로 넣습니다. 운영 기본값 `ANNOTATE=1`에서는 이 값이 `::error` 주석 및 잡 로그 본문으로 나갑니다. `SUMMARY_FILE`이 설정되면 `write_summary`의 `detectors`에도 들어갑니다(현재 workflow의 Scan 단계에는 SUMMARY_FILE 설정 없음). **실제 비밀값 유출은 확인하지 않았으며**, `DetectorName`에 민감문자열·줄바꿈·GitHub 명령 문법이 들어올 수 있는지 엔진 출력 스키마·공격 재현이 아직 없습니다. 그럼에도 엔진 유래 문자열이 무검증 공개되는 경로 자체는 존재합니다.
- **고칠 문안:** `DetectorName` 원문을 공개하지 말고 **사전 고정한 탐지기 코드/허용목록에만 매핑**해 집계하거나, 공개면은 탐지기 이름도 빼고 *총 건수만* 표시. 임의 JSON 필드·줄바꿈·제어문자·`::` 시퀀스가 공개 출력에 들어가지 않는지 **ANNOTATE=1** 포함 음성/양성 주입 시험. 원문은 임시 비공개 파일로만 보존. P0 후보이므로 안전성 반증 또는 수정 뒤 **동일 PR에서 고침 확인 1회** 요청.

**[Q1-2] P1(판독 강건성) — 결과 건수/깨끗 판정의 JSON 검증 부족.**
- 위치: `scan.sh:118, 122, 128–137`.
- 근거: **정적 추정**. 결과 건수는 `grep -c '^{' results.jsonl`로 셉니다. 엔진이 종료 0을 돌려주고 로그의 chunks가 양수인데 결과 JSON이 손상되거나 들여쓰기되어 `^{`로 시작하지 않으면 `count=0`으로 **깨끗**에 들어갈 수 있습니다. 현재 고정 엔진에서 실제로 발생했다는 증거는 없습니다. 비정상 결과 포맷을 정상 '0건'으로 오인하지 않는지 확인이 필요합니다. **실제 누락 재현 시 P0로 격상**.
- 고칠 문안: JSONL 전 줄의 구조/필수 필드를 엄격 파싱하고 파싱 실패·알 수 없는 출력은 **검사 오류(빨강)**. `rc=0/count=0`만으로 파서 유효성을 추정하지 말 것.

**[Q1-3] P1(이미 공개된 한계) — 오류 경로 주석 형식은 자체시험과 다름.**
- 위치: `self-test.sh:155, 242–246`, `scan.sh:31–37, 143–146`.
- 근거: **정적 확인**. S6(d)는 `ANNOTATE=0`에서 `[검사 오류]` 두 줄의 문구 일치를 확인합니다. 운영 `ANNOTATE=1`의 `::error title=검사 오류::...` 형식을 직접 검증하지 않습니다. 엔진 오류 원문을 찍는 옛 `msg` 경로는 현재 `scan.sh`에서 제거된 것을 확인했지만, 실제 오류/찾음 경로의 공개 주석 안전성은 미실측.
- 고칠 문안: `ANNOTATE=1`로 실제 `::error` 생성 및 출력 문자 허용범위를 별도 자체시험에 추가하고, 엔진 기록 유래 문자가 주석·로그·요약에 없음을 대조. 숫자 칸만 통과하는 기존 한계도 그대로 기록.
