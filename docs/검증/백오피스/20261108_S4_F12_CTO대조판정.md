## 1. 근본원인 반증 결과

### 1-1. 기록 대조 — 일치
- 지금 판(E_sweep_cur · 방향당 300 · Enter · 기다림 900): Esc keydown 9166 = 단추 → 첫 항목 focusin 9330(Esc 뒤 164ms = Esc 가 서버에 닿기 전에 이미 보내진 초점) → 래퍼 focus() ×2 10412 → focusout→null 10413 → 목록 제거 10415 → 단추 초점 호출 0 → BODY. PM §3 과 같은 꼴.
- 고침 A(E_sweep_A · 같은 조건): … 목록 제거 **10449** → 단추 focusin **10450**(`FocusActivatorAsync`). 「제거 다음 단추」 순서가 기록으로 서 있다.
- 기다림 0(E_sweep_A): 래퍼 focus() 3회는 있는데 **첫 항목 focus() 0회** — Esc 가 먼저 처리돼 L510 `Clear()` 가 L1023 길을 막은 증거.
- 틈 너비 ≈ 1 왕복(그려진 뒤 약 1~2 왕복) — Blazor Server 의 OnAfterRenderAsync 는 렌더 배치 수신 확인 뒤 돈다 → 그려짐 → 서버(+0.5) → 래퍼 초점(+0.5) → 결과(+0.5) → 첫 항목 초점 도착(+0.5) = 2 왕복. PM §3-1 · §4 와 맞다.

### 1-2. 순서 주장 — 성립 (조건 5개)
「늦은 첫 항목 초점(F1)」 은 **Esc 처리 전에 이미 보내졌거나, 아예 못 보내진다.** 그래서 A 의 닫기 렌더(R3)·단추 초점(B)보다 늘 먼저 도착한다.
- F1 이 Esc 처리 전에 나갔으면: R3·B 는 그 뒤(L511 Yield · L517 해제 왕복 · L525~526 · L553)에 나가므로 같은 연결 순서상 F1 → R3 → B.
- F1 이 Esc 처리 뒤에 나가려 하면: L1023 검사 시점에 `_menuItems` 가 비어(L510) 못 나간다. `_lastInteractionWasKeyboard` 를 다른 키가 다시 참으로 세워도(L1131) 항목 0 이라 막힌다. 검사·발송은 한 디스패처 안에서 끊김 없이 돈다(L1023~1026 → L1046~1063).
- 전제(하나라도 깨지면 다시 봐야 함):
  1. 회로 단일 디스패처(서버 코드 순차 실행)
  2. SignalR 한 연결 · 순서 보장
  3. 클라이언트가 렌더 배치·JS 호출을 받은 순서대로 동기 처리
  4. CloseMenuAsync 가 첫 await 전에 `_menuItems` 를 비운다 — **하위 메뉴가 없을 때만**(L501~505 의 await 은 열린 하위 메뉴가 있을 때만 생김) · CsStatusCell 은 하위 메뉴 0
  5. MudMenuItem 등록 = OnInitialized 뿐(MudMenuItem.razor.cs L171~174)
- 뒤집힐 수 있는 곳(지금 판에도 있는 위험 · A 가 만든 것 아님):
  - **회로 재연결** — 렌더 배치는 다시 보내지만 JS 호출(B)은 다시 안 보낸다 → BODY. 연결 끊김 시나리오로 따로 다룰 일.
  - **닫는 1 왕복 안에 부모가 다시 그려 새 MudMenuItem 이 생기고(옛 값 줄 생김·사라짐 등) + 키 입력** — 늦은 OnAfterRenderAsync 이어달리기가 지워진 요소에 FocusItemAsync → 초점 도둑이 아니라 서버 JSException 쪽. 원격 확률. 확인 필요: CS 목록이 주기 갱신(폴링·푸시)으로 Status·Channel 을 바꾸나.
  - 9.3 판 올림 · 하위 메뉴 도입 → 이 판정 무효, 재검.

### 1-3. 문서 정정 2건 (결론 영향 없음)
- PM §3 기록 `10554 focus() 첫 항목(이미 떨어져 나감)` — MudMenu 호출로 읽히지만, 목록 제거 직후 `before=BODY` 로 떨어진 요소에 거는 모양이라 **Blazor 렌더러가 렌더 배치 적용 뒤 하는 초점 복원 시도로 보인다(추정 · 확인 필요)**. 「단추로 돌려놓는 호출 0」 결론은 그대로.
- PM §5 「A 가 닫는 까닭」 의 「같은 회로 순서로 도착」 → 위 1-2 문장(보내졌거나 못 보내진다 · 전제 5개)으로 바꿔 적을 것. 「같은 순서」 만으로는 F1 이 B 보다 늦게 나갈 가능성을 못 막는다 — 막는 것은 L510 이다.

### 2-1. A 가 못 고치는 같은 뿌리 형제 (지금 판에도 있음 · A 판정과 별개)
- **틈 안 Enter/Space 재누름** — 9.3 ToggleMenuAsync(L653~654) → CloseMenuAsync(초점 복원 없음) → 늦은 F1 → 목록 제거 → BODY 예상. Esc 와 같은 증상.
- **틈 안 Tab** — 초점이 다음 칸으로 갔다가 늦은 F1 이 1번 줄 목록 안으로 끌고 간다(목록 열린 채).
- **키보드로 열고 바깥 클릭** — OnClosed=CloseMenuAsync → BODY.
- 뿌리 = 9.3 OnAfterRenderAsync 의 「래퍼 초점 왕복 뒤 첫 항목 초점」(L1020 → L1026). 근본 고침은 라이브러리 몫(PM 안 D · 범위 밖). HQA 가 다음 관문에서 이것을 밟으면 또 실패한다 → [4] 에서 미리 재 둔다.
