## §2 축별 판정

### 축 1 — 죽은 장치 방지 🔴

**(1-a) 🔴 P1-1 — `HITPAN_ISCC_EXPECT_VERSION` 이 비면 N4 단언이 통째로 사라진다. FAIL 도, 표식도 없다.**

`InstallerBootstrapMessageGateTests.cs:828` + `:833`

```csharp
string expectVer = Environment.GetEnvironmentVariable("HITPAN_ISCC_EXPECT_VERSION") ?? "";
...
if (expectVer.Length > 0
    && !IsSameInnoVersion(fileVer, expectVer)
    && !IsSameInnoVersion(prodVer, expectVer)
    && !vOut.Contains(expectVer, StringComparison.Ordinal))
    throw new XunitException(...);
```

`expectVer == ""` 이면 `&&` 가 첫 항에서 끊기고 **게이트는 그냥 초록**이다.
오타 1자(`HITPAN_ISCC_EXPECT_VERION`), env 블록 삭제, 잡 분리 — 어느 경우든 N4 는 **소리 없이** 없어진다.

이것이 심각한 이유는 **같은 파일·같은 워크플로에 이미 반대 사례가 있다**는 것이다:

| 축 | 없을 때 | 근거 |
|---|---|---|
| `HITPAN_REQUIRE_ISCC` | **FAIL** — "이 게이트는 스킵하지 않는다" | 테스트 `:789` |
| `HITPAN_GATE_SKIP_OK` | 잡 수준 **명시 선언** 패턴 | `build-and-test.yml:27` |
| `HITPAN_ISCC_EXPECT_VERSION` | **조용히 초록** · 선언 없음 | 본 PR |

`grep -rn "EXPECT_VERSION" src/` → **적중 1곳**(위 828줄). 존재를 단언하는 코드가 레포에 없다.
「게이트는 글자가 아니라 동작」 누적 26회 · 「`[SKIP]` 표시조차 없이 조용히 초록」(10/7 작10)의 **같은 모양**이다.

**(1-b) 🔴 P1-2 — 글자 대조 보조항이 음성 대조군 1번을 되열어 준다. 그리고 합성식에는 대조군이 없다.**

봉합은 글자 대조 `vOut.Contains(expectVer)` 를 "보조 경로"로 **남겼다**. 이건 OR 항이다 ⇒ **면죄부**가 된다.

| 입력 | `IsSameInnoVersion` | 게이트 합성식 |
|---|---|---|
| 판 자원 `6.7.10.0`, 배너에 판 **없음** | 막는다 ✔ | 막는다 ✔ |
| 판 자원 `6.7.10.0`, 배너가 `Inno Setup 6.7.10` | 막는다 ✔ | 🔴 **통과한다** (`"…6.7.10".Contains("6.7.1")` = true) |

즉 **음성 1(`6.7.10`)은 헬퍼에서만 막히고 게이트에서는 안 막힐 수 있다.**
오늘은 안 터진다 — 실측으로 ISCC 6.7.1 출력에 판 번호가 **아예 없기 때문**이다(§2 축6 참조).
위험은 미래 ISCC 가 판을 찍기 시작하는 순간이고, 그때 되살아나는 것이 **바로 이 봉합이 막겠다던 사고**다.

더 구조적인 문제: **대조군 `G_T6_5e` 는 `IsSameInnoVersion` 만 부른다**(`:1105~1120`).
게이트의 **실제 판정 지점은 4항 합성식**인데, 그 식에는 양성도 음성도 없다. 대조군이 지키는 것과
게이트가 쓰는 것이 다른 물건이다.

**(1-c) 🟢 `FileVersionInfo` 가 빈 문자열을 돌려줄 때** — 바르게 막힌다.
`vInfo.FileVersion ?? ""` → `IsSameInnoVersion` 첫 줄 `if (actual.Length == 0 ...) return false`.
FileVersion·ProductVersion **둘 다** 비어도 두 항이 false 가 되고, 남은 글자 항까지 실패하면 throw.
음성 대조군 3(`"" ↔ 6.7.1`)이 이 경로를 실제로 잰다. 판 자원 없는 바이너리의 조용한 초록은 **안 생긴다.**

### 축 2 — 게이트가 재는 것이 출하물인가 🔴

**(2-a) 🔴 P1-3 — `6.7.1` 이 네 곳에 흩어져 있다. 단일 진실원 없음.**

```
.github/workflows/build-and-test.yml:107   choco install innosetup --version=6.7.1   (시험본 설치)
.github/workflows/build-and-test.yml:114   HITPAN_ISCC_EXPECT_VERSION: "6.7.1"       (게이트 기대값)
.github/workflows/build-installer.yml:179  choco install innosetup ... --version=6.7.1  (출하)
.github/workflows/deploy-update.yml:581    choco install innosetup ... --version=6.7.1  (출하)
```

**그 자체로 결함이다.** 이유는 숫자가 흩어졌다는 것보다 더 나쁘다 —
게이트는 **같은 파일에서 설치한 판을 같은 파일의 기대값과 맞춰 본다.** 즉 **자기 일관성**을 단언한다.
N4 가 막겠다던 것은 「시험본 판 == **출하본** 판」인데, 출하본의 숫자는 게이트가 **읽지 않는 두 파일**에 있다.

한쪽만 올라갈 때 벌어지는 일:

| 사건 | 게이트 | 실제 |
|---|---|---|
| `build-installer.yml`·`deploy-update.yml` 만 6.7.3 으로 올림 | 🟢 **초록** (6.7.1 설치 → 6.7.1 기대) | 🔴 출하는 6.7.3 · 게이트는 **출하 안 하는 판**을 잼 ⇒ N4 무효 |
| `build-and-test.yml` 만 올림 | 🔴 빨강 | 출하 그대로 — 올바른 경보 |

⇒ **N4 가 진짜로 막아야 하는 방향(출하만 드리프트)에서 게이트는 초록이다.** 이 PR 이 만든 결함은 아니지만,
이 PR 이 "N4 를 지킨다"고 적으면서 넘어가는 지점이다.

**(2-b) 🔴 P1-4 — choco 핀이 핀이 아니다. 실측.**

run `37621671829` · 단계 `ISCC 설치 (… 출하와 같은 6.7.1)`:

```
InnoSetup v6.7.1 already installed.
 Use --force to reinstall, specify a version to install, or try upgrade.
Chocolatey installed 0/1 packages.
```

그리고 게이트가 실제로 집은 경로는 **러너 이미지에 원래 있던** `C:\Program Files (x86)\Inno Setup 6\ISCC.exe` 다.
⇒ 세 워크플로의 `--version=6.7.1` 은 **아무것도 설치하지 않았다.** 판을 정한 것은 choco 핀이 아니라
**windows-latest 이미지**다. 지금 우연히 일치한 것이다.

GitHub 이 이미지의 Inno 를 올리는 날: 출하(`build-installer`·`deploy-update`)도 같은 no-op 를 쓰므로
**조용히 새 판으로 굽는다**. 이 게이트는 빨개진다(그건 잘한다) — 그러나 그때 가장 손 쉬운 처방은
`HITPAN_ISCC_EXPECT_VERSION` 을 새 숫자로 올리는 것이고, 그러면 **드리프트 사건 자체가 덮인다.**

⚠️ **미측정**: 다른 판이 선재할 때 choco 가 6.7.1 로 **내려** 깔아 주는지는 재지 않았다.
이 PC 에 ISCC 설치는 #29 사전승인 대상이라 **시도하지 않았다.** 추정으로 적지 않는다.
