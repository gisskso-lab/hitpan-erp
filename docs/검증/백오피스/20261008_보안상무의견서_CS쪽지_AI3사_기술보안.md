## §2 축 A — 기술스택 판정: 🟡 조건부

### A-1 새 기술스택을 들여오는가 — 아니다 (확정)
- 두 설계서 모두 기존 스택 안이다: ASP.NET Core 8 · Blazor · MariaDB · Dapper · NCP. 3사(챗GPT·제미나이·클로드) 호출도 HttpClient 로 직접 HTTP — ERP 에 이미 같은 모양이 있다(`src/HitPan.Infrastructure/Services/AnthropicChatProvider.cs:69` `IChatCompletionProvider` — **키는 메서드 인자**(`CompleteAsync(string decryptedApiKey, ...)` :76) — 어댑터가 키를 안 품는 좋은 패턴. 설계서가 "본뜬다"고 한 것과 일치).
- 교정① 전제도 확정: `HitPan.Backoffice.csproj`·`HitPan.Backoffice.API.csproj` 둘 다 **ProjectReference 0건**(내가 직접 셈) — ERP 코드를 참조할 길 자체가 없다. "ERP 어댑터 재사용" 표현은 최신판 설계서에서 이미 폐기됐다(§6ⓑ "백오피스에 신설 · 패턴만 본뜬다"). 교정 4건과 어긋나는 문장 — **발견 0건**.
- ⚠️조건 1: 3사 연결을 각사 SDK(NuGet 패키지 3개)로 하면 그게 새 스택이다. 작업지시서에 **"SDK 금지 · HttpClient 직접"** 한 줄을 박아라(ERP 선례도 직접 HTTP).

### A-2 전송 길이 버티는가 — 길 선택은 맞고, 울타리가 없다
- 설계가 고른 길(HTTPS API + ERP 로컬 DB 큐 + 멱등키 + 재시도)은 이 스택에서 검증된 패턴이고, 버린 두 길의 버린 이유도 실측과 일치한다(확정):
  - `MetaPingClient`(Watchdog)는 실패하면 **버린다** — 핑에는 맞고 쪽지(고객이 쓴 글)에는 안 맞다.
  - `OutboxPollerWorker.cs:50·81` — 고객 PC 가 **백오피스 DB 에 직접 접속**하는 길. 재사용 금지 판정 타당. 🟢 안심 재료 하나: 그 연결문자열(`Outbox:BackofficeConnectionString`)은 레포 appsettings·출하 payload appsettings 에 **0건**(내가 셈) — 기본값은 "폴러 비활성". 단 **실물 고객 PC appsettings 는 ⚠️미확인**(설계서도 [1-V] 몫으로 남김 — 동의).
- 🔴 울타리 0건 (확정): `src/HitPan.Backoffice.API` 전체에 `RateLimit`/`AddRateLimiter` **0건** · `MaxRequestBodySize`/`RequestSizeLimit` **0건**. 지금도 익명 엔드포인트가 **18곳**(13개 컨트롤러)이다. 여기에 "본문을 실은 쓰기 API"(쪽지 수신)를 하나 더 열면, NCP 서버를 지키는 것은 운뿐이다. 쪽지 1만 건 난사·10MB 본문 1건 — 둘 다 지금 설계로는 못 막는다. **CS 설계서에 rate limit·크기 상한 줄이 없다 — 지적 1호.**
- 타임아웃·비용 폭주(3사): 설계가 이미 좋은 답을 품었다 — 호출 장부 `cs_ai_calls`(DECIMAL) · 티켓당 토큰 상한 · 하루 상한 · 4xx 는 재시도 금지("틀린 요청 3번 = 돈 3배") · 초안 비동기. 🟢. 버전 변화 위험은 1차에 외부 호출 0건이라 지금은 없음.

### A-3 1차 범위가 현실적인가 — 몸통은 맞고, 곁가지가 붙어 무겁다
- "송신·수신·화면·답 왔음 표시를 쪼개면 3개월 허공 재발" — 동의. 이 **왕복 한 묶음 + 금지필드 3문 + 멱등 + 동의 게이트 신설**까지가 1차의 몸통이다.
- 그러나 1차 표에는 내 응대함·전화 30초 틀·답 약속 시계·누리집 승격까지 얹혀 있다. 이건 왕복이 끊겨도 되는 **책상 기능**이다. 권고: **1차A(왕복+보안장치) → 1차B(책상 기능)** 로 순차 — 같은 사이클 안이면 되고, 한 작업지시서에 다 넣으면 갈래가 늘어 작8(CS0535 — 갈래별 0/0 ≠ 합류 0/0) 꼴이 재발한다.
- 메뉴 재구성 설계서는 규모가 작고(#1 보존 · 파일 5개) 현실적 🟢.

## §3 축 B — 보안: 안 되는 경우

### B-1 부모계정 파이프라인 인증 — 🔴 **열쇠가 설계서에 없다** (가장 큰 구멍)

CS 설계서는 "본사 인증 = 부모계정(테넌트) 신원"이라고만 쓰고 **그 신원을 무엇으로 증명하는지(시리얼? 토큰? 서명?)를 안 정했다.** 이대로 작업지시서로 가면 구현자가 임의로 정한다 — 가장 위험한 임의 결정이 된다.

**사장님 추가 지시 ②(3중 일치: 테넌트넘버·시리얼넘버·부모계정)가 답의 틀이다.** 그 틀로 실측·판정한다.

**(1) 지금 백오피스에 이미 있는 자물쇠 (확정 · 파일:줄)** — 쪽지 수신은 이 선례와 **같은 계열 자물쇠를 새 컨트롤러에 복제**하면 된다(기존 설치·시리얼 발급 코드는 **무접촉** — 지시 ①):
- 시리얼 대조: `SerialVerifyController.cs:49·83` — 클라이언트가 보낸 키를 서버가 HMAC(pepper) 해시 → `tenants.license_key_hash` + **`status='active'`** 대조. 실패는 지문 단위 잠금(`serial_verify_locks`) + INSERT ONLY 이력(`serial_verify_attempts`).
- 같은 식 2곳 더: `InstallerBootstrapController.cs:83~119`(정지·미승인 고객은 유효 키로도 401) · `TelemetryController.cs:107`.
- 더 센 선례 둘: `DeviceRegistrationController.cs:159`(검증 후 **발급 토큰**을 해시 보관 — 소유 증명) · `SerialSignatureService`(**ECDSA 서명 증표** — 발급은 `LandingPublicController.cs:263` 온보딩 때).

**(2) 3중 일치의 구멍 하나 (확정)**: 테넌트넘버(`tenant_id`)·시리얼(`license_key_hash`)은 백오피스 `tenants` 표에 있다(`installer/backoffice/00_backoffice_core.sql:104~`). 그런데 **부모계정(로그인 아이디) 컬럼은 백오피스에 0건**(grep 전수 — `owner_login`·`parent_account` 류 0). 세 번째 다리가 없다. 이것은 10/5 사장님 「백오피스는 대표 아이디·이메일을 반드시 수집」 지시와 한 몸 — **수집 경로 실측·확정이 쪽지 인증의 선결 과제**다.

**(3) 하나가 바뀔 때 쪽지가 끊기는가 (사장님 질문 그대로)**:
- **재설치**: 시리얼 그대로·기기 지문만 바뀜 — 선례는 지문을 잠금에만 쓰고 인증엔 안 쓰므로 안 끊긴다 🟢.
- **시리얼 재발급**: 해시가 바뀌는 순간 옛 시리얼의 ERP 는 401. 🔴 설계 §5 는 "4xx = `rejected` 종결"인데, 401/403 을 rejected 로 종결하면 **인증 갱신 한 번 늦었다고 고객이 쓴 쪽지가 죽는다.** 401/403 은 rejected 가 아니라 **「보류(재인증 대기)」** 상태로 멈추고, 재인증 후 자동 재송신해야 한다 — 설계 수정 필요.
- **부모계정 변경**: 3중 일치면 그 순간 전부 끊긴다. 변경이 백오피스에 전파되는 길이 설계에 없다 ⚠️ — 결재 올림(추-3).
- **공격자가 셋 중 하나만 알면**: 못 뚫린다 — 3중이 2중(현 Telemetry 는 시리얼 단독)보다 명백히 세다. 지지. 🔴 단 **셋 다 클라이언트가 payload 에 적어 보내는 "아는 값"이면**, 셋을 같이 턴 공격자(고객 PC 악성코드는 셋을 한 자리에서 턴다)에게는 1중과 같다. **최소 한 요소는 소유 증명**이어야 한다 — 위 선례 둘(발급 토큰 또는 ECDSA 증표)이 이미 있으니 새 발명 불요.
- **탈취되면 무엇이 가능한가**: 위장 송신(A사 명의 거짓 쪽지)보다 **답 Pull 이 더 아프다** — 답에는 상담원이 인용한 고객 문의 맥락이 실린다. 즉 자격증명 탈취 = **A사 CS 대화 열람**. 답 Pull 자격증명을 송신과 동급으로 둘지 더 세게 둘지 결재 올림(추-2). 테넌트 간 위장(A가 B 명의)은 3중 일치 + 멱등 `UNIQUE(tenant_id, uid)` 구조상 막힌다 🟢.

**(4) 시리얼 영구 보관(지시 ②)이 보안에 추가로 요구하는 것**:
- 폐기 시리얼 거부: 선례의 `status='active'` 조건(`InstallerBootstrapController.cs:119`)을 쪽지 수신에도 **복제 필수** — 해지·정지 고객의 시리얼로 쪽지가 들어오면 안 된다.
- 보관 암호화: 현 보관은 평문이 아니라 HMAC+pepper **해시**다 🟢. 보관을 이유로 **평문 시리얼 저장소를 새로 만들자는 설계가 나오면 반려** — 발급 대장(누구에게 언제)과 해시 대조면 "정상설치·잘 돌고 있나·과금 이슈" 판단에 충분하다.
- 🔴 충돌 발견 (확정): **테넌트 삭제 흐름이 시리얼 검증 이력을 지운다** — `TenantsAdminController.cs:240` `DELETE FROM serial_verify_attempts WHERE tenant_id=@Id`. 사장님 「발급 시리얼은 삭제하지 말고 보관」과 정면 충돌. 무접촉 전제이므로 내가 고치자는 게 아니다 — **보관 정책의 방침 결재로 올린다**(추-1).

### B-2 수신 API 공격면 — 🔴 조건 3개 전 착수 불가
1. **인증**: 익명 금지 — B-1 의 3중+소유증명. 익명 18곳에 19번째를 더하는 설계는 반려.
2. **rate limit·크기 상한**: A-2 실측 그대로 0건. 테넌트당 횟수 상한 + `MaxRequestBodySize`(쪽지 수신 경로) + 지문/IP 잠금(선례 `serial_verify_locks` 모양) — **1차 필수, 2차로 못 미룬다**(입구 열면 양이 2~3배 — 현장 ⚠️추정이지만 방어는 추정에 걸지 않는다).
3. **수신측 거부 기록 표 누락** (발견): §1 게이트②는 "화이트리스트 밖 payload → 거부 + **거부 로그 실존**"을 재는데, §1 테이블 목록에는 `bo_cs_tickets`(+2칸)·`bo_cs_ticket_logs` 뿐 — **백오피스 쪽 거부 로그 표가 없다**(ERP 쪽 DB-142 는 ERP 로컬). 게이트가 잴 대상이 설계에 없으면 그 게이트는 글자다. 표 1개(INSERT ONLY · 막힌 값 자체는 저장 안 함 — DB-142 와 같은 원칙) 추가 정의 필요.
- 멱등키 위조: `UNIQUE(tenant_id, client_ticket_uid)` — 남의 테넌트 티켓을 못 건드리는 모양 🟢. 자기 테넌트 안 uid 선점은 UUID 라 실효성 낮음 🟢.

### B-3 본사 데이터 최소주의(#18·#22) — 🟢 (결-5 조건부)
- 3문 검사(ERP 저장 전·송신 직전·백오피스 수신) + 자식계정 식별자는 화이트리스트 밖(보내는 쪽이 안 싣고 받는 쪽이 거부 — 2중) — 구조 타당 🟢.
- 선례의 빈틈을 설계가 알고 있는가 — 알고 있다: `MetaPingClient.cs:20-27` 금지필드는 **JSON 키 이름만** 본다. 자유 본문(결-5 ㉯)을 채택하면 **값 패턴 검사**(주민번호 등)가 3문 전부에 있어야 하고, 설계 게이트 ④⑤가 이를 동작으로 잰다 🟢. **보안 관점 한 줄**: ㉮(태그만)가 더 안전하다. ㉯를 고르시면 조건 = 패턴 검사 3문 + FAIL 게이트 **같은 커밋**(설계서 결-5 조건과 일치 — 지지).
- 잔여위험(막을 수 없는 것): 고객이 본문에 직원 이름·거래처명을 **제 손으로** 쓰는 것. R-8 고지 한 줄("담당 대리점과 본사 상담원이 봅니다")이 그 커버다 — 결-2(본사만 보기)를 법무 위탁 묶음과 같이 보는 설계 판단 지지.

### B-4 외부 AI 반출 — 🟡 (1차 0건이라 당장 위험 0 · 2차 조건 3개)

- 백오피스 DDL 실측 (설계서 ⚠️미확인을 내가 확정): `installer/backoffice/*.sql` 전수에 `bo_cs_*`·`bo_kb_*`·`bo_ai_export_consents` **전부 0건 — 없다. 전부 신설이 맞다.** 시드 0건 = 전 테넌트 닫힘으로 출발 🟢.
- 전역 스위치 금지 · 동의 임의 INSERT 금지 · 법무 4건 전 동의 수집 화면 선개발 금지 — 전부 설계에 있음 🟢. §8-5 정합: 1차 외부 호출 0건 ↔ 법무 열쇠 — 정합 🟢.
- 2차 조건 3개(작업지시서에 글자로): ① **외부 호출 단일 통로** — 3사 호출은 `CsAutoDraftService` 경유만, HttpClient 는 3사 도메인 고정(named client) — 게이트를 돌아가는 두 번째 호출 지점이 생기는 순간 fail-closed 는 거짓이 된다 ② `cs_ai_calls` 장부에 **본문·응답 원문 저장 금지**(토큰 수·비용·티켓ID만 — 장부가 제2의 데이터 저장소가 되는 사고 방지) ③ 누리집 승격 식별정보 제거의 강제 = 재스캔 API(화면 아닌 서버) + 승인본만 WHERE — 설계에 있음, **게이트에 "재스캔을 빼면 통과해 버림" 음성 대조군 포함** 확인 🟢.

### B-5 테넌트 격리 — 🟡
- 막혀 있는 길 (설계 확인): 초안 근거 = `bo_kb_docs` 승인본만(WHERE 절 — if 분기 금지) · 타 테넌트 **티켓 원문** 근거 저장 금지 · 대리점 `reseller_id` 는 토큰에서만(#2 동원리) · 승격 초안이 tenant_id·상호를 SELECT 자체를 안 함 🟢.
- 남은 길 1 (메뉴 설계서 쪽 — 이 사이클의 실질 위험): 본사 페이지 대부분이 맨 `[Authorize]` 이고 실 방어는 API `[BoPermission]` 인데 **대리점 토큰을 실제 거부하는지 미실측**(메뉴 설계서 §1-5 스스로 인정). 메뉴 재배치로 대리점 로그인 동선이 생기는 바로 그 사이클이다 — **게이트 ⓐ(G-1c)를 [3] 착수 전 선실측**으로 당겨라. 뚫려 있으면 메뉴 숨김은 가림막일 뿐이다. §6-4 의 `PlatformOnlyV2` 6개 파일 추가는 지지, §9-④(tenants·signups 도 잠금)는 **(가) 잠근다** 에 한 표.
- 남은 길 2: 「본사만 보기」(결-2) 전에는 대리점이 자기 고객 티켓 전문을 본다 — 설계가 법무와 묶은 것 타당. 다만 1차 출발 때 **대리점 화면은 자기 `reseller_id` 범위 밖 0건**을 게이트 ③이 재므로 A사↔B사 간은 막힌다 🟢.

### B-6 5중 검증(#23) — 🟡 (좋다 · 2개 모자람)
- 두 설계서 모두 게이트가 동작+음성 대조군이다(멱등 UNIQUE 빼면 2건 · 검사 빼면 통과 · 게이트 빼면 호출이 나감 · 메뉴 G-1c 본사 계정 200 대조 · G-3 소요시간 판별) — 26번 사고 교훈이 글자가 아니라 구조로 들어왔다. CI `db-gate` 초록만 증거 조항도 있음 🟢.
- 모자란 것: ① **남용 게이트 0건** — "같은 테넌트가 1분에 100건 → 상한 거부 + 기록" · "본문 상한 초과 → 413" FAIL 게이트 추가 ② "대리점 토큰으로 CS 설정(§4) 변경 시도 → 거부" 게이트 추가. 외부 노출 금지어(#23)는 결-8(히트판 도우미)로 설계가 이미 올림 🟢.

## §5 1차 착수 전 반드시 고칠 것 (번호)

1. **수신 인증 구체화**(설계서에 글자로): 3중 일치(tenant_id + 시리얼 해시 대조 + 부모계정 증표) + 최소 1요소는 소유증명(발급 토큰 `DeviceRegistrationController.cs:159` 또는 ECDSA 증표 `SerialSignatureService` 선례 — 새 발명 금지) + `status='active'` 조건 복제. 기존 설치·발급 코드는 무접촉 — 새 CS 컨트롤러에 같은 모양만.
2. **부모계정 식별자의 백오피스 수집 경로** 실측·확정(10/5 지시와 한 몸) — [1-V] 선행.
3. **수신 API 울타리**: 테넌트당 rate limit + 본문 크기 상한 + 실패 잠금(선례 `serial_verify_locks` 모양) — 1차 필수.
4. **백오피스 수신측 거부 로그 표** 1개 정의(INSERT ONLY · 막힌 값 저장 안 함).
5. **송신 워커 401/403 처리 수정**: rejected 종결 금지 → 「재인증 대기」 보류 + 재인증 후 자동 재송신(시리얼 재발급·부모계정 변경 때 고객 글이 죽는 길 차단).
6. **게이트 ⓐ 선실측**(대리점 토큰 → 본사 admin API 401/403 + 본사 계정 200 대조군) — 메뉴 재배치 [3] 착수 전.
7. **남용 FAIL 게이트 2개** 추가(§3 B-6) + (결-5 ㉯ 채택 시) 본문 값 패턴 검사 3문 + FAIL 게이트 같은 커밋.

**2차로 미뤄도 되는 것**: 3사 연결 전부(법무 열쇠 — 설계대로) · 외부 호출 단일 통로·장부(코드가 2차니 조건도 2차) · 교차확인 · CS 현황 · 내 응대함·전화 틀·약속 시계(1차B — 왕복 뒤 순차).
