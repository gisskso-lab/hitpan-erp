# 병렬이슈 PI-13 — 장비넘버는 위조·복사가 가능하다. 그리고 UNIQUE 를 풀면 동시 로그인이 줄을 두 개 만든다

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시 병렬검증 · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 §4-3 ② (장비넘버 단독 조회) · §4-4 |
| 등급 | 🟠 **P1** — 과소·과다 계수 양방향. 설계에 방어가 없다 |
| 상태 | ⬜ 미봉합 |

---

## 1. 무엇이 문제인가 — 두 갈래

### (A) 장비넘버 **단독** 조회(②)가 위조에 무방비다

명세서 §4-3 이 조회 순서 ②를 **"장비넘버 단독 — 인증 전 기기"** 로 정했다.
🔴 **②에는 아무 증명도 없다.** 값이 맞기만 하면 그 줄을 연다.

### (B) 지문 UNIQUE 를 풀면 **중복 INSERT 를 막는 것이 사라진다**

PI-09 에서 지적한 `UNIQUE(tenant_id, fingerprint)` 는 지금 **의도치 않게
동시 로그인 경합을 막아주는 유일한 장치**다. 설계가 지문을 열쇠에서 내리면서
이 방어가 같이 사라지는데, **대체물이 설계에 없다.**

---

## 2. 근거 (실측)

### (A) 장비넘버는 localStorage 평문이다

`src/HitPan.Web/wwwroot/js/device-fingerprint.js:234-243`
```javascript
getDeviceId: function () {
    try { return localStorage.getItem('hitpan_device_id'); }
    ...
setDeviceId: function (id) {
    try { if (id) localStorage.setItem('hitpan_device_id', id); }
```

- 브라우저 개발자도구에서 **읽기·쓰기 자유**
- `setDeviceId` 가 **JS 전역으로 노출**돼 있어 콘솔 한 줄이면 바뀐다
- 값은 `Guid.NewGuid()` 라 추측은 어렵지만, **복사는 쉽다**

⇒ 명세서 §4-1 원칙 *"기기는 서버가 준 이름표를 들고 온다"* 는 맞다.
그러나 **그 이름표가 남의 것인지 확인하는 절차가 ②에 없다.**

### (B) INSERT 에 경합 방어가 없다

`TenantDeviceService.cs:298-323` — 조회(`:141`) 후 판단하고 `:299` 에서 INSERT.
🔴 **조회와 INSERT 사이에 잠금이 없다.** 트랜잭션도 없다.

지금 이것이 사고가 안 나는 이유는 **오직 DDL 의 UNIQUE 때문이다**:
`installer/hitpan_db_clean.sql:3748` — `UNIQUE KEY uq_tenant_fp (tenant_id, fingerprint)`

같은 기기에서 두 요청이 동시에 오면 둘 다 "없다" 로 판단하고 둘 다 INSERT 를 시도하지만,
**두 번째가 UNIQUE 위반으로 튕긴다** ⇒ 줄은 하나만 남는다.

---

## 3. 이게 터지면 무슨 일이 나는가

### (A-1) 남의 장비넘버를 넣으면 — 과소 계수(요금 누수)

직원이 승인받은 동료의 장비넘버를 콘솔로 복사해 넣는다.
- ② 가 그 줄을 찾는다 → **기존 기기로 인정** → 새 슬롯 안 생김
- 🔴 **기기 2대가 슬롯 1개.** 한도를 우회하는 방법이 된다

⚠️ 게이트에 이 시험이 **없다**(PI-08 과 같은 구멍 — G-1~G-10 전부 "합쳐지면 정답" 방향).

### (A-2) 🔴 테넌트 격리는 **뚫리지 않는다** — 반증의 반증

*"남의 회사 장비넘버를 넣으면?"* 을 실측으로 따져봤다.

`TenantDeviceService.cs:141-148` · `:479-497` · `DeviceAuthMiddleware.cs:107-112`
**전부 `WHERE tenant_id = @TenantId` 가 들어 있다.** 그리고 그 `tenantId` 는
JWT 로 로그인한 결과에서 온다(`AuthController.cs:99` — `response.TenantId`).

⇒ **다른 회사의 장비넘버를 넣어도 조회에 안 걸린다.** ④ 신규 등록으로 갈 뿐이다.
🔴 **헌법 #2 위반은 없다. 이 설계는 tenant_id 를 파라미터로 받지 않는다** — 명세서 §11 의 주장은 사실이다.

**위조 위험은 "같은 회사 안" 으로 한정된다.** 이것이 이 이슈를 P0 가 아닌 P1 으로 두는 이유다.

### (B) UNIQUE 를 풀면 — 과다 계수(고객 손해)

PI-09 권고대로 지문을 별도 표로 빼거나 UNIQUE 를 제거하면:
- 같은 기기에서 **탭 두 개로 동시 로그인** → 조회 둘 다 "없다" → **INSERT 두 번 성공**
- 🔴 **한 기기가 슬롯 2개.** I-1 · I-2 정면 위반

⚠️ 이것은 **드문 일이 아니다.** 로그인 화면을 두 탭에 띄워두고 둘 다 누르는 것은 흔하다.
게다가 명세서 §6 이 *"새 창마다 슬롯"* 을 **원인 미상**으로 남겨뒀다(§10-3).
🔴 **원인이 바로 이 경합일 가능성이 있는데, 설계는 그것을 확인하지 않은 채
그 방어막(UNIQUE)을 걷어내려 한다.**

---

## 4. 어떻게 고쳐야 하나

### (1) ② 장비넘버 단독 경로에 **조건을 건다**

②의 목적은 *"인증 전 기기"* 를 잡는 것이다. 그렇다면 **인증 전 상태로 한정**한다:
```
WHERE tenant_id=@T AND device_id=@Did AND auth_key_hash IS NULL
```
🔴 **이미 인증키를 발급받은 줄은 ②로 열리지 않게 한다.**
인증된 기기는 ①(장비넘버+인증키)로만 열린다.

⇒ 이러면 (A-1) 위조가 **인증 안 된 줄에만** 통한다. 그 줄은 어차피 슬롯을 쓰고 있고,
훔쳐봐야 승인 대기 상태를 물려받을 뿐 이득이 없다.

### (2) UNIQUE 를 **없애지 말고 대상만 바꾼다**

PI-09 권고(지문 별도 표)를 따르되, `tenant_devices` 에 새 유일성을 반드시 만든다:
- 장비넘버가 PK 이므로 **같은 장비넘버로는 두 줄이 안 생긴다** — ①② 경로는 자동 방어
- 🔴 **④ 신규 등록 경로**가 문제다. 여기는 매번 새 `Guid` 라 유일성이 안 걸린다

⇒ **④에 잠금을 건다**: 트랜잭션 + `INSERT ... ON DUPLICATE KEY UPDATE`,
또는 **지문 표에 UNIQUE 를 걸고 그 위반을 "기존 기기 발견" 으로 해석**한다.
후자가 낫다 — 지금 굴러가는 방식과 같고, 실패가 아니라 **정상 경로**가 된다.

### (3) 게이트 신설

| 게이트 | 검사 |
|---|---|
| **G-13** | 같은 기기에서 **동시 로그인 2건** → **1줄이어야 통과.** 2줄이면 FAIL |
| **G-14** | 남의 장비넘버를 심고 로그인 → **2줄이어야 통과** (합쳐지면 FAIL) |
| **G-15** | 다른 회사 장비넘버를 심고 로그인 → 신규 등록. **남의 줄에 안 붙는다**(헌법 #2 회귀 방어) |

⚠️ G-13 은 **P3 착수 전에 현행 코드로 먼저 돌려본다.**
🔴 **"새 창마다 슬롯"(§10-3 미결)의 원인이 여기면, P0 실측에서 바로 잡힌다.**
작지서 P0 이 *"재현되면 원인, 안 되면 재현 안 됨으로 기록"* 이라고만 했는데,
**무엇을 의심해서 어떻게 재현할지**가 없다. 이 가설을 P0 대본에 넣는 것을 권고한다.

## 5. 등급 판정 근거

**P1** — 이유:
1. (A) 위조는 **같은 회사 안으로 한정**된다 — 테넌트 격리는 실측상 뚫리지 않는다
2. (B) 경합은 **아직 안 터진다** — 현행 UNIQUE 가 막고 있다. 단 **설계가 그것을 걷어내려 한다**
3. 🔴 **P3 착수 시점에 P0 로 승격된다.** 지금 설계에 방어를 넣으면 0원이다
4. §10-3 미결(새 창마다 슬롯)의 **검증 가능한 가설**을 제공한다 — P0 에서 즉시 확인 가능
