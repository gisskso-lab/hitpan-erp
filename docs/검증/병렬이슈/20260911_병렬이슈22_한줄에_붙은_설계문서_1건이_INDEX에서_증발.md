## 1. 무엇이 잘못됐나

`docs/설계/erp/INDEX.md` 원본(HEAD, 줄이기 전) 27번째 **물리줄**에는 표 행이 **2개** 이어붙어 있었다 — 앞 행("20260821_설계_근태축_경비통합_옵션모듈화.md")이 `| 2026-08-21 |` 로 끝나자마자 **줄바꿈 없이** 바로 다음 행("20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md")이 시작된다:

```
...⚠️U1 옵션 문구만 미확정 | 2026-08-21 || **[20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md](...)** 🆕🟢 | 🟢 **결재 범위 확정 — 사장님 오더 12항**. ...| 2026-08-21 |
```

개발명세서 §3 은 원본의 표 모양 이상 3종(칸 늘어난 줄·두 줄에 걸친 줄·빈 줄 뒤 머리 없는 줄)을 문서화했지만, **"한 물리줄에 표 행 2개가 붙어있는 경우"는 그 3종에 없다.** 그 결과 스크립트는 이 물리줄 전체를 행 1개로만 처리했고, 뒤에 붙은 두 번째 행("그룹웨어결재_범위확정") 은 **현재 `docs/설계/erp/INDEX.md` 어디에도 없다** — 링크도, 제목도, 흔적도 없다.

## 2. 재현 (node 로 원본·현재본 직접 대조)

```
docs/설계/erp/INDEX.md        (현재) 에서 grep "그룹웨어결재_범위확정_ERP분리_회계기표" → 0건
docs/설계/erp/INDEX_원본상세_20260911_이력.md 에서 같은 grep → 1건 (원문 보존)
docs/설계/erp/20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md → 실재하는 문서 파일 (삭제 안 됨)
```

전체 5개 원본을 "한 물리줄에 문서링크 시작 패턴이 2개 이상"인 줄로 재스캔 — **5개 파일 전체에서 이 1줄(설계/erp 27번째 줄)만 걸린다.** 다른 4개 파일·설계/erp 의 다른 모든 줄에는 이 패턴이 없다(1회성 사고로 추정 — 원본 자체가 과거 어느 시점 편집 때 줄바꿈이 빠진 것으로 보이며, 이번 작2 스크립트가 만든 게 아니라 **원본에 이미 있던 결함을 스크립트가 못 알아챈 것**).

## 3. 왜 위험한가

- 이 문서("결재 범위 확정 — 사장님 오더 12항")는 내용상 가볍지 않다 — ERP/그룹웨어 결재 분리 설계의 근거 문서인데, INDEX 에서 찾을 방법이 없어지면 다음 세션이 "이 설계가 있었는지도 모르고" 다시 조사하거나 다른 문서와 중복 판단할 위험이 있다.
- 더 중요한 것은 **안전장치 두 겹이 전부 이 사고를 놓쳤다는 사실**이다 — ①구현자 스크립트의 자체 안전장치("첫 칸 링크 목록이 순서까지 다르면 중단")도, ②이번 독립검증이 처음 돌린 자동 대조 스크립트(첫 칸 링크 44=44 순서까지 일치)도 **둘 다 통과라고 답했다.** 원인은 같다 — 두 스크립트 모두 "물리줄 = 표 행 1개"를 전제로 파싱했기 때문에, 사라진 행은 애초에 **양쪽 모두에서 카운트에 들어가지도 않았다**(44 는 사실 45 여야 한다). 자동 대조가 초록불이어도 "혹시 놓친 게 있는지" 원본과 나란히 읽는 반증 없이는 못 잡는 사고 — [[feedback_gate_must_test_behavior]] 동형.

## 4. 봉합 방향 (적발만, 코드는 안 고침)

- `docs/설계/erp/INDEX.md` 에 "20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md" 행을 되살린다 — 이력 파일(`INDEX_원본상세_20260911_이력.md`)에 원문이 그대로 있으므로 그 문구를 같은 60자 규칙으로 잘라 추가하면 된다(위치는 "20260821_설계_근태축..." 행 바로 다음, 원본 순서 기준).
- 재발 방지: `idx-diet.js` 의 행 경계 인식을 "줄 시작이 `|` 인가" 대신 "`| YYYY-MM-DD |` 로 행이 끝난 지점 뒤에 같은 줄에서 또 표 행이 시작되는가"도 같이 본다(이번 5개 파일 재스캔에서 쓴 방법과 동일).
- 봉합 후 같은 방식(원본·현재본 문서링크 목록 전수 대조 + "물리줄당 링크 1개" 전수 스캔)으로 5개 파일 전체 재확인.

## 6. P2 부수 발견 — 이력 파일 3개가 EOL 기준으로는 "바이트 동일"이 아니다

작업지시서 §5 검증 방법은 "이력 파일 본문 = 원본 바이트 동일"을 요구한다. 5개 중 3개(`docs/설계/erp/`·`docs/검증/erp/`·`docs/개발/erp/` 의 `INDEX_원본상세_20260911_이력.md`)는 본문(머리 6줄 제외)을 CRLF 로 저장했고, HEAD 원본은 LF 다 — 텍스트 내용은 개행문자 차이를 빼면 100% 동일(node `Buffer.compare` 로 확인)하지만 **줄 끝(EOL) 까지 포함한 바이트 비교는 이 3개에서 실패**한다. 같은 3개 파일은 현재 `INDEX.md` 자체도 CRLF 로 저장돼 있다(나머지 2개 파일·이력은 LF 유지 — 스크립트가 파일마다 다르게 동작).

- 리스크는 낮다 — 이 저장소는 `core.autocrlf=true` 라 커밋 시 CRLF→LF 로 자동 정규화된다(`git hash-object` 로 확인: 디스크 63,831B → 커밋될 blob 63,769B, 그 안에서 CRLF 정규화 후 HEAD 원본과 완전 동일). 즉 **커밋 이후에는 이 불일치가 자연히 사라질 가능성이 높다.**
- 그래도 지금 작업트리 상태가 작업지시서 §5 문구("바이트 동일")를 문자 그대로 만족 못 하고, 5개 파일이 서로 다른 EOL 정책을 쓰는 것 자체가 스크립트 동작의 일관성 결함이라 기록해 둔다. 봉합 필수는 아님(커밋 전 3개 파일을 LF 로 재저장하면 완전 해소) — PM 판단.

**PM 판단 (2026-09-11)**: 재저장하지 않는다. 스크립트는 파일마다 **작업트리 원본의 줄 끝을 그대로** 따랐다 — 줄이기 전 실측(`idx-survey.js`)에서 설계/erp · 검증/erp · 개발/erp 는 원래 CRLF, 병렬이슈 · 검증은 원래 LF 였다. 이력 본문은 **줄이기 직전 작업트리 파일과 바이트 동일**하고, HEAD 가 LF 인 건 `core.autocrlf=true` 가 저장소에 LF 로 넣기 때문이다. 위 검증팀 실측(정규화 후 5/5 동일 · `git hash-object` 대조)대로 커밋하면 LF 로 들어가 HEAD 원본과 같아진다.
