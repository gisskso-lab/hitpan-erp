## 0. 한 줄

**봉합 코드는 맞다. 그런데 그 코드가 `origin/main` 에 없어서, 지금 게시를 실행하면 옛 워크플로가 돌아 EXE 없이 success 로 끝난다.**

## 1. 사장님 질문에서 출발

> "왜 랜딩에서 표기되는 다운로드 버젼이랑 실제 설치파일 버젼이 다른거야?? / 다르면 안되지"

**버전은 다르지 않았다.** 랜딩이 표시하는 `1.2.41` 이 맞고, manifest 도 `1.2.41` 이다.
다른 것은 버전이 아니라 **확장자·게시 유무**였다.

| 서버에 있는 것 | 랜딩이 찾는 것 |
|---|---|
| `packages/hitpan-1.2.41.zip` (자동업데이트) → **200** | `packages/HitPan-ERP-Setup-1.2.41.exe` → **404** |

같은 1.2.41 인데 ZIP 만 올라가고 EXE 는 아무도 올리지 않았다.

## 2. 실측 (추측 0)

### 2-1. 전 버전 404 — 처음부터 하나도 없었다

```
packages/hitpan-1.2.41.zip                → 200   (자동업데이트, 정상)
packages/HitPan-ERP-Setup-1.2.41.exe      → 404   (랜딩이 찾는 것)
packages/HitPan-ERP-Setup-1.2.40.exe      → 404
packages/HitPan-ERP-Setup-1.2.39.exe      → 404
packages/HitPan-ERP-Setup-1.2.34.exe      → 404
packages/HitPanInstaller-1.2.41.exe       → 404   (빌드 산출물 실제 이름)
packages/hitpan-1.2.41.exe                → 404
```

이름을 바꿔 찔러봐도 전부 404 = **파일명 문제가 아니라 게시 자체가 없다.**
작3 §1-2 의 선행 결론(1.2.29~1.2.41 전부 404, 한 번도 작동한 적 없음)을 독립 재확인했다.

### 2-2. manifest 는 정상 — 랜딩 연동도 의도대로 작동 중

```json
{ "version": "1.2.41", "channel": "Major",
  "downloadUrl": ".../packages/hitpan-1.2.41.zip",
  "signature": "MEQCID...", "kid": "upd-v1" }
```
`manifest.json` = **200**, 서명·kid 정상. 7/21 에 넣은 "랜딩은 무조건 최신" manifest 연동은
**결함이 아니다.** 랜딩은 manifest 의 `version` 만 읽어 파일명을 조립한다
(`DownloadPage.razor:140-141`) — 그 조립 대상 EXE 가 존재하지 않았을 뿐이다.

### 2-3. ⭐ 진짜 막힌 지점 — 봉합이 main 에 없다

| 항목 | 값 |
|---|---|
| EXE 게시 배선 커밋 `bf26a01` | 2026-07-30 **11:45:25** KST |
| 마지막 `deploy-update` 성공 run `30503805843` | 2026-07-30 **09:48** KST, sha `649ed88` |
| `origin/main` 현재 | `649ed88` (7/28 19:18) |
| `bf26a01` → `origin/main` 포함? | **NO** |
| `origin/main:deploy-update.yml` 의 EXE 스텝 | **0건** |

**게시 실행이 봉합보다 약 2시간 앞선다.** 그 run 이 쓴 워크플로에는 EXE 빌드 스텝이 아예
없었으므로 ZIP 만 올리고 잡 2개 모두 success 로 끝났다.
**실패한 게 아니라, EXE 를 만들 스텝이 없는 버전이 돈 것이다.**

> ⚠️ **여기가 이번 이슈의 급소다.** run 결과가 `success` 라서 "게시 성공"으로 읽힌다.
> 그 상태로 다시 dispatch 하면 **또 success 로 끝나고 404 는 그대로다.** 승인만 기다렸다면
> 같은 바퀴를 한 번 더 돌았다.

### 2-4. 배선 자체는 종단까지 정상 (PR #14 head 기준)

`bf26a01` 의 `deploy-update.yml` 검증 — EXE 관련 스텝 11건 존재:

- `Download dependency bundle` — 번들 5종 + `hitpan_db.sql`, 8개 사전 확인 (`:256-265`)
- `Scan installer-only payload for secrets` — **EXE 전용 동봉물 게이트** (검증팀 [3-V] D3 봉합, `:274-283`)
- ISCC 컴파일 (`:344`)
- **파일명 정합 검증** — `$expect = "HitPan-ERP-Setup-$ver.exe"` (`:357-358`)
- NCP 전송 — 래퍼가 zip 버전에서 `/tmp/HitPan-ERP-Setup-<VER>.exe` 유도 (`:500-503`)

**랜딩이 찾는 파일명과 빌드·게시 파일명이 정확히 일치한다.** 코드에 고칠 것은 없다.

> `deploy-update` 는 `production` environment 승인벽(reviewer = 사장님, 폰 1탭).
> 자동승인 분류기가 PM 의 원격 admin 머지를 차단한다(종전 확인).

1. **PR #14 머지** — 1인 승인벽 우회 절차(종전 PR #3 과 동일):
   `main Ruleset 잠깐 Disabled → gh pr merge 14 --admin → 즉시 Active 복구`
2. **`deploy-update` dispatch + 폰 승인** — 이때 비로소 EXE 가 게시된다.
3. **실측 게이트** — 아래가 200 이어야 봉합 완료:

4. 그다음 사장님 오더대로 **고객 경로 그대로 실측** — 랜딩 → 가입 → 다운로드 → 설치.

## 6. 남은 개선사항 (별건 — 이번 범위 아님)

**랜딩이 파일명을 조립하는 구조 자체가 이 사고의 근본이다.** 지금은 ①안(버전별 EXE,
사장님 결재·구현 완료)을 유지하되, 아래를 별건으로 남긴다.

- 랜딩이 `Release:InstallerUrl` 고정 주소를 쓰게 하면 버전 조립이 사라져 같은 계열 사고가 구조적으로 불가.
- ⚠️ 단 **manifest 에 `installerUrl` 필드를 추가하는 방식은 채택하면 안 된다.**
  서명 대상은 `version·channel·url·sha256·size·migration` 6개 필드뿐이다
  (`UpdateManifestSigning.BuildSigningPayload`). 필드 추가는 서명을 깨지 않지만(안전),
  **서명 밖 필드는 위조 가능**하다. 랜딩이 그걸 신뢰하면 feed 장악 시 최초 설치 EXE 를
  공격자 서버에서 받는 경로가 열린다 — 설치 EXE 는 SYSTEM 권한으로 MariaDB·.NET 을 설치한다.
  주소는 반드시 **우리 설정값**에서 와야 한다.

## 7. 교훈

1. **`success` 는 게이트가 아니다.** 스텝이 없는 워크플로는 할 일을 안 하고도 성공한다.
   "무엇을 했는가"를 산출물 실측으로 확인해야 한다.
2. **봉합 커밋 시각 vs 실행 시각을 대조하라.** 코드에 봉합이 보이면 "됐다"고 읽기 쉽다.
   그 봉합이 **실행된 브랜치에 있었는지**가 별개 질문이다.
3. **선택지를 새로 만들기 전에 기존 결재를 찾아라.** PM 은 A/B 두 안을 제시했으나
   작3 에 사장님 ①안 결재가 이미 있었다. 같은 날 같은 사안에 결재가 갈릴 뻔했다
   (헌법 #37 계열 — 뒤 결재가 앞 작업을 덮음). **결재 이력 조회가 제안보다 먼저다.**
