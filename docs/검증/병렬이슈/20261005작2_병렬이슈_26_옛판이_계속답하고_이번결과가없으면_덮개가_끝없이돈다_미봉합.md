## 무엇이
- 판 = from 이고 상태 `Last` 가 이번 결과(rollback·To=to·신선·refused/reverted/broken)가 아니면 J-7 `Waiting`(`RollbackWatch.cs:105-113`).
- 10분 뒤 `Stalled` → 본문 「히트판은 계속 되돌리기를 진행하고 있습니다」 → [다시 확인] → `CheckOnceAsync` 도 판 = from 이면 `Waiting` → **새 10분**(`RollbackProgressOverlay.razor:140-153`). 판이 from 인 한 `Other`(J-8)로도 안 빠진다.
- 덮개에는 닫기·돌아가기 버튼이 없다 ⇒ 이 순환을 끝낼 길이 사용자에게 없다(F5·탭 닫기뿐 · 설계는 F5 를 권하지 않는다).

## 이 상태에 들어가는 길(셋)
1. **받기(세 번째 길) 중 터널 깜빡임** — 화면 받기 폴링이 `IsHitpanDown(r.Status)` 로 넓어졌다(`LocalRollbackPage.razor` 폴링 갈래 · 이전 `== 0` → 이제 502·503·504·520~530 포함). 받는 동안 히트판은 안 멈추므로 이 때의 502 는 교체가 아니라 회선 깜빡임이다 → `BeginWatch()` → 그 뒤 받기가 거절(`PreviousPackageFetch.Refuse` — **메모리 단계만** 바꾸고 `Last` 는 안 쓴다)되면 J-6 이 볼 것이 없다.
2. **D-1 「받기 진행 사라짐」** — 서버가 교체가 아닌 이유(충돌·워치독 재기동)로 다시 떠도 같은 `BeginWatch()` → 결과 기록 없음.
3. 시작은 받아들여졌는데 일꾼이 결과를 안 남긴 경우(`requested` 그대로).
- 공통 결과: 「되돌리는 중」 10분 ↔ 「예상보다 오래 걸립니다 / 계속 진행하고 있습니다」 무한 반복 — **아무것도 진행되지 않는데** 진행 중이라고 말한다.

## 왜 위험한가
- 오더 「고객사가 볼 때 자연스러운 화면전개 · 그렇지 않으면 오류처럼 보인다」 정면 위반 + 문구가 사실과 다르다.
- 이전 동작(받기 거절 → 실패 문구 + 다시 누르기)보다 나빠지는 갈래가 생겼다(1번).

## 재현 방법(순수 루프 · 운영 조작 0)
- 가짜 `getVersion` = 늘 `(200,"1.3.50")`, 가짜 `getStatus` = `Ok` + `Last=null` 로 `RunAsync` → `Stalled`; 이어 `CheckOnceAsync` → `Waiting`. 게이트에 이 갈래(판 = from 지속 · 결과 없음)를 재는 항목이 없다(G-W1~W10 전수 확인).

## 봉합(권고 — 결정은 설계·PM)
- 받기 폴링의 끊김 판정은 넘김(`handed_off`) 이전이면 바로 덮개로 넘기지 말고 한 번 더 확인, 또는 받기 거절도 덮개가 볼 수 있게(상태 응답 `Fetch.Stage=refused` 를 J-6 처럼 판정).
- [다시 확인] 때 판 = from 이 살아 있고 이번 결과가 없으면 J-8 처럼 끝내는 카드(기존 결과 한 줄로 걷기 등) — 문구는 사장님 결재.
