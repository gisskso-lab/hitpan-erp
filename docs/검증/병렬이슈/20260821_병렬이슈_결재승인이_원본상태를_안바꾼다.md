## 0. 한 줄

**결재만 배선하면 "결재는 승인됐는데 신청서는 대기중"** 이 된다.
설계서 §2-3 이 쟁점으로 올려둔 항목이 **실측으로 확정**됐다.

---

## 1. 실측 — `ProcessAsync` 가 동기화하는 원본은 딱 2개다

`ApprovalService.ProcessAsync` 안의 `UPDATE` 전수 (실측):

```
UPDATE approval_documents SET ...   ← 결재 자신
UPDATE hr_reports         SET ...   ← 업무보고서
UPDATE leave_requests     SET ...   ← 연차
```

`employee_leave_of_absence`(휴직) · `overtime`(초과근무) · `hr_expense_requests`(경비) 동기화: **0건**

### 🔴 즉 원본 동기화는 자동이 아니라 **doc_type 마다 손으로 짠 것**이다

`leave` 와 `report_*` 만 `if (docType == ...)` 블록이 손으로 들어가 있다.
새 doc_type 을 배선해도 **원본 상태는 저절로 안 따라온다.**

> 코드 주석이 이미 그 사고를 겪었다고 적고 있다:
> *"결재함서 승인했는데 연차 미반영"* → 그래서 `leave` 블록을 나중에 넣은 것이다.
> **같은 사고가 휴직·초과근무·경비에 그대로 남아 있다.**

---

## 2. 그래서 각 결함의 진짜 크기

### 결함① 휴직 — 라벨만 추가하면 **절반만 고쳐진다**

| 단계 | 라벨 추가 후 |
|---|---|
| 설정화면에 "휴직" 행 | ✅ 뜬다 |
| 켜기 | ✅ 된다 |
| 상신 | ✅ 결재함에 간다 |
| **결재 승인 → 휴직 상태 반영** | 🔴 **안 된다** |

⚠️ 게다가 `AbsenceService.ApproveAsync` 는 **승인 시 사원 상태(재직→휴직)까지 바꾼다**
(사장님 지시 *"상태처리 : 재직 휴직 연차"*). 결재로 승인해도 **이게 안 돈다.**

⇒ **결재함에서 승인 → 사원은 여전히 "재직", 휴직은 "대기중".**
지금(상신 자체가 안 됨)보다 **더 헷갈리는 상태**가 될 수 있다.

### 결함② 초과근무 — **이중 승인** 모순이 실재한다

`HrService.ApproveOvertimeAsync` 주석 실측:
> *"초과근무 승인/반려 (사장님 결재 2026-06-23 — **신청만 되고 승인 경로가 없던 워크플로우 끊김 봉합**)"*

⇒ 자체 승인 경로는 **사장님 결재로 만들어진 정본**이다. 함부로 지울 수 없다.
결재를 배선하면 승인 경로가 **둘**이 된다:

```
경로A  화면의 승인 버튼      → overtime.status = approved
경로B  결재함에서 승인        → approval_documents 만 approved, overtime 은 pending 그대로
```

**두 경로가 서로를 모른다.**

## 3. 🔴 판정 — 설계서 §2-3 대로 "미해결이면 배선하지 않는다"

설계서가 스스로 건 조건:
> *"2번(원본 상태 연동)이 미해결이면 이번 범위에서 배선하지 않고 사장님께 별도 보고한다."*

**미해결로 확정됐다.** 따라서:

| 결함 | 이번 범위 | 근거 |
|---|---|---|
| ① 휴직 **라벨 추가** | ✅ **한다** | 상신조차 안 되던 것이 되게 한다. 되돌리기 쉽고 위험 낮음 |
| ① 휴직 **원본 동기화** | ⬜ **사장님 결재 후** | `ApproveAsync` 의 사원상태 전이까지 결재 경로에 옮겨야 함 — 설계 판단 필요 |
| ② 초과근무 **배선** | 🔴 **하지 않는다** | 이중 승인 모순 미해결. 배선하면 새 거짓봉합 |

## 5. 이 적발이 막은 것

봉합안 그대로 갔으면:
- 초과근무: 결재는 올라가는데 **신청서는 영원히 대기중** → *"결재했는데 왜 그대로냐"*
- 휴직: 결재 승인해도 **사원이 재직으로 남음** → 급여·근태가 휴직을 모름

**둘 다 화면·빌드·시험은 정상이다.** 전형적인 "고쳤는데 안 갔다"(project_fixed_vs_delivered_gap).

## 6. 🔴 사장님 결재 (2026-08-21) — V1 확정 + 급여 원칙 못박음

> *"영향 없다면 결재승인 작업해"*
> *"급여는 수동입력원칙이야 그래서 급여가 휴직을 모르고 사원만 알면 됨"*
> *"사원마스터에 상태처리 급여는 수동설정으로 고객이 알아서"*
> *"연봉계산기는 정식배포때 추후 업데이트 예정 / 일단은 수동원칙"*

### 확정된 것

| 축 | 결재 |
|---|---|
| **V1 원본 반영** | ✅ **한다** — 휴직 결재 승인 시 원본 + **사원마스터 상태**까지 |
| **급여 연동** | 🔴 **하지 않는다** — 급여는 **수동입력 원칙**. 고객이 알아서 |
| 연봉계산기 | ⬜ **정식배포 때 추후** — 지금은 수동원칙 유지 |

### 🔴 PM 정정 — 봉합 근거가 틀렸었다

당초 주석에 *"안 고치면 급여가 그대로 나간다"* 를 봉합 근거로 적었다. **틀렸다.**

실측 결과 `PayrollService` 는 휴직을 **읽기는 하지만 금액을 자동계산하지 않는다** —
`absence_id` 로 *"이 명세가 어느 휴직분인지"* **잇기만** 하고, 금액은 고객이 넣은 `lines` 에서 나온다.
⇒ **사장님 수동입력 원칙이 코드에 이미 지켜지고 있었다.**

봉합의 진짜 근거는 급여가 아니라 **사원마스터 상태**다:
> 결재함에서 휴직을 승인해도 **사원이 '재직' 으로 남는다** → 조직도·화면이 휴직자를 재직자로 본다.

주석을 사장님 말씀대로 고쳤다. **급여 표는 한 줄도 안 건드린다.**
