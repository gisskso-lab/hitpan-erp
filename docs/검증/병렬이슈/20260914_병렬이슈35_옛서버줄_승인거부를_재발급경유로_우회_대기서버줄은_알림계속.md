## A. 승인 거부(③)가 [인증키 재발급] → verify-key 로 우회된다

- ③ 가드는 `ApproveAsync` 한 곳에만 있다. `status='approved'` 로 바꾸는 다른 입구 `VerifyAuthKeyAsync`(:1079-1089)는 **그 줄의 해시만 맞으면** 승인으로 올린다.
- 그 해시를 채우는 `ReissueAuthKeyAsync`(:1157) 는 **`revoked` 만** 막는다 — 대기·반려 옛 서버줄에 새 키를 준다.
- 검증자 탐침(격리 33307 · 실제 서비스 · 스크래치 시험 · 원복함): 표식 없는 서버줄(`MAINPC-` ∧ `is_main_pc=0`) + 사장님 줄(표식 1) → `ReissueAuthKeyAsync("서버줄")` → `VerifyAuthKeyAsync(key, tenant, "서버줄")`
  - `pending`: **status=approved · 승인 PC 1→2 · 기계비밀 발급됨**
  - `rejected`: **같음(1→2)**
- 화면 도달: [설정 → 등록 기기 관리] 대기 목록 한 줄에 [승인]·[인증키 재발급]·[거부] 가 나란히 있다(`DeviceManagePage.razor:79-92`). [승인]이 「회사 서버의 옛 기록은 승인할 수 없습니다」로 막히면 대표가 옆 [인증키 재발급]을 누를 수 있고, 키를 합류 화면에 넣으면 슬롯이 먹힌다. 관문이 `staleServerRow` 일 때 **키 입력칸을 숨기는지는 미확인**(자기승인 버튼만 숨김 확인).
- 반려 줄은 대기 목록에 안 뜨므로 API 직접 호출만(대표 권한) — 도달성 낮음.

## B. 대기(pending) 옛 서버줄은 알림 생략(②) 조건에 안 걸린다

- 알림 생략은 `reason == DeviceMessages.StaleServerRow` 일 때만이다. 그 사유는 가드 ①(`revoked`·`rejected`)만 돌려준다.
- 대기 옛 서버줄 로그인은 가드를 안 타고 일반 갈래로 가 `"기기 승인 대기 중입니다."` 를 돌려준다.
- 검증자 탐침: 표식 없는 **대기** 서버줄 합류 로그인 local·원격 모두 `allowed=False reason=기기 승인 대기 중입니다.` ⇒ `AuthController` 가 **대표 `device_pending` 알림을 로그인마다 보낸다** — 대표는 [승인]을 눌러도 거부된다(③).
- 병렬이슈34 ② 의 실측 경우(「대기(표 무변화 · 알림 발송 갈래)」)가 **바로 이 대기 상태**였다. 반려·폐기 경우만 닫혔다.
- 관문(`gate-status`)은 `!approved` 전부에 `staleServerRow` 를 실으므로 화면 안내는 대기에도 맞게 뜬다 — 알림만 어긋난다.
- 게이트 G-M8e~h 에 「대기 옛 서버줄 로그인 → 알림 없음/사유」 경우 0건. 컨트롤러 알림 시험 0건.

## 과하지 않은가 (회귀 확인 · 참고)

- 기기 계열 게이트 129/129 · Skipped 0(격리 33307 · `HITPAN_REQUIRE_DB=1`). 표식 든 서버줄 · 일반 기기 승인(G-M8g) · 모바일 · 8/11·DP-2 계통 초록.

## 봉합 방향 (검증자는 고치지 않는다 · 결재 안건)

- A: `ReissueAuthKeyAsync`(또는 `VerifyAuthKeyAsync`)에도 같은 판정(`IsServerRowWithoutMarkAsync`) 거부 / 옛 서버줄 대기 행에는 재발급 버튼을 안 그리는 안 — 서버 가드가 문지기. 게이트: 재발급→대조 경로 승인 PC 불변 + 무력화.
- B: 가드 ① 에 `pending` 을 넣어 같은 사유로 거부(표 무변경)하는 안 / 알림 생략 조건을 사유 글자 대신 `IsServerRowWithoutMarkAsync` 판정으로 두는 안 — 설계 결재(대기 줄의 localhost 표식 이전 차단(가드 ②)과 충돌 여부 확인 필요).
