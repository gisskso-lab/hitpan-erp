## 1. 최우선 질문 — INFO 앞 200자에 비밀값이 들어가나

### 1-1. 전제 정정: 「Dapper 매개변수면 INFO 에 값이 안 보인다」는 이 스택에서 **거짓**

- 드라이버 = `MySqlConnector 2.5.0` (`src/HitPan.Application/HitPan.Application.csproj:14`). `.Prepare()` 호출 0건(`src` 전체 grep). Dapper 는 Prepare 를 부르지 않는다.
- MySqlConnector 는 준비문이 아니면 **매개변수를 클라이언트에서 글자로 풀어 넣은 SQL 문장**을 보낸다(드라이버 문서 근거 · ⚠️실물 PROCESSLIST 미측정 — 대조군 R-4 의 `[INSERT INTO refresh_tokens]=` 기록이 잰다).
- ⇒ PROCESSLIST `INFO` 에는 `@TokenHash` 가 아니라 **해시 값 자체**가 보인다. 이음새를 막는 것은 매개변수 방식이 아니라 **글자 위치**뿐이다.

### 1-2. 실제 SQL 모양 (파일:줄)

| 경로 | 위치 | 문장 | 이 시험이 타나 |
|---|---|---|---|
| 로그인 | `src/HitPan.Application/Services/AuthService.cs:253-254` | `INSERT INTO refresh_tokens (token_id, user_id, token_hash, expires_at, is_revoked, session_id)` + 줄바꿈 + 공백 18 + `VALUES (@TokenId, @UserId, @TokenHash, @ExpiresAt, 0, @SessionId)` | ✅ G_B31b·대조군 모두 `LoginAsync` |
| 갱신 회전 | `AuthService.cs:1138-1139` | 같은 문장 · 줄바꿈 뒤 공백 22 | ❌ |

- `TokenHash` = `HashToken(response.RefreshToken)` = SHA-256 16진 64자 (`AuthService.cs:259` · `:1441-1442`). **토큰 원문은 SQL 에 안 들어간다**(해시만).
- 비밀번호 해시: SQL 에 0건 — `BCrypt.Verify` 메모리 비교뿐(`AuthService.cs:55` · `:1470`). 연결 문자열: SQL 문장에 들어갈 길 0.
- `TokenId` = `Guid.NewGuid().ToString()` 36자 · `UserId` = 시험 상수 36자(`SessionRecordConcurrentPcGateTests.cs:85`) · 둘 다 따옴표 포함 38자.

- 판정 단계 문장(대조군이 찍는 것): `DELETE FROM refresh_tokens WHERE user_id = … AND expires_at < …`(`AuthService.cs:322`) · 판정 SELECT(`LivePcSessionPredicate` `:327-330`) — 값은 user_id·시각뿐, 비밀 0.

### 1-4. 왜 🟢 가 아닌가 — 우연에 기대는 방어

- 「안 닿는다」의 근거가 **제품 코드의 줄바꿈+들여쓰기 19글자**다. 누가 `AuthService.cs:253` 을 한 줄로 펴거나 상수로 빼서 들여쓰기가 줄면 해시 시작이 184 근처로 당겨져 **해시 앞 16자 이상이 공개 CI 로그에 매 실행마다** 찍힌다. 제품 코드 리팩터는 이 시험의 검토 범위 밖에서 일어난다.
- 찍히는 빈도: `G_B31b` 는 잡으면 **통과 때도** 찍는다(`:2535`) · 대조군은 **매 실행** 3줄(`:2639`·`:2660`·`:2661`). 실패 때만이 아니다.
- 영향(지금 판 기준): 일회용 CI 컨테이너 DB · 시험 전용 계정 · 해시는 원문 복원 불가 ⇒ 실제 피해 ≈ 0. 그래서 🔴 가 아니라 🟡.
- ⚠️미확인: xUnit v2 + `dotnet test --verbosity normal` 에서 testhost 의 `Console.Error` 가 CI 콘솔 로그에 실제로 실리는지(개발명세서 §1-1 ② 도 미측정). 실리지 않으면 노출면은 실패 메시지(trx·콘솔) 쪽만 남는다.

## 2. 잠금·트리거·연결이 어떤 끝에서도 풀리나

| 끝 | G_B31b (`:2490-2576`) | 대조군 (`:2590-2700`) |
|---|---|---|
| 정상 | finally: `KILL` → `await login` → `DropTrigger` → 표지 정리 → `db.Dispose` (`:2541-2559`) | finally: `UNLOCK TABLES` → `KILL` → `await login` → `DropTrigger` → 정리 (`:2663-2686`) |
| 탐침 중 예외 | finally 로 감 ✅ | finally 로 감 ✅ (`LOCK TABLES` 는 `try` 안 `:2624`) |
| 시간초과(150×100ms) | 루프 종료 → finally ✅ | 루프 종료 → finally ✅ |
| `login` 예외 | `CaptureAsync` 가 예외를 값으로 받음 → `await` 가 안 던짐 ✅ | 같음 ✅ |
| `UNLOCK` 실패 | 해당 없음 | `catch` 기록 후 진행(`:2670-2673`). 실패 원인이 locker 연결 끊김이면 서버가 이미 표 잠금을 풀었다. `using var locker` 가 메서드 끝에 반납 ✅ |
| `KILL` 실패 | 기록 후 진행 · 트리거 SLEEP 최대 20초 뒤 끝남 ✅ | 같음 ✅ |
| 계정 잠금(`GET_LOCK` · 서버 전역 이름 `hp_login_<UserId>` `AuthService.cs:354`) | 로그인 연결 `KILL` 로 풀림 ✅ | 같음 ✅ — S-2 연쇄의 뿌리를 두 시험 모두 finally 에서 끊는다 |
| 취소(실행 중단) | 시험에 취소 토큰 0 · 프로세스 종료 시 서버가 연결·잠금 회수. 트리거는 시험 전용 DB(`_dbName` = 무작위 `:81`)에 남을 뿐 다른 시험 DB 에 안 번짐 | 같음 |

- 🟢 새 경로에서 「잠금이 남아 뒤 게이트가 막히는」 끝은 찾지 못했다.
- 🟡 경미(C-3): `DropTrigger`(`:3148-3149`)는 `catch` 가 없다 — `admin` 연결이 죽은 끝에서는 finally 안에서 던져 **원래 실패 원인을 덮는다**. 시험 전용 DB 라 잔여는 격리되지만 진단성이 떨어진다. 기존 G_B31b 와 같은 모양(이번에 새로 만든 결함 아님).
