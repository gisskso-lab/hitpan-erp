## 1. 무엇이 났나 (🟢 격리 실측)

- 보관 개수 2 · 실패 덤프 2회 → 성공 1회 ⇒ 남은 파일 = **0B 1개 + 성공 1개**, 그 전 **진짜 백업 2개 삭제**.
- 원인: `ApplyRetention` 이 파일 **개수**만 세고 크기·성공 여부를 안 본다. 실패한 덤프는 출력 파일을 먼저 만들고(0B) 지우지 않는다.
- `ccd9b4ec` 는 호출 위치만 옮겼다(C-9) — 이번 커밋이 만든 결함은 아니다.
- 함께: `ApplyRetention` 의 `catch { _ = ex; }` 는 기록이 없어 사실상 빈 catch (#15 · P2).

## 2. 봉합 (C-16)

1. 덤프 실패 경로에서 방금 만든 출력 파일(부분·0B) 삭제 — 삭제 실패는 `LogWarning`
2. 보관 계산·삭제 대상에서 0바이트 제외
3. 빈 catch → `LogWarning(ex, …)`
4. 게이트: 보관 N · 실패 N회 뒤 성공 1회 → 이전 성공 백업 보존 + 무력화 1행

## 3. 남는 것

- 사장님 PC 옛 폴더(`System32\HitpanBackup`)의 0B 파일은 새 기본 폴더와 달라 보관정책 대상이 아니다(🟡 — 저장 경로 교정 K3 이후).
