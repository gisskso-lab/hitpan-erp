## 2. 🔴 trace 처리 판정 (질문 2) — **안 ⓐ 채택 권고**

**사실 (코드 읽기 · 실행 미측정)**
- trace 는 `device-check.js:104` 에서 **늘** 기록을 시작하고, 실패한 브라우저만 `trace/` 에 남긴다(`:163~165`).
- 그런데 같은 문맥에서 `screenLogin` 이 비밀번호를 `fill(password)` 로 넣는다(`device-check.js:74`). Playwright trace 는 동작 인자를 그대로 적으므로(⚠️ 미측정 · 일반 동작 지식) **비밀번호 원문이 trace 에 들어간다.** 로그인 요청 본문·인증 헤더·SignalR 주소 질의까지 더하면 한 곳이 아니라 **여러 곳**이다.
- ⇒ 개발자 예상(인증 헤더·SignalR 토큰)보다 확실하다: **실패해서 trace 가 남는 모든 런에서 S10 은 반드시 빨강**이고(비밀번호 `UI_PW_NA` 는 S0 값 — `leak-scan.js:214`), S11 규칙상 `main/`(결과표·스크린샷)까지 업로드 0. trace 업로드 단계(`ui-browser.yml:228~237`)는 사실상 **영영 안 도는 코드**다.
- 보안 쪽 결과는 「안전하게 닫힘」(공개 0)이다. 깨지는 것은 **증거**다 — 실패 런일수록 증거가 없다.

**판정: 안 ⓐ — trace 를 기록도 업로드도 하지 않는다. 실패 증거 = 결과표 · 스크린샷 · API 로그 · 단언 메시지(+ 필요하면 화면 콘솔 오류를 `L.sanitize` 거쳐 `main/` 에).**

근거
1. **PUBLIC 레포.** trace 는 비밀번호·토큰이 들어가는 자리가 동작 인자·요청 본문·헤더·주소 질의·DOM 스냅샷(저장소 값 ⚠️미확인) 등 여럿이고, 그 꼴은 아직 한 번도 실측하지 않았다(§8 ⑧). 모르는 꼴을 공개 업로드 직전에 다루는 설계는 받지 않는다.
2. **안 ⓑ(지우고 올리기)는 반려.** ① 미측정 압축 형식 안에서 「토큰 자리만 지우기」는 놓친 한 자리가 곧 공개다 ② 지우는 코드가 S10 앞에 서면, S10 은 「지우기가 잘 됐나」만 보게 되어 **검사를 통과시키려고 손질한 업로드**가 된다(게이트는 글자가 아니라 동작) ③ ⑨ PM 안 「문 하나 · 예외 0」에 손질 단계라는 둘째 문을 더한다.
3. **안 ⓒ(trace 를 가볍게 — 스냅샷·네트워크 끄기)도 부족.** 동작 인자의 `fill` 값은 남는다 → 여전히 늘 빨강.
4. 값이 런 안 일회 난수라 실제 피해는 작다 — 그래도 공개 저장소에 비밀번호·JWT **모양**을 올리는 것은 「자격증명 모양 어디에도 금지」 규칙과 비밀값 탐지기 경보에 걸린다. 그리고 ⓐ 는 **증거가 오히려 늘어난다**(main/ 이 실패 런에도 올라간다).

조치 (이번 갈래 [3] 몫 · 상신 필요)
- `device-check.js:104·161~171` trace 시작·저장 제거 · `ui-browser.yml:228~237` trace 업로드 단계 제거 · S10 은 `main/` 만 검사(trace 갈래 남겨도 무해).
- 실패 지점마다 스크린샷이 남는지 확인(지금은 `:118`·`:159` 두 곳) · 단언 메시지는 지금처럼 `rec` 의 `got`(sanitize 경유).
- 🔴 이 변경은 `:168` PM 결정 ⑩ 의 「S8 실패 런에서도 S10 을 통과한 trace 는 올라간다(실패 시 trace 보존)」을 **바꾸는 일**이다 — 글자 넓힘·좁힘 0 원칙상 PM 재결재(필요하면 대표) 뒤 반영. 개발자가 혼자 고치지 말 것.
