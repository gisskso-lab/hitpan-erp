## 무엇이 문제인가

절A3 이 끝나면:

| 누가 | 경로 | [예] 넣기 |
|---|---|---|
| 메인PC | `update-consent` | ✅ |
| 다른 PC 의 로그인한 직원 | `update-consent` | ❌ 403 `main_pc_only` |
| **로그인도 안 한 아무나(터널 · 인터넷)** | `update-consent-local` `[AllowAnonymous]` (`src/HitPan.API/Controllers/AuthController.cs:724-821`) | ✅ **버전당 1회** |

`update-consent-local` 의 막음(멱등 `:781-795`)은 **「그 버전에 approve 가 한 줄이라도 있으면 안 넣는다」**이다. 그래서:
- 메인PC 가 첫 안내에서 **[나중에]만** 눌렀다(approve 없음) → 누구든 `{고객사ID}.hitpan.kr` 로그인 화면에서 [업데이트]를 누르거나 주소를 직접 부르면 approve 가 들어간다 → 규칙 C 에서 `latest=approve · id > used` ⇒ **새 [예]로 적용된다.** 사장님의 [나중에]가 인증 없이 뒤집힌다.
- 사장님 오더 ③(9/29) 「직원이 [예]를 눌러도 되나 → 메인PC 에서만」 — 직원보다 권한이 낮은 익명에게는 열려 있는 셈이다.

지금 고객 PC 에서는 `tenants` 빈 표(N-UPD7) 때문에 이 경로가 400 으로 끝나 **가려져 있을 뿐**이다. N-UPD7 을 고치는 순간 열린다.

## 🔴 N-UPD7 을 고칠 때의 함정 (재시작 반복 DoS)

설계 §8 은 「N-UPD7 은 이 묶음 뒤에, 규칙 C 를 따라」라고 적었다. 만약 그 때 로그인창 승인의 멱등을 규칙 C 식으로 바꿔 **「최신 approve 가 이미 쓴 것이면(latest.id ≤ used) 새 approve 를 넣는다」**고 하면:

> 익명 호출 → 새 approve → 워치독 시도(백업·서비스 중지·교체·검증) → 실패(rolled_back) → used 갱신 → 익명 호출 → 새 approve → …

⇒ 인증 없이 **업무 중 ERP 를 반복해서 끄는 입구**가 된다(작12 B안 결재가 멱등으로 막은 바로 그 위험). 지금 멱등이 DoS 를 막는 이유는 「버전당 approve 1회」라는 **동의 id 가 새로 생기지 않는 성질** 때문이고, 규칙 C 는 그 성질에 기대고 있다.

## 확인한 것 — 이번 작업이 새 입구를 여나? (결론: 안 연다, 무접촉이 지켜지면)
- `update-consent-local` 을 건드리지 않으면 익명은 버전당 approve 1개밖에 못 만든다 ⇒ 규칙 C 에서 「새 [예]」는 최대 1회 ⇒ 반복 재시작 없음.
- 워치독 인메모리 키가 버전 → 동의 id 로 바뀌어도, 새 id 를 만들 수 있는 입구가 인증된 메인PC 뿐이면 반복은 메인PC 사람 손으로만 생긴다(오더 「[예] 한 번 = 시도 한 번」의 의도).
- 출입증 발급(`DeviceController.cs:556-559`)은 `IsLocalConsole` 만 쓴다 ⇒ `update-consent` 를 재시도 경로에 넣어도 출입증이 출입증을 갱신하는 고리는 안 생긴다.

## 권고
1. 작업리뷰서·결재 보고에 「비메인PC [예]/[나중에] 차단」을 적을 때 **「로그인 사용자 기준 · 로그인 전 익명 경로는 N-UPD7 별건에서」**라고 범위를 밝힌다(거짓 「닫혔다」 방지).
2. N-UPD7 작업지시서에 필수 조건으로 넘긴다: (a) 로그인 전 승인은 **메인PC(`IsLocalConsole`) 에서만** 받거나, (b) 받더라도 **[나중에]가 최신이면 익명 approve 를 받지 않는다**, (c) 어떤 경우에도 「이미 쓴 approve 뒤 익명 새 approve」는 넣지 않는다. 게이트 = 익명 반복 호출 N회 → 동의 행 증가 ≤ 1.
3. 사장님 확인이 필요한 결정이다(작12 B안 「터널 허용」은 사장님 결재) — PM·설계가 대신 정하지 않는다(#33).
