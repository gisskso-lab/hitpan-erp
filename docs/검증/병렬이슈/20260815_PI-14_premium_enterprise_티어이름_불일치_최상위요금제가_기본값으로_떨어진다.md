# 병렬이슈 PI-14 — `premium` / `enterprise` 티어 이름이 갈렸다. 최상위 요금제가 **basic 한도로 떨어진다**

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시 병렬검증 · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 §9 · §10-4 (premium 미결) · P2 설정화 |
| 등급 | 🟠 **P1** — 과금 직결. 설계가 미결로 남긴 자리에 **이미 사고가 있다** |
| 상태 | ⬜ 미봉합 |

---

## 1. 무엇이 문제인가

명세서 §9 는 premium 을 **범위 밖**으로 두면서, 이렇게만 적었다:

> *"다만 `GetLimitsForTier` 에 `"premium" => (100, 80)` 이 살아 있어,
>   premium 티어 값이 들어오면 **조용히 동작한다.** 막을지 · 별도 경로로 보낼지는 **미결**(§10-4)."*

🔴 **실측하면 반대다. premium 은 "조용히 동작" 하지 않는다.
시스템의 나머지 전부가 그 요금제를 `enterprise` 라고 부르기 때문이다.**

⇒ 명세서가 걱정한 위험(*"premium 이 100/80 으로 통과"*)이 아니라,
**정반대 위험(최상위 고객이 basic 한도 5/3 으로 막힘)** 이 실재한다.

---

## 2. 근거 (실측)

### 코드는 `premium` 을 쓴다 — 딱 두 곳

| 위치 | 값 |
|---|---|
| `TenantDeviceService.cs:666` | `"premium" => (100, 80)` |
| `SessionLimitMiddleware.cs:19` | `["premium"] = 100` |

### 나머지 전부는 `enterprise` 를 쓴다

| 위치 | 내용 |
|---|---|
| `installer/hitpan_db_clean.sql:1978` | `COMMENT 'basic / pro / **enterprise**'` |
| `installer/hitpan_db_clean.sql:3909` | `subscription_tier … 'basic / pro / **enterprise**'` |
| `ResellerSerialController.cs:86-87` | `if (tier != "basic" && tier != "pro" && tier != "**enterprise**") return BadRequest` |
| `Tenant.cs:42` | `/// 구독 티어: basic / pro / **enterprise**` |
| `BackofficeModels.cs:236` | `"**enterprise**" => "Enterprise"` |
| `scripts/pricing_plans_seed.sql:6` | `plan_id … 'basic', 'pro', '**enterprise**'` |

🔴 **시리얼 발급(`ResellerSerialController`)이 `premium` 을 아예 거부한다.**
`enterprise` 만 통과시킨다. ⇒ **`premium` 이라는 값은 정상 경로로는 DB 에 들어올 수 없다.**

### 그래서 실제로 일어나는 일

`TenantDeviceService.cs:662-669`
```csharp
private static (int pc, int mobile) GetLimitsForTier(string? tier) => (tier ?? "basic").ToLowerInvariant() switch
{
    "basic"   => (5, 3),
    "pro"     => (10, 8),
    "premium" => (100, 80),
    "trial"   => (10, 5),
    _         => (5, 3)          // ← enterprise 가 여기로 떨어진다
};
```

🔴 **`enterprise` 고객은 `_ => (5, 3)` 으로 간다.**
최상위 요금제를 낸 고객이 **basic 과 똑같은 PC 5대 / 모바일 3대**로 막힌다.

그리고 한도 초과는 **로그인 차단**이다(§10-1 사장님 결재).
⇒ **가장 비싼 고객이 6번째 PC 에서 로그인을 못 한다.**

## 3. 이게 터지면 무슨 일이 나는가

### (1) 최상위 고객의 로그인 차단 — 가장 아픈 고객에게

돈을 가장 많이 낸 고객이 가장 좁은 한도를 받는다.
🔴 **과금 사고 중 최악의 형태다** — 과다 청구보다 설명하기 어렵다.

### (2) 설계의 미결 §10-4 가 **틀린 질문을 하고 있다**

§10-4 는 *"premium 티어 값이 들어오면 막을지 · 별도 경로로 보낼지"* 를 묻는다.
🔴 **premium 값은 들어오지 않는다.** 들어오는 것은 `enterprise` 다.
⇒ **미결 안건 자체를 다시 써야 한다.**

### (3) P2 설정화가 이 사고를 **굳힌다**

작지서 §6 리스크가 이렇게 적었다:
> *"설정화하며 기본값이 달라져 한도가 바뀜 → **현행 값(5,3)/(10,8)을 초기값으로 그대로**"*

🔴 **"현행 값 그대로" 를 지키면 `enterprise` 가 없는 상태가 그대로 설정에 복사된다.**
그러면 사고가 코드에서 설정으로 자리만 옮겨 **더 안 보이게 된다.**

⚠️ 백오피스 `pricing_plans` 는 `enterprise` 를 갖고 있다(`pricing_plans_seed.sql:6`).
⇒ P2 의 목표(*"ERP 와 백오피스가 같은 값을 본다"*)를 제대로 하면 **이 사고가 저절로 닫힌다.**
반대로 대충 하면 **영구화된다.** 갈림길이다.

### (4) 프리미엄 = 별도 트랙이라는 §9 판단과도 어긋난다

§9 는 프리미엄이 *"클라우드·서버구축 방식"* 이라 **아키텍처 전제가 다르다**고 했다.
그렇다면 `enterprise` 티어가 **이 ERP 코드에 들어오는 것 자체**를 어떻게 다룰지 정해야 한다.
지금은 **정의도 없이 `_ => (5,3)` 으로 조용히 흡수**되고 있다.
🔴 **가장 나쁜 형태다 — 막지도, 지원하지도 않고, 틀린 답을 준다.**

## 4. 어떻게 고쳐야 하나

### (1) 명세서 §10-4 안건을 다시 쓴다

현행: *"premium 티어 값이 들어오면 막을지 · 별도 경로일지"*
⇒ 수정: **"`enterprise` 티어가 ERP 로 들어오면 어떻게 하나. 그리고 코드의 `premium` 이라는
   이름은 어디서 온 것이며 유효한가"**

### (2) 🔴 `_ => (5, 3)` 조용한 폴백을 없앤다 — 가장 중요

모르는 티어를 **basic 으로 흡수하면 안 된다.** 이것이 진범이다.
⇒ **모르는 티어는 로그를 남기고 명시적으로 처리**한다(헌법 #15 정신 — 조용히 삼키지 않는다).

⚠️ 다만 **예외를 던지면 로그인이 막힌다.** 그것도 사고다.
⇒ 권고: **넉넉한 쪽으로 폴백 + 경고 로그.** 고객을 막는 것보다 낫고, 로그가 남아 발견된다.
🔴 **지금은 좁은 쪽으로 폴백하면서 로그도 없다** — 발견될 방법이 0이다.

### (3) 티어 이름을 **한 곳에서 정의**한다

`basic` / `pro` / `enterprise` 를 상수로 모으고, `premium` 이 남아 있는 두 자리
(`TenantDeviceService.cs:666` · `SessionLimitMiddleware.cs:19`)를 정렬한다.
⚠️ **`SessionLimitMiddleware` 는 이 작지서 범위 밖**이다 — 같은 사고가 **동시 접속 수**에도 있다.
⇒ 작지서 §2 에 넣거나, "하지 않는 것" 에 명시해 **추적되게** 한다. 지금은 둘 다 아니다.

### (4) 게이트 신설

| 게이트 | 검사 |
|---|---|
| **G-16** | 각 티어(`basic`·`pro`·`enterprise`·`trial`)가 **자기 한도**를 받는가. `enterprise` 가 5/3 이면 **FAIL** |
| **G-17** | 모르는 티어 문자열 → **경고 로그가 남는가.** 조용히 통과하면 FAIL |

## 5. 등급 판정 근거

**P1** — 이유:
1. **실재하는 과금 사고**다 — 가설이 아니라 코드 대조로 확인됐다
2. 최상위 요금제 고객의 **로그인 차단** 경로다
3. 🔴 **P2 가 이 사고를 굳힐 수 있다** — 지금 잡지 않으면 설정으로 옮겨가 더 안 보인다
4. P0 가 아닌 이유: 실사용 고객 0명(사장님 확인)이고 `enterprise` 계약이 아직 없다
   ⚠️ **단 베타에 enterprise 고객이 한 명이라도 들어오면 즉시 P0 로 승격된다**
