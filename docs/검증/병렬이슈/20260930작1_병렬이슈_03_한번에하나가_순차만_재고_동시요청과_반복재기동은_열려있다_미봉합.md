## 무엇이 문제인가

**(1) 동시 요청 경주** — P-f 는 「`request.json` 상태를 읽어 진행 중이 아니면 통과」(§1)다. 읽기와 쓰기 사이가 원자적이지 않다.
- 같은 순간 두 요청(더블클릭 · 두 탭 · 업데이트 화면과 되돌리기 화면) → 둘 다 P-f 통과 → (update 면) **백업 두 번** → 뒤 요청이 `request.json` 을 덮고 새 1회용 번호 → `schtasks /Create … /F` 면 작업 정의가 덮인다.
- 앞 작업이 이미 S3(정지)에 들어가 있으면: 번호가 바뀌어 앞 일꾼의 S7·성공 정리가 `request.json` 상태를 **남의 요청 위에** 쓴다. 뒤 작업이 `/Run` 되면 두 일꾼이 한 폴더를 교체한다(실행 중 작업을 `/F` 로 다시 만들 때 앞 인스턴스가 어떻게 되는지는 ⚠️미확인).
- G-U5 는 「update 진행 중 rollback 요청 → 거부」 — **순차**만 잰다.

**(2) 묵은 요청** — 1회용 번호는 「명령줄 번호 = `request.json` 번호」만 본다(§2). 등록만 되고 안 돈 작업(재부팅 등)을 나중에 `/Run` 하면 번호가 맞으니 **그때 가서** 교체가 돈다. 요청 시각 기준 유효시간이 설계에 없다.

**(3) 반복 재기동** — 되돌리기 → 수동 업데이트 → 되돌리기 … 를 끝없이 돌릴 수 있다(되돌린 판에서 피드 판 > 현재 ⇒ 업데이트 허용 · 업데이트 성공 ⇒ `prev` 생김 ⇒ 되돌리기 허용). 매번 약 5~10분 멈춤.
- 문을 여는 데 필요한 것 = 관리자 JWT + 메인PC. 메인PC 판정 `IsLocalConsole`(`MainPcOnlyAttribute.cs`)은 「터널 헤더 없음 + 루프백」이라 **메인PC 브라우저 안에서 도는 스크립트면 그대로 통과**한다(또는 `X-MainPc-Pass` 를 함께 가져간 경우 터널로도).
- 비밀번호 재확인·쿨다운 둘 다 설계에 없다. 백업 **복원**은 재확인을 넣은 전례가 있다(20260910작2 `f4c20ff1` 「백업 복원 비밀번호 재확인」 — 이 레포 main 컨트롤러에 반영 여부는 ⚠️미확인).
- 곁: update 요청이 백업을 **먼저** 하고 뒤에서 실패하면(작업 등록 불가 등) 백업 파일만 쌓인다 — 반복 호출 = 디스크 소모.

**(4) 잠금 유효시간** — S0 가 잡는 워치독 `UpdateLockFile` 은 `Ttl = 15분`(`UpdateLockFile.cs`). 교체+확인(S6 180초)+원위치(S7)가 길어지면 S5 에서 다시 켠 워치독이 잠금을 묵은 것으로 보고 자동 적용에 들어갈 수 있다 ⇒ U-9 에 「15분 초과 시」 칸을 더한다.

## 권고 (봉합 조건)
1. API 안 **원자적 자물쇠**: 프로세스 안 `SemaphoreSlim` + 보호 폴더(병렬이슈 01 조건 충족)에 `FileMode.CreateNew` 잠금 파일. 둘째 요청은 즉시 거부(사유 한 줄). 순서 = **자물쇠 → 전제 재판정 → 다운로드·해시 → 백업 → `request.json` → 작업 등록**(백업은 자물쇠 안).
2. 작업 등록에 `/F` 금지 — `HitPan-LocalSwap` 이 이미 있으면 거부(작업 이름 = 자물쇠라는 설계 §13-2 ① 을 실제로 성립시키는 조건).
3. `request.json` 에 `issued_at` 을 넣고 일꾼 S0 가 **유효시간(예: 10분)** 을 넘으면 `refused` · 작업 스스로 삭제.
4. 교체 [예] 에 **대표 계정 비밀번호 재확인**(또는 직전 교체 뒤 쿨다운) — 사장님 결재 사항(화면 한 칸이 는다 · 「쉬움」과 부딪힘)이라 PM 이 상신.
