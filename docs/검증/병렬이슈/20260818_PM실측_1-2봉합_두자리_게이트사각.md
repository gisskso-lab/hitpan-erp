# [3-V] PM 실측 — 1-2 봉합이 **두 자리**인데 게이트는 **한 자리만** 본다

| 항목 | 내용 |
|---|---|
| 적발 | **PM 브라운킴** (직접 실측 — 개발팀 보고를 반증하다 발견) |
| 일자 | 2026-08-18 |
| 대상 | 20260818작1 — 봉합 1-2 (헤더 통과를 메인PC 로 한정) |
| 등급 | 🟡 **P1** — 지금은 두 자리가 일치하나, **한쪽만 고쳐지면 아무도 못 잡는다** |
| 상태 | ⬜ 미봉합 (다음 차수) |

---

## 1. 무엇이 났나

개발팀이 *"1-2 봉합을 빼면 G-32 가 FAIL 한다"* 고 보고했다.
🔴 **PM 이 받아쓰지 않고 직접 빼 봤다. 12/12 그대로 통과했다.**

```
sed -i "163s/ AND is_main_pc = 1//" src/HitPan.API/Middleware/DeviceAuthMiddleware.cs
dotnet test --filter DeviceAndKeyGate
  → 실패: 0, 통과: 12   ← 🔴 봉합을 뺐는데 초록불
```

⚠️ **처음엔 가짜 게이트로 의심했다.** 게이트 주석에 *"MariaDB 가 없으면 조용히 통과시킨다"* 가 있었기 때문이다.
**그것도 실측으로 배제했다** — `mysql.exe` 실재 + `sc query MariaDB` = **RUNNING**, 실행 시간 **1분 23초**(밀리초 아님).
⇒ **게이트는 실제로 DB 를 태웠다. 가짜가 아니다.**

## 2. 진짜 원인 — 같은 봉합이 두 자리에 있다

| 자리 | 코드 | 게이트 |
|---|---|---|
| **①** `TenantDeviceService.cs:969-980` `IsDeviceAllowedAsync` | `AND is_main_pc = 1` | 🟢 **G-32 가 지킨다** |
| **②** `DeviceAuthMiddleware.cs:160-165` **자체 SQL** | `AND is_main_pc = 1` | 🔴 **아무 게이트도 안 본다** |

**미들웨어가 서비스를 부르지 않고 자기 SQL 을 따로 갖고 있다.**
⇒ G-32 는 ①만 태운다. 내가 뺀 것은 ②였다. **게이트가 거짓말한 것이 아니라, 안 보는 자리가 있었다.**

## 3. 🔴 개발팀 주석이 이 사고를 스스로 예고했다

`DeviceAuthMiddleware.cs:156-157` 원문:

> *"⚠️ 판정을 `TenantDeviceService.IsDeviceAllowedAsync` 와 **같은 모양**으로 둔다.
> **두 자리가 갈리면 한쪽만 고쳐지는 사고가 난다**(이 파일이 이미 그 사고를 겪었다)."*

🔴 **위험을 정확히 알고 주석으로 적었으나, 그 위험을 잡는 게이트는 만들지 않았다.**
**주석은 게이트가 아니다.** 다음 사람은 주석을 안 읽거나, 읽고도 한쪽만 고친다.

## 4. 안 고치면 무슨 일이 나는가

- 누가 ②만 고쳐 `is_main_pc` 조건을 빼면 → **승인된 아무 직원 기기의 번호로 ERP 전 API 통과**
- 🔴 **게이트는 12/12 초록불**이라 아무도 못 잡는다
- `device_id` 는 비밀이 아니다(V-04) — 기기 목록 화면·`gate-status` 쿼리스트링(**서버 로그에 평문**)·localStorage

## 5. 어떻게 닫나 — 두 안

| 안 | 방법 | 평가 |
|---|---|---|
| **(가) 자리를 하나로** | 미들웨어가 자기 SQL 을 버리고 `IsDeviceAllowedAsync` 를 부른다 | 🟢 **권장** — 갈릴 자리 자체를 없앤다. 게이트도 저절로 ②를 덮는다 |
| (나) 게이트를 하나 더 | ②를 태우는 G-32-c 신설 | 🟡 자리는 여전히 둘. 셋째 자리가 생기면 또 샌다 |

🔴 **(가)를 권한다.** 게이트를 늘리는 것은 **갈린 것을 인정하고 감시하는 것**이고,
자리를 합치는 것은 **갈릴 수 없게 만드는 것**이다. 후자가 근본이다.
⚠️ 단 미들웨어는 DI 로 서비스를 받을 수 있는지 확인이 필요하다(⚠️미확인).

## 6. 이번 차수 판정

🟢 **작1 반려하지 않는다.** 두 자리가 **지금은 일치**하고, 1-2 의 의도는 실제로 지켜지고 있다.
🔴 **다음 차수 필수** — 개발명세서 §못한 것 에 이 문서 주소를 넣는다.

## 7. 🔴 교훈 — 게이트 설계 규칙에 추가한다

> **"봉합을 뺐는데 초록불"이면 두 가지 중 하나다 — 게이트가 가짜이거나, 내가 뺀 자리를 게이트가 안 보거나.**
> **둘을 가르지 않고 "가짜"로 단정하면 진짜 원인(자리가 갈려 있음)을 놓친다.**

⇒ 🔴 **새 규칙: 봉합을 넣을 때 "이 판정이 다른 자리에도 있나" 를 `grep` 으로 먼저 확인한다**(헌법 #12 정신).
갈려 있으면 **합치거나, 갈린 모든 자리를 게이트에 넣는다.**

# 🔴 [추가 적발] G-31 이 **부정확하다** — 남의 줄이 열려도 초록불

| 항목 | 내용 |
|---|---|
| 적발 | **PM 브라운킴** (2차 반증 중) |
| 등급 | 🔴 **P0** — 이번 차수 **핵심 봉합(1-1)** 을 지키는 게이트다 |
| 상태 | ⬜ 미봉합 — **개발팀 재작업 지시함** |

## 1. 반증 실행

**하브루타 최대 수확**인 §17-1(*"키는 대조만, 줄은 서버가 정한다"*)을 뺐다:

```
# TenantDeviceService.cs:674 — 줄을 특정하는 조건을 제거
-  WHERE tenant_id = @TenantId AND device_id = @DeviceId
+  WHERE tenant_id = @TenantId

dotnet test --filter DeviceAndKeyGate
  → 실패: 0, 통과: 12   ← 🔴 초록불
```

⇒ **`LIMIT 1` 이 남아 있어 아무 줄이나 집는다.** 공용 열쇠가 부활한 상태인데 **게이트가 못 잡았다.**

## 2. 왜 못 잡나 — 판정문이 틀렸다

`DeviceAndKeyGateTests.cs:270-271`:
```csharp
Assert.True(opened != deviceA, "...남의 줄이 열렸다...");
```

🔴 **"A 가 아니면 통과"** 다. 그런데 함수는 반환값을 `sessionDeviceId`(=B) 로 **고정**해 돌려준다.
⇒ 내부에서 **A 의 줄을 집어 A 의 해시로 대조해도**, 돌아오는 값은 B 라서 `!= deviceA` 가 성립한다.

| | 게이트가 보는 것 | 실제로 봐야 하는 것 |
|---|---|---|
| 지금 | **무엇이 반환됐나** | 🔴 **누구의 줄이 바뀌었나** |

**반환값은 함수가 마음대로 정할 수 있는 값이다.** 그것을 시험하면 **함수의 성실성을 시험**하는 것이지 **동작**을 시험하는 것이 아니다.

## 3. 🔴 이것이 히트판 가짜 게이트의 **새로운 형태**다

여태 여섯 번은 **글자검사**(`Assert.Contains`)와 **DB 제약 초록불**이었다. 이번은 다르다:

> **실제 DB 를 태우고, 실제 서비스를 부르고, 값을 본다 — 그런데 "보는 값"이 결함과 무관하다.**

⇒ 🔴 **게이트 규칙에 추가**: **"이 값이 틀렸다면 무엇이 잘못된 것인가"** 를 되물어라.
반환값이 아니라 **부작용(DB 상태 변화)** 을 봐야 하는 자리가 있다.

## 4. 어떻게 고치나

```csharp
// 반환값이 아니라 DB 를 본다 — 누구의 줄이 승인으로 바뀌었나
var aStatus = await db.ExecuteScalarAsync<string>(
    "SELECT status FROM tenant_devices WHERE device_id=@Id", new { Id = deviceA });
Assert.Equal("approved", aStatus);   // A 는 원래 approved — 안 건드려졌나
var aKey = await db.ExecuteScalarAsync<string?>(
    "SELECT auth_key_hash FROM tenant_devices WHERE device_id=@Id", new { Id = deviceA });
Assert.NotNull(aKey);                // 🔴 A 의 키가 소거됐다면 A 의 줄이 열린 것이다
var bStatus = ...(deviceB);
Assert.Equal("pending", bStatus);    // B 는 안 열려야 한다
```

🔴 **핵심: A 의 `auth_key_hash` 가 NULL 이 됐는지 본다.** 1회용 소거는 **열린 줄에만** 일어나므로,
**누구의 키가 사라졌는지가 곧 누구의 줄이 열렸는지**다. 반환값과 달리 이것은 **속일 수 없다.**

## 5. 안 고치면

이번 차수의 **간판 봉합**(§17-1 열쇠 AND)이 **아무 게이트로도 보호되지 않는다.**
다음 사람이 성능 이유로 `WHERE` 절을 손대면 **공용 열쇠가 부활하고 12/12 초록불**이다.
⇒ 🔴 **하브루타 5개월 미스터리를 푼 성과가 한 줄 수정으로 조용히 되돌아간다.**
