## 반증 질문 판정 (작업지시서 18-1 필수 #2 · #4)
- **#2 받은 zip 바꿔치기** — p2 는 「API 가 놓은 뒤 ~ 일꾼 S1」 사이의 바뀜은 잡는다(PM 결재 「p2 빠지면 반려」 그 취지는 선다). **그러나 일꾼 안의 창은 남는다**: 기존 update 모드와 같은 모양이면 `Get-FileHash -LiteralPath $zip`(`local-swap.ps1:681`) → 파일 닫힘 → `Expand-Material $zip`(`:686` → `:617` `ZipFile.ExtractToDirectory`)이 **같은 경로를 다시 연다.** 해시한 바이트와 푼 바이트가 같다는 보장은 그 사이 `{app}\manual\staging` 에 쓸 수 있는 자가 없다는 ACL 뿐.
  - 받는 폴더 ACL: `ManualFolders.EnsureRestricted` → `EnsureRestrictedSystemFolder`(SYSTEM·Administrators·실행 계정 + **관리자가 붙인 개별 사용자 줄 허용** C-12 ⓑ). 일꾼은 이 폴더 ACL 을 **다시 재지 않는다**(update 모드도 동일 · 기존 동작).
  - 쓸 수 있는 자 = 관리자·SYSTEM·API 계정. API 가 LocalSystem 이면(⚠️) API 탈취 = 이미 SYSTEM 이라 권한 상승 없음 ⇒ 지금은 새지 않음.
- **#4 이름 조립 0** — 판정: 지켜진다(설계 기준). 받는 주소 = 서명 본문에 든 `DownloadUrl`(`UpdateClient.cs:214`) · 로컬 파일 이름만 `hitpan-{Version}.zip`(`:208` · 서명된 판 값). 단 구현에서 `DownloadAsync` 가 던지면 경로를 돌려주지 않으므로 받기 일이 「즉시 지움」을 하려면 **같은 이름을 스스로 조립**해야 한다 — URL 조립은 아니라 K-2 위반은 아니지만, 그 조립이 `Version` 을 검증 전 값으로 쓰지 않는지 [4] 가 볼 것(G-NP5 「받은 파일 0」이 잰다).

## 받기 크기 상한 없음
- `DownloadAsync`(`:204-222`)는 `CopyToAsync` 로 **끝까지 쓴 뒤** 길이를 본다(설계 ⑥). T6 `HasEnoughSpace(size)` 는 서명된 size 로 미리 재지만, 서버가 그보다 길게 보내면 C: 를 채울 때까지 쓴다(제한 시간 30분). 주소가 서명돼 있어 공격자 = 본사 서버(NCP) 탈취 또는 TLS 깨기 ⇒ P3. 이 PC 는 1.3.47 적용이 C: 부족으로 막힌 이력(메모리 9/29)이 있어 「디스크 꽉 참」의 영향은 작지 않다.

## 막는 방향 (적발만 · 결정은 설계)
- 설계 문구를 「p2 = API 가 놓은 뒤 일꾼 S1 전 바뀜 차단 · 일꾼 안 해시~풀기 창은 폴더 ACL 이 지킨다」로 바로잡는다.
- 창을 닫으려면: 일꾼이 zip 을 `FileShare.Read`(쓰기 거부)로 연 **한 핸들**로 해시하고 같은 핸들(`ZipArchive(stream)`)로 푼다 — 단 「일꾼 기존 줄 수정 0」 제약과 부딪히면 p2 덧붙임 안에서 rollback+`manual_zip` 만 그렇게(기존 update 줄 무접촉).
- 받기는 서명된 size 를 넘는 순간 끊는다(받기 일이 `DownloadAsync` 대신 쓰는 게 아니라면, 끝난 뒤 길이 검사 + 시작 전 `Content-Length` > size 면 즉시 중단 정도) — 「새 암호 코드 0」과 무관.
- 게이트: rig 에서 p2 해시 통과 직후 zip 을 바꾸는 주입(`Test-FailAt` 같은 시험 고리) → 바뀐 내용이 깔리면 FAIL. 대조군 = 지금 모양.
