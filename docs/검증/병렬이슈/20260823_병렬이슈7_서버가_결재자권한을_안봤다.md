# 병렬이슈 7 — 서버가 결재자 권한을 안 보고 저장했다 (G1 [3-V] 적발)

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시검증 · 2026-08-23 |
| 대상 | 20260822작1 G1-[B] 권한자만 결재 |
| 심각도 | **P1** — 화면만 거르면 규칙이 아니라 권유다 |
| 상태 | 🟢 **봉합 완료** (같은 커밋) |

---

## 무엇이 틀렸나

`ApprovalService.SaveLinesAsync` 는 결재자가 **활성 사원인지만** 봤다.
**APPROVAL 권한도, 대표 여부도 안 봤다.**

실측 — 해당 메서드에 `user_permissions`·`APPROVAL`·`is_parent` 참조 **0건**.

## 왜 사고인가

이번 작업 [B] 는 결재자 후보를 **화면에서** 걸렀다. 그런데 저장 경로가 안 보므로
화면을 거치지 않는 저장이면 권한 없는 사람이 그대로 결재선에 앉는다.
그러면 그 사람은 결재함에 못 들어가고 **그 문서가 영영 안 간다.**

## ⚠️ 심각도를 정확히 적는다 — 권한 상승 구멍이 아니다

`POST /api/approval/lines` 는 `[Authorize(Policy = "TenantAdminOnly")]` 다.
정책 실측 — `account_type == "tenant_admin"` 만 통과한다.

⇒ **직원이 권한을 훔치는 자리가 아니다. 대표가 자기 발등을 찍는 자리다.**
   "보안 취약점" 으로 부르면 과장이다. **"자기발등 방지 가드"** 가 맞다.

🔴 이렇게 적는 이유 — 헌법 #32(점수·평가 받아쓰기 금지). 심각도를 부풀리면
   진짜 P0 와 구별이 안 된다.

## 어떻게 찾았나

*"화면에서 거른 게 서버에서도 지켜지나?"* 를 물었다.
저장 경로를 따라가 보니 검증이 **퇴직 여부까지만** 있었다.

## 봉합 — 작업지시서 §7 과 어긋나지 않는다

§7 은 *"막지 말고 알린다"* 인데 여기서는 **막았다.**

| 자리 | 판단 |
|---|---|
| **이미 저장된 결재선** | 알린다 — 갑자기 막으면 **지금 도는 결재가 선다**(§7 이 지키는 것) |
| **지금 새로 저장하는 순간** | 막는다 — 막아야 잘못된 결재선이 **안 생긴다** |

바로 위 퇴직자 검사도 **똑같이 저장 시점에 막는다**(2026-06-20 P1-7). 같은 판단이다.

## 값으로 확인했다

`hitpan_e2e` 에 3명(대표·권한자·무권한자) 세우고 검사 SQL 을 돌렸다.

| | 결과 |
|---|---|
| 봉합 그대로 | **박무권만** 걸린다 (대표는 권한 줄 없어도 통과) |
| `NOT` 절 제거 | **0명** 걸린다 = 저장이 그냥 통과 |

## 남은 것

⚠️ 실측 미완 — 화면에서 저장할 때 이 메시지가 **실제로 뜨는지** 봐야 한다.
   (화면은 이미 후보를 걸러서 보여주므로 정상 경로로는 이 오류가 안 난다.
    **일부러 어긋나게 만들어야** 볼 수 있다.)
