## 1. 무엇이 잘못됐나

`guard-big-md.js:22`:
```js
if (toolInput.offset != null || toolInput.limit != null) process.exit(0);
```
`offset` **또는** `limit` **둘 중 하나만 있어도** 통과(허용)시킨다. 그런데 Read 툴은 `limit` 을 안 주면 **기본값 2000줄**까지 읽는다. 즉 파일이 2000줄 미만이면 `offset:1` 만 주는 것으로 **파일 전체**가 돌아온다 — 정확히 이 훅이 막으려는 그 행동이다(§3-3 근거: "부분 읽기만 허용, 전체 금지").

바이트가 커도 줄 수가 적은 실제 문서에서 특히 치명적이다: `docs/운영기록/INDEX_원본상세_20260911_이력.md` 는 **217KB 인데 172줄뿐**이다. `Read(file_path=…, offset=1)` 하나면 훅은 통과시키고 Read 는 172줄 전부(217KB)를 돌려준다.

## 2. 재현 (node 로 훅 직접 호출, 대조군 포함)

860KB · 402줄짜리 임시 `docs/BIG.md` 를 만들어 동일 훅을 7가지 입력으로 호출:

```
[1 offset·limit 둘다 없음]        → DENY   (정상 — 의도한 동작)
[2 offset:1 만, limit 없음]       → ALLOW  (🔴 통과 — 402줄 전체가 그대로 나간다)
[3 offset:0, limit:null]          → ALLOW  (🔴 동일)
[4 limit:40 만, offset 없음]      → ALLOW  (설계상 의도된 통과 — 실제로 40줄만 나가 문제 없음)
```
`.MD`(대문자 확장자)·워크트리 경로(`.claude/worktrees/x/docs/BIG.md`)·`/` 구분자·INDEX.md(10KB 문턱) 4가지는 전부 정상 DENY — 이 4가지는 **우려한 바이패스가 아니다.**

## 3. 왜 위험한가

- P2 의 존재 이유가 "쉼표 하나 바뀌면 20KB 문서가 통째로 캐시에 다시 쓰인다"(매뉴얼 §3-3)인데, `offset` 하나만 붙이면 그 방지가 무력화된다. 방어가 "명시적 큰 limit" 이 아니라 "**offset 존재 여부**"를 기준으로 삼은 게 원인 — `limit` 이 없을 때 Read 의 기본 동작(최대 2000줄)을 고려하지 않았다.
- 표준 에이전트(hp-designer 등) 카드 문구가 "필요한 절만: Read offset={시작줄} limit={길이}" 라고 **둘 다** 쓰라고 안내하지만, 강제하는 코드는 없다 — 안내문은 코드가 아니다([[feedback_easy_claim_needs_refutation]] 패턴과 동형).

## 4. 봉합 방향 (적발만, 코드는 안 고침)

`offset` 만 있고 `limit` 이 없는 경우를 "무제한 읽기"로 간주해 DENY 유지 — 예: `if (toolInput.limit == null) { /* offset 단독은 무제한과 동일 취급 */ }` 로 조건을 `limit != null` 단독 기준으로 좁히거나, `offset` 이 있어도 `limit` 이 없으면 통과시키지 않는 방향.
