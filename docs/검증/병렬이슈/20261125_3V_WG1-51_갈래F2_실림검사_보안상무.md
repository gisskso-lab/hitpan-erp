### S-1 🔴 (V2 · 설계) 번들 표식 = 「`.net core bundle` 의 SHA-256 을 계산」 은 실물 표식이 아니다

- **근거**: 지시서 §4-2 G3 「표식 = ASCII `.net core bundle` 의 SHA-256 32바이트를 시험이 **계산**해 exe 에서 찾음(바이트를 손으로 적지 않음)」.
- **실측(이 PC · 읽기만 · 작은 스크립트)**
  - `sha256(".net core bundle")` = `db2a6c16fec7fbeb…f90427`
  - 실물 표식(.NET 호스트 고정 상수) = `8b1202b9 6a612038 727b9302 14d7a032 13f5b9e6 efae3318 ee3b2dce 24b36aae`
  - 계산 값 적중: apphost 8.0.27(nuget 캐시) **0** · singlefilehost 8.0.27 **0** · 실물 단일 파일 `HitPan.API.exe`(PM scratch `pub4v_sf` · 151,980,613 B) **0**
  - 고정 상수 적중: 위 셋 모두 **정확히 1회**(apphost @141088 · 머리 위치 0 / 단일 파일 @7953960 · 머리 위치 151,956,997)
  - 즉 .NET 소스 주석의 「SHA-256 for ".net core bundle"」 은 글자 그대로 재현되지 않는다.
- **결과**: 지시서대로 짜면 G3 는 **어느 판에서도 빨강**(거짓 빨강). 개발 탐침 `scratchpad/f2_probe.ps1` 도 계산 값으로 찾는 꼴 → 적중 0 이 날 것.
- **위험(보안 쪽)**: 「표식 0 이니 우회」 하는 손질 — 예) 표식 없이 머리 위치를 끝에서 추정 · 글자 `.net core bundle` 로 찾기 · 표식 못 찾으면 낱개 dll 로 대체 — 이 들어가면 **단일 파일이 아닌 판도 초록**이 되는 길이 열린다.
- **권고**: 지시서 §4-2 「읽는 법이 실측과 다르면 멈추고 설계 회송」 그대로 **회송**. 회송안 제안(설계 몫): 32바이트 고정 상수를 출처 주석과 함께 적고, 시험 안에서 **복원된 apphost 팩**(`microsoft.netcore.app.host.win-x64/{판}/runtimes/win-x64/native/apphost.exe`)에서도 같은 상수가 정확히 1회 나오는지 자기 대조 → 「손으로 적은 바이트」 의 오타 위험을 동작으로 막음. 우회(표식 없는 판 허용) 금지 문구를 지시서에 넣을 것.

### S-2 🟡 (V1) 전용 단계 판정이 「레코드 수」 만 세면 실패 · 스킵도 초록

- **근거**: 지시서 §4-3 ② `dotnet test … --logger trx` · ④ 「`testName="…"` 수를 시험 이름별로 셈 — 1 미만이면 빨강」. 선례 `build-and-test.yml:178` 은 `set -o pipefail` + `| tee` 꼴인데 지시서 ①~⑥ 에 **pipefail · 종료 코드 판정이 글로 없다**.
- **재현(생각 실험 · 꼴 그대로)**: ② 를 `| tee` 로 받고 pipefail 을 빼면 G2 가 실패해도 단계 종료 코드 = tee 의 0 → trx 에 G2 레코드 1건(outcome=Failed) → ④ 통과 → **초록**. 또 누가 G2 에 `Skip=` 을 달면 레코드(outcome=NotExecuted) 1건 · dotnet test 종료 0 → **초록**.
- **권고**: ④ 를 「G1~G4 각각 `outcome="Passed"` 레코드 ≥1」 + 「이 클래스 `outcome="Failed"` · `"NotExecuted"` = 0」 으로. trx 의 `UnitTestResult` 는 `testName` 이 `outcome` 앞에 오므로 한 줄 grep 가능. `set -o pipefail` 필수. [4] R1 에 「G2 를 Skip 시킨 판에서 단계 빨강」 변이 1건 보탤 것을 권함.
- **덧**: DisplayName 에 ⑤ · 🔴 같은 다바이트 글자가 들어간다(기존 ①②③ 도 🔴). bash grep 은 바이트 대조라 동작은 하나, 셈 열쇠를 **메서드 이름**(trx `TestMethod name=`) 이나 ASCII 머리(`F-2 G2` 등)로 두면 깨질 일이 줄어든다.

### S-5 🟢 기록 (V3 · 한계) 「nuget 원본」 이 증명하는 범위

- **CI**: 캐시 없음 → 매 런 새로 받음 · Windows 의 NuGet 은 **풀 때(추출 때)** 꾸러미 서명을 검증 · 추출 뒤 폴더는 다시 검증하지 않음.
- **이 PC 실측**: `questpdf.2026.2.4.nupkg` SHA-512 = `.nupkg.sha512`(`8fhYwSUs…`) 일치 · `.nupkg.metadata` contentHash(`fajBdRJF…`)는 다름 = 서명 꾸러미의 「서명 뺀 내용 해시」 라 정상 · `runtimes/win-x64/native` = 6 이름 그대로.
- **G4 가 증명하는 것** = 「게시 폴더 6개 = **이 런의 복원이 풀어 둔** 6개」. **못 잡는 것** = 꾸러미 원천(피드 · 러너 이미지) 오염 · 추출 뒤 폴더 바꿔치기(로컬 PC). 상수 고정을 뺀 것(§12 Q4 · O14 보류)의 대가로 받아들임.
- **선택 보강(이 갈래 필수 아님)**: 같은 폴더의 `.nupkg`(zip) 안 `runtimes/win-x64/native/*.dll` 항목과도 대조(`System.IO.Compression` · 공용 프레임워크) → 추출 뒤 바꿔치기만 잡음. 원천까지는 `dotnet nuget verify --all` 또는 잠금 파일 contentHash(O14) 가 있어야 함 — O14 결재 때 함께 볼 거리.

### S-10 🟡 (V2 · 증거) 개발명세서 「출시 꼴」 실측 값이 자기 포함(self-contained) 번들과 똑같다

- **권고**: 회송 뒤 다시 잴 때 개발명세서에 「호스트 = apphost / singlefilehost」 · 「번들 안 `System.Private.CoreLib.dll` 유무」 · exe 크기 · 출력 폴더 = 새로 만듦 · publish 명령 전문을 함께 적을 것. [4] R5 에 이 축(출시 꼴이 정말 의존형인가) 추가 권함. 의존형이 맞으면 표식 위치는 수십만 바이트 안쪽이어야 한다.
