# 병렬이슈 PI-16 — UNIQUE 와 NOT NULL 을 어떻게 할지 안 적혀 있다. 지문은 여전히 필수다

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시 병렬검증 **2회차** · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 **§17-2** ("PI-09 를 닫았다") · 작지서 작3 **P2.5** |
| 등급 | 🔴 **P0** — 1차에서 **실제로 DDL 을 건드린다.** 되돌리기 가장 어려운 자리인데 지시가 비어 있다 |
| 상태 | ⬜ 미봉합 |

---

## 1. 무엇이 문제인가

§17-2 는 이렇게 닫았다고 적었다.

> **칸을 나눈다** — 서버가 읽는 하드웨어 식별값을 담을 컬럼을 추가하고,
> `fingerprint` 는 **옛 기기 호환 전용**으로 남긴다.

그런데 PI-09 가 지적한 것은 **컬럼이 없다는 것이 아니라 제약이 막는다는 것**이었다.
현행 제약은 둘이다.

| 제약 | 무엇을 막나 |
|---|---|
| `fingerprint varchar(64) **NOT NULL**` | 지문 없이는 **줄을 만들 수 없다** |
| `UNIQUE KEY uq_tenant_fp (tenant_id, fingerprint)` | 회사 안에서 지문이 **겹치면 안 된다** |

🔴 **§17-2 는 이 둘을 어떻게 할지 한 글자도 적지 않았다.**
컬럼만 추가하고 `NOT NULL` 을 그대로 두면 **지문은 여전히 필수**이고, PI-09 가 지적한 자리가 그대로 남는다.

작지서 P2.5 도 마찬가지다.
> - [ ] UNIQUE 제약 재설계 — 한 줄이 장비넘버와 지문을 **동시에** 가질 수 있게

"재설계" 라고만 적혀 있다. **무엇으로 바꾸는지가 없다.**
헌법 #33(의중 100% 이해 후 코드)·명세서 §3 서문(*"정하지 않으면 구현자가 임의로 고른다"*) 위반이다.

## 2. 근거 (실측)

### (1) 현행 DDL — `installer/hitpan_db_clean.sql:3734, 3748`
```sql
`fingerprint` varchar(64) NOT NULL COMMENT 'UA+OS+해상도+시간대 SHA-256',
...
UNIQUE KEY `uq_tenant_fp` (`tenant_id`,`fingerprint`),
```

### (2) 메인PC 는 이 칸에 **자기 지문을 채워 넣어** 줄을 만든다

`src/HitPan.API/HostedServices/MainPcRegistrationService.cs:200-210`
```sql
INSERT INTO tenant_devices
  (device_id, tenant_id, user_id, device_type, device_name,
   fingerprint, ip_address, user_agent, status, is_main_pc, ...)
VALUES
  (@Id, @TenantId, NULL, 'pc', @Name,
   @Fp, NULL, NULL, 'approved', 1, ...)
```
`@Fp` 는 `BuildServerFingerprint()` 가 만든 `MAINPC-…` 다 (`:238`).

🔴 **여기가 핵심이다.** 메인PC 는 지금 **`fingerprint` 칸을 점유하고 있다.**
설계 §4-5 는 "메인PC 와 그 PC 브라우저 접속이 한 줄로 합쳐져야 한다" 고 한다.
그러려면 **한 줄이 `MAINPC-…`(하드웨어) 와 `HFPv2-…`(브라우저) 를 동시에** 가져야 하는데,
새 컬럼을 추가한 뒤에도 **기존 메인PC 행의 `fingerprint` 에는 `MAINPC-…` 가 들어 있다.**
그 줄에 브라우저 지문을 쓰려고 하면 **덮어써야 한다**(헌법 #1 위반 소지) 또는 **UNIQUE 충돌**이 난다.

⇒ **컬럼 추가만으로는 §4-5 가 여전히 성립하지 않는다.** 기존 행의 **데이터 이동(migration)** 이 필요하다.
§17-2 도 작지서도 **그 이동을 언급하지 않았다.**

### (3) 🔴 UNIQUE 를 바꾸면 기존 데이터가 걸린다 — 다루는 곳이 없다

지시 프롬프트가 물은 것 — *"중복 행이 있으면 마이그레이션이 실패한다. 그 경우를 다루는가"* — 의 답은 **안 다룬다.**

작지서 6장 리스크에 이렇게만 적혀 있다.
> **UNIQUE 제약 변경이 되돌리기 어려움** | **중** | 🔴 변경 전 **백업 필수**. 실사용 고객 0 이나 demo·테스트 데이터 보존

🔴 **"백업" 은 대응이 아니라 사고 후 수습이다.** 그리고 *"실사용 고객 0"* 은 **틀린 전제다** —
사장님은 8/15 시점에 **1.2.80 을 게시**했고 demo 가 돌고 있다(메모리 진실원).
게다가 §7 이 *"되돌릴 수 없는 위험 — 기존 고객 재매핑"* 을 이미 P0 로 적어놨다. **문서 안에서 서로 모순된다.**

## 3. 터지면 무슨 일이 나나

| 구현자의 선택 | 결과 |
|---|---|
| `fingerprint` 를 `NULL` 허용으로 바꾼다 | 🔴 **UNIQUE 가 무력해진다.** MySQL/MariaDB 는 **NULL 을 중복으로 안 본다** ⇒ `(tenant, NULL)` 이 **무한히 들어간다** ⇒ 🔴 **같은 기기가 계속 새 줄을 만든다 = 사장님이 고치라는 증상 그 자체가 악화** |
| `NOT NULL` 유지 + 새 컬럼만 추가 | PI-09 미봉합. 메인PC 합류 여전히 불가 |
| UNIQUE 를 새 컬럼으로 옮긴다 | 옛 기기는 새 컬럼이 NULL ⇒ 위와 같은 무력화 |
| UNIQUE 를 그냥 DROP 한다 | 🔴 **중복 방어가 사라진다.** 동시 로그인 2창이면 두 줄(→ PI-13 · G-16 과 충돌) |

🔴 **네 갈래가 전부 나쁘다.** 그런데 설계는 어느 것도 고르지 않았다.
**가장 그럴듯한 선택(NULL 허용)이 가장 나쁜 결과를 낸다** — 이것이 이 건이 P0 인 이유다.

## 4. 어떻게 고치나

설계가 **다음을 명시**한 뒤에 P2.5 를 착수한다.

1. **`NOT NULL` 을 유지한다.** 대신 **채울 값의 규칙을 정한다** —
   지문이 없는 기기는 `device_id` 를 지문 칸에 넣는 식으로 **항상 유일한 값이 들어가게** 한다.
   (NULL 허용은 UNIQUE 를 무력화하므로 **금지**로 명문화)
2. **UNIQUE 를 둘로 나눈다** — 새 하드웨어 컬럼에 **별도 UNIQUE**(`tenant_id`, 새컬럼) 를 걸되,
   NULL 중복 문제를 피하려면 **부분 인덱스가 없는 MariaDB 특성상** 애플리케이션 보장 + `INSERT ... ON DUPLICATE KEY` 로 간다.
   🔴 **어느 쪽을 택할지 설계가 정한다.** 구현자에게 남기지 않는다.
3. **기존 메인PC 행의 데이터 이동을 마이그레이션에 포함한다** —
   `UPDATE tenant_devices SET 새컬럼 = fingerprint WHERE fingerprint LIKE 'MAINPC-%'`.
   이것이 빠지면 §4-5 는 코드를 아무리 고쳐도 안 된다.
4. **마이그레이션 앞에 중복 검사 SELECT 를 넣는다.** 중복이 있으면 **ALTER 를 실행하지 않고 멈춘다.**
   조용히 실패하면 고객 DB 가 반쯤 바뀐 상태로 남는다.
5. 위치는 `src/HitPan.API/Migrations/SQL/DB-100_*.sql` — **현재 최신은 DB-99**(실측: `DB-99_employee_work_status.sql`).
   ⚠️ 명세서·작지서가 인용한 *"최신 DB-91"* 은 **낡은 값**이다.

## 5. 판정

🔴 **PI-09 는 절반만 닫혔다.** "칸을 나눈다" 는 방향은 맞지만,
**제약(NOT NULL·UNIQUE)·기존 데이터 이동·중복 대응** 셋이 비어 있다.
**1차에서 실제로 DDL 을 건드리는 차수**이므로 이 셋을 채우기 전에는 P2.5 착수를 보류해야 한다.
