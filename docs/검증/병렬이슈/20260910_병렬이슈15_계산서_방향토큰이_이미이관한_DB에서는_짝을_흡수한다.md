## 1. 무엇을 잰 것인가

갈래 C 개발자가 보고서 (f)2 에 *"옛 DB 위에서 한 쌍이 한 행으로 흡수될 수 있다"* 고 **추정**으로 적었다. 추정을 그대로 넘기지 않고 `hitpan_e2e` 에서 실물 표 구조로 재현했다(테스트 표 `zz_3v_ti`/`zz_3v_stage` — 실제 `tax_invoices` 는 읽지도 쓰지도 않았고 시험 뒤 지웠다. `tax_invoices` 66,610행 불변 확인).

시험은 `CREATE TABLE … LIKE tax_invoices` 로 **UNIQUE 4종을 그대로** 가진 표를 만들고, 코드와 같은 모양의 `INSERT … SELECT … FROM stage ORDER BY source_id ON DUPLICATE KEY UPDATE invoice_no = VALUES(invoice_no), …` 를 그대로 던졌다.

## 2. 결과 — 세 경우가 갈린다

| 시작 상태 | 재이관 후 | 판정 |
|---|---:|---|
| **빈 DB** (덮어쓰기 후 · 신규 고객) | **2행** — `B-…`/`S-…` 각 1 | ✅ C1 이 의도대로 |
| 이미 이관한 DB · 옛 행의 `direction` 이 `source_id` 토큰과 **맞는** 경우 | **2행** | ✅ 옛 행은 새 형식으로 제자리 정정되고 짝은 새로 들어온다 |
| 이미 이관한 DB · 옛 행의 `direction` 이 토큰과 **어긋난** 경우 (e2e 실측 **14행** 중 토큰 2 인데 `B` 인 **8행**) | 🔴 **1행** | ❌ 짝의 한쪽이 흡수돼 사라진다 |

세 번째가 왜 그런지 — 후보 2개가 **서로 다른 UNIQUE 로 같은 한 행**을 잡는다.
1. `mig-1`(매입) 후보가 `uq_tax_invoices_io_no(tenant, direction, tax_no)` 로 옛 행(`direction='B'`)을 잡아 그 행을 매입으로 갱신한다. `source_id` 는 갱신 목록에 없어 `mig-2` 인 채 남는다.
2. 이어서 `mig-2`(매출) 후보가 `uq_tax_invoices_source` 로 **같은 행**을 다시 잡아 매출로 덮는다.
⇒ 두 후보가 한 행에 겹쳐 앉고 매입 쪽이 없어진다. `ORDER BY source_id` 는 순서를 고정할 뿐, **다른 열쇠로 같은 행에 닿는 것**은 막지 못한다.

## 3. 이것이 뜻하는 것

- 🔴 **작지서 §5 의 실측 기준 `tax_invoices = 66,631` 은 "빈 DB 에 이관" 일 때만 성립한다.** 이미 이관한 DB 위에 병합 재이관하면 66,631 − (어긋난 짝 수) 가 나온다. 검증팀장은 이 조건을 붙여 재야 한다 — 안 그러면 **정상 동작을 결함으로**, 또는 **결함을 정상으로** 읽는다.
- 회귀는 아니다. 1.3.38 도 같은 자리에서 21쌍을 합쳤다(승자만 무작위였다). C1 은 **빈 DB 를 확실히 고치고, 옛 DB 는 그대로 둔다**.
- 근본 해소는 **덮어쓰기 모드**(작22 A1)다. 사장님 Q1 답 후 A1 이 서면 재이관 경로가 "초기화 → 빈 DB → 이관" 이 되어 이 자리 자체가 사라진다.

## 4. 지금 하지 않는 것과 그 이유

재이관 전에 옛 행의 `direction`·`invoice_no` 를 토큰 기준으로 미리 정정하는 한 줄(UPDATE)을 넣는 안을 검토했고 **넣지 않았다**:
- 방향을 뒤집는 UPDATE 는 `uq_tax_invoices_io_no` 에서 **다른 행과 충돌(1062)** 할 수 있고, 그러면 이관 전체가 그 자리에서 죽는다. 지금 증상(1행 흡수)보다 나쁜 결과다.
- 작지서 §2 "하지 않는 것" 밖의 신설이라 **PM 결재 범위를 넘는다**(헌법 #33·#42).
⇒ 대신 **덮어쓰기 후 재이관**을 공식 경로로 못 박고(이미 결1 §3-④ · 9/9 인계1 에 있다), 검증 기준에 조건을 붙인다.

## 6. 곁가지로 확인된 것 (둘 다 ✅)

- `INSERT … SELECT … ORDER BY … ON DUPLICATE KEY UPDATE` 는 **MariaDB 11.4 에서 그대로 실행된다**(구문 오류 없음). 빌드·단위시험이 못 잡는 자리라 실물 DB 에 던져 확인했다 — 8/26 `0AND` 파싱 사고와 같은 계통이기 때문이다.
- 갈래 D 의 `hr_reports` 19컬럼 multi-row `INSERT IGNORE` 도 실물 표 사본에 두 번 던져 **1차 2행 · 2차 0행 · 합계 2행**(멱등) 확인. 컬럼 19 ↔ 값 19 일치.
