# 병렬이슈 PI-17 — 계수·티어는 5곳이 아니다. `SessionLimitMiddleware` 가 통째로 빠졌다

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시 병렬검증 **2회차** · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 **§17-3** ("5곳") · **§17-4**(`enterprise` 정정) · 작지서 작3 **P1·P2** |
| 등급 | 🟠 **P1** — 1차 작업 범위가 실제보다 좁게 잡혀 있다. 고쳐도 한 자리가 남는다 |
| 상태 | ⬜ 미봉합 |

---

## 1. 무엇이 문제인가

§17-3 은 1차 초안의 "4곳" 을 **"5곳"** 으로 정정하며 이렇게 적었다.

> 1차 초안 "4곳" 은 부정확하다. **5곳이고 모양이 서로 다르다.**

🔴 **5곳도 부정확하다.** 티어로 한도를 정하는 자리가 **하나 더 있다.**
그리고 그 자리는 §17-4 가 고치겠다는 **`premium` 문자열을 똑같이 쓰고 있다.**

`src/HitPan.API/Middleware/SessionLimitMiddleware.cs:15-22`
```csharp
private static readonly Dictionary<string, int> TierLimits = new()
{
    ["basic"] = 8,       // PC5 + 모바일3
    ["pro"] = 20,        // PC10 + 모바일10
    ["premium"] = 100,   // PC50 + 모바일무제한
    ["trial"] = 50,      // 체험판
    [""] = 50            // 기본값 (개발 모드)
};
```

🔴 **`premium` 이 여기에도 있다.** §17-4 는 *"코드만 `premium`"* 이라며 `TenantDeviceService:666` **한 자리만** 가리켰다.
작지서 P2 도 `GetLimitsForTier(:662-669)` 한 곳만 적었다.
⇒ **`enterprise` 로 정정해도 이 자리는 그대로 남아**, 최상위 고객이 **동시 세션 50**(기본값) 으로 떨어진다.
사고의 **모양만 바뀌고 사라지지 않는다.**

---

## 2. 근거 (실측) — 왜 이 자리가 같은 사고인가

### (1) 주석의 숫자가 이미 서로 안 맞는다
`SessionLimitMiddleware` 주석은 `basic = PC5 + 모바일3` 이라 적었고,
`TenantDeviceService.GetLimitsForTier:663` 도 `"basic" => (5, 3)` 이다. **여기까지는 맞다.**

그런데 `pro` 는
- `SessionLimitMiddleware:17` — 주석 `PC10 + 모바일10`
- `TenantDeviceService:664` — `"pro" => (10, 8)` ⇒ **모바일 8**

🔴 **같은 티어의 한도가 두 파일에서 다르다.** 이미 갈라져 있다.
⇒ P2 가 `GetLimitsForTier` 만 설정화하면 **이 불일치가 설정과 코드로 갈려 더 굳어진다.**

### (2) `premium`/`enterprise` 불일치는 §17-4 가 본 것보다 넓다 (실측)

| 자리 | 값 | 근거 |
|---|---|---|
| `TenantDeviceService.cs:666` | `premium` | §17-4 가 본 유일한 자리 |
| 🔴 `SessionLimitMiddleware.cs:19` | `premium` | **§17-4 가 못 본 자리** |
| `local_subscription` DDL | `enterprise` | `installer/hitpan_db_clean.sql:1978` — `COMMENT 'basic / pro / enterprise'` |
| 백오피스 시리얼 발급 | `enterprise` | `ResellerSerialController.cs:86-87` — `basic/pro/enterprise` 아니면 **400 거부** |
| 랜딩 결제 | **둘 다** | `PaymentPage.razor:121-124` — `"premium" => "enterprise"` **호환 변환이 이미 있다** |

⭐ **주목** — `PaymentPage.razor:121` 에 이런 주석이 있다.
```csharp
// 옛 키 호환: premium → enterprise, standard → pro
```
🔴 **랜딩은 이미 `premium` 을 옛 이름으로 판정하고 변환하고 있다.**
즉 `enterprise` 가 정답이라는 §17-4 의 판정은 **맞다.** 다만 **고칠 자리를 하나 빠뜨렸다.**

### (3) 지시 프롬프트가 물은 것 — *"DB 에 `premium` 으로 저장된 행이 있으면?"*

**있을 수 있다.** 근거:
- 랜딩이 **옛 키 호환 변환을 두고 있다** = 과거에 `premium` 이 흘러다녔다는 증거
- `local_subscription.subscription_tier` 는 `varchar(20)` 이고 **CHECK 제약이 없다** (`hitpan_db_clean.sql:1978`)
- 값을 채우는 경로가 웹훅이다 — `WebhookInboundController.cs:103-120` 이 백오피스에서 받은 값을 그대로 쓴다

⇒ `premium` 행이 남아 있는 상태에서 코드만 `enterprise` 로 바꾸면
**그 행이 `_ => (5,3)` 으로 떨어진다.** 🔴 **지금과 정반대 방향으로 같은 사고가 난다.**
작지서 P2 에 **데이터 정정(UPDATE) 이 없다.**

---

## 3. 터지면 무슨 일이 나나

1. 최상위 고객이 **기기 한도는 고쳐지고 동시 세션은 여전히 기본값** ⇒ 접속이 막히는 새 증상
2. `premium` 으로 저장된 기존 행이 있으면 **정정이 오히려 한도를 떨어뜨린다**
3. `pro` 모바일 한도가 8 인지 10 인지 **아무도 모르는 채로 설정 초기값이 정해진다**
   ⇒ 작지서가 *"현행 값을 초기값 그대로"* 라고 했는데 **현행 값이 두 개다.** 지시를 따를 수 없다

---

## 4. 어떻게 고치나

1. **P1 대상에 `SessionLimitMiddleware.cs:15-22` 를 추가한다.** 계수는 5곳이 아니라 **6곳**이다.
2. **`enterprise` 정정을 두 파일 동시에** 한다. 헌법 #12(구현체 전수 grep) 를 실제로 돌린다 —
   `grep -rn '"premium"' --include=*.cs src/` 가 **0 이 될 때까지**.
3. **데이터 정정 SQL 을 같은 마이그레이션에 넣는다** —
   `UPDATE local_subscription SET subscription_tier='enterprise' WHERE subscription_tier='premium'`.
   코드만 고치면 저장된 행이 반대로 떨어진다.
4. **`pro` 모바일 한도를 사장님이 확정한다** (8 인가 10 인가). 설정 초기값이 여기서 갈린다.
   🔴 **PM 이 임의로 고르면 그것이 곧 요금이 된다.**
5. 티어 문자열을 **한 곳에 모은다**(상수 클래스). 지금은 문자열이 파일마다 흩어져 있어 같은 사고가 반복된다.

---

## 5. 판정

🟠 **§17-3 의 "5곳" 과 §17-4 의 "코드만 premium" 은 둘 다 실측이 덜 됐다.**
1회차 PI-11 이 *"사실오류 — 실측이 덜 됐다"* 를 지적했는데, **개정본에서 같은 종류의 누락이 다시 났다.**
착수 전 `grep` 한 번으로 닫히는 건이므로 **1차 범위 안에서 바로 정정 가능하다.**
