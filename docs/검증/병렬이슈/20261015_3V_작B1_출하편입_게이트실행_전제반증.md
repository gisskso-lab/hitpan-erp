## 1. 🔴 지금 멈춰야 할 것 — V7-a 갈래 B 의 DI 수명 (착수 중이면 즉시)

🟢 실측 — `IEmailSender` 는 **Singleton** 이다.

- `src/HitPan.Backoffice.API/Program.cs:43` — `AddSingleton<IEmailSender, EmailSender>()`
- `src/HitPan.Backoffice.API/Services/EmailSender.cs:30-36` — 생성자 인자는 `IConfiguration` · `ILogger` **둘뿐**

§4 **B-3** 은 *"B-2 가 커넥션을 받아야 할 때만 DI 1줄 추가"* 로만 적혀 있다. 여기서 **Scoped 커넥션·Scoped 팩토리**를
Singleton 에 주입하면 ASP.NET Core 의 범위 검증이 기동 시 `InvalidOperationException`
(*Cannot consume scoped service from singleton*) 으로 **백오피스 전체를 못 띄운다**. 갈래 B 혼자 빌드 0/0 이어도
합류·기동에서 터지는 모양이고, 이것이 10/7 작8 「갈래별 0/0 ≠ 합류 0/0」과 **같은 씨앗**이다.

🟢 안전한 길은 이미 레포에 선례가 있다 — 백오피스 연결문자열은 `ConnectionStrings:BackofficeDb` 키 하나로
구성에서 꺼내 쓴다(`BackofficeCsOutboundGateTests.cs:537` · `BackofficePromotionPricingDbGateTests.cs:180` 이 그 키로 조립).
`EmailSender` 는 **이미 `IConfiguration` 을 들고 있으므로** 그 키로 자기 `MySqlConnection` 을 열면
**B-3 은 0줄**이 되고 수명 충돌도 0 이다.

⇒ **PM 조치 제안**: §4 B-3 을 *"`IConfiguration` 의 `ConnectionStrings:BackofficeDb` 로 자체 커넥션 ·
DI 등록 변경 0줄. 수명(Singleton) 변경·Scoped 주입 금지"* 로 못 박는다. 결재조건 3(교집합 0)과도 맞는다.

## 3. 반증 기록

### V1 — 출하 편입: 「새 게이트 불필요」는 **절반만** 맞다

🟢 **자동 포함은 사실이다.** 복사 규칙이 손으로 적은 목록이 아니라 **와일드카드**다.

- `src/HitPan.Backoffice.API/HitPan.Backoffice.API.csproj:38-41`
  `<Content Include="..\..\installer\backoffice\*.sql" … CopyToOutputDirectory CopyToPublishDirectory />`
- `src/HitPan.Tests/Integrity/BackofficeSchemaShipGateTests.cs:67-80` — **개수·명단을 손으로 적지 않는다.**
  레포 폴더를 `Directory.GetFiles(…, "*.sql")` 로 긁어 `expected` 를 만들고 `expected.Except(actual)` 로 본다.
  ⇒ 46 을 더하면 `expected` 가 자동으로 1 늘고, 산출물에 없으면 그 자리에서 FAIL 한다.
- 🟢 **전이 복사도 실측했다** — 빌드 결과물에 이미 실려 있다.
  `src/HitPan.Tests/bin/{Debug,Release}/net8.0/installer/backoffice/*.sql` = **30개**(15 × 2구성) ·
  `src/HitPan.Backoffice.API/bin/*/net8.0/installer/backoffice/*.sql` = **30개** · 레포 원본 = **15개**.
  (`src/HitPan.Tests/HitPan.Tests.csproj:42` 가 백오피스 API 를 ProjectReference 하므로 Content 가 따라온다.)
- 🟢 하드코딩 개수 함정도 없다 — `BackofficeSchemaMysql8GateTests.cs:367` 은 `files.Count >= 14`(이상)이라
  16개가 되어도 안 깨진다. 전시명의 「14파일」은 글자일 뿐 판정식이 아니다.

🔴 **그러나 이 게이트가 **못 무는 것 2개**가 10/14 작9 사고의 실제 자리다.**

1. **`publish` 단독 회귀를 못 본다.** 게이트가 재는 곳은 `AppContext.BaseDirectory/installer/backoffice`
   (`:44-45`) = **빌드** 산출물이다. 배포가 rsync 하는 것은 **publish** 산출물인데, 같은 한 줄의
   `CopyToPublishDirectory` 만 지워도 **게이트는 초록인 채 서버에 .sql 이 0줄**이 된다 —
   10/08 사고와 글자까지 같은 모양이다. csproj 주석(`:21-22`)·시험 주석이 스스로 *"대리 측정"* 이라 적고 있다(🟡).
2. **「실렸다」 ≠ 「적용됐다」.** 적용은 `HITPAN_BO_AUTO_MIGRATE=1` 일 때만 돈다
   (`SchemaMigrator.cs` ApplyAsync 머리 · 폴더 없으면 `LogWarning` 후 `return` = 예외 없이 통과).
   운영 NCP 의 그 값은 🔴**기록없음**이고, 10/14 작9 의 「시드는 적용됨인데 산물이 없다」는 바로 이 틈이었다.

⇒ **판정**: §4 의 🟢*"출하 편입은 새 게이트가 필요 없다"* 는 **「산출물에 실린다」 범위에서만 승인 가능**.
PM §13 확1 이 이미 이것을 **게시 차단 조건**으로 돌려놓았으므로 재발은 *게시* 단계에서 막힌다 —
다만 작지서 문장이 「게이트 초록 = 출하 안전」으로 읽히면 안 된다. **문구에 1·2 를 명시**해야 [4] 가 인정한다.

### V3 — §13 ⓑ 는 #36·#37·`:176` 과 충돌하지 않는다

🟡 코드 주석이 **백오피스 DDL 의 별개 진실원**을 직접 선언한다 —
`src/HitPan.Backoffice.API/Services/SchemaMigrator.cs` §「20261011작1」 머리:
*"`installer/backoffice/*.sql` 은 한 글자도 안 고친다 — 백오피스 DDL 진실원(#36·#37·#41)이고 … 보정은 적재기 한 곳에서만"*.
🟢 코드로도 선다 — 적재 경로는 `Directory.GetFiles(_scriptsDir, "*.sql")` 하나뿐이고(ApplyAsync),
ERP 출하 DDL(`hitpan_db_clean.sql`)에 백오피스 표가 들어가는 경로는 **0건**이다.
⇒ #36 의 「단일 진실원」은 **ERP 신규설치** 축이고 백오피스는 적재기 축이다. **두 축이 겹치지 않는다.**
`:176` 주석의 「한 글자도 안 고친다」가 **기존 파일 수정** 금지라는 PM 독해도 맞다 —
그 문장의 이유로 적힌 것이 *"그 파일을 파싱해 표→칸 색인을 만드는 게이트(`BackofficeColumnContractGateTests`)가 산다"*,
즉 **내용 변경**이 색인을 깨는 것을 막는 문장이고 신규 파일 추가는 색인을 **늘릴 뿐**이다.

### V4 — `46` 은 공석이고, 백오피스는 **번호가 키가 아니다**

🟢 `installer/backoffice/*.sql` 실측 **15개** = `00·10·11·20·30·31·32·40·41·42·43·44·45·90·91` ⇒ **46 공석**.
🟢 9/25 전례(번호 겹치면 뒤 파일 skip)는 **이 적재기에 해당하지 않는다** —
`_schema_migrations` 의 `PRIMARY KEY (file_name)` 이고 멱등 판정은 **파일명 + 내용 SHA256** 쌍이다
(`SchemaMigrator.cs` ApplyAsync 중단부 — `QueryHashAsync(db, fileName, …)`).
같은 번호의 다른 파일명이면 **둘 다 적용된다** ⇒ 조용한 skip 없음.
⚠️ 다만 적재 순서는 `OrderBy(fileName, StringComparer.Ordinal)` **문자열 순**이다. 두 자리 번호에서는
46 이 45 뒤·90 앞으로 정확히 들어가지만, 장래 **세 자리(`100_`)** 를 쓰면 `100_` 이 `20_` **앞**으로 간다.
지금 사고는 아니고, 46 에는 영향 0.

### V5 — 「값 없이 검증」은 선다. 단 **병렬 오염 장치가 작지서에 없다**

🟢 구조 실측 — `CredentialsStatusController.cs` `Probe(envName, configKey, display)` 는
`Environment.GetEnvironmentVariable(envName)` **직접 호출** → 없으면 `_config[configKey]` 폴백 →
`Present` = 공백 아님. ⇒ 컨트롤러를 **직접 new** 하고 가짜 `IConfiguration` 만 주면 호스트 없이 잰다.
`Environment.SetEnvironmentVariable` 로 넣고 되돌리는 것도 가능하다. **설계 주장 자체는 깨지지 않았다.**

🔴 **그러나 환경변수는 프로세스 전역**이고 xUnit 은 **컬렉션 단위로 병렬**이다.
`src/HitPan.Tests` 안의 다른 게이트가 같은 순간 환경변수를 읽는다(`DbGateEnvironment.cs:33`·`:103` —
`HITPAN_REQUIRE_DB`·`HITPAN_GATE_SKIP_OK`). 이름이 달라도 **같은 프로세스**라서,
G1 게이트가 `Smtp__*`/`HITPAN_SMTP_*` 를 넣고 되돌리는 사이에 다른 시험이 **같은 이름**을 읽으면 결과가 흔들린다.
🟢 레포에 **이미 쓰는 봉합**이 있다 — `[Collection(...)]` 로 직렬화
(`BackofficeSettlementStatusGateTests.cs:26` · `BackofficeRoleScopeGateTests.cs:21` · `BackofficeRoleDowngradeGateTests.cs:54`).
10/14 작9 에서도 *"[Collection] 을 더한 뒤 재측정"* 으로 같은 처방을 썼다(🟡 `build-and-test.yml` db-gate 주석).
⇒ **A-2 에 `[Collection]` + `try/finally` 원복을 작지서 조건으로 넣어야** G1 이 「선다」고 볼 수 있다. 지금 §5·§7-1 에 그 글자가 **0건**이다.

*"healthz 가 보는 키 이름 집합 = 발송기가 읽는 집합과 **완전일치**(차집합 0)"* 인데,

또한 발송기의 **차단 조건은 `Host`·`User` 둘뿐**(`:58` — `Password` 가 비어도 발송을 시도한다)이라

⇒ ⓒ 를 *"healthz 가 보는 키가 전부 `Smtp:*` 정본 이름이다(폐기 `HITPAN_SMTP_*` 0건) ·
healthz 의 **차단 판정**이 발송기의 차단 조건(`Host`·`User`)과 **같은 방향으로** 움직인다"* 로
고치지 않으면, [3] 은 **달성 불가한 숫자** 아니면 **글자검사**로 갈 수밖에 없다.

### V6 — G2 에 「실 DB 없이 초록」 길이 **열려 있다**

🟢 결정적 실측 — 워크플로 **최상단 env** 에 `HITPAN_GATE_SKIP_OK: "1"` 이 걸려 있다
(`.github/workflows/build-and-test.yml:57`). ⇒ `build` 잡(DB 없음)에서 `SkipOrFailStrict` 는
`Verdict.Skip` 로 떨어져 `[SKIP]` 한 줄만 찍고 **`true` 를 돌려주며 PASS** 로 집계된다
(`DbGateEnvironment.cs:112-117`). `[SKIP]` 은 stdout/stderr 뿐이라 `dotnet test` 요약에서 **안 보인다**
(그 함정 자체가 `:61-67` 주석에 적혀 있다).
⇒ G2 가 `db-gate` 에 **등록되지 않으면**, `build` 잡의 초록만 보고 「표에 실패 1행이 남는다」가 통과된 것으로 읽힌다.
§5 ⓑ 가 `:1194` 등록을 적어 두었고 PM §13 확2 가 **「`[SKIP]` 없이 돌았다는 증거(이름+소요시간)」** 를 조건으로 박았다 —
🟢 **이 조건이 이 구멍의 유일한 마개**다. 그래서 확2 는 **권고가 아니라 반려 사유**로 유지해야 한다.

🟢 **G2 ⓐ-1 의 전제는 코드로 성립한다**(여기는 안 깨졌다) — 미설정 시 `EmailSender` 는
`LogInformation` 후 **`return false`**(`EmailSender.cs:58-63`)다. ERP 쪽 거짓 `true`(갈래 C 의 과녁)와 달리
백오피스 발송기는 거짓말을 하지 않으므로 「실패 1행」이 의미를 가진다.
