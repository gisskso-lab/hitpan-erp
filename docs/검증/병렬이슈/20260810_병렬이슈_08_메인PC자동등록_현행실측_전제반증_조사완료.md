## 0. ⭐ 먼저 — 작업지시서의 전제를 반증한다

작업지시서 §1-4 는 두 가지를 적었다. **하나는 맞고, 하나는 틀렸다.**

| 작업지시서 문장 | 실측 판정 | 근거 |
|---|---|---|
| *"버튼은 있는데 눌러도 되지 않는 상태일 가능성이 높다"* | ✅ **맞다 — 확정** | `UserInfoPage.razor.cs:82-88` — 항상 첫 갈래로 빠져 안내만 내보낸다 |
| *"DB 를 가진 메인PC 라는 개념 자체가 없다 — 모든 기기가 동등하게 취급된다"* | 🔴 **틀렸다** | `AuthController.cs:43-56` — **메인PC 개념은 이미 있고 이미 돌고 있다** |

🔴 **이것이 이번 병렬검증의 핵심 적발이다.**
`AuthController.cs:43-50` 에 **loopback = 메인PC** 판정이 이미 구현되어 있고,
2026-07-02 사장님 결재(작1)로 들어간 코드다. 주석 원문:

`src/HitPan.API/Controllers/AuthController.cs:43-48`
```

//   메인PC = 데이터+ERP 설치마법사가 깔린 PC(1도메인 1대). 설치 시점에 이미 등록된 존재라
//   접속 기기인증/슬롯에서 제외한다. 클라이언트PC(브라우저 접속)만 기기 슬롯 대상.
//   판별 = loopback 접속 여부.
```

⇒ **"개념이 없다"가 아니라 "개념은 있는데 화면에 안 보인다"** 가 정확한 현행이다.
T3·T4 는 **새로 만드는 일이 아니라 이미 있는 판정을 화면까지 잇는 일**에 가깝다.

⚠️ 다만 그 주석의 *"설치 시점에 이미 등록된 존재"* 는 **사실이 아니다** — 설치마법사는
`tenant_devices` 에 아무것도 넣지 않는다(§3-2). **면제만 있고 등록은 없다.**
즉 메인PC 는 **"등록된 기기"가 아니라 "검사를 건너뛰는 기기"** 다. 이 간극이 T3 의 실체다.

## 4. 메인PC 를 어떻게 판정할 수 있나 (구현 가능성)

### 질문 4-1. ERP API 가 자기 PC 에 로컬 MariaDB 가 있는지 알 수 있나 — ✅ **알 수 있다**

`src/HitPan.Infrastructure/Extensions/InfrastructureExtensions.cs:20`
```csharp
var host = TenantConfigReader.Get("DB_HOST") ?? "localhost";
```

`installer/HitPan-Universal.iss:1825`
```

```

⇒ **설치마법사가 `db.conf` 에 `DB_HOST=localhost` 를 직접 기록한다.**
ERP API 는 이 값을 읽어 **자기 DB 가 로컬인지 즉시 알 수 있다.** 통신 0회, 본사 의존 0(헌법 #30).

같은 `TenantConfigReader.Get("DB_HOST")` 를 쓰는 곳이 이미 8곳 이상 —
`CompanyBootstrapProvisioner.cs:33` · `AuditLogMiddleware.cs:87` · `IntegrityCheckService.cs:145` ·
`IdempotencyCleanupService.cs:64` · `WebhookInboundController.cs:172` ·
`AppDbContextFactory.cs:14` · `MigrationDbConnectionFactory.cs:32` · `tools/MigrationIdempotencyCheck/Program.cs:42`

**판정: 있음. 기존 패턴 그대로 쓰면 된다(신규 인프라 0).**

### 질문 4-2. 연결 문자열이 localhost/127.0.0.1 인지로 판정 가능한가 — ⚠️ **가능하나 단독으로는 약하다**

| 관점 | 판정 |
|---|---|
| 기술적 가능성 | ✅ `InfrastructureExtensions.cs:20` 의 `host` 값 비교면 끝 |
| **⚠️ 반증** | **API 프로세스가 도는 PC = DB 가 있는 PC** 는 성립하지만, **그 판정을 브라우저에 어떻게 전하느냐**가 별개 문제 |

🔴 **핵심 반증**: 클라이언트PC 는 **자기 PC 에 ERP API 가 없다.** 브라우저로 메인PC 의
API 에 붙는다. 그러므로 API 가 *"내 DB 는 localhost 다"* 라고 답하면 **클라이언트PC 브라우저도
똑같은 "예" 를 받는다.** DB_HOST 만으로는 **"이 서버가 DB 를 갖고 있다"** 는 알아도
**"지금 보고 있는 이 브라우저가 그 PC 위에 있다"** 는 알 수 없다.

⇒ **두 값이 함께 필요하다:**
| 알아야 할 것 | 쓸 수 있는 값 | 위치 |
|---|---|---|
| 이 서버가 DB 보유 서버인가 | `DB_HOST` | `InfrastructureExtensions.cs:20` |
| 이 접속이 그 PC 본인인가 | **loopback 여부** | `AuthController.cs:49-50` |

**loopback 판정이 이미 있다는 것이 T3·T4 에서 가장 중요한 실측이다.**

| D | 메인PC 여부 **DB 컬럼** | 컬럼 자체 부재 | ❌ **없다** | `hitpan_db_clean.sql:3423-3445` |
| E | **설치 시 자동 등록** 경로 | 설치마법사가 등록 0건 | ❌ **없다** | `.iss` 전체에 `tenant_devices` 0건 |
| F | 화면의 **메인PC 표식** | 표시 UI 0건 | ❌ **없다** | `UserInfoPage.razor:230-284` |
| G | `[이 컴퓨터 등록]` **실동작** | 도달 불가 코드 | ❌ **없다** | `UserInfoPage.razor.cs:82-88` |
| H | 등록에 필요한 **시리얼 키** | 화면에서 취득 경로 소멸 | ❌ **없다** | `UserInfoPage.razor.cs:78`(대입 코드 없음) |
| I | ERP 로컬 **기기 등록 API** | 로그인 경유만, POST 없음 | ⚠️ **부분** | `DeviceController.cs` 에 register 없음 |
| J | 표식 **문구·위치 결재** | 미정 | ❌ **없다** | 작지서 §T4 *"사장님 결재 필요"* |

### 6-1. 가장 짧은 경로 (사실 관계만)

**A·B 가 이미 있으므로 T4(표식)에 새로 필요한 것은 C 하나다.**
판정 결과를 화면이 읽을 수 있게 하는 통로가 없을 뿐, 판정 자체는 이미 돈다.

**T3(자동등록)는 성격을 먼저 정해야 한다** — 현행에서 메인PC 는
*"등록된 기기"* 가 아니라 *"검사를 건너뛰는 기기"* 다(`AuthController.cs:56`).
**"자동등록" 이 ① 실제로 `tenant_devices` 에 행을 넣는 것인지,
② 지금처럼 면제하되 화면에 보이게만 하는 것인지에 따라 슬롯 영향이 정반대다**(§7-1).
⚠️ 이 갈림은 **사장님 결재 사항**이다 — 병렬검증은 판단하지 않는다.

## 7. 자동 등록이 만들 수 있는 사고

### 7-1. 🔴 슬롯 소진 — 가장 큰 위험

**현행**: 메인PC 는 loopback 이라 **슬롯을 0 소모**한다(`AuthController.cs:56` 조건에서 제외).

**만약 T3 를 "실제로 `tenant_devices` 에 INSERT" 로 구현하면**:
- basic 티어 PC 한도 = **5**(`TenantDeviceService.cs:252`)
- 메인PC 가 1칸을 먹으면 → 클라이언트 가용 **5 → 4**
- **기존 고객도 전원 1칸씩 줄어든다** (한도는 티어 고정값이므로 자동 보정 없음)
- 이미 5대를 쓰던 고객은 **다음 로그인에서 401 거부**(`TenantDeviceService.cs:175-178` → `AuthController.cs:82`)
- 증상 = *"어제까지 되던 PC 가 오늘 로그인 안 됨"* → **고객은 100% 전화한다**

⚠️ 이것은 정책 제안이 아니라 **현행 상수로 계산되는 산술 결과**다.

### 7-2. 🔴 중복 등록 — 지문이 두 갈래

| 경로 | 지문 형태 | 위치 |
|---|---|---|
| ERP 로그인 | `HFPv2-` + 환경 해시 **평문** | `device-fingerprint.js:66` → `TenantDeviceService.cs:207` |
| 백오피스 버튼 | `UA\|해상도\|시간대` 를 **HMAC 해시** | `UserInfoPage.razor.cs:95-96` → `DeviceRegistrationController.cs:60` |

⇒ **같은 PC 가 두 DB 에 서로 다른 지문으로 들어간다.** 게다가 두 산식의 입력 자체가 다르다
(`device-fingerprint.js:48` 은 UA 에서 **버전 숫자를 제거**하고, `UserInfoPage.razor.cs:97` 는 **UA 원본**).
⇒ 한쪽이 다른 쪽을 **절대 같은 기기로 인식하지 못한다.** 기기 수 대사(對査)가 성립하지 않는다.

⚠️ 추가 위험: `device-fingerprint.js:15-16` 주석이 이미 경고한다 —
*"지문 산식을 바꾸면 기존 등록 기기와 안 맞아 재인식될 수 있다"*.
T3 에서 새 산식을 도입하면 **기존 기기 전부가 신규 기기로 재인식되어 슬롯이 순식간에 소진**된다.
이것이 §7-1 과 겹치면 **전 고객 로그인 차단**이 된다.

### 7-3. 🔴 오판정 — loopback 이 항상 메인PC 인가

**성립하는 근거** (`AuthController.cs:48` 주석): 터널(cloudflared)은 loopback 으로 올 수 없어
프록시가 위조 불가 — **신뢰 가능**하다는 판단.

**⚠️ 반증 3가지 (실측 미완 — 검증팀 실동작 확인 필요):**

| # | 시나리오 | 우려 |
|---|---|---|
| ①-역방향 | 메인PC 에서 **터널 도메인**으로 접속 | RemoteIp 가 loopback 이 아니게 되어 **메인PC 가 메인PC 로 안 보인다** → 표식이 사라지고 **슬롯을 소모**할 수 있다 |
| ②-리버스프록시 | 앞단 프록시가 같은 PC 에 있으면 | RemoteIp 가 **127.0.0.1 로 보일** 수 있다 → 클라이언트가 메인PC 로 오판정 |
| ③-원격데스크톱 | 직원이 RDP 로 메인PC 에 붙어 브라우저 실행 | 접속은 loopback → **메인PC 로 판정**된다 |

①은 실제로 일어난다 — `installer/HitPan-Universal.iss` 의 바로가기가 상황에 따라
도메인/localhost 로 갈린다는 것이 이미 기록되어 있다
(`docs/설계/설치배포/20260702작1_접속기기슬롯_P0_지문근본결함_봉합작업지시서.md:74`).

🔴 **R3 대응(작지서 §4 *"판정 근거를 로그로 남긴다"*)만으로는 ①을 못 막는다.**
로그는 사후 추적이지 오판정 방지가 아니다.

### 7-4. ⚠️ 표식이 클라이언트PC 에도 보이는 사고

§4-2 의 반증이다. 판정을 **`DB_HOST` 만으로** 하면 **모든 접속자에게 같은 답**이 간다
→ 클라이언트PC 화면에도 *"이 컴퓨터가 주 컴퓨터입니다"* 가 뜬다.
작지서 §3 실동작 판정 *"메인PC 표식이 실제 메인PC 에서만 보이는가"* 를 **바로 위반**한다.
⇒ **`DB_HOST` 단독 판정은 T4 를 못 만족한다. loopback 과 함께 써야 한다.**

### 7-5. ⚠️ 두 DB 동시 기록 시 부분 성공

`UserInfoPage.razor.cs:100`(본사) 와 `AuthController.cs:76`(로컬)이 서로 모른다.
한쪽만 성공하면 **본사 기기 수 ≠ 고객 실제 기기 수**. 되돌리는 코드도 없다.
⚠️ 헌법 #18·#22 관점: 본사가 고객 기기 목록을 갖는 것은
`tenant_devices_snapshot`(`hitpan_db_clean.sql:3455-3466`, 3컬럼 Pull)로 이미 설계되어 있다.
**T3 가 본사로 직접 Push 하는 형태가 되면 그 설계와 갈린다** — 확인 필요.
