# 병렬이슈 PI-19 — G-13 진단이 틀렸다. `tablet` 은 애초에 저장되지 않고, 진짜 구멍은 다른 자리다

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시 병렬검증 **2회차** · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 **§17-3**·**§16 G-13** · 작지서 작3 P1 |
| 등급 | 🟠 **P1** — 게이트가 **안 나는 사고를 막고**, 실제로 나는 사고는 **그대로 통과**시킨다 |
| 상태 | ⬜ 미봉합 |

---

## 1. 무엇이 문제인가

명세서 §17-3 · §16 은 백오피스 등호 비교를 이렇게 진단했다.

> 백오피스 `DeviceRegistrationController.cs:98-101` — `device_type = @Type` **등호**
> → 🔴 **`tablet` 이 어느 칸에도 안 잡힌다** … 백오피스 등호가 특히 나쁘다 — **공짜로 쓰이는 기기**가 생긴다(→ G-13)
>
> **G-13** | **`tablet` 이 어느 칸에도 안 빠진다** (백오피스 `device_type = @Type` 등호 구멍)

🔴 **`tablet` 은 저장되지 않는다.** 서버가 받는 순간 `mobile` 로 바꾼다.
그리고 백오피스는 `tablet` 을 **받지도 않는다.** ⇒ **G-13 은 일어나지 않는 일을 막는 게이트다.**

반면 **진짜 구멍은 같은 줄 바로 위에 있는데** 설계가 못 봤다.

---

## 2. 근거 (실측)

### (1) 서버는 `tablet` 을 `mobile` 로 흡수한다 — 저장 시점에

`src/HitPan.Infrastructure/Services/TenantDeviceService.cs:713-725`
```csharp
private static string? NormalizeDeviceType(string? raw)
{
    if (string.IsNullOrWhiteSpace(raw)) return null;
    var t = raw.Trim().ToLowerInvariant();
    // 태블릿은 휴대기기 칸으로 흡수한다 (사장님 판정 — 컴퓨터 운영체제가 아니다)
    if (t is "tablet") return "mobile";
    if (t is "mobile" or "pc") return t;
    // 모르는 값은 휴대기기로 본다 — 비싼 칸을 잘못 깎지 않는 쪽
    return "mobile";
}
```
⇒ **`device_type` 칸에 `tablet` 이 새로 들어갈 길이 없다.**

### (2) 클라이언트도 `tablet` 을 안 보낸다

`src/HitPan.Web/wwwroot/js/device-fingerprint.js:187-189`
```javascript
//   [칸은 둘뿐이다] 종전엔 'tablet' 을 따로 돌려줬으나, 요금 계산이 이미
//     (서버도 tablet 을 받으면 mobile 로 흡수한다 — TenantDeviceService.NormalizeDeviceType)
```

### (3) 백오피스는 `tablet` 을 **받는 즉시 `pc` 로 만든다**

`src/HitPan.Backoffice.API/Controllers/DeviceRegistrationController.cs:76-79`
```csharp
var deviceType = string.IsNullOrWhiteSpace(req.DeviceType) ? "pc" : req.DeviceType.ToLowerInvariant();
if (deviceType != "pc" && deviceType != "mobile")
    deviceType = "pc";
```
🔴 **`tablet` 이 오면 `pc` 가 된다.** 그러니 `device_type = @Type` 등호에서
**`tablet` 이 조회되지 않는 상황 자체가 생기지 않는다.** 등호의 오른쪽은 항상 `pc` 아니면 `mobile` 이다.

⇒ **§17-3 의 *"tablet 이 어느 칸에도 안 잡힌다 · 공짜로 쓰이는 기기가 생긴다"* 는 성립하지 않는다.**

---

## 3. 🔴 진짜 구멍 — 설계가 못 본 것

### 구멍 ① 태블릿이 **PC 칸(비싼 칸)** 을 먹는다 — 방향이 반대다

위 (3) 때문에 **백오피스 경로로 등록한 태블릿은 `pc` 로 저장된다.**
그런데 ERP 경로(`NormalizeDeviceType`)는 같은 태블릿을 `mobile` 로 저장한다.

| 경로 | 태블릿이 저장되는 칸 |
|---|---|
| ERP 로그인 | `mobile` |
| 백오피스 등록 | 🔴 `pc` |

🔴 **같은 기기가 어느 문으로 들어오냐에 따라 다른 칸을 먹는다.**
그리고 백오피스 쪽은 **더 비싼 칸(PC)** 을 먹으므로 **고객이 손해**다(과다 청구 · §16 방향 ①).
설계는 정반대(*"공짜로 쓰인다 = 본사 손해"*)로 진단했다.

### 구멍 ② 등호가 진짜로 놓치는 것은 **옛 `tablet` 행**이다

`NormalizeDeviceType` 은 **2026-08-11 작2 에서 들어온 최근 코드**다(`:257` 주석).
그 이전에 등록된 행에는 **`tablet` 이 실제로 저장돼 있을 수 있다.**
ERP 는 그 행을 센다 — `:107` `x.t == "mobile" || x.t == "tablet"`.
🔴 **백오피스만 못 센다**(등호). ⇒ **두 시스템의 대수가 어긋난다.**

⇒ G-13 이 막아야 할 것은 *"tablet 이 안 잡힌다"* 가 아니라
**"같은 기기가 두 경로에서 다른 칸으로 계수된다"** 이다.

---

## 4. 터지면 무슨 일이 나나

1. 태블릿 사용 고객이 **PC 슬롯을 소진** ⇒ PC 한도(5)가 먼저 차서 **PC 를 못 붙인다** ⇒ 고객 항의
2. ERP 화면의 기기 대수와 백오피스 화면의 기기 대수가 **다르게 보인다** ⇒ §5-A-3 청구 대조가 무너진다
3. 🔴 G-13 을 설계대로 만들면 **시험은 통과하는데 사고는 계속 난다** —
   **가짜 게이트**다. §16 이 G-8 을 두고 지적한 바로 그 실수(*"동작을 검사해야 게이트다"*) 가 G-13 에 재현된다

---

## 5. 어떻게 고치나

1. **G-13 을 다시 쓴다** — *"tablet 이 안 빠지는가"* → 🔴 **"같은 기기를 ERP 경로와 백오피스 경로로 등록했을 때
   같은 칸에 계수되는가"**. 두 경로의 정규화를 **같은 규칙**으로 맞춘다.
2. **백오피스 `:76-79` 의 `deviceType = "pc"` 폴백을 고친다.**
   모르는 값은 ERP 와 같이 **`mobile`(싼 칸)** 로 간다 — 잘못 청구하지 않는 쪽.
   ⚠️ 단 작지서가 *"백오피스 싼 칸 정렬은 2차"* 라고 했으므로 **차수 판단은 PM 결재**로.
3. **옛 `tablet` 행을 실측한다.** `SELECT device_type, COUNT(*) FROM tenant_devices GROUP BY device_type`.
   있으면 마이그레이션으로 `mobile` 정규화. 없으면 G-13 자체가 불필요.
4. §17-3 의 *"공짜로 쓰이는 기기가 생긴다"* **문장을 정정한다.** 방향이 반대다.

---

## 6. 판정

🟠 **§17-3 의 백오피스 진단은 틀렸고, G-13 은 현재 형태로는 가짜 게이트다.**
같은 자리에 **진짜 결함(경로별 계수 불일치)이 있다**는 점에서 "지적 자체가 무효" 는 아니다 —
**증상 이름과 방향이 틀렸다.** 게이트를 그대로 만들면 사고를 못 잡는다.
