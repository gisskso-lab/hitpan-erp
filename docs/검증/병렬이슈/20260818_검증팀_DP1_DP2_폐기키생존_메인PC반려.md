## 🔴 DP-2 (더 급함) — `RejectAsync` 에 메인PC 가드가 없다

### 실측 (PM 확인)

| 함수 | 메인PC 가드 |
|---|---|
| `RevokeAsync` (폐기) | 🟢 **있다** — `SELECT COALESCE(is_main_pc,0) …` 로 먼저 막는다 (`:581`) |
| `RejectAsync` (반려) | 🔴 **없다** |

**그런데 메인PC 가 `pending` 일 수 있다** — `MainPcRegistrationService:156-163` 이 `pending` 줄을 승격시키는 경로가 있다.
⇒ 검증팀이 **메인PC 를 `rejected` 로 넣는 데 실제로 성공**했다.

### 🔴 왜 급한가 — 8/16 P0 와 같은 계통이다

8/16 에 **메인PC(대표계정)가 자기 화면에서 막혀 스스로 못 빠져나오던** P0 가 있었다(커밋 `30e3873`).
그때 만든 구제책이 `:271` `if (status == "revoked" && !isMainPc)` 인데 — 🔴 **`revoked` 에만 있다.**

⇒ **메인PC 가 `rejected` 가 되면 구제 경로가 없다.** 대표가 자기 화면에서 다시 막히고,
승인해 줄 수 있는 유일한 사람이 승인 화면에 못 들어간다. **8/16 사고의 재현이다.**

⚠️ 작1 이 `rejected` 를 **새로 만들었기 때문에** 이 자리가 생겼다 — 다만 **원인은 `RejectAsync` 에 가드가 없던 것**이고,
`revoked` 일 때도 같은 결함이 있었으나 `:271` 구제책이 가려 주고 있었다.

### 안전망도 없다 (DP-3)
`DB-89` 메인PC 보호 트리거가 **출하 DDL 에 `CREATE TRIGGER` 0건**이고, 적용해도 `revoked` 를 안 되돌린다.
⇒ **선행 결함. 작1 무관.** 그러나 DP-2 의 안전망이 없다는 뜻이다.

### 고치는 법
`RejectAsync` 에 `RevokeAsync` 와 **같은 메인PC 가드**를 넣는다. 또는 `:271` 구제 조건을 `revoked` → `revoked|rejected` 로 넓힌다.
🔴 **둘 다 하는 것이 맞다** — 막는 자리(가드)와 빠져나오는 자리(구제)는 다른 역할이다.

## 🔴 DP-1 — 폐기 기기의 인증키가 살아 있고, 그 방어를 아무 게이트도 안 지킨다

### 실측 (PM 확인)

`RevokeAsync` (`:590-598`):
```sql
UPDATE tenant_devices
SET status = 'revoked', revoked_at = NOW(), revoked_reason = @Reason
WHERE device_id = @Id AND tenant_id = @TenantId
```
🔴 **`auth_key_hash` 를 안 지운다.** 폐기해도 **옛 키가 표에 그대로 살아 있다.**

막는 것은 `VerifyAuthKeyAsync` 안의 **한 줄뿐**이다:
```csharp
if (status == "revoked") return null;
```

### 🔴 그 한 줄을 빼도 12/12 초록불이다 (검증팀 실측)
**유일한 방어를 지켜보는 눈이 0개다.**

### 왜 위험한가
1-8(인증키 1회용화)과 **얽힌 자리**다. 1회용 소거(`auth_key_hash=NULL`)는 **승인 경로에만** 있고 **폐기 경로엔 없다**.
⇒ 다음 사람이 두 경로를 정리하다 저 한 줄을 건드리면 **폐기한 기기가 옛 키로 되살아나고, 게이트는 초록불이다.**

### 고치는 법
| 안 | 방법 | 평가 |
|---|---|---|
| **(가)** `RevokeAsync` 가 `auth_key_hash = NULL` 도 함께 | 🟢 **권장** — 키가 없으면 방어할 것도 없다. **근본** |
| (나) 게이트 신설(G-35) | 🟡 필요하나 (가)가 우선. **(가)를 하면 (나)는 회귀 감시용** |

🔴 **(가)+(나) 둘 다.** (가)는 결함을 없애고, (나)는 되돌아오는 것을 막는다.

## 🔴 교훈 — "구제책이 상태 이름에 묶여 있었다"

8/16 구제책은 `status == "revoked"` 라는 **문자열 하나**에 걸려 있었다.
작1 이 **정당한 이유로** `rejected` 를 새로 만들자, 구제책이 **조용히 그 상태를 안 덮게** 됐다.

⇒ 🔴 **새 상태를 추가할 때는 "이 상태를 이름으로 검사하는 곳"을 전부 찾아라**(헌법 #12 정신).
`grep -n '"revoked"'` 한 번이면 나왔다.
