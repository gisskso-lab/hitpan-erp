## 2. 실측 (추측 0)

### 2-1. 워치독이 보내는 3곳 중 1곳이 404

`src/HitPan.Watchdog/appsettings.json:20-22`

| 워치독 송신 대상 | 실측 응답 |
|---|---|
| `back.hitpan.kr/watchdog/ping` | 400 |
| `back.hitpan.kr/watchdog/emergency` | 400 |
| 🔴 `back.hitpan.kr/api/telemetry/update-history` | **404** |

### 2-2. 🔴 대조 실험 — 400 과 404 의 뜻이 다르다

**`TelemetryController.cs:19-21` 이 이미 경고해 둔 함정이다:**

> *"`POST /아무거나없는경로` → **400** ← 400 은 그 경로 고유 증상이 아니었다"*

그래서 **없는 경로를 일부러 만들어 대조했다:**

```
404  <=  /api/telemetry/update-history      ← 8/06 에 만든 수신부
404  <=  /api/telemetry/절대없는경로xyz      ← 존재하지 않음
404  <=  /api/절대없는것xyz                  ← 존재하지 않음
400  <=  /watchdog/절대없는것xyz             ← 이 경로군은 400 을 낸다
```

⇒ 🔴 **`update-history` 의 404 는 "없는 경로"와 완전히 동일하다.**
페이로드 문제가 아니라 **그 라우트가 서버에 없다.**

### 2-3. 코드는 `main` 에 있다

```
git log origin/main -- src/HitPan.Backoffice.API/Controllers/TelemetryController.cs
  → 2fcada9  feat(백오피스/P0): 고객사 업데이트 기록 수신부 (#63)

git merge-base --is-ancestor 2fcada9 origin/main   →  ✅ 포함됨
```

**코드 결함이 아니다. 배포 결함이다.**

## 3. 🔴 진범 — 트리거 브랜치가 어긋나 있다

`.github/workflows/deploy-ncp.yml`

```yaml
on:
  push:
    branches: [develop]          ← 🔴 develop 만 본다
    paths:
      - 'src/HitPan.Backoffice.API/**'
      - 'src/HitPan.Backoffice/**'
      - 'src/HitPan.Landing/**'
  workflow_dispatch:
```

**그런데 작업은 전부 `main` 으로 간다.** PR #63·#43·#41·#37 전부 `main` 머지다.

| | 워크플로가 기다리는 것 | 실제로 일어나는 것 |
|---|---|---|
| 브랜치 | `develop` push | 🔴 **`main` 머지** |
| 결과 | — | **아무 일도 안 일어남** |

⇒ **`workflow_dispatch`(수동)로만 배포된다.** 8/02 이력이 전부 `workflow_dispatch` 인 이유다.
**사람이 기억해서 눌러야 한다.** 8/06 에는 아무도 안 눌렀다.

## 5. 왜 이것이 2순위(백오피스)의 진짜 답인가

인수인계서가 백오피스를 *"미확인 · 가장 뒤처짐"* 으로 적었는데, **뒤처진 이유가 화면 부족이 아니었다.**

| 오해 | 실측 |
|---|---|
| 백오피스가 덜 만들어졌다 | ❌ **59화면 · 28컨트롤러** — 규모는 있다 |
| 그래서 검증을 못 했다 | ❌ **만든 것이 서버에 안 올라가 있다** |

⇒ 🔴 **만든 것과 도는 것이 다르다.** 이 상태로는 무엇을 점검해도 실제와 어긋난다.
**§2 교육 체인의 첫 단추가 여기서 막혀 있다** — 본사 직원이 배울 화면이 최신이 아니다.
