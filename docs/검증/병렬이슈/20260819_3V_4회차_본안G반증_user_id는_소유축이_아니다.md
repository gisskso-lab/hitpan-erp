## 🔴 치명 1 — G 는 **P0 를 못 닫는다**

**시나리오**: 직원이 그 PC 브라우저를 **먼저** 열어 로그인 ⇒ 그 줄 `user_id = 직원`.
나중에 대표가 **같은 브라우저**(같은 `device_id`)로 터널 접속 ⇒ **갱신 경로만 탄다**
⇒ `user_id` 는 **여전히 직원** ⇒ `OR user_id = @CurrentUserId` **거짓**
⇒ 🔴 **대표는 8/18 과 똑같이 갇힌다.**

> 🔴 **G 의 성립이 "누가 먼저 로그인했나" 라는 우연에 달려 있다.** 그 자체가 결함이다.

## 🔴 치명 2 — 메인PC 서버 줄은 `user_id = NULL` 이라 **G 가 아무것도 안 더한다**

`MainPcRegistrationService.cs:205` — `VALUES (@Id, @TenantId, NULL, 'pc', ...)`

SQL 3값 논리에서 `NULL = '값'` 은 **UNKNOWN** ⇒ `WHERE` 가 통과시키지 않는다.
그 줄은 어차피 `is_main_pc=1` 로 통과하므로 **G 가 더해주는 것이 없다.**
G 가 새로 구하려던 대상은 `is_main_pc=0` 브라우저 줄뿐인데 **그것이 치명1 로 불확실하다.**

🟢 **G 에 유리한 유일한 발견**: `revoked` 옛 서버 줄도 `user_id=NULL` 이라 **되살아나지 않는다.**

## 🔴🔴 치명 3 — **공유 계정 = 기기 과금 붕괴.** G 가 직접 여는 문

`device_id` 는 **비밀이 아니다** — `DeviceAuthMiddleware.cs:161-164` 주석이 직접 그렇게 적어 뒀다
(목록 화면 노출 · `gate-status` 쿼리스트링 평문 · 브라우저 저장소).

**시나리오**: 현장에서 흔한 공유 계정(`창고@…`)으로 A 가 PC 를 등록·승인 ⇒ 그 줄 `user_id = 창고계정`.
B·C·D 가 **같은 계정**으로 자기 폰·집 PC 에서 로그인하고, **목록에서 본 A 의 `device_id`** 를 헤더에 넣으면
⇒ `user_id = @CurrentUserId` **참** ⇒ 🔴 **전원 통과.**

⇒ 🔴 **미승인·미등록 기기가 무제한으로 업무 API 를 쓴다. `CountUsedSlotsAsync` 가 무너진다.**

### 🔴🔴 그리고 이것이 **설계서의 핵심 주장을 반증한다**

설계서 §3-4-1 은 *"주인이어야 통과하므로 **좁힘이 더 강해진다**"* 고 적었다.

| | 통과 가능 집합 |
|---|---|
| 종전 | `is_main_pc=1` **한 줄** |
| G | `is_main_pc=1 한 줄` **∪** `내 user_id 가 붙은 모든 줄` |

🔴 **집합이 순증한다. 좁힘이 아니라 넓힘이다.**
⇒ *"더 강해진다"* 는 **거짓봉합 문장**이며, 이대로 문서에 남기면 안 된다.

## 🔴 치명 4 — **한 사람 여러 기기** — 자기 폰이 자기 PC 번호로 통과

### 대안 방향 (보안상무 제안 — 결재 대상 아님)

8/18 주석(`DeviceAuthMiddleware.cs:167-170`)이 이미 적어 뒀다 —
*"남은 구멍은 **기기별 비밀값**이고 다음 차수 몫"*.

⇒ 🔴 **판정 축은 `device_id`(비밀 아님)가 아니라 기기별 비밀값(인증키 계열)이어야 한다.**
⇒ 대표 브라우저 줄의 P0 는 **그 줄에 열쇠를 주는 쪽**으로 되돌아가야 한다
(3회차에 반증한 F 의 **문제의식은 옳았고, 구현이 틀렸던 것**).

⚠️ 이는 설계팀·CTO 결재 사항이며, 보안상무 소관은 **G 반려까지**다.
