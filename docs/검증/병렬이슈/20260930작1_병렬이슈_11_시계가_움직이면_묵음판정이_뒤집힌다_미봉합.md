## 무엇이 문제인가
① **시계 뒤로** — 열린 요청 판정 `age < OpenRequestStale`(`LocalSwapLauncher.cs:93`)·`ClearStale` 재판정(`:130`)은 **아래 한계가 없다**(음수 나이도 「30분 안」). 반면 `swap.lock`(`IsLockFresh :359-360`)·쿨다운(`:94`)·예약(`:234`)은 `age >= 0` 을 요구한다 — 판정마다 규칙이 다르다. 요청서 `updated_at` 이 미래 시각인 채 일꾼이 죽으면(시계가 앞서 있던 PC 가 나중에 바로잡힘) 시계가 그 시각을 지날 때까지 `swap_in_progress` — 몇 달·몇 년 가능.
② **시계 앞으로** — 일꾼은 `swap.lock` 을 걸 때 한 번만 시각을 찍고 갱신하지 않으며(`TryCreateLock :363-`), 요청서는 단계 경계에서만 갱신된다(`local-swap.ps1 Set-State`). S5 뒤 새 API 가 떠 있는 S6(최대 180초)·`Clear-AfterSuccess`(해시·옮기기) 중 시계가 30분 넘게 앞으로 보정되면, 새 API 의 상태 조회 한 번으로 `ClearStale` 이 요청서를 `broken/worker_interrupted` 로 덮고 **실행 중인** `HitPan-LocalSwap` 을 지운다(`:141-153`). 일꾼이 계속 살면 다음 `Set-State` 가 덮어 원상 복구되나, 지우기가 일꾼을 끝내면(⚠️가설) S6 검증·S7 되돌리기 한가운데서 멈춘다 = 06 ④ 의 모양.

## 막는 방향 (한 줄)
묵음 판정을 벽시계가 아니라 **일꾼 생존 신호**(작업 실행 상태 `schtasks /Query` Running · 일꾼이 주기적으로 갱신하는 `swap.lock` 시각)로 하고, 모든 나이 판정에 같은 규칙(음수 = 비정상 → 로그 + 묵은 것으로 취급)을 쓴다.
