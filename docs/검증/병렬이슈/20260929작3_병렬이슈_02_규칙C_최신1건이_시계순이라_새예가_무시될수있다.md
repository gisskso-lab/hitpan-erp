## 무엇이 문제인가

설계 §3 은 스스로 「왜 시각이 아니라 id 인가 — 두 시계를 비교하지 않는다. id 는 한 표 안의 순번이라 정확하다」고 적었다. 그런데 **「최신 1건」을 고르는 정렬은 여전히 시각이 먼저**다.

- 설계 §5-1 SQL: `ORDER BY c.consented_at DESC, c.id DESC LIMIT 1`
- 종전 `src/HitPan.Watchdog/AutoUpdate/WatchdogConsentReader.cs:59` 도 같은 정렬
- `consented_at` = API 프로세스의 `DateTime.Now` (`src/HitPan.API/Controllers/AuthController.cs:585` · `:810`) — **메인PC 윈도우 시계**

시계가 한 번이라도 앞으로 갔다가 돌아오면(바이오스 배터리 · 전원 강제종료 뒤 시계 초기화 · 사람이 시계를 고침 · 시간 동기화 보정), 나중에 넣은 행이 **더 이른 시각**을 갖는다. 그러면 `id` 가 가장 큰 행이 「최신」으로 뽑히지 않는다.

| 순서(id) | 시계 | 결과 |
|---|---|---|
| [예] id5 (시계가 앞서 있던 때 · 실패 → used=5) → 시계 바로잡힘 → 메인PC [예] id6 | id6 가 id5 보다 이른 시각 | 「최신」= id5 ⇒ **「이미 쓴 [예]」** ⇒ 적용 0 · 펜딩 해제 · 보고 0. 팝업이 다시 뜨고 [예]를 눌러도 또 무시 — 시계가 id5 시각을 넘을 때까지 **N-UPD2 그대로 재발** |
| [나중에] id4 (시계가 1년 앞서 있던 때) → 시계 바로잡힘 → [예] id9 | id9 가 더 이른 시각 | 「최신」= [나중에] id4 ⇒ **[예]를 몇 번 눌러도 영영 적용 안 됨** |
| [예] id5 (시계 앞섬 · 워치독 꺼져 있어 아직 안 씀) → [나중에] id6 | id6 가 더 이른 시각 | 「최신」= [예] id5 ⇒ **[나중에]를 눌렀는데 적용된다** (#43 「[나중에]=적용 안 함」 위반) |

추가로, 설계 §4 판정표에는 **`C`=approve · `C.id < A.consent_id`** 인 칸이 없다(`requested` 는 `>` · `failed` 는 `=`). 위 첫 줄이 바로 그 경우라 API 가 어떤 kind 를 낼지 정해져 있지 않다.

「시계 조작」 관점: 이 입력(시계)을 바꿀 수 있는 사람은 메인PC 앞 사람뿐이라 **외부 공격 입구는 아니다.** 문제는 공격이 아니라 **고장 난 시계 하나로 업데이트가 영구히 막히는** 쪽이다 — 이번 오더가 없애려는 바로 그 막다른 길.

## 권고

1. 워치독 새 판독 메서드와 API 판정 조회 **둘 다** `ORDER BY c.id DESC LIMIT 1` 로 고른다(AUTO_INCREMENT 순번 = 넣은 순서). 두 쪽이 **같은 정렬**을 써야 화면 안내와 워치독 동작이 갈리지 않는다.
2. 종전 `ReadLatestAsync`(`:59`)는 #1 상 남겨도 되지만, 규칙 C 는 새 메서드만 쓰게 한다.
3. 판정표에 `C.id < A.consent_id` 칸을 명시(정렬을 id 로 바꾸면 원리적으로 안 생기지만, 생기면 `failed` 로 떨어뜨려 **다시 묻게** 한다 — 막다른 길보다 한 번 더 묻는 쪽).
4. 게이트: G-W3 옆에 「id 는 크고 `consented_at` 은 이른 [예] → 적용 1」 · 「id 는 크고 시각은 이른 [나중에] → 적용 0」 두 줄. 대조군 = 정렬을 시각 먼저로 되돌리면 FAIL.

## 참고 — 같이 본 것(문제 아님)
- 두 표는 모두 `utf8mb4_unicode_ci`(출하 DDL `:2226` · `:2272` · 워치독 자가생성 DDL 도 같음) ⇒ `applied_version = update_version` JOIN 에서 콜레이션 충돌(1267) 없음.
- `local_update_apply_status` 는 `UNIQUE(applied_version)` ⇒ LEFT JOIN 이 여러 줄로 불어나 엉뚱한 `consent_id` 를 집는 일 없음.
- 데이터 초기화 기능은 두 표를 지우지 않는다(참조 코드 `AuthController` 한 곳뿐) ⇒ id 되감김 경로 없음. 백업 복원은 두 표가 함께 되돌아가 서로 맞는다. 단, 워치독 인메모리 `_consentAppliedVersions`(`Worker.cs:102`, 키를 동의 id 로 바꿀 예정)는 복원 뒤 같은 id 가 다시 나오면 한 번 건너뛸 수 있다 — 드묾 · 재기동이면 풀림 · 참고만.
