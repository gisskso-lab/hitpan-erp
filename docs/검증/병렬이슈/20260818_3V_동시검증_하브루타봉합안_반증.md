| 🔴 P0 | **6건** | 이대로 작업지시서가 나가면 사고 |

1. **V-01** — 봉합 1-3(경로 화이트리스트)이 **헌법 #43 을 정면으로 깬다.** 실측 화이트리스트는 6개인데 봉합안은 2개만 적었다. 나머지 4개를 지우면 **업데이트·워치독이 막힌다.**

3. **V-05** — 봉합 2-1 의 *"막지 않고 안 바꾼다"* 는 **요금 구멍을 못 막는다.** PC 를 mobile 로 등록하는 길은 **승격 경로가 아니라 최초 등록 경로**에 있다.

## §1. 🔴 P0 — 봉합안의 해법이 새 구멍을 만든다

### 🔴 V-01. 봉합 1-3 이 헌법 #43(업데이트·워치독 불변)을 깬다 — **최우선**

**봉합안 주장** (131행 표, 봉합 1-3):
> *"대표 예외를 경로 화이트리스트로 한정 (`/api/devices`·`/api/auth` 만)"* — 🔴 P0

**실측** — `src/HitPan.API/Middleware/DeviceAuthMiddleware.cs:38-47`:

```
BypassPrefixes = {
    "/api/auth",        // 로그인·갱신
    "/api/devices",     // 기기 인증·목록·승인
    "/api/appversion",  // ← 봉합안에 없다
    "/api/watchdog",    // ← 봉합안에 없다
    "/health",          // ← 봉합안에 없다
    "/swagger"          // ← 봉합안에 없다
}
```

🔴 **봉합안은 6개 중 2개만 적었다.** 작업지시서에 *"`/api/devices`·`/api/auth` 만"* 이 그대로 실리면 구현자는 **나머지 4개를 지운다.**

**그 순간 무슨 일이 나는가**:
- `/api/appversion` 이 막힘 ⇒ **업데이트 확인 자체가 403**
- `/api/watchdog` 이 막힘 ⇒ **워치독이 서버에 못 물음**
- ⇒ 🔴 **헌법 #43 위반** — *"Major 팝업 Y/N 흐름은 안 바뀐다"*. 팝업이 뜰 근거를 가져오는 길이 끊긴다.
- ⇒ 🔴 **[[project_fixed_vs_delivered_gap]] 5차** — 고칠 방법 자체가 사라진다. 코드 주석이 **이미 경고**하고 있다: *"막으면 고칠 방법이 사라진다"*(`:44`).

**재현**: `DeviceApproval:Enabled=true` 상태에서 `BypassPrefixes` 를 2개로 줄이고 `GET /api/appversion/check` 호출 → 403.

**안 고치면**: 고객 PC 전체가 **업데이트를 영구 수신 못 함.** 그 상태를 고치는 배포가 또 업데이트로만 가므로 **자력 복구 불가**(4차 사고와 동일한 닭과 달걀).

🔴 **작업지시서 필수 문구**: *"BypassPrefixes 6개는 그대로 둔다. 1-3 이 좁히는 대상은 BypassPrefixes 가 아니라 **`tenant_admin` 무조건 통과 절**(`:166-171`)이다."*

### 🔴 V-02. 봉합 1-1 "서버가 device_id 를 발급" — DDL 이 물리적으로 막는다

**봉합안 주장** (19-20행, 83행):
> *"`verify-key` 가 성공하면 서버가 **그 자리에서 device_id 를 발급해 내려준다.**"*

**실측** — `installer/hitpan_db_clean.sql:3734,3749`:

```
`fingerprint` varchar(64) NOT NULL          ← NULL 불가
UNIQUE KEY `uq_tenant_fp` (`tenant_id`,`fingerprint`)
```

🔴 **새 줄을 만들려면 `fingerprint` 가 반드시 있어야 하는데, 봉합안은 같은 문서에서 그 값을 포기했다** (169행):
> *"`hardware_id` 는 당분간 비워 둔다"*

⇒ **발급할 device_id 를 담을 줄을 만들 수 없다.** `INSERT` 하면 `fingerprint` 가 NOT NULL 에 걸리고, 빈 문자열로 채우면 **두 번째 기기가 `uq_tenant_fp` 1062 에 걸린다.**

⚠️ 이 함정은 **이미 적발된 적이 있다** — `20260815_PI-09_UNIQUE_tenant_fp_NOTNULL_이_설계를_물리적으로_막는다.md`. **봉합안이 PI-09 를 반영하지 않았다.**

**안 고치면**: 1-1 구현 착수 당일 개발팀이 막힌다. 또는 빈 문자열로 우회해 **2대째 등록에서 1062** — 사장님 8/16 3증상 중 하나와 **정확히 같은 모양**이 재발한다.

### 🔴 V-03. 봉합 1-1 은 "세션이 신청한 줄을 잡는 법"이 **비어 있다** — 위조 가능

**봉합안** (96-97행):

```
바꿈 (맞음):  이 세션이 신청한 줄을 먼저 잡는다 → 그 줄의 키와 대조
```

🔴 **"어떻게 잡는가"가 문서 어디에도 없다.** 실측한 `verify-key` 는 요청 본문에 `AuthKey` **하나뿐**이다 — `src/HitPan.API/Controllers/DeviceController.cs:294-297`:

```csharp
public sealed class VerifyKeyRequest { public string AuthKey { get; set; } = ""; }
```

세션이 가진 것은 JWT 의 `tenant_id`·`user_id` 뿐이다. 그런데 **"신청한 줄"은 user_id 로 특정되지 않는다**:
- `RegisterMobileByTokenAsync` 는 `user_id` 에 **NULL 을 넣는다**(`TenantDeviceService.cs:733`) — 봉합안 자신이 2-5 로 인정한 결함
- 한 사람이 PC·폰·태블릿 3대를 신청하면 **같은 user_id 로 pending 이 3줄**

⇒ 🔴 **"그 세션이 신청한 줄"이 유일하게 정해지지 않는다.** 여러 줄 중 하나를 골라야 하는데 고르는 규칙이 없으면 구현자는 결국 **`LIMIT 1`** 을 쓴다 — **지금 코드와 똑같아진다**(`TenantDeviceService.cs:600`).

**남은 사각지대**: 봉합안 100행은 *"키는 맞나 틀리나만 판정"* 이라 했으나, **판정 대상 줄을 정하는 축이 없으면 그 문장은 구현될 수 없다.** 설계서에 **줄 선택 규칙**(예: `user_id AND status='pending'` 중 가장 최근 1줄, 2줄 이상이면 거부)이 명시되지 않으면 1-1 은 **글자만 바뀌고 동작은 그대로**가 된다.

### 🔴 V-04. 봉합 1-2 "is_main_pc=1 로 한정" — **여전히 무기명 도용이 가능하다**

**봉합안**: *"device_id 헤더 통과를 `is_main_pc=1` 로 한정 (무기명 도용 차단)"* 🔴 P0

**실측** — `DeviceAuthMiddleware.cs:138-145`: 지금은 `status='approved'` 만 본다. 봉합안대로 `AND is_main_pc=1` 을 더해도 —

🔴 **메인PC 의 device_id 하나만 알면 여전히 아무나 통과한다.** 대상이 N대에서 1대로 줄 뿐 **성질은 그대로다.** device_id 는 비밀값이 아니다:
- 대표 화면 기기 목록 조회에 **그대로 실린다** (`TenantDeviceService.cs:111-115`)
- `gate-status` 가 **쿼리스트링으로 받는다** (`DeviceController.cs:101-102`) ⇒ **서버 접근 로그·프록시 로그에 평문으로 남는다**
- 클라이언트 localStorage 에 저장된다 (`device-fingerprint.js:238`)

⇒ 🔴 **1-2 는 P0 을 P1 로 낮출 뿐 닫지 않는다.** 봉합안이 *"무기명 도용 차단"* 이라고 단정한 것은 **과장이다.** 진짜로 닫으려면 device_id 가 **추측·열람 불가한 비밀**이거나, 별도 비밀값과 **AND** 여야 한다.

**안 고치면**: 검증팀이 G-32 를 초록으로 만들고 "닫혔다"고 보고한다. 그러나 메인PC device_id 를 아는 사람(=기기 목록 화면을 본 사람 전원)은 **어느 기기에서든 통과**한다.

### 🔴 V-05. 봉합 2-1 — **요금 구멍은 승격 경로에 있지 않다.** 이 해법은 구멍을 못 막는다

**봉합안 공격 시나리오** (177행):
> *"PC 를 `mobile` 로 싸게 등록 → 다음 로그인부터 `pc` 신고 → 한도 검사 없이 승격"*

**봉합안 해법** (186행): *"mobile→pc 는 한도 재검사. 초과 시 막지 않고 **안 바꾼다**."*

🔴 **PM 이 스스로 던진 질문에 답을 못 했다.** 지시문의 질문이 정확하다 — *"안 바꾸면 그 기기는 계속 mobile 로 과금된다. PC 를 mobile 로 등록해 싸게 쓰는 길이 그대로 남는 것 아닌가?"*

**실측으로 답한다 — 남는다. 그리고 승격조차 필요 없다.**

`TenantDeviceService.cs:1045-1057` `NormalizeDeviceType`:

```csharp
if (t is "tablet") return "mobile";
if (t is "mobile" or "pc") return t;
return "mobile";   // 모르는 값은 휴대기기
```

⇒ **종류를 정하는 것은 클라이언트가 보낸 문자열 하나다.** 서버는 그 값이 참인지 검증하지 않는다.

🔴 **공격자는 승격할 이유가 없다.** 최초 등록에서 `deviceType: "mobile"` 로 보내고 **영원히 그대로 쓰면 된다.** PC 로 승격시키는 것은 **자기 요금을 올리는 행위**라 아무도 안 한다.

⇒ 봉합안이 막겠다는 `mobile→pc` 승격은 **공격 경로가 아니라 정직한 고객이 겪는 경로**다. 진짜 구멍은:

```
최초 등록에서 mobile 이라고 말하면 → 서버가 그대로 믿는다 → 끝
```

**안 고치면**: 🔴 **작업지시서 2 가 P0 4건을 발주하는데 그중 2-1 은 실제 구멍을 안 닫는다.** 구현 후 G-13b 는 초록이 되고 팀은 "요금 구멍 닫힘"으로 보고한다 — **거짓봉합 7번째.**

⚠️ 진짜 봉합은 **서버측 종류 판정**(User-Agent 대조 등)이거나, 구멍을 **받아들이고 문서화**하는 것이다. 지금 안은 **둘 다 아니다.**

### 🔴 V-06. 봉합 2-4 는 **이미 구현돼 있다** — P0 오판, 중복 발주

**봉합안**: *"2-4 QR 은 스위치와 무관하게 항상 대표 승인"* 🔴 **P0**

**실측** — `TenantDeviceService.cs:726`:

```csharp
var qrStatus = _approvalEnabled ? "pending" : "approved";
```

주석이 명시한다 — *"🔴 2026-08-16 20260816작2 — **QR 도 대표 승인을 거친다**(사장님 전결)"*.

🔴 **그러나 봉합안 문구와 코드는 다르다.** 봉합안은 *"**스위치와 무관하게** 항상"* 이라 했고, 코드는 **스위치를 본다.**

두 갈래 중 하나인데 봉합안이 안 갈랐다:

**안 고치면**: 구현자가 (나)로 읽어 스위치를 지운다 ⇒ 시험 환경 QR 이 전부 막히고 **8/10 계통 사고**(규칙을 켜서 쓰던 사람이 막힘)가 재발한다.

## §2. 🔴 거짓게이트 재범 — §3 게이트 표 반증

> **G-21 교훈**: 초록불이 **내 코드가 아니라 DB·프레임워크**에서 오면 가짜다.

### 🟡 V-07. G-13b 는 **이미 초록일 가능성이 높다** — "빨간불로 시작" 주장 반증

**봉합안 316행**: *"🔴 G-31·G-32·G-13b·G-30a/c/d 는 **지금 당장 빨간불로 시작한다.**"*

**G-13b 판정 기준**(311행): *"mobile→pc 승격 시 `pcUsed <= pcLimit`"*

🔴 **이 판정식은 승격과 무관하게 참일 수 있다.** `CountUsedSlotsAsync`(`TenantDeviceService.cs:817-832`)는 **DB 를 GROUP BY 로 다시 센다.** 승격 후 pcUsed 를 재계산하면, 한도가 넉넉한 시험 데이터에서는 **가드가 없어도 `pcUsed <= pcLimit` 이 성립한다.**

⇒ **초록불이 내 코드(가드)가 아니라 시험 데이터의 여유에서 온다.** G-21 과 **같은 형태**다.

🔴 **필수 조건**: G-13b 는 **`pcLimit` 을 정확히 꽉 채운 상태**에서 승격을 시도하고, **가드를 빼면 곧바로 FAIL 하는지 확인**해야 한다. 봉합안에 그 조건이 없다.

### 🟡 V-08. 기존 G-13 계열 게이트가 **문자열 검사** — 이미 가짜다

**실측** — `src/HitPan.Tests/Integrity/DeviceSlotGuardTests.cs:355`:

```csharp
Assert.True(Regex.IsMatch(countSql.Value, @"is_main_pc", RegexOptions.IgnoreCase), ...)
```

그리고 `:250`, `:254` 도 `Regex.IsMatch(code, ...)` — **소스 문자열을 정규식으로 훑는다.**

🔴 **이것이 정확히 가짜 게이트다.** 판정 근거가 **동작이 아니라 글자**다:

**안 고치면**: 새 게이트를 아무리 잘 세워도 **옛 게이트가 초록으로 덮어** 회귀를 못 잡는다.

## §3. 🟡 P1 — 고쳐야 함

### 🟡 V-10. 봉합 1-4 `rejected` — 무한 재신청으로 대표 화면이 막힌다

지시문의 질문이 맞다. 봉합안 117행 전이 ⑥ *"반려 → 미등록"* + *"재신청 허용"* 인데 **재신청 제한이 없다.**

**실측** — `RejectAsync`(`TenantDeviceService.cs:610-628`)는 `status='pending'` 인 줄만 `revoked` 로 바꾼다. `rejected` 로 분리하고 재신청을 열면:
- 전이 ①의 조건이 *"로그인 성공 + 미등록"* 이라 **사람 의사와 무관하게 자동으로 다시 pending INSERT** 된다
- ⇒ 🔴 **반려해도 다음 로그인에 즉시 되살아난다.** 대표는 같은 기기를 무한히 반려한다.

⇒ 전이 ⑥ 뒤에 **"재신청은 사람이 버튼을 눌러야 한다"** 또는 **쿨다운**이 없으면 반려 기능이 무의미하다. 봉합안에 없다.

### 🟡 V-11. 봉합 3-1 nonce — 실측이 봉합안보다 **더 나쁘다**

봉합안 240행 *"`sync_source` 는 단일 컬럼 — 마지막 하나만 기억"* ✅ **사실 확인**(`WebhookInboundController.cs:88-91`, `installer/hitpan_db_clean.sql:2005` `varchar(64) NOT NULL DEFAULT 'bootstrap'`).

🔴 **봉합안이 놓친 것**: 중복 판정이 `sync_source = @Nonce` **정확 일치**다. 즉 **직전 1건만** 기억한다. 서로 다른 이벤트가 A→B→A 순으로 오면 **A 가 두 번 처리된다** — 재시도 경합이 아니어도 **정상 순서로도 뚫린다.** 봉합안은 이것을 "재시도 경합"으로만 좁혀 봤다.

### 🟡 V-12. 봉합 3-3 `iat` — 실측 일치, 단 §3-2 표의 숫자 근거가 미확인

`iat` 고정 ✅ 사실 — `WebhookOutboundService.cs:98` 에서 생성되고, `WebhookDispatcher.cs:104,106` 이 `row.PayloadJson`·`row.Signature` 를 **그대로 재전송**한다. **재서명 코드 0곳** 확인. 수신측 ±600초 ✅ (`WebhookInboundController.cs:34,80`). `MaxRetry=5` ✅ (`WebhookDispatcher.cs:31`).

⚠️ 다만 §3-2 표의 "1분/6분/21분" 은 `BackoffSteps` **실제 값을 대조하지 못했다.** 결론(3회차부터 401)의 방향은 유효하나 **표의 수치를 작업지시서에 그대로 옮기지 말 것.**

### 🟡 V-13. 봉합 2-6 `tablet` 저장 — **기존 게이트와 정면충돌**

봉합안 195행: *"저장은 `tablet` 으로 살린다."*

**실측 충돌 2곳**:
1. `NormalizeDeviceType`(`:1052`)이 `tablet` → `"mobile"` 로 **되돌려 놓는다**
2. 🔴 기존 시험 `DeviceSlotGuardTests.cs:270` 이 **그것을 정답으로 못 박고 있다**:

   ```csharp
   Assert.Equal("mobile", TenantDeviceService.NormalizeDeviceType("tablet"));
   ```

⇒ 2-6 을 구현하면 **기존 게이트가 빨간불이 된다.** 작업지시서에 *"`I6_모르는_기기종류는_휴대기기로_본다` 시험의 tablet 줄을 함께 고친다"* 가 없으면 개발팀이 **빌드 깨짐으로 멈추거나, 시험을 지워 버린다.**

⚠️ 반대로 `MobileUsedFrom`(`:846`)은 이미 `mobile` **또는** `tablet` 을 센다 ⇒ **과금 쪽은 이미 준비돼 있다.** 저장만 바꾸면 되는데 **그 사실이 봉합안에 없다.**

### 🟡 V-14. 봉합 2-2 `setDeviceId` "폰이 안 부름" — **부르는 곳이 이미 2군데 있다**

## §4. 결재 1 해석 검증 — 🟡 오더를 반쯤 넘었다

**사장님 결재 1**: *"결제 확인 후 승인이 아니라, 신청 후 백오피스에서 승인. 단 백오피스에서 결제상태를 확인할 수 있어야 함"*

### 🟢 해석 자체는 오더 범위 안이다

*"결제 확인 후 승인이 아니라"* = 관문 부정, *"확인할 수 있어야"* = 표시 요구. **PM 해석은 문장 그대로다.** 이 각도로는 **반증 실패.**

### 🟡 V-15. 그러나 **"왜 옳은가" 논증이 오더를 넘었다**

봉합안 387행은 사장님이 **말하지 않은 이유**를 PM 이 만들어 붙였다:
> *"대리점이 먼저 열어주고 나중에 정산하는 실제 영업 흐름이 막힌다"*

그리고 384행 표에 **"대리점 선공급 — ✅ 가능"** 을 **확정처럼** 적었다.

🔴 **사장님은 대리점 선공급을 말한 적이 없다.** 이것은 [[feedback_pm_verify_business_premise]] 와 **같은 형태**다 — 사업 구조를 **추측으로 적어** 문서에 고정하는 것. 8/07 에 세 번 반복한 실수다.

⇒ 설계서에 *"대리점 선공급 가능"* 이 요구사항으로 실리면 **아무도 결재하지 않은 기능**이 구현된다. **⚠️미확인으로 낮추고 사장님께 되물어야 한다.**

### 🟡 V-16. **"백오피스가 결제 상태를 어디서 가져오나" 가 비어 있다**

봉합안은 결제 상태를 **표시하라**고만 하고 **출처를 안 적었다.**

**실측**: `local_subscription` 은 **ERP 로컬**에 있고(`WebhookInboundController.cs:88`), 백오피스는 **자기 DB** 를 본다.

⇒ 두 갈래 모두 위험:
- (가) **ERP 에서 결제상태를 가져온다** ⇒ 🔴 **헌법 #35 위반.** 봉합안 자신이 267행에서 *"ERP 가 백오피스 주소를 알면 #35 위반"* 이라 했다 — **반대 방향도 같은 축**이다.
- (나) **백오피스 자기 DB 의 구독 정보를 본다** ⇒ 🟢 헌법 정합. **이쪽이 정답인데 봉합안에 안 적혀 있다.**

⇒ 3-2 는 *"결제 상태 표시 칸 추가"* 만 적혀 있어 **출처를 구현자가 정하게 된다.** 설계서에 **(나)로 명시**하지 않으면 (가)가 만들어진다.
