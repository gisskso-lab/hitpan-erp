# 병렬이슈 PI-09 — `UNIQUE(tenant_id, fingerprint)` + `NOT NULL` 이 이 설계를 물리적으로 막는다

| 항목 | 내용 |
|---|---|
| 적발 | [3-V] 동시 병렬검증 · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 §4-3 · 스케줄 P3/P4 · 작지서 (DDL 언급 없음) |
| 등급 | 🔴 **P0** — 설계가 DDL 제약과 충돌하는데 세 문서 어디에도 없다 |
| 상태 | ⬜ 미봉합 |

---

## 1. 무엇이 문제인가

설계는 **"지문을 1차 열쇠에서 내린다"**(§3 모순 #5, §4-3)고 정했다.
그런데 **DB 가 지문을 필수값으로, 그리고 유일값으로 강제하고 있다.**

세 문서(명세서·스케줄·작지서) 어디에도 **이 제약이 언급되지 않는다.**
명세서 §11 *"이 설계가 건드리지 않는 것"* 에도 없고, 작지서 §4 의 DDL 항목은
*"DDL 변경 시 → clean DDL 편입"* 이라는 **조건문 한 줄뿐**이다.
⇒ 설계는 **DDL 변경이 필요한지 아닌지조차 판단하지 않았다.**

---

## 2. 근거 (실측)

`installer/hitpan_db_clean.sql:3728-3754` — 출하 DDL 단일 진실원(헌법 #36)

```sql
`device_id`   varchar(36) NOT NULL,
`fingerprint` varchar(64) NOT NULL COMMENT 'UA+OS+해상도+시간대 SHA-256',
...
PRIMARY KEY (`device_id`),
UNIQUE KEY `uq_tenant_fp` (`tenant_id`,`fingerprint`),
```

세 가지가 동시에 걸린다:

| # | 제약 | 설계와 충돌하는 지점 |
|---|---|---|
| A | `fingerprint NOT NULL` | 지문을 열쇠에서 내려도 **값은 반드시 넣어야 한다.** 무엇을 넣나? |
| B | `UNIQUE(tenant_id, fingerprint)` | 장비넘버로 식별하는 두 기기가 **우연히 같은 지문**이면 INSERT 가 **터진다** |
| C | 지문이 UNIQUE 라 **한 기기에 지문 한 개** | 메인PC 합류(P4) — `MAINPC-` 와 `HFPv2-` 를 **한 줄에 담을 칸이 없다** |

---

## 3. 이게 터지면 무슨 일이 나는가

### (1) P4 메인PC 합류가 DDL 상 불가능하다 — 스케줄의 핵심 단계가 막힌다

명세서 §4-5 는 이렇게 적었다:
> *"서버가 자기 장비넘버를 화면에 내려주면 브라우저가 그것을 저장하고,
>   다음부터 그 값으로 조회된다 → **`MAINPC-` 행에 그대로 붙는다.**"*

붙는 것까지는 된다. 그러나 그 줄의 `fingerprint` 는 **`MAINPC-…` 인 채로 남는다.**
그 PC 의 브라우저 지문 `HFPv2-…` 는 **저장될 자리가 없다** — 칸이 하나고 UNIQUE 다.

🔴 그래서 **지문 경로(③)로 그 PC 를 다시 찾을 길이 영원히 없다.**
장비넘버가 지워지는 순간(localStorage 삭제·브라우저 초기화) ③으로 떨어지는데,
③이 찾는 `HFPv2-` 는 **어디에도 저장돼 있지 않다** ⇒ ④ 신규 등록 ⇒ **슬롯 하나 더.**

⇒ **P4 로 닫았다고 선언한 사고가 localStorage 한 번 지우면 되살아난다.**
스케줄 P3 §위험은 *"지워지면 ③ 지문 경로로 떨어지게 설계한다 — 새 줄이 아니라"* 라고
적었지만, **메인PC 에 대해서는 그 ③이 물리적으로 성립하지 않는다.**

### (2) 지문 충돌 시 INSERT 예외 — 로그인 500

지문은 `HFPv2-` + FNV-1a 다(`device-fingerprint.js:66`). **FNV-1a 는 암호학적 해시가 아니고**
`_envSeed` 재료도 좁다(브라우저 환경 + UA). 같은 기종·같은 브라우저·같은 설정이면
**동일 지문이 나오는 것이 정상 동작이다.**

지금은 그래도 굴러간다 — 같은 지문이면 ③이 **기존 줄을 찾아** 붙기 때문이다(과다계수는 없음).
그런데 설계가 ①②를 앞에 놓으면:
- 기기 B 가 장비넘버 없이 옴 → ③ 지문으로 A 를 찾음 → 붙음 (여기까진 같음)
- 그러나 **장비넘버가 서로 다른 두 기기**가 ①에서 갈렸다가 ④ INSERT 로 가면
  → `UNIQUE(tenant_id, fingerprint)` **위반 → 예외 → 로그인 실패**

🔴 **과금 사고가 아니라 장애다.** 그리고 사무실에서 같은 노트북 모델을 쓰면 재현된다.

### (3) 헌법 #36 위반 가능성

DDL 을 바꿔야 하는데 세 문서가 **바꾼다고도 안 바꾼다고도 하지 않았다.**
구현자가 판단하게 되고, 판단하면 [[project_migration_real_path]] 사고 계통으로 간다
(마이그를 엉뚱한 자리에 두면 **고객에게 안 간다**).

---

## 4. 어떻게 고쳐야 하나

### (1) 설계 문서에 **DDL 변경 필요 여부를 명시**한다 — 이번 차수에서

최소한 다음을 결정해 문서에 남긴다:

| 결정할 것 | 선택지 |
|---|---|
| `fingerprint` 를 **nullable** 로 바꾸나 | 장비넘버 시대에는 지문이 없을 수 있다 |
| `UNIQUE(tenant_id, fingerprint)` 를 **어떻게 하나** | 유지 / 제거 / `device_id` 기준으로 교체 |
| 지문을 **여러 개** 담나 | 메인PC = `MAINPC-` + `HFPv2-` 둘 다 필요(§3-(1)) |

⚠️ **UNIQUE 를 그냥 제거하면 안 된다.** 지금 그 UNIQUE 가 **중복 INSERT 를 막는
마지막 방어선**이다(PI-10 참조). 제거하면 과다 계수가 오히려 늘어난다.

### (2) 권고 방향 — 별도 표로 지문을 뺀다

```
tenant_devices          — 기기 한 줄 (장비넘버가 PK). 과금 단위
tenant_device_prints    — 그 기기가 보인 지문들 (N개). 호환 조회 전용
    UNIQUE(tenant_id, fingerprint)   ← 지문 유일성은 여기서 지킨다
```

이렇게 하면 세 가지가 동시에 풀린다:
- 메인PC 가 `MAINPC-` 와 `HFPv2-` 를 **둘 다** 가질 수 있다 → §4-5 가 실제로 성립
- ③ 지문 경로가 **모든 옛 지문**을 커버한다 → G-9 재매핑이 실측 가능해진다
- `tenant_devices` 한 줄 = 슬롯 한 개가 **표 구조로 강제**된다 → I-1 이 DDL 로 지켜진다

🔴 **I-1 을 코드가 아니라 표 구조로 지키는 것이 핵심이다.** 코드 규칙은 다음 사람이 어긴다.

### (3) 마이그레이션 경로 못박기

DDL 을 바꾸면 **반드시** `src/HitPan.API/Migrations/SQL/DB-NN_*.sql` 에만 둔다
([[project_migration_real_path]] — 최신 DB-91). 그리고 clean DDL 편입(#36).
⚠️ 8/12 사고 재발 자리다 — **빌드·시험 전부 통과하고도 고객 화면에서만 터진다.**

## 5. 등급 판정 근거

**P0** — 이유:
1. **P4 가 DDL 상 성립하지 않는다.** 스케줄의 한 단계가 통째로 불가능한데 문서에 없다
2. 지문 충돌 시 **로그인 장애**(500) 경로가 열린다
3. DDL 판단이 **구현자에게 떠넘겨져** 있다 — 명세서 §3 서문의 원칙을 스스로 어겼다
4. 🔴 **지금은 고객이 0명이라 DDL 을 자유롭게 바꿀 수 있다**(명세서 §7 이 스스로 지적한 "유일한 창").
   베타가 나가면 이 창이 닫힌다 ⇒ **지금 안 정하면 영원히 비싸진다**
