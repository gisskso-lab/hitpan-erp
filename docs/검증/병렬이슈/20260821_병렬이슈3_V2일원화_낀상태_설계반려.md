## 0. 한 줄

**"결재설정 ON 이면 버튼 감춤" 은 위험하다.** 결재가 ON 인데도 **돌지 않는 상태**가 실재하고,
그때 버튼까지 감추면 **승인 수단이 0개**가 된다.

---

## 1. 🔴 낀 상태 — 실측으로 확인됨

### 재현 경로 (전부 코드 확인)

```
결재 ON → 초과근무 상신(pending) → 결재자 퇴사
   ↓
GetPendingAsync 는 approver_id 로 INNER JOIN     → 퇴사자 외엔 결재함에 안 뜬다
ProcessAsync 는 line.ApproverId != employeeId   → "결재 권한이 없습니다"
   ↓
관리자가 결재선을 고치려 하면
ApprovalService.cs:286  pendingCount > 0 → InvalidOperationException
   "진행 중인 결재가 N건 있어 결재선을 변경할 수 없습니다"
   ↓
V2 봉합 후에는 자체 승인 버튼도 감춰져 있다
   ↓
🔴 승인 0 · 반려 0 · 결재선 수정 0  → overtime.status = 'pending' 영구 고착
```

**퇴사가 이걸 막지 않는다** — `EmployeeService.GetResignPrecheckAsync` 는 주석에
*"막지는 않고 무슨 일이 벌어지는지 알려준다(반자동 원칙)"* 라고 **명시**돼 있다.

⇒ **헌법 #20 워크플로우 끊김 = P0.**

### 더 넓은 자리 — OFF→ON 전환

결재 OFF 시절에 쌓인 pending 초과근무들은 **결재 문서가 없다.**
설정을 ON 으로 켜는 순간 전역 판정으로는 **그 재고 전부의 버튼이 사라진다.**
결재 문서가 없으므로 결재함에도 안 뜬다 ⇒ **같은 고착이 재고 규모로.**

---

## 2. 🔴 두 번째 반증 — 판정 수단이 화면에 없다

설계서 §2-1 은 *"이미 있는 것을 쓴다 — `DescribeApprovalBlockerAsync`"* 라고 했다. **성립 안 한다.**

- 시그니처가 `static (IDbConnection db, ...)` — **Blazor WASM 은 DB 에 못 붙는다**
- 기존 호출자는 전부 **서버 측**(`AbsenceService`·`HrService`)
- `ApprovalController` 에 blocker 판정 엔드포인트 **0건**

### ⚠️ 우회로의 함정 (중요)

`api/approval/settings` 로 `IsEnabled` 만 보고 판정하면 **판정 조건이 갈라진다**:

| | 보는 조건 |
|---|---|
| `DescribeApprovalBlockerAsync` | 설정 ON **AND 결재선 1행 이상** |
| `settings` API | 설정 ON **만** |

⇒ *"설정은 켰는데 결재선을 안 짠"* 고객에게서 **버튼이 사라지고 결재도 안 돈다.**
`ApprovalTriggerHelper.cs:20` 주석이 *"판정 조건이 갈라지면 안 되므로 같은 두 조건만 본다"* 고
**이미 경고한 자리**다.

추가로 `settings` API 는 `[RequirePermission("APPROVAL","view")]` 라
HR 권한만 있는 직원은 **403** → 화면이 빈 목록으로 뭉개 **오판**한다.

## 3. ✅ 채택 — 행 단위 판정으로 바꾼다

전역 "결재 ON/OFF" 가 아니라 **이 건에 결재 문서가 실제로 있나** 로 판정한다.

```
버튼 감춤 조건  =  이 초과근무/휴직 건에 대한
                   approval_documents (doc_type, ref_id) 가 존재하고 pending 인가
```

| 상황 | 결재문서 | 버튼 | 결과 |
|---|---|---|---|
| 결재 OFF 고객 | 없음 | ✅ 보임 | 끊김 0 |
| 결재 ON · 정상 상신 | pending | 감춤 | 결재로 일원화 ✅ |
| 결재 ON · **상신 실패** | 없음 | ✅ 보임 | **고착 안 됨** |
| OFF→ON 전환 **재고** | 없음 | ✅ 보임 | **고착 안 됨** |
| 결재자 퇴사 | pending | 감춤 | ⚠️ **남는 위험** |

### 이 방식의 장점
- **DDL 변경 0** — `ref_id` 로 조회 가능(설계서 §3 판단이 이 용도에서 참)
- 판정 조건 분기 사고 **원천 차단** — 설정·결재선을 안 보고 **결과**를 본다
- 상신 실패·전환 재고를 **자동으로** 구제

### ⚠️ 남는 위험 — 결재자 퇴사
행 단위로 바꿔도 **결재문서가 pending 인 채 결재자가 사라진 경우**는 여전히 고착이다.
⇒ **별건**으로 "결재 회수·강제 종결" 경로가 필요하다(사장님 결재 필요).
지금 `approval_documents` 를 pending 에서 빼는 코드 경로는 `ProcessAsync` **하나뿐**이고
현재 결재자만 부를 수 있다.

## 4. 반증 중 PM 이 재확인한 것 — 2건은 기각/이미 반영

| 검증 지적 | PM 재확인 | 판정 |
|---|---|---|
| *"leave 는 amount 에 뭘 넣는지 확인 실패"* | `LeaveRequestService.cs:120` **`amount: request.LeaveDays`** 실재 | ⚠️ **검증 오류** — 비금액 선례 있음 |
| `overtime.reject_reason` 부재 → 500 위험 | **맞다.** 다만 PM 구현이 이미 그 컬럼을 **안 쓴다** | ✅ **이미 반영** |

🔴 `reject_reason` 지적은 **정확했다.** leave 블록을 그대로 복제했으면 런타임 500 +
트랜잭션 롤백으로 **결재함이 죽었다.** 구현 시 DDL 을 먼저 읽어 피했다(헌법 #13).

⚠️ 다만 **반려 사유를 초과근무 화면에서 볼 수 없다** — `approval_history.comment` 에는
남지만 `HrOvertimePage` 가 읽지 않는다. **본안에서 다룬다.**

## 5. 🔴 `auto_approve_below` 함정 — 별건 승격 권고

`amount < threshold` 면 **결재를 안 만들고 조용히 return** 한다.
비금액 문서(연차 `LeaveDays`·휴직 `0m`·초과근무 `hours`)가 이 자리에 들어가면
고객이 기준을 **금액 감각으로** 잡는 순간 전부 건너뛴다.

**휴직은 `0m` 이라 `threshold > 0` 이면 항상 건너뛴다** — 이미 있는 폭탄이다.

⇒ 비금액 문서유형에서 `auto_approve_below` 를 **무시**하도록 헬퍼에 분기가 필요하다.
**설계 변경이라 사장님 결재 후 별건.**
