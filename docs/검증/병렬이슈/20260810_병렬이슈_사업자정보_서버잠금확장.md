## I-1. 잠금 확장이 SELECT 만 되고 UPDATE 인자에 안 붙은 구간 — **해소됨**

| 항목 | 내용 |
|---|---|
| **ID** | I-1 |
| **등급** | ~~P0~~ → **해소** (개발팀 자체 봉합, 관측 2회차) |
| **최초 관측** | 1회차 |

### 발견 근거

1회차 관측 시 `SettingsService.cs:279-292` 의 `selectRequired` 는 8필드를 읽도록 확장돼 있었으나,
쓰기측(`SettingsService.cs:344-350`, 당시 줄번호)은 종전 그대로였다.

```
var zipCode  = TruncateNullable(dto.ZipCode, 10);     // ← required.ZipCode 를 안 봄
var bizType  = TruncateNullable(dto.BizType, 50);     // ← required.BizType 를 안 봄
var bizItem  = TruncateNullable(dto.BizItem, 100);    // ← required.BizItem 를 안 봄
```

즉 **SELECT 만 8필드로 늘고 잠금 판정은 여전히 3필드**였다. 주석은 "8필드를 잠근다"고 적혀 있었다.

### 왜 위험한가 (재발 방지 관점)

주석과 SELECT 는 "확장 완료"처럼 보이는데 실제 동작은 종전과 같다.
**코드리뷰에서 SELECT 문만 보고 통과시키기 가장 쉬운 형태**다.
잠금이 목적인 작업에서 잠금이 안 도는 것을 못 잡으면, 이후 검증은 전부 거짓 통과가 된다.

### 현재 상태 (최종 관측)

`SettingsService.cs:343·353·365·366·367` 에서 5필드 전부 `LockIfPresent` 를 경유한다. **해소 확인.**

```
343: var address = TruncateNullable(LockIfPresent(lockedFromLanding, required.Address, dto.Address), 200);
353: var corpNo  = LockIfPresent(lockedFromLanding, required.CorpNo, dto.CorpNo)?.Trim();
365: var zipCode = TruncateNullable(LockIfPresent(lockedFromLanding, required.ZipCode, dto.ZipCode), 10);
366: var bizType = TruncateNullable(LockIfPresent(lockedFromLanding, required.BizType, dto.BizType), 50);
367: var bizItem = TruncateNullable(LockIfPresent(lockedFromLanding, required.BizItem, dto.BizItem), 100);
```

### 권고

리뷰 체크리스트에 **"SELECT 확장 = 잠금 확장 아님. 쓰기 인자까지 따라갔는지 확인"** 한 줄 추가.

⇒ **이번 작업의 목적(무단사용 차단)이 4번 한 줄로 무효화된다.**

### 왜 P0 인가

작업지시서가 잠금을 확장한 이유는 §1-1 *"정상 가입한 뒤 5필드만 바꿔 다른 사업장처럼 쓰는 경로"* 차단이다.
그런데 그 5필드 중 4개가 **다른 문 하나로 그대로 열린다.**
문 하나만 잠그고 "잠갔다"고 하면 **거짓 봉합**이다.

구현설계서 §3-1 표는 `SettingsService.cs` 와 `SettingsController.cs` 만 나열했다 —
**`CompanyService.cs` 는 조사 대상에서 빠져 있었다.** 이것이 이번 설계의 사각지대다.

### 권고

1. `CompanyService.UpdateAsync` 의 잠긴 분기에서 **`biz_type`·`biz_item`·`address`·`zip_code` 를 UPDATE 문에서 제거**하거나 `SettingsService` 와 **동일한 `LockIfPresent` 규칙**을 적용
2. 더 나은 방향 — **잠금 판정을 한 곳으로 모은다.** 두 서비스가 각자 판정하는 한 규칙은 반드시 다시 갈라진다(이번이 그 증거다)
3. 커밋 전 필수: `local_company` 를 쓰는 **모든** 경로 재확인 (헌법 #12 — 인터페이스 확장 시 구현체 전수 grep)

### 서버측 — 개발팀이 이 함정을 스스로 인지하고 봉합했다 ✅

`:314-319` 주석이 이 위험을 정확히 서술하고 있다. **이 판단은 옳다. 서버측은 통과.**

그리고 우편번호를 채우는 유일한 수단인 **"우편번호 찾기" 버튼이 잠금 분기에 없다.**

### 재현 시나리오 (지금 `demo-tenant-0001` 에서 그대로 재현된다)

1. 잠긴 테넌트(`lk=1`)로 로그인 → 사용자정보설정
2. 업태·종목·법인등록번호 — 값이 NULL 이라 `_lock*` 이 `false` → 🟢 입력 가능, 저장됨
3. **우편번호** — 값이 NULL 인데 `ReadOnly="true"` 고정 → 🔴 입력 불가
4. **주소** — `_lockAddress = false` 라 입력란은 열리지만, 잠긴 분기에 "우편번호 찾기" 버튼이 없다
   → 주소는 직접 타이핑으로 채울 수 있으나 **우편번호는 끝내 빈칸으로 남는다**
5. 거래명세서·세금계산서 출력 시 사업장 우편번호가 계속 비어 있다

⇒ **서버는 열어 뒀는데 화면이 잠갔다.** I-5 를 서버에서 봉합한 의미가 화면에서 사라진다.

### 권고

## I-7. 화면과 서버 규칙 불일치 — 부분 정합 (**잔여 P1**)

| 항목 | 내용 |
|---|---|
| **ID** | I-7 |
| **등급** | 🟡 **P1** |
| **상태** | 대부분 정합 ✅ / **우편번호 1건 불일치** 🔴 |

### 확인 결과 — 개발팀이 화면도 함께 고쳤다 (부분 인정)

과제에 적힌 *"`UserInfoPage.razor` 는 아직 3필드만 ReadOnly"* 는 **최종 관측 시점에는 사실이 아니다.**
개발팀이 화면까지 확장했고, `UserInfoPage.razor.cs:27-34` 주석에 의도를 정확히 적었다:

> *"서버(SettingsService.SaveCompanyAsync)와 **같은 규칙**을 쓴다. 규칙이 갈리면 화면에서는 고칠 수 있는데 저장이 조용히 무시되는 상태가 되고, 고객은 이유를 모른다."*

**판단 자체는 정확하다.** 정합 상태:

| 필드 | 서버 (`SettingsService.cs`) | 화면 (`UserInfoPage.razor`) | 정합 |
|---|---|---|---|
| 상호 | `:323` 무조건 되돌림 | `:56` 잠긴 분기 → 표시 전용 | 🟢 |
| 대표자 | `:326` 무조건 되돌림 | 〃 | 🟢 |
| 사업자번호 | `:329` 무조건 되돌림 | 〃 | 🟢 |
| 업태 | `:366` `LockIfPresent` | `:62` `ReadOnly="@_lockBizType"` | 🟢 |
| 종목 | `:367` `LockIfPresent` | `:65` `ReadOnly="@_lockBizItem"` | 🟢 |
| 법인등록번호 | `:353` `LockIfPresent` | `:68` `ReadOnly="@_lockCorpNo"` | 🟢 |
| 주소 | `:343` `LockIfPresent` | `:74` `ReadOnly="@_lockAddress"` | 🟢 |
| **우편번호** | `:365` `LockIfPresent` (**빈칸이면 열림**) | `:71` **`ReadOnly="true"` 고정** | 🔴 **불일치** |

### 🔴 불일치가 남은 방향에 주의

이번 불일치는 **"화면이 서버보다 느슨한"** 흔한 방향이 아니라 **반대**다.
화면이 서버보다 **더 엄격**해서, 서버가 허용하는 입력을 **화면이 원천 봉쇄**한다.

- 보안 구멍은 아니다 (더 엄격하므로)
- 그러나 **고객이 정상 업무를 못 하는 상태**다 — I-5 와 같은 뿌리
- 히트판 최종 통과 기준 *"이 화면, 처음 보는 사람이 혼자 쓸 수 있냐?"* 에 **불합격**

### 부수 위험 — 다이얼로그가 잠금을 우회한다

`OnAddressSelected`(`UserInfoPage.razor.cs:247-253`)는 ZipCode·Address 를 **동시에** 덮어쓴다.

```csharp
250   _model.ZipCode = zonecode ?? string.Empty;
251   _model.Address = fullAddress ?? string.Empty;
```

`_lockAddress` 를 **확인하지 않는다.** 주소가 잠긴 상태에서 이 다이얼로그가 열리면
화면상 주소가 바뀌고 → 저장 → 서버가 되돌림 → **I-6 의 조용한 무시**로 이어진다.
현재는 잠긴 분기에 버튼이 없어 도달 불가하나, I-5 권고대로 버튼을 되살리면 **즉시 현실 문제가 된다.**

### 권고

1. I-5 권고 1·2·3 적용
2. `OnAddressSelected` 진입부에 `if (_lockAddress && _lockZipCode) return;` 가드 추가
3. 🔴 **잠금 규칙이 서버·화면 두 곳에 각각 적혀 있는 구조 자체가 원인이다.**
   `LockIfPresent`(서버 `:320`)와 `RecomputeLockFlags`(화면 `:40`)는 같은 규칙의 복사본이고,
   **이미 우편번호 한 건이 갈라졌다.** 잠금 대상 목록·판정 규칙을 **한 곳**에서 내려주고
   화면은 받아 쓰기만 하도록 바꿀 것을 권고한다 (지금은 두 번 고쳐야 하고, 한 번 빠뜨리면 오늘 같은 상태가 된다)

### 9-3. 가장 위험한 것 — "고쳤다"가 "막혔다"가 아니다

`SettingsService.cs` 만 보면 8필드가 확실히 잠겨 있다. 주석도 정확하고 `LockIfPresent` 판단도 옳다.

⇒ 검증 질문을 **"잠갔나"** 가 아니라 **"이 테이블을 쓰는 문이 몇 개고, 전부 잠겼나"** 로 바꿔야 한다.
