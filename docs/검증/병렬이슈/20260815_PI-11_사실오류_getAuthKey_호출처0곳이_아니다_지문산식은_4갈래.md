## 오류 ① — `getAuthKey` 호출처는 0곳이 아니다

### 명세서가 적은 것 (§2-2 · §4-4)

> *"함수는 이미 있다(`device-fingerprint.js:234,253`). **부르는 쪽만 없다.**"*
> 표: `로그인 때 서버로 보냄` → 🔴 **없음 — 호출처 0곳**

스케줄 P3 도 그대로 인용했다(`:166`).

### 실측

`src/HitPan.Web/Services/HitPanApiAuthHandler.cs:134`
```csharp
var key = await js.InvokeAsync<string?>("hitpanDevice.getAuthKey", Array.Empty<object?>())
    .ConfigureAwait(false);
if (!string.IsNullOrWhiteSpace(key))
    request.Headers.TryAddWithoutValidation(DeviceKeyHeader, key);
```

🔴 **`getAuthKey` 는 이미 호출되고 있고, 이미 모든 API 요청 헤더에 실려 나간다.**
받는 쪽도 있다 — `DeviceAuthMiddleware.cs:98-112` 가 그 헤더를 읽어 대조한다.

**정확한 사실**: `getDeviceId` 는 호출처 0곳이 맞다.
**`getAuthKey` 는 0곳이 아니라 이미 동작 중인 경로가 있다.**

### 왜 중요한가

1. **P3 작업량 판단이 틀어진다.** *"부르는 쪽만 없다"* 는 *"둘 다 새로 붙이면 된다"* 로 읽힌다.
   실제로는 **인증키는 이미 헤더로 가고 있고**, 로그인 body 에 또 넣으면
   **같은 값이 두 경로로 가는 이중 전달**이 된다. 어느 쪽이 진실인지 정해야 한다.
2. 🔴 **PI-08 과 연결된다.** 인증키 경로가 이미 살아 있다는 것은
   그 경로의 성격(출입증 vs 신분증)을 **지금 정의해야 한다**는 뜻이다.
3. 명세서 §2-2 표의 마지막 줄이 **설계 전체의 "결정적 사실"**(§0)로 제시됐다.
   그 줄이 절반 틀렸다 ⇒ 근거의 무게가 달라진다.

### 고칠 것

명세서 §2-2 표를 둘로 가른다:

| 있는 것 | 상태 |
|---|---|
| `getDeviceId()` 호출 | 🔴 **호출처 0곳** (사실) |
| `getAuthKey()` 호출 | ✅ **`HitPanApiAuthHandler.cs:134` — 이미 헤더로 전송 중** |

그리고 §4-4 를 **"장비넘버만 새로 붙인다. 인증키는 이미 가는 길이 있으니 그 길과의 관계를 정한다"** 로 고친다.

## 오류 ② — 지문 산식은 3갈래가 아니라 **4갈래**다

### 명세서가 적은 것 (§2-3)

> *"같은 `tenant_devices.fingerprint` 한 컬럼에 **서로 다른 산식 셋**이 들어온다."*
> (`device-fingerprint.js:66` / `MainPcRegistrationService.cs:230-239` / `UserInfoPage.razor.cs:116-117`)

### 실측 — 네 번째가 있다

`src/HitPan.Backoffice.API/Controllers/DeviceRegistrationController.cs:60`
```csharp
// fingerprint 해시 정규화 — 평문 길이 저장 사고 차단 + 헌법 #22 정합
var fingerprintHash = ComputeHmacSha256(req.Fingerprint, pepper);
```
그리고 `:125-140` 이 그 값을 `fingerprint` 컬럼에 **INSERT 한다.**

`ComputeHmacSha256` (`:225-230`) = **HMAC-SHA256 + pepper**, 64자 hex.
⇒ 접두어도 없고, 산식도 다르고, **pepper 라는 비밀값이 섞여 있어 ERP 가 절대 재현할 수 없다.**

| # | 만드는 곳 | 형식 |
|---|---|---|
| 1 | `device-fingerprint.js:66` | `HFPv2-` + FNV-1a |
| 2 | `MainPcRegistrationService.cs:230-239` | `MAINPC-` + SHA-256 |
| 3 | `UserInfoPage.razor.cs:116-117` | (eval 조립) |
| 4 | 🆕 **`DeviceRegistrationController.cs:60`** | **HMAC-SHA256(pepper)** — 백오피스 |

### 다만 — 정상 참작 (반증의 반증)

백오피스는 **자기 DB 의 자기 `tenant_devices`** 에 쓴다.
실측: `installer/backoffice/00_backoffice_core.sql:666` 에 **별도 `tenant_devices` 표**가 있다
(ERP 것과 컬럼이 다르다 — `device_token_hash`·`os_info` 있고, `is_main_pc`·`auth_key_hash` 없다).

⇒ **같은 컬럼에 4개가 섞이는 것은 아니다.** 명세서의 *"한 컬럼에 셋"* 은 **ERP DB 안에서는 맞다.**

🔴 **그러나 더 나쁜 사실이 드러난다** — 이게 진짜 지적이다:

**슬롯을 세는 곳이 ERP 4곳이 아니라, 서로 다른 DB 에 있는 두 계산기다.**

`DeviceRegistrationController.cs:65-66,99-101` 이 **백오피스 DB 에서 독자적으로**
한도를 읽고(`pricing_plans.max_pc_devices`) 기기를 세고 INSERT 한다.
- ERP: `local_subscription` + 코드 switch `(5,3)` 로 계산
- 백오피스: `pricing_plans` 표로 계산
- 🔴 **두 계산기가 서로의 존재를 모른다.** 같은 회사의 기기 대수에 대해 **다른 답을 낸다.**

### 왜 중요한가

명세서 §2-5 는 이것을 *"이중 진실원"* 이라며 **요금 기준값(한도) 문제**로만 다뤘다.
실측하면 **한도뿐 아니라 기기 등록·계수 자체가 이중화**돼 있다.

⇒ **I-4 불변식(*"슬롯을 세는 코드는 한 곳뿐"*)을 P1 에서 닫는다는 계획이 성립하지 않는다.**
P1 은 ERP 안의 4곳만 합친다. **백오피스 계산기는 그대로 남는다.**
🔴 **I-4 는 P1 이 끝나도 깨진 채다.** 스케줄 §4 대조표의 *"I-4 → P1 에서 닫는다"* 가 틀렸다.

### 고칠 것

1. 명세서 §2-3 에 **4번째 산식**과 **백오피스가 별도 DB·별도 표**임을 적는다
2. §2-5 "이중 진실원" 을 **"한도값 이중 + 계수기 이중"** 두 층으로 나눠 적는다
3. 🔴 스케줄 §4 에서 **I-4 를 P1 이 아니라 별도 단계로** 옮긴다.
   또는 *"P1 은 ERP 내부만 닫는다. 백오피스 계수기는 범위 밖"* 을 **명시**한다
   (작지서 §2 "하지 않는 것" 에 넣는다 — 지금은 **빠져 있다**)
