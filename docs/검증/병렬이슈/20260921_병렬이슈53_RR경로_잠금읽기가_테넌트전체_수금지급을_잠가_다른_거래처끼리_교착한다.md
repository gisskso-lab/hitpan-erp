## 증상

RR 경로(`LegacyMatchMode.RepeatableReadLocking`)가 붙이는 `LOCK IN SHARE MODE` 는
**논리적으로는 거래처 1건**이지만, **실제로는 그 회사의 `collections` 전 행**을 공유 잠금한다.
거래처 필터가 조인 상대 테이블(`sd`/`pr`)에 있어서 스캔 대상 테이블은 `tenant_id` 접두만으로 접근하기 때문이다.

결과:
1. 거래처 A 의 이월잔액 매칭이 도는 동안, **전혀 상관없는 거래처** P3·P9 의 수금 등록·수정이 1205 로 막힌다.
2. **서로 다른 두 거래처**가 동시에 이월잔액 매칭을 하면 교착 1213 이 난다 — `partner_legacy_balances` 행 `FOR UPDATE` 로 거래처 단위 직렬화를 해 둔 설계 전제(§11)가 RR 경로에서는 성립하지 않는다.
3. 사용자에게 남는 문구는 `MsgMatchBusyCollection` = 「지금 **다른 사용자가 같은 거래처의** 수금을 처리하고 있습니다」 — **사실과 다르다**(다른 거래처다). 헌법 #25 「쉽게」 위반.

이 모양은 3판이 이미 폐기한 것이다 — `LegacyBalanceMatching.cs:365` 주석:
> `파생표 LOCK IN SHARE MODE 방식은 다른 거래처 동시 매칭에서 교착 실측 → 폐기 · G8-w`

S1b ㉯ 는 파생표를 실테이블 직접 읽기로 바꿔 **최신성**은 고쳤지만, **잠금 범위**는 안 고쳤다.

## 해당 문장 (전부 `LOCK IN SHARE MODE` 꼬리 · 거래처 필터가 스캔 대상에 없다)

`src/HitPan.Application/Services/LegacyBalanceMatching.cs`
- `ReceivableMatchedDocLockedSql` (247줄대) — 스캔 = `collections ec`, 필터 = `sd.partner_id`
- `PayableMatchedDocLockedSql` — 스캔 = `payments ep`, 필터 = `pr.partner_id`
- `PayableMatchedReturnLockedSql` — 스캔 = `purchase_returns rt` + `purchase_return_items rti`, 필터 = `pr.partner_id`

`src/HitPan.Application/Services/CollectionService.cs`
- `EnsureCollectionTargetAllowedAsync` 전표 합(806줄대) — `ref_doc_id` 에 인덱스가 없다 → `idx_tenant_partner` 의 `tenant_id` 접두만 탄다
- `EnsurePaymentTargetAllowedAsync` `paid` / `returned` 두 문장 — 같다

즉 **이월잔액 매칭뿐 아니라 「거래명세서에 붙이는 일반 수금」 등록도** 회사 전체 `collections` 를 공유 잠금한다.
참조문서 없는 맨 수금은 잠금 읽기를 안 하지만, INSERT 가 위 잠금 범위 안이라 **똑같이 막힌다**(아래 실측 ②).

## 재현 절차 (실측 · 2026-09-21)

```
-- 위험 인스턴스 33406 · hitpan_v3rc_lock
-- 출하 DDL 과 같은 인덱스로 collections / sales_deliveries 생성, 거래처 P1·P2·P3·P4 행 4건
```

**① 실행계획 — 잠금 범위가 회사 전체임을 보인다**

```
EXPLAIN  (ReceivableMatchedDocLockedSql 과 같은 문장, @PartnerId='P1')
sd  ref  idx_sd_tenant_partner  key_len=292  rows=1
ec  ref  idx_tenant_partner     key_len=146  rows=4   ← tenant_id 접두만. 4 = 그 회사 전 행
```

**② 무관한 거래처 UPDATE 차단** — A 세션이 P1 매칭 문장을 `LOCK IN SHARE MODE` 로 잡은 상태에서

```
SET innodb_lock_wait_timeout=3;
UPDATE collections SET amount=amount+1 WHERE collection_id='C3';   -- 거래처 P3
→ ERROR 1205 (HY000): Lock wait timeout exceeded
```

**③ 무관한 거래처 INSERT 차단** — 같은 상태에서

```
INSERT INTO collections VALUES ('C9','T1','P9',...);               -- 거래처 P9 (새 행)
→ ERROR 1205 (HY000): Lock wait timeout exceeded
```

**④ 서로 다른 거래처끼리 교착** — A=P1 매칭, B=P2 매칭을 동시에 (각각 잠금 읽기 → INSERT)

```
A: 1000.00 → INSERT ok
B: 2000.00 → ERROR 1213 (40001): Deadlock found when trying to get lock
```

## 왜 재시도 껍질로 못 덮나

- `MatchTxMaxAttempts = 3` · 대기 50·150ms + 지터 ≤50ms → 체감 상한 약 0.5초.
- 재시도가 **같은 테넌트 전체 잠금**을 다시 잡는다 → 동시 사용자가 3명만 돼도 재시도끼리 또 교착한다.
- 소진하면 `InvalidOperationException(MsgMatchBusyCollection)` = 400. **수금 등록이 실패로 끝난다**(#20).
- CI 주석(`.github/workflows/build-and-test.yml`)은 이 1213 을 이미 보고도
  「재시도는 RR 경로에서 정상 동시 등록의 성립 조건」으로 **정상으로 기록**했다. 원인(잠금 범위)은 안 봤다.

## 요구 (코드는 안 고쳤다 · 판단은 설계·PM)

1. 거래처 필터를 **스캔 대상 테이블에 직접** 건다 — 예: `ec.partner_id = @PartnerId` 를 함께 붙이거나(이관 명세서 수금은 `ec.partner_id = sd.partner_id` 가 성립하는지 먼저 확인), 이관 전표 id 목록을 먼저 뽑아 `ec.ref_doc_id IN (…)` 으로 좁힌다.
2. 전표 합 문장(D1)은 `collections(tenant_id, ref_doc_type, ref_doc_id)` · `payments(tenant_id, payment_type, ref_order_id)` 인덱스가 없으면 잠금이 못 좁혀진다 → **인덱스 선행**(#9).
3. 좁힌 뒤 ②③④ 를 **게이트로** 등록한다 — 지금 게이트 11사례에는 「무관한 거래처가 안 막힌다」 대조군이 없다(→ 병렬이슈54).
4. 좁힐 수 없다면 재시도 상한·대기를 늘리는 게 아니라, **사용자 문구를 사실대로** 고치고 「STATEMENT 서버는 동시 수금 1명」을 제약으로 명시 결재.
