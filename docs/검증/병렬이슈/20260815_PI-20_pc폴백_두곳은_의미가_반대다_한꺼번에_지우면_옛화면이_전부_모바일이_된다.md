# 병렬이슈 PI-20 — `?? "pc"` 두 곳은 **의미가 반대다.** 함께 지우면 옛 화면이 전부 모바일이 된다

|---|---|
| 적발 | [3-V] 동시 병렬검증 **2회차** · 보안상무 안철수 · 2026-08-15 |
| 대상 | 명세서 **§17-5** · 작지서 작3 P1 · 함정 **D-9** |
| 등급 | 🟠 **P1** — 지시가 *"두 곳을 함께 지워라"* 인데, 그대로 하면 **PC 가 모바일 칸으로 계수된다** |
| 상태 | ⬜ 미봉합 |

## 1. 무엇이 문제인가

§17-5 · D-9 는 이렇게만 적혀 있다.
> `AuthController.cs:93` **와** `TenantDeviceService.cs:260`. **한 곳만 고치면 아무것도 안 바뀐다.**
> 작지서 P1: `?? "pc"` 폴백 제거 — 🔴 **두 곳**

🔴 **두 곳은 같은 코드가 아니다. 하는 일이 반대다.**
한 곳은 **값을 만들어 보내는 쪽**, 한 곳은 **안 온 값을 메우는 쪽**이다.
"둘 다 제거" 로 뭉뚱그리면 **옛 화면에서 접속한 PC 가 전부 모바일로 계수된다.**

---

## 2. 근거 (실측)

### (1) `AuthController.cs:93` — **보내는 쪽**의 기본값

```csharp
var deviceReq = new RegisterDeviceRequest
{
    Fingerprint = request.DeviceFingerprint!,
    DeviceType = request.DeviceType ?? "pc",
    ...
```
로그인 요청에 종류가 없으면 **`"pc"` 라는 값을 만들어** 서비스에 넘긴다.

### (2) `TenantDeviceService.cs:260` — **받는 쪽**의 기본값

```csharp
var type = NormalizeDeviceType(req.DeviceType) ?? "pc";
```
`NormalizeDeviceType` 이 **null 을 돌려줄 때만** `"pc"` 로 메운다.
그리고 그 null 은 **오직 한 경우** 뿐이다 — `:715`
```csharp
if (string.IsNullOrWhiteSpace(raw)) return null;
```
⇒ **"종류를 아예 안 보냈을 때"** 다. 모르는 값이 왔을 때는 null 이 아니라 `"mobile"` 이 나온다(`:724`).

### (3) 🔴 그래서 (1) 을 지우면 (2) 의 동작이 **바뀐다**

지금은 `AuthController:93` 이 `?? "pc"` 로 **항상 값을 채워 보내므로**,
`TenantDeviceService:260` 의 `?? "pc"` 는 **로그인 경로에서 사실상 도달하지 않는다.**

`AuthController:93` 의 `?? "pc"` 를 **먼저 지우면** `DeviceType` 이 null 로 흘러가고,
`NormalizeDeviceType(null)` → **null** → `:260` 의 `?? "pc"` 가 **비로소 살아난다.**

⇒ **둘을 같이 지우면** 그 null 이 갈 곳이 없다.
구현자가 `?? "mobile"` 로 바꾸면(§17-3 의 *"모르는 값은 싼 칸"* 논리를 따라)
🔴 **종류를 안 보내는 옛 화면의 PC 가 전부 모바일 칸으로 들어간다.**

### (4) 종류를 안 보내는 화면이 **실제로 있다** — 코드가 그렇게 말한다

`TenantDeviceService.cs:203-204` 주석
```
//   ⚠️ COALESCE 인 이유: 지문만 보내고 종류를 못 보내는 옛 화면이 있으면
//     기존 값을 지우지 않는다. 넘어온 값이 있을 때만 고친다.
```
`:709-712`
```
///   ⚠️ null 을 돌려주는 경우: 클라이언트가 종류를 **안 보냈을 때**.
///     신규 등록 경로는 호출부에서 ?? "pc" 로 받는다 — 값이 아예 없으면 종전 동작을
///     유지한다(옛 화면 호환). 값이 왔는데 모르는 값일 때만 휴대기기로 본다.
```

🔴 **`?? "pc"` 는 실수가 아니라 옛 화면 호환을 위해 의도적으로 둔 것**이고,
**그 이유가 코드에 적혀 있다.** §17-5 는 그 주석을 읽지 않고 "제거" 로 판정했다.

## 3. 터지면 무슨 일이 나나

| 상황 | 결과 |
|---|---|
| 옛 화면(종류 미전송) PC 접속 | 🔴 **모바일 칸으로 계수** ⇒ 모바일 한도(3) 가 먼저 참 ⇒ **진짜 휴대폰이 못 붙는다** |
| 반대로 `?? "pc"` 를 살리고 모르는 값만 mobile | 현행과 동일 — **아무것도 안 바뀐다**(D-9 가 경고한 그 상태) |
| 구현자가 (1) 만 지움 | (2) 가 살아나 **현행 동작 유지** ⇒ 시험은 통과, 사고는 그대로 |

🔴 **어느 쪽으로 가도 요금 계수가 바뀐다.** 그런데 작지서는 이것을
*"P0 스냅샷과 입력→출력 대조"* 로만 잡겠다고 한다 —
**스냅샷이 "종류 미전송" 입력을 포함하지 않으면 안 잡힌다.**

---

## 4. 어떻게 고치나

1. **"제거" 를 "정정" 으로 바꾼다.** 지울 것이 아니라 **어느 값으로 메울지를 정하는 것**이 본질이다.
2. **설계가 답을 확정한다** — *"종류를 안 보낸 기기는 무엇으로 보는가."*
   - 권고: **`pc` 유지**. 안 보내는 것은 **옛 브라우저 화면(=PC)** 이라는 근거가 코드에 있다(`:203`).
   - 🔴 `mobile` 로 바꾸면 **모바일 한도가 먼저 차서 차단이 빨라진다** — PI-12 가 이미 같은 이유로
     백오피스 싼 칸 정렬을 2차로 미뤘다. **같은 논리가 여기에도 걸리는데 작지서는 이 자리를 1차에 뒀다.**
3. **`AuthController:93` 은 지운다**(값을 만들어 보내는 쪽은 판정하면 안 된다).
   **`TenantDeviceService:260` 은 남긴다**(판정은 서비스 한 곳에서). ⇒ **한 곳만 지우는 것이 정답이다.**
   §17-5 의 *"한 곳만 고치면 아무것도 안 바뀐다"* 는 **틀렸다** — 한 곳(`AuthController`)만 고치는 것이
   판정을 서비스로 모으는 올바른 방향이고, 그것이 `20260811작2` 가 하던 일이다(`:257` 주석).
4. **시험에 "종류 미전송" 입력을 반드시 넣는다.** 이 입력이 없으면 어떤 게이트도 이 사고를 못 잡는다.

## 5. 판정

🟠 **§17-5 · D-9 는 실측이 얕다.** 두 자리의 역할 차이와 **의도적 호환 주석**을 보지 않았다.
지시대로 "둘 다 제거" 하면 **요금 계수가 조용히 바뀐다.**
착수 전 **"종류 미전송 = 무엇인가" 를 사장님/설계가 확정**해야 한다.
