## 2. 🔴 V10-1 (P0) — 판정축이 바뀌지 않았다

### 2.1 설계가 주장하는 안전 근거

작업지시서 `§4` 표가 이렇게 적는다.

> | 판정이 흔들리지 않음 | db.conf 는 **그 PC 에만** 있다. 클라이언트PC 에는 히트판이 설치돼 있지 않다 |

**앞 문장은 참이다. 뒤 문장에서 결론이 어긋난다.**

### 2.2 반증 — 질문이 잘못됐다

`MAIN_PC=1` 이 답하는 질문은 이것이다.

> **"이 API 프로세스가 도는 PC 가 메인PC 인가?"** → 언제나 **예**

그런데 기기를 등록하려면 이 질문에 답해야 한다.

> **"지금 로그인한 이 브라우저가 그 PC 위에서 도는가?"** → **`MAIN_PC` 는 이걸 모른다**

**히트판에 API 프로세스는 메인PC 에 단 하나뿐이다.** 그리고 클라이언트PC 의 브라우저도,
사내 다른 PC 도, 터널 밖 노트북도 — **전부 그 하나의 API 에 붙는다.**

`src/HitPan.API/Controllers/AuthController.cs:97-136` 의 로그인 처리는 **그 단일 프로세스 안에서** 돈다.
그 안에서 `TenantConfigReader.Get("MAIN_PC")` 를 부르면,
**누가 로그인했든 상관없이 `"1"` 이 나온다.** 파일에서 읽는 상수이기 때문이다.

`src/HitPan.Application/Common/TenantConfigReader.cs:18-26`
```
public static string? Get(string key)
{
    EnsureLoaded();
    if (_cache.TryGetValue(key, out var v) && ...) return v;   // ← 요청과 무관한 정적 캐시
```

`:14` `private static readonly Dictionary<string, string> _cache` — **static 이다.**
`HttpContext` 도, 요청도, 접속자도 이 함수에 들어가지 않는다.
**입력이 요청이 아니므로 출력이 요청별로 달라질 수 없다.**

### 2.3 병렬이슈 09 와 정확히 같은 형태다

| | 작2 (무너짐) | 작3 (지금) |
|---|---|---|
| 판정식 | `RemoteIpAddress 가 loopback인가` | `db.conf 의 MAIN_PC 가 1인가` |
| 의도한 뜻 | 메인PC 본인이 접속했다 | 메인PC 본인이 접속했다 |
| 실제 뜻 | 요청이 API 에 도달했다 | **이 서버가 메인PC 에 설치됐다** |
| 고객사에서 값 | **항상 참** | **항상 참** |
| 거짓이 되는 조건 | 이론상 있음(외부 바인딩 시) | **없음 — 파일 상수** |

⚠️ **마지막 행이 핵심이다.** 작2 의 loopback 은 배포 형태가 바뀌면 거짓이 될 수 있었다.
`MAIN_PC` 는 **설치된 그 서버에서 영원히 1** 이다. 더 단단해 보이지만, **틀린 것을 더 단단하게 만든 것**이다.

### 2.4 그래서 실제로 무슨 일이 일어나는가

설계 §4 흐름을 그대로 따라간다.

```
[첫 로그인]  아직 메인PC 가 없으면 → 이 기기를 메인PC 로 확정
```

**"이 기기"가 누구인가?** — `MAIN_PC` 가 아니라 **그때 로그인한 사람의 지문**이다.
`AuthController.cs:125` 이 넘기는 `request.DeviceFingerprint` 는 **브라우저가 만든 값**이고,
그 브라우저는 클라이언트PC 의 것일 수 있다.

⇒ **테넌트 전체에서 맨 처음 로그인한 사람의 PC 가 메인PC 표식을 가져간다.**
그게 사장님 노트북이든, 경리 직원 PC 든, 사무실 밖 휴대폰이든 상관없다.

**재현 경로**
1. 고객사 메인PC 에 히트판을 설치한다 (`db.conf` 에 `MAIN_PC=1` 기록됨)
2. 설치가 끝나고 브라우저가 뜨지만 **사장이 자기 노트북에서 터널 주소로 먼저 로그인한다**
3. 서버는 `MAIN_PC=1` 을 읽는다 → 참
4. 그 테넌트에 `is_main_pc=1` 이 0건 → **노트북이 메인PC 로 확정된다**
5. 나중에 진짜 메인PC 에서 로그인한다 → 이미 1건 있음 → **일반 기기로 등록**

⇒ **CS 가 목록을 보면 정확히 반대로 알려준다.** 사장님이 지적하신 그 전화에서
CS 는 "그 PC 가 메인PC 입니다" 라고 **틀린 안내**를 하게 된다.
구분이 없는 것보다 **틀린 구분이 더 나쁘다** — CS 가 그것을 믿고 조치하기 때문이다.

### 2.5 ⚠️ [추정] — 확률이 낮지 않다

이것이 드문 사고인지 따로 봤다. **아니다.** §3 (V10-2) 참조.

## 3. 🔴 V10-2 (P0) — "첫 로그인 = 메인PC" 가 실제로 자주 틀린다

설계는 첫 로그인이 메인PC 에서 일어난다고 **암묵적으로** 가정한다.
그런데 작업지시서 어디에도 그 가정이 명시되지 않았다. **가정을 적지 않으면 검사할 수 없다.**

### 3.1 첫 로그인이 클라이언트가 되는 경로 — 전부 실재한다

| # | 경로 | 근거 | 실재성 |
|---|---|---|---|
| 1 | 설치 담당자(대리점 기사)가 설치만 하고 **로그인 안 하고 나감**. 다음날 사장이 자기 자리 PC 에서 첫 로그인 | 베타=대리점이 고객사에 설치 (메모리: 공영정보(주) 5만 고객사) | **[확인] 높음** |
| 2 | 메인PC 는 **서버 역할로 구석에 두고** 사람은 자기 자리에서 쓴다 | 메인PC=DB·터널 보유 PC. 사람이 그 앞에 앉을 이유가 없다 | **[확인] 높음** |
| 3 | 부모계정 최초 생성·약관동의를 **사장 노트북**에서 한다 | 첫 로그인 약관 동의는 전원 필수 (CLAUDE.md) | **[추정] 중간** |
| 4 | 설치 직후 브라우저가 **터널 도메인**을 열어, 메인PC 본인조차 클라이언트와 구분 불가 | `hitpan-start.bat:80` — V10-4 | **[확인]** |

⚠️ **경로 2 가 가장 무섭다.** 히트판 설계상 메인PC 는 **"자료를 가진 PC"** 이지
**"사람이 쓰는 PC"** 가 아니다. 오히려 **사람이 안 쓰는 PC 일수록 좋은 서버**다.
그런데 설계는 "그 PC 에서 사람이 가장 먼저 로그인한다" 에 기대고 있다.
**히트판 자신의 아키텍처와 어긋나는 가정이다.**

### 3.2 되돌릴 수단이 없다

한 번 잘못 확정되면 고칠 방법이 있는지 봤다.

- `DeviceController.cs:24·44·53` — 입구 3개(목록·쿼터·폐기). **메인PC 지정·해제 API 0건**
- `ITenantDeviceService` — 그런 기능 없음
- 화면에서 고칠 수단 0건

⇒ **틀리면 영구히 틀린 채로 남는다.** DB 를 손으로 고치는 수밖에 없고,

## 4. 🔴 V10-3 (P0) — 기존 고객은 메인PC 가 영원히 안 생긴다

작업지시서 §4·DB-86 주석이 이렇게 약속한다.

> *"이미 일반 기기로 등록돼 있으면 **그 행이 승격된다**(새 행을 만들지 않는다 — 슬롯 이중소모 방지)."*
> — `DB-86_tenant_devices_is_main_pc.sql:41`

**그 승격을 수행할 코드 자리가 지금 UPDATE 문에 없다.**

`src/HitPan.Infrastructure/Services/TenantDeviceService.cs:161-176`
```
UPDATE tenant_devices
SET last_seen_at = NOW(),
    ip_address   = @Ip,
    user_agent   = COALESCE(@Ua, user_agent),
    device_name  = COALESCE(@Name, device_name)
WHERE device_id = @Id
```

`is_main_pc` 가 **없다.** 그리고 이 경로는 **기존 고객 전원이 반드시 타는 경로**다.

### 왜 반드시 타는가 — UNIQUE 제약이 강제한다

`installer/hitpan_db_clean.sql:3440`
```
UNIQUE KEY `uq_tenant_fp` (`tenant_id`,`fingerprint`)
```

`TenantDeviceService.cs:119-128` 이 `(tenant_id, fingerprint)` 로 먼저 조회하고,
있으면 `:161` UPDATE 로 가고 **`:262` INSERT 에 도달하지 않는다.**

기존 고객의 메인PC 는 **이미 일반 기기로 등록돼 있다**(작2 이전부터 로그인해 왔으므로).
⇒ 마이그(DB-86)로 컬럼이 생기고 전 행이 `is_main_pc=0` 이 된 뒤,
그 PC 에서 로그인하면 **UPDATE 경로로 빠지고, `is_main_pc` 는 0 그대로 남는다.**

**재현 경로**
1. 기존 고객이 업데이트를 받는다 → DB-86 적용 → 전 기기 `is_main_pc=0`
2. 메인PC 에서 로그인한다 (지문이 이미 `tenant_devices` 에 있다)
3. `:128 existing is not null` → `:161` UPDATE → `is_main_pc` 손대지 않음
4. **`:262` INSERT 에 영원히 도달하지 않는다**
5. ⇒ 그 테넌트의 `is_main_pc=1` 은 **영원히 0건.** 표식도 CS 축도 작동 안 함

⚠️ **이것이 조용한 결함이다.** 오류도 화면 이상도 없다.
목록에 표식이 안 보일 뿐인데, 그게 "메인PC 가 아직 안 잡혔다" 인지
"이 화면이 원래 그런 것" 인지 아무도 모른다. **병렬이슈 09 가 지적한 것과 같은 성질**이다.

⭐ **신규설치 고객만 동작하고 기존 고객은 안 되는 형태** — 이것은 작2 의 D-4 가
정확히 같은 이유로 반려됐던 형태다(`TenantDeviceService.cs:152-157` 주석이 그 이력을 적고 있다).
**같은 함정을 같은 파일에서 두 번째로 밟는다.**

## 5. 🟠 V10-4 (P1) — 메인PC 본인도 터널 도메인으로 들어온다

작업지시서 §3-2 #5 가 이 사실을 **이미 알고 적었다.** 그런데 §4 설계가 그것을 **소비하지 않았다.**

`installer/hitpan-start.bat:60-61`
```
set OPEN_URL=http://localhost:%API_PORT%
if not "%PRIMARY_DOMAIN%"=="" if not "%PRIMARY_DOMAIN%"=="localhost:5234" set OPEN_URL=https://%PRIMARY_DOMAIN%
```
`:75` `start "" cmd /c "timeout /t 5 /nobreak >nul && start %OPEN_URL%"`

⇒ 터널이 발급된 정상 고객사에서는 **메인PC 바탕화면 아이콘이 터널 도메인을 연다.**

**설계에 미치는 영향** — 두 가지다.

1. **판정 축으로는 무영향** ✅ — `MAIN_PC` 는 어차피 요청과 무관하므로 주소가 뭐든 같다.
   작업지시서가 이걸 §3-2 에 적은 것은 **"주소로 구분하지 마라"** 근거로서 정확하다.
2. **그러나 지문 축에 영향이 있다** 🟠 — 메인PC 사용자와 클라이언트 사용자가
   **같은 origin(터널 도메인)** 을 쓰게 된다. `device-fingerprint.js:5-16` 이 origin 격리를

### 작업 항목별 판정

| | |
|---|---|
| ✅ 그대로 진행 | **T1**(DB-86) · **T2**(db.conf `MAIN_PC=1`) — 둘 다 정확하고 필요하다 |
| 🟠 보강 필요 | **T1** clean DDL 반영(V10-6) · **T4** SELECT·DTO 배선 명시(V10-7) |
| 🔴 재설계 | **T3** — "첫 로그인이 확정" 이 성립하지 않는다 |
| ⬜ 별건 결재 | 한도 꽉 참 시 메인PC 탈출구(V10-5) · 기존 고객 `MAIN_PC` 전달 경로(V10-9) · 오지정 복구 수단(V10-2) |

### ⚠️ 왜 이번에도 개발PC 에서는 안 보이나

개발 PC 에는 **`db.conf` 자체가 없거나 `MAIN_PC` 가 없다.**
⇒ `Get("MAIN_PC")` 가 `null` → 아무 기기도 메인PC 가 안 됨 → **아무 일도 안 일어난다.**
결함이 **드러나지 않고 조용히 무동작**한다. 사장님 못박으신 그대로다 —
*"개발환경 PC 정상작동은 큰 의미 없다."*

**실측 제안** (10분이면 확정된다)
1. Sandbox 에 설치 (`db.conf` 에 `MAIN_PC=1` 생성 확인)
2. **다른 기기(휴대폰·다른 브라우저)에서 터널 도메인으로 먼저 로그인**
3. `SELECT device_name, is_main_pc FROM tenant_devices;`
4. **그 기기에 `is_main_pc=1` 이 붙으면 V10-1·V10-2 가 확정된다**

## 13. 권고 — 판정축 대안 (결정은 사장님·CTO)

**코드는 수정하지 않았다(SoD).** 방향만 적는다.

문제를 한 문장으로 줄이면 이렇다.

> **서버는 자기가 어느 PC 위에 있는지 안다. 그런데 브라우저가 어느 PC 위에 있는지는 모른다.**
> 이 둘을 잇는 것이 없다.

이으려면 **설치가 만든 사실**과 **브라우저가 만든 지문**을 **한 번은 만나게** 해야 한다.

| 축 | 방법 | 장점 | ⚠️ 걸림돌 |
|---|---|---|---|
| **(가) 로컬 접속에 한정** | `MAIN_PC=1` **그리고** 접속 주소가 `localhost`/`127.0.0.1` 일 때만 확정. 브라우저가 보낸 `Origin`/`Referer` 로 판정 | 메인PC 본인만 로컬 주소를 쓸 수 있다 | `hitpan-start.bat:80` 이 터널 주소를 여는 것을 **로컬 주소로 되돌려야** 한다(V10-4). 설치 변경 동반 |
| **(나) 설치가 1회용 표를 만든다** | 설치마법사가 `db.conf` 에 난수 `MAIN_PC_CLAIM=<난수>` 를 쓰고, **메인PC 브라우저만** 그 값을 읽어(로컬 파일·로컬 전용 엔드포인트) 첫 로그인에 제시 | 지문과 설치 사실이 실제로 만난다 | 브라우저가 그 값을 어떻게 받는가가 새 설계. 로컬 전용 엔드포인트 필요 |
| **(다) 사람이 지정한다** | 자동 확정을 포기하고, 기기 목록에서 관리자가 **"이 컴퓨터를 메인PC 로 지정"** 을 누른다 | 가장 단순하고 **틀려도 고칠 수 있다** | 사장님 오더 *"자동등록"* 과 어긋난다. 다만 **되돌릴 수단**은 어느 안이든 필요하다 |
| **(라) (가)+(다) 병행** | 로컬 접속이면 자동 확정, 아니면 미확정으로 두고 화면에서 지정 | 자동을 살리면서 탈출구 확보 | 구현량이 가장 크다 |

⭐ **어느 안을 택하든 반드시 함께 가야 하는 것 2가지:**
1. **되돌리는 길** — 잘못 확정됐을 때 고치는 수단(V10-2·§11.4)
2. **승격 경로** — 기존 고객의 이미 등록된 행을 메인PC 로 올리는 UPDATE(V10-3)

## 14. 이번 건에서 남길 교훈

> **판정식을 바꿨다고 판정축이 바뀐 것은 아니다.**

작2 는 `RemoteIpAddress` 를 봤고, 작3 은 `db.conf` 를 본다. **식은 완전히 다르다.**
그래서 "고쳤다" 고 느끼기 쉽다. 그러나 두 식은 **같은 답을 낸다** — 언제나 참이다.

바뀐 것은 **틀리는 이유**뿐이다.
- 작2: 모든 요청이 loopback 으로 **수렴**해서
- 작3: 서버가 **하나**뿐이라 서버 속성이 전 요청에 **공통**이라서

⇒ 다음에 판정 근거를 고를 때는 식을 보지 말고 **이 질문 하나를 던진다.**

> 🔴 **"이 값은 요청마다 달라지는가?"**
>
> 달라지지 않는다면, 그것으로 **요청을 구분할 수 없다.** 식이 아무리 그럴듯해도 마찬가지다.

`MAIN_PC` 는 **서버를 설명하는 값**이지 **접속을 설명하는 값**이 아니다.
서버를 설명하는 값으로 접속을 구분하려 한 것이 이번 설계의 한 줄짜리 오류다.

⭐ 그리고 하나 더 — **작업지시서 §3-2 는 훌륭했다.** 못 쓰는 축 5개를 정확히 열거했다.
무너진 자리는 *"그래서 무엇을 쓸 것인가"* 였다. **못 쓰는 것을 다 지운 뒤,
남은 것이 정말 되는지는 다시 묻지 않았다.** 소거법의 마지막 후보도 검증 대상이다.
