## §1 S-5 — 키 이름은 PC 당 하나인데, 봉인값은 회사당 하나다 🔴

### §1-1 사실

- 작지서 §1-3: 상수 `HitPan.MainPc.SealKey` **하나**. 회사 식별자가 이름에 안 들어간다.
- 봉인값이 들어가는 칸은 **회사마다 따로**다 — `MainPcProofService.cs:112-117` 이 `tenant_id` 로 골라 읽는다.
- 그 칸이 회사마다 있을 수 있다는 것은 **스키마의 전제**다:
  `src/HitPan.API/Migrations/SQL/DB-120_main_pc_single_row_guard.sql:107` *"main_pc_key = 메인PC 일 때만 tenant_id, 아니면 NULL"* · `:179` 그 컬럼에 UNIQUE.
  ⇒ **회사당 1대**를 보장하는 장치다. 「PC 당 1회사」를 보장하는 장치가 아니다.
  (⚠️ 한 설치에 회사가 둘 이상 서는 **실물 분포**는 PM 권한 밖 — 사장님 결재 `multi_business_per_pc` 가 근거이나 **확인 필요**로 남긴다.)

### §1-2 무슨 일이 생기나 (TPM `P` 갈래일 때)

```
회사A 등록 → HitPan.MainPc.SealKey 생성        → A 칸에 봉인값A
회사B 등록 → 같은 이름 · OverwriteExistingKey  → 키가 바뀐다 → B 칸에 봉인값B
회사A 다음 로그인 → 봉인값A 가 안 풀린다 → NotThisPc → [이 컴퓨터로 바꾸기] 팝업
      대표가 누른다 → 키가 또 바뀐다 → 이번엔 회사B 가 죽는다
```

**같은 PC 에서 두 회사가 서로를 영구히 쫓아낸다.** 고객에게는 *"컴퓨터가 바뀌었습니다"* 로만 보인다 — 9/23 **M-12 와 글자 하나 다르지 않은 모양**이다(공유 키 이름 + 덮어쓰기).
🔴 작지서·설계 어디에도 **두 번째 봉인**을 다루는 문장이 없다. 게이트 8건도 왕복을 **1회**만 돈다(작지서 §5-1 G-21a·G-21b).

### §1-3 회사가 하나여도 남는 것 — 등록이 실패하면 옛 값이 죽는다

`MainPcProofService.cs:235` 봉인 → `:259-265` DB 쓰기 → `:267` `rows == 0` 이면 `false` 반환.
**봉인이 먼저다.** 덮어쓰기 키라면 이 시점에 옛 키는 이미 사라졌고, DB 에는 **옛 봉인값이 그대로** 남는다.
⇒ **등록 실패 1회가 옛 봉인값을 영구히 못 풀게 만든다.** 되돌리는 경로가 없다.
🔴 가설이 아니라 지금 열려 있는 **M-22 의 남은 후보 D-2(`rows==0`)** 와 정확히 겹치는 자리다. 새 서비스가 같은 순서를 물려받으면 같은 일이 새 키에서 반복된다.

### §1-4 무엇을 정해야 하나 (PM·사장님)

1. 키 이름에 회사 식별자를 섞을 것인가 (`HitPan.MainPc.SealKey.{tenant_id}`) — 섞으면 §1-2 가 사라진다.
2. 또는 봉인을 `L` 고정으로 두어 **이름 있는 키를 아예 안 쓸 것인가** — DPAPI 는 키 이름이 없어 덮을 것이 없다. 단 §4 의 대가를 받는다.
3. 봉인과 DB 쓰기의 **순서**(먼저 쓰고 나중에 봉인 · 또는 실패 시 옛 값 복구)를 작지서에 명시할 것인가.
🚫 셋 다 **내가 고르지 않는다** — 모듈 경계·등급은 PM·사장님 결재 사항이다(9/22 지적).

## §3 S-2 — 출입증은 30분짜리 이동식 bearer 이고, 절C 가 그 발급을 넓힌다 🔴

### §3-1 지금 무엇이 있나

- `MainPcProofService.cs:193` `_passes` 는 **static** · 값은 **만료 시각 하나**.
- `:210-222` `IsPassValid` 는 **존재와 만료만** 본다. 회사·사용자·기기 대조 **0**.
- `MainPcOnlyAttribute.cs:83-92` 는 그 헤더(`X-MainPc-Pass`) 값 하나로 통과시킨다.

⇒ 헤더 한 줄을 복사하면 **다른 컴퓨터에서도 30분간 메인PC 다.** 한 프로세스가 회사를 둘 담고 있으면(§1-1) **다른 회사 요청도 그 출입증으로 통과한다.**
**열린 쟁점 O-2 는 실재한다** — 반증이 아니라 확인이다.

### §3-2 봉합이 구멍을 넓히는가 — **넓힌다**

| | 지금 | 절C 뒤 |
|---|---|---|
| 누가 받나 | `MainPcGate.razor:126` — **대표(`tenant_admin`)만** 왕복을 돈다 | **로그인한 누구든.** `mainpc-challenge`(`DeviceController.cs:513-521`)·`mainpc-verify`(`:566-581`)는 `account_type` 을 **안 본다** |
| 언제 | 로그인 직후 **1회**(`MainPcGate.razor:111-114` `_ran`) | **403 이 날 때마다**(요청당 1회·60초 쿨다운) |
| 어디서 | 메인PC 관문이 걸린 화면 | **모든 화면** — 핸들러는 전역이다(`HitPanApiAuthHandler.cs:33`) |

기능 차단은 아직 `TenantAdminOnly` 가 잡는다(`BackupController.cs:16` · `DataResetController.cs:16` · `MigrationController.cs:21`).
🔴 그러나 **메인PC 자물쇠 자체(출입증)는 그 PC 를 쓰는 직원 전원의 브라우저로 복제된다.** 유출 표면이 1인 → n인이 된다. 자물쇠와 권한은 **다른 축**이라 「어차피 대표만 쓴다」는 방어가 안 된다.

- `IsPassValid` 에 회사 대조를 더하는 것은 **O-2 별건** — 여기서 요구하지 않는다. 다만 **O-2 가 닫히기 전에는 절C 가 발급을 넓히지 않아야 한다.**

## §4 S-6 — O-3 의 「`L` 은 안전하다」 반증 🟡

PM 결재(작지서 §7): *"`L`(DPAPI LocalMachine)은 **TPM 이 없어도 된다** … `U` 까지 내려가는 건 비정상 상황"*.
**결론은 지지한다**(`U` 를 봉인에서 빼는 것은 옳다 — 프로필이 바뀌면 조용히 죽는다). **근거 문장은 틀렸다.**

| 축 | `P`(TPM) | `L`(DPAPI LocalMachine) |
|---|---|---|
| TPM 없는 PC | 못 쓴다 | **된다** ✅ O-3 의 주장 |
| 값을 다른 PC 로 옮기면 | 못 푼다 (키가 칩 밖으로 안 나온다) | **DB + `%ProgramData%\Microsoft\Crypto\RSA\MachineKeys` 를 함께 복사하면 풀린다** 🔴 |

설계 §6 이 **대안 B(`SealKey` 를 Software 금고로 낮추기)** 를 버린 이유가 *"DB 가 새면 봉인값도 새고, 그 값을 다른 PC 로 옮기면 풀린다"* 였다.
⇒ **TPM 없는 고객은 대안 B 를 고른 것과 같은 상태가 된다.** 그 말이 설계·작지서 어디에도 없다. 「안전하다」가 아니라 **「가용성을 위해 위조저항을 낮춘다」**로 적혀야 사장님이 판단할 수 있다.

### §4-1 같은 PC 인데 `L` 이 안 풀리는 조건 (있다)

- `MachineKeys` 폴더 소실·ACL 손상(백신·정리도구·수동 권한 변경) — 드물지만 **복구 불가**
- Windows **「이 PC 초기화」·복구 재설치** · 시스템 복원 지점 롤백
- 이미지 복제(sysprep 없이 배포한 PC) — **같은 키가 여러 PC 에 있다** ⇒ 여러 PC 가 동시에 메인PC 로 판정될 수 있다 ⚠️분포 미확인
- (도메인 가입/탈퇴·계정 SID 변경은 `L` 에 영향 없다 — 그것은 `U` 의 약점이다. **PM 판단 그 부분은 맞다**)

## §5 S-1 · S-3 — 봉투와 재왕복 🟡

### §5-1 S-1 — 갈래 강등은 성립하지 않는다. 그러나 봉투는 무방비다

- 강등이 성립하려면 `[4]` 를 `L` 로 바꾸고 **그 PC 의 machine key 로 만든 본문**을 함께 넣어야 한다. 본문을 못 만들면 해제가 실패해 `NotThisPc` 로 끝난다(작지서 §5-1 **G-23** 이 바로 이것을 문다). ⇒ **온라인 강등 공격 없음.**
- 남는 것 둘:
  1. **무결성 보호가 없다.** 봉투 5바이트는 MAC 없이 평문이다 ⇒ DB 를 읽을 수 있는 사람은 **어느 PC 가 `L`(이식 가능)인지 한 바이트로 안다.** 공격 대상을 고르는 정찰 정보다.
  2. **판정이 「복호 성공 여부」뿐이다** — `MainPcProofService.cs:128-135` 는 풀린 바이트를 **무엇과도 대조하지 않는다.** 봉인은 비밀 대조가 아니라 **복호 오라클**이다. 지금과 같은 성질이라 새 구멍은 아니지만, 봉투가 이 성질을 **고정**한다. 원문을 어딘가에 함께 두고 대조할지는 **설계 결정 사항**으로 남는다.

### §5-2 S-3 — 무한 왕복은 아니다. 세 가지가 빠졌다

작지서 §3-1 의 방어는 유효하다: 왕복 3콜 **경로 제외**(고리 차단) · 요청당 1회 · 60초 쿨다운.
악의적 클라이언트는 이 핸들러를 안 거치고 API 를 직접 때릴 수 있으므로 **새 공격면도 아니다**(표 발급은 인증이 필요하다 `DeviceController.cs:518`).
빠진 것:
1. **쿨다운이 「실패 시」에만 걸린다.** 왕복은 성공하는데 서버가 계속 403 인 상태 — 표·출입증이 **메모리에만** 있으므로(`MainPcProofService.cs:46,193`) API 가 재시작되면 실제로 그렇게 된다 — 에서는 **매 요청마다 3콜**이 영구히 돈다. 폴링 화면이 있으면 초당 왕복이다.
2. **직렬화가 없다.** 401 에는 `RefreshLock`(`HitPanApiAuthHandler.cs:31`)이 있는데 §3-1 에는 대응물이 없다. `BackupPage.razor:39-50` init 3콜이 동시에 403 ⇒ **왕복 3중 동시 실행 · 표 3장 소모 · 마지막 응답이 `sessionStorage` 를 덮는다.** 절C 가 없애려는 소음을 절C 가 만든다.
3. `_challenges`(`:46`)는 static 이고 `SweepThreshold`(`:40`)는 **상한이 아니라 청소 방아쇠**다 — `Sweep()`(`:314-319`)은 **만료된 것만** 턴다. 60초 안에 표를 계속 발급하면 딕셔너리가 계속 자란다. 절C 는 그 호출을 **자동화**한다. 🟡 인증이 필요하므로 외부 공격이 아니라 **자기 PC 가 자기를 때리는** 쪽이다.
