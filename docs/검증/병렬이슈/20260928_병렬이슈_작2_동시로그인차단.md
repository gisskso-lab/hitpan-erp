## PI-1 🔴 P0 — 토큰이 sessionStorage 다: 브라우저를 닫으면 자기 PC 에 8h 갇힌다

**무엇이**
- `src/HitPan.Web/wwwroot/js/storage.js:1-10` — `SESSION_KEYS = new Set(['access_token','refresh_token'])` → 두 토큰은 **`sessionStorage`**(탭 종료 시 소거). `index.html:70` 에서 로드된다.
- 이름은 `HitPanProtectedLocalStorage` 지만 실제 뒷단은 위 JS 다(`HitPanProtectedLocalStorage.cs` → `hitpanStorage_set`).
- 🔴 [1-V] 선행검증서 [`쿨타임 §56`](../선행/20260928_선행검증서_쿨타임_자동로그아웃.md) 은 *「`HitPanProtectedLocalStorage`(브라우저를 닫아도 남는 저장소 ⚠️파일 이름 기준)」* 이라 적었다 — **파일 이름 기준 추정이 틀렸다.** 설계 §12 는 「저장소를 비우면」을 드문 예외로 다뤘으나 실제로는 **탭을 닫을 때마다** 저장소가 빈다.

**왜 잠기나** (설계 §3-1 · 작지 절B)
1. PC1 에서 09:00 로그인 → `user_sessions` 행 `expires_at = 17:00`(`AuthService.cs:328` · `AccessTokenLifetime = 8h` `:21`).
2. 사용자가 로그아웃 없이 **탭/브라우저를 닫는다**(또는 브라우저 충돌 · Windows Update 재부팅 · 주소창에 새 탭으로 다시 입력).
3. 다시 열면 토큰 없음 → 로그인 화면 → 로그인 → `EnforceSinglePcLoginAsync` 의 생존 PC 조회(`:252-256` — `user_id` + `pc` + `expires_at > now`)가 **방금 닫은 자기 세션**을 찾는다 → 409 「다른 PC에서 사용 중입니다.」
4. K-4 (다): 버튼 없음 · 풀어 주는 기능 없음 · 쿨타임 미구현 ⇒ **17:00 까지 그 계정은 어느 PC 로도 못 들어온다.** 갱신도 불가(토큰이 없다).
- 사장님 판정(설계 §9-1)이 받아들인 것은 *「퇴근 뒤 집 PC」「다른 브라우저」* 이지 **「같은 PC 에서 창을 닫았다 다시 연 것」이 아니다.** 흐름 끊김 #20 · 쉬움 헌법 정면 충돌.
- 근퇴: 로그아웃 = 퇴근 기록(`AuthController.cs` `CheckOutAsync`). 창을 닫고 나간 사람은 **퇴근 기록도 없고 다음 PC 로그인도 막힌다.**

**재현 (⚠️가설 — 브라우저 실측 필요 · [4] 에 넘김)**
- 켬 · 크롬 1탭 로그인 → 탭 닫기 → 새 창으로 `{id}.hitpan.kr` → 로그인 → 기대 409. 대조군: 같은 절차에서 로그아웃 후 닫기 → 로그인 성공.
- 추가 갈래: 로그인된 탭에서 주소창에 URL 을 새 탭으로 입력(sessionStorage 는 탭별) → 로그인 → 409.

**봉합 방향(결재 대상 — 코드 수정은 [3] 몫, 여기선 선택지만)**
- (가) 토큰을 localStorage 로(XSS 노출창 확대 — `storage.js:1-3` 이 일부러 옮긴 이유와 충돌 · 보안 결재 필요)
- (나) 「같은 브라우저 재진입」을 서버가 알아볼 표식(브라우저별 난수를 localStorage 에 두고 세션 행에 기록 → 일치하면 자기 세션 인계). 9/25 「기기 식별 쓰지 않는다」와 경계 — 기기가 아니라 **브라우저 프로필 표식**임을 결재로 가를 것
- (다) K-4 (다) 게시를 쿨타임(1-b) 또는 해제 경로와 **같이** 내보냄
- ⛔ 이대로 게시하면 사장님 PC 확인(작지 §5 마지막 줄)에서 「브라우저 닫았다 열기」 한 번에 사장님 계정이 하루 잠길 수 있다. 되돌림은 비상 끔 `enforce_one_pc_login = 0`(사장님 PC DB — #39 상 사장님 손).

## PI-2 🟠 P1 — 갱신 경주: 회전 성공 뒤 두 번째 갱신이 저장소를 지운다

**무엇이**
- 서버 회전은 옛 토큰 **DELETE**(`AuthService.cs:794-800`) — 같은 옛 토큰 두 번째 사용 = 401 「이미 사용된 토큰」.
- 화면 갱신 호출처 둘: ① `HitPanApiAuthHandler.TryRefreshAsync`(`:295~` · `RefreshLock` + 이중확인) ② `HitPanAuthStateProvider.cs:22-29` → `AuthTokenRefresher.TryRefreshAsync`(`:8-32`) — **락도 이중확인도 없다.** 실패 시 둘 다 토큰 3개 삭제(`HitPanApiAuthHandler.cs:91-93` · `HitPanAuthStateProvider.cs:27-29`). 게다가 **비 2xx 전부**(502 터널·500)를 실패로 본다(`:324-328` · `AuthTokenRefresher.cs:21-24`).

**왜 잠기나**
- 만료 토큰으로 화면을 열 때 `GetAuthenticationStateAsync`(①) 와 첫 API 401 핸들러(②)가 같은 refresh 토큰으로 동시에 갱신 → 하나 성공(세션 `expires_at` +8h 연장 `:863-867`) · 하나 401 → 진 쪽이 **이긴 쪽의 새 토큰까지** 지움 → 로그인 → 방금 연장된 자기 세션에 409 → 8h.
- 같은 경로: 갱신 서버 성공 후 응답 유실(터널) → 화면은 옛 토큰 보유 → 다음 시도 401 → 삭제 → 409.
- 1.3.46 까지는 결과가 「다시 로그인」 한 번이었다. **K-4 (다)에서 8h 잠김으로 승격된다.**

**재현 (⚠️가설)** — 만료 access 를 저장소에 둔 채 새로고침, 네트워크 탭에서 `api/auth/refresh` 가 2회 나가는지 · 두 번째가 401 인지. 대조군: 1회만 나가면 PI-2 는 이 경로로는 안 선다.

## PI-3 🟠 P1 — 로그인 경주: 판정과 기록 사이에 잠금이 없다

**무엇이** — `AuthService.cs:144` 판정(SELECT) → `:146-148` `SaveChangesAsync`(EF 왕복 · 창을 넓힌다) → `:178` 세션 INSERT. 행 잠금·유일 제약·트랜잭션 없음. 설계 §4 는 「로그인 트랜잭션 새로 씌우지 않는다」.
- ⓐ **우회**: 같은 계정 PC 두 대가 수십 ms 안에 로그인 → 둘 다 「살아 있는 PC 없음」 → **두 PC 가 선다.** 이후 둘 다 갱신 가드 ③(자기 생존 → 연장)을 통과해 무기한 공존. 스크립트로 의도 재현 가능. 설계 §12 는 「되살림 × 새 로그인」 경주만 적었고 **로그인 × 로그인** 은 없다.
- ⓑ **잠김**: `Login.razor:308-323` — 재진입 막음(`if (_busy) return;`)이 없고 `_busy = true` 가 `await _form.ValidateAsync()` **뒤** ⇒ 더블클릭/Enter+클릭이 두 요청을 보낼 수 있다. 둘 다 통과하면 화면은 마지막 응답 토큰만 갖고 다른 한 세션은 **고아**(토큰 없이 8h 생존). 이후 그 PC 에서 로그아웃 → 같은 날 재로그인 → 고아에 막혀 409.

**재현 (⚠️가설)** — 켬 · 같은 계정으로 `api/auth/login` 을 병렬 2회(PC UA) → `user_sessions` PC 행 2개 · 둘 다 200 이면 ⓐ 성립. 대조군: 순차 2회 → 두 번째 409.
**봉합 방향(선택지)** — 판정 전 `SELECT ... FROM users WHERE user_id = @Id FOR UPDATE` 로 계정 단위 직렬화 + 같은 트랜잭션에서 INSERT · 또는 계정별 앱 잠금(단일 프로세스). 화면 재진입 막음 1줄.

## PI-4 🟠 P1 — 로그아웃 실패가 성공으로 끝난다

- 서버 `AuthController.cs:375-405` — 세션/토큰 정리 예외를 `LogWarning` 후 **200 「로그아웃 완료」**.
- 화면 `Web/Services/AuthService.cs:221-225` — 응답 상태 **무시**, 네트워크 예외는 빈 `catch`(#15 위반 소지 — 별건 기록), 무조건 저장소 삭제.
- ⇒ DB 순간 오류·터널 끊김 한 번이면 세션 행이 살아남고 사용자는 로그아웃된 줄 안다 → 같은 날 재로그인(점심 뒤 등) → **자기 세션에 409** → 로그인 후 8h 까지.

- 재현(⚠️가설): `BEFORE DELETE ON user_sessions` 트리거로 실패 유도 → 로그아웃 200 → 재로그인 409.

## PI-5 🟠 P1 — F-4 보상이 원인과 같이 죽는다 / 응답 유실은 못 덮는다

- 보상 `CompensateNewSessionRowAsync`(`AuthService.cs:387-400`)는 실패한 쓰기와 **같은 `db` 연결**로 DELETE 한다. refresh INSERT 실패 원인이 연결 끊김·DB 재시작(업데이트 중 서비스 재기동 · #28)이면 보상도 실패 → 경고 로그만 → 잔여 행 8h. G-B24 는 **트리거**(연결은 멀쩡) 로만 재서 이 갈래를 못 본다.
- 서버는 끝까지 성공했는데 **응답이 화면에 못 닿는** 경우(cloudflared 재연결 · 브라우저 탭 닫힘 · #27 17시나리오) → 화면 「서버에 연결할 수 없습니다」(`Web/Services/AuthService.cs:168-175`) → 재시도 → 자기 세션 409. 서버 쪽 보상으로는 **원리적으로 못 막는다**(PI-1 과 같은 뿌리: 「같은 사용자의 재진입」을 서버가 못 알아본다).
- 작지 §6 「G-B24 가 유일한 방어」 는 과대 — G-B24 는 트리거 갈래 하나만 막는다.

## PI-6 🟡 P2 — 게이트가 회전된 토큰을 안 잰다

- 불변식 「`refresh_tokens.session_id` = 그 JWT 의 `sid`」(설계 §2)는 **로그인 INSERT 와 갱신 회전 INSERT(`:813-822`) 두 자리**에서 지켜져야 한다. G-B18(로그아웃)·G-B20(죽은 PC 정리)은 로그인 직후 토큰만 쓴다.
- 회전 INSERT 에서 `session_id` 를 빠뜨려도 두 게이트는 초록 → 실물에선 **한 번 갱신한 PC** 의 로그아웃이 refresh 를 못 지우고(0행), 죽은 PC 정리도 0행. 생존 확인이 명시 `0` 인 고객사에선 로그아웃된 토큰이 세션 행 없이 되살아나 **세지 않는 PC** 가 된다(가드 ② `validity == 0` 통과 → `UPDATE ... WHERE session_id`(0행) → `sid` 실은 토큰 발급).
- 요청: G-B18·G-B20 준비에 「갱신 1회 후 회전된 토큰으로」 한 갈래 추가 + 대조군(회전 INSERT 의 `session_id` 빼기 → FAIL).

## PI-7 🟡 P2 — `sid` 없는 refresh + UA 공백 = 모바일로 새 세션

- 갱신의 새 세션 갈래(`AuthService.cs:676-680`)는 `ResolveDeviceType(null, request.UserAgent)` — UA 공백·Mac UA 면 판정 포기 → 신고값 없음 → `mobile` → 판정 건너뜀 → PC 가 **모바일 세션**으로 선다. `sid` 없는 refresh 는 DB-130 이전 발급분(7일)·세션 기록 실패분. 9/27 병렬이슈(UA 한 칸 회피)의 **갱신판**이며 설계 §3-1 정리 SQL 도 `session_id NULL` 을 못 잡는다. 브라우저 실사용 경로는 UA 를 자동으로 붙이므로 의도적 우회만 해당.

## PI-8 🟡 P2 — 서버 시계 역보정

- `expires_at` 은 앱 시계(`DateTime.UtcNow.Add(8h)` `:328`·`:867`), 판정은 DB `UTC_TIMESTAMP(6)`. 같은 PC 라 평소 어긋남 0. 단 메인 PC 시계가 앞서 있다가 시간 동기화로 **뒤로** 맞춰지면 그 차이만큼 잠김이 8h 를 넘는다(예: +1일 틀어진 BIOS → 32h). 탈출구가 없으므로 상한이 시계에 달린다. 권고: `expires_at` 도 DB 시계(`UTC_TIMESTAMP(6) + INTERVAL 8 HOUR`)로 기록해 기준을 하나로.

## PI-9 🟡 P2 — 409 기록 무제한

- 절B-3 은 맞는 비밀번호로 409 가 날 때마다 1행. PI-1 로 잠긴 사용자가 여러 번 시도하면 행이 쌓여 「화면 경고」(9/25 §2)가 **본인 실수로 가득 찬다.** 같은 사용자·짧은 간격은 묶는 규칙 여부를 화면 트랙 설계에서 결정.

### 🟠 R-1 P1 — 서버 고장이 「400」으로 나가고, 화면은 400 을 「로그인 끝」으로 읽어 지운다
- 사실: `RefreshGate.Decide` 는 4xx(408·429 제외)를 전부 `Clear` 로 본다. 그런데 `GlobalExceptionMiddleware.cs` 는 **`InvalidOperationException` → 400** 으로 내보낸다. `AuthController.Refresh` 는 `UnauthorizedAccessException` 만 잡는다.
- 사실: 갱신 경로 첫 줄 `TenantConfigReader.GetRequired("JWT_SECRET")` 이 설정을 못 읽으면 `InvalidOperationException` 을 던진다(`Application/Common/TenantConfigReader.cs:32` · `Infrastructure/Configuration/TenantConfigReader.cs:35`). MySqlConnector 의 연결 상태 예외(열린 DataReader·닫힌 연결 등)도 같은 형이다.
- 귀결: 서버가 **판정을 안 했는데** 화면은 저장소 3칸을 지운다(`AuthTokenRefresher.cs:88-92`) → 서버 세션 행은 살아 있다 → 다시 로그인하면 **자기 PC 409**(최대 8h). 설계 전제 「4xx = 서버가 판정했다」가 이 서버에서는 거짓이다.
- ⚠️가설: 실제로 갱신 중 `InvalidOperationException` 이 얼마나 나는지는 안 쟀다(모양은 사실 · 빈도는 미측정).
- 확인 방법: W-1 표(상태값 12가지)에 400 이 `Clear` 로 들어가 있으면 게이트가 이 결함을 **정답으로 굳히고 있다** — 판정은 「서버가 명시적으로 401 을 줬을 때만 지운다」 쪽이 맞는지 [2] 결재 사항.

### 🟠 R-2 조건부 P1 — `navigator.locks` 가 없는 곳에서는 PI-2 경주가 그대로다
- 사실(웹 규격): `navigator.locks` 는 **보안 출처(https·localhost)에서만** 있다. `http://사내IP:5234`·`http://PC이름:5234` 로 열면 없다 → `hitpanLock_acquire` 가 0 → 탭 사이 잠금 없이 진행. 15초 기다림 초과(`RefreshTabLock.WaitMs`) 때도 같다.
- 사실: 토큰을 탭끼리 나눠 쓰므로 access 만료는 **모든 탭에서 같은 순간** 온다 ⇒ 동시 갱신이 예외가 아니라 기본 모양이다.

### 🟡 R-4 P2 — 1회 이전이 로그아웃한 로그인을 되살린다(업데이트 과도기)
- 사실: `remove` 는 **그 탭의** sessionStorage 만 지운다(`storage.js:41-42`). `get` 은 localStorage 가 비었으면 sessionStorage 값을 localStorage 로 옮긴다(`storage.js:26-37`). `hitpanStorage_inheritFromOpener` 도 부모 창 sessionStorage 를 복사한다.
- 경로: 공용 PC — 업데이트 전부터 열린 탭 X(sessionStorage = 직원 A) · 새 탭에서 직원 B 로그인 → B 로그아웃(localStorage 비움) → 탭 X 가 새 `storage.js` 로 다시 읽으면 **A 토큰을 localStorage 로 끌어와 모든 탭이 A 로 열린다.** 로그아웃 누른 B 는 모른다.

### 🟡 R-5 P2 — 「유지(Keep)」에 끝이 없다
- 사실: 5xx·408·429·빈 2xx·예외는 전부 Keep. 상한·만료·물러서기(backoff)가 없다. `HitPanAuthStateProvider` 도 Keep 이면 **만료된 access 로 로그인 상태를 돌려준다.**
- 귀결: 폭주는 아니다(요청 1건당 갱신 1회 · 탭 안 직렬 · 지수 증가 없음). 그러나 갱신 경로만 계속 500 이면(예: 갱신 SQL 이 기다리는 마이그 누락 — M-23 류) 화면은 **영영 로그인 화면으로 안 가고** 빈 목록 + 30초마다 「서버에 연결할 수 없습니다」. 로그인 경로는 멀쩡한데 사용자는 로그아웃해야 한다는 것을 모른다(「처음 보는 사람이 혼자 쓸 수 있냐」 실패).

### 🟡 R-6 P2 — `GET_LOCK` 이 안 풀리는 길
- ✅ 닫힌 것: `await using` 이 예외·취소에도 `RELEASE_LOCK` 을 부른다 · 갱신 트랜잭션은 `using (tx)` 로 잠금 해제 **전에** 끝나 「트랜잭션 불일치」 예외 자리 없음 · 연결이 죽으면 MariaDB 세션과 함께 잠금 소멸(자가 해소) · 잠금은 **비번 확인 뒤**라 비번 모르는 사람이 남의 로그인을 잠금으로 막을 수 없다 · 바쁨(0)이면 로그인 401「잠시 후」 / 새세션 갱신 `TimeoutException` → 500 → 화면 Keep(지우지 않음).
- 남은 것 ①: `RELEASE_LOCK` 이 예외로 실패했는데 연결은 살아 풀로 돌아가면 잠금이 풀 연결에 붙은 채 남는다 → 그 계정 로그인이 매번 5초 뒤 「잠시 후」. 해소는 MySqlConnector 의 재사용 시 초기화 또는 유휴 정리에 달렸다 — ⚠️가설(MariaDB 의 `COM_RESET_CONNECTION` 이 이름 잠금을 푸는지 · 유휴 정리 시간 미확인). 또 같은 풀 연결이 그 계정 잠금을 **다시** 잡으면 재진입 카운트가 2 가 되어 해제 1회로 안 풀린다(MariaDB 10.0.2+) ⚠️. 이 트리거를 만드는 코드 경로는 못 찾았다.
