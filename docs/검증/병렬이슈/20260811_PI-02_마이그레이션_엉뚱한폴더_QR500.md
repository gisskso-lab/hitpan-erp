## 무엇이 났나

사장님이 [모바일기기 등록] 을 누르니 **"QR생성실패 500"**.

## 진범

**PM 이 마이그레이션을 아무도 실행하지 않는 폴더에 두었다.**

| | 경로 | 실행 주체 |
|---|---|---|
| PM 이 둔 곳 | `installer/migrations/` | **없음** — 파일만 존재 |
| 진짜 진실원 | `src/HitPan.API/Migrations/SQL/DB-NN_*.sql` | `MigrationRunner` |

`device_register_tokens` 테이블이 test1 DB 에 생성되지 않았고, 토큰을 INSERT 하려다 500.

## 왜 CI 가 못 잡았나

- **빌드 0/0** — SQL 파일 위치는 컴파일과 무관하다
- **DDL Smoke pass** — `hitpan_db_clean.sql`(신규설치 진실원)에는 제대로 넣었기 때문에 통과했다.
  **신규 설치는 정상이고, 기존 DB 업데이트만 깨진 상태**였다
- ⇒ 이 결함은 **이미 돌고 있는 DB 에 업데이트를 얹어야만** 드러난다. 사장님 실측이 잡았다

## 계통 — 8/10 아침 "4차 사고" 와 같은 자리

메모리에 기록된 패턴: *"고쳤다 ≠ 고객에게 갔다 — 끊기는 자리만 옮겨간다."*
이번은 그 변주다: **"SQL 을 썼다 ≠ 그 SQL 이 실행된다."**

코드는 정상이었고 파일도 존재했다. 끊긴 것은 **그 파일을 읽는 손**이었다.

**검증한 것**

  (7월에 "마이그 SQL 이 publish 에 0개" 사고가 있었다. csproj `DB-*.sql` 복사 지시가 살아 있음도 함께 확인)

## 🔴 다음 게시의 필수 조건

**`requiresMigration: true` 로 게시해야 한다.**

`false` 로 나가면 워치독 교차검증 게이트가 *"SQL 은 있는데 플래그가 false"* 로 판정해
**업데이트를 강제 중단**한다(`UpdateOrchestrator` ①번 게이트). 1.2.63 은 `false` 로 나갔다.

## 재발 방지

새 테이블·컬럼을 넣을 때 **세 곳을 모두** 확인한다:
1. `hitpan_db_clean.sql` — 신규 설치 (헌법 #36)
2. `src/HitPan.API/Migrations/SQL/DB-NN_*.sql` — **기존 DB 업데이트**
3. 게시 시 `requiresMigration: true`

①만 하면 신규 고객은 되고 **기존 고객만 깨진다.** CI 는 이걸 못 잡는다.
