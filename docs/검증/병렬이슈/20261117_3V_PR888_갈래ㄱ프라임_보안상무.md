## 4. `jq -R` 과 grep 공백 판정 (§7 ④)

| 입력 | grep(C 지역 · `-cv '^[[:space:]]*$'`) | jq(`-R` · 6종 공백 정규식 → `fromjson`) | 닫히는 쪽 |
|---|---|---|---|
| CR 끝 줄 `{…}\r` | 공백 아님 1 | CR 은 JSON 공백 → 객체(읽기 판정 · jq 미실행) | 정상 해석 |
| CR · FF · VT 만 있는 줄 | 공백(실측 0) | 정규식 공백 | 같음 |
| BOM 만 / BOM 앞머리 줄 | 공백 아님(실측 1) | 해석 실패 → false | **검사 오류**(안전) |
| 잘못된 UTF-8 | 바이트 그대로 셈 | U+FFFD 로 바꿔 해석 · 객체면 이름은 `기타` | 안전 |
| 매우 긴 줄 | 셈 | 선형 정규식 · 해석 | 안전(메모리 한도뿐) |
| U+00A0 · U+3000 같은 비 ASCII 공백만 | 공백 아님 | 정규식 불일치 → 해석 실패 | **검사 오류**(안전) |
| **NUL(+공백)만 있는 줄** | **공백(실측 0)** — 바이너리 판정으로 NUL 을 줄 끝처럼 처리 | 공백 아님 → 해석 실패 → false | ⚠️ **어긋남이 상쇄된다**(P2-1) |
| `{}` + NUL + 글자 한 줄 | 2줄로 셈(실측) | 1줄 · 해석 실패 | 검사 오류(안전) |

**P2-1 상세** — NUL·공백만인 줄은 grep 몫 0 · objects 몫 0 이라 `bad` 에 안 잡힌다.
- 엔진 종료 0 + 결과가 그런 줄뿐 → `nonempty=0` → 「깨끗」. 바닥 코드(`^{` 개수 0)도 「깨끗」 이었으므로 **넓어진 길은 아니다.** 그런 줄은 탐지 결과를 담을 수 없다.
- 엔진 종료 183 + 객체 + 그런 줄 → 엄격 해석은 통과하지만, 이어지는 이름 추출(파일 통째 해석)이 NUL 에서 실패 → 검사 오류. 어느 쪽이든 빨강.
- 바이너리 처리는 GNU grep 문서상 「그럴 수 있다(may)」 이고 이 PC 는 3.0 — **러너 grep 판에서는 미측정.**
- 권고(막지 않음): ⓐ 개발명세서 §6 ④ 문장을 「NUL 은 grep 이 공백 쪽으로 센다 · 깨끗 길은 바닥과 같음」 으로 고친다, 또는 ⓑ `grep -a` 로 텍스트 강제 + 자체시험 S10f(종료 0 · NUL 한 줄 → 검사 오류 기대) 추가. ⓑ 는 작업지시서 §4 밖이라 PM 판단.

## 6. 「깨끗」 판정이 넓어진 길 (추가 ⑥) — 0

| 실패 상황 | 동작 |

| grep 자체 오류(파일 못 읽음) | 표준 출력 빈 값 → 숫자 아님 → 검사 오류 |
