## 무엇이
- 봉합1 의 `Unconfirmed`(`RollbackWatch.cs:228`)는 「[다시 확인] 때 판 = from · 이번 결과 없음」이면 무조건 덮개를 걷는다. **상태 응답의 `Fetch.Stage` 가 `checking`·`downloading`·`verifying`(이번 시도 · 판 to · 신선)인지 보지 않는다.**
- 덮개가 걷히면 화면은 `OnWatchClosedAsync` → `LoadAsync` + 「진행 상황을 더 확인하지 못했습니다…」(`UpdateStatusLost`). `LoadAsync` 는 `Fetch` 를 안 본다(`LocalRollbackPage.razor` 의 `Fetch` 사용은 `FollowFetchAsync` 안뿐) ⇒ 받기 진행을 따라가는 것이 **아무도 없다**.
- 서버는 계속 받는다 → 다 받으면 넘김 → 교체 → 히트판이 멈췄다 뜬다. 이때 브라우저에는 덮개가 없다 = 10/5 사장님 실측 1·2(완료 안내 없음 · 「페이지를 찾을 수 없습니다」 위험)와 같은 모양.

## 이 상태에 들어가는 길
1. 세 번째 길 [예] → 화면 `FollowFetchAsync` 가 받는 중 → 터널 깜빡임(502 · 봉합 뒤 `IsHitpanDown` 으로 넓어짐) 또는 「받기 진행 사라짐」 → `BeginWatch()`(덮개 시작).
2. 받기가 10분을 넘긴다(느린 회선 · 큰 꾸러미). 종전 화면 폴링은 30분(`PollLimit`)까지 따라갔다 — 덮개 상한은 10분.
3. 「예상보다 오래 걸립니다」 → [다시 확인] → 판 = from · `Last` 는 이번 것 아님 → `Unconfirmed` → 걷힘.
- 문구도 사실과 다르다: 서버는 「받는 중」이라고 답하고 있는데 「진행 상황을 더 확인하지 못했습니다」.

## 재현 방법(순수 루프 · 운영 조작 0)
- 가짜 `getVersion` = 늘 `(200, from)`, 가짜 `getStatus` = `Ok` + `Last=null` + `Fetch={Stage="downloading", To=to, AtUtc=시작+1분}` 로 `RunAsync` → `Stalled`(10분) → `CheckOnceAsync` → **`Unconfirmed`**(코드 판독 `:221-228` · `IsThisFetchRefused` 만 보고 진행 단계는 안 본다). 게이트에 이 갈래가 없다(G-W12 는 `downloading` 이 「거절 아님」만 잰다).

## 봉합(권고 — 결정은 설계·PM)
- [다시 확인] 때 이번 받기가 진행 단계(신선 · 판 to)면 `Unconfirmed` 가 아니라 `Waiting`(새 10분) — 이 경우는 실제로 진행 중이므로 Q-1 결재 문구 「계속 되돌리기를 진행하고 있습니다」가 사실이다. 끝없는 순환은 받기 자체의 끝(넘김·거절·사라짐)이 막는다.
- 대조군: 위 재현 대본으로 게이트 1개(진행 중 → Waiting · 진행 없음 → Unconfirmed 둘 다).
