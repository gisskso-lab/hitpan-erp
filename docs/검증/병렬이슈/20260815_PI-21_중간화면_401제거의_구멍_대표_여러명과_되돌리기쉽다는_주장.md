## 1. 검증 결과 요약 — 무엇은 괜찮고 무엇이 구멍인가

| 프롬프트가 물은 것 | 판정 |
|---|---|
| 미승인 기기가 SignalR 로 **남의 알림**을 받는가 | ✅ **안 받는다** — 구조가 옳다 (아래 §2) |
| 우회 목록으로 **업무 데이터가 새는가** | ⚠️ **일부 샌다** (§3) |
| **대표가 여러 명**이면 어떻게 되나 | 🔴 **정해지지 않았다** (§4) |
| "통과만 시키면 지금과 똑같다" 가 사실인가 | 🔴 **사실이 아니다** (§5) |

## 2. ✅ SignalR 은 안전하다 — 지적할 것이 없다

`src/HitPan.API/Hubs/NotificationHub.cs:55-76`
```csharp
public override async Task OnConnectedAsync()
{
    var tenantId = Context.User?.FindFirstValue("tenant_id");
    var employeeId = Context.User?.FindFirstValue("employee_id");
    if (string.IsNullOrWhiteSpace(tenantId) || string.IsNullOrWhiteSpace(employeeId))
    { ... 그룹 없이 연결 ... return; }
    await Groups.AddToGroupAsync(Context.ConnectionId, GroupFor(tenantId, employeeId));
}
```
- 그룹 배정은 **전적으로 서버**가 한다. 클라이언트가 그룹을 못 고른다.
- 그룹 키에 **테넌트가 포함**된다(`n:{tenantId}:{employeeId}`) — 헌법 #2 정합.
- `employee_id` 가 없으면 **아무 그룹에도 안 들어간다** ⇒ 남의 알림을 받을 수 없다.

⇒ §14-4 의 *"서버가 JWT 클레임으로 그룹 배정 (옳은 설계)"* 는 **실측으로 확인된다.**
미승인 기기가 붙어도 **자기 알림만** 받는다. **이 자리는 문제 없다.**

⚠️ 단 하나 — `employee_id` 클레임이 없는 계정은 **승인 알림을 못 받는다**(`:60-68` 이 조용히 통과).
대표 계정에 `employee_id` 가 안 실리면 **승인 요청이 아무에게도 안 간다.**
과거에 같은 종류의 사고가 있었다 — `AuthController` 주석: *"HR employee_id 부분봉합 회귀"*.
⇒ **2차 착수 전 대표 계정의 `employee_id` 실측 필요.**

## 3. ⚠️ 우회 목록 — 새는 경로가 있다

`DeviceAuthMiddleware.cs:34-42`
```csharp
"/api/auth", "/api/devices", "/api/appversion", "/api/watchdog", "/health", "/swagger"
```

§14-5 는 *"업무 데이터는 그대로 잠겨 있다"* 고 단언한다. **대체로 맞다.** 다만 둘이 걸린다.

1. 🔴 **`/api/auth` 는 접두 일치(`StartsWith`)** 다. `/api/auth` 로 **시작하는 모든 경로**가 열린다.
   `AuthController` 에 내 정보·사원 정보성 응답이 붙으면 **자동으로 열린 문이 된다.**
   지금 당장의 유출은 확인되지 않았으나, **"앞으로 추가되는 것이 자동 통과" 라는 구조 자체가 위험**하다.
2. ⚠️ **`/swagger`** — 운영에서 열려 있으면 **API 전체 구조가 노출**된다.
   미승인 기기가 토큰을 갖게 되는 §14 이후에는 의미가 달라진다.

⇒ **1차·2차 어느 것도 여기를 안 건드린다.** 401 을 걷어내기 **전에** 우회 목록을 재점검해야 한다.

## 4. 🔴 대표가 여러 명이면 정해진 답이 없다

§14-4 는 이렇게만 적었다.
> 대표 `employee_id` 조회 — `employees WHERE tenant_id=@t AND role='tenant_admin'` (현재 코드에 없음)

**`LIMIT 1` 인지 전원인지 안 적혀 있다.** 그리고 `tenant_admin` 은 **여러 행일 수 있다.**

**근거** — `role` 컬럼에 유일성 제약이 없고, 값이 문자열로 흩어져 들어간다.
`CompanyBootstrapProvisioner.cs:255` 가 `'tenant_admin'` 으로 INSERT 하고,
`UserConfiguration.cs:60-70` 에는 **snake_case 로 저장된 기존 행을 자가치유**하는 코드까지 있다
(*"언더스코어 어휘('tenant_admin' 등 snake_case로 저장된 기존 행) 자가치유"*).
⇒ **표기가 갈렸던 이력이 있다.** 조회가 정확히 몇 행을 집을지 **아무도 모른다.**

| 구현자의 선택 | 결과 |
|---|---|
| `LIMIT 1` | 🔴 **그 한 명이 자리에 없으면 승인이 영원히 안 난다.** §18 은 *"대표 부재 시 대기 처리는 안 함"* 으로 닫았는데, 그 판정의 전제가 "대표는 한 명" 이었다 |
| 전원 발송 | 여러 명이 **동시에 승인**을 누른다 ⇒ 슬롯 중복 소진(§16 G-16 과 충돌) |
| 0 행 | 🔴 **조용히 아무 일도 안 일어난다.** 직원은 영원히 대기 화면 |

🔴 **0 행 케이스가 가장 나쁘다.** 알림 발송 실패는 대개 예외를 안 내므로 **아무도 모른다.**

**고칠 방법**: ① 전원 발송 + **승인은 선착순 1회만 유효**(멱등 — `ApproveAsync:395` 가 이미 `if (curStatus == "approved") return null;` 로 멱등이다. 이 성질을 활용)
② **0 행이면 경고 로그 + 화면에 "관리자에게 직접 문의" 안내**. 조용히 실패하지 않게.

## 5. 🔴 "되돌리기 쉽다" 는 주장은 사실이 아니다

§14-6 이 이렇게 적었다.
> 🔴 **되돌리기 쉽다** — 이 화면이 통과만 시키면 지금과 똑같이 동작한다.
> 문제가 나면 화면에서 판단을 끄면 된다. **서비스 로직을 헤집지 않는다.**

**틀렸다.** §14-5 가 **`AuthController.cs:101-105` 의 401 을 걷어낸다**고 했기 때문이다.

```csharp
if (!allowed)
{
    return Unauthorized(new { message = reason });
}
```

이 줄이 사라지면 **화면을 통과 모드로 두는 순간, 한도초과·폐기 기기가 토큰을 받고 그대로 업무 화면까지 간다.**
🔴 **"통과만 시키면 지금과 똑같다" 가 아니라 "통과만 시키면 기기 제한이 통째로 없어진다" 이다.**

남는 방어는 `DeviceAuthMiddleware` 뿐인데, 그것은
- `DeviceApproval:Enabled` 가 **false 면 통째로 건너뛴다**(`:55, :60-64`) — **현재 기본값이 false 다**
- 검사가 실패하면 **통과시킨다**(`:126-131`, 의도된 설계)

⇒ **401 을 걷어내고 화면을 통과 모드로 두면, 기본 설정에서 기기 제한이 0 이 된다.**
이것이 §16 이 말한 **"방향 ② 요금 누수"** 의 가장 큰 구멍인데, **설계가 이것을 "안전장치" 로 적었다.**

**고칠 방법**: 롤백은 "화면을 통과 모드로" 가 아니라 **"401 을 되돌리는 것"** 으로 명시한다.
그리고 401 제거와 중간 화면 도입은 **반드시 같은 배포에** 나가야 한다(따로 나가면 그 사이가 무방비).
