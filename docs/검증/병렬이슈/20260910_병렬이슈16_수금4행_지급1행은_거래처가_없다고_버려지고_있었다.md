# [3-V] 병렬이슈 16 — 수금 4행·지급 1행은 **거래처가 없다고 버려지고** 있었다 (미수·미지급 DIFF 의 진짜 원인)

| 항목 | 내용 |
|---|---|
| 발견 | [3-V] 동시 병렬검증 (PM 브라운킴) · 2026-09-10 · 작22 1차 실측 로그 판독 중 |
| 대상 | `MdbMigrationService.cs` `MigrateCollectionsAsync`(수금) · `MigratePaymentsAsync`(지급) — **5월부터 있던 자리**, 작22 회귀 아님 |
| 등급 | **P1** — 사장님 오더 1(*"레거시에서 뽑는 값이랑 같은 값"*)에 정면으로 걸린다 |
| 판정 | ✅ **원인 확정 + 봉합** (PM 전결 — 아래 §4 근거) |

## 1. 증상

작21 부터 대사표에 남아 있던 DIFF 3건이 서로 같은 뿌리였다.

| 대사 항목 | 레거시 | 히트판 | 차이 |
|---|---:|---:|---:|
| 수금 | 109,822건 12,097,929,700 | 109,818건 12,096,479,700 | **−4건 −1,450,000** |
| 미수금 | 5,565,664 | 7,048,718.20 | **+1,483,054.20** |
| 미지급금 | −82,606,946 (2,228건) | −82,556,945 (2,227건) | **+50,001** |

9/9 선행검증서 §2-6 은 이 셋을 *"수금 4행·지급 1행 미이관"* 으로만 적고 **원인은 미규명**으로 남겼다.

## 2. 원인 — 코드가 그렇게 짜여 있었다

1차 실측 로그가 스스로 답을 적고 있었다:

```
[MDB마이그레이션] DOCF5 수금 후보 109818행 — 제외: … 거래처 미매핑=4
[MDB마이그레이션] DOCF5 지급 후보 2227행 — 제외: 계열 불일치=0 거래처 미매핑=1
```

```csharp
var buyCode = GetInt(row, "S_BUY");
if (!partnerMap.TryGetValue(buyCode, out var partnerId))
{
    skipPartner++;
    continue;          // ← 거래처가 DOCF8 에 없으면 그 수금·지급을 버린다
}
```

**중복 키 때문이 아니다** — 이것부터 반증했다. MDB 직독(`Mode=Read`): 수금 계열 109,822행의 `(S_BUY, S_YMD, S_SUN, S_GU)` DISTINCT = **109,822**, 중복 그룹 **0**. 지급도 중복 0. 멱등 키 충돌로 IGNORE 된 게 아니라 **INSERT 후보에서부터 빠져 있었다.**

## 3. 왜 이게 남아 있었나 — 같은 사고를 한쪽만 고쳤다

거래처 미등록 라인을 **버리지 않고 폴백 거래처(`LEGACY_UNKNOWN_PTNR`, 5/16 신설)로 잇는다**는 규칙은 이미 있다. 작21 A3(P0-C)가 명세서 경로의 `skipPartner++; continue;` 를 걷어내고 폴백으로 바꿨다(`:4634`). 전결1 D1 도 품목 쪽에 같은 규칙을 세웠다 — *"버리지 않는다."*

그런데 **수금·지급 경로만 그 전 상태로 남았다.** 작21 이 P0-E(수금/지급 계열 분리)를 고치면서 이 두 메서드를 직접 손댔는데도, 바로 위 몇 줄에 있던 같은 모양의 `continue` 는 지나쳤다.

> 🔴 이번에도 **"한쪽 사고는 반대쪽에 같은 코드가 있는지 그 자리에서 확인"** 이 안 된 것이다([[project_sales_chain_dup_guard_20260827]] 와 같은 계통). 고친 경로 옆에 안 고친 경로가 있었다.

## 4. 봉합 (PM 전결 근거)

두 자리를 명세서 경로와 **같은 모양**으로 맞췄다 — 새 정책이 아니라 **이미 결재된 규칙의 누락분 적용**이다(D1 · 작21 A3). 새 표·새 함수 0, 있는 `EnsureLegacyFallbackPartnerAsync` 를 부른다(헌법 #1 추가만).

```csharp
if (!partnerMap.TryGetValue(buyCode, out var partnerId))
{
    fallbackPartnerIdLazy ??= await EnsureLegacyFallbackPartnerAsync(tenantId, now, tx, ct);
    partnerId = fallbackPartnerIdLazy;
    fallbackPartner++;      // 로그 문구도 "거래처 미매핑" → "거래처 폴백" 으로
}
```

작지서 §2 는 이 건을 *"[3-V] 가 캐되 봉합은 원인 확정 후"* 로 적었다 — **원인이 확정됐으므로 그 조건이 충족된다.** 사장님 결재가 필요한 정책 판단(Q1 계열)이 아니라, 결재된 규칙이 두 경로에 안 붙어 있던 결함이다.

## 5. 재는 방법 — 게이트는 대사표 그 자체

이 자리는 DB·MDB 를 둘 다 타는 경로라 **글자 검사로는 아무것도 증명되지 않는다**(가짜 게이트 누적 24번). 재는 자는 대사표다:

| 무엇 | 봉합 전 | 봉합 후 기대 |
|---|---:|---:|
| 대사 ⑦ 수금 차이 | −1,450,000 | **0** |
| `payments` 행수 | 2,227 | **2,228** |
| 대사 ⑧ 미수 차이 | +1,483,054.20 | **+33,054.20** (= DOCFE↔DOCFB 레거시 내부 불일치 33,059.20 − 부가세 반올림 5) |
| 대사 ⑨ 미지급 차이 | +50,001 | **+1** (반올림) |
| 폴백 거래처 몫 | — | 수금 4 · 지급 1 (로그 "거래처 폴백=") |

⇒ **미수·미지급의 남는 차이가 "설명되는 잔차" 로 내려앉으면 봉합이 맞은 것이다.** 실측 결과는 작업리뷰서에 붙인다.

## 6. 남는 것

- 폴백 거래처(`LEGACY_UNKNOWN_PTNR`)에 수금 4건·지급 1건이 붙는다. 명세서 565건(판매 356 · 매입 209)과 같은 그릇이다 — **사장님 정리 대상**(D1 결재 그대로, 화면에서 실제 거래처로 옮기실 수 있다).
- 남는 미수 +33,054.20 는 **레거시 내부 불일치**다(헤더표 DOCFE 에 없는 DOCFB 헤더그룹 353개). 히트판이 라인표를 100% 옮긴 결과이므로 고칠 것이 아니라 기록할 것이다(작21 리뷰서 §3 (d-3)).
