## 2. 이슈

### P2-1 · E7 일괄 저장은 예외를 던지지 않는다 — R-n 이 `Assert.Throws` 면 빨강/엉뚱한 초록
- 파일: `src/HitPan.API/Services/DeliveryBatchService.cs` 바닥 :144~160 `catch (Exception ex) { tx.Rollback(); return requests.Select(_ => new BatchSaveResult { Success = false, ErrorMessage = ex.Message }) }`
- 근거: 가드 예외는 삼켜져 **건별 실패 목록**으로 돌아옴. §5-4 R-n 「`InvalidOperationException` · 문구 같음」 꼴 그대로 쓰면 E7 은 항상 빨강이거나, 우회로 짠 단언이 약해짐.
- 개발에 돌려줄 한 줄: **E7 R-n 은 「결과 전부 `Success=false` + `ErrorMessage == ItemTenantGuard.NotThisTenantItemMessage` + 머리 · 상세 행 0」 으로 단언.**

### P2-2 · 「형식만 같은 예외」 함정 — 단언은 문구까지, EF 입구 「쓴 행 0」 은 빈 측정
- 근거 ①: MySqlConnector 는 트랜잭션이 열린 연결에서 `transaction` 없이 질의하면 **역시 `InvalidOperationException`**(다른 문구)을 던짐. 가드를 `tx` 없이 부른 실수가 있으면 형식만 보는 R-n 이 초록이 됨(빈 측정). 지금 작업 트리는 E7 `tx` · W3 `dbTx` 를 넘겨 맞음 — 시험이 이걸 **잡을 수 있게** 해야 함.
- 근거 ②: E3 · E5 · E8 · E9 는 가짜 작업 단위라 가드가 없어도 실표에 행이 안 생김 → 「쓴 행 0」 은 늘 참.
- 개발에 돌려줄 한 줄: **R-n 은 문구 같음(`Assert.Equal(NotThisTenantItemMessage, ex.Message)`) 필수 · A-n 은 성공(또는 가드 문구 아님) 필수 · EF 입구는 가짜 저장소 `AddAsync` · `SaveChangesAsync` 가 `Times.Never` 임을 함께 잰다.**

### P2-3 · 견적 → 수주 전환은 트랜잭션이 없다 — R-n 이 머리 행까지 세야 함
- 파일: `src/HitPan.Application/Services/QuotationService.cs` 바닥 :322 번호 따기 → :326 `INSERT INTO sales_orders` → :352 상세 INSERT → :368 견적 상태 UPDATE (트랜잭션 0)
- 근거: 지금 작업 트리는 가드를 :313 뒤(번호 따기 · 머리 INSERT 전)에 둬서 **맞음**. 그러나 뒤에 누가 가드를 상세 루프 앞으로 옮기면 고아 수주 머리가 남음 — 이걸 막는 장치는 시험뿐.
- 개발에 돌려줄 한 줄: **전환 R-n = `sales_orders` · `sales_order_items` 행 수 그대로 + 견적 `status` · `converted_order_id` 그대로 를 함께 단언.**

### P2-4 · TEMPORARY 표는 연결마다 따로 — 서비스가 다른 연결을 쓰면 실표 접촉 + 빈 측정
- 파일: `PurchaseService.cs` W3 = `_unitOfWork.GetDbConnection()` · `_unitOfWork.BeginTransactionAsync` (바닥 :934~936) · 가드도 그 `conn` 을 씀
- 근거: 시험이 가짜 작업 단위를 **시험 연결과 다른 연결**로 묶으면 가드 · INSERT 가 `hitpan_e2e` 실표 `items` · `purchase_returns` 를 봄 → 실표 쓰기(#39 정신) + 가드가 빈 실표를 보고 거절해 R-n 이 「맞는 이유 없이」 초록. 또 `HasSalesReturnLossColumnAsync`(판매 반품 상세 · W4 · W5)와 매입 반품 손실 칸 판정은 정보 스키마를 볼 수 있어, TEMPORARY 표에 `is_loss` 가 없으면 1054.
- 개발에 돌려줄 한 줄: **모든 서비스 연결 = 시험 연결 하나(가짜 작업 단위의 `GetDbConnection` · `BeginTransactionAsync().DbTransaction` 도 같은 연결) · 반품 TEMPORARY 표는 출하 DDL 칸 그대로(`is_loss` 포함) · TEMPORARY 표 `ENGINE=InnoDB`(#17 · E7 롤백 뜻 유지).**

### P3-1 · 커밋 메시지 「@」 1건 — `c54026a7` 넷째 줄
- 근거: `- PdfRenderService 로더 6: 견적만 AND i.tenant_id = @TenantId` — 3축 「@」 0 글자 위반(알림 대상 아님 · 도구 꼬리 줄 0 · 경로 · 자격증명 꼴 0 은 통과).
- 개발에 돌려줄 한 줄: **리베이스 · 강제 push 금지라 그대로 두고, 남은 커밋 · 합류 커밋 · PR 스쿼시 본문에서는 「@」 를 빼서 적는다(예: 「JWT 회사 매개변수」).**

### P3-2 · 검사한 값 ≠ 저장한 값(공백) — 지금은 악용 길 없음
- 근거: 가드는 `Trim()` 한 값을 보고, E1 ~ E4 · E6 · E8 ~ E13 은 원래 값을 저장. 앞 공백 · 비공백 유니코드 공백이 붙은 값은 어느 품목에도 안 맞는 고아 줄(남의 품목 아님). 품목 id 는 서버 GUID(`ItemService.cs:160`)라 「공백 + 같은 id」 를 남이 미리 만들 길 0. MDB 이관 id(Q7)만 예외 후보.
- 개발에 돌려줄 한 줄: **이번엔 손 0 · 명세서에 「검사 값 = 자른 값 / 저장 값 = 원래 값」 한 줄 적어 두고 Q7 판단 때 같이 본다.**

### P3-3 · 자동 발주는 K3 (가) 와 같은 까닭(옛 무검사 원본)이 있는데 손 0

### 4-2. 이슈

#### P2-6 · 확정이 줄 · 머리를 **묶음 밖에서 잠금 없이** 읽고, 나중에 머리를 상태 조건 없이 통째로 덮어씀 → 반대 순서 겹침이 남음
- 파일: `SalesService.cs:414`(머리 `GetByIdAsync` · 묶음 밖 · 잠금 없음) · `:416`(상태 검사 · 메모리 값) · `:430`(줄 `FindAsync` · 묶음 밖) · `:573~574`(`Status = Confirmed` · `deliveryRepo.Update`) · `:579`(묶음 시작) · `:583`(`SaveChangesAsync` — `Repository.cs:41` `DbSet.Update` = **모든 열 수정 표시** · 키만 조건 · 상태 조건 · 동시성 토큰 0) · `:589~610`(재고 · 원장 = **`:430` 에서 읽은 옛 줄**).
- 안 되는 경우: 사용자 B 가 확정을 누르고 `:430` 을 지난 직후(뒤에 수주 잔량 · 재고 합산 검사가 여러 번 있어 길이가 짧지 않음), 사용자 A 의 수정 저장이 처음부터 끝까지 커밋 → 머리 = 새 값 · 줄 = 새 줄. 이어 B 의 `:583` 이 머리를 **옛 합계 · 옛 거래처 · 옛 날짜 + confirmed** 로 덮어쓰고, 재고 · 원장 · 분개를 **옛 줄** 로 넣음 → **확정 문서의 줄(새) ≠ 머리 · 원장(옛)**. A 는 「저장됨」 을 보고, A 의 머리 변경은 소리 없이 사라짐. A 의 UPDATE 가 B 의 `:583` 보다 먼저 잠금을 잡은 경우도 B 가 기다렸다가 같은 결과.
- §15-9 고침은 수정 쪽 문만 닫음 — 확정 쪽은 고침 대상이 아니었음(3차 3-3 「못 본 거리」 그대로). **§15-9 가 만든 구멍 아님 · 기존 구멍.**
- 개발에 돌려줄 한 줄: **확정 묶음 안 첫 줄에서 `SELECT status … FOR UPDATE`(또는 `UPDATE … SET status='confirmed' WHERE … AND status='draft'` 행 수 1 확인) 뒤 줄을 묶음 안에서 다시 읽기 — 같은 PR 에 넣을지 후속 대장에 둘지 PM 결재.** 측정: 확정 `:430` 뒤에 멈춤점을 두고 수정 저장을 끼운 뒤 `sales_delivery_items` 수량 합 ↔ `stock_ledger` 해당 `source_id` 수량 합 · 머리 `total_amount` ↔ 줄 합 대조([4] 시험환경 · #39).

#### P3-11 · 시험이 본문 글자 게이트 — 동작은 안 봄
- 파일: `DeliveryUpdateRowCountGateTests.cs`(R1 · R2 = 소스 글자 · 순서 대조). 변이(조각 되돌리면 빨강)는 확인됐다고 적혀 있으나, 「0행이면 줄이 실제로 안 지워진다」 는 DB 동작 증거는 아님. 개발에 돌려줄 한 줄: **손 0 · [4] 에서 시험환경 겹침 실측 1회(①·P2-6 같이)로 동작 증거를 채울지 PM 판단.**
