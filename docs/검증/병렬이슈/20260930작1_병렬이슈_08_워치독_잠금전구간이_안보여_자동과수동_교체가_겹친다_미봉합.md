## 무엇이 문제인가
- 워치독 자동 적용은 받기·검증(`UpdateOrchestrator.cs:161`) → 백업(`:174`) → 슬롯 판정 → **그 다음에야** `_lock.Acquire`(`:201`). `Acquire` 는 있는지 안 보고 쓴다(`UpdateLockFile.cs:64-69`). 교체 표식(`update-swap.marker`)은 첫 폴더 이동 직전에야 생긴다.
- API `CheckBusy`(`LocalSwapLauncher.cs:93-100`) · 수동 업데이트 `IsAutoUpdateInProgress`(`WatchdogUpdateCoreAdapter.cs:100`) · 일꾼 S0 `Test-UpdateBusy`(`local-swap.ps1:511-519`) 는 전부 잠금·표식·`.rbk`·자가교체 작업만 본다 ⇒ 워치독 받기·백업 구간은 **안 보인다**.
- 일꾼 `Set-Lock` 도 덮어쓰기(`local-swap.ps1:273-277`)이고 S0 한 번만 남의 잠금을 본다. 워치독은 S3 에서야 멈춘다(`local-swap.ps1:293-298` — 서비스 강제 정지 + 프로세스 kill).

## 발생 시나리오
워치독이 N+1 을 받아 백업 중(잠금 없음) → 관리자가 수동 되돌리기 [예] → 두 판정 통과 → 일꾼 S1(해제) 중 워치독이 `Acquire`(덮어씀)·정지·`web → web.old` 시작 → 일꾼 S3 가 워치독을 **교체 한가운데서 kill** → 일꾼 S4 가 반쯤 바뀐 `api`/`web` 을 `.rbk` 로 밀고 옛 판을 넣음 → 검증 실패 시 S7 이 반쯤 바뀐 것을 되돌려 놓음 → `broken` 또는 판 섞임. 워치독 재기동 복구(R1~R4)는 `.old` 만 보므로 `.rbk` 와 섞인 모양을 모른다.

## 막는 방향 (한 줄)
일꾼이 워치독을 **먼저 멈춘 뒤**(S3 앞당김 또는 S0 에서 서비스 정지) 표식·잠금·`.old` 모양을 다시 재고, 하나라도 있으면 거부 — 워치독 코드 무변경 조건 안에서 닫는 유일한 순서.
