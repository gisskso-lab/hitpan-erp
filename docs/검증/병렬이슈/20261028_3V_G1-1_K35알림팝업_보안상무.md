## 카드 (반증 5건)
1. **방 번호 끼워넣기 — 안 깨짐.** `Link` 는 서버가 `"/chat/" + roomId` 로 만든다(ChatService.cs:849). 방 이름·본문·파일명 등 다른 사용자 글자는 `Title`/`Body` 에만 들어가고 링크에는 안 섞인다. roomId 는 서버 `Guid.NewGuid()`(:202·:903)이고, 보내는 길은 라우트 값이지만 `IsMemberAsync` 를 통과해야 한다(:372·:662). 남의 방 `/chat-window/{남의방}` 은 메시지 읽기 API 가 403 으로 막는다(:296 → ChatController.cs:105-112).
   - ⚠️ 잔여(미측정 · 실DB): `chat_room_members` 정렬규칙이 `utf8mb4_unicode_ci`(hitpan_db_clean.sql:4867)라서, 방 참여자는 **대소문자를 바꾼 값 · 끝에 공백을 붙인 값**으로 보내도 참여 검사를 통과한다. 그러면 링크에 그 변형된 값이 실린다. 같은 방 · 같은 참여자 안에서만 생기는 일이라 해는 없다. 판정 함수가 거짓을 내면 기존 본 창 길로 간다.
2. **팝업이 같은 출처 밖으로 — 안 깨짐(조건).** 팝업 주소 = 고정 앞머리 `"/chat-window/"` + 판정을 통과한 roomId. 빗금 하나로 시작하므로 `//evil` 같은 꼴이 생길 수 없다. 조건: 팝업 주소를 **`n.Link` 를 바꿔 끼워 만들면 안 된다**(예 `Link.Replace("/chat/","/chat-window/")` 는 `//evil/chat/x` 에서 외부로 샌다).
   - 기존 길 `Nav.NavigateTo(n.Link)` 는 받는 쪽에서 외부 주소(`//host` · 절대 URL)를 거르지 않는다(정적 판단 · 미측정). 다만 알림을 만드는 곳 3곳(AuthController.cs:235 · ApprovalTriggerHelper.cs:243 · ChatService.cs:849)이 전부 고정 앞머리를 쓰는 같은 출처 경로라 **지금 악용할 길은 없다** → 기존 잠재 결함으로만 기록한다.
3. **`Type` 위장 — 안 깨짐.** `Type` 은 서버가 정한다(ChatService.cs:846). `kind` 는 코드 경로마다 고정이다(문자 :410/:423 · 파일 :742 · 결재 :478/:486). `SendMessageRequest` 에는 종류를 고르는 칸이 없다(Body·RefType·RefId만 · ChatDtos.cs:141-148). 알림 허브는 클라이언트가 부를 수 있는 메서드가 없고, 그룹은 JWT 로 정한다(NotificationHub.cs:20-36). 남는 것은 본문 글자로 결재 안내처럼 꾸미는 사회공학뿐이다. 그래도 제목은 「새 메시지」에 보낸 사람 이름이 붙는다(:837-840). 기존 문제이고 범위 밖이다.
4. **`await` 뒤 `window.open` 팝업 차단 — ⚠️미측정 · 위험 중.** 「상단바와 같은 꼴」 전제는 **반만 맞다.** 상단바는 버튼 클릭 → 첫 await 가 곧바로 JS 호출이다(TopHeader.razor:58). 종 목록은 `MudMenuItem` 클릭이다(NotificationBell.razor:55 · MudBlazor 9.3.0 · HitPan.Web.csproj:24). 메뉴 닫기를 기다린 뒤 OnClick 이 불리면 `window.open` 이 다음 작업으로 밀린다. 토스트는 `Snackbar` OnClick(:99)이고, MudBlazor 가 그 Task 를 기다리지 않으므로 await 뒤 예외는 아무도 받지 않는다. 지금 `Open`·토스트는 동기에 `Nav` 만 써서 사용자 동작이 필요 없었다. **이번에 처음으로 사용자 동작이 필요해진다.**
5. **대체 길 무한 반복 — 안 깨짐.** 본 창 `/chat/{방}` 은 알림을 만들지 않는다. 알림은 서버가 보낼 때만 생기고, 읽음 처리는 UPDATE 한 줄뿐이다(ChatService.cs:489-499). 안내 토스트는 누를 동작이 없으니 사람이 누르지 않으면 반복도 없다.

## 조건 (구현·[4] 에 넘김)
- C1 팝업 주소 = 상수 `"/chat-window/"` + `TryGetRoomId` 통과 값만 쓴다. `n.Link` 를 바꿔 만들면 반려한다. 판정 허용 글자는 GUID 꼴(16진수·`-` · 36자)로 좁혀도 서버 생성분과 맞는다(:202·:903).
- C2 G1·G2 는 **종 목록 길과 토스트 길을 따로** 재고(§5-2 [4] 독립반증 ③), 상단바 통과를 근거로 갈음하지 않는다. Edge/Chrome 에 더해 차단이 더 엄격한 브라우저(Safari·모바일) 결과를 개발명세서에 적는다(⚠️미확인).
- C3 토스트 OnClick 람다 **안에** try/catch 를 둔다(#15). 밖에서는 아무도 기다리지 않는다.
- C4 안내 토스트에 「다시 열기」 OnClick 을 달지 않는다(반복 여지 0 유지). `openRoom` 이 예외로 false 를 낸 것(차단이 아닌 경우)도 「팝업 허용」 문구로 뭉개지므로 문구 정확성은 저위험으로 기록한다.

## 범위 밖 관찰 (별건 · 기존)
- O1 Web `Services/ChatService.cs:78-79` — roomId 를 인코딩하지 않고 API 경로에 넣는다(클라이언트 측 경로 끼워넣기). 사용자가 직접 친 `/chat/{RoomId}`·`/chat-window/{RoomId}` 에 기존부터 있던 문제다. 이번 팝업 길은 허용 글자로 좁히므로 **넓히지 않는다.** 저.
- O2 창 이름 `'hitpanChat'` 으로 이름 붙인 창을 다시 쓰는 것과, 차단 확장이 「곧바로 닫힌 창」을 돌려주면 `open` 이 true 를 내 조용히 실패하는 것 — 상단바와 공통인 기존 문제다. 저.
