## 2. 🔴 V9-1 · V9-2 · V9-3 — 하나의 뿌리: "메인PC 판정"이 성립하지 않는다

### 2.1 봉합이 딛고 선 전제

`src/HitPan.API/Controllers/AuthController.cs:43-49` 이 이렇게 적고 있다.

> *"메인PC 본인은 localhost/127.0.0.1(loopback)로 접속하고, **클라이언트는 터널 도메인으로만 온다.**
> IP 기반이 아니라 loopback 여부라 cloudflared 터널 프록시가 위조할 수 없다(신뢰 가능)."*

봉합 3건(D-3·D-4·D-5)이 전부 이 한 문장 위에 서 있다.
**이 문장이 틀리면 3건이 동시에 무너진다.** 그래서 이것부터 반증했다.

### 2.2 반증 — 우리 코드가 스스로 반대로 적고 있다

**증거 ① 터널은 히트판을 "같은 컴퓨터 안에서" 부른다**

`installer/HitPan-Universal.iss:1134`
> *"터널 — ingress origin = `http://localhost:5257`(API)"*

`installer/build-installer-universal.ps1:130-131` — **3중 실측으로 확정된 문장이다**
> *"터널(test1.hitpan.kr)은 ingress origin=`http://localhost:5257`(API) 직결이라(3중 실측:
> /health 200=API전용·ingress 코드값 5257·WASM바이트=API옛것 일치), 터널로 오는 실고객은…"*

cloudflared 는 고객사 PC 안에서 도는 프로그램이다.
바깥에서 온 요청을 받아 **자기가 있는 그 PC 의 `localhost:5257` 로 다시 부른다.**
히트판 입장에서 그 요청은 **바로 옆에서 온 요청 = loopback** 이다.

**증거 ② 히트판은 loopback 말고는 아예 듣지도 않는다**

`installer/HitPan-Universal.iss:2355-2359`
> *"보강 2026-06-17 (1.2.12, P1 #2): --urls 바인딩 0.0.0.0 → **127.0.0.1** (LAN 노출 차단)"*
> `... --urls http://127.0.0.1:{포트}`

히트판 본체는 **127.0.0.1 로만 귀를 열어 둔다.**
즉 **loopback 이 아닌 요청은 애초에 히트판에 도달할 수 없다.**
도달한 요청은 100% loopback 이다 — 판정이 항상 참이 된다.

**증거 ③ 사내 다른 PC(5234 경로)도 마찬가지다**

`installer/web-server.ps1:54` — 이쪽은 **모든 방향으로 귀를 연다**
> `$listener.Prefixes.Add("http://+:$port/")`

그리고 `installer/web-server.ps1:33, 89-91` 에서 받은 요청을 히트판에 다시 넘긴다.
> `$apiBase = "http://localhost:$apiPort"`
> `$targetUrl = "$apiBase$($ctx.Request.Url.PathAndQuery)"`

`installer/web-server.ps1:96-103` 을 보면 요청 헤더를 옮기면서
**"이 요청을 원래 보낸 사람이 누구인지" 는 붙이지 않는다**(X-Forwarded-For 없음).
⇒ 사내 다른 PC 에서 접속해도 히트판이 보는 것은 **자기 자신(loopback)** 이다.

**증거 ④ 반대 방향 보정 장치도 없다**

`src/` 전체에 `UseForwardedHeaders` 배선이 **0건**이다.
`src/HitPan.API/Controllers/HealthController.cs:19-20` 이 이 사실을 이미 적어 두었다.
> *"⚠️ 단 이 판정 경로는 단일 실패점이다 — … **UseForwardedHeaders 배선이 없어 프록시 경유 시
> RemoteIpAddress 가 프록시 IP 가 되며**, 터널 ingress 를 5257(API) 직결로 붙이는 배포 형태가 실재한다."*

`src/HitPan.API/Controllers/AppVersionController.cs:16-18` 도 같은 말을 한다.
> *"터널이 로컬 프록시라 RemoteIpAddress 가 **우연히 127.0.0.1 이 될 수는 있으나**,
> 그건 보장이 아니라 **배포 형태에 기댄 우연**이다."*

**이 두 문장이 결정적이다.**
`AppVersionController` 는 이 "우연"을 **위험**으로 보고 화이트리스트를 피해 갔다.
그런데 이번 봉합은 **같은 우연을 "신뢰 가능" 이라고 부르며 근거로 삼았다.**
같은 사실을 한 파일은 피하고 다른 파일은 기댄 것이다 — **둘 다 옳을 수는 없다.**

### 2.3 그래서 실제로 무슨 일이 일어나는가

`isMainPcLoopback` 은 고객사 실제 환경에서 **언제나 참**이다.
`AuthController.cs:107` 이 그 참값을 그대로 넘긴다.

| 봉합 | 의도한 대상 | 실제 적용 대상 | 결과 |
|---|---|---|---|
| **D-3** (`TenantDeviceService.cs:237`) | 메인PC 1대만 한도 면제 | **전 기기** | 🔴 basic 5대 제한이 **무제한**이 된다 |
| **D-5** (`TenantDeviceService.cs:142, 168`) | 메인PC 만 폐기 해제 | **전 기기** | 🔴 폐기한 기기가 **다음 로그인에 전부 부활** |
| **D-4** (`AuthController.cs:91-93`) | 메인PC 만 표식 | **전 기기** | 🟠 전부 "자료 보관 컴퓨터" — 표식이 무의미 |

### 🔴 V9-1 (P0) — 요금 정책이 무너진다

`src/HitPan.Infrastructure/Services/TenantDeviceService.cs:237-244`
```
if (overLimit && isMainPc)   // ← isMainPc 가 항상 true
{
    _logger.LogWarning(...);   // 거부하지 않는다
}
else if (type == "pc" && pcUsed >= pcLimit) { ... 거부 ... }
```

`if` 가 항상 먼저 걸리므로 **아래 두 개의 거부 분기(`:245`, `:250`)에는 영원히 도달하지 않는다.**
PC·모바일·태블릿 **전부** 마찬가지다 — 질문 주신 "모바일 경로가 종전대로 막히는가" 의 답은
**아니오, 모바일·태블릿도 함께 뚫린다** 이다(`:250` 이 `else if` 체인 뒤에 있기 때문).

**재현**
1. basic(PC 5대) 테넌트에서 PC 5대를 등록해 한도를 채운다
2. 6번째·7번째·8번째 PC 로 접속해 로그인한다
3. **전부 등록되고 전부 로그인된다.** 로그에 경고만 한 줄 남는다

**왜 P0 인가**
사장님 결재는 *"메인PC가 슬롯기기를 소모해야 정상이지. 그래야 요금정책이 의미가 있지"* 였다.
슬롯을 **1개 더 쓰게 하려던 봉합**이, 결과적으로 **슬롯 제한 자체를 없앴다.**
결재의 목적과 정반대다. 히트판의 과금 근거(기기 대수)가 사라진다.

⚠️ 이것이 **조용히** 일어난다는 점이 가장 나쁘다. 오류도 화면 이상도 없다.
경고 로그 한 줄뿐이라 아무도 모르는 채로 몇 달이 지날 수 있다.

**보조 확인 — 지문이 갈라지는 문제는 이것과 별개로 더 나쁘게 겹친다**
`src/HitPan.Web/wwwroot/js/device-fingerprint.js:35-49` 의 씨앗에 브라우저 종류가 들어간다.
같은 PC 라도 Chrome ↔ Edge 를 바꾸면 **다른 기기로 잡힌다.**
종전에는 한도가 이 갈라짐을 막아 줬으나, V9-1 이후에는 그 제동이 없다.

### 🔴 V9-2 (P0) — 폐기가 폐기되지 않는다

`src/HitPan.Infrastructure/Services/TenantDeviceService.cs:142-146, 168`
```
if (!isMainPc) { ... 거부 ... }        // isMainPc 항상 true → 거부 안 함
...
status = CASE WHEN @IsMainPc = 1 THEN 'approved' ELSE status END   // → 항상 approved
```

**재현**
1. 관리자가 기기 목록에서 직원 PC 를 폐기한다
2. 그 직원이 다시 로그인한다
3. **되살아나서 정상 로그인된다**

**왜 P0 인가 — 보안 축**
"폐기" 는 히트판이 고객에게 준 **유일한 접근 차단 수단**이다(`DeviceController` 에 폐기 말고 없다).
그 수단이 작동하지 않는다.

질문 주신 위협 모델을 그대로 따져 본다.
- *"메인PC 는 사무실의 물리적 DB 보유 PC 이니 실제 위협인가?"* — **메인PC 만 그렇다면** 위협은 낮다.
  실제로 그 PC 앞에 앉을 수 있는 사람은 이미 자료에 접근할 수 있으므로 폐기의 의미가 작다.
- **그러나 지금은 전 기기가 그렇게 된다.** 퇴사자 노트북, 분실한 태블릿, 집 PC 를 폐기해도
  다음 로그인에 살아난다. 이건 위협 모델이 다르다 — **폐기해야 할 진짜 이유가 있는 기기들**이다.

⇒ D-5 는 **대상이 메인PC 1대로 한정될 때만** 받아들일 만한 절충이다.
   지금처럼 전 기기에 걸리면 **접근 통제의 붕괴**다.

### 🟠 V9-3 (P1) — 표식이 표식 구실을 못 한다

`src/HitPan.API/Controllers/AuthController.cs:91-93` 이 항상 `BuildMainPcName` 을 탄다.
D-4 의 `COALESCE`(`TenantDeviceService.cs:167`) 덕분에 이제 **기존 기기까지 소급해서** 이름이 바뀐다.
⇒ 기기 목록 전체가 `Windows · Chrome (자료 보관 컴퓨터)` 로 채워진다.

사장님이 표식을 요구하신 이유는 *"함부로 정리하면 안 되는 기기를 구분"* 하기 위해서다.
**전부 붙으면 아무것도 구분되지 않는다.** 목적이 정확히 반대로 달성된다.

⚠️ 이 P1 은 D-4 의 `COALESCE` 가 **없었다면 신규 기기에만** 생겼을 것이다.
D-4 자체는 옳은 봉합이지만, V9-1 의 뿌리와 겹치면서 **오염 범위를 과거 기기까지 넓혔다.**

### 2.4 이 뿌리를 어떻게 봐야 하나 (권고 — 결정은 사장님)

**코드 수정은 하지 않았다(SoD).** 방향만 적는다.

`isMainPc` 를 **접속 경로**로 판정하는 것은 이 구조에서 원리적으로 불가능하다.
경로가 전부 loopback 으로 수렴하기 때문이다. 판정의 근거를 **경로가 아닌 다른 것**으로 바꿔야 한다.

생각해 볼 수 있는 축(택일은 설계팀·사장님 몫):
- (가) **설치 시점에 아는 사실을 쓴다** — 설치마법사가 메인PC 지문/식별자를 남기고 그걸 대조
- (나) **한 대만 허용한다** — 테넌트당 메인PC 표식은 1건까지, 이미 있으면 이후는 일반 기기
- (다) **봉합 범위를 되돌린다** — D-3·D-5 를 보류하고 D-1·D-4 만 게시

⚠️ (다)를 택하면 데이비드 박이 지적한 **"메인PC 가 잠기는 P0"** 가 되살아난다.
그러나 그건 *한도가 꽉 찬 테넌트*에서만 나는 사고이고,
지금 봉합은 *모든 테넌트*에서 과금·차단을 무너뜨린다. **지금 상태가 더 나쁘다.**

## 3. 나머지 항목 — 결함 있는 것과 없는 것

### 3.1 D-1 — 되살아나는가 (요청하신 흐름 추적)

**✅ 되살아난다 — 결함 없음.**

`src/HitPan.Web/Components/Common/UpdateProgressOverlay.razor:273` 이 `_stalled = true` 를 세운다.
그 뒤 `RetryAsync`(`:150`)를 따라가면
- `:161` `if (!_stalled)` → 이제 false 이므로 **통과한다**(종전엔 여기서 그냥 돌아갔다)
- `:172-174` 이전 감시를 취소하고 새로 만들어 다시 시작한다

`_cts` 도 정상이다. `:172` 에서 옛것을 취소하고 `:173` 에서 새로 만든 뒤 `:174` 에 그 토큰을 넘긴다.
감시가 둘이 되지 않는다.

**✅ 10분 상한 초기화 — 문제 아님.**
새 감시의 `started`(`:179`)가 다시 잡히므로 상한은 초기화된다.
그러나 이 경로는 **사람이 [다시 확인] 을 누를 때만** 열린다.
스스로 반복하지 않으므로 무한 대기가 되지 않는다.
오히려 "다시 기다리겠다" 는 뜻으로 누른 것이므로 초기화가 **의도에 맞다**.
(`:168` 주석도 "같은 상한이 또 적용된다" 고 정확히 적고 있다.)

### 🟡 V9-5 (P2) — 다만 문구가 사실과 다르다

`_stalled = true` 가 되면 화면은 `:27-35` 분기로 간다.
> **"업데이트가 예상보다 오래 걸립니다"**
> "히트판은 계속 업데이트를 진행하고 있습니다."

10분 초과라면 맞는 말이다. 그러나 **예외로 죽은 경우엔 두 문장 다 근거가 없다.**
화면은 몇 초 만에 이 말을 하게 되고, "계속 진행 중" 인지는 확인한 바가 없다.

## 5. 이번 건에서 남길 교훈

> **주석에 "신뢰 가능" 이라고 적는다고 신뢰 가능해지지 않는다.**

`AuthController.cs:47` 은 *"터널 프록시가 위조할 수 없다(신뢰 가능)"* 라고 적었다.
위조할 수 없다는 말은 맞다. **그러나 위조가 필요 없었다** — 터널을 거치면 **원래** loopback 이다.
"공격자가 속일 수 있나" 만 묻고 **"속이지 않아도 참이 되나"** 를 묻지 않았다.

그리고 같은 저장소의 다른 두 파일(`HealthController.cs:19`, `AppVersionController.cs:16`)이
**이미 정답을 적어 두고 있었다.** 새로 조사할 필요조차 없었다 —
**우리가 쓴 경고를 우리가 읽지 않은 것이다.**

⇒ 접속 경로(IP·loopback)를 권한 판정에 쓰려 할 때는,
**"이 경로로 들어오는 것이 정말 그 사람뿐인가" 를 배포 형태로 확인**한 뒤에만 쓴다.
