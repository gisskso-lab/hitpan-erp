### #3926 — 오탐
`LandingSignupController.cs:414-415` 가 로그에 넣는 값은 `MaskToken(req.SignupToken)` 이다.
`MaskToken`(`:530-535`)은 `SHA256.HashData` → `Convert.ToHexString(...)[..12]` — **단방향이고 앞 12자만 남는다.** 원문 복원 경로 0.
전수 확인: `MaskToken` 호출 3곳(`:347` 접수 · `:415` 결제확인 · `:453` 실패) **전부** 거쳐서 나간다. 같은 파일에 토큰 원문을 쓰는 로그 호출은 **0건**(grep `signupToken|req\.SignupToken` 전수).
⇒ CodeQL 이 해시를 정화기로 인정하지 않아 생긴 오탐. **주석이 아니라 코드로 확인했다.**

### #1140 · #1139 — 오탐 (전수 추적 **했다**)
두 자리 모두 **국세청(api.odcloud.kr)으로 나가는 요청 본문** 조립이다. 브라우저 응답 싱크가 아니다.

**등급 — P1(P0 아님). 근거:**

- 🔴 `:75-80` 주석이 *「unknown 해시는 받지 않는다 — 받으면 현황 1행을 서로 덮어쓴다」* 고 **같은 사고를 이미 알고 있었다.** 상수 하나만 막고 일반 경우를 안 막았다. 이게 가장 아픈 대목이다.
- 추가(PM 미기재): `tenant_update_history` 는 UPSERT 가 아니라 **INSERT** 다(`:141`). 중복창은 60초뿐이라(`:45`) 인증된 고객이 **자기 해시로도** 임의 `from/to_version` 행을 무한 적재해 CS 현황을 더럽힐 수 있다. 테넌트 넘기는 아니지만 같은 뿌리다.

## 2. 🔴 CodeQL 이 못 짚은 진짜 2호 — #3926 **바로 위**에 있다

지시 ③(짚은 자리가 병의 전부라 가정하지 마라)에 따라 같은 메서드를 끝까지 읽었다.

`LandingSignupController.ConfirmPayment` 는 **회사명을 키로 테넌트를 고른다.**

```
:407-411  UPDATE tenants SET status='active', license_key_hash=@Hash
            WHERE company_name = @CompanyName AND status = 'pending'
:419-421  SELECT tenant_id FROM tenants
            WHERE company_name = @CompanyName AND status='active' ORDER BY created_at DESC LIMIT 1
```

실측한 전제 3개:
1. `tenants` 의 UNIQUE 는 **`tenant_code` 뿐**이다 — `company_name` 에 UNIQUE 없음(`00_backoffice_core.sql:135-138`).
2. 가입 저장부(`:259-324`)는 **동명 회사를 막지 않는다** — 중복 검사 0건.
3. `landing_signups` 에 **`tenant_id` 칸이 아예 없다**(`00_backoffice_core.sql:147-167`) ⇒ `ConfirmPayment` 가 토큰에서 테넌트로 되짚을 길이 없어 회사명으로 떨어진 것이다. **이게 뿌리다.**

⇒ 동명 회사 2곳이 동시에 `pending` 이면:
- **한 라이선스 해시가 두 테넌트에 박힌다**(UPDATE 가 여러 행을 맞춘다 · `affected` 는 로그만 하고 아무 판단도 안 한다 `:414-415`),
- 또는 **엉뚱한 회사가 active** 되고 **그 회사의 라이선스로 남의 테넌트가 열린다**,
- 뒤이어 `Telemetry:111` 의 `WHERE license_key_hash = @Hash LIMIT 1` 이 **둘 중 아무 쪽이나** 고른다,
- 웹훅도 `:419-421` 에서 **엉뚱한 테넌트로** 나간다.

이건 #1999 과 **같은 병**이다 — *식별자를 키로 쓰지 않는다.* 그리고 국내 상호는 동명이 흔하다(가정이 아니라 사업 상수다).
🔴 **1차 판정서 §3 에 이 건이 없다.** high 5건만 보면 안 보이고, CodeQL 규칙에도 안 걸린다.

처분: 오늘 손대지 않는다(#29 · 봉합 즉석 금지). 작업지시서 → PM 결재 → 차수 편성.
게이트는 **동작으로** 재야 한다(#글자 금지): 동명 `pending` 2행을 만든 뒤 `confirm-payment` 1회 → `affected` 와 `license_key_hash` 가 **1행에만** 들어가는지, 음성 대조군(동명 1행)은 통과하는지.

### 참고 — `confirm-payment` 가 결제를 검증하지 않는 건 **결재된 베타 전제**다
`:378-392` 는 `signup_token` 만으로 `status='paid'` 로 바꾸고 라이선스를 발급한다. 결제 승인 대조는 0건이다.
그러나 호출부 `src/HitPan.Landing/Components/Pages/Landing/PaymentPage.razor:174-179` 에 **「사장님 결재 2026-06-02 — 베타: 결제 SDK 미적용, API 직접 호출로 active / 정식 = 토스 빌링키 + webhook」** 이 적혀 있고 코드가 그 설명과 일치한다(`TossPaymentsController` `api/payments/toss/confirm` 가 정식 경로로 따로 있다).
⇒ **내 판정: 결함이 아니라 결재된 전제.** 단 🔴 **외부 공개(정식 전환) 전 반드시 재검토 대상**으로 남긴다. 이 경보 5건의 dismiss 와는 무관하다.

## 4. 🔴 내가 못 잰 것 (받아쓰지 마시라)

1. **medium 214건 — 한 건도 안 봤다.** high 만 과녁이었다. 진짜가 섞여 있을 가능성은 **열려 있다**. `cs/user-controlled-bypass` 같은 규칙이 medium 에도 깔려 있을 수 있다.
2. 전체 열린 경보 **2,934** · medium **214** 총계는 내가 재검증하지 못했다(페이지별로만 세었다). 내가 직접 확인한 숫자는 **high 5 · dismissed 0** 두 개뿐이다.
3. **요청 1건도 쏘지 않았다.** 전부 코드 독해다. #1999 의 「A 라이선스 + B 해시」 교차 요청을 **실제로 재현하지 않았다** — 재현 전에는 가설이다. 운영 접촉 금지(#39)라 운영에서는 재지 않았고, 테스트 환경 기동도 이번 과녁 밖이라 안 했다.
4. **`tenant_id`(GUID) 가 고객·대리점에게 노출되는 경로 전수**를 재지 못했다. 노출 경로가 1곳이라도 있으면 #1999 등급이 P1 → P0 로 올라간다. **다음 측정의 1순위다.**
5. 운영 DB 에 **동명 `pending` 테넌트가 실제로 있는지** 0회 측정(§2 의 발동 조건 · 운영은 읽기만이라 이번엔 안 봤다).
6. BizNoVerify 가 국세청 응답 `bStt`·`taxType` 를 `Message` 에 담아 화면으로 보낸다(`:170`). **외부 서비스가 준 문자열이 UI 로 간다.** Blazor 기본 렌더는 인코딩하므로 xss 는 아닐 것이나, 랜딩 화면이 `MarkupString` 으로 그리는 자리가 있는지 **렌더 경로를 재지 않았다**.
7. 작B1 이전 판(`#1665` 시절) 과의 차이는 안 봤다. 현재 `81f058df` 한 판만 읽었다.
