## 무엇이
- 봉합2 `RollbackWatchPlan.IsThisFetchActive`(`RollbackWatch.cs:140-144`)의 신선 판정은 `fetch.AtUtc >= startedUtc − 2분` 이다. `startedUtc` 는 [예] 누른 시각으로 고정 ⇒ **이번 시도의 표지는 시간이 아무리 지나도 늘 신선**하다. 「진행이 멈췄는가」를 보는 재료가 없다.
- 서버 `PreviousPackageFetch.Job._at` 은 **단계에 들어간 시각**일 뿐 심장박동이 아니다(`Move`·`Refuse` 때만 갱신 · `:476-490`). 받는 동안은 갱신이 없다.
- 받기 본체 `UpdateClient.DownloadAsync`(`src/HitPan.Watchdog/AutoUpdate/UpdateClient.cs:211-218`)는 `http.Timeout = 30분` + `ResponseHeadersRead` + `CopyToAsync(fs, ct)`. ⚠️가설(판독 · 미실측) — .NET 의 `HttpClient.Timeout` 은 머리말 수신까지만 걸리고 본문 스트림 읽기에는 안 걸린다 ⇒ 반쯤 열린 연결(RST 없음)이면 `CopyToAsync` 가 끝나지 않는다. `PreviousPackageFetch` 쪽 상한은 크기 초과(`cap`)와 앱 종료(`_stopping`)뿐 — 시간 상한 0.
- 그 사이 상태 응답은 계속 `Fetch={Stage=downloading, To=to, AtUtc=시작 직후}` ⇒ 덮개: 10분 → 「예상보다 오래 걸립니다」 → [다시 확인] → `Waiting`(`RollbackWatch.cs:239`) → 새 10분 → … **끝이 없다**. 덮개 Stalled 화면은 [다시 확인] 버튼 하나뿐(`RollbackProgressOverlay.razor:32-35`) = 병렬이슈 26 ② 「덮개가 끝없이 돈다」가 이 좁은 길로 되살아남.
- 문구도 사실과 다르다: 받기가 멎었는데 「계속 되돌리기를 진행하고 있습니다」.

## 끝나는 길(코드 판독) — 반대로 이것들이 아니면 안 끝난다
- 모든 실패 갈래는 `Refuse`(→ refused · 활성 아님) · 넘김 성공은 `HandedOff`(활성 아님) · API 재시작은 메모리 표지 소멸(`Current` null) · 상태 응답 실패는 `s.Ok=false` ⇒ 이 넷은 `Unconfirmed`/`Refused` 로 정상 종료.
- 남는 것 = **받기 본문이 멈춘 채 예외도 취소도 없는 경우** 하나.

## 재현 방법(순수 루프 · 운영 조작 0)
- 가짜 `getVersion` = 늘 `(200, from)` · 가짜 `getStatus` = `Ok` + `Last=null` + `Fetch={downloading, to, 시작+1분}` · 시계를 10분씩 N회 밀며 `CheckOnceAsync` → **N회 전부 `Waiting`**(G-W14 가 바로 이 모양을 PASS 로 잰다 — 시간 축이 없다).

## 봉합(권고 — 결정은 설계·PM)
- 활성 판정에 상한을 둔다: 예) `now − startedUtc` 가 종전 화면 폴링 상한(`PollLimit` 30분)을 넘으면 활성이어도 `Unconfirmed`. 또는 서버 표지에 진행 바이트·마지막 진행 시각을 싣고 그것으로 신선 판정.
- 받기 본문 정지 자체(⚠️가설)는 별건 — 본문 읽기 시간 상한(읽기 사이 무진행 N분이면 취소 → `Refuse(download_failed)`) 여부는 설계 몫.
- 대조군: 위 재현 대본에서 30분 넘긴 [다시 확인] = Unconfirmed · 30분 안 = Waiting 둘 다.
