## 1. 코드 순서 (`RunBackupAsync`)

덤프(`:158`) → 파일 확인(`:160-162`) → 미러 복사(`:166-171`) → **보관정책 삭제**(`:174-176`) → 이력 `success` UPDATE(`:185-192`, `ct`) → 설정 `last_*` UPDATE(`:199-201`, `ct`) → 예외면 `catch` 실패 UPDATE(`:215-222`) — 조건은 `WHERE backup_id = @BackupId` **뿐, 상태 조건 없음**. 🟢

## 2. 창

| 창 | 현행 (ct 그대로) | ④ 적용 뒤 (None) |
|---|---|---|
| W1 이력 `success` 커밋 뒤 · 설정 UPDATE 에서 취소 | 실패 UPDATE 도 취소 예외 → 이력 **`success` 유지** (우연히 맞음) | 실패 UPDATE 가 성공 → **`success` → `failed` 로 덮음** · `primary_file` 은 남음 |
| W2 보관정책 삭제 뒤 · 이력 `success` 전에 취소 | 이력 `running` 잔존 · 가장 오래된 성공 백업 파일은 **이미 삭제** | 이력 `failed` · 오래된 파일 **이미 삭제** (기존 결함 — ④ 와 무관하게 존재) |

W1 결과: 복원 대상 조회는 `status = 'success'` 만 본다(`:249`) → **완전한 백업 파일이 복원 목록에서 사라진다.** 응답은 `Success=false` → 초기화는 중단(안전 방향)이지만 사용자는 "백업 실패"로 알고 다시 누른다.
W2 결과: 이번 실행은 실패로 끝났는데 보관 개수는 이미 줄었다 → `backup_history` 에 `success` 로 남은 행이 **없는 파일**을 가리킨다.

## 3. 재는 법 (격리 인스턴스 · 작업리뷰서 §3 ⓒ)

잠금 없는 작은 DB · 덤프 프로세스 종료를 감시하다 종료 즉시 취소 · 지연 Δ 0~200ms 를 나눠 20회 · 끝 상태를 표로 센다.
**FAIL 조건(하나라도)**: 「파일 완전 + 이력 `failed`」 · 「이력 `success` + 파일 없음」 · 「이력 `running`」.
대조군: 취소 없이 20회 → 전부 `success` + 파일 있음.

## 4. 봉합 제안 (코드 0 — [3] 판단 재료)

- 실패 UPDATE 에 `AND status = 'running'` — 이미 끝난 기록은 건드리지 않는다 (복원 `:318-325` 도 같은 모양).
- 보관정책을 이력 `success` 기록 **뒤로** 옮긴다 — 단 지시서 §3 "보관정책(`:464-476`) 변경" 넘김과 경계가 겹침 → PM 판단 (호출 위치 이동 ≠ 정책 변경으로 볼지).
