## 무엇이 잘못됐나

`MdbMigrationService.RunTableStepAsync` 가 잡 전용 conn 을 **try 블록 밖**에서 발급했다.

```csharp
// 🔴 종전
jobConn = await _migrationFactory.CreateOpenAsync(ct);   // ← try 밖
IDbTransaction? tx = null;
try { tx = effectiveConn.BeginTransaction(); … }
catch (Exception ex) { …; if (!continueOnFail) throw; }   // ← 여기까지 못 온다
```

`continueOnFail=true`(PANDATA 잡 기본)는 *"한 표가 실패해도 다른 표는 계속"* 이 약속인데,
**발급 실패는 그 약속 밖**에 있었다. 예외가 `Task.WhenAll` 로 올라가 병렬 단계 전체가 faulted 로 끝난다.

## 🔴 왜 5월엔 안 났나

잡이 14개였고 그날 서버가 25초 안에 다 받아줬다. **15번째 잡(작21 `payments`)이 문턱을 넘겼을 뿐** — 결함은 처음부터 있었고 고객 PC(느린 디스크·백신 실시간 검사)에서는 14개로도 날 수 있는 모양이다.

## 봉합

| 자리 | 변경 |
|---|---|
| `MdbMigrationService.RunTableStepAsync` | conn 발급을 **try 안**으로 → 발급 실패도 `failed` 콜백 + `migration_errors` 기록 + `continueOnFail` 존중 |
| `MdbMigrationService.OpenJobConnectionWithRetryAsync` 신설 | 2·4·8초 뒤 3회 재시도, 취소면 즉시 중단 |
| `MigrationDbConnectionFactory` 연결문자열 | `ConnectionTimeout=60`(기본 15) — 핸드셰이크·풀 대기 상한 |
| 게이트 `W12` | 발급이 try 안에 있고 재시도 헬퍼를 부르는지 — 되돌리면 빨간불 |

## 교훈

| | |
|---|---|
| 🔴 | **"한 표 실패해도 계속" 은 try 의 범위만큼만 참이다** — 자원 획득이 try 밖이면 약속이 깨진다 |
| 🔴 | **병렬 폭을 늘리면 문턱이 옮겨진다** — 잡 하나 추가가 전체 실패로 바뀌는 자리가 있다. 잡을 늘릴 땐 발급 경로부터 |
| ⚠️ | 세션 튜닝 3종 중 첫 SET(`innodb_flush_log_at_trx_commit`)이 MariaDB 11.4 에서 GLOBAL 전용이라 실패하고 **나머지 2종(`foreign_key_checks`·`unique_checks`)도 안 걸린다** — 그러나 `unique_checks=0` 은 INSERT IGNORE 멱등과 부딪힐 수 있어 **일부러 손대지 않았다**(작22 에서 재검토) |
