## 2. 진범 규명 (조사 완료 — 추측 아님)

### 사실 1 — SQL 55개는 누적 이력이다
`migrations-1.2.36.txt` 사이드카 실측: `DB-02_3tier_schema.sql` ~ `DB-84_schema_migrations.sql`.
프로젝트 전체 마이그레이션 역사. **이번 1.2.34→1.2.36 신규가 아니라 이미 모든 DB에 적용된 것들.**

### 사실 2 — 게이트 ①이 "존재"로 판정한다 (너무 거침)
[`UpdateOrchestrator.cs:456`](../../src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs#L456):
```csharp
// ① manifest.RequiresMigration==false 인데 .sql 이 존재 → 손입력 오타. 강제 중단.
if (sqlFiles.Length > 0 && !manifest.RequiresMigration) { ... return false; }
```
누적 이력은 **항상 `sqlFiles.Length > 0`** 이므로, `RequiresMigration=false` 인 모든 릴리스가 차단된다.

### 사실 3 — requiresMigration 자동산출은 미구현 (알려진 결재 대기)
[`build-manifest.ps1:24-27`](../../installer/updates/build-manifest.ps1#L24-L27):
> "requiresMigration 자동 산출은 아직 못박지 않았다 (사장님·CTO 결재 대기)
>  → 지금은 -RequiresMigration 스위치로 '명시 입력'만 받고, 자동 산출은 W4-2 착수 시 결재 후 배선."

CI(`build-installer.yml`)는 이 스위치 없이 호출 → 항상 `requiresMigration=false`.
**게이트 ①(무조건 차단) + 자동산출 미구현(항상 false) = 모든 업데이트 영구 차단.**

### 사실 4 — 다른 두 게이트는 이미 정밀하다 (게이트 ①만 거침 = 모순)
| 게이트 | 위치 | 판정 | 오탐 |
|---|---|---|---|
| 빌드타임 §3 | `build-manifest.ps1:161-173` | `local_update_` 테이블 **ALTER/DROP만** 차단 | 없음(정밀) |
| 런타임 ② | `UpdateOrchestrator.cs:470~` | 가드 3테이블 **ALTER/DROP만** 차단 | 없음(정밀) |
| **런타임 ①** | `UpdateOrchestrator.cs:456` | **SQL 파일 존재** = 차단 | **있음(진범)** |

게이트 ②는 오탐을 피하려 "존재가 아니라 변경(ALTER/DROP)"으로 정교하게 설계됐다.
그런데 ①이 그 **앞에서** 무조건 막아, ②의 정밀함이 무의미해졌다.

## 3. 봉합안 (2개 — CTO·사장님 택1 또는 병행)

### A안 — 게이트 ①을 "신규 마이그" 기준으로 정밀화 (워치독 단독, 즉효)
게이트 ①의 판정을 "누적 SQL 존재"에서 **"이번 릴리스가 실어온 신규 마이그가 있는가"**로 좁힌다.
- 판정 기준: **로컬 DB의 `schema_migrations` 테이블에 없는 .sql 이 zip 에 있으면** = 신규 마이그.
  (DB-84가 `schema_migrations` 테이블 — 적용 이력 추적용. 이미 존재.)
- 신규 마이그가 있는데 `RequiresMigration=false` → 그때만 차단(진짜 오타). 없으면 통과.
- 장점: manifest 신뢰 안 해도 로컬 사실로 판정(더 안전). 자동산출 미구현과 무관하게 즉시 통과.
- ⚠️ 헌법 #26·#36 직결 — `schema_migrations` 조회 로직·마이그 적용 순서 정합 필요.

### B안 — build-manifest 자동산출 배선 (빌드타임, 근본)
`build-manifest.ps1` 이 "이번 zip 의 Migrations\SQL 중 직전 릴리스 대비 신규 .sql"을 세어
`requiresMigration` 을 **자동 산출**한다. 신규 있으면 true, 없으면 false.
- 장점: 사람 손입력 제거(헌법 #36 정신). 게이트 ①이 옳게 동작(true 릴리스만 마이그).
- ⚠️ "무엇 대비 신규"(기준선) 정의가 필요 — 코드 주석이 결재 대기로 남긴 바로 그 지점.
  기준선 후보: 직전 게시 manifest 버전 / `schema_migrations` 최신 등.

### PM 권고: **A안 우선(즉효) + B안 후속(근본)**
- A안은 워치독 로컬 판정이라 **오늘 재실측까지 가능**. 게이트를 사실 기반으로 정밀화.
- B안은 기준선 정의에 사장님·CTO 결재가 필요(주석이 명시)하므로 별도 안건으로 이어간다.
- 단, A안도 `schema_migrations` 조회가 헌법 #26 마이그 무결성과 직결되므로 CTO 정밀 검토 필수.

## 4. 작업 항목 (A'안 — CTO B-1 반영 확정본)

> ⚠️ A안 원안은 CTO 반려. 아래 A'안은 **"신규 마이그가 있으면 RequiresMigration 값과 무관하게

### W-1 (워치독/DB) — 게이트 ① 판정 정밀화 (A'안)
- 파일: `src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs` `PassesMigrationCrossCheck`
- 현재 ①: `sqlFiles.Length > 0 && !RequiresMigration` → 무조건 차단(누적 이력에 항상 걸림 = 오탐)
- 변경 ① (A'안):
  ```
  zip 의 Migrations\SQL 중 로컬 schema_migrations 에 미적용인 .sql 이 있는가?
    · 신규 없음                → 통과 (누적 이력만 = 정상 코드배포 릴리스)   ← 오탐 제거
    · 신규 있음                → 차단 (RequiresMigration 값 무관 — 고리5 부재)  ← B-1 핵심
  ```
  - **신규 마이그가 있으면 `RequiresMigration` 참·거짓 무관하게 차단.** 워치독은 마이그를 적용
    못 하므로(고리5 범위), 마이그 필요 릴리스는 고리5 완성 전까지 자동업데이트 대상에서 제외.
- 게이트 ②(ALTER/DROP 정밀 검사)는 **그대로 유지** — 이번 봉합 대상 아님(CTO A-1).
- 방어: `schema_migrations` 조회 실패 시 안전측(차단) — 검증 없이 교체 안 함(헌법 #20, CTO A-3).
- 판정 근거: `schema_migrations` 실재·`MigrationRunner`(API)가 채움 확인. `migration_id` 로 대조.
