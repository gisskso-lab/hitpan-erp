## 발견 (파일:줄 · 재현 · 등급)

### 코드 추적 메모 (확인한 사실)
- 워치독은 `.rbk` 를 모른다(`src/HitPan.Watchdog` 전체 grep `.rbk` 0건) · 설치 버전 = 자기 어셈블리 판(`Worker.cs:153-158` `EffectiveInstalledVersion` ← `VersionInfo.Current`).
- 워치독 `UpdateLockFile.Acquire`(`UpdateOrchestrator.cs:201`)는 기존 잠금을 **보지 않고 덮는다** · 표식 `update-swap.marker` 는 정지 **뒤** 교체 직전(`:403`) · 안전망은 `StopForSwapAsync` 0단계에서 `/F` 로 같은 이름 등록(`UpdateProcessGate.cs:75,243`).
- 워치독 `.old` 정리는 best-effort — 실패하면 「다음 시도에서 재정리」 로그만(`UpdateOrchestrator.cs:710-719` · `:1093-1095`) ⇒ **다음 자동 업데이트까지 `.old` 가 남을 수 있다**.
- 런처 `CheckBusy`(`LocalSwapLauncher.cs:78-114`)·일꾼 S0 `Test-UpdateBusy`(`local-swap.ps1:721-729`) 둘 다 `.old` 를 **보지 않는다** — `.old` 는 S3 정지 **뒤** `Test-OverlapAfterStop`(`:407-418`)에서만 본다.

### N-1 🟡 P2 — 문지기가 `api.rbk` 를 남긴 「성공」 뒤: 영구 「업데이트가 진행 중입니다」 + 첨부가 화면에서 사라진다 (코드 추적 · 재현 미실시)
- 경로: 되돌리기 성공 `Clear-AfterSuccess` → `Remove-AppDirSafe api.rbk`(`local-swap.ps1:783`) → 싣기 실패 시 `kept …` 로그만(`:357`) · 끝 상태는 그대로 **`success`**(`:878`). 수동 업데이트 쪽 `Save-PrevGeneration` 거부 갈래(`:750-753`)도 같은 모양.
- 그다음: 런처 `CheckBusy` 는 `.rbk` 를 보면 마지막 요청이 **`broken` 일 때만** `swap_interrupted`, 그 밖은 **`update_in_progress`**(`LocalSwapLauncher.cs:105-108`) ⇒ 쿨다운 10분 뒤부터 되돌리기·수동 업데이트 화면이 **영원히** 「업데이트가 진행 중입니다. 끝난 뒤 다시 열어 주세요.」(`LocalSwapUiText.cs:172`) — 06ⓑ 가 없애려던 「영구 거짓 진행 중」이 성공 갈래로 되살아난다. 일꾼 S0 도 `.rbk` 로 `refused/update_in_progress`(`:724` · `:822`).
- 고객이 보는 것: 되돌리기 「성공」 → 남은 첨부는 `api.rbk\chat-files` 에 있어 앱(`{app}\api\chat-files` 만 읽음)에선 **첨부가 안 열린다**. 파일은 무손실이지만 고객 체감은 소실 · 알림 0(로그만). 워치독은 `.rbk` 를 몰라 자동 업데이트는 계속 된다(`.rbk` 는 계속 남음).
- 판정 요청(PM): `success` + `.rbk` 도 `swap_interrupted`(고객센터 안내)로 보일지 · 끝 상태를 `success` 가 아닌 별도 사유로 적을지. 발생 조건 = 서비스 정지 뒤에도 잠긴 첨부(백신 검사 등) ⚠️빈도 미측정.

### N-2 🟡 P2 — 워치독 `.old` 가 남은 PC: 되돌리기·수동 업데이트가 **매번 ERP 를 끄고 켠 뒤** 거부된다 · 다음 자동 업데이트까지 반복 (코드 추적 · 재현 미실시)
- 워치독 `.old` 정리는 실패해도 로그만 · 「다음 시도에서 재정리」(`UpdateOrchestrator.cs:710-719`·`:1093-1095`) ⇒ 첨부 파일 잠김 등으로 `api.old` 가 다음 업데이트까지 남을 수 있다.
- 우리 쪽: 런처 `CheckBusy`·일꾼 S0 는 `.old` 를 안 본다 ⇒ S1 재료 풀기 · S2 안전망 · **S3 `Stop-All`(ERP·워치독 정지)** 까지 간 뒤에야 `Test-OverlapAfterStop` 이 `.old` 로 `refused/update_in_progress`(`local-swap.ps1:411` · `:870-875`) 후 다시 켠다.

- 권고(설계 판단): S0/런처에서도 `.old` 를 보게 하거나(정지 전 거부) · 거부 사유를 「이전 업데이트 정리가 남았습니다」로 분리.

### N-3 🟡 P2 — `S6,S7R2` 섞인 판으로 켜진 상태의 뜻 (S-3 전제 · 코드 추적)
- 되돌리기(1.3.48→1.3.47) 판: api·web = 1.3.47(원하던 판) · 워치독 = 1.3.48 · `api.rbk`·`web.rbk` 남음 · `broken/revert_failed` · 부팅 안전망 남음(K1 §4-2 표와 코드 일치 `:885-901`).
  - 워치독은 설치 판을 **자기 어셈블리 판**으로 잰다(`Worker.cs:153-158`) ⇒ 1.3.48 로 알아 피드가 1.3.48 이면 **아무것도 안 한다**. 섞인 상태가 스스로 풀리지 않고, 피드가 1.3.49 이상이 될 때 워치독이 셋 다 바꿔 판은 맞춰진다. `.rbk` 둘은 워치독이 몰라(grep 0) **영구 잔존**(디스크 수백 MB ⚠️미측정).
  - 우리 화면: 런처 `.rbk` + `broken` ⇒ `swap_interrupted`(「이전 교체가 끝까지 되지 않았습니다. 고객센터로 연락 주세요.」 `LocalSwapUiText.cs:204`) — **정직하나 영구**(워치독 업데이트 뒤에도 `request.json` 이 `broken` 이라 계속). 고객센터 쪽 정리 절차 문서 없음.
- 수동 업데이트(1.3.47→1.3.48) 판: 워치독 = 1.3.47(옛) · api·web = 1.3.48(**방금 S6 확인에 실패한 판**). 워치독이 피드 1.3.48 > 자기 판이라 **같은 1.3.48 을 자동 적용**하러 간다(비Major 자동 · Major 팝업) ⇒ 그 교체는 워치독 경로라 `api.old` 삭제 = 별건 트랙(F-2 워치독 쪽)의 첨부 위험에 그대로 노출.
- 부팅 안전망: 워치독은 자기 업데이트 뒤(`UpdateOrchestrator.cs:294`) 또는 keepalive 가 꺼져 있을 때만(`UpdateProcessGate.cs:170-180`) 지운다 ⇒ 다음 워치독 업데이트까지 남음(매 부팅 keepalive ENABLE — 해 없음).
- 판정: S-3(섞인 판으로라도 켠다)은 「꺼진 채보다 낫다」는 점에서 성립 · 단 **정리 경로(고객센터 절차 또는 다음 교체가 `.rbk` 를 흡수)** 가 없으면 이 PC 는 수동 기능이 영구 잠긴다 — PM 결재 때 같이 보라.

### N-4 ⬜ P3 — 겹침 분기가 워치독이 덮어 등록한 안전망까지 지울 수 있다 · 실해 없음
- 워치독 `StopForSwapAsync` 는 정지 전 같은 이름 `/F` 로 등록(`UpdateProcessGate.cs:75`·`:243`). 우리가 S2 에서 만든 뒤(`CreatedNet`) 워치독이 덮으면 겹침 분기 `:874` 가 그걸 지운다. 그러나 바로 앞 `Start-All`(`:872`)이 keepalive 를 켰고, 워치독은 다음 정지 때 다시 등록한다 ⇒ 재부팅 복원 공백 0.

### N-5 ⬜ P3 — `Set-Lock`(S3 `:850`)이 S1~S2 사이 워치독 잠금을 덮는다 · 폴더 겹침은 0
- 워치독 `Acquire` 도 확인 없이 덮는다(`UpdateOrchestrator.cs:201`). 그 틈의 워치독은 잠금 → 안전망 → 정지 단계이고, 교체 표식(`:403`)·`.old` 는 정지 **뒤**에 생긴다 ⇒ 우리 S3 가 워치독을 멈추면 폴더를 건드리기 전이다. 워치독은 다음 주기에 재시도. ⚠️워치독의 시도 행(`in_progress`)이 어떻게 닫히는지는 미확인.
