## 2. W1 — 경고가 실제로 사라지나 (V1·V2)

### 대조실험 — 같은 데이터에 가드만 바꿔 돌렸다

| 단계 | 봉합 전(`pending` 만) | 봉합 후(`pending`+`ordered`) |
|---|---|---|
| 최초 조회 | pending 1 | pending 1 |
| 발주 | ordered 1 | ordered 1 |
| **화면 갱신** | 🔴 **pending 1 재생성** | 🟢 **pending 0** |
| 알림 행 수 | 🔴 2 (유령 누적) | 🟢 1 |
| 갱신 10회 | — | 🟢 1행 유지 |

🔴 **봉합 전에서 증상이 재현됐다** — 재현 없이 고치면 "원래 됐던 것"과 구분이 안 된다.

### 🔴 반대 방향도 쟀다 (V-역방향)

봉합이 **경고를 영원히 죽이지 않았는지**가 더 중요하다. 안 재면
*"경고가 다시는 안 뜨는"* 더 나쁜 상태를 초록불로 통과시킨다.

| | 결과 |
|---|---|
| 매입확정 → `received` 로 닫힘 | 🟢 |
| 재고 25(>안전재고 10) → 알림 없음 | 🟢 |
| **재고 3으로 다시 떨어짐 → 새 알림 생김** | 🟢 **재감지 정상** |

### 두 경로를 함께 고쳤다

`BomService.GetAlertsAsync` 와 `SyncEventPublisher` **양쪽** 가드를 일치시켰다.
🔴 한쪽만 고치면 이벤트 경로로 되살아난다 — **8/21 이 정확히 그 실수였다**
(주석 *"BOM 경로는 이미 정상"* 이 틀렸다).

## 3. W2 — 🔴 반제품 차단이 **회계까지** 막나 (V12)

이번 작업에서 **가장 무거운 자리**다. 매입확정은 재고만 올리는 게 아니라
매입 분개를 만들고 외상매입금을 가산한다.

### 정책 함수만 재면 안 된다

*"정책은 맞는데 아무도 안 부르는"* 경우를 놓친다.
⇒ **실제 `BomService.OrderAlertAsync` 를 돌려** 회계로 가는 통로가 열리는지 쟀다.

| 시험 | 결과 |
|---|---|
| 반제품 + 스위치 ON + 사슬 선택 | 🟢 **`ConvertOrderToReceiptAsync` · `ConfirmReceiptAsync` 호출 0회** |
| 〃 | 🟢 발주서는 만들어짐 (외주 매입 길 유지 — #20) |
| 〃 | 🟢 이유가 화면에 나감 |
| **대조군** 자재 + 스위치 ON | 🟢 **매입확정 1회 호출 — 끝까지 감** |
| 자재 + 스위치 OFF | 🟢 발주서만 (반자동 원칙) |

🔴 **대조군이 핵심이다** — 없으면 *"그냥 사슬이 아예 안 도는 것"* 과 구분이 안 된다.

### 게이트 진위 확인

반제품 차단을 **일부러 빼고** 돌렸다 → **G-76 이 FAIL**(매입확정이 실제로 불렸다). 확인 후 되돌렸다.

### 판매 경로도 함께 막았다

`SalesService` 의 사슬 실행부에 같은 정책(`AutoChainPolicy`)을 적용.
🔴 BOM 만 막으면 **반제품을 판 뒤 자동발주가 돌면서 그대로 샌다.**
G-74·G-75 가 두 경로가 **같은 판정**을 쓰는지 지킨다.

### 트랜잭션 — 초판 지시대로 했으면 실패했다

작업지시서 초판은 *"판매 패턴 그대로 재사용"* 이라 적었으나,
`BomService` 는 트랜잭션이 메서드 끝까지 열려 있어 **커넥션이 달라 미커밋 발주서가 안 보인다.**
⇒ **커밋 → 사슬** 순서로 본문을 재구성했다(판매 정본과 같은 순서).
⚠️ 사슬이 실패해도 **발주서는 남는다** — 발주는 실제로 났고 매입확정만 사람이 마저 하면 된다(#20).

## 4. W3·W4 — 안내와 중복 차단

### 🔴 초판 자기적발 — **스낵바로는 지시를 못 지킨다**

검증 중 PM 이 W3 를 **절반만 구현한 것**을 스스로 잡았다.
사장님 지시는 *"매입처리 될 때까지"* · *"30분간"* 인데 **스낵바는 몇 초 뒤 사라진다.**
⇒ **배너**로 다시 만들었다. 두 화면(상품마스터·BOM) 모두.

| | 검증 |
|---|---|
| 발주만 된 건 | 🟢 **파란 배너 상시** — *"매입처리 하셔야 재고에 반영됩니다"* + 「매입처리 하러 가기」 |
| 〃 언제 사라지나 | 🟢 매입확정하면 서버가 알림을 닫아 **저절로** 사라진다(새 코드 0) |
| 사슬까지 간 건 | 🟢 **초록 배너 30분** — 서버가 `updated_at` 기준으로 잘라서 준다 |
| 30분 자르기 실측 | 🟢 10분 전 → 나옴 · **45분 전 → 빠짐** · `dismissed` → 빠짐 |
| 두 화면 일관 | 🟢 BOM 화면에도 같은 배너 (같은 알림을 읽는데 안내가 다르면 안 된다) |
| 사슬 못 탄 이유 | 🟢 스낵바로 그때 한 번 (반제품·단가 없음) |
| 개발용어 | 🟢 `alert`·「트리거」·내부 식별자 **제거** |
| BOM 발주 버튼 잠금 | 🟢 신설 (종전 없었음) |
| 서버 중복 가드 | 🟢 `status != 'pending'` throw + 원장 UNIQUE 키 |

⚠️ **덤으로 잡힌 것** — 서버 조회를 넓히면서 BOM 화면이 `ordered`·`received` 까지
*"재고 부족"* 으로 띄울 뻔했다(그 화면엔 상태 필터가 없었다). 상태별로 갈라 담았다.
⚠️ **라우트 실측** — 「매입처리 하러 가기」를 `/purchase/orders` 로 적었다가
실제가 `/purchase-orders` 임을 확인하고 고쳤다. **추측했으면 빈 화면으로 갔다.**

🔴 **결과를 `bool` 에서 DTO 로 바꾼 것이 핵심**이다. 종전엔 실패 이유가 통째로 사라져
사장님이 *"1건 실패"* 라는 노란 알림만 보셨다.

### 생산가능 수량 — 손 계산과 대조

| | 정답 | 결과 |

| 자재A 100(60+40 두 창고)÷2=50 · 자재B 30÷5=6 | 6 | 🟢 6 |
| 자재 수 (창고 2개) | 2 | 🟢 2 |
| BOM 원가 | 450 | 🟢 450 |
| 자재 0개 BOM | 0 | 🟢 0 |
| 재고 행 없음 | 0 | 🟢 0 |

🔴 **창고 함정** — 단순 조인이었으면 자재 수 3, 원가 650 으로 부풀었다.
게이트 진위 확인: 창고합산을 단순조인으로 바꾸니 **G-68 이 FAIL**.

## 8. ⚠️ 이 검증이 **못 한 것** — 사장님 실측의 몫

🔴 **개발PC 정상은 검증이 아니다.** 아래는 화면에서 확인하셔야 한다.

| # | 무엇 |
|---|---|
| 1 | 상품마스터 배너에서 **자동발주 → 경고가 실제로 사라지는지** |
| 2 | 「자동 사슬」을 골랐을 때 **재고가 실제로 오르는지** |
| 3 | 반제품에 사슬을 걸면 **발주서만 만들어지고 이유가 보이는지** |
| 4 | 발주서 목록에 **자동발주서가 뜨고 「매입전환」이 되는지** |
| 5 | BOM 그리드의 **「단계」·「생산가능」 숫자가 현장 감각과 맞는지** |
| 6 | 안내 문구가 **읽어서 이해되는지** (개발용어 없이) |

   실제로 셋이 동시에 뜨면 화면 위쪽이 길어진다. *"스크롤 없이 한 화면"* 원칙과 부딪히는지는
   **실제 데이터로 보셔야 판정된다.** 지금은 각각 한 줄로 압축해 뒀다.
