## 1. 검증 방법 — 구현자 하네스를 쓰지 않은 독립 경로

구현자 게이트는 **맨손 `ApplicationBuilder`** 위에서 돌고, 그 안에서 `IHttpContextAccessor` 를 대역한다(개발명세서 §4-1 3항 자백). 그래서 「필터가 실물 호스트에서도 붙는가」는 그 하네스로 증명되지 않는다.

그래서 **실물 프로세스**를 세워 직접 쟀다.

| 축 | 어떻게 |
|---|---|
| 서버 | 실물 `dotnet run --project src/HitPan.Backoffice.API --no-build --no-launch-profile` · Kestrel · `ASPNETCORE_URLS=http://127.0.0.1:539x` |
| DB | 격리 시험 DB `hitpan_trgtest` (출하 DDL `installer/backoffice/*.sql` + 게이트 시드) · **운영 무접촉(#39)** |
| 토큰 | 실물 `POST /api/backoffice/auth/{admin,reseller}/login` 이 발급한 진짜 JWT (손으로 만든 `ClaimsPrincipal` 0) |
| 요청 | `curl` — HTTP 상태코드 + **응답 본문**으로 차단 주체를 가른다(가드 「대리점 계정은…」 / CSV 「권한이 없습니다 (필요 권한: …)」 / 컨트롤러 `Forbid()` 빈 본문) |

> 🔴 구현자 주의 2건 모두 확인됨. `HITPAN_BO_JWT_SECRET` 는 발급(`BackofficeAuthController.cs:162`)·검증(`Program.cs:69`) **양쪽**에서 `Jwt:Secret` 을 이긴다 ⇒ 실물 프로세스는 같은 변수를 쓰므로 401 오진 없음. 전체 회귀는 **환경변수 없이** 돌려 기준 숫자를 냈고, 작10 게이트는 `--filter` 로만 돌렸다.

## 3. 🔴 머지 전 필수 교정 — 4건

### ① 🔴 본사 갈래의 **역할 하향이 전혀 강제되지 않는다** (D-4 자백보다 넓다)

실측(실물 호스트 · 같은 토큰 · 재로그인 0회):

| 조작 | `tenants` | `owner/bo-users` | `resellers` |
|---|---|---|---|
| 기준 (`role=super_admin`) | 200 | 200 | — |
| `UPDATE platform_admins SET role='readonly'` | **200** | **200** | **200** |
| `is_active=0` (대조군) | **403** | — | — |

즉 **비활성·소속변경·삭제는 본사에도 즉시 먹히지만, 역할 하향(ⓐ)은 본사 갈래에서 효과가 0**이다.

근거(전수 grep):
- `src/HitPan.Backoffice.API/Filters/BoAccessGuard.cs:126` — `Items[EffectiveRoleItemKey] = effective` 로 **쓰기만** 한다. 이 키를 **읽는 곳은 레포 전체에 0곳**(`src` 전수 grep 결과 선언 41행·쓰기 126행뿐).
- `src/HitPan.Backoffice.API/Filters/BoPermissionAttribute.cs:37` — `var role = user.FindFirst("role")?.Value` ⇒ **토큰 raw 역할**을 읽는다. 하향된 DB 값을 보지 않는다.
- `BoAccessGuard.cs:129-132` — 본사 갈래는 `effective` 를 계산한 직후 **그냥 `return`** 한다(등급 검사 없음).

⇒ 개발명세서 §2 흐름도의 「유효역할 = 좁은 쪽 ← **하향 즉시**」와 설계 §3-3 의 「좁은 쪽 우선」은 **대리점 사다리에만** 참이다. D-4 는 「제품 라우트가 관리자 전용이 아니다」로 좁게 적었지만, 실제로는 **본사 갈래에 하향 강제 경로 자체가 없다.**

대리점 쪽도 제품 라우트에서는 효과 0으로 실측됐다: `role` 을 `reseller_admin`→`reseller_readonly` 로 낮춘 뒤 포털 3개 **200**(최소등급이 기본값 `reseller_user` 이므로 **정당**하지만, 그래서 **하향 차단을 보여 주는 제품 라우트가 0개**다 — G-8ⓐ 과녁이 시험 어셈블리 `BoGateLadderController` 라는 자백이 맞다).

**교정**: (a) 설계·명세서에서 「하향 즉시」의 적용 범위를 **대리점 사다리 한정**으로 정정 — 지금 문장은 다음 사람에게 「본사도 즉시 끊긴다」로 읽힌다(사실이 아니다). (b) `BoPermissionAttribute` 가 `EffectiveRoleItemKey` 를 읽도록 하는 것을 **2차수 과녁으로 명시 등재**(지금 고치면 CSV 어휘와 충돌 — 교정 ⑦ 참조).

⇒ 같은 파일 **20줄 주석** 「익명 입구는 이 필터 소관이 아니다」와, G-1 이 세운 **익명 버킷 26개**가 런타임에서 지켜지지 않는다. G-1(`BackofficeRoleScopeGateTests.cs:58-99`)은 **표식만** 보고 버킷을 세며, 「익명 버킷이 익명으로 동작하는가」는 **재지 않는다**.

**교정**: 가드가 `[AllowAnonymous]`(`IAllowAnonymous` 메타데이터)를 **먼저 보고 면제**하도록 하고, G-1 에 **동작 대조군 1줄**(익명 라우트 1개 + 대리점 토큰 = 가드 메시지 아님)을 추가. 코드를 안 고치려면 최소한 주석과 설계에서 「익명 소관 아님」을 삭제하고 **「토큰이 실려 오면 익명 라우트도 닫힌다」를 명시**해야 한다 — 지금 글자는 사실과 반대다.

### ③ 🔴 ② 인자 덮어쓰기 — **양성 증거가 0**이고, 안 덮는 입력 경로가 많다

- `[ResellerScoped]` 가 붙은 액션은 `ResellerPortalController` **3개뿐**이고, 그 3개의 매개변수는 `[FromQuery] string? status` 와 `CancellationToken` **뿐**이다(`resellerId` 파라미터 0). ⇒ `ResellerScopeArgumentFilter` 가 **실제로 덮어쓰는 자리가 0개**다.
- 실측: 대리점A 가 `?resellerId=<B의 id>` · `?reseller_id=<B의 id>` 를 붙여도 **200 + 고객사A1·A2 만**. 값이 「덮였다」가 아니라 **읽는 코드가 없다**.

  - 라우트 세그먼트 · 헤더 · `[FromForm]` · 배열·중첩 객체 · 다른 이름(`rid`·`targetResellerId`)

### ④ 🔴 게이트가 **DB 없이 조용히 초록**이다

**교정**: `DbGateEnvironment` 가 로컬에서 DisplayName 또는 출력에 `[SKIP]` 를 남기게 하고(선례 있음), PM 이 **CI `db-gate` 잡 초록(SHA 로 확인) 없이는 머지 금지**로 못 박는다. 이 건이 닫히기 전까지 M-1 은 미확인이다.

- ※※ 시험 DB 에 없는 표/미설정 자격증명 — 토큰 없음에서도 같은 500.

**판정**: 본사 정상 경로 **14라우트 200** · 대리점 정상 경로 **포털 3개 200 + 자기 행만** · 익명 경로는 토큰 없이 전부 종전대로. ⇒ **「전부 막는 필터」가 아니다.** 단 **익명 경로는 토큰이 실리면 대리점에만 닫힌다**(교정 ②) — 이것이 유일하게 확인된 과차단이다.

## 5. 라이브 판독의 실패 모드 — **fail-closed 실측 확인**

같은 인스턴스에서 **전후 대조**로 쟀다(대조군 없는 측정은 쓰지 않았다).

| 단계 | 대리점 `toss/config` | 대리점 `tenants` | 대리점 포털 | 본사 `tenants` |
|---|---|---|---|---|
| 대조군 — 판독 대상 표 있음 | 403 「대리점 계정은…」 | 403 「대리점 계정은…」 | 200 | **200** |
| 처리군 — `DROP TABLE reseller_accounts`(판독 쿼리 1146) | **403** 「권한을 확인하지 못했습니다」 | **403** 동일 | **403** 동일 | **403** 동일 |

서버 로그: `fail: HitPan.Backoffice.API.Filters.BoAccessGuard[0] [BoAccessGuard] 라이브 계정 판독 실패 sub=… path=/api/backoffice/tenants — fail-closed 403` + 스택.

⇒ **열리지 않는다. 닫힌다.** 근거 `BoAccessGuard.cs:80-86`(`catch (Exception)` → `LogError` 1줄 + `Deny`). #15 빈 catch 0 확인(`BoAccessGuard.cs:80` · `BoLiveAccountReader.cs:172-178` · `BoPermissionService.cs:114`).

운영 영향으로 기록할 것: 이제 **모든 인증 요청이 DB 왕복 1회에 의존**한다. DB 가 느리면 요청이 명령 타임아웃까지 끌리고, DB 가 끊기면 **사장님까지 전면 403**(503 아님)이 된다. 설계 의도대로이나 운영 설명서에 적어 둘 사실이다.

### ⚠️ 재현 실패 1건 — 전역 가드가 한 인스턴스에서 돌지 않은 것으로 보인 관측
두 번째 실물 인스턴스에서 대리점 토큰이 `toss/config`·`admin/serial-locks` 에서 **200** 이었고, `api/backoffice/tenants` 는 **CSV 메시지**로 403 이었으며 `[BoAccessGuard]` 로그가 **0줄**이었다(= 가드가 실행되지 않았다는 모양). 세 번째 인스턴스에 **같은 라우트로 대조군을 먼저 세우고** 다시 재니 정상이었고(위 표), 두 번째 시도로는 **재현하지 못했다.** ⇒ **원인 미확정 · ⚠️미확인으로 남긴다**(「진단도 실측 전엔 가설이다」).

그 관측과 무관하게 **분명한 문제 하나**: 가드가 **통과할 때 로그를 0줄** 남기므로, 「전역 필터가 실제로 붙어 있는가」를 운영에서 확인할 신호가 **0**이다. `Program.cs:30-31` 주석이 「이 두 줄을 지우면 36엔드포인트가 다시 열린다」고 적은 그 상태가 **조용하다**. 기동 시 1줄(가드 등록 + `[ResellerScoped]` 액션 수) 로그를 권한다.
