### 🟢 반증 4의 대조군 — 이게 결정적이다

**같은 데이터**에 옛 검사와 새 검사를 나란히 돌렸다.

| 검사 | 결과 |
|---|---|
| 옛 검사 (매입만) | **0** ← 매출반품 기표누락을 **못 본다** |
| 새 검사 (매출반품 포함) | **1** ← **잡는다** |

**대조군이 없으면 「1이 나왔다」는 그냥 숫자다.** 0 vs 1 이 나와야 봉합이 증명된다.

## 4. 코드리뷰 발견

| # | 등급 | 위치 | 내용 | 봉합 |

| 1 | **P2** | 개발명세서 §4 | 🔴 **문서가 틀렸다** — 명세서취소 `source_id` 를 `'{deliveryId}:cancel'` 로 적었으나 **회계 호출은 순수 `deliveryId`** 를 넘긴다 | ✅ **봉합됨** |

### 🔴 P2 상세 — 받아쓰기였다

`:cancel` 접미는 **`MonthlySummaryGuard` 멱등키** 얘기다(`SalesService.cs:1217` 주석).
회계 분개 호출(`1197`행)은 **`deliveryId` 를 그대로** 넘긴다.
⇒ **주석을 읽고 다른 서브시스템의 규칙을 회계에 옮겨 적었다.**

**코드는 안전한가**: 🟢 안전하다. 다만 **근거가 문서에 적힌 것과 다르다.**
`delivery_id`·`return_id` 는 **둘 다 `Guid.NewGuid()`**(신규·마이그 경로 모두) ⇒ 충돌 실질 0.

**왜 P0/P1 이 아닌가**: 현재 코드에 두 id 가 같아지는 경로가 **없다.** 실피해 0.
**왜 그냥 넘기지 않았나**: 이 문서가 **다음 세션의 근거**가 된다(헌법 #42).
틀린 근거를 남기면 **ID 발급 방식을 바꿀 때 아무도 이 전제가 깨지는 걸 모른다.**

⇒ 개발명세서 §4 를 정정하고 **한계를 명시**하도록 요구 → **봉합 확인.**
