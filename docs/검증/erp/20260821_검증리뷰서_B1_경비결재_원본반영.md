## 3. 🔴 E — 검증 중 발견한 별건 2건

### E-1. 경리 등록분은 **반려 사유를 알 수 없다**

`expenses` 표에 `reject_reason` **컬럼 자체가 없다.**
`ExpensesPage.razor` 도 상태만 보여주고 사유 칸이 없다.

⇒ 경리가 올린 경비가 반려되면 **왜 반려됐는지 알 방법이 없다.**
`hr_expense_requests` 는 사유가 남는다 — **같은 경비인데 경로에 따라 정보가 갈린다.**

> ⚠️ **이번 봉합이 만든 것이 아니다.** 기존 `ApproveExpenseAsync` 도 동일.
> 다만 B1 로 결재 경로가 **실제로 살아나면서** 이 구멍이 처음으로 사람 눈에 닿게 된다.

### E-2. 🔴 기존 코드가 **승인자 자리에 테넌트 ID** 를 넣는다

```
FinanceService.ApproveExpenseAsync:
  UPDATE hr_expense_requests SET ... approved_by = @TenantId ...
                                                  ^^^^^^^^^ 사람이 아니라 회사
```

⇒ **누가 승인했는지 기록이 처음부터 틀렸다.** 감사 추적이 안 된다.

🟢 **B1 봉합은 `Who = employeeId` 로 올바르다.** 두 경로가 서로 다른 값을 넣는 상태가 됐다.

**⇒ 별건 P1 로 이월**(§6).

## 7. 검증팀 의견

🟢 **잘한 것**
- 정본을 고르지 않고 **두 표 모두 시도** — 사장님 *"케바케"* 와 정확히 맞물린다

- [3-V] 에 뚫린 것을 **감추지 않고 병렬이슈로 남겼다**
- 남은 한계(문자열 검사)를 **"고쳤다"로 적지 않았다**

🔴 **지적**
- *"대조실험 성립"* 보고가 **성급했다.** 블록 통째 제거는 가장 약한 반증이고,
  그것으로 "게이트가 진짜" 라고 보고한 것이 [3-V] 에 뒤집혔다.
  **제거 방식이 실제 회귀 방식과 같은지**를 먼저 물었어야 한다.
