## 0-0. 🔴🔴 최상위 시험항목 — 이것이 첫 번째다

> 사장님 (2026-08-10): *"사업자등록증 OCR로 **자동등록으로 써지도록** 하는게 사장의 의도야"*

⭐ **이것은 검증 기능이 아니라 입력 기능이다.** 검증팀이 시험 순서를 바꾼다.

```
고객이 하는 일:  사업자등록증 한 장 올린다.  ← 끝
시스템:  상호 · 사업자번호 · 대표자명 · 주소 · 우편번호 · 업태 · 종목 · 법인등록번호
        → 기본사업장정보에 자동으로 써진다
```

### T-0 · 🔴 등록증 한 장으로 칸이 실제로 채워지는가 (**최우선 · 1번 항목**)

| | |
|---|---|
| **목적** | 이 작업 전체의 **존재 이유**. 고객이 손으로 치는 칸이 몇 개 남는가를 센다 |
| **사전조건** | 백지 Sandbox · **손대지 않은 신규 가입** · 실제 사업자등록증 1장 |
| **절차** | ① 가입 화면에서 등록증 **한 장만** 올린다 ② **그 외에 사람이 타이핑한 값이 없는 상태**로 가입을 완료한다 ③ 설치 후 ERP → 계정관리 → 회사정보 → 기본사업장정보를 연다 ④ **8개 잠금 대상 필드**(§0-3 표)가 채워졌는지 **하나씩 센다** ⑤ 각 값을 등록증 원본과 대조한다 |
| **합격기준** | 🔴 **8개 필드 전부 채워져 있고 원본과 일치한다.** 사람이 타이핑해야 하는 잠금 대상 필드 = **0개** |
| **불합격** | **P0** — 등록증을 올렸는데 **여전히 손으로 쳐야 하면 이 작업은 아무것도 안 한 것**이다. 검증만 통과하고 입력이 안 되면 사장님 의도 정면 위반 |

> 🔴 **판정 주의** — "OCR 이 인증을 통과했다"는 **합격 근거가 아니다.**
> `is_match=true` 만 반환하고 값이 안 써지면 **불합격**이다. 대조는 부산물이고, **입력이 본체**다.
> ⇒ §2 의 T-1~T-5(진위 시험)는 전부 **T-0 을 전제로** 한다. T-0 이 불합격이면 나머지는 판정 의미가 없다.

### 0-3. 필드 분류 — 전부 잠그는 것이 아니다 (PRD §0-2)

| 갈래 | 필드 | 시험 기준 |
|---|---|---|
| 🔒 **잠금 대상** (등록증에 있음) | 상호 · 사업자번호 · 대표자명 · 주소 · 우편번호 · 업태 · 종목 · 법인등록번호 (**8개**) | **편집 가능하면 P0** (임의등록 경로) |
| ⬜ **열림 대상** (등록증에 없음) | 전화번호 · 팩스 · 홈페이지 · 이메일 · 종사업장번호 | **잠기면 P1** (고객이 연락처를 못 넣는다) |
| 🟡 **보완 입력** | 상세주소 | 등록증 주소에 포함되기도 하므로 **열림**. §3 M-10 참조 |

⚠️ **양방향 시험이다.** "다 잠기면 안전"이 아니다. 열림 대상이 잠기면 고객이 업무를 못 한다.
검증팀은 **잠금 과잉도 결함으로 판정**한다.

## 0. 이 시험계획의 전제 — 검증팀이 먼저 못 박는 것

### 0-1. 검증의 목적

> **"됐다"를 확인하는 게 아니라 "안 되는 경우를 찾는다."**

구현팀이 "동작합니다"라고 보고한 것을 재현하는 작업은 검증이 아니다.
정상 경로는 구현팀이 이미 확인했다. 검증팀이 볼 것은 **정상 경로 밖**이다.

| 빌드 0/0 만으로 통과 | 빌드 0/0 **＋** 실동작 **＋** 독립반증 3관문 전부 |

> 이 조합에서 무너진다. 두 기능이 각각 옳은데 합쳐지면 고객이 갇힌다.

| | |
|---|---|
| **깨뜨릴 것** | OCR 이 **틀린 값을 읽게** 만든 뒤, 그 틀린 값이 **잠긴 채로** 저장되는지 본다 |
| **실패 시나리오** | 등록증 주소가 `○○시 ○○구 ○○로 123, 4층` 처럼 **상세주소를 포함**할 때, 파싱이 `주소=○○로 123, 4` / `상세=층` 으로 잘못 끊는다 → **틀린 주소가 잠긴 필드에 들어간다** → 고객이 스스로 못 고친다 → **본사 승인을 받아야 주소 한 줄을 고칠 수 있다** |
| **사전조건** | ⓐ 상세주소 포함 주소 ⓑ 긴 상호(괄호·영문 혼용, 예: `(주)○○테크놀로지코리아`) ⓒ 업태·종목이 **여러 줄**인 등록증 ⓓ 저화질·기울어진 스캔 ⓔ 구형 양식 |
| **절차** | ① 5종 각각으로 가입한다 ② ERP 기본사업장정보에 들어간 값을 **원본과 한 글자씩 대조**한다 ③ 틀린 값이 있으면 **고객이 그 자리에서 고칠 수 있는지** 시도한다 ④ 못 고치면 **복구 경로가 몇 단계인지** 센다 |
| **기대(정상)** | ⓐ 오독이 있으면 **가입 확정 전에 고객이 확인·정정할 기회**가 있다(PRD L-3 "오독 정정만") ⓑ 확정 후 오독이 발견돼도 **본사 승인 없이 풀 수 있는 경로**가 최소 1개 있다 |
| **🔴 이러면 불합격** | ⓐ 오독값이 **확인 화면 없이 바로 잠긴다** ⓑ 고객이 **주소 한 줄 고치려고 본사 승인 대기**를 해야 한다 |
| **등급** | **P0** — 5만 고객 규모에서 **CS 폭증**으로 직결된다. 잠금이 보안 장치가 아니라 **고객을 가두는 장치**가 된다 |

> ⚠️ **설계 검토 요청 사항** — 이 시험은 설계에 **"오독 정정 창"이 없으면 반드시 불합격**한다.
> PRD L-3 은 *"오독 정정만 허용"* 이라고 적었으나, **정정을 언제 어디서 하는지**가 정의되어 있지 않다.
> **가입 확정 전 확인 단계**가 설계에 없으면 구현 전에 추가돼야 한다.

## 7. 🔴 이 시험계획으로도 못 잡는 것 (정직하게)

> 검증의 한계를 적지 않으면, 통과가 **"안전하다"** 로 잘못 읽힌다.
> 아래는 **이 계획을 100% 통과해도 여전히 열려 있는 구멍**이다.

| # | 못 잡는 것 | 왜 못 잡나 | 그래서 어떻게 |
|---|---|---|---|
| 1 | **OCR 정확도의 실제 분포** | 시험은 몇 장으로 한다. 실제로는 스캔 품질·기울기·구형 등록증·수기 정정본이 5만 건 들어온다. **표본 몇 장 통과 ≠ 현장 통과.** M-10 은 오독을 **유발해** 보는 시험이지 **오독률을 측정하는 시험이 아니다** | 베타 대리점 실물 등록증 **최소 20종**(법인·개인·간이·구형 양식·팩스 사본 포함)으로 확대. 그전까지는 **정확도를 주장하지 않는다** |
| 1-1 | 🔴 **잠금과 오독률의 곱** | 잠금 대상 8필드 × 오독률이 곧 **본사 승인 대기 건수**다. 오독률 1%만 되어도 5만 고객이면 **500건 CS**. 이 계획은 그 수치를 산출하지 못한다 | 베타 20종 시험에서 **필드별 오독률**을 측정해 **잠금 범위를 재조정**할 근거로 삼는다. 오독이 잦은 필드는 잠금에서 빼는 판단이 필요할 수 있다 — **사장님 결재 사항** |
| 2 | **위조된 사업자등록증** | OCR 은 글자를 읽을 뿐 **진위를 판정하지 않는다.** 포토샵으로 만든 등록증도 글자는 읽힌다 | 국세청 API 와 **교차 대조**가 최소 방어(T-3). 완전 차단은 이 설계로 불가 — **알려진 잔여 리스크로 사장님께 보고** |
| 3 | **본사 내부자에 의한 평문 유출** | 접근 로그는 **사후 추적**이지 사전 차단이 아니다. 권한자가 정당하게 조회하면 로그도 정상으로 남는다 | 최소권한·분리보관은 설계 사항. 검증으로 증명 불가 — 보안상무 영역 |
| 4 | **장기 잔존 데이터** | T-14 는 시험 시점에 확인한다. **3개월 뒤 백업 로테이션·스냅샷·로그 아카이브**에서 되살아나는 것은 못 본다 | 파기 정책에 **보존주기 전체**를 포함시키고 **분기 재점검** 항목으로 등록 |
| 5 | **기존 가입자 소급**(PRD §9-3 / R5) | 이 계획은 **신규 가입만** 시험한다. `test1` 등 기존 계정은 해시만 있어 대상 밖 | **베타 청구 전 별도 시험 필요.** 지금 통과해도 기존 고객에게는 세금계산서를 못 끊는다 |
| 6 | **레거시 5만 고객 전환** | 대상 시스템이 다르다(공영정보(주) 팩스 보관본) | 별도 결재·별도 시험계획 (작업지시서 §3-1 말미) |
