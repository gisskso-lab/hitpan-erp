## 🎯 MigrationProgressService 분석 (백엔드 측)

### 설계 평가
- **Singleton + Concurrent Store + Hub Push 병행** = 폴링 fallback 가능 ✅
- 헌법 #15·#16·#19·#25 모두 정합 ✅
- 10분 후 자동 정리 (재접속·디버깅 여유) ✅

### 흐름
```
1. RunTableStepAsync 잡 시작
   → cb("running", 0, 0, null) 호출
   → MigrationController progressCallback이 _progress.UpdateAsync 호출
   → _store에 snapshot 저장 + Hub Push "ProgressUpdate"

2. 잡 완료
   → cb("completed", N행, elapsed, null) 호출
   → _store snapshot 갱신 + Hub Push "ProgressUpdate"

3. 전체 잡 완료
   → CompleteJobAsync("completed")
   → Hub Push "JobCompleted"
   → 10분 후 _store 정리
```

### 진범 #22 진짜 본질 재박제
```
TIME LINE
00:00  Frontend: POST /start → 즉시 JobId 반환 (~500ms)
00:00  Backend: 잡 시작 (즉시) → warehouse_migration RunTableStepAsync 실행
00:00.197  Backend: warehouse_migration "completed" → _store 저장 + Hub Push 시도
       (그러나 Frontend 아직 Hub 연결 안 됨 → Push 실패 → catch LogWarning)

00:00.5  Frontend: SignalR Hub 연결 시작
00:01.5  Frontend: SubscribeJob(jobId) → Hub Group 가입
       (이미 warehouse_migration "completed" Push는 1.3초 전에 끝남)
       (Group 가입 전 Push는 수신 못 함 — SignalR 설계상 정상)

이후: pyojun_master 등은 Hub 구독 후라 정상 수신.
```

## 🚨 진범 #43 (확정) — 폴링 fallback 미사용

### 현재 Frontend 코드 (MdbMigration.razor)
- SignalR Hub 신호 의존 100%
- 폴링 fallback 0건 (status API는 JobCompleted 시점에만 1회 호출)
