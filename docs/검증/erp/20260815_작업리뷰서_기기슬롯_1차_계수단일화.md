## ① 최종 판정

### 🔴 조건부 승인 — **R-1 하나 때문이다**

**승인할 수 없는 이유는 딱 하나다.** 신규 설치 고객에게 이 작업의 **핵심 성과가 도달하지 않는다.**

이 작업은 요금 한도를 코드에서 DB 설정으로 꺼내는 일(헌법 #11)이었다. 그런데 출하 DDL 이
`schema_migrations` 에 `('DB-104','clean-ddl',1)` 을 **성공으로 미리 기록**하면서 **시드 INSERT 는 넣지 않는다.**
`MigrationRunner` 는 `success=1` 이면 건너뛰므로, **신규 고객의 정책 표는 영원히 비어 있고
`FallbackLimits`(코드 상수)로만 돈다.** 설정화가 신규 고객에게 무력이다.

🔴 이것은 [[project_fixed_vs_delivered_gap]] 의 **재발**이다 — 코드는 맞는데 **고객에게 안 간다.**
빌드 0/0 · 시험 504 · ddl-smoke PASS · 반증 13/13 이 **전부 통과했는데도** 이 결함은 드러나지 않았다.
**개발PC 는 멀쩡하다.** 신규 설치를 실제로 해봐야만 보인다.

### 그러나 나머지는 견고하다 — 반려가 아니라 조건부 승인인 이유

부정적 판정만 내리는 것은 검증이 아니므로 함께 기록한다. 아래는 **내가 직접 반증해서 확인한** 것들이다.

- **3관문 전부 실측 통과** — 빌드 0/0, 시험 504건, ddl-smoke PASS (③)
- **G-7 은 진짜 게이트다** — 복제 SQL 을 실제로 되살렸더니 **FAIL 했다**(독립반증 1)
- **G-8 은 진짜 게이트다** — 순수 판정부를 시험이 직접 부른다. 글자 검사가 아니다
- **핵심 설계 판단(hardware_id NULL 허용)이 옳다** — 반대로 만들면 실제로 깨지는 것을 실측했다(독립반증 2)
- **코드리뷰 6건 중 2건은 재현되지 않았다** — R-2·R-3 (④). 근거 없는 지적을 반려 사유로 쓰지 않았다
- **병렬검증 지적 중 2건은 사실과 달랐다** — 충돌 ①·② (⑤)

⇒ **R-1 만 봉합하면 통과다.** 나머지는 2차로 넘겨도 과금 사고가 나지 않는다(등급은 ④·⑥에).

## ② 무엇을 어떻게 검증했는가 (SoD)

나는 **만든 사람도 설계한 사람도 아니다.** "됐다" 를 확인하지 않고 **"안 되는 경우"** 를 찾았다.

| 방법 | 내용 |
|---|---|
| 3관문 직접 실행 | 개발팀 보고를 인용하지 않고 **내 손으로 돌렸다**(③) |
| 격리 DB 실측 | 신규 설치를 **실제로 재현**했다. 운영 demo·NCP **무접촉**(헌법 #39) |
| 코드 돌연변이 | 고친 것을 **되돌려 게이트가 정말 FAIL 하는지** 확인(독립반증 1) |
| 대조 실험 | 위험한 설계로 바꾼 DDL 과 현재 DDL 을 **같은 시나리오로 나란히** 돌렸다(독립반증 2) |
| 게이트의 게이트 | 게이트가 **글자만 보는 가짜인지** 검사(독립반증 2·3) |

**⚠️ 검증 중 발생한 사고와 그 처리 (숨기지 않고 기록한다)**
G-7 반증 중 `git checkout` 으로 워킹트리를 되돌리는 순간 **개발팀 미커밋 작업 380줄이 날아갔다.**
돌연변이 주입 **전에 백업**(`/tmp/tds.bak`)을 떠 둔 덕에 즉시 복원했다.
복원 후 **빌드 0/0 · 시험 504 · diffstat 380줄 일치 · 돌연변이 잔존 0** 을 확인했다.
🔴 [[feedback_check_before_write]] 가 경고한 자리다 — **미커밋 상태에서 검증하면 검증이 작업을 지운다.**
이후 반증은 **repo 를 건드리지 않고 사본으로만** 했다.

### R-1 (blocking) — 🔴 **재현됨. 이것이 유일한 반려 사유다**

**재현 방법** — 격리 DB 에 출하 DDL 을 그대로 import(= 신규 고객 설치와 동일)

```
$ mysql -u root -e "CREATE DATABASE hitpan_verify_dpark ..."
$ mysql -u root hitpan_verify_dpark < installer/hitpan_db_clean.sql
$ mysql -u root hitpan_verify_dpark -e "SELECT ..."
q                          v
policy 표 행수              0     ← 🔴 비어 있다
DB-104 success 로 기록됨?    1     ← 🔴 이미 "성공" 으로 기록
DB-103 success 로 기록됨?    1
local_subscription 행수      0
```

**왜 영원한가** — `MigrationRunner.cs:91-92`
```sql
SELECT migration_id FROM schema_migrations WHERE success = 1;
```
`:104` 에서 `applied.Contains(mig.MigrationId)` 이면 **건너뛴다.**
회사를 만든 뒤에도 DB-104 는 `success=1` 이라 **다시 돌지 않는다.** 실측으로 확인했다 —
테넌트를 넣고 다시 조회해도 정책 표는 **0행 그대로**였다.

**고객이 겪는 것**
- 정책 표 0행 → `LoadSlotPolicyAsync` 가 빈 사전 반환 → `Pick` 이 전부 `FallbackLimits` 로 떨어짐
- ⇒ **한도는 여전히 코드 상수로 결정된다.** 헌법 #11 이 요구한 설정화가 신규 고객에게 **무력**
- ⇒ 사장님이 "베이직을 6대로" 하시려면 **여전히 재배포가 필요하다.** 이 작업의 목적 자체가 미달

⚠️ **정상 동작하는 부분은 정확히 적는다** — 한도가 **사라지지는 않는다.** `FallbackLimits` 가
종전 숫자와 동일해 **로그인은 죽지 않고 과금 숫자도 종전과 같다.** 즉 **회귀는 아니고 미달성**이다.
`enterprise` 정정은 `FallbackLimits` 에도 들어가 있어 **그 효과만은 신규 고객에게도 간다.**

🔴 **이것은 이 작업이 처음 만든 결함이 아니다 — 선례가 이미 같은 상태다.**
`DB-96`(노무 기준값)도 동일한 `CROSS JOIN local_subscription` 방식이고,
신규 설치 DB 에서 `labor_policy_settings` 도 **0행**임을 실측했다.
⇒ **레포 전체의 구조적 패턴**이다. 개발팀 명세서 ⑦-2 도 이 한계를 **스스로 밝혔다**(정직하다).
다만 **"2차 과제"로 미루는 것에 동의하지 않는다** — 미루면 이 차수의 성과가 신규 고객에게 0 이다.

✅ **봉합할 자리가 이미 있고, 선례도 있다** — `CompanyBootstrapProvisioner.cs:354`
그 파일은 회사 생성 시점에 **`labor_policy_settings` 를 이미 시드하고 있다**(`INSERT … WHERE NOT EXISTS`).
**같은 자리에 `device_slot_policy_settings` 시드를 추가하면 끝난다.** 새 구조가 필요 없다.

### R-2 — ⚠️ **부분 재현 (P2). 코드리뷰가 말한 "배포 즉시 발생" 은 사실이 아니다**

### R-3 — ✅ **재현 안 됨. 실측으로 반증했다**

코드리뷰 주장: `ExecuteScalarAsync<int>` 가 0행이면 `InvalidCastException` → 쿼터 조회 500.

**실제 Dapper + MySqlConnector 로 돌려서 확인했다** (격리 DB, 존재하지 않는 테넌트):
```
R-3 결과: 예외 없음, 값 = 0
tier(0행) = (null)
GetLimitsAsync 튜플(0행): tier=(null), extra=0
```
⇒ **예외가 나지 않는다.** `ExecuteScalarAsync<int>` 는 0행에서 `default(int)` = 0 을 돌려준다.
**이 지적은 근거가 없다.** 반려 사유로 쓰지 않는다.

**두 번째 주장(한 행을 세 번 나눠 읽어 값이 어긋날 수 있다)** — 구조는 사실이다
(`GetQuotaAsync` 가 `local_subscription` 을 `GetLimitsAsync`·tier·extra 로 **3회** 조회).
그러나 이 경로는 **화면 표시 전용이고 한도 비교를 하지 않는다**(코드 주석대로 확인).
⇒ 과금 판정에 영향 없음. **P3(정리 대상)** 으로만 남긴다.

### R-5 — 🔴 **재현됨 (P1). 헌법 #15 취지 위반이 맞다**

`TenantDeviceService.cs` `LoadSlotPolicyAsync` catch:
```csharp
System.Diagnostics.Debug.WriteLine(
```

`Debug.WriteLine` 은 `[Conditional("DEBUG")]` 이라 **Release 빌드에서 호출 자체가 제거된다.**

**왜 위험한가** — 이 catch 는 **요금 한도가 설정에서 안 읽혔다는 신호**를 삼킨다.
R-1 과 겹치면 **정책 표가 비어 있어도 아무도 모른 채 `FallbackLimits` 로 조용히 돈다.**

⚠️ 봉합 시 주의: 이 클래스에는 **`ILogger` 가 주입돼 있지 않다**(생성자는 `IDbConnection`·`IAuditService`·`IConfiguration?`).
생성자 변경은 DI 등록에 영향을 주므로 **작업지시서에 명시하고 가야 한다.**

**반증 1 — 위험한 변경을 넣어도 두 문자열은 살아남는다**
```
$ sed "s/`hardware_id` varchar(128) DEFAULT NULL/`hardware_id` varchar(128) NOT NULL DEFAULT ''/" ...
'`hardware_id`' 출현: 2 / 'uq_tenant_hardware' 출현: 1
3735:  `hardware_id` varchar(128) NOT NULL DEFAULT '' COMMENT '...'
```
⇒ **게이트는 초록불이다.**

**반증 2 — 그 DDL 로 설치하면 실제로 깨진다** (같은 시나리오, 나란히 대조)
```
[변형 DDL] 기기 2대 등록 시도
ERROR 1062 (23000): Duplicate entry 'T-1-' for key 'uq_tenant_hardware'   ← 🔴 2번째 기기부터 죽는다

[현재 DDL] 같은 시나리오
등록성공_대수  3                                                          ← ✅ 정상
```

⇒ 코드리뷰 지적대로 **`hardware_id` 가 NULL 이어야만 안전한데 그것을 보장하는 장치가 없다.**
지금 DDL 은 **옳다.** 위험한 것은 **미래의 변경을 아무도 못 막는다**는 점이다.

🟢 **함께 기록할 것 — 개발팀의 설계 판단 자체는 옳았다.**
명세서 ③-갈림 5 의 *"NOT NULL DEFAULT '' 로 했다면 기존 고객의 두 번째 기기부터 INSERT 가 죽는다"*
는 주장을 내가 **독립적으로 재현해 사실임을 확인했다.** 판단은 맞고, **그 판단을 지키는 게이트가 없을 뿐**이다.

| 6 | 업데이트 경로로 **마이그가 고객에게 도달**하나 | 게시 미실시 | 🔴 [[project_migration_real_path]]·[[project_fixed_vs_delivered_gap]] — **"고쳤나" 가 아니라 "갔나"** |

## ⑩ 검증자 소견

개발팀 작업의 **품질 자체는 높다.** 계수 8곳을 2곳으로 모으면서 **호출부마다 다른 비교식을 그대로 둔 것**
(QR 은 모바일만·갱신 경로는 한도 미검사)은 리팩터링에서 가장 틀리기 쉬운 자리를 **정확히 피한 판단**이고,
G-7·G-8 을 **동작 게이트로 만든 것**은 8/15 메신저 사고를 실제로 학습한 결과다. 내가 되돌려 보니 **진짜 FAIL 했다.**
`hardware_id` NULL 허용 판단도 **내가 독립적으로 재현해 옳음을 확인**했다.

🔴 **그럼에도 통과시킬 수 없는 이유는 하나다 — 이 작업의 목적이 신규 고객에게 도달하지 않는다.**
요금 한도를 설정으로 꺼내는 것이 이 차수의 존재 이유인데, 신규 설치 고객은 **여전히 코드 상수로 돈다.**
그리고 그 사실을 **알려줄 로그마저 Release 에서 사라진다**(R-5).

**가장 무거운 교훈은 게이트에 관한 것이다.**
개발팀은 "반증 13/13" 을 보고했고 **그 13건은 진짜였다**(내가 하나를 직접 되돌려 확인했다).
그런데 **13건 전부를 통과하고도 P0 가 남았다.** 게이트가 **없는 자리**에 결함이 있었기 때문이다.
🔴 **통과한 게이트의 개수는 안전의 증거가 아니다.** 작업지시서 §5 가 *"통과하는 게이트는 증거가 아니다"* 라고
경고했는데, 그 경고는 **"가짜 게이트"** 뿐 아니라 **"게이트가 없는 자리"** 에도 걸린다.

> 사장님: *"과금에 연결된거니 더욱 촘촘하게 신경쓰도록"*
> ⇒ **C-1 을 봉합하고 백지 환경에서 눈으로 확인한 뒤 재검증을 요청한다.**
> C-1 은 봉합할 자리(`CompanyBootstrapProvisioner`)와 선례가 **이미 있어 크지 않은 일**이다.
