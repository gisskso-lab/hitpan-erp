## 2. 반증 시도한 것과 결과

### 2-1. 🔴 반증 성공 — §19-1 근거 3 「잠그는 행 집합이 같다」는 **틀렸다**

PM 주장(작지 §19-1 근거 3 · 명세서 §8-2):
> `idx_pay_partner`(partner=Y) 가 잠그는 행 집합 = `idx_pay_tenant_partner`(tenant=X, partner=Y) 가 잠그는 집합과 **같다**.

**반증 근거 ①** — 대상 문장 `LegacyBalanceMatching.PayableMatchedLegacyLockedSql` (src/HitPan.Application/Services/LegacyBalanceMatching.cs:285) 는
`LOCK IN SHARE MODE` 이고, 게이트가 쓰는 인스턴스는 **위험 33406 = `binlog_format=STATEMENT` → RR(REPEATABLE READ)** 이다.
RR 의 잠금 읽기는 **일치하는 행**만 잠그지 않는다 — **훑은 인덱스 레코드 + 그 다음 간극(next-key)** 을 잠근다.
「일치하는 행 집합」과 「잠기는 인덱스 구간」은 **다른 것**이다. PM 의 근거 3 은 이 둘을 같은 것으로 놓았다.

**반증 근거 ②** — 간극의 이웃이 다르다.
- `idx_pay_tenant_partner(tenant_id, partner_id)` 의 정렬은 `(X,Y)` → 마지막 레코드 다음 간극의 이웃은 **같은 회사 X 의 다음 거래처**다.
- `idx_pay_partner(partner_id)` 의 정렬은 `(Y)` **전역** → 마지막 레코드 다음 간극의 이웃은 **아무 회사의 아무 거래처**다.
  `payments.partner_id` 는 `varchar(36)` GUID(installer/hitpan_db_clean.sql `payments`) 라 실데이터에서 회사끼리 **뒤섞여 정렬된다.**
  즉 A 회사가 L3 을 쥐는 동안 **B 회사의 `payments` INSERT 가 그 간극에 걸린다.**

**반증 근거 ③ — 팀 자신의 실측이 이미 이렇게 적었다.**
개발명세서 §3-4 · 게이트 주석 `SeedGapSeparatorAsync` XML doc:
> 「RR 의 next-key 잠금은 스캔한 마지막 레코드 **다음 간극**까지 잠그므로, 인덱스 순서상 **바로 옆**에 끼어드는 INSERT 는 거래처가 달라도 막힌다.」

「거래처가 달라도 막힌다」를 `idx_pay_partner` 위에서 읽으면 **「회사가 달라도 막힌다」**가 된다.
같은 문서가 한쪽에서는 「인접 거래처는 막힌다」를 사실로 적고, 다른 쪽에서는 「잠그는 집합이 같다」를 안전 근거로 썼다. **둘은 같이 못 선다.**

**영향 범위(정직하게)**: 데이터 유출은 아니다 — L3 의 `WHERE` 에 `tenant_id = @TenantId` 가 있어 **읽히는 값은 여전히 한 회사**다(#2 위반 아님).
넘어가는 것은 **잠금 구간**이다. 실기(고객 PC)는 보통 회사 1개(PM 이 잰 `hitpan_v4_a` 도 회사 1개)라 현장 체감 위험은 낮다.
그러나 게이트가 **「남의 회사 행이 들어올 수 없다」는 문장으로 초록을 준다.** 문장이 사실보다 넓다.

### 2-2. 🔴 반증 성공 — 새 규칙의 조건 ③ 은 **절대 발동하지 않는다** (감시자 0)

③ 은 `SELECT COUNT(*) FROM (SELECT col FROM tbl GROUP BY col HAVING COUNT(DISTINCT tenant_id) > 1) x` 로 센다.
이 값이 0 이 아니려면 **한 `partner_id` 값이 두 회사에 걸린 행**이 시험 DB 에 있어야 한다. 그런데 —

- 시드 `SeedNoiseRowsAsync` 는 거래처 id 를 `CONCAT('noise-', @T8, '-', LPAD(seq,4,'0'))` 로 만든다 → **회사 8자리가 id 안에 들어간다 = 회사별로 값이 원천 분리**.
- `PA`·`PB` 는 `NewTenantAsync` 가 회사마다 새로 만든다.
- 두 번째 회사(`other`)도 **같은 함수**로 심는다.

⇒ **두 회사에 걸친 값은 구조상 만들어질 수 없다.** ③ 은 언제나 0 이다.
게다가 PM 의 무력화 5건 중 **③ 을 겨눈 것이 없다** — ⑤(`FORCE INDEX(idx_pay_type)`)는 `payment_type` 이 어느 표의 단일칸 PK 도 아니라 **② 에서** 떨어진다(`installer/hitpan_db_clean.sql` 전 표 PK 목록 확인 — `payment_type` PK 없음).
명세서 §8-2 의 「데이터가 규칙을 깨면 **여기서 먼저 빨간불이 난다**」는 **한 번도 확인되지 않은 문장**이다.

이것은 [4] 1차가 잡은 **병렬이슈60(「아무도 안 잰다」)** 과 같은 모양이 그 봉합물 안에서 재발한 것이다.

### 2-3. 🟡 반증 성공(부분) — 「통과하면 안 되는데 통과」하는 경로가 있다

`IndexSafety.MeasureAsync` 의 ② 질의에는 **`TABLE_NAME IN @T` 필터가 없다**(①·③ 에는 있다).
즉 `_globallyUniqueId` 는 **DB 전체의 단일칸 PK 「칸 이름」 집합**이다. 출하 DDL 실측:

- `PRIMARY KEY (id)` **9개 표** · `line_id` 5 · `log_id` 5 · `history_id` 3 · `setting_id` 3 … 총 ~110개 이름.

규칙 ② 는 「**어느 표든** 그 이름이 단일칸 PK 면 통과」다. 즉 **참조관계(FK)가 아니라 이름 일치**로 면제한다.
`payments.partner_id` 에 FK 가 없다는 사실(명세서 §8-2 가 스스로 인정)을 ③ 으로 메운다고 했는데, **그 ③ 이 §2-2 대로 죽어 있다.**
⇒ 지금 ② 는 사실상 **이름 기반 면제 목록**이다. PM 이 지운 `TenantPrefixExempt`(손으로 적은 이름 3개)가 **자동 생성되는 이름 110개짜리 목록**으로 바뀐 것에 가깝다.
「손으로 적은 목록을 지웠다」는 명세서 §8-2 의 서술은 **형태만 맞고 성질은 덜 바뀌었다.**

### 2-4. ✅ 반증 실패(= PM 이 맞다) — `RealTableOf` 실패 시 빨간불

`RealTableOf` 는 못 되돌리면 **별칭을 그대로** 돌려주고, `IndexSafety._firstCol` 은 `(실제표명, 인덱스명)` 으로만 채워져 있어
`TryGetValue` 가 실패 → `why="판정 불가라 통과시키지 않는다"` → `return false` → **Assert 빨간불**. 코드 경로 확인 완료(파일 1298~1310 · 1370 부근).
파생표(`<derived2>`)·UNION 도 같은 길로 빨간불이 된다(`AliasesOf` 정규식이 `FROM (` 를 안 잡으므로 매핑 없음).
다만 **그 앞 단언**(`type != ALL && Key is not null`)이 먼저 걸릴 가능성이 높아, 「파생표면 안전판정에서 빨간불」은 **경로상 옳지만 실측된 적은 없다.**
현재 8문장에 파생표·UNION 은 없다(`LegacyBalanceMatching` L1~L5 · `CollectionService` D1-a/b/c 전수 확인).

### 2-5. ✅ 반증 실패(= PM 이 맞다) — G-RC15 문구 앵커는 **자기참조가 아니다**

## 3. 발견한 문제 (심각도 순)

### 🔴 F-1. 안전판정의 **근거 문장이 사실보다 넓다** (갭 잠금)

- **어디가 어떻게 틀렸나**: 작지 §19-1 근거 3 · 명세서 §8-2 · 게이트 실패 메시지(`RcSafePathGateTests.cs` AssertPlans)
  「고른 인덱스 {Key} 의 범위에 **남의 회사 행**이 들어올 수 있다」 / 「잠그는 행 집합이 같다」.
  RR next-key 잠금에서 **일치 행 집합은 같아도 잠기는 간극은 다르다**(§2-1 근거 ①②③). 같은 문서 §3-4 가 정반대를 적어 놨다.
- **어떻게 고쳐야 하나** (제품·DDL 손대지 않는다):
  1. §19-1 근거 3 을 **삭제하거나** 「**일치 행 집합**은 같다. **간극 잠금 범위는 같지 않다** — 전역 정렬이라 이웃이 남의 회사일 수 있다」로 정정.
  2. 게이트의 실패/통과 문구를 **`IndexSafety` 가 실제로 재는 것**으로 좁힌다 —
     「이 인덱스로 **읽히는 값**은 한 회사 안이다(간극 잠금은 이 단언의 범위 밖 — 설계 §12-6 · 명세서 §3-4)」.
  3. `DB-124` 마이그·출하 DDL 주석의 `idx_pay_partner(테넌트를 넘어간다)` 와 **정면 충돌**한다(아래 F-4) — 한쪽으로 통일.

### 🔴 F-2. 규칙 ③ 은 **자백 불가능한 단언** (감시자 0 재발)

- **어디가 어떻게 틀렸나**: `IndexSafety.MeasureAsync` 의 ③ COUNT. 시드가 `partner_id` 에 **회사 8자리를 접두**로 넣어 값이 원천 분리된다(§2-2).
  0 이 아닌 값이 나올 경로가 없고, 무력화 5건 중 ③ 을 겨눈 것도 없다. 명세서 §8-2 「데이터가 규칙을 깨면 여기서 먼저 빨간불」은 **미검증 서술**.
- **어떻게 고쳐야 하나**: 게이트 파일 안에서 끝난다 —
  **음성 대조군 1건**을 추가한다: 회사 A 의 `partner_id` 를 그대로 쓰는 `payments` 행 1건을 회사 B 로 심고
  `IndexSafety.MeasureAsync` → `IsSafe("payments","idx_pay_partner")` 가 **false** 가 되는 것을 확인(심은 뒤 즉시 삭제).
  그 대조군을 **무력화 표 ⑥** 으로 명세서에 싣는다. 대조군을 못 넣을 사정이면 ③ 을 **「지금 데이터에 대한 관찰」로 격하**해 적고, 안전 근거에서 뺀다.

### 🟡 F-3. ② 의 `information_schema` 질의만 **표 필터가 빠졌다**

- **어디가 어떻게 틀렸나**: ①(`STATISTICS`)·tenant 보유 질의(`COLUMNS`)에는 `TABLE_NAME IN @T` 가 있는데 ②(`KEY_COLUMN_USAGE`)에만 없다.
  결과적으로 DB 전체 ~110개 이름(`id` 9표 포함)이 면제 후보가 된다 = **참조관계가 아니라 이름 일치로 면제**(§2-3).
- **어떻게 고쳐야 하나**: ② 를 `(표, 칸)` 쌍으로 좁히거나, 최소한 **실제 FK**(`KEY_COLUMN_USAGE.REFERENCED_TABLE_NAME`)가 있는 칸을 **우선 경로**로 두고
  FK 가 없는 칸(`payments.partner_id`)만 ③ 로 내려보낸다. 그러면 ③ 의 책임이 좁아져 F-2 대조군도 겨누기 쉬워진다.

  (무력화 ③ DROP 은 `type=ALL`·rows 상한으로 잡히므로 감시자 0 은 아니다.)
- **어떻게**: DisplayName 을 실제 단언(「테넌트 밖 값이 안 섞이는 인덱스 + rows 상한 + 10배 불변」)으로 고치고,
  `RequiredKey` 는 **지우거나** 「참고: S3 0단계 실측 계획」이라고 용도를 명시(§3-3 이 흔들린다고 한 축이므로 단언 복원은 권하지 않는다).

### 🟡 F-7. **완료 정의 ㉤ 가 보고되지 않았다**

- 작지 §19-5 ㉤ = 「안전 33306 회귀 40 + 마이그·DDL 274 + 빌드 0/0」. 명세서 §8-6 은 **빌드 · 위험 33406 15사례 · 제품 무변경** 셋만 적었다.
  **안전 33306 회귀 40 · 마이그/DDL 274 는 결과가 없고, §8-7 에도 자백이 없다.** 중단분 §5 에서는 「🔴 안 돌렸다」로 정직하게 적었던 항목이다.
- **어떻게**: PM 이 도는 중인 전체 회귀가 끝나면 그 숫자를 §8-6 에 채우거나, 못 돌렸으면 §8-7 에 한 줄.

### 🟢 F-8 (참고). `IsSafe` 의 ③ 은 **없으면 통과**한다 — 잠재적 fail-open

`_spanning.TryGetValue(...)` 가 실패하면 그냥 통과한다. `_spanning` 은 **`tenant_id` 칸이 있는 표**에만 채워지므로,
`tenant_id` 없는 표가 `ExplainTables` 에 들어오는 날 ③ 이 조용히 건너뛰어진다.
현재 7개 표 전부 `tenant_id` 보유(출하 DDL 확인) → **지금은 미발현**. `_firstCol` 미발견과 같이 **fail-closed** 로 맞추면 좋다.

## 5. 내가 **못 잰 것** (정직하게)

1. **시험을 한 번도 안 돌렸다** — PM 이 33306·33406 에서 회귀 중이라 금지. 따라서 명세서 §8-1·§8-4·§8-6 의 **모든 숫자**
   (「14사례 통과 13」·「15사례 전부 초록」·무력화 5건 FAIL·빌드 0/0)는 **PM 의 보고를 받아쓴 것이고 내가 재현하지 않았다.**
   특히 **무력화 5건은 [4] 가 독립 재현해야 하는 항목**이다 — 이번 리뷰서는 그 재현을 **포함하지 않는다.**
2. **빌드를 안 돌렸다** — #19(경고 0)은 미검증. 정적으로 읽었을 때 컴파일 오류가 보이지는 않았다(그 이상은 말 못 한다).
3. **F-1 의 갭 잠금을 실측으로 못 보였다** — 「회사 B 가 회사 A 의 L3 간극에 막힌다」를 직접 재려면 두 회사 동시 세션이 필요하고 DB 를 써야 한다.
   내 근거는 ① InnoDB RR next-key 의 정의 ② 인덱스 정렬 차이 ③ **팀 자신의 §3-4 실측**이다. 논증이지 실측이 아니다.
4. **F-2 의 「③ 은 항상 0」도 실측이 아니다** — 시드 코드(`SeedNoiseRowsAsync` · `NewTenantAsync`)를 읽고 내린 결론이다.
   COUNT 를 직접 돌려 0 임을 확인하지 않았다(그건 오히려 0 이 나오는 것이 내 주장이라 반증력이 없다 — 필요한 것은 **음성 대조군**이다).
5. **CI 의 STATEMENT 스텝 실동작** — 명세서 §8-7 4번 그대로. PR 첫 실행이 최종 확인이다.
6. **`hitpan_v4_a` 실물규모 사본 · C-1a ALTER 4.76초** 등 S3 실측치는 이번 범위 밖이라 재확인 안 했다.
7. **파생표·UNION 에서 빨간불이 나는지** 는 경로만 읽었고 실행으로 확인 못 했다(§2-4).
