## 2. ⚠️ G-32 계열은 "반환값 판정"이 남아 있다 — 그러나 이번엔 무해

G-32 · G-32-b · G-32-c · G-33-c 는 여전히 **함수 반환값(`bool`)**을 본다.
§9 개발팀 교훈표 기준으로는 ❌ 계열이다. **왜 이번엔 통과로 보는가**를 적는다:

- `IsDeviceAllowedAsync` 는 **반환값이 곧 동작 그 자체**다 — 이 함수는 표를 바꾸지 않고 판정만 한다.
  G-31 이 가짜였던 이유는 *"반환값과 결함이 무관"* 해서였다. 여기서는 **반환값이 결함의 정의**다.
- 실측 근거: PM 이 `AND is_main_pc = 1` 을 빼자 **G-32 계열 4건이 FAIL** 했다(개발명세서 ③, PM 실측).

🔴 **다만 한계가 있다** — 이 4개는 **서비스 함수만** 태운다. 실제로 문을 여는 **미들웨어**는 안 태운다(§3-B).

## 3. 🔴 발견 — 게이트가 안 지키는 자리

### 3-A. 🔴 **[신규 발견] 폐기(`revoked`) 기기가 옛 인증키로 되살아나는 것을 아무 게이트도 안 지킨다**

**실측**:
```
VerifyAuthKeyAsync 의  if (status == "revoked") return null;  → if (false) return null;
⇒ 결과: 실패 0, 통과 12 — 초록불
```

**왜 위험한가** — 독립 반증 DP-1 로 확인했다:
```
[DP-1] 폐기 후 status=revoked / 폐기 후 auth_key_hash = **ALIVE(살아있음)**
```
🔴 **`RevokeAsync` 는 `auth_key_hash` 를 지우지 않는다.** (`TenantDeviceService.cs:519-527` — `status`·`revoked_at`·`revoked_reason` 만 UPDATE)
⇒ 폐기된 기기의 **옛 키가 표에 그대로 남는다.** 그 키를 막는 것은 **오직 저 `revoked` 가드 한 줄**이고,
   그 한 줄을 지켜보는 게이트가 **0개**다.

⚠️ **지금 코드는 정상 동작한다**(DP-1 에서 `verifyReturn=null`, 상태 `revoked` 유지). **결함이 아니라 게이트 사각이다.**
🔴 그러나 이 자리는 **1회용(1-8)과 정면으로 얽힌다** — 다음 사람이 *"1회용이니 소거는 verify 가 한다"* 고 읽고
   저 가드를 정리하면 **대표가 폐기한 기기가 옛 키로 부활**한다. 소거 책임이 두 함수에 갈려 있어 **갈릴 자리**다.

### 3-B. 🔴 **[개발명세서 §7-1b 재확인] 미들웨어 쪽 1-2 를 게이트가 안 태운다**

코드리뷰로 재확인했다 — `DeviceAuthMiddleware.cs:156-165` 가 **자기 SQL 을 갖는다**:
```sql
SELECT COUNT(*) FROM tenant_devices
 WHERE tenant_id = @Tid AND device_id = @Did
   AND status = 'approved' AND is_main_pc = 1
```
`TenantDeviceService.IsDeviceAllowedAsync` 와 **같은 조건을 두 번 적었다.**
🔴 **실제로 문을 여는 것은 미들웨어**인데 게이트 4개는 전부 서비스만 태운다.
개발팀이 **주석으로 위험을 예고해 놓고 게이트는 안 만들었다**(§7-1b 자인). **주석은 게이트가 아니다.**

### 3-C. 🔴 **[신규 발견] `RejectAsync` 에 메인PC 가드가 없다 — `RevokeAsync` 에는 있다**

| 함수 | 메인PC 보호 | 근거 |
|---|---|---|
| `RevokeAsync` | ✅ **있다** — `is_main_pc` 면 `InvalidOperationException` (`:502-517`) | 20260810작3 |
| `RejectAsync` | 🔴 **없다** — 조건은 `AND status='pending'` 뿐 (`:786-794`) | 1-4 신설 |

**메인PC 가 `pending` 일 수 있는가 — 있다.** `MainPcRegistrationService.cs:156-163` 이
**기존 줄을 `is_main_pc=1` 로 승격**시키는데 **`status` 는 안 건드린다.**
⇒ 직원이 신청해 만든 `pending` 줄이 그대로 메인PC 가 된다.

**실측 (격리 DB · 출하 DDL + DB-89 적용)**:
```
pending + is_main_pc=1  →  RejectAsync 의 SQL 그대로 실행
결과: status = 'rejected', is_main_pc = 1   ← 메인PC 가 거절 칸에 들어갔다
```

⚠️ **지금은 P0 가 아니다** — `rejected` 는 재신청 경로가 있어(1-4) 다음 접속에 `pending` 으로 돌아온다.
🔴 **그러나 `revoked` 에는 있는 메인PC 구제가 `rejected` 에는 없다**(`:267` 은 `status == "revoked" && !isMainPc`).
   `rejected` 상태의 메인PC 는 **`RegisterOrRefreshAsync` 를 거쳐야만** 풀린다 —
   즉 **관문을 통과하기 전 화면에서 대표가 자기 메인PC 를 거절하면 한 바퀴 더 돌아야 한다.**
   8/16 P0(*대표가 자기 화면에서 막힘*)와 **같은 계통**이고, 방어가 한 겹 얇다.

### 3-D. ⚠️ **[선행 결함 · 작1 무관] DB-89 메인PC 보호 트리거가 무력하다**

검증 중 확인했다. 작1 이 만든 문제가 **아니지만**, 3-C 의 안전망이 없다는 뜻이라 함께 적는다.

출하 DDL + `DB-89_main_pc_db_guard.sql` 적용 후 실측:
```
is_main_pc=1 인 줄에 UPDATE status='revoked'  →  결과: revoked  (트리거가 되돌리지 않음)
```
- `installer/hitpan_db_clean.sql` 에 **`CREATE TRIGGER` 가 0건** — 신규 설치엔 트리거 자체가 없다.
- `uq_tenant_main_pc` UNIQUE 는 **살아서 동작한다**(1062 실측) — 메인PC 1대 보장은 유효.

⇒ **메인PC 보호는 사실상 애플리케이션 코드에만 있다.** 그래서 3-C 의 `RejectAsync` 누락이 더 중요하다.

### 5-1. DP-5 판정 — **결함 아님, 그러나 문서에 없다**

`ReissueAuthKeyAsync` 는 `revoked` 만 막고 **`pending` 은 허용**한다(`:742-743`).
⇒ 대표가 대기 중 기기에 [인증키 재발급] 을 누르면 **승인 버튼을 안 눌러도** 그 키로 `approved` 가 된다.

🔴 **입구가 대표계정 전용**(`DeviceController.cs:350-352` `account_type != "tenant_admin"` → `Forbid`)이므로
**권한 상승이 아니다.** 대표가 키를 알려주는 행위 = 승인 의사로 보는 것이 자연스럽다.
⚠️ 다만 **작지서·개발명세서 어디에도 이 동작이 적혀 있지 않다.** *"재발급은 승인과 같은 효력"* 이라는
사실이 문서에 없으면 다음 사람이 **승인 우회 결함으로 오인해 막을** 수 있고, 그러면 1-8 의 구제 기능이 죽는다.

## 7. 🔴 "이대로 사장님 PC 에 게시해도 되는가"

### **아니다. 지금 이 워킹트리는 게시 불가다.**

🔴 **그러나 사유가 작1 이 아니다. 이것이 이번 검증의 가장 중요한 발견이다.**

검증 도중 `TenantDeviceService.cs` 가 **14:33 에 외부에서 수정**됐다. 확인 결과:
- **작2(모바일 QR·종류변경) 작업이 같은 파일을 동시에 수술 중**이다 (`20260818작2` 표지 11곳 · `knownDeviceId` 신설)

## 8. 🔴 이 각도로 찾았으나 못 찾은 것 — 남은 사각지대

> "문제 없음"을 결론으로 내지 않는다. **어디를 못 봤는지** 적는다.

| 사각지대 | 왜 못 봤나 |
|---|---|
| **관문 뒤 업무 API 0건** | xUnit 으로 불가. `@if (!_gateActive)` 구조는 코드리뷰로 옳다고 판단했으나 **논증이지 증거가 아니다.** Playwright 네트워크 탭 실측 필요 |
| **origin 격리(localStorage)** | 브라우저 동작 — 재현 수단 없음 |
| **미들웨어 실동작** | `DeviceAuthMiddleware` 를 태우는 시험 인프라가 없다. SQL 대조는 **눈으로만** 했다(3-B) |
| **관문 fail-open** | `CheckGateAsync` 의 `catch` 가 통신 실패 시 **관문을 안 켠다**(`initialProbe` 에서 예외 나면 `_gateActive=false` 로 본문이 그려진다). 미들웨어가 서버측에서 막으므로 **자료 유출은 없다**고 판단했으나, **화면이 잠깐 열리는 모양**은 실측 안 했다 |
| **기존 고객 `approved` + `is_main_pc=0` 기기** | 실제 고객 DB 가 없어 **분포를 모른다.** 1-2 가 그런 기기의 헤더 경로를 새로 막는다 — 인증키 경로는 살아 있으나 **키를 잃은 기기 수**를 아무도 모른다 |
| **작2 와의 상호작용** | 작2 가 수술 중이라 **합쳐진 상태의 게이트를 못 돌렸다**(§7-2) |
