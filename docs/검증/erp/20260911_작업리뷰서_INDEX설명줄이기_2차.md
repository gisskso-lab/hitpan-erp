## 3. 독립 반증 — 가장 중요한 발견 (P1)

개발명세서 §1 의 링크 개수 일치("44=44" 등)는 **원본과 현재본이 서로 같은 파싱 실수를 똑같이 반복했을 때도 똑같이 나온다.** 그래서 "개수가 맞다"를 믿지 않고, 원본 5개 파일 전체를 "한 물리줄에 문서링크 시작 패턴(`[YYYYMMDD..._....md](`)이 2개 이상 있는 줄"로 독립 재스캔했다.

**결과: `docs/설계/erp/INDEX.md` 원본 27번째 줄에서 1건 적발.** 이 줄은 "20260821_설계_근태축_경비통합_옵션모듈화.md" 행이 `| 2026-08-21 |` 로 끝나자마자 **줄바꿈 없이** "20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md" 행이 바로 이어 붙어 있었다(원본 자체의 오래된 결함으로 추정 — 이번 작2 가 만든 게 아니다). 개발명세서 §3 이 문서화한 표 모양 이상 3종(칸 늘어난 줄·두 줄에 걸친 줄·빈 줄 뒤 머리 없는 줄) 중 **이 "한 줄에 행 2개 붙음"은 없다** — 그래서 스크립트도, 내 1차 자동 대조도 이 줄을 "행 1개"로만 셌다.

결과: **`docs/설계/erp/INDEX.md` 현재본에 "20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md" 가 전혀 없다** — grep 0건. 실제 문서 파일은 살아 있고(`docs/설계/erp/20260821_설계_그룹웨어결재_범위확정_ERP분리_회계기표.md`), 이력 파일에도 원문이 있어 **데이터 자체는 안 없어졌지만, INDEX 로는 못 찾는다.**

5개 파일 전체를 같은 방법(물리줄당 링크 시작 패턴 2개 이상) + 더 넓은 패턴(문서링크 열기 정규식 2개 이상)으로 재스캔 — **다른 곳에서는 0건**, 이 1줄이 유일하다. 상세 재현·봉합 방향 → **병렬이슈22** (`docs/검증/병렬이슈/20260911_병렬이슈22_한줄에_붙은_설계문서_1건이_INDEX에서_증발.md`).
