# 1. T1 — 502 봉합 (`4136c8b`)

## 1-1. 지시서 관문 2 — "화면에 F5 를 권하는 문구 0건"

**✅ 통과.**

`grep "F5"` 전수 결과(`src/HitPan.Web/Components`·`Pages`·`Layout`) 잔존 11건은 **전부 주석**이다.
고객이 읽는 마크업에 F5 는 0건이다.

| 위치 | 성격 |
|---|---|
| `UpdateProgressOverlay.razor:12,14,48,49,51,83,89,91,143,189,199` | 주석·XML doc — 화면 출력 없음 |
| `UpdateConsentGate.razor:53` | 주석 |

교체된 실제 마크업 (`UpdateProgressOverlay.razor:56-60`):
```razor
@if (_showManualHint)
{
    <div class="hp-upd-hint">조금 더 걸리고 있습니다</div>
    <button class="hp-upd-btn hp-upd-btn-quiet" @onclick="RetryAsync">다시 확인</button>
}
```

⭐ **설계 판단 자체는 옳다.** 지시서 §1-3 R4(*"시간이 아니라 상태로 판정"*)를 실제로 이행했다.
시간 상수를 늘리는 대신 **확인 후 진입** 경로 하나로 통일한 것은 재발을 구조적으로 줄인다.

## 1-2. 🔴 D-1 — `_stalled` 분기가 폴링 중복은 막지만, **죽은 폴링을 되살리지 못한다** (P1)

지시받은 반증 항목이다. **가능하다. 실재하는 경로다.**

### 근거

`UpdateProgressOverlay.razor:256-262` — `WatchAsync` 의 마지막 catch:
```csharp
catch (Exception ex)
{
    Console.Error.WriteLine("[UpdateProgressOverlay] " + ex.GetType().Name + ": " + ex.Message);
    _showManualHint = true;
    StateHasChanged();
}
```

이 catch 는 **`_stalled` 를 세우지 않는다.** 그런데 `_showManualHint = true` 는 세운다.
즉 이 시점의 상태는 정확히 이렇다.

| 상태값 | 값 | 의미 |
|---|---|---|
| `_stalled` | **false** | "폴링이 살아 있다" 고 주장 |
| `_showManualHint` | **true** | `[다시 확인]` 버튼이 화면에 보인다 |
| 실제 `WatchAsync` | **종료됨** | catch 를 지나 메서드가 끝났다 — 폴링은 죽었다 |

이 상태에서 고객이 `[다시 확인]` 을 누르면 `RetryAsync`(`:150-175`)가 이렇게 흐른다.

```
:152  live = await TryGetLiveVersionAsync(...)   → 아직 안 떴으면 null
:153  if (live is not null) → 거짓, 진입 안 함
:161  if (!_stalled)  → _stalled 는 false 이므로 **참**
:165      return;     ← 🔴 아무것도 하지 않고 끝난다
```

`:163-164` 주석은 *"폴링이 살아 있다. 아무것도 바꾸지 않고 그대로 기다린다"* 라고 적혀 있으나,
**이 경로에서는 폴링이 살아 있지 않다.** 주석의 전제가 이 한 경우에 성립하지 않는다.

### 결과 (고객이 겪는 것)

- 화면은 `조금 더 걸리고 있습니다` + `[다시 확인]` 을 계속 보여준다
- 버튼을 눌러도 **화면이 아무 반응도 하지 않는다** (StateHasChanged 조차 안 부른다)
- 폴링이 죽었으므로 **히트판이 살아나도 자동 복귀가 영영 안 된다**
- 10분 `_stalled` 경로도 `WatchAsync` 안에 있으므로 **도달하지 않는다** — 빠져나갈 길이 닫힌다

⚠️ 이것은 지시서가 없애려던 상황과 **동형**이다. 종전 사고는 "F5 를 눌러 502 를 봤다"였고,
이 결함은 "버튼을 눌러도 아무 일이 없다"다. 둘 다 **고객이 화면에서 못 빠져나온다.**
`:196-200` 주석 자신이 *"영원히 도는 것은 502 보다 나쁘다"* 라고 적어 둔 그 상황이다.

### 재현

1. 업데이트 [예] → 오버레이 진입
2. `WatchAsync` 루프 안에서 `OperationCanceledException` 이 아닌 예외를 발생시킨다
   (예: `Nav.NavigateTo` 실패, `StateHasChanged` 가 폐기된 렌더트리에서 던지는 경우,
   `Task.Delay` 외 지점의 예기치 않은 JS interop 예외)
3. 브라우저 콘솔에 `[UpdateProgressOverlay] …` 1줄이 찍히고 버튼이 뜬다
4. `[다시 확인]` 을 누른다 → **아무 반응 없음** (히트판이 아직 안 떴을 때)

### 발생 확률에 대한 정직한 기록

`TryGetLiveVersionAsync`(`:279-302`)가 **자체 catch-all 로 모든 예외를 삼키고 null 을 돌려주므로**
(`:296-301`), 폴링 루프에서 예외가 새어나올 자리는 좁다. **드문 경로다.**

그러나 **드문 것과 없는 것은 다르다.** 그리고 그 catch 블록은 **누군가 의도적으로 만들어 둔 것**이다
— 즉 설계자 자신이 "예외가 날 수 있다"고 인정한 자리다. 인정해 둔 자리에 대해
`_stalled` 가 거짓을 말하게 된 것이 이 결함의 본질이다.

⭐ **이 결함은 이번 커밋이 만든 것이다.** 종전에는 `RetryAsync` 가 `_stalled` 를 보지 않고
항상 `WatchAsync` 를 다시 걸었으므로, 이 경우에도 폴링이 되살아났다.
`_stalled` 분기를 넣으면서 **되살리는 경로가 닫혔다.** 회귀다.

### ⚠️ 되짚음 — 지시서 §3 실동작 판정과의 관계

지시서 §3 은 *"[다시 확인] 을 아직 안 떴을 때 눌러도 502 가 안 뜨는가"* 를 묻는다.
**502 는 안 뜬다 — 그 판정은 통과한다.** 그러나 "502 가 안 뜬다"가 "고객이 빠져나간다"는 아니다.
판정 기준이 502 하나만 보고 있어 이 결함을 못 걸러낸다. **판정 기준 자체의 구멍**으로 함께 기록한다.

## 1-3. 🟡 D-2 — `_showManualHint` 이중 관리 (P2)

`WatchAsync` 는 힌트 노출 여부를 **지역변수 `hintShown`**(`:180`)으로 관리하고,
화면은 **필드 `_showManualHint`**(`:114`)를 본다. 두 값이 별개다.

`RetryAsync` 의 `_stalled=true` 경로(`:168-174`)는 `_showManualHint = true` 를 유지한 채
`WatchAsync` 를 새로 건다. 새 `WatchAsync` 의 `hintShown` 은 `false` 로 시작하므로,
**90초 뒤 다시 `_showManualHint = true` 를 세운다** — 이미 true 이므로 무해하다.

**실해는 없다.** 다만 10분 초과 후 재시도 시 버튼이 **즉시 다시 보인다**(90초를 안 기다린다).
사장님 의도(*"오래 걸리면 안내"*)와 어긋나지만, 이미 10분을 기다린 고객이므로
**오히려 합리적**일 수 있다. 판정: **결함 아님 · 설계 의도 확인만 권고.**

## 1-4. `TryGetLiveVersionAsync` 실패 시 — ✅ 회귀 없음

`:279-302` 를 전수로 읽었다. 실패 시 **예외를 던지지 않고 항상 `null`** 을 돌려준다.

| 실패 유형 | 처리 | 위치 |
|---|---|---|
| 502(터널)·503·403 | `IsSuccessStatusCode` 거짓 → `null` | `:290` |
| 연결 실패·타임아웃 | catch → `null` | `:296-301` |
| JSON 파싱 실패 | catch → `null` | `:296-301` |
| 빈 버전 문자열 | `IsNullOrWhiteSpace` → `null` | `:294` |

`RetryAsync` 에서 `null` 이면 `:153` 을 통과해 `:161` 분기로 간다 — **502 로 이어지는 경로가 없다.**
4초 타임아웃(`:284`)이 폴링 간격 5초보다 짧아 요청이 겹치지도 않는다.

⚠️ 다만 `RetryAsync` 는 `CancellationToken.None` 으로 부른다(`:152`).
컴포넌트가 `Dispose` 된 뒤 이 호출이 살아 있으면 4초간 매달리나,
`Nav.NavigateTo` 전에는 Dispose 되지 않으므로 **실해 없음.**

## 1-5. 10분 초과 경로(`_stalled=true`) — ✅ 회귀 없음

`WatchAsync:201-206` 이 `_stalled=true` 를 세우고 `return` 한다.
그 뒤 `[다시 확인]` → `RetryAsync:161` 의 `!_stalled` 가 **거짓** → `:168-174` 로 정상 진입해
`_stalled=false` 복원 + `_cts` 교체 + `WatchAsync` 재기동.

`_cts?.Cancel()` 을 먼저 부르므로(`:172`) **옛 토큰이 취소되고 새 토큰으로 하나만 돈다.**
✅ **종전 동작 그대로 보존된다. 이 경로의 회귀는 없다.**

## 1-6. 폴링 중복 방지가 실제로 되나 — ✅ 된다 (단, D-1 조건 제외)

`_stalled=false` 이고 폴링이 **정상적으로 살아 있는** 경우, `RetryAsync` 는 `:165` 에서
`return` 하므로 `WatchAsync` 를 추가로 걸지 않는다.
⇒ **폴링 중복도, 10분 상한 초기화도 일어나지 않는다.** 커밋 메시지의 주장은 사실이다.

**단, D-1(폴링이 이미 죽은 경우)에서는 "중복 방지"가 "복구 불가"로 뒤집힌다.**
같은 코드 한 줄이 정상 경로에서는 맞고 예외 경로에서는 틀리다.

## 1-7. T2 — 불가 판정의 타당성 ✅

지시서 §T2 의 *"Blazor 로 못 막는다"* 판정은 **근거가 정확하다.**
`installer/HitPan-Universal.iss:1134-1137`(ingress origin=API 5257, API 가 Blazor 서빙)에 비추어
API 가 꺼지면 Blazor 자산이 안 내려오므로 가로챌 코드가 브라우저에 없다.

⭐ **커밋 메시지가 *"줄인 것이지 없앤 것이 아니다"* 라고 적은 것을 높이 평가한다.**
거짓봉합으로 적지 않았다. 헌법 #24 준수.

## 2-2. 🔴 D-4 — 표식이 **의도한 형태로 만들어지지 않는다** (P0 · T4 미달성)

클라이언트에 이름을 넣는 후속 작업이 들어오는 순간, 메인PC 만 이름이 없는 기기가 된다.

### 🔴 더 큰 문제 — 이미 등록된 메인PC 에는 표식이 **영원히 안 붙는다**

`TenantDeviceService.RegisterOrRefreshAsync` 의 **기존 기기 갱신 경로**(`:135-143`):
```sql
UPDATE tenant_devices
SET last_seen_at = NOW(),
    ip_address   = @Ip,
    user_agent   = COALESCE(@Ua, user_agent)
WHERE device_id = @Id
```

🔴 **`device_name` 을 갱신하지 않는다.** `device_name` 이 쓰이는 곳은 **INSERT(`:191,205`) 단 한 곳**이다.

⇒ **표식은 "그 기기가 처음 등록되는 순간" 에만 붙는다.**

| 시나리오 | 표식 |
|---|---|
| 메인PC 가 이번 배포 후 **처음** 로그인 | ✅ 붙는다 |
| 메인PC 가 **과거에 클라이언트로 이미 등록**되어 있었다 | 🔴 **영원히 안 붙는다** |

그리고 후자가 **실제로 흔하다.** 지시받은 UNIQUE KEY 질문의 답이 여기 있다(§2-3).

## 2-3. UNIQUE KEY `uq_tenant_fp` — 중복 INSERT 로 터지나, 이름이 덮이나

**답: 터지지 않는다. 그리고 이름도 안 덮인다. 조용히 아무 일도 안 일어난다.**

### 근거

`installer/hitpan_db_clean.sql:3440`:
```sql
UNIQUE KEY `uq_tenant_fp` (`tenant_id`,`fingerprint`)
```

`TenantDeviceService.cs:115-122` 가 INSERT **전에** 같은 `(tenant_id, fingerprint)` 를 SELECT 하고,
있으면 `:124-148` 의 갱신 경로로 빠진다. **INSERT 까지 가지 않으므로 UNIQUE 위반 500 은 안 난다.**
⇒ 이 축은 ✅ **안전하다.**

### 🔴 그런데 그 안전장치가 D-4 를 고착시킨다

메인PC 가 이미 등록돼 있는지가 **지문으로 결정**되는데, 지문은 **접속 주소와 무관하다.**

`src/HitPan.Web/wwwroot/js/device-fingerprint.js:28-54` `_envSeed()` 는
`navigator.platform`·`language`·`hardwareConcurrency`·해상도·시간대·UA(버전 제거)만 쓴다.
**origin(localhost / 터널 도메인)이 씨앗에 들어가지 않는다.** 파일 주석 `:10-11` 이 명시한다:
> *"환경 특성은 origin·저장소와 무관하므로 주소가 달라도 같은 PC면 같은 씨앗이 나온다"*

⇒ **메인PC 가 과거에 터널 도메인으로 접속해 로그인한 적이 있으면**
(병렬이슈 §7-3 ①-역방향 시나리오 — *"실제로 일어난다"* 고 기록됨),
그 PC 는 **이미 같은 fingerprint 로 `tenant_devices` 에 들어가 있다.**

그 상태에서 이번 커밋이 배포되면:
1. 메인PC 가 localhost 로 로그인 → `isMainPcLoopback = true`
2. `BuildMainPcName` 이 `자료 보관 컴퓨터` 를 만든다
3. `RegisterOrRefreshAsync` 가 **기존 행을 찾는다**(같은 지문)
4. 갱신 경로로 빠져 **`device_name` 을 안 쓰고 버린다**(`:135-143`)
5. 🔴 **표식이 안 붙는다. 로그도 안 남는다. 아무도 모른다.**

⚠️ **T4 는 "새로 설치한 고객" 에게만 동작한다.** 기존 고객에게는 무효다.
사장님 오더 *"메인PC에 대한 표식 같은건 분명 있어야 한다"* 를 **기존 고객 대상으로 만족하지 못한다.**

## 2-4. 🔴 D-3 — 메인PC 가 슬롯에 막히면 **고객이 자료에 접근할 수단이 없다** (P0)

지시받은 항목 중 **가장 위험한 것**이다. 실측 결과 **우려가 맞다.**

### 경로 (코드로 확정)

```
AuthController.cs:103   RegisterOrRefreshAsync(...)
  └ TenantDeviceService.cs:175-178   pcUsed >= pcLimit
      └ return (false, "등록된 기기가 아닙니다. PC 기기 한도(5대)를 초과했습니다…")
AuthController.cs:106-110   if (!allowed) return Unauthorized(new { message = reason });
```

`AuthController.cs:106-110` 은 **`try` 블록 안에 있지만 `catch` 로 가지 않는다** — `return` 이다.
커밋 메시지도 이 점을 정확히 인지하고 있다(*"아래 catch 가 아니라 `allowed=false` 경로"*).

### 왜 P0 인가 — 메인PC 는 다른 PC 와 위상이 다르다

클라이언트PC 가 막히면 고객은 **메인PC 로 가서 기기를 폐기**하면 된다.
`DeviceManagePage.razor:112-118` 의 폐기 버튼이 그 탈출구다.

**그런데 막힌 것이 메인PC 라면 그 탈출구 자체가 잠긴다.**

| 시도 | 가능한가 | 근거 |
|---|---|---|
| 메인PC 에서 기기 폐기 | 🔴 **불가** — 로그인이 401 로 막혔다 | `AuthController.cs:109` |
| 다른 PC 에서 폐기 | ⚠️ 그 PC 도 이미 한도 안에 있어야 한다. 한도가 꽉 찼다는 것은 **여유 슬롯이 없다**는 뜻 | `TenantDeviceService.cs:175` |
| 기기 등록 없이 로그인 | 🔴 **불가** — 지문이 있으면 반드시 검사를 탄다 | `AuthController.cs:74` |
| 지문을 없애 우회 | ⚠️ `device-fingerprint.js:69-72` 가 **빈 문자열 반환을 금지**한다. 고객이 할 수 있는 조작이 아니다 | — |
| 본사에 전화 | ⚠️ 본사 DB 는 **다른 테이블**이다. 고객 로컬 `tenant_devices` 를 본사가 못 고친다 | 병렬이슈 §2-3 |

⇒ 🔴 **고객이 스스로 풀 수 있는 경로가 0개다.**
그리고 그 PC 는 **회사의 모든 자료를 가진 PC** 다(`DB_HOST=localhost`).

### 발생 조건 — "언젠가"가 아니라 "다음 로그인"이다

이번 변경으로 메인PC 가 **신규 기기 1건**으로 들어간다(D-4 §2-3 의 기존등록 케이스가 아닌 경우).
basic 티어 PC 한도는 **5**(`TenantDeviceService.cs:252`).

| 현재 approved PC 수 | 이번 배포 후 메인PC 로그인 |
|---|---|
| 0~4대 | ✅ 등록됨 (슬롯 1 소모) |
| **5대(한도 도달)** | 🔴 **401 거부 — 메인PC 잠김** |

⚠️ 병렬이슈 §7-1 이 **이 산술을 배포 전에 이미 경고했다.**
> *"이미 5대를 쓰던 고객은 다음 로그인에서 401 거부 … 고객은 100% 전화한다"*

커밋 메시지도 인지하고 있다:
> *"⚠️ 슬롯이 1개 줄어드는 효과가 있다. 한도를 꽉 채운 테넌트는 다음 로그인에서 거부될 수 있다."*

🔴 **인지한 것과 방어한 것은 다르다.** 코드에 방어가 **한 줄도 없다.**
경고를 주석과 커밋 메시지에만 적고 **그대로 게시하면, 적어 둔 사고가 그대로 일어난다.**

### ⭐ 검증팀 의견 — 사장님 결재의 범위

사장님 결재는 *"메인PC가 슬롯기기를 소모해야 정상이지"* 이며 **이 방향은 옳다.**
검증팀은 방향을 반대하지 않는다.

문제는 **"메인PC 가 슬롯을 쓴다"와 "메인PC 가 슬롯 때문에 잠긴다"가 다른 사안**이라는 점이다.
슬롯을 소모하되 **메인PC 만은 한도 초과 시에도 거부하지 않는다**(초과 상태로 등록하고 안내)는
설계가 가능하며, 그것이 사장님 결재를 위배하지도 않는다.
⚠️ **다만 이는 설계 변경이므로 검증팀이 정하지 않는다. 사장님·CTO 결재 사항으로 올린다.**

## 2-5. 🟠 D-5 — 메인PC 가 `revoked` 이면 영구 잠김 (P1)

`TenantDeviceService.cs:127-132`:
```csharp
if (status == "revoked")
{
    await LogDeniedAsync(...);
    return (false, "폐기된 기기입니다. 관리자에게 문의하세요.", null, false);
```

메인PC 가 과거에 클라이언트로 등록됐다가(§2-3) **관리자가 목록 정리 중 폐기**했다면,

D-3 보다 확률은 낮으나 **결과는 같다(메인PC 잠김) + 복구가 더 어렵다**(한도는 플랜 상향으로
풀 수 있지만 `revoked` 는 DB 를 직접 고쳐야 한다).

## 2-6. ✅ D-6 — `BuildMainPcName` 경계값: **결함 없다**

지시받은 경계값 전수다. **억지로 결함을 만들지 않는다 — 이 함수는 정확하다.**

`AuthController.cs:490-511` 기준.

| 입력 | 코드 경로 | 결과 | 판정 |
|---|---|---|---|
| `null` | `:492` `IsNullOrWhiteSpace` 참 | `자료 보관 컴퓨터` | ✅ NRE 없음 |
| `""` | `:492` 참 | `자료 보관 컴퓨터` | ✅ |
| `"   "`(공백만) | `:492` 참 (`WhiteSpace` 포함) | `자료 보관 컴퓨터` | ✅ 공백만 남는 사고 없음 |
| 이미 표식 포함 | `:499` `Contains(mark, Ordinal)` 참 → `:501` | 그대로 반환 | ✅ **반복 누적 없음** |
| 앞뒤 공백 | `:498` `Trim()` | 정리 후 처리 | ✅ |
| 정확히 89자 | `:507` `89 > 89` 거짓 | `89 + 11 = 100자` | ✅ **경계 정확** |
| 90자 | `:507` 참 → `:509` `[..89]` | `89 + 11 = 100자` | ✅ |
| 100자 초과 | `:509` 절단 | 항상 **정확히 100자** | ✅ |
| 표식이 잘린 상태(예: `… (자료 보관 컴`) | `:499` `Contains` 거짓 → 절단 후 재부착 | `… (자료 보관 컴 (자료 보관 컴퓨터)` | ⚠️ 아래 |

### 산술 검증 (문자 수 기준)

```
mark   = "자료 보관 컴퓨터"        → 8자
suffix = " (자료 보관 컴퓨터)"     → 11자  (공백1 + 괄호2 + 8)
room   = 100 - 11 = 89
결과 최대 = 89 + 11 = 100자  ≤ varchar(100)   ✅
```

🔴 **`device_name` 은 `varchar(100)`** 이며(`hitpan_db_clean.sql:3429`),
MariaDB 의 `varchar(N)` 은 **문자 수** 기준이다(바이트 아님).
`utf8mb4` 한글이 3바이트라 100자 = 최대 300바이트지만, **컬럼 정의가 문자 단위이므로 안전하다.**
⇒ **잘리지 않는다. 산술이 정확하다.** ✅

⚠️ 표기만 남기는 사항(결함 아님): 마지막 행 — 이름이 잘려 표식 일부만 남은 값이 다시 들어오면
표식이 두 번 보이는 문자열이 된다. 그러나 §2-3 에서 확인했듯 **`device_name` 은 UPDATE 되지 않으므로
이 값이 함수로 되돌아오는 경로가 없다.** 이론적 경우이며 실해 없음. **P2 도 아닌 참고 사항.**

⭐ **`Contains` 재부착 방지(`:499-502`)는 잘 만들어졌다.** 로그인마다 이름이 길어지는 사고를
사전에 막았다 — 이런 방어를 미리 넣은 것은 인정한다.

# 5. 🔴 게시해도 되는가

## 판정: **게시 불가 (조건부 분리 게시 가능)**

### 5-1. 전체 게시 — 🔴 **불가**

**`5599c31`(T3·T4)이 포함된 게시는 승인하지 않는다.**

사유는 하나로 충분하다:

> 🔴 **D-3 — 슬롯이 꽉 찬 테넌트의 메인PC 가 다음 로그인에서 잠기고,
> 그 PC 는 회사의 모든 자료를 가진 PC 이며, 고객이 스스로 풀 방법이 없다.**

⚠️ 이 사고는 **"고쳤다 ≠ 갔다"류의 전달 문제가 아니라, 갔을 때 터지는 문제**다.
게시가 성공할수록 피해가 커진다. **정상 게시가 곧 사고**인 구조다.

그리고 이 사고는 **예측되지 않은 것이 아니다.**
병렬이슈 §7-1 이 배포 전에 산술까지 적어 경고했고, 커밋 메시지도 같은 내용을 적었다.
**경고를 읽고, 이해하고, 코드에 반영하지 않은 채 게시하는 것**은 헌법 #33(의중 이해 후 코드)과
#25(안전하게)에 어긋난다.

### 5-2. 분리 게시 — 🟠 **조건부 가능**

`4136c8b`(T1) **단독** 게시는 가능하다. 조건이 있다.

| 조건 | 내용 |

| **C1** | **D-1 봉합 후** 게시. `RetryAsync` 가 `_stalled` 대신 **폴링 생존 여부**를 보게 하거나,<br>`WatchAsync` catch 에서 `_stalled = true` 를 함께 세운다 (⚠️ 방식은 개발팀·CTO 판단, 검증팀이 정하지 않는다) |

### 5-4. ⭐ 검증팀이 인정하는 것

반려 판정과 별개로, 이번 작업에서 **잘된 점을 정직하게 남긴다.**

- T1 이 **시간 상수를 늘리는 손쉬운 길을 택하지 않았다.** 지시서 R4 를 실제로 이행했다
- T2 를 **"불가능하다"고 정직하게 적었다.** 봉합했다고 쓰지 않았다(헌법 #24)
- 커밋 메시지가 **자기 변경의 위험(슬롯 1 감소)을 스스로 적었다.** 숨기지 않았다
- 병렬이슈가 적발한 **주석의 거짓**(*"설치 시점에 이미 등록된 존재"*)을 받아들여 주석을 정정했다
- `BuildMainPcName` 의 경계 처리(재부착 방지·100자 산술)가 **정확하다**(§2-6)
- 변경 범위를 **1파일**로 지켰다. 사장님 지시(*"슬롯 관련 수정은 따로"*)를 넘지 않았다

🔴 **그러나 위험을 적는 것과 막는 것은 다르다.**
D-3 는 적혀 있었고, 막히지 않았다. 그것이 이번 반려의 전부다.
