## §1 조건

### 🔴 C-1 — 20자를 넘는 종류값이 **말없이 잘려** 저장된다 (로그 0건)

| | |
|---|---|
| 자리 | `src/HitPan.API/BackgroundServices/CsOutboxSenderWorker.cs:538~552` (`INSERT IGNORE … purpose`) |
| 대조 | 같은 파일 `:516~522` — 본문이 2000자를 넘으면 **`LogWarning` 을 남기고** 자른다(작2 [4] V-5 봉합 「말없이 자르지 않는다」) |

**왜 조건인가** — `purpose` 는 `varchar(20)` 이다. 본사가 `promotion_year_end_2026`(23자)을 보내면 `STRICT_TRANS_TABLES` 에서는 1406 이어야 하는데, 이 문장이 **`INSERT IGNORE`** 라서 **에러가 경고로 눕고 20자로 잘려 저장된다**(실측 §2-5). 결과:

- 저장값 `promotion_year_end_2` → 칩 4종 어디에도 안 걸린다(`update/notice/promo/etc` 아님 · NULL 도 아님)
- 그 줄의 낱말은 「본사안내」 — 본문 머리는 `[본사안내]` 라 **제목과 칩은 맞지만**, 사장님이 「프로모션 안내」 칩을 눌러도 **그 쪽지는 안 나온다**
- 🔴 **기록이 0건이다.** 나중에 「왜 이 공지는 프로모션에 안 뜨나」를 아무도 못 찾는다

**봉합 제안** — 수신 한 줄에서 **길이를 보고 눕힌다**. 자를 게 아니라 **모른다(NULL)로 두고 경고를 남긴다**:
`Purpose = ...Trim() is { Length: > 0 and <= 20 } p ? p : null` + 잘릴 때 `LogWarning`. (NULL 이면 「기타 공지사항」 칩에서 보인다 — 사라지지 않는다.)

### 🔴 C-2 — 빈 문자열·공백만 든 종류값은 **「기타」 칩에도 안 걸린다**

| | |
|---|---|
| 자리 | `src/HitPan.API/Controllers/CsRequestController.cs:324` (`"etc" => " AND (r.purpose = 'etc' OR r.purpose IS NULL)"`) · 표시는 `:417` (`PurposeLabel(raw ?? "etc")`) |

**왜 조건인가** — 설계가 가른 두 사실은 「값이 있다」와 「모른다(NULL)」 두 가지뿐인데, **DB 가 허용하는 세 번째 모양**이 있다: `''` 와 `'  '`. 실측(§2-6) 결과 그 행은

- 칩 **전체에서만** 보이고 `update`·`notice`·`promo`·`etc` **넷 다 0건**
- 낱말은 「본사안내」 — `raw ?? "etc"` 는 `null` 만 받으므로 `''` 는 fallback 을 못 탄다

수신 경로(`:551`)는 `IsNullOrWhiteSpace → null` 로 눕히므로 **지금 본사에서 오는 길로는 안 생긴다.** 그러나 ① 칸 기본값이 그것을 막지 않고 ② 두 번째 쓰는 자리가 생기면 바로 생긴다. 「보이는 것과 걸러지는 것이 같아야 한다」는 과녁 자신의 원칙이 이 모양에서 깨진다.

**봉합 제안** — 거르는 쪽과 보여 주는 쪽을 **같은 판정**으로 맞춘다:
`etc` 분기를 `AND (NULLIF(TRIM(r.purpose),'') = 'etc' OR NULLIF(TRIM(r.purpose),'') IS NULL)` · 표시는 `PurposeLabel(string.IsNullOrWhiteSpace(raw) ? "etc" : raw)`.

### 🔴 C-3 — 필터의 **대소문자 판정이 두 군데에서 다르다**

| | |
|---|---|
| 자리 | DB 쪽 `CsRequestController.cs:325` (`r.purpose = @Purpose`) · 낱말 쪽 `CsOutboxSenderWorker.cs:777~790` (`switch` = ordinal) |

**왜 조건인가** — `cs_requests.purpose` 의 콜레이션은 `utf8mb4_unicode_ci` 다(실측). 그래서 `'UPDATE'` 가 저장되면

- **필터는 걸린다** — 「업데이트공지사항」 칩에 그 줄이 나온다
- **낱말은 「본사안내」** — C# `switch` 는 대소문자를 가린다

⇒ 업데이트 칩을 눌렀는데 **거기 나온 줄의 종류 칩은 「본사안내」**다. 작2 [4] C-5(한 줄에서 두 번 말하고 값이 달랐다)가 **값의 대소문자 축으로 되살아난다.** 본사가 어떤 대소문자로 보내는지는 ERP 가 정하지 못한다 — 그래서 ERP 가 눕혀야 한다.

**봉합 제안** — 수신에서 `Trim().ToLowerInvariant()` 로 적는다. (옛 행은 안 건드린다 — #1. ci 콜레이션이라 필터는 그대로 맞는다.)

### C-4 — 종류 필터가 **`origin` 에 묶여 있지 않다** (마이그 주석이 코드와 다르다)

| | |
|---|---|
| 자리 | `CsRequestController.cs:320~328`(`purposeWhere`) 가 `:391` 에서 `sideWhere` 와 **독립으로** 붙는다 |
| 어긋난 문서 | `src/HitPan.API/Migrations/SQL/DB-146_cs_requests_purpose.sql:42~43` — 「필터는 **항상 공지 쪽(origin='hq')에서만** 걸린다」 |

**왜 조건인가** — 실측(§2-7):

- `?purpose=etc` (origin 미지정) → **고객 자기 문의가 함께 온다**(고객 문의는 늘 NULL 이므로 `etc` 가 전부 데려온다)
- `?origin=local&purpose=update` → **0건**(고객 문의 목록이 빈다)

지금 화면 둘은 `origin=hq`·`origin=local`(종류 없음)만 부르므로 **오늘 보이는 사고는 아니다.** 그러나 ① 코드가 지키지 않는 사실이 마이그 주석에 **단정형으로** 적혀 있고(다음 사람에게 사실이 된다 — 「진단도 실측 전엔 가설」) ② 새 인덱스 `idx_cs_req_purpose (tenant_id, origin, purpose, created_at)` 는 **origin 이 없으면 쓰이지 않는다.**

**봉합 제안** — `purposeWhere` 를 `origin == "hq"` 일 때만 붙이거나, 붙일 때 `AND r.origin = 'hq'` 를 동반한다. 둘 다 싫으면 **마이그 주석을 사실로 고친다**(둘 중 하나는 해야 한다).
