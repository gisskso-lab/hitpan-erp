## 📜 헌법 1조 — 본사·고객사 데이터 경계 #18 v3

### 사장님 격언
> "본사로 오는 것 = SaaS 운영 데이터 + 대리점 영업 데이터. 끝."
> "고객사 DB에 접근 = 업무 X, 개인정보 X, 단 CS 요청 시 부분 허용."

### ✅ 본사가 받을 수 있는 것 (3종, 메타·카운터·식별자에 한함)

#### ① SaaS 운영
- 가입 정보 (회사명, 사업자번호, 대표자, 청구용 연락처)
- 결제 (토스 빌링 ID, 금액, 주기)
- 라이선스 (키, HW 핑거프린트 SHA-256+솔트, 만료일, 기기 수)
- 텔레메트리 (활성 사용자 수, 화면 ID 카운터, 에러 코드 — 본문 X, AI 토큰 사용량)
- 헬스체크 (CPU/디스크/DB 응답속도, 5xx 카운트)
- 버전·배포 (설치 버전, 마지막 업데이트 일시)
- 인프라 (터널 ID, 서브도메인, 토큰 발급 이력)
- 백업 메타 (시점·크기·성공여부 — **파일 본문 절대 X**)

#### ② 대리점 영업
- 대리점 정보, 파이프라인, 계약, 수수료, KPI

#### ③ 법적 의무 인프라 (베타 0일차 필수)
- 약관 동의 기록 (5년 보관)
- 처리위탁 계약 (개인정보보호법 §26)
- 국외이전 동의 (Cloudflare 사용)
- 데이터 파기 로그 (§21)
- 보안 감사 로그 (§29, 1년+ 위변조 방지)

### ❌ 본사가 받으면 안 되는 것

#### 헌법상 차단
- 매출/매입/원장/거래처/직원/급여/세금계산서/결재/BOM (업무 본문)
- 첨부파일·도면·이메일 본문
- 백업 파일 자체
- 챗봇·CS 입력 원문 (3중 마스킹 후 카운터만)
- 에러 로그 본문 (자동 마스킹 필수)

#### 법령상 형사 리스크 (접근 자체가 범죄)
| 영역 | 차단 근거 |
|---|---|
| 매출/매입/원장 | 부가가치세법 §32 |
| 거래처 정보 | 신용정보법 §32 |
| 직원 급여·근태 | 근로기준법 §39 |
| 직원 주민번호 | 개인정보보호법 §24의2 |
| 의료정보 | 개인정보보호법 §23 |
| 사업자 통장·카드 | 신용정보법 §15 |
| 견적서·계약서 첨부 | 영업비밀보호법 |
| 도면·기술자료 | 영업비밀보호법 + 산업기술보호법 |
| 이메일·카톡 본문 | 통신비밀보호법 §3 |

### 🟡 예외 — CS 모드 (Just-In-Time Access)
- 고객사 명시 동의 + 일회용 토큰 (범위·시간 제한)
- 30분 만료 또는 화면 이탈 시 자동 차단
- 모든 접근 = 위변조 방지 감사로그 1년+ 보관

## 📜 헌법 2조 — 가입 동의 (은행 대출 약관 구조 + 토스 UX)

### 필수 동의 5종 (체크 안 하면 가입 불가)
1. 서비스 이용약관 (전자상거래법)
2. 개인정보 수집·이용 (개인정보보호법 §15)
3. 개인정보 처리위탁 (§26, 본사 메타정보 수탁)
4. 국외이전 동의 (Cloudflare 미국, §28)
5. 신용정보 수집·이용 (신용정보법 §32, 사업자번호·계좌)

### 선택 동의 2종 (체크 안 해도 가입 가능)
6. 마케팅·광고 수신
7. 챗봇 학습용 비식별 데이터 활용

### 7단계 다층 고지 (한국 법원 판례: "동의했어도 인지 못 하면 무효")
1. 홈페이지 보안 페이지 (가입 전)
2. 가입 화면 동의 (필수 5 + 선택 2)
3. 첫 로그인 Welcome 모달 (인지 강화)
4. 챗봇 사용 시 입력창 옆 상시 안내
5. CS 요청 시 JIT 토큰 동의 (매번 새로)
6. 백업·해지 시점 안내
7. 사후 의무 (정보주체 권리 10일·침해사고 24시간)

### 절대 금지
- "전체 동의" 한 방 묶기 (개인정보위 가이드라인 위반)
- 필수·선택 시각적 미분리
- 항목별 분리 동의 생략

## 📜 헌법 4조 — 검증의 진짜 정의 (사장님 헌법 2단계)

### 사장님 격언

#### 1차 정의
> "DB에 DB 넣고 잘 들어간다 이게 아니야. 직접 버튼 일일히 하나하나 눌러보며 찍어봐야 그게 검증이야."

#### 2차 정의 (최종 완성형)
> "DB-백엔드-프론트 모든 게 연결끊김 없이 잘 돌아가고 고객이 보기에 문제가 전혀 없어야 그게 검증이다."

### 검증 통과 5중 동시 만족
```
검증 = ① DB 무결
       + ② 백엔드 무결
       + ③ 프론트 무결
       + ④ DB↔백엔드↔프론트 연결 끊김 0
       + ⑤ 고객 시선 = 0 문제 (혼자 쓸 수 있냐)

5개 중 1개라도 미달 → 즉시 반려
```

### ❌ 검증 아닌 것 (가짜 검증)
- DB INSERT 후 SELECT 확인만
- API 200 OK 응답만
- 단위 테스트 통과만
- 빌드 성공만
- "코드는 맞게 짰습니다" 자체 보고
- Postman·curl만으로 종결
- 자동 테스트만 + 수동 클릭 생략

### ✅ 진짜 검증
- 사람이 직접 브라우저 열기
- 사람이 직접 신규 가입 또는 로그인
- 사람이 직접 모든 버튼·입력란 클릭
- 사람이 직접 워크플로우 처음~끝 (예: 견적→수주→거래명세서→세금계산서)
- 사람이 직접 화면 캡처
- 3계층(DB·백엔드·프론트) 끊김 없이 흐르는지
- "처음 보는 사람이 혼자 쓸 수 있냐?"

### 검증 보고서 의무 양식
```markdown
## 검증 보고서 — {화면/기능명}

### 1. DB 계층
- 클릭 전 SELECT (캡처)
- 클릭 후 SELECT (캡처)
- 정합성 (stock_ledger·journal_lines 동시 반영)

### 2. 백엔드 계층
- API 호출·요청·응답
- 트랜잭션 경계
- 에러·경고 0건

### 3. 프론트 계층
- 입력→로딩→성공
- 화면 갱신
- 다음 화면 데이터 전달

### 4. 연결 끊김 검증 ⭐
- 프론트→백엔드→DB→백엔드→프론트 양방향
- 워크플로우 다음 화면 데이터 인식

### 5. 고객 시선 검증 ⭐
- 처음 보는 직원: 혼자 쓸 수 있나?
- 에러 시 친절한 안내?
- 한 화면 완결?

### 캡처 (필수)
- DB 전/후 + 프론트 입력/결과 + 다음 화면

### 판정
- 5개 모두 ✅ → 통과
- 1개라도 ❌ → 반려
```

### 3중 검증 책임 (모두 풀스택 트레이스 의무)
| 단계 | 책임자 | 방식 |
|---|---|---|
| 1차 | 매니저 | 도메인 + 풀스택 + 캡처 |
| 2차 | 검증팀 | EVF 6게이트 직접 클릭 + 영상 |
| 3차 | CTO | 신규 사용자 행세 + "혼자 쓸 수 있냐" |

### 절대 금지
| 위반 | 처벌 |
|---|---|
| "DB에 들어갔으니 통과" | 매니저 즉시 교체 |
| 본인 계층만 보고 사인 | 검증 무효 + 매니저 교체 |
| 캡처·영상 없는 보고 | 검증 무효 |
| "이전에 됐으니 됐겠죠" | 절대원칙 #19 위반 |
