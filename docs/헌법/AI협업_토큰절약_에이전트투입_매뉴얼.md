## §0. 카드 — 이것만 읽고 시작한다

| # | 규칙 | 막는 낭비 (실측) |
|---|---|---|
| 1 | **문서는 카드(§0)만 읽는다.** 나머지는 `Grep -n "^## §N"` → `Read offset + limit` 로 그 절만 (limit 없으면 통째) | 9/10 에이전트 8개가 문서만 52.5만 토큰 |
| 2 | **에이전트에게는 주소 + 절 + 사실목록(파일:줄)만 준다.** "문서 읽고 파악해라" 금지 | 회의록 1개(127KB)를 8개가 25번 읽음 |
| 3 | **에이전트 결과는 파일에 쓰고, 메인에는 15줄 + 주소만** 돌려받는다 | 메인 컨텍스트 누적 |
| 4 | **5분 넘게 쉰 에이전트는 깨우지 않는다.** 결과 주소를 들고 새로 띄운다 | 9/10 5시간 창의 36% |
| 5 | **투입은 §4-1 판정 트리를 통과할 때만.** 의견 수렴은 역할 체크리스트(§4-6) | 에이전트 개당 2.1~10.7M |
| 6 | **읽기 전용 조사는 Explore** — CLAUDE.md 를 안 싣고 1.3만 토큰으로 시작 | general-purpose 는 6.5만으로 시작 |
| 7 | **컨텍스트 30만이면 인수인계서 쓰고 새 창** | 60만 초과 호출 응답 중앙값 114초 |
| 8 | **1시간 넘게 쉴 거면 인수인계서 먼저 → 돌아와 새 창** | 재개 메시지 1번에 1.26M |

| 10 | **생각량 기본 high.** xhigh 는 지정 작업만, 그 세션에만 | 호출당 출력 2배 |

## §1. 왜 — 3줄

- 9/10 5시간 한도가 **1시간 45분 만에** 바닥났다 (20:40 → 22:25, 환산 22.3M). 그중 **36%는 쉰 에이전트의 대화를 캐시에 다시 쓰는 값**이었다.
- *"문서만 읽으면 가볍다"* 는 전제가 실측에서 깨졌다. 문서 자체가 30~127KB 라 **코드만큼 무겁고**, 에이전트마다 **같은 문서를 처음부터** 읽었다.
- 컨텍스트가 클수록 느리다. 60만 초과 호출 응답 중앙값 114초, 30만 이하는 9~12초.

| [3-V]·[4] 동시검증 | hp-verifier — 규모 S·M 은 1개가 두 관점 · L 은 2개 | 작업지시서 카드·§5 + 변경 파일 목록 | 병렬이슈 · 작업리뷰서 (2종 그대로) | 1~2 |

**작업 1건 에이전트 상한** — S 2 · M 5 · L 8. 넘기면 PM 이 작업지시서에 사유 한 줄.

## §3. 문서 규격 — 인덱스로 찾히게 쓴다 (신규 문서부터)

### 3-1. 상한

| 문서 | 카드 (§0) | 본문 상한 | 실측 (9/10) |
|---|---|---|---|
| 작업지시서 | ≤40줄 | ≤300줄 · 20KB | 351줄 · 39KB |
| 선행검증서 · 설계/개발 브리핑 | ≤40줄 | ≤250줄 · 20KB | 32~45KB |
| 회의록 | 결론 카드 ≤40줄 | **라운드별 파일 분리**, 파일당 ≤300줄 | 869줄 · 127KB 한 파일 |
| 인수인계서 | §0 + §9 ≤40줄 | ≤120줄 | 164줄 · 11.5KB |
| INDEX 한 줄 | — | 주소 · 상태 · 설명 60자 이내 (설명 문단 금지) | 운영기록 INDEX 한 줄 중앙값 1,068B · 최대 6.3KB · 전체 217KB |
| CLAUDE.md | — | ≤200줄 (공식 권장) | 525줄 · 30KB — 매 호출 · 매 에이전트에 실림 |
| MEMORY.md | — | ≤200줄 · 25KB (공식 로드 한도) | 114줄 · 30KB |

### 3-2. 절 앵커

- 모든 절 머리는 `## §N` 또는 `## §N [키]` (예: `## §4 [K1] 서버 판정`). 누구든 `Grep -n "^## §4"` 한 번으로 줄 번호를 얻는다.
- 카드(§0)에는 **결론 · 결정 · 다음 행동**만. 근거는 본문 절 주소로 (참조식 원칙 그대로).

### 3-3. 읽는 순서 (사람 · 메인 · 에이전트 공통)

```
① 주소는 이미 받았다 — INDEX · START_HERE 를 매번 거치지 않는다
② Read {문서} limit=40                           ← 카드
③ Grep -n "^## §" {문서}                          ← 목차 (줄 번호)
④ Read {문서} offset={절 시작줄} limit={절 길이}    ← 필요한 절만
⑤ 코드: Grep -n "{메서드명}" → Read offset ±60줄
🚫 20KB 넘는 .md 통째 Read · 10KB 넘는 INDEX 통째 Read · 헌법원문 통째 Read (해당 조항만)
   ← P2 훅이 막고, 거절 메시지에 목차(줄 번호)를 돌려준다
```

## §4. 에이전트 투입 매뉴얼

### 4-1. 투입 판정 트리

```
Q1 규범상 독립 문맥이 필수인가?   [1-V] · [2] 작성자≠결재자 · [3-V]·[4] SoD   → 투입
Q2 서로 안 겹치는 코드 갈래가 2개 이상이고 동시에 해야 하나?             → 갈래당 hp-implementer 1 (최대 3)
Q3 파일 30개 넘게 훑어야 하는데 결과만 필요한가?                          → Explore 1 (사실목록 반환)
그 외                                                                     → 투입 안 함. 메인이 직접
```

### 4-2. 투입하지 않는다

- 파일 1~3개 확인 · 문서 한 절 확인 · 빌드·테스트 실행 · 한 파일 수정
- 역할별로 *"의견만"* 받는 브리핑 (설계팀 · 개발팀 · 현장팀 각 1개) → 메인이 §4-6 체크리스트로 한 번에
- 끝난 지 5분 넘은 에이전트에게 후속 질문 → 새 에이전트 + 이전 결과 주소
- 같은 문서를 여러 에이전트에게 각자 읽히기 → PM 이 사실목록을 한 번 뽑아 나눠준다

### 4-3. 표준 에이전트 (`.claude/agents/hp-*.md`)

| 이름 | 쓰는 단계 | model | effort | maxTurns | 캐시 수명 | 비고 |
|---|---|---|---|---|---|---|
| Explore (내장) | 사실목록 · 전수 grep | 호출 시 `sonnet` 지정 | — | — | 5분 | CLAUDE.md · git status 를 안 실음 |
| hp-designer | [2] 설계 · 작업지시서 초안 | inherit | high | 40 | 5분 | 설계팀장 존 |
| hp-implementer | [3] 갈래 구현 | inherit | high | 60 | 5분 | `isolation: worktree` |
| hp-verifier | [1-V] · [3-V] · [4] | inherit | high | 50 | **1시간** | [3] 이 도는 동안 계속 불리므로 |
| hp-judge | 주심 · [5] 규모 L | inherit | xhigh | 25 | **1시간** | 입력 = 쟁점표 · 리뷰서 카드만 |

> 페르소나 소개는 에이전트 정의 파일에 **한 번만** 둔다 → 매 프롬프트에서 뺀다.
> 1시간 캐시(`experimental.cacheTtl: 1h`)는 쓰기 단가가 높다 → **다시 부를 에이전트에만** 준다.

### 4-4. 투입 카드 (프롬프트 틀 — 1,500자 이내)

```
[목적]  한 줄
[역할]  hp-verifier · 관점: 보안상무 [3-V] + 검증팀장 [4]
[입력]  docs/운영기록/{작업지시서}.md §0 · §4[K1]~[K3]   (절은 Grep -n 으로 찾기)
[사실]  {파일}:{줄-줄} · {파일}:{줄-줄} · …
[예산]  파일 25개 · .md 는 절 단위만 · 셸 출력 40줄
[산출]  docs/검증/병렬이슈/{파일명}.md   (틀: docs/_틀/…)
[반환]  15줄 이내 — 판정 · 발견 (한 줄씩) · 산출물 주소
[금지]  코드 수정 · 문서 전문 재인용 · 운영 환경 직접 조작 (#39)
```

### 4-5. 수명

```
띄움 → 일함 → 산출물 파일 → 15줄 반환 → 끝
후속이 필요하면  5분 이내 (hp-verifier · hp-judge 는 55분 이내) → SendMessage
                넘었으면 → 새로 띄우고 "이전 결과: {주소}" 만 준다   ← P3 훅이 막는다 (#재개승인 으로 예외)
백그라운드 에이전트가 읽는 파일을 메인이 동시에 통째로 읽지 않는다
```

### 4-6. 역할 체크리스트 — 에이전트 없이 관점만 적용

| 역할 | 반드시 묻는 것 (정의 전문은 [`TEAM_DEFINITION.md`](TEAM_DEFINITION.md)) |
|---|---|
| CTO 래리 | 나중에 안 터지나 · 빌드 0/0 (#19) · 5중검증 (#23) · 정식완성도 (#34) |
| 보안상무 안철수 | tenant_id 는 JWT 에서만 (#2) · 본사 데이터 0 (#18·#22) · 외부노출 금지어 (#23) |
| 검증팀장 데이비드 박 | 안 되는 경우를 찾았나 · 백지 환경 실측인가 · 대조군이 있나 |
| 설계팀장 존 | 3시스템 연결 끊김 없나 (#20·#35) · 프론트~DB 수직 정합 |
| ERP 매니저 | 현장 직원이 3분 안에 쓰나 |
| 김삼성 상무 | 실제 인사팀이 이렇게 일하나 |
| 기술영업 · 마케팅 | 팔리나 · 30초 안에 설명되나 |
| 법무팀장 | 법적으로 못 하는 것은 없나 |

### 4-7. 하브루타 저비용 진행

```
R0 PM      쟁점표 v1 (≤60줄: 쟁점 · 선택지 · 사실목록 주소)            → 회의록_R0.md
R1 팀 의견  메인이 §4-6 체크리스트로 초안 · 사실 반증이 필요한 쟁점만 hp-verifier 1
R2 주심    hp-judge 1~2 (1시간 캐시) — 쟁점표 + R1 카드만 읽는다        → 회의록_R2.md
R3 결론    결론 카드 → 사장님 결재                                     → 회의록 §0
```

> 9/10 하브루타는 설계 · 개발 · 검증 3개 + 주심 2개가 **각자 코드와 문서를 처음부터** 읽었고, 라운드 사이에 16~220분 쉬었다가 재개돼 대화 전체가 다시 기록됐다.

## §5. 바이브코딩 매뉴얼 — 메인 세션 (PM)

### 5-1. 세션 수명과 캐시

| 대상 | 캐시 유지 | 넘기면 |
|---|---|---|
| 메인 세션 | 마지막 응답 후 **1시간** | 다음 메시지 1번에 컨텍스트 전체를 다시 쓴다 (60만 컨텍스트 → 약 1.2M) |
| 서브에이전트 | **5분** (hp-verifier · hp-judge 는 1시간) | 재개 1번에 그 에이전트 대화 전체 재기록 |

```
시작    CLAUDE.md (자동) → START_HERE §0-1 한 줄 → 진실원 인수인계서 §0·§9
작업 중  상태줄: 20만 주의 · 30만 새 창 (상태줄에 표시된다)
휴식    1시간 넘게 → 인수인계서 먼저 → 돌아와 새 창   (짧게 쉴 땐 /compact 후)
끝      [6] 커밋 → [★] 인수인계서 → [7] 일일보고서 (token-report 한 줄)
```

### 5-2. 읽기 · 셸 · 보고

- 읽기는 §3-3 순서. 수정 후 확인은 Edit 결과로 충분 — 같은 파일 통째 재읽기 금지.
- 빌드: `powershell -NoProfile -File scripts/dev/build-brief.ps1 -Project <csproj>` — 오류·경고와 요약만
- 테스트: `powershell -NoProfile -File scripts/dev/test-brief.ps1 -Project <csproj> [-Filter …]` — 실패 목록과 요약만
- DB 조회는 `LIMIT` 필수 · git 은 `--stat` · `-n 20` · 긴 출력은 파일로 저장 → `Grep`
- 채팅 보고는 결론 + 표. 긴 분석은 문서 파일에 쓰고 주소만.

### 5-3. 생각량 · 모드

- 기본 `high` (사용자 설정). `xhigh` 는 설계 반증 · 보안 판정 · 원인 불명 버그에만 — `/effort xhigh` 후 `s` (이 세션만).
- ultracode 는 끈다. 여러 에이전트 워크플로는 사장님이 *"워크플로로"* 라고 할 때만.
