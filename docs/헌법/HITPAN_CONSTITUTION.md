# 히트판 헌법 통합본 (계열별)

> **이 문서의 성격 — 반드시 먼저 읽을 것** (사장님 확정 2026-07-28)
>
> ### 판단 서열 (사장님 확정 2026-07-28)
>
> ```
> 1차: 통합본으로 판단한다          ← 평소는 여기서 끝난다
>        ↓ 유권해석이 필요할 때만
> 2차: 각주(→ #NN 원문)로 원문 참조
>        ↓ 원문을 봐도 애매하면
> 3차: 사장님 결재                  ← AI가 혼자 해석하지 않는다
> ```
>
> **"유권해석이 필요할 때"란**: 통합본 문구가 애매하다 / 두 계열이 충돌한다 / "이 경우도 포함되나?" 싶다 /
> 통합본에 없는 상황이다 — 이럴 때 각주를 따라 원문을 펼친다. **판단이 조금 걸린다고 매번 펼치지 않는다.**
>
> ### 🚨 예외 — 아래는 유권해석 여부와 무관하게 **무조건 원문 필독**
>
> | 조항 | 언제 | 왜 예외인가 |
> |---|---|---|
> | **#37** | `reseller_id`·`reseller_tier`를 만지거나 "잔재"로 판단하려 할 때 | AI가 잔재로 오판하는 것을 막으려고 만든 조항. 요약만 믿으면 조항의 목적이 무너진다 |
> | **#29** | cloudflared·DNS·방화벽·Windows 서비스·레지스트리 조작 | 실제로 사람이 해고된 조항 |
> | **#39** | 운영(demo) 환경에 무언가 하려 할 때 | 두더지잡기 사고의 원인 |
> | **#33** | 작업 지시를 받고 코드를 시작하려 할 때 | 예외 해당 여부를 원문에서 확인해야 함 |
> | **#40** | 부모계정·비밀번호·시리얼 흐름을 바꿀 때 | 이행기 규칙(공개키 전환·착수 순서)이 원문에만 있음 |
>
> 이 5개는 **사고에서 나온 조항**이라 통합본 요약을 신뢰하지 않는다. 본문의 ⚠️트리거에도 표시돼 있다.
>
> ### 그 밖의 원칙
> - 이 통합본은 **원문을 대체하지 않는다.** 원문은 `CLAUDE.md` 절대원칙 #1~#41에 그대로 살아 있다.
> - 통합본과 원문이 어긋나면 **언제나 원문이 이긴다.** 어긋남을 발견하면 즉시 사장님께 보고한다.
> - 원문이 개정되면 통합본도 같은 커밋에서 갱신한다. 통합본만 고치는 것은 금지.
>
> 작성 2026-07-28 | 방식: 사장님 지시 "원문 보존 + 통합본을 얹고 원문 참조 각주 + 유권해석은 결재"
> 목적: 헌법이 41개로 늘며 같은 뿌리(#18·#22 등)를 매번 다시 인용하게 된 중복을 정리해,

## 계열 A — 데이터 주권 (본사는 고객 업무 데이터를 갖지 않는다)

> 관련 원문: **#18 · #22 · #24 · #30** (+ #5 부분)
> 이 계열은 히트판에서 **가장 많이 인용되는 뿌리**다. (#22 9회, #18 8회 피인용 — 2026-07-28 실측)

### A-1. 원칙 — 본사가 안 가지면 본사가 털릴 일 없다

사장님 격언 (2026-05-12)[^a1]:
> *"본사가 안 가지면 본사가 털릴 일 없다. 본사가 안 알면 본사가 책임질 일 없다. **사장님 데이터는 사장님 것이다.**"*

쿠팡·SKT·KT 사고 시대의 핵심 생존 원칙. 이건 기술 선택이 아니라 **사업 생존 전략**이다.

[^a1]: → **#22 원문** (본사 데이터 최소주의, 2026-05-12). #22 본문에 *"헌법 #18 v3와 통합 적용"* 이 이미 명시되어 있다 — 즉 #18과 #22는 사장님이 이미 한 몸으로 선언하신 것이다.

### A-2. 본사가 받아도 되는 것 / 절대 안 되는 것

| 구분 | 항목 |
|---|---|
| ✅ **본사 보유 가능** | ① SaaS 운영 데이터 (가입·결제·라이선스·텔레메트리·CS) ② 대리점 영업 데이터 (채널·수수료·KPI) |
| 🚫 **본사 전송·보유 절대 금지** | 매출·매입·원장·거래처·직원·상품·재고·세금계산서·결재 등 **고객사 업무 데이터 일체** + **자식계정** + **백업 원본** |

- 백업조차 **E2E 암호화**로 본사가 내용을 모르게 한다.[^a2]
- 위반 = 4프로토콜 #3 민감 작업으로 **즉시 반려**.

[^a2]: → **#18 원문** (본사 서버로 고객사 ERP 업무 데이터 전송 금지, 2026-04-25 / DESIGN_PRINCIPLES §14.3) + **#22 원문**. 전송 코드를 작성하려는 순간 두 원문을 모두 펼칠 것.

### A-3. 책임은 나누되, 가르치지 않고 넘기지 않는다

본사는 본사가 만든 영역만 책임진다. **단 책임 분산 ≠ 방치.**
가이드·매뉴얼·튜토리얼·AI 챗봇·콜센터를 충분히 제공할 의무가 있다.
> *"가르치지 않고 책임을 넘기는 것은 거짓말이다."*
> 데이터 주권은 사장님이, 데이터 관리 가이드는 본사가.

책임 3축: ① 본사(SaaS 결제·부모계정 인증·백오피스 메타·본사 인프라) / ② 고객(고객 PC·자식계정·백업 보관·내부 망) / ③ 제3자(카카오·토스·이세로·메이크빌·Cloudflare·PG).[^a3]

[^a3]: → **#24 원문** (책임 분산 + 가르침 의무, 2026-05-12). 약관·SLA 문구를 쓰거나 책임 경계를 판단할 때는 #24 원문의 3축 정의를 그대로 확인할 것.

### A-4. 그래서 고객 PC가 스스로 회복한다 (본사 의존 0)

통신 무결성은 **고객 PC 자체에서** 해결한다. 본사 클라우드 이전 = 금지.
본사 역할은 모니터링·CS·가르침뿐. 워치독(Windows 서비스)이 1분마다 자가 진단·자동 봉합하고, 본사는 **메타 ping만** 받는다(고객 데이터 0건).[^a4]

[^a4]: → **#30 원문** (고객 PC 자가 회복, 2026-05-15). #22·#24의 직접 파생이다 — "본사가 안 가지려면 고객 PC가 스스로 살아야 한다"가 인과. 워치독·터널 복구를 설계할 때 #27·#28과 함께 볼 것.

### ⚠️ A계열 판단 트리거 — 이때는 원문을 펼쳐라

| **부모계정** | `tenant_admin` | **존재** (계정 ID = 라이선스) | ERP 최상위, 자식계정 생성·권한부여 |
| **자식계정** | `tenant_user` | **안 남음** (ERP 로컬 DB에만) | 부모가 부여한 권한만 |

- `platform_admin`(본사)·`reseller_admin`(대리점)은 **백오피스 계층**이지 ERP 계층이 아니다.
- ERP JWT에 `platform_id`·`reseller_id` **계정 식별자 클레임 미발급** (2026-06-18 보안 격벽).
- SaaS 계층 ↔ ERP 내부 권한 **혼용 금지**.[^b3]

[^b3]: → **#38 원문** (ERP 계정 계층 2계층, 2026-06-22) + **#7 원문** (SaaS↔ERP 권한 혼용 금지). ERP 코드에 남은 platform_admin/reseller_admin **권한 분기**는 청소 대상이나, 제거 시 부모/자식 인증이 안 깨지는지 확인 후 진행 — 상세는 #38 원문.

### B-4. 🚨 `reseller_id`·`reseller_tier`는 **잔재가 아니다** — 절대 제거 금지

**"안 읽힌다 ≠ 잔재".** 이 컬럼들은 백오피스→ERP **수신**해 보관하는 **영업 출처 메타데이터**다.
쓰기(수신 UPSERT)는 살아 있고, ERP 안에서 SELECT하는 코드가 0건인 것은 **정상**이다(자리 선점).

- **계정 계층(B-3)과 혼동 금지** — reseller_id는 *계정 계층*이 아니라 *영업 출처*다.
- "ERP는 부모/자식뿐인데 reseller_id가 있네 = 잔재" **← 이 추론이 바로 오판이다.**
- A계열 위반 아님 — ERP→본사 *전송*이 아니라 본사→ERP *수신*이다.
- 제거하려면 DDL+부트스트랩/웹훅 SQL+DTO+백오피스 송신 계약을 3시스템 동시 수술해야 하고,
  `tenants.reseller_tier`는 NOT NULL DEFAULT 없음이라 컬럼만 떼면 **부모계정 가입 500**.

> ⛔ **사장님 사전 결재 없이 제거 절대 금지. 만질 일이 생기면 코드 손대기 전 보고.**[^b4]

[^b4]: → **#37 원문 필독** (수신 캐시 컬럼 제거 금지, 2026-06-22) + **#38 원문**의 "핵심 인과" 절. 전수조사·리팩터링 중 이 컬럼을 마주치면 **반드시** 두 원문을 펼칠 것. 이건 실제로 반복 발생한 오판이라 사장님이 헌법에 못박으셨다.

### B-5. 부모계정 온보딩 — 본사는 비밀번호를 **0건** 갖는다

```
① 랜딩 가입 → 백오피스에 고객사 정보만 저장 [비밀번호 안 받음·안 저장]
② ERP 설치 시 시리얼넘버 입력
③ 설치마법사에서 부모계정 = 아이디 + 비밀번호 직접 등록 (이메일 방식 아님)
④ 비밀번호는 고객 PC ERP 로컬 users 에만 BCrypt 해시
⑤ 그 아이디+비번으로 로그인
```

- 랜딩 가입 화면에 **비밀번호 입력칸이 없는 것은 결함이 아니라 의도된 설계**다. 다시 추가하지 말 것.
- "부모계정을 백오피스에서 호출해 온다"고 고치려는 시도 = **즉시 반려** (본사 비번 보유 = A계열 위반).
- 브라우저→백오피스 **직접호출 금지** (CORS 참사 진범). 서버간 1회로.[^b5]

[^b5]: → **#40 원문** (부모계정 온보딩, 2026-07-07 + 재조정). 공개키 오프라인 검증 전환·kid 롤오버·착수 순서 강제(기존 시리얼 소진 후 HMAC 제거) 등 이행기 규칙이 원문에 있다. 계정 흐름을 건드리기 전 필독.
