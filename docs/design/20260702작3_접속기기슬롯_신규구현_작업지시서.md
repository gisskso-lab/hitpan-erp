## 1. 구현 항목

### I3 — F3 "처음 접속하는 기기입니다. 등록하시겠습니까?" UI (프론트)
- 배경: 작1에서 백엔드 기반 완료 — `LoginResponse.DeviceNewlyRegistered`/`DeviceNotice` 서버가 채움. 그러나 프론트가 아직 소비 안 함(현재 조용히 자동 등록).
- 사장님 정의 정상 흐름: 등록기기→통과 / 처음기기→"등록하시겠습니까?"(슬롯여유) / 슬롯초과→"등록된 기기가 아닙니다".
- 구현 대상:
  1. 프론트 DTO `src/HitPan.Web/Models/AuthModels.cs:23 LoginApiResponse` 에 `DeviceNewlyRegistered`(bool)·`DeviceNotice`(string?) 필드 추가 (서버 응답 수신). ⚠️ 현재 `DeviceId` 만 있음.
  2. `src/HitPan.Web/Services/AuthService.cs` LoginAsync — 응답의 DeviceNewlyRegistered=true면 결과에 안내 플래그 전달.
  3. 로그인 성공 후 UI — 신규 기기면 "이 기기가 새 기기로 등록되었습니다"(1차 자동등록 유지형) 또는 사장님 의중이 "등록 전 사용자 확인"이면 로그인 흐름에 확인 다이얼로그 삽입.
- ⚠️ **설계 갈림(사장님 결재 필요)**: 현재 백엔드는 "자동 등록 후 통지"다. 사장님 정의 "등록하시겠습니까?"가 **(a) 등록 후 사후 통지**인지 **(b) 등록 전 사전 동의(거부하면 등록 안 함)**인지에 따라 백엔드까지 바뀐다. (b)면 로그인 2단계(선 조회→확인→후 등록)로 백엔드 재설계 필요. → §3에서 확정.
- 완료 기준: 처음 기기 로그인 시 안내 노출, 등록기기 재접속 시 조용히 통과, 슬롯초과 시 명확한 차단 메시지.

### I4 — 지문 재매핑 마이그레이션 (백엔드+DB)
- 배경(검증팀 우려): 2차에서 지문 산식을 난수→환경해시(HFPv2-)로 바꿈. **기존 등록 기기(옛 난수 지문)는 새 지문과 안 맞아** 재접속 시 "새 기기"로 재인식 → 슬롯 초과·로그인 차단 위험(헌법 #20).
- 현 규모: 운영 tenant_devices 7건(전부 데모 본인) — 경미. 그러나 **정식 출시 전 필수**, 베타 고객 늘기 전에.
- 구현 후보(택1 결재):
  - **(A) 최초 재접속 1회 유예·재매핑**: 옛 지문으로 등록된 기기가 새 지문으로 처음 접속하면, 슬롯 초과로 막지 말고 옛 행의 fingerprint를 새 값으로 UPDATE(같은 user_agent/최근 last_seen 매칭). 사고 0, 자동.
  - **(B) 배포 시 기존 기기 전부 유예 플래그**: 신규 지문 도입 시점에 기존 approved 기기에 유예 마킹, 재접속 1회는 무조건 허용하며 재매핑.
  - **(C) 관리자 수동 초기화**: 기존 기기 목록 비우고 재등록. 가장 단순하나 고객 재등록 부담.
- ⚠️ **구현 위치 = 마이그 파일 아님, 런타임 로직**(§3 CTO 죽은봉합 경고 참조). `MigrationRunner.ApplyPendingAsync` 호출 0건이라 DB-85 마이그는 안 돌아감 → `TenantDeviceService.RegisterOrRefreshAsync`에 얹는다. clean DDL(헌법 #36) 무접촉.
- ⚠️ 운영 반영은 검증된 스크립트로만, 테스트DB 검증 후(헌법 #39). demo 7건 재매핑도 운영 직접수술 금지.
- 완료 기준: 지문 산식 교체 후에도 기존 기기가 로그인 일괄 차단 안 됨(재접속 1회 유예로 자동 재매핑).

### ✅ I3 확정 = (a) 자동 등록 후 통지 (CTO 권고 채택)
- 이유(CTO): (b) 사전동의는 로그인 2단계 재설계 → 자동출근(`AuthController:113`)·약관(`:134`) 부수효과가 기기 확정 전 실행돼 순서 꼬임. 현장에선 "등록?" 물어도 답할 권한자(관리자)가 그 자리에 없음. 히트판 정신("혼자 쓸 수 있냐").
- **구현(프론트 최소)**: ① `src/HitPan.Web/Models/AuthModels.cs` LoginApiResponse 에 `DeviceNewlyRegistered`(bool)·`DeviceNotice`(string?) 필드 추가(현재 DeviceId만) ② `AuthService.cs` 결과에 전달 ③ 로그인 성공 후 신규기기면 통지 노출("이 기기가 새 기기로 등록되었습니다"). 백엔드 무변경(이미 서버가 채움).
- 슬롯초과 차단 메시지는 이미 작동(`TenantDeviceService:178,183` → `AuthController:82` → `AuthService:58-65`).

### ✅ I4 확정 = (A) 재접속 1회 유예·재매핑 + 좁은 매칭키 (CTO 권고 채택)
- 이유(CTO): (B) 무제한 등록 창구, (C) 로그인 일괄차단(#20). (A)가 사고 0에 가장 근접.
- **⭐ 핵심 정정(CTO 죽은봉합 경고 반영)**: **I4는 DB-85 마이그 파일이 아니라 `TenantDeviceService.RegisterOrRefreshAsync` 런타임 로직으로 구현한다.** 근거: `MigrationRunner.ApplyPendingAsync`가 프로젝트 전체에서 **호출 0건**(전수 grep, `Program.cs:73` 주석 "수동 호출만") → DB-85만 만들면 아무도 안 돌리는 죽은 봉합. **DB-85 마이그 파일 생성 계획 폐기.** (필요 시 보조 로그만.)
- **삽입 위치**: `RegisterOrRefreshAsync` 의 **신규 기기 분기 앞**(옛 지문은 새 지문과 달라 `:115` fingerprint 매칭에서 안 잡히고 신규로 감 → `:150` 한도검사 직전). "신규로 판정됐지만 이 user의 옛 approved 행이 있으면 UPDATE로 흡수".
- **좁은 매칭키(오매칭 방지)**: `user_id` 소유 + 옛 행 approved + **그 user의 옛 행이 유일** + 새 지문이 `uq_tenant_fp` UNIQUE에 미충돌 — 이 4조건 전부일 때만 자동 UPDATE. 복수 후보·충돌이면 자동 재매핑 금지, 신규 등록 흐름 폴백(안전측).
- clean DDL 무접촉(헌법 #36) — 신규설치엔 옛 지문 없음. 순수 데이터 재매핑(UPDATE), 스키마 변경 아님 → ddl-smoke 무영향.
