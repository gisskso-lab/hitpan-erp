## 1. 진범 (코드 라인으로 확정 — 추측 아님)

### 🎯 진범: 기기 지문이 "기기"가 아니라 "브라우저 저장소 난수"에 묶여 있다
- 파일: `src/HitPan.Web/wwwroot/js/device-fingerprint.js` L7-22 `getFingerprint()`
- 실제 구현: `localStorage['hitpan_fp_id']`에 **`crypto.randomUUID()` 난수**를 한 번 심어 재사용. **기기 특성(하드웨어·OS·화면·UA)을 하나도 반영하지 않음.**
- **설계-구현 불일치**:
  - 코드 주석 L5-6 = *"브라우저 환경값 기반 간이 해시"* (실제로 환경값 0개 사용 — 그냥 난수)
  - DDL 주석 = `tenant_devices.fingerprint` COMMENT *"UA+OS+해상도+시간대 SHA-256"* (`installer/hitpan_db_clean.sql`) → 설계 의도는 기기 특성 해시였으나 구현은 난수.
- **결과**: localStorage가 리셋되는 모든 경로에서 새 난수 = 새 기기로 잡힘.
  1. 캐시·쿠키·사이트데이터 삭제, 브라우저 정리 도구, 저장소 만료
  2. 접속 도메인/포트가 달라지면 localStorage 격리 (예: `localhost` vs 터널 도메인 vs `{id}.hitpan.kr`) — **메인PC에서 로컬 접속하다 클라이언트가 도메인으로 접속하면 서로 다른 저장소**
  3. 시크릿 모드·다른 프로필·다른 브라우저
- **판정**: 이건 "가끔 나는 사용자 환경 사고"가 아니라 **난수 UUID는 애초에 같은 기기를 보장하지 못한다는 근본 설계 결함**이다. (정독 1차의 "시크릿 모드 탓" 결론을 PM이 기각 — 증상의 일부만 본 것)

### 부수 결함 (같은 건에 묶어 봉합 검토)
- **F2 — 빈 지문 처리**: `getFingerprint` 예외 시 `''` 반환(L21) → 백엔드 `TenantDeviceService.RegisterOrRefreshAsync`가 빈 지문이면 등록 스킵/신규 처리. 지문이 흔들리면 이 경로로도 새 기기.
- **F3 — 안내 흐름 부재**: 사장님이 정의한 정상 흐름 중 **"처음 접속하는 기기입니다. 등록하시겠습니까?"** 안내가 코드에 없음(자동 등록만, 사용자 고지 0). `TenantDeviceService` L212 신규 시 조용히 approved INSERT.

### 진범 아님 (반증 완료 — 재조사 금지)

## 2. 봉합 목표 (사장님 정의한 정상 흐름 = 완료 기준)
```
기기 접속/로그인
  → 이 접속이 메인PC 본인인가?
      ├─ 예(메인PC)        → 인증 없이 통과 (설치 때 이미 등록됨, 슬롯 소모 안 함)
      └─ 아니오(클라이언트PC)
            → 지문으로 등록된 기기인가?
                ├─ 예(등록기기)   → 통과, last_seen 갱신
                └─ 아니오(처음 기기)
                      ├─ 슬롯 여유 O → "처음 접속하는 기기입니다. 등록하시겠습니까?" (사용자 확인)
                      └─ 슬롯 여유 X → "등록된 기기가 아닙니다" (차단·기기교체 안내)
```
- **핵심**: 같은 기기는 무슨 일이 있어도 같은 지문으로 인식돼야 한다. localStorage 리셋·도메인 차이에도 흔들리지 않아야 한다.

## 3. 봉합 방향 (⭐ 실측으로 우선순위 재확정 2026-07-02)

### 🎯 실측이 바꾼 것 — "지문 알고리즘"이 아니라 "origin"이 급소
호스트 실측(tests/device-fp-probe, F12 관찰) 결과:
- `localhost:5599` 지문 A = `01a7075d-6f07-4015-b1fd-8ec97ea6a877` / 새로고침 = A 그대로(재사용 정상)
- `127.0.0.1:5599` 지문 B = `40ba83fe-6bf1-4a1d-96be-5bba281b9693` = **A와 완전히 다름**
- **같은 PC·같은 브라우저·같은 포트, host 문자만 달라도 새 지문.** localStorage가 origin(scheme+host+port)별 격리라서. 지문은 빈값 아님(정상 생성) → F2 빈지문은 이번 증상 주범 아님.

**결론**: 봉합 1순위는 **접속 origin을 하나로 통일**(도메인 일원화)이다. origin이 하나면 저장소도 하나 → 같은 기기 = 같은 지문. 지문 알고리즘 교체(구 방향 A/B/C)는 그 다음 보강이며, 알고리즘을 안 바꾸고 origin만 통일해도 **기존 데이터 재인식 사고(마이그레이션 폭발) 없이** 해결 가능하다(검증팀 우려 해소).

### 봉합 1순위 — 도메인 일원화 (근본)
- 클라이언트PC가 항상 **단일 origin**으로만 접속하게 고정한다.
- **origin 실태(코드 정독 확정 2026-07-02)** — 클라이언트가 붙을 수 있는 origin이 실제로 **3종**:
  | origin | 언제 | 근거 |
  |---|---|---|
  | `https://{id}.hitpan.kr` | 정식 외부(터널) | .iss:456 `G_PrimaryDomain`, :731·1302 바로가기 |
  | `http://localhost:5234` | 메인PC 본인·LOCAL 폴백 | .iss:526·564·1311·1316 |
  | `http://127.0.0.1:5234` | (사장님 실측 주소) | web-server 무차별 수신 |
- **핵심 결함**: `web-server.ps1:42` 가 `http://+:5234` 로 **모든 host 무차별 수신 + canonical 리다이렉트 0**(host 검사·정규화 코드 없음). 게다가 설치 후 바로가기가 상황따라 갈림(.iss:1302 도메인 vs :1311·1316 localhost) → 같은 메인PC도 다른 origin으로 접속 → 지문 갈림.
- **무엇을→무엇으로**: 여러 origin(localhost/127.0.0.1/도메인) → **정식 단일 `https://{id}.hitpan.kr` 로 고정.**
- **최소 변경**: (a) `web-server.ps1` 에 canonical 리다이렉트 추가(정식 도메인 아닌 host로 들어오면 301) (b) .iss 바로가기를 항상 정식 도메인으로 통일(LOCAL은 예외 설계).

### 봉합 2순위 — 지문을 origin에 덜 의존하게 (보강, 선택)
- 도메인 일원화만으로 대부분 해결되나, localStorage 리셋(캐시삭제·시크릿)까지 막으려면 지문을 기기 특성 기반으로 보강.
- 후보: 환경값(UA+플랫폼+해상도+시간대+언어) 해시 + localStorage 캐시 이중화(구 방향 C). ⚠️ 단독 환경해시(구 방향 A)는 **사무실 동일 기종 충돌**로 여러 기기가 1대로 뭉치는 반대 사고 → 검증팀·CTO 공통 반려. 캐시 병행 필수. 충돌회피용 고엔트로피 신호(canvas 등)는 개인정보·핑거프린팅 규제 있어 보안·법무 검토 후.

### 봉합 3순위 — 사장님 정의 정상 흐름 완성 (F3)
- "처음 접속하는 기기입니다. 등록하시겠습니까?"(슬롯 여유) / "등록된 기기가 아닙니다"(초과) 안내 분기 신설. 현재 조용히 자동 approved INSERT.

### ⚠️ 공통 선결 — 메인PC 판별 (사장님 확정: 메인PC는 인증 면제)
- 메인PC 본인 접속은 슬롯/등록에서 제외해야 함(사장님 확정).
- **판별 근거(코드 정독 확정 2026-07-02)**:
  - ❌ IP 기반 = 불가. `AuthController.cs:56` `HttpContext.Connection.RemoteIpAddress` 원시값만, X-Forwarded-For 파싱 없음 → 터널 경유 시 프록시 IP로 뭉개짐(CTO 지적 확인).
  - ✅ **loopback 판별 = 가능·신뢰**. 메인PC 본인은 브라우저로 `localhost`/`127.0.0.1`(loopback)로 접속(.iss:1311·1316), 클라이언트는 터널 도메인으로만 접속. **접속 host가 loopback이면 메인PC 본인** — `Request.Host`/`RemoteIpAddress.IsLoopback` 판별. **터널은 loopback으로 못 옴(프록시 위조 불가)이라 IP 신뢰 문제와 무관하게 성립.**
  - ✅ **로컬 마커 존재**. 설치 시 메인PC `{app}\bootstrap.conf`(TENANT_CODE·PRIMARY_DOMAIN·BOOTSTRAP_TOKEN, Administrators/SYSTEM만, .iss:825-844) — 클라이언트엔 없음. "이 API가 도는 PC=메인PC" 자명. 필요시 보조 근거로.
- **채택안**: loopback 접속 = 메인PC 면제(슬롯/등록 제외). 단, 도메인 일원화(1순위)로 클라이언트가 모두 정식 도메인으로 오면 loopback=메인PC 등식이 더 깨끗해짐 → 1순위와 함께 가야 안전.

## 5. 검증 기준 (검증팀 동시검증 = 완료 게이트) — CTO 6조건 반영
1. **⭐ 다중 origin 지문 일관성** (CTO 조건 5 — 이번 봉합의 결정 시험): 같은 PC에서 `localhost:포트`→`127.0.0.1:포트`(이미 다른 origin, 실측 확정) 순차 접속 시 **신규 기기 증식 0**. 도메인 일원화가 origin 격리를 실제로 이겼는지 판별하는 유일 게이트. **단일 origin 스모크만으론 거짓 PASS**(CTO 지적) — 반드시 origin 2개 이상.
2. **같은 기기 반복 접속** — 로그아웃→재로그인 N회, tenant_devices 1건 유지(증식 0). 캐시 삭제 후 동일 인식(지문 보강 시).
3. **⭐ 마이그레이션 안전** (CTO 조건 1 — 최대 리스크): 지문 방식/도메인 바꿔도 **기존 등록 기기가 일괄 "새 기기" 재인식 → 슬롯초과 → 로그인 일괄차단(헌법 #20 위반) 안 나는지.** 현 단계 운영 tenant_devices 7건(데모 본인)이라 폭발 모수는 작으나(검증팀 실측), 최초 재접속 1회 유예·재매핑 설계 필수. **운영 반영 전 샌드박스/테스트DB에서만.**
4. **빈 지문 방어** (검증팀 발굴): 지문 보강 후에도 해시 실패 시 `''`가 INSERT로 흘러 `fingerprint NOT NULL`(hitpan_db_clean.sql:3374) 위반 500 안 나게 빈값 스킵 분기 유지.
5. **revoked × 지문교체** (검증팀 발굴): 지문 산식 바뀌어도 폐기 기기 부활/정상 기기 오차단 없는지(demo revoked 2건 기준).
6. **슬롯 한도** — 한도 내 정상, 초과 시 "등록된 기기 아님" 차단·안내(사장님 정의).
7. **처음 기기 안내(F3)** — 슬롯 여유 시 "등록하시겠습니까?" 실제 노출.
8. **메인PC 면제** — loopback 접속은 슬롯 소모·등록 대상 제외.
9. **3관문**: 빌드 errors 0/warnings 0 + ddl-smoke + 독립 반증(SoD).
10. 실측 환경 = 정적 실측은 호스트 무접촉 도구(tests/device-fp-probe, 완료), 동작 검증은 **Windows Sandbox**(휘발성, 헌법 #39). 운영·NCP 무접촉.
