# 기기 지문 origin 격리 — 실측 대본 (샌드박스, 코드변경 0)

> 목적: 사장님 실측 "같은 PC·같은 브라우저인데 매번 다른 기기"의 **진짜 트리거**를 코드 추측이 아니라 브라우저 값으로 못박는다.
> 가설: 지문 `hitpan_fp_id` 는 브라우저 localStorage 에 **origin(scheme+host+port)별로 격리** 저장된다. 같은 PC라도 접속 주소가 다르면(`localhost:5234` ↔ `127.0.0.1:5234` ↔ 터널 도메인) 저장소가 분리돼 새 난수 = 새 기기.
> 헌법 #39: **샌드박스에서만.** 운영 demo(3306)·NCP 절대 무접촉. 관찰은 F12(코드 변경 0).

---

## 준비 (샌드박스 새로 띄워 클린)
1. Windows Sandbox 새로 실행 (휘발성 = 어제 잔재 0).
2. 레포 기동: API(5257) + Web(5234) 로컬 실행. (M4 셋업 스크립트대로)
3. Chrome/Edge 하나 연다.

---

## 관찰 지점 (F12, 값을 눈으로)
로그인할 때마다 아래 2개를 본다:
- **Network 탭** → `login` 요청 클릭 → **Payload(요청 본문)의 `deviceFingerprint` 값**
- **Application 탭 → Local storage → (현재 origin)** → **`hitpan_fp_id` 값**

이 두 값은 같아야 정상(브라우저가 만든 걸 그대로 서버로 보냄).

## 실측 순서 (핵심: 주소만 바꾼다, PC·브라우저는 그대로)

### STEP 1 — localhost 로 로그인
1. 주소창: `http://localhost:5234`
2. 로그인 (admin@hitpan.kr / Admin1234!)
3. F12 → **Network: login payload 의 deviceFingerprint 값 A 기록**
4. F12 → **Application: localStorage `hitpan_fp_id` 값 = A 확인** (같아야 함)

### STEP 2 — 로그아웃 후 localhost 로 다시 로그인 (같은 origin)
1. 로그아웃 → 다시 `http://localhost:5234` 로그인
2. **deviceFingerprint = 여전히 A 인가?**
   - **A 그대로** → 같은 origin·저장소 유지되면 지문 재사용됨 = 정상. (증식 안 함)
   - **A 아님(새 값)** → origin 격리 아닌 다른 리셋 경로가 있다는 뜻 (진단 재조정 필요)

### STEP 3 — 127.0.0.1 로 로그인 (⭐ 결정 시험 — 주소만 바꿈)
1. 주소창만 바꾼다: `http://127.0.0.1:5234` (같은 PC, 같은 브라우저, 포트도 같음 — **host 문자만 다름**)
2. 로그인
3. F12 → **Network: login payload 의 deviceFingerprint 값 B 기록**
4. F12 → **Application → Local storage: 여기 `127.0.0.1` origin 에는 `hitpan_fp_id` 가 비어있거나 B(새 값)** 인가 확인

### 판정
- **B ≠ A (새 난수)** → ✅ **진범 확정: origin 격리.** 같은 PC·같은 브라우저인데 접속 주소(localhost vs 127.0.0.1)만 달라도 저장소가 분리돼 새 기기로 잡힌다. 사장님 실측 = 이것.
- **B = A** → origin 격리는 트리거 아님. 진짜 원인은 다른 곳(배포 시 사이트데이터 정리 등) → 재조사.

### (선택) STEP 4 — 기기 증식 최종 확인
- STEP 1·3 후 각각 로그인됐다면, 샌드박스 **로컬 DB**(운영 아님) tenant_devices 건수를 본다: 1건 → 2건 증식이면 증상 재현 완결.

## 이 실측이 답하는 것
1. "매번"의 트리거가 **origin 격리가 맞는지** (B≠A로 확정/반증)
2. 지문이 **빈값으로 가는지**(deviceFingerprint 가 ''면 F2 빈지문 경로가 진짜 원인)
3. 봉합 방향 판정 근거:
   - origin 격리가 진범 → **도메인 일원화가 봉합의 핵심**(지문 알고리즘만 바꿔선 미해결)
   - 지문이 빈값/미전송 → **알고리즘 안 바꿔도 전송·저장 경로만 고치면 됨**(마이그레이션 폭발 리스크 소멸)

## 결과 기록란 (실측 완료 2026-07-02, tests/device-fp-probe 로 호스트 실측)
- STEP1 값 A (localhost:5599): `01a7075d-6f07-4015-b1fd-8ec97ea6a877`
- STEP2 값(새로고침): **A 그대로** (같은 origin이면 재사용 = 정상, 저장소가 함부로 리셋되진 않음)
- STEP3 값 B (127.0.0.1:5599): `40ba83fe-6bf1-4a1d-96be-5bba281b9693` — **A와 완전히 다름**
- **판정: ✅ origin 격리 진범 확정.** 같은 PC·같은 브라우저·같은 포트, host 문자(localhost↔127.0.0.1)만 달라도 지문 새로 생성. localStorage가 origin별 격리라서. 지문은 빈값 아님(정상 생성됨) → F2 빈지문 경로는 이번 증상의 주범 아님.
- **봉합 함의**: 핵심은 지문 알고리즘이 아니라 "같은 기기=같은 지문" 보장. (근본) 도메인 일원화로 클라이언트 접속 origin 단일화 / (보강) 지문을 origin에 안 묶기(기기특성 해시). 알고리즘 안 바꾸고 도메인만 일원화하면 마이그레이션 사고 없이 해결 가능성.
