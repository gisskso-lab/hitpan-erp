# 히트판 ERP 설계 원칙 (DESIGN_PRINCIPLES)

> **이 문서는 히트판 ERP의 설계·구현·운영 전 과정에서 흔들리지 않아야 할 원칙을 박는다.**
> 모든 작업지시서·리뷰·코드 변경은 이 원칙과 대조된다.
>
> - 최초 확정: 2026-04-24 어벤져스 설계 재정립 회의
> - 문서화: 2026-04-25 (작업지시서 20260425작1)
> - 개정 절차: §9 참고

**이 문서를 누가 읽는가**
- 신규 합류 개발자·디자이너·기획자
- 미래의 Claude Code 세션 (PM 닥터스트레인지)
- 외주 파트너 (인증서·전자세금계산서·설치·CS 등)
- 사장님이 다른 누군가에게 "히트판이 어떻게 만들어지나" 보여줘야 할 때

## 1. 서문 — 히트판이 살아남은 이유

> "레거시 히트판이 VB + Access + 낡은 UI로도 살아남은 이유는 딱 하나. **쓰기가 겁나 쉬웠기 때문이다.**"

히트판은 기술로 이긴 게 아니다. **쉬움으로 이겼다.**

- 현장 직원이 설명서 없이, 교육 없이, 처음 앉아서도 그냥 됐다.
- 그게 히트판의 전부였고, 그게 히트판이 살아남은 이유다.

**새 히트판도 이 정신을 이어간다:**

- 기능이 많아도 **쉬워야** 한다.
- 화면이 예뻐도 **헷갈리면 실패**다.
- 처음 쓰는 직원이 **물어보지 않고** 해결할 수 있어야 통과다.

**최종 통과 기준** — 모든 화면에 적용:

> **"이 화면, 처음 보는 사람이 혼자 쓸 수 있냐?"**

**구체화된 통과 기준 3가지:**

1. **3분 룰** — 현장 직원(경리·구매·창고)이 처음 앉아서 **3분 안에** 핵심 동작을 끝낼 수 있는가.
2. **한 화면 완결** — 스크롤·탭 전환 없이 한 화면에서 핵심 정보가 보이는가.
3. **셀링 포인트** — 베타 체험단·고객에게 **30초 안에** "왜 좋은지" 설명되는가.

> **사장님 철학**: "쉬움 + 탄탄함 = 90% 먹고 들어간다."

## 2. PM 3계명

PM 닥터스트레인지(프로젝트 지휘자)가 매 판단마다 지키는 3가지.

1. **늦더라도 항상 검증한다.**
   - 빠르게 흘려보내느니 한 번 더 본다.
   - "그럴 것이다"는 검증이 아니다.

2. **버튼 이벤트 하나도 소홀히 않는다.**
   - **스텁 버튼·위장 성공·silent swallow는 즉시 반려.** (P0 #1~#7 교훈)
   - 모든 버튼은 실제 동작 또는 명시적 비활성(disabled + 사유 툴팁).
   - 빈 `catch` 블록 금지 — 최소 `_logger.LogWarning(ex, ...)` 한 줄.

3. **현 워크플로우·기존 코드 뒤집는 수정·재작성은 하지 않는다.**
   - 얹는다. 수정한다. 덮어쓰지 않는다.
   - 리팩터링 욕구가 생기면 먼저 멈춘다.

## 3. PM 설계수정 4프로토콜

설계·스키마·API를 **건드려야 할 때** 밟는 순서.

1. **왠만하면 건들지 않는다.**
   - "안 건드려도 되는 방법"을 먼저 찾는다.

2. **건드릴 경우 작업지시서 필수.**
   - 구두·즉흥 수정 금지.
   - 작업지시서 없이 들어간 변경은 반려·롤백.
   - **DB 스키마 변경은 마이그레이션 스크립트 필수**(롤백 가능 형태).

3. **민감 작업은 별도 알림.**
   - 민감 영역 7가지: **DB 스키마 / API 시그니처 / 원장 / 금액 / 인증 / 재고 / 암호화 컬럼**
   - 사장님에게 "지금 민감 작업 들어갑니다" 사전 고지.
   - 근거: §6 무결성 — 이 7개가 깨지면 무결성이 붕괴.

4. **쪼개기 필수.**
   - **논리적 1단위·1커밋** 원칙.
     - 자연 묶음(컨트롤러+서비스+DTO 한 기능 단위)은 1단위로 인정.
     - 무관한 변경 섞지 않음.
   - 위험 구간은 **주당 0.5% 이내** 변경.
   - 한 번에 무관한 여러 영역을 건드리는 수정은 재쪼개기.

## 4. 타임키퍼 5게이트

PM이 **매 변경 직전** 자가 검증하는 5개 질문. 하나라도 "아니오"가 나오면 멈춘다.

1. **안 건드려도 되나?** — 대안을 다 뒤졌나.
2. **작업지시서 제출됐나?** — 없으면 멈추고 발행.
3. **민감 작업인가?** — §3 #3의 7개 영역 중 하나면 사장님 알림.
4. **쪼개기 단위로 왔나?** — 무관한 묶음이면 재쪼개기.
5. **기존 테스트·샘플 영향 없나?** — 깨질 것이 있으면 대응 계획 먼저.

## 5. 4축 설계 규약

장기적으로 히트판이 **확장 가능한 골격**을 갖기 위한 4축. **점진 도입** — 기존 코드 일괄 뒤집기 금지.

### 도입 진행도 (2026-04-25 기준)

| 축 | 현재 진행도 | MVP 도입 범위 | 다음 마일스톤 |
|---|---|---|---|
| 5.1 Contract-First | 0% (미착수) | **신규 API만** (옵션 C) | 계산서 발행 API부터 적용 |
| 5.2 Explicit State Machine | 10% (코드 산재) | MVP 내 100% | 6개 엔티티 YAML 1차 작성 |
| 5.3 UoW + Idempotency | 10% (검증 필요) | MVP 내 100% | UoW PoC + 쓰기 엔드포인트 멱등키 |
| 5.4 Result<T, Error> | 20% (일부 적용) | 신규 컨트롤러부터 전면 | 신규 작성분 100% |

> **§5.1 Contract-First 도입 결정 (2026-04-25 사장님 결재 — 옵션 C)**
> - **MVP 범위**: 신규 작성되는 API만 Contract-First 적용 (예: 계산서 발행, 원클릭 설치 토큰 발급 등)
> - **기존 영역**: 그대로 유지 (회귀 버그 위험 0)
> - **Phase 2**: MVP 후 베타 피드백 반영하며 기존 영역 점진 이전
> - **신규 기준**: 새 컨트롤러 신설 또는 기존 컨트롤러에 새 엔드포인트 추가 시 적용. 기존 엔드포인트 수정은 비대상.
> - **개발팀 혼동 방지**: 작업지시서에 "Contract-First 대상 여부" 필수 명시

### 5.1 Contract-First (`HitPan.Contracts` SharedKernel)

- API 응답·요청 DTO와 도메인 이벤트는 **별도 프로젝트**에 둔다.
- Web·API·외부 통합이 **같은 계약**을 참조한다.
- **이유**: 계약이 코드 조각마다 흩어지면 프론트-백 불일치·마이그레이션 지옥.

### 5.2 Explicit State Machine

- 상태를 가지는 6개 엔티티(**발주·매입·수주·판매·계산서·반품**)는 상태 전이를 **YAML로 문서화**한다.
- 코드의 상태 체크는 YAML을 진리로 삼는다.
- **저장 위치**: `docs/design/state-machines/{entity}.yaml` (6개 파일)
- **DB enum/varchar 컬럼과 YAML의 동기화 책임은 DB 매니저**가 진다.
- **동기화 검증**: PR 머지 전 DB 매니저가 수동 비교 (자동화는 Phase 2 추후).
- **이유**: 상태 전이가 코드 여기저기 흩어지면 "이 상태에서 이 버튼 눌러도 되나?"를 아무도 답 못 함.

### 5.3 UoW + Idempotency

- **Unit of Work**: EF + Dapper가 **같은 트랜잭션**을 공유한다.
  - EF의 `IDbContextTransaction`을 Dapper에 주입.
  - **현재 검증 상태**: PoC 미완료 (CTO 지적 [C-1]). MVP 전 UoW 헬퍼 클래스 신설·검증 후 클래스명·파일경로 본 문서에 추가 기재.
- **Idempotency**: 쓰기 엔드포인트(확정·발행·분개)에 **멱등키** 헤더 필수.
  - 표준 헤더명: `Idempotency-Key` (UUID v4 권장)
  - **저장소**: `idempotency_keys` 테이블 (DB), TTL **24시간**, 키별 결과 캐시
  - 같은 키 재요청 → 같은 응답, 부작용 1회만.
  - `monthly_summary`는 `source_id` UNIQUE 키로 보강.
- **이유**: 네트워크 재시도·저장 연타로 인한 중복 확정·중복 원장 반영 원천 차단.

### 5.4 Result<T, Error>

- 내부 예외는 `Result<T, Error>`로 감싸 반환한다.
- **내부 에러 메시지**와 **사용자 표시 메시지**를 분리.
- HTTP 응답은 사용자 메시지만 노출. 로그에만 내부 에러.
- **HTTP 상태 매핑 원칙**: `Validation` → 400, `NotFound` → 404, `Conflict`(상태머신/멱등) → 409, `Forbidden`(권한·테넌트) → 403, `Unexpected` → 500. 상세 매핑은 별도 가이드.
- **이유**: 사용자에게 스택트레이스 노출 금지 + 디버깅 추적 가능성 동시 확보.

## 6. 무결성 재정의

히트판이 말하는 "무결성"은 학술 용어가 아니다.

> **고객이 화면에서 누른 대로 데이터가 유실·왜곡·중복 없이 끝까지 흐르고, 누가 언제 눌렀는지 추적 가능한가.**

### 6.1 데이터 무결성

- **유실 없음** — 확정 버튼 눌렀는데 저장 안 됐다? 실패.
- **왜곡 없음** — 100개 매입했는데 원장에 99개? 실패.
- **중복 없음** — 저장 연타로 같은 매입이 2번 원장에? 실패.
- **끝까지 흐름** — 매입 확정 → 재고 반영 → 분개 기표. 중간에 끊기면 실패.
- **원장 INSERT ONLY** — `stock_ledger`, `journal_lines`는 UPDATE/DELETE 금지. 정정은 역분개로.

### 6.2 시각적 무결성

- 사용자가 "확정됐다"고 **시각적으로 확신**하는가. (스피너→성공 토스트→상태 칩 변경)
- 확정 후 화면은 **readonly**로 잠근다 — 사용자가 "아직 수정 가능한가?"로 의심하지 않게.

### 6.3 감사 추적 (Audit Trail)

- 누른 사람(`user_id`), 누른 시각(`created_at`), 무엇을 눌렀는지(`action`)가 **남는가**.
- 추적 못 하면 무결성 깨진 것으로 본다.
- **MVP 전 결정 사항**: before/after 스냅샷 저장 여부 — 사장님·CTO 별도 안건으로 처리 (CTO 지적 [C-4]). SOX·세무 감사 대응 시 핵심.

### 6.4 현장 시각

- 경리가 "내가 누른 게 맞나?" 의심하면 **무결성 깨진 것**.
- 구매가 "이 발주, 진짜 들어갔나?" 다시 클릭하게 만들면 **무결성 깨진 것**.

테스트·리뷰·승인의 **최종 질문**은 이것뿐이다: **"누른 대로 흘렀나? 누가 언제 눌렀는지 보이나?"**

## 7. 3계층 세금계산서 구조

세금계산서는 **3계층**으로 분리되어 있다. **재확인·재협의 금지** — 사장님 확정 설계.

```
거래명세서 확정
    ↓
[계산서 발행] 버튼        ← 1계층: 내부 마킹 (현재 구현 범위)
    ↓
[전자세금계산서 발행] 버튼  ← 2·3계층: 국세청 연동
    ├─ 2계층: 즉시발행
    └─ 3계층: 예약발행 (타이머 일괄)
```

**불변 규칙:**

- 계산서 발행과 전자발행은 **완전히 다른 버튼**.
- 계산서 발행 상태가 **전자발행의 전제 조건**.
- 전자발행 단계(자체개발 vs 외주, 시점)는 **사장님 별도 결정 사항**.

**버튼 명명 규약 (현장 혼동 방지):**

- 1계층 버튼명: **"계산서 발행"** (회색 → 활성 시 파랑)
- 2계층 버튼명: **"전자세금계산서 즉시 발행"**
- 3계층 버튼명: **"전자세금계산서 예약 발행"**
- 같은 색·같은 위치·같은 폰트로 묶지 않는다 — 시각적으로도 분리.

**고객 설명 가능성 (영업·마케팅 기준):**

- "왜 버튼이 2개로 나뉘어 있나요?" 질문에 **30초 안에** 답할 수 있어야 함.
- 표준 답변: "계산서 발행은 우리 시스템 내 마킹이고, 전자세금계산서는 국세청 전송입니다. 전송 시점을 스스로 정하실 수 있게 분리했습니다."

**관련 외부 문서:**

- 전자발행 인증서 분리 정책: 메모리 `project_cert_separation` 참조 (범용=법인 / 간편=개인 2트랙)
- 전자세금계산서 외주 검토: 메모리 `project_etax_outsource` 참조

## 8. 절대 원칙 (CLAUDE.md와 동기)

CLAUDE.md §절대 원칙 17개는 이 문서의 일부다. 요약:

1. 수정 OK, 덮어쓰기 금지
2. `tenant_id`는 JWT 클레임에서만
3. INSERT ONLY 원장 (`stock_ledger`, `journal_lines`)
4. 금액은 `decimal`
5. 암호화 필수 컬럼 — Value Converter 미적용 PR 반려
6. 원장 반영은 `confirmed` 시점에만
7. SaaS 계층 ↔ ERP 내부 권한 혼용 금지
8. 6단계 워크플로우 순서 엄수
9. DB는 미리 다, 코드는 필요할 때만
10. 한 화면씩 완성 → 사장님 확인 → 승인 → 써밋
11. 권한은 어드민이 직접 설정 (업종·규모별 템플릿 금지)
12. 인터페이스 확장 시 모든 구현체 grep 필수
13. 새 SQL 작성 전 DESCRIBE 테이블 의무
14. Razor(.razor) 파일에 C# raw string(`"""..."""`) 금지
15. 빈 catch 블록 금지 (최소 `_logger.LogWarning`)
16. `MySqlConnection` + `Task.WhenAll` 조합 금지
17. 신규 DB 테이블 `ENGINE=InnoDB` 명시

## 9. 장애 등급 (CTO 신설 [A-1])

무결성이 깨졌을 때 **얼마나 심각한가**를 판단하는 공통 기준. 작업지시서·인시던트 리포트·우선순위 결정의 근거.

## 11. 문서 운영 규칙 및 결재 체계

- 이 문서는 **설계 원칙의 단일 출처(Single Source of Truth)**.

### 11.1 결재 라인 — 3중 검증 → CTO → 사장님 (2026-04-25 확정)

```
[1] PM 닥터스트레인지 (작업지시서 발행)
        ↓
[2] 어벤져스 매니저 8명 (파트별 리뷰)
        ↓ ─────────── 3중 검증 게이트 ───────────
[3] 데이비드 박 — DB 보안 검증
[4] 데이비드 박 — 데이터 정합성 검증
[5] 브라운킴 — 파이프라인 정상 가동 검증
        ↓ ──────────────────────────────────────
[6] CTO 래리 앨리슨 — ⭐ 최종 검증자 (Final Verifier)
    · 3중 검증 결과 종합 + 기술 적정성 + 전략 리스크 검토
    · 검증 충돌 시 조율·재검증 지시 권한
    · 추가 리스크 발견 시 사장님께 별도 안건 제기 권한
    · 검증 미흡 시 반려·재검증 명령 권한
        ↓
[7] 사장님 (최종 승인 — 사업·전략 결정에 집중)
```

> **CTO는 단순 결재 도장이 아닌 "최종 검증자(Final Verifier)"** — 사장님께 정제된 안건만 올라가도록 책임지는 자리. (2026-04-25 사장님 지시 확정)

### 11.2 검증 책임자 직무

| 검증 | 담당 | 검증 영역 |
|---|---|---|
| **DB 보안** | 데이비드 박 (DB Security Verification Manager) | SQL 인젝션 / RLS / 암호화 컬럼 / 백업 암호화 / 권한 최소화 / 감사로그 |
| **데이터 정합성** | 데이비드 박 | 원장 INSERT ONLY 준수 / 금액 decimal / FK 무결성 / 테넌트 격리 / 멱등성 |
| **파이프라인 정상 가동** | 브라운킴 (Backend & Pipeline Architect) | 매입→재고→분개 흐름 / 판매→계산서→전자세금계산서 흐름 / UoW 트랜잭션 / 상태 전이(State Machine) |

**SoD 원칙 (Segregation of Duties)**:
- **브라운킴**은 **설계·구현(Build)**, **데이비드 박**은 **검증(Verify)** — 같은 사안을 **다른 시각**으로 본다.
- 자기가 만든 것을 자기가 검증하지 않는다.

### 11.3 운영 트랙 (경량/풀)

| 트랙 | 결재 단계 | 적용 대상 |
|---|---|---|
| **경량 트랙** | [1]→[2]→[6]→[7] (4단계, 검증 생략) | UI/CSS/문구/리포트 출력 형식 |
| **풀 트랙** | [1]→[2]→[3]→[4]→[5]→[6]→[7] (7단계) | 민감 작업 7개 영역 (§3 #3) — DB 스키마/API 시그니처/원장/금액/인증/재고/암호화 컬럼 |

**트랙 판정**: PM이 작업지시서 발행 시 트랙 명시 → CTO가 트랙 적정성 확인.
