## §0. 결론 한 줄

**래퍼(`publish-run.sh`) 인자를 건드리지 않고**, EXE 를 zip 과 같은 게시 단위로 묶는다.
신뢰경계 무변경. 한 번 게시 = **zip + EXE 동반**.

## §1. 착수 전 실측 — 지시서 조사 3건 + 추가 2건

| # | 조사 | 결과 |
|---|---|---|
| 1 | nginx 가 `.exe` 를 막는가 | ❌ 안 막음. zip 200 / 없는 exe 404(부재) / 디렉터리 목록 404(정상) → **파일만 올리면 200** |
| 2 | `publish-run.sh` 가 EXE 를 받는가 | ❌ 거부. `--zip`/`--manifest` 2인자 외 전부 `die` ([`publish-run.sh:47-61`](../../../installer/deploy/publish-run.sh#L47-L61)) — **의도된 보안장치(B-2)** |
| 3 | EXE 크기 | 약 **260MB** (1.2.29 = 261,319,039 bytes) |
| **4** ⭐ | **CI 가 EXE 를 만들 수 있는가** | ✅ **된다.** `build-installer.yml` 7/22 성공 4회, 아티팩트 `HitPanInstaller-1.2.39` 실재 |
| **5** ⭐ | 워크플로 주석의 *"이 CI 로 EXE 가 만들어진 적이 없다"* | **옛 상태 설명.** 7/21~22 봉합 완료(실패 3 → 성공 4). 주석이 안 갱신됨 |

> ⭐ **4·5 가 판단을 바꿨다.** 지시서 작성 시엔 "EXE 생산 자체가 되는가"를 몰랐다.
> 된다면 남은 구멍은 **"만든 EXE 를 NCP 로 보내는 것" 하나뿐**이다. 범위가 줄었다.

## §2. 현재 배선 (실측)

```
build-installer.yml  ──ISCC──> installer/output/*.exe
                                  ├─ upload-artifact (30일·로그인 필요)
                                  └─ GitHub Release (태그 push 시만)
                                        ⛔ NCP 전송 스텝 없음

deploy-update.yml    ──build──> dist/updates/hitpan-{V}.zip
                                  └─rsync─> NCP /tmp ─래퍼─> /var/www/updates/packages/  ✅

랜딩 DownloadPage ──본다──> https://updates.hitpan.kr/packages/HitPan-ERP-Setup-{V}.exe  ← 404
```

**세 곳이 서로 다른 목적지를 본다.**

## §3. 설계 — ①안 상세

### 3-1. 원칙

| 원칙 | 이유 |
|---|---|
| **래퍼 인자 불변** | `--zip`/`--manifest` 2인자 유지. sudoers·B-2 오버라이드 차단 그대로 |
| **한 게시 = zip + EXE** | 사장님 오더 *"자동업데이트와 묶는다"*. 구조적으로 묶여야 다음에 또 안 빠진다 |
| **EXE 도 sha 검증** | zip 과 동급으로 전송 손상·변조 차단 |
| **fail-closed** | EXE 도달 실패 시 게시를 실패 처리 |

### 3-2. 변경 지점 3곳

| # | 파일 | 무엇 |
|---|---|---|
| A | `.github/workflows/deploy-update.yml` | EXE 빌드(ISCC) 추가 + `/tmp` 로 rsync + sha 전달 |
| B | `installer/updates/publish-update.sh` | `packages/` 에 EXE 배치 + sha 대조 (zip 배치 옆) |
| C | `installer/deploy/publish-run.sh` | **EXE 경로 접두 검증만 추가. 인자는 불변** |

### 3-3. EXE 를 래퍼에 어떻게 넘기나 — **인자 추가 없이**

래퍼는 `--zip /tmp/hitpan-{V}.zip` 을 받는다. 버전이 그 안에 있다.
**EXE 경로는 버전에서 유도**한다 — 새 인자가 필요 없다.

```bash
# publish-run.sh 안에서 (인자 파싱 불변)
VER_FROM_ZIP="$(basename "$ZIP" .zip)"        # hitpan-1.2.41
VER="${VER_FROM_ZIP#hitpan-}"                  # 1.2.41
EXE="/tmp/HitPan-ERP-Setup-$VER.exe"           # 유도 — 인자로 안 받음
[[ -f "$EXE" ]] || die "EXE 없음 — 게시 중단(fail-closed)"
```

> **이것이 ①안의 핵심이다.** 인자를 안 늘리므로 sudoers·B-2 차단이 그대로다.
> 경로도 `/tmp/HitPan-ERP-Setup-{3자SemVer}.exe` 로 고정이라 임의 경로 주입이 불가능하다.

### 3-4. sha 검증 방식

zip 은 `manifest.sha256` 과 대조한다. EXE 는 manifest 에 없으므로 **별도 파일**로 넘긴다.

```
/tmp/HitPan-ERP-Setup-{V}.exe          ← EXE 본체
/tmp/HitPan-ERP-Setup-{V}.exe.sha256   ← 러너가 계산한 sha (rsync 동반)
```

래퍼가 NCP 에서 실측 sha 를 계산해 이 파일과 대조한다. 불일치 시 `die`.

> ⚠️ **한계 명시**: 이 대조는 **전송 손상**을 잡지 훼손된 러너를 잡지는 못한다(둘 다 러너발).
> zip 은 B-4 독립 재조회(GitHub API 로 commit·run 확인)가 그 역할을 하고, **EXE 는 같은 게시
> 단위 안에 있으므로 그 B-4 통과에 함께 묶인다.** 즉 EXE 단독 위조 경로는 열리지 않는다.

## §4. 하지 않은 것 (범위 밖 — 명시)

| 안 한 것 | 왜 |

| EXE 전용 래퍼 신설 | ③안. sudoers 추가 = 인프라 조작(#29) |
| 코드 서명(Authenticode) | 별건. `build-installer.yml:186` "결재 2 OK 후 활성화" 주석대로 미결 |
| 랜딩 가입·프로비저닝 | 지시서 §6 후속 |
| 구버전 EXE 정리 정책 | 디스크 관리 별건 |
| **NCP 상주본 갱신** | 🔴 **PM 이 못 한다** — §6 참조 |

## §5. 리스크

| 리스크 | 대응 |
|---|---|
| EXE 260MB rsync 로 게시 시간 급증 | 측정 후 판단. 필요시 별 잡 분리 |
| NCP 디스크 부족 | 게시 전 `df -h` 확인 스텝 추가 |
| ISCC 빌드가 deploy-update 에 추가되며 게시 시간 +6~8분 | 현 4분 + 약 7분 = 약 11분. 허용 범위 |
| 기존 zip 전용 게시가 깨짐 | EXE 부재 시 `die` 이므로 **기존 경로도 EXE 없으면 실패** ← 의도됨(fail-closed) |

## §6. 🔴 PM 이 못 하는 것 — 사장님 실행 필요

`publish-update.sh`·`publish-run.sh` 는 **NCP 상주본**이 진실원이다(`/opt/hitpan/deploy/`).
리포 파일을 고쳐도 **NCP 에 반영하지 않으면 아무 일도 일어나지 않는다.**

| 단계 | 누가 |
|---|---|
| 리포 스크립트·워크플로 수정 | PM (본 작업) |
| **NCP 상주본 갱신** | **사장님 SSH 1회** (헌법 #29 — PM 원격 실행 금지) |
| 게시 재실행 | 사장님 dispatch + 폰 승인 |

> 상주본 갱신 절차는 [4] 검증 통과 후 별도 문서로 정리해 올린다.

## §6-2. [3-V] 병렬검증 적발 6건 → 봉합 (2026-07-30)

보안상무 병렬검증이 **BLOCKER 1 · HIGH 2 · MEDIUM 2 · LOW 1** 을 적발했다.
**보안 경계는 안 넓어진 것으로 확인**됐다(주입 10종 전부 차단, 래퍼 인자 2개 불변, sudoers 무변).
그러나 **PM 의 가정 하나가 틀렸다.**

| # | 적발 | 봉합 |
|---|---|---|
| **D2** 🔴 BLOCKER | **`emergency-recovery.sh:132` 가 래퍼를 우회해 `publish-update.sh` 를 직접 부른다.** PM 은 *"래퍼 경유면 항상 설정된다"* 고 가정했으나 **두 번째 호출자가 이미 리포에 있었다.** 그 경로에선 manifest 만 새 버전으로 올라가고 EXE 는 warn 하나 남기고 빠진다 = **오늘 봉합하려는 404 가 비상경로에 그대로 재현** | ① `publish-update.sh` 의 조용한 skip 제거 → **미지정이면 `die`**. 예외는 `HITPAN_ALLOW_NO_INSTALLER=1` 명시 필요 ② `emergency-recovery.sh` 가 래퍼와 동일 규칙으로 EXE 를 유도해 export. 없으면 예외 플래그 + 경고 3줄 + 감사로그 |
| **D3** 🔴 HIGH | **EXE 가 시크릿 게이트를 한 번도 안 거친다.** zip 게이트는 `dist/updates/*.zip` 만 스캔. EXE 는 zip 에 없는 **`hitpan_db.sql`(DDL) + 헬퍼 스크립트 4종**을 더 담는데 무검사 | EXE 전용 동봉물 6종을 **컴파일 전에 소스에서 스캔**하는 게이트 신설(EXE 는 LZMA 라 산출물을 못 연다). 로컬 dry-run 으로 위양성 0 확인 |
| **D4** 🟠 HIGH | **strip 이 EXE payload 에도 적용돼 `build-installer.yml` 과 산출물이 갈라진다** | **위험도 재판정 = 낮음** (§6-3). 단 사실은 명세에 남긴다 |
| **D1** 🟡 LOW | `[IO.File]::WriteAllText` 상대경로가 .NET CWD 기준 | rsync 스텝이 fail-closed 로 막는다. 다만 11~15분 태우고 실패 — 운영 중 개선 |

| **D6** 🟠 MEDIUM | 롤백 후 orphan EXE 260MB 누적, 회전 로직 없음 | 디스크 관리 별건 — 후속 |

> **D2 가 이번 검증의 값어치다.** PM 이 검증하지 않은 가정("호출자는 래퍼뿐")을 병렬검증이 소스에서
> 반증했다. 게시 후 발견했으면 **비상 상황에서 404 가 나고 아무도 못 알아챘을** 건이다.

## §6-3. D4 위험도 재판정 — 낮음 (근거)

검증팀 우려: *"strip 이 EXE 에서 환경별 appsettings 를 걷어내는데, 신규 설치가 거기 의존하는지 확인이 없다."*

**실측으로 확인했다:**

| 확인 | 결과 | 근거 |
|---|---|---|
| Blazor 가 읽는 키 | `Configuration["ApiBaseUrl"]` | [`src/HitPan.Web/Program.cs:14`](../../../src/HitPan.Web/Program.cs#L14) |
| 그 값이 어느 파일에 있나 | **`wwwroot/appsettings.json`** (환경접미사 **없음**) | 해당 파일 실독 |
| strip 이 그 파일을 걷어내나 | ❌ **아니다.** 정규식 `^appsettings\.[A-Za-z]+\.json$` 은 접미사 있는 것만 | 어제 실행 대조 확인 |
| 인스톨러가 고치는 대상 | `appsettings.json` **먼저**, `Local.json` 은 추가로 | [`HitPan-Universal.iss:1046-1061`](../../../installer/HitPan-Universal.iss#L1046-L1061) |
| `Local.json` 없으면 | `FileExists` 검사 후 **조용히 Exit** — 오류 아님 | [`:1014-1017`](../../../installer/HitPan-Universal.iss#L1014-L1017) |

> **⇒ `Local.json` 이 빠져도 부트에 지장 없다.** WASM 이 실제로 읽는 `appsettings.json` 은 보존된다.
> 오히려 `api-demo.hitpan.kr` 고정값이 든 파일이 고객 EXE 에 안 실리는 편이 **더 안전**하다(헌법 #39 정신).
>
> ⚠️ **다만 "두 워크플로가 다른 EXE 를 만든다"는 사실 자체는 남는다.** `build-installer.yml` 에는
> strip 이 없다. 어느 쪽으로 빌드했느냐에 따라 EXE 구성이 달라지는 상태는 정합하지 않다.
> **후속으로 `build-installer.yml` 에도 strip 을 넣어 통일**해야 한다(별건 — 본 작업 범위 밖).

### 게이트 실효성 실측 (N2·B3 봉합 후)

검증팀이 심었던 시크릿을 그대로 넣어 시험했다.

| 심은 것 | 최초 게이트 | 봉합 후 |
|---|---|---|
| `IDENTIFIED BY 'Hitpan2025!'; -- MariaRootPw` | ❌ **SUPPRESSED** | ✅ 적발 |
| `sk-ant-api03-…` | ❌ 통과 | ✅ 적발 |
| `ghp_…` | ❌ 통과 | ✅ 적발 |
| `set DBPASS=Hitpan2025!` | ❌ 통과 | ✅ 적발 |
| `Server=…;Pwd=RealSecret99;` | ✅ | ✅ 적발 |

| `%DB_PASSWORD%` · `$env:SECRET` · `CHANGEME_…` (안전) | — | ✅ **제외** |

**결과: 6건 적발 / 위양성 0.** 실제 동봉물 6종 재스캔도 **적발 0**(위양성 없음).

> ⚠️ **커버리지 한계 명시**(검증팀 요구): 이 게이트는 **알려진 형태의 시크릿**만 잡는다.
