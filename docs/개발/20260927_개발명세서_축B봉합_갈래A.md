## 7. 검증팀에 요청 · 내가 판단한 것

### 🔴 내가 판단한 것 (PRD·설계에 없어서 내가 정한 것 — 여기부터 봐 주십시오)

1. **`ToSessionDeviceKind` 를 새로 만들었다** (`DeviceTypeResolver.cs:224`).
   - **왜**: DESCRIBE 결과 `user_sessions.device_kind` 는 `enum('pc','mobile')` **두 값뿐**인데, `ResolveDeviceType` 은 `tablet` 을 돌려줄 수 있다(신고값 `tablet` + 휴대기기 UA ⇒ 어긋남이 아니라 신고값 존중). 그 값을 그대로 넣으면 **INSERT 가 실패**해 세션 행이 안 남는다. 절B 와 겹쳐 *"로그인은 되는데 `sid` 없는 토큰"* 이 태블릿 사용자 전원에게 일어난다.
   - **판정이 아니라 접기다**: 한 줄(`pc` 냐 아니냐)이고, 판정은 위에서 이미 끝났다. §3 #2(판정 자리 둘 금지)에 걸리지 않게 **판정과 같은 파일**에 뒀다.
   - ⚠️ **이 판단을 반증해 주십시오.** 다른 길은 ① 절G 에서 enum 에 `tablet` 추가(범위 밖·과금 축 건드림) ② 저장 직전 SQL 에서 접기(판정이 SQL 로 흩어짐) 였다.
2. **절C 가드를 토큰 회전 *앞*에 뒀다** (`:531`). 회전 뒤에 거절하면 쓴 토큰은 이미 소비돼 새 토큰을 굽고 버린다. 설계 §5 는 *"내 세션 한 줄을 먼저 읽는다"* 만 적고 회전과의 순서를 안 정했다.
3. **만료 판정을 DB 안에서 했다** (`CASE WHEN expires_at > UTC_TIMESTAMP(6)`). 시각을 받아 코드에서 비교하면 서버·DB 시간대 해석에 따라 *"만료됐나"* 의 답이 갈린다.
4. **절D 감사 문구에 밀어낸 건수와 이전 사용 시각을 넣었다**. `description` varchar(500) 안이고 개발용어는 없다.

### 특히 봐줬으면 하는 곳

- `AuthService.cs:160-166` — **순서**. INSERT 실패 시 `sid` 가 정말 안 실리는지, 그리고 `sid` 없는 토큰이 미들웨어를 통과하는지는 **절E(갈래 B)와 맞물린다**. 양쪽을 같이 태워 봐 주십시오(G-B5).
- `AuthService.cs:531` — 가드가 `sid` **있을 때만** 돈다. 옛 토큰(sid 없음)은 종전 그대로 통과한다(의도).
- `DeviceTypeResolver.cs:224` `ToSessionDeviceKind` — 위 §7-1.
