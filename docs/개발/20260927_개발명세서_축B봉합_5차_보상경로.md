## 3. 어떻게 만들었나

### 3-1. ① `G_B13b` 재설계 — 회전 **트랜잭션 안**에서 실패시킨다

**무엇이 틀렸었나** — 3차 시험은 `StealRefreshToken`(refresh_tokens 전삭)으로 401 을 만들었다.
그 401 은 `RefreshAsync` 의 **회전 전** 확인(*"로그아웃된 토큰입니다"*)에서 나오고, 그 자리는
`conn.BeginTransaction()` **앞**이다 ⇒ `CompensateNewSessionRowAsync` 가 **0회** 불렸다.
그래서 보상을 무력화해도 PASS 했다(PM 음성대조군 ② 가 그 증거).

**어떻게 트랜잭션 안에서 실패시켰나** — `StealRefreshTokenWhenSessionInserted` 트리거를 쓴다.
`user_sessions` 의 `AFTER INSERT` 로 그 계정의 `refresh_tokens` 를 지우므로,
운영 코드는 다음 순서를 **실제로** 탄다:

1. 토큰 판독(`SELECT is_revoked …`) **통과** — 이 시점엔 토큰 행이 살아 있다
2. `InsertSessionAsync` 로 새 세션 행 INSERT → **그 순간 트리거가 토큰을 지운다**
3. `conn.BeginTransaction()` → `DELETE … refresh_tokens …` = **0행** ⇒ 단일사용 거부
4. `tx.Rollback()` → `UnauthorizedAccessException("이미 사용된 토큰입니다…")`
5. `catch (UnauthorizedAccessException)` → **`CompensateNewSessionRowAsync` 실제 호출**

시험은 그것이 **그 401 인지** 두 줄로 확인한다 — `Assert.Contains("이미 사용된")` **그리고**
`Assert.DoesNotContain("로그아웃된")`. 두 번째 줄이 3차의 재발을 막는다.

**「이어받은 세션이 살아남는지」를 실제로 재는가 — 정확히 적는다.**
🔴 **이어받은 갱신 그 자체로는 음성 대조군이 성립하지 않는다. 구조상이다.**
보상 인자는 `isNewSession && sessionRecorded ? sessionId : null` 이므로
이어받은 갱신(`isNewSession == false`)은 인자가 **항상 `null`** 이고
`CompensateNewSessionRowAsync` 첫 줄이 즉시 반환한다 ⇒ helper 안의 `WHERE session_id` 를
`WHERE user_id` 로 바꿔도 **그 시나리오의 결과는 안 바뀐다**(= 과잉 봉합을 못 잡는다).

⇒ 과잉 봉합이 실제로 드러나는 모양으로 바꿨다: **보상이 실제로 도는 갱신**(새 세션을 만든 갱신)에
**같은 계정의 살아 있는 `pc` 세션**(= 다음 갱신이 이어받을 그 행)이 **공존**하게 만들고,
그 행이 살아남는지를 잰다. 시험이 확인하는 것은 두 개다 —
`SessionCount == 1`(보상이 만든 행만 지웠다) · `IsAlive(workingSid)`(일하는 PC 가 살아 있다).

⚠️ 출발 상태는 **운영 경로로만** 만든다(행을 심지 않는다): 정상 로그인 1회(일하는 PC) +
`HideSessionTable` 상태에서 로그인 1회(`sid` 없는 옛 토큰). 축 B 기본값이 꺼짐이라
(`tenant_settings` 행 없음 → `?? 0`) 두 번째 `pc` 로그인이 일하는 PC 를 밀어내지 않는다.

### 3-2. ② 세 번째 실패 경로 — 어디를 어떻게 감쌌나

`AuthService.RefreshAsync` — 종전에는 연결 열기 블록(`if (conn.State != Open)`)과
`using (var tx = conn.BeginTransaction())` 이 **`try` 밖**이었다. 거기서 터지면
방금 넣은 세션 행이 보상 없이 남는다(3차 주석이 *"그 둘뿐"* 이라 단정한 그 구멍).

**바꾼 방식 — 보상 호출 자리만 늘렸다. 트랜잭션 구조는 새로 짜지 않았다.**

- `System.Data.IDbTransaction tx;` 를 먼저 선언하고, **연결 열기 + `tx = conn.BeginTransaction()`** 두 줄만 `try` 로 감쌌다.
- 그 `catch (Exception)` 이 `CompensateNewSessionRowAsync(conn, user, isNewSession && sessionRecorded ? sessionId : null, "회전 준비 중 예외(연결 열기·트랜잭션 시작)")` 를 부르고 **`throw;`** 한다.
- 아래 본문은 `using (tx)` 로 **그대로** 이어진다 — 기존 `catch` 두 곳은 **한 줄도 안 건드렸다.**

**원인 예외가 그대로 전파되는가 — 잰다.**
`throw;`(재던지기)이므로 원인 예외 종류·메시지가 보존된다. `G_B13c` 가
`Assert.ThrowsAsync<InvalidOperationException>` + `Assert.Contains("게이트 주입 G-B13c", ex.Message)`
로 **그것을 직접 확인한다** — 보상이 401/500 으로 바꿔치면 그 자리에서 FAIL 한다.

**`G_B13c` 가 그 경로를 어떻게 재는가.** `BeginTransaction` 은 DB 상태만으로 결정적으로
터뜨릴 방법이 없다 ⇒ `BeginTransactionFailingConnection`(시험 내부 `sealed class`, `DbConnection` 상속)이
**`BeginDbTransaction` 한 동작만** 던지고 나머지 전부를 실제 `MySqlConnection` 에 넘긴다.
SQL·표·트랜잭션 의미는 전부 실제 MariaDB 가 처리한다 — 래퍼가 하는 일은 **고장 하나의 결정적 재현**이고,
판정(*행이 남았나*)은 운영 코드와 실제 표가 한다.

🔴 **양성 조건도 함께 잰다.** `MarkSessionInsert`(`user_sessions` `AFTER INSERT` → `security_alerts`)로
*"세션 INSERT 가 실제로 돌았다"* 를 남긴다. 이게 없으면 INSERT 가 아예 안 돌아도
`0 == 0` 으로 통과하는 **빈 통과**가 된다. 시험은 `AlertCount(...) == 1`(돌았다)과
`SessionCount == 0`(보상이 지웠다)을 **둘 다** 확인한다.

| 2 | **R-4** (Web 이 D-3 문장을 고정 스낵바로 덮는다) | 화면 결재 사안 · 범위 밖 |
| 3 | **R-5** (INSERT 성공 + 응답 실패 → `sessionRecorded == false` 라 보상 대상 아님) | 보상 인자 자체를 바꿔야 하고 그건 구조 변경이다. **네 번째 실패 모양이며 이번에 닫지 않았다** |
| 4 | **R-6** (`tx.Rollback()` 실패 시 보상 DELETE 가 조용히 무효) | 연결이 상한 경우 새로 만든 ③번째 경로도 **같은 한계**다 — 주석에 명시하고 닫지는 않았다 |
| 5 | `CompensateNewSessionRowAsync` 에 `tenant_id`·`user_id` 방어 술어 추가 | [4] §2-4 의 ⚠️ 제안. 지시에 없어 손대지 않았다(PK + 서버생성 Guid 라 #2 위험 0) |
| 6 | 이어받은 갱신(`isNewSession == false`) + tx 안 401 조합의 **직접 재현** | **결정적 재현 방법이 없다.** 토큰 판독과 회전 `DELETE` 의 술어가 같으므로 `deleted == 0` 을 만들려면 그 사이에 토큰 행을 지워야 하는데, 이어받은 경로에는 그 사이에 `user_sessions` 쓰기(=트리거 걸 자리)가 없다. ⇒ §3-1 대로 **보상이 실제로 도는 모양**으로 옮겨 쟀다 |
| 7 | `StealRefreshToken` 헬퍼 제거 | 안 지웠다(#1). 쓰지 말라는 경고 주석만 붙였다 — 이 헬퍼가 만드는 401 은 회전 **전** 에서 걸린다 |
