## 7. 검증팀에 요청 (자기 판단 아님)

- **특히 봐줬으면 하는 곳 ①** — `DB-128` 의 `MODIFY` 는 컬럼이 **이미 있다**고 전제한다. DB-127 이 아직 안 붙은 고객 DB 에서는 러너가 번호 순서(`MigrationRunner.cs:68` `OrderBy(num)`)로 DB-127 → DB-128 을 돌리므로 성립한다고 봤다. **그 전제가 맞는지** 봐달라 — 틀리면 1054 로 마이그가 멈춘다.
- **특히 봐줬으면 하는 곳 ②** — `UPDATE tenant_settings SET … WHERE enforce_single_pc_login <> 0` 은 **고객이 일부러 켜둔 테넌트가 있었다면 그것도 내린다.** 지금은 켤 경로가 없으니 무해하다고 판단했으나, 켜는 결재가 **DB-128 보다 먼저** 나간 DB 가 있으면 그 설정을 되돌린다. 위험 낮음으로 봤지만 내 판단이다.
- **회귀 우려 ①** — `DB-127` 의 `DEFAULT 1 → 0` 은 **아직 DB-127 을 안 돌린 DB** 에만 효과가 있다. 이미 돌린 DB(개발·CI)는 DB-128 이 처리한다. 두 경로가 서로를 덮지 않는지 봐달라.
- **회귀 우려 ②** — 축 B 가 **꺼진 채** 출하되면, A·B 가 살린 차단 코드는 실행 경로에 들어가지 않는다. 즉 **이번 차수에서 차단 자체는 고객 환경에서 검증되지 않는다.** 「봉합했다」와 「동작을 확인했다」를 구분해 판정해달라.
- **회귀 우려 ③** — `DB-127` 주석에서 순환논증(*"과금으로 이어지지 않는다"*)을 걷어내고 UA 교차검증 서술로 갱신했다. 그 서술이 **A·B 가 실제로 구현한 것**과 일치하는지(특히 `ResolveDeviceType(신고값, 서버 UA)` 의 우선순위가 정말 "서버가 이긴다" 인지) 합친 트리에서 대조해달라. 나는 코드를 고치지 않았고 A·B 코드는 이 worktree 에 없다.
