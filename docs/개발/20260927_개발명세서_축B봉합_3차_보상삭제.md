🔴 `isNewSession == false`(이어받은 세션)는 **아예 넘기지 않는다** — 이 호출이 만든 행이 아니고,

### 4-3. G-B13 이 노리는 경로를 어떻게 **결정적으로** 만들었나

`deleted == 0`(단일사용 거부 401)은 원래 *"동시 갱신 2발"* 이라야 나온다. 시험이 두 번 동시에 부르면
어느 쪽이 이길지 몰라 **깜빡이는 게이트**가 된다(MEMORY: 간헐적이면 구조가 아니라 타이밍).
⇒ `user_sessions` 에 **AFTER INSERT 트리거**를 달아, 운영 코드가 세션 행을 넣는 **그 순간** refresh 토큰 행이
사라지게 했다. 그 뒤 회전 `DELETE` 가 0행 ⇒ 401.

🔴 **이 트리거가 도는 것 자체가 *"세션 INSERT 가 회전보다 먼저"* 를 증명한다.** 순서를 되돌리면
트리거가 안 돌아 401 이 아니라 성공이 되고 **G-B13 이 먼저 깨진다** ⇒ 2차 봉합(D-2)의 순서도 함께 지킨다.
⚠️ 트리거는 **상태 만들기**이고 판정하지 않는다(이 파일 규칙 · 작지 §3 금지 #8 — 운영 SQL 복사 금지).

## 7. 검증팀에 요청 (자기 판단 아님)

- 🔴 **가장 위험한 곳 — 보상 삭제가 "내가 만든 행"을 정말 정확히 가리는가.** 판정은 `isNewSession && sessionRecorded`
  단 하나다. 만약 `sessionId` 가 다른 행을 가리킬 수 있는 경로가 있다면 **남의 세션을 지우는 코드**가 된다.
  내가 읽은 바로는 `isNewSession` 일 때 `sessionId` 는 이 호출이 `Guid.NewGuid()` 로 만든 값이고
  그 사이에 바뀌는 곳이 없다 — **그 전제를 다른 문맥에서 반증해 달라.**
- 🔴 **G-B13 이 진짜 무엇을 재는지** — 트리거로 만든 경주가 실제 동시 갱신과 **같은 모양인지** 봐 달라.
  내 판단은 *"DELETE 대상 행이 없는 상태"* 로 동일하다는 것인데, 실물 경주는 타이밍이 더 넓을 수 있다.
- ⚠️ **회귀 우려 ① 갱신 실패 후 재로그인** — 보상 삭제가 돌면 잔여 행이 없으니 축 B ON 에서도 409 가 안 나야 한다.
  반대로 **보상이 실패**하면(로그만 남는다) 종전과 같은 409 가 난다 ⇒ 그때 고객에게 보이는 말이
  *"다른 컴퓨터에서 사용 중"* 인데 실제로는 **자기 잔여 행**이다. 이 말이 맞는 말인지 판정해 달라.
- ⚠️ **회귀 우려 ②** — `catch (UnauthorizedAccessException)` 에 `await` 가 들어갔다. 롤백은 그 앞(단일사용 거부는
  `tx.Rollback()` 뒤에 던진다)이라 순서는 맞다고 봤지만, **연결 상태**를 다른 문맥에서 확인해 달라.
