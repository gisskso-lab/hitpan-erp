→ 「안 고르면 멈추고 PM 보고」 조건에 **걸리지 않았다.** 처방 (가) 재상정 불필요.

### 2-3 ⚠️ 이 표가 드러낸 것 하나 — 인덱스 ③이 안 쓰인다

`payments(tenant_id, partner_id)`(`idx_pay_tenant_partner`)는 **8문장 중 어느 것도 선택하지 않았다.**
L3 는 `possible_keys` 에 올라오기만 하고 실제로는 `idx_pay_tenant_type_ref` 를 골랐다 —
`lp.partner_id=@PartnerId` 와 `lp.ref_order_id=lp.partner_id` 가 맞물려 `ref_order_id` 까지 상수로 전파되기 때문이다.

- 설계 §12-5 가 이 인덱스에 준 임무(「L3 옵티마이저 갈림 제거」)는 **결과적으로 달성됐다** — 전에는 테넌트를 넘는 `idx_pay_partner` 를 골랐고, 후에는 테넌트 접두 인덱스를 고른다. 다만 **그 일을 한 것은 ②이지 ③이 아니다.**
- ③은 지금 **쓰기 비용만 늘리고 있을 가능성**이 있다. 다만 작지 §16-1 ㉳ 가 인덱스를 4개로 명시했고 독단 축소는 범위 이탈(#33)이므로 **넣은 채로 두고 PM 결정 안건으로 올린다**(§6 참조).

| 항목 | 값 |

| 사본 행 수 | `collections` **109,822** · `payments` **2,228** · `purchase_returns` **0** |
| 운영 무접촉 | 3306·5257·5234·서비스 **안 건드림**(#39). 33306 은 격리 시험 인스턴스다 |

| # | `ALTER TABLE` | 대상 행 | **소요시간** | 10초 게이트 |
|---|---|---|---|---|
| 1 | `collections ADD KEY idx_coll_tenant_doc` | 109,822 | **4.08초** | 🟢 통과 |
| 2 | `payments ADD KEY idx_pay_tenant_type_ref` | 2,228 | **0.23초** | 🟢 통과 |
| 3 | `payments ADD KEY idx_pay_tenant_partner` | 2,228 | **0.25초** | 🟢 통과 |
| 4 | `purchase_returns ADD KEY idx_rt_tenant_receipt` | **0** | **0.20초** | 🟢 통과(⚠️ 아래) |

- **합계 4.76초** — PM 조건 「10초를 넘으면 멈추고 보고」에 **걸리지 않았다.**
- ⚠️ **④는 숫자를 신뢰하면 안 된다** — 이 고객 데이터에 `purchase_returns` 가 **0행**이다. 0행 표의 `ALTER` 가 0.2초인 것은
  측정이 아니라 동어반복이다(#32 「숫자 받아쓰기 금지」). 반품을 쓰는 고객에서는 다시 재야 한다.
- ⚠️ **①의 4.08초도 상한이 아니다** — 공영정보 `collections` 는 11만 행이다. 5만 고객사 전체에서 가장 큰 DB 가
  이만하다는 근거는 없다. 「11만 행 = 4초」까지가 사실이고, 선형이라고 쓰지 않는다.
### 3-A-1 도중 다른 세션이 읽기·쓰기가 되는가

| 잰 것 | 결과 |
|---|---|
| `ALTER` 도는 중 다른 세션 **읽기** (`SELECT COUNT(*) FROM collections`, `lock_wait_timeout=2`) | 🟢 성공 — `109822` |
| `ALTER` 도는 중 다른 세션 **쓰기** (`UPDATE collections …`) | 🟢 성공(오류 없음) ⚠️ 아래 |
| **`ALGORITHM=INPLACE, LOCK=NONE` 을 서버가 받는가** — 네 `ALTER` 전부 | 🟢 **4/4 수용** (거부면 `ERROR 1846`) |

- ⚠️ **경합 실측은 증거로 약하다** — 두 번째 실행에서 `ALTER` 가 **0.67초**(버퍼풀 워밍)로 끝나,
  프로브가 정말 `ALTER` 와 겹친 순간에 쳤다는 것을 보장 못 한다. 「성공했다」까지가 사실이고 「막히지 않는다」의 증거로 쓰지 않는다.
- 🟢 **증거는 `LOCK=NONE` 수용 쪽이다.** MariaDB 는 그 조작이 온라인으로 안 되면 `ALTER` 자체를 거부한다(1846).
  네 개 모두 받았다 = **인덱스 추가 도중 읽기·쓰기가 허용된다**는 서버의 선언이다.
- `DB-124` 파일에는 `ALGORITHM`·`LOCK` 절을 **일부러 안 적었다** — InnoDB 가 알아서 가장 덜 막는 방식을 고르고,
  절을 박으면 그 방식을 못 쓰는 서버에서 마이그가 통째로 실패한다(고객 DB 를 세우는 것보다 느린 편이 낫다).
