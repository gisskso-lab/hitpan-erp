## 1. 이 갈래의 목적 — 「감시자 0」을 없앤다

[4] 실측(작지 §18): **반품 잠금절만 빼면 전체 1,524 시험 중 한 건도 안 깨진다.**
초록불이 봉합을 지키고 있지 않았다. S4 는 초록불을 만드는 갈래가 아니라 **빨간불이 나게 만드는 갈래**다.

그 관점으로 게이트를 고쳤더니, **게이트가 먼저 봉합(DB-124)을 반증했다.** 아래가 그 기록이다.

## 3. 🔴 실측이 뒤집은 것 셋 — 이게 이번 갈래의 본체다

### 3-1 「다른 거래처 동시 = 교착 0」은 **인덱스로 도달할 수 없다** (병렬이슈60 의 답)

**절차**: 위험 33406 · 전용 DB · 거래처 PA(이월 미수 100,000)·PC(50,000) / PB(미지급 80,000)·PF(50,000).
두 연결이 **제품 진입점**(`CreateCollectionAsync`·`CreatePaymentAsync`)으로 **서로 다른 거래처**를 동시에 등록.

**결과**: DB-124 가 들어간 상태에서도 **1213 교착이 난다.**
```
[CollectionService] 수금 매칭 트랜잭션 재시도 attempt=1 errno=1213 mode=RepeatableReadLocking
[CollectionService] 지급 매칭 트랜잭션 재시도 attempt=1 errno=1213 mode=RepeatableReadLocking
```
재시도 1회로 둘 다 성공한다 — **고객 눈에는 안 보이고, 예전 단언(「예외가 안 샜다」)도 초록이었다.**

**그런데 교착 상대가 매칭 잠금이 아니다.** `SHOW ENGINE INNODB STATUS` 원문:
```
*** (1) TRANSACTION: ... inserting
INSERT INTO payments (payment_id, tenant_id, partner_id, ... payment_type, ref_order_id, ...)
VALUES ('6f006827-…', 'f727c4a3-…', '3bb97fe3-…', …, 'legacy_balance', '3bb97fe3-…', NULL, 'rc')
*** WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS index uq_payments_source of table `hitpan_s2_rc_…`.`payments`
  lock_mode X insert intention waiting
  Record lock, heap no 1 … asc supremum;;
*** CONFLICTING WITH:
RECORD LOCKS index uq_payments_source … lock mode S
  heap no 1 … supremum ;;
  heap no 8 … (tenant_id 'f727c4a3-…', SQL NULL, SQL NULL, PK '41771279-…')
```

- 잠금 대상 = **`uq_payments_source` (`tenant_id`, `source_id`)** · 값 구간 = **`source_id` 가 NULL 인 자리 + supremum 간극**.
- 손으로 넣는 수금·지급은 `source_type`·`source_id` 가 **NULL** 이다(이관분만 값이 있다). 그래서 **모든 수기 등록이 이 유니크 인덱스의 같은 자리**에 들어간다.
- INSERT 는 유니크 중복검사로 그 자리에 **S 잠금**을 잡고, 상대의 **insert intention X** 를 막는다. 서로 그러면 1213.
- RR 에서만 난다 — RC 는 간극을 안 잠근다. **즉 STATEMENT 고객사 전용 사고다.** `collections` 도 `uq_collections_source`·`uq_collections_source_hash` 로 같은 모양이다.

🔴 **결론**: 병렬이슈53 이 지목한 원인(매칭 잠금 범위)은 **원인의 일부**였다. 남은 교착은 **유니크 중복검사 간극 잠금**이고, 이건 DB-124 로 안 없어진다.
PM 이 §13 에서 결재 근거로 적은 「교착 **원인 제거**」는 **지금도 성립하지 않는다.** (병렬이슈60 의 지적이 맞다.)

⇒ 게이트는 「교착 0」 대신 **「교착이 나더라도 그 상대가 매칭 잠금 인덱스여서는 안 된다」**로 단언을 바꿨다(도달 가능하고, DB-124 를 지우면 빨간불이 되는 축). 유니크 축은 **별도 사례(G-RC14)로 분리해야 한다 — 못 만들었다**(§6).

### 3-2 무관 거래처 **지급** INSERT 는 아직 막힌다 (6건 중 1건 · B4)

**절차**(S3 명세서 §3-1 과 같은 모양): 세션 A 가 RR 트랜잭션에서 매칭 8문장(L1~L5 + D1-a/b/c)을 잠근 채 유지 →
세션 B(`innodb_lock_wait_timeout=3`)가 **무관 거래처**(noise-0003·noise-0009, 양옆에 남의 행 30건)에 6건.

| # | 세션 B | 결과 |
|---|---|---|
| B1 | `collections` UPDATE (무관 거래처) | 🟢 3ms |
| B2 | `collections` INSERT | 🟢 3ms |
| B3 | `payments` UPDATE | 🟢 3ms |
| **B4** | **`payments` INSERT (`payment_type='legacy_balance'`)** | 🔴 **3,008ms · ERROR 1205** |
| B5 | `purchase_returns` UPDATE | 🟢 4ms |
| B6 | `purchase_returns` INSERT | 🟢 4ms |

- S3 는 **전/후 대조(5/6 → 6/6)** 를 쟀고 여기서는 **다른 시드**(거래처 30명 · 각 1행)로 쟀다. 모양이 달라 값이 갈린다.
- 유력한 원인: **L3 `PayableMatchedLegacyLockedSql`** 이 `idx_pay_tenant_type_ref` 를 `(tenant_id, payment_type)` **두 칸만** 쓰면
  그 회사의 **`legacy_balance` 지급 전부**가 잠긴다(S3 §2-2 도 L3 만 `ref|filter` 로 적었다 — 상수 3칸이 아니다).
  ⚠️ **확정 아님** — 잠금 대상 인덱스를 직접 못 찍었다(1205 는 교착이 아니라 `INNODB STATUS` 에 기록이 안 남는다).
- 같은 모양인 `collections` 축(B2)은 통과했다 — 수금 축은 좁혀졌고 **지급 축만 남았다.**

### 3-3 EXPLAIN 기대표가 **데이터에 따라 갈린다** (G-RC13)

실측: `L1 ReceivableMatchedLegacyLockedSql` · 표 `lc` · `type=ref` · **`key=idx_tenant_partner`** · `rows=1`.
S3 0단계는 같은 문장을 **`idx_coll_tenant_doc`** 으로 쟀다(명세서 §2-2). 둘 다 **테넌트 접두 · rows 1** 이라 잠금 범위는 좁지만,
「문장별로 이 인덱스여야 한다」는 고정표는 **시드 분포에 따라 흔들린다.**

⇒ 단언을 「**DB-124 인덱스여야 한다**」가 아니라 「**테넌트 접두 인덱스 + rows 상한 + 무관 행 10배에도 불변 + 테넌트 넘는 인덱스 금지**」로 바꿔야 한다.
**안 바꿨다**(턴 한도) — 지금 G-RC13 은 L1 에서 빨간불이다.

### 3-4 곁가지 실측 — 갭 잠금은 **인접 거래처**에서 진짜로 남는다

거래처가 둘뿐인 표에서는 두 거래처가 인덱스에서 **바로 이웃**이라, 거래처가 달라도 서로의 간극에 INSERT 해서 막힌다(1205·1213).
게이트에 **완충 시드**(`5s-…` 구분자 · 무관 행 30건)를 넣고서야 안정적으로 재진다. 설계 §12-6 이 「갭 잠금은 게이트로 못 지운다」고
적어 둔 그 자리가 **시험에서 그대로 드러났다.** ⇒ G-RC12 가 재는 것은 「무관 거래처면 무조건 안 막힌다」가 **아니라**
「**회사 전체가 통째로 막히지는 않는다**」까지다. 코드 주석에 그대로 적었다.

## 4. 무력화 실측 — 🔴 **못 했다**

작지 §16-2 의 4건(①반품 꼬리절 ②문구 한 글자 ③DB-124 DROP ④`USE INDEX` 강제)을 **한 건도 못 돌렸다.**
사례 2건(G-RC12·G-RC13)이 아직 빨간불이라, 무력화 전/후를 가를 기준선이 없다. **초록불만 보고 CI 에 등록하지 않는다**는 관례대로
CI(`GATES`)도 **안 건드렸다**.

## 6. 안 한 것 · 못 한 것

1. **G-RC12 를 초록으로 못 만들었다** — B4(지급 INSERT)가 1205. 봉합이 덜 된 것인지 시드 탓인지 **확정 못 했다**(§3-2).
2. **G-RC13 기대표를 못 고쳤다** — 「테넌트 접두 + rows 상한 + 10배 불변」으로 바꿔야 한다(§3-3). 30→300 대조군은 코드에 있으나 **한 번도 못 돌았다**.
3. **G-RC14(유니크 축) 안 만들었다** — PM 지시 3항. 유니크 중복검사 교착을 별도로 재는 사례.
4. **무력화 4건 안 돌렸다**(§4). **CI 주석·GATES 안 고쳤다.**
5. **안전 서버 회귀·전체 회귀 안 돌렸다.**
6. **전표 조회 문장(FOR UPDATE) 2개는 아직 복제다** — S3 가 뺀 것은 합계 3문장뿐이라 게이트가 술어를 손으로 맞춰 뒀다. 그 술어가 갈라지면 아무도 못 잡는다.
7. **1205 의 잠금 대상 인덱스를 직접 못 찍었다** — MariaDB 11.4 에는 `performance_schema.data_locks` 가 없다. 교착(1213)은 `INNODB STATUS` 로 찍었지만 대기(1205)는 대기 중에만 보인다.
