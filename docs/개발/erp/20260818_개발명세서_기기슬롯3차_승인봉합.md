## 2. 🔴 [3-V] V-02 · V-03 을 어떻게 닫았나 — 코드로

### V-02 — "새 줄을 만들면 착수 당일 1062"

**PM 판정: 새 줄을 만들지 마라. 기존 pending 줄을 쓴다. INSERT 가 아니라 UPDATE.**

실측 확인한 함정 (`installer/hitpan_db_clean.sql:tenant_devices`):
```
fingerprint varchar(64) NOT NULL          ← NULL 불가
UNIQUE KEY uq_tenant_fp (tenant_id, fingerprint)  ← 같은 지문 두 줄 불가
```

⇒ 봉합안대로 "성공 시 새 device_id 발급 + 새 줄" 을 짰다면 그 줄의 `fingerprint` 에
NULL(불가) · 같은 지문(1062) · 임의값(다음 접속에 못 찾아 또 새 줄) 중 무엇도 답이 안 된다.

**닫은 방법** — `TenantDeviceService.cs` `VerifyAuthKeyAsync` 마지막 단계:
```sql
UPDATE tenant_devices
SET status = 'approved',
    approved_at = COALESCE(approved_at, NOW(6)),
    auth_key_hash = NULL,          -- 1회용
    last_seen_at = NOW(6)
WHERE tenant_id = @TenantId AND device_id = @DeviceId
```
🔴 **INSERT 가 한 줄도 없다.** 줄은 직원이 관문에서 신청할 때 이미 생겼고,
verify-key 는 **그 줄을 승인으로 바꿀 뿐**이다. ⇒ UNIQUE·NOT NULL 을 건드릴 일이 없다.

### V-03 — "'세션이 신청한 줄을 잡는다' 의 방법이 비어 있다"

**PM 판정: 관문에서 발급받은 `device_id` 로 특정. 키는 대조만.**

**닫은 방법** — 3단으로 갈랐다:

```csharp
// ① 열 줄을 모르면 아무것도 열지 않는다 (LIMIT 1 로 도망가지 못하게)
if (string.IsNullOrWhiteSpace(sessionDeviceId)) return null;

// ② 줄을 먼저 특정한다 — 키로 찾는 것이 아니다
SELECT auth_key_hash, status FROM tenant_devices
WHERE tenant_id = @TenantId AND device_id = @DeviceId LIMIT 1

// ③ 그 줄의 해시와만 대조한다
if (!string.Equals(storedHash, Sha256Hex(authKey), StringComparison.OrdinalIgnoreCase))
    return null;
```

🔴 **반환값이 `sessionDeviceId` 다.** DB 에서 읽은 남의 `device_id` 를 돌려주는 경로가
**함수 안에 물리적으로 존재하지 않는다.** 남의 키를 넣어도 자기 줄에서 대조되어 틀림으로 끝난다.

**PM 이 지시한 시험 결과**: 기기 B 가 기기 A 의 키 입력 → **A 의 device_id 반환 안 됨 (G-31 PASS)**.
봉합을 되돌리자 **FAIL** 로 뒤집혔다(§4).

### V-04 — 표현 정정

1-2 를 **"무기명 도용 차단"** 이라 쓰지 않았다. `device_id` 는 비밀이 아니다
(기기 목록 화면 · gate-status 쿼리스트링=서버 로그 평문 · localStorage).

⇒ 코드 주석·인터페이스 문서·이 명세서 전부 **"통과 가능한 범위를 메인PC 한 줄로 좁힌다"** 로 적었다.
🔴 그리고 **그 한계를 게이트로 세웠다** — `G-32-d` 가 *"메인PC 번호를 훔치면 여전히 통과한다"* 를
값으로 고정한다. 나중에 누가 "1-2 로 도용이 막혔다" 고 적으면 그 시험이 반증이 된다.

### 1-3 — 대표 예외를 경로로 한정

예외를 **지우지 않았다**(헌법 #1 · 8/16 PR#169 무회귀). 조건만 더했다:
```csharp
if (string.Equals(accountType, "tenant_admin", StringComparison.Ordinal)
    && IsOwnerEscapePath(path))          // ← 추가된 조건
    ok = true;
```
`OwnerEscapePrefixes = { "/api/devices", "/api/auth" }`

⇒ 대표계정으로 로그인해도 **미승인 기기가 ERP 전체를 쓰던 길이 닫혔다.**
막다른 길(대표가 스스로 못 빠져나오는 방)은 그대로 없다.

### 1-4 — 거절을 폐기에서 분리

- `RejectAsync`: `SET status='revoked'` → **`'rejected'`**
- `RegisterOrRefreshAsync`: `rejected` 갈래 신설 → **다시 오면 `pending` 으로 되돌려 대기 줄에 세운다**

🔴 **두 번째 것이 진짜 봉합이다.** 칸 이름만 바꾸고 재신청 길을 안 만들면 아무것도 안 고친 것이다
(직원은 여전히 갇히고 대표 목록에도 안 뜬다). G-33-b 가 이것을 따로 지킨다 — §4 에서 **독립적으로 FAIL** 함을 확인했다.

🔴 `revoked` 의 뜻·기존 `revoked` 행은 **한 글자도 안 건드렸다**(작지서 §8).

| gate-status 구멍 | `deviceId` 공백 시 `approved=true` → **`approved=false`** |

그래서 작지서가 **1-1 뒤에** 닫으라고 순서를 정한 것이고, 그 순서를 지켰다.

> 초록불은 증거가 아니다. **빨간불이 뜨는 것을 확인해야** 게이트가 존재한다.

신규 게이트 **12개** (`DeviceAndKeyGateTests.cs`) — 격리 DB + **출하 DDL** + **실제 서비스**를 태운다.

### 🔴 4-0. 1차 제출 G-31 은 **가짜였다** — PM 실측이 적발 (2026-08-18)

**개발팀은 "G-31 봉합 빼면 FAIL" 이라 보고했다. 그 보고가 틀렸다.**
PM 이 받아쓰지 않고 직접 **이번 차수 간판 봉합**(§17-1 열쇠 AND)을 뺐다:

```
# TenantDeviceService.cs:674
-  WHERE tenant_id = @TenantId AND device_id = @DeviceId
+  WHERE tenant_id = @TenantId        ← LIMIT 1 이 아무 줄이나 집는다 = 공용 열쇠 부활
```
⇒ 🔴 **결과: 실패 0, 통과 12. 초록불이었다.** (개발팀이 재현 확인함)

**원인 — 판정문이 반환값을 봤다:**
```csharp
Assert.True(opened != deviceA, ...);   // ❌ 옛 판정
```
함수는 반환값을 `sessionDeviceId`(=B)로 **고정**해 돌려준다.
⇒ 내부에서 **A 의 줄을 집어 A 의 해시로 대조해도** 돌아오는 값은 B 라서 `!= deviceA` 가 성립한다.

🔴 **반환값은 함수가 마음대로 정하는 값이다.** 그걸 시험하면 **동작이 아니라 함수의 성실성**을 시험하는 것이다.
⚠️ **히트판 가짜 게이트의 새로운 형태다.** 여섯 번은 글자검사이거나 DB 제약 초록불이었다.
이번은 **실제 DB 를 태우고 실제 서비스를 부르고 값을 보는데, 그 값이 결함과 무관**했다.

**고친 방법 — 표를 본다:**
🔴 **1회용 소거(`auth_key_hash=NULL`)와 승인은 실제로 열린 줄에만 일어난다**
⇒ **누구의 키가 사라졌는지가 곧 누구의 줄이 열렸는지**다. 이건 함수가 못 속인다.

```csharp
var (aHash, aStatus) = await ReadRowAsync(db, deviceA);
var (_, bStatus)     = await ReadRowAsync(db, deviceB);

Assert.True(aHash is not null,      "A 의 키가 소거됐다 = A 의 줄이 열렸다");
Assert.True(aStatus == "approved",  "A 의 상태가 안 바뀌어야 한다");
Assert.True(bStatus == "pending",   "B 가 남의 키로 승인되면 안 된다");
Assert.True(opened is null,         "반환값도 함께 본다(보조)");
```

**같은 병을 앓던 게이트 4개도 같이 고쳤다** — G-31-b · G-31-c · G-34 · G-34-b 전부 반환값 판정이었다.
⚠️ G-34 는 추가 결함도 있었다: 전제 확인으로 `VerifyAuthKeyAsync` 를 먼저 불러 **1회용 소거가 일어나서**
"재발급이 옛 키를 죽였는지" 와 "인증이 죽였는지" 가 구분되지 않았다 → **표의 해시를 직접 읽는 방식**으로 교체.

## 5. 🔴 작업 중 스스로 잡은 P0 1건 — 관문 판정 분리

**무엇을 잡았나**: 1-2 로 `IsDeviceAllowedAsync` 를 메인PC 로 좁혔는데,
**`gate-status`(관문)가 그 함수를 같이 쓰고 있었다.**

**그대로 뒀다면**: 승인받은 평범한 직원 기기가 **영원히 "승인 대기" 화면에 갇힌다.**
대표가 [예] 를 눌러도 화면이 안 넘어간다 — 메인PC 가 아니라서 `false` 가 돌아오기 때문이다.
⇒ 정확히 **8/10 사고와 같은 모양**(규칙을 좁혀서 쓰던 사람이 막힘)이고, **사장님 실측에서 바로 드러날 자리**였다.

**고침**: 물음이 다르므로 함수를 갈랐다.
- `IsDeviceAllowedAsync` = *"이 헤더만으로 문을 열어도 되나"* → **메인PC 만**
- `IsDeviceApprovedAsync` = *"이 기기가 승인은 났나"* → **모든 승인 기기** (관문 전용, 문을 열지 않는다)

⚠️ 두 물음을 한 함수로 합치려는 유혹이 앞으로도 생긴다. 인터페이스 주석에 이유를 적어 뒀다.

**origin 격리(localStorage)는 xUnit 으로 불가능하다** — 브라우저 동작이라 재현 수단이 없다.
게이트로 만들지 않았고, **Playwright 실측 항목으로만 남긴다**:

| Playwright 실측 항목 | 통과 기준 | 상태 |
|---|---|---|
| origin 격리 (`localhost` ↔ 터널) | 주소가 달라져도 행이 안 는다 | ⬜ 미실행 |
| 증상③ 관문 노출 | 로그인 후 "등록을 하시겠습니까" 가 실제로 뜬다 | ⬜ 미실행 |
| 관문 뒤 API 정지 | 관문 상태에서 업무 API 호출 **0건**(네트워크 탭) | ⬜ 미실행 |
| 거절 → 첫 화면 회귀 | 대표가 N → 직원 화면이 죽지 않고 재신청 가능 | ⬜ 미실행 |

🔴 **관문 뒤 API 정지**는 이번 차수 핵심 변경(관문 승격)의 **유일한 최종 증거**인데 **xUnit 으로 못 잡는다.**
구조상 `@if (!_gateActive)` 로 본문을 안 그리므로 호출이 없어야 **맞지만**, 실측 전까지는 **논증이지 증거가 아니다.**

## 9. 🔴 이번 차수가 남기는 교훈 — 게이트 판정 기준

> **"실제 DB 를 태웠다" 는 것만으로 진짜 게이트가 아니다. 어느 값을 보느냐가 갈랐다.**

| 판정 대상 | 진짜인가 | 왜 |
|---|---|---|
| 소스 글자(`Assert.Contains`) | ❌ | 주석만 고쳐도 초록불 (8/15~16 사고 6건) |
| DB 제약이 막는 자리 | ❌ | 코드 가드를 다 빼도 DB 가 막아 초록불 (8/16 G-21) |
| **함수의 반환값** | ❌ | 🆕 **함수가 마음대로 정하는 값** — 결함이 있어도 값만 맞게 주면 초록불 (8/18 G-31) |
| **동작의 흔적이 남는 값(표의 상태·소거)** | ✅ | 실제로 그 일이 일어난 줄에만 남는다 — 못 속인다 |

*"이 값을 누가 정하는가 — 내가 시험하려는 그 동작인가, 아니면 함수가 그냥 정해서 주는 값인가?"*
