## 2. 🔴 선행검증이 P0 를 찾아냈다 — 계산서를 취소하면 매출이 사라진다

`TaxInvoiceService.CancelAsync` 가 **발행이 만들지도 않은 분개를 되돌리고** 있었다.

| 시점 | 기표 |
|---|---|
| 거래명세서 확정 (`SalesService.cs:581`) | 🟢 `RecordSalesConfirmAsync` |
| 계산서 발행 (`IssueAsync` 43~188) | 🔴 **0건** |
| 계산서 취소 (`CancelAsync`) | 🔴 **역분개 1건** |

**실측** — 명세서 확정 1건 + 계산서 취소 1건:

| 계정 | 취소 후 |
|---|---|
| 외상매출금 | **0.00** |
| 매출 | **0.00** |
| 부가세예수금 | **0.00** |

🔴 명세서는 `confirmed` 이고 재고도 나갔는데 **장부에서 매출만 사라진다.**
⇒ 재고↔회계 분리(헌법 #20) + 부가세 매출세액 **과소**신고.
⇒ `FinanceService` 에 `sales_cancel` 낱말 **0건** — 정합성 검사도 못 잡는다.

### 원인은 「주석을 믿은 것」

종전 주석: *"역분개 — **IssueAsync 기표의** 차/대변 반전"*
그런데 `IssueAsync` 에 `AutoJournalHelper` 호출이 **한 건도 없다.**
`CancelAsync:268` 주석도 *"발행(IssueAsync:50)이 … **기표하던**"* 이라 했는데 **50행은 검증 쿼리**다.

⇒ 8/28작12 에서 [4] 가 잡은 것과 **같은 유형의 받아쓰기.**

⚠️ `amendment_of` 는 **국세청 「수정세금계산서」 축**이라 반품 연결과 의미가 다르다. 분리 유지.

### ⚠️ 마이너스 계산서는 회계를 기표하지 않는다

매출반품 분개는 **반품 확정** 시점에 이미 `sales_return` 키로 들어간다(20260828작12).
계산서가 또 기표하면 **이중계상**이다 (헌법 #6 — 원장 반영은 confirmed 시점에만).
게이트 6번이 `AutoJournalHelper` 혼입을 **금지 조건으로** 잡는다.

## 4. 사슬연결도

```
매출반품 (반-20260828-901)
   └─ tax_invoices.source_type='sales_return'
      tax_invoices.source_id  = return_id
         └─ 마이너스 계산서 (세-20260828-00N, 금액 음수)
            └─ delivery_id → 원 거래명세서 → 원 계산서
```

응답에 `ReturnNo`·`OriginalInvoiceNo` 를 실어 화면이 **「반품전표 : 반-…」** 을 그릴 수 있게 했다.

| `decimal(15,2)` 음수 허용 | 🟢 UNSIGNED 아님 |
| 음수 계산서 저장 | 🟢 `-100,000` / `-10,000` / grand `-110,000` |
| 사슬 조회 | 🟢 `source_id` → `반-20260828-901` 로 이어짐 |
| **국세청 신고 합계** | 🟢 **공급가 0 / 부가세 0** (양수 + 마이너스 상계) |
| P0 가드 쿼리 | 🟢 일반 계산서에 **0** 반환 ⇒ 원장 안 지워짐 |
