### 구현 주의(§5-3) 준수

- **(B) 는 한 UPDATE 안에서 판정한다** — 별도 선행 `SELECT` 0건. MariaDB 1093 을 피하려 **파생표 2겹**으로 감쌌다.
  격리 실측에서 1093 없이 돌았다(§4 탐침).
- **「최신 1줄」은 결정적이다** — `(last_seen_at IS NULL) ASC → last_seen_at DESC → registered_at DESC → device_id ASC`.
  마지막이 PK 라 **반드시 하나로 갈린다.** 게이트 V3 가 동값·NULL 을 잰다.
- **러너와 같은 방식으로 실행해 잰다** — 게이트가 `DB-120` 파일을 읽어 Dapper `ExecuteAsync` **한 번**으로 보낸다
  (`MigrationRunner.cs:135-137` 과 동일). `SET @…`/`PREPARE` 가 동작하는 근거는 연결의
  `AllowUserVariables=true` (`MigrationDbConnectionFactory.cs:58`) — **글자검사 0건.**
- **출하 DDL 은 기존 모양을 따랐다** — 생성컬럼은 이미 3곳에 있던 `GENERATED ALWAYS AS (…) VIRTUAL` 형식 그대로.

## 7-2. 🔴 재작업 (2차) — 사장님 결재 **(가) 채택** 실측 기록

**결재**: 사장님 **(가) ③단 조건부 UNIQUE 채택** (2026-09-13) · (나)·(다) **반려** ·
CTO 결재문 [`20260913결1`](../../운영기록/20260913결1_메인PC표식_V4_마이그정지_CTO결재.md) §1 · §3-3 · §6 **D-1~D-4**.

`status` 쓰기 0 · `DELETE` 0 · 계수 SQL 무접촉 · 운영 DB(3306)·5257·5234 접속 **0**(#39 · 격리 33306 만).

### D-1 — ③단을 조건부로 (판정은 **DB 전체**)

`DB-120` ③단. 기존 멱등 검사 `@idx_exists = 0` 을 **유지**하고 중복 검사를 **AND 로 더했다**(`:168-181`):

```sql
SET @dup_tenants := (
  SELECT COUNT(*) FROM (
    SELECT `tenant_id` FROM `tenant_devices`
     WHERE `is_main_pc` = 1 GROUP BY `tenant_id` HAVING COUNT(*) >= 2
  ) AS `dup`);

SET @sql := IF(@idx_exists = 0 AND @dup_tenants = 0,
  'ALTER TABLE `tenant_devices` ADD UNIQUE KEY `uq_tenant_main_pc` (`main_pc_key`)', 'SELECT 1');
```

🔴 **테넌트별이 아니라 DB 전체다** — 그 SQL 에 `WHERE tenant_id = …` 절이 **없다.**
UNIQUE 는 표 전체 제약이라 한 회사만 더러워도 `ALTER` 가 통째로 거부되므로 판정 단위도 표 전체여야 한다
(결1 §6 D-1 · PM 반증 2: **실물은 단일 테넌트지만 `local_company` 행 2개를 코드가 막지 않는다** —
「실물이 1개」와 「구조가 1개를 보장」은 다르다).
