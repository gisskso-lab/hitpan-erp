# 【추가 작업】 휴직 결재 승인 → 원본·사원상태 반영 (사장님 결재 후)

> 사장님: *"영향 없다면 결재승인 작업해"* (2026-08-21)
> 선행: [4] 검증 **승인**(조건부) — 조건 #2 가 정확히 이 작업이다.

## A. 무엇을 했나

`ApprovalService.ProcessAsync` 에 **`absence` 원본 반영 블록** 신설.
정본 패턴은 바로 위 `leave` 블록을 **그대로 따랐다**(새 방식 발명 금지, 헌법 #1).

| 동작 | 처리 |
|---|---|
| 반려 | `employee_leave_of_absence.status='rejected'` + 사유 |
| 최종승인 | 시작일 판정 → `active`(이미 시작) / `approved`(시작 전) |
| 최종승인 + 시작일 지남 | **+ `employees.work_status='absence'`** |

### 🔴 시작일 판정을 `AbsenceService` 와 같은 규칙으로 맞췄다
```
started = start_date <= 오늘  →  'active'
아니면                        →  'approved'
```
두 경로가 다른 값을 넣으면 **사원 상태가 경로에 따라 갈린다.**

### 멱등
`status='pending'` 가드 — 휴직 화면이 먼저 처리했으면 **0행**이라 무해하다.
`work_status` 변경도 `absenceAffected > 0` 일 때만 → **이중 처리 없음.**
전부 결재와 **같은 트랜잭션**(`tx`).

## B. 🔴 급여는 안 건드린다 — 사장님 못박음

> *"급여는 수동입력원칙이야. 급여가 휴직을 모르고 사원만 알면 됨"*
> *"사원마스터에 상태처리, 급여는 수동설정으로 고객이 알아서"*
> *"연봉계산기는 정식배포때 추후 업데이트 예정 / 일단은 수동원칙"*

**실측으로 UPDATE 대상 전수 확인:**
```
UPDATE employee_leave_of_absence   ← 휴직 신청서
UPDATE employees (work_status)     ← 사원마스터 상태
payroll_*                          ← 0건 ✅
```

⚠️ **PM 정정**: 당초 주석에 *"급여가 그대로 나간다"* 를 근거로 적었는데 **틀렸다.**
`PayrollService` 는 `absence_id` 로 **잇기만** 하고 금액을 자동계산하지 않는다.
사장님 수동원칙이 **이미 코드에 지켜지고 있었다.** 주석을 사실대로 고쳤다.
