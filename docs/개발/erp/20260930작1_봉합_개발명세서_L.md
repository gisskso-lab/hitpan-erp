## 7. 검증팀에 요청 (자기 판단 아님)

1. **기존 게이트 전제 변경**: `LocalSwapOneAtATimeGateTests.Create_has_no_force_and_existing_task_blocks` 의 두 번째 장면(작업만 있고 요청·잠금 없음 ⇒ `swap_in_progress`)은 설계 06ⓑ 가 **바로 그 규칙을 버그로** 지목했다. 장면을 「살아 있는 다른 요청(running 1분) + 작업」으로 바꾸고, `/F` 없음 성질은 새 장면(등록 직전 남이 같은 이름을 만듦 ⇒ `task_register_failed` · `/Run` 0)으로 따로 잰다. 설계 §14-3 「기존 게이트 영향」 줄에 없던 것 — 판정 요청.
2. **`ClearStale` 경합**: `_gate` 안에서 요청서·`swap.lock` 을 **다시 읽고** 판정한다(그 사이 `Launch` 가 새 요청을 걸었으면 덮지 않음). 다른 **프로세스**(API 두 개)는 `_gate` 가 못 막는다 — 한 PC 한 API 전제. 반증 부탁.
3. **끝 상태를 적을 때 `updated_at` 을 안 바꾼다**(계약 §4 봉합 합의에 명시): 바꾸면 `broken` 이 쿨다운 10분을 새로 걸어 첫 호출 `swap_interrupted` → 다음 호출 `cooldown`(「방금 버전을 바꾸었습니다」 = 거짓) 으로 흔들린다. 일꾼이 쓰는 `updated_at` 의 뜻(일꾼이 마지막으로 만진 때)과 맞는지 확인 부탁.
4. **묵은 요청이지만 작업이 없는 경우에도** 끝 상태를 적는다(설계 문언은 「둘 다 묵었으면 작업을 지우고 요청서를 끝 상태로」 — 작업 유무를 조건으로 읽지 않았다). 작업 없는 `requested` 묵음 = 런처가 요청서만 쓰고 죽은 경우.
5. **예약 만료 30분**(`OpenRequestStale` 재사용)은 설계에 숫자가 없어 **구현이 고른 값**이다(해제 누락이 영구 바쁨으로 번지지 않게). 느린 회선에서 받기+백업이 30분을 넘으면 되돌리기가 끼어들 수 있다(그때도 `swap.lock` 이 두 번째 `Launch` 를 막으므로 교체 겹침은 0 · 대신 받은 수동 업데이트가 버려짐). ⚠️PM 확인 필요.
6. **05 ⓐ 「replaced-by 없거나 못 읽음」도 묵은 prev 로 본다**(막는 쪽). 반쯤 지워진 `prev` 가 비상 경로 ② 를 막을 수 있다 — 의도된 보수성인지 판정 요청.
7. **`TryReserve` 는 파일 상태(`swap.lock`·쿨다운)를 보지 않는다** — 순수 프로세스 안 예약. 호출부(M)가 `CheckReady` → `CheckBusy` → `TryReserve` 순서로 부르는 것이 계약 §4 의 전제.
8. `CheckReady` 가 폴더 문지기(`EnsureRestrictedSystemFolder`)를 부르므로, M 이 `GetStatus` 에서 부르면 **상태 조회만으로 `{app}\rollback\run` 이 만들어진다**(종전엔 `Launch` 때만). 설계 07 의 뜻과 같다고 봤다.
