### 0-2. 🔴 실측에서 발견한 불일치 — 우편번호·주소가 "빈칸인데 잠겨 있다"

`:39` 우편번호와 `:48` 주소는 **`ReadOnly="true"` 하드코딩**이다(`IsLocked` 조건이 아니다).

```
현재:  값이 없다  +  ReadOnly=true  +  자동으로 채워줄 데이터도 없다
   ⇒  영원히 빈칸으로 잠긴 칸
```

⭐ **사장님이 *"전화번호, 주소, 상세주소, 우편번호는 그대로 비어있어"* 라고 하신 것이 이 상태다.**
우편번호는 `우편번호 찾기` 버튼(`:42`)으로만 채울 수 있게 설계됐으나, 주소는 그 버튼이 채우는지
**확인 필요**(⬜ 미검증).

⇒ **백오피스가 주소를 수집하면 이 두 칸은 자동으로 채워지고, 잠김이 비로소 의미를 갖는다.**
지금은 잠금이 **값을 지키는 게 아니라 입력을 막고만 있다.**

### 0-3. 비활성화 구현 규칙

- `ReadOnly` 가 아니라 **`Disabled`** 로 할지 결정 필요 — MudBlazor 에서 `ReadOnly` 는 값이 폼에
  제출되지만 `Disabled` 는 제출되지 않는다. **저장 로직 영향 확인 필수**
- 🔒 자물쇠 + `"랜딩 자동 반영 (변경 불가)"` **헬퍼텍스트를 잠금 필드 전체에 통일** 적용
  (현재는 3개 필드에만 있다 — `:36`·`:54`·`:69`)
- ⚠️ **서버도 함께 막는다** — 화면만 비활성화하면 API 직접 호출로 뚫린다.
  `SettingsService.cs:296` 이 현재 **3필드만** 거부하므로 **8필드로 확장** 필요.
  화면 비활성화는 안내이고, **실제 방어선은 서버**다.

#### 🔴 `ReadOnly` 로 확정 — 종전 미결 해소

§0-3 에 *"`Disabled` 는 폼 제출에서 값이 빠질 수 있어 확인 필요"* 라고 적었다.
**이 화면에는 해당되지 않는다** — `UserInfoPage.razor.cs:285-303` 이 폼 제출이 아니라
`_model.*` 을 직접 읽어 DTO 를 만들기 때문이다.

**그럼에도 `ReadOnly` 를 쓰는 이유는 따로 있다**:
- `Disabled` 는 **글자를 흐리게** 만든다 → 읽으라고 자동으로 채운 값을 못 읽게 된다
- `Disabled` 는 **선택·복사를 막는다** → 사업자번호를 복사해 쓰지 못한다

| 3 | **자동으로** 백오피스 전송 | 🔴 *"바로 본사로 넘어가고"* — 고객이 따로 연락 안 함 |
| 4 | 본사 승인 화면 | 🔴 **자동 승인 금지** — 2관문 (사장님 결재) |
| 5 | 승인 → **시리얼 재발급** | 트랜잭션: 승인·발급·발송이 함께 성공/실패 |
| 6 | 📧 **이메일 발송** | 🔴 **§0-6 재발 방지 필수** |
| 7 | ERP 자동 갱신 | 부트스트랩 경로 재사용 |

⭐ **3번과 5번의 "바로"** — 사람이 중계하는 단계를 넣지 않는다.
고객이 전화하거나 본사가 수동으로 파일을 옮기는 경로가 생기면 이 설계는 실패다.

### 0-5-1. 🆕 확정 흐름 — 시리얼 재발급까지 (사장님 지시 2026-08-10)

> *"기본사업장 정보변경요청은 OCR검증 후 사업자정보 백오피스로 데이터 입력 → 백오피스에서 승인

```
[고객 ERP]                      [본사 백오피스]              [고객]
[기본 사업장 정보 변경 요청]
      ↓
등록증 업로드 → OCR 검증
      ↓ (반자동 확인 §PRD 4-1-0)
"일치합니까?" [예]/[아니오]
      ↓
              ──────────►  사업자정보 데이터 입력(접수)
                                  ↓
                           본사 담당자 검토 → [승인]
                                  ↓
                           시리얼넘버 재발급
                                  ↓
                                              ──► 📧 시리얼 발송
      ◄─── ① 자동 반영 (기본)
      ◄─── ② 시리얼 입력 (자동 실패 시 보조)
      ↓
사업자정보 자동 반영 + 🔒 재잠금
```

#### 🔴 반영 경로 2개 — 사장님 결재 "둘 다"

| # | 경로 | 언제 | 고객 손 |
|---|---|---|---|
| ① | **자동 반영** (기본) | 승인 즉시 ERP 가 받아온다 | **0번** |
| ② | **시리얼 입력** (보조) | 터널 끊김·장애로 ①이 안 될 때 | 메일 시리얼 입력 |

②는 **①이 실패했을 때의 탈출구**이지 정상 경로가 아니다.

#### 🆕 ②의 위치 — 변경요청 화면 **안**에 둔다 (사장님 지시 2026-08-10)

> *"수동입력은 '사업자정보변경요청' 버튼에서 OCR등록할 때 '시리얼넘버 수동등록' 을 넣자"*

```
[기본 사업장 정보 변경 요청] 클릭
        ↓
┌─ 변경 요청 화면 ────────────────────────┐
│  ① 사업자등록증 올리기  (OCR 인증)      │  ← 요청할 때
│  ─────────────────────────────────────  │
│  ② 시리얼넘버 수동등록                  │  ← 승인 메일 받은 뒤
│     [                    ] [등록]        │     다시 들어와서
└──────────────────────────────────────────┘
```

⭐ **기본사업장정보 화면에는 시리얼 입력란을 두지 않는다.**
같은 버튼으로 두 번 들어온다 — **요청할 때**(등록증 올리기)와 **승인 메일 받은 뒤**(시리얼 입력).

⚠️ **8/09 에 제거한 입력란과 성격이 다르다.**
`UserInfoPage.razor.cs:42` 주석: *"시리얼 인증 제거(설치시 진행하기에 사실상 필요 없음)"*
그때 지운 것은 **회사정보 화면에 상시 노출된 설치·인증용 입력란**이고,
이번 것은 **변경요청 화면 안에만 있는 일회성 입력란**이다. 상시 노출은 여전히 하지 않는다.

⚠️ **상태에 따라 화면이 달라야 한다** — 요청 전에 들어오면 등록증 올리기가 먼저이고,
승인된 뒤 들어오면 시리얼 입력이 먼저 보여야 한다. 둘을 한 화면에 나란히 두면
고객이 지금 무엇을 해야 하는지 헷갈린다(§0-4 상태 표시와 연동).

#### 🔴 경로가 2개면 규칙도 2개가 된다 — 반드시 같게 맞춘다

오늘 `local_company` 를 쓰는 문이 3개인데 잠긴 문이 2개여서 우회로가 생겼다([3-V] I-3).
**같은 실수를 반복하지 않는다.**

- ①과 ②는 **같은 반영 함수**를 호출한다(경로만 다르고 처리는 하나)
- 시리얼 검증·재잠금·감사 로그를 **양쪽 모두** 통과시킨다
- ②로 들어온 시리얼도 **본사가 발급한 것인지** 서버에서 확인한다(입력값 신뢰 금지)

