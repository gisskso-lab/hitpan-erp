## 4. 마이그레이션이 안전한 이유

과거분은 `source_id` 로 가려진다.

| | source_id |
|---|---|
| 매출반품 확정 | `returnId` (`SalesService.cs:2487`) |
| 명세서 취소 | `deliveryId` (`SalesService.cs:1200`) |

⇒ `sales_returns` 에 그 id 가 **실재하는 행만** 반품이다.

### 🔴 [4] 검증 지적 — 이 절의 종전 서술이 틀렸었다

종전엔 명세서취소 `source_id` 를 `'{deliveryId}:cancel'` 로 적었다. **틀렸다.**
`:cancel` 접미는 `MonthlySummaryGuard` 멱등키 얘기(`SalesService.cs:1217` 주석)이고,
**회계 분개 호출(1197행)은 순수 `deliveryId` 를 넘긴다.**
주석을 읽고 **다른 서브시스템의 규칙을 회계에 옮겨 적었다** — 받아쓰기다.

**그래서 안전한가**: 🟢 안전하다. 다만 근거가 다르다.

- `delivery_id`·`return_id` 는 **둘 다 `Guid.NewGuid()`** 다
  (`SalesService.cs:255` · 마이그 경로 `MdbMigrationService.cs:3886·4276`)
- ⇒ 서로 겹칠 확률은 실질적으로 0. 레거시 마이그 데이터도 GUID 로 새로 발급된다

⚠️ **한계 명시**: 만약 어떤 경로가 `delivery_id` 와 `return_id` 에 **같은 값**을 넣는다면
그 명세서취소 분개는 반품으로 오분류된다. 현재 코드에 그런 경로는 없으나,
**ID 발급 방식을 바꿀 때 이 마이그의 전제가 깨진다.**
