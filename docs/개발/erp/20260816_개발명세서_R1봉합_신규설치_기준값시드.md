## ① 무엇이 고장나 있었나

검증팀장 데이비드 박이 격리 DB 에 출하 DDL 을 그대로 넣어 실측한 결과다.

| 확인 | 결과 |
|---|---|
| `device_slot_policy_settings` 행 수 | **0행** |
| `schema_migrations` 의 DB-104 | **이미 `success=1`** (`installer/hitpan_db_clean.sql:3354`) |
| `MigrationRunner.cs:91-104` | `success=1` 이면 **건너뛴다** |

**진짜 원인은 시드가 "아직 없는 것"을 기준으로 도는 것이다.**
DB-104 시드는 `FROM (SELECT DISTINCT tenant_id FROM local_subscription) AS t` 로 회사를 고르는데,
**신규 설치 시점에는 그 표가 0행**이다(회사가 아직 안 만들어졌다).
그 뒤 회사가 생겨도 DB-104 는 이미 성공 표시라 **다시 돌지 않는다.**

⇒ **신규 고객은 정책 표가 영원히 비어** 요금 한도가 언제나 코드 상수(`FallbackLimits`)로 결정됐다.

⚠️ **회귀가 아니라 미달성이다.** `FallbackLimits` 숫자가 시드와 같으므로 **요금이 틀리지는 않았다.**
다만 대표가 화면에서 한도를 고쳐도 **반영될 표가 없었다** — 헌법 #11(기준값은 어드민이 설정)이
신규 고객에게만 무력이었다.

## ② 무엇을 어떻게 고쳤나

### ②-1 회사 생성 경로에 기준값 시드 추가 — 선례를 그대로 따랐다

**`src/HitPan.API/Services/CompanyBootstrapProvisioner.cs:412`** (호출) ·
**`:465-`** (`SeedDeviceSlotPolicyAsync`)

바로 위 `labor_policy_settings`(DB-96) 시드(`:353-374`)가 **똑같은 문제를 이미 이렇게 풀었다.**
새 구조를 만들지 않고 **같은 자리에 같은 방식**으로 붙였다. 회사가 만들어지는 이 시점에는
테넌트가 존재하므로 `CROSS JOIN` 문제가 없다.

### ②-2 🔴 트랜잭션 **밖**에 둔 이유 — 시드가 회사 생성을 막으면 안 된다

작업지시서 §7 이 못 박은 자리다. 위 트랜잭션 **안**에 넣으면 이 표 하나가 잘못됐을 때
**부모계정·사원·창고까지 통째로 되돌아가 설치 자체가 실패**한다.

그런데 이 표는 **없어도 회사가 돈다** — 안전망이 같은 숫자를 준다.
⇒ **커밋 뒤에 따로**, 실패해도 회사는 만들어지게. 단 **기록은 반드시 남긴다**(헌법 #15).

```
catch (Exception ex)  // CompanyBootstrapProvisioner.SeedDeviceSlotPolicyAsync
    _logger.LogError(ex, "[CompanyBootstrap] 🔴 기기 슬롯 기준값 시드 실패 — 회사 생성은 계속한다. …");
```

### ②-3 B-5 — `Debug.WriteLine` → `ILogger.LogWarning` (범위 포함)

**`src/HitPan.Infrastructure/Services/TenantDeviceService.cs:79-95`**(생성자) · **`:842`**(catch)

`Debug.WriteLine` 은 `[Conditional("DEBUG")]` 이라 **Release 빌드에서 호출 자체가 사라진다.**
고객 PC 에는 아무 기록도 안 남았다. **운영에서 사라지는 기록은 기록이 아니다.**

🔴 이 조항이 삼키는 것은 **"요금 한도를 설정에서 못 읽었다"** 는 신호다.
**R-1 을 눈에 안 띄게 만든 것이 바로 이 catch** 라, 검증팀이 둘을 한 몸으로 보라고 판정했다.

**DI 영향 없음** — `ILogger<TenantDeviceService>? logger = null` 선택 인자로 받고
미주입 시 `NullLogger` 로 떨어뜨렸다. `Program.cs:107` 등록(`AddScoped<ITenantDeviceService, TenantDeviceService>`)은
**한 글자도 안 고쳤고**, 컨테이너가 알아서 실제 로거를 넣는다.
로그 때문에 로그인이 막히는 일이 없어야 하므로 안전측으로 잡았다.

## ③ 🔴 값이 갈라지지 않게 어떻게 막았나 (작업지시서 최우선 요구)

### 문제 — 이제 같은 숫자를 **세 곳**이 알아야 한다

① 마이그 `DB-104`(기존 고객) · ② 회사 생성 시드(신규 고객) · ③ 안전망 `FallbackLimits`

세 곳에 숫자를 따로 적으면 **하나를 고칠 때 나머지가 옛 숫자로 남는다** —
이 차수가 계수 8곳을 2곳으로 모으며 없앤 바로 그 병이다.

### ⚠️ 완전한 단일 정의는 **불가능하다** — 왜인지 정확히 적는다

`DB-104` 는 `MigrationRunner` 가 실행하는 **순수 `.sql` 파일**이라 C# 값을 주입할 수 없다.
그리고 **이미 적용된 고객이 있을 수 있어 고쳐서도 안 된다**(작업지시서 §2 "하지 않는 것").

### ⇒ 택한 방법 — 한 벌을 두 표현으로 적고 **기계가 대조**한다

**신규 파일 `src/HitPan.Infrastructure/Services/SlotPolicyDefaults.cs`** 가 코드 쪽 유일한 정의다.

| 무엇 | 어디서 값을 읽나 |
|---|---|
| ② 회사 생성 시드 | `SlotPolicyDefaults.Rows` |
| ③ 안전망 `FallbackLimits` | `SlotPolicyDefaults.Value(...)` — **숫자를 지웠다**(`TenantDeviceService.cs:891`) |
| ① 마이그 `DB-104` | 못 바꾼다 ⇒ **게이트가 전수 대조**(G-20) |

🔴 **종전 `FallbackLimits` 는 `switch` 안에 `(5,3)·(10,8)…` 을 직접 적고 있었다.**
그대로 두면 시드와 **같은 숫자가 두 벌**이 된다. 그래서 안전망도 같은 정의를 읽게 바꿨다.
**②와 ③ 사이에는 이제 갈라질 여지 자체가 없다.**

①과의 일치는 게이트가 막는다 — 값이 갈라지는 순간 **시험이 빨간불**이 된다.
그 시험은 **DB 없이도 도는 순수 파일↔코드 대조**라 **어디서 돌리든** 걸린다(실측 0.75초 만에 FAIL).

## ⑤ 🔴 판단이 갈린 자리 — 게이트가 내 코드의 버그를 잡았다

### 갈림 1 — `WHERE NOT EXISTS` 의 기준을 **어디에 두나** (이번 작업 최대 함정)

처음에 DB-104 를 그대로 옮겨 **줄마다** `WHERE NOT EXISTS (… p.tenant_id = @TenantId)` 를 걸었다.
**G-19 가 즉시 잡았다:**

```
Assert.Equal() Failure: Values differ
Expected: 15
Actual:   1
```

**왜 1줄만 들어갔나** — 조건의 기준이 **열쇠가 아니라 테넌트**라서,
**첫 줄이 들어간 순간 그 줄이 스스로 조건을 깨뜨려** 2~15번째가 전부 건너뛰었다.

⚠️ DB-104 에서는 이 형태가 옳다. 그것은 `CROSS JOIN` 으로 **15줄을 한 문장에** 넣어
조건이 **한 번만** 평가되기 때문이다. **줄마다 도는 C# 루프로 옮기면 의미가 달라진다.**

⇒ **판단을 루프 밖으로 뺐다.** "손댔는가" 를 맨 앞에서 **한 번만** 묻는다.
이러면 세 요구가 동시에 선다 — 손 안 댄 회사는 15줄 전부(G-19) / 손댄 회사는 무접촉(G-22) /
두 번 돌려도 안 늘어남(G-21).

🔴 **이것이 "동작을 검사하는 게이트" 의 값어치다.** 글자만 봤다면
`WHERE NOT EXISTS` 가 멀쩡히 적혀 있으니 **초록불이었을 것**이고,
신규 고객은 **15줄 중 1줄만 받은 채** 출하됐을 것이다.

### 갈림 2 — G-22 가 처음엔 **가짜 게이트**였다 (반증 3 이 드러냈다)

반증 중 변형을 넣었는데 **G-22 가 통과**했다. 파고들어 보니:

대표가 고친 열쇠로 **첫 번째 열쇠**(`tier.basic.pc_limit`)를 골랐더니,
시드가 그 열쇠에서 **UNIQUE 1062 로 죽어** 나머지 14줄을 시도조차 안 했다.
⇒ "안 덮어썼다" 는 결과가 **막아서가 아니라 죽어서** 나왔고, 게이트는 그 차이를 못 봤다.

```
ERROR 1062 (23000): Duplicate entry 'T-PROBE-tier.basic.pc_limit' for key 'uk_slot_policy_tenant_key'
```

⇒ 대표가 고친 열쇠를 **마지막 열쇠**(`SlotPolicyDefaults.Rows[^1]`)로 바꿨다.
그러면 시드가 앞의 14줄을 **먼저 넣으려 시도**하므로 무접촉이 깨지면 **행 수로 반드시 드러난다.**
바꾼 뒤 같은 변형에서 **FAIL 했다**(위 반증 4).

🔴 **게이트를 만든 뒤 반증하지 않았으면 이 가짜를 그대로 뒀을 것이다.**

### 갈림 3 — DB 가 없는 환경에서 **조용히 통과**시키는 것의 대가

G-19·G-21·G-22 는 MariaDB 가 없으면 맨 앞에서 `return` 한다(거짓 실패 방지).
**대가를 정확히 적는다** — 그 환경에서는 **아무것도 검사하지 않는다. 초록불이 곧 안전이 아니다.**
⇒ 진짜 실행은 MariaDB 가 있는 자리에서만 일어나고, 그래서 **⑥ 에 실제 출력을 남긴다.**
🔴 다만 **G-20 의 값 대조는 DB 없이도 돌아** 값 갈라짐만큼은 환경과 무관하게 막힌다.
