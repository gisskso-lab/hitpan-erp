## 1. 진범 (5인 실측 확정, 받아쓰기 아님)

### 1.1 관측된 사고
- Windows Sandbox에 범용 EXE(1.2.25) 설치 → 터널 `test1.hitpan.kr/setup/license` = **"페이지를 찾을 수 없습니다"(NotFound)**.
- 그런데 로컬 `localhost:5234/setup/license` = **setup 화면 정상 표시**.

### 1.2 진범 (파일:라인 근거)
**HitPan.API는 Blazor를 ProjectReference 하지 않는데도, `dotnet publish -o` 가 출력 폴더를 청소하지 않아 개발 PC의 로컬 `wwwroot` 잔재(2026-05-20자 옛 WASM, setup 라우트 없음)가 `bundle/api` 에 남아 설치본에 실려 나가고, API가 그 옛 SPA를 서빙한다.**

| 근거 | 파일:라인 | 실측값 |
|---|---|---|
| API가 Blazor 서빙 (진입) | `src/HitPan.API/Program.cs:355~372, 392~395` | `hasBlazor` → `UseBlazorFrameworkFiles`+`MapFallbackToFile("index.html")` |
| API는 Web 참조 안 함 | `src/HitPan.API/HitPan.API.csproj:12` | `WebAssembly.Server` 패키지만, HitPan.Web ProjectReference **없음** |

### 1.3 설계 정합 (배포 런타임 단일 진입점)
- 배포 시 WASM 서빙 = **`web-server.ps1`(5234, `web\wwwroot`) 하나여야 정합.** API(5257)는 순수 `/api/*` JSON 서버.
- web-server.ps1이 `/api/*` → 5257 프록시(`web-server.ps1:88~139`) + SPA fallback(`152~163`)을 이미 전담. **API의 Blazor 서빙은 중복·오염 경로.**

## 2. 봉합 범위 (4인 수렴 — 5개 작업)

### W1. API의 Blazor(WASM) 정적 서빙 제거 — 단일 진입점 정합
- **대상**: `src/HitPan.API/Program.cs` L354~372(hasBlazor 분기 + UseBlazorFrameworkFiles/UseStaticFiles), L392~395(MapFallbackToFile).
- **조치**: API가 WASM/index.html을 서빙하지 않도록 정리. 배포 정본은 web-server.ps1(5234) 단일 진입점.
- **⚠️ 확인 필요(착수 전)**: 로컬 개발 시 API 단독으로 Blazor를 띄우는 경로가 있는지(개발 편의) 전수. 있으면 개발 전용 조건(`!IsProduction()`)으로 격리하고 배포에선 완전 제거. **회귀 방지 = 로컬 개발 흐름 안 깨지게.**

### W2. 빌드 산출물 청소 — publish 전 api 폴더 청소
- **대상**: `installer/build-installer-universal.ps1:97` (API publish 직전).
- **조치**: `dotnet publish` 전 `Remove-Item -Recurse -Force "$BundleDir/api"` (기존 잔재 완전 제거 후 새로 publish). Web·Watchdog도 동일 점검.

### W3. api/wwwroot 재오염 FAIL 게이트 신설 (헌법 #36 Web판 대칭)
- **대상**: `build-installer-universal.ps1` W2 직후.
- **조치**: publish 후 `$BundleDir/api/wwwroot/_framework/*.wasm` 존재 시 **FAIL(exit 1) 출시 차단**. (API는 WASM을 담으면 안 되므로 존재 자체가 오염 신호.) 기존 Web 완전성 게이트(L104~117)와 대칭.

### W4. 리포 잔재 삭제
- **대상**: `installer/api-wwwroot-backup-20260526/` (82MB·1322파일·git 미추적).
- **조치**: 디렉터리 삭제. git 미추적이라 커밋 영향 0. (재오염 재유입원 제거.)

### W5. 종단 스모크 게이트 검토 (설계팀장 제안, 별건 가능)
- **대상**: `build-installer-universal.ps1` DB 게이트(현재 테이블124·트리거3·데이터0만 검사).
- **조치**: 컬럼 레벨 정합 + 3흐름(매입/판매/BOM 확정) 종단 스모크 추가 검토. **범위 크면 별도 작업지시서로 분리** (헌법 #36·#20 재끊김 차단, but W1~W4와 결합도 낮음).

## 3. 완료 기준 (검증팀장 못박음 — 봉합 커밋 ≠ 완료)

**아래 종단 실측 로그가 남기 전엔 "봉합 완료"·"종단 통과" 단어 금지. 개발PC·로컬 5234 정상은 증명 0 ([[feedback_dev_pc_proves_nothing]]).**

1. 정본 재빌드 → **깨끗한 Windows Sandbox**(새로 켠 백지)에 EXE 한 방 설치
2. **터널 URL(test1.hitpan.kr)로만** 접속 (localhost 금지):
   - ① 브라우저가 받은 WASM = 방금 publish한 새것(해시/크기 대조, 옛것 배제)
   - ② setup 화면 표시 → 부모계정 생성 응답 201 + DB users 1행
   - ③ 로그인 200 + `/me` 복호화 200 (회사정보 자동반영 확인)
   - ④ 6단계 각 1개: 설정(사원목록)·마스터(상품목록)·매입(발주저장)·판매(거래명세서)·현황(재고)·재무(회계) 각 200 + 화면 렌더
3. **SoD**: 만든 사람 ≠ 검증. 검증팀이 Sandbox 종단 로그(응답코드·화면) 독립 재현·첨부한 것만 종합보고에 오름. 로그 없는 "통과" = 반려.

**검증 방식(검증팀장)**: "전부 봉합 후 한 번에 종단" 금지 → **한 벽 봉합 → 즉시 터널 종단 실측 → 다음 벽** (깨진 지점 못 잡으면 두더지잡기 재발).

## 4. 4인이 경고한 남은 벽 (이번 W1~W4로 다 안 풀림 — 종단서 드러날 것)

이번 봉합은 **1차 벽(터널 setup NotFound)**만 근본 제거. 실고객 종단엔 아래가 **터널 경유 미검증**으로 남아있음. 종단 실측서 순차 발화 예상:

| # | 남은 벽 | 지목 | 근거 |
|---|---|---|---|
| a | create-parent 토큰키(BOOTSTRAP_TOKEN_KEY) 정합 | 풀스택 | 최근 fa3f03f가 손댐 = 흔들리는 구간, 정본 환경변수 미확증 |
| b | 로그인 후 회사정보 자동반영(local_company) | 풀스택 | 터널 경유 미검증 |
| c | **6단계 clean DB 시드 500** | 설계팀 | 컬럼 미편입·accounts/enum 시드·원장 트리거 = 헌법 #36 상습 벽 (재끊김 확률 최고) |
| d | 재설치 터널 secret 복구 (헌법 #28) | 네트워크 | 관리형 터널 D경로 백지PC 발화 미실증 |
| e | 2대째 설치 터널 name 재사용 → UUID 경합 | 네트워크 | 한 tenantCode 두 PC = 비결정적 라우팅. "1 tenantCode ↔ 1 활성 오리진" 불변식 미강제 |

→ **a~e는 종단 실측에서 하나씩 드러나면 각각 근본 봉합**(한 벽씩). W5(스모크 게이트)가 c를 사전 차단.

## 6. PM 종합 판단

사장님 목적(재발 방지)에 정합한 근본 봉합 = **"API가 WASM을 서빙하는 구조 자체를 없애 web-server(5234) 단일 진입점으로 통일 + 빌드가 잔재를 재오염 못 하게 게이트."** 이것이 W1~W4. W5는 6단계 재끊김(c)을 사전 차단하는 상류 방어. 종단 통과의 진짜 확정은 **깨끗한 Sandbox 터널 경유 실측**뿐이며, 그 과정에서 a~e가 드러나면 순차 근본 봉합.
