## ① 현행 계수 스냅샷 — 어떤 입력에 몇 슬롯을 세는가

### ①-0 계수의 원형 — 네 곳에 복제된 같은 SQL

슬롯을 세는 SQL 은 **한 가지 모양**이고, 그것이 **네 번 복제**돼 있다.

```sql
SELECT device_type AS t, COUNT(*) AS c
FROM tenant_devices
WHERE tenant_id = @TenantId AND status = 'approved'
GROUP BY device_type
```
```csharp
int pcUsed     = counts.Where(x => x.t == "pc").Sum(x => x.c);
int mobileUsed = counts.Where(x => x.t == "mobile" || x.t == "tablet").Sum(x => x.c);
```

| 복제 위치 | 파일:줄 | 부르는 경로 | 모양 |
|---|---|---|---|
| 복제 A | `TenantDeviceService.cs:97-107` | `GetQuotaAsync` (화면 표시용) | `GROUP BY` 전체형 |
| 복제 B | `TenantDeviceService.cs:245-255` | `RegisterOrRefreshAsync` 신규 경로 | `GROUP BY` 전체형 |
| 복제 C | `TenantDeviceService.cs:410-420` | `ApproveAsync` 승인 시 재검사 | `GROUP BY` 전체형 |
| 복제 D | `TenantDeviceService.cs:597-603` | `RegisterMobileByTokenAsync` (QR) | **모양이 다르다** — `COUNT(*)` 단일값 · `device_type IN ('mobile','tablet')` · **모바일만** |
| 복제 E (별 시스템) | `DeviceRegistrationController.cs:98-101` | 백오피스 등록 | **또 다르다** — `device_type = @Type` 등호 비교. `tablet` 이 어느 칸에도 안 잡힌다 |

🔴 **D 와 E 는 A·B·C 와 형태부터 다르다.** "네 곳 복제"라고 부르지만 **똑같은 복제가 아니다.**
P1 이 단일 메서드로 모을 때 **D 를 A 형태로 바꾸면 PC 칸까지 계산하게 되고, E 를 옮기면 `tablet` 처리가 달라진다.**
→ 아래 §"P1·P2 구현자에게 넘기는 주의사항" D-1·D-2 참조.

### ①-1 한도값이 만들어지는 방법 (계수의 반대편)

| 항목 | 파일:줄 | 값 |
|---|---|---|
| 티어별 기본값 | `TenantDeviceService.cs:662-669` | `basic (5,3)` · `pro (10,8)` · `premium (100,80)` · `trial (10,5)` · 그 외 `(5,3)` |
| 추가슬롯 산식 | `:93-94` · `:242-243` · `:407-408` · `:595` | `pcLimit += extra` · `mobileLimit += extra * 2` |

⚠️ **추가슬롯 산식도 4곳 복제**다. 그런데 `:595`(QR 경로)는 **`mobileLimit` 만** 더한다 — PC 를 안 쓰므로 자연스럽지만, 단일화 시 놓치기 쉬운 자리다.
⚠️ 사장님 확정은 **1+1**(추가슬롯 1만원 = PC 1 + 모바일 1). 현행 코드는 **1+2**. **P2 범위**이며 P0 에서는 고치지 않는다.

### ①-3 각 경우의 상세 — 무엇이 세어지고 무엇이 안 세어지는가

**경우 1 — 신규 기기 로그인 (`RegisterOrRefreshAsync` 신규 경로)**
- 지문이 비었으면 `:128-136` 에서 **등록 자체를 건너뛴다** → 슬롯 +0, 로그인은 통과. (`fingerprint` NOT NULL 방어)
- 종류 결정: `AuthController.cs:93` 이 `request.DeviceType ?? "pc"` 로 **미리 채운 뒤** 넘긴다 → `TenantDeviceService.cs:260` 이 `NormalizeDeviceType(...) ?? "pc"`.
  🔴 즉 **클라이언트가 종류를 안 보내면 무조건 `pc`(비싼 칸)** 다. `NormalizeDeviceType` 의 "모르면 mobile" 원칙(`:724`)이 **이 경로에서는 도달하지 않는다** — `:93` 의 `?? "pc"` 가 먼저 채워 버리기 때문. (명세서 §3-3, **P1 범위**)
- 한도 초과 시 `:278`/`:283` 이 `allowed=false` 반환 → `AuthController.cs:101-105` 가 **401 Unauthorized**. (`:271` 주석은 "로그인 거부 아니다"라 하나 **코드는 거부한다**. 사장님 결재로 **막는 것이 맞다**고 닫혔다 — 명세서 §10-1. **주석이 틀렸다**)
- 승인제 스위치 `_approvalEnabled`(`:55`, `appsettings` `DeviceApproval:Enabled`, **기본 false**)가 켜지면 `status='pending'` 으로 INSERT → **그 순간엔 계수에 안 잡힌다**(I-7).

**경우 2 — 기존 기기 재로그인 (갱신 경로) — 🔴 한도 검사를 다시 하지 않는다**
- `:150` `if (existing is not null)` 분기로 들어가면 **계수 SQL 도 한도 비교도 전혀 실행되지 않는다.**
- 이것은 **의도된 설계**다 — `:196-201` 주석: *"이미 등록된 기기만 지나간다… 한도 검사에 다시 들어가지 않는다… 쓰던 사람이 쫓겨나지 않는다."*
- 부수 효과: `:214` 가 `device_type` 을 COALESCE 로 갱신하므로 **기기가 PC 칸 ↔ 모바일 칸을 옮겨 다닐 수 있고, 그때 한도를 잠깐 넘길 수 있다.** 주석이 이를 명시적으로 허용한다(`:198-201`).
- `revoked` 인데 `is_main_pc=1` 이면 `:170` 조건이 거짓 → **막지 않고 통과**시킨다(메인PC 자기구제).

**경우 3 — 메인PC 자동 등록 (`MainPcRegistrationService`)**
- 로그인과 무관하게 **API 기동 시** 1회 실행(`BackgroundService`). 최대 3회 재시도(`:93-124`).
- 지문 = `"MAINPC-" + SHA256(MachineName|TENANT_CODE|SLOT_INDEX)[..16]` (`:230-239`). **브라우저 `HFPv2-` 와 접두어부터 다르다.**
- 🔴 **한도를 보지 않고 INSERT 한다**(`:192-196` 이 의도적이라 명시). 그러나 `status='approved'`, `device_type='pc'` 이므로 **다른 모든 계수(복제 A·B·C)에는 정상적으로 1대로 잡힌다.**
- ⇒ **`TenantDeviceService.cs:165` 주석 "메인PC 는 슬롯을 세지 않고 한도에도 안 걸린다" 는 절반만 맞다.**
  - 맞는 절반: 메인PC **자신을 등록할 때** 한도를 안 본다.
  - **틀린 절반: 등록된 뒤에는 다른 기기들의 한도 계산에 1대로 포함된다.** `is_main_pc` 를 제외하는 절이 **계수 SQL 5곳 어디에도 없다.**
  - 사장님 확정(*"기기 1대 = 슬롯 1개, 메인PC 포함"*)은 **코드 동작과 일치**한다. **주석을 고쳐야 한다**(P1 범위).
- 중복 방지 2겹: ① 같은 지문 있으면 표식만 갱신 후 return(`:153-171`) ② 이미 `is_main_pc=1` 인 행이 있으면 새로 안 만듦(`:179-189`).

**경우 4 — QR 모바일 등록 (`RegisterMobileByTokenAsync`)**
- 계수가 **복제 D** — 유일하게 `COUNT(*)` 단일값이고 **모바일만 센다.** PC 칸은 아예 계산하지 않는다.
- 한도도 `mobileLimit` 만 만든다(`:594-595`, `GetLimitsForTier` 의 PC 값은 `_` 로 버림).
- 같은 지문이 이미 있으면 `:583-587` 로 **멱등 성공**(+0). 없으면 `:609` INSERT (+1).
- 🔴 **승인제 스위치(`_approvalEnabled`)를 보지 않는다.** QR 을 띄운 것 자체가 대표의 승인이라는 설계(`:551`). 즉 승인제를 켜도 QR 경로는 **즉시 `approved`** 다.

**경우 5 — 승인(`ApproveAsync`) 시 재검사**
- **조회 열쇠가 `device_id`** 인 유일한 경로(`:387-389`). 지문을 안 본다.
- 멱등 가드: 이미 `approved` 면 `null` 반환하고 **아무것도 안 한다**(`:395`) → 재검사도 안 돈다. `revoked` 면 `throw`(`:396-397`).
- `pending` 인 것만 **복제 C** 로 재검사한다(`:410-417`). 검사 대상 칸은 **그 기기의 `device_type` 기준**(`:422-425`).
- 🔴 재검사가 존재하는 이유가 `:399-401` 에 있다: *"대기 목록에 3대가 쌓여 있고 남은 슬롯이 1대라면 첫 승인은 되고 나머지는 막혀야 한다."*
- ⚠️ **자기 자신은 아직 `pending`** 이므로 계수(`status='approved'`)에 안 들어간다 → `pcUsed >= pcLimit` 비교가 올바르게 성립한다. **P1 이 계수 대상을 넓히면 이 경계가 깨진다** (주의사항 D-4).

### ①-4 계수에서 제외되는 것 (I-7 현행 준수 확인)

| 상태 | 계수 포함? | 근거 |
|---|---|---|
| `approved` | ✅ 포함 | 5곳 전부 `status = 'approved'` |
| `pending` | ❌ 제외 | 동일 |
| `revoked` | ❌ 제외 | 동일 |
| `is_main_pc = 1` | ✅ **포함** (제외 절 없음) | 5곳 전부 `is_main_pc` 언급 0 |
| `device_type = 'tablet'` | ✅ mobile 칸 (단, **복제 E 는 제외**) | A·B·C `x.t=="tablet"` / D `IN(...)` / **E `= @Type` 등호라 누락** |

🟢 **I-7(승인된 것만 계수)은 현행에서 지켜지고 있다.** P1 은 이것을 **유지만** 하면 된다.

## ② 3증상 재현 대본

> 🔴 **헌법 #39 — 운영(demo·3306)·NCP 절대 무접촉.** 아래는 **샌드박스 또는 별도 테스트 슬롯**에서만 한다.
> ⚠️ 실측 자체가 슬롯을 먹는다(명세서 §8). basic 기본값이 PC 5 / 모바일 3 이므로 **PC 슬롯 5개를 쓰면 그 다음 로그인이 401 로 막힌다.** 대본을 돌리기 전에 남은 슬롯을 먼저 확인하라.

### ②-0 공통 준비

1. 샌드박스(또는 테스트 슬롯)에 히트판을 설치하고 API·Web 을 띄운다.
2. 🔴 **접속 주소를 하나로 고정한다.** 사장님 실측과 같은 조건을 만들려면 `test1.hitpan.kr` **하나만** 쓴다.
   `localhost` · `127.0.0.1` 을 섞으면 **7/2 에 확정된 origin 격리**가 끼어들어 원인이 뒤섞인다(옛 대본 참조).
3. 대표계정으로 로그인 → **등록기기 관리 화면**을 연다. **시작 시점의 줄 수와 각 줄의 이름·종류를 적어 둔다.** 이것이 기준선이다.

### ②-1 관찰 지점 (F12 — 값을 눈으로 본다)

| 무엇을 | 어디서 | 봐야 할 값 |
|---|---|---|
| 브라우저가 보낸 지문 | F12 → **Network** → `login` 요청 → **Payload** | `deviceFingerprint` · `deviceType` · `deviceName` |
| 브라우저에 저장된 지문 | F12 → **Application → Local storage → (현재 origin)** | `hitpan_fp_id` |
| 서버가 돌려준 장비넘버 | F12 → **Network** → `login` **응답 본문** | `deviceId` · `deviceNewlyRegistered` |
| 브라우저에 저장된 장비넘버 | Application → Local storage | `hitpan_device_id` · `hitpan_auth_key` |
| 슬롯 증가 여부 | ERP **등록기기 관리 화면** | **줄 수** · 새 줄의 이름/종류/등록시각 |

🔴 **판정의 핵심은 `hitpan_fp_id` 와 등록기기 줄 수 두 가지다.**
- 줄이 늘었는데 `hitpan_fp_id` 가 **바뀌었으면** → 지문이 흔들린 것.
- 줄이 늘었는데 `hitpan_fp_id` 는 **그대로면** → 지문이 아닌 다른 축(주소·서버 조회)이 원인.
- 응답의 `deviceNewlyRegistered=true` 가 **"슬롯이 방금 하나 늘었다"** 는 서버의 자백이다. 이 값을 먼저 보라.

### ②-2 증상 1 — 메인PC 자동 등록 + 그 PC 브라우저 접속 = 슬롯 2개

| 단계 | 할 일 | 관찰 | 기대(현행 코드 기준) |
|---|---|---|---|
| 1-1 | 히트판 API 를 **재기동**한다 (`MainPcRegistrationService` 는 기동 시 1회 실행) | API 로그에 `[MainPc] 메인PC 를 등록 기기로 추가했다 … 슬롯 1대를 사용한다` | 이 줄이 뜨면 등록 성공 |
| 1-2 | 등록기기 화면을 새로고침 | **줄 수 +1**, 이름 = `회사 서버 (자료 보관 컴퓨터)`, 종류 = 컴퓨터 | 🔴 **슬롯 1개 사용** |
| 1-3 | **그 메인PC 자체의 브라우저**로 `test1.hitpan.kr` 접속 → 로그인 | Network `login` Payload 의 `deviceFingerprint` = `HFPv2-xxxxxxxx` | 접두어가 `HFPv2-` |
| 1-4 | 응답 본문을 본다 | `deviceNewlyRegistered` | 🔴 **`true` 로 나와야 증상 재현** |
| 1-5 | 등록기기 화면 새로고침 | **줄 수 또 +1** (예: `Windows · Chrome`) | 🔴 **한 대의 PC 가 2줄 = 슬롯 2개** |

**왜 이렇게 되나 (코드 근거 — 확정)**
`MainPcRegistrationService.cs:238` 이 만드는 지문은 `MAINPC-…`, `device-fingerprint.js:66` 이 만드는 지문은 `HFPv2-…`.

## ③ 🔴 "새 창마다 슬롯" 원인 규명

### ③-0 결론 — 먼저 밝힌다

> ## ⚠️ **재현/원인 미확인 — 코드상 설명되지 않음**

주소를 `test1.hitpan.kr` **하나만** 썼다는 사장님 확정을 전제로 하면, **같은 브라우저의 새 창이 새 지문을 만드는 경로를 코드에서 찾지 못했다.**

**왜 설명되지 않는가 — 판정의 뼈대**

`getFingerprint`(`device-fingerprint.js:56-77`)는 **캐시를 먼저 본다.**

```js
var cached = localStorage.getItem('hitpan_fp_id');
if (cached) return cached;          // :59-60
```

`localStorage` 는 **origin 단위**로 공유된다 — **창·탭 단위가 아니다.**
주소가 하나(= origin 하나)이고 같은 브라우저 프로필이면, 새 창은 **같은 `localStorage` 를 본다.**
⇒ 1-3 에서 이미 `hitpan_fp_id` 가 저장됐으므로(`:75`), 새 창은 **`_envSeed()` 를 아예 실행하지 않고 캐시값을 그대로 돌려준다.**

🔴 **따라서 `_envSeed` 재료가 창마다 달라지는지 여부는, 캐시가 살아 있는 한 애초에 문제가 되지 않는다.**
증상이 실재한다면 **캐시가 안 읽히는 경로가 먼저 있어야 한다.** 그 경로를 코드에서 찾지 못했다.

### ③-2 🔴 `availWidth`/`availHeight` — 지시된 핵심 검토

**`availWidth`/`availHeight` 는 "창" 이 아니라 "화면(모니터)에서 창이 쓸 수 있는 영역" 이다.**

| 조건 | 값이 달라지는가 | 근거 |
|---|---|---|
| 창 **크기**를 바꾼다 (최대화/복원/드래그) | ❌ **안 달라진다** | 창 크기는 `window.innerWidth`/`outerWidth` 다. `screen.avail*` 은 창을 보지 않는다 |
| 창 **위치**를 옮긴다 (같은 모니터 안) | ❌ **안 달라진다** | 동일 |
| **새 창을 연다** | ❌ **안 달라진다** | 동일 |
| **작업표시줄을 자동 숨김/표시로 바꾼다** | ⚠️ **달라질 수 있다** | `avail*` 은 작업표시줄 등 시스템 UI 를 뺀 값이라는 것이 이 속성의 정의다 |
| **다중 모니터**에서 창을 **다른 모니터로 옮긴 뒤** 페이지를 새로 연다 | ⚠️ **달라질 수 있다** | 브라우저는 대개 **창이 놓인 모니터**를 기준으로 `screen` 을 보고한다. 해상도·배율이 다른 보조 모니터면 값이 바뀐다 |
| **디스플레이 배율(DPI)** 을 바꾼다 | ⚠️ **달라질 수 있다** | `screen.*` 은 CSS 픽셀로 보고되어 배율의 영향을 받는다 |

> 🔴 **판정**: 사장님이 겪으신 **"새 창을 열면"** 이라는 조작 자체로는 `avail*` 이 달라지지 않는다.
> **단, 그 새 창이 다른 모니터에 뜨는 환경이라면 달라질 수 있다.** 이것은 **후보 가설**이며 확정이 아니다.
> ⚠️ 그리고 **이 가설조차 캐시(`hitpan_fp_id`)가 살아 있으면 성립하지 않는다.** 캐시가 먼저 반환되기 때문이다.

### ③-3 `localStorage` 캐시가 안 읽히는 경로 — 전수 검토

**증상이 실재하려면 이 중 하나가 참이어야 한다.** 코드에서 찾은 것과 못 찾은 것을 가른다.

| `getFingerprint` 가 캐시를 안 보는 분기 | ❌ 없음 | `:59-60` 이 **무조건 먼저** 캐시를 본다. 우회 분기 0개 |
| 앱이 `hitpan_fp_id` 를 **지우는** 코드 | ❌ **0곳** | 전수 grep 결과 `hitpan_fp_id` 를 `removeItem`·`clear` 하는 코드가 **repo 전체에 없다**. `clearDeviceId`(`:242`)·`clearAuthKey`(`:261`)는 **다른 키**를 지운다 |

🔴 **결론: `hitpan_fp_id` 가 창마다 새로 만들어지는 경로를 코드에서 찾지 못했다.**

### ③-4 🔴 로그인 페이지가 별도 창/시크릿으로 열리는 경로가 있는가 — 전수 검토

**`window.open` 호출처는 repo 전체에 2곳뿐이다.**

| 위치 | 무엇을 여나 | 로그인/지문에 닿나 |

**메신저 팝업 축 — 검토 결과**

- 팝업은 히트판 URL 을 열므로 **Blazor 가 새로 부팅되고 `device-fingerprint.js` 가 다시 로드된다.**
- 🔴 그러나 팝업은 **같은 origin** 이므로 **`localStorage` 를 부모와 공유한다** → `hitpan_fp_id` 가 이미 있으면 그대로 읽는다.
- 🔴 그리고 팝업은 **로그인을 다시 하지 않는다.** `storage.js:46-69` `hitpanStorage_inheritFromOpener` 가 부모 창의 `sessionStorage` 에서 **토큰을 물려받아** 로그인 화면을 건너뛴다(`index.html:97-101`, Blazor 시작 **전에** 실행).

- ⚠️ **단, 물려받기가 실패하면**(부모 창이 닫혔거나 예외 — `:64-68`) 팝업은 **로그인 화면을 띄운다.** 거기서 로그인하면 `login` 이 호출된다.
  🟢 그래도 지문은 공유 `localStorage` 에서 같은 값이 나오므로 **기존 기기 갱신 경로(경우 2)로 들어가 슬롯은 안 는다.**
- ⇒ **후보 가설이지만, 코드상으로는 슬롯 증가로 이어지지 않는다.** ②-4 의 3-6 으로 실측 확인 대상.

**시크릿(private) 창을 여는 코드** — ❌ **없다.** 브라우저는 스크립트로 시크릿 창을 열 수 없고, repo 에 그런 시도도 없다.
⚠️ **사람이 직접 시크릿 창을 열면** `localStorage` 가 격리되어 지문이 새로 만들어진다. 그러나 그 경우에도 **환경해시는 같은 값**이라 슬롯은 안 늘어야 한다(같은 PC·같은 브라우저).

### ③-5 배제된 가설 (실측으로 기각한 것 — 기록해 둔다)

**가설: 옛 지문 스크립트(난수 방식)가 고객에게 서빙되고 있다** → 🔴 **기각**

이것은 매우 그럴듯한 가설이었다. repo 에 **`device-fingerprint.js` 사본이 14개** 있고, 그중 **`src/HitPan.Web/wwwroot/js/` 것만 현행(308줄, `HFPv2-`)** 이며 나머지는 전부 **옛 `crypto.randomUUID()` 난수 방식(45~48줄)** 이다.
난수 방식이라면 **저장소가 갈릴 때마다 새 기기**가 되므로 증상과 맞아떨어진다.

**그러나 서빙 경로를 추적한 결과 기각된다:**

| 근거 | 내용 |
|---|---|
| 터널 종착지 | `test1.hitpan.kr` → API(5257) 직결. 고객은 **`{app}\api\wwwroot`** 의 화면을 받는다 (`build-installer-universal.ps1:130-134` 3중 실측 기록) |
| 그 자리를 채우는 것 | `build-installer-universal.ps1:139-140` 이 `api\wwwroot` 를 **지우고** `src/HitPan.Web` 의 **새 publish 결과로 덮는다** |
| 드리프트 게이트 | `:150-154` — `web/wwwroot` 와 `api/wwwroot` 의 SHA256 이 다르면 **빌드가 실패**한다 |
| 설치본이 담는 것 | `HitPan-Universal.iss:120-121` — `{#BundleDir}\api\*` 와 `\web\*` **뿐**. 14개 사본 중 **어느 것도 참조되지 않는다** |
| 소스트리 오염원 | `src/HitPan.API/wwwroot/` 는 **존재하지 않는다**. `.gitignore:83-87` 이 재오염원으로 차단해 둠 |

⚠️ **단 하나 남는 구멍**: `build-installer-universal.ps1:90,158-159` 의 **`-SkipErpBuild`** 플래그를 쓰면 publish·wipe·copy·드리프트 게이트를 **전부 건너뛴다.** 그 상태로 옛 bundle 이 남아 있으면 옛 스크립트가 실려 나갈 수 있다. **정상 빌드 경로에서는 일어나지 않는다.**
🔴 사장님 실측 환경이 **어떤 플래그로 빌드된 설치본인지**는 이 문서에서 확인하지 못했다 — **⚠️미확인 항목**이며, 실측 시 **화면에서 실제 `deviceFingerprint` 접두어를 보면 즉시 판정된다: `HFPv2-` 면 현행, UUID 모양이면 옛 스크립트다.** ②-1 의 첫 관찰 항목이 이것인 이유다.

### ③-6 후보 가설 정리 (🔴 **확정 아님** — 실측으로 가려야 할 것)

| # | 가설 | 코드 근거 | 상태 |
|---|---|---|---|
| H-1 | 실제로는 **새 창이 아니라 다른 브라우저**였다 (증상 2 와 같은 현상을 다르게 인지) | 증상 2 는 코드로 완전히 설명됨 | ⚠️ 실측 필요 (②-4 3-2) |
| H-2 | 다중 모니터에서 창이 **다른 모니터**에 떠 `screen.*`·`avail*` 이 달라졌다 | ③-2 | ⚠️ **캐시가 살아 있으면 성립 안 함**. 실측 3-5 |
| H-3 | **옛 난수 스크립트**가 실린 설치본이었다 (`-SkipErpBuild` 등) | ③-5 | ⚠️ 접두어 확인으로 즉시 판정 |
| H-4 | 사이트 데이터가 창 사이에 **격리**되는 브라우저 설정·확장프로그램·정책 | ③-3 예외 경로 | ⚠️ 실측 필요. **단 그래도 환경해시가 같아 슬롯은 안 늘어야 함** |
| H-5 | 메신저 팝업에서 토큰 물려받기가 실패해 재로그인이 일어났다 | ③-4 | ⚠️ **코드상 슬롯 증가로 이어지지 않음.** 실측 3-6 |
| H-6 | 실측 당시 **주소가 하나가 아니었다**(사장님 기억과 실제가 다름) | 7/2 에 origin 격리가 실증됨 | ⚠️ Application 탭의 **origin 목록**을 보면 즉시 판정 |

🔴 **위 6개 중 어느 것도 확정이 아니다.** 헌법 #32 — 짐작을 결론으로 쓰지 않는다.

### ③-7 이 미확인이 P1·P2 를 막는가

**막지 않는다.**
- 명세서 §6 이 이미 그렇게 설계돼 있다 — *"§4-3 으로 **견딤**(원인과 무관하게 장비넘버로 잡힘)"*.
- **P3 에서 조회 열쇠를 장비넘버로 바꾸면**, 지문이 무엇으로 흔들리든 같은 기기는 한 줄로 잡힌다.
- 🔴 다만 **원인 규명을 포기하지는 않는다.** 원인을 모른 채 구조를 바꾸면, 그 구조가 **왜** 통하는지도 모르는 채로 배포하게 된다. ②-4 대본을 반드시 돌린다.

### ④-A 계수 통합(P1 · G-7 · I-4)에서 깨질 위험이 있는 자리

| # | 깨지는 자리 | 왜 위험한가 | 어떻게 지키나 |
|---|---|---|---|
| **D-1** | 🔴 **QR 경로(복제 D `:597-603`)는 모바일만 센다** | 단일 메서드가 PC·모바일을 **둘 다** 돌려주게 만들고 QR 경로가 그대로 쓰면, **PC 한도까지 검사하게 되어 종전에 통과하던 QR 등록이 막힌다** | 단일 메서드는 **두 값을 계산해 돌려주되**, QR 호출부는 **모바일 값만 비교**한다. 호출부의 비교식을 그대로 둔다 |
| **D-2** | 🔴 **백오피스(복제 E `:98-101`)는 `device_type = @Type` 등호다** | `tablet` 이 **어느 칸에도 안 잡힌다**(ERP 는 mobile 칸에 합산). 백오피스를 ERP 식으로 바꾸면 **기존 tablet 행이 갑자기 모바일 칸을 먹어 한도를 넘길 수 있다** | 🔴 **백오피스는 별 시스템(별 DB·별 배포)이다.** ERP 단일 메서드를 **그쪽에서 부르게 만들지 않는다.** 작지서 P1 은 `:77-79` 의 `pc` → `mobile` 폴백 정렬만 지시한다. **계수 통합은 ERP 안에서만** |
| **D-3** | 🔴 **`is_main_pc` 제외 절을 "정리하다가" 넣지 마라** | 현행 5곳 전부 메인PC 를 **1대로 센다.** 사장님 확정(*"메인PC 포함"*)과 일치한다. `:165` **주석만 틀렸다.** 주석을 보고 코드를 맞추면 **요금정책이 샌다**(적게 세는 사고) | P1 은 **주석을 고친다.** SQL 에 `AND is_main_pc = 0` 을 **절대 넣지 않는다** |

| **D-5** | **갱신 경로(경우 2)는 한도를 안 본다 — 이것이 정상이다** | 단일화하며 "일관성" 을 이유로 갱신 경로에도 한도 검사를 넣으면, **쓰던 사람이 로그인에서 막힌다.** 8/10 에 두 번 무너진 계통(`:196-201` 주석이 명시) | 갱신 경로에 계수 호출을 **추가하지 않는다.** 리팩터링이 아니라 **동작 변경**이다 |
| **D-6** | **메인PC 자동등록은 한도를 안 본다 — 이것도 정상이다** | `MainPcRegistrationService.cs:192-196` 이 의도를 명시. 여기에 한도를 걸면 **한도가 찬 고객사에서 메인PC 표식이 안 붙어 CS 가 메인PC 를 못 찾는다** | 이 서비스는 P1 범위 **밖**. 건드리지 않는다 |
| **D-7** | **추가슬롯 산식도 4곳 복제**(`:93-94`·`:242-243`·`:407-408`·`:595`) | 계수만 합치고 **한도 계산을 안 합치면** 여전히 4곳이 갈린다. G-7 이 계수만 보면 통과해 버린다 | **한도 계산도 같은 메서드로** 모은다. `:595`(모바일만 더함)를 놓치지 마라 |
| **D-8** | 🔴 **P0 스냅샷과 입력→출력을 대조하라** | 작지서 §6: *"다르면 즉시 중단"* | ①-2 추적표의 7개 경우를 **그대로 재현**해 슬롯 증감이 같은지 확인한다 |

### ④-D 게이트를 만들 때 (작지서 §5 — 반증까지)

- 🔴 **시험이 0건인 자리다**(명세서 §2-6). 새로 만드는 게이트가 **처음 생기는 안전망**이다.

- I-6 반증: **모르는 종류를 `pc` 로 바꾸면 FAIL**.
- ⚠️ **테스트가 슬롯을 먹지 않게** 하라 — 단위시험은 실제 DB 를 쓰지 않는 쪽이 안전하다.
