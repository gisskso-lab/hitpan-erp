**스키마**: `rc_safe_s1` ← 출하 DDL `installer/hitpan_db_clean.sql` 적재(테이블 155) · `--default-character-set=utf8mb4`.

| 단계 (REPEATABLE READ · 실제 테이블) | 결과 |
|---|---|
| `SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ` → `@@tx_isolation` = `REPEATABLE-READ` | ✅ |
| `BEGIN` | ✅ |

| `INSERT INTO collections …` | ✅ 통과 |
| `COMMIT` | ✅ 통과 |

**대조군(같은 인스턴스 · 같은 테이블 · 격리수준만 RC)** — 실패해야 판정이 성립한다:

```
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED; BEGIN;
SELECT balance_id FROM partner_legacy_balances WHERE tenant_id='t1' AND partner_id='p1' FOR UPDATE;
→ ERROR 1665 (HY000) at line 3: Cannot execute statement: impossible to write to binary log
  since BINLOG_FORMAT = STATEMENT and at least one table uses a storage engine limited to
  row-based logging. InnoDB is limited to row-logging when transaction isolation level is
  READ COMMITTED or READ UNCOMMITTED.
```

→ 변수는 **격리수준**이다(선행 F5 와 같은 결론, 이번엔 우리 실제 테이블로). 설계 §10-1 미실측 **해소**.
→ 이 대조군이 곧 무력화 시험 **M1**(§4) 의 실측 근거다 — 모드 분기를 빼면(=RC 고정) 이 서버에서 등록의 첫 문장이 1665 로 거절된다.

## §3-2 🔴 **설계 §10-2 실측 결과 — 절반은 성립, 절반은 성립하지 않는다 (PM·설계 판단 필요)**

설계 §10-2 「파생표 `LOCK IN SHARE MODE` 가 STATEMENT 서버에서 최신 커밋을 읽는가」를 같은 33406 인스턴스에서 **두 연결**로 쟀다.
방법: A 가 RR 로 열고 **일반 읽기로 스냅숏을 먼저 연다**(G8-u 가 재는 이슈44 경우 B) → 그 사이 B 가 INSERT·커밋 → A 가 같은 값을 ① 일반 읽기 ② `LOCK IN SHARE MODE` 로 읽는다. 타임스탬프로 B 의 커밋이 A 의 창 **안**임을 확인했다(앞선 2회는 B 가 창 밖이라 무효 · 폐기).

| 대상 | 문장 모양 | 일반 읽기 | `LOCK IN SHARE MODE` | 판정 |
|---|---|---|---|---|
| **D1 — 전표 남은금액 SUM** (설계 §4-4) | `SELECT SUM(amount) FROM collections WHERE …` (실테이블 직접) | `0.00` (옛 스냅숏) | **`11000.00`** (최신 커밋) | 🟢 **설계대로 작동** |
| **R 재계산** (설계 §4-2) | `SELECT … FROM (공용 식) x WHERE …` (**파생표**) | `90000.00` | **`90000.00`** (그대로 옛값) | 🔴 **작동 안 함** |

- R 쪽 기대값: 커밋된 상태의 M = 30,000 · L0 = 100,000 → **R = 70,000** 이어야 한다. 두 읽기 모두 **90,000**(옛 M=10,000)을 돌려줬다. 트랜잭션 밖 확인: `matched_now = 30000.00` · `balance_amount = 100000.00`.
- 원인(관찰): 꼬리의 잠금절이 **파생표 바깥**에 붙으면 안쪽 기본 테이블 행에 닿지 않는다 — 파생표가 트랜잭션 스냅숏으로 먼저 만들어진다. D1 처럼 **실테이블을 직접** 읽는 문장에서는 최신 커밋을 읽는다.
- 뜻: 설계 §4-2 의 처방(공용 식 본문 무수정 + 꼬리 한 줄)만으로는 **RR 경로의 G8-u 동등(G-RC3)이 통과하지 못한다.** 선행검증 F7 이 적은 「RR 로 바꾸면 최종 R 음수」와 같은 자리다.
- ⚠️ 다만 **모든 RR 경로가 틀린다는 뜻은 아니다**: 트랜잭션 안에서 앞선 일반 읽기가 **없으면** 읽기 뷰가 `FOR UPDATE` 뒤에 열려 R 이 최신일 수 있다. 지금 서비스의 이월잔액 경로는 트랜잭션 첫 문장이 `FOR UPDATE` 다. **이 갈림은 안 쟀다 — G-RC3·G-RC4(S2)가 판정한다.**
- 🔴 **나는 여기서 멈췄다.** 처방을 바꾸는 것(예: 잠금절을 파생표 **안쪽** 하위 질의로 내리기 · 재계산 전에 기본 테이블 행을 먼저 잠그기)은 **설계 §4-2 의 구조 변경**이라 구현 담당이 독단으로 못 한다(#33 · 작지 §4-3 「공용 식 본문 수정 금지」와도 걸린다). **PM·설계팀장 판단 안건**으로 올린다.
- 현재 코드 상태: 설계 §4-2 그대로(꼬리절) 구현돼 있다. RC 경로·D1 봉합은 영향 없다.

### §8-2-1 RR 경로가 도는 모양 (읽는 사람용 · 한 트랜잭션)

```
BEGIN (REPEATABLE READ)
 ① SELECT balance_id, base_date, balance_amount … FOR UPDATE        ← ㉮ 최신 L0 · 거래처 직렬화
 ② SELECT COALESCE(SUM(...),0) … LOCK IN SHARE MODE   (미수 2 / 미지급 3 문장)   ← ㉰ 최신 M
 ③ R = GREATEST(L0,0) − ΣM   (C# decimal · 클램프 없음)              ← ㉯
```
RC 경로는 ①만 같고 ②③ 대신 **파생표 한 문장** — 3판 그대로다(설계 §11-5).
