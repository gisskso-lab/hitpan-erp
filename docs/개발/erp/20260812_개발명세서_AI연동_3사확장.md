### 2-3. 🔴 Tool Use 는 "되는 척" 하지 않는다

신규 2사의 `CompleteWithToolsAsync` 는 **`ToolUseResponse.Fail()` 을 반환**한다.

- 왜: `ToolUseResponse.RawAssistantContent` 가 클로드 고유 content 블록 원본을 그대로 돌려주는 계약이고,
  엔진(`AiAgentService`)이 그 포맷에 직접 의존한다. 다른 사 응답을 그 포맷으로 흉내내면
  **엔진 동작(=챗봇)을 건드리게 되어** 사장님 *"챗봇은 나중에 할거야"* 범위를 벗어난다.
- 🔴 그래서 **성공을 가장하지 않고 실패를 정직하게** 반환한다.
  같은 날 본사 알림메일이 *안 보내면서 성공(true)* 을 반환하는 것을 P0 로 적발했다(작업지시서 부록 A).
  **같은 함정을 내가 만들지 않는다.** 호출부는 Fail 을 받으면 기존 KB/도우미 폴백으로 정상 처리한다.
- 시험 `신규_공급자는_되는척하지_않는다` 가 이걸 소스 수준에서 고정한다.

### 2-6. 🔴 [연결 확인] 실검증 — 이번 봉합의 핵심

지금은 `CheckConnectionAsync` 가:
1. 저장된 키를 복호화 → 없으면 정직하게 "키가 없다"
2. `_providerFactory.Resolve(provider)` → **실제 짧은 호출 1회**
3. 실패 시 `*_key_status='invalid'` 기록 + **실패 사유를 그대로 안내**
4. 성공 시에만 `*_key_verified_at` 기록

화면도 **"저장됨"과 "실제로 연결해 봤음"을 구분해 표시**한다
(확인 전에는 *"아직 연결을 확인하지 않았습니다"*).

### 🔴 게이트를 일부러 깨뜨려 봤다 (오늘 §5-① 함정)

### P0-1 — 공급자를 골라도 대화는 계속 클로드로 나갔다 (봉합 완료)

**무엇이 잘못됐나**: `AiProviderFactory` 를 만들어 놓고 **실제 대화 경로에 연결하지 않았다.**
팩토리는 `CheckConnectionAsync`(연결 확인) **한 곳에서만** 쓰였고,
정작 대화 경로(`TryProviderAnswerAsync`)는 `anthropic_*` 컬럼을 고정으로 읽고 클로드를 불렀다.
`GetActiveProviderAsync` 는 만들어 놓고 **아무도 호출하지 않는 죽은 코드**였다.

**고객에게 무슨 일이 났을까**: 챗GPT 키 저장 → [연결 확인] 성공 → 챗GPT 선택 →
"챗GPT 를 사용하도록 변경했습니다" 안내. **그런데 대화는 클로드로 나간다.**
클로드 키가 없으면 도우미가 조용히 죽는다. **화면은 전부 정상으로 보인다.**

> 🔴 이 명세서 §2-3 에 *"알림메일이 안 보내면서 성공을 반환하는 P0 를 적발했다.
> 같은 함정을 내가 만들지 않는다"* 라고 써 놓고 **정확히 같은 함정을 한 층 위에서 만들었다.**
> Tool Use 는 정직하게 `Fail()` 을 반환하게 했는데, 정작 그 위의 공급자 선택이 성공을 가장했다.

**봉합**: `TryProviderAnswerAsync` 가 `GetActiveProviderAsync` → 해당 공급자 키 컬럼 →
`_providerFactory.Resolve(provider)` 를 타도록 배선했다.
`TryRunAgentAsync`(AI 직원)는 **클로드 고정을 유지**하되 — 신규 2사가 Tool Use 를 못 하므로
넘기면 AI 직원이 죽는다 — **왜 고정인지를 코드 주석에 명시**했다(조용한 고정은 오해를 부른다).

### P1-1 — 시험 24건이 이 P0 를 하나도 못 잡았다 (봉합 완료)

기존 게이트는 전부 ①순수함수 ②파일 문자열 검사 ③소스 정규식이라
**서비스를 실행하는 시험이 0건**이었다. 팩토리를 아무 데서도 안 쓰게 해도 267건이 통과했다.
*"게이트를 깨뜨려 봤다"* 던 것도 순수함수를 깨뜨려 순수함수 시험이 걸린 것이라,
**배선 결함을 잡는 능력은 증명하지 못했다.**

**봉합**: `AiProviderRoutingTests` **17건 신설**. 팩토리를 실제로 돌려 어느 어댑터가 나오는지 확인하고,
대화 경로가 팩토리를 타는지 소스로 검사한다.
**P0-1 을 인위적으로 되살려 확인** → `일반대화_경로가_선택된_공급자를_탄다` 가 즉시 실패.

> 🔴 **1차 봉합은 절반이었다** — 재검증에서 검증팀이 **우회에 성공**했다.
> 1차 명세서의 *"이제 진짜로 잡는다"* 는 **과장이었다.**
>
> 시험 6·8번이 소스 **문자열 존재**만 검사해서, 아래 한 줄이면 통과했다:
> ```csharp
> adapter = _providerFactory.Resolve("anthropic");   // ← 이 한 줄로 P0-1 완전 재발
> ```
> 검사 대상 문자열이 그대로 남아 Assert 3개를 전부 만족 →
> **P0-1 이 되살아난 상태로 284건 전부 통과했다.**
>
> ✅ **2차 봉합 완료 (같은 날)** — 시험 **2건 추가**해 구멍을 막았다:
> - `대화경로가_공급자를_문자열로_박아넣지_않는다` — `Resolve("리터럴")` 호출 자체를 **정규식으로 금지**.
>   공급자는 항상 **읽어온 값**이어야 한다.
> - `대화경로는_어댑터를_한_번만_정한다` — `adapter =` **대입 횟수를 1회로 고정**.
>   리터럴이 아니어도 뒤에서 덮어쓰는 수법을 막는다.
>
> 🔴 **검증팀이 쓴 우회를 그대로 재현해 확인** → **2건 모두 즉시 실패**. 원복 후 286건 통과.
>
> ⚠️ **그래도 이건 여전히 소스 검사다.** 근본은 `ChatbotService` 를 가짜 팩토리와 함께 **실행**해
> *"openai 를 고르면 openai 어댑터가 실제로 불렸다"* 를 **관찰**하는 것이다.
> `IDbConnection` 을 직접 받는 구조라 실 DB 없이는 못 돌려 이번엔 못 했다 —
> **다음 차수 과제로 남긴다.** 지금 것은 알려진 우회 2종을 막을 뿐이다.

### P1-2 — 일시 장애를 키 무효로 오판해 멀쩡한 키를 죽였다 (봉합 완료)

연결 확인 실패 시 원인을 가리지 않고 `status='invalid'` 를 적었다.
인터넷이 잠깐 끊긴 사이 [연결 확인]을 누르면 **멀쩡한 키가 죽고 재입력해야 살아났다.**

**봉합**: `ChatProviderResult.StatusCode` + `IsAuthFailure` 추가.
**키가 실제로 거부된 경우(400/401/403)에만** `invalid` 를 적고,
429·5xx·타임아웃은 저장된 키를 **건드리지 않는다**(화면도 "저장된 키는 그대로 있습니다" 라고 안내).
⚠️ 400 을 포함한 이유 — **제미나이는 틀린 키에 400 을 준다**(실측). 401/403 만 보면 제미나이를 놓친다.

### 검증팀이 결함 없음으로 확인한 것

기존 고객 무회귀(#1·#37) / [연결 확인] 실호출 / 키 유출 0(제미나이 URL 쿼리 미사용 포함) /
SQL 인젝션 2중 화이트리스트 / 테넌트 격리(#2) / DTO 호환 / 빈 catch 0(#15)

### ⚠️ 알고도 수용한 트레이드오프 (P3)

`IsAuthFailure` 에 **400 을 포함**한 것 — 제미나이가 틀린 키에 400 을 주기 때문인데,
**정상 키인데 400 이 나는 경우**(모델명 오설정 등)에는 멀쩡한 키가 `invalid` 로 적힌다.

검증팀 판정 = **수용 가능**. 근거:
- 연결 확인은 `history: null` + 고정 문자열이라 요청 형식 오류가 날 여지가 거의 없다
- 모델명은 `appsettings`(관리자 설정)이지 고객 입력이 아니다
- 그런 일이 나도 **키 재입력으로 복구**되고, 화면에 원인이 표시된다

> 400 을 빼면 **제미나이의 틀린 키를 "일시 장애" 로 오판**해 고객이 영영 원인을 못 찾는다.
> 두 위험을 견줘 이쪽을 택했다. 판단 근거를 남겨 다음 사람이 다시 저울질할 수 있게 한다.
