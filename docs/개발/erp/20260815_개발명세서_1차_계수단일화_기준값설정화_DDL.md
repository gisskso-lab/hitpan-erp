## ① 30초 요약

**무엇을 했나** — 요금을 계산하는 자리가 **여덟 곳으로 갈려 있던 것을 두 곳으로 모았고**, 요금 숫자를 **코드에서 DB 설정으로 꺼냈고**, 장비넘버를 담을 **DDL 칸을 만들었다.**

**왜** — 2차에서 열쇠(기기를 알아보는 기준)를 바꾸기 전에 바닥을 고르는 일이다. 계수가 갈리고 숫자가 코드에 있는 채로 열쇠를 바꾸면, 요금이 틀렸을 때 **어디가 틀렸는지 못 찾는다.**

**무엇이 실제로 고쳐졌나 (고객이 겪던 것)**
| 증상 | 지금까지 | 고침 |
|---|---|---|
| 최상위 고객이 베이직 한도를 받고 있었다 | `enterprise` 갈래가 코드에 없어 `_ => (5,3)` 으로 떨어짐 | `enterprise` (100,80) 정정 |
| 태블릿이 **공짜로** 쓰였다 | 백오피스가 등호 비교라 어느 칸에도 안 잡힘 | 휴대기기 칸에 합산 |
| 종류를 안 보내면 **비싼 칸**을 먹었다 | `?? "pc"` 폴백 (실측하니 **4곳**) | 전부 제거 → 싼 칸(mobile) |
| 추가슬롯이 1+2 였다 | `mobileLimit += extra * 2` | **1+1** (사장님 확정) |

**바뀌지 않은 것** — ERP 의 계수 결과. 같은 데이터에 같은 값이 나온다(⑤ 대조표).

## ③ 판단이 갈렸던 자리와 그 근거

### 갈림 1 — 🔴 설정을 어디에 둘 것인가 (헌법 #21)

`appsettings.json` 은 **금지**다. 그런데 `DeviceApproval:Enabled` 가 **이미 appsettings 를 읽고 있어** 전례로 삼고 싶어지는 자리다.

**전례로 삼지 않았다.** P0 실측 D-13 이 그 유혹을 미리 경고했고, 성격도 다르다 — 그것은 켜고 끄는 스위치이고 이것은 **회사마다 다른 요금 한도**다. 파일 설정으로는 ①테넌트별로 다른 값 ②대표계정이 화면에서 고치기 ③수정 이력을 **셋 다 못 담는다.**

⇒ **DB 표**로 갔다. 근거는 `DB-96`(노무 기준값)의 선례다: *"법정값은 전부 설정 테이블. 하드코딩 금지, **상수로 빼는 것도 금지**(재배포가 필요하면 실패다)"*

### 갈림 2 — 백오피스를 ERP 단일 메서드로 부를 것인가

**부르지 않았다.** 백오피스는 **별 시스템·별 DB·별 배포**다. ERP 서비스를 끌어다 쓰면 본사와 고객 PC 가 코드로 묶여 **헌법 #30**(본사 의존 0)·**#35**(3시스템 분리) 를 어긴다.
⇒ **같은 규칙을 쓰되 코드는 각자 갖는다.** 고친 것은 규칙의 어긋남(`tablet` 누락) 하나뿐이다. (P0 실측 D-2 가 지시한 방향)

### 갈림 3 — 🔴 G-8 을 어떻게 만들 것인가 (가짜 게이트 회피)

작업지시서 §5 가 못 박았다 — *"코드에 리터럴이 없는지"* 는 **상수를 옮기면 통과하는 가짜**다. 8/15 메신저 사고(`ChatWindowGuardTests` 가 글자만 보고 통과)를 근거로 든 지적이다.

**문제**: Dapper 확장 메서드는 `static` 이라 Moq 로 흉내낼 수 없다. DB 를 붙이면 시험이 **슬롯을 먹는다**(P0 ④-D 가 금지).

**해법**: 판정의 순수 부분(`설정값 + 요금제 + 추가슬롯 → 실제 한도`)을 `ResolveLimits` 로 떼어 `internal` 로 열고, 시험이 **직접 부른다**. `InternalsVisibleTo` 는 이 repo 에 이미 선례가 있다(`HitPan.Watchdog`).
⇒ G-8 은 **설정 사전을 바꿔 넣고 나오는 숫자가 달라지는지**를 본다. 반증으로 검증했다(④-나).

### 갈림 4 — `premium` 을 지울 것인가

**안 지웠다.** `enterprise` 가 옳지만 옛 데이터에 `premium` 이 남아 있을 수 있다 — 랜딩 `PaymentPage.razor:124` 가 *"옛 키 호환: premium → enterprise"* 라고 적고 있는 것이 **실재했다는 증거**다. 지우면 그 고객이 조용히 basic 으로 떨어진다(D-16).
⇒ **두 값을 같은 한도로** 둔다. 어느 쪽이 와도 안 깨진다.

### 갈림 5 — `hardware_id` 를 NOT NULL 로 할 것인가

**NULL 허용으로 갔다.** 이것이 이 DDL 설계의 핵심이다.
MariaDB UNIQUE 는 **NULL 을 서로 다른 값으로 본다** ⇒ 장비넘버를 아직 못 받은 **기존 고객 기기가 몇 대든 공존한다.**
`NOT NULL DEFAULT ''` 로 했다면 빈 문자열이 서로 충돌해 **기존 고객의 두 번째 기기부터 INSERT 가 죽는다.**
실측으로 확인했다 — NULL 2행 공존 OK / 같은 회사 안 같은 값은 `1062` 로 차단 OK / **한 줄이 지문과 장비넘버를 동시에 보유 OK**.

| 백오피스 "싼 칸" 정렬 | **2차.** 모바일 한도(3) < PC 한도(5)라 **차단이 빨라진다**(PI-12) |
| P3 열쇠 교체 · P4 메인PC 합류 · P5 중간 화면 | 2차(작4) |
| 401 제거 · 승인 알림 · 수동 3단 | 2차 |
| 지문 산식 개선 | 지문은 열쇠에서 내린다 |
| 기본 제공 슬롯 **숫자** 확정 | 구조만. 숫자는 사장님 |
| 워치독·업데이트·운영 demo | 무접촉 |

### 만들었으나 아직 아무도 안 읽는 것

**`hardware_id` 컬럼** — 칸만 만들고 **읽고 쓰는 코드는 2차(P3)** 다.
*"DB 는 미리 다, 코드는 필요할 때만"*(헌법 #9). 지금 전 행이 NULL 이고 아무도 안 읽으므로 **무회귀**다.

### 🔴 다음 차수가 반드시 알아야 할 것

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **`FallbackLimits` 는 설정의 대체물이 아니다** | 마이그 전 DB 에서 로그인이 안 죽게 하는 **안전망**일 뿐이다. 이 숫자를 고쳐 요금제를 바꾸려 하면 안 된다 — 설정표(DB-104)를 고쳐야 한다 |
| 2 | **DB-104 시드는 회사가 있어야 들어간다** | `local_subscription` 기준 CROSS JOIN 이라 **신규 설치 시점엔 0행**이다. 그때는 `FallbackLimits` 로 돈다(한도가 사라지지 않는다). ⚠️ **회사 생성 경로에 시드를 붙이는 일이 2차 과제**다 |
| 3 | **추가슬롯 1+2 → 1+1 은 실질 축소다** | 모바일 한도가 줄어든다. 실사용 고객 0 이라 안전하나, 추가슬롯을 산 테스트 환경이 있으면 **새로 늘릴 때** 막힐 수 있다. 쓰던 기기는 갱신 경로가 한도를 안 봐서 안 막힌다 |
| 4 | **백오피스 `pricing_plans` 와 아직 두 진실원이다** | ERP 는 로컬 설정표를, 백오피스는 자기 표를 본다. 🔴 ERP 가 본사를 **실시간 조회하게 만들면 헌법 #30 위반**이다. **내려받아 저장**하는 동기화가 2차 과제(D-15) |
| 5 | **P0 미확인 U-1 은 그대로다** | "새 창마다 슬롯" 재현·원인은 아직 미확인. 1차는 이것을 **막지 않는다**(P0 ③-7). P3 열쇠 교체가 원인과 무관하게 견디게 만든다 |

### ⚠️ 이 명세서가 스스로 밝히는 한계

- 이 작업의 검증은 **빌드·단위시험·DB 실측**까지다. **백지 환경(Sandbox) 종단 실측은 하지 않았다.**
  사장님 못박음 — *"개발환경 PC 정상작동은 큰 의미 없다"*. ⇒ **[4] 검증 단계에서 종단 확인이 필요하다.**
- 특히 **DB-104 시드가 실제 고객 DB 에서 채워지는지**는 회사가 있는 DB 에서 봐야 한다(위 ⑦-2).
