## §2 A — 표 존재 가드 (증상 ①②③)

### A-1 백오피스 `CsAdminController`
- `HasOutboundSchemaAsync(db)` 신설 — `information_schema.tables` 로 `bo_cs_outbound`·`bo_cs_retention_policy` 실재를 묻는다.
  **기존 `HasPurgeColumnsAsync`(칸 가드)와 같은 모양** — 캐시는 DB 이름별.
- 가드를 **입구 7곳**에 세웠다: `CreateOutbound` · `ListOutbound` · `CancelOutbound` · `GetRetention` · `SetRetention` · `PurgeCandidates` · `PurgeOutbound`.
- 표가 없을 때의 답:
  - 읽기(`GetRetention`·`ListOutbound`·`PurgeCandidates`) → **200 + `schemaPending: true`**. 화면이 선다.
  - 쓰기(`CreateOutbound`·`SetRetention`·취소·폐기) → **503 + 사람이 읽을 문장**.
    🔴 500 이 아닌 이유: 500 은 빈 body 라 화면이 해석하지 못한다 — 사장님 증상 ② 가 정확히 그 모양이었다.

### A-2 백오피스 `CsInboundController.PullReplies` — 🔴 이게 증상 ③ 의 자리
종전: `bo_cs_outbound` 를 **조건 없이** SELECT ⇒ 표가 없으면 **Pull 응답 전체가 500** ⇒
같은 응답에 실린 `replies`(본사 답변)도 **함께 못 내려갔다.**
사장님 화면엔 「답이 없다」로 보였지만 **답은 본사에 있었고 담은 응답이 죽은 것**이었다.

고친 뒤: 표가 없으면 선발신·폐기 블록만 건너뛰고 **답은 그대로 내려간다** (#20).
표가 있으면 종전과 한 글자도 다르지 않다.

> 🔴 가드는 「안 터지게」 까지다. **보관기한·선발신 기능 자체는 45번이 적용돼야 돈다.**
> 둘을 같은 것으로 적지 않는다.

## §3 B — 본사 상태 하행 (증상 ④)

| 자리 | 바뀐 것 |
|---|---|
| 마이그 | `DB-145_cs_requests_hq_status.sql` — `hq_status` varchar(10) NULL · `hq_status_at` datetime(6) NULL (추가형) |
| 출하 DDL | `installer/hitpan_db_clean.sql` `cs_requests` 에 같은 2칸 (#36 — 같은 커밋) |
| 백오피스 | `PullReplies` 응답에 `statuses[]` 추가 — 열쇠·상태·시각 **셋뿐**(#18·#22) · 기존 3키는 무변경(#1) |
| ERP 워커 | `StatusDto` · `ApplyHqStatusesAsync` — 답과 **독립** 처리(답 0건이어도 상태는 움직인다) |
| ERP API | `CsRequestController.List` 가 `hqStatus`·`hqStatusAt` 을 조건부로 싣는다 (`HasHqStatusColumnsAsync`) |
| ERP 화면 | `CsRequestPage.razor` — 쪽지 상태 칩 **옆에** 「본사 처리중/완료」 칩. 완료만 초록 |

### 설계 판단 3건
1. **「접수」는 안 내려보낸다.** 내려보내면 모든 쪽지에 「본사 접수」가 붙어 본사가 실제로 손댄 건과 구분이 사라진다 ⇒ `hq_status = NULL` 의 뜻을 「본사 미착수」로 지킨다.
2. **뒤로 안 간다.** 더 이른 `changedAt` 은 무시한다 — 응답 순서가 어긋나도 「완료」가 「처리중」으로 되돌아 보이지 않는다.
3. **`status` 를 안 덮는다.** 쪽지 자신의 진행과 본사 진행은 다른 축이다(사장님 결재).
