## §1. 🔴 착수 전 실측 — 진짜 원인이 갈렸다

작지서를 쓸 때 세운 가설과 **실측이 다르다.** 실측을 먼저 적는다.

### 1-1. 지문은 **브라우저가 바뀌면 달라진다**
`src/HitPan.Web/wwwroot/js/device-fingerprint.js` 의 `_envSeed()` 가 씨앗에
**`navigator.userAgent` 를 포함**한다(`:48`).

```js
var ua = (nav.userAgent || '').replace(/[0-9]+\.[0-9.]+/g, '');
parts.push(ua);
```

버전 숫자는 지웠지만 **브라우저 계열은 남는다.**
⇒ 같은 PC 라도 **Edge 로 들어가면 A, Chrome 으로 들어가면 B.**

7/2 봉합은 origin 격리(`localhost` ↔ `127.0.0.1`)를 잡았고 그건 유효하다.
**브라우저 차이는 그때 못 잡았고, 그래서 한 달 반 만에 재발했다.**

### 1-2. 🔴 조회가 **지문으로만** 한다 — `hardware_id` 는 아무도 안 쓴다
`TenantDeviceService.RegisterOrRefreshAsync:181`

```sql
SELECT device_id, status, is_main_pc FROM tenant_devices
WHERE tenant_id = @TenantId AND fingerprint = @Fp    -- ← 지문으로만
```

그런데 DDL 에는 이미 이렇게 적혀 있다(DB-103, 어제 1차):

| 컬럼 | 주석 |
|---|---|
| `fingerprint` | **[옛 기기 호환 전용]** … 새 기기는 `hardware_id` 로 잡는다 (DB-103 **격하**) |
| `hardware_id` | 장비넘버. **서버가 읽는 변하지 않는 값** |

**실측: `hardware_id` 를 읽거나 쓰는 코드가 ERP 본체에 0곳이다.**
(`grep` 결과 `HitPan.Contracts` 의 프로비저닝 계약 2곳뿐 — 다른 축이다.)

> 🔴 **어제 1차는 컬럼만 깔고 배선을 안 했다.**
> 그래서 "격하됐다"고 적힌 지문이 여전히 유일한 열쇠로 돌고 있었다.

### 1-3. 세 증상의 뿌리가 **하나**다

| 증상 | 뿌리 |
|---|---|
| ① 메인PC 슬롯 2개 | 브라우저 바뀌어 지문 흔들림 → 새 행 |
| ② QR 모바일 "등록 안 됨" | **등록은 됐다.** 폰 지문 흔들려 **중복 등록**된 것 (사장님 실측: *"등록문구 뜸. 한 기기에서 슬롯 중복"*) |
| ③ 중간 화면 없음 | 애초에 미착수 (1차 범위 밖) |

⇒ **①②는 같은 결함이다.** ③을 만들면서 ①②를 함께 닫는다.

### 1-4. 승인 API 는 **이미 있다**
`DeviceController` 실측 — `approve/{id}`(`:117`) · `reject/{id}`(`:156`) 존재.
**새로 만들 게 아니라 화면과 이어 붙이는 일이다.**

## §2. 설계 — 두 겹으로 막는다

작지서는 "승인제만 켜면 된다"로 썼다. 실측 결과 **그것만으로는 부족하다.**

### 왜 승인제만으로 부족한가
승인제를 켜면 새 기기가 `pending` 이 되어 슬롯은 안 먹는다. **요금 유출은 멈춘다.**
그러나 **지문이 흔들릴 때마다 대표에게 승인 요청이 뜬다.**
같은 PC 로 브라우저만 바꿔도 *"등록을 요청합니다"* 가 뜬다 ⇒ 대표가 시달린다.
**증상은 요금에서 알림으로 옮겨갈 뿐이다.**

### 그래서 두 겹
| 겹 | 무엇 | 효과 |
|---|---|---|
| **1겹 — 알아보기** | `hardware_id` 를 **1순위 열쇠**로 쓴다 (지문은 폴백) | 브라우저 바뀌어도 **같은 기기로 알아본다** ⇒ 승인 요청 자체가 안 뜬다 |
| **2겹 — 사람** | 그래도 못 알아보면 `pending` → **대표 승인** | 알아보기가 틀려도 **슬롯이 자동으로 안 샌다** |

> 🔴 이것이 사장님 오더의 정확한 구현이다 — *"자동화보단 물리적으로 수동으로."*
> 알아맞히기를 **더 정교하게** 하는 게 아니라(7/2 가 그 길이었고 재발했다),
> **틀려도 안전하게** 만든다.

### 🔴 1겹이 없으면 안 되는 이유 (반드시 읽을 것)
1겹 없이 2겹만 넣으면 **대표가 승인 요청 폭탄을 맞는다.**
그러면 대표는 **아무거나 Y 를 누르게 되고**, 그 순간 2겹도 무력해진다.
**사람이 판단할 수 있으려면 요청이 드물어야 한다.**

## §8. 🔴 착수 후 발견한 P0 — 승인제를 켜면 로그인이 막혔다

작업지시서에 없던 건이다. **R-1 만 했으면 사장님이 로그인조차 못 하실 뻔했다.**

### 무엇이 났나
`TenantDeviceService` 는 승인제가 켜지면 `allowed=false` 를 돌려주면서
주석에 *"⚠️ 단 이것은 **로그인 거부가 아니다**"* 라고 적어 뒀다.

그런데 `AuthController:113` 은 **`allowed=false` 를 전부 401 로** 바꿨다.

```csharp
if (!allowed) return Unauthorized(new { message = reason });   // ← 종전
```

⇒ **두 파일의 약속이 갈려 있었다.** 한쪽은 "거부가 아니다", 다른 쪽은 "전부 거부".

### 왜 P0 인가
사장님 결재(20260815 §3)와 정면으로 어긋난다 —
> *"한도 초과. **401 을 내지 않는다.** 로그인은 통과, 중간 화면에서 제어"*

로그인이 막히면 사장님이 설계하신 **[디바이스 인증] 관문에 도달조차 못 한다.**
화면을 아무리 잘 만들어도 **아무도 그 화면을 볼 수 없다.**

### 고침
승인 대기(`deviceId` 가 발급된 경우)는 **통과시키고 상태만 실어 보낸다.**
⚠️ `deviceId` 가 null 이면 등록 자체가 안 된 것(폐기된 기기) → **종전대로 401.**
이 갈래를 없애면 폐기한 기기가 다시 들어온다. 게이트 **G-24-b** 로 지킨다.

## §9. 🔴 게이트 반증 — 봉합을 빼고 FAIL 을 눈으로 확인했다

> 게이트를 짜자마자 봉합을 빼서 FAIL 을 봤다. **안 뜨면 그 게이트는 없는 것이다.**
> 어제(1차)까지 가짜 게이트가 **다섯 번** 나왔다.

| 게이트 | 무엇을 뺐나 | 결과 |
|---|---|---|
| **G-24** | `deviceAwaitingApproval` 갈래를 지우고 `if (!allowed)` 로 되돌림 | ✅ **FAIL 확인** |
| **G-25** | 장비넘버 조회 SQL 을 지문 조회로 되돌림 | ✅ **FAIL 확인** (G-25·G-25c 둘 다) |
| **G-27** | QR 의 `status` 를 `"approved"` 고정으로 되돌림 | ✅ **FAIL 확인** |
| **G-28c** | `AuthService` 가 장비넘버를 안 보내게 (`DeviceId = null`) | ✅ **FAIL 확인** |

⇒ **가짜 게이트 0건.**

### 초록불이 어디서 오는가 — 이번엔 어떻게 피했나
어제 G-21 은 `UNIQUE` 제약 때문에 **코드 가드를 둘 다 빼도 초록불**이었다(DB 를 시험하고 있었다).
이번 게이트는 전부 **DB 없이** 도는 것만 본다:
- 확인번호 → **실제 함수를 불러 값으로** 대조 (G-26 계열)
- 조회 순서·스위치 분기 → **주석을 걷어낸 실제 코드**의 SQL 모양·식 모양

⚠️ 소스를 읽는 게이트는 `CodeOnly()` 로 **주석을 전부 제거한 뒤** 찾는다 —
주석에 적힌 설명 문장이 게이트를 속이지 않게.

### ⚠️ 반증 방법 — `git checkout` 을 쓰지 않았다
1차에서 `git checkout` 으로 **미커밋 380줄이 날아간 사고**가 있었다.
⇒ 반증 전 **사본을 떠 두고**(scratchpad) 편집한 뒤 사본으로 되돌렸다.

## §10. ⏸ R-6 — 사장님 결재 대기 (아직 안 함)

### 왜 남겼나
스위치를 켜도 **이미 `approved` 인 중복 행은 안 줄어든다.** 새로 먹는 것만 막힌다.
사장님 `test1` 환경에 메인PC 가 2줄로 잡혀 있는 것이 그대로 남아 있다.

### 왜 지금 안 하나
1. 어떤 행이 몇 개인지 **실측을 안 했다** — 추측으로 지우면 **쓰던 기기가 죽는다**

   (`RevokeAsync` 가 메인PC 폐기를 막는 이유가 그것이다)

### 제안 방법 (결재받으면)
- 지우지 않고 **`revoked` 로 표시** — 되돌릴 수 있다
- 남길 것 = `is_main_pc = 1` 인 행 **하나**
- 사장님 화면에서 **[해제] 버튼으로** 하는 것이 가장 안전하다 (SQL 없이, 이미 있는 기능)

## §11. 이 차수가 사장님 3증상을 어떻게 닫나

| 사장님 실측 증상 | 무엇이 닫나 |
|---|---|
| ① 메인PC 가 슬롯 2개 | **R-2a** — 장비넘버로 알아보니 브라우저가 바뀌어도 한 줄. 못 알아봐도 **R-1** 이 `pending`(슬롯 0) 으로 잡아둔다 |
| ② QR 모바일 중복 | 같은 뿌리 — **R-2a** + **R-5**(대표가 확인하고 승인) |
| ③ 중간 화면 없음 | **R-2b** — 로딩 구간에 관문. 인증된 기기는 그대로 통과(화면 안 늘어남) |

🔴 **단, ①의 이미 잡힌 2줄은 R-6 을 해야 사라진다**(§10).
