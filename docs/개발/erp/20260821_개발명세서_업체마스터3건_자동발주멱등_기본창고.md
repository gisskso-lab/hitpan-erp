## 1. W1 — 업체주소 좌표

### 🔴 설계 전제가 틀렸다 — 그리고 코드 쓰기 전에 잡았다

설계 초안은 **"Daum 우편번호 서비스가 좌표를 함께 준다"** 는 B안을 채택했다. 키 0건이라는 이유였다.
공식 문서로 확인한 결과 **`oncomplete` data 에 좌표 필드가 아예 없다.** 전제가 성립하지 않았다.

> 이 확인을 안 했으면 "좌표를 받아서 저장" 하는 코드를 짜고, 좌표는 늘 NULL 이고,
> 지도는 여전히 안 찍히는데 코드는 정상으로 보이는 상태가 됐을 것이다. **가짜 봉합이 될 뻔했다.**

사장님 결재로 **카카오 REST 지오코딩** 채택.

### 원인 (실측)
`PartnerDetail.razor` 이 카카오 스킴의 좌표 자리에 **주소 문자열**을 넣고 있었다.
스킴은 `lat,lng` 를 요구 ⇒ 파싱 실패 ⇒ 좌표 없이 기본 위치로 열림.

### 구현
| 파일 | 내용 |
|---|---|
| `DB-105` | `partners.latitude/longitude` DECIMAL(10,7), `geocoding_settings` |
| `IGeocodingService.cs` | 계약. 실패해도 예외 안 던짐 (§#20) |
| `KakaoGeocodingService.cs` | 카카오 로컬 API. 키 미설정 시 `NotConfigured=true` |
| `PartnerService.cs` | 저장 시 좌표 확보. **화면이 좌표를 보냈으면 존중**(반자동 원칙) |
| `PartnerDetail.razor` | 좌표 있으면 좌표 링크, 없으면 주소검색 링크 |

### 설계 판단
- **키는 DB(`geocoding_settings`)에 테넌트별 암호화** — `appsettings.json` 금지(§#21) + 고객사 키(§#18·#22)
- **키 미설정 = 거짓 좌표를 만들지 않는다.** `0,0` 같은 값을 넣으면 지도가 엉뚱한 곳을 가리킨다
- **좌표 실패해도 업체 저장은 된다** (§#20)

### ⚠️ 미확인 (실측 필요)
- 카카오 REST 키 **미발급** — 사장님 발급 전까지 좌표 경로는 **미검증**
- 폴백(`kakaomap://search?q=`)은 안드로이드 문서상 좌표가 선택 파라미터이나 **iOS 문서는 필수라고 기술** — 문서 상충. 실기 확인 필요

### 🔴 이 구현의 핵심 안전장치 (§#23)

`MockFaxProvider` 는 `Success=false` 를 돌려준다. 이력은 `status='mock'`.
다이얼로그는 **열자마자** 경고를 띄운다 — 누른 뒤가 아니라 누르기 전이다.

> 팩스가 실제로 나가려면 외부 유료 계약이 필요하다. Mock 이 "성공"을 돌려주면
> 화면은 초록불이 되고 거래처는 못 받는다. **가장 위험한 거짓봉합**이라 원천 차단했다.
>
> ⚠️ 후임자: `MockFaxProvider` 가 `Success=true` 를 돌려주게 바꾸는 것은
> 기능 개선이 아니라 **안전장치 제거**다.

## 4. W4 — 자동발주·자동매입확정 멱등 (P0)

### 원인
`SalesService.GetAutoOrderCandidatesAsync` 가 **실시간 재고만** 봤다.
발주해도 입고 전까지 재고는 그대로 ⇒ 다음 거래명세서 확정 때 **같은 품목이 또 후보**.
`purchase_orders.is_auto=1` 을 **쓰기만 하고 읽지 않았다.**

BOM 경로(`BomService.OrderAlertAsync`)는 `stock_alerts.status` 로 **이미 정상**이었다 — 판매 경로만 비어 있었다.

### 구현
`NOT EXISTS` 로 미결 자동발주가 있는 품목을 후보에서 제외.

### DESCRIBE 실측이 설계 2건을 교정했다 (§#13)
```
status enum('draft','ordered','partial','received','cancelled')
is_deleted tinyint(1) NOT NULL DEFAULT 0
```
- 🔴 **`partial` 누락** — 초안은 `('draft','ordered')` 였다. 부분입고는 **잔량이 미결**이라 반드시 포함.
  빠뜨렸으면 부분입고에서 **중복 발주가 그대로 재발**했다
- `is_deleted` 실재 확인 → 조건 확정
- `cancelled`·`is_deleted=1` 은 **제외 안 함** — 재발주 가능해야 한다 (§#20)

## 5. W5 — 기본창고 코드리뷰

### 사장님 지적이 맞았다. 원인은 예상과 달랐다.

`ItemDetail.razor:121` 에 그대로 적혀 있었다:
```csharp
private string? _selectedWarehouseId; // 참조용 — DB에 저장하지 않음
```

- 드롭다운이 **아무것도 저장하지 않았다**
- `items` 실측 40컬럼 — **창고 컬럼 자체가 없었다** (저장 버그가 아니라 저장할 자리가 없음)
- 발주·매입은 **테넌트 폴백만** 사용, 품목별 기본창고는 **조회조차 안 함**

⇒ 설정해도 **아무 변화 없음**. 화면이 사용자에게 거짓말 중이었다.

### 부가 발견
활성 창고 0건이면 `"등록된 창고가 없습니다."` 로 매입확정 중단.
사장님이 보신 게 이 오류였다면 원인은 **창고 미등록**이다 — 실측에서 분리 확인 필요.

### 🔴 유령창고 재발 방지 (10차 P0-4)

FK 를 걸지 않은 이유: 창고가 비활성화돼도 품목 저장이 막히면 안 된다.
무효한 값은 사전에서 빠지고 **테넌트 폴백이 받는다.**

## 9. 🔴 검증팀 지적 — 사장님 판단 필요

### 수동발주 후 자동발주가 또 나갈 수 있다

멱등 필터는 `is_auto=1`(자동발주)만 제외한다. **담당자가 수동으로 발주한 건은 통과**한다.
⇒ 수동 발주 직후 판매 확정이 나면 같은 품목에 자동발주가 **한 번 더** 나갈 수 있다.

**이번에 안 고친 이유**: 사장님 오더는 *"자동발주 클릭한 항목"* 의 중복이었다.
수동발주까지 막는 것은 **오더 범위를 넘고**, 판단이 갈린다:
- 막으면 — 수동발주 후 자동발주가 안 나가 재고가 부족할 수 있다
- 안 막으면 — 중복 발주가 날 수 있다

**설계팀 의견**: 수동발주는 담당자가 의도를 갖고 넣은 것이므로 자동발주도 참고해야 한다고 보나,
현장 판단이 필요하다. **사장님·ERP매니저 결재 사항으로 올린다.**
