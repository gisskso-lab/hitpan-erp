## 7. 검증팀에 요청 (자기 판단 아님)

- **가장 위험한 곳 ①** — `MigrateDeliveriesAndReceiptsAsync` 의 `existingDeliveryMap`/`existingReceiptMap` PK 재사용(C-2). 방향이 바뀌었으니 **봉합 전 DB 위에 재이관하면 옛 행이 남는다**(§5). 빈 DB 실측만으로는 이 경로가 안 보인다 — 덮어쓰기 없이 병합 재이관하는 시나리오를 반증해 달라. 같은 코드로 **두 번** 돌리면 행수가 그대로인지(멱등)도.
- **가장 위험한 곳 ②** — `PartnerLedgerKind` 수단 매핑이 종전(`2→card, 3→note`)과 다르다(전결1 Q2: 2=계좌 적요, 3=충전). 값 자체는 결재됐지만 **화면의 수금수단 필터**가 `note` 를 기대하는 자리가 있는지 grep 을 부탁.
- **가장 위험한 곳 ③** — `LEGACY_UNKNOWN_ITEM` 폴백(품명·규격 둘 다 빈 DOCFB 라인). 몇 행이 여기로 갔는지 로그 카운트로 확인 — 많으면 재고현황에 "알 수 없는 품목" 한 줄이 크게 뜬다.
- **회귀 우려** — `MigrationJobResult.Payments` 추가로 완료 요약 JSON 이 한 필드 늘었다. 구 화면 캐시(이전 버전 WASM)가 이 응답을 받아도 깨지지 않는지. `RunTableStepAsync` 구조 변경(try 범위)이 취소 경로(`OperationCanceledException`)를 바꾸지 않았는지.
- **대사표 자체의 반증** — 대사표가 초록이면 좋은 게 아니다. **일부러 한 항목을 틀리게 만들고**(예: `hitpan_e2e` 에서 stock_ledger 한 행 삭제 후 `--skip-migrate --reconcile`) DIFF 로 바뀌는지 봐 달라. 초록불이 어디서 오는지가 이 작업의 핵심이다.
- **사원 +1·판매 공급가 +33,059** — [4] 에서 규명됨: 사원 +1 = `LEGACY_FALLBACK` 자리표시 · +353건/+33,059.20 = DOCFB 헤더그룹 중 DOCFE 에 없는 353그룹(MDB 직독 정확 일치 — 폴백 거래처 몫 356건/1,351,241.20 이 **아니다**) = 레거시 내부 불일치.
