# 자동 업데이트 배포 절차 (NCP, 사장님 실행용) — publish-update.sh

> 2026-07-20 / 대표 결재·CTO 부분수정후승인 완료 / 헌법 #29(NCP=사장님 손)·#22(개인키 NCP 격리)
> 이 문서 = 사장님이 NCP 에서 **무엇을 실행하는지·무엇을 만지는지** 아는 용도.
> PM 은 스크립트를 만들 뿐 실행하지 않는다. 실행은 사장님 sudo 1회.

---

## 0. 한 줄 요약

새 버전 배포 = **NCP 에서 명령 하나**. 그러면 manifest 가 자동으로 최신을 가리키고, 전 고객 워치독이 다음 점검 때 스스로 올라간다.
```bash
sudo bash publish-update.sh --zip hitpan-1.2.34.zip --manifest manifest-1.2.34-unsigned.json
```

---

## 1. 이 스크립트가 만지는 것 (딱 이것뿐 — 헌법 #29 투명성)

| 대상 | 무엇을 | 되돌리기 |
|---|---|---|
| `{webroot}/packages/hitpan-{ver}.zip` | 새 zip **생성**(복사) | 실패해도 무해(옛 manifest 가 이 zip 을 안 가리킴) |
| `{webroot}/manifest.json` | 새 버전으로 **원자 교체**(tmp→mv) | 자기검증 실패 시 **자동 롤백** |
| `{webroot}/manifest.json.bak-{옛버전}-{released}` | 옛 manifest **백업 생성** | 롤백 재료 (최근 10개 유지) |
| `/var/hitpan/update-keys/publish.lock` | 동시실행 방지 락 | 스크립트 끝나면 해제 |

- **건드리지 않는 것**: 개인키(읽기만), DB, 고객 데이터, DNS·방화벽·서비스. cloudflared 무관.
- **개인키는 NCP 밖으로 안 나간다**(#22). 서명은 이 스크립트가 NCP 안에서 openssl 로 수행.

---

## 2. 사전 준비 (최초 1회)

### 2-1. 공개키 파일 (자기검증용) — 없으면 개인키에서 뽑기
자기검증이 "방금 서명한 게 진짜 유효한가"를 공개키로 확인한다. 공개키는 노출돼도 무해(위조 불가).
```bash
# 이미 있으면 생략. 없으면:
sudo openssl ec -in /var/hitpan/update-keys/update_private.pem \
  -pubout -out /var/hitpan/update-keys/update_public.pem
```
> ⚠️ 이 공개키는 EXE 내장 공개키(upd-v1)와 **같은 키쌍**이어야 한다. 워치독이 그 공개키로 검증하므로, 서명은 반드시 그 짝 개인키로 해야 한다. (2026-07-20 생성한 그 키.)

### 2-2. 필수 도구
`jq openssl curl sha256sum` 이 NCP 에 있어야 한다(없으면 스크립트가 멈추고 알려준다).
```bash
which jq openssl curl sha256sum   # 없으면: sudo apt install jq
```

## 3. 배포 재료 (PM 이 만들어 전달 — 사장님은 NCP 로 올리기만)

PM 이 빌드 PC 에서 `build-manifest.ps1` 로 만든 2개 파일을 NCP 로 올린다(scp 등):
- `hitpan-{ver}.zip` — api/web/watchdog publish 묶음
- `manifest-{ver}-unsigned.json` — 서명 없는 manifest 본문 (버전·sha256·크기·downloadUrl 이 이미 채워져 있음)

두 파일을 NCP 의 한 폴더에 두고 그 폴더에서 아래를 실행.

---

## 4. 실행 (매 배포)

```bash
cd {재료를 올려둔 폴더}
sudo bash /path/to/installer/updates/publish-update.sh \
  --zip      hitpan-1.2.34.zip \
  --manifest manifest-1.2.34-unsigned.json
```

### 스크립트가 순서대로 하는 일 (화면에 다 찍힌다)
1. **입력 검증** — zip 실측 sha256 == manifest 값, zip 파일명 == downloadUrl. 다르면 즉시 중단.
2. **다운그레이드 게이트** — 현 서빙보다 **높은 버전만** 허용. 낮거나 같으면 중단(옛 버전 되돌림 사고 차단).
3. **zip 배치** — packages/ 로 복사.
4. **서명** — openssl 로 서명해 manifest 에 signature·kid 자동 삽입(손붙여넣기 없음).
5. **원자 교체** — manifest.json 교체 + 옛것 백업.
6. **자기검증** — `curl` 로 서빙되는 manifest 를 다시 받아 버전·서명(공개키 검증)·zip 접근성 확인. 하나라도 실패 → **자동 롤백**(옛 manifest 유지).

### 끝 화면
```
[publish] ✅ 배포 완료 — updates.hitpan.kr 이 이제 1.2.34 를 가리킵니다.
```
이게 뜨면 끝. 전 고객 워치독이 다음 점검 주기에 감지한다.

---

## 5. 특수 상황

- **같은 버전 재배포(서명 갱신 등)**: `--allow-republish` 추가. (기본은 동일 버전 거부 — 실수 방지.)
- **자기검증 실패 시**: 스크립트가 스스로 옛 manifest 로 롤백하고 붉은 메시지를 낸다. **전 고객은 정지 아님**(옛 버전 유지). 원인(캐시·서명·zip 경로) 확인 후 재실행.
- **캐시 주의(N-1)**: manifest.json 서빙에 `Cache-Control: no-cache` 가 걸려 있어야 워치독·자기검증이 최신을 본다. nginx 설정에서 manifest.json 만 no-cache, packages/*.zip 은 캐시 OK. (최초 1회 nginx 확인.)

## 6. 실측 순서 (이 스크립트로 하는 것)

```
① manifest 를 지금 1.2.30 → 1.2.33 으로 정정 (아래 6-1)
② 1.2.33 EXE 로 Sandbox 신규 설치 → 정상 확인          ← 실측 1: 설치마법사
③ publish-update.sh 로 1.2.34 업로드 → manifest 자동 1.2.34
④ 1.2.33 PC 가 워치독으로 1.2.34 로 스스로 올라감 관측   ← 실측 2: 자동 업데이트
```

### 6-1. 먼저 manifest 를 1.2.33 으로 정정
지금 manifest 가 1.2.30(옛것)을 가리켜 실측이 성립 안 한다. 1.2.33 용 unsigned manifest 를 PM 이 만들어 드리면:
```bash
sudo bash publish-update.sh --zip hitpan-1.2.33.zip --manifest manifest-1.2.33-unsigned.json
```
> 1.2.30 → 1.2.33 은 상향이라 다운그레이드 게이트 통과. 이후 1.2.33 설치 PC 가 1.2.34 로 올라가는 걸 관측하면 자동업데이트 실증 완료.
> (1.2.33 zip 이 packages 에 이미 있으면 sha256 대조 후 재복사 생략됨.)
