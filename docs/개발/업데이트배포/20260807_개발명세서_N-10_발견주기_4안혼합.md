## 2. 게이트 판정 — 전후 대조

**종전** (`Worker.cs` 구 :325-327)
```csharp
var today = DateOnly.FromDateTime(DateTime.Now);
if (_lastUpdateCheckDate == today)
    return;                      // ← 로그 0줄
```

**지금** (`Worker.cs:416-444`)
```csharp
var nowUtc = DateTime.UtcNow;
var checkInterval = _options.ResolvedUpdateCheckInterval;
if (_lastUpdateCheckUtc is { } lastChecked && nowUtc - lastChecked < checkInterval)
{
    …(건너뜀 로그 — §4)…
    return;
}
```

**성질 변화**

| | 종전 | 지금 |
|---|---|---|
| 판정 축 | 로컬 날짜 | UTC 시각 차 |
| 최대 지연 | 24시간 (자정 넘겨야 열림) | **N분 (기본 60)** |
| 자정 의존 | 있음 — 23:59 에 평가하면 1분 뒤 열림, 00:01 에 평가하면 24시간 | **없음** — 어느 시각이든 균일하게 N분 |
| 재시작 시 | 게이트 통째 소실(우연히 열림) | 디스크 기록으로 유지 — **단 N분 지났으면 열림** |
| 건너뛸 때 흔적 | **0줄** | 주기당 Information 1줄 + 매 루프 Debug |

> 🔴 **UTC 로 판정한 이유**: `DateTime.Now`(로컬) 로 차를 재면 서머타임·시간대 변경 구간에서 1시간이 통째로 뛰거나 되감긴다.
> 저장도 UTC(`"O"` round-trip)라 파일을 옮겨도 해석이 흔들리지 않는다.
> `TrackUpdateStallAsync` 에 넘기는 `today` 만 **로컬 날짜 그대로 유지**했다 — 그 함수는 이번에 손대지 않는다(결재-5·§5).

## 3. N 값 상·하한과 근거

`WatchdogOptions.cs:44-45`

| | 값 | 근거 |
|---|---|---|
| **기본** | **60분** | 결재-1. 사장님 3단계(코드수정→업데이트→실측)가 최대 1시간 / 평균 30분에 성립. 1,000사 기준 24,000 req/일 ≈ 0.28 req/s |
| **상한** | **60분** | 🔴 **야간 창.** `IsNightWindow` 는 새벽 3시대 **1시간뿐**(`UpdateOrchestrator` — `Hour >= 3 && Hour < 4`). N > 60분이면 3시대를 **통째로 건너뛸 수 있다**(결재-3). 상한을 60분에 두면 3시대에 반드시 1회 이상 평가가 걸린다 |
| **하한** | **5분** | 고객사가 15초로 낮추면 본사 오리진 자해(설계서 §6-1). manifest 는 **no-cache** 라 Cloudflare 가 흡수하지 않는다 — 폴링 1건 = 오리진 1건(설계서 §1-4). 5분이어도 1,000사 288,000 req/일로 이미 상당하다. `MetaPingIntervalMinutes`(5분)와 같은 자릿수로 맞춰 "워치독이 본사를 두드리는 최소 간격"을 통일 |

**강제 방식** — `ResolvedUpdateCheckInterval` 프로퍼티가 `Math.Clamp` 로 잘라내며, **설정을 읽는 모든 경로가 이 프로퍼티만 쓴다.**
`UpdateCheckIntervalMinutes` 원시값을 직접 읽는 코드는 clamp 경고 로그 한 곳뿐이다(값 대조용).
0·음수 같은 무의미한 값도 하한 5분으로 수렴하므로 **"설정 실수 = 폴링 폭주"가 성립하지 않는다.**

**우회 불가 확인** — `appsettings.json` 을 `"UpdateCheckIntervalMinutes": 1440` 으로 고쳐도 실제 주기는 60분이고,
기동 시 `LogWarning` 으로 *"허용 범위(5~60분)를 벗어나 60분으로 조정됐습니다"* 가 남는다(`Worker.cs:155-164`).

> ⚠️ **개발과 고객이 같은 N 을 쓴다**(설계서 §10-2·A-10). 환경 분기는 넣지 않았다 —
> 분기하는 순간 "개발 PC 에선 됐는데"가 구조가 되고, 이번 N-10 이 정확히 그 형태의 사고였다.

## 4. 상태파일 — 경로·형식·손상 대비

`src/HitPan.Watchdog/AutoUpdate/UpdateCheckStampFile.cs`

| 항목 | 내용 |
|---|---|
| **경로** | `{app}\update-check.stamp` — `AppContext.BaseDirectory` 에서 `..` 로 올라감. `UpdateLockFile.ResolvePath` 와 **동일 로직**. 상위 폴더가 없으면 실행 폴더로 폴백 |
| **왜 여기** | `%LOCALAPPDATA%` 는 워치독이 SYSTEM 이라 `C:\Windows\System32\config\systemprofile\...` 로 숨어 CS 도 고객도 못 찾는다. `{app}` 루트는 `db.conf` 가 있는 곳이라 사람이 열어보고, 백신 예외·ACL 이 이미 잡혀 있다(헌법 #31) |
| **왜 DB 아님** | 결재-2. ① 업데이트 발견은 DB 생존과 무관해야 한다(DB 가 죽었을 때야말로 업데이트가 필요할 수 있다) ② 코드리뷰서 P1-3(DB 비밀번호 명령줄 노출)의 노출면을 늘리지 않는다 |
| **형식** | UTC ISO-8601 round-trip 문자열 1줄 (`DateTime.ToString("O")`). 예: `2026-08-07T10:31:44.1234567Z` |
| **부수 이득** | CS 가 파일 하나 열어 "마지막으로 언제 확인했나"를 즉시 안다. 종전엔 프로세스 메모리 안에만 있어 볼 방법이 없었다 |

### 4-1. 손상 대비 — 전부 **fail-open** (설계서 A-2·A-3, 작2 §4-2)

| 상황 | 동작 | 로그 |
|---|---|---|
| 파일 없음 (첫 기동·사용자 삭제) | `null` = 확인한 적 없음 → **즉시 확인** | 없음 (정상 상태) |
| 내용 파싱 실패 (깨진 문자열·빈 파일) | `null` → **즉시 확인** | `LogWarning` |
| **미래 시각** (시계 변경·NTP 보정) | `null` → **즉시 확인** | `LogWarning` |
| 읽기 예외 (권한·잠금·I/O) | `null` → **즉시 확인** | `LogWarning` (예외 포함) |
| **쓰기 실패** | 🔴 **업데이트를 막지 않는다.** 예외를 삼키고 진행 | `LogWarning` (예외 포함) |

**미래 시각을 반드시 처리한 이유**: 걸러내지 않으면 그 미래 시각이 실제로 지날 때까지 업데이트가 **영영 막힌다.**
시계 변경은 공격이 아니라 사고로 깨진다 — `UpdateLockFile` 이 같은 함정을 겪고 같은 처방을 이미 쓰고 있다.

**쓰기 실패가 업데이트를 막지 않는 이유**: 이 기록은 **보조 장치**이지 업데이트의 전제조건이 아니다.
막으면 디스크·권한 사고 하나가 고객을 옛 버전에 영구히 고정시킨다.
쓰기가 실패해도 인메모리 `_lastUpdateCheckUtc` 는 갱신되므로 **정상 PC 의 게이트는 그대로 동작**하고,
잃는 것은 재시작 폭주 상한뿐이다(크래시 루프 PC 에만 영향).

> ⚠️ **방향을 혼동하지 말 것**: 이 파일 판정은 **fail-open**(모르면 확인한다).
> manifest **서명 검증**은 정반대 **fail-closed**(`UpdateClient`). 두 방향이 반대인 것은 의도다.

### 4-2. 영속화의 목적 — 오해 방지

작2 §4-2 가 못 박은 대로 **"게이트 유지"가 아니라 "재시작 폭주 상한"** 이다.

- 워치독은 `sc failure`(5초) · Guardian(5분)이 되살린다. 크래시 루프 PC 는 기동마다 manifest 를 1회씩 두드린다.
- 인메모리만으로는 그 반복에 **상한이 없다.** `eaba641`(NCP 디스크 100%)이 가르친 것은 *"1회당 비용이 작아도 회전이 없으면 반드시 죽는다"* 였다.
- 🔴 **반대로 N분이 지났으면 재시작 여부와 무관하게 확인한다.** 이 파일이 확인을 막는 근거가 되면 3안(영속화) 단독이 되어 개발 사이클이 24시간에 고정된다 — 그래서 반려된 안이다.

## 5. 건너뜀 로그 — 빈도 판단 근거

`Worker.cs:420-442`

### 5-1. 무엇이 문제였나

`:326` 의 조용한 `return` 때문에 **워치독 이벤트 500건을 뒤져도 무슨 일인지 알 수 없었다**
(문제 구간 15분 0건, `[Update|manifest|W4-|1.2.5` 0건 — 작1 §2-3). 원인 규명이 반나절 지연됐다.

### 5-2. 두 후보와 각각의 함정

| 후보 | 함정 |
|---|---|
| 매 루프 Information | 60초 루프 × 하루 = **1,440줄.** 정작 봐야 할 복구·터널 로그를 밀어낸다. `eaba641` 당시 동반 증상이 access.log 폭증이었다 — 로그량은 실재하는 비용이다 |
| 전부 Debug | 고객 PC 기본 로그레벨이 **Information**(`appsettings.json`)이라 **또 아무것도 안 남는다.** 이번 사고와 같은 상태로 되돌아간다 |

### 5-3. 채택 — 두 층

| 층 | 수준 | 빈도 | 내용 |
|---|---|---|---|
| 주기당 1회 | **Information** | N분에 1줄 (기본 60분) | 마지막 확인 시각 · **다음 확인 예정 시각** · 주기 |
| 나머지 매 루프 | **Debug** | 60초 | 다음 확인까지 남은 분 |

**판정 기준 — "다음에 같은 일이 나면 로그로 알 수 있는가"**: 통과한다.
기본 설정(Information)에서도 **시간당 1줄**이 남고, 그 한 줄에 *"마지막 확인 언제 / 다음 확인 언제 / 주기 몇 분"* 이 전부 들어 있다.
사장님 사례로 되짚으면, 19:30 이후 매시간 *"마지막 확인 19:30, 다음 확인 20:30"* 이 남았을 것이므로
채증 500건에서 **즉시** 게이트가 원인임이 드러났을 것이다.

**빈도 조절 상태(`_lastUpdateSkipNoticeUtc`)는 인메모리로 충분**하다 — 디스크에 둘 이유가 없다.
재시작하면 다음 건너뜀에서 한 줄이 더 나올 뿐이고, 그건 오히려 기동 사실이 남아 유익하다.

### 5-4. 게이트 **통과** 쪽에도 남긴다 (합격조건 G-2 "양쪽")

`Worker.cs:449` — 확인을 시작할 때 `LogInformation("[Update] 새 버전 확인 시작(current=…, 주기 …분)")`.

## 8. `installer/payload` 사본 판단 — **손대지 않았다**

**결론: `installer/payload/HitPan.Watchdog/appsettings.json` 에 `UpdateCheckIntervalMinutes` 를 추가하지 않았다.**

### 8-1. 판단 근거

**그 파일은 사람이 관리하는 설정 파일이 아니라 `dotnet publish` 산출물이다.**

`installer/README_v110_HYBRID.md:27`
```
dotnet publish src\HitPan.Watchdog -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o installer\payload\HitPan.Watchdog
```

즉 이 디렉터리는 **정본(`src/HitPan.Watchdog/appsettings.json`)의 빌드 출력 대상**이다.
정본을 고치고 publish 하면 **자동으로 갱신된다.** 지금 손으로 고쳐 넣어도 다음 publish 가 덮는다.
`git status` 에 같은 디렉터리의 `HitPan.Watchdog.exe`·`.pdb` 가 미추적 산출물로 잡혀 있는 것이 같은 사실의 방증이다(코드리뷰서 §288).

**게다가 이 파일의 내용은 설치 시점에 통째로 폐기된다.**
`installer/HitPan-Universal.iss:1163-1206` `FixupWatchdogAppSettings()` 가 `{app}\watchdog\appsettings.json` 을 **처음부터 새로 써서 저장한다.** payload 사본의 Watchdog 섹션은 신규 설치 PC 에 도달하지 못한다.

### 8-2. 그래서 실제로 필요한 것 — **범위 밖이라 하지 않았고, 별건으로 올린다**

`UpdateCheckIntervalMinutes` 를 **신규 설치 PC 의 설정 파일에서 사람이 볼 수 있게** 하려면 고쳐야 할 곳은 payload 사본이 아니라 **`FixupWatchdogAppSettings()` 의 JSON 문자열**(`.iss:1182-1200`)이다.

> ⚠️ **동작에는 지장이 없다.** `WatchdogOptions.cs:44` 에 기본값 60 이 있고 `IConfiguration.Bind` 는 없는 키를 건드리지 않는다 — `UpdateHistoryEndpoint` 가 payload 사본에 없어도 무해했던 것과 정확히 같은 구조다(코드리뷰서 P1-2).
> 다만 **고객 PC 설정 파일에 이 키가 안 보인다**(손댈 자리가 없다). `.iss` 는 이번 작업지시서의 대상 파일 목록에 없고 인스톨러 수정은 검증 표면이 다르므로, **PM 결재를 받아 별건으로 간다**(§11-2).

### 8-3. 기존 P1-2(정본과 갈라진 사본) 에 대하여

지시대로 **API 포트 5234 오기는 고치지 않았다** — 별건이다.
다만 위 §8-1 분석은 그 P1-2 자체에도 적용된다: **payload 사본을 손으로 고치는 것은 근본 해결이 아니다.**
다음 `dotnet publish` 가 정본으로 덮으므로, 이미 정본이 옳은 지금 그 사본의 갈라짐은 **publish 를 한 번 돌리면 사라진다.**
이 사실을 코드리뷰서 후속 처리에 참고로 남긴다.
