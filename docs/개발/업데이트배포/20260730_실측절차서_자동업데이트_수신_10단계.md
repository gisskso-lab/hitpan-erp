### 함정 2 — **기본 로그 레벨에서 "새 버전 없음"이 안 보인다**

| 로그 | 레벨 | 기본설정(Information)에서 |
|---|---|---|
| `[Update] 새 버전 발견: …` | Information | ✅ 보임 |
| `[Update] 최신 버전 유지 (…)` | **Debug** | ❌ **안 보임** |
| `[Update] 새 버전 없음 또는 적용 대상 아님(current=…)` | **Debug** | ❌ **안 보임** |
| `[Update] Normal 채널 새 버전(…) — 야간 대기` | **Debug** | ❌ **안 보임** |

근거: [`UpdateClient.cs:101`](../../../src/HitPan.Watchdog/AutoUpdate/UpdateClient.cs#L101) · [`Worker.cs:323`](../../../src/HitPan.Watchdog/Worker.cs#L323) · [`Worker.cs:341`](../../../src/HitPan.Watchdog/Worker.cs#L341)

> 🔴 **"아무 로그도 없다"가 두 가지를 뜻한다** — ① 조회를 안 했다(고장) ② 조회했는데 새 버전이
> 없었다(정상). 기본 레벨로는 **구분 불가**다. 없는 진범을 쫓게 된다.

#### 🔴 대응책 — appsettings 편집은 **듣지 않는다** (초판 오류 · B-1 적발)

초판은 *"`{app}\watchdog\appsettings.json` 의 `Logging.LogLevel.Default` 를 Debug 로 올려라"* 고 지시했다.
**두 겹으로 무효다:**

| # | 왜 무효인가 | 근거 |
|---|---|---|
| 1 | `Logging` 아래에 **`EventLog` 전용 `LogLevel.Default: "Information"`** 이 따로 있다. .NET 은 **provider 별 섹션이 상위 Default 를 override** 한다 → 상위만 Debug 로 올려도 **이벤트 로그 싱크는 Information 그대로** | [`src/HitPan.Watchdog/appsettings.json:7-11`](../../../src/HitPan.Watchdog/appsettings.json#L7-L11) |
| 2 | 인스톨러가 설치 시 이 파일을 **통째로 재작성**한다(문자열 하드코딩 SaveStringToFile). 설치 전에 고쳐두면 날아간다 | [`installer/HitPan-Universal.iss:1084-1085`](../../../installer/HitPan-Universal.iss#L1084-L1085) |

**✅ 실제로 듣는 방법 — 환경변수 (파일 덮어쓰기에도 살아남는다)**

`Host.CreateApplicationBuilder` 는 환경변수 구성 공급자를 기본 포함하고, **환경변수가 appsettings 파일보다
우선**한다([`Program.cs:13`](../../../src/HitPan.Watchdog/Program.cs#L13)).

```powershell
# 관리자 PowerShell — Machine 스코프여야 한다(서비스가 SYSTEM 계정으로 돌기 때문)
[Environment]::SetEnvironmentVariable('Logging__EventLog__LogLevel__Default','Debug','Machine')
[Environment]::SetEnvironmentVariable('Logging__LogLevel__Default','Debug','Machine')

# 서비스 재시작해야 새 환경변수를 읽는다
sc.exe stop HitPanWatchdog ; sc.exe start HitPanWatchdog
```

| 주의 | 내용 |
|---|---|
| 구분자 | **밑줄 2개(`__`)** — `:` 아니다. Windows 환경변수 규칙 |
| **`EventLog__` 키 필수** | 이것이 B-1 의 핵심. 상위 `Logging__LogLevel__Default` 만 넣으면 **이벤트 로그엔 여전히 안 나온다** |
| 스코프 | `Machine` — `User` 로 넣으면 SYSTEM 서비스가 못 읽는다 |
| 반영 시점 | **서비스 재시작 필요.** 실행 중 프로세스는 기존 값을 유지 |

**적용 확인**: 재시작 후 이벤트 로그에 Debug 급 로그(`[Update] 최신 버전 유지 …` 등)가 하나라도
보이면 성공. 안 보이면 스코프(`Machine`)와 `EventLog__` 키를 다시 본다.

### 함정 3 — **워치독은 팝업을 띄우지 않는다**

명세서 §4-5 는 "동의 팝업 — 워치독 로그 확인"이라 적었으나, **그런 로그는 존재하지 않는다.**

```
워치독:  manifest 감지 → local_update_status 에 적재 → 여기서 끝
           ↓ (DB 경유)
ERP Web: api/auth/update-status 폴링 → UpdateConsentGate.razor 가 팝업 표시
```

| 실제 확인 지점 | 로그 원문 (⭐교정본) | 근거 |
|---|---|---|
| 워치독 쪽 | `[Update] Major 채널 새 버전(1.2.41) — ERP 로그인 동의 대기(고리2 처리). 로컬 적재 완료. 워치독 자동 적용 안 함. 메타 ping 으로 본사 통지 예약.` | [`Worker.cs:362`](../../../src/HitPan.Watchdog/Worker.cs#L362) |
| 적재 확인 | `[Update/Status] 새버전 1.2.41(Major) 로컬 적재 완료 — ERP 로그인 팝업 노출 가능` | [`WatchdogStatusWriter.cs:73`](../../../src/HitPan.Watchdog/AutoUpdate/WatchdogStatusWriter.cs#L73) |
| **팝업 실물** | **ERP 화면에 로그인해야 보인다** — `새 버전 1.2.41 이(가) 나왔습니다. 업데이트하시겠습니까?` | [`UpdateConsentGate.razor:55`](../../../src/HitPan.Web/Components/Common/UpdateConsentGate.razor#L55) |

> 🔴 **팝업을 보려면 Sandbox 에서 ERP 에 로그인해야 한다.** 워치독만 켜두고 기다리면 영원히 안 뜬다.
>
> ⚠️ **초판은 위 첫 줄을 `…(고리2 처리)` 까지만 적었다**(B-6 적발). 실측자가 이벤트 뷰어 필터에
> 문자열을 그대로 붙여 쓰면 **부분 문자열이라 검색은 되지만**, "로그가 잘렸나" 하고 의심하게 된다.
> 위가 완전한 원문이다.

### 함정 5 — 🔴 **백업이 실패하면 7~10단계는 도달 자체가 불가능하다** (B-2 적발)

6단계 백업은 "확인 항목"이 아니라 **종단 차단 게이트**다. 실패하면 그 자리에서 실측이 끝난다.

| 사실 | 근거 |
|---|---|
| 백업 실패 → `return false` — 슬롯 판정·파일 교체·재시작 **전부 미실행** | [`UpdateOrchestrator.cs:146-153`](../../../src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs#L146-L153) |

#### ✅ Sandbox 에서는 백업이 성공한다 (검증팀 확정)

| 확인 | 근거 |
|---|---|
| 설치 EXE 가 MariaDB **11.4.4** MSI 번들 | `installer/download-bundle.ps1:87` |

> 그래도 **"백업 실패 = 실측 종료"** 라는 종단 차단 성질은 반드시 기억한다 —
> 6단계에서 차단 로그가 뜨면 실측 실패가 아니라 **거기서 정상 종료**다.
> 별도 이슈로 기록하고(§3 즉석 봉합 금지), 7~10단계는 **"미도달"로 판정**한다. 기다리지 않는다.

```powershell
where.exe mysqldump                                            # 폴백 경로 확인
Test-Path "{app}\db.conf"                                      # 자격증명 파일
```

> (`HitPan-Universal.iss:1440`), 워치독 3개 리더는 **11.4 경로만** 본다. 기존 10.11 고객 PC 에서
> 자동업데이트가 조용히 죽는다. **이번 Sandbox 실측 범위 밖**(11.4 가 깔리므로 안 터짐)이라
> 즉석 봉합하지 않고 별도 지시서로 이관했다 → [`20260730작2`](../../운영기록/20260730작2_워치독_MariaDB경로_비대칭_작업지시서.md)

### 함정 6 — **`--health` 의 워치독 버전은 안 올라간다 (정상)**

워치독 자기교체는 **미구현(W4-3)** 이다. 신버전 워치독은 `{app}\watchdog.new` 에만 놓였다가

> **`--health` 가 1.2.40 을 계속 보고해도 업데이트 성공이다.** 판정 기준은 **API 버전**(10-b·10-c)이다.

## §2. 실행 절차 (게시 확인 후 순서대로)

> 🔴 **1번이 2번보다 반드시 먼저.** (명세서 §1-4b — 설치가 먼저면 그날 감지 0)

### 0단계 — 게시 실행 (사장님) ⭐이게 선행조건

```bash
gh workflow run deploy-update.yml --ref main \
  -f version=1.2.41 -f channel=Major -f environment=production
```

| 입력란 | 값 | 왜 |
|---|---|---|
| `version` | **`1.2.41`** | 필수 입력, **기본값 없음.** 안 넣으면 게시가 안 된다 |
| `channel` | **`Major`** | Normal 이면 새벽 3시까지 대기 — 실측 불가 (함정 아님, 설계대로) |
| `environment` | `production` | beta 는 nginx 403 — 실동작 아님 |

실행 중 **폰 1탭** 승인 필요(`environment: production` required reviewer).
고객 PC **0대**라 실 고객 영향 없다.

#### ⏱️ 게시 소요 시간 — **승인만 바로 누르면 약 5분** (7/28 실측)

| 구간 | 실측 (run `30350523595`) |
|---|---|
| Build update package (재빌드·SSOT) | **3분 56초** |
| Sign & publish on NCP | **29초** |
| **실작업 합계** | **약 4분 25초** |

#### 🔴 마이그 게이트 — 초판 판정이 **반대였다** (B-3 적발)

초판은 *"1.2.41 에 DDL 있으면 여기서 정상 차단"* 이라 적었다. **틀렸다.**

게이트는 **"SQL 파일이 있는가"가 아니라 "로컬에 미적용된 신규 마이그가 있는가"** 로 판정한다.

| 판정 | 조건 | 결과 |
|---|---|---|
| 통과 | zip 의 `DB-*.sql` 이 전부 로컬 `schema_migrations`(success=1)에 있음 | ✅ 자동교체 진행 |
| 차단 | **로컬에 없는 신규** `DB-NN` 이 하나라도 있음 | 🛑 중단(수동 재설치 경로) |
| 차단 | `schema_migrations` **조회 자체가 실패**(null) | 🛑 안전측 중단 |

근거: [`UpdateOrchestrator.cs:474-510`](../../../src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs#L474-L510).
코드 주석이 이력을 명시한다 — 종전엔 `sqlFiles.Length>0` 만으로 차단해서 **모든 릴리스가 영구 차단**됐고,
**2026-07-22 에 봉합**된 자리다. 초판은 **그 봉합 이전 논리**를 적어놨다.

> 🔴 **1.2.41 실측의 기대값은 "통과"다.**
> 신규 설치 DB 는 clean DDL 이 마이그 55건을 전부 시딩하고, `Migrations/SQL` 도 같은 55건
> (DB-02~DB-84 완전 일치 — 검증팀 실측). **신규 0건 → 게이트 통과가 정상이다.**
>
> **⇒ 여기서 차단 로그가 뜨면 그건 "정상 차단"이 아니라 결함 신호다.**
> 특히 `schema_migrations 를 읽지 못해…` 로그면 **DB 접속 문제**이지 마이그 문제가 아니다.
> 초판대로 "정상 차단"이라 판정했으면 **진짜 결함을 덮을 뻔했다.**

| 차단 로그 | 실제 의미 |
|---|---|
| `[Update] 🛑 교차검증 차단 — 로컬 미적용 신규 마이그 N개({List}).…` | 1.2.41 에 **신규 DDL 이 실제로 들어갔다** — 릴리스 내용 확인 필요 |
| `[Update] 🛑 교차검증 — schema_migrations 를 읽지 못해 …안전측(중단)…` | **DB 접속·권한 문제**(MariaDB 경로 등). 마이그와 무관한 결함 |

## §4. 게시 전 지금 확정된 것 (§6-1 위험 해소)

7/29 명세서 §6-1 이 **"게시 실패 시 1순위 용의자"** 로 지목한 위험 — *게시 빌드가 payload 를 새로
만들면 그 산출물엔 `.bak` 이 있을 수 있다* — 를 실측했다.

| 확인 | 명령 | 결과 |
|---|---|---|
| main 에 백업접미사 파일 | `git ls-tree -r main --name-only \| grep -iE "\.(bak\|old\|orig\|save)$"` | **0건** |
| strip 대상 범위 | 워크플로 실독 | `installer/payload` **전체 재귀** |

### §4-2. 버전 범프 커밋은 필요 없다 (검증팀 B-4 → **철회** 확정)
