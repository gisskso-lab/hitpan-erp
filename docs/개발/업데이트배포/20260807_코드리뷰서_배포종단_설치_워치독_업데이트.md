### P1-1 🟠 거부 후 같은 버전이 같은 날 재안내되는 반복 고리

**파일**: `src/HitPan.Watchdog/Worker.cs` :304-308 (게이트 해제) ↔ :450-457 (거부 처리)
**교차**: `src/HitPan.Web/Components/Common/UpdateConsentGate.razor` (sessionStorage 버전 가드)

**무엇이 문제인가**

`ConsentDecision.Reject` 처리는 펜딩만 비우고 **거부 사실을 기억하지 않는다**. `_consentAppliedVersions` 에는 Approve 만 등록된다(:442). 그런데 :304-308 이 "펜딩 해소" 를 이유로 하루 게이트를 즉시 해제하므로, 다음 루프에서 feed 를 재조회해 **같은 Major 버전**을 다시 발견하고 `_pendingConsentUpdate` 에 다시 담는다(:373). `UpsertLatestAsync`(:379)도 다시 돈다.

**실패 시나리오**

1. 고객이 [나중에] 를 누른다 → `local_update_consents` 에 reject 기록, 본사에 `rejected` 1건 보고.
2. 워치독이 하루 게이트를 풀고 60초 뒤 같은 버전을 재발견 → 펜딩 재설정.
3. `ConsumeConsentForMajorAsync` 가 `ReadLatestAsync` 로 **최신 동의 = reject** 를 다시 읽는다 → 또 Reject 분기 → `ReportConsentRejected` **재호출** → 게이트 재해제 → 2번으로 복귀.

**실제 피해 범위 (완화 요인)**

- ERP 팝업은 재노출되지 않는다 — `sessionStorage` 가 그 버전을 이미 기록해 같은 탭에서는 다시 안 뜬다. **고객이 팝업 폭탄을 맞지는 않는다.**
- 본사 중복 보고는 `TelemetryController.cs` :122-136 의 60초 중복창이 흡수한다. 다만 워치독 루프가 60초(`LoopIntervalSeconds`)라 **경계에 걸려 일부는 통과**할 수 있다 — 그 경우 `tenant_update_history` 에 동일 `rejected` 행이 반복 적재된다.
- 순수 비용은 60초마다 feed 재조회 + 로컬 DB 조회 1회. 무한루프이되 **저비용 무한루프**다.

**왜 P0 이 아닌가**: 고객 화면·업데이트 동작·데이터 무결성에 영향이 없다. 다만 "펜딩 해소 → 게이트 해제" 가 거부 케이스에서 자기 자신을 재무장시키는 구조는 설계 의도(재배포 사이클 단축)의 부작용이며, 다음 세션에 정리할 대상이다.

**권고**: 거부한 버전을 `_consentAppliedVersions` 와 같은 성격의 집합에 기록하거나, 게이트 해제를 **Approve 종결 시에만** 하도록 좁힌다. (⛔ 본 리뷰에서는 수정하지 않았다.)

### P1-3 🟠 DB 비밀번호가 프로세스 명령줄에 노출된다

**파일**: `src/HitPan.Watchdog/AutoUpdate/WatchdogConsentReader.cs` :62, :125

```
var args = $"-h {host} -P {port} -u {user} \"-p{pass}\" -N -B ... ";
```

**실패 시나리오**

1. 워치독은 SYSTEM 권한으로 상시 구동한다. 동의 폴링은 Major 펜딩이 있는 동안 **60초마다** `mariadb.exe` 를 새 프로세스로 띄운다.
2. 그 순간 같은 PC 의 **표준 사용자 계정**이 `wmic process get CommandLine` / `Get-CimInstance Win32_Process` 로 명령줄을 조회하면 `-p{평문비밀번호}` 가 그대로 보인다. Windows 에서 프로세스 명령줄 조회는 관리자 권한을 요구하지 않는다.
3. 고객사 PC 는 여러 직원이 쓰는 사무실 PC 다. 경리 계정이 DB root 비밀번호를 획득하면 `stock_ledger`·`journal_lines` 원장에 직접 접근할 수 있다.

**완화 요인**: 로그 유출은 없다. `RunQueryAsync` 는 실패 시 stderr 만 예외 메시지에 담고(:184), args 는 담지 않는다. mariadb 클라이언트 stderr 는 "Using a password on the command line interface can be insecure" 경고를 낼 뿐 비밀번호를 되뱉지 않는다. 즉 **로그 평문 노출 0건**이고, 노출면은 "같은 PC 의 다른 로컬 계정" 하나다.

**동일 패턴 확산 여부**: `WatchdogBackupRunner`·`WatchdogStatusWriter` 도 같은 자격증명 해석기(`ResolveDbCredentials`)를 공유한다. 이 항목은 워치독 DB 접근 **전반의 공통 설계**이므로 단발 수정이 아니라 별도 작업지시서 대상이다.

**권고**: `MYSQL_PWD` 환경변수 또는 `--defaults-extra-file` 로 옮긴다. (⛔ 본 리뷰에서는 수정하지 않았다.)

### P2-1 🟡 핸드오프 스크립트의 인코딩 가정이 여전히 아슬아슬하다

**파일**: `src/HitPan.API/Startup/WatchdogHandoffBootstrap.cs` :256-262

주석이 스스로 실측을 기록하고 있다 — swap 5,572B 중 **1,805B 가 비ASCII**(한글 주석). BOM 을 넣어(`UTF8Encoding(true)`) 봉합했으므로 현재는 안전하다.

그러나 **자매 코드인 워치독 본체는 BOM 없이(`UTF8Encoding(false)`, `UpdateOrchestrator.cs` :1049) 쓰면서 "순수 ASCII 라 안전"을 근거로 삼는다.** 본체 스크립트(:1112-1246)는 실제로 순수 ASCII 이므로 지금은 참이다. 문제는 **두 파일이 상반된 전제로 같은 종류의 작업을 한다**는 점이다. 본체 스크립트에 한글 주석 한 줄만 추가되면 PS 5.1(CP949)에서 파싱이 깨지고, 그 결과는 워치독 자기교체 전면 불능이다.

**권고**: 본체도 BOM 방식으로 통일하거나, 최소한 "본체 스크립트에 비ASCII 금지" 를 검증 항목으로 고정한다.

### P2-2 🟡 핸드오프 시도 카운터가 성공 시 초기화되지 않는다

**파일**: `src/HitPan.API/Startup/WatchdogHandoffBootstrap.cs` :214-238

`scripts\.handoff-attempts` 는 예약을 걸 때마다 증가하지만(:237), **교체 성공 시 지우는 코드가 없다.** swap 스크립트(:431-458)의 성공 경로는 `watchdog.bak` 삭제와 Recover 작업 삭제만 한다.

**실제 영향은 제한적** — 교체가 성공하면 다음 기동에서 :198 `IsSameVersion` 가드에 걸려 카운터를 읽기 전에 반환하므로 누적이 판정을 막지 않는다. 그러나 다음 업데이트 라운드에서 새 `watchdog.new` 가 왔을 때 **카운터는 3 부터 시작**한다 → :228 `attempts >= 3` 에 즉시 걸려 **그 라운드의 교체가 통째로 스킵**된다.

**실패 시나리오**: 1.2.55 로 핸드오프 교체 성공(카운터 1~3 적립) → 1.2.56 배포 → API 기동 → 카운터 3 → "3회 시도했으나 완료되지 않았습니다" 경고와 함께 재료 삭제 → 워치독 구버전 잔류.

**단, 이 경로는 현실에서 거의 안 탄다** — 교체가 성공하면 워치독이 1.2.55 가 되고, :142 `HasSelfReplaceCapability` 가 true 라 핸드오프가 **아예 물러난다**(:147 return). 카운터를 읽는 지점에 도달하지 않는다. 즉 "핸드오프가 성공했는데 워치독 버전은 1.2.54 미만" 이라는 조합에서만 발현하며, 그 조합은 정상 흐름에서 생기지 않는다. **조건이 바뀌면 터지는 부류**로 §4 에 올린다.

### P2-3 🟡 `RunSchtasks` 의 stdout/stderr 를 성공 경로에서 회수하지 않는다

**파일**: `src/HitPan.Watchdog/AutoUpdate/UpdateOrchestrator.cs` :1295-1330

`ReadToEndAsync` 두 개를 시작해두고(:1308-1309), `ExitCode != 0` 일 때만 `IsCompletedSuccessfully` 로 조건부 조회한다(:1324-1325). 성공 경로에서는 두 Task 를 **await 하지도 관측하지도 않는다.**

- 파이프 버퍼가 차서 교착이 나지는 않는다 — `schtasks` 출력이 수백 바이트라 버퍼(4KB) 안이다.
- `IsCompletedSuccessfully` 가 false 면 실패 사유가 빈 문자열이 되어 헌법 #15 취지에 미달할 수 있다(30초 대기 후이므로 실제로는 거의 항상 완료 상태).

핸드오프 쪽(`WatchdogHandoffBootstrap.cs` :712)은 `Task.WaitAll([so, se], 5_000)` 로 명시 회수한다. **같은 목적의 두 헬퍼가 다르게 구현되어 있다.**

### 개선 제안 (결함 아님)

1. **`RestoreOneFromOld` 의 `.failed` 누적** — `UpdateOrchestrator.cs` :1350. 롤백이 연달아 실패하면 `api.failed`/`web.failed` 가 남는다. `CleanupAfterSuccess`(:964-965)가 다음 성공 시 치우므로 무한 누적은 아니지만, **성공이 영영 안 오는 PC** 에서는 남는다. 디스크 100% 사고(eaba641) 전례가 있어 기록해 둔다.

   - #23 (외부 노출에 AI/Claude/Cursor 금지) — 3파일 전수 확인, **0건**.

## 7. 개발팀 최종 판정

# 🟡 조건부 합격

### 합격 근거

1. **작업지시서 대조 결과 지시 항목 전건 구현.** 미구현·부분구현 0건이며, 범위 밖으로 명시된 2건(백오피스 조회 화면, `/watchdog/ping` 복구)은 문서에 사전 선언되어 있다.
2. **P0 0건.** 종단을 멈추거나 고객 PC 를 영구 고립시키는 결함을 찾지 못했다.
3. **과거 사고 재발 없음.** f5640fc 테넌트 격리 붕괴는 리포 값·CI 게이트 양쪽에서 차단되고, 게이트는 중립화 실패 시 **배포를 중단**한다.
4. **두 달 무한루프의 구조적 원인이 실제로 끊겼다.** `watchdog.new` 를 받아서 버리던 고리(구 `CleanupAfterSuccess`)가 자기교체 재료로 전환됐고(W4-3), 구버전 PC 는 API 핸드오프(W4-3-H)가 덮는다. **두 체계의 이중 교체 차단까지 구현되어 있다** — 이것이 없었다면 P0 였다.
5. **실패 경로 설계가 일관되게 보수적이다.** "모르면 통과" 가 없다. 검증 불가 = 차단, 안전망 등록 실패 = 교체 미개시, 롤백 실패 = 본사 긴급 통지.

### 조건 (해소 전 정식 합격 보류)

| 조건 | 내용 | 담당 |
|---|---|---|
| **C-1** | P1-2 payload 워치독 설정 정본 동기화 (`UpdateHistoryEndpoint` 추가 · 포트 5257 정정) | 백엔드 + 네트워크 |

### 불합격이 아닌 이유

사장님 지적 *"머 하나 제대로 수정된거 없이 버젼만 계속 올라가네"* 의 구조적 원인 — **워치독 코드 봉합이 고객에게 도달할 경로 자체가 없었던 것** — 이 이번 작업으로 실제로 닫혔다. 코드에서 확인했다:

- `UpdateOrchestrator.cs` :966-977 — 재료를 버리지 않고 자기교체에 쓴다
- `WatchdogHandoffBootstrap.cs` 전체 — 이미 깔린 구버전도 API 가 대신 바꾼다
- `WatchdogHandoffBootstrap.cs` :140-148 — 두 체계가 서로를 밟지 않는다

이 세 개가 동시에 있어야 성립하는 구조이고, 셋 다 있다.
