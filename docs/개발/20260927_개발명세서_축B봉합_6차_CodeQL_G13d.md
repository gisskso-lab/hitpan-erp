## 3. 어떻게 고쳤나

### 3-1 V-1 — 죽은 가지를 없앴다 (동작은 그대로)

**지운 것** (⬛ 로 같은 자리 주석에 보존):

```
if (conn is System.Data.Common.DbConnection dbConn) { await dbConn.OpenAsync(ct); }
else { conn.Open(); }
```

**남은 것** — `if (conn.State != Open) { await conn.OpenAsync(ct).ConfigureAwait(false); }`

**왜 죽은 가지인가** — `IUnitOfWork.GetDbConnection()` 의 **반환형이 이미 `DbConnection`** 이다
(`src/HitPan.Application/Interfaces/IUnitOfWork.cs` — `DbConnection GetDbConnection();`).
⇒ `conn is DbConnection` 은 **항상 참**이고, `else` 가지는 `conn == null` 일 때만 닿는데 그때는 바로 앞
`conn.State` 가 먼저 NRE 다. CodeQL 이 *"Variable `conn` is always null at this dereference"* 를 **error** 로 올렸다.

**동작이 안 바뀌었다는 근거 — 3가지**
1. **닫힌 연결을 여는 일은 그대로다.** `if (conn.State != Open)` 검사와 `OpenAsync` 호출이 둘 다 남아 있다.
   이 두 줄의 목적은 운영 주석이 과거 실제 사고로 기록한 *"EF/Dapper 가 커넥션을 암묵적으로 닫아둔 상태면
   `BeginTransaction` 이 **open and available Connection** 예외로 터진다"* 를 막는 것이고, 그 목적은 온전하다.
2. **없앤 가지는 도달 불가였다.** 위 정적형 근거 — 실행 시 한 번도 타지 않던 줄이다.
3. **트랜잭션 구조·`try` 범위·`catch` 두 곳·보상 호출 인자를 한 글자도 안 건드렸다**(#1) ⇒ ③경로 보상은 5차 그대로다.
   🟢 실측 뒷받침: `G-B13c`(회전 준비 예외 → 행 안 남음)·`G-B13d`(이어받은 세션 생존)가 **둘 다 PASS** 한다
   — 열기·`BeginTransaction` 경로를 실제로 태우는 게이트다.

**같은 모양이 남아 있는 다른 자리 — 범위 밖 (건드리지 않았다)**

| 자리 | 왜 안 고쳤나 |
|---|---|
| `src/HitPan.API/Controllers/AuthController.cs` `:372`·`:488`·`:683`·`:769` | DI 가 `System.Data.IDbConnection` 으로 꺼낸다 ⇒ `is DbConnection` 이 **실재 검사**다(죽은 가지 아님) |
| `src/HitPan.API/Controllers/HealthController.cs` `:44` | 같음 |
| `src/HitPan.API/Middleware/SessionValidityMiddleware.cs` 생존조회 안 | 같음 |
| `src/HitPan.API/Middleware/SessionLimitMiddleware.cs` `:109` | 같음 + 축 A 파일 무접촉 결재 |

| `src/HitPan.Application/Services/*.cs` 다수 (`_db is DbConnection …`) | 전부 `IDbConnection` 필드 ⇒ 실재 검사 |

🔴 **이번 차수가 만든 자리(= `AuthService` 하나)만 고쳤다.** CodeQL 이 error 로 올린 것도 그 한 자리다
(4차 `31b802b9` success → 5차 `ead2f63d` failure). 위 목록은 **고칠 대상이 아니라 확인한 목록**이다.

### 3-2 V-2 — `G-B13d` 신설 (결재 조건 ②)

**무엇을 재나** — `sid` **있는** 토큰(= 이어받은 세션, 그 행이 이미 존재)으로 갱신 → 회전 준비가 터진다
→ **그 행이 살아남는다.**

**왜 5차까지 무계측이었나** — 보상 인자는 `isNewSession && sessionRecorded ? sessionId : null` 인데
`sessionRecorded` 는 이어받은 경로에서 **`true` 로 고정**되고 `sessionId` 는 **일하고 있는 그 번호**다
⇒ **`isNewSession &&` 한 조각이 유일한 보호대**다. 그런데 `G-B13`·`B13b`·`B13c` 는 셋 다 `HideSessionTable` 로
**`sid` 없는** 토큰을 만들어 쓰므로 전부 `isNewSession == true` ⇒ 그 조각을 지워도 **FAIL 이 0건**이었다.

**어떻게 재게 만들었나 — 새 하네스 0개.** 기존 헬퍼 둘로 만들었다.
정상 로그인 1회(`sid` 실린 토큰) → `BeginTransactionFailingConnection` 주입 연결로 세운 서비스에 그 토큰으로 갱신
→ `GuardExpiredPcSessionRevivalAsync` 는 살아 있는 세션이라 그냥 반환 → `isNewSession == false` 라 INSERT·축B판정 없음
→ 회전 준비 `BeginTransaction` throw → 보상 호출(인자 `null`) → **행 생존**.
🔴 트리거도 경주도 필요 없다 — ③경로는 `deleted == 0` 을 **요구하지 않는다.**

**양성 조건 3개** (없으면 빈 통과가 된다)
- ⓐ 토큰에 `sid` 가 실렸다(`Assert.NotNull(workingSid)`) = 이어받은 경로다. 없으면 `G-B13c` 와 같은 것을 재게 된다
- ⓑ 회전 준비가 **실제로 터졌다** — `Assert.Contains("게이트 주입 G-B13d")` + `Assert.Equal(1, faulty.BeginAttempts)`
- ⓒ 갱신이 **새 행을 만들지 않았다** — `Assert.Equal(1, SessionCount(db))`
  ⚠️ ⓒ 를 **본체 뒤에** 두었다. 보호대를 빼면 행 수도 같이 틀리는데 행 수가 먼저 터지면 실패 메시지가
  *"행을 만들었나"* 로 읽혀 원인을 가린다.
