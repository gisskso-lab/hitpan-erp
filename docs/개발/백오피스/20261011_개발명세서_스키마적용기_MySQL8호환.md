### §2-1 🔴 설계 도중 바뀐 것 두 가지 (게이트가 잡았다)

**① 토큰 벗기기를 「모양 열거」에서 「위치 기반」으로 바꿨다.**
처음 구현은 `ADD COLUMN IF NOT EXISTS` 처럼 **모양을 열거**하는 정규식이었다.
G-M8-5c(실물 14파일)가 바로 FAIL 했다 — `31` 번에 **실행되는** 문장이 하나 더 있었다:

```
ADD CONSTRAINT fk_landing_signups_tenant
    FOREIGN KEY IF NOT EXISTS (tenant_id) …
```

이름(`fk_…`)이 `CONSTRAINT` 와 `FOREIGN KEY` 사이에 끼어 열거형 정규식이 못 잡는다.
⇒ **MySQL 8 의 `ALTER` 에는 이 토큰이 설 자리가 아예 없다**는 사실을 근거로, 인용·주석 밖이면 전부 벗기는 방식으로 바꿨다.
🔴 이 한 건을 못 잡았으면 **봉합하고도 운영에서 31번에서 또 멈췄다.** PM 의 1차 전수조사(`^\s*(ALTER|ADD|…)` grep)는 **줄 머리가 `FOREIGN KEY` 인 이어진 줄**을 못 셌다.

**② 관용 오류코드에 1826 을 더했다.**
`31` 번 FK 는 `IF NOT EXISTS` 가 없다. 파일이 중간에 실패하면 이력에 안 남아 다음 기동이 처음부터 다시 돌리는데,
그때 FK 이름 중복(1826)에서 또 멈춰 **영영 안 열린다.** G-M8-3(이력 비우고 2회차) 설계가 이 덫을 드러냈다.

## §7-1 🔴 V-1 (P1) — 여러 절 `ALTER` + 1060 관용 = 「적용됨」 기록하고 칸을 안 만든다

**PM 이 직접 재확인했다**: `32_backoffice_s2_owner.sql` 은 **세미콜론 1개 · `ADD COLUMN` 4절 한 문장**이고,
`42_backoffice_cs_stages.sql` 첫 문장은 **6절**이다(G-M8-5d 가 코드로 센다). `44` 는 같은 일을 3문장으로 쪼개 놨다 — **그게 올바른 모양**이다.

| | 내용 |
|---|---|
| 사고 경로 | 4절 중 **한 칸만 이미 있어도** 문장 **전체 롤백** + 1060 → 우리가 관용 → `_schema_migrations` **기록** → 해시 멱등이 **영영 skip** ⇒ 칸 3개(42면 5개)가 없는데 적용기는 **성공을 보고** |
| 왜 현실적인가 | `00_backoffice_core.sql:101` 이 스스로 「`domain_alias` … **운영 수동 ALTER만**」 전례를 적어 둔다 |
| 운영 지금은? | 🟢 **안 터진다** — 운영에 그 4칸이 **0개**임을 10/11 실측했다(1차 적용은 전절 성공) |

## §7-2 🔴 V-3 — 「보정은 MariaDB 에서도 정답」은 **틀렸다** (내 주장이 틀렸다)

검증자 MariaDB 11.4.10 실측: **같은 이름 FK 재추가는 `1005`(errno 121)** — **1826 이 아니다.**
⇒ 판 판정이 MariaDB 를 오인하면 `31` 번 `ADD CONSTRAINT` 에서 **기동 영구 거부**. 내가 MySQL 쪽에서 막은 덫이 반대 판에 열려 있었다.

**봉합 ⓑ 채택**: **판독 실패(빈 문자열) → 종전(MariaDB) 경로.** 그게 「아무것도 안 바뀐 상태」이고 새 덫을 만들지 않는 쪽이다.
(MySQL 인데 판독이 실패하면 종전처럼 1064 로 멈춘다 — 오늘과 같을 뿐 더 나빠지지 않는다.) 1005 를 관용 목록에 넣는 ⓐ 는 **안 했다** — 1005 는 「표를 만들 수 없다」는 넓은 코드라 진짜 사고를 덮는다.

## §7-3 🔴 V-2 — 1060 은 **형을 안 본다**. 게이트도 안 봤다

`varchar(10)` 있는 자리에 `VARCHAR(100)` 을 요청해도 1060 으로 넘어가고 **짧은 칸이 그대로 남는다**(검증자 실측).
G-M8-2 는 `table.column` 만 봤다 — **존재만** 본 것이다. ⇒ **`column_type` 15칸 검산 추가**(MySQL 8 은 `int` 표시폭을 떼므로 `int` 로 적었다).
