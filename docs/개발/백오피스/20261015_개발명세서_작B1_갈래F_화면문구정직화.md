## 7. 검증팀에 요청 (자기 판단 아님)

**특히 봐줬으면 하는 곳**
1. 🔴 **§5-1** — F-1·2·3 이 「실물 `.razor` 를 읽어」 재는 방식으로 충분한가. 글자 세기의 변형이라는 지적이 가능하다. 승격(공용 `.cs` 분리)을 지금 할지 판정을 요청한다.
2. 🔴 **§5-5** — G-B1-F-3 의 과녁을 「메일 관련 기본 문장」으로 좁힌 것이 맞나. 「성공 화면 전체에 '발송' 단정 없음」으로 넓히면 `:30`(정식 계약서 미래 약속)과 `:21`(폼 안내)이 함께 걸린다. **갈래로 쪼갠 조건을 내가 임의로 넓히지 않았다**는 점을 확인해 주기 바란다.
3. **`BuildEmailHtml` 을 `public static` 으로 올린 것** — `[ApiController]` 클래스의 public 멤버다. MVC 는 **static 메서드를 액션으로 보지 않으므로** 라우트에 노출되지 않는다는 전제로 올렸고 `[NonAction]` 도 함께 붙였다. 이 전제를 독립 반증해 주기 바란다(라우트 목록 실측).
4. **빈 문장 판정 기준** — 화면은 `IsNullOrWhiteSpace` 로 공백만 있는 문장도 「아무 말 안 함」으로 본다. 갈래 E 가 공백을 의미 있게 쓸 일은 없다고 봤는데, 맞는지 확인 요청.

**회귀 우려**
- `BuildEmailHtml` 시그니처가 바뀌었다. 같은 이름의 다른 호출부가 없음을 확인했으나(이 컨트롤러 안 1곳), **합류 후 D·E 가 같은 함수를 건드렸다면 충돌**한다 — 합류 직후 전수 확인 요청.
- `ResellerApplyPage.razor` 성공 화면에 `<p>` 가 1개 늘었다(신청 이메일 줄). `.ra-done p` 스타일만 적용되므로 레이아웃 위험은 낮다고 보지만 **화면 실행 확인은 안 했다**(§4-8).
- `.github/workflows/build-and-test.yml` 은 **갈래 D·E 도 건드린 파일**이다. 내 삽입은 앵커 기준이고 줄번호 의존이 없으나, 합류 시 손 끼우기가 필요할 수 있다(§4-5).
