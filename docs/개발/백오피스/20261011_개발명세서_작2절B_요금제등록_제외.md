### 1-1. 🔴 PM 실측 전제 1건이 틀렸다 — B-3 은 「신설」이 아니라 「개명·보강」이다

PM 이 전달한 전제: *「화면에 「제외/비활성」 버튼 0개(API 에는 `toggle-active` 가 있는데 사람이 쓸 길이 없다)」*

**실측 결과 — 버튼은 `main`(`16669004`)에 이미 있었다.** 요금제 카드 안에 양방향 토글 버튼과
상태 칩이 둘 다 있었고, `ToggleAsync` 가 `toggle-active` 를 실제로 호출하고 있었다.

```
main 원본 (AdminPricing.razor)
  상태 칩   : @(plan.IsActive == 1 ? "활성" : "비활성")
  토글 버튼 : @(plan.IsActive == 1 ? "비활성화" : "활성화")  → ToggleAsync(plan)
```

PM 이 「0개」로 읽은 이유는 **낱말이 「제외」가 아니라 「비활성화」였기 때문**으로 보인다.
즉 **없던 것은 기능이 아니라 사장님이 쓰신 말**이었다.

그래서 B-3 은 다음으로 범위를 좁혀 구현했다. **입구 신설 0건 · 호출 경로 변경 0건.**

| 바꾼 것 | 전 → 후 | 왜 |
|---|---|---|
| 상태 칩 글자 | 활성 / 비활성 → **판매중 / 제외됨** | 「활성」은 개발 용어다. 고객 노출 용어 금지 원칙 |
| 상태 칩 모양 | 색만 → 아이콘 + Filled + Warning 색 | 제외 상태가 눈에 띄게 (상태가 한눈에) |
| 버튼 글자 | 비활성화 / 활성화 → **제외 / 포함** | 사장님 오더 낱말 그대로 |
| 설명 한 줄 | 없음 → **추가** | 「삭제되지 않는다 · 다시 포함할 수 있다」를 화면이 직접 말한다 |

🔴 **`ToggleAsync` 본문·`toggle-active` 호출·서버 코드는 한 글자도 안 건드렸다.**
🔴 **PM 판단 요청**: 「제외」가 `is_active` 축이 맞는지. 지금 제외는 `is_active=0` 이고
`is_visible`(랜딩 노출)은 **안 건드린다**. 과금 축을 둘로 갈라서는 안 되므로 기존 축을 그대로 썼다.

### 4-3. 🔴 FAIL 대조 — 봉합을 빼면 빨간불인가

세 번 다 **봉합을 실제로 망가뜨려 보고** 재측정했다. 매번 빌드 0/0 을 다시 확인하고 돌렸다.

| # | 망가뜨린 것 | 어느 게이트가 물어야 하나 | 실측 |
|---|---|---|---|
| S1 | 중복 선조회를 무력화(`&& false`) + `INSERT … ON DUPLICATE KEY UPDATE` 로 바꿈 | G-W2-5 | **Failed 1 / Passed 2** → G-W2-5 단독 실행도 **Failed 1 / Passed 0** ✅빨간불 |
| S2 | 이력 `action` 을 `'create'` → `'update'` 로 바꿈 | G-W2-4 | **Failed 1 / Passed 0** ✅빨간불 |
| S3 | `ToggleActive` 의 `UPDATE` 를 `DELETE FROM pricing_plans` 로 바꿈 | G-W2-6 | **Failed 1 / Passed 0** ✅빨간불 |

S1 이 가장 중요한 대조다. **이 트랙에서 새로 생기는 위험은 「중복 등록이 운영 요금제 가격을 조용히 덮는 것」**
이고, 가장 그럴듯한 사고 모양이 `ON DUPLICATE KEY UPDATE` 다(한 줄로 「등록도 수정도 되는」 편한 코드).
그 한 줄을 넣는 순간 G-W2-5 가 빨간불이 된다.

복구는 `git checkout -- <그 파일 하나>` 로 했고, 매번 `git status --porcelain` 이 비는 것까지 확인했다
(작업은 사전에 커밋해 뒀다 — 커밋 안 한 봉합이 함께 지워지는 사고 방지).

### 4-4. 게이트가 실제로 무는 것

| 게이트 | 문다 |

### 4-5. 설계 판단과 근거

| 판단 | 왜 그렇게 했나 |
|---|---|
| 맨 `INSERT` + 선조회 409 + 1062 catch 409 | `ON DUPLICATE KEY UPDATE`/`REPLACE INTO` 면 같은 코드로 한 번 더 누르는 순간 운영 가격이 조용히 덮인다. 「기존 행은 한 글자도 안 바꾼다」가 지시였고, 그걸 **구조로** 보장한다. 선조회만으론 동시 2번 누름(PK 경주)에 1062→500 이 되므로 1062 도 같은 409 로 수렴시켰다 |
| `is_active` 를 `CreatePlanRequest` 에서 **안 받는다** | 포함/제외 축이 두 입구로 갈라지면 과금 축이 둘이 된다. 새 행은 출하 DDL 기본값(1=포함)으로 선다 — INSERT 컬럼 목록에서 뺐다(#36) |
| `max_devices` 를 화면에 **안 낸다** | 집행에 안 쓰이는 표시용 레거시 칸이다(실측: `LandingPublic`·`PromotionsAdmin` 이 **조회만** 하고 COALESCE 집행 0건). 처음 앉은 사람에게 물을 칸이 아니다. 화면이 안 보내므로 DTO 기본값 3(=DDL DEFAULT)이 들어간다 — **0 이 조용히 들어가지 않는다**(G-W2-4 가 문다) |
| 기기 두 칸은 NULL 그대로 INSERT | 0 이면 `DeviceRegistration` 의 `COALESCE(…,5)`/`(…,3)` 폴백이 죽어 **그 요금제의 기기 등록이 전부 막힌다**(작16 결재 D-2). `COALESCE` 로 감싸지 않은 이유 = 생성에는 「기존 값」이 없다 |
| `CreatePlanRequest` 를 `UpdatePlanRequest` **상속 안 함** | 등록에만 필요한 DDL 일치 기본값 2개(`MaxUsers`=3·`MaxDevices`=3)를 둬야 하고, 상속 프로퍼티의 기본값은 바꿀 수 없다. 칸 구성은 동일하게 유지 |
| 201 Created 반환 | 생성 의미에 맞다. 화면은 `IsSuccessStatusCode` 로 받으므로 영향 없고, 409 와 함께 상태코드로만 판정 가능해져 게이트가 글자를 안 읽는다 |
| 폼을 목록 **위**에 둠 | 0행이면 목록은 아무것도 안 그린다. 그 상태에서 첫 등록이 되어야 한다는 것이 지시의 핵심이었다. 0행 전용 빈 화면(「등록된 요금제가 없습니다」 + 첫 등록 버튼)도 함께 뒀다 |
| 사유(`reason`)를 서버 필수로 **안 함** | 「`PUT` 과 같게」가 지시였고 `PUT` 은 서버 필수가 아니다(화면에서만 강제). `CreateAsync` 도 같은 방식으로 화면에서 강제한다 |

## 7. 검증팀에 요청 (자기 판단 아님)

**특히 봐줬으면 하는 곳**

1. 🔴 **§1-1 — PM 전제 1건이 틀렸다.** 「제외 버튼 0개」가 아니라 「낱말이 달랐다」다.
   그래서 B-3 을 글자 교체로 좁혔다. 이 좁힘이 사장님 오더(「제외 버튼을 **추가로** 넣을것」)를
   만족하는지 **판정해 주셔야 한다.** 만족 못 하면 별도 버튼을 더하는 쪽으로 다시 가야 한다.
2. 🔴 **제외의 축이 `is_active` 가 맞는가.** 사장님 이유에 「베타 테스트시 필요」가 있다.
   베타에서 「요금제를 랜딩에서만 감추고 과금은 유지」가 필요하면 `is_visible` 축이 맞다.
   지금 구현은 `is_active` 한 축만 움직인다.
3. **201 Created 가 다른 소비자를 깨뜨리지 않는가.** 실측했다 —
   `grep -rn 'pricing/plans' --include=*.cs --include=*.razor src/ | grep -i post` 결과
   POST 호출부는 `AdminPricing.razor:302`(내가 더한 등록) 과 `:389`(기존 toggle-active) **둘뿐**이다.
   레포 밖 소비자(랜딩·설치기)가 있는지는 내가 못 쟀다.
4. **`max_devices` 를 화면에 안 낸 판단.** 집행에 안 쓰인다는 근거는 `grep` 실측 7곳이다
   (조회 3곳 · PUT 대입 1곳 · 시험 2곳 · 주석 1곳). 집행 경로를 내가 놓쳤는지 봐 달라.
5. **게이트가 `hitpan_trgtest` 의 표를 전부 비운다.** 다른 트랙이 그 DB 를 쓰고 있었다면
   내 측정이 그 트랙 데이터를 지웠을 수 있다(하네스가 override DB 의 모든 표를 DROP 한다 —
   선례 그대로의 동작이다). 실측 당시 그 DB 는 백오피스 게이트 잔재 40개 표였다.

**회귀 우려**

- `AdminPricing.razor` 의 상태 칩·버튼 글자가 바뀌었다. 이 글자를 보는 **E2E/Playwright 시나리오가
  있으면 깨진다**(「활성」·「비활성화」로 찾는 선택자). `scripts/playwright-audit/**` 와
  `tests/scenarios/**` 교차 확인 부탁한다 — 나는 안 쟀다.
- `BackofficePromotionPricingDbGateTests` 4/4 는 직접 재서 통과 확인했다.
- 전체 회귀(1500+건)는 **안 돌렸다**. 변경이 신설 입구 + 화면 글자라 범위를 좁혀 쟀다.
