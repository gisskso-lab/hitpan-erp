### 4-4 G-PRICE-1 (DB)

| 실험 | 제거한 것 | 결과 |
|---|---|---|
| **했다** | `PricingAdminController.PlanRow` 두 칸을 `int?` → `int` 로 되돌림 | **G-PRICE-1 만 FAIL** → 원복 뒤 PASS |

🔴 **이 실험에서 설계보다 나쁜 사실을 하나 쟀다.** 설계 §4-2 ② 는 「NULL 을 `int` 로 받으면 다시 500」이라 적었다.
실측은 **500 이 아니었다** — Dapper 가 NULL 을 **조용히 `0` 으로** 매핑했다
(`Assert.Null() Failure: Value of type 'Nullable<int>' has a value / Actual: 0`).
⇒ `int` 로 두면 화면에 **0 이 표시되고**, 그 0 이 그대로 저장되어 **그 요금제의 기기 등록이 전부 막힌다**.
500 보다 **덜 시끄럽고 더 위험한** 경로다. `int?` 전환은 이 조용한 0 을 막는다.

무는 것(봉합 뒤 실측): 요금제 목록 **200** · 두 칸 **NULL 매핑** · `price_display` 기본값 **`number`**(D-4) ·

두 칸을 **안 보낸** 저장 뒤에도 기존 **9 가 보존**(UPDATE `COALESCE` 가 실제로 돈다).

### 4-5 G-MIG-1 (DB)

| 실험 | 제거한 것 | 결과 |

🔴 **못 한 이유를 적는다**: `00` 이 이미 `promotions_legacy`·`promotion_usages`·세 칸을 만들기 때문에

⇒ `43`·`44` 의 멱등은 **「2회 적재 2회 성공」 양성 측정으로만** 확인했다(음성 대조군 없음). [4] 가 이 구멍을 보셔야 한다.

무는 것(봉합 뒤 실측): `31`·`43`·`44` 2회차 적재 **3/3 성공** ·
2회 뒤에도 `pricing_plans` 의 세 칸 존재 · `promotions_legacy`+`promotion_usages` **2/2 존재** ·
